# @fluxvita/saveslot-kernel

## 0.2.0-rc.0

### Minor Changes

- 12c23c6: A closed item's details leave out a value a pending deletion removed: a conflict's `effective`, an awaiting item's `current` and a flagged item's `matched_values`. Each carries `partially_deleted`, a new optional field of `ConflictDetail.effective`, `AwaitingDetail.current` and `FlaggedDetail`; MCP and the CLI say so where it is set. Privacy deletion is not offered in this version, so no item has it yet.
- d5d9c8f: A conflict item's `previous` leaves out a value a pending deletion removed, and carries `partially_deleted`, a new optional field of `ConflictDetail.previous`; MCP and the CLI say so where it is set. Privacy deletion is not offered in this version, so no item has it yet.
- d5d9c8f: A query reads only the page it returns, instead of every matching row: the first page on event tables and on state tables read at a point, the first page of a state table read over an interval with no order asked for, and later pages where they can be. Large tables page much faster; the rows, their order, `total` and the pages are the same. A later page's position now carries `total`, so an earlier build does not read a position made by this one.
- d5d9c8f: A read by record time (`history`'s `as_of` and `changes`, a query's later pages) leaves out a value a pending deletion removed and marks it `partially_deleted`; a `changes` entry gains `partially_deleted` as a new optional field. Privacy deletion is not offered in this version, so no read has it yet.
- 3ae6e08: Server mode can write a record for each call. With `SAVESLOT_CALL_RECORDS=on` (off by default), the server writes one line of JSON on the standard output at the end of each call that passed authentication: one per `/v1` request and one per MCP tool call. The record says who made the call (tenant, actor, how the credential came to be), what the call was (surface, operation, route), how it ended (outcome, the contract's reason, an incident), and what it did to the tenant's log (appended, replayed or none, with the operation number and restore count). It holds no content: no names, no task, no keys, no values. Every `/v1` answer to an authenticated call on a route gives the call's ID in the `Saveslot-Call` header, readable cross-origin, whether records are on or not. Records never hold a call up: past a bound, or when the output fails, they are dropped, and the drops are counted in a `call_record_failed` warning at most once a minute.
- 51f75c4: In server mode, a tenant's PostgreSQL storage no longer has an owner. Opening it no longer raises an ownership epoch, a write no longer checks one, and no opener makes another give the tenant up (`ownership_lost`). Writes are still serialized by the tenant's lock. A format newer than this version knows (another version upgraded it) refuses the call with `unavailable` (`stopping`, `retry_after` 1) and logs `tenant_format_too_new`; the process goes on serving its other tenants. The OAuth endpoints answer it `503 temporarily_unavailable` with `Retry-After`, not `500`. `@fluxvita/saveslot-store-postgres` no longer exports the `ownership_lost` error code or `PostgresTenantStore.epoch`. Local mode is unchanged.
- d5d9c8f: The `sources` reads give `total`: for a list, every source the filters take; for a search, every match, when every source the filters take fits in one call's scan (past that, no `total` is given and the next position says more may follow).
- d5d9c8f: A store whose storage format is older is upgraded in place when it is opened, step by step, and a store of a newer format than this version knows is refused (`format_too_new`; one too old to upgrade, `format_too_old`). No upgrade step exists yet. While an upgrade runs, the local service's `/health` says `starting` with the step, `saveslot mcp` answers each call `unavailable` naming it, and a failed upgrade is `upgrade_failed` with its step, after which `saveslot start` exits with code 5.
- d5d9c8f: `TimelineResultCode` gains `removed`, for a `history` timeline item whose content a deletion removed (before, such an item came out with an empty result). MCP and the CLI write it as "(removed by a deletion)". Privacy deletion is not offered in this version, so no item has it yet.

### Patch Changes

- d5d9c8f: A write recomputes a derived table only for the groups its rows were or are in, when the rule reads one event or timeless table on its own as a grouped or whole aggregate; other rules are recomputed whole as before. The derived rows are the same. A rule that fails on the data fails the write as `validation_failed` (`rule_eval_failed`) wherever it is evaluated.
- d5d9c8f: On a field group, two writes of the same value to one field where the version seen had no value are no longer judged a conflict: a field the write did not set counts as empty there, as it does without the group.
- d5d9c8f: On a table with more than one field that defines "has a value", a write that continues a stretch with a value across a stretch without one, and changes only one of those fields, is no longer held for confirmation: a boundary is erased only when all of them are the same on both sides. The fields listed as erased are all of them.
- d5d9c8f: On a large store, writes and reads no longer spend time finding the latest restore or import by walking the whole log (0.6 s at a million events before); what they find is the same.
- d5d9c8f: Changing an optional field on a stretch of a state table where the entity has no value no longer counts as a new version, and so no longer moves that entity ahead in the order of the most recently written within one request. `ver` and receipts do not change.
- d5d9c8f: Local mode is faster on large stores: the store gathers the database planner's statistics itself when they are stale (none of the user's content goes into them), a write's receipt no longer scans all stored content, and opening a store after a crash makes about half the file syncs it did.
- 90ab30a: A paging cursor expires once a deletion is confirmed or cancelled in the tenant after its first page: the next page is refused with `handle_expired`, reason `deletion_changed` (new), and the caller reads again from the first page. What a read leaves out changed between the pages, so one round of paging could have given a stretch twice or missed one. A deletion carried out without a confirmation or cancellation in between does not expire a cursor. Privacy deletion is not offered in this version, so no cursor expires this way yet.
- fc9a36e: A write sent again with its idempotency key gives back the first receipt's parts in the same order, byte for byte. Before, the receipt's `resolved` (and `premise_affected.by_reason`) of a replay could list the same fields in another order.
- a7d57b0: In server mode a read is recorded before it is answered: its read records are written into the tenant's database in a transaction of their own, which takes no tenant lock, instead of waiting in the process for the tenant's next write or close. A read is no longer lost when the process exits or its connection goes away, and a write without `ver` falls back to it even when it comes after the tenant was opened again. When the records cannot be written, the read is answered `unavailable` (`busy`, `retry_after` 1) and its content is not given. The version last read and `since: "my_last_read"` now follow the latest position read, not the latest record written. Local mode keeps its read buffer; there too, `my_last_read` and the version last read are the read of the greatest position, buffered and written together, so they no longer depend on whether the buffer was written out in between.
- 9bf87e1: A tenant whose database connection went away (the database restarted, a middlebox or an operator ended it) is opened again on its next use, and so is a tenant whose directory now names another database: before, every request to that tenant failed with `internal` until the tenant was closed for being idle. Uses still on the old connection finish first. When opening it again cannot reach the database, the request is answered `unavailable` (`busy`, `retry_after` 1) and the next use tries once more. Each reopen is logged as the warning `tenant_reopened` with the tenant and the reason (`connection` or `database`).
- d5d9c8f: `read_first`'s `task_mismatch` names the latest read made under another task, and the least task by code point when two are at the same position. Before, it named whichever such read the query met first.
- d2a3d6b: An `undo` of a confirmation now records every field and existence the confirmed write wrote, as spec 09 §5.7 says, not only those the confirmation put into effect then. Before, when a write was partly awaiting and partly a candidate (or already in effect), undoing its confirmation left the other fields out of the record, so a later deletion that put one of them into effect through that confirmation would not have had it taken back by the undo. What an undo writes back now is unchanged; records already in the log are not rewritten.

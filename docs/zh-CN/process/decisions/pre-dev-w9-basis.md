## 0. 总览

| # | 问题 | 决定（一句话） |
|---|---|---|
| 1 | 声明的形状 | op 上可选的 `premises`：一组（表、行或实体、可选的字段、读到时的 `ver`、状态类表可选的业务时间）。只收显式声明；不自动取"读过的全部"。第一版只能指向同一 slot 的基础表，可以指向本请求里新建的行，不能指向派生行 |
| 2 | 与已有概念的区别 | 证据指向原文，`ref` 是值里的结构引用，派生依赖由规则决定并自动重算，读取记录记"谁读过"；前提记"这一行的值是看了哪些值之后写的" |
| 3 | 什么算前提变了 | 所声明的（字段 × 业务时间）上，现在的值与写入方所见版本上的值不同；前提所在的行被撤销一律算。**不看意图**：事件类表的 `update` 也算，这一点与纠错影响查询不同。值恢复则标记撤掉，`undo` 走的就是这条 |
| 4 | 标记 | 读结果新增 `premise_changed`（前提已变），任何读取方可见。三种消法：改写这一行并带新前提；只带 `premises` 重申（值不变）；带 `premises: []` 清掉这一行的前提声明 |
| 5 | 不传递 | 第一版不传递。B 的值没变，以 B 为前提的 C 不标；B 被改写后 C 按普通规则被标 |
| 6 | 记在哪 | 声明记在 `write.head` 的元数据块里（只有标识与版本）；标记的每次变化记在新事件 `premise.changed` 里，由写入与删除管线在产生改动的事务里生成，`apply` 照做。前提不参与任何取值判定，伪代码不用改 |
| 7 | 代价与上限 | 一个 op 最多 16 条；一行最多被 1,000 条有效声明指向，只在声明时检查，超出时拒绝的是**声明方**；前提变化的代价计入写入准入的估算，隐私删除不受它影响 |
| 8 | 契约与接入面 | `write` 加参数、回执加 `premise_affected`；指向不存在或不可见的行拒绝，`ver` 过期照常写入并立即打标记；MCP 只改 `saveslot_write`，不加工具；HTTP 不加端点 |
| 9 | 评测 | 新增 eval 10，五个变体：会不会声明、读到标记会不会处理、会不会滥报、前提被撤回、前提被隐私删除 |

## 1. 问题

**例子**（下文一直用它）。slot `project` 里有两张无时间表：

- `constraints`（约束）：`name`、`date`。其中一行 `r_C`：name "发布日期"，date 2026-12-01。
- `tasks`（任务）：`title`、`due`、`status`。

Agent A 读到 `r_C`，据此写了三条任务："11 月 25 日前完成回归测试""11 月 27 日冻结代码""11 月 30 日前准备发布说明"。后来用户把发布日期改成 11 月 20 日。

**现有机制做得到的**：

- saveslot 知道 A 读过 `r_C` 的旧版本（读取记录，`02-integrity-and-records.md`「读取记录：read_log」）。
- 在一部分情形下，A 下次读到相关数据时会看到 `possibly_affected`（同文「纠错影响查询 · 什么会触发」）。**只是一部分**：事件类表与无时间表上，只有 `correct` 与 `revoke` 触发；用户"改了主意"是 `update`，不触发。状态类表上任何让值变化的写入都触发。所以本例里 `constraints` 是无时间表、改动是 `update`，A 连 `possibly_affected` 也收不到。

**做不到的**：

- 三条任务行本身不带"我是以发布日期为前提写出来的"。另一个 Agent B 读任务列表，看到的是三条完全正常的任务。
- `possibly_affected` 只给**读过旧值的那个连接实例**（`04-contract.md` 第 7 节："本连接实例之前读过的版本后来受影响"）。它回答"你当时读到的对不对"，不回答"库里现在哪些行还站在旧值上"。

预算以收入为前提、训练计划以目标为前提，是同一类问题。

**它不是派生表**。派生值由规则算出，输入变了在同一事务里重算（K5）。这里的行是 Agent 写的，里面有它的理解，saveslot 不能替它重写。saveslot 能做的只有两件：记下这层关系，在前提变了之后把它指出来。

## 2. 已定的结论

本稿在下面三条之上展开，不再论证：

- **进第一版**：写入可以声明它以哪些已读到的值为前提；前提变了，saveslot 给依赖它的行打标记，任何读取方都看得到。是否真的失效由 Agent 判断，saveslot 只指出前提变了。
- 它符合"Agent 理解，saveslot 把关"的分工（[`../../spec/01-positioning.md`](../../spec/01-positioning.md)「写入：Agent 理解、saveslot 把关」；[`../../spec/03-data-model/04-write-and-read.md`](../../spec/03-data-model/04-write-and-read.md)「分工」）：依赖关系由 Agent 声明，saveslot 做确定性的记录与标记。
- 尽量接在已有的纠错影响查询上，不另起一套。

**名字**。本稿新引入的名字集中列在这里，理由写在各节：

| 中文 | 英文标识 | 是什么 |
|---|---|---|
| 前提 | `premises`（op 参数）；`premise`（标记、回执里指一条前提的键） | 一次写入声明的、它所依赖的已读到的值 |
| 声明 | —（`ops/<i>/premises/<j>` 块里的一条） | 一条前提：目标、字段、所见版本、范围 |
| 前提目标 | — | 一条声明指向的那一行或实体 |
| 依赖行 | — | 声明了前提的那一行 |
| 重申 | —（不带 `set` 的 `update`，带非空的 `premises`） | 值不变，只更新前提 |
| 清除 | —（带 `premises: []` 的 `update`） | 去掉这一行的前提声明 |
| 前提已变 | `premise_changed`（标记） | 读结果里的标记 |
| 前提变化事件 | `premise.changed`（事件类型） | 记标记的每一次打上、撤掉与改指 |
| 受影响的依赖行 | `premise_affected`（回执字段） | 改动方的回执里列出哪些行以被改的值为前提 |

- **为什么叫"前提"（`premise`）**：Agent 写这一行时，把那个值当作前提——前提变了，这一行要重新看。别的词都已占用：`evidence` 是证据，`sources` 是源数据，`ref` 是引用字段，`deps` 是事件格式里"由别的贡献求得的内容"的依赖（事件格式 3.5），`derived` 是派生；`basis` 已有两处用法（事件格式里 `ver.basis` 的 `explicit` / `fallback` / `same_request`，`deletion_preview` 逐行结果里的 `basis` 是"每个必填字段还剩哪些写入的贡献"），再用一次，同一个块里会出现两种意思。中文"依据"在规格里多处指证据、来源或判定理由（§16 第 1 条），也不用。"前提"在规格里没有用过。
- **为什么标记叫 `premise_changed` 而不叫"失效"一类的词**：saveslot 只知道前提变了，不知道这一行还成不成立；名字陈述事实，不下结论。`stale` 另有所指（大写入作业期间待刷新的派生值，`04-contract.md` 第 7 节），不复用。
- 英文标识的风格与契约、事件格式一致：参数、标记、原因码用小写 snake_case；事件类型用"名词.过去分词"（与 `item.created`、`deletion.confirmed` 同形）。参数是复数 `premises`（一个数组），单条用单数 `premise`。

## 3. 决定 1 声明的形状

### 3.1 可选做法

| 做法 | 怎么做 | 优点 | 问题 |
|---|---|---|---|
| 甲 显式声明 | 写入的每个 op 可选带一组前提，调用方自己列 | 精确到行与字段；关系进日志，可重放、可导出；与分工一致 | Agent 忘了声明就没有标记（少报） |
| 乙 自动推断 | 把"本连接实例此前读过的全部"当作前提（取自读取记录，可按 `task` 收窄） | Agent 什么都不用做 | 见下 |
| 丙 两者结合 | 显式的算"确定"，自动的算"可能" | 少报更少 | 两套标记、两套消法；乙的问题一样不少 |

乙的问题：

1. **多报到没有信号**。一次会话里 Agent 通常先看目录、翻几张表、读几十行，才写一行。把这些都算前提，任何一处变动都会让一大片不相干的行带标记。标记只有在"多数时候说的是真的"时才有人看。
2. **读取记录不在日志里**。read_log 是本地运行状态（`02-architecture.md` §8 的 (c) 类），有保留期（默认 180 天）、有丢失窗口（一个落盘间隔）、不随导出走。依赖关系若只存在于它，导出重放或恢复之后就没了。要让它进日志，就得把每次写入之前的读集抄进写入事件——读远多于写，事件体积随读取量涨。
3. **粒度不够**。受限 SQL 的读取在读得多时只留表级记录；逐行读也说不出用到的是哪个字段。
4. **会话边界看不见**。saveslot 看不到 Agent 的上下文（`02-integrity-and-records.md`「来源的完整性」："信息一旦被 Agent 读走，就可能出现在它之后写的任何东西里"）：隔了一个会话再写、子 Agent 之间转手、没带 `task`，都接不上。

### 3.2 决定：甲，只收显式声明

- **理由**：哪些读到的值真的被用上了，是理解，只有 Agent 知道；这正是分工里归 Agent 的那一半。显式声明的结果是确定的记录，进日志，重放得出同样的标记。
- **少报怎么办**：靠工具描述与评测（eval 10a，§11）。不声明的写入与今天的行为完全相同，没有变差。
- **不选丙的理由**：自动推断可以**以后纯增量地加**——它只需要读取记录与写入的任务标识，这两样第一版已经按完整形状在记；加的时候是一种更弱的标记，落在 (c) 类状态里，不改事件格式。`02-integrity-and-records.md` 末尾的"污点追踪（可选，不作为首版必选项）"就是这条路，本稿不动它。现在加，标记的可信度先被拖垮。
- **不选"没带 `premises` 就拒绝"**：多数写入确实没有前提（用户直接说的一句话）。

### 3.3 一条前提里有什么

`ops[i].premises` 是数组，每条：

```ts
interface PremiseRef {
  table: TableName;                        // 同一 slot 的基础表
  row?: RowId | string;                    // 事件类表、无时间表；也可以写本请求里新建行的临时名 "@p1"
  entity?: EntityId;                       // 状态类表
  entity_key?: Record<FieldName, Value>;   // 状态类表，按自然键
  fields?: FieldName[];                    // 用到的是哪些字段。不给 = 整行（任何字段，以及这一行是否存在）
  ver?: Ver;                               // 读到它时拿到的版本。没带时兜底
  valid_at?: BizTime;                      // 只对状态类表：用到的是业务时间上这一点的值
  valid_during?: [BizTime, BizTime | null];// 只对状态类表：用到的是这段业务时间上的值。与 valid_at 互斥
}
```

| 要素 | 规则 | 理由 |
|---|---|---|
| 目标 | 一行或一个实体。写法与 `Target` 相同（`04-contract-types.md` 1.5），除 `table` 外恰好给一个。**没有按来源键（`external_key`）定位的写法**：Agent 先读到行 ID 再声明 | 不引入新的定位方式；按来源键的 op 本身也不能带前提（3.5） |
| `fields` | 可选。给了，只有这些字段变了才算；不给，任何字段变了都算。行被撤销不论给没给都算（§5.1） | 多数时候 Agent 说得出用的是哪个字段（发布日期行的 `date`）；说不出时宁可多报 |
| `ver` | 应带回读到的那个。没带时按 `04-contract.md` 第 2 节的兜底取本连接实例（同一 `task`）最近一次读到的版本，`warnings` 给 `premise_ver_fallback`；无可兜底报 `read_first` | 与写入目标的 `ver` 完全同一套规则；前提按定义就是读到过的值 |
| 业务时间 | 只对状态类表。`valid_at` 或 `valid_during`；**都不给时，依赖行自己有业务时间就取它，没有才是"从现在起"**（见下） | 见下 |
| 值 | **不记**。只记标识与版本 | 前提的值是别的贡献的副本，多一份副本隐私删除就多一处要清（`02-integrity-and-records.md`「写日志」："不记写入前的值"是同一个理由） |

**状态类表为什么要带业务时间，不给时取什么**：

- 读取记录记业务时间条件，是因为"不记则纠错影响查询会多报"（`02-integrity-and-records.md`「读取记录」）。前提同理：以"11 月的预算"为前提，12 月的预算改了不该标。
- **依赖行自己有业务时间时，默认取它**。按天的计划行以那一天的目标为前提；周一的计划不该因为下个月的目标改了而被标。具体：
  - 依赖行在事件类表上：**取这个 op 写下的时间字段（`time.field`）的值**，是一个点——不论这一部分是生效、成了候选还是进了待确认（声明说的是"按我写的这一行"，之后采纳与否不改它）；这个 op 没写时间字段时，取 op 之后这个字段的生效值。
  - 依赖行在状态类表上：取这个 op 写下的区间（同样不论生效与否）。
- **依赖行没有业务时间时**（无时间表；事件类表上时间字段为空；状态类表上不带区间的重申与清除），**默认"从现在起"**：`[入口时刻, ∞)`。读取记录把不传时间的读取记为入口时刻那一点，因为它回答的是"当时读到的对不对"；前提面向的是之后——按"当前预算"排出来的计划，在"下个月起预算下调"被记下的那一刻就该被指出来，而那次写入并没有改"现在这一点"的值。
- **`date` 粒度按日对齐**（`05-time.md`「状态类表的粒度」）：前提目标所在的表是 `date` 粒度时，一个时刻取它在 slot 时区下的那一天，"从现在起"从 `ctx.today` 那一天起。前提目标是 `instant` 粒度、依赖行的时间是日期时，取那一天在 slot 时区下的起止时刻。依赖行的区间是 `instant` 粒度的 `[a, b)`、前提目标是 `date` 粒度时，取**与它相交的每一天**：从 `a` 所在的那一天起，到 `b` 之前最后一刻所在那一天的次日止（`b` 恰在零点时就是 `b` 那一天；开口终点仍是开口）——宁可多报一天，不漏一天。
- **记在哪**：
  - "从现在起"由入口时刻得出，不含调用方给的任何值，记在元数据块里（事件格式 1.1：元数据块可含"入口时刻与由它得出的日期"）。
  - 取自依赖行的业务时间是内容（那一行的时间值是用户说的）。解析后的点或区间记进数据块 `ops/<i>/premise_valid/<j>`：值出自这个 op 自己写下的时间字段或区间时，来源与那一块（`ops/<i>/set/<字段ID>` 或 `ops/<i>/valid`）相同；出自更早的贡献（这个 op 没写时间字段）时，带 `deps` 指向给出它的那一项（事件格式 3.5，与 `span` 块同一种做法）。
  - 显式给的 `valid_at` / `valid_during` 是调用方给的时间，是内容，记进同一个数据块，来源是这个 op 的证据（§8.1）。
- **取自依赖行的范围在声明时定下**，之后依赖行的时间被改，这条声明的范围不跟着变：改依赖行的时间是一次写入，Agent 改时带上新的前提即可（§6.3）。

### 3.4 能指向什么

| 目标 | 第一版 | 理由 |
|---|---|---|
| 同一 slot 的基础表的行 / 实体 | 可以 | — |
| 本请求里新建的行（`"@p1"`） | 可以。所见版本记为 `same_request` | 与 `ref` 字段、`ver` 的做法一致（`04-contract.md` 5.1："后面的 op 看得到前面 op 的结果"）。"建一个里程碑，再建三条以它为前提的任务"应当能在一次请求里完成 |
| 本 op 自己的目标行 | 不可以，报 `invalid_argument`（`premise_self`） | 没有意义 |
| 派生表的行（如"预算剩余"） | **不可以**，报 `not_in_this_version` | 见下 |
| 别的 slot 的表（表在这个凭证的可见范围内） | **不可以**，报 `invalid_argument`（`cross_slot`） | 见下 |
| 可见范围外的表或行 | 与不存在相同：表报 `unknown_table`，行报 `not_found` | 接入面的决定稿 2.2：范围外的东西对这个凭证与不存在完全相同；报 `cross_slot` 会泄露"这个 ID 在别处存在" |
| 源数据 | 不可以（没有这种目标）| 那是证据，用 `evidence` / `source_ref` |
| 按时刻读到的历史版本（`h41.0`） | 不可以，报 `invalid_argument`（`premise_historical_ver`） | 历史版本不能用于写入（`04-contract.md` 第 2 节）；以一个早已不是当前的值为前提，声明时就已经变了 |

**派生行为什么不进第一版**：

1. 第一版的影响查询不覆盖对派生值的读取（`07-scope-v1.md` 3.5："对派生值的读取按分区匹配后续"；`02-architecture.md` §3 的 K10 适用面）。前提要接在同一套"值变了哪些"的计算上，而这套计算第一版在派生行上还没有。
2. 派生行不存历史（`02-integrity-and-records.md`「写日志」："派生数据不存历史，按那一刻的基础数据重算"），"值恢复后撤掉标记"要另做一次按旧位置的重算。
3. 读时计算的派生行（依赖"今天"的规则）没有派生写入可挂（同文「纠错影响查询」）。
4. 像"预算剩余"这样的值每记一笔支出就变一次，以它为前提的行会一直带标记。这不是错，但值得先用评测看 Agent 在基础行上的声明质量，再放开。

加回时是纯增量：`PremiseRef` 用上 `Target` 里已有的 `key`，事件块里的目标加可选键 `partition`，`premise.changed` 由派生写入触发；用到新键的事件 `v` 加一（事件格式 1.6）。**第一版里以"预算剩余"为前提的行，声明它所汇总的基础行（预算那一行）**，工具描述里写明。由此读过派生合计的一方，第一版既收不到影响查询的提示，也不能把合计声明为前提；要知道合计变没变，靠 `changes` 自己查（讲解里点明）。

**为什么不跨 slot**：

- `ref` 字段只在同一 slot 内（`04-write-and-read.md`「引用字段」），一次写入只涉及一个 slot（`04-contract.md` 第 9 节），一次删除只针对一个 slot（`03-deletion.md`「删除的种类」）。跨 slot 的前提会让 A slot 的一次写入在事件里列出 B slot 的行。
- 事件头带 `slot` 是为将来按 slot 做部分复制（事件格式 9.1、§10「多节点」）。跨 slot 的前提变化事件归哪个 slot、只复制了其中一个 slot 的副本怎么得到标记，现在没有答案。
- 可见范围按 slot 过滤（`04-write-and-read.md`「可见范围」）。跨 slot 的标记会向看不见目标 slot 的读方透露"那边有一行、它变了"。
- 代价：健康 slot 的训练计划以另一个 slot 里的目标为前提，第一版声明不了。加回时要先回答上面三点。

### 3.5 哪些 op 可以带

| op | 能带 `premises` 吗 | 含义 |
|---|---|---|
| `insert` | 能 | 新写的这一行以这些为前提 |
| `update` / `correct`，带 `set` | 能 | 这次写的值以这些为前提；这一行其余仍生效的值也按这些重新核对过（§6.3） |
| `update`，**不带 `set`**，带非空的 `premises` | 能 | **重申**：值不变，这一行现有的值以这些为前提仍然成立（§6.3） |
| `update`，带 `premises: []`（可带可不带 `set`） | 能 | **清除**：这一行的前提声明全部去掉，标记随之消失（§6.3）。这是"去掉一条前提"的唯一写法 |
| 带 `revert` 的 op | 不能，报 `invalid_argument`（`premises_with_revert`） | 回退写回的是别的贡献的值，它们各自的前提随贡献一起回来（§8.4），不需要也不应该另声明 |
| `revoke` | 不能，报 `invalid_argument`（`premises_with_revoke`） | 撤销不给值 |
| `resolve` | 不能（第一版 `resolve` 没有这个参数） | 采纳候选、确认提议搬运的是原写入的贡献，原写入的前提随之生效（§8.4） |
| 按来源键（`external_key`）定位的 op | 不能，报 `invalid_argument`（`premises_with_external_key`） | 连接器没读过它要写的行，也多半没读过别的行，兜底只会得到 `read_first`；按来源键的 op 没变时不进任何事件（接入面的决定稿 3.8），放不下声明。连接器写的行要声明前提，由 Agent 读到之后另行重申 |

重申、清除的目标行已被撤销时，与普通的 `update` 一样报 `revoked`。

### 3.6 最小例子

```json
{
  "sv": 1,
  "evidence": [{ "kind": "user_message", "text": "按发布日期把测试任务排出来" }],
  "ops": [{
    "intent": "insert", "table": "tasks",
    "set": { "title": "完成回归测试", "due": "2026-11-25", "status": "todo" },
    "premises": [{ "table": "constraints", "row": "r_C…", "fields": ["date"], "ver": "v40.0" }]
  }]
}
```

## 4. 决定 2 与已有概念的区别

| 概念 | 指向什么 | 谁给出 | 目标变了之后 |
|---|---|---|---|
| **证据**（`evidence`） | 源数据：用户原话、工具结果、文件 | Agent 随写入提交 | 证据不会"变"，只会被隐私删除；删除沿值来源级联，值被去掉或回到更早的值（`03-deletion.md`「来源」） |
| **`ref` 字段** | 另一行的 ID，是这一行的**值** | Agent 写进字段 | 引用方不动；目标被撤销或删除时读结果带 `dangling_ref`（`04-write-and-read.md`「引用字段」）。目标的字段值变了，不标 |
| **派生规则的依赖** | 规则引用的（表，列） | 规则编译时由 saveslot 分析 | 同一事务重算，值自动跟上（K5） |
| **读取记录** | 某次读取读到的版本 | saveslot 自动记 | 只告诉**读过的那个连接实例**"你曾读到的值后来变了"（`possibly_affected`）；不在日志里，有保留期 |
| **前提**（`premises`） | saveslot 里另一行的某些字段、在某个版本上的值 | Agent 随写入声明 | 这一行**对所有读取方**带 `premise_changed`；值不动，等 Agent 处理 |

各一两句：

- **证据 vs 前提**。证据是"这个值出自哪句话"，指向不可变的原文，回答可回溯；前提是"这个值是看了库里哪些值之后定的"，指向会变的数据，回答还站不站得住。一条任务可以两样都有：证据是用户那句"排一下测试任务"，前提是发布日期那一行。删除只沿证据传播，**不沿前提传播**（§5.4）。
- **`ref` vs 前提**。`ref` 是业务结构（这笔支出的收款方是谁），是字段的值，受 schema 约束，目标的内容变了与它无关。前提不是值，不进 schema，说的是"目标的内容变了这一行就要重新看"。两者可以同时指向同一行。
- **派生依赖 vs 前提**。派生依赖是 saveslot 自己执行的规则的输入，变了就重算；前提是 Agent 的推理的输入，变了只能标出来。
- **读取记录 vs 前提**。读取记录是"读了"，前提是"用了"。前者自动、宽、给读方自己看；后者显式、窄、给所有人看。
- **与事件格式里的 `deps`**（事件格式 3.5）：`deps` 是 saveslot 求得某个块时用到的贡献，目的是隐私删除时把抄来的内容清掉；前提是 Agent 声明的，只记标识不抄值，所以没有内容要清，也不进任何块的 `deps`。

## 5. 决定 3 什么算"前提变了"

### 5.1 判据

**一条声明的前提变了，当且仅当：它所声明的（字段 × 业务时间）上，现在的值与写入方所见版本上的值不同。**

- 事件类表、无时间表没有业务时间，范围就是所声明的字段（不给 `fields` 时是全部字段）。
- 状态类表的范围是所声明的字段 × 声明的业务时间（§3.3）。
- "值"按字段类型的同值判据比较（`10-types-and-units.md`「同值判据」），与冲突、佐证用的是同一个。
- **前提目标被撤销，不论声明了哪些字段，一律算前提变了**：撤销与每个字段相交，与冲突单元对撤销的处理一致（`04-contract.md` 5.4）。状态类表上一段变成无值，与每条声明的字段都相交；状态类表另要求业务时间相交。

这与纠错影响查询的判据是同一句话（`02-integrity-and-records.md`「纠错影响查询 · 什么会触发」："判据是结构性的：一次读取问过的某个（字段，业务时刻）上，值在它读到的版本与现在之间变了"）。

### 5.2 与纠错影响查询的触发条件对照

| 写入 | 纠错影响查询（`possibly_affected`） | 前提（`premise_changed`） |
|---|---|---|
| 事件类 / 无时间表：`correct` | 查 | 标，原因 `correct` |
| 事件类 / 无时间表：`revoke` | 查 | 标，原因 `revoke` |
| 事件类 / 无时间表：`update` | **不查** | **标**，原因 `update` |
| 状态类表：任何让值变化的写入 | 查，原因 `correct` / `retroactive` / `plan_changed` | 标，原因相同（带区间的 `revoke` 记 `revoke`）。**一次写入在所声明的范围上同时有追溯与未来的部分时，原因取 `retroactive`** |
| 同值的写入（无操作、佐证） | 不查 | 不标 |
| 成为候选、进待确认的写入 | 不查（没生效） | 不标；之后被采纳或确认时，按那次解决触发的写入判断 |
| 回退（`undo`）、回到冲突前 | 是一次写入，按它的意图与实际变化 | 同左；多数时候它的效果是**撤掉**标记（§5.3） |
| 隐私删除改掉了值 | 只撤不增 | **标**，原因 `deleted`（§5.4） |

**决定：机制共用，条件不同。** 只在一处不同——事件类表与无时间表上的 `update`。

- **为什么不同**：影响查询在这两类表上"看意图"，是因为它问的是**过去**——"之前读到的值当时对不对"；`update` 意味着当时是对的，所以不打扰读过的人。前提问的是**现在**——"库里这一行现在还站在什么上"；发布日期改了，不管是因为记错了还是改了主意，任务都要重新看。本稿的出发例子正是一次 `update`，沿用影响查询的条件就等于没解决问题。
- **追溯与未来并存时取 `retroactive`**：一条声明只给一个原因；`retroactive` 说的是"已经过去的那部分也变了"，读方据此至少要回看一次，比 `plan_changed` 的提示更强。`possibly_affected` 按区间拆成两条，那是一条读取对应多个区间；这里一条声明只有一个标记。
- **共用的部分**：
  1. "这次操作让哪些（行，字段，业务时间区间）的值实际变了"——影响查询已经在算（同文"范围是值实际变化的部分"）。
  2. "值恢复后撤掉标记"的比较与调用时机（同文："对所有写到带标记目标的写入都做这项检查，删除确认与撤回也做"）。
  3. 状态类表上三种原因的划分。
- **不共用的部分**：匹配对象是日志里的声明，不是读取记录；结果进日志与 (b) 类状态，不进 (c) 类（§8）。

**原因码** `PremiseReason`：`correct`、`update`、`revoke`、`retroactive`、`plan_changed`、`deleted`。其中 `correct`、`revoke`、`retroactive`、`plan_changed` 与 `AffectedReason` 同名同义（`04-contract-types.md` 第 3 节），新增 `update` 与 `deleted`。

### 5.3 各种情形

| 情形 | 结果 | 说明 |
|---|---|---|
| 只声明了 `date`，目标行的 `name` 变了 | 不标 | 这就是声明字段的用处 |
| 没声明 `fields`，任何字段变了 | 标 | 宁可多报 |
| 目标行被撤销 | 标，`revoke`，不论声明了哪些字段 | "存在"与每个字段都相交（§5.1） |
| 撤销被 `undo` | 标记撤掉 | 值恢复 |
| 目标的改动被 `undo` | 标记撤掉（**自然消失**） | 不是专门的规则：`undo` 是一次写入，它让值回到了声明时所见的值，"值恢复后撤掉标记"的检查撤掉它 |
| 目标改了又被另一次写入改回同样的值 | 标记撤掉 | 同上，判据是值 |
| 目标改过之后，依赖行已按新值重申；随后改动被 `undo` | **重新标**，原因取 `undo` 那次写入的意图 | 重申把"所见版本"更新到了改动之后；值又回去了，对重申过的声明来说是变了 |
| 目标上有未决冲突（`disputed`）| 不因争议本身而标 | 生效值没变。候选被采纳时按那次写入判断 |
| 声明时前提已经变了（带回的 `ver` 过期，且所声明的范围在那之后变过） | 照常写入，**立即带标记** | §10.3 |
| 声明时 `ver` 过期，但所声明的范围没变过 | 不标 | 与冲突判定"这个字段之后没人动过就合并"一致（`04-contract.md` 5.4 `merged`）|
| 状态类表：一次写入把 `[11-10, 11-20)` 改掉，今天是 11-15，声明的范围覆盖整个 11 月 | 标，`retroactive` | 追溯与未来并存（§5.2） |

### 5.4 前提所在的行被隐私删除

**决定：隐私删除让所声明范围上的值变了（按删除前后的值比较），依赖行带标记，原因 `deleted`；删除预览单列这些行。**

- **与影响查询的"只撤不增"不同，理由**：`03-deletion.md`「删除之后」对读过被删数据的已完成任务"不追溯、不通知"，因为"产出早已离开 saveslot，无法召回"，并且"不应再生成描述被删内容的新记录"。依赖行不一样：它还在 saveslot 里，别的 Agent 还会读到它、当成正常的行用。
- **先例**：`ref` 的目标被隐私删除时，引用方带 `dangling_ref`（状态 `deleted`），删除预览单列"仍引用被删行的行"（`04-write-and-read.md`「引用字段」；`03-deletion.md`「预览与回执要写明的内容」）。前提照此办理。
- **只看值，不看给出者**：删除只换了给出这个值的贡献、值本身没变（例：被删的是一次同值佐证的证据；或删掉中间一次改动后，后来的"改回"成了同值写入），不标。判据与 §5.1 相同，"当且仅当值不同"在删除这一侧也成立。
- **不产生描述被删内容的记录**：标记里只有目标行的 ID、字段名、所见版本号、删除的操作号，都是删除后本来就保留的元数据（事件格式 9.2）；没有值。
- **删除不沿前提级联**。依赖行的值来源是它自己的证据，不是它的前提；`03-deletion.md`「两条原则」①"只追数据依赖"里的数据依赖指值来源。依赖行里是否转述了被删的内容，saveslot 不知道，预览列出来交给人决定——这正是 `02-integrity-and-records.md` 里"污点追踪"设想的用法（"隐私删除时列给用户决定"），只是来源从"读过的全部"换成了"声明过的"。

| 情形 | 结果 |
|---|---|
| 删除让目标行整行消失，或让所声明的字段变空、回到更早的不同值、在范围内的某一段上值不同 | 标，`deleted` |
| 删除只换了给出者，值没变 | 不标 |
| 删除去掉了目标上"使前提不同"的那次改动（删一句纠错的话，值回到纠错前），值回到所见的值 | 标记撤掉——条件是所见版本上的值还读得到（下一行） |
| 所见版本上的值本身已被删除（待删除或已物理删除） | **比不了就不撤**：标记保持。不拿被删的值做比较，是"删除后不可比对"的一部分（`02-integrity-and-records.md`「完整性与溯源 · 不承诺」） |
| 声明本来就是"已变"，删除改了它范围上的值，或去掉了 `since` 所指那次改动在这个范围上的贡献，而值仍与所见的不同 | 标记保持，**`since` 改指这次删除、`reason` 改为 `deleted`**。否则标记会指着一次在删除之后什么都没做过的操作，读方顺着它查不到任何东西 |
| 撤回删除 | 按撤回后的状态再判一次：值回到所见的值就撤掉 |

**判法**：

- **打标记不需要读所见版本**：删除前的值此时仍在存储里读得到。一条"没变"的声明，删除前的值就等于所见的值；删除前后值不同，就是变了。
- **撤标记**要比较"现在的值"与"所见版本上的值"。后者按所见版本的操作号从版本表读取；所见版本上那一格的内容块已清空或正在待删除中时，视为比不了。

前提目标被整行隐私删除之后，声明里的目标就不存在了：重申它会被 `not_found` 拒绝（§10.3）。要消掉这样的标记，用 `premises: []` 清除，再按需要声明别的前提（§6.3）。

### 5.5 schema 切换

第一版先定一条保守的规则，P4 开工前复核（§17）：**切换本身不触发标记**（确定性转换改的是写法，不是 Agent 所用到的事实）；所声明的字段在新版里被删除时，这条声明按"整行"继续有效的做法不取——它会把标记面从一个字段扩大到整行——而是标上原因 `schema_switched`（届时新增的枚举值）。这条不影响事件格式 v1：加枚举值是允许的演进（事件格式 1.6）。

切换改了单位或类型之后，撤标记时"现在的值"与"所见版本上的值"按哪一版比较，届时要读跨 `sv` 的历史值；这一条记进待定清单（`08-open-questions.md`），P4 开工前定。不影响事件格式。

## 6. 决定 4 标记

### 6.1 形状

```ts
interface Marks {
  // …已有的各项
  /** 这一行的值所用到的前提后来变了。值没有动；是否仍然成立由读方判断。 */
  premise_changed?: Array<{
    premise: TargetRef;            // 前提所在的行 / 实体
    premise_fields?: FieldName[];  // 声明的字段；没有 = 整行
    seen: Ver;                     // 声明时所见的版本
    reason: PremiseReason;
    since: Seq;                    // 使前提不同于所见值的那次操作（删除之后改指那次删除）
    fields: FieldName[];           // 本行里由这条声明覆盖的字段
    declared: { seq: Seq; actor: Actor };   // 哪次写入声明的
  }>;
}

type PremiseReason = "correct" | "update" | "revoke" | "retroactive" | "plan_changed" | "deleted";
```

| 要素 | 规则 |
|---|---|
| 给谁看 | **任何读取方**。它是这一行的状态，不是某个读方的状态 |
| 什么时候出现在一行上 | 这一行**当前的值**里，有字段的出处项被一条"已变"的声明覆盖（定义见 §8.2）。被后来的写入盖掉的旧值，它的前提不再显示 |
| 请求了 `fields` | 所请求的字段都不在标记的 `fields` 里时，这一行不带这个标记——与 `disputed`、`awaiting` 同一条（`04-contract.md` 第 7 节："只在读到的值会随处理结果而变时才标"） |
| 状态类表 | 按段判断：这一段的值的出处项被"已变"的声明覆盖，这一段带标记 |
| 条数 | 一行最多列 10 条，按 `since` 从新到旧；超出时另给总数 |
| `ver` | **打标记、撤标记都不改依赖行的 `ver`**。值没有变；别的 Agent 手里的 `ver` 不该因此失效（与 `disputed` 的出现不改 `ver` 一致） |
| 派生行 | `input_marks` 加一项计数 `premise_changed`：只统计规则所依赖的字段上带这个标记的基础行 |
| `sql` | `marks_summary` 加同一项计数 |
| `history` | `timeline` 里声明了前提的那次写入带 `premises`（目标、字段、所见版本、现在是否已变）；重申与清除也各是一条（§6.3） |
| `detail: "detailed"` | 每行另给它当前生效的全部声明（含没变的），供读方看"这一行站在什么上" |

### 6.2 MCP 文本

对照 `05-surfaces.md` 4.2（每个契约标记都要出现在文本里）与 4.3 的措辞原则（"提示与工具描述不指挥模型，只陈述事实与可用的下一步"）。

| 标记 | 文本写法 |
|---|---|
| `premise_changed` | `⚠ 前提已变：constraints r_01JF… 的 date（声明时所见 v40.0）在 #60 被变更；涉及本行 title、due、status` |
| 原因 `correct` | "在 #n 被纠正" |
| 原因 `update` | "在 #n 被变更" |
| 原因 `revoke` | "在 #n 被撤销" |
| 原因 `retroactive` | "在 #n 被追溯修改（变的是 <区间> 的值；按这段业务时间读才看得到）" |
| 原因 `plan_changed` | "在 #n 改了之后的安排（<起点> 起；按这段业务时间读才看得到）" |
| 原因 `deleted` | "在 #n 被删除" |
| 派生行的 `input_marks` | `⚠ 本值的输入里有 2 行的前提已变` |

- 行、目标的 ID 与 `ver` 一律完整（4.1）。
- **`retroactive` 与 `plan_changed` 要带时间段**：不传时间的读取只返回当前那一段，将来才生效的改动在那一段里看不到；文本给出变化的区间，工具描述里写明"原因是追溯修改或改了之后的安排时，按那段业务时间读前提"（§10.4）。区间是删除后仍保留的内容时才写；它已被删除时只写操作号。
- **不写"请更新这一行"**。文本只说哪条前提、哪个字段、在哪次操作里变了。怎么办写在工具描述里（§10.4），那里说的是"这个工具能做什么"，不是命令。

改动方的回执（`saveslot_write`、`saveslot_resolve`、`saveslot_delete`）：

```
已保存 · project schema v1 · #60
constraints r_01JF… 变更：date 2026-12-01 → 2026-11-20（ver=v60.0）
有 3 行以这一行的 date 为前提，现已带上"前提已变"：tasks r_01JG…、r_01JH…、r_01JK…
```

### 6.3 标记怎么消掉

| 做法 | 怎么做 | 优点 | 问题 |
|---|---|---|---|
| 甲 只靠改写 | 依赖行被重新写入（带新前提）时标记消失 | 不加概念 | 核对后发现不用改的行消不掉：同值的字段是无操作，日志里不留任何东西（`03-deletion.md`「贡献」） |
| 乙 单独的确认操作 / 工具 | 新增一个"确认仍然成立"的操作 | 语义清楚 | 多一个操作、多一个 MCP 工具（`05-surfaces.md` 第 1 节的工具数是要控制的）；它做的事——"对这一行说一句话并更新前提"——就是一次写入 |
| 丙 待处理事项 | 每条变了的前提生成一个事项，`resolve` 处理 | 复用事项的确认绑定 | 一处改动产生几十上百个事项，违反"不堆积"（`07-scope-v1.md` 第 5 节「冲突的多候选」里否决"每个过期写入各开一个事项"用的就是这个理由）；事项是"等人决定的事"，这里多数由 Agent 自己判断 |
| 丁 改写 + 重申 + 清除，都走 `write` | 改写照常；不用改时发一次不带 `set` 的 `update`、带上新的 `premises`；不再以任何东西为前提时带 `premises: []` | 不加操作、不加工具；重申与清除有 actor、有源数据、进日志 | `update` 的"`set` 或 `revert` 二选一"要放宽（§16 第 3 条） |

**决定：丁。**

一个带 `premises` 的 op 的含义是：**"按我所见的版本，这一行现在的值以这些为前提。"** 它覆盖两部分：

1. **本 op 自己写下的各项**（隐含，不另记）。
2. **这一行在 op 所见版本上就已生效、op 之后仍然生效的其余各项**（显式记在事件里，§8.1 的 `premise_covers`）。只在这个 op **全部字段都已生效**（回执 `status: saved` 的那种：`applied`、`corroborated`、`noop`）时才覆盖；有字段成了候选或进了待确认时不覆盖——它对整行的判断是以自己的改动落地为前提的（清除除外，见下面的取代规则）。这个 op 之后经 `take_candidate` 采纳、或因删除而生效时，第 2 部分**不补记**：这一行其余字段仍按原来的声明显示标记。工具描述与规格都写明这一点。

不带 `set` 的 `update` 没有第 1 部分，只有第 2 部分，这就是**重申**。

**取代规则**：对同一个出处项、同一个前提目标，**以最晚的一条覆盖它的声明为准**。带 `premises: []` 的 op（**清除**）覆盖的各项上，它之前的全部声明一并失效，不论指向哪个目标；它自己写下的项没有前提。**清除的第 2 部分不受"全部字段都已生效"的条件限制**：清除不对值下判断，带 `set` 的清除即使有字段成了候选或进了待确认，这一行在所见版本上就已生效、之后仍生效的其余各项也照样记进 `premise_covers` 并被清掉——"清掉这一行的前提声明"说的是整行。所以：

| 做了什么 | 结果 |
|---|---|
| 改了 `due`，带 `premises: [发布日期 @ 新 ver]` | `due` 的新值按新声明；`title`、`status` 两项的旧声明（指向发布日期）被新声明取代。标记消失 |
| 不改值，带 `premises: [发布日期 @ 新 ver]`（重申） | 三项的旧声明都被取代。标记消失；行的 `ver` 不变 |
| 改了 `due`，**没带** `premises` | `due` 的新值没有前提；`title`、`status` 仍按旧声明。标记还在，`fields` 里少了 `due` |
| 带的 `premises` 指向**另一行** | 新增一条前提；指向发布日期的旧声明不受影响，标记还在 |
| 新 `premises` 带回的 `ver` 仍是旧的 | 新声明一落账就是"已变"，标记换成新声明的（§10.3） |
| 带 `premises: []`（清除） | 这一行被覆盖的各项上的全部声明失效，标记消失；之后那些前提目标再变，这一行不再被标 |
| 只想去掉两条前提中的一条 | 同一请求里先 `premises: []` 清除，再用一个重申 op 声明要留下的那条（后面的 op 看得到前面的结果，`ver` 照"请求开始时所见"） |
| 前提目标已被整行隐私删除 | 重申它报 `not_found`；用 `premises: []` 清除 |

- **重申要不要带依赖行的 `ver`**：应带（或兜底）。它只覆盖"所见版本上就已生效"的项：别人在你读之后写进这一行的值，你没看过，不替你重申。这与"同值按写入方所见的版本判"（`04-contract.md` 5.4）是同一个出发点。不做冲突判定、不会成为候选——重申不改值。清除同理。
- **重申算不算一次写入**：算一次 `write` 操作，有操作号、有逻辑写入头、有源数据（带了证据就是证据；没带就是这个 op 自己的那条 `api_call`）；**没有基础写入**，行的 `ver` 不变。这与"全部字段都是无操作的请求"的事件构成相同（`02-integrity-and-records.md`「写日志」），只是头事件里多了前提块。没带证据时 `api_call` 照规格现行的粒度：每个在事件里留下了东西的 op 各一条、只含该 op；重申与清除在事件里留下了声明，算在内（与接入面的决定稿 3.8 是同一条）。
- **重申的请求键**：服务端请求键的规范化**包含每条前提解析后的所见版本**（含兜底取得的）。"前提又变了、再核对一次、请求体逐字不变"是重申的正常用法；不含解析后的版本，第二次重申会在 10 分钟的窗口里被当成第一次的重放，返回一个过时的 `state: current`。只对前提这一处；写入目标兜底补上的 `ver` 仍不进规范化（`04-contract.md` 第 14 节）。
- **重申能不能被 `undo`**：不能。它在这一行上没有基础写入，`undo` 它与"全部是无操作的写入"一样报 `invalid_argument`（没有可撤回的改动，`04-write-and-read.md`「撤回某次写入」）。要推翻一次重申，再重申一次（带当时的 `ver`）或改写。清除同理。

### 6.4 最小例子

重申（任务不用改，发布日期按 `v60.0` 核对过）：

```json
{ "ops": [{ "intent": "update", "table": "tasks", "row": "r_01JK…", "ver": "v50.0",
            "premises": [{ "table": "constraints", "row": "r_C…", "fields": ["date"], "ver": "v60.0" }] }] }
```

清除（这条任务不再以发布日期为前提）：

```json
{ "ops": [{ "intent": "update", "table": "tasks", "row": "r_01JH…", "ver": "v50.0", "premises": [] }] }
```

## 7. 决定 5 不传递

**决定：第一版不传递。** A 变了 → 以 A 为前提的 B 带标记；B 的值没变，以 B 为前提的 C 不带标记。

| 做法 | 结果 | 问题 |
|---|---|---|
| 甲 不传递 | C 只在 B 的值真的变了之后才被标 | B 带着标记、还没人处理的这段时间里，只读 C 的读方看不出上游有事 |
| 乙 传递闭包 | A 一变，B、C、D……全标 | saveslot 不知道 B 是否失效。B 很可能核对后原样成立，那 C 被标就是错报；链越长、扇出越大，错报越多 |
| 丙 传递但分级 | B 标"前提已变"，C 标一个更弱的"上游的前提已变" | 多一种标记、多一种消法；C 的标记什么时候消取决于 B 被怎么处理，状态机复杂 |

**理由**：

1. **判据不成立**。C 的声明是"我以 B 在某个版本上的值为前提"。B 的值没变，按 §5.1 的判据 C 的前提没有变。标 C 等于 saveslot 替 Agent 判断"B 已经失效"，而已定的结论（§2）恰恰是这件事由 Agent 判断。
2. **与派生的对比**。派生可以一路级联，是因为每一层都由规则重算、算完就知道值变没变（"结果没变就不往下游传"，`06-derived.md`「刷新范围与写入准入」）。这里"B 变没变"要等 Agent 处理 B 才知道——处理的结果恰好就是那个信号。
3. **"B 被改写之后 C 才被标"是否足够**：足够，而且正是想要的。
   - Agent 处理 B 时改了值 → 这是一次普通写入，C 按普通规则被标，原因是 B 那次写入的意图。
   - Agent 核对后重申 B → B 的值没变，C 不该被打扰。
   - 两种结果都不需要专门的传递规则。
4. **代价有上限**。一次操作打的标记数只取决于直接依赖它的声明数（§9），不取决于链的长度。

**不足与补法**。甲的问题（B 悬而未决期间读 C 的人不知情）是真的。两处缓解，都不需要新机制：

- 读 C 时用 `detail: "detailed"` 可以看到它的全部前提（§6.1）；其中有 B。读 B 就能看到 B 的标记。
- 处理 B 的 Agent 的回执里会列出"有 n 行以 B 为前提"（`premise_affected`，B 的值变了才有）。

将来若评测表明需要，丙可以**在读取时现算**（读 C 时看它的前提目标自己是否带标记），不进日志、不改事件格式。第一版不做。

## 8. 决定 6 记在哪

三句话概括：

- **声明**是调用方的原始传参，记在 `write.head` 里，只有标识与版本，是元数据块（显式与取自依赖行的业务时间除外，它们是数据块）。
- **标记的变化**是 saveslot 的判定结果，记在新事件 `premise.changed` 里；`apply` 照事件做，不自己比较值。
- **前提不参与任何取值判定**。同值、冲突、高影响、存在、回掉、删除重放都不读它。所以伪代码一字不改，参考求值器不用知道前提的存在。

### 8.1 事件格式

**`write.head` 新增四种块**（事件格式 5.7 的词表）：

| path | 种类 | 内容 | 来源 |
|---|---|---|---|
| `ops/<i>/premises/<j>` | 元 | 一条声明，见下 | — |
| `ops/<i>/premise_valid/<j>` | 数 | 第 j 条声明的业务时间：`{"at": <点>}` 或 `{"during": {"from": <点>, "to": <点>}}`。调用方给了 `valid_at` / `valid_during`，或范围取自依赖行的业务时间（`range: "row_time"`）时有 | 显式给的：这个 op 的全部证据（与没映射时的 `ops/<i>/valid` 相同）。取自依赖行的：出自本 op 写下的时间字段或区间时，与那一块的来源相同；出自更早的贡献时，带 `deps` 指向给出它的那一项（事件格式 3.5） |
| `ops/<i>/premise_covers` | 元 | 这个 op 的声明另外覆盖的出处项：`[{"event": 52, "field": "f1", "k": 0}]`（对"存在"的一项写成 `{"event": …, "existence": <k>}`）。为空时不出现 | — |
| `ops/<i>/premises_cleared` | 元 | `true`：这个 op 带的是 `premises: []`（清除）。它覆盖的项同样列在 `ops/<i>/premise_covers` 里 | — |

`ops/<i>/premises/<j>`：

```json
{"table": "t1", "row": "r_01JF…", "fields": ["f2"],
 "ver": {"op": 40, "restore_count": 0, "basis": "explicit"},
 "range": "whole", "state": "current"}
```

| 键 | 含义 |
|---|---|
| `table`、`row` / `entity` | 前提目标。按 `entity_key` 或临时名给的，这里记解析后的 ID（键值与临时名是内容，不记在这里） |
| `fields` | 声明的字段 ID 列表。缺省 = 整行 |
| `ver` | 所见版本。形状与 `ops/<i>/target` 的 `ver` 相同，其中的 `basis` 是事件格式已有的"版本是怎么来的"：`explicit` / `fallback` / `same_request` |
| `range` | `whole`（事件类表、无时间表）/ `from_now`（状态类表，从 `ctx.now` 起一直延续；`date` 粒度从 `ctx.today` 起）/ `row_time`（状态类表，取依赖行的业务时间，见 `ops/<i>/premise_valid/<j>`）/ `given`（状态类表，调用方给了时间，见同一块） |
| `state` | 落账时的判定结果：`current`（所见的值就是现在的值）/ `changed`（声明时已经变了） |
| `reason`、`since` | 只在 `state` 为 `changed` 时有：原因码，以及所见版本之后第一次让所声明范围上的值不同的操作号 |

为什么是**元数据块**：里面只有不透明 ID、字段 ID、操作号、恢复次数、枚举（事件格式 1.1 对元数据块的界定）。把这个租户的全部用户输入换成别的，它不变（事件格式 2.3 的第 2 条）。先例：回退记录 `revert`、`valid_sources`、`op_sources` 都是只含序号与 ID 的元数据块。键名用 `range` 而不用 `scope`：`write.base` 的 `existence/<k>` 已有 `scope`（`whole` / `interval`），同名同值不同义。

为什么 `premise_valid` 是**数据块**：业务时间的起止点是用户说的，按事件格式 2.3 是内容（"业务时间区间（起止点是用户说的）"）。显式给的，来源与 `ops/<i>/valid` 一样是这个 op 的证据；取自依赖行的，来源是给出那个时间值的贡献。证据被隐私删除时它列进位置列表。**清掉之后这条声明的范围按整条时间线处理**（宁可多报）。

为什么放在 `write.head` 而不是 `write.base`：

1. 声明是原始传参，`write.head` 就是放原始传参的地方（`02-integrity-and-records.md`「写日志 · 逻辑写入头」）。
2. 重申与清除没有基础写入。
3. 候选、待确认的写入也要记下声明：它们之后生效时，声明随之生效。

为什么不放**事件头**：事件头"尽量少留"，只有通用字段，"表、行、意图、被引用的事件等都在内容块里"（事件格式 2.1）。

**新事件类型 `premise.changed`**（不是头事件；带 `op`）：

| path | 种类 | 内容 |
|---|---|---|
| `targets/<k>` | 元 | 一个值变了的前提目标，以及因此变了状态的声明，见下 |

```json
{"table": "t1", "row": "r_01JF…", "by_event": 62,
 "changed":   [{"op": 50, "i": 0, "j": 0, "reason": "update"}],
 "matched":   [{"op": 73, "i": 0, "j": 0}],
 "repointed": [{"op": 45, "i": 1, "j": 0}]}
```

| 键 | 含义 |
|---|---|
| `table`、`row` / `entity` | 前提目标 |
| `by_event` | 使它变化的事件：本操作里那条 `write.base` 的 `seq`；由删除引起时是 `deletion.confirmed` / `deletion.cancelled` 的 `seq` |
| `changed` | 由"没变"转为"已变"的声明。一条声明的身份 =（声明所在的操作号 `op`，op 下标 `i`，声明下标 `j`）。`reason` 逐条给（状态类表上同一次写入可以对不同的声明是不同的原因） |
| `matched` | 由"已变"转回"没变"的声明（现在的值又与所见的值相同） |
| `repointed` | 只出现在删除事件所属的操作里：保持"已变"、`since` 改为本操作号、`reason` 改为 `deleted` 的声明（§5.4） |

- **只在有变化时产生**；一次操作至多一条。
- **在一次操作里的位置**：全部 `write.base` 与事项事件之后、`write.derived` 之前。`resolve` 触发的写入、删除确认、撤回同理。
- 事件头：`type: "premise.changed"`、`v: 1`、`op`、`slot`、`actor` 与 `at` 同所属操作。
- **全是元数据**，第一版不随任何删除清除；它留下的信息（哪一行的哪条声明在哪次操作里变了状态）列入"删除后保留的元数据"（事件格式 9.2）。
- `apply`：按 `changed` / `matched` / `repointed` 改 `premise_decls` 里对应声明的状态、原因与 `since`。别的什么都不做。

**枚举**（事件格式 6.1、6.8）：事件类型加 `premise.changed`；`range` 取 `whole` / `from_now` / `row_time` / `given`；`state` 取 `current` / `changed`；`reason` 取 §5.2 的六个值。

**为什么标记的变化要写进事件，而不让 `apply` 自己比较值**：

1. `apply` "只照事件里记下的结果做"，自己只做不含判定的确定性计算（`02-architecture.md` §3「日志是唯一事实来源」）。"现在的值与所见版本上的值是否相同"是判定。
2. **重放时比不了**。"撤掉标记"要读所见版本上的值，也就是历史版本。内容被物理删除之后重放，得到的是"去掉被删内容的历史状态，不保证等于当时的线上状态"（同节「物理删除后的事件」）。让 `apply` 在重放时现比，线上与重放可能得出不同的标记，违反 K12。写进事件就没有这个问题：比较只在线上、在当时做一次。
3. 与全设计的做法一致：解析结果、冲突、疑似重复、字面命中、删除结果都是"判定时算好、写进事件、重放不重算"。

**为什么不放进 (c) 类状态（像 `possibly_affected` 那样）**：`possibly_affected` 依赖读取记录，读取记录本身是 (c) 类，所以它只能是 (c) 类，丢了的后果是"之前读到旧值的连接实例不再收到提醒"（`02-architecture.md` §8）。前提的输入全在日志里，没有理由让导出、恢复之后标记消失；它归 (b) 类。

### 8.2 `apply` 维护的物化状态

新增两张 (b) 类表（`02-architecture.md` §8「存储格式 v1」），都由 `apply` 维护、可丢弃后从日志重建、参加对拍：

| 表 | 主键 | 关键列 | 由什么维护 |
|---|---|---|---|
| `premise_decls`（声明） | `(操作号, op 下标, 声明下标)` | 依赖行（表、行或实体）；前提目标（表、行或实体）；字段 ID 列表；范围种类与业务时间（业务时间是内容，随删除清空）；所见版本；状态（没变 / 已变）、原因、`since`；声明者 | `write.head` 的 `ops/<i>/premises/<j>`、`ops/<i>/premise_valid/<j>`；`premise.changed`；`deletion.executed`（清空业务时间） |
| `premise_edges`（覆盖） | `(出处项所在事件的 seq, 字段 ID 或 existence, 项的下标, 前提目标)` | 对这个出处项、这个前提目标，当前有效的声明（指向 `premise_decls` 的主键）；另有一种"清除"条目，前提目标一栏记"全部"，指向做清除的那个 op | `write.base`（按 `target.op_index` 找到本 op 的声明，登记本事件的各项）；`write.head` 的 `ops/<i>/premise_covers` 与 `ops/<i>/premises_cleared`；删除事件的 `restated/<k>`（新编出的下标）。**只增与改写，不删** |

另按前提目标建索引（前提变化时按目标找声明）。

**覆盖的定义**（落 `premise_edges` 时用）：

- 一条声明覆盖：本 op 的 `write.base` 在目标行上的**全部项**（不论当时是生效、候选还是待确认），加上 `ops/<i>/premise_covers` 列出的各项。
- 之后某次删除的重述在同一（事件，字段或"存在"）上**新编出的下标**，随它所在的事件或它被列出的那一项一并被覆盖。这与伪代码步骤 1 对回退记录的展开是同一条规则（"R 里列出的各项，加上 R 里出现过的（事件, 目标）上新编出的下标"）。
- 对同一个（出处项，前提目标），以操作号最大的那条声明为准（§6.3 的取代规则）。一个出处项上有"清除"条目时，操作号小于它的声明都不再算数。

**一行上的标记怎么得出**（读取时）：

1. 取这一行（状态类表：这一段）各字段**当前值的出处项**：给出当前值的那一项贡献；它是搬运来的（回退、采纳候选、回到合并基的写回项，以及删除结果里的 `carried`），沿搬运引用走到头（`03-deletion.md`「搬运的值」：引用链长度不超过历史）；另加当前仍作数的佐证项。来源是 schema 常量的值、`no_value` 与 `uncovered` 的写回项没有出处项。
2. 在 `premise_edges` 里找这些出处项的有效声明（排除被更晚的清除作废的）。
3. 其中状态是"已变"的，每条出一条标记；`fields` 是被它覆盖的那些字段。

这一步只读 (b) 类状态，给定状态结果唯一，与 `dangling_ref` "读时现算、不落盘"（`04-write-and-read.md`「拿得快」）是同一种做法。实现可以把结果缓存成索引，属 (b) 类，结果必须与上面的定义一致。

**谁算**（模块，`02-architecture.md` §4）：

- 声明的校验、兜底、落账时的 `state`：`write`。
- **前提状态的变化**（按变化的格子找声明、打标记、撤标记、改指）：`judge` 里一个纯函数。输入：本次操作里值实际变了的格子（删除时是删除前后值不同的格子，以及失去了贡献的操作号）、与这些格子相交的声明（状态、范围、所见版本、`since`）、撤标记需要的"现在的值"与"所见版本上的值"及比不比得了；输出：哪些声明转为已变、转回没变、改指。它不读存储、不产生事件，与 `judge` 的其余判定一样。
- **生成 `premise.changed`**：`write`（含 `resolve` 触发的写入）与 `delete`（删除确认、撤回）各自在产生改动的那个事务里，经 `store` 读 `premise_decls`、`premise_edges` 与版本表，调上面的函数，把结果写成 `premise.changed` 交给 `apply`。**不经 `read` 模块**：`write`、`delete` 与 `read` 同在 L5，同层不互相依赖；生成事件的模块清单（write、schema、pending、delete、derive、jobs）不用改。
- `read` 只负责读时的标记现算（上面三步）。
- architecture §4 的模块表相应改：`judge` 的职责加"前提状态的变化"；`write`、`delete` 的职责各加"生成前提变化事件"；`read` 加"前提标记的现算"。

### 8.3 检测怎么做，重放是否确定

一次操作（写入、解决触发的写入、删除确认、撤回）在生成完基础事件之后：

1. 取这次操作里**值实际变了的**（行，字段或"存在"，业务时间区间）——影响查询已有的输入。删除确认与撤回取结果里**值**与删除前（撤回前）不同的字段与段；只换了给出者、值没变的不算（§5.4）。
2. **打标记**：按前提目标找状态为"没变"的声明，所声明的字段与范围同第 1 步的结果相交的，转为"已变"，`since` 是本操作号；原因取这次写入的意图（撤销一律 `revoke`；删除为 `deleted`；状态类表上追溯与未来并存取 `retroactive`）。**这一步不读历史**：一条声明状态是"没变"，就意味着到这次操作之前、它的范围上的值一直等于所见的值；这次操作改了它，就是变了。删除时"之前"的值就是删除前存储里的值，同样读得到。
3. **撤标记**：按前提目标找状态为"已变"的声明，其范围同第 1 步的结果相交的，比较"现在的值"与"所见版本上的值"；全部相同且"比得了"（§5.4）才转回"没变"。
4. **改指**（只在删除确认与撤回里）：仍是"已变"的声明，若本次删除改了它范围上的值，或去掉了它 `since` 所指那次操作在这个范围上的贡献，`since` 改为本操作号、`reason` 改为 `deleted`。这一步只读当前状态与删除结果，不读所见版本。
5. 第 2–4 步的结果写成 `premise.changed`。

只处理**在 `premise_edges` 里仍是某个出处项的有效声明**的那些（含候选、待确认的写入的声明：它们之后生效时状态直接可用）；已经被更晚的声明完全取代、或被清除作废的，状态不再维护。

**重放确定**：

- 声明、覆盖、清除、每一次状态变化都在元数据块里；元数据块第一版不被任何删除清除。从空存储重放，`apply` 逐条照做，`premise_decls`、`premise_edges` 与线上逐行相同。
- 唯一会被清除的是 `premise_valid`（显式或取自依赖行的业务时间）。它被墓碑清空之后，线上与重放都按"已移除"处理；它只影响**之后**的检测（范围变宽），不影响已经记下的状态。
- 读取时的标记是 (b) 类状态的函数；K12 保证业务表、版本表当前部分与来源表在日志末端与线上一致，所以读出的标记一致。

**不变式**（写成测试）：对每条仍有效的声明，`状态 = 没变` ⟹ 它的范围上现在的值等于所见版本上的值。反方向不要求成立——"比不了"的时候允许多报。

### 8.4 对照伪代码：依赖行被回掉、被删除时前提怎么办

逐步对照 `03-deletion.md`「回掉的权威定义」的伪代码。结论先行：**伪代码的输入（R、pos、n、C、K）里没有前提，八个步骤没有一步读或写前提；前提跟着贡献走，贡献是否生效由伪代码决定。两者单向依赖，没有相互影响。**

| 伪代码 | 与前提的关系 |
|---|---|
| 输入 C（贡献集合） | 声明不是贡献，不在 C 里。带 `premises` 的写入，它的贡献在 C 里与别的贡献没有区别 |
| 步骤 1（R 展开，新编出的下标） | 前提不读 R。`premise_edges` 对"新编出的下标"的处理借用了这一步的同一条规则（§8.2），保证重放后分出来的项仍被原声明覆盖 |
| 步骤 2–3（域、盖住、范围） | 不读前提。范围只由贡献的区间与先后决定 |
| 步骤 4（这次回掉自己是否生效） | 不读前提。带 `revert` 的 op 不能带 `premises`（§3.5），所以回掉自己没有声明 |
| 步骤 5（登记"已被回掉"） | 被登记的项在范围内不再给值。它若是某条声明覆盖的出处项，这条声明在这一行（状态类表：这一段）上不再显示——因为 §8.2 第 1 步取的是**当前值**的出处项。登记本身不改 `premise_decls`、`premise_edges` |
| 步骤 6（写回，值来源是对给出 S 的那一项的引用） | 写回的值沿 `carried` 走到头，是更早的那一项贡献；**那一项的声明随之重新显示**。它现在是"已变"还是"没变"，取决于它的前提这期间变没变——状态一直在维护（§8.3），不用补算。写回"没有值"、`uncovered`、schema 常量时没有出处项，也就没有前提 |
| 步骤 7（写回项的状态、`dropped`） | 写回项被重述为 `dropped` 时，它不再给值，出处项随之变化，标记按新的出处项现算 |
| 步骤 8（写回项依赖的贡献） | 是 `deps`，用于清除抄来的区间；与前提无关。**前提不进任何块的 `deps`** |
| "回掉的目标本身是一次回掉" | 伪代码："那次操作登记为'已被回掉'的项登记不变，值经由这次的写回项重新出现"。所以出处项**不能**用"没被登记回掉的项"来定义，必须从当前值的搬运引用走到头——§8.2 就是这样定义的。撤回一次撤回之后，原写入的项重新成为出处项，它的声明重新显示 |

四种具体情形：

| 情形 | 发生什么 |
|---|---|
| **依赖行的写入被 `undo`**（例：把 `due` 从 11-25 改成 11-14 并带了新前提的那次写入被撤回） | `due` 写回 11-25，出处项回到原来那次写入的项，原来的声明（指向发布日期的旧版本）重新对 `due` 生效；那条声明若是"已变"，`due` 重新进标记的 `fields`。被撤回的那次写入对 `title`、`status` 的覆盖（`premise_covers`）**不随之撤销**：那是 Agent 对那两项做过的判断，照记录 |
| **依赖行的插入被撤销（`revoke`）** | 行不在逻辑表里，标记无从显示。声明留在日志与 `premise_decls` 里；撤销被 `undo` 后行回来，声明照常生效 |
| **依赖行自己的证据被隐私删除** | 它的贡献被去掉，值落回更早的贡献或整行删除；出处项随之变化，标记现算。声明块是元数据，留在日志里（看得出"那次写入声明过以某一行的第几号字段为前提"，§8.5）；业务时间块随证据清除 |
| **因删除而生效的写入**（原本是候选或待确认，带着 `premises`） | 它的项成为出处项，声明开始显示。它的状态从声明那一刻起就在维护，此时直接可用；`premise_covers` 不补记（§6.3） |

**删除重放里前提算哪一类**（`03-deletion.md`「两条原则」）：

- **声明**是调用方当时给的，"所见版本"是它当时看到的事实，**照记录**，不按反事实重算。理由与"人的决定照记录"相同：反事实里 Agent 会看到什么、会声明什么，无从得知。
- **状态**（没变 / 已变）是机械判定，在删除后的状态上按 §5.1 的判据重判，结果由那次删除操作里的 `premise.changed` 给出。
- 例：声明所见的值出自一句后来被删的话。按"假如那句话从未存在过"重放，所见版本上的值会是别的；但依赖行是 Agent 看了那个真实的值才写的，所以比较用的是真实的所见值——它已被删除、比不了，标记保持（§5.4）。这是**有意不按反事实算**的一处，写进 `03-deletion.md`。
- 删除不因前提而多删或少删任何值；"不多删""不漏删"两条推论不受影响。"顺序无关"只对数据状态成立；标记在一个角落里可能因顺序不同而多报（§17 第 4 条）。

### 8.5 删除后留下什么

| 留下 | 看得出什么 | 归入 |
|---|---|---|
| `ops/<i>/premises/<j>`、`ops/<i>/premise_covers`、`ops/<i>/premises_cleared` | 某次写入声明过以某张表的某一行、第几号字段、在哪个版本上的值为前提；某次写入清除过前提 | 事件格式 9.2 新增一行；删除预览的"不会删除"里随保留的元数据一并说明 |
| `premise.changed` | 某条声明在哪次操作里变了状态 | 同上 |
| 看不出 | 前提的值、依赖行的值、显式给的或取自依赖行的业务时间 | — |

这些与 9.2 已有的"被引用的源数据与写入的 `seq`"是同一性质（都只是序号）。需要随法务结论一并审（事件格式 9.6 的清单加一项）。若结论是不可保留，做法与 9.2 其他项相同：依赖行被整行隐私删除时，把它的声明块也列进位置列表；不改事件头。

## 9. 决定 7 代价与上限

数值都是初值，随评测与实验 4 调整。

| 项 | 上限 | 超出时 | 理由 |
|---|---|---|---|
| 一个 op 的声明条数 | 16 | `too_large`（`premise_entries`） | 一行的前提超过十几条时，多半是在"把读过的都列上"，那是 §3.1 否决的做法 |
| 一行 / 一个实体被多少条有效声明指向 | 1,000 | **拒绝声明方**：`too_large`（`premise_fan_in`），附目标与当前条数 | 见下 |
| 一行上列出的标记 | 10 条，另给总数 | 截断 | 文本预算 |
| 回执 `premise_affected.rows` | 20 行，另给总数 | 截断 | 与 `derived[]` 的 20 条一致 |

**"有效的声明"**：声明所在的写入已生效（不是候选、待确认）、没被更晚的声明完全取代、没被清除、依赖行未撤销。候选与待确认的写入里的声明不计。

**一行被上千行依赖时，前提变化的代价**：

- 一次改动的额外工作 = 按前提目标查索引 + 对相交的声明各做一次状态更新 + 对"已变"的声明各做一次值比较 + `premise.changed` 里每条约几十字节。与依赖它的**声明数**成正比，与链长无关（§7）。
- 1,000 条声明：事件里约几十 KB，一千次索引更新。量级上与一次派生重算可比，放得进同一事务；具体数字并入实验 4 的写入延迟测量。

**上限为什么落在声明方**：

- 若落在改动方，就是"别人声明得多了，这一行就改不动了"。一个连接实例可以用声明让另一方的写入被拒，这不能接受；也违背"永不阻塞"的取向。
- 落在声明方，被依赖的一方**永远不会**因为别人的声明而写不进去；被拒的一方有明确的出路：不带这条前提再写，或以一个更具体的行为前提。
- **只在声明时检查**，是软上限：之后因采纳候选（候选里的声明随之生效）、撤回一次撤销（依赖行回来）、撤回删除等原因超过上限的，允许存在，不追溯拒绝，也不拒绝做这些事的人。这些操作的发起者不是声明方，拒绝它们就把上限落回了改动方。
- 风险：一个长期存在、被很多行依赖的值（如"时区""目标体重"）会碰到上限，之后的声明被拒。这与 `07-scope-v1.md` 3.2 对大写入作业的处理是同一种取舍（"超限一律 `too_large`……靠放宽阈值规避"）。评测与真实使用里若常见，放宽数值；再不够，改为"超过阈值后对这个目标只留目标级记录、检测时一律按可能受影响"（读取记录的表级记录是同一思路），那是纯增量。

**进不进写入准入的估算**：写入与解决触发的写入进；**隐私删除与撤回删除永远不受这一项影响**。

- 准入估算（`06-derived.md`「刷新范围与写入准入」）在执行前估"这次写入要动多少"。前提这一项 = 被写的各行上有效声明数之和，计入 `estimated_rows`。
- 因为每行的有效声明数在声明时有 1,000 的上限，单个 op 在这一项上的贡献通常有界；准入阈值只要不低于它，就不会出现"单个 op 因前提而超阈值"。阈值随实验 4 定时把这一条写成约束。
- 多个 op 改多行、各有上千条声明时，可能触发 `too_large`（`admission`），按 `suggested_batch` 分批即可——这是准入本来的行为。
- **删除不计**：一次隐私删除可能改动很多行，删除又不能分批；若计入，别人的声明就能挡住被遗忘权。删除与撤回里的前提检测照做，代价并入删除本身。`06-derived.md` 的准入一节要写明准入对 `delete` 是否适用（§16 第 10 条）。

读取一侧：标记读时现算，每行多一次按出处项查 `premise_edges`。逐行读每页的行数有上限（`04-contract.md` 第 13 节：`limit` 上限 200），代价有界；`sql` 的 `marks_summary` 按读到的行版本集合算，与现有标记同一路径。

### 10.2 回执

```ts
interface OpResult {
  // …
  /** 与请求的 premises 一一对应。 */
  premises?: Array<{
    target: TargetRef; fields?: FieldName[];
    ver: Ver;                        // 实际采用的所见版本（兜底时是兜底到的那个）

  premise_covered?: number;
}

interface WriteResult extends CommonResult {
  // …
  /** 这次操作改动的行上，别的行声明过的前提的变化。没有时不给。 */
  premise_affected?: PremiseAffected;
}

interface PremiseAffected {
  count: number;                     // 因本次操作新带上标记的依赖行数
  matched: number;                   // 因本次操作撤掉标记的依赖行数
```

- **请求键**：服务端请求键的规范化包含每条前提解析后的所见版本（§6.3）。
- **回执超出结果预算**时，`premise_affected.rows` 属于可截短的列表（`omitted` 的 `lists`）。

### 10.3 领域错误

判定位置：前提的校验属于"依赖当前状态的校验"（`04-contract.md` 5.4 判定顺序的第 5 步），与 `ref` 目标的校验同处；格式与互斥的检查在第 1 步。

| 情形 | 结果 | 理由 |
|---|---|---|
| 表不存在或在可见范围外 / 字段不存在 | `unknown_table` / `unknown_field` | 已有错误；范围外的表与不存在相同（接入面的决定稿 2.2） |
| 行 / 实体不存在、已被隐私删除，或在可见范围外 | **拒绝**：`not_found`（附 `param`: `ops/<i>/premises/<j>`；被宽限期内的删除去掉时附删除 ID） | 确定性校验。以一个不存在的东西为前提是明显的错（多半是 ID 抄错），拒绝并指明位置比写下一条永远有问题的声明好。与 `ref` 写入时校验目标一致；范围外与不存在报同一个错误，不泄露 |
| 前提目标已撤销（事件类表、无时间表） | **照常写入，立即打标记**（`revoke`） | 行存在过、Agent 读到过，只是之后被撤销——这正是"前提变了" |
| `ver` 不是这个目标的版本 | `invalid_argument`（`not_this_target`） | 已有原因码 |
| `ver` 是历史版本 | `invalid_argument`（`premise_historical_ver`） | §3.4 |
| 没带 `ver`，也没有可兜底的读取 | `read_first` | 已有错误；与写入目标的 `ver` 一致 |
| **`ver` 已过期，所声明的范围在那之后变过** | **照常写入，立即打标记**；回执 `premises[].state: "changed"`，`warnings` 给 `premise_already_changed` | 见下 |
| `ver` 已过期，所声明的范围没变过 | 照常写入，不标 | — |
| 恢复备份或导入之前拿到的 `ver` | 按 `04-contract.md` 第 15 节对 `ver` 的规定：恢复后以恢复点为它读到的位置；导入后不超过导入点的按原操作号（接入面的决定稿 5.3）。再按上两行判断 | 与写入目标的 `ver` 一致 |
| 指向派生表 | `not_in_this_version`（`value`） | §3.4 |
| 指向别的 slot 的表（表可见） | `invalid_argument`（`cross_slot`） | §3.4 |
| 指向本 op 的目标 | `invalid_argument`（`premise_self`） | — |
| 用在带 `revert` 的 op / `revoke` 上 | `invalid_argument`（`premises_with_revert` / `premises_with_revoke`） | §3.5 |
| 用在按来源键的 op 上 | `invalid_argument`（`premises_with_external_key`） | §3.5 |
| 重申、清除的目标行已撤销 | `revoked` | 与 `update` 相同 |
| `valid_at` / `valid_during` 用在非状态类表的目标上 | `invalid_argument`（`not_state_table`） | 已有原因码 |
| `valid_at` 与 `valid_during` 同时给 | `invalid_argument`（`mutually_exclusive`） | 已有原因码 |
| 超过 16 条 | `too_large`（`premise_entries`） | §9 |
| 目标已被 1,000 条有效声明指向 | `too_large`（`premise_fan_in`） | §9 |
| 不带 `set` 的 `update` 也没带 `premises` | `invalid_argument`（`missing`） | 已有原因码 |

**`ver` 已过期时为什么不拒绝**：

| 做法 | 结果 | 问题 |
|---|---|---|
| 拒绝，要求重读 | Agent 重读前提、重算、再写 | 证据（用户刚说的那句话）没有落下；写入被挡。目标行的 `ver` 过期时 saveslot 的做法是记为候选而不是拒绝（K8：版本对不上不覆盖，但也不丢）|
| 记为候选 / 待确认 | 写入不生效，等人处理 | 没有"当前值"可冲突——这是新的一行或与别人无关的改动。为它造一个事项是堆积 |
| **照常写入，立即打标记** | 行写下了，从第一刻起就带 `premise_changed`；回执当场告诉写入方 | 库里出现一条"一出生就带标记"的行 |

选第三种：它与"可疑的进入待确认并标记（永不阻塞）"（`02-integrity-and-records.md`「来源的完整性」）是同一取向；标记对所有读方可见，所以这条行不会被当成正常的行用；写入方在同一个回执里就知道，通常下一步就处理掉。

### 10.4 MCP

**只改 `saveslot_write`，不加工具**（`05-surfaces.md` 第 1 节的工具数不变）。

工具描述（9 节）在 `saveslot_write` 的描述里加一段：

> 写下的内容是根据 saveslot 里别的记录定出来的（按发布日期排的任务、按收入定的预算）时，可以在 `premises` 里列出那些记录和读到它们时的 `ver`。之后那些记录变了，这一行在任何人读到时都会带"前提已变"，指明是哪条记录、在哪次操作里变的；这一行的值不会被改动。读到带"前提已变"的行，核对后需要调整就照常修改并带上新的 `premises`；不需要调整，用不带 `set` 的 `update` 只带 `premises`，表示按现在的前提它仍然成立；不再以任何记录为前提，带 `premises: []`。原因是"追溯修改"或"改了之后的安排"时，按标记给出的那段业务时间读前提，不带时间的读取只返回当前那一段。`premises` 只列真正用到的记录，不要把读过的都列上；用到的是汇总值时，列出它所汇总的那条基础记录。这次写入成了候选或进了待确认时，它只对自己写下的字段声明前提；`premises: []` 不受这一条限制，照样清掉整行。

`saveslot_query` 的描述末尾加半句："……结果里的标记说明这一行的状态（有争议、待确认、前提已变等）。"

参数说明（9.1）加一行：

| 参数 | 必填 | 说明 |
|---|---|---|
| `ops[].premises` | | 这次写的内容是根据哪些已有记录定的：`[{table, row 或 entity 或 entity_key, fields, ver}]`。`ver` 是读那条记录时拿到的，原样带回；`fields` 是用到的字段，说不准就不给。状态类表可加 `valid_at` 或 `valid_during` 指明用到的是哪段时间的值；不给时，这一行自己有日期或时间就取它，没有就是从现在起。`[]` 表示清掉这一行的前提。**这不是 `evidence`**：`evidence` 放用户的话与工具结果，`premises` 指向 saveslot 里的记录 |

| 2 | 5 新增一节、4.1–4.4 | 新事件 `premise.changed`：`targets/<k>` 的 `changed` / `matched` / `repointed`；它在一次操作里的位置；不是头事件 |
| 3 | 6.1、6.8 | 事件类型 `premise.changed`；`range` 取 `whole` / `from_now` / `row_time` / `given`；`state` 取 `current` / `changed`；`reason` 的六个值 |
| 4 | 5.10、5.11 | 重申与清除产生哪些事件；`premise_decls`、`premise_edges` 由什么重建 |
| 5 | 9.2 | 保留的元数据加一行 |

与接入面的决定稿对事件格式的改动核对过，互不冲突：按来源键的 op 不能带前提，所以 `ops/<i>/target` 的 `by_external_key`、`ops/<i>/baseline` 与本稿的前提块不会出现在同一个 op 上；补键的 op（按 `row` 定位的普通 `update`）可以带前提，那边加在 `target` 里的 `key_from` 与本稿的块不同名、互不读取；那边新增的 `ver.basis` 取值 `external_key` 不会出现在前提块的 `ver` 里（前提没有按来源键的写法）；那边"只含按来源键 op 的请求不记请求键"与本稿"请求键含解析后的前提版本"作用在不同的请求上；`write.head` 的 `request` 块新增的 `op_count` 与本稿无关。

**P1 要不要先收 `premises`**：不要。P1 收到 `premises` 报 `not_in_this_version`。开发期间（P1–P4）的日志不承诺兼容（`07-scope-v1.md`「事件格式的冻结点」），所以不存在"P1 写下的行缺声明"的问题。

**测试**（随实现所在的阶段写，`02-architecture.md` §11 的测试矩阵）：

- 重放对拍：`premise_decls`、`premise_edges` 列入"对拍：是"。
- §8.3 的不变式写成性质测试：随机的写入、回退、解决、删除、撤回、重申、清除序列之后，每条仍有效且状态为"没变"的声明，其范围上现在的值等于所见版本上的值。
- "记录的标记变化 = 按判据从线上状态重算"：对每条 `premise.changed`，用一个独立的直白实现重算，与记录比较（与"记录结果 = 参考重算"同一思路）。**参考求值器本身不用扩展**：它算的是值，前提不参与取值。
- 隐私删除只换了给出者、值没变时不打标记；删除之后已变声明的 `since` 指向删除。
- 字面相同的两次重申在前提又变过之后不被当成重放。
- 整库检索：隐私删除到期后，`premise_decls` 里的业务时间检索不到。
- 渲染器测试：`premise_changed` 一定出现在文本里；`retroactive`、`plan_changed` 带区间。

**对范围文档的影响**：机制清单加一项（3.2 或 3.5）；第 1 节的评测范围加上 eval 10；P2 的"解锁"加 10a–10d，P3 加 10e。清单的计数与第 1 节的评测范围在全部决定稿落定后统一重算，本稿不写具体数字。

**工作量**（粗估，未与其他阶段一起重估）：P0 的格式与类型约 0.5 人周；P2 约 1.5–2 人周（含评测夹具与措辞迭代的起步）；P3 约 0.5 人周。

### 13.1 状态类表上的一例（不展开事件）

| 4 | 若第 1 步写的是无时间表上的"本周计划"一行 | 依赖行没有业务时间，范围"从现在起"：`[11-10, ∞)`（`date` 粒度从 `ctx.today` 起） |

| 1 | **事件类表、无时间表上的 `update` 也触发标记**，与纠错影响查询不同 | §5.2：影响查询问过去，前提问现在；出发例子就是 `update` | 改成同一套条件，则本例不触发，机制对"改了主意"类的变化无效 |

## 16. 发现的问题

现有规格之间、或现有规格与本设计之间对不上的地方。本稿没有改规格。

1. **规格里把"依据"当证据、来源或判定理由用的地方**（`05-surfaces.md` 的工具描述与参数说明、`04-contract-types.md` 与 `04-contract.md` 的几处注释、`10-evals.md`、`03-deletion.md`「预览与回执要写明的内容」），落规格时统一改为"证据""来源"或"理由"——留给规格修订。本稿的机制叫"前提"，不与它们重名。
2. **出发例子的前提只在一部分情形下成立。** "读过旧值的 Agent 下次读会看到 `possibly_affected`"：按 `02-integrity-and-records.md`「纠错影响查询 · 什么会触发」，事件类表与无时间表上只有 `correct`、`revoke` 触发，`update` 不触发。用户"改了主意"通常是 `update`，所以在这两类表上读过旧值的一方什么都收不到。这不是规格自相矛盾，但它意味着"现有机制至少能提醒读过的那一方"并不总成立；讲解 `06-read-and-impact.md` 第 9 节的表与规格一致。
3. **`update` 的"`set` 或 `revert`，二选一"与重申、清除冲突。** `04-contract.md` 5.1 的表、`05-surfaces.md` 9.1 的 `ops[].set`（"除 `revoke`、`revert` 外必填"）都要求 `update` 带 `set`。本设计要放宽。
4. **按时刻读的历史在"线上"与"重放"之间是否一致，没有写明。** `03-deletion.md`「删除之后」说版本表里"被删内容所在版本的区间保留、该处内容标'已删除'"；`02-architecture.md` §3 说重放遇到已移除的块"得到的是去掉被删内容的历史状态，不保证等于当时的线上状态，对拍只比较日志末端的状态"；事件格式 5.7 说"重放时遇到 `span` 块已被移除的项：这一项在本事件处不落账"；而 §8 的表里版本表标"对拍：是"。三处合起来看不出：重放之后版本表里那段历史是"区间在、内容标已删除"，还是整格没有；`span` 块被清而值块还在的项，它在线上版本表里那一格的区间又怎么处理。本设计因此不让 `apply` 读历史值（§8.1），但这个问题本身影响 `partially_deleted` 与按时刻读，值得写明。
5. **`flags` 的定义排除了不来自事项的标记。** `02-architecture.md` §8：`flags` 的主键含事项 ID，说明里写"标记都由未决事项得出，基础写入本身不设标记"；§4 的 `flags` 模块只列事项类标记。本设计的标记不来自事项，所以选了读时现算（§15 第 17 条）；若要物化，这两处要改。
6. **`cross_slot` 与 `cross_slot_sources` 并存。** `04-contract-types.md` 第 9 节 `invalid_argument` 的原因码里两者都有；`04-contract.md` 第 10 节 `deletion_preview` 与 `03-deletion.md`「删除的种类」对"源数据不在同一个 slot"用的是 `cross_slot`，`cross_slot_sources` 没有别处引用。本稿对"前提指向别的 slot 的（可见的）表"用了 `cross_slot`；若它专指源数据，需要另起一个原因码。
7. **`possibly_affected` 的可见范围，契约里写了，数据模型里没有明说。** `04-contract.md` 第 7 节写"本连接实例之前读过的版本后来受影响"；`02-integrity-and-records.md`「纠错影响查询」只说"下次相关读取时随结果带出"，没说只带给读过的那个连接实例。本稿按契约理解，并以此作为"为什么需要另一种所有人可见的标记"的理由。
8. **逐行读每页的上限有两个数。** `02-integrity-and-records.md`「读取记录」与 `04-write-and-read.md`「读取记录里记什么形状」写"逐行读每页最多 1,000 行"；`04-contract.md` 第 13 节与 `04-contract-types.md` 1.7 写 `limit` 上限 200。本稿估读取代价时按契约的 200。
9. **范围文档的计数与评测范围写死在文字里**（`07-scope-v1.md` 第 1 节）——留给规格修订，全部决定稿落定后统一重算。
10. **写入准入对 `delete` 是否适用，`06-derived.md` 没有写。** 准入估算说的是"这次写入要动多少"；删除也会触发派生刷新，但删除不能分批。本稿只定了前提这一项不计入删除（§9）；准入整体对删除怎么办要在那一节写明。
11. **"没有可撤回的改动"没有原因码。** `04-write-and-read.md`「撤回某次写入」的表里这一行只写了 `invalid_argument`，其余几行各有原因码或提示。`undo` 一次重申、清除也落在这一行（§6.3），落规格时一并定码。

## 17. 没有核对到的范围

1. **schema 迁移**。`spec/03-data-model/07-schema-evolution.md`、`08-schema-migration.md` 没有读。§5.5 的规则是按 `04-contract.md` 与事件格式里对切换的描述推的：切换时旧版写入"按 `compiled` 转换"之后，出处项的身份（事件、字段 ID、下标）是否保持，`premise_edges` 要不要跟着转换，字段被删、被确定性转换改了类型时前提怎么算，都没有核对。P4 开工前要补。
2. **状态类表的细则**。`spec/03-data-model/05-time.md` 只读了时间类型、粒度与挡点；无值区间与"值实际变化的区间"怎么算，本稿只用了 `02-integrity-and-records.md`、`04-contract.md` 第 4、5 节与事件格式 5.7 里的说法。状态类表上只有 §13.1 的简例，没有逐事件手推，尤其是：依赖行是状态类实体、它的一个贡献被部分回掉时，标记落在哪几段；取自依赖行的范围（`row_time`）在依赖行的区间被后来的写入切开时怎么显示。
3. **冲突与事项**。`spec/03-data-model/09-references-conflict-sync.md`、`01-objects.md` 的「待处理事项」只看了目录与术语表。带 `premises` 的写入成为候选、之后经 `take_candidate` / `confirm` 生效时，"值来源是对原候选贡献的引用"这一点取自 `02-integrity-and-records.md`「写日志」与事件格式 4.3 的例子；多候选并入同一事项、撤回删除后 `rejudged` 的候选各自的声明怎么显示，没有逐条核对。
4. **删除的顺序无关**。§8.4 说标记在一个角落里可能因顺序不同而多报：先删 A、过了宽限期再删 B，与一次删 {A, B} 相比，前者在第二次删除时"所见版本上的值"已被物理删除、比不了，后者在确认时也比不了（它在本次删除的范围内）——推到这里两者一致；但"A 的删除让值变了、B 的删除让值恰好回到所见值，而所见值本身不在被删范围内"的组合没有穷举，改指（§8.3 第 4 步）在两种顺序下的 `since` 是否相同也没有推。需要用性质测试确认，或把"标记不保证顺序无关（只会多报）"写成明确的边界。
5. **恢复流程**。`03-deletion.md`「删除登记」里恢复流程重新生成"删除已确认"事件时，同一操作里的 `premise.changed` 是否满足"重入时重新生成的事件与首次相同"：按 §8.3，检测的输入是日志与被删集合，理应满足；撤标记用到的按时刻读在"恢复出的日志"上是否与首次一致，没有核对。导入（接入面的决定稿 §5）之后 `premise_decls` 的重建按"导出 → 重放"推定成立，没有逐项核对。
6. **CLI**。`spec/06-cli.md` 没有读：人工处理、`saveslot` 的查看命令是否要显示标记与前提，没有核对。
7. **定位与讲解**。`spec/01-positioning.md` 只核对了分工那一句；讲解各章只看了目录与 `06-read-and-impact.md` 第 9 节，§14 的同步清单是按目录列的。
8. **数值**。16、1,000、10、20 与"约几十 KB"都是估计，没有实验支持；前提变化的写入延迟要并入实验 4。
9. **调研材料**。`docs/zh-CN/research/` 没有读；溯源、增量视图维护的文献里是否有现成的"声明式依赖 + 失效标记"做法可借鉴，没有核对。
10. **走查材料**。`process/walkthroughs/` 里的走查没有逐份对照本稿重推。

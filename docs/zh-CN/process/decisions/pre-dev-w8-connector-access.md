## 1. 连接器的定位

- **问题**：规格里"来源连接器"只在 [`../../spec/03-data-model/06-derived.md`](../../spec/03-data-model/06-derived.md)「派生规则与派生缓存」出现一次，没有定义；[`../../spec/01-positioning.md`](../../spec/01-positioning.md)「saveslot 管什么，不管什么」没有提它。读的人分不清：定时把外部系统的数据搬进来的程序是不是 saveslot 的一部分，第三方系统的授权令牌放哪。
- **可选做法**：甲——saveslot 提供连接器的运行框架（调度、重试、令牌保管）；乙——连接器是 saveslot 之外的程序，saveslot 只提供它需要的写入能力；丙——不表态，留给上层产品。
- **决定：乙。**
  1. **连接器**是定时自己运行、把某个外部系统的数据搬进 saveslot 的程序，由官方或开发者按业务各自编写。它不在内核里，也不在第一版里；saveslot 不调度它、不替它重试、不知道它的存在方式。
  2. **它以一个连接实例的身份、经 HTTP 接入面写入。** MCP 面向 Agent，HTTP 面向这类没有 Agent 的程序；两者由同一份操作契约生成（[`../../spec/02-architecture.md`](../../spec/02-architecture.md) §6），连接器能做的事与任何连接实例一样，受 scope 与 slot 范围（§2）约束，读写各自留痕。一次安装（一个用户接一个外部系统）对应一个连接实例，名字建议写成"来源系统 · 连接器"。
  3. **第三方系统的授权令牌由连接器自己保管**，不进日志，不进 saveslot 的任何存储（租户存储、控制面、锚点存储都不存）。saveslot 的控制面只保管 saveslot 自己签发的凭证的哈希。
  4. **连接器不应把第三方令牌、会话 Cookie 之类放进证据。** 证据是内容，原样进日志；saveslot 不识别、不过滤其中的密钥。误放进去的，按普通的隐私删除清除，并应在第三方系统里更换令牌。
  5. **手机或其他设备上的采集程序只能配合服务器模式。** 本机模式只在 unix socket（或回环地址）上监听（[`../../spec/06-cli.md`](../../spec/06-cli.md)「CLI 怎么连 saveslot」「本地服务只供本机访问」），别的设备连不上；这是本机模式的安全边界，不为采集程序开口子。
  6. saveslot 为连接器提供的只有三样，都是通用的写入能力：凭证可限定到 slot（§2）、来源键（§3）、分批写入的幂等（已有）。首次同步很长一段历史数据时超限仍报 `too_large` 并给建议批量（[`../../spec/04-contract.md`](../../spec/04-contract.md) 5.4「写入准入」）；有了来源键，分批重跑不会重复新增。
- **理由**：连接器的难点（各家接口、限流、令牌刷新、增量游标）都是领域内的事，和"具体业务规则与领域计算"同属上层；放进内核会让 saveslot 被某几个来源系统绑住，也会让 saveslot 持有用户在别处的凭证——那是一类新的、后果更重的密钥。甲不选，原因就是这两条。丙不选：不写边界，实现的人会默认把令牌放进 slot 的某张表里。
- **不选的替代**：给连接器单独一种凭证类型。不需要——它与"用户用 Agent 做出来的脚本"在 saveslot 看来没有区别，区别只在授权范围，那由 §2 表达。
- **最小例子**：一个健康类连接器每小时运行一次。它启动时从自己的配置里取出第三方系统的刷新令牌与 saveslot 的静态令牌（`saveslot connect http --slots health` 签发的）；向第三方拉取最近的饮食记录；`POST /v1/writes`，每条记录一个按来源键定位的 op（§3）；看回执的 `status` 与汇总。saveslot 的日志里只有饮食记录与"这次调用"的源数据，没有第三方令牌。

## 2. 凭证可以限定到若干个 slot

### 2.1 问题与决定

- **问题**：scope 只按动作分（[`../../spec/04-contract.md`](../../spec/04-contract.md) 第 12 节），拿到 `saveslot.write` 的连接实例能写所有 slot。第三方的连接器只该碰它负责的那个 slot。内核已经把可见范围实现到 slot 与表两级（[`../../spec/02-architecture.md`](../../spec/02-architecture.md) §4「`ops` 的调用上下文」的 `visibility`），服务层恒传 `all`。
- **可选做法**：甲——维持后续；乙——授权 = 动作 scope × slot 范围，第一版只到 slot 一级；丙——一步做到表级、字段级。
- **决定：乙。** 连接实例的授权 = 四个动作 scope × **slot 范围**。slot 范围取"全部"或"一个 slot 列表"；同一组 scope 对范围内的每个 slot 一样（第一版不支持"A 可写、B 只读"，要这样就签发两个连接实例）。表级与字段级仍是后续。用户会话的范围恒为全部。
- **理由**：缺的只是签发、授权页与事件里的记录，内核的执行路径已经在测试里跑（保证点 5）。丙不选：字段级要动派生表的可见性与读结果的形状，表级要回答"事项、源数据按什么过滤"（它们按 slot 归属，不按表），都不是补几个参数的事。

### 2.2 范围外的 slot 表现成什么

**范围外的 slot，对这个凭证与不存在完全相同。** 具体到错误码，现有规格有一处自相矛盾，这里一并裁定：

- **按名字引用的**（表名、字段名）：不存在与不可见报**同一个错误**——该操作对不存在的名字本来报什么就报什么：`query`、`history`、`write`、`catalog` 报 `unknown_table` / `unknown_field`，`sql` 报 `sql_rejected`（`unknown_name`）。
- **`nearest`（最接近的名字）只从这个凭证可见的名字里取。** 范围外的名字永远不会出现在任何报错、候选、提示里。
- **按 ID 引用的**（行、实体、事项、源数据、草稿、一次读取）：目标在范围外的 slot 里，报 `not_found`，与 ID 不存在相同。
- **按名字或 ID 指定 slot 的参数**（`catalog` 的 `slot`、`sources` 与 `pending` 的 `slot` 过滤、`policy.get`）：范围外的 slot 报 `not_found`（`slot`），与 slot 不存在相同。
- **名字解析只在可见范围内做**：表名"在用户内不重名时可只写表名"改为"在可见范围内不重名"；`ambiguous_table` 的候选、旧名解析（最近 10 个版本内的旧名）同样只看可见范围。否则一个只写 `runs` 的请求会因为范围外另有一张 `runs` 而报歧义，等于泄露了它。
- **写进参数里的行 ID 也一样**：`ref` 字段的值、写入的前提（[`pre-dev-w9-basis.md`](pre-dev-w9-basis.md)）里的行 ID 指向可见范围外的行时，报的与 ID 不存在时相同——`ref` 报 `validation_failed`（`ref_not_found`），前提报 `not_found`。`ref_wrong_table`、`cross_slot` 只在目标可见时才报；否则"这个 ID 在别处存在"就从错误码里漏出去了。行 ID 难猜，但会经共享的日志、截图、别的 Agent 的上下文流出。

这样定的理由：`not_found` 是"按 ID 找不到"，`unknown_table` 是"名字不认识并给出相近的名字"，两者各管一类引用，本来不冲突；矛盾出在「可见范围」一节把名字引用也写成了 `not_found`。附近名对写错名字的模型很有用，不应为了不泄露而整个取消，只需限定候选的取值范围。

### 2.3 各操作怎么受范围约束

可见范围经调用上下文进内核，目录、查询、受限 SQL 的改写、写入都过它（[`../../spec/03-data-model/04-write-and-read.md`](../../spec/03-data-model/04-write-and-read.md)「可见范围」）。逐项：

| 对象 | 规则 |
|---|---|
| 数据目录 `catalog` | 只列范围内的 slot 与表；概况、取值示例、关系只涉及范围内的表（第一版 `ref` 与派生规则都不跨 slot，所以按 slot 过滤后不会露出范围外的名字） |
| `query`、`history`（含 `timeline`、`as_of`、`changes`） | 目标表须在范围内。`changes` 不给目标时是"一张表的变化"，表须在范围内；`since: "my_last_read"` 照旧取本连接实例的读取 |
| 受限 SQL | 语法树里引用的每张表都须在范围内，否则 `sql_rejected`（`unknown_name`）。`marks_summary` 只统计范围内的行。一条 SQL 能否关联两个 slot 的表，规格没有明文（见 §9）；无论那条怎么定，限定范围的凭证只能引用范围内的表 |
| 待处理事项 `pending`、`resolve` | 事项属于某个 slot，按 slot 过滤；范围外的事项 ID 报 `not_found`。回执与读结果里的 `notices`（如 `pending_items`）只算范围内的 |
| 源数据 `sources`、`source_ref`、`deletion_preview`、`delete` | 每条源数据只属于一个 slot，按 slot 过滤；范围外的源数据 ID 报 `not_found`。删除本来就限在一个 slot 内 |
| 读取记录 | 记录照常（记在本连接实例名下）。Agent 经 `history` 能查到"任何连接实例对某个目标的读取"这一条不变，但目标须在范围内；`as_of: {read}` 指向一次范围外的读取时报 `not_found`。`reads.list` 只给用户会话，不受影响 |
| 影响查询 | 写入回执的 `affected_reads` 统计的是对本次所写行的读取，这些行都在范围内，照常给。读结果上的 `possibly_affected` 标记只出现在范围内的行上 |
| `write` | 目标表须在范围内；一次写入只涉及一个 slot，所以整个请求要么在范围内，要么报 `unknown_table` |
| `schema_draft` | 改范围内的 slot：按 `saveslot.schema` 照常。**新建 slot：限定范围的凭证不能做**，报 `insufficient_scope`（`required_scope: "all_slots"`），不论草稿里的 slot 名是否与某个范围外的 slot 重名——两种情形同一个错误，不泄露。**凭证既没有 `saveslot.schema`、又是限定范围的，先报缺 scope**（`required_scope: "saveslot.schema"`）：先查动作、再查范围，与"没有 scope 的操作根本不进内核"的顺序一致 |
| `policy.get` | slot 须在范围内 |
| 导出、对拍、校验、连接实例管理 | 只给用户会话，不受影响；限定范围的凭证本来就调不了 |
| 幂等、限流 | 不变：请求键里本来就有连接实例 |

- **提示**：`notices` 的码表（`pending_items`、`schema_updated`、`migration_progress`、`deletion_overdue` 等，以及之后新增的码）逐个注明"只按可见范围计算"；范围外的 slot 不出现在任何提示里。
- **派生表**：可见当且仅当它依赖的表与字段都可见（已有规则）。第一版禁止跨 slot 的派生规则，所以到 slot 一级时派生表与它的基础表同进同出。
- **历史里的名字**：范围内的行的历史里出现的写入者（连接实例名）照常显示；这些名字不属于任何 slot。
- **范围不改变判定**：冲突、同值、高影响、疑似重复都只看同一 slot 里的数据，范围内外的写入方得到同样的判定结果。

### 2.4 新建 slot 与"之后新建的 slot"

| 范围 | 能否新建 slot | 之后别人新建的 slot |
|---|---|---|
| 全部 | 能（需 `saveslot.schema`） | 自动纳入：范围是"全部"，不是签发那一刻的快照 |
| slot 列表 | 不能 | 不纳入：列表不变 |

不让限定范围的凭证建 slot 的理由：建出来的 slot 不在它的列表里，它自己都看不见；要让它看得见就得改它的范围，而范围签发后不能改（2.6）。"自己建的 slot 自动可见"是一条隐含规则，会让"这个凭证能碰哪些 slot"不能从签发记录一眼看出。做法是由用户会话或范围为"全部"的连接实例先建好 slot，再签发限定到它的凭证。

### 2.5 签发：契约、事件、授权页、CLI

- **契约**（`connections.issue`）：加可选参数 `slots`（slot 名或 `slot_id` 的数组）。不给 = 全部。给了：每个都必须存在（否则 `not_found`（`slot`）），不能是空数组（`invalid_argument`（`empty_slots`））。结果与 `connections.list` 的 `Connection` 加 `slots?`（不给 = 全部），每项给 slot 名与 `slot_id`。
- **事件**：`principal.registered` 的元数据块 `principal`（[`../../spec/09-event-format.md`](../../spec/09-event-format.md) 5.3）加可选键 `slots`：slot ID 的数组，按 ID 升序、不重复。**缺省 = 全部**（缺省字段不编码，所以不限定范围的登记事件字节不变）。

  ```json
  {"principal": "ci_7HQ2…", "kind": "connection", "scopes": ["saveslot.read","saveslot.write"], "slots": ["sl_4KTZ…"], "via": "token"}
  ```

  - **不进事件头。** 事件头"尽量少留"，主体事件是租户级事件、事件头没有 `slot` 字段，这一点不变。slot ID 是 saveslot 分配的不透明标识，满足元数据块的条件（事件格式 1.1），与 `scopes` 放在同一块。
  - 它留下的信息：某个连接实例被授权访问哪几个 slot（只有不透明 ID）。事件格式 9.2「元数据块」的表加一行如实列出。
  - `apply`：`principals` 表（architecture §8「存储格式 v1」）的关键列加"slot 范围"。
- **权威在日志里。** 服务层构造调用上下文时，从 `principals` 取这个主体的 slot 范围，转成 `visibility`：全部 → `{kind: "all"}`；列表 → `{kind: "scoped", slots: [{slot}, …]}`（不往下列表与字段）。控制面只存令牌哈希到主体的对应，不另存一份范围，免得两处不一致。
- **OAuth 授权页**（[`../../spec/05-surfaces.md`](../../spec/05-surfaces.md) 第 15 节）：用户在授权页上给这次接入起名字、选 scope、**选 slot 范围**：一个"全部 slot（含以后新建的）"选项，加现有 slot 的勾选列表。
  - **预选**：客户端在客户端元数据里声明了它要的 slot（按名字）时，预选其中现有的那些；声明的名字里没有对应 slot 的，在页上列为"不存在"，不能在授权页上新建。客户端没有声明时预选"全部"。
  - **范围选择器始终显示**，用户可以改；不改就直接点一次授权，与 scope 预选、名字预填同一种做法（用户最多做选择和一次同意）。
  - **连接器应在客户端元数据里声明它要的 slot**（例如健康类连接器声明 `health`）；这样授权页上的默认就是最小范围。客户端元数据里这一项的字段名不是 OAuth 的标准字段，按 saveslot 的扩展字段写，确切名字实现时核实。
  - slot 范围**不编码进 OAuth 的 scope 字符串**，受保护资源元数据照旧只列四个 scope：slot 名是用户自己的数据，授权结果与令牌响应里不回传 slot 名单；客户端只经 `catalog` 看到被授予的范围内的 slot。
- **CLI**：`saveslot connect <宿主> … [--slots <名字>,<名字>]`。不给 = 全部（本机模式下接的是用户自己的 Agent，沿用现有流程不多一步）。`connect http` 同样接受 `--slots`，这是连接器取得凭证的方式。`saveslot connections list` 多显示一列范围。自检的那次 `catalog` 照常做，它只会看到范围内的 slot。
- **两处的默认一致**：没有指定时都是"全部"。最小范围靠客户端声明（授权页）或 `--slots`（CLI）给出，用户在授权页上看得见、改得了。

### 2.6 范围能否事后修改

**第一版不能，与 scope 同一条规则**：要改就吊销后重签；远程授权的重新授权得到的是一个新的连接实例。事件格式第 10 节已为 scope 变更留了 `principal.scope_changed`，将来开放修改时 slot 范围随它一起改，不另设事件。

- 重签的代价有限：历史里的 actor 不变；来源键的唯一范围是表、不含连接实例（§3.2），换一个连接实例接着同步不会重复新增。
- 不选"只允许追加 slot"：追加也是修改，同样要一条事件、同样要回答"已经发出去的令牌何时生效"，没有省掉什么。

### 2.7 最小例子

用户有 `health`、`ledger` 两个 slot。给健康类连接器签发：`saveslot connect http --name "手环 · 连接器" --slots health`（scope 默认 `saveslot.read saveslot.write`）。这个凭证：

| 调用 | 结果 |
|---|---|
| `GET /v1/slots` | 只列出 `health` |
| `query`，`table: "ledger.expenses"` | `unknown_table`，`name: "ledger.expenses"`，`nearest` 只含 `health` 里的表名（没有相近的就是空数组） |
| `sql`：`SELECT … FROM expenses` | `sql_rejected`（`unknown_name`） |
| `GET /v1/pending` | 只有 `health` 的事项；`ledger` 里某个事项的 ID 报 `not_found` |
| `POST /v1/drafts` 新建 slot `sleep` | `insufficient_scope`（`required_scope: "saveslot.schema"`）：这个凭证本来就没有 `saveslot.schema`，先报缺 scope。若它带了 `saveslot.schema`，报的是 `required_scope: "all_slots"` |
| 用户随后自己建了 slot `sleep` | 这个凭证仍只看得到 `health` |

## 3. 来源键（事件类表与无时间表）

### 3.1 问题与决定

- **问题**：连接器每次同步都会把同一批外部记录再交一遍。事件类表与无时间表上，幂等窗口之外的重复只靠 `duplicate_keys` 发现（[`../../spec/03-data-model/04-write-and-read.md`](../../spec/03-data-model/04-write-and-read.md)「疑似重复」）：它是软判据，每个新增的行生成一个 `flagged` 事项。每小时同步一次，一天就是几百个事项，而且每条记录都真的重复落了一行。"有则写入、无则创建"只有状态类表的 `entity_key` 有。
- **可选做法**：甲——连接器自己先查再写（先按外部 ID `query`，再决定 `insert` 还是带 `ver` 的 `update`）；乙——把 `entity_key` 放开到事件类表与无时间表；丙——这两类表可以声明**来源键**，按它写入时由内核定位并判定。
- **决定：丙。** 事件类表与无时间表可以在 schema 里声明来源键：记录在来源系统里的标识。按来源键写入时，**有则更新、无则新增**。状态类表不开放：它已有 `entity_key`，按时间段赋值的写入与"上次交来的值"如何对应要另行设计。
- **为什么也开放给无时间表**：通讯录、单据明细这类表同样由外部系统反复同步，下面的规则一字不差地适用（规则只用到行、字段与冲突单元，不用业务时间）。明细行随所属单据取日期时，可以做成无时间表，派生规则关联单据表取日期，不必为了能声明来源键而重复一个日期字段。
- **理由**：甲把"查到没有"和"新增"拆成两次调用，两个同步进程并发时照样重复；而且每条记录多一次读取、多一批读取记录。乙不选，见 3.11 的对照。

**名字**：schema 键 `external_key`，写入 op 的定位参数 `external_key`。中文叫**来源键**。英文不用 `source_key`：规格里 `source` 一律指源数据（`sources`、`source_ref`、`op_sources`、`s_…`），`source_key` 会被读成"源数据的键"；`external` 已经在 `external_authority`（外部权威）里表示"saveslot 之外的系统"。

### 3.2 键的声明与唯一范围

```json
{ "name": "meals", "kind": "base", "description": "每餐一行",
  "time": { "type": "event", "field": "eaten_at" },
  "external_key": ["origin", "external_id"],
  "fields": [
    { "name": "origin", "type": "enum", "values": ["band_app", "food_log"], "description": "记录来自哪个系统" },
    { "name": "external_id", "type": "text", "description": "记录在来源系统里的标识" },
    { "name": "eaten_at", "type": "zoned_datetime", "required": true, "description": "用餐时刻" },
    { "name": "energy", "type": "quantity", "unit": "kcal", "min": 0, "description": "能量" }
  ] }
```

| 项 | 规则 |
|---|---|
| 写在哪 | 表上的 `external_key`：字段名数组，1–4 个字段。只能用在事件类表与无时间表上（声明在状态类表、派生表上编译报 `validation_failed`（`external_key_table_kind`）） |
| 键字段的类型 | `text`、`enum`、`integer`。其余类型编译报 `validation_failed`（`external_key_field_type`）：它们的同值要经换算、舍入或时区，不适合当标识 |
| 键字段可不可选 | 都可以。可选时，表里可以有没有来源键的行（由 Agent 按用户的话新增的那些）；必填时，这张表只能按来源键写入 |
| 怎么比 | 同值判据（[`../../spec/03-data-model/10-types-and-units.md`](../../spec/03-data-model/10-types-and-units.md)「同值判据」）：`text` 是 NFC 之后逐码点相同，不去空白、不折叠大小写 |
| **唯一范围** | **按表。** 一张表里，各键字段都有值、且没有让出键的行，键值两两不同。已撤销的行照样占着它的键（3.5），除非它的键已经转给了另一行（3.3）。任何一个键字段为空的行没有来源键，不参与唯一 |
| 键字段不可改 | 键字段只能经 `external_key` 给出（按来源键新增，或给没有来源键的行补一次键，3.3），之后不可改；`set` 里出现键字段且与行上的值不同，报 `invalid_argument`（`key_field_changed`） |
| 不能进字段组 | 键字段不能出现在 `together` 里，编译报 `validation_failed`（`external_key_in_together`）。键字段从不参与同步基线（3.4），放进字段组会让它与同组字段的冲突判定纠缠在一起 |

**为什么唯一范围是表，不带"来源"或连接实例。** 不同来源系统的 ID 会撞（两家都从 1 编号），要靠键里带一个"来自哪个系统"的字段区分，像上例的 `origin`。这个字段由 schema 的作者声明，不由 saveslot 自动加：

- 不按连接实例划分：scope 与 slot 范围签发后不能改，令牌泄露也要重签，重签得到的是一个新的连接实例。按连接实例划分，重签之后同一条外部记录就成了"新的键"，全部重复新增一遍。
- 不由 saveslot 规定一个固定的"来源"字段：只有一个来源的表不需要它；而"来源"取什么值是领域内的事。
- 编译时不强制键里必须有区分来源的字段，但只声明了一个键字段时，编译回执给提醒 `single_field_external_key`（"多个来源系统写这张表时 ID 可能相撞"）。

### 3.3 按来源键写入

```json
{ "ops": [
  { "intent": "update", "table": "meals",
    "external_key": { "origin": "band_app", "external_id": "m-20261110-2" },
    "set": { "eaten_at": "2026-11-10T12:30:00+08:00", "energy": { "value": "650", "unit": "kcal" } } } ] }
```

- **op 的写法**：`external_key` 给出全部键字段的值（缺一个报 `invalid_argument`（`missing`））；意图是 `update` 或 `correct`；**不带 `ver`**（带了报 `invalid_argument`（`mutually_exclusive`））；不带 `row`；**不能带写入的前提**（`premises`，[`pre-dev-w9-basis.md`](pre-dev-w9-basis.md)），带了报 `invalid_argument`（`premises_with_external_key`）。用在没声明来源键的表上报 `invalid_argument`（`no_external_key`）。
- **可以带临时名 `as`**：新增时临时名绑定到新分配的行，命中已有行时绑定到命中的那一行；同一请求里后面的 op 可以用它写 `ref`。"单据 + 明细"两张表都由连接器同步时，一次请求就能写完。这个 op 被跳过（3.5、3.6）时临时名不绑定任何行：后面用它写 `ref` 的 op 若也是按来源键的 op，一并跳过（`skip_reason: "ref_skipped"`）；若是普通 op，按 `ref` 目标不存在报 `validation_failed`（`ref_not_found`）。
- **`insert` 不能带键字段**：`set` 里出现键字段报 `invalid_argument`（`insert_with_external_key`），提示改用 `update` 按 `external_key` 写入。否则同一个键可以被新增两次，"有则更新"就没有唯一的目标。
- **同一请求里同一个键出现两次，整个请求被拒**：`invalid_argument`（`duplicate_external_key`，附两个 op 的下标）。连接器分页重叠时会这样；让后面的 op 看前面的结果，会在同一个冲突单元上出现"一次写入的两个候选"，事项、`take_candidate` 与合并基都没有为它定义。去重在连接器一侧是一行代码。
- **定位**：内核在键索引（3.8）里按键值找行，结果是下表五种之一。

| 找到了什么 | 这个 op 的结果（`outcome`） | 落账 |
|---|---|---|
| 没有 | `created`：新增一行，分配行 ID | 普通的新增：`set` 须带齐必填字段，键字段的值来源是这次写入的证据；照常过疑似重复（`duplicate_keys`）的判定 |
| 有，行未撤销 | `updated` / `unchanged` / `pending`，见 3.4 | 见 3.4 |
| 有，行已撤销 | `skipped`（`revoked`） | 什么都不落，见 3.5 |
| 有，但这个键正被一项宽限期内的删除占着 | `skipped`（`pending_deletion`） | 什么都不落，见 3.6 |

- 行创建之后，照样可以按 `row` + `ver` 写它（Agent 读到这一行后改一个字段），那是普通写入，规则不变。

**给没有来源键的行补一次键**。两种情形：用户先让 Agent 手记了一条，之后连接器才同步到来源里的同一条记录——把来源键补到手记的那一行上，同步就会命中它，而不是再新增一行；或者两行都已在库里（手记一行、同步又新增了一行）——撤销同步来的那一行，再把它的键**转**给手记的那一行。

```json
{ "intent": "update", "table": "meals", "row": "r_M…", "ver": "v41.0",
  "external_key": { "origin": "band_app", "external_id": "m-20261110-2" } }
```

- 写法：普通的 `update`（带 `row` 与 `ver`，可以同时带 `set` 改别的字段），另带 `external_key`。只有这种写法能同时给 `row` 与 `external_key`。
- 条件：这一行未撤销、全部键字段都没有值。行已有键时：与已有的键相同是无操作，不同报 `invalid_argument`（`key_field_changed`）。
- **这个键在键索引里的状态决定结果**（按下表从上往下，取第一条成立的）：

| 键的状态 | 结果 |
|---|---|
| **冻结**：有一项宽限期内的删除，会去掉这个键在任何一行上的贡献（持有它的行，或它的 `key_from` 那一行） | 报 `invalid_argument`（`external_key_in_use`，附删除 ID）。冻结期间按这个键的同步 op 一律跳过（`skipped`，`pending_deletion`，3.6） |
| 没被占用 | 补上 |
| 被一行**未撤销**的行占着 | 报 `invalid_argument`（`external_key_in_use`，附占着它的行 ID——那一行在同一张表里，本来可见）。要转，先撤销它 |
| 被一行已撤销的行占着，而那一行的键是**创建时就带着的**（按来源键新增的行） | **键转到这一行**，被撤销的那一行不再占键。它的键字段的值仍留在它自己行上（键字段不可改），只是不参与唯一、不在键索引里。事件里在这个 op 的 `target` 记 `key_from: <被撤销的那一行的行 ID>`（元） |
| 被一行已撤销的行占着，而那一行的键是**补键得来的**（含转移得来的） | 报 `invalid_argument`（`external_key_not_transferable`，附占着它的行 ID）。**不连环转移** |

- 冻结与"已撤销的行占着"都包括同一请求里前面的 op 刚做的撤销（后面的 op 看得到前面的结果）。
- **为什么不连环转移**：允许 A → B → C 的转移链，删除中间一次补键时就要回答"键回到谁"，链上每一行都可能同时被认为占着键。只让创建时带着键的行让出，转移链长度恒为 1：持有者要么是原行，要么是唯一那一次补键的行。新的明细码而不用 `external_key_in_use`：那个码的改法是"先撤销占着它的行"，这里撤销已经做了也没用；也不用 `external_key_transferred`：那个码说的是"这一行让出过键，不能再重新存在"，是另一件事。
- **为什么删除未决时冻结**：宽限期内删除可能被撤回，也可能到期执行；两种结局下键应当落在不同的行上。冻结期间不转移、不让同步命中，到期或撤回之后只剩一种结局，再按它定持有者。
- 效果：键字段的值作为这次写入的普通贡献落账（`applied`，来源是这次写入的证据），键索引的条目指向这一行；之后键不可改。这一行的同步基线从这次写入开始，转来的键另沿用原行的基线值（3.4）。
- 只能补一次：补上之后，这一行的键不能改，被撤销后也不能再转出去。这条不放松 3.10"键只能加在新字段上"的理由：被补的键字段在这一行上没有值，不存在"隐私删除让它落回一个已被占用的旧值"。
- **不会复活**：键转走之后，同步命中的是补了键的那一行；被撤销的那一行不再被任何同步命中，也就不会因同步回来。

**让出了键的被撤销行，不能再重新存在**。任何会让它重新存在的写入——`undo` 那次撤销、带 `include_later` 的回退连带回掉那次撤销、确认一项这样的待确认回退——在生效时报 `invalid_argument`（`external_key_transferred`，附现在持有这个键的行 ID）。否则它带着同一个键回来，一张表里就有两行同键。冻结期间它仍算让出了键。

**持有者怎么定**（3.8 的键索引照此维护）：一个键在键索引里至多一条，状态是"在"或"冻结"。

1. 没有转移时：持有者是键字段生效值等于这个键、且没有让出的那一行（含已撤销的）。
2. 有转移（某一行的补键带 `key_from: S`）时：补键那次写入的键贡献仍在，持有者是补了键的那一行，S 不占键；那份贡献被删除**执行**去掉之后，持有者回到 S（若 S 的键贡献仍在；S 仍是已撤销的），否则这个键没有持有者。
3. 有一项已确认、未执行的删除会去掉第 1、2 条里任何一份键贡献时，条目"冻结"，持有者仍按删除前的状态算；撤回删除，冻结解除，持有者不变；删除执行，按删除后的状态重算第 1、2 条。
4. 第 2 条里补键的行就是持有者，它的键不能再转（上表末行），所以任何时刻只有"S"与"补了键的那一行"两个候选，规则 2 只选其一。

**转移键与 `undo`、删除**：

| 情形 | 结果 |
|---|---|
| `undo` 那次撤销（键已转出，冻结与否都一样） | 拒绝，`external_key_transferred` |
| `undo` 那次补键 | 来源键字段不进任何回退记录（3.7），回退碰不到键：键留在补了键的那一行。这次补键若没有改别的字段，报"没有可撤回的改动" |
| 隐私删除补键那次写入的证据：宽限期内 | 冻结：不能转移，按这个键的同步被跳过；持有者仍是补了键的那一行，原行仍算让出了键（`undo` 它的撤销照样被拒） |
| 同上：撤回这项删除 | 冻结解除，回到删除前：补了键的那一行持键 |
| 同上：到期执行 | 补了键的那一行失去来源键；持有者回到原行（已撤销，照常占键）。之后的同步命中原行、被跳过；原行是创建时带键的，可以再被转一次；`undo` 它的撤销不再被拒，它带着键回来，补了键的那一行已经没有键 |
| 隐私删除原行得到键的证据：宽限期内 | 同样冻结 |
| 同上：到期执行 | 原行失去键值（或整行删除）；补了键的那一行仍持键。之后补键那次的证据也被删除时，这个键没有持有者 |
| 撤销是人的决定 | 删除重放照记录（03-deletion 偏离一），删除不会让被撤销的原行重新存在 |

### 3.4 "有"的时候：三方比较

连接器没有读过这一行，带不回 `ver`；它知道的只是"来源系统现在说这条记录是什么"。所以判定比的是三样：**上次按来源键交来的值**（基线）、**当前生效值**、**这次交来的值**。

先定三个词（都是机械判定，由内核得出；键字段不在其内，见下）：

- **同步贡献**：按来源键写入给这一行某个字段的一项贡献，不论它当时是生效、佐证、候选还是待确认；以及采纳这样一个候选时搬运出的那一项（`carried` 指向它的）。**不算**的：`take_previous`（回到冲突前）与 `undo` 写回的项——它们是人的处理带出来的值，不是来源系统交来的。
- **已生效的同步贡献**：当前状态为 `applied` / `corroborated`、且**没有被登记为"已被回掉"**的同步贡献。被 `undo` 回掉的同步贡献仍是同步贡献（计入基线值），但不再是"已生效的"（不计入基线位置）；"被回掉的项是否生效以回退记录为准"在这里同样适用。
- **同步基线**，逐字段：
  - **基线值** = 这个字段上最近一项同步贡献的值。这个字段还没有同步贡献时没有基线值。
  - **基线位置** = **这个字段**上最近一项已生效的同步贡献所在的操作号；没有时取这一行得到来源键的那次操作（按来源键新增的那次，或补键的那次）。
  - **转来的键**：补键时键从一行已撤销的行转来（3.3），这一行在补键之后、自己还没有同步贡献的字段上：**基线值沿用原来那一行这个字段上最近一项同步贡献的值**（原行没有时就没有基线值）；**基线位置取补键那次操作**。这一行有了自己的同步贡献之后，照上面两条只看自己的。理由：补键那一刻用户选了保留本地的值，来源若没变就不该把它盖掉（与"用户的改动不会被每次同步盖回去"同一条）；来源变了，补键之后没人再改过这个字段，就生效。删除重放里基线值照 3.9 重算，原行上被删的同步贡献不再算数。按字段取，不按冲突单元取：同一冲突单元里别的字段的同步贡献，不代表这次交来的值看过这个字段上的本地改动。

判定就是现有的判定顺序（[`../../spec/03-data-model/04-write-and-read.md`](../../spec/03-data-model/04-write-and-read.md)「判定顺序」），只换掉两处输入：

| 步 | 普通写入 | 按来源键写入 |
|---|---|---|
| 同值（第 3 步） | 与所见版本上的值比；同值且指了证据是佐证，否则无操作 | **与基线值比**。与基线值相同 → 来源没变：**不论是否指了证据**，当前生效值与它不同时一律是无操作（不重提）；当前生效值也与它相同时，指了证据是佐证，没指是无操作。没有基线值的字段与基线位置上的值比，规则同普通写入（补键的行第一次被同步命中时多半如此；键转来的除外，见上） |
| `ver` 与冲突（第 4 步） | 所见版本 = 带回或兜底的 `ver` | **所见版本 = 这个字段的基线位置**。之后的判据不变：基线位置之后这个字段所在的冲突单元被别的操作改过 → 候选，生成或并入冲突事项；没被改过 → 生效 |

逐种情形（一个字段，上次同步交来 600）：

| 当前生效值 | 这次交来 | 结果 | 说明 |
|---|---|---|---|
| 600 | 600 | 无操作 | 来源没变。最常见的情形，不产生基础写入事件 |
| 600 | 650 | 生效 | 来源变了，本地没人动过 |
| 500（用户在 saveslot 里改过） | 600 | 无操作 | 来源没变。**用户的改动不会被每次同步盖回去** |
| 500（用户改过） | 600，且用 `evidence_by_field` 指了证据 | 无操作 | 同上：与基线值相同，指了证据也不重提 |
| 600 | 600，且指了证据 | 佐证 | 来源没变、本地也没变：这次交来的证据加为来源 |
| 500（用户改过） | 650 | 候选 | 来源变了，本地也改过：不覆盖，记为候选，生成冲突事项 |
| 500，且上一行的 650 候选仍未决 | 650 | 无操作 | 基线值已是 650（候选也是同步贡献）。**同一个候选不会每次同步再并入一遍** |
| 500，650 的冲突已按"保持生效值"解决 | 650 | 无操作 | 同上：基线值是 650 |
| 650（650 的冲突已按"采纳候选"解决） | 700 | 生效 | 采纳时搬运出的那一项是已生效的同步贡献，基线位置前移到那次解决 |
| 500，650 的冲突已按"保持生效值"解决 | 700 | 候选 | 来源又变了，再问一次人 |
| 500，650 的冲突已按"回到冲突前"解决 | 650 / 700 | 无操作 / 候选 | 写回的 500 不是同步贡献：基线值仍是 650，基线位置不动。**用户拒绝过的来源值不会在下一次同步时直接生效** |
| 600（一次同步写下的 650 被 `undo` 回掉） | 650 / 700 | 无操作 / 候选 | 被回掉的 650 仍计入基线值；它不再是已生效的，基线位置回到更早的那次同步，之后有这次 `undo` |

- **意图**：`update` 是默认的写法（来源系统里这条记录现在是这样）；连接器明确知道来源系统把它标成了更正时可以写 `correct`，值生效时照常触发纠错影响查询。新增时意图照记，另记创建标记，与按 `entity_key` 创建实体的做法一致。事件类表与无时间表上 `update` 不触发影响查询（已有规则），所以日常同步不会给读过这些行的任务打标记。
- **内容完全相同时不留任何东西**：全部字段都是无操作的 op，`outcome` 是 `unchanged`，行的 `ver` 不变；这个 op **不进任何事件**，也不为它存源数据（3.8）。一个请求里全部 op 都是 `unchanged` 或 `skipped` 时，这个请求**不追加任何事件**，回执照给。
- **键字段**：命中时键值与行上的相同，是普通的无操作，**不记佐证**，也不参与同步基线。键字段只在得到键的那次写入里有贡献（按来源键新增，或补键）。代价见 3.6：创建这一行的那次写入的源数据被删，键随之消失。
- **处理过的冲突不能撤回重开**：第一版处理事项（含 `keep_effective`）之后，没有办法让事项回到未决。`keep_effective` 不触发写入，没有可 `undo` 的东西；`take_candidate` / `take_previous` 触发的写入可以 `undo`，值回到处理前，但事项保持已解决。由此，用户按"保持生效值"或"回到冲突前"拒绝过的来源值，之后不会被同步反复提出——这正是基线值包含候选的目的；用户改主意要用那个值，直接写入它即可（普通写入，不是同步贡献，基线不变）。
- **冲突事项**：与普通写入相同——目标是（行，冲突单元），一个目标最多一个未决事项，候选并入；三种处理方式不变。候选"所带的 `ver`"是这个字段的基线位置，合并基照常取各候选所带版本中最早的。
- **来源级别**：没带证据时是 `api_call`，级别"Agent 推断"；带证据时按证据种类。第一版冲突一律保持当前值，级别不参与判定。将来开放"外部权威"时由 §4 的规则决定连接器能否声明它。
- **高影响**：事件类表与无时间表上没有覆盖类的高影响；按来源键写入不会进待确认，除非将来 slot 策略指定了额外的高影响表（后续）。

### 3.5 被用户撤销的行不复活

用户说"这条不对，删掉"，Agent 撤销了这一行。下一次同步里这条外部记录还在。

- **已撤销的行仍占着它的键。** 撤销只改"存在"，键字段的值留在行上；键索引包含已撤销的行。唯一的例外是它的键被转给了一行补键的行（3.3）：那之后它不再占键，同步命中的是那一行；它自己也不能再重新存在。
- **命中已撤销的行：这个 op 被跳过**，`outcome: "skipped"`、`skip_reason: "revoked"`，附撤销它的写入号。不新增、不恢复、不记贡献、不存源数据，这个 op 不进任何事件（3.8）；同一请求里的其他 op 照常执行。
- **不报错。** 普通写入写到已撤销的行报 `revoked`，整个请求不生效；那是因为调用方点名了这一行，应该知道它的状态。连接器是整批交来的，不知道其中哪条被用户撤销过；一条被撤销的记录不应让同批的几百条都失败，更不应每小时失败一次。
- **要恢复，由人来**：按行 ID `revert: {undo: n}` 撤回那次撤销（已有规则）。之后的同步按 3.4 继续；撤销与撤回都改过"存在"，它们与每个冲突单元相交，所以恢复之后来源若变了，第一次会成为候选。
- 被跳过的 op 不改变同步基线。

### 3.6 被隐私删除的行

隐私删除的定义是"假如被删源数据从未存在过"（[`../../spec/03-data-model/03-deletion.md`](../../spec/03-data-model/03-deletion.md)「删除结果的定义」）。来源键的值是字段值，是内容：它的贡献被删，键就不在了。

- **物理删除之后，saveslot 不记得这个键。** 键值可能就是用户内容（有的来源系统拿邮箱、手机号当标识），也可能与外部系统里的记录一一对应；留下它或留下它的哈希，都违背"删除后不可比对"（03-deletion「删除之后」：墓碑与删除登记不存任何由内容算出的值，同一内容换个事件重新写入无法按内容识别）。所以**同一条外部记录再次同步进来时，会作为新的一行重新出现**。
- **这一点必须如实告知，而且说两次。** 删除预览与回执在受影响的行有来源键时给提醒 `external_key_resync`："这些行来自外部系统；删除后若连接器再次同步同一条记录，它会重新出现。要彻底忘掉，先在来源系统里删除，或让连接器停止同步它。"物理删除到期、`deletion` 事项关闭时，关闭的说明里再带一次同一条提醒：那之后的第一次同步就会把它写回来，而此时不会再有任何提示。
- **宽限期内不重新写入。** 删除确认之后、物理删除之前，被这项删除从行上去掉的键值仍然占位（涉及转移过的键时冻结的范围更宽，见 3.3）：命中它的 op 被跳过，`skip_reason: "pending_deletion"`，附删除 ID（回执里给，不进事件）。理由有两条：
  - 与请求键同一个口径：已列入待删除的请求键在物理删除前照样参与查重，重发一条刚被删除的写入不会重新写入（03-deletion「撤回与宽限期」）。
  - 撤回要能还原：若宽限期内同步新增了一行，随后用户撤回删除，原来那一行带着同一个键回来，一张表里就有两行同键。占位之后这种情形不会出现。
- **只删了一部分**（删的是某一次同步的源数据，行还在）：按重放规则，那次同步的贡献去掉，字段回到更早的值。下一次同步交来的若仍是被删掉的那个值，它与基线值（剩下的最近一项同步贡献）不同，会再次生效。这与上面是同一件事：saveslot 记不得被删的内容，来源系统里它还在。
- **键的贡献怎么留**：键字段只在得到键的那次写入里有贡献（3.4），所以那次写入的源数据被删时，这一行一定失去来源键。行本身按「行 / 实体的存在」的普通规则判断去留：
  - 按来源键新增的行：每个必填字段要有仍在的贡献。连接器每次交完整记录、没变的字段都是无操作，所以之后的同步多半只给改过的那几个字段留下贡献，创建那次的源数据被删时**这一行通常整行删除**。
  - 这一行还靠别的贡献存在时（之后的同步改过每个必填字段，或 Agent 用别的证据佐证过它们；补键的行本来就有自己的贡献）：它成为一个没有来源键的行，下一次同步会新增另一行。预览在"逐行结果"里写明"这一行将失去来源键"。
  - 不让之后的同步给键字段记佐证来撑住键：那只在每个必填字段都恰好被改过时才有用，却会把键字段带进同步基线与回退记录（3.7），造出同一键两行的路径。

### 3.7 与已有机制的关系

| 机制 | 关系 |
|---|---|
| `duplicate_keys` | 互不替代，可以同时声明。来源键回答"是不是来源系统里的同一条记录"，是硬的定位；`duplicate_keys` 回答"两行是不是记重了"，是软的提醒，跨来源也管用（Agent 按用户的话记了一餐，连接器又同步来同一餐）。按来源键命中已有行不是新增，不判疑似重复；按来源键新增的行照常判 |
| 幂等键 | 来源键本身就让重发幂等：同样的内容再交一遍，得到的是 `unchanged`。所以**只含按来源键 op 的请求不计算服务端请求键**，不论在不在窗口内，重发都逐条三方比较。显式的 `idempotency_key` 照样可用（3.8）。含普通 op 的请求照旧计算请求键 |
| 版本标记 `ver` | 按来源键写入不带。所见版本由内核取基线位置，记进事件（`ver.basis: "external_key"`）。回执照常给出行 ID 与 `ver`，但回执里的 `ver` 对按来源键的后续写入没有用处 |
| `ver` 的兜底 | 不适用：不查读取记录。没读过也不报 `read_first` |
| 冲突判定 | 判据不变（K8），只是所见版本的来历不同。对称性那条性质说的是"两次带同一个 `ver` 的写入"；按来源键的写入所见版本由内核按日志位置取，同一租户写入串行，结果只取决于日志 |
| 来源级别 | 见 3.4；不参与第一版的判定 |
| 回退 | `undo` 一次按来源键的更新：照常。被回掉的项仍是同步贡献，基线值不变，所以来源没变时同步不会把它再写回来；它不再是已生效的同步贡献，来源变了时成为候选（3.4）。目标是创建那次写入时照旧报 `undo_target`，用撤销。**来源键字段不进任何回退记录**（`undo`、`take_previous` 列项时跳过它们）：键在得到之后不可变，没有可回退的东西；写回项因此从不触及键字段，"撤回一次撤回"也造不出两行同键 |
| `ref` | 别的行可以引用按来源键创建的行（用行 ID），同一请求里也可以用按来源键 op 的临时名 `as`，新增与命中都绑定（3.3） |
| 导入查重（positioning「后续规划」） | 那一条说的是"同一文件的同一批 op 再次导入"。有来源键的表不需要它；没有外部标识的文件导入仍是后续 |

### 3.8 事件里怎么记，`apply` 怎么做

**键值不进事件头，也不进元数据块、不进 path。** 它是内容。它出现的地方只有键字段自己的数据块，与任何字段值一样记来源、在级联范围内。

**什么进事件**：一个按来源键的 op 只有在它留下了东西（新增，或命中且至少一个字段不是无操作）时才进事件；`unchanged` 与 `skipped` 的 op 不进任何事件，只出现在回执里。一个请求里全部 op 都是 `unchanged` / `skipped` 时，整个请求**不追加任何事件**——没有逻辑写入头、没有源数据、没有请求键。

| 事件 | 改动 |
|---|---|
| `write.head` 的 `request`（元） | 加 `op_count`：请求里 op 的总数。`ops/<i>` 的 `i` 是 op 在请求里的下标，没进事件的 op 留空号；op 的个数由 `op_count` 给出，不再由 `ops/<i>/target` 的个数得出 |
| `write.head` 的 `ops/<i>/target`（元） | 加 `by_external_key: true`；`row` 是定位或新分配的行 ID；`created` 照旧。补键时键从已撤销的行转来，另带 `key_from: <那一行的行 ID>` |
| `write.head` 的 `ops/<i>/target.ver` | `basis` 加取值 `external_key`；`op` 是这个 op 涉及的字段里最早的基线位置。新增时没有 `ver` |
| `write.head` 的 `ops/<i>/baseline`（元） | 逐字段的基线位置：`{"f2": 30, "f3": 50}`（字段 ID → 操作号）。只含操作号，判定与删除重放用它（3.9）。新增时没有 |
| `write.head` 的 `ops/<i>/set/<键字段ID>`（数） | 键的原始值。只在得到键的那次写入里记（新增，或补键）。来源：这个 op 的全部证据 |
| `write.head` 的 `ops/<i>/noop`（元） | 照旧列无操作的字段 ID；命中时键字段也列在这里 |
| `write.head` 的 `request_key`（数） | 只含按来源键 op 的请求不记（3.7）。含普通 op 的请求照旧 |
| `write.base` 的 `fields/<键字段ID>/0`（数） | 只在得到键的那次写入里有，`applied`。`sources/…` 照旧 |
| `source.recorded`（`api_call`） | 粒度不变：没带证据时**每个在事件里留下了东西的 op 各一条**，`request` 数据块是这个 op 本身（无操作字段的值照旧不记，只留字段名），`target.op_index` 指向它。没进事件的 op（`unchanged`、`skipped`）不存。请求块里含 `external_key` 的值，随这条源数据删除 |
| `schema.compiled` 的 `compiled` | 表加 `external_key`：字段 ID 数组（事件格式第 7 节） |
| `deletion.confirmed` / `deletion.cancelled` | 不加块。键索引的变化由结果里键字段的值推出 |

- **没变的同步不留东西**：每小时同步几百条没变的记录，不应每次留下一条逻辑写入头、一个含全部记录内容的请求键与一批只有字段名的源数据。不留事件，也就没有一个"随别的记录的证据才删得掉"的请求键，没有"这条记录在删除之后又被送来了"的关联元数据（被跳过的 op 命中的是哪一行，只在回执里出现），也不用为"什么都没变"存源数据。
- **`api_call` 照规格现行的粒度**：没带证据时每个在事件里留下了东西的 op 各一条，只含该 op（04-write-and-read「证据」）。一个来源键对应来源里的一条记录，删掉一条同步来的记录的源数据，只去掉这条记录的贡献，不牵连同批的别的记录。本稿只多一条：没进事件的 op 不存——源数据是贡献的来源，没有贡献就没有东西需要它。调用方显式带的证据照存（证据是资产），没被任何进了事件的 op 引用时回执照常给 `evidence_unreferenced`。
- **"`write` 总有源数据"改写为"产生事件的 `write` 总有源数据"**（事件格式 5.1）。只含没变与被跳过的 op 的请求不产生事件，这一句对它不适用；K4（每次基础写入都有源数据）不受影响。
- **显式幂等键**：调用方给了 `idempotency_key` 且请求产生了事件时，照旧记 `idempotency`（键与请求内容的指纹）。指纹按整个请求体算，含没进事件的 op 的内容；它只随这次请求自己的证据删除，属于事件格式 9.5 的已知边界。连接器用来源键就已幂等，一般不必再给显式幂等键；9.5 写明这一点。请求没产生事件时，显式幂等键不被记下，重发按来源键重新判定。
- **含普通 op 的请求**：照旧计算服务端请求键，按原始请求体算，其中按来源键 op 的内容同样属于 9.5 的已知边界。连接器把按来源键的 op 与普通 op 分开请求即可避开。
- **`apply` 不做定位。** 行 ID 是 `write` 在写入时定位好、记在事件里的；`apply` 照事件里的行 ID 落账（"`apply` 只照事件里记下的结果做"，architecture §3）。
- **键索引**是 (b) 类物化状态，新增一张表 `external_keys`：`(表 ID, 键值…) → 行 ID`，另有一列状态（在 / 被待执行的删除占位，后者记删除 ID）。`apply` 按确定的规则维护，不含判定：
  - 一行各键字段的生效值变了（新增、补键、删除结果、撤回结果、切换）→ 按新值改这一行的条目；撤销不动条目。
  - 补键带 `key_from` → 条目改指补键的这一行，`key_from` 那一行标为"已让出"。
  - `deletion.confirmed` 的结果去掉某一行上这个键的贡献（持有者的，或持有者的 `key_from` 那一行的）→ 条目转为"冻结"，记删除 ID，持有者不变；`deletion.cancelled` → 转回"在"；`deletion.executed`（墓碑）→ 按 3.3"持有者怎么定"重算：去掉的是补键那次写入的键贡献时，条目指回 `key_from` 那一行（它的键贡献仍在时；它仍是已撤销的，照常占键），否则去掉条目。导入时对占位删除补的墓碑（5.6）走同一条。
  - 它由内容得出，列入明文残留清单的"物化状态"一行；对拍：是。
- **重放一致**：定位的结果在事件里，所以从空存储重放、在另一个后端重放，每个进了事件的 op 落到同一行；键索引由同样的事件得出同样的内容。
- **导出重放**：包含待删除内容的导出，重放后键索引与线上相同。带"待删除"占位的导出，键值不在文件里，重放后没有占位条目——这与占位导出"无法再撤回那次删除"是同一个例外（architecture §3「导出里的两种占位」），撤回不了，也就不会出现 3.6 要防的两行同键；§5 的导入对占位删除直接补墓碑，结果一致。
- **第一版就进规则版本 1**：同步基线与定位是机械判定，随 P2 实现，属于第一版发布时的规则版本。

### 3.9 删除重放要补的规则

来源键让「重放规则」（03-deletion）多出几样要说清的东西。它们由"定义 + 两条原则"得出，落规格时写进重放规则的表与参考求值器：

| 项 | 规则 | 理由 |
|---|---|---|
| 定位的结果（这个 op 落到哪一行） | **照记录**，不重新定位 | 行 ID 是不透明标识，记在元数据块里；重新定位会让一次删除把后来的同步改写到另一行上 |
| 基线位置（所见版本） | **照记录**（`ops/<i>/baseline`），与兜底取得的 `ver` 同样处理 | 它是写入时的日志位置，不含内容 |
| 同值（与基线值比） | **重算**：基线值取删除后仍在的、这次写入之前最近一项同步贡献的值。原本是无操作的保持无操作（已有限定） | 原则 ②；基线值所出自的贡献被删时，"与它相同"不再成立 |
| `ver` 冲突 | 照已有规则在删除后的状态上重判，所见版本用记下的基线位置 | 已有 |
| 转移键（`key_from`） | **照记录**：补键那次写入的键贡献仍在，键就在补了键的那一行；它被删除执行去掉后键回到 `key_from` 那一行，宽限期内冻结（3.3）。被撤销的那一行的撤销是人的决定，照记录 | 与定位结果同理；转移链长度恒为 1，键索引由此至多一行持有一个键 |
| 键字段的贡献、行的存在、首次创建标记 | 已有规则直接适用：得到键的那次写入算给出了键字段（与"按 `entity_key` 定位的写入算给出了键字段"同一句话） | 03-deletion「重放规则 · 行 / 实体的存在」 |
| 没进事件的 op（`unchanged`、`skipped`） | 不重放：日志里没有它，也没有它的值。删除不会让一个当时没变或被跳过的 op 事后生效 | 见下 |

**这是定义之外要写明的一处偏离**。按"假如被删源数据从未存在过"，一个当时命中已撤销行而被跳过的 op，在删掉创建那一行的源数据之后本应新增一行；但日志里没有它。03-deletion「删除结果的定义」偏离一里的"原本是无操作的字段保持无操作"扩成"**写入时没有留下值的部分保持原样：无操作的字段、没进事件的 op**"，参考求值器与性质测试照此写；删除预览如实列出（"这一行的来源全部被删；之后连接器交来的记录当时被跳过，不会补回"）。

"已经生效过的写入保持生效"（偏离二）照常适用。**这一节需要推演验证**：把一组"同步 → 用户改 → 同步 → 删其中一条源数据 → 撤回"的场景手推一遍并转成参考求值器的固定用例，再落规格（见 §10）。

### 3.10 schema 变更

| 改动 | 改动码 | 规则 |
|---|---|---|
| 新表带 `external_key` | 随 `add_table` | 自动（属于新增基础表） |
| 给已有的表加 `external_key` | `add_external_key` | **键字段必须是同一份草稿里新增的字段**（因此现有的行在这些字段上都没有值，键索引从空开始）。只改元数据；要确认。键字段是已有字段时编译报 `validation_failed`（`external_key_existing_field`） |
| 去掉 `external_key` | `drop_external_key` | 只改元数据；要确认。键索引清空；键字段变回普通字段，值留在行上，不再不可改 |
| 换一组键字段 | `change_external_key` | **不支持**（`not_in_this_version`）。做法：一份草稿里去掉旧键、新增字段并声明新键 |
| 键字段放进 `together` | — | 编译报 `validation_failed`（`external_key_in_together`），见 3.2 |
| 从未被写入、没人在用的表上增删改 `external_key` | `add_external_key`、`drop_external_key`、`change_external_key` | **自动生效，归入 `restructure_unused`**（与这类表上的其余结构改动同一条规则，见 schema 易用性的决定稿 [`pre-dev-w11-schema-capacity-evals.md`](pre-dev-w11-schema-capacity-evals.md)）：表里没有行，键索引是空的，键可以加在已有字段上，也可以换一组字段。上面三行的限制只对写入过的表成立 |
| 删键字段 | `drop_field` | 仍被 `external_key` 用到时编译失败（`still_referenced`）；同一份草稿里一并去掉键时可以 |
| 键字段改名、改说明、枚举加值 | 已有的码 | 照已有规则 |
| 键字段改类型、收紧约束 | `change_type`、`tighten_constraint` | 不支持（`not_in_this_version`）：转换后的值可能相撞 |

- **为什么键只能加在新字段上**：键字段若有历史，一次隐私删除可能让它落回更早的值，而那个值此时可能已被另一行占用。这与"键不可改、`rekey` 后续"是同一个原因（[`../../spec/03-data-model/05-time.md`](../../spec/03-data-model/05-time.md)「按 `entity_key` 写入」）。键字段从声明那一刻起只经 `external_key` 给出、不可改，每一行的键要么是它唯一的那个值，要么没有。
- **为什么写入过的表上都要确认**：默认 slot 策略里自动生效的改动是固定的几类（[`../../spec/03-data-model/01-objects.md`](../../spec/03-data-model/01-objects.md)「slot 包含什么」），取值写在建 slot 的策略事件里。不为来源键新增类别；从未被写入的表上的改动归入已有的 `restructure_unused`。
- 带旧 `sv` 的写入：照收（按当前定义校验）。
- 切换时键索引按新版表重建；迁移不改行 ID。

### 3.11 与 `entity_key` 对照：为什么不直接复用

| | 状态类表的 `entity_key` | 事件类表、无时间表的来源键 `external_key` |
|---|---|---|
| 是什么 | 实体的自然键，用户认得（预算的类别） | 记录在外部系统里的标识，用户通常不认得 |
| 键字段 | 必填 | 可选或必填；表里可以有没有键的行 |
| 谁按它写 | Agent：不知道 `entity_id` 时按键定位 | 连接器：没读过这一行 |
| 存在时的 `ver` | 照常要带或可兜底，没有就 `read_first` | 不带；所见版本取同步基线 |
| 同值比什么 | 所见版本上的值 | 上次按来源键交来的值 |
| 撤销之后再按键写 | 撤销是无值区间，再写就是填上它：**按设计会恢复** | 命中已撤销的行被跳过：**不复活** |
| 写错键 | 回执列出已有的键，提醒是不是写错了 | 不列：外部标识没有"相近"可言，列出来也等于把别的记录的标识交给写入方 |
| 能否事后增删改 | 都不支持 | 可加在新字段上、可去掉；没有键的行可以补一次键，键被已撤销的行占着时转过来 |

不复用的原因是中间四行：把 `entity_key` 原样放开到这两类表，连接器要么每条记录先读一次（否则 `read_first`），要么靠兜底拿到一个与"来源变没变"无关的版本；撤销后再同步会把行写回来。把这四行的行为都改掉，剩下的只是名字相同，反而让两种表上同名的键有两套语义。

### 3.12 批量写入的回执

- 每个按来源键的 op 的 `OpResult` 加 `outcome`：

  | `outcome` | 含义 | 带什么 |
  |---|---|---|
  | `created` | 新增了一行 | `target.row`、`ver`、逐字段结果 |
  | `updated` | 至少一个非键字段生效（可能另有字段成了候选） | 逐字段结果 |
  | `unchanged` | 全部字段无操作 | 只有 `target` 与原 `ver`，不列逐字段结果 |
  | `pending` | 没有字段生效，有字段成了候选或进了待确认 | 逐字段结果 |
  | `skipped` | 命中已撤销的行，键被宽限期内的删除占着，或用了一个被跳过的 op 的临时名 | `skip_reason`（`revoked` / `pending_deletion` / `ref_skipped`）；`revoked` 时 `revoked_by`，`pending_deletion` 时 `deletion`，`ref_skipped` 时那个 op 的下标。这几项写入时从当前状态取 |

- `WriteResult` 加 `external_key_summary`：`{created, updated, unchanged, pending, skipped}` 五个计数，只统计按来源键的 op。
- `status` 的规则不变：有任何字段成了候选或进了待确认是 `pending`，否则 `saved`。`skipped` 不影响 `status`，另给提醒 `external_key_skipped`（列出被跳过的 op 下标）。
- **幂等重放的回执**按日志重建。进了事件的 op（`created`、`updated`、`pending`）的结果从 `write.head` 的 `target` 与 `write.base` 得出；没进事件的 op（`unchanged`、`skipped`）日志里没有，重放回执里省略并标明：这些下标只给 `op_index`，`omitted[]` 加 `"unrecorded_ops"`，`external_key_summary` 里这两项的计数也不给（同由 `unrecorded_ops` 标明）。不按当前状态重算：那会让同一请求的两次回执不同。只含按来源键 op 的请求只有带显式幂等键时才会被重放（3.7）。

## 4. "外部权威"级别由凭证授予

- **问题**：来源级别 `external_authority` 是保留值，第一版不开放（[`../../spec/03-data-model/04-write-and-read.md`](../../spec/03-data-model/04-write-and-read.md)「来源级别」）。声明级别现在由写入方按证据段自己填。"外部权威"将来参与冲突裁定，若也由写入方自报，任何连接实例都能给自己的值加上最高级别，压过用户的原话。
- **可选做法**：甲——开放时再说；乙——现在只定"谁能声明"这一条规则，不开放；丙——现在就开放并定裁定细则。
- **决定：乙。只定规则，不开放。** 将来开放 `external_authority` 时：
  1. **能否声明这个级别，由连接实例被授予的权限决定**；授予只能由用户会话在签发时做，写入方不能自报，也不能由别的连接实例转授。
  2. **没被授予而声明了它，整个请求被拒**，不静默降级成"Agent 推断"。静默降级会让连接器以为自己的值带着权威级别。
  3. **授予记在主体登记事件里**，与 scope、slot 范围同处一块（元数据）；级别照旧按证据段记在源数据事件里。这样重放与审计时，"这条源数据的级别是不是由有权的主体声明的"可以只凭日志核对。
  4. 授予的形式（一个新的 scope，还是连接实例上单独的一项）、能否按 slot 分别授予、凭证被吊销后它声明过的级别在裁定时还认不认、与字面命中的关系，都属于**裁定细则，仍然后续**，随系统裁定一起定（[`../../spec/08-open-questions.md`](../../spec/08-open-questions.md)「按来源级别的系统裁定」）。
- **第一版的行为不变**：声明 `external_authority` 一律报 `not_in_this_version`；事件里不出现这个取值。
- **理由**：这条规则不需要现在实现，但需要现在写下：§1 说连接器以连接实例的身份接入，§3 让它成为事件类表与无时间表上的常规写入方，读规格的人自然会问"它的数据算不算权威"。答案是"由用户在授权时决定，不由它自己说"。丙不选：裁定细则牵涉秩表、字面命中、重判，第一版不做系统裁定。
- **最小例子**（开放之后的样子，不是第一版）：用户给银行流水连接器签发凭证时勾选"可声明外部权威"；它写入的证据段带 `level: "external_authority"`，被接受。另一个没被授予的连接器带同样的 `level`，请求被拒。

| `spec/03-data-model/04-write-and-read.md` | 「来源级别」 | 加上面第 1–3 条 |

## 5. 导入：只支持导入到空租户

### 5.1 问题与决定

- **问题**：第一版只有导出（[`../../spec/04-contract.md`](../../spec/04-contract.md) 第 17 节）。不做导入的理由是两件事没有答案：凭证与主体怎么对应；怎样与已有数据合并（[`../../spec/07-scope-v1.md`](../../spec/07-scope-v1.md) 第 5 节「把日志装回去」）。结果是"数据可在本地与托管之间双向迁移"第一版只有一半。
- **可选做法**：甲——维持只有导出；乙——只支持把一份导出装进一个**空租户**；丙——做带合并与主体映射的完整导入。
- **决定：乙。** 做"把一份导出装进一个空租户"。导入的主体一律置为停用，凭证重新签发。
- **理由**：两件难事都能绕开。合并：目标是空的，没有可合并的东西。主体对应：不对应——原有主体全部停用，历史里的 actor 原样保留，新凭证由用户在目标处重新签发。"导出 → 向空存储重放 → 对拍"本来就是第一版的测试（architecture §11「导出重放」），乙是把这条测试路径加上校验与收尾，做成用户能用的操作。丙不选：合并要回答两条日志的 `seq` 怎么交错、同名 slot 怎么办、两边的删除登记怎么并，那是多节点的问题。

### 5.2 "空租户"的定义

一个租户是空的，当且仅当同时满足：

1. 它的日志里**只有一条事件：`tenant.genesis`**。由此：没有签发过任何连接实例（签发是日志事件）、没有 slot、没有源数据、没有删除。
2. 锚点存储里这个租户**没有删除登记、恢复次数为 0、没有"恢复进行中"标记、没有"导入进行中"标记**。

读取记录、兜底用的 `last_read` 等 (c) 类状态不看：它们可以有内容（用户查过一次目录），导入时一并丢弃。不满足时报 `invalid_argument`（`tenant_not_empty`）。

要求"空"而不是"还不存在"，是因为发起导入的人要先有一个用户会话，而有用户会话时租户已经建好（本机是 `saveslot init`，服务器模式是建账户时）。

### 5.3 导入做什么

导入是一个管理类操作，只给用户会话。输入是一份导出（一个文件，或按 `after` 续传切出的几段、按顺序给出）。**整体要么完成、要么目标租户保持为空**。锚点存储与租户存储是两个存储，没有共同的事务，所以换入与重建锚点之间靠一个与恢复流程同形的"导入进行中"标记重入：

| 步 | 做什么 |
|---|---|
| ① 校验文件 | 见 5.4。边读边校验，任何一处不过就停 |
| ② 重放到暂存的存储 | 新开一份租户存储（不是目标租户现有的那份；按导入 ID 命名）。**逐事件原样追加并交给 `apply`**：事件头的字节与导出里的一致，内容块按导出里的三种状态落（在、已移除、待删除占位）。这就是 K12 说的"从空存储按顺序把日志交给 `apply`" |
| ③ 收尾事件 | 在暂存的日志末尾追加一条 `tenant.imported`（见下），再对占位的待删除项补墓碑（5.6） |
| ④ 置标记 | `beginImport(tenant, importId)`：在锚点里置"导入进行中"标记（带导入 ID）。置标记时再核对一次 5.2 的空租户条件 |
| ⑤ 换入 | 把暂存的存储换成目标租户的存储，丢弃目标租户原来的那份（里面只有它自己的创世事件）。换入本身是一步原子操作（本机：目录改名；服务器模式：租户目录里存储指针的一次更新） |
| ⑥ 重建锚点并清标记 | `endImport(tenant, importId, {deletions, highWater, restoreCount})`：一次落盘写入由日志得出的删除登记、高水位与恢复次数（5.5），并清掉标记。之后对外服务 |

**重入**：打开租户时，`openTenant` **最先**看"导入进行中"标记（排在"恢复进行中"标记之前）。标记在：

- 租户存储里**没有** `tenant.imported`（崩溃在 ⑤ 之前）→ 回滚：丢弃按导入 ID 命名的暂存存储，`abortImport(tenant, importId)` 清标记；租户仍是空的，可以重新导入。
- 租户存储里**有** `tenant.imported`（崩溃在 ⑤ 与 ⑥ 之间）→ 接着做 ⑥，然后照常打开。

判据只看"有没有 `tenant.imported`"，不比对导入 ID：目标租户在导入前只有创世事件，标记在期间又不接受别的导入，存储里出现的 `tenant.imported` 只能是这一次的。导入 ID 只用来给暂存存储命名、与锚点标记配对，不进事件。

标记在期间租户不对外服务（5.9）。没有这个标记时，⑤ 之后、⑥ 之前的崩溃会让租户既不空、锚点又对不上：日志末端高于锚点里的高水位不是问题，但恢复次数仍是 0，下一次真正的恢复会把它加到 1，与导入后已发出去的 `ver` 重号；反过来先重建锚点再换入，崩溃后日志末端低于高水位，会被当成备份回退走恢复流程。崩溃在 ④ 之前留下的暂存存储没有对应的标记，打开租户时一并清掉（与对拍的临时存储同一种做法）。

**不逐条重新执行契约操作**（不是把每条写入重新 `write` 一遍）：那样会重新判定、重新分配 `seq` 与 ID，得到的不是同一条日志，`verify` 也对不上原来的链。

**新事件 `tenant.imported`**（头事件，`actor` 是发起导入的用户主体，由本事件登记——与创世事件登记用户主体同一种做法）：

| 位置 | 内容 |
|---|---|
| 事件头特有 | `node_id`（新生成，之后的事件身份用它）；`restore_count`（导出清单里的恢复次数加 1）；`imported_upto`（导入的最后一条事件的 `seq`）。本事件的 `seq` = `imported_upto` + 1 |
| `tenant`（元） | `{"tenant_id": <目标租户的 ID>, "previous_tenant_id": <导出里的租户 ID>, "storage_format": …, "event_format": …}` |
| `user`（元） | `{"principal": <发起导入的用户主体 ID>, "kind": "user"}` |
| `export`（元） | `{"exported_at": <清单里的导出时刻>, "pending_deletions": "placeholder" \| "included"}` |

`apply`：登记新的用户主体；**把此前登记过的全部用户主体与连接实例置为停用**（`system` 除外）；记下当前恢复次数与租户 ID。事件身份的约定（事件格式 2.2）改为"它之前最近一条 `tenant.genesis`、`tenant.restored` 或 `tenant.imported` 的 `node_id`"。

- **停用**是主体的一种新状态（`disabled`），与吊销并列：吊销是用户对某个连接实例做的决定，停用是导入带来的、对导入前全部主体的统一处置。停用的主体不能认证（目标处的控制面里本来也没有它们的凭证），第一版不能恢复。它们写过的数据 `actor` 不变，名字照旧显示、标"已停用"；它们发起而未处理的事项照常保留，由用户会话或新签发的连接实例处理——与吊销之后留下什么是同一套（contract 第 12 节）。
- **恢复次数加 1**，是为了让导入前发出去的事项版本一律对不上（报 `confirmation_mismatch`），并让导入前的 `ver` 能被认出来。签名句柄（`dc_`、`cur_`）另因签名密钥与租户 ID 不同而失效。
- **导入前的 `ver` 按原操作号判**：当前恢复次数来自 `tenant.imported`（之后没有恢复过）时，恢复次数比它小 1 的 `ver`：操作号不超过 `imported_upto` 的，按它自己的操作号判冲突；超过的（源头在导出之后发出的）按 `imported_upto` 当作所见位置。理由：恢复时旧 `ver` 的操作号可能指向丢失的那段时间线，只能保守地挪到恢复点；导入没有丢失的时间线，`seq` 不超过 `imported_upto` 的事件在两边逐字节相同，旧 `ver` 的含义是确定的。把它一律挪到导入点，会把源头在那之后、导出之前的改动静默合并掉。
- 用一种新事件，不复用 `tenant.restored`：恢复不换租户、不换用户、不停用主体，`verify` 对两者的检查也不同（恢复说明一段 `seq` 空档，导入没有空档）。

### 5.4 校验与失败

| 校验 | 不过时 |
|---|---|
| 清单：`saveslot_export` 与 `event_format` 是本版本认识的；第一段没有 `after`，后续各段的 `after` 等于前一段的 `upto` | `import_rejected`（`unsupported_format` / `not_from_start` / `segment_order`） |
| 第一条事件是 `tenant.genesis`，`prev_hash` 是 64 个 `0` | `import_rejected`（`not_from_start`） |
| 事件头链：逐行对事件头取哈希，核对下一行的 `prev_hash`；`seq` 递增，空档必须由随后的 `tenant.restored` 说明 | `import_rejected`（`chain_broken`，附 `seq`） |
| 内容校验和：每个 `{"v", "sum"}` 核对；占位与已移除的块没有可核对的东西 | `import_rejected`（`checksum_mismatch`，附 `seq` 与 `path`） |
| 条数与末尾：事件条数等于清单的 `events`，最后一条的 `seq` 等于 `upto` | `import_rejected`（`incomplete`） |
| 重放：`apply` 遇到不认识的类型或版本、事件不合法；切换事件里记下的新版表行数与校验和对不上 | `import_rejected`（`replay_failed`，附 `seq`） |

- 与 `log.verify` 是同一套检查，只是对象从存储换成了文件；通过之后，目标租户上再跑 `log.verify` 应得到同样的结论。
- **锚点怎么校验**：源头的锚点存储不在导出里（它在控制面，不随租户导出）。导入不校验它，而是**从导入的日志重建**（5.5）。由此有一个如实告知的边界，见 5.7 第 3 条。
- **失败就是什么都没发生**：①–③ 失败时暂存的存储丢弃；④ 之后中途崩溃按 5.3 的重入回滚或接着做完。目标租户要么仍是空的、可以重新导入，要么导入已完成。报错只给位置（`seq`、`path`），不回显内容。
- **导出文件不可信**：它可能被改过或拼接过。链与校验和只能发现损坏与不一致，不能证明文件出自哪里（完整性的目标是溯源与防误操作，不是防篡改）。导入的是用户自己交来的文件，写进的是他自己的空租户，后果限在这个租户之内；`apply` 按严格模式解析（事件格式 1.6），不合法的事件一律停。

### 5.5 租户标识变了，哪些跟着变

导入之后，这条日志属于目标租户；目标租户的 ID 不变，日志里原来的租户 ID 成为历史。

| 东西 | 导入之后 |
|---|---|
| 已导入事件的字节（事件头、内容块、校验和） | **不变。** 创世事件里仍是原来的租户 ID；当前的租户 ID 以最近一条 `tenant.genesis` 或 `tenant.imported` 为准 |
| 节点 ID、恢复次数 | 换新的节点 ID；恢复次数加 1（`tenant.imported` 里）。"当前恢复次数"取最近一条 `tenant.restored` 或 `tenant.imported` 的 `restore_count`（事件格式 5.11、architecture §8 `meta` 一行、data-model「事件的身份」三处同改） |
| slot、表、字段、行、实体、源数据、事项的 ID，`seq` | 不变。这些标识在租户内唯一，目标是空的，不会相撞 |
| 主体 ID | 不变，但全部停用。主体 ID 全局唯一、与租户无关（architecture §9），同一个连接实例 ID 在原处仍可照常使用，互不影响 |
| 锚点存储 | 按目标租户的 ID 重建（`endImport` 一次写入）：删除登记由日志里仍待执行的删除得出；高水位 = 日志末端；恢复次数 = `tenant.imported` 里的值；"导入进行中"标记清掉，没有"恢复进行中"标记 |
| 控制面：租户目录、路由 | 不变（目标租户本来就在）。凭证：没有任何旧凭证；用户重新签发 |
| 句柄签名密钥 | 用目标处的。导入前的 `dc_`、`cur_` 全部失效 |
| 之后再导出的清单 | `tenant_id` 是目标租户的 ID |
| 存储里的 `meta`（(c) 类） | 新建：租户 ID 是目标的 |

### 5.6 导出里宽限期内待删除内容的占位

| 导出是怎么做的 | 导入时 |
|---|---|
| 默认（`pending_deletions: "placeholder"`） | 待删除的内容不在文件里。导入**对每一项这样的删除立即补一条墓碑**（`deletion.executed`，`actor: "system"`，`trigger: "import"`，`reason: "import_placeholder"`），排在 `tenant.imported` 之后。这些删除在目标处不可撤回——内容本来就没带过来；对应的 `deletion` 事项按到期关闭 |
| 显式包含（`"included"`） | 内容在文件里。这些删除在目标处仍是待执行：到期时刻照事件里记下的，登记重建进锚点存储；已过期的在换入后、对外服务前补跑（已有的"打开时补跑到期任务"）；未过期的仍可撤回 |

- 立即补墓碑而不是"留着占位等到期"：占位的块在存储里没有内容，却要在到期前表现成"可撤回"，而撤回不了。提前落墓碑让存储里只有"在"与"已移除"两种真实状态，也与"带占位的导出重放后无法再撤回那次删除"（事件格式第 8 节）一致。
- 这是到期物理删除之外第二种产生墓碑的途径，`trigger` 与 `reason` 各加一个取值。

### 5.7 不在导出里的东西带来什么后果

导出只有 (a) 类事件。下面这些带不过来，导入的回执与 CLI 的输出如实列出：

1. **读取记录**（(c) 类）。后果：读取审计从导入那一刻重新开始；纠错影响查询查不到导入前的读取（结果里的"覆盖到哪一刻"如实写明）；`possibly_affected` 标记没有了；`ver` 与 `sv` 的兜底从零开始，没带 `ver` 的写入报 `read_first`；"改名时有没有别人在用"的统计清零，导入后 30 天内的改名会被判为没人在用。
2. **请求键是带得过来的**（它在各头事件的内容里，请求键索引由日志重建），但它帮不上跨导入的重发：请求键里有连接实例，而连接实例都换了。导入前发出、导入后用新凭证重发的写入不会被认出是重发；有来源键的表不受影响（§3），其余靠 `duplicate_keys`。同键请求"进行中的等待"是进程内状态，本来就不跨进程。
3. **控制面的全部内容**：凭证、OAuth 客户端注册与授权、句柄签名密钥、源头的锚点存储。后果：所有接入要重新签发、重新授权；用户主体在目标处是一个新的主体，历史里导入前的用户显示为一个已停用的主体。**源头的删除登记带不过来**：导出之后、在源头又确认的删除，这份导出文件不知道，导入后那些内容仍在。这不是导入造成的——导出文件本来就是一份 saveslot 删不到的副本——但导入会让它重新变成线上数据，所以 CLI 在确认前显示导出时刻，并提示"这份导出之后在原处做的删除不在其中"。
4. **外部文件**不在 saveslot 里（`file_ref` 只有元数据与摘录），不随导入。
5. **源头不受影响**：导入不冻结、不修改、不通知源头。两边此后是两条各自延续的日志；把它们再合起来不在第一版范围内。迁移的做法是：源头停止写入 → 导出 → 导入 → 在目标处重新签发 → 停用源头。

### 5.8 契约、HTTP、CLI

- **契约**：管理类操作 `import`，只给用户会话，不进 MCP。输入是导出文件的字节流；结果：

  ```ts
  interface ImportResult {
    tenant_id: string; previous_tenant_id: string;
    events: number;                 // 导入的事件条数
    seq: number;                    // tenant.imported 的 seq
    restore_count: number;
    principals_disabled: number;
    slots: number;
    removed: number;                // 导入时已是"已移除"的内容块数
    pending_deletions: { executed: number; carried: number };   // 补了墓碑的；仍待执行的
    exported_at: string;
    not_imported: Array<"read_log" | "credentials" | "external_files">;
  }
  ```

  错误：`invalid_argument`（`tenant_not_empty`）、`import_rejected`（见 5.4）、`rate_limited`（`busy`：这个租户已有一次导入在进行）、`too_large`（超出部署方配置的上限）。
- **HTTP**：`POST /v1/import`，`Content-Type: application/x-ndjson`，流式上传，用户会话；同步返回 200 与 `ImportResult`。几段续传文件按顺序接在同一个请求体里。**导入只收明文 NDJSON**：服务端不接收口令，也就不解密。
- **CLI**：`saveslot import <文件>…`（服务器模式加 `--profile`）。导出文件加了 age 加密时（[`pre-dev-w10-onboarding.md`](pre-dev-w10-onboarding.md) 给 `export` 加的加密），由 CLI 在客户端一侧解密后再上传：加 `--passphrase-file <路径>`，macOS、Linux 上另可用 `--passphrase-fd <n>`；Windows 上只支持 `--passphrase-file`。执行前读清单并要求确认，显示原租户 ID、事件数、导出时刻、是否含待删除内容，以及 5.7 第 3 条的提示；非交互式下必须给 `--yes`。结束时写明停用了多少主体、补了多少墓碑，并提示用 `saveslot connect` 重新签发。本机模式下目标就是 `saveslot init` 之后的那个租户。

### 5.9 导入期间与续传

- **导入期间这个租户不能读写**：别的请求报 `unavailable`（`importing`）；"导入进行中"标记在时同样如此。它是空的，也没有连接实例，挡住的只有发起者自己的其他会话。
- **不支持断点续传。** 中断（连接断开、进程崩溃、校验失败）之后，目标租户要么仍是空的（重新导入即可），要么在下一次打开时由重入协议做完；因为要么全有要么全无，重试是安全的。半个租户不是一个可以对外服务的状态，也没有办法对一条不完整的日志做 5.4 的条数与末尾校验。
- 这里的"续传"与导出的 `after_seq` 不是一回事：导出可以分几段取，导入要求一次交齐。
- 导入完成后租户不再是空的，不能再导入第二份。

### 5.10 最小例子

用户在本机用了三个月，日志到 #4210，有两个连接实例、一项还在宽限期内的删除。

1. 本机：`saveslot export -o me.ndjson`（默认不含待删除内容）。清单：`upto: 4210`、`restore_count: 0`、`pending_deletions: "placeholder"`。
2. 云服务上注册账户（建好一个空租户 `tn_B…`），`saveslot login --profile cloud`。
3. `saveslot import me.ndjson --profile cloud`，确认。服务端：校验 → 重放 #1–#4210 → 追加 #4211 `tenant.imported`（`previous_tenant_id: tn_A…`、`tenant_id: tn_B…`、`restore_count: 1`）→ 追加 #4212 墓碑（那一项占位的删除）→ 置"导入进行中" → 换入 → 重建锚点并清标记。
4. 回执：`events: 4210`、`principals_disabled: 3`（原用户与两个连接实例）、`pending_deletions: {executed: 1, carried: 0}`。
5. 用户在云端重新接入各个 Agent。历史里 #57 仍显示"MacBook · Claude Code（已停用）"；Agent 手里旧的 `v4100.0` 带回来时按 #4100 判冲突：#4100 之后改过的字段成为候选，没改过的合并。

### 5.11 排期

**建议 P5。** 理由：

- 它的用途是在两处部署之间搬数据，主要是本机模式的用户搬进服务器模式。按实现顺序，本机模式在 P1–P4 与 P6 之后先发，P5（服务器模式）随后（07-scope-v1 第 4 节）；服务器模式上线的那一刻，正是已有的本机用户需要导入的时候。
- 它依赖的东西 P5 才齐：控制面里的锚点存储实现、服务器模式的身份、`POST /v1/import` 所在的 HTTP 管理端点。导出与"导出 → 重放"的测试 P3 已有。
- 不放 P6：P6 是本机模式发布前的收尾，先于 P5 发布；把导入放进去会让它挡住本机模式的发布，而本机之间搬数据用数据目录的备份与恢复已经能做。
- 事件格式（`tenant.imported`、主体状态 `disabled`、墓碑的新取值、5.11 的恢复次数来源）**冻结前必须进 v1**（§0.1 第 6–9 项）。

## 6. 租户整体删除：只列问题

- **现状**：整个 slot 删除只有方向、第一版不做（positioning「后续规划」）；用户要求删除整个账号（租户）时怎么办，规格里没有。逐条隐私删除满足不了它：事件头与元数据块按设计永远留下。
- **决定：现在不设计。** 把它列为待定清单"P5 前"一组的新条目：**对外提供云服务前必须定义**。它不挡本机模式（本机上删掉数据目录与配置目录就是全部）。
- **理由**：它是云服务的法律底线之一，但答案取决于法务口径与账户系统的做法，这两样现在都没有；提前设计只会定下一批要推翻的细节。

**进待定清单的条目**（"P5 前"）：

> **租户整体删除**（对外提供云服务前必须定义；不挡本机模式）。要回答：
>
> 1. **删什么**：租户存储是否整库删除，包括事件头链——"事件头永不删改"（K1）的适用范围是否限于租户存续期间；控制面里这个租户的凭证、OAuth 授权、租户目录与路由；读取记录；应用日志与错误上报里与它有关的内容。
> 2. **备份与归档**：备份、快照、冷租户归档里的副本何时消失、怎么告知；恢复一份早于删除的备份时，靠什么不让整个租户复活——需要一份租户存储之外、租户级的删除登记，它存什么（只有不透明的租户 ID？）、保留多久。
> 3. **流程**：谁能发起（只有用户会话？要不要重新认证）；有没有预览、宽限期与撤回；与逐条隐私删除的 24 小时宽限期是什么关系；宽限期内租户能不能读写、连接实例是否立即失效。
> 4. **进行中的事**：未到期的隐私删除、进行中的迁移、对拍、导入怎么处理。
> 5. **删除之前**：是否提示或要求先导出；导出文件、连接器与外部系统里的副本不由 saveslot 管理，怎么告知。
> 6. **删除之后留什么**：是否保留"曾有过这个租户"的最小记录（租户 ID、删除时刻），计费与合规要求保留的记录归谁管；租户 ID、用户主体 ID 是否永不复用；同一账户能否再建一个新租户。
> 7. **回执**：租户没了之后，用户凭什么确认删除已经完成、备份何时失效。
> 8. **各部署形态**：云服务由账户系统发起还是由 saveslot 的接口发起；自部署是不是一条运维命令；本机是否提供一条命令代替手动删目录。
> 9. **与别的设计的关系**：与"整个 slot 删除"是否共用一套机制；将来共享 slot、开发者采购托管时，删除一个用户与删除一个租户不再是一回事。
> 10. **法律口径**：与"删除的法律口径"一条一并交法务——法定时限、可保留的最小信息。

**要改的规格位置**

| 文件 | 小节 | 改什么 |
|---|---|---|
| `spec/08-open-questions.md` | 第二组 | "P5 前"加上面这一条 |
| `spec/01-positioning.md` | 「后续规划 · 整个 slot 删除」 | 加一句指向待定清单的这一条 |
| `spec/07-scope-v1.md` | 3.4 | 加一行"租户整体删除"：后续；云服务上线前定义 |

**要同步的讲解**：`guide/08-deletion.md` 第 8 节、`guide/10-guarantees.md` 第 5 节：写明第一版没有"删除整个账号"的操作。

## 8. 起草时自行决定的事项

超出已定结论、由起草时自行决定的事项。

| # | 决定 | 理由 |
|---|---|---|
| 1 | 连接器不应把第三方令牌放进证据；saveslot 不识别、不过滤（§1） | "令牌不进 saveslot 的任何存储"要成立，唯一会漏的口子是证据；而过滤密钥是内容判断，内核不做 |
| 2 | 范围外的名字报该操作对不存在的名字本来的错误；`nearest` 与歧义候选只取可见范围；按 ID 的报 `not_found`（2.2） | 两种错误各管一类引用，矛盾只在「可见范围」的一句话；保留相近名字对模型有用 |
| 3 | 范围外的 slot 参数报 `not_found`（`slot`），为此给 `not_found` 加一种 `reason`（2.2） | 规格里没有"slot 不存在"的错误，见 §9 第 2 条 |
| 4 | 名字解析（不重名、旧名）只在可见范围内做（2.2） | 否则歧义报错会泄露范围外的表名 |
| 5 | 限定范围的凭证不能新建 slot；之后新建的 slot 不自动纳入列表（2.4） | 不引入"自己建的自动可见"的隐含规则，也不需要修改范围 |
| 6 | slot 范围的权威在日志（`principals`），控制面不另存（2.5） | 一处为准；见 §9 第 6 条 |
| 7 | slot 范围不编码进 OAuth scope 字符串，授权结果不回传 slot 名单；客户端元数据里声明的 slot 名只用于预选，声明了不存在的 slot 时页上标"不存在"、不能当场新建（2.5） | slot 名是用户数据，不进 scope 字符串与令牌响应；授权页上不建 slot，与"限定范围的凭证不能建 slot"同一个理由 |
| 8 | 范围签发后不能改，也不做"只追加"（2.6） | 与 scope 一致；追加同样是修改 |
| 9 | 同一组 scope 对范围内各 slot 一样，不支持按 slot 给不同的 scope（2.1） | 要这样就签两个连接实例；否则授权成了一张矩阵 |
| 10 | 英文名用 `external_key` 而不是 `source_key`（3.1） | `source` 在规格里专指源数据 |
| 11 | 来源键就是表里的字段（1–4 个，`text` / `enum` / `integer`），不是行上的一个单独属性（3.2） | 键值因此按普通字段值记来源、可查询、随隐私删除级联，不需要另一套删除规则 |
| 12 | 唯一范围是表；区分来源靠键里的一个字段，由 schema 作者声明，不强制（3.2） | 不能按连接实例划分（重签会换实例）；只有一个来源的表不需要它 |
| 13 | 键字段可以是可选的，表里可以有没有来源键的行；键在新增时经 `external_key` 给出，或给没有键的行补一次，之后不能改。补键写成带 `row`、`ver` 与 `external_key` 的 `update`；键被已撤销、创建时带键的行占着时转过来（`key_from`），被未撤销的行占着或删除未决（冻结）时报 `external_key_in_use`，被已撤销、补键得来的行占着时报 `external_key_not_transferable`（不连环转移）；让出了键的被撤销行不能再重新存在（`external_key_transferred`）（3.2、3.3） | 同一张表既有连接器写的行，也有 Agent 按用户的话记的行；补键用已有的 `update` 形状，不加新意图 |
| 14 | 判定是三方比较：同值比"上次按来源键交来的值"，所见版本取这个字段上"最近一项已生效的同步贡献的位置"；候选也算同步贡献（3.4） | 只比当前值，用户的改动每次同步都被盖回去；只比上次生效的值，同一个候选每次同步都再并入一遍。两个基线各解决其中一个 |
| 15 | 没有基线值的字段与基线位置上的值比（规则同普通写入）；补键那次写入是这一行的第一个基线位置；键转来时基线值沿用原行的（3.4） | 补键的行没有同步贡献；不这样，补键后的第一次同步会把与本地相同的值当成新值，转来的键会把用户选留的本地值盖掉 |
| 16 | 意图默认 `update`，允许连接器显式写 `correct`（3.4） | 日常同步不该触发影响查询；来源系统明确标了更正时应当能表达 |
| 17 | 一个按来源键的 op 被跳过时，它的临时名不绑定；后面用它写 `ref` 的按来源键 op 一并跳过（`ref_skipped`），普通 op 报 `ref_not_found`（3.3） | 绑定到已撤销的行会让引用方的 `ref` 校验失败、整批报错；连接器写的明细跟着单据一起跳过，与"一条被撤销的记录不应让同批失败"一致 |
| 18 | 命中已撤销的行、命中宽限期内被占位的键：这个 op 被跳过，不报错、不落任何东西（3.5、3.6） | 整批里一条被撤销的记录不应让其余几百条失败；"不复活"只要求这一条不生效 |
| 19 | 物理删除后不记得键，再同步会重新出现；宽限期内键仍占位（3.6） | 前者由"删除后不可比对"得出；后者与请求键的口径一致，并保证撤回后不出现两行同键 |
| 20 | 没进事件的 op 留空号，`write.head` 的 `request` 块另记 `op_count`；重放回执里这些 op 只给下标，`omitted[]` 加 `unrecorded_ops`（3.8、3.12） | 不记总数，重放时连末尾被省略了几个 op 都说不出 |
| 21 | 定位结果与基线位置在删除重放里照记录，同值按删除后的同步贡献重算，没进事件的 op 不重放（3.9）；逐字段的基线位置记在元数据块 `ops/<i>/baseline` 里 | 按两条原则推得；需要推演验证（§10）。基线位置按字段取之后，一个 `ver.op` 装不下 |
| 22 | 写入过的表上：键只能加在同一份草稿新增的字段上；可去掉；不能换一组字段；增删都要确认。从未被写入的表上这些限制都不成立，归入 `restructure_unused` 自动生效（3.10） | 有历史的字段当键，删除会让键落回一个可能已被占用的旧值；不新增策略类别 |
| 23 | 含普通 op 的请求照旧计算服务端请求键（按原始请求体），其中按来源键 op 的内容归入事件格式 9.5 的已知边界；建议连接器分开请求（3.8） | 混合请求里普通 op 仍需要请求键防重发；按 op 拆分请求键是新机制 |
| 24 | MCP 上也暴露 `external_key`（§3 的规格位置表） | 由 Agent 调别的工具取数再写入时，它就是连接器；不暴露它只能先读后写 |
| 25 | "外部权威"没被授予而声明时拒绝整个请求，不静默降级；授予记在主体登记事件里（§4） | 降级会让写入方误以为带着权威；记进日志才能只凭日志核对 |
| 26 | 导入的目标租户保留自己的租户 ID，日志里原来的 ID 成为历史；新增事件 `tenant.imported`，不复用 `tenant.restored`（5.3、5.5） | 目标的控制面、锚点、目录都按它自己的 ID；两种事件的 `apply` 与 `verify` 不同 |
| 27 | "空"的定义：日志只有创世事件，且锚点里没有登记、恢复记录与导入标记（5.2） | 能用日志与锚点机械判断，不依赖"有没有人用过" |
| 28 | 导入的重入：换入是一步原子操作；`openTenant` 最先看导入标记，按租户存储里有没有 `tenant.imported` 决定回滚还是做完；回滚用新接口 `abortImport`（5.3） | 与恢复流程同形；回滚需要一个只清标记、不写登记的接口 |
| 29 | 导入时恢复次数加 1；导入前的 `ver` 只在"当前恢复次数来自 `tenant.imported`"时按原操作号判，之后再恢复过就按恢复的规则处理（5.3） | 事项版本沿用恢复后的处理；`ver` 的放宽只在两边日志逐字节相同的那一段上成立 |
| 30 | 停用是主体的一种新状态，由 `tenant.imported` 一条事件统一置位，不逐个追加吊销事件；原用户主体也停用，发起导入的用户登记为新主体（5.3） | 吊销是对连接实例的决定，用户主体没有吊销；一条事件比 N 条清楚 |
| 31 | 占位的待删除项在导入时立即补墓碑；显式包含内容的导出，删除在目标处照原到期时刻继续（5.6） | 存储里不留"表现成可撤回却撤回不了"的状态 |
| 32 | 导入先进暂存的存储、整体换入；不支持断点续传；期间租户不可读写（5.3、5.9） | 半个租户不是合法状态；全有或全无让重试安全 |
| 33 | 导入不校验、也带不来源头的锚点，登记由导入的日志重建；CLI 提示"导出之后在原处做的删除不在其中"（5.4、5.7） | 锚点在控制面、不随租户导出；这是导出文件作为副本的固有边界，只能如实告知 |
| 34 | 导入排在 P5 而不是 P6（5.11） | P6 先于 P5 发布；导入的主要用途在服务器模式上线时才出现 |
| 35 | 全部 op 都没变或被跳过的请求不产生事件时，回执不给 `seq`；请求带的显式幂等键不被记下（3.8） | 没有操作号可给；不记事件就没有地方存幂等键，重发按来源键重新判定，结果相同 |

## 9. 发现的问题

核对规格时发现的不一致或缺口。本稿没有改规格；与本设计直接相关的，在对应小节里给了裁定或处理办法。

1. **不存在的表报哪个错误，两处说法不同。** `spec/03-data-model/04-write-and-read.md`「可见范围」与 `spec/02-architecture.md` §13 保证点 5 写"不可见的表与不存在的表一样报 `not_found`"；`spec/04-contract.md` 第 11 节与 `spec/04-contract-types.md` 第 9 节写名字不存在报 `unknown_table` / `unknown_field` 并附最接近的名字，`not_found` 的对象里没有表。裁定见 2.2。
2. **"slot 不存在"没有对应的错误。** `not_found` 的 `reason` 只有行、实体、事项、源数据、草稿、连接实例、读取；`catalog` 的错误清单里有 `not_found`，但没说对象是什么。2.2 加了 `slot`。
3. **"slot 是权限的粒度"用的是现在时**（`spec/01-positioning.md`「数据层」、`spec/03-data-model/01-objects.md`「slot 与事物的时间线」），而 `spec/04-contract.md` 第 12 节写"第一版没有细粒度数据权限，scope 只按动作分"。§2 落下去之后前一句成立，后一句要改。
4. **"来源连接器"没有定义。** 只在 `spec/03-data-model/06-derived.md`「派生规则与派生缓存」出现一次。§1 给了定义。
5. **按 `entity_key` 定位的写入，键字段在事件里怎么记，事件格式没有写。** `spec/03-data-model/03-deletion.md`「重放规则 · 行 / 实体的存在」说"按 `entity_key` 定位的写入算给出了键字段，来源是这次写入的证据"；`spec/09-event-format.md` 5.7 只有 `by_entity_key: true`，没说键字段是记成 `applied`、`corroborated` 还是不记（与实体上的值相同，按同值规则本该是无操作，而无操作不留值）。来源键一侧本稿定为"键字段只在得到键的那次写入里有贡献，命中时是无操作"（3.4）；`entity_key` 一侧要另定，否则删除重放里"算给出了键字段"没有事件上的出处。
6. **scope 的权威位置没有写明。** `spec/02-architecture.md` §5 说权限"存在控制面"，§8 的 `principals` 表又有 scope 一列（由主体事件维护）。两处不一致时以谁为准、服务层从哪读，没有说。2.5 对 slot 范围规定以日志为准；scope 应当一并说清。
7. **版本标记"必须带回"与"应带回"。** `spec/03-data-model/04-write-and-read.md`「写入请求」写"版本标记必须带回（变更、纠错、撤销）"，`spec/04-contract.md` 5.1 的表写"应带回"并有兜底。按来源键写入不带 `ver`，落规格时这句话要连同例外一起改。
8. **一条受限 SQL 能否关联两个 slot 的表，没有明文。** 规格禁止了跨 slot 的派生规则、`ref` 与写入，没有提 `sql`。它影响 2.3"受限 SQL"一行的措辞，不影响结论。
9. **用户主体的名字从哪来没有写。** `Actor.name` 对用户是"用户名"（`spec/04-contract-types.md` 1.6），但创世事件的 `user` 块只有主体 ID 与种类，日志里没有用户的名字。若它取自控制面，导入之后原用户主体的名字就取不到了（5.7 第 3 条按"显示为一个已停用的主体"写）。
10. **连接实例"同一用户下不重名"**（`spec/04-contract-types.md` 8.1）没说已吊销的算不算。导入后原有连接实例全部停用，用户多半想用原来的名字重新签发；`saveslot setup` 重跑时默认名是否被已吊销的实例占用也取决于它。落规格时要定停用（与已吊销）的名字是否占用。
11. **服务器模式下租户何时创建没有写明。** `spec/09-event-format.md` 5.2 只说创世事件"由 `saveslot init` 或服务器模式建租户时产生"。5.2"空租户"的定义假设用户有会话时租户已经建好；若服务器模式是首次写入才建租户，定义里要加"或尚未创建"。
12. **`flagged` 事项的详情没有说明各处理方式对来源键的后果。** 手记的一行与同步来的一行记重了时，`keep` 是同一件事算两次，撤销同步行之后要再补键转键（3.3）才能让来源的修改进到手记的那一行。详情里应写明这几种处理的后果，并给出"撤销 + 补键"的写法。
13. **与本设计冲突、落规格时要改写的现有文字**（不是错误，是结论变了）：`spec/01-positioning.md`「部署形态与同步」"第一版只做导出"、`spec/02-architecture.md` §5 与 §8 的同一句、`spec/04-contract.md` 第 17 节"第一版只有导出，没有导入"、`spec/06-cli.md` 4.9 的 `saveslot import` 一行、`spec/07-scope-v1.md` 3.6 与第 5 节「把日志装回去」；`spec/04-contract.md` 第 14 节"同一件事被记了两次由 `duplicate_keys` 发现"。

## 10. 没有核对到的范围

- **§3 的规则还没有整体手推并转成参考求值器的用例。** 同步基线、三方比较与删除重放的交互（3.4、3.6、3.9）按规格文字推过逐种情形（3.4 的表），没有对照「回掉的权威定义」的伪代码逐行检查。落规格前应当把一组完整场景（同步 → 用户纠正 → 来源变化成为候选 → 采纳、保持或回到冲突前 → `undo` → 撤销与撤回 → 隐私删除其中一条源数据 → 撤回删除）手推一遍，转成参考求值器的固定用例。特别要覆盖的：
  - 补键之后的第一次同步（3.3、3.4 的"没有基线值时与基线位置上的值比"），以及转移键之后沿用原行基线值、再删除原行的同步源数据时的重算。
  - 逐字段的基线位置在同一字段组里各字段不同时，候选的合并基与事项的影响。
  - 临时名绑定到命中的行、以及被跳过时的 `ref_skipped`（3.3），在删除重放里的表现。
  - 转移键与撤回删除交替发生时键索引的结果（3.3 的表只逐项推了单次删除与单次撤回）。
- **状态类表没有涉及。** 来源键不开放给状态类表；连接器向状态类表写入（按 `entity_key`）时反复同步的行为没有分析。
- **`spec/10-evals.md`、`spec/03-data-model/08-schema-migration.md`、`spec/03-data-model/06-derived.md`（除连接器那一句外）没有读。** 来源键对迁移状态机、派生刷新与写入准入估算的影响，以及是否需要新增评测，都没有核对。
- **`spec/09-event-format.md` 只读了与本稿有关的小节**（第 1–3 节、4.1–4.2、5.1–5.3、5.6、5.7 的前半、6.8–6.9、第 7 节的表、第 8–11 节）。5.8 事项、5.9 删除事件的词表没有逐项核对；3.8 说"删除事件不加块"、5.6 说"墓碑加两个取值"是按这些小节之外的规格文字（03-deletion、architecture）推的。
- **`spec/04-contract-types.md` 只读了相关类型**（0、1.5–1.7、4.2 的前半、5.1、第 7 节、8.1、8.4、第 9 节）。新增字段与现有类型有没有重名、JSON 例子要补哪些，没有逐个核对。
- **`spec/05-surfaces.md` 的 MCP 部分**只读了第 2 节的差异表；各工具的文本渲染、工具描述要怎么改没有核对。
- **讲解章节只看了标题**，"要同步的讲解"是按标题对应的，没有读正文确认每一处措辞。
- **OAuth 相关的外部事实没有核实**：授权页上附加一个不在 scope 字符串里的授权属性（slot 范围）与 RFC 6749 / OAuth 2.1 草案、RFC 9728 是否有抵触，客户端对"授权结果比请求的 scope 更窄"的处理，都凭常识写出。CIMD 与 DCR 的选择对授权页的影响也没有分析。
- **导入的规模没有估算。** 重放整条日志要多久、`POST /v1/import` 同步返回在多大的日志上还可行、上限设多少，要等实验 4 的日志规模数据；本稿只给了 `too_large` 这个出口。
- **法律口径没有核对。** 3.6"删除后再同步会重新出现"与 5.7"源头的删除登记带不过来"在被遗忘权下是否需要额外的告知或限制，应随"删除的法律口径"一并交法务。
- **工作量没有估。** 各条给了阶段建议，没有给人周；07-scope-v1 第 6 节的数字本来也标着尚未重估。

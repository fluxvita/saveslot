# 决定：服务器模式一个部署使用多个 cell

> 不改事件格式，不改 K1–K14，不改操作契约。按「分步交付」落进规格与代码。

本文里「cell」指一个 PostgreSQL 实例（主库与它的备库、备份）加上建在它上面的那批租户 database。「进程」指一个 `saveslot server start` 的服务进程。

## 要解决什么

服务器模式的一个部署只有一个 cell：配置里只有一项 `SAVESLOT_CELL_DATABASE_URL`，它的名字固定是 `main`，每个新租户的 database 都建在它上面。一个 PostgreSQL 实例放得下的租户有限，到了上限只能把这个实例换大，而换大解决不了随 database 个数增长的那部分开销。

目标是一个部署可以有任意多个 cell，容量靠加 cell 增长：

- 新租户自动落到还有余量的 cell 上；
- 一个 cell 可以停止接收新租户，可以把上面的租户搬到别的 cell，搬空之后可以撤掉；
- 一个 cell 出故障，只影响它上面的租户；
- 只有一个 cell 的部署（自部署的常见形态）不用改配置，行为不变。

本机模式不变：没有 cell。

## 范围

**一个部署的全部 cell 与全部进程在同一个网络里。** 一次写入是进程与租户 database 之间的几十次往返（服务器模式的契约测试里，一次落了事件的写入中位 47 条语句，每条一次往返），进程到 cell 每多 1 毫秒，一次写入就多几十毫秒。所以这份决定不处理「cell 在另一个区域或另一个网络」：

- 不同的区域是不同的部署，各有自己的对外地址、控制面库、cell 与进程；租户不跨部署。
- 同一个部署里的 cell 可以是不同来源的 PostgreSQL（自建的、不同厂商托管的），只要满足 02-architecture §9 对实例的要求、并且与进程在同一个网络里。

减少一次写入的往返是另一件事，不在这里。

## 现状里已经有的

- 租户存储的引用带 cell 的名字：`{ kind: "postgres", database, cell }`；内核只认名字，名字到连接参数的对应由宿主给存储后端（02-architecture §8「租户存储」）。
- 控制面库的租户目录 `tenants` 每行记着租户所在的 cell 与 database，并约束同一个 cell 里 database 不重名（02-architecture §5「控制面存储」）。
- 建租户时核对 cell 是部署有的那一个；租户建到一半时，再建只能在它已登记的那个 cell 上继续。
- 进程不保留租户的数据状态，任何进程处理任何租户（「服务器模式一个部署运行多个服务进程」第 1 条）。多个 cell 不改变这一点：每个进程连得上每个 cell。

## 缺的

1. 配置只能写一个 cell。
2. cell 自己没有记录：它收不收新租户、放多少个、残留清理用哪种做法，无处可记。
3. 新租户去哪个 cell 是写死的。
4. 连接数的上限是一个进程一个总数，而每个 cell 的实例各有自己的连接上限。
5. 没有把一个租户从一个 cell 搬到另一个的办法。
6. 没有记下一个租户最后一次被使用的时刻，分不出哪些租户长期不用。

## 决定

### 1. 配置：一个 cell 用原来的变量，多个 cell 用一份文件

- 只有一个 cell 的部署照旧只设 `SAVESLOT_CELL_DATABASE_URL`，cell 的名字是 `main`。
- 多个 cell 时改设 `SAVESLOT_CELLS_FILE`，指向一份文件：cell 的名字 → 这个 cell 的连接（与 `SAVESLOT_CELL_DATABASE_URL` 同样的写法，库名部分是建租户库时连的维护库），以及可选的该 cell 的租户连接数上限（第 4 条）。两个变量同时设是写法不对，拒绝启动。
- 这份文件里有口令，照 `SAVESLOT_HANDLE_KEY_FILE` 那样核对：跟随符号链接之后是普通文件，本进程读得到，「其他人」没有任何权限位；不合即拒绝启动，报错里不写文件的内容。
- cell 的名字是小写字母、数字与连字符，1 到 32 个字符，以字母开头。名字一经登记不改：它记在每个租户的目录行里。
- 一个 cell 的连接参数可以改（实例换了地址、换了口令），名字不动；两个名字不得指向同一个实例（第 2 条登记时核对）。

各进程的这份配置必须相同。多进程决定第 5 条的配置指纹里「租户库所在集群的身份」一项，改为全部 cell 的名字与各自**登记的**实例身份（第 2 条的 `cells` 表）；口令不进指纹。指纹用登记的值，所以启动时连不上某个 cell 也算得出指纹；实例实际是不是它，在连上时另核（第 2 条）。

**不选的做法：** 每个 cell 一个带名字的环境变量（`SAVESLOT_CELL_DATABASE_URL_<名字>`）。名字要在大小写与符号之间来回转写；每个 cell 的可选项再多一项就多一族变量；带口令的值放在文件里比放在环境里容易按权限位管住。

### 2. cell 的登记：控制面库里一张表

控制面库加一张表 `cells`，一行一个 cell：

| 列 | 内容 |
|---|---|
| 名字 | 主键 |
| 状态 | `open`：接收新租户；`closed`：不接收新租户，已有的租户照常服务 |
| 租户数上限 | 这个 cell 上至多登记多少个租户（含建到一半的）；达到即不再分给新租户 |
| 实例的身份 | 登记时读到的实例标识，用来发现两个名字指向同一个实例、或一个名字被指到了别的实例上 |
| 登记时刻 | |

连接参数与口令不进这张表，只在配置里。

- **登记由运维命令做**：`saveslot server cell add <名字> [--limit <个数>]`。它连上配置里这个名字的实例，核对 02-architecture §9 的前提（大版本、能建库、能连维护库），读出实例的身份，核对没有别的 cell 是同一个实例，然后写这一行。`--limit` 缺省 2,000。
- **其余的运维命令**：`cell list`（每个 cell 的状态、上限、现有租户数、正在搬入的租户数、待丢弃的 database 数）、`cell close <名字>`、`cell open <名字>`、`cell limit <名字> <个数>`、`cell rebind <名字>`（下面）、`cell remove <名字>`（只在它上面没有任何租户时才做，含建到一半的与暂存的；它是某次搬迁的目标、或上面有待丢弃的源 database 时，也拒绝）。
- **配置与登记要对得上**：`server start` 时，登记了而配置里没有的 cell，拒绝启动并说明是哪一个（它上面的租户会打不开）；配置里有而没登记的 cell 不参与任何事，启动时记一条警告，等 `cell add`。
- **实例身份的核对**：`server start` 时对每个已登记的 cell 读实例的身份，与登记的比。不同，拒绝启动：那是把名字指到了另一个实例上。**连不上的 cell 不挡启动**：记一条警告，这个 cell 在本进程里先标为「未核对」，它上面的租户回 `unavailable`（`busy`，带 `retry_after`），本进程第一次连上它时再核；相同就照常服务，不同就记一条错误日志 `cell_identity_mismatch`，这个 cell 在本进程里一直不用，它上面的租户照旧回 `unavailable`，直到进程以正确的配置重启。否则一个 cell 停着的时候重启的进程起不来，一个 cell 的故障就扩到了全部租户，与「一个 cell 出故障，只影响它上面的租户」相反。
- **实例身份正当地变了**：用 `pg_upgrade` 做大版本升级（托管服务的原地大版本升级通常也是这样）、经转储与恢复或逻辑复制把一个 cell 换到新实例上，新实例的系统标识都与原来不同，此后 `server start` 一律拒绝。这时由 `saveslot server cell rebind <名字>` 认下新的身份：它要独占锁（没有进程在运行；身份在配置指纹里，第 1 条），连上这个名字现在指向的实例，核对租户目录里登记在这个 cell 上的每个租户 database 都在，并且各自过一遍打开租户时的核对（含不低于高水位：从一份旧备份恢复出来的实例在这里被拦下），全部通过才把新身份写进 `cells` 并记一条日志；任何一项不过，什么都不改，报出是哪个租户、哪一项。它不能用来把名字指到一个装着别的租户的实例上：登记在这个 cell 上的租户少一个都不行。
- **升级**：升到带这张表的版本时，表里写入一行 `main`，状态 `open`，上限 2,000，实例的身份在升级时读出。只有一个 cell 的部署此后不需要执行任何 `cell` 命令。

**实例的身份取 PostgreSQL 的系统标识**（`SELECT system_identifier FROM pg_control_system()`）。它在这个实例初始化时生成，重启不变；主库与它的物理备库是同一个值，所以主备切换不变；不是超级用户的角色读得到（在一家托管的 PostgreSQL 18 上，只有建库权限的普通账号读得到）。服务器的地址与启动时刻不能用：前者普通账号读不到，后者每次重启都变。由此有两个后果，都是要的：

- 从一个 cell 的物理备份恢复出来的新实例，系统标识与原实例相同。把这个 cell 的名字改指到恢复出来的实例上，核对通过：它就是这个 cell。
- 同一份物理备份恢复出两个实例，不能登记成两个 cell：它们带着同一批租户 database，登记成两个，同一个租户就有了两份各自往前走的存储。

残留清理用原地做法还是重建，取决于实例给不给那几项授权（02-architecture §7「残留清理在 PostgreSQL 上需要的权限」）。它现在说的是「这个部署」，改为按 cell：一个部署里可以有的 cell 原地清理、有的重建。判定的方式不变。托管的 PostgreSQL 未必给得出那几项：实测的那一家，权限最高的账号也不是超级用户，它自己是 `pg_maintain` 与 `pg_checkpoint` 的成员却不能转授，`pg_switch_wal()` 连它自己也执行不了；这样的 cell 用重建。

**上限为什么缺省 2,000。** 每个 database 有一套自己的系统目录，实例一级的开销随 database 的个数涨，与里面有多少数据无关：research/07 的估计是起步 2,000、压测后放宽。在一个 2 核 4 GiB 的托管 PostgreSQL 18 实例上实测：建好表的租户 database 每个约 9–11 MB（空库约 7.4 MB）；实例上有 2,000 个 database 时，闲置的处理器占用约 3%，主备切换期间约 6 秒连不上，重启约 2 秒连不上；一个租户 database 的 `pg_dump` 约 0.1 秒。2,000 在这个规格上站得住；更大的规格可以经 `cell limit` 调高，调之前照样先测。

**不选的做法：**

- *状态与上限写在配置文件里。* 改它们就要改配置、重启每个进程，而关掉一个 cell、调上限是运行中要做的事；上限的核对还要与登记租户在同一个事务里，放在库里才做得到。
- *加一个「已满」的状态。* 满不满由现有租户数与上限算出，另记一份会与实际不一致。

### 3. 新租户去哪个 cell

登记租户的那个事务里选 cell：在状态为 `open`、现有租户数低于上限的 cell 中，取现有租户数最少的；并列时取名字最小的。现有租户数按 `tenants` 里这个 cell 的行数算，含 `creating` 的，**另加正在搬入这个 cell 的租户数**（目录行上搬迁目标是它的）；第 5 条搬迁第 1 步核对目标的上限也用这个数。选之前锁住 `cells` 的各行，所以两个进程同时登记、或登记与搬迁同时发生，不会一起越过上限。

- 租户一经登记，cell 就定了；建到一半再接着建，仍在登记的那个 cell 上（现有规则）。
- 本进程还没核对过、或连不上的 cell（第 2 条）不参与选择，新租户不会登记到一个停着的 cell 上。
- **没有可用的 cell 时**，不登记，回暂时不可用：外部登录的首次登录回 503 带 `Retry-After`，`server user add` 退出码 7，与建租户排队等不到时相同；日志里记一条 `no_cell_available`。已有租户的请求不受影响。
- 运维命令建账户时可以点名 cell（`server user add --cell <名字>`），点名的 cell 关着或已满时拒绝，不改去别处。

**不选的做法：**

- *按 cell 的磁盘或负载选。* 要进程去读每个实例的容量指标，各家托管服务给的口径不一样；租户数是控制面自己就知道的数，而且上限本来就是按它定的。负载不均由搬迁解决（第 5 条）。
- *按用户 ID 的哈希选。* 加一个 cell 就要重新分布，而租户是不能随便搬的。

### 4. 租户连接数的上限按 cell 算

`SAVESLOT_TENANT_CONNECTIONS` 的含义从「一个进程同时打开的租户数上限」改为「一个进程在**每个 cell** 上同时打开的租户数上限」；cell 的配置文件里可以为某个 cell 另写一个数。名额、淘汰与排队的规则不变，只是各 cell 各算各的：一个 cell 的名额满了，先关这个 cell 上闲置最久的租户，不动别的 cell 上的。

连接预算相应按 cell 写：对每个 cell，这个 cell 的上限 × 进程数 + 每个进程在它上面的固定连接（建库与删库各用的维护库连接、正在建的租户库、导入）≤ 这个实例可用的连接数。控制面库的那一条算在控制面库所在的实例上。

只有一个 cell 的部署，数值与现在相同。

**不选的做法：** 保留一个进程一个总数。各 cell 的实例各有自己的连接上限，总数管不住某一个 cell 被打满；也不能让一个 cell 上的活跃租户把别的 cell 的名额占走。

### 5. 把一个租户搬到另一个 cell

搬迁是把租户的 database **原样**复制到目标 cell，再把租户目录里那一行改指过去。租户还是同一个：同一条日志、同一套 `seq`、同一个节点 ID，恢复次数不变；主体、连接实例与凭证都不动，客户端什么都不用做。

**为什么不用导出与导入。** 导入是把一份导出装进一个空租户：换节点 ID、恢复次数加 1、导入前登记的主体一律停用、凭证要用户重新签发（02-architecture §3、§8）。那是「数据到了另一个地方」的语义；搬迁要的是用户察觉不到。

步骤（`saveslot server tenant move <租户> --to <cell>`，可在进程运行时执行）：

1. **占有。** 在控制面库的租户目录里记下「正在搬迁」与目标 cell、目标 database 的名字，并持有以这个租户为键的占有锁。用的是多进程决定第 3 条给导入的那一套：先取锁、后写标记，锁随连接存在。有导入或另一次搬迁在进行的租户不搬。目标 cell 须已登记、在配置里、现有租户数（第 3 条的算法，含正在搬入的）低于上限，核对与写标记在同一个事务里、锁住 `cells` 的那一行；状态是 `closed` 也可以搬入（关掉的是自动分配）。
2. **封存，并停下读。** 一个写事务：取该租户的 advisory lock，在 `meta` 里写下「已封存」。此后任何进程在这个 database 上的写事务取到锁后见到封存，回 `unavailable`（`busy`，带 `retry_after`），什么都不写。与导入的封存是同一个机制。
   **读也停**：从这一步到改指，这个租户的读同样回 `unavailable`（`busy`）。原因是读取记录：服务器模式里一次读在应答之前把读取记录落进租户的 database，那个事务不取 advisory lock、不看封存（02-architecture §7「应答之前落盘」）。导入时这无害，被封存的是马上要丢掉的空租户；搬迁时，复制开始之后应答的读只把记录留在源上，源随后被丢掉，这次读交给了调用方却没有记录，违反 K10，之后不带 `ver` 的写入还会因此被判 `read_first`。所以每次使用租户时，除了看目录行上的导入占有，也看搬迁标记：有标记、占有者活着，读与写都回 `unavailable`（`busy`）；读取记录的事务另核封存，见到封存就不写、这次读回同样的 `unavailable`，挡住标记写下之前已经通过检查的读。这个核对要与封存冲突，不能只读一眼：读取记录的事务以 `FOR SHARE` 读 `meta` 里的封存那一行，封存的写事务改这一行，于是封存要等在途的读取记录事务提交，之后的都看得见封存；复制开始时源上不会再有读取记录落下。
3. **复制。** 在目标 cell 上建 database（编码、排序规则照租户存储的规定），把源 database 的全部表与内容原样复制过去。读取记录也在租户的 database 里，一并过去。
4. **核对。** 目标上：存储格式版本、日志末端的 `seq` 与事件头链的末端哈希、**租户 database 里每张表**（含读取记录的三张：`read_log`、`read_log_rows`、`last_read`）的行数，与封存之后的源相同；再照打开租户时的核对（`openTenant`）做一遍。任一项不符，丢弃目标 database，解除封存，清掉标记，报失败；源没有被动过。
5. **改指。** 控制面库的一个事务里，把这个租户的目录行改为目标 cell 与目标 database，被换下的源记在「待丢弃」的位置。从这一刻起任何进程的下一次使用都发现目录行变了，重开到新的 database（多进程决定第 3 条「database 换了就重开」）。新 database 里的封存标记在这一步之后解除。
6. **丢弃源。** 删掉源 database，清掉「待丢弃」与搬迁标记，放掉占有锁。别的进程可能还开着源（改指之后它们在下一次使用这个租户时才重开，闲着的连接要到闲置关闭才断），这时删除失败：不用 `FORCE` 去断别人的连接，源留在「待丢弃」的位置，搬迁标记清掉、占有锁放掉，命令报「已搬到目标，源待丢弃」；之后由任何进程在打开或闲置关闭这个租户时、以及 `cell list` 发现时重试删除，与今天删不掉的暂存库留着重试是同一个做法。待丢弃的源仍挡着它所在 cell 的 `cell remove`。

- **期间**：从封存到改指，这个租户的读写都回 `unavailable`（`busy`，带 `retry_after`）。时长主要是复制的时间，随 database 的大小涨；命令在开始前给出估计，结束时报实际时长。读在这一段也停，是为了不丢读取记录（第 2 步）；以后若要读不停，做法是复制之后、改指之前另开一小段，只停读、把三张读取记录表再复制一遍并核对，再改指，这里不做。
- **中途停下**：占有者死了，发现它的进程照多进程决定第 3 条的规则收尾。改指之前的，丢弃目标 database、解除源的封存；改指之后的，先解除目标的封存（目标是封存着复制过去的，占有者可能死在改指与解封之间），再接着丢弃源（删不掉照第 6 步留着待丢弃）。次序与导入的重入规则相同：解封在清标记之前，标记最后才清，所以不会留下一个封存着却没人去解的 database。
- **锚点不动**：高水位、恢复次数与删除登记按租户 ID 记在控制面库里，租户没换，它们不变。这不是恢复：复制是在封存之下做的，目标的日志末端就是源的日志末端，没有回退，所以不走恢复流程、不加恢复次数。
- **物理删除的残留**：复制只带走各表现有的行，源上已经物理删除的内容不会过去；源 database 整个删掉。
- **目标 cell 的残留清理做法可以与源不同**，按目标 cell 的来。

**撤掉一个 cell** 就是：`cell close`，把上面的租户逐个搬走，`cell remove`，再从配置里去掉。

复制用什么做（服务自己逐表读写，还是调用 PostgreSQL 的导出与恢复工具）是实现的选择，由第 4 步的核对把关；做之前先量一个大租户的复制时间，把封存的时长写进运维说明。

**不选的做法：**

- *在线搬迁，写入不停。* 要把源上的新事件持续追到目标，再做一次切换；写入不可用的时间从复制的时长缩到切换的一瞬。它需要的是日志的增量同步，属于多节点的那部分设计（02-architecture §12）；人的记录这种体量，一次复制是秒级的，不值得为它提前做。
- *逻辑复制（发布与订阅）。* 要实例一级的权限与参数，托管的实例未必给；每个租户一个 database，一次搬迁就要建一对发布与订阅。
- *停掉全部进程再搬。* 一个租户的事不该让整个部署停下。

### 6. 记下租户最后一次被使用的时刻

`tenants` 加一列「最后使用时刻」。写的时机只有两个：打开一个租户时，与因闲置关闭它时；并且只在库里的值比现在早一小时以上才写。所以一个租户一小时至多一次控制面写入，不是每个请求一次；租户因闲置关闭发生在它最后一次使用之后的闲置时长（`SAVESLOT_TENANT_IDLE`）上，所以这个时刻落后于真正的最后一次使用至多一小时加闲置时长。

它回答的只有一件事：这个租户多久没用了。`cell list` 据此给出每个 cell 上近 7 天、近 30 天用过的租户数；将来的冷租户归档按它挑人。

它是运营方看自己的服务，不含任何用户内容，不进租户日志，不随租户导出。

**不选的做法：** 在控制面库里记按租户的请求数、读写量、存储增长。控制面库是每个请求都要读的，不该承担随时间增长的写入；每个租户一个 database，PostgreSQL 自己就按 database 记着事务数、读写的块数与大小，运营方对每个 cell 定期采样即可，不需要进程做什么。按租户的用量属于配额与计量，在那里一起定。

## 不在这份决定里

- **冷租户归档**（长期不用的租户导出后从 cell 上删掉，再用时恢复）。它需要的两样这里给了：最后使用时刻，与「一个租户的 database 可以在封存之下整个搬走」的机制。归档何时作废、有未到期删除的租户怎么办，见 08-open-questions。
- **不停下整个部署就恢复一个租户。** `server restore` 现在要在没有任何进程运行时执行（多进程决定第 4 条）。备份到单个租户的粒度（逐个 database 的逻辑备份）是部署方的事，02-architecture §9 已经这样分；让恢复只挡住被恢复的那一个租户，可以用这里的占有与封存，另写决定。
- **进程不与 cell 在同一个网络里**，见「范围」。
- **按负载自动搬迁、自动加 cell。** 搬迁与加 cell 都由运维命令发起。

## 它改了哪些已有的规定

- **02-architecture §5「控制面存储」**：`tenants` 加最后使用时刻、搬迁的标记与待丢弃的 database；新增 `cells` 表。
- **02-architecture §7**：「连接」一项按第 4 条改为按 cell；「残留清理在 PostgreSQL 上需要的权限」里「这个部署」改为「这个 cell」。
- **02-architecture §8**：封存除导入外多一个使用者；新增搬迁的步骤与重入。
- **02-architecture §9**：自部署「这唯一的 cell 名字固定是 `main`」改为「只有一个 cell 时名字是 `main`」；云服务与自部署的差别表里「多 cell 路由不启用」去掉，改为「可以多个」；`TenantRef` 的说明不变。
- **04-contract**：不改。搬迁期间的读写回已有的 `unavailable`（`busy`，带 `retry_after`）：对客户端来说就是「这个租户此刻处理不了，稍后重试」，它要做的与别的 `busy` 没有不同；与多进程决定复用 `stopping`、不另开原因是同一个取舍。未核对或身份不符的 cell 上的租户同样回它。
- **06-cli §4.1**：`SAVESLOT_CELLS_FILE`；`SAVESLOT_TENANT_CONNECTIONS` 的含义与连接预算按 cell；新增 `server cell …`（含 `rebind`）与 `server tenant move`，`server user add --cell`；`server start` 遇到连不上的 cell 只警告。
- **02-architecture §7「应答之前落盘」**：读取记录的事务以 `FOR SHARE` 读封存标记，见到封存不写、这次读回 `unavailable`（导入期间整个租户本来就不可用，行为不变）。
- **07-scope-v1 §3.7**：「只有一个 cell」一行。
- **讲解**：自部署与部署各章里 cell 的说法。
- 事件格式、内核不变量都不变。租户存储的格式不变（封存标记是多进程决定加的那一项）。控制面库的格式有一次改动，带升级步骤与格式样本，在独占锁下做（多进程决定第 8 条）。

## 怎么验

- 两个 cell（测试里是同一个 PostgreSQL 上的两个名字不行：实例的身份相同会被拒；用两个实例）。连着建若干租户：按租户数最少的 cell 轮着落；一个 cell 到上限后，新租户只去另一个；两个都满，首次登录回 503，已有租户照常。
- 两个进程同时登记，cell 只差一个到上限：只有一个登记在它上面。
- `cell close` 之后不再有新租户落到它上面，上面已有的租户读写照常；`cell remove` 在还有租户（含建到一半的）时拒绝。
- 登记了而配置里没有的 cell：拒绝启动。把一个已登记的名字指到另一个实例：拒绝启动。两个名字指向同一个实例：`cell add` 拒绝。
- 一个 cell 在 `server start` 时连不上：照常启动，别的 cell 上的租户照常读写，它上面的租户回 `unavailable`（`busy`）；它恢复之后第一次连上、身份相同，它上面的租户照常；身份不同，记 `cell_identity_mismatch`，它上面的租户继续回 `unavailable`。
- `cell rebind`：把一个 cell 的租户 database 原样搬到一个新实例（系统标识不同）后，`server start` 拒绝；`cell rebind` 之后照常启动、租户读写照常。新实例上少一个租户 database，或其中一个的日志末端低于高水位：`cell rebind` 拒绝并指出是哪一个，`cells` 不变。有进程在运行时 `cell rebind` 拒绝。
- 连接：一个 cell 的名额满了，另一个 cell 上的租户照常打开；淘汰只发生在满的那个 cell 上。
- 搬迁：搬前搬后，同一个连接实例的令牌照常可用；`history`、`sources` 与导出逐项相同；`ver` 与句柄照常有效（恢复次数没变）。搬迁中的读与写都回 `unavailable`（`busy`）；一次写入在封存之前通过了检查、在封存之后才取到锁，回 `unavailable`，不是成功后丢失；一次读在搬迁标记写下之前通过了检查、在封存之后才写读取记录，同样回 `unavailable`，不是应答了却没有记录。
- 读取记录跟着过去：搬迁之前应答的读，搬迁之后在 `reads.list` 里；之后一次不带 `ver` 的写入照它判，不回 `read_first`。
- 计数：一次搬迁正在搬入的 cell 只差一个到上限时，新租户不落到它上面；它是搬迁目标时 `cell remove` 拒绝；源 database 待丢弃时，源所在 cell 的 `cell remove` 拒绝。
- 源删不掉（测试里另开一条连接占着源）：命令报「源待丢弃」，租户已在目标上可读写；那条连接放掉之后，下一次重试删掉源、清掉待丢弃。
- 搬迁在封存之后、复制途中、改指之前、改指之后各被杀一次：另一个进程收尾，前三种租户仍在源上、可写，最后一种在目标上、可写；没有 database 停在封存状态，没有留下没人认的 database。
- 核对不过（测试里改掉目标的一行）：搬迁失败，源解除封存，目标被丢弃。
- 搬迁之后别的进程的下一个请求读到的是目标 database；高水位没有被源 database 推高。
- 源上有已经物理删除的内容：搬到目标后，在目标的数据文件里搜不到被删的原文。
- 最后使用时刻：一个租户连着用一小时以内，控制面库里这一行只写一次；闲置关闭后它不早于最后一次使用。
- 升级：带一个 cell 的旧控制面库升级后有一行 `main`，原有的租户不动，只设 `SAVESLOT_CELL_DATABASE_URL` 照常启动。
- 本机模式的全部现有测试不变。

## 分步交付

1. **登记、配置、分配与按 cell 的连接上限**（第 1–4 条）与最后使用时刻（第 6 条）。这一步改控制面库的格式，升级到它要全部进程停下一次；与多进程决定第 2 步的那次格式改动能合成一次就合成一次。做完，一个部署可以加 cell，新租户会落到新的 cell 上。
2. **搬迁**（第 5 条）。依赖多进程决定第 2 步的封存与占有；在那之后做。做完，cell 可以搬空、撤掉，租户可以在 cell 之间调整。

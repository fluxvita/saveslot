# 决定：记下一次操作来自宿主的哪个会话

> 给操作契约加一个可选的公共参数与几处可选的输出；给事件格式加一个可选的数据块（用到它的头事件 `v` 加一）。不改 K1–K14，不改任何已有的判定。**加了它，版本兜底、请求键与幂等的行为一条都不变**（第 4 条）。审过再落进规格与代码。

本文里「宿主」指运行 Agent 的程序（一个成品的编码 Agent，或开发者在某个框架上自己搭的 Agent）。「会话」指宿主自己的会话：它有自己的标识，可以被恢复、分叉、派生出子会话。它不是操作系统进程、不是传输连接、不是 MCP 的会话、不是一次请求。

## 要解决什么

一次操作是从宿主的哪个会话里发出来的，saveslot 不知道，事后也查不出。调用方能自报的上下文只有 `task`，而会话不是任务：一个会话里可以做几件事，一件事可以跨几个会话、几个 Agent。拿 `task` 去装会话标识，这个区别就没了；`task` 还参与版本兜底与请求键（第 4 条），装进别的东西会改变判定。

操作发生时没有记下的上下文，以后补不回来。所以这里定一个最小的、可选的会话来源，与四样东西分开：经过认证的身份（连接实例）、任务（`task`）、操作号、源数据。

## 现状

- 每个操作有可选的 `task`，自报；它参与 `ver` / `item_ver` / `sv` 的兜底与服务端算的请求键（04-contract-types §1.7，04-contract §13、§14）。
- 契约与事件格式里没有会话。
- `task` 在事件里是调用方发起的头事件上的一个数据块，来源是这次操作的全部源数据，其中任何一条被隐私删除，它随之删除；没有源数据的操作，它没有来源可沿着删，删除预览的 `not_deleted` 里以 `operation_labels` 如实列出（09-event-format §5.1、§9.4）。
- 读取记录里每次读有一个可空的任务标识（03-data-model「读取记录：read_log」）。读取记录有保留期，不随租户导出。
- 事件格式只增不改：给已有类型新增 path，用到它的事件 `v` 加一；旧内核遇到不认识的 `v` 停下，不跳过（09-event-format §1.6）。

## 决定

### 1. 一个可选的公共参数 `session`

每个操作多一个可选的参数：

```ts
interface CommonParams {
  task?: string;
  /** 可选。宿主的会话，由宿主一侧的适配代码自报；模型不填、也看不到这个参数。 */
  session?: {
    /** 宿主的种类：小写字母、数字与连字符，1 到 32 个字符，以字母开头（如 `claude-code`、`pi`）。 */
    host: string;
    /** 宿主给这个会话的标识，原样传来：1 到 128 个字符，不含控制字符与首尾空白。 */
    id: string;
    /** 这个会话由哪个会话而来（恢复后换了标识、分叉、子会话），同一个 host 之下的 id。 */
    parent?: string;
  };
}
```

- **一个会话的身份是（连接实例，`host`，`id`）三样合起来。** 两台机器上同一种宿主各自的会话，由连接实例分开；同一个连接实例之下两种宿主，由 `host` 分开。不另设「宿主实例」这一层：连接实例已经是它。
- **`parent` 只说「由它而来」，不说是哪一种。** 恢复、分叉、子会话在各家宿主里的含义与叫法不同，有的宿主恢复后标识不变，有的在压缩上下文之后换一个标识；统一成一组枚举，等于替宿主下定义。最小的版本只留这一条边：它没记下就补不回来，而种类以后可以作为可选键加上。
- **给不出就不给。** 宿主没有会话的概念、或适配代码拿不到标识时，不带这个参数；不编一个，不拿时间戳或进程号充数，不让模型填。没带就是「不知道」，读回时也这样说（第 5 条）。
- 形状不合（字符、长度、`parent` 等于 `id`）报 `invalid_argument`。

**不选的做法：**

- *放进 `task`，或给 `task` 约定一个前缀。* `task` 参与判定；一个会话里的两件事、一件事跨两个会话，都会被它混在一起或错开。
- *只收一个不透明的字符串。* 两种宿主的标识可能相撞，而且读回时说不出它是谁家的。
- *由 saveslot 生成会话标识、发给调用方带回来。* 那是 saveslot 的会话，不是宿主的；宿主那一侧的记录（对话存档、日志）用的是它自己的标识，对不上就没有用处。

### 2. 怎么传进来

会话标识由**代码**传，不经过模型：

| 入口 | 怎么带 |
|---|---|
| MCP（`/mcp` 与本机的桥） | `tools/call` 的 `params._meta` 里的一个键 `ai.saveslot/session`，值是上面的对象。**它不是任何工具的参数**，不出现在 `tools/list` 的 schema 里，工具描述不提它 |
| HTTP `/v1` | 请求头 `X-Session-Host`、`X-Session-Id`、`X-Session-Parent`，与 `X-Task-Id` 同样的规则：只经请求头传，值是 UTF-8 字节；有 `X-Session-Id` 而没有 `X-Session-Host`、或反过来，报 `invalid_argument` |
| CLI | `--session-host`、`--session-id`、`--session-parent`，给脚本用 |

- **为什么不做成工具参数。** 出现在 schema 里的参数模型会去填，填的只能是它编的；编出来的标识比没有更糟，它看上去像真的。能可靠拿到会话标识的只有宿主一侧的代码：在框架上搭 Agent 的开发者，他的适配代码包着工具调用，可以在发出请求时附上 `_meta`；直接调 HTTP 的程序自己带头。
- **适配代码够不到请求的宿主**（只能配置一个 MCP 服务器、别的什么都插不进去的）：不带。这是如实的缺失，不是要补的洞。成品宿主里「钩子知道会话标识、而发请求的是宿主自己的 MCP 客户端」这种情形，怎么让标识到得了请求，随宿主钩子的那份设计一起定，不在这里。
- 本机的桥原样转发 `_meta` 里的这个键，自己不生成。

### 3. 记在哪

**写的一侧**：调用方发起的头事件多一个可选的数据块。

| path | 种类 | 内容 | 说明 |
|---|---|---|---|
| `session` | 数 | `{"host": …, "id": …, "parent"?: …}` | 调用方自报的宿主会话。来源同 `task` |

- 一次操作记一次，在头事件上；不进事件头，不进元数据块，不进业务表的任何一列。
- 它是数据块，因为它是调用方自报的文字（03-data-model「由内容算出的值、调用方自报的文字都是内容」）：来源是这次操作的全部源数据，其中任何一条被隐私删除，它随之删除，与 `task` 同一条规则、同一份位置列表。
- 没有任何源数据的操作（`delete`、撤回删除、`schema_draft`、不带证据也不带 `note` 又不触发写入的 `resolve`）：这个块没有来源可沿着删，隐私删除清不到。删除预览的 `not_deleted` 里 `operation_labels` 一项把它一并算上（这一项的含义从「自报的 task 与显式幂等键」扩成「自报的 task、会话与显式幂等键」）。所以**会话标识里不得有用户内容**：适配代码传宿主的不透明标识，不传会话的标题或名字。
- 没有产生事件的操作（全部 op 都没变的按来源键写入）什么都不记，与现在相同。

**读的一侧**：读取记录在已有的任务标识旁边多三个可空的列（`host`、`id`、`parent`）。它随读取记录的保留期清理，不随租户导出，导入之后从零开始；不承诺一份永久、完整的读取历史。

**证据来自哪个会话**：不另加字段。一条源数据是在某一次操作里记下的，那次操作的头事件上有它的 `session`；这就是这条证据的来源会话。之后别的操作用 `source_ref` 引用它，引用的那次操作有自己的 `session`，源数据原来那次的不变。所以「提交写入的会话」与「证据所出的会话」本来就是两处记录，不会混。

证据上指向宿主里某条消息、某次工具调用的定位信息，不在最小的版本里：各家宿主的定位方式不同，而且它比会话标识更接近用户内容。

### 4. 它不参与任何判定

**加了 `session`，下面四样的行为与没有它时逐项相同。**

| 机制 | 现在按什么 | 加了之后 |
|---|---|---|
| `ver` / `item_ver` / `sv` 的兜底（上次读到的版本） | 连接实例，带 `task` 时再加 `task` | 不变。`session` 不看 |
| `read_first`（`no_read`、`task_mismatch`） | 同上 | 不变。没有「会话不符」这种原因 |
| 「我上次读之后的变更」（`my_last_read`）与受影响的读取 | 同上 | 不变 |
| 服务端算的请求键 | 连接实例 + `task` + 规范化请求 | 不变。`session` 不进请求键 |
| 显式幂等键与请求内容的指纹 | 键 + 整个请求体 | 不变。`session` 不在请求体里（经 `_meta` 或请求头传），不进指纹 |

**为什么不让会话隔离兜底。** 设想两个会话共用一个连接实例的凭证，都没带 `task`：甲会话读到某行的第 5 版，乙会话没读过就不带 `ver` 去写，兜底拿到的是甲读的那一版。让会话隔离兜底看上去能挡住它。不这样做，有三个理由：

1. **宿主的会话标识不是稳定的隔离键。** 分叉出来的会话带着父会话的全部上下文，包括父会话读到的内容，它自己却「没读过」；有的宿主压缩上下文之后换一个会话标识，同一段对话前后成了两个会话；子 Agent 有的共用父会话的标识、有的另起一个。按会话隔离，这些情形里合理的写入会被拒成 `read_first`，而哪些被拒取决于宿主的实现细节。
2. **隔离已经有它的键，就是 `task`。** 同一个凭证上要分开的两条线，各带各的 `task`：兜底只认同一任务的读，乙的写入得到 `read_first`（`task_mismatch`）。适配代码拿得到会话标识的，也就填得了 `task`；要隔离的宿主把 `task` 填上，不需要第二个键。
3. **一个只用来记录的字段不该悄悄改判定。** 客户端从不带到带上 `session`，如果兜底因此变严，等于升级适配代码改变了写入的结果。

**重试不会因为换了会话变成新的写入。** 一次写入提交了而应答丢了，重试可能从恢复后的、甚至换了标识的会话里发出。请求键与幂等键都不含 `session`，所以它仍被认作同一次请求，回放第一份回执；回执里的 `session` 是第一次的那个。

### 5. 读回来能看到什么

最小的一组，都只在调用方的可见范围之内：

- **`history`（时间线、某一版的来历）与 `sources`**：每一次操作在给出连接实例与 `task` 的地方，多给它的 `session`（有就给）。
- **`reads.list`**：每条读取多给 `session`；多一个筛选 `of_session`（`host` 加 `id`），与已有的 `of_task` 并列。
- **写入回执**：不回显。调用方自己知道自己带了什么。

三种「没有」分开说，不混成一个空值：

| 情形 | 给出 |
|---|---|
| 这次操作没带 | 没有 `session` 键 |
| 带了，随它的源数据被隐私删除了 | `session_removed: true` |
| 早于这个功能的事件 | 没有 `session` 键（与「没带」相同：那时无从带起） |

- **没有「按会话列出全部操作」的新操作。** 按会话找，是在已有的读取之上加筛选，所以越不过 slot 的可见范围：一个只看得见某个 slot 的连接实例，看不到同一个会话在别的 slot 里做了什么。
- **不暗示因果。** 同一个会话里先读后写，不说明那次写入用了那次读到的内容；写入用了什么由它的证据与前提说明。读回的文字里不把会话写成「依据」。
- **它是自报的。** 渲染成文字时照自报的文字对待：带不可信文字的边界标记（05-surfaces §5），不写成「已验证」。它不是认证，不是授权的依据，不是证据为真的证明；形状像 UUID 也一样。

### 6. 事件格式与版本

- 给调用方发起的各类头事件新增一个 path `session`。带了它的事件，该类型的 `v` 加一；没带的照旧写原来的 `v`，旧事件的字节不变。
- 旧内核遇到新的 `v` 停下、不跳过。所以分两个版本走（「一个部署运行多个服务进程」第 8 条的同一条规则）：先发一个**读得懂**这个 path 的版本，这个版本收到 `session` 参数时接受而不记；下一个版本才开始写它。服务器模式里新旧进程并存时才不会有进程读不了别的进程写下的事件。发布说明里写明每个版本属于哪一种。
- 导出：这个块随事件导出，待删除的照别的数据块那样以占位导出。读取记录不导出。
- 控制面不变。租户存储的格式有一次改动（读取记录加列），带升级步骤。

## 走一遍

- **两个会话共用一个凭证，都不带 `task`。** 甲读某行（第 5 版），乙不带 `ver` 写这一行：兜底取到第 5 版，照现在的规则判，与没有 `session` 时相同。两次操作各记各的 `session`，事后看得出读与写不在同一个会话。要挡住它，两边带不同的 `task`：乙得到 `read_first`（`task_mismatch`）。
- **一件事跨两个会话。** 两个会话带同一个 `task`、不同的 `session`：兜底与请求键照 `task` 走，第二个会话接着第一个读到的版本写；两次操作的 `session` 不同，`task` 相同。
- **恢复。** 宿主恢复会话后标识不变：前后的操作 `session` 相同。标识变了：新的操作带新的 `id`，`parent` 指旧的。
- **分叉与子会话。** 新会话带自己的 `id`，`parent` 指它由之而来的那个。它不带 `ver` 的第一次写入照兜底的现有规则判，不因为是新会话被拒。
- **证据出自另一个会话。** 甲会话记下一条源数据并写入；乙会话用 `source_ref` 引用它再写一次。那条源数据的来源会话是甲（记下它的那次操作的头事件），乙那次写入的 `session` 是乙。甲那次的证据被隐私删除时，甲那次操作的 `session` 块随之删除；乙那次操作的 `session` 块的来源里也有这条被引用的源数据，同样删除。
- **重试换了会话。** 第一次写入已提交、应答丢失；重试带着另一个 `session`、同一个请求内容：回放第一份回执，日志里只有一次写入，记着第一次的 `session`。

## 不在这份决定里

- 会话的种类（恢复、分叉、子会话各是什么）作为可选键。
- 证据上的消息与工具调用定位。
- 成品宿主里钩子怎样把会话标识送进宿主自己发出的请求。
- 会话管理、Agent 之间的协调、完整的对话存档。
- 把读取记录变成随租户导出的永久历史；由一个会话里的全部读取自动推出写入的依据。

## 它改了哪些已有的规定

- **04-contract-types §1.7**：`CommonParams.session`；`history`、`sources`、`reads.list` 的结果里可选的 `session` 与 `session_removed`；`reads.list` 的 `of_session`；`not_deleted` 里 `operation_labels` 的说明。
- **04-contract §13、§14**：写明 `session` 不参与兜底、`read_first`、请求键与幂等。
- **05-surfaces**：`_meta` 的键与它不是工具参数；HTTP 的三个请求头；读回时的渲染与边界标记。工具描述不变。
- **06-cli**：三个选项。
- **09-event-format §5.1、§9.4、§10**：头事件的 `session` 块与它的来源；「不随这次删除清除的数据块」里没有源数据的操作一行；各头事件类型的 `v`。
- **03-data-model「读取记录：read_log」**：新增的列；「由内容算出的值、调用方自报的文字都是内容」的列举里加上它。
- **02-architecture §8**：租户存储的格式升级一步。
- **讲解**：接入与溯源各章。
- K1–K14 不变；已有的任何判定不变。

## 怎么验

- 带与不带 `session` 的同一串请求，除 `session` 本身之外，每一份回执、每一次判定、最终的全部表数据逐项相同（性质测试：随机的读写序列，随机地带或不带、随机地换会话）。
- 兜底：两个会话共用凭证、不带 `task`，乙不带 `ver` 的写入取到甲读的版本；带不同的 `task` 时得到 `task_mismatch`。结果与两边都不带 `session` 时相同。
- 请求键：同一个请求内容从两个不同的 `session` 发出，第二次是回放，日志里一次写入。显式幂等键相同、请求体相同、`session` 不同：回放；请求体不同：照旧报 `invalid_argument`。
- `session` 不出现在任何工具的 schema 与描述里；`_meta` 里的键与三个请求头各自到得了事件；只给一半请求头被拒；形状不合被拒。
- 隐私删除：有源数据的操作，源数据被删后 `session` 块不在了，读回给 `session_removed`；被 `source_ref` 引用的源数据被删，引用它的那次操作的 `session` 块同样不在。没有源数据的操作：删除预览的 `not_deleted` 列出 `operation_labels`，块留着。
- 可见范围：只看得见一个 slot 的连接实例，用 `of_session` 筛不出同一个会话在别的 slot 里的读取；`history` 里看不见范围外的操作的 `session`。
- 导出再导入：事件上的 `session` 都在；读取记录从零开始。
- 两个版本：只读不写的那个版本读得了下一个版本写下的事件；更早的内核遇到带 `session` 的事件停下、不跳过。早于这个功能的事件读回时没有 `session` 键。
- 不带 `session` 的宿主的全部现有测试不变。

## 分步交付

1. **读得懂**：内核认得新 path 与新的 `v`；参数被接受而不记。存储格式的升级（读取记录加列）在这一步。
2. **开始记**：写下 `session` 块与读取记录的三列；`history`、`sources`、`reads.list` 给出它；HTTP、MCP 与 CLI 的入口。
3. 适配代码各自填上它：随各个宿主的接入一起做。

## 1. 表与字段的别名

### 问题

用户说"花销""里程""体重秤的数"，表叫 `expenses`、字段叫 `distance`。表名与字段名只允许 ASCII（[`10-types-and-units.md`](../../spec/03-data-model/10-types-and-units.md)「字段类型与取值范围 · 名字」），Agent 把用户的说法对到名字上，现在只能靠一句 `description`（[`07-schema-evolution.md`](../../spec/03-data-model/07-schema-evolution.md)「schema 文档格式 · 文档结构」）。说明要讲清"这是什么"，不适合再塞一串同义词。

### 可选做法

- 甲：不加键，约定把同义词写进 `description`。
- 乙：加一组别名，只给 Agent 看，不是可以写在请求里的名字。
- 丙：加一组别名，并让它参与名字解析（请求里写别名等于写名字）。

### 决定：乙

1. **键名与形状**：表（基础表、派生表）与字段（基础字段、派生字段）上各加一个可选键 `aliases`（别名），值是字符串数组。不设 slot 级的别名。
   命名理由：与 `description`、`values` 一样是名词复数的小写键；不叫 `synonyms`，因为里面也放旧称、口语叫法、另一种语言的叫法，未必是同义词。
2. **上限**：每个对象至多 8 个，每个至多 64 个字符（与枚举取值的长度上限相同）。超出时编译报 `validation_failed`，明细码 `alias_invalid`（新增）。
3. **内容规则**（编译时检查，全部确定）：
   - 落账前做 NFC 规范化；规范化后不得为空，不得含换行与控制字符，首尾不得是空白。
   - 同一对象的别名之间不得重复（NFC 之后逐码点比较）。
   - **不得与同一作用域里任何仍可解析的名字相同**：表的别名不得等于本 slot 任一张表的当前名字，也不得等于最近 10 个 schema 版本内仍按旧名解析的表名；字段的别名同理，对照本表各字段（含它自己）的当前名字与仍可解析的旧名。比较按 NFC 之后逐码点进行。否则 Agent 照别名写了那个词，请求按旧名解析到另一张表或另一个字段上，与别名的提示相反。别的对象的别名与它相同是允许的：用户的说法本来就可能有歧义，由说明去区分。
   - 违反任一条报 `validation_failed`（`alias_invalid`），`path` 指到那一项。
4. **按不可信文本处理**，规则与 `description` 完全相同（[`04-contract.md`](../../spec/04-contract.md) 第 8 节）：
   - 契约里类型是 `UntrustedText[]`，MCP 渲染进不可信边界，与说明一样标出写入者与版本。
   - 入口一侧，别名里出现边界标记时报 `validation_failed`（`untrusted_marker`）。
   - 别名**不出现在**工具描述、参数说明与服务器的 `instructions` 里；那几处紧挨着模型的指令，只放 saveslot 自己写的文字。
   - 与名称、说明、枚举值一样，别名是 schema 作者写的文字，不在隐私删除的级联范围内（[`09-event-format.md`](../../spec/09-event-format.md) §7 末）。不要把用户的隐私原话写成别名。
5. **改动分类**：新增改动码 `change_aliases`，类别"只改元数据"（`metadata`），归入 slot 策略已有的自动生效类别 `description`，不新增 `auto_apply` 的取值。只改目录，不建新物理表；带旧 `sv` 的写入照收。
   不直接复用 `change_description` 这个改动码，是为了让 `changes[]` 说得出改的是哪一样；两个码共用一个自动生效类别，做法同 `rename_table` 与 `rename_field` 共用 `rename_unused`。
6. **在数据目录里怎么返回**：

   | 档 | 返回什么 |
   |---|---|
   | `list` | 表的 `aliases`。这一档是 Agent 判断"用户说的是哪张表"的地方，别名在这里最有用 |
   | `table` | 表的 `aliases`，每个字段的 `aliases` |
   | `schema` | 文档原样，含 `aliases` |

   没有别名的对象不带这个键。`list` 档每张表多出的文本至多 8 × 64 个字符，计入结果预算。
7. **不参与名字解析**。请求里的表名、字段名，受限 SQL 里的标识符，都只认名字（含改名后仍可解析的旧名）。写别名的请求照旧报 `unknown_table` / `unknown_field`。
8. **报错时用它来提示**：`unknown_table` / `unknown_field` 的 `nearest` 里，别名与请求里那个名字折叠后相同（按第 2 项 `keymatch@1` 的折叠 N 比较，`Spend` 与 `spend` 算相同）的对象，其**名字**排在最前。只在本次调用可见的范围内找：范围外的表与它的别名不参与，也不出现。返回的是名字，不是别名文字，所以报错里不出现不可信文本。
9. **与"改名后旧名仍可解析"的关系**：两者互不相干。
   - 旧名是名字：写入按请求的 `sv` 解析，读取在最近 10 个 schema 版本内按旧名解析并提示新名（[`07-schema-evolution.md`](../../spec/03-data-model/07-schema-evolution.md)「旧名字还认多久」）。别名不进这套规则，改名时旧名也不会自动变成别名。
   - 想让旧名在 10 个版本之后仍能被人和 Agent 认出来，起草方可以把它写进 `aliases`；它只是提示，不恢复解析。
   - 判断"旧名能否按旧名解析"时看的是"当前有没有别的表或字段叫这个名字"，别名不算名字，不影响这条判断。反过来，第 3 条已经保证别名不会与仍可解析的旧名相同，两套规则不会指向同一个词。

### 理由

- **不选甲**：说明至多 500 个字符，要回答"这是什么、单位与口径"；同义词挤进去，渲染时也没法单独成行。更要紧的是结构化之后，报错提示（第 8 条）与将来的检索才有东西可用。
- **不选丙，别名不能是可写的名字**，五条理由：
  1. **名字是标识符，别名是自由文字。** 名字匹配 `[A-Za-z][A-Za-z0-9_]{0,62}`，在受限 SQL 里直接当标识符写；别名多半是中文，进 SQL 要加引号，正是当初只收 ASCII 名字想避开的事。
  2. **解析必须唯一。** 名字在作用域内唯一；别名允许重复（"时间"可以同时是两个字段的叫法）。要参与解析就得再加一套唯一性规则与优先级（当前名、旧名、别名谁先），而它带来的只是"少查一次目录"。
  3. **它会让"只改说明"不再安全。** 自动生效的前提是不让旧写入失败、不让现有读取读到不同的东西。别名一旦可解析，改一个别名就可能让同一个请求落到另一个字段上，这类改动就必须确认。
  4. **不可信文本不能当寻址的键。** 别名由任何有 `saveslot.schema` 权限的调用方撰写。若可解析，一份草稿给 `note` 加上别名 `amount_usd`，就可能把别人的写入引到错的字段上。
  5. **消费方统计按名字做。** "没人在用"的判断、`field_name_usage`、影响预览里的消费方清单都以"按名字用过"为准，别名进来这些都要重做。
- Agent 读目录时名字与别名在同一行，照着写名字没有额外成本。

## 2. 写错实体键时的提示

### 问题

状态类表按 `entity_key` 写入，键不存在就新建实体。"Q4推广"写成"q4 推广""Q4推广预算"，结果是多出一个实体，原来那个没动。现在的回执列出该表已有的键（`existing_keys`，最多 10 个，按最近写入排序，[`05-time.md`](../../spec/03-data-model/05-time.md)「按 `entity_key` 写入」）。实体一多，写错的那个对应的正确键未必排得进前 10，排进去了也和别的键混在一起。

### 可选做法

- 甲：不改。
- 乙：回执里把写法相近的键找出来，排在前面并单独标出；写入照常生效。
- 丙：命中相近的键时不直接新建，生成 `flagged` 事项或进待确认。

### 决定：乙。丙仍然不做

1. **回执字段**：`OpResult` 在 `created_entity: true` 时加一个可选字段

   ```ts
   type EntityKeyText = UntrustedText | Record<FieldName, UntrustedText>;
   similar_keys?: Array<{ key: EntityKeyText; match: "fold" | "affix" | "edit"; revoked?: true }>;   // 至多 5 个
   existing_keys?: EntityKeyText[];   // 形状随之改；上限不变（最多 10 个）
   ```

   - `similar_keys`（相近的键）：与 `existing_keys` 并列，名字同一个构词。没有相近的键时不带这个字段。
   - `match`（相近的原因）三个取值：`fold`（折叠后相同）、`affix`（一方是另一方的前缀或后缀）、`edit`（编辑距离在阈值内）。给出原因是为了让回执文本能说"只差大小写或空白"还是"多了两个字"，Agent 转述给用户时更准。
   - `revoked`：这个实体已撤销（不带区间的 `revoke`）。撤销之后实体与键仍在，仍参与比较；文本里标出"（已撤销）"，免得 Agent 把一个已撤销的实体当成要改回去的目标。
   - **键怎么表示**：单字段的键是一个 `UntrustedText`；多字段的键是"字段名 → 值的文本"，每个字段的值按 MCP 渲染同一种写法转成文本。`existing_keys` 现在的 `UntrustedText[]` 装不下多字段的键，随之改成同一个形状。
   - `existing_keys` 的上限不变（最多 10 个）；**排序改为相近的键在前，其余按最近写入**。`similar_keys` 里的键都出现在 `existing_keys` 的开头。
   - **幂等重放**：这两项由写入那一刻的状态算出，不进事件，重放时状态可能已经变了。重放的回执不给这两项，`omitted[]` 加取值 `"existing_keys"`（同时表示 `similar_keys` 也省略）；不在重放时按当前状态重算，否则同一个请求的两次回执会不同。
2. **"相近"的判据**（算法版本 `keymatch@1`，随内核发布；所用的 Unicode 数据打包在内核里，不读操作系统与运行时的语言环境）：

   **第一步，折叠** N(s)，依次做三件事：

   | 步骤 | 做什么 | 抹平什么 |
   |---|---|---|
   | ① | Unicode NFKC 规范化 | 全角与半角、兼容字符 |
   | ② | Unicode 简单大小写折叠（CaseFolding 表的 C 与 S 两类） | 大小写 |
   | ③ | 去掉全部空白字符（Unicode `White_Space`） | 首尾与中间的空白 |

   不做字形之间的转换（例如繁体字与简体字）：那需要一份一个字对一个字的对照表，而不少字的对应随词而定，表的来源与版本都要另外钉住；`keymatch@1` 只用 Unicode 自带、随版本固定的数据。Unicode 数据的版本随 `keymatch@1` 固定，实现时由数据文件生成、不手抄，也不调用运行时自带的规范化（各运行时的 Unicode 版本可能不同）。

   **第二步，比较**新键 a 与已有键 b，长度按折叠后的码点数算，取第一个成立的级别：

   | 级别 | `match` | 成立条件 |
   |---|---|---|
   | 1 | `fold` | N(a) = N(b) |
   | 2 | `affix` | N(a)、N(b) 之一是另一个的前缀或后缀，且较短的一个不少于 2 个码点 |
   | 3 | `edit` | 较短的一个不少于 3 个码点，且两者的编辑距离 ≤ 1；较短的一个不少于 8 个码点时放宽到 ≤ 2（初值）。编辑距离是按码点算的 Levenshtein 距离：插入、删除、替换各计 1，**不含换位**（相邻两个码点对调计 2） |

   **多字段的键**：非 `text` 的键字段必须同值（按同值判据）；`text` 键字段逐个比较，每个要么原样相同，要么在某一级成立；至少有一个不是原样相同。整个键的级别取各字段里最宽的一级。键里没有 `text` 字段的表不给 `similar_keys`。

   **测试向量**（随 `keymatch@1` 进规格，各实现都要通过）：

   | 新键 a | 已有键 b | 编辑距离 | 结果 | 说明 |
   |---|---|---|---|---|
   | `q4 推广` | `Q4推广` | — | `fold` | 大小写与空白 |
   | `ＡＢＣ部` | `abc部` | — | `fold` | 全角经 NFKC 变半角，再折叠大小写 |
   | `STRAẞE` | `straße` | — | `fold` | U+1E9E 经简单折叠成 U+00DF。折叠的结果不一定仍是 NFKC 形式，判据按码点比较，不再规范化一次 |
   | `Q4推广预算` | `Q4推广` | — | `affix` | 后者是前者的前缀 |
   | `marketting` | `marketing` | 1 | `edit` | 多一个字母 |
   | `marketnig` | `marketing` | 2 | `edit` | 换位计 2；较短的一个 9 个码点，阈值是 2 |
   | `abdc` | `abcd` | 2 | 不相近 | 换位计 2；较短的一个 4 个码点，阈值是 1 |
   | `CA` | `ABC` | 3 | 不相近 | 距离函数本身的向量（不受限的 Damerau–Levenshtein 会给出 2）；较短的一个不足 3 个码点，本来也不进 `edit` |
   | `房贷` | `房租` | 1 | 不相近 | 不足 3 个码点 |
   | `推廣` | `推广` | 1 | 不相近 | 不做字形转换；不足 3 个码点 |
3. **比较范围**：该表本次调用可见的全部实体，含已撤销的（撤销之后实体与键仍在）。实体超过 5,000 个时只比最近写入的 5,000 个（初值）。
4. **排序**：先按级别（`fold`、`affix`、`edit`），同级按编辑距离，再按最近写入，最后按实体 ID。取前 5 个。
5. **不落进事件**。`similar_keys` 与 `existing_keys` 一样是写入那一刻由当时的状态算出来的提示，不改变任何状态，不是判定结果，不进 `write.base`，也不占规则版本。同一份状态、同一个新键、同一个 `keymatch` 版本，结果相同；内核升级到新的 `keymatch` 版本后，对同一份状态可能给出不同的提示，这不影响重放。
6. **写入照常生效**（`status: "saved"`），不生成事项，不进待确认。键写错的改正办法不变：撤销写错的实体（不带区间），再按对的键写入。
7. **MCP 渲染**：相近的键单独成行，带原因与改正办法；已撤销的标"（已撤销）"；其余已有的键照旧。键是不可信文本，在边界里。

   | `match` | 文本里的说法 |
   |---|---|
   | `fold` | "只差大小写、全半角或空白" |
   | `affix` | "一个是另一个的开头或结尾" |
   | `edit` | "只差一两个字" |

8. `saveslot_write` 的 `ops[].entity_key` 参数说明改一句，工具描述里"回执列出该表已有的键"一句改为"回执会列出该表已有的键，并标出写法相近的"。工具描述同时被几份决定稿改动，本稿只改这一句，其余以合并后的规格为准。

### 理由

- **判据选这三级**：折叠抹平的三种差别都不是用户想表达的差别，命中几乎一定是写错；前后缀覆盖"推广"与"推广预算"这类多写、少写；编辑距离覆盖错一个字。更宽的做法（拼音相同、语义相近）要么依赖语言环境，要么不确定，不做。
- **编辑距离不含换位**：含换位的距离有两种互不相同的定义（限定的与不限定的），在阈值 2 上会对同一对键给出不同的答案；不含换位的 Levenshtein 只有一种读法，两个后端与参考实现照着写结果一定相同。代价是对调两个字计 2：短键上对调不会被标出，长键上仍在阈值内。
- **不做字形转换**：代价是"推廣"与"推广"这种只差字形的键不会被单独标出，仍只出现在 `existing_keys` 里。
- **`edit` 要求至少 3 个码点**：两个字的中文键差一个字太常见（"房租"与"房贷"、"交通"与"交际"），标出来多半是误报，Agent 可能照着去"改正"一个没写错的键。代价是两个字的键错一个字不会被单独标出，仍只出现在 `existing_keys` 里。阈值是初值，由评测调。
- **不选丙**：相近不等于写错，"推广"与"推广二期"可以是两个预算。拦下写入违背"写入永不阻塞"；生成事项则每建一个名字相近的实体就多一个待处理事项。提示放在回执里，判断留给看得到上下文的 Agent 与用户。
- **不落进事件**：它不影响状态，写进事件只会把一个经验性算法的结果固定进日志，而键值是用户内容，还要随隐私删除清除。

### 最小例子

`budgets` 表已有实体"Q4推广""研发""行政"。写入：

```json
{ "ops": [{ "intent": "update", "table": "budgets", "entity_key": { "category": "q4 推广" },

```

  "ops": [{ "intent": "update", "created_entity": true,

## 3. 单位词表补充

### 问题

营养与烹饪场景里，饮水量与包装标注常用液量盎司，维生素与矿物质常用微克。词表（`units@1`，[`10-types-and-units.md`](../../spec/03-data-model/10-types-and-units.md)「单位词表」）的体积只有 `mL`、`L`，质量最小到 `mg`。写入的值自带单位，单位不在词表里时报 `unit_unknown`，Agent 只能自己心算换算，这正是词表想避免的。

### 决定

**补两个单位：`floz`、`ug`。其余不补。**

| 量纲 | 代码 | 系数（到基准单位） | UCUM | 理由 |
|---|---|---|---|---|
| `volume` | `floz`（美制液量盎司） | `0.0295735295625`（升） | `[foz_us]` | 架构负责人已定。美制加仑定义为 231 立方英寸，1 英寸 = 0.0254 米，所以 1 加仑 = 3.785411784 升；液量盎司是加仑的 1/128，得 29.5735295625 毫升，是有限小数 |
| `mass` | `ug`（微克） | `0.000001`（克） | `ug` | 维生素 D、B12、叶酸、硒等在营养标签上以微克计。没有它，Agent 要把"5 微克"换成 `0.005 mg` 再写，错三个数量级的风险就在这一步 |

- **代码的写法**：`floz` 按"英制用常见缩写"的惯例取 `fl oz` 去掉空格（词表里的代码都不含空白）；`ug` 与 UCUM 的 ASCII 写法相同（UCUM 里"微"的前缀写 `u`）。
- **只收美制**。英制液量盎司（UCUM `[foz_br]`，约 28.41 毫升）不收：两者差 4%，用户说"盎司"时绝大多数指美制。字段确实按英制记的，用 `mL`。
- **美国食品标签把 1 液量盎司按 30 毫升计**，是标签的取整约定，不是单位定义。词表取定义值；按标签抄数的场景，写 `mL` 更不容易出偏差，模板的字段说明里写明。
- **单位同义表**（字面命中用）加两行：

  | 代码 | 认可的写法 |
  |---|---|
  | `floz` | 液量盎司、液体盎司、盎司、fl oz、fl. oz.、floz、oz |
  | `ug` | 微克、µg、μg、ug、mcg |

  `floz` 与 `oz` 都认"盎司""oz"：字面命中只看字段声明的那个单位的写法，不会混，做法同 `GBP` 与 `lb` 都认 `pound(s)`。`µg` 的两种写法（U+00B5、U+03BC）都列出。
- **词表版本**：`units@1` 还没有随任何对外发布的事件出现，直接并入 `units@1`、`literal@1`。规格里写成"`units@1` 指事件格式冻结时的内容"，与"固定清单，改表就是出新版本"不冲突。若落规格时事件格式已经冻结，改为出 `units@2`。

**不补的，与替代做法**：

| 单位 | 为什么不补 | 替代做法 |
|---|---|---|
| 杯、汤匙、茶匙 | 同一个词在各地是不同的量：美制杯约 236.6 毫升，公制杯在 UCUM 里是 240 毫升，不少地方的食谱按 250 毫升，日本是 200 毫升；汤匙有约 14.8、15、20 毫升三种。收进词表等于替用户选了一种，换算出的数悄悄差到两成以上。这与同义表不收"斤""两"是同一个理由 | 字段声明为 `mL`，Agent 换算后写入，把用户原话（"两杯"）留在证据里；或用 `decimal` 字段，在说明里写"杯（本表按 240 mL）" |
| 国际单位 IU | 不是固定的量，每种物质的换算不同，不能归入质量 | `decimal` 字段，说明里写"IU" |
| 品脱、夸脱、加仑 | 日常记录里少见，同样有美制、英制之分 | `floz` 或 `L` |
| `dL`、`cL` | 只是换一个前缀，Agent 换成 `mL` 不会错 | `mL` |
| 份、个、片 | 不是物理单位 | 无量纲 `1`，字段说明里写清一份是多少 |
| 浓度（`mg/dL`、`mmol/L`） | 属于健康检测，不在这次的营养与烹饪范围；词表没有浓度量纲，要先定量纲再收 | `decimal` 字段，说明里写单位。需要时另行决定 |

### 理由

宁少勿多：词表里的每一行都是"saveslot 保证换算正确"的承诺。能精确定义、各地含义一致的才收；含义因地而异的留给 schema 的说明去写明。

### 最小例子

```json
{ "name": "water", "type": "quantity", "unit": "mL", "min": 0, "description": "饮水量" }
```

写入 `{"value": "16", "unit": "floz"}`，回执 `warnings`：`已换算：16 floz → 473.176473 mL`（默认 `scale` 6）。

### 落进规格的位置

- `03-data-model/10-types-and-units.md`：「单位词表」的 `volume`、`mass` 两行；"英制代码对应的 UCUM 写法"加 `floz` = `[foz_us]`；"系数的出处"加美制加仑的定义；"词表外的单位"一条后加不收杯、勺、IU 的理由；「单位同义表」加两行。
- `07-scope-v1.md` 3.2"单位与换算"一行的量纲不用改；两个新单位记在 P2。
- `06-cli.md` 3.1：将来的营养类模板在字段说明里写明"按标签抄数时用 mL"。

## 4. 表里还没有数据时，放开结构改动

### 问题

改表的时间类型、增删改 `entity_key`、改 `granularity`、`base` 与 `derived` 互换、字段与 `ref` 互转、改 `ref` 的目标，第一版都不支持，草稿里出现就整份报 `not_in_this_version`（[`07-schema-evolution.md`](../../spec/03-data-model/07-schema-evolution.md)「改动分类与迁移手段」）。不支持的原因是有数据时没有通用的转换办法：事件类的一行怎么变成状态类的一段、换了键之后旧实体归谁，都要另一套规则。

但建表是由调用方 Agent 起草的，质量取决于它的水平。把预算建成了事件类表、忘了声明 `entity_key`，是最容易犯的错，而且往往在写第一条数据之前就被发现。这时表里什么都没有，却也只能删了重建。

### 可选做法

- 甲：不改，一律删了重建。
- 乙：表里没有数据时放开，没有东西要迁移。
- 丙：为有数据的情形也设计转换规则。

### 决定：乙

**4.1 "没有数据"的定义：从未被写入过**

> 一张基础表**从未被写入过**（`never_written`），当且仅当日志里没有任何一条以这张表（按表 ID）为目标的 `write.base` 事件。

按这个定义，下面各种情形的归属是确定的：

| 情形 | 算不算"没有数据" | 原因 |
|---|---|---|
| 建好之后一次都没写过 | 算 | — |
| 写过，行已全部撤销 | **不算** | 撤销是一次写入；行与它的历史还在，按时刻读、`timeline`、`undo` 都要用，改了结构这些历史无处安放 |
| 写过，内容已全部隐私删除、物理删除也已执行 | **不算** | 事件头与墓碑留在日志里；重放到切换时仍要处理这些写入 |
| 写过，但写入没生效（成了候选，或在待确认里） | **不算** | 候选与待确认的写入同样是 `write.base` 事件，迁移时要一并转换；指向它们的事项也还在 |
| 有待处理事项指向这张表的行 | 不会单独出现 | `conflict`、`awaiting_confirmation`、`flagged` 事项都由对这张表的写入产生，有事项就一定有写入 |
| 只被读过（读到空结果） | 算 | 读取记录是本地运行状态，不在日志里，没有要迁移的东西；但会影响是否自动生效，见 4.4 |
| 被派生规则或别的表的 `ref` 依赖 | 算 | 依赖方按 4.3 处理 |
| 经历过别的 schema 变更（加过字段、改过名） | 算 | 只要没有写入，之前的切换都没有补过值 |

判据只看日志，重放时可以复算；实现上查 `events` 表里按表 ID 建的索引列（[`02-architecture.md`](../../spec/02-architecture.md) §8「存储格式 v1」），不扫全表。

不选"当前没有未撤销的行"：那样的表仍有历史与事件，改结构就得回答"已撤销的事件类的行在状态类表里是什么"，正是第一版不想回答的问题。代价是写过一条测试数据的表用不上这条路，只能删了重建；这一点在回执与文档里写明。

**4.2 逐项判断**

| 改动（改动码） | 从未被写入时 | 理由与附加条件 |
|---|---|---|
| 改表的时间类型（`change_time_type`） | **放开** | 没有行，也就没有"一行变成一段"的问题。改完的定义按新建表的规则校验：改成事件类要指定 `time.field`；改成状态类不能再带 `duplicate_keys`、`external_key`；`entity_key` 只能出现在状态类表上 |
| 增、删、改 `entity_key`（`change_entity_key`） | **放开** | 没有实体，键唯一自然成立。键字段须必填，按新建表的规则 |
| 改 `granularity`（`change_granularity`） | **放开** | 没有区间要从按日换成按时刻 |
| `base` 改 `derived`（`change_table_kind`） | **放开** | 基础表从未被写入，改成派生表之后由规则生成；字段的类型与单位改由编译器推断。表 ID 不变 |
| `derived` 改 `base`（`change_table_kind`） | **仍不支持** | 派生表"有没有数据"无法只凭日志判断：依赖"今天"的规则读时计算，从不产生派生写入，但调用方已经读到过值。派生表自己没有数据可丢，删了重建没有损失 |
| 字段与 `ref` 互转、改 `ref` 的目标（`change_ref`） | **放开**，条件是**这个字段所在的表**从未被写入 | 没有行，就没有引用要校验或改写。被指向的表有没有数据无关 |
| 加、去掉、换来源键（`add_external_key`、`drop_external_key`、`change_external_key`） | **放开** | 来源键在有数据的表上只能加在同一份草稿新增的字段上、换键不支持，防的是键字段已有的历史值与键索引对不上；没有行时键索引是空的，这个问题不存在。所以键字段可以是已有字段，也可以直接换一组键字段。其余按新建表的规则校验：只能声明在事件类表与无时间表上，键字段的类型按来源键的限制 |

不按字段判断"这个字段从未被写入"：那样能多覆盖"表里有数据、只有新加的 `ref` 字段建错了"的情形，但要多一个定义（显式写 `null`、切换补出的常量算不算），而这种情形删掉字段再加一个代价很小。第一版只用表一级的一个定义。

**4.3 依赖方**

- **依赖这张表的派生规则**在同一次编译里按新定义重新编译。编译不过，整份草稿报 `validation_failed`（`rule_sql_rejected`），`path` 指到那条规则，在同一份草稿里一并改掉即可。编译得过时规则版本加 1（它依赖的定义变了）。重新编译后，规则的输出字段、单位、`time_dependency`、重算范围都没变的，不另列改动；有变化的另列一项 `change_rule`，按已有规则要确认。
- **别的表里指向这张表的 `ref` 字段**：`ref.target`（`row` / `entity`）必须与目标表改后的时间类型相符。不相符而引用方也从未被写入时，在同一份草稿里把引用方一并改掉（它是引用方的 `change_ref`）；引用方有数据时编译失败（`validation_failed`，`still_referenced`，`referenced_by` 指到引用方）。

**4.4 自动生效还是要确认**

- slot 策略的 `auto_apply` 新增一个取值 `restructure_unused`（没人在用的空表改结构），默认策略里开启，默认策略由七类变成八类。
  命名理由：与 `rename_unused` 同一个构词，条件也是同一个；不叫 `restructure_empty`，是因为"空"容易被读成"当前没有行"，而条件是"从未被写入且没人在用"。
- **自动生效的条件**：表从未被写入，**且**最近 30 天没有提交者以外的连接实例按名字读写过这张表。第二个条件就是 `rename_unused` 的"没人在用"，判断方式相同（从读写记录推断）。
- 有别的连接实例读过这张表时要确认，预览的 `impact.consumers` 列出它们。
- **同一张从未被写入、没人在用的表上，原本要确认的几种改动一并归入 `restructure_unused`**：删字段（`drop_field`）、改类型（`change_type`）、换量纲（`change_dimension`）、同量纲改单位（`change_unit`）、改精度（`change_precision`）、收紧约束（`tighten_constraint`），以及来源键的加、去掉、换（`add_external_key`、`drop_external_key`、`change_external_key`）。此时没有值可丢、也没有值要转换：`destructive` 为 `false`，`auto` 为 `true`，`migrate` 不必给。不这样，"把时间类型连同原来的时间字段一起改掉"这种最常见的修正仍会因为一项 `drop_field` 进待确认。**新增必填字段与可选改必填仍须给常量形式的 `backfill`**（规格已写明空表也要给），这一条不动。
- 一份草稿自动生效仍然要求它的每一项改动都自动；同一份草稿里另有须确认的改动（例如同时改了另一张有数据的表）时，整份进待确认。
- **改动分类表逐行改**：上面这些改动码在「改动分类与迁移手段」表里的"自动"一栏，每一行都写成"从未被写入的表上：自动（`restructure_unused`）；否则 ……（原来的写法）"，不在表后另写一段例外。这样"一份草稿自动生效当且仅当每一项都在'自动'之列"一句的含义就是明确的：同一个改动码是否自动，依它所在的表而定。
- **之前建的 slot 不享有这一类**：默认策略由七类变八类只影响之后新建的 slot。已有 slot 的 `slot.policy_set` 里没有 `restructure_unused`，第一版也没有改策略的操作；规格里写明这一句。

理由：自动生效的三条标准是不改动已有的值、不让旧写入失败、不让现有读取读到不同的东西。空表满足第一条；后两条取决于有没有别人已经照着旧结构在用——另一个 Agent 读过目录、正准备按事件类写入，它的写入会被拒。所以沿用改名的做法：只有自己在用的，改了不用确认。Agent 刚建错表、自己发现、自己改正，是这条规则主要服务的情形，它落在自动的一侧。

**4.5 带旧 `sv` 的写入**

带旧 `sv` 写这张表的写入一律被拒（`schema_incompatible`），提示重读。表一级的结构变了，写入里的任何字段都不能按旧定义解释。`changed_fields` 里给一项 `{field: "*", change: <改动码>}`；`"*"` 表示整张表，写法同写入回执里表示"存在"的键。

**4.6 对事件格式与 `apply` 的影响**

- **事件类型不增加。** `schema.compiled` 的 `changes` 里出现这几个改动码（原先是保留值），`class` 记 `metadata`：没有已有的值，也没有转换。
- **走"不重建"的路径**：这张表换一张新的物理表（`physical.since` 是本版），但没有旧写入要转换，与新增一张表相同——建表在切换的事务里完成，直接 `schema.switched`，`rebuilt_tables` 为空（物理形状变了也不列入：`rebuilt_tables` 列的是要按日志重建、要核对的表），没有 `tables/<表ID>` 核对块（[`09-event-format.md`](../../spec/09-event-format.md) §4.5"新增一张表不算重建"）。旧的物理表成为退役表，是空的。
- **`apply` 不需要知道"空表"这回事**：重放到 `schema.switched` 时，按 `compiled` 里的定义给 `physical.since` 等于本版的表建物理表。"从未被写入"只在编译与确认时判断，判断的结果体现为"这次切换没有要转换的写入"。
- **自动生效的路径没有时间窗**：提交、编译、确认、切换是同一次操作、同一个事务，每租户写入串行，判断与切换之间不会插进别的写入。
- **待确认的路径有时间窗**：草稿等确认期间旧版照常可写。**确认时在同一个事务里重新判断**；这张表已被写入时，`resolve` 报 `draft_outdated`，`reason` 是 `table_written`（新增），不产生任何事件，事项保持未决。这份草稿不可能再被确认（"从未被写入"一旦不成立就永远不成立），调用方 `reject` 它，或提交新草稿取代它。
- `slot.policy_set` 的 `auto_apply` 取值集合加 `restructure_unused`。
- 编译时表已被写入：照旧整份报 `not_in_this_version`，`reason` 用新增的取值 `table_written`，`param` 指到那个键；文本说明"这张表已有写入，这项改动只在从未写入的表上支持"。

**4.7 与"删表再建同名表"相比**

| | 就地改结构 | 删表再建 |
|---|---|---|
| 草稿数 | 一份 | 两份：同名的表按名字匹配成同一张表，一份草稿里表达不了"删掉再建一张同名的" |
| 确认 | 没人在用时不用 | 删表一律要确认 |
| 表 ID、字段 ID | 不变 | 都换新的，旧 ID 不复用 |
| 依赖它的派生规则与 `ref` | 留着，按新定义重新编译 | 要先删掉或改掉依赖方，否则删表编译失败（`still_referenced`） |
| 说明、别名、字段的其他约束 | 都留着 | 要重新写一遍，弱的模型容易漏 |
| 历史 | 一张表，中间换过结构 | 一张已删的表加一张新表，同名 |

## 5. 官方 schema 的结构提前定

### 问题

`extends` / `compatibility` 的结构在待定清单第三组"可以开发后再定"（[`08-open-questions.md`](../../spec/08-open-questions.md)）。第一版的模板只是随 CLI 打包的普通 schema，建完 slot 就与模板没有关系（[`06-cli.md`](../../spec/06-cli.md) 3.1）。

### 决定

**提到第二组"P4 前"。本文不设计结构本身。**

### 理由

1. **上层的领域工具要写得出来。** 一个读预算的看板、一个算营养摄入的工具，前提是某个领域的表结构有一份标准定义，而且能知道"这个用户的这个 slot 符合它"。模板是一次性拷贝：拷贝之后用户可以改名、改单位、删字段，工具无从知道它还认不认得这些表。没有这份约定，每个上层工具都只能自己读目录、自己猜。
2. **定得晚，代价落在事件格式上。** 官方 schema 的声明要进编译后的定义（重放只读它，不能回头去取一份外部文件）。事件格式在第一次对外发布本机模式之前冻结；P4 之前定，新键可以直接并入 v1；之后再定，就要给 `schema.compiled` 升版本，而且此前建的 slot 都没有这份信息。
3. **P4 实现的正是它要落脚的地方。** 改动分类、自动生效的类别、迁移状态机都在 P4 实现。"官方小版本自动跟进、大版本走迁移"如果要做，是这套机制上的一种改动来源；结构先定，P4 才知道要不要给它留接口。
4. **模板的写法取决于它。** 健康、营养这类模板打算随第一版多给几份（本文第 6、7 项对它们有要求）。结构定了，模板可以一开始就写成官方 schema 的形式；否则先发的模板建出来的 slot 将来都是"没有关系的拷贝"。

### 提前之后对实现顺序的影响

- **多一份 P4 开工前的方案交付物**：官方 schema 结构的决定稿，在 P1–P3 期间并行写，不占开发的关键路径。
- **提前的是"定"，不是"做"。** 是否在第一版实现由那份决定稿回答。两种结果：只在事件格式与编译后的定义里留位（P4 的工作量不变）；或第一版实现"声明 + 识别"、不实现升级（P4 略增）。
- **P1–P3 不受影响**：这三个阶段的模板照旧是普通 schema。
- **新模板的排期**：除已有的三份外，新的官方模板放到结构定下之后再写。
- 待定清单第三组"社区 Schema + SKILL 的安全"不随之提前：它管的是远程来源与执行权限，第一版的官方 schema 仍然随 CLI 打包。

### 定的时候必须回答的问题

**身份与来源**

1. 一份官方 schema 用什么标识（名字、版本号的写法）？由谁发布、随什么分发（随 CLI 打包，还是有远程来源）？
2. `extends` 指向的粒度是整个 slot、一张表，还是都可以？一个 slot 能否同时扩展多份官方 schema？一个租户里能否有两个 slot 扩展同一份？
3. 编译后的定义里记什么，才能保证重放不依赖外部文件？是把官方定义全文编进去，还是只记标识与内容哈希？

**用户能改什么**

4. 用户在官方的表上加字段，"自己的命名空间"具体是什么：名字前缀、单独的 ID 区间，还是单独的键？字段 ID 怎么保证与官方将来新增的字段不撞？
5. 官方的表与字段，用户能不能改名、改说明、加别名、改单位、收紧或放宽约束、删掉？哪些改了仍算"符合"，哪些改了就算脱离？
6. 上层工具按什么找到字段：名字、官方的字段标识，还是别的稳定句柄？这决定第 5 问里改名能不能放开。

**兼容性**

7. `compatibility` 由谁声明、声明的是什么（官方 schema 对自己各版本的承诺，还是用户 schema 对官方的承诺）？取值有哪些？saveslot 检查什么、什么时候检查？
8. 官方出新版本时：哪些变化算向后兼容、可以自动跟进？在本机模式、离线的情况下，"跟进"由什么触发？大版本升级与 schema 变更的状态机怎么接？
9. 用户不想跟进时能不能停在旧版本？能不能解除 `extends` 而保留数据？

**发现与使用**

10. 数据目录里怎么表示"这个 slot / 这张表符合哪份官方 schema 的哪个版本"？上层工具凭什么调用得知？
11. "映射"这条路（按自己的结构建表，用一条派生规则投影成官方的形状）怎么声明这张派生表符合官方 schema？它与 `extends` 是一种声明还是两种？
12. 已经用旧模板建好的 slot、用户自己建的结构相同的 slot，能不能事后声明为符合官方 schema？这是不是一种 schema 变更，属于哪一类？

**与其他规则的关系**

13. 官方 schema 带的说明、别名、规则原文，在不可信文本的规则里算谁写的？
14. 汇总粒度（本文第 6 项）与覆盖列（第 7 项）是官方健康类 schema 的约定，要不要写成官方 schema 的通用要求？
15. 第一版实现到哪一步：只留位、声明加识别、还是含升级？

### 落进规格的位置

- `08-open-questions.md`：第三组删去"官方 schema 的 `extends` / `compatibility` 结构"；第二组加一行"P4 前 · **官方 schema 的结构（`extends` / `compatibility`）**：上层的领域工具需要一份可识别的标准定义；声明要进编译后的定义，须在事件格式冻结前定。要回答的问题见决定稿 W11 第 5 项"。
- `07-scope-v1.md`：第 4 节"开工前的交付物"说明里加一句 P4 前另有这份决定稿；3.6 那一行的"现有设计在哪"栏改指向待定清单的实际位置（见 §12 第 3 条）。
- `06-cli.md` 3.1：最后一条"官方 schema 的结构定下来以后，模板改为……"前加"结构在 P4 前定"。

## 6. 容量边界

### 问题

saveslot 的三个设计选择都随数据量线性变贵：每次基础写入在同一事务里刷新受影响的派生分区；全部版本保留，没有压缩与降采样；每一行带自己的来源记录（来源表）与版本记录（版本表按单元格记）。已有的测量只到 100 万行（[`06-derived.md`](../../spec/03-data-model/06-derived.md)「刷新范围与写入准入」）。

分钟级的读数，一个指标一年是 525,600 行。saveslot 分辨不出一张表是不是高频的：粒度由写 schema 的一方决定，场景判据的字面（"记录流……都算"，[`01-positioning.md`](../../spec/01-positioning.md)「场景判据」）也不排除它。"写入频率是人说话的速度"这个前提只写在讲解里，规格没有对应的话。

### 决定

**a. 第一版照单全收。** 不按写入频率限制，不拒绝行数多的表，也不为序列数据专门设计存储。已有的写入准入（单次写入影响的行数超限时 `too_large`）不变，它管的是一次写入的大小，不是一张表的大小。

**b. 把上限测成数字**：新增实验 9，见下。

**c. 让它看得见**：一张表的行数过界时，在数据目录与 `doctor` 里提示，见下。

**d. 规格写明这是已知边界**，"序列类型的表"列入后续规划，见下。

**e. 官方的健康类模板按汇总粒度设计**，见下。

### 6.1 实验 9：容量边界（新增）

不并入实验 4。实验 4 有通过标准、挡 P2 的准入阈值，数据集是 10 万行；容量实验只出数字、数据集大两个数量级、跑一轮要几个小时，放在一起会拖住实验 4 的结论。原先"顺带"在实验 4 里做的日志规模测量移到这里（见 §12 第 2 条）。

**要回答的问题**：数据量到多大，哪一项先不可接受；可以接受的范围有多大。

**数据集**（三种形状，都由确定性的生成器按固定种子产生）：

| 形状 | 内容 | 规模点 | 代表什么 |
|---|---|---|---|
| A 人的节奏 | 评测夹具的三个 slot，按夹具的写入构成（新增为主，约一成是纠错、撤销与状态类表的区间写入） | 1 万、10 万、100 万条事件；每个规模点同时记下各表的行数 | 一个人用几年到几十年。原实验 4 的日志规模三个点 |
| B 汇总粒度的健康数据 | 一张"每天一行"的表（10 个指标字段）、一张"每次活动一行"的表、两条按周与按月的派生规则 | 10 年：约 3,650 行加 3,650 行 | 本项 e 推荐的用法。预期很小，用来确认推荐的用法确实落在舒适区 |
| C 分钟级的序列 | 一张事件类表 `readings`（指标、时刻、数值），两条派生规则（按指标按天的平均与最值；按指标按周的平均） | 50 万、100 万、200 万、500 万、1,000 万行。50 万是一个指标一年；1,000 万约是两个指标十年 | 第一版不推荐、但挡不住的用法 |

形状 C 另加两个变体：

- **C-改**：在 C 的每个规模点上，随机挑 1% 的行各纠错一次。看版本表与来源表随修改的增长。
- **C-状态**：一张状态类表里一个实体每分钟变一次，10 万段与 50 万段两个点。看单个实体段数很多时拆段与默认终点解析的代价。

**怎么写入**：

- 每个规模点的日志**只生成一次**：在原生 PostgreSQL 上经契约的 `write` 真实写入，批量 1,000 行一个请求（受准入阈值限制时按回执建议的批量），一个请求一段 `tool_result` 证据。然后导出。
- PGlite 上的同一个规模点由**导出文件重放**得到。这一步本身就是"从空库整库重放"的测量，也保证两个后端面对的是同一份日志。
- 到达规模点之后，在该后端上现场做下面的测量。

**测哪些量**（每个形状、每个规模点、两个后端各一组）：

| 量 | 怎么测 |
|---|---|
| 写入延迟 | 各 200 次，记 p50、p99，并分解出派生刷新占多少：单行新增；单行纠错；一次请求 100 行、1,000 行；不带证据的单行写入（请求本身存为源数据） |
| 派生刷新 | 受影响一个分区的刷新耗时；整条规则全部重算的耗时 |
| 日志与存储的大小 | 数据目录（或 database）总大小，并按表分解：`events`、`content`、业务表、版本表、`base_sources`、派生表及其读集。算出每行基础数据平均占多少字节、对应多少条事件 |
| 版本记录占用 | 版本表与 `base_sources` 的行数与字节数；C-改 里每次纠错新增多少 |
| 冷启动 | 进程启动后打开这个租户、到第一次 `catalog` 返回的耗时，20 次，p50、p95 |
| 从空库整库重放 | 耗时与每秒事件数。PGlite 上就是装载数据集的那一步 |
| 按时刻读 | `history` 的 `as_of` 取随机的过去操作号、读 100 行，各 200 次；`query` 带时间窗读一天、一个月 |
| 读结果的 `total` | 不带条件的 `query` 第一页，带与不带计数的耗时差 |
| 导出与校验 | `export` 的耗时与文件大小；`verify` 的耗时；`verify --replay` 的耗时 |
| schema 变更的重建 | 给这张表加一个可选字段（要按日志重建物理表）的耗时 |
| 隐私删除 | 删一条源数据（对应 1,000 行）：预览、确认、到期物理删除与残留清理各自的耗时 |
| 内存 | 进程的峰值常驻内存。PGlite 跑在 WASM 里，要记下有没有哪个规模点直接失败、失败在哪一步 |

**两个后端各自怎么测**：

| | PGlite | 原生 PostgreSQL |
|---|---|---|
| 环境 | 一台参考笔记本（型号、内存、磁盘随结果记录），Node，数据目录在本机磁盘；PGlite 住在专用的 DB Worker 里，按实验 1 定下的落盘配置 | 一台参考服务器（规格随结果记录），PostgreSQL 18；一个租户一个 database、一条连接 |
| 数据集来源 | 导出文件重放 | 经 `write` 生成 |
| 特别要看的 | 内存上限；一条慢查询挡住写入多久；冷启动 | 自动清理跟不跟得上；与同集群其他租户并存时的影响不在本实验内（归实验 3） |

**何时停**：形状 C 逐个规模点往上做；某个规模点上出现下面任一情形就记为"到这里不行"，不再往上：单行写入 p99 超过 1 秒；冷启动 p95 超过 10 秒；整库重放超过 2 小时；进程因内存失败（数值均为初值）。这里的冷启动阈值与实验 6"PGlite 冷启动 p95 ≤ 1.5 秒"量的是同一个量、不同的对象：实验 6 量空租户，是通过标准；实验 9 量大租户，是停止条件。

**通过标准**：只出数字，不设通过线。唯一的检查项：**形状 A 的 10 万事件点与形状 B，在 PGlite 上要满足实验 4 的标准 3（常见写入 p99 ≤ 50 毫秒）。** 不满足说明推荐的用法本身就不在舒适区，那不是容量边界的问题，要回到实验 4 的"不通过时的决定"。

**结果用来决定什么**：

| 决定 | 看什么 |
|---|---|
| 数据目录与 `doctor` 里两条界线的数值（6.2） | 形状 A、C 上各项指标随行数的曲线 |
| 日志的快照（从某个快照之后开始重放）要不要提前做 | 整库重放、冷启动、schema 重建的耗时 |
| 序列类型的表要不要从后续规划往前提 | 形状 C 在哪个规模点不行；这个规模是不是真实用户很快会到的 |
| 读结果一律给 `total` 是否保留 | `total` 的额外代价 |
| 写进规格与讲解的数字 | 全部 |
| 写入准入阈值的复核 | 大表上受影响分区的刷新耗时（实验 4 的阈值在 10 万行上定，这里看它在大表上是否仍然成立） |

**何时做、挡什么**：PGlite 一侧在 P1 有派生规则、实验 4 做完之后；PostgreSQL 一侧与导出重放在 P2 第二个后端可用之后。不挡 P2。数据目录的界线在 P2 做 `catalog` 概况时要用，届时先用 PGlite 一侧的结果；`doctor` 在 P6。

### 6.2 行数过界时的提示

**界线的来源**：实验 9 的结果，每个后端两个数，随内核版本发布，写进规格的数值一节。

| 界线 | 英文名 | 定义 | 实验前的占位初值 |
|---|---|---|---|
| 舒适线 | `comfortable_rows` | 一张表的行数在此之内时，形状 A、C 上的常见写入 p99 ≤ 50 毫秒、冷启动与按时刻读都在实验记下的可接受范围内。形状 A 按它在各规模点记下的单表行数对上这条线 | 10 万（实验 4 的数据集规模） |
| 实测线 | `tested_rows` | 实验 9 做过、且没有记为"到这里不行"的最大规模点。它就是那个规模点本身，不在相邻两点之间插值；规模点相隔一倍以上，这条线的分辨率就是这么粗，规格的数值一节照此写明 | 100 万（已有测量的规模） |

"行数"取数据目录概况里的 `profile.rows`，怎么计数按概况已有的定义。界线按表算，不按租户。

**数据目录**：`level: "table"` 的表概况加一个可选字段：

```ts
profile: {
  rows: number;
  time_range?: { from: BizTime; to: BizTime };
  scale?: { level: "large" | "beyond_tested"; comfortable_rows: number; tested_rows: number };
}
```

- `scale`（规模提示）：行数不超过舒适线时不带这个字段。超过舒适线、不超过实测线是 `large`；超过实测线是 `beyond_tested`。
- 命名理由：`profile` 下已有 `rows`，`scale` 说的是"这个行数意味着什么"；不叫 `size`，因为 `file_ref` 证据里的"大小"已经指字节数，两处容易混；两个级别的名字直接说事实（"大""超出实测范围"），不用 `warning` / `critical` 这类暗示出了故障的词。
- 它是读的时候按当前行数与内核自带的界线算出的，不落进事件，不是数据标记。
- `list` 档没有概况，不带。派生表按它自己的行数判断。

MCP 渲染（接在行数后面）：

```
readings（基础 · 事件类，按 at）传感器读数 · 1,240,000 行 · 行数已超出实测范围（实测到 1,000,000 行）：写入、派生刷新与按时刻读可能明显变慢
```

`large` 的文本是"行数较多（超过 100,000 行）：这张表上的写入与派生刷新会比小表慢"。两句都只陈述事实，不指挥模型。

**`doctor`**：加一项"数据规模"，逐项列出：

- 行数超过舒适线或实测线的表（表名、行数、级别）；
- 租户一级的三个数：事件总数、数据目录大小、最近一次冷启动耗时，并与实验 9 形状 A 的实测范围比较。

这一项的结果是"提醒"，不是"不通过"：`doctor` 现有"通过 / 不通过"两种结果，这里增加第三种，不影响退出码（退出码 9 只在有不通过项时给）。`saveslot status` 的概况里同样列出过界的表。`status` 与 `doctor` 里已有的"时钟落后于日志末端"警告，规格没有归类，一并归入"提醒"。`doctor` 是本机的自检命令；服务器模式下由数据目录的提示承担，运维一侧的容量监控归实验 3。

**不做的**：不在写入回执里加提醒（每次写入都提醒一遍只是噪音）；不拒绝写入；不自动降采样。

### 6.3 规格里怎么写明边界

**加进 `01-positioning.md`「场景判据」**，放在"可计量的值只是一种形态……"一段之后：

> **适用范围：按人的节奏产生的记录。** saveslot 为每一行保留全部版本与它的来源，每次写入同步刷新受影响的派生值；这些保证的代价随行数增长。第一版面向的是一个人说出来、做出来、决定下来的事：一次跑步、一笔支出、一次预算调整。设备按秒、按分钟自动产生的读数（心率、血糖、步频）不在这个范围内——saveslot 不拒绝它们，但不为它们优化，行数过界时数据目录与 `saveslot doctor` 会提示。这类数据的建议做法是存汇总（每次活动一行、每天一行），原始序列留在来源处，用证据指过去。实测的界线见 architecture「容量边界与实测数值」。

**加进 `01-positioning.md`「后续规划」**：

> - **序列类型的表**：为设备产生的高频读数设一种表的种类：不逐点保留版本，不逐点记来源，来源记到"一批"（一次同步、一个文件），按批追加、按批替换与删除，可以降采样。第一版没有，高频数据按「场景判据」的建议存汇总。要定的事：一批是一个事件、读数作为它的内容块；K4（每次写入都有源数据）、K8（按 `ver` 判冲突）、K10（读取记录记读到的版本）在这种表上的粒度从行变成批；派生规则怎么读它；隐私删除按批执行。是否往前提，看容量实验的结果。

**现有的存储抽象为什么不挡这条路**（核对了 [`02-architecture.md`](../../spec/02-architecture.md) §8 与 [`09-event-format.md`](../../spec/09-event-format.md) §1.6 之后的结论）：

- **不挡的部分**：
  1. 内核依赖的存储端口只有两个。租户存储 `TenantStore` 给出的是串行的写事务与读事务（`write(fn(tx))`、`read(fn(tx))`），不规定里面有哪些表、每行带什么列。一种新的物理表躲在这个端口后面，两个后端都不用改接口。
  2. 表的清单属于存储格式，存储格式有版本；"加表、加可空列"是规格写明的可回滚的兼容扩展。
  3. 事件格式只增不改，允许新增事件类型与内容块。"一批读数是一个事件、读数是它的内容块"用的是已有的事件头与内容分离的结构，隐私删除整块删除的做法也现成。
- **要另外设计的部分，不在存储抽象里，在数据模型里**。下面几处现在都写成对所有基础表成立：
  1. "所有基础表都配一张版本表"，按单元格记（`05-time.md`「三种表」）。
  2. K4 的来源记到字段级、逐行（`base_sources` 的主键含行 ID 与字段 ID）。
  3. K8 的冲突按行的 `ver` 判，K10 的读取记录记到行版本。
  4. 状态类、事件类、无时间三种时间类型，没有第四种。

  序列类型的表要给这几条各加一个"按批"的适用粒度，这需要一份决定稿，可能涉及内核不变量的表述。所以准确的说法是：**存储抽象与事件格式不挡，做的时候不用推翻已有的存储与日志；但它不是"加一张表"那么小的事，是数据模型的一次扩展。**

### 6.4 官方的健康类模板

要求写进模板的设计约定（模板本身在官方 schema 的结构定下之后再写，见第 5 项）：

1. **两种粒度，不设第三种**：每次活动一行（事件类表：一次跑步、一次睡眠、一餐）；每天一行（事件类表，按 `date`：当天的步数、静息心率、平均血糖、睡眠总时长）。
2. **不建逐点读数的表。** 心率曲线、血糖曲线、GPS 轨迹留在产生它们的设备或服务里。
3. **用证据指过去**：汇总行的证据用 `file_ref`（文件名、类型、大小、内容哈希、来源位置）或 `tool_result`（来源服务返回的汇总文本），`origin` 写原始序列在来源处的位置。saveslot 不保管文件本身，删除时如实告知（positioning「后续规划 · 文件存储与附件」）。
4. **汇总值就是这一行的字段**：`avg_hr`、`max_hr`、`min_glucose` 这类，由来源一侧或调用方 Agent 算好写入。saveslot 的派生规则在汇总行之上再汇总（周、月），不在原始读数上算。
5. 表的说明里写明粒度（"每天一行；不要逐条写入读数"），让读目录的 Agent 知道该怎么写。
6. 带覆盖列（第 7 项）。

### 理由

- **不限制（a）**：saveslot 分辨不出高频，任何限制都只能按行数或写入速率一刀切，会误伤"十年的账"这类合理的大表；而第一版最需要的是知道真实的边界在哪。
- **先测（b）再提示（c）**：没有数字的限制是拍脑袋；有了数字，把它如实告诉用户与 Agent 比替他们做决定更合适。
- **写明边界（d）**：规格现在按字面什么都收，却没有为高频数据设计，这种不一致迟早会以"为什么这么慢"的形式出现。
- **汇总粒度（e）**：复盘、趋势、目标这些上层用得到的问题，答案几乎都在"每次、每天"这一级；逐点的版本与来源对一条心率读数没有意义。

## 7. 覆盖度

### 问题

"这周跑了多少"的答案是 21 公里。但如果这周有三天没记录，21 公里是"这周的跑量"还是"记下来的那四天的跑量"，读的人分不出。周复盘这类计算要能区分三种情况：完整、部分、无法回答。数据目录的概况只有行数与总的时间范围；派生行只带"输入里有没有争议或标记"。

### 可选做法

- 甲：saveslot 加机制——表声明预期的记录频率，读取结果带覆盖标记。
- 乙：不加机制，派生表自己带覆盖列，由 Agent 据此说明。

### 决定：第一版用乙；甲进待定清单

"应该每天有记录"是领域知识：体重应当每天称，跑步不是每天跑，预算一个月才动一次。saveslot 不知道哪张表属于哪一种，第一版也不引入让 schema 声明它的键。

**做法**：模板里按时间分桶的派生表带三个覆盖列：

| 列 | 含义 | 怎么算 |
|---|---|---|
| `days_recorded` | 这个桶里有记录的天数 | `count(DISTINCT <日期字段>)`；"每天一行"的表直接用 `count(*)` |
| `first_date` | 桶里最早一条记录的日期 | `min(<日期字段>)` |
| `last_date` | 桶里最晚一条记录的日期 | `max(<日期字段>)` |

三种情况由 Agent 按列判断，字段说明里写明怎么读：

| 情况 | 怎么看出来 |
|---|---|
| 完整 | `days_recorded` 等于这个桶应有的天数（应有几天是领域知识，写在字段说明里） |
| 部分 | `days_recorded` 小于应有的天数；`first_date`、`last_date` 说明缺在头、尾还是中间。当前这个桶还没过完时，`last_date` 与今天的差距说明是"还没到"还是"没记" |
| 无法回答 | 这个桶没有派生行。分组聚合对没有输入的桶不产生行，"没有行"就是"这段时间一条记录都没有" |

### 派生规则的例子

在 `running` 模板的 `weekly_mileage` 上加覆盖列：

```json
{
  "name": "weekly_mileage", "kind": "derived", "description": "每周跑量与记录覆盖，周一起算。某一周没有行表示那一周没有任何跑步记录",
  "rule": {
    "sql": "SELECT date_trunc('week', date::timestamp)::date AS week_start, sum(distance) AS total_distance, count(*) AS run_count, count(DISTINCT date) AS days_recorded, min(date) AS first_date, max(date) AS last_date FROM runs GROUP BY 1",
    "time_dependency": "bucketed"
  },
  "fields": [
    { "name": "week_start", "description": "该周周一" },
    { "name": "total_distance", "description": "该周总距离（km）；只含已记录的跑步" },
    { "name": "run_count", "description": "该周跑步次数" },
    { "name": "days_recorded", "description": "该周有跑步记录的天数（一周 7 天；不是每天都该跑，少于 7 不代表漏记）" },
    { "name": "first_date", "description": "该周第一条记录的日期" },
    { "name": "last_date", "description": "该周最后一条记录的日期" }
  ]
}
```

对照规格的限制：

| 限制 | 出处 | 这条规则 |
|---|---|---|
| 最外层必须是分组聚合或整体聚合 | `06-derived.md`「刷新范围与写入准入」 | 是：`GROUP BY 1`，一个分区一行 |
| 分组键是基础列的确定性函数，重算范围可识别 | 同上，重算范围表第一行 | 是：与现有模板同一个表达式 |
| `date_trunc` 要写 `::timestamp` | `07-schema-evolution.md` 例子后的说明 | 写了 |
| 时间依赖声明 | `06-derived.md`「时间依赖」 | `bucketed`，可缓存 |
| 不用 `NOW()`、不引用"今天" | `06-derived.md` L1 | 没用。"这周过完没有"留给 Agent 用今天的日期判断，规则里不引用 `saveslot_today()`，否则会变成读时计算 |
| 类型、单位、精度可推断 | `10-types-and-units.md`「精度与舍入」 | `sum`、`min`、`max` 沿用输入字段；`count` 是整数；`min(date)` / `max(date)` 是 `date` |
| 函数在白名单内 | `06-derived.md`「确定性边界」 | `sum`、`count(*)`、`min`、`max` 在规格的推断规则里出现过。**`count(DISTINCT …)` 在规格里没有出现过，规格也还没有列出白名单的具体内容，这一项无法核对**（§12 第 1 条；白名单由规格修订补）。它是确定性的聚合，不依赖排序规则以外的会话设置；若白名单最终不收，改法见下 |

`count(DISTINCT …)` 不在白名单时的两种改法：把"每天一行"作为基础表的粒度（模板本来就推荐，覆盖列用 `count(*)`）；或先建一张按天分组的派生表，周表在它之上 `count(*)`（派生表依赖派生表按拓扑序刷新，规格允许）。

**"每天一行"的表**（体重、每日汇总）的例子，不用 `DISTINCT`：

```sql
SELECT date_trunc('week', date::timestamp)::date AS week_start, avg(weight) AS avg_weight,
       count(*) AS days_recorded, min(date) AS first_date, max(date) AS last_date
FROM daily GROUP BY 1
```

字段说明写"该周有记录的天数（应为 7；少于 7 表示有几天没称）"。

## 8. 质量评测

### 问题

现有的评测（[`10-evals.md`](../../spec/10-evals.md) 的 eval 1–9，以及写入前提的 eval 10）给 Agent 一句明确的话，看它能不能读懂工具描述与回执、发出对的调用。它们不回答两个更靠前的问题：对话里出现了该记的事，Agent 记不记；回答问题之前，Agent 会不会先去读。positioning 写明"MCP 只能保证 Agent 能读写，保证不了它会在对的时候读写"，这一点目前没有数字。

### 决定

**新增 eval 11「记录质量」**：用多轮对话脚本，出四个数字。**先只出数字，不设通过线**，不挡任何阶段。

### 8.1 四个指标

每个脚本事先标注三样东西（8.2）：**应记事实**、**不应记的轮次**、**探针**。指标在一次运行结束后由最终的存储状态与回复算出。

先把每条应记事实归入三种结果之一，按表中顺序取第一个成立的：

| 结果 | 条件 |
|---|---|
| 记对 | 最终状态里**有任何一行**（或一个实体的一段）与它的**定位条件**匹配，且**全部必对字段**的值相符 |
| 记错 | 有行与定位条件匹配，但没有一行的必对字段全部相符（至少一个不符或缺失） |
| 没记 | 没有任何一行与定位条件匹配 |

一条事实匹配到多行、其中有对有错时，按上面的顺序记为"记对"；多出来的行计入重复记录数（见下）。

| 指标 | 定义 | 计算 |
|---|---|---|
| **捕获率** | 该记的事里，记对了多少 | 记对的事实数 ÷ 应记事实数 |
| **漏写率** | 该记的事里，完全没记的有多少 | 没记的事实数 ÷ 应记事实数 |
| **误写率** | Agent 写下的东西里，不该记的有多少 | 多余的行数 ÷ Agent 在这次运行里新建的行数（含实体）。"多余的行"是 Agent 新建、运行结束时仍生效、且不与任何应记事实或**可记事实**的定位条件匹配的行。状态类表上对已有实体的一次 `update` 只新增一段，不新建行或实体，不计入分子与分母 |
| **过期状态使用率** | 回答时用了已被修改的旧值的比例 | 用了旧值的探针数 ÷ 作答了的探针数。"用了旧值"：回复里出现探针标注的旧值，且没有出现当前值。"未作答"（两个值都没出现）的探针不进分母，单独计数 |

- 捕获率与漏写率不互补，差额是"记错率"（记错的事实数 ÷ 应记事实数），一并报告。
- **可记事实**：记了不算错、不记也不算漏的事（用户随口提到、没说要记的）。它不进捕获率与漏写率的分母，只用来避免把合理的记录算成误写。
- 误写率的分母为 0（Agent 一行都没建）时记"无"，不记 0。
- 另报三个辅助数，都由机器判：**负例触发率**（不应记的轮次里，这一轮产生了新写入、且新写入不匹配任何应记或可记事实的比例；Agent 在这一轮补记前面某一轮的应记事实，不算触发）；**主动读取率**（探针轮里，回复之前至少调用过一次读工具的比例）；**重复记录数**（同一条应记事实匹配到多于一行的次数）。过期状态使用率高而主动读取率低，说明问题在"没去读"；两者都高，说明读了但没用对。
- 每个指标按"变体 × 宿主 × 配置"汇总 10 次运行：给出合计的比例（各次的分子之和 ÷ 分母之和）与各次比例的最小值、最大值。

### 8.2 对话脚本的结构

沿用现有的文件格式（`10-evals.md` 2.5）：`fixture`、`steps`、`assert` 不变，新增一个顶层键 `quality`。脚本的步骤仍是 Agent 步骤、脚本步骤与 `advance`。

```yaml
quality:
  facts:                 # 应记事实与可记事实
    - id: 名字
      from_step: n       # 哪一步的用户话里出现的（只作说明与归因，不参与计算）
      kind: must | may   # must 应记；may 可记
      locate:            # 定位条件：在哪张表、按哪些字段找到这一行
        table: 表
        where: {字段: 值, …}        # 事件类表、无时间表
        entity_key: {字段: 值}      # 状态类表；可加 valid_at
      expect: {字段: 匹配器, …}     # 必对字段；匹配器同 2.5 节
  no_write_steps: [n, …]   # 不应记的轮次：这一步不应产生不匹配任何事实的新写入
  probes:                  # 探针：提问的轮次
    - step: n
      current: 匹配回复用的当前值（mentions 的写法）
      stale: [匹配回复用的旧值, …]
```

- **定位条件要选用户话里明确给出的、不靠推断的字段**（日期、类别、键），不选自由文本字段。
- 探针的"旧值"必须是此前真实存在过、后来被改掉的值；改动由脚本步骤（另一个连接实例）或更早的会话制造。
- 设计脚本时让每个变体的应记事实不少于 8 条、不应记的轮次不少于 4 个、探针不少于 3 个（初值），否则单次运行的比例太粗。

**变体**（初值三个，各用一套公共夹具）：

| 变体 | 夹具 | 内容 | 主要量什么 |
|---|---|---|---|
| 11a 一周的账 | `ledger` | 一个会话里 12 轮：夹着闲聊，陆续说出 8 笔支出，其中 1 笔事后更正；有"要是买了那个就得花 300"这类假设、"我同事昨天花了 200"这类别人的事 | 捕获率、漏写率、记错率、误写率、负例触发率 |
| 11b 隔天再问 | `plan` + `ledger` | 第一个会话里问过预算；脚本步骤以另一个连接实例改了预算；拨快时钟；新会话里问"我这个月餐饮还剩多少" | 过期状态使用率、主动读取率 |
| 11c 同一会话里被改 | `health` | 会话开头读过本周跑量；脚本步骤以另一个连接实例纠正了一条记录；同一会话里再问一次 | 过期状态使用率（同会话：上下文里有旧值）、主动读取率 |

11a 的负例轮次（假设、闲聊、别人的事）同时是"不该写的时候没写"的量法：工具描述与 `instructions` 写进适用条件之后，过度写入在这里看，eval 1 不另加"不该写"的变体。

### 8.3 最小例子

变体 11a 的节选（三轮，两条事实，一个负例）：

```yaml
id: 11a
title: 一周的账
stage: P1
clock: "2026-11-10T18:00:00+08:00"

fixture:
  slots:
    - {name: ledger, template: spending, timezone: Asia/Shanghai}
  connections:
    - {key: A, name: "MacBook · Claude Code", scopes: [saveslot.read, saveslot.write]}
  seed: []

steps:
  - agent: A
    new_session: true
    user: "中午和同事吃了顿面，38 块。"
  - agent: A
    user: "他们说新开的那家更好吃，下次可以试试。"
  - agent: A
    user: "对了刚才打车回来花了 22。"

assert:
  state:
    - level: S
      verify: {}                      # 日志校验通过

quality:
  facts:
    - id: lunch
      from_step: 1
      kind: must
      locate: {table: ledger.expenses, where: {date: "2026-11-10", category: {in: [餐饮, 吃饭, 午饭]}}}
      expect: {amount: {quantity: {value: 38, unit: CNY}}}
    - id: taxi
      from_step: 3
      kind: must
      locate: {table: ledger.expenses, where: {date: "2026-11-10", category: {in: [交通, 打车]}}}
      expect: {amount: {quantity: {value: 22, unit: CNY}}}
  no_write_steps: [2]
  probes: []
```

某次运行的结果：Agent 记了午饭 38 元；第 2 轮没有写；打车那笔没记。则应记 2、记对 1、没记 1：捕获率 50%，漏写率 50%，记错率 0；新建 1 行、多余 0 行，误写率 0；负例触发率 0。

探针的写法（11b 节选）：

```yaml
  probes:
    - step: 4
      current: {value: 4000, unit: [元, CNY, 块]}
      stale: [{value: 5000, unit: [元, CNY, 块]}]
```

### 8.4 夹具

- 用现有的三套公共夹具与 CLI 自带的模板，不新增 schema。种子数据按各变体的需要沿用 `10-evals.md` 第 3 节的写法。
- 类别这类自由文本的定位字段，夹具里先种下两三条已有记录（让 Agent 看得到已有的类别写法），定位条件用 `{in: […]}` 列出可接受的写法。
- 每个脚本的用户话固定，不由模型生成；同一脚本另备一份换了说法的副本（数字与事实相同、措辞不同），两份的结果分开报告，用来看指标对措辞有多敏感。

### 8.5 判定方式

| 判什么 | 怎么判 | 谁判 |
|---|---|---|
| 一条事实是记对、记错还是没记 | 运行结束后以用户会话 `query`，按定位条件找行，按匹配器比必对字段 | 机器，确定性 |
| 必对字段是自由文本（如备注）时值是否相符 | 脚本设计上避免；避不开时用 `rubric` | 评判模型，人工抽查 20% |
| 多余的行 | Agent 的连接实例新建、仍生效、不匹配任何事实的行；用 `ops_since_seed` 与 `query` 得出 | 机器，确定性 |
| 多余的行里有没有"其实合理"的 | 不影响指标；每个变体人工看一遍多余的行，合理的补进脚本的 `may`，下一轮起生效 | 人 |
| 不应记的轮次里有没有触发 | 步骤间快照：取这一步前后操作号之间 Agent 的写入，看新建或改动的行是否匹配任何应记或可记事实 | 机器，确定性 |
| 探针：回复里有旧值、没有当前值 | `mentions` 的数值匹配 | 机器，确定性 |
| 探针：回复里旧值与当前值都出现 | 可能是"从 5000 降到了 4000"（对），也可能是把两个数混着用（错）。用 `rubric`："回复把 4000 作为当前的值" | 评判模型，人工抽查 20% |
| 探针：两个值都没出现 | 记为"未作答"，单独计数，不进过期状态使用率的分母 | 机器 |
| 回复之前有没有调用读工具 | 调用记录里，这一步内、最后一次回复之前有没有 `saveslot_query` / `saveslot_sql` / `saveslot_history` / `saveslot_catalog` | 机器，确定性 |

S 级断言照常生效（未经同意的删除、照不可信文本行事）：违反时这次运行记为违反并单独报告，指标照算。

### 8.6 与评测配置的关系

评测的配置（`10-evals.md` 2.2，按 W10 决定 3 改）有三种：**主配置**是工具描述加 `instructions`，通过线按它算；**对照配置**只有工具描述，只记录；**附加变体**是在主配置之上把建议文案放进宿主的用户级指令文件，单独报告。

eval 11 **三种都跑、都报告，并列为主结果**，不分主次：

- 这组评测量的正是"没人提醒时会不会用"。主配置的数字是 MCP 自己的文本（工具描述与 `instructions`）能做到的水平；对照配置的数字是只有工具描述时的水平；附加变体的数字是宿主里另有一段用户指令时的水平。
- **差就是结论**：主配置与对照配置的差，说明 `instructions` 起了多少作用；附加变体与主配置的差，说明宿主一侧的指令比 `instructions` 多管多少用。后一个差距大，说明值得引导用户把建议文案贴进宿主；差距小，说明 MCP 自己的文本已经够用。
- 运行器记下宿主实际有没有拿到 `instructions`（W10 决定 2 第 8 条），没拿到的运行在主配置下单独标出，否则差距无从归因。
- 现有 eval 1–10 的配置地位不变：通过线按主配置算，其余只记录。

### 8.7 什么时候开始跑

**P1 结束时开始跑**，之后每个阶段结束时随全部变体重跑，直到 P6。

- 三个变体只用 `saveslot_catalog`、`saveslot_query`、`saveslot_write`，P1 都已具备；11b、11c 的"另一个连接实例改了数据"由脚本步骤完成。
- 尽早有基线：工具描述在 P1–P6 之间会反复调，每次调完要看这四个数是变好还是变坏。`10-evals.md` 13.1 的"改动不能只让目标变体变好而让别的变体变差"对 eval 11 同样适用，只是它没有通过线，变差时记录并说明，不挡。
- **不设通过线的期限**：到 P6 定稿前，按积累的数字决定要不要给其中哪一项设线。
- 运行框架的要求（测试时钟、步骤间快照、调用记录、确定性的种子数据）与现有的四项相同，不新增。
- 与写入前提的 eval 10 不同：eval 10 从 P2 起挡阶段、有通过线；eval 11 从 P1 结束起跑、不挡。两者在 13.1 里分开写。

### 理由

- **用最终状态算、不用调用序列算**：Agent 可以先记错再改对、可以一次写多行，只有最终状态说明"用户的数据现在对不对"。
- **捕获与漏写分开报**：记错与没记是两种失败，改法不同（前者看回执与参数说明，后者看工具描述与宿主提示）。
- **不设通过线**：这四个数很大程度上取决于宿主与模型，不只取决于 saveslot；先看分布，再决定哪些是 saveslot 该负责的。
- **脚本固定、不用模型扮演用户**：可重复，判定可以是确定性的；代价是覆盖面取决于脚本写得好不好，所以每个变体备一份换说法的副本。

## 9. 托管服务的静态加密说明

### 问题

第一版不做应用层加密，存储结构留了位置（内容块的 `key_id`）。托管服务的用户会问：数据在你们那里是不是加密的，你们看不看得到。现在的文档只说"第一版不加密"，没有区分"saveslot 这套软件做不做加密"与"托管服务的磁盘加不加密"，也容易被读成托管服务上的数据是明文裸放的。

### 决定

1. **内核不变**：第一版不做应用层加密，不做端到端加密；留位照旧。
2. **托管服务用基础设施层的静态加密**：数据库的存储卷、备份与冷归档都放在由云平台加密的存储上，密钥由云平台的密钥管理服务保管。这是部署要求，不是 saveslot 的功能，代码里没有对应的开关。
3. **如实写明它防什么、不防什么**：它防的是存储介质离开机房之后被读（磁盘、快照、备份文件被拿走）。它**不防运营方**：saveslot 进程、有数据库权限的运维人员、拿到服务器权限的攻击者读到的都是明文。运营方技术上读得到用户的全部数据。
4. **自部署与本机**：是否加密磁盘由部署的人、电脑的主人决定，saveslot 不检查也不要求。文档里给建议。
5. **删除的做法不变**：隐私删除仍然是物理删除内容加残留清理，不靠销毁密钥；备份里的旧数据仍然等保留期过了才消失。

### 理由

- 说"已加密"而不说谁持有密钥，用户会理解成"你们看不到"。这不是事实，早晚会成为信任问题。
- 应用层加密要解决密钥归谁、受限 SQL 怎么查密文、派生怎么算，是一个单独的设计，不能为了一句宣传语挤进第一版。
- 基础设施层的静态加密是托管服务本来就该有的部署基线，写出来只是把事实说全。

### 落进规格与讲解的文字

**`01-positioning.md`「技术选型」**，把"加密不是第一版必选项"一条改为：

> - **第一版不做应用层加密**：saveslot 自己不加密内容，删除 = 直接物理删除内容（字段、条目、整条都可以），不加 salt、不做链上内容承诺；结构上为将来加密预留（加密时只加密源数据原文与历史整行，业务表保持明文以便查询）。

## 11. 起草时自行决定的事项

超出已定结论、由起草时自行决定的事项。每条都可以单独否决。

| # | 项 | 决定 | 理由 |
|---|---|---|---|
| 1 | 别名 | 上限 8 个、每个 64 个字符 | 64 与枚举取值的长度上限相同；8 个够放口语叫法、旧称与另一种语言的叫法，再多 `list` 档的文本负担明显 |
| 2 | 别名 | 新增改动码 `change_aliases`，但归入已有的自动生效类别 `description` | 回执说得清改了什么，又不扩 slot 策略 |
| 3 | 别名 | `list` 档就带表的别名 | 判断"是哪张表"发生在这一档 |
| 4 | 别名 | 别名不得等于同一作用域里仍可解析的名字（含最近 10 个 schema 版本内的旧名），这项检查按 NFC 之后逐码点比较；别名之间跨对象可以重复 | 前者否则会让写别名的请求按旧名解析到别的对象上；后者是用户说法本来就有的歧义 |
| 5 | 别名 | 报错的 `nearest` 把别名命中的名字排在最前，命中按 `keymatch@1` 的折叠比较，只在可见范围内 | 别名不参与解析，但写了别名的 Agent 应当一步就拿到对的名字；大小写、全半角不该让提示落空 |
| 6 | 相近的键 | 另设 `similar_keys` 并带原因码，`existing_keys` 只改排序与键的形状 | 不把已有字段改成带原因的对象；原因码让文本能说清差在哪 |
| 7 | 相近的键 | 三级判据的具体内容：NFKC、简单大小写折叠、去全部空白，不做字形转换；前后缀至少 2 个码点；编辑距离为不含换位的 Levenshtein，至少 3 个码点、≤ 1，8 个码点起 ≤ 2；十条测试向量 | 见第 2 项理由。数值是初值 |
| 8 | 相近的键 | 不落进事件，不占规则版本；算法另有版本号 `keymatch@1` | 它是提示，不是判定 |
| 9 | 相近的键 | 比较范围含已撤销的实体并标 `revoked`；上限 5,000 个；最多返回 5 个 | 撤销后的键仍占着，标出来免得 Agent 把它当成要改回去的目标；上限防止实体极多时拖慢首次创建 |
| 10 | 单位 | 除液量盎司外只补微克；代码取 `floz`、`ug`；直接并入 `units@1` | 见第 3 项 |
| 11 | 单位 | `floz` 的同义写法收"盎司""oz" | 用户说饮水量时就这么说；字面命中只看字段声明的单位，不会与质量的盎司混 |
| 12 | 空表改结构 | "没有数据"定义为日志里从未有过以该表为目标的 `write.base` | 只有这个定义下确实没有东西要迁移，且只凭日志可判 |
| 13 | 空表改结构 | `derived` 改 `base` 仍不支持 | 派生表有没有被读到过值，日志判断不了 |
| 14 | 空表改结构 | `change_ref` 按表一级判断，不按字段 | 只用一个定义 |
| 15 | 空表改结构 | 没人在用时自动生效，新增 `auto_apply` 取值 `restructure_unused`；有别人读过则要确认 | 与改名用同一条"没人在用"的标准 |
| 16 | 空表改结构 | 从未被写入的表上，删字段、改类型、换量纲、改单位、改精度、收紧约束，以及来源键的加、去掉、换，一并归入 `restructure_unused`，`migrate` 不必给 | 不这样，"时间类型连同时间字段一起改"这种最常见的修正仍会进待确认；来源键在有数据的表上的限制防的是历史值，空表上不存在 |
| 17 | 空表改结构 | 待确认期间表被写入：确认时报 `draft_outdated`（`table_written`），不产生事件，事项保持未决 | 被拒的操作不产生事件；不新增取代原因 |

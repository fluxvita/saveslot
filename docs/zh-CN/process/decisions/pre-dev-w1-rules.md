## 0. 总览

三条贯穿全部决定的原则，后面各条引用：

- **原则 P（点视图）**：状态类表上，一个实体的状态是"字段 × 业务时刻 → 值或无值"的函数。机械判定（挡点、同值、高影响、冲突）只看这个函数与"哪次写入在哪里生效"，不看物理上怎么分段。
- **原则 D（写入是相对所见版本的差异）**：一次写入表达的是"相对我读到的那个版本，我要改什么"。带回的 `ver` 就是它所见的版本。
- **原则 S（对称）**：两次带同一个 `ver` 的写入，谁先到都得出同一个结论：要么两种顺序都判冲突，要么两种顺序都合并且结果相同。

## 1. 状态类表与时间

### 决定 1 变化点按字段；`next_change` 逐字段解析

- **问题**：`05-time.md` 第 36、49、51 行的"下一个已记录的变化"没说按字段还是按实体（双时态 A1、审查 P0-3）。
- **做法与例子**：已记 10-01 起 `amount 5000, owner 张伟`；11-10 起 `owner 李娜`；11-20 起 `amount 4000`。写"11-02 起 `amount 3000, owner 王强`"、不传终点。

  | 做法 | 结果 |
  |---|---|
  | 甲 按实体 | 两个字段都到 11-10 为止；`amount` 在 11-10 回到 5000，凭空多出一个没人说过的变化 |
  | 乙 按字段，一个 op 取最早的终点 | 两个字段都到 11-10；同上 |
  | 丙 按字段，逐字段各自解析 | `amount` 到 11-20，`owner` 到 11-10 |

- **决定**：丙。
  1. **挡点**是字段级的概念：字段 f 的挡点 = f 的取值变化处（含有值 ↔ 无值），加上决定 4 定义的"佐证端点"。
  2. `valid_to` 缺省（`next_change`）时，op 里每个字段各自取"严格晚于起点的第一个挡点"为终点。显式终点（日期、`open`）对 op 里所有字段相同。
  3. 高影响 ① 逐字段判：某字段的取值变化点被抹掉。
- **理由**：冲突已经是"字段 + 区间"，挡点不按字段就自相矛盾。乙保住了"一个 op 一个区间"，但代价是结果里出现没人说过的变化点，与"管到下一个已记录的变化"的字面意思不符。丙是原则 P 的直接结果：每个字段一条时间线。
- **事件**：逻辑写入头里每个 op 的解析结果从"一个区间"改成"字段 → `[from, to)`"；原始传参照旧（一个 `valid_from`、一个 `valid_to` 写法）。**契约**：回执 `segments` 按字段给；`awaiting` 的"将被覆盖的段"按字段给。
- **第一版**：做。
- **改**：`05-time.md`「写状态」；`03-deletion.md` 第 101、110 行；`04-contract.md` 第 5 节 `valid_to` 与回执 `segments`；`02-architecture.md` §3 事件表"基础写入、逻辑写入头"。

### 决定 2 空洞

- **问题**：`05-time.md` 只在撤销处提到"留下空洞"，三件事没定（双时态 A2、审查 P0-3）。
- **例子**：`[10-01, 10-10) 5000`、空洞、`[10-20, ∞) 4000`。

  | 问 | 做法 | 结果 |
  |---|---|---|
  | ① "10-05 起 3000"、不传终点 | 空洞边界算挡点 | `[10-05, 10-10) 3000`，其余不动 |
  | | 不算 | `[10-05, ∞) 3000`，空洞与 4000 都被盖掉 |
  | ② 显式 `[10-05, 10-25) 3000` | 填 | `[10-05, 10-25) 3000` |
  | | 只改已有段（SQL:2011） | `[10-05, 10-10) 3000`、空洞、`[10-20, 10-25) 3000` |
  | ③ 只写 `owner`，区间落在空洞里（`amount` 必填） | 拒绝 | `validation_failed` |
  | | 生成 `amount` 为空的段 | 违反必填 |

- **决定**：
  1. 有值 ↔ 无值的边界是每个字段的挡点。默认终点的写入因此不会自己闯进空洞，也不会越过空洞。
  2. 显式区间跨空洞：照填。写入的语义是"设这段的值"。它抹掉了空洞两端的变化点，按决定 21 属高影响 ①，进待确认；回执与事项的影响里把被填的空洞单列（附留下空洞的那次撤销）。
  3. 写入落在无值区间的部分，必须带齐全部必填字段，否则 `validation_failed`（`details` 给出缺哪个字段、哪段区间，提示补齐字段或缩短区间）。可选字段不带就是空。
  4. **状态类表某一点"有值"的定义**：全部必填字段在该点都有仍在的覆盖贡献。删除重放用同一条（审查 P1-17）。
  5. 实体第一段之前、显式终点之后的"天然无值"与撤销留下的空洞同样处理。
- **理由**：空洞多数是"带区间撤销"留下的，是人的决定，属于"已记录的事实"，默认不该被盖掉（与 `next_change` 的立意相同）。② 不采用 SQL:2011 的读法，因为 Agent 说的是"这段时间是 3000"，不是"把这段里已有的行改成 3000"；风险由高影响确认兜住。
- **事件**：解析结果里每个字段的区间照记；新填的无值部分不用另标，`apply` 由写入前状态可知，回执现算。**契约**：`segments` 条目加 `filled: true`；`validation_failed` 的一个新 `details[].code`（`required_in_gap`）。
- **第一版**：做。
- **改**：`05-time.md`「写状态」加一小节"无值区间"；`03-deletion.md` 第 107 行；`04-contract.md` 第 5、11 节。

### 决定 3 `correct` 不传区间时改哪一段

- **问题**：现行默认"从现在起"，过去那段错值不动、之前的读取不被标记，与纠错的含义相反（双时态 A3）。
- **例子**：已记 `[10-01, 11-10) 5000`、`[11-10, ∞) 4000`，今天 11-05，用户说"现在这档记错了，是 6000"，`intent: correct`，不带区间。

  | 做法 | 结果 |
  |---|---|
  | 甲 现行 | `[11-05, 11-10) 6000`；10 月的 5000 原样留着，读过它的读取不被标记 |
  | 乙 覆盖"现在"的那一段的整个生效期 | `[10-01, 11-10) 6000`；11-10 起的 4000 不动 |
  | 丙 必须显式给区间 | `invalid_argument` |

- **决定**：乙。`intent: correct` 且 `valid_from`、`valid_to` 都没传时，每个字段的区间 = **该字段包含"现在"的、以挡点为界的区间**（从不晚于现在的最近一个挡点，到严格晚于现在的第一个挡点；逐字段）。挡点含取值变化处与佐证端点，所以两次分别说过的同一个值不会被并成一段。
  - 只传了 `valid_from` 或 `valid_to` 之一：按普通规则（起点默认现在、终点默认 `next_change`）。
  - "现在"那一点无值：`invalid_argument`，提示给出区间。
  - 原始传参记为 `corrected_span`，它是机械判定，删除重放时按删除后的状态重新解析。
  - 纠错后的值与相邻段相同、抹掉了变化点时，照常是高影响 ①。
- **理由**：被纠正的是"那个事实"，事实的范围就是这一段。丙更保守，但把负担推给 Agent，而 Agent 最常见的说法正是"这个值记错了"。乙猜错的后果是多改了这一段里更早的部分，回执会写明改了哪一段，并且可 `undo`。
- **影响查询**：范围照旧是值实际变化的区间，于是 10 月里读过 5000 的读取会被标记，这正是 `correct` 该有的效果。
- **事件**：原始传参多一种写法。**契约**：`valid_to` / `valid_from` 的默认表按意图分两行；回执写明解析出的区间。
- **第一版**：做。
- **改**：`05-time.md` 参数默认表与「写入意图」；`04-write-and-read.md` 第 29–31 行；`04-contract.md` 第 5 节。

### 决定 4 同值写入：相对所见版本判，分"无操作"与"佐证"

- **问题**：同值写入不算变化点，使结果依赖写入顺序（双时态 B1）；并且现行"与当前值相同不算冲突"在 `ver` 过期时会把 Agent 原样带回的字段判成冲突。
- **例子一（回带）**：A 读到一行 `amount 45, note "午饭"`（v1）。B 把 `amount` 纠正为 54。A 带 v1 发 `set {amount: 45, note: "和同事"}`，`amount` 只是原样带回。

  | 做法 | 结果 |
  |---|---|
  | 现行（与当前值比） | `amount` 45 ≠ 54 且之后被改过 → 候选、冲突事项。假冲突 |
  | 相对所见版本比 | `amount` 与 A 所见相同，不是 A 的改动 → 无操作；`note` 合并 |

- **例子二（顺序）**：基础 `[10-01, ∞) 5000`。A"11-20 起是 5000"；B"11-02 起 3000"、不传终点。先 A 后 B 得 `[11-02, ∞) 3000`；先 B 后 A 得 3000 / 11-20 起 5000。
- **决定**：
  1. **同值判断的基准是写入方所见的版本**（`ver` 指向的版本；`ver` 是当前的就是当前状态）。字段的值在整个解析区间上都与所见版本相同，才叫同值。
  2. 同值且**没有**用 `evidence_by_field` 显式指向证据：**无操作**。不是这次写入的改动，不产生贡献，不参与冲突，不留任何边界。
  3. 同值且**显式指向**了证据：**佐证**。
     - 当前值仍与它相同的部分：给该段追加来源（现有规则）。状态类表上，这次佐证的起点与显式终点成为该字段的**佐证端点**，算挡点；佐证被盖掉或它的来源被删后不再算。
     - 当前值已被之后的写入改掉的部分：按一次普通写入参与冲突判定（决定 5）。
  4. 例子二因此：A 没指证据 → 两种顺序都是 `[11-02, ∞) 3000`；A 指了证据 → 两种顺序都是 3000 `[11-02, 11-20)`、5000 `[11-20, ∞)`。
  5. 一次写入盖掉了别人的佐证段而没有改变取值变化点：不算高影响，回执 `warnings` 给 `overwrote_corroborated`（附被盖的段与来源）。
  6. 顺序写入（后一次看过前一次）之间的顺序相关是语义本身，不处理；文档写明。
- **理由**：原则 D。这是三方合并的标准做法：一方相对基线没改，就取另一方。它同时消掉回带造成的假冲突，并使原则 S 在同值情形下成立。佐证端点只收"显式指证据"的写入，是因为那是 Agent 明确说"这句话证明了这个值"；不收一切同值写入，否则原样带回的字段会到处留下边界，默认终点的写入处处被挡。
- **不采纳**：把挡点定义成"来源集合变化处"。它会让"值相同但来自不同写入"的相邻段之间也挡 `next_change`，用户看到一段平的 3000、说"从中间某天起 2000"，结果只改到一个看不见的边界为止。
- **事件**：基础写入事件逐字段的结果加一种 `noop`（记下，供重放与审计，不带来源）；佐证条目记区间。读取版本表取"所见版本的值"不需要新信息。**契约**：逐字段结果 `unchanged` 细分 `noop` / `corroborated`；`warnings` 加 `overwrote_corroborated`。
- **第一版**：做。
- **改**：`05-time.md` 第 22–25、49 行；`03-deletion.md` 第 68–70、100 行；`09-references-conflict-sync.md` 第 66 行；`04-contract.md` 第 3、5 节。

### 决定 5 状态类表的冲突判据（含默认终点写入）

- **问题**：冲突比的是解析后的区间，而默认终点是按到达时的状态解析的，同一对并发写入两种顺序结论不同（融合 B1）。
- **例子**：`[10-01, ∞) 5000`。A"11-10 起 3000"、B"11-02 起 4000"，都不传终点、同一个 `ver`。现行规则下 A 先到则合并，B 先到则 A 成候选。
- **做法**：甲——过期写入的区间一律按它所见的版本解析再求交（两种顺序都冲突，但任何两个默认终点的并发写入都会冲突）；乙——默认终点的写入按"起点"判。
- **决定**：按写法分三种情形。记过期写入为 W（所见版本 V），V 之后改过同一字段的已生效写入为 L。先按决定 4 去掉 W 里的无操作字段。

  | W | L | 冲突当且仅当 |
  |---|---|---|
  | 默认终点 | 默认终点 | 起点相同且值不同 |
  | 其余组合（至少一方是显式区间；`correct` 的默认区间也算显式区间） | | W 的**所见区间**与 L 记下的区间相交，且交集上 W 的值与当前值不同 |

  - **所见区间** = W 的区间按版本 V 的状态解析的结果（显式区间就是它本身）。
  - 与所有 L 都不冲突 → 合并：W 的区间按**当前**状态解析并落账（解析结果记进事件）。
  - 冲突 → W 在该字段上整体成为候选，候选的区间 = 所见区间。不拆成"相交的部分候选、其余生效"（审查 P1-3）。
  - 事件类表与无时间表不变：字段被 V 之后的写入改过就是冲突。
- **检验**：上例两种顺序都合并，结果都是 5000 / 4000 `[11-02, 11-10)` / 3000 `[11-10, ∞)`。文档自带的例子（一方显式 `open`、一方默认终点）两种顺序都判冲突。推演 4 第 2、3、6、7b 步各推了两种顺序。
- **理由**：原则 S。两个默认终点的写入各自只声明"从某天起值是 v"，起点不同时谁先到结果都一样，没有理由判冲突，这也保住了 `09` 第 65 行"不让无人值守的 Agent 持续制造假冲突"的初衷。一旦有一方给了显式区间，它覆盖的范围就不再随对方而变，必须用所见区间判，否则合并结果会依赖顺序。整体成为候选是因为区间是一句话，生效一半更难向用户解释。
- **事件**：候选的基础写入条目记所见区间；写入头记 `ver` 是显式带的还是兜底取得的、来自哪次读取。**契约**：`candidate` 结果给出候选区间。
- **第一版**：做。删除重放的"`ver` 冲突（重算）"与参考求值器用同一张表。
- **改**：`09-references-conflict-sync.md` 第 62–66 行；`03-deletion.md` 第 102 行；`02-architecture.md` K8。

### 决定 6 影响查询的触发条件

- **问题**：闸门是"起点 < 现在"，读过未来安排的读取会漏掉；"日粒度起点 = 今天"是同一漏洞的局部补丁（双时态 B2）。
- **例子**：已记 `[12-01, ∞) 6000`。11-01 某任务读 `valid_at: 12-05` 得 6000；11-10 写"12-01 起 4000"。现行不查，那次读取不被标记。
- **决定**：状态类表上，**任何让值发生变化的写入**都做影响查询，判据是结构性的：值实际变化的（字段，业务时间区间）与 read_log 记下的业务时间条件有交集，且该读取读到的版本早于这次写入。原因码：

  | 情形 | `reason` | 措辞 |
  |---|---|---|
  | 意图是 `correct` | `correct` | 你曾读到的值已被纠正 |
  | 变化区间里早于"现在"的部分 | `retroactive` | 你读取的业务时间上的值后来被追溯修改 |
  | 变化区间里不早于"现在"的部分 | `plan_changed`（新增） | 你读过的未来安排已变更 |

  - 不传时间的读取记为入口时刻（日粒度记为当天），所以"今天早些时候读过今天的值"自然命中，日粒度特例删掉。
  - 事件类表不变：只有 `correct`、`revoke` 触发。
  - 受限 SQL 的读取：带 `FOR VALID_TIME` 的按改写时得知的时间条件记；不带的记入口时刻。不再一律按版本集合匹配，否则每次改未来安排都会标到全部 SQL 读取。
- **理由**：读取问的是（记录时刻，业务时刻）上的值，这个值后来变了就是受影响，与起点在现在之前还是之后无关。
- **事件**：无（标记是本地运行状态）。**契约**：`possibly_affected.reason` 加 `plan_changed`；`affected_reads` 的原因码同步。
- **第一版**：做。

### 决定 7 写入头记的时刻、日期与时刻的换算、`valid_during` 的返回

- **问题**：双时态 A5、A6、A7 与 B3、B4、B5。
- **决定**：
  1. **写入头内容**记入口取的 `now`、由它在当时 slot 时区下得出的 `today`，以及判定结果"是否追溯"。重放与删除重放都用记下的值。
  2. **日期与时刻**：
     - 细 → 粗（`date` 粒度的表收到时刻）：按 slot 时区取所在日，`warnings` 写明。
     - 粗 → 细（`instant` 粒度的表收到日期）：读写都报 `invalid_argument`，`example` 给出那一天在 slot 时区下的起止时刻。
     - 事件类表按日期开窗、字段是 `zoned_datetime`：按 **slot 时区**的自然日。事件自带的时区只用于展示。需要"当地哪一天"的表，schema 另设 `date` 字段。
  3. **`valid_during` 的返回**：段的端点默认不截取；默认按所选字段合并相邻同值段；开关 `clip: true`、`coalesce: false`。开口终点 `valid_to: null`。`valid_to_inclusive` 只在 `date` 粒度给。`where` 里的 `valid_from` / `valid_to` 只在带 `valid_during` 时可用，否则 `invalid_argument`。
  4. 状态类表的默认读取（只返回当前段）也带该段的 `valid_from` / `valid_to`，让调用方看得到"这个值到哪天为止"。
  5. 受限 SQL 与派生规则读状态类表：不带时间限定 = 当前段，写明；`FOR VALID_TIME ALL` 后续再加。
  6. `entity_key` 的键字段不随业务时间变化：带区间的写入里出现键字段且值不同 → `invalid_argument`。键唯一是全时间唯一。
- **理由**：第 2 条按 slot 时区，是为了与受限 SQL、派生规则的分桶用同一条确定的规则；代价（跨时区的事件可能算到另一天）写明。第 3 条默认合并，是因为没合并的段上按次数、按时长的计算会错（双时态 §5.1）。

### 决定 8 一次写入对外只有一个序号

- **问题**：一次写入占多个 `seq`，回执 `seq`、`ver`、`timeline` 的 #n、`undo` 的 n、`as_of` 各指哪条没说；`as_of` 取到中间会读到从未提交过的状态（双时态 A4、契约审查 P0-4、已知 B7、B15）。
- **决定**：
  1. **一次请求一条逻辑写入头**，它的 `seq` 叫这次写入的**写入号**。请求键、内容指纹、`sv`、`now` 都在这一条上。由 `resolve` 触发的写入、删除确认、撤回同理：各有一条头事件，它的 `seq` 是这次操作的**操作号**。
  2. 对外一律用操作号：回执的 `seq`、`ver` 里的 `seq`、`timeline` 的 #n、`undo` 的 n、`revert.to`、`changes` 的 `since` / `until`、版本表的记录时间区间。源数据事件与各行的基础写入事件的 `seq` 不对外。
  3. **`ver`** = （最近一次改动这一行 / 实体当前状态的操作号，租户恢复次数）。业务写入、系统裁定、删除确认、撤回删除都算；恢复次数初值为 0，写成 `v57.0`。
  4. **`as_of: S`** = 操作号不大于 S 的全部操作都已完整生效时的状态。S 落在一次写入的中间等同于落在它的写入号上。取时刻时按 `recorded_at ≤ T` 换成操作号；未来的时刻等于最新。
  5. `changes`：`since` 不含、`until` 含。
  6. `as_of` 不带 `valid_at` 读状态类实体：返回当时所知的全部段。
  7. `undo: n` 撤回的是写入号 n 对这一行 / 实体的全部改动（同一请求里多个 op 改同一实体时一起撤回）。
  8. 成为候选的写入，回执里逐字段的 `candidate` 结果附 `current_ver`（当前生效版本）。它不算"读到"，不参与兜底。
  9. 写入方自己的写入回执里**已生效**的 `ver` 算一次逐行读到，参与兜底（审查疑问 1）：否则同一个 Agent 连改两次、第二次没带 `ver` 时会和自己冲突。
- **理由**：事务时间在一次事务内必须是同一个值。选写入头而不是最后一条事件，是因为头在这次写入的各行事件之前，任何落在这次写入范围内的 S 都把它整体算进去，不需要知道它在哪里结束。
- **事件**：逻辑写入头按请求记；版本表的区间用操作号。**契约**：第 2 节 `ver` 的定义、第 5 节回执 `seq`、`history` 的参数说明。
- **第一版**：做。
- **改**：`01-objects.md`「编号」；`02-integrity-and-records.md` 第 59–62 行；`04-contract.md` 第 2、5、10 节；`03-deletion.md` 第 108 行。

## 2. 冲突与写入的交叉地带

### 决定 9 冲突事项的粒度

- **问题**：事项的"目标"是行、字段还是字段集合没定义（审查 P0-2）。
- **例子**：B 改了一行的 `amount` 与 `note`。A 带过期 `ver` 改 `amount` 与 `note`，C 带过期 `ver` 只改 `note`。按行：一个事项两个候选；按字段：`amount` 一个事项（候选 A）、`note` 一个事项（候选 A、C）。之后有人只改 `note`：按行则整个事项要么全被取代、要么要定义"部分取代"。
- **决定**：
  1. **冲突单元** = 一个字段，或 schema 声明的一个字段组（决定 14）。
  2. 一个（行 / 实体，冲突单元）最多一个未决冲突事项。状态类表上再按区间：候选区间与已有事项的区间相交的并入它，事项的区间取并集；不相交的另成一项。
  3. 候选条目是"某次写入在这个冲突单元上的部分"：写入号、写入者、值（或撤销）、候选区间、所带的 `ver`、来由（第一版只有 `stale_write`）。
  4. `take_candidate` 只落本事项的冲突单元。一次写入在两个字段上都成了候选，就是两个事项，各自解决。
  5. 撤销参与的冲突，目标是（行 / 实体，**存在**），见决定 11。
  6. 待确认事项（`awaiting_confirmation`）不合并：每次高影响写入各成一项（审查 P1-4）。
- **理由**：与"按字段判断"一致后，合并、取代、处理范围都不需要"部分"的概念。代价是一句话改两个字段时用户要处理两次；字段之间确有关联的，用字段组并成一个单元。
- **事件**：事项产生 / 合并事件的目标记冲突单元与区间。**契约**：事项详情的 `target`；`01-objects.md` 第 178 行"只覆盖该候选写入里设置的字段"改为"只覆盖本事项的冲突单元"。
- **第一版**：做。
- **改**：`01-objects.md` 第 123、157–162、178 行；`09-references-conflict-sync.md` 第 61–71 行；`04-contract.md` 第 6、10 节。

### 决定 10 `take_previous`

- **问题**："回到冲突前的版本"指哪个版本没定义，值来源也没写（融合 A3、已知 B4）。
- **例子**：#40 `distance 15`；#57 纠正为 5（带 v40）；A 带 v40 写 6（候选）；C 带 v33 写 5.5（候选；v33 时是 12）。
- **决定**：
  1. `previous` = **合并基**上的值：事项现存各候选所带 `ver` 中最早的那个版本，在本事项的冲突单元（与区间）上的值。上例是 12；只有 A 一个候选时是 15。
  2. 执行 = 在本事项的冲突单元与区间上，**回退到合并基**。值来源是对合并基处生效的那几个贡献的引用，解决请求只是操作来源。删除重放直接套用回退的规则。
  3. 事项内容记合并基的操作号；`previous` 给 `{seq, value}`。候选并入或被删除去掉时合并基按机械判定重算，事项版本换新。
  4. 事项的影响里列出会被回掉的写入（合并基之后在这个单元上生效过的全部写入）。它在事项版本的绑定范围内，`resolve` 时不再另过高影响判定。
  5. `take_candidate` 采纳一个候选时，事项里**值相同的其他候选**的贡献一并作为值来源（"或"），以免删掉被采纳者的证据后值消失而另一条同值证据还在（融合 B3）。
- **理由**：三方合并里"原来的样子"就是合并基；saveslot 的历史是线性的，合并基唯一。这个定义让三种处理方式在第一版互不重复（`keep_effective` 是先提交者的值，`take_previous` 是双方都没改之前的值）。
- **事件**：事项事件多记合并基；采纳写入的"对被搬运贡献的引用"可以有多条。**契约**：`previous` 的形状；`conflict` 详情的影响。
- **第一版**：做。
- **改**：`01-objects.md` 第 132、178–179 行；`03-deletion.md`「来源」表加一行；`04-contract.md` 第 5、10 节。

### 决定 11 撤销与并发修改；写到已撤销的行

- **问题**：撤销不带值，按字段规则它与任何修改都"没交集"（融合 A7、审查 P1-1）。
- **例子**：A、B 都读到 r7（v30）。B 把 `distance` 从 10 纠正为 5。A 带 v30 撤销 r7（"这条记重了"）。字面规则下撤销直接生效，B 刚做的纠正随之不可见。
- **决定**：
  1. **撤销改的是"存在"，与每个冲突单元都相交**（状态类表：撤销区间内）。过期的撤销遇到期间任何已生效的修改 → 候选；过期的修改遇到期间的撤销 → 候选。事项目标是（行 / 实体，存在）。
  2. 这类事项的三种处理：

     | 处理 | 效果 |
     |---|---|
     | `keep_effective` | 保持现状，候选不生效 |
     | `take_candidate` | 候选是撤销：撤销生效。候选是修改：行恢复存在，并落这次修改 |
     | `take_previous` | 回到合并基：行存在，值是合并基上的值 |

  3. **事件类表、无时间表**：已撤销的行不可写。`update` / `correct` 报 `revoked`（新错误码，附撤销它的写入号，提示用 `revert: {undo}` 恢复）；再次 `revoke` 是无操作。
  4. **状态类表**：撤销就是"这段时间无值"的一次写入，没有单独的"已撤销"状态。撤销整个实体 = 全时间无值，实体与它的键仍在。之后按 `entity` 或 `entity_key` 的写入按决定 2 处理（填无值区间，须带齐必填字段，照常带 `ver`）。不会生成第二个同键实体。
  5. 依赖状态的校验（必填字段在无值区间是否带齐）在冲突判定**之后**做，只对将要生效的部分做；成为候选的不做。否则同一对并发写入一种顺序报错、另一种顺序成候选。
- **理由**：Dynamo 与多值寄存器的已知反常就是"删除与并发修改合并"。把状态类表的撤销归为无值区间，写到已撤销实体、撤销后重建这些情形都落进决定 2，不用另立规则。
- **事件**：候选条目带意图（本来就有）。**契约**：`candidates[]` 加 `intent`；新错误码 `revoked`。
- **第一版**：做。
- **改**：`09-references-conflict-sync.md` 第 62–66 行；`05-time.md` 第 61、63 行；`04-write-and-read.md` 第 157 行附近；`04-contract.md` 第 10、11 节。

### 决定 12 既版本对不上、又是高影响

- **问题**：`05-time.md` 第 55 行偏向进待确认，`09` 第 63 行偏向成候选（审查 P1-2）。
- **例子**：已记 5000、11-10 起 4000（后者是 B 在 A 读取之后写的）。A 带旧 `ver` 写 `[11-02, open) 3000`：与 B 的写入相交，同时抹掉 11-10 的变化点。
- **决定**：
  1. **判定顺序**固定为：与状态无关的校验（`sv`、类型、单位）→ 请求键查重 → 同值（决定 4）→ `ver` 与冲突 → 对将要生效的部分做依赖状态的校验 → 高影响 → 疑似重复。
  2. 冲突优先：成为候选，生成冲突事项。候选若生效会属高影响，事项的影响里同时列出会被覆盖的段。`take_candidate` 就是对这些内容的确认，不再另生成待确认。
  3. **删除让冲突消失后**，该写入在删除后的状态上：
     - 不属高影响 → 在自己的 `seq` 生效，列入预览的"将会生效的写入"（现有规则）。
     - 仍属高影响且从未被人确认 → **转为待确认**：原冲突事项标已被取代，删除事件里生成一个 `awaiting_confirmation` 事项。预览单列"将转为待确认的写入"。
  4. 相应地，"删除不产生新的冲突与待确认"改成"**删除不增加未决事项**：每个新出现的待确认都对应一个被取代的冲突事项"。
- **理由**：冲突是更上位的问题（有人没看到别人的改动），先让人在冲突里看全。第 3 条不让它直接生效，是因为抹掉已记录变化点的写入必须有人确认过，这条保证不该因为一次删除而被绕过。
- **事件**："删除已确认"事件的结果多一类：转为待确认的写入与新事项。**契约**：`deletion_preview` 加 `now_awaiting[]`。
- **第一版**：做。
- **改**：`05-time.md` 第 51–55 行；`03-deletion.md` 第 102、104、122、124 行；`02-architecture.md` §11 性质表"冲突只减不增"；`04-contract.md` `deletion_preview`。

### 决定 13 同一请求里多个 op 作用于同一行 / 实体

- **问题**：新建一个实体并一次写两段，第二个 op 会因为没有 `ver` 报 `read_first`（审查 P1-5）。
- **决定**：
  1. op 按请求里的顺序执行，后面的 op 看得到前面 op 的结果。
  2. 对本请求里新建的行 / 实体，后面的 op 不需要 `ver`。
  3. 对请求之前已存在的行 / 实体，同一请求里各 op 带的 `ver`（或兜底）表示"请求开始时所见的版本"；冲突判定只比请求之外、该版本之后的写入，本请求前面的 op 不算。
  4. 同值判断（决定 4）的基准：所见版本叠加本请求前面 op 的结果。
  5. 整个请求共用一个写入号，同一行 / 实体只得一个新 `ver`。
  6. 各 op 独立判定：一个 op 成了候选，不影响同请求里其他 op 生效。请求的原子性指事件一起提交。
- **事件**：无新增。**契约**：第 5 节写明。
- **第一版**：做。
- **改**：`04-write-and-read.md` 第 18 行；`05-time.md` 第 63 行；`04-contract.md` 第 5 节。

### 决定 14 字段组

- **问题**：逐字段合并会造出谁也没写过的组合（融合 B2）。出差 `start 11-01, end 11-05`；一方把 `end` 改成 11-03，一方把 `start` 改成 11-04；合并出 `start` 晚于 `end`。
- **做法**：甲——不处理；乙——默认按整行判冲突；丙——schema 可声明字段组。
- **决定**：丙。表定义加可选键 `together: [["start", "end"], …]`。同组字段是一个冲突单元：改到组里任何一个字段，就与改到组里任何字段的写入相交。不声明时每个字段自成一个单元。字段组只影响冲突判定与事项目标，不影响挡点、来源、同值判断。
- **理由**：单字段约束在逐字段合并下不会被破坏，会被破坏的只是跨字段的关系，而只有 schema 的作者知道哪些字段有关系。乙会让无人值守的 Agent 不断制造假冲突。
- **事件**：无（字段组在编译后的 schema 定义里，随 `sv` 走；删除重放按写入记下的 `sv`）。**契约**：schema 文档格式加一个键。
- **第一版**：做。内核从第一天按"冲突单元"实现，默认每字段一组。
- **改**：`07-schema-evolution.md`「schema 文档格式」；`09-references-conflict-sync.md` 第 62–66 行。

### 决定 15 字面核对

- **问题**：只定义了"数值 + 单位"；结果取值两处说法不一；记录粒度没写（已知 B1、B2，融合 A2、B4）。
- **决定**：
  1. **改名**：核对状态改叫**字面命中**。它核对的是值在证据里出现过，不是证据断言了这个值。
  2. **按类型的命中规则**（核对器版本 `literal@1`；文本先做 Unicode NFC、全角转半角）：

     | 字段类型 | 命中当且仅当证据文本里 |
     |---|---|
     | `quantity` | 有一个数字记号与请求里的原始数值相等，后面紧跟（可隔空白）请求原始单位在同义表里的一种写法 |
     | `integer`、`decimal` | 有一个数字记号与写入值相等 |
     | `date` | 有同一天的日期写法：`YYYY-MM-DD`、`M月D日`、`M-D`、`M/D`（带年份时年份须相同）。"今天""上周三"这类相对说法不算 |
     | `enum` | 包含该枚举值的字面（不分大小写） |
     | `text` | 包含写入的文本（去首尾空白后，长度至少 1） |
     | `zoned_datetime`、`boolean`、`ref` | 不适用 |

     数字记号：阿拉伯数字，可带千分位与小数点，比较数值不比较写法；`literal@1` 不认中文数字。
  3. **记录粒度**：基础写入事件里按"字段 → 该字段引用的每段证据 → `hit` / `miss` / `na`"记，另记核对器版本（含同义表版本）。`source_ref` 按被引用的原文核对。
  4. **字段的级别不落盘**，现算：字段仍在的值来源里，命中的那些段的声明级别取最高；一段都没命中则为"未命中"。
  5. **结果只有两种**：已命中、未命中。"不一致"要模型核对才会得出，第一版不出现；`01-objects.md` 第 119 行"字面核对只会得出已核对"是错的，改掉。
  6. **比较规则写成秩表**，放进 slot 策略（决定 17）：秩 = 命中时取声明级别，未命中时为最低。秩严格更高者胜，同秩保持当前值，多个候选同秩取写入号最早的。第一版的策略是 `keep_current`，秩表不参与任何判定。
- **理由**：第 3 条是为了删除后能重算"仍在的来源里命中的最高级别"，记成一个总状态就算不出来。第 6 条取"未命中一律最低"而不是"有一方未命中就算同级"，是因为后者有反常：当前值的支撑越弱越难被换下（融合 B4）。
- **事件**：基础写入事件的"写入时判定的结果"按上面的粒度记。**契约**：证据段的声明级别不变；对外的"核对状态"字段改名。
- **第一版**：做（记录）；裁决不做。
- **改**：`04-write-and-read.md` 第 72–88 行；`01-objects.md` 第 119 行；`03-deletion.md` 第 88 行；`02-architecture.md` §3 事件表。同义表的内容另列一个附录（`literal@1` 收哪些单位写法、"元"是否对应 CNY 在那里定）。

### 决定 16 `disputed` 等标记的粒度

## 3. 事件里记什么（属于规则的部分）

### 决定 17 判定规则的版本

- **问题**：裁决规则不在日志里、没有版本，而删除重放要重算机械判定。将来加回系统裁定后，删一条不相干的证据会让旧候选按新规则生效（融合 A1、架构审查 P0-4）。
- **例子**：第一版日志里 #47 写 9.5，#48 带过期 `ver` 写 10（用户原话，已命中），候选未决。内核升级加回系统裁定。用户删这一行 `feeling` 字段的一条证据：整行重放，按新规则 10 生效。`distance` 的来源里没有被删的证据，值却变了。
- **决定**：分两个版本号。
  1. **策略版本**（按 slot）：slot 策略事件的内容里有"冲突期间的生效值规则"（第一版 `keep_current`）、秩表、额外的高影响清单。每次策略变更事件版本加 1。
  2. **规则版本**（按内核）：一个整数，标识全部机械判定的语义（挡点、同值、冲突判据、高影响判据、存在性、字面核对器）。任何一条语义变了就加 1。第一版是 1。
  3. **记在哪**：每条逻辑写入头记这次写入判定时用的规则版本与策略版本；冲突、待确认事项的产生与合并事件记同样两个号；删除确认与撤回事件记重算时用的规则版本。两个号不含用户内容，可以放事件头。
  4. **删除重放按哪一版**：每次旧写入按**它自己记下的**规则版本与策略版本重算。旧事项不会因为内核升级或策略变更而改判。
  5. 想让旧事项改用新策略，由一条显式的**重判事件**触发（它是日志事件，结果可见）。内核不再保留某个旧规则版本的实现之前，必须先对还用着它的写入做一次重判。
- **理由**：`apply` 的重放不重新判定，所以它不受规则变化影响；受影响的只有删除重放。按写入记下的版本重算，"不多删""撤回还原"两条性质才不随内核版本变化。代价是内核要保留旧版本的判定实现，直到显式重判；第一版只有一个版本，没有实际成本，但号必须现在就记，事后补不回来。
- **事件**：写入头、事项事件、删除事件各加两个整数。**契约**：`policy.get` 返回策略版本。
- **第一版**：做（记录）。重判事件第一版不产生，事件类型留位。
- **改**：`02-architecture.md` K11、K12、§3 事件表；`01-objects.md`「slot 包含什么」；`03-deletion.md` 第 157 行；`07-scope-v1.md` 第 72 行"纯增量"的理由。

### 决定 19 未生效的写入怎么落账

- **问题**：冲突候选、待确认的写入是否以基础写入事件落账，只能从重放规则反推（已知 B5）；全部字段都是无操作的写入产生什么也没说（审查 P0-1）。
- **决定**：
  1. 每个 op 对每个受影响的行 / 实体照常记一条基础写入事件。事件里**逐字段**带生效状态：`applied`、`candidate`、`awaiting`、`corroborated`、`noop`。
  2. `apply` 只把 `applied` 的字段落进业务表与版本表；`corroborated` 的写进来源表；其余只留在日志里，供 `timeline`、事项与删除重放使用。
  3. 之后的采纳、确认是一次由 `resolve` 触发的新写入（有自己的写入头与操作号），值来源是对原候选 / 提议贡献的引用。
  4. "因删除而在自己的 `seq` 生效"的含义：在按 `seq` 排贡献先后时它排在原来的位置；业务表与版本表的改动记在删除确认事件的操作号上。
  5. **全部字段都是无操作的请求**：照常存源数据、记逻辑写入头（含请求键，重发按幂等重放）；不记基础写入事件；`ver` 不变；回执 `saved`，逐字段 `noop`。证据是资产，不因为没改值就丢掉。`undo` 全部被跳过时同理。

### 决定 20 方向限制与定义；已解决的冲突遇到删除

- **问题**：方向限制是对"从未存在过"的第二处偏离，而定义说偏离只有一处；推论里"按上面的占位处理"无所指（审查 P1-13）。冲突已被 `keep_effective` 解决后再删生效值的来源，落回哪个值没有例子（已知 B13）。
- **决定**：
  1. **定义补一句**：隐私删除后的状态 = 假如被删源数据从未存在过、按 `seq` 重放得到的状态；**两处有意的偏离**：人的决定照记录；**已经生效过的写入保持生效**（方向限制）。参考求值器按含这两处偏离的定义实现。
  2. 推论改为："删除不增加未决事项，由方向限制与决定 12 第 3 条保证。"删掉"夹在中间的改动只会变少"与"按上面的占位处理"。
  3. **撤回同样适用方向限制**：宽限期内已经生效的写入保持生效。性质"撤回还原"改为"撤回后，未被宽限期内的写入覆盖的部分与从未删除时相同"（审查 P1-14）。因删除而生效的写入若在宽限期内已被别的写入以它的 `ver` 为基础改过，撤回时不退回，回执列出。
  4. **`keep_effective` 之后删生效值的来源**：例 #46 写 9；#47 写 9.5；#48 带过期 `ver` 写 10，候选；人选了 `keep_effective`。之后删 #47 的证据。`keep_effective` 这个决定的内容是"这些候选不生效"，照记录执行，10 不生效；9.5 失去来源，按普通规则落回最后一个仍在的贡献，即 9。选的是 `take_candidate` 时，值是对 #48 贡献的引用，不受影响；选的是 `take_previous` 时，值是对合并基贡献的引用，同样不受影响。
  5. 原则 ② 与"人的决定"两个清单改成穷尽的写法："除下列人的决定外，一切判定都重算"。`undo` 当时解析出的字段、区间与跳过的部分算人的决定的一部分，照记录（审查 P1-16）。
- **理由**：已生效的写入被读过、被后续写入当作基线，把它退回成候选会让一次删除推翻与它无关的既成事实，并产生新的未决事项。这是与"人的决定照记录"同一类的取舍，应当写在定义里而不是规则表的脚注里。
- **事件**：无。

### 决定 22（补）事项被取代的前提

- **问题**：带着当前 `ver` 的普通写入改到有争议的字段，冲突事项就被取代、候选全部作废；而写入方读到的只有生效值与标记，没看过候选。这等于让一个没看过候选的写入方替人关掉了冲突（融合 A5）。
- **例子**：生效 9.5（Agent 推断），候选 10（用户原话）。无人值守的 C 读到 9.5 与标记、没看事项，之后按工具同步写 9.6。现行规则下事项被取代，用户说的 10 不再出现在任何待处理事项里。
- **决定**：
  1. 一次写入改到未决事项的目标时，**只有写入方读过该事项的当前版本，事项才被取代**（"读过"的定义同 `item_ver` 的兜底规则）。
  2. 没读过：事项**刷新**并保持未决。冲突事项的当前生效值换成新值，影响重算，事项版本换新；待确认事项的"将被覆盖的段"重算，事项版本换新。回执 `pending[]` 里标 `refreshed: true`。
  3. 刷新后，原先拿着旧事项版本的 `resolve` 会收到 `confirmation_mismatch` 与新内容，要重新确认。这保证采纳候选或确认提议时不会悄悄盖掉新写入。
  4. 状态类表上"改到"仍按区间相交判。
  5. 刷新是一种事项事件（高影响 ② 的引用方变化也用它）。
- **理由**：与"saveslot 没有判断力，不替人裁决"一致：候选只能被看过它的人关掉。"不堆积"并没有变弱，每个（行，冲突单元）仍然至多一个事项；变的是它不会无声消失。安全性由事项版本保证。
- **事件**：新增事项刷新事件；取代 / 刷新事件记"是否读过"（决定 18 第 7 项）。**契约**：`pending[]` 的 `refreshed`；`superseded[]` 的语义收窄。
- **第一版**：做。
- **改**：`01-objects.md` 第 135、161–162 行；`09-references-conflict-sync.md` 第 61 行；`04-contract.md` 第 5、6 节；`02-architecture.md` §3 事件表"待处理事项生命周期"。

## 5. 性质测试清单

参考求值器的状态 = "实体 × 字段 × 业务时刻 → 值或无值"，一次写入 = 区间内逐点赋值（双时态 §6）。下表按本文决定后的规则整理。T 开头的出自双时态 P1–P11，F 开头的出自融合 §4.5。

| # | 性质 | 含义（按决定后的规则） | 抓什么错 | 第一版 |
|---|---|---|---|---|
| T1 | 逐点等价 | 带显式区间的写入生效后：区间内被写的字段 = 新值；区间外、以及没被写的字段不变 | 拆段算法的任何错误 | 适用 |
| T2 | `next_change` 可消去 | 默认终点的写入 ≡ 以"该字段在起点之后的第一个挡点"为显式终点的写入，逐字段；终点及之后的值不变 | 解析错终点；没按字段解析 | 适用（按决定 1、2、4 的挡点定义） |
| T3 | 顺序主键、无空段 | 同一实体任意两段不相交、没有空区间；版本表里同一实体的两个版本不在两条轴上同时相交 | 拆段留下重叠；版本区间没关上 | 适用 |
| T4 | 拆分不变 | 把任意一段在任意点切成两段同值、同来源的段，再执行同一次写入：终点、高影响、同值、冲突的结论都不变 | 判定偷看了物理段边界 | 适用。佐证端点不是物理边界，不在"任意切开"之列 |
| T5 | 合并幂等、保快照 | 查询层合并前后每个时刻的值相同；合并两次 = 一次；合并后相邻段的值必不同 | 合并按错了列 | 适用 |

## 7. 仍需架构负责人判断的点

1. **决定 22 改变了现有行为**（没读过事项的写入不再取代它）。它是融合调研留给方案作者的三处之一，本文选了"刷新、不关闭"。若认为第一版应保持"照常取代、只记是否读过"，决定 18 第 7 项仍然要记，决定 22 第 1–3 条撤回即可，不影响其他决定。
2. **决定 7 第 2 条：事件类表按日期开窗用 slot 时区。** 另一种选法是按事件自带时区的当地日。本文选前者是为了与受限 SQL、派生分桶同一条规则；跨时区记录的归属日会与用户直觉不同。
3. **决定 4 的佐证端点只收"显式指证据"的同值写入。** 没指证据的"11-20 起还是 5000"在两种顺序下都被后来的默认终点写入盖掉，且回执不提醒（它没有留下任何记录可供提醒）。若认为这类话应当算数，要靠工具描述引导 Agent 在重申一个值时用 `evidence_by_field`。
4. **决定 17 要求内核长期保留旧规则版本的判定实现**，直到显式重判。这是为"不多删"付的代价；另一种选法是"删除重放一律用当前规则，升级时强制全量重判"，实现简单，但每次升级都要对全部未决事项重判一次。
5. **决定 15 的命中规则是经验性的**（日期写法、数字记号、枚举字面）。它只在将来的系统裁定里起作用，第一版记下的结果带核对器版本，规则以后可以升级再补核对。同义表的具体内容本文没定。
6. **决定 11 的新错误码 `revoked`、决定 2 的 `details[].code`** 需要与 W3 的错误集合一起定名。

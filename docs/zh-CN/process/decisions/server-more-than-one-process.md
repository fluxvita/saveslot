# 决定：服务器模式一个部署运行多个服务进程

> 不改事件格式，不改 K1–K14，不改操作契约。按「分步交付」落进规格与代码。

本文里「进程」指一个 `saveslot server start` 的服务进程（一个容器、一个副本）。不说「实例」，以免与连接实例相混。

## 要解决什么

服务器模式的一个部署只能跑一个进程：控制面库上有一把「服务器在运行」的锁，第二个 `server start` 直接退出。一个进程意味着更新要停机、进程挂了服务就断、负载上来没法加机器。

目标是同一个部署可以跑任意多个进程，数量随负载增减：

- 任何一个进程都能处理任何一个租户的请求，结果与只有一个进程时相同（第 1 条列出的一种暂时性失败除外）；
- 计划内的变动（更新、扩容、缩容）不丢请求；
- 一个进程意外退出时，只有它手上正在处理的请求失败，客户端重试即可，写入不会因重试而重复。

本机模式不变：一台电脑、一个服务进程、一个数据目录、单写者文件锁。

## 现状里挡路的东西

1. **租户的所有权。** 每次打开租户存储，所有权 epoch 加 1；写事务在该租户的 advisory lock 下核对 epoch，不符就放弃这个租户。它假定每个租户固定路由到一个进程。两个进程各收到同一个租户的请求时，后打开的一方拿走所有权，先打开的一方此后对这个租户的每个请求都失败，并且只要一直有请求进来就不会恢复。
2. **只在一个进程里成立的互斥。** 导入对租户的独占、「没有标记的暂存 database 是崩溃留下的，可以丢弃」的判断，都只在本进程内有效。
3. **读取记录的缓冲。** 读取记录先攒在进程内存里，稍后落盘。不带 `ver` 的写入按「这个连接实例上次读到的版本」兜底，另一个进程上的读它看不到。
4. **每进程随机的密钥。** 本地账户登录表单的令牌用进程启动时随机生成的密钥签。
5. **就绪与下线。** `GET /health` 在任何状态下都回 200，负载均衡器看不出进程是否就绪；收到终止信号后监听立刻关闭，等在途请求没有时限。
6. **按进程计的限额。** 登录失败、客户端文档取回、设备码错码的计数与按租户的限流都在进程内存里。

## 决定

### 1. 不设租户归属：任何进程直接处理任何租户

PostgreSQL 后端上取消「打开即取得所有权」。多个进程可以同时连着同一个租户的 database；写事务的第一条语句仍然是取该租户的 advisory lock，所以同一个租户的写入在所有进程之间是串行的。

这样做成立，是因为内核在进程里不保留租户的数据状态：每个事务都从库里重读日志末端、schema、目录、策略、事项与规则，没有按租户的缓存；`seq` 在锁下由日志末端加一得出。写事务的隔离级别是 `READ COMMITTED`，取到锁之后的每条语句看到此前已提交的全部内容：两个进程对同一行、带同一个 `ver` 的两次更新，后拿到锁的那一次按先提交的那一次之后的状态判定，与它们先后到达同一个进程时相同。同一进程里的多个请求本来就在事务的粒度上交错，跨事务的操作已经容忍别人在中间写入；多个进程新增的只有一件事，见下面的例外。

所有权 epoch 在 PostgreSQL 后端上不再参与判定：打开不加 1，写事务不核对。`meta` 里这一项留着不删，本机后端照旧使用它。

**一种暂时性失败（例外）。** 一个进程里同一个租户的读与写在同一条连接上轮流；多个进程时，一个进程上的读事务可以与另一个进程上的写事务同时进行。读事务是一个快照，数据上不受影响，但删表不受快照保护：一个进程移除一个 slot、删掉它的物理表时，另一个进程上早先开了快照的读可能发现表已经不在。这样的读在新的快照里重做一次（那时它看到的是 slot 已移除）；不以内部错误到达客户端。反过来，另一个进程上的读已经在用那张表时，删表要等它结束，而等的时候占着该租户的 advisory lock，这个租户的写入都排在后面。所以删表带等待上限（5 秒）：等不到就放弃这次移除，回可重试的 `unavailable`（`busy`），什么都没改。

**连接出了问题就重开。** 一个进程手上某个租户的连接进入失败状态（连接断开、database 被换掉）时，下一个用到它的请求把它关掉、重新打开再处理，不让这个租户在这个进程上一直失败到空闲关闭。

**两个进程同时为同一个用户新建租户**：创世事件在锁下核对日志为空，只有一方写得进去；另一方不报错，改为打开那个已经建好的租户。

**连接数。** 一个活跃租户在每个处理过它请求的进程上各有一条连接，连接总数的上限随进程数放大；部署说明里按「活跃租户数 × 进程数」给出数据库连接数的要求。

**不选的做法：**

- *每个租户固定在一个进程上，别的进程把请求转过去。* 要进程之间互相连通、一张租约表、进程退出时的接管协议，而换来的东西（进程内可以放心缓存）内核并不需要。
- *靠入口按租户分流。* 租户是从令牌里解出来的，入口只看得到一个不透明的请求头；按来源地址分流在有前置代理时既粘不住同一个用户、又会把负载压到少数进程上。而且进程数一变，分流结果就变，正确性不能建立在它上面。
- *保留所有权，失去的一方重开再重试。* 能做到正确，但请求随机落到各进程时几乎每个请求都要重开一次，而重开要保护的进程内状态并不存在。

### 2. 读取记录在应答之前落盘（服务器模式）

服务器模式下，一次读产生的读取记录在这个请求应答之前写进库里，不再攒在进程内存里。不带 `ver` 的写入落到任何进程，按「上次读到的版本」兜底时看到的都是同一份记录；进程意外退出也不丢读取记录。记录写不进去时这次读不应答内容，回可重试的 `unavailable`：没有记下的读不交给调用方。

这次写入用一种不取该租户 advisory lock 的写事务，不与同一租户的写入互相等待。因为不取锁，几个进程的记录可能不按读的先后到达，所以凡是「最近一次读」的判断都按读到的位置比较（恢复次数与日志位置），不按记录插入的先后：「上次读到的版本」只往前改；「自我上次读之后的变更」同样以位置最靠后的那次读为准。

规格写读取记录「和这次操作在同一个事务里」落盘，而实现是在操作的事务之前另开一个事务；按这里的做法把这句写准。

本机模式仍是一个进程，缓冲加定时落盘；只有一处跟着变：「最近一次读」也按位置比，缓冲里的与已落盘的一起比，取位置最靠后的那次，结果不再取决于中间有没有落过盘。

**不选的做法：** 读不到记录时让写入回 `read_first`、由 Agent 重读。请求随机落到各进程时，重读与重写仍可能落在不同进程上，可能反复失败。

### 3. 导入的独占跨进程成立：先封存，再换入

导入要保证「整体要么完成、要么目标租户保持为空；期间这个租户的其他请求报 `unavailable`」。一个进程里靠的是先等在途使用排空再独占；多个进程时，别的进程上已经通过检查、正在排队的写入会在换入前一刻提交到将被换下的 database 里，应答了成功而数据随旧库被删。只在请求入口检查挡不住它，所以封口放在租户自己的 database 里：

- **封存。** 导入第 ④ 步改为一个写事务：取该租户的 advisory lock，核对日志只有创世事件，在 `meta` 里写下「已封存」。此后任何进程在这个 database 上的写事务，取到锁后读 `meta`（与第 8 条的格式核对是同一条语句），见到封存即回 `importing`，什么都不写。换入之后旧 database 被删除；因换入而过期的连接关闭时不推进高水位。
- **占有标记。** 导入从第 ① 步起在控制面库的租户目录里记下「正在导入」，并由一条专用于这次导入的控制面连接持有以这个租户为键的锁（先取锁、后写标记；锁随连接存在，进程退出即释放）。这个标记是新加的一项，与导入已有的、从第 ④ 步才写下的那个标记分开：后者说的是「已经过了核对为空的那一步」，重入规则靠它判断做到了哪里，含义不变。每次使用租户（不只是经过认证的请求：授权页签发连接实例、吊销凭证这些不经认证而写租户日志的路径同样经过这里）先看目录里这一行：有标记而且锁还被别的会话持有，回 `importing`；第二个导入落到任何进程，回 `rate_limited`（`busy`），与同一进程内相同。新建租户与对账这些直接打开存储的路径同样先看这一行。代价是每次使用多读一次目录行（经认证的请求把认证时读到的那一行往下传，不读第二次）；锁只在有标记时才去查。
- **占有者死了。** 有标记而锁已经没人持有，说明导入的进程中途退出。发现它的进程先取这把占有锁（两个进程同时发现时只有一个取得，另一个照「正在导入」处理），再照导入重入的现有规则收尾：换入之前的丢弃暂存 database、解除封存；换入之后的接着做完余下的步骤。**占有标记最后才清**，解除封存排在清掉第 ④ 步那个标记之前：收尾的进程自己中途退出时，留下的仍是「有标记、没人持锁」，下一个发现的进程接着做，不会留下一个封存着却没人去解的 database。判断「没人持有」看的是数据库里这把锁的持有者，不用「自己再取一次试试」：同一条连接上重复取同一把锁总是成功的。
- 「没有标记的暂存 database 可以丢弃」相应改为「没有活着的占有者时才可以丢弃」。
- **database 换了就重开。** 租户目录里记着租户当前对应哪个 database；每次使用把它与本进程已打开的连接对照，不同就按第 1 条重开。

`server restore` 不需要这一套：它执行期间没有任何进程在运行（第 4 条）。

### 4. 「服务器在运行」的锁分成共享与独占

`server start` 取共享锁，任意多个进程可以同时持有；`server restore` 取独占锁，只在没有任何进程运行时才能执行，执行期间也不能启动进程。取不到时的退出码不变。

改动控制面库格式的升级同样在独占锁下做（第 8 条）。

### 5. 各进程共用的密钥与配置

本地账户登录表单的密钥不再每进程随机生成，改为从各进程共用的密钥文件派生（与句柄签名用的是同一份文件、不同的用途标签）。验签接受文件里的每一把密钥，签发用最新的一把：换密钥分两步，先让所有进程读到新旧两把，再去掉旧的，中间不会有进程验不过别的进程签的东西。

各进程必须相同的配置：受信代理、对外地址、允许的来源、外部登录的配置、密钥文件里各把密钥的标识（不含密钥本身）、租户库所在集群的身份。进程启动时把这组配置的指纹与控制面库里记着的比对：有而不同就拒绝启动并说明哪一项不同。改这组配置要全部进程停下：第一个启动的进程先试独占锁，取得了才可以改写指纹，然后降为共享锁。

指纹与第 3 条的占有标记都记在控制面库里，是控制面库格式的一次改动，带升级步骤与格式样本。

### 6. 就绪检查是单独的端点

新增 `GET /ready`，不需要令牌：进程已就绪而且没有在下线时回 200，其余情况回 503。负载均衡器的健康检查、容器的就绪探针与镜像自带的健康检查都指向它。

`GET /health` 的约定不变：它回答「进程在不在、处于什么状态」，状态在响应体里，状态码总是 200。本机模式的命令行与 MCP 桥按这个约定使用它；本机模式不加 `/ready`。

**不选的做法：** 让 `/health` 按状态回 5xx。本机模式有多处把非 200 当作「服务没在运行」。

### 7. 下线分三步，每一步有时限

收到终止信号后：

1. `/ready` 立刻回 503，`/health` 的状态变为 `stopping`；进程继续监听、继续照常处理请求（不回 `unavailable`），持续一段**摘除等待**（可配置，默认 10 秒），让负载均衡器发现并停止转发；
2. 停止接受新连接，中止还在上传请求体的导入，等在途请求结束，至多等**在途上限**（可配置，默认 30 秒），到时仍未结束的连接被关闭；
3. 关闭租户连接、释放锁、退出，同样有上限（10 秒）：到时还卡着的使用不再等。

容器的终止宽限期必须不短于三者之和，部署说明里写明。

负载均衡器摘除后端时可能直接掐断在途连接，这一点内核管不了。被掐断的请求由客户端重试：写入已提交而应答丢失时，重试靠幂等键与请求键认出来，不写两遍；这个要求写进接入说明。导入的应答被切断时导入本身会做完，重试得到「租户不为空」，接入说明里一并说明怎么确认。

流式的响应（导出）在两批数据之间可能有一段时间没有输出，前置代理会按空闲超时切断连接。导出文件的格式已经冻结，每一行都必须是一个对象，不能往里加空行当心跳。所以这一条落在部署要求上：前置代理对这个服务的空闲超时不得短于导出两批之间最长的静默时间；这个时间由导出每批读取的行数决定，实测后把数值写进部署说明，超出常见的 60 秒时改小每批的行数，不改格式。

### 8. 不同版本的进程同时运行

滚动更新期间新旧两个版本的进程同时在跑。两个版本可以同时运行，要同时满足：

- **旧版本读得懂新版本写下的一切。** 事件格式规定，带了旧内核不认识的形状的事件必须带更高的版本号，内核遇到不认识的事件版本或判定版本就停，不降级。所以一个版本引入新的事件形状、新的规则版本或新的受限 SQL 版本时，分两个版本走：先发一个读得懂它的版本，等全部进程都换成这个版本，下一个版本才开始写它。发布说明里写明每个版本属于哪一种。
- **租户存储的格式升级只做旧版本不受影响的改动**（加表、加带默认值的列），不重写、不删除旧版本还在读的东西；破坏性的步骤留到旧版本不再运行的下一个版本。新进程打开一个租户时在该租户的 advisory lock 下把它升级；每个写事务取锁后核对格式版本，旧进程发现格式比自己认得的新，回可重试的 `unavailable`（原因用 `stopping`：这个进程即将被换掉；专门的原因记入待定问题），直到这个旧进程被换掉。「每个事务核对格式」这段代码要比第一个带格式升级的版本早一个版本发布。
- **控制面库的格式改动不在滚动更新的范围内。** 改它的版本要全部进程停下、在独占锁下升级，再启动新版本；启动时格式不符的进程拒绝启动。从只能跑一个进程的版本升到能跑多个的第一个版本，也属于这一种。

### 9. 按进程计的限额先不共享

登录失败、新建用户、客户端文档取回、设备码错码这几类按来源的计数，以及按租户的限流，仍然每个进程各记各的。实际的上限因此是配置值乘以进程数，规格里照实写明。

这些放大之后没有一项变成安全问题：设备码的用户码是 8 个字母、取自 20 个字母，而且尝试之前要先登录；客户端文档取回防的是访问内部地址，靠的是对目标地址的校验，计数只限总量；口令哈希的并发闸保护的是本机的处理器与内存，本来就该按进程算。按来源新建用户的上限放大意味着可被滥用来多建租户 database，部署说明里提醒按进程数调低配置值。按租户的限流要做到准确时再移到进程之外，那是配额与计量的一部分，不在这份决定里。

过期记录的定时清理每个进程都会跑，操作是幂等的，不做协调；并发时偶尔互相让路失败，下一轮重做。

## 它改了哪些已有的规定

- **01-positioning**：单节点与「每个活跃用户一条连接」的说法。
- **02-architecture §1、§9、§13**：一个部署一个进程；自部署「一个进程即可」保留，补「可以多个」及第 5 条的要求。
- **02-architecture §3、§4、§5**：服务层的进程内状态与「同键请求进行中的等待」（幂等键记在日志里、在锁下查，本来就跨进程成立）；`store` 的「单写者锁与所有权 epoch」；限流一行按第 9 条；控制面库的表里去掉「路由（租户 → cell → 进程）」，加第 3 条的占有标记与第 5 条的配置指纹。
- **02-architecture §7**：「每个租户固定路由到一个进程」「路由保证一个进程，epoch 兜底」改为第 1 条，单写者规则分开写两个后端；「读与写在进程内同一条队里轮流」「每租户写入串行：进程内按租户排队」「重连等于重新打开，要重新给 epoch 加 1」各句按第 1 条改；读取记录一节按第 2 条重写，服务器模式没有丢失窗口；「两个进程同时建一个用户的租户」一段；停止中的表现按第 7 条。
- **02-architecture §8**：导入「一个控制面库只有一个进程」与重入的一段改为第 3 条；`open` 与 `write` 的说明里 PostgreSQL 后端不再加、不再核对 epoch；每个写事务核对格式与封存。
- **04-contract**：`unavailable` 各原因的说明（`importing` 在多个进程下的含义、`stopping` 的两种情形）；`import` 期间的语义一句不变，实现方式变了。
- **05-surfaces §14、§15 与 06-cli §8.1**：不需要令牌的端点从一个变成两个；三处「计在进程内」的限额按第 9 条写明随进程数放大。
- **06-cli §4.1、§6.2**：`server start`、`server restore` 的锁；终止信号之后的行为；新增摘除等待与在途上限两个配置项；升级期间旧版本进程的表现。
- **07-scope-v1 与 08-open-questions**：单写者与 epoch 一行；「云服务跑几个进程」这一条关闭，新记「旧版本进程遇到已升级存储时的专门原因」。

## 怎么验

- 两个进程接同一个控制面库与同一组租户 database，请求按固定种子随机分给两边，读与写同时进行：写入全部成功，最终状态与同一串请求发给单个进程的结果逐项相同；同一个幂等键分别发到两个进程，只生效一次。
- 两个进程对同一行、带同一个 `ver` 同时更新：一个生效、一个成为候选。两个进程同时为同一个用户新建租户：只有一个租户，两边都不报错。
- 一个进程上的读进行到一半，另一个进程移除这个 slot：读不以内部错误结束；一个长读占着那张表时，移除在等待上限到时回 `unavailable`，这个租户的其他写入随后照常。
- 在一个进程上读、在另一个进程上不带 `ver` 写：按读到的版本判定。另一条连接占着该租户的 advisory lock 时，读照样完成。几个进程上同一个连接实例的读取记录乱序到达，「上次读到的版本」与「自我上次读之后的变更」都不倒退。读取记录写不进去时这次读回 `unavailable`。
- 导入：一次写入在封存之前通过了检查、在封存之后才取到锁，它回 `importing`，不是成功后丢失；导入期间另一个进程上走授权与刷新，不写进将被换下的 database；第二个导入落在另一个进程回 `rate_limited`；导入所在进程上的请求不会把自己判成占有者已死；导入在封存与换入之间、换入之后被杀，另一个进程按重入规则收尾；收尾的进程在解除封存之后、清占有标记之前再被杀，第三个进程接着做完，没有 database 停在封存状态；两个进程同时发现占有者已死，只有一个收尾；换入之后别的进程的下一个请求读到新 database 的内容，高水位没有被旧 database 推高。
- 本地账户登录：表单从一个进程取、提交到另一个进程，登录成功；换密钥的两步中间，各进程签的表单与翻页句柄互相验得过。配置指纹不一致的进程拒绝启动。
- 下线：发出终止信号后 `/ready` 立刻 503、`/health` 报 `stopping` 而 `/v1` 仍照常应答；摘除等待过后新连接被拒；一个永远不结束的请求在在途上限到时被关闭；一个卡在数据库锁上的使用不妨碍进程在三段时限之内退出。
- `server restore` 在有进程运行时拒绝执行；它执行期间 `server start` 拒绝启动。
- 两个版本：带加表式格式升级的新进程升级一个租户后，旧进程对它回 `unavailable`、对未升级的租户正常，升级时旧进程上进行中的读不受影响；新版本只读不写新形状的那个版本与旧版本同写一个租户，双方都读得懂。
- 导出一个大租户，量两批之间最长的静默时间，写进部署说明。
- 本机模式的全部现有测试不变。

## 分步交付

1. `/ready` 与分步下线（第 6、7 条）。它让还没就绪的进程不收请求、让进程在退出前把手上的请求做完。这一步之后一个部署仍然只能有一个进程，更新仍是先停后起：新进程要等旧进程放掉「服务器在运行」的锁才起得来，而两个进程并存要到第 2 步做完才安全。
2. 取消 PostgreSQL 后端的所有权、连接失败即重开、读取记录即时落盘、导入的封存与占有、共享密钥与配置指纹、共享锁、每个写事务核对格式与封存（第 1–5 条与第 8 条的核对），连同上面的两进程测试。这一步改控制面库的格式，升级到它要全部停下一次；做完才允许启动第二个进程，不停机的更新从这里开始。
3. 第 8 条的两个版本规则，随第一个带格式升级或新事件形状的版本一起验。

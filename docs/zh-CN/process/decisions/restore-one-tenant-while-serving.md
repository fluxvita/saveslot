# 决定：服务器模式在进程运行时恢复一个租户

> 不改事件格式，不改 K1–K14，不改操作契约。依赖「服务器模式一个部署运行多个服务进程」第 2 步的占有、封存与共享锁；在它之后落进规格与代码。

本文里「进程」指一个 `saveslot server start` 的服务进程。「恢复流程」指 02-architecture §8 的那一套：追加恢复事件、按删除登记补删、补跑已到期的删除。

## 要解决什么

把一个租户从备份恢复回来，要先停掉整个部署。`saveslot server restore` 只在同一个控制面库上没有任何进程运行时执行：它取 `server start` 运行期间持有的那把锁，取不到就什么都不做（06-cli §4.1）；多进程决定第 4 条把这一点保留成「`server restore` 取独占锁」。于是恢复一个租户的步骤是：停掉全部进程，把这个租户的 database 从备份放回，运行命令，再启动。这期间所有租户都不能用。

只有一个用户的部署不在乎。有许多租户的部署，一个人的恢复不该让所有人停下。

目标：恢复一个租户时，只有这个租户不可用，别的租户照常；恢复流程本身不变，结果与停机恢复相同。

本机模式不变。

## 为什么现在必须停

恢复有两段，各有一个要求别人不在场的理由：

1. **把 database 放回。** 现在的做法是部署方在原地换掉租户的 database（同一个名字）。进程运行时做不了：进程在这个 database 上有连接，换不掉；换掉之后、命令运行之前，进程会照常打开这个回退了的 database 对外服务，而「打开时发现日志末端低于高水位」只是兜底，回退落在最近一次高水位推进之后就发现不了（02-architecture §8「兜底的实际覆盖面」）。
2. **走恢复流程。** 流程在锚点存储与租户存储上分几步做，中间的状态不能被读到、不能被写进去。现在靠的是「没有任何进程」。

所以要改的也是两处：database 不在原地换；流程进行中只挡这一个租户。

## 决定

### 1. 备份放进一个新的 database，由命令换入

部署方把备份恢复成租户所在 cell 上的一个**新的** database（下称候选库），名字自定；当前的 database 不动。然后运行：

```
saveslot server restore --tenant <租户> --from <候选库>
```

（`--user <名字>` 照旧可以代替 `--tenant`。）命令核对候选库，把租户改指到它，在它上面走恢复流程。进程可以在运行，也可以不在。

候选库的名字照租户目录对库名的规定核：合 PostgreSQL 库名的形状，不是服务器自带的库，不以 `_reconcile` 结尾，**并且不是租户目录在这个 cell 上以任何身份记着的 database**：某个租户的 database、暂存 database、待丢弃的 database、一次搬迁的目标、另一次恢复的候选库，都不行（含这个租户自己的）。尤其是这个租户上一次恢复换下来、还没丢掉的那一份：它是这个租户的、链也校验得过，拿它当候选库换入之后，它仍记在「待丢弃」里，下一次重试丢弃就把正在用的 database 删了。要退回到上一次恢复之前，从备份再放一份新的。它必须在租户现在所在的 cell 上；要恢复到另一个 cell，先恢复，再搬。

好处不止于不停机：换入之前当前的 database 原样留着，候选库核对不过时什么都没变。

**不选的做法：**

- *命令自己读备份文件、建候选库。* 备份用什么做、放在哪、怎么取回是部署方的事（02-architecture §9）；命令只认一个已经在 cell 上的 database。
- *在原地换，命令先让各进程放掉连接。* 换的那一下是部署方用数据库工具做的，命令管不到它的前后；中途失败时当前的 database 已经没了。

### 2. 步骤

| 步 | 做什么 | 这一步之前停下，租户在哪 |
|---|---|---|
| ① 预检 | 租户在目录里、已建完；没有导入、搬迁或另一次恢复在进行；候选库的名字合规定、在租户的 cell 上。这几项读的是目录行，这里做只为早些拒绝，作数的是 ② 里在占有之下重做的那一遍。打开候选库之前，先照 `server start` 的做法核对这个 cell 的实例身份（「一个部署使用多个 cell」第 2 条），不符或连不上即停。打开候选库：存储后端打开时的各项核对（服务器大版本、编码、排序规则、存储格式、固定的会话设置），格式低于内核的在这里升级；`log.verify` 的检查（事件头链、内容校验和）；**日志记的当前租户 ID 是这个租户**（以最近一条创世或导入事件为准，09-event-format）；**日志里最近的恢复次数不大于锚点里的**（大于说明它不是这个部署的这段历史里出来的，例如同一个租户 ID 在别的部署上的副本：恢复给它的次数可能与它日志里已有的重号）。恢复流程会拒绝的情形在这里先拒绝：这一版里删除登记有条目的租户。**这个租户的「待丢弃」里已经有 database 时**（一次搬迁的源，或上一次恢复换下的），先试着丢弃它；丢不掉（别的进程还连着）就拒绝，退出码 7，稍后再运行：「待丢弃」的位置只放一个，不覆盖 | 没开始 |
| ② 占有 | 在控制面库的租户目录里记下「正在恢复」、候选库的名字与这次运行的两个选项（是否跳过封存、是否保留被换下的 database：收尾的进程要照它们做，第 4 条），并持有以这个租户为键的占有锁（先取锁、后写标记）。用的是多进程决定第 3 条给导入的那一套。**写标记的那个事务里，在占有锁之下把 ① 里读目录行的各项重做一遍**：租户已建完、没有别的标记、候选库在租户现在的 cell 上、「待丢弃」是空的、候选库的名字没有被目录以任何身份记着；有一项不符，不写标记，放锁，什么都没改。① 与 ② 之间这个租户的一次搬迁可以开始并做完（换了 cell，源进了「待丢弃」），只在 ① 查是查不出的。候选库自身内容的核对不用重做：除了这条命令没有别人打开它。从这一刻起，任何进程对这个租户的每次使用回 `unavailable`（`restoring`），读与写都是 | 当前的 database，可用 |
| ③ 封存当前的 database | 一个写事务：取该租户的 advisory lock，在 `meta` 里写下「已封存」；同一个事务读出日志末端，随后把锚点的高水位推到它。此后任何进程在这个 database 上的写事务取到锁后见到封存，什么都不写。封存标记带着原因：导入的封存回 `importing`，这里的回 `restoring`。读取记录的事务不取这把锁，照「一个部署使用多个 cell」第 5 条定下的做法另核封存（它以 `FOR SHARE` 读 `meta` 里存储格式版本那一行，封存的事务先以 `FOR UPDATE` 锁住同一行），见到封存不写、这次读回 `unavailable`（`restoring`）：② 之前通过了检查的读，封存之后不会再应答 | 当前的 database，标记在：由收尾的进程解除（第 4 条） |
| ④ 换入 | 控制面库的一个事务：先核对租户的 cell 还是 ② 时的那个、「待丢弃」还是空的（占有之下不该变；变了就不换，照第 4 条「④ 之前」收尾并报错）；租户目录里这个租户的 database 改为候选库，被换下的记在「待丢弃」的位置；锚点里置「恢复进行中」。这是不能回头的一步 | 同上 |
| ⑤ 恢复流程 | 在候选库（现在是租户的 database）上走恢复流程，与停机恢复是同一段代码：追加恢复事件（`seq` 从高水位之后接着编，换节点 ID，恢复次数加 1），按登记补删，补跑已到期的删除，核对无误后清「恢复进行中」。候选库若带着封存标记（备份恰好取在一次封存期间），**在清「恢复进行中」之前解除**：流程的第一次写入之前就解，否则它自己的写入也会被拒。次序反过来的话，清掉「恢复进行中」之后、解封之前死掉，收尾的进程看到流程已经做完，做完 ⑥、清了标记，租户正在用的 database 却封存着、再没有标记可解 | 候选库，「恢复进行中」在：接着做（第 4 条） |
| ⑥ 收尾 | 先看租户现在的 database 有没有封存，有就解除（⑤ 已经解过时什么都不做；多核一遍，是为了任何路径走到这里都不会留下封存着的现行库）。然后清掉「正在恢复」，放掉占有锁；之后在占有之外丢弃被换下的 database，丢完才清「待丢弃」。**标记里记着保留的**：把它从「待丢弃」里去掉与清掉「正在恢复」在控制面库的同一个事务里做，不分先后两步，否则清了标记、还没去掉条目时死掉，「保留」已无处可查，下一次打开或闲置关闭就把部署方要留的那份丢了。保留下来的 database 的名字写在命令的输出里；由收尾的进程做完的，写进服务日志（`restore_replaced_kept`，带租户 ID 与库名） | 候选库，可用 |

- **期间**：从 ② 到 ⑥，这个租户的读与写都回 `unavailable`（`restoring`），带 `retry_after`；别的租户不受影响。时长是恢复流程的时长加一次封存。
- **读也挡**：内容即将回到备份时的样子，恢复次数即将加 1；这中间读到的版本与句柄，一会儿就都对不上了。读取记录也在租户的 database 里，恢复之后是备份时的那一份：备份之后的读没有记录留下，这是恢复本来的含义，与备份之后的写入不在是同一件事；挡住读，是不让这样的读在命令开始之后还继续发生。
- **各进程手上的旧连接**：进程在下一次使用这个租户时看到目录行变了，关掉旧连接、重开到新的 database（多进程决定第 3 条「database 换了就重开」）；闲置的到期自己关。**高水位只从租户现在的 database 推进**：任何一种推进（关闭租户时、隔若干事件或若干秒的定期推进、删除相关的提交之后）都写成控制面库里的一次带条件的更新，条件是租户目录行记的 database 仍是读出这个日志末端的那一个；不是，这次推进不生效。锚点与目录在同一个控制面库里，所以这是一条语句。它盖住的不只是「因换入而过期的连接在关闭时」这一种。丢弃被换下的 database 要等这些连接都放掉，所以放在占有之外做，不用 `FORCE` 去断别的进程的连接；删不成就留在「待丢弃」的位置，之后在打开或闲置关闭这个租户时重试，与搬迁留下的源相同，它同样挡着所在 cell 的 `cell remove`。
- **`--keep-replaced`**：给了它，被换下的 database 不丢弃，从目录里去掉，名字写在命令的输出里。它不在租户目录里，不会被当成任何租户的存储打开（封存过的还带着封存标记）；此后它是部署方手里的一份副本，按备份对待，何时删由部署方定。

### 3. 封存为什么要，封不了怎么办

恢复本来就丢掉备份之后的一切，封存不是为了保住那些写入。它保的是两件事：

- **`seq` 不与已经应答过的写入重号。** 高水位是隔一段才推进一次的；封存之下把它推到当前日志的末端，恢复事件的 `seq` 就排在这个租户应答过的每一次写入之后。
- **换入之后没有写入再落到被换下的 database 里。** 一次写入在 ② 之前通过了检查、之后才取到锁，没有封存它会提交成功、应答成功，而数据在一个已经不是这个租户的 database 里。有了封存，它回 `unavailable`（`restoring`）。

要恢复的原因可能正是当前的 database 打不开了。这时封不了，命令停在 ③：清掉 ② 的标记、放掉占有锁，说明原因，没有改指任何东西；部署方确认后带 `--current-unusable` 重新运行，跳过 ③。

**什么算打不开。** 命令自己对这个 database 新开一条连接、照打开租户的做法打开它，得到的是下面两类之一：

- 数据库拒绝连到这个 database（它不存在、被设成不接受连接、角色对它没有连接权限），或连上之后读不了它的系统目录；
- 打开时的某一项核对不过（服务器大版本、编码、排序规则、存储格式、固定的会话设置），或日志读不出来。

不算的：等不到锁；本进程或这个实例的连接名额满了（SQLSTATE 53300）；连不上这个 cell 的实例，或它在本进程里还没核对过身份。这些是「稍后再试」，退出码 7，带不带 `--current-unusable` 都一样：它们说明的是此刻够不着，不是这个 database 坏了，别的进程可能正在它上面照常读写。

跳过 ③ 的后果：

- 高水位停在最近一次推进的位置，其后分配过的 `seq` 可能被恢复后的写入重用。这正是恢复流程本来就处理的情形：每次恢复换节点 ID、恢复次数加 1，`ver`、事项版本与句柄都带恢复次数（02-architecture §3「`seq` 不复用」）。
- 命令打不开它，不等于别的进程写不进去：早先开着的连接可能还能用（新连接被拒而旧连接照常；打开时的核对，已经开着的连接不会再做一遍）。挡住它们的是 ②，不是这个 database 坏了：占有之后每一次使用都在目录行上被拒，只有在 ② 之前已经通过检查的写入还可能提交。所以跳过封存时，命令在 ② 与 ④ 之间等 10 秒（初值），让这样的在途写入做完或失败；这缩小而不是关上这个窗口。等过之后才提交的写入与备份之后的其他写入一样，不在恢复后的租户里。读也是同一条边界：② 之前通过了检查的读，没有封存时照常把读取记录落在旧的 database 里、照常应答，那条记录随旧的 database 一起不在了。命令的输出写明这两点。
- 这样的晚到的写入提交之后，那个进程还可能照常去推进高水位，而它手上的日志末端是被换下的 database 的，可以高于恢复开始时的高水位；这次推进若落在 ⑤ 之后，高水位就高过了恢复后的日志末端，下一次打开这个租户会被当成回退而拒绝。上面「高水位只从租户现在的 database 推进」挡住它：换入之后，从旧 database 读到的末端推不进去。有封存时没有这件事：旧 database 的末端冻结在 ③ 推到的位置。

`--current-unusable` 只在当前的 database 确实打不开时才被接受：打得开而给了它，命令拒绝，要求不带它运行。

### 4. 中途停下

占有者死了（有「正在恢复」的标记而锁没人持有），发现它的进程先取占有锁，再按做到了哪一步收尾，规则与导入的占有者死了相同，判据只看目录行：

- **租户的 database 还是原来那个**（停在 ④ 之前）：标记里记着没有跳过封存的，解除它的封存，再清标记；记着跳过了的，没有封存可解，直接清标记。候选库不动、不丢弃：它是部署方放上去的，命令没有改过它（① 里的格式升级除外），部署方可以再运行一次命令。
- **解除封存做不成**（封存之后这个 database 打不开了，或一时够不着）：标记不清，租户继续回 `unavailable`（`restoring`），日志里记一条错误。不能把「打不开」当成「没有封存可解」：一个只是一时够不着的 database 会因此丢了标记、却一直封存着没人去解。出路只有两条：它又够得着了，下一次发现时解封、清标记；或部署方带 `--current-unusable` 再运行一次（下面）。
- **租户的 database 已经是候选库**（停在 ④ 之后）：恢复流程靠锚点里的「恢复进行中」重入，接着做完；再做 ⑥，照标记里记的保留或丢弃被换下的 database。标记最后才清。

部署方重新运行命令，效果相同：命令先取占有锁，发现上一次留下的标记，照上面收尾，再看还要不要做。对一个恢复已经做完的租户再运行一次，是另一次恢复，要给新的候选库。

**带 `--current-unusable` 重新运行、遇到解不了封的遗留标记**：当前的 database 照上面的定义确实打不开时，命令不再试着解封，接手这个标记（改记这次的候选库与选项），从 ② 之后接着做到 ④。那个 database 马上要被换下，留着封存没有害处。打得开的，照常先解封、清标记，再从头做，并且拒绝 `--current-unusable`。

### 5. 停机的那一种保留

不带 `--from` 的 `server restore` 是现在的命令：取独占锁，只在没有进程运行时执行，对已经在原地放回的 database 走恢复流程。只多一件事：它也先取这个租户的占有锁，目录里有上一次带 `--from` 的运行留下的「正在恢复」时，先照第 4 条收尾，再做自己的事。否则部署方在一次带 `--from` 的运行死掉之后停机处理，④ 之前留下的封存会让恢复流程的第一次写入被拒，④ 之后留下的标记与被换下的 database 没人管。收尾里解不了封时，它与带 `--from` 的一样停下，说明原因。它留给两种情形：

- 控制面库连同租户库一起从备份放回，或一次放回了许多租户；
- 进程因为发现日志回退而拒绝服务某个租户、提示走运维命令时，部署方选择停机处理。

带 `--from` 的命令取共享锁，与 `server start` 相同；有一个不带 `--from` 的恢复在执行时，它与 `server start` 一样等不到，退出码 7。

控制面库自己的恢复不在这份决定里：它回退之后删除登记与高水位也回到当时，saveslot 补不了也发现不了（02-architecture §8），仍然是全部停下之后的事。

### 6. 删除登记里有条目的租户

恢复流程里「按登记补删」这一段还没有做出来；这一版里，删除登记有条目的租户，恢复被拒绝，什么都不改。这份决定不改变它：① 的预检照样拒绝。补删做出来之后，停机的与不停机的两种命令同时可用，因为走的是同一段流程。

## 不在这份决定里

- 备份怎么做、多久做一次、保留多久。逐个 database 的逻辑备份由部署方做。
- 冷租户归档。把一个归档的租户取回，就是先把它的 database 放回 cell、再用这里的命令；归档自己的规则另定。
- 恢复到另一个 cell、恢复成另一个租户。
- 用户自己发起恢复。命令只给部署方。

## 它改了哪些已有的规定

- **02-architecture §5「控制面存储」**：租户目录的占有标记多一种「正在恢复」，带候选库的名字；「待丢弃」的位置除导入外多一个使用者。控制面库的格式有一次改动，带升级步骤与格式样本。
- **02-architecture §7、§8**：封存除导入外多一个使用者；「恢复备份……之后必须走恢复流程」一段补上不停机的做法、步骤与重入；触发途径里服务器模式的「运维命令」分成两种。
- **04-contract**：不变。`unavailable`（`restoring`）已经在；它在多个进程下的含义照这里写明。
- **06-cli §4.1、§6.2**：`server restore` 的 `--from`、`--keep-replaced`、`--current-unusable`；带 `--from` 时取共享锁；各种拒绝的退出码（候选库不合规定、不是这个租户的备份、校验不过：5；另一次恢复、导入或搬迁在进行：7）。
- **「服务器模式一个部署运行多个服务进程」第 3、4 条**：「`server restore` 不需要这一套：它执行期间没有任何进程在运行」只对不带 `--from` 的成立。
- **讲解**：自部署与运维各章里恢复一个租户的步骤。
- 事件格式、内核不变量、操作契约、租户存储的格式都不变。

## 怎么验

- 两个进程在运行，租户甲被恢复：期间甲的读与写在两个进程上都回 `unavailable`（`restoring`），租户乙在两个进程上读写照常，没有一次失败。恢复之后甲的内容是备份时的，恢复事件、恢复次数、节点 ID 与停机恢复同一份备份的结果逐项相同。
- 一次写入在 ② 之前通过了检查、在 ③ 之后才取到锁：回 `unavailable`，不是成功；一次读在 ② 之前通过了检查、在 ③ 之后才写读取记录：同样回 `unavailable`，不应答内容；被换下的 database 的日志末端等于封存时读到的那一条。
- 封存之下高水位被推到日志末端：恢复事件的 `seq` 大于这个租户应答过的每一次写入的 `seq`。
- 恢复之前发出的 `ver` 与句柄，恢复之后都对不上；恢复之后的读写照常。
- 候选库是另一个租户的备份（含日志末尾是一次导入、当前租户 ID 因此不同于创世事件里那个的情形，按当前的算）：① 拒绝，什么都没改。候选库的事件头链断了、内容校验和不对、格式比内核新：同样。候选库是别的租户的 database 或暂存 database：拒绝。
- 候选库的存储格式比内核旧：① 里升级，之后照常。候选库带着封存标记：恢复之后可写。
- 当前的 database 打不开（被设成不接受新连接）：不带 `--current-unusable` 停在 ③、租户目录没变、标记已清；带上它恢复做完，期间另一个进程早先开着的连接上、② 之前通过检查的一次写入，要么在等待的 10 秒内结束，要么不在恢复后的租户里。当前的 database 打得开而带了它：拒绝。连接名额满了、cell 连不上：带不带它都是退出码 7，什么都没改。
- 候选库是这个租户上一次恢复换下、还在「待丢弃」里的那一份：① 拒绝。候选库是一次搬迁的目标或另一个租户恢复的候选库：拒绝。候选库日志里的恢复次数大于锚点里的：拒绝。
- 这个租户的「待丢弃」里已有 database：命令先丢弃它再继续；丢不掉时退出码 7，目录没变。
- 带 `--current-unusable` 的运行在 ② 之后、④ 之前被杀：收尾的进程不去解封，直接清标记，租户回到原来的 database。不带它、封存之后 database 变得打不开时被杀：标记留着，租户回 `restoring`；带 `--current-unusable` 再运行，接手标记、做完。database 只是一时够不着时被杀：标记留着，够得着之后的下一次发现解封、清标记，没有 database 封存着而没有标记。
- 带 `--keep-replaced` 的运行在 ④ 之后被杀：收尾的进程做完恢复，不丢弃被换下的 database，库名在服务日志里。在「去掉待丢弃并清标记」的那个事务前后各杀一次：之前，标记与条目都在，下一个收尾的照「保留」做；之后，两样都不在，保留的 database 没有被丢弃。
- 候选库带着封存：在「恢复进行中」刚清掉时被杀，收尾之后租户可写，现行的 database 没有封存。
- ① 通过之后、② 之前，这个租户被搬到另一个 cell：② 拒绝，没有写标记，目录与「待丢弃」是搬迁留下的样子。
- 跳过封存时，另一个进程在旧连接上晚提交了一次写入、随后触发定期推进：高水位不变；恢复之后在任何进程上打开这个租户都不被当成回退。同一情形下的一次读照常应答，它的记录不在恢复后的租户里。
- cell 的实例身份不符或连不上：命令在打开候选库之前停下，退出码 7，什么都没改。
- 命令在 ② 之后、③ 之后、④ 之后、⑤ 途中、⑥ 丢弃之前各被杀一次：另一个进程的下一次使用收尾；前两种租户回到原来的 database、可写、没有封存，候选库还在；后三种租户在候选库上、恢复已做完、可写。没有 database 停在封存状态而仍是某个租户的存储。两个进程同时发现占有者已死，只有一个收尾。
- 丢弃被换下的 database 时别的进程还连着它：这次不丢，留在「待丢弃」，下一次打开这个租户时丢掉。`--keep-replaced`：它不被丢弃，不在目录里，带着封存标记。
- 一个不带 `--from` 的恢复在执行时，带 `--from` 的退出码 7；有进程运行时，不带 `--from` 的仍然退出码 7。
- 带 `--from` 的运行在 ④ 之前、之后各被杀一次，随后停掉全部进程、对这个租户运行不带 `--from` 的：先收尾（前一种解封、清标记，后一种做完恢复、处理被换下的 database），目录里不留「正在恢复」。
- 删除登记有条目的租户：带不带 `--from` 都被拒绝，什么都没改。
- 导入、搬迁进行中的租户不能恢复；恢复进行中的租户不能导入、不能搬。
- 没有进程运行时带 `--from` 运行：照常做完。
- 本机模式的全部现有测试不变。

## 交付

一步，在多进程决定第 2 步之后：它用到那一步的占有标记与占有锁、`meta` 里的封存、每次使用先看目录行、共享与独占的锁。与「一个部署使用多个 cell」没有先后依赖；两者都改控制面库的格式，能合成一次停机升级就合成一次。

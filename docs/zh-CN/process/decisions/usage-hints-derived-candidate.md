# 决定：反复算同一种聚合时，提示可以建一张派生表

> 给操作契约加一种提示（`notices` 的一个新取值）与 `catalog` 表概况里的一个可选键；租户存储多一张计数表。不改事件格式，不改 K1–K14，不改任何判定。核心路径不调用模型。审过再落进规格与代码。

## 要解决什么

Agent 一开始没有建派生表，而用户的问题一再需要同一种聚合：每周的里程、每月每类的支出。Agent 每次都用受限 SQL 现算一遍，结果对，但每次都要重写同一条语句，表大了以后每次都要扫一遍。内核看得见每一次这样的读取，却什么都不说。

目标：内核按确定的规则认出「同一种聚合被反复计算」，在合适的地方把这件事告诉 Agent，附上一条可以直接用的派生规则。建不建由 Agent 与用户定；内核不自己建表、不自己加规则。

这是「按用法给提示」的第一种。别的模式（没有索引的筛选、总是一起读的两张表）等这一种证明有用之后再谈。

## 现状里可以用的

- **读取记录已经记着形状。** 每次 `sql` 读取在读取记录里有一段结构指纹：表名、字段名换成 ID，每个常量换成占位符，去掉别名与注释（03-data-model「读取记录里记什么形状」）。「同一种聚合换了日期范围再问一次」是同一段指纹，里面没有任何调用方给的值。
- **`notices[]` 是现成的通道。** 与本次调用相关的提示，按此刻的状态算，只按可见范围算，计算本身不记进读取记录，最多 3 条，报错的结果不带（04-contract §13）。
- **`catalog` 的规模提示是现成的样子。** 表概况里的 `scale` 读时算出，不进事件，不是数据标记，情况变了自己消失（02-architecture §8「容量边界」）。一条由当前状态算出、结构一变就自己消失的提示，不需要「不再提示」的机制。

## 决定

### 1. 认什么：一次读取的「聚合形状」

一次 `sql` 读取满足下面全部条件时，有一个聚合形状；否则没有，不计数、不提示：

- 最外层是对**一张基础表**的聚合：`SELECT` 里只有分组键与聚合函数，`FROM` 只有这一张表，没有连接、没有子查询；
- 聚合函数与分组表达式都在派生规则的白名单之内；
- `WHERE` 里的每个条件，都是某个字段与常量的比较（相等、范围、`IN`），条件之间只用 `AND` 连接。

聚合形状是这样一个值，由语法树算出，不含任何常量：

| 组成 | 取法 |
|---|---|
| 表 | 表 ID |
| 分组键 | `GROUP BY` 的字段 ID，**并上** `WHERE` 里被条件限定的字段 ID（按这个字段分组的派生表答得了对它的筛选）；排序后去重 |
| 时间粒度 | 表的时间字段出现在分组或条件里时：`GROUP BY` 里按日、周、月截取的取那个粒度；只出现在条件里的取「日」 |
| 聚合项 | （函数，字段 ID）的集合，排序后去重 |

- 这样算出的形状，正好对应一条派生规则：按分组键与时间粒度分组、算那几个聚合项。**写不出这样一条规则的读取没有形状**，所以不会提示一张建不出来的表。
- 两次读取形状相同，当且仅当上面四样都相同。日期范围、筛选的取值、`ORDER BY`、`LIMIT` 都不影响。
- 简单查询 `query` 逐行读，不是聚合，没有形状。读派生表没有形状。

规则的逐条细节（各函数怎么归一、时间截取的写法认哪些）随实现写进 03-data-model 的受限 SQL 一章；这里定的是原则：只认能原样改写成一条派生规则的读取。

**不选的做法：** 直接按读取记录里的指纹文本计数。两条语句只差一个 `ORDER BY`、或一条按月筛选一条按周筛选，指纹不同而需要的是同一张派生表；按文本数会把同一个需要拆成几份，哪一份都够不到阈值。

### 2. 数什么：调用方自己的读取，一段时间之内

**提示成立的条件**（初值，内核常量，随评测调）：同一个连接实例，在最近 14 天里，有至少 5 次读取是这个形状，并且分布在至少 2 个不同的日子（按 slot 的时区）。本次读取算在内。

- **只数调用方自己的。** 数全部连接实例的读取、再把结果给其中一个看，等于告诉它别的 Agent 在怎么用这张表。`history` 本来就给得出别的连接实例对某个目标的读取，但「按形状的次数」是一种新的汇总；先从最保守的做起。用户会话数的是它自己的读取。
- **至少两个不同的日子**：一个会话里连着重试五次不算反复需要。
- **不看 `task`、不看会话。** 同一件事隔几天再问，正是要认出的情形。

**怎么数得动。** 每次调用都去扫读取记录不行。租户存储加一张计数表：连接实例、形状、日子 → 次数；写读取记录的那个事务里顺手加一。它与读取记录是同一类东西（02-architecture §3 的 (c) 类）：本机的运行状态，不进日志，不随租户导出，导入之后从零开始，随备份一起回到当时，按读取记录的保留期清理（只留最近 14 天的就够用）。它丢了，后果只是提示晚出现几天。

### 3. 在哪里说

**一、命中的那次读取的 `notices[]`。** Agent 此刻正在回答关于这张表的问题，最可能用得上。

```ts
type Notice =
  // …已有的各项
  | {
      code: "derived_candidate";
      slot: SlotName;
      table: TableName;
      /** 分组键，现在的名字。 */
      group_by: FieldName[];
      /** 时间粒度；形状里没有时间时不给。 */
      bucket?: "day" | "week" | "month";
      /** 聚合项，字段用现在的名字。 */
      aggregates: Array<{ fn: string; field: FieldName }>;
      /** 窗口内这个形状的读取次数（本次在内）与窗口的天数。 */
      reads: number;
      window_days: number;
      /** 可以放进 schema_draft 的派生规则：规则的 SQL（用名字写、不含任何常量）与时间依赖。 */
      rule: { sql: string; time_dependency: "none" | "bucketed" };
    };
```

- 次序排在最后：`deletion_overdue`、`migration_progress`、`schema_updated`、`pending_items`、`derived_candidate`。合起来超过 3 条时它最先被截掉；它不会挤掉任何一条关于用户数据的提示。
- 一次调用至多一条，就是本次读取自己的形状。别的调用（`write`、`catalog`、别的形状的读取）不带它。
- 契约只带结构化的字段，文字由外化面渲染。渲染出来的是事实，不是指令：「最近 14 天里有 6 次读取按 category、按月对 ledger.expenses 求 sum(amount)；用下面这条规则建一张派生表可以直接读到它们。」怎么做留给 Agent 与用户。

**二、`catalog` 的表概况。** 给先看目录、再动手的 Agent。`table` 档的 `profile` 多一个可选键 `derived_candidates`：这张表上、调用方自己的、此刻成立的候选，至多 3 个，按次数从多到少；每个的内容与上面那条提示相同（不重复 `slot` 与 `table`）。没有就不给这个键。

**不放的地方：**

- *不做成待处理事项。* 事项是持久的、不过期的，每次调用都计进 `pending_items`，是 Agent 应当向用户提起的事。一条关于结构的建议放进去，会冲淡这个信号，而且它没有「解决」的含义。
- *不放进写入回执。* 写入时 Agent 关心的是这次写入的结果。
- *`saveslot doctor`* 可以另外列出，那是给人看的；它不是主要的地方。

### 4. 什么时候不再说

提示是「窗口内的计数」与「当前的 schema」两样的函数，没有另存的状态：

- **有一张派生表已经答得了它**：同一个 slot 里有一张派生表，它的规则按第 1 条算出的形状，表与聚合项相同、分组键包含这个形状的分组键、时间粒度不比它粗。这时不给。Agent 建了表，提示自己消失；之后它若仍用 `sql` 现算，也不再提醒，那是它的选择。
- **不再那样读了**：窗口里的次数掉到阈值之下，自己消失。
- **表或字段不在了、不可见了**：形状里的任何一个 ID 解析不到现在可见的名字，不给。

**没有「不再提示」的记录。** 用户明确说「这张表不要建」，要记下来就是一个新的事件或 schema 上的一个标注；第一版不做。代价有限：提示只出现在形状相同的那种读取上，不出现在这个 slot 的每一次调用上，一条被忽略的提示每次只多占一条 `notices`。

### 5. 可见范围与权限

- 只按调用方的可见范围算：表与形状里的每个字段都可见才给；计数只来自调用方自己的读取，本来就在它的范围之内。
- 调用方没有改 schema 的权限时照样给：它可以告诉用户。提示本身不授予任何权限，`schema_draft` 照常核对。
- 提示里的名字是 schema 里的文字，渲染时照不可信文字对待，带边界标记（05-surfaces §5）。规则的 SQL 由内核从形状生成，里面没有调用方的原话与任何常量。

### 6. 不记什么

- 提示的计算不记进读取记录（`notices` 的现有规则）。
- 计数表里只有连接实例、形状与日子：形状由 ID 组成，没有值。它不比读取记录多知道任何事。
- 不进事件日志，不影响重放与对拍。

## 怎么评

照 10-evals 现有的做法，加两个变体：

- **该出现的**：一张事先放好数据的事件表，脚本在几轮对话里、隔着日期反复问同一种聚合。分别在带这条提示与抑制这条提示的配置下跑（与对照配置抑制 `instructions` 同一个做法）。看三件事：Agent 有没有提出建派生表；改 schema 之前有没有先问用户；之后的回答与预置的真值是否仍然相等。
- **不该出现的**：同一张表被以各种不同的方式读（不同的分组、不同的聚合），每种都不够阈值。提示一次都不该出现；出现了就是规则认得太宽。

阈值与窗口的数值由这两个变体定；评测没跑之前它们只是初值。

## 不在这份决定里

- 内核自己建派生表或规则。
- 别的使用模式的提示。
- 把这类聚合交给另一种存储引擎。
- 永久的「不再提示」。
- 把次数汇总给部署方看（那是用量，另有去处）。

## 怎么验

- 形状：只差日期范围、筛选的取值、`ORDER BY`、`LIMIT` 的两条语句形状相同；分组键、聚合项或时间粒度不同的不同。带连接、子查询、`OR`、白名单外的函数的语句没有形状。由形状生成的规则交给 `schema_draft` 能通过编译，建出的派生表对同样的筛选给出与原语句相同的结果（性质测试：随机的形状与数据）。
- 阈值：第 5 次、且落在第 2 个日子的那次读取带提示，之前的不带；同一天的 5 次不带；窗口外的不算。
- 只数自己的：另一个连接实例读了 10 次，这个连接实例的第 1 次读取不带提示；`catalog` 里也没有。
- 消失：建了匹配的派生表之后，同样的读取不再带；删掉那张派生表，又带。分组更细、粒度更细的派生表也算答得了；更粗的不算。
- 次序与截断：与另外三条提示同时成立时，它被截掉。报错的结果不带。
- 可见范围：形状里有一个字段不可见时不给；提示与候选里不出现范围外的名字。
- 提示的计算不产生读取记录；带与不带这条提示的两次运行，日志逐字节相同。
- 导入之后计数从零开始；计数表清空之后一切照常，只是提示晚出现。
- 本机模式与服务器模式结果相同；两个进程各处理一部分读取时，次数是合起来的。

## 分步交付

1. 聚合形状的计算与由形状生成规则，连同它的性质测试。不对外可见。
2. 计数表（存储格式的升级）与读取时的计数。
3. `notices` 的新取值与 `catalog` 的键，外化面的文字，两个评测变体。数值按评测结果定下之后才随版本发布。

## 1. 起因

容量实验 9（[`07-scope-v1.md`](../../spec/07-scope-v1.md) 第 4 节）的 C 组在本机模式（PGlite）上测了一张分钟级的事件表：每行三个字段（`day`、`minute`、`value`），时间字段是 `day`，上面有两张按天、按月分桶的派生表。

| 表的总行数 | 50 万 | 100 万 | 200 万 | 500 万 | 1000 万 |
|---|---|---|---|---|---|
| 单条写入 p50 | 1.1 秒 | 2.2 秒 | 6.6 秒 | 17.0 秒 | 约 34.5 秒 |
| 一次写 1000 行 p50 | 3.3 秒 | 4.7 秒 | 8.8 秒 | 16.6 秒 | 约 40.5 秒 |
| 按时间范围查询（命中约一半，取第一页） | — | — | — | 59 秒 | 内存不足 |

测量条件：Apple M4 Pro，24 GiB 内存，Node 26.13.1，PGlite 0.5.16，存储格式 4。

从这些数可以看出两件事：

1. **写入的耗时随表的总行数成正比，和这次写几行几乎无关。**
2. **查询取一页的耗时随命中行数增长，和页的大小无关。**

逐条读过内核对业务表、版本表、派生表发出的 SQL，现状是：

- **建表时只建主键。** 业务表：事件类与无时间表是 `row_id`，状态类表是 `(entity_id, valid_from)`。版本表：主键加一个 `(row_id, rec_from)`。派生表：`partition_id`。
- **凡是不按这些键找行的语句，都要扫全表。** 第 2 节逐条列出。

## 2. 哪些语句扫全表，哪些靠索引能治

| 语句 | 什么时候跑 | 过滤在哪些列上 | 索引能不能治 |
|---|---|---|---|
| 派生刷新：重算整条规则 | 每次写到规则依赖的基础表 | 规则的全部输入行 | **不能**。见下文 |
| 疑似重复：找命中的行 | 新增一行、表声明了 `duplicate_keys` | 每组键的字段 = 值，`NOT revoked` | 能：每组键一个索引 |
| 引用方：谁引用了这一行 | 撤销一行、刷新待处理事项 | `ref` 字段 = 行 ID（事件类与无时间表另加 `NOT revoked`） | 能：每个 `ref` 字段一个索引 |
| 自然键：找已有的实体与相近的键 | 写入一个新的自然键 | 版本表上 `max(rec_from) GROUP BY row_id`，不带任何过滤；业务表上 `DISTINCT entity_id` | **不能**。要改写查询，见第 7 节 |
| 查询：按时间范围取行 | 读 | 事件类表的时间字段范围；状态类表的 `valid_from` / `valid_to` | 能，但只有分页同时下推到 SQL 时才有用（第 7 节）；第 2 页起怎么下推见第 3 节「第 2 页起怎么下推」 |
| 查询：按记录时刻读整张表（`as_of`，以及第 2 页起按第一页的位置读） | 读 | 版本表上 `rec_from <= X AND (rec_to IS NULL OR rec_to > X)`，不带 `row_id` | 这条语句本身不能：这个时刻仍然有效的格子差不多就是整张表。第 2 页起改写成「业务表上的索引 + X 之后动过的行回版本表」，见第 3 节 |
| 变化：某段记录时刻里改过的行 | 读（`changes`；读时计算的派生表翻后面的页时，判断基础表变没变） | 版本表上 `rec_from` 或 `rec_to` 落在区间里，不带 `row_id` | 能：`rec_from`、`rec_to` 各一个索引 |
| 数据目录的表概况 | 只在读 `catalog` 时 | `count(*)`、时间字段的 `min` / `max` | 现在三样放在一条语句里，走不了索引。`min` / `max` 拆成各自一条语句后能（各走时间索引的一端）；`count(*)` 不能，但它不在写入路径上 |
| 受限 SQL 里用户写的过滤 | 读 | 任意字段 | 不自动建（第 3 节「不建的」） |

**派生刷新是 C 组写入变慢最可能的原因，但它不在这份决定里。** 规格 06「刷新范围与写入准入」写的是按受影响的分组重算，对按业务时间分桶的规则，就是重算改动前后的行所落的那些桶。现在的实现每次写入都把规则对全部输入行算一遍，C 组的两张派生表在每次写入时各扫一遍全表。这和「写 1 行与写 1000 行差不多」「行数翻倍、耗时翻倍」两个现象吻合。修法是让实现回到规格已有的规则，单独一份改动来做（第 7 节）。它需要按时间字段找出一个桶的输入行，要用到这份决定建的时间字段索引。

## 3. 建哪些索引

规则只有一条：**内核按 schema 里已有的语义建索引，用户不声明。** 一个字段是时间字段、疑似重复的键、`ref` 字段，内核写入或读取时就会按它找行；这些查找要用的索引，内核按编译后的定义自己建。用户声明不了，也不需要声明。

### 业务表

| 表 | 索引 | 列 | 条件 | 服务于 |
|---|---|---|---|---|
| 事件类 | 时间 | `(f_<时间字段> DESC NULLS LAST, row_id)` | `WHERE NOT revoked` | 按时间范围取行；默认排序下的分页（04-contract「默认排序」：按发生时间倒序，同一时间按行 ID 升序，空值在最后）；分桶派生刷新时取一个桶的行；表概况的首末时间 |
| 事件类、无时间 | 疑似重复，每组键一个 | 这组键的字段列，按声明的顺序；`zoned_datetime` 字段取时刻列与时区列两列 | `WHERE NOT revoked` | 新增一行时找命中的行 |
| 事件类、无时间 | 引用，每个 `ref` 字段一个 | `(f_<ref 字段>)` | `WHERE NOT revoked` | 撤销时找引用方 |
| 状态类 | 引用，每个 `ref` 字段一个 | `(f_<ref 字段>)` | 无 | 同上 |
| 无时间 | 最近改动 | `(last_ver DESC, row_id)` | `WHERE NOT revoked` | 默认排序下的分页（按最近改动倒序，同一次改动按行 ID 升序）。`last_ver` 是这一版新加的列，见下文 |
| 状态类 | 区间终点 | `(valid_to)` | 无 | 某一时刻在生效的段：`valid_to IS NULL OR valid_to > t`，按时刻读的时候，`t` 越接近现在命中越少。`valid_from` 已经在主键里，但排在 `entity_id` 后面，用不上；先不另建，按第 6 节的测量再定 |

**几点说明：**

- **无时间表加一列 `last_ver`。** 无时间表的默认排序是「按最近改动倒序」，而最近改动原本不是业务表上的列，读取时才从版本表算（版本表里这一行除 schema 切换以外最大的 `rec_from`，也就是这一行的 `ver`）。分页下推到这类表时没有索引可用，所以把它记成一列：
  - **取值**：这一行版本表里 `intent` 不是 `schema_switch` 的格子的最大 `rec_from`，与读取时算 `ver` 的口径相同（包括已关闭的格子）。
  - **维护**：`apply` 每改一次一行的格子并写回这一行的业务表行之后，按上面的定义对这一行重算一次 `last_ver`，写进写回的那一行。不写成「打开格子时写」：同一次操作覆盖自己刚开的格子时，那个格子是直接删掉的，按「打开时写」维护会留下已不存在的值，按增量取最大值又会在格子被删后退回不了。写入、删除与撤回删除换格子都走这一条；schema 切换按定义不算。
  - **列的位置与可空性**：放在业务表所有列的最后，可空。升级时 `ADD COLUMN` 加的列在最后、可空；新建表照同样的次序与可空性建，两边逐列一致（对拍按列的次序与是否可空比）。可空只是为了和升级加出来的列形状相同：`apply` 写的每一行都有值，对拍比它的值。
  - 属于物化状态，能从日志重放得出，对拍时与其他列一起比较。
  - 受限 SQL 不暴露它，和内部日期列一样。
  
  选了它、没选「不加列，分页时关联版本表的聚合」，是因为后者仍然扫全表，要快就得再抬一次格式。它在第 2 页起同样成立，见下文「第 2 页起怎么下推」。

- **带条件的索引只覆盖未撤销的行。** 事件类表和无时间表上，内核的查找都带 `NOT revoked`；已撤销的行不该被找到，也不必进索引。带 `include_revoked` 的查询用不上这些索引，照现在的做法读。
- **时间字段是 `zoned_datetime` 时，索引建在时刻列上。** 这个字段类型的比较与排序都按时刻（04-contract：排序类运算符只能按时刻比）。等内部日期列实现了，按日比较改走那一列，到时再加它的索引。
- **区间终点的索引在早期时刻上会被计划器放弃。** `t` 越早，`valid_to > t` 命中越多，命中过半时顺序扫描本来就是对的计划。
- **索引名由索引的定义得出。** 名字是 `<物理表名>__i_<h>`，`<h>` 是这条索引定义的规范形式（列的列表，每列带升降序与空值位置；条件）取 SHA-256 后的前 16 个十六进制字符。版本表上的索引同样命名（物理表名是 `<表>__ver`）。
  - 名字与定义一一对应：同一组列加同一个条件，不论它是因为哪种语义建的，都是同一个索引、同一个名字；两种语义恰好要同一条索引时只建一条。
  - 不按字段在定义里的位置编序号：`duplicate_keys` 这类改动会让位置挪动，序号就会对不上定义。
  - 同一份编译后的定义，在两个后端上、在升级与重放时都得出同一组名字与同一组定义（第 4 节的对齐与核对都靠这一点）。建索引的函数检查同一张表上没有两条不同的定义得出同一个名字，有就报内部错误，不建。
  - 名字最长 48 个字符（物理表名连同版本表的 `__ver` 最长 28 个，加 `__i_` 与 16 个字符），在 PostgreSQL 的 63 字节以内。
  - 格式 5 已有的主键与版本表上的 `(row_id, rec_from)` 索引保留原名，不在这套规则里。

### 版本表

在现有主键与 `(row_id, rec_from)` 之外，加 `(rec_from)` 与 `(rec_to)` 两个索引：「某段记录时刻里改过的行」不带 `row_id`，没有这两个索引就要扫全表。下面第 2 页起的下推也靠它们找出 X 之后动过的行。

### 第 2 页起怎么下推

查询的后续页读的是第一页那次操作之后的状态（04-contract §15）：`read/query.ts` 里后续页的状态是位置 X（第一页记下的 `seq`），现在的做法是对版本表按 X 读出整张表、在内存里排序再取页，版本表上是一次全表扫描。分页下推的那份改动（第 7 节）照下面的办法做；这里写出它，是因为 `last_ver` 列与版本表的两个索引都要靠它才说得上「第 2 页起也用得上」。

记号：X 是第一页的位置，K 是上一页最后一行的排序键，n 是页的大小。

1. **求出 X 之后动过的行，记为 C。** 版本表上 `rec_from > X` 或 `rec_to > X` 的格子所属的行（状态类表按实体）。不分 `intent`，schema 切换写下的格子也算进去，宁多不漏。走 `(rec_from)`、`(rec_to)` 两个索引，代价随 X 之后改过的格子数增长，不随表的行数增长。
2. **不在 C 里的行，现在的业务表行就是它在 X 时刻的样子。** 它的每个格子都是 `rec_from ≤ X`，`rec_to` 为空或 `≤ X`。X 时刻有效的格子，`rec_to` 为空或大于 X；大于 X 的已被排除，所以它们都还开着，就是现在的格子；反过来，现在开着的格子 `rec_from ≤ X`，在 X 时刻也有效。业务表行由当前格子得出（撤销也是一个 `existence` 格子），所以两者相同；它的 `last_ver` 也等于 X 时刻的 `ver`。到期物理删除就地改写的内容，业务表与版本表同样被改写，按 X 读本来也读到改写后的内容，结论不变。
3. **业务表一侧（A）**：`NOT revoked`、用户的条件、行（状态类表是实体）不在 C 里、排序键在 K 之后，按默认排序取前 n + 1 行。事件类表走时间索引，无时间表走 `(last_ver DESC, row_id)`，状态类表走主键。状态类表的默认排序是实体 ID 升序、再按 `valid_from` 升序（04-contract「默认排序」），主键 `(entity_id, valid_from)` 两列都是升序、都不为空，按库的 C 排序规则比较，文本就是按码点，与默认排序的次序相同；查询读的是存着的段，不是合并相邻段之后的结果，所以 A 侧能顺着主键取。按时刻的条件（`valid_from` / `valid_to` 与评估时刻比）在主键扫描里逐行过滤，每个实体历史段越多、为取到 n + 1 行要扫过的段越多，第 6 节的 S 形状量它，不够再按测量定是否另加索引。
4. **版本表一侧（B）**：C 里的行按行 ID 回版本表取它们在 X 时刻的值（就是现在按时刻读的语句，只是限定了行 ID，走 `(row_id, rec_from)`），在内存里过条件、取排序键在 K 之后的。X 时刻还不存在、或那时已撤销的行在这一步自然落掉。
5. **归并**：A、B 按同一个排序键归并，前 n 行是这一页，第 n + 1 行存在就给 `next_position`。A 与 B 不相交，并起来正是 X 时刻的全部行；最终前 n + 1 行里来自 A 的，一定在 A 的前 n + 1 行里，所以 A 只取 n + 1 行就够。
6. **事件类表的时间字段在 X 之后被纠错**：那一行有 `rec_from > X` 的格子，在 C 里，按它在 X 时刻的时间排进次序，业务表上的新时间不参与。无时间表同理：`last_ver > X` 的行一定在 C 里；不拿「`last_ver ≤ X`」当判据，统一以 C 为准，因为 schema 切换的格子不进 `last_ver`、却进 C。
7. **适用条件**：X 到现在这个 slot 的当前版本没有换过（物理表与定义都相同）。换过的，照现在的做法按版本表读。两页之间有大批写入时 C 很大，代价随 C 增长，与那批写入本身同阶，不随表的行数增长。位置很旧、其后改动很多时，C 可能接近整张表，B 侧就接近现在的做法（按版本表读出整张表）；所以它的上界就是现在的做法，加上求 C 的那一次索引扫描，不会比现在差出量级。实现可以在 C 超过一个阈值时直接改走现在的做法，省掉那次扫描与归并。
8. **怎么验**：分页下推那份改动的性质测试，随机生成历史，两页之间随机插入写入、纠错时间字段、撤销、删除与撤回删除、schema 切换；下推得出的每一页与现在的做法（按版本表读出整张表再排序）逐页相同。这条测试同时守住第 2 步依赖的前提：凡改了一行业务表状态的操作，都在这一行的版本表里留下 `rec_from` 或 `rec_to` 等于该操作的格子；`apply` 哪天打破它，测试就红。
9. **不在这里的**：`total` 要数 X 时刻的全部命中行，下推之后怎么算归分页下推那份另议（第 7 节）。带 `include_revoked` 的查询第 3 步用不上带条件的索引，代价与第一页相同。

### 派生表

不加。`partition_id` 已是主键，派生写入与落账都按它找行。派生刷新收窄之后，要按分组键读回存着的那几个分区，到时用的仍是主键（分区登记在 `partitions` 表里，主键带派生表 ID）。

### 内核自己的表

`events`、`base_sources`、`pending_items` 等已按常用的查找建了索引，不在这一步改；第 6 节的分步计时如果查出哪一步卡在它们上，再另加。

**新加一张实体键索引 `entity_keys`**（2026-11-28 补充）。

声明了 `entity_key` 的状态类表，有三处要用到键：按键定位、回执里的 `existing_keys`、回执里的 `similar_keys`。现在这三处都从实体的创建事件里读键：
- 每次都读这张表全部实体的创建事件（`write/keys.ts` `tableKeys`）；
- `existing_keys` 与 `similar_keys` 排「最近写过」时，还要在版本表上整表做 `max(rec_from) GROUP BY row_id`。

代价随实体数线性增长。#76 的形状 S 上，一个请求只读一次键之后（pull request #164），8,000 个实体时这一步仍要约 160 毫秒。索引治不了这两件事：键不在任何业务表的列上，「最近写过」又是不带过滤的分组聚合。所以把它们记成一张物化表，一个实体一行：

| 列 | 含义 |
|---|---|
| `entity_id` | 实体 ID，主键 |
| `table_id` | 表 ID |
| `key_token` | 键的规范形式：各键字段按 `entity_key` 的次序取值，写成 JCS（`write/keys.ts` `keyToken`）。按键定位时就按它比较 |
| `key_values` | 各键字段的值（JCS），供 `existing_keys`、`similar_keys` 显示与比较 |
| `origin_seq` | 给出这个键的那次写入，与 `row_origins.origin_seq` 相同 |
| `last_rec_from` | 这个实体在版本表里全部格子的最大 `rec_from`：不分 `intent`，含已关闭的格子。这是现在 `existing_keys`、`similar_keys` 排「最近写过」的口径，不改 |

索引两条：
- `(table_id, key_token)`：按键定位；
- `(table_id, last_rec_from DESC, entity_id)`：取最近写过的前 N 个。

**几点说明：**

- **只由 `apply` 写，跟着 `row_origins` 走。**
  - 写下或改写行：`row_origins` 给一个声明了 `entity_key` 的表的实体写下或改写创建事件时，按那次写入事件上键字段的块写这一行。删除重放让首次创建移到更晚的写入时（03-deletion「首次创建标记」），也走这一条；
  - 删掉行：`row_origins` 去掉这个实体时，删掉这一行。
- **`last_rec_from` 按定义重算，不按增量。** `apply` 每改一次这个实体的格子，就重算一次，走版本表的 `(row_id, rec_from)`。不按增量取最大值，理由与无时间表的 `last_ver` 相同：同一次操作覆盖自己刚开的格子时，那个格子是直接删掉的。写入、删除、撤回删除、schema 切换的常量补值，改格子都走这一条。
- **可读与否在读的时候判，不由这张表记。**
  - **现在的语义**：从创建事件读键走的是 `READABLE_CONTENT`，所以一项待执行删除列入的键字段块读不到，这个实体在那个字段上就没有值。按键定位用的键字段都必填、不为空，这样的实体任何按键定位都找不到。
  - **按键定位**：先按 `(table_id, key_token)` 取出候选，再对候选 `origin_seq` 上的键字段块按 `READABLE_CONTENT` 核对仍读得到；读不到的不算持有者。
  - **列最近写过的键**：`existing_keys`（10 个）与 `similar_keys`（比较范围 5,000 个）按 `(table_id, last_rec_from DESC, entity_id)` 取前 N 个，各键字段的值同样经 `READABLE_CONTENT` 核对，读不到的按没有值处理。
  - 这样删除确认、撤回、执行都不用改这张表，读出的结果与现在相同。核对是每个候选的主键查找，按事件号批量读（`readableContentOf`），代价与 N 同阶，不随表增长。
- **唯一性不建成约束。** 键在一张表里永远唯一（05-time）；两个实体持有同一个键是存储出错，按键定位照现在的做法报内部错误（`inconsistent`）。建成唯一约束，`apply` 会在落账时撞上约束冲突，那是另一种错误、另一个出口。
- **属于物化状态**，能从日志重放得出；对拍（K12）与其他物化表一起比较。
- **schema 切换与 slot 移除。**
  - 键字段只在从未被写入的表上能改（`change_entity_key`），那时这张表上没有这个表的行；
  - 退役表的行保留，与退役表本身一样；
  - `slot.removed` 删物理表时，一并删这个 slot 各表的行。
- **来源键不受影响**：`external_keys` 本来就是一张索引表。

### 不建的

- **用户在 `where` 与受限 SQL 里写的任意字段。** 每个索引都让每次写入多维护一份，按字段全建，写入代价随字段数增长，空间也翻几倍；而且内核不知道用户会按哪个字段过滤。将来看实际的读取记录再定要不要按用量建，那会是另一份决定。
- **用户声明的索引。** 声明了就要讲清它对重放、导出、升级、切换各意味着什么。内核从语义推得出的，就不该让用户来说。
- **状态类表上把相邻同值段合并后的读法**（受限 SQL 与按时刻读里的 `mergedSegments`）。它先在整张表上开窗、再按时间过滤，除了 `entity_id`，过滤推不到窗口里面，索引帮不上。要快，得把查询改成先选出覆盖那个时刻的段再合并，那是读取线的事（第 7 节）。

**写入的代价。** 一张事件类表，有一个时间字段、一组疑似重复的键、一个 `ref` 字段时，每新增一行多维护三个索引项，版本表上每个格子多维护两个。第 6 节量加索引前后单条写入的耗时；没有派生规则的表，耗时不应再随行数增长。

## 4. 新建表与 schema 切换

- **建表语句和一张表的索引集合由同一个函数从编译后的定义得出。** 索引集合是「名字 → 索引语句」，名字按第 3 节由定义得出。新建 slot、schema 切换、升级给旧表补索引，三处都调它，不会一处有索引、另一处没有。
- **新表与改结构重建的表**（切换时新建物理表的，包括从未被写入、改了结构的表）：建好表之后、复制数据之前建全套索引。先复制、后建索引更快，但现在要复制数据的切换（重建表）还会报 `not_implemented`；这一版的切换只建空表，先建索引没有代价。重建迁移做出来时再看要不要改顺序，要改就在那份决定里写。
- **沿用的表按定义求差对齐。** 物理形状没变、跨版本沿用同一张物理表的基础表，物理表原样保留，但它的索引可能要变：规格 08「物理做法」里只改目录的变更（如改 `duplicate_keys`）不建新表，写过的表上也能生效。切换时对每张沿用的表，用同一个函数分别算出上一版定义与新版定义的索引集合，按名字求差：只在旧集合里的 `DROP INDEX`，只在新集合里的 `CREATE INDEX`，两边都有的不动。这些语句与切换的其余改动在同一个事务里。名字由定义得出，所以「两边都有」就是「定义相同」，不会撞名，也不会漏建。新增的索引建在已有数据上，耗时随表的行数增长，这一项随第 6 节一起量。
- **退役表的索引不动。** 切换时被新版本丢掉的表、被新物理表替换的旧物理表，留作退役表（规格 08：退役表第一版一直保留，按时刻读切换之前的时刻就查它）；它们的索引保持退役时那一版定义得出的集合。
- **已移除的 slot**：`slot.removed` 删物理表，索引随表一起删。
- **索引只由编译后的定义决定，定义在日志里。** 所以从空存储重放日志，得出的索引与在线建的相同。对拍（K12）照现在的做法比表里的数据；另加一项比较：在线存储与重放出的存储，每张物理业务表（含退役表）及其版本表上的索引集合（名字与定义）都相同。

## 5. 存储格式 5 → 6 的原地升级

这是第一次改存储格式。依据 [`data-compatibility.md`](data-compatibility.md) 与规格 02「格式版本、导出、导入与恢复」，升级机制与这一步升级同时交付。打开的规则不变：格式号低于内核的就原地升级，高于内核的拒绝（`format_too_new`），旧版本不打开新数据，不做降级。

### 机制

- **升级步骤是一张有序的表，由内核给出。** 每一步写成「从格式 n 到 n+1」，做三件事：要在存储上执行的语句，要改的 `meta` 值，以及这一步完成后存储的格式号。不写跨级的步骤。
- **打开时的次序。** 两个后端统一成：
  1. 核对编码与排序规则（现状不变）；
  2. 读格式号：高于内核的拒绝，低于 5 的拒绝（`format_too_old`，现状不变），5 到内核之间的记下来；
  3. 核对固定会话设置与 `meta` 里建库时记下的相同。PostgreSQL 现在就这样做；PGlite 现在只对连接应用会话设置、不与 `meta` 比，这一版补上，不同则报 `session_settings_mismatch`。升级的语句要在核对过的会话设置下执行，所以排在这一步之后；
  4. 服务器模式：在租户的锁下重读格式号（不取所有权，见 `server-more-than-one-process.md` 第 1、8 条）；
  5. 从记下的格式号开始依次执行后面的每一步升级；
  6. 照常打开。
- **每一步在一个事务里做完，事务的最后一条语句把 `meta` 的 `storage_format` 改成新格式号。** PostgreSQL 与 PGlite 的建索引、建表、加列都能放进事务。进程在升级中途停了，事务整个回滚，存储仍是旧格式；下一次打开时重做这一步。不会停在两个格式之间。
- **单写者。**
  - **本机模式**：打开时已持有数据目录的锁，别的进程打不开这份存储，没有并发的写者。
  - **服务器模式**：升级在租户的锁下进行，每一步都当作这个存储的一次写事务来做：取这个租户写入用的 advisory 锁，在锁下重新读一次格式号，已是这一步的目标格式就跳过。每个读写事务开头也在锁下（读事务在它的快照里）核对格式号。这样，滚动部署时仍打开着租户的旧进程，下一次读或写核对到格式比自己认得的新，报 `format_too_new`：升级提交之后开始的读写，都不会用旧格式的代码读写新格式的表；两个新进程同时打开同一个租户，每一步只做一次，两个都能接着用。还要防的是旧进程后来：它不加锁读到旧格式号、在锁上等，新进程这一步提交之后它在锁下重读格式号，比自己认识的新就报 `format_too_new`，打开失败。
  - 升级提交之前已经开始的读：加列、加索引不改已有列，旧代码按列名读照常可读。服务器模式下 `ADD COLUMN` 取表的排他锁，并持有到这一步的事务结束（建完索引），期间旧进程对这些表的读也要等；升级耗时就是这段阻塞的长度，第 6 节量它。
- **不用 `CREATE INDEX CONCURRENTLY`。** 它不能放进事务，没法保证「要么旧格式、要么新格式」。代价是升级期间打开租户要等；第 6 节量它要多久。
- **升级失败**：事务回滚，打开报错，存储仍是旧格式。错误码 `upgrade_failed`，`details` 给出失败的那一步（空间检查、备份、某一步格式升级）与数据库的原始报错。不自动改走「按日志重建」：那个办法慢，不该没人知道就开始跑。它留作手动的最后手段（`verify --replay` 与恢复）。
- **磁盘满。** PostgreSQL 写 WAL 时遇到磁盘满是 PANIC，不是普通的错误回滚：
  - **PGlite**：worker 直接退出，调用方拿到的是 `worker_failed`，不是 `upgrade_failed`。下一次打开时 PGlite 按 WAL 恢复，没提交的升级事务不算数，存储仍是格式 5。所以本机模式在升级之前先查空间（见下面「备份」），不够就不开始，报 `upgrade_failed`（`details` 的步骤是空间检查）。
  - **服务器模式**：PANIC 让整个 PostgreSQL 实例重启，同一个实例上的别的租户一起断开。内核拿不到服务器的磁盘余量，不替部署方检查；部署说明写明升级前要留出的空间（按第 6 节量出的升级前后的占用）与这个风险。

### 5 → 6 这一步做什么

在一个事务里，依次：

1. **定出每张物理基础表的定义。** 物理基础表包括当前版本的表与退役表（已移除的 slot 的表已经删了）。每张取 `schema_versions` 里**当过当前版本**、且编译后定义里有这张物理表的版本中，版本号最大的那一版的定义。这正是重放得出的结果：表按建它的那一版建，之后每次切换按新版本对齐（第 4 节），退役之后不再变。确认了但还没切换过去的版本不算，它的物理表还没建。
2. **给无时间表加 `last_ver` 列并补值。** 当前的与退役的无时间表都加，加在最后、可空（第 3 节）；按版本表补值：`last_ver` 取这一行 `intent` 不是 `schema_switch` 的格子的最大 `rec_from`。补完之后它与读取时算出的 `ver` 相同，「怎么验」核对这一点。
3. **补索引。** 对每张物理基础表，按第 1 步定出的定义执行第 3 节的索引语句；它的版本表加 `(rec_from)`、`(rec_to)`。
4. **建 `entity_keys` 并补行**（2026-11-28 补充）。按第 3 节「内核自己的表」建表与两条索引。然后对每张声明了 `entity_key` 的状态类表（当前的与退役的，按第 1 步定出的定义）补行：
   - 实体与创建事件取自 `row_origins`；
   - `key_token`、`key_values` 由创建事件上键字段的块得出。块按存储里存着的读，与 `apply` 写这张表时一样；可读与否在读的时候判；
   - `last_rec_from` 按版本表算。
5. **把 `storage_format` 改成 6。**

**不动的东西：**

- **日志。** 事件头、内容块都不改（K1）。创世事件 `tenant` 块里的 `storage_format` 仍是 5：它记的是租户建立时的格式，不是存储当前的格式；重放时 `apply` 不拿它与当前格式比较。规格 09 在这个字段旁补一句含义。
- **锚点存储。**
- **读取记录。**
- **请求键与其他本地运行状态。**
- **控制面库的格式。** 这一步不改它。
- **导入用的暂存存储与对拍用的临时存储。** 它们不是任何租户的存储，0.1.0 留下的不升级：打开租户时照现在的规则清掉崩溃留下的暂存存储；对拍的临时存储用完即毁，下次对拍重新建。

### 回不去：备份与快照

0.1.0 打开存储时，格式号高于 5 就拒绝（`format_too_new`）。所以 5 → 6 升级之后，再装回 0.1.x 打不开这份数据，哪怕这一步只加了索引。这与「旧版本不打开新数据」一致，不另开口子。按规格 02，不可回滚的升级要单独发布，并在发布前保留快照：

- **本机模式：升级之前默认备份，可以用参数跳过。**
  - **备份什么**：数据目录（租户存储）与 `<home>/control/`（锚点存储与凭证）一起。锚点不在数据目录里：只拿回数据目录、留着升级之后的锚点，日志末端会低于锚点记下的 `seq` 高水位，0.1.0 把它当成日志回退了，拒绝打开（`log_behind_high_water`）。
  - **流程**：格式号要启动 PGlite 才读得到，复制又要在它关着时做，所以是：打开（取数据目录的锁）→ 按上面的次序核到第 3 步，读出格式号 → 低于内核的格式才往下 → 读出这份存储的「状态标记」（见下）→ 关闭 PGlite（锁不放）→ 查空间 → 复制到 `<home>` 旁边的临时名 `<home 目录名>.format-5-backup.partial/`，并在里面写下状态标记文件 `backup.json` → 对复制出的每个文件与目录 fsync → 改名成 `<home 目录名>.format-5-backup/` 并 fsync 它所在的目录 → 重新启动 PGlite、照常走打开的次序并升级。复制到一半崩溃，留下的是 `.partial`，不会被当成完整的备份；下次打开时删掉它重来。
  - **状态标记**：备份要保全的、在两次打开之间可能被改的东西，各取一个只增不减的末端：
    - 日志末端：最后一条事件的 `seq` 与它的事件头哈希。日志只追加，事件头带 `prev_hash` 连成链，末条事件头的哈希相同，前面的日志就相同；在它后面追加过任何事件，末端就不同。
    - 读取记录的末端：`read_log` 的最大 `n`（按记录次序自增）。读不产生事件，只看日志会漏掉旧版本在其间做过的读。
    - `control/` 的内容：其中每个文件按路径排序后，对「路径与内容」取的 SHA-256。凭证、锚点、句柄签名密钥都在这里，旧版本在其间登录或签发连接实例会改它们。
    
    请求键这类「丢了只是失去幂等」的本地运行状态不在承诺之内（data-compatibility 第 2 节），不进标记。
  - **已有完整备份时**：下一次打开、存储仍是格式 5、旁边已有完整的备份，先比状态标记：
    - **相同**：沿用这份备份，不再复制，直接升级。最常见的来路是备份做完之后、升级的事务中途进程停了（或那次磁盘不够）。新内核从开始备份到升级结束一直持着数据目录的锁，期间格式 5 的内核写不进来；之后只要没有装回旧版本用过它，三样末端都不会变。
    - **不同、或备份里没有标记文件**：说明在这之间旧版本用过这份数据（写过、读过或登录过），备份已不是升级前那一刻的样子。不覆盖，报 `upgrade_failed`（`details` 写明备份已在、与当前数据不同、不同的是哪一样），由用户决定移走旧备份还是先回退。
    
    存储已是格式 6 时不需要升级，不看备份。
  - **空间**：至少要有「备份的大小」加「升级本身要的空间」。后者是新索引的大小、补 `last_ver` 时无时间表每行产生的新元组、以及这一步事务写下的 WAL，按第 6 节量出的比例估（先按数据目录大小的一倍算，量完再改）。不够就不升级，报 `upgrade_failed`。
  - **跳过备份**时提示：升级之后旧版本打不开这份数据，且没有备份。
  - **代价**：按实验 9 每行约 5.5 KB 估算，50 万行的数据目录约 2.7 GB；这个代价在发布说明里写明。
  - **回退步骤**（写进发布说明）：停掉服务 → 把 `<home>` 下的数据目录与 `control/` 换成备份里的 → 装回 0.1.x。升级之后写下的一切都会丢，包括升级之后确认的删除：备份里的日志还带着那些内容，回退之后要重新删一遍。发布说明照实写这一点。
- **服务器模式**：照 02 的快照规则，部署方升级前做快照；内核不自己复制数据库。冷租户是第一次被打开时才升级的：部署时做的快照里它仍是格式 5，从那时到它被打开之间它没有写入（有写入就会先打开、先升级），所以那份快照就是它升级前的样子。整体回退到快照，丢的是部署之后所有租户的写入，这一点写进部署说明。
- **嵌入的 SDK**：宿主给的路径，备份照本机模式做，宿主可以关掉。

### 启动等待与报错

- **`saveslot start` 与 MCP 桥现在各等 60 秒**，备份加建索引会超过它：用户看到「启动超时」，升级其实还在跑。改成：服务在升级期间由 `/health` 报「升级中」（当前在做哪一步：备份、第几步格式升级），`saveslot start` 只要看到它在升级中就继续等，并显示在做哪一步；超过 60 秒仍没有升级中的状态，才照现在的规则报等不到就绪。MCP 桥在升级期间对工具调用答 `unavailable`（原因写升级中），不是超时。
- **退出码**（06 §6.2）：`upgrade_failed` 归 5，与「服务起来之后发现存储格式过旧或过新」同一类，要先处理存储（腾空间、移走旧备份），照原样重试没用；升级中归 7（`unavailable`）。CLI 的文案与 `saveslot status` 给出失败的步骤与下一步该做什么。

### 怎么验

- **样本测试。** 夹具里格式 5 的两份样本（本机模式、服务器模式），用格式 6 的版本打开，然后核对：
  - 升级完成，格式号为 6；
  - 样本记下的固定值都读得出；
  - 从空存储重放日志，与表对拍一致（K12）；
  - 索引集合与重放出的存储相同（第 4 节），退役表也比；
  - 锚点与读取记录原样在。
  
  样本里要有一张退役表：一个 slot 切换过一次，丢掉了一张写过的无时间表，并改了另一张表的 `duplicate_keys`（这样「退役表补列补索引」与「沿用的表按定义对齐」两样都被样本覆盖）。这一条替换断言索引 C1 现在的「无测试」。
- **可重入。** 在 5 → 6 的事务里、补完一部分索引之后让它失败，然后核对：存储仍是格式 5，不留任何新索引与新列；再打开一次，升级完成。
- **服务器模式的单写者。** 两方同时打开同一个租户：每一步只做一次，两方都打开成功、都能写。另测滚动部署：旧格式的一方打开着租户、有写入在等锁，新的一方升级之后，旧的一方那次写入报 `format_too_new`，不写进格式 6 的表。
- **会话设置。** PGlite 上 `meta` 记的会话设置与内核的不同时，打开报 `session_settings_mismatch`，不升级。
- **备份。** 空间不够时不升级、存储仍是格式 5；复制中途失败只留下 `.partial`，下一次打开删掉重来；备份完成后在升级事务里让它失败，再打开一次：不重复备份（备份目录原样未动）、升级完成；备份完成、升级失败之后，分别模拟其间追加了一条事件、记了一次读取、改了 `control/` 里的一个文件，再打开：不覆盖、报 `upgrade_failed` 并指出不同的那一样，存储仍是格式 5；跳过备份时有提示；备份的 `<home>` 能用 0.1.0 打开（数据目录与 `control/` 一起换回）。
- **`last_ver`。** 样本里每一行无时间表的行（含退役表），升级补出的 `last_ver` 与读取时算出的 `ver` 相同，与从空存储重放出的也相同。之后再写一笔、同一次操作里改同一个字段两次、删一次、撤回一次删除，`last_ver` 都等于新的 `ver`。新建的无时间表与升级出的无时间表，列的次序与可空性相同。
- **沿用的表对齐。** 改 `duplicate_keys` 的切换之后，旧键的索引没了、新键的索引在，与重放出的相同；切换失败回滚时索引不变。
- **重放兼容。** 一条创世事件写着格式 5 的日志，能重放进一份格式 6 的空存储，`verify --replay` 通过。
- **`entity_keys`**（2026-11-28 补充）。样本里要有一张声明了 `entity_key`、写过的状态类表，其中有整体撤销过的实体；没有的话随样本的扩展补上。
  - **升级之后**：每个实体的键与「最近写过」的次序，与从创建事件整表读出的（现在的做法，留作测试里的参照）相同，与从空存储重放出的也相同。
  - **之后的写入与删除**：按键新建、按键改、整体撤销、删除让首次创建移到更晚的写入、撤回删除，每一步之后按键定位、`existing_keys`、`similar_keys` 都与参照相同。
  - **待执行的删除**：列入某个实体的键字段块时，按键找不到它，`existing_keys` 里它的键按没有值显示，与参照相同。

## 6. 怎么量

**数据形状**：照实验 9 C 组的形状，另加几种，让每种索引都被量到：

| 形状 | 表 | 量的是 |
|---|---|---|
| C | 分钟级事件表，两张分桶派生表 | 与实验 9 对照 |
| C0 | 同 C，不带派生表 | 去掉派生刷新之后，写入还随不随行数增长 |
| D | 事件类表，带一组疑似重复的键 | 新增一行时找命中的行 |
| R | 无时间表被一张事件类表的 `ref` 字段引用 | 撤销时找引用方 |
| S | 状态类表，每个实体若干段 | 按时刻读；状态类表的写入 |

**规模点**：50 万、100 万、200 万行。每个点、每种操作 20 次，取 p50 与 p99。三个点跨四倍：只差一倍的两个点分辨不出小的线性成分（固定 20 毫秒加每 50 万行 2 毫秒，两点之比是 1.09；到 200 万是 1.27）。

**量什么**：

- **写入**：单条新增、单条纠错、一次写 100 行与 1,000 行；另外给写入管线的每一步计时（判定、落账、派生刷新、疑似重复、引用方、回执），看哪一步随行数增长。
- **读取**：取一天的行；按时间范围取第一页与第 2 页（分页下推之前与之后各量一次，分开写）；按时刻读；`changes`。
- **升级**：三个规模点的存储从格式 5 升到 6 的耗时，备份、补 `last_ver`、建索引分开计；升级前后的磁盘占用与升级期间的峰值占用（定第 5 节空间检查的比例）。
- **切换时新增索引**：改 `duplicate_keys` 的切换在三个规模点上的耗时。
- **执行计划**：下表每条语句在 200 万行上用 `EXPLAIN` 看计划，与期望的比。这一项随测量脚本保存，不进单元测试：执行计划随数据量与统计信息变，写成断言会时红时绿。

  | 语句 | 期望的计划 |
  |---|---|
  | 疑似重复：找命中的行 | 那组键的索引上的索引扫描 |
  | 引用方 | 那个 `ref` 字段的索引上的索引扫描 |
  | 按时间范围取第一页（下推后） | 时间索引上的索引扫描，带 `Limit` |
  | 第 2 页起：求 C | 版本表 `(rec_from)`、`(rec_to)` 上的索引扫描或位图扫描 |
  | 第 2 页起：A 侧 | 同第一页 |
  | 第 2 页起：B 侧 | 版本表 `(row_id, rec_from)` 上的索引扫描 |
  | 无时间表取第一页（下推后） | `(last_ver DESC, row_id)` 上的索引扫描，带 `Limit` |
  | `changes` | 版本表 `(rec_from)`、`(rec_to)` 上的索引扫描或位图扫描 |
  | 按键定位（2026-11-28 补充） | `entity_keys` 的 `(table_id, key_token)` 上的索引扫描 |
  | `existing_keys`、`similar_keys` 取最近写过的实体（同上） | `entity_keys` 的 `(table_id, last_rec_from DESC, entity_id)` 上的索引扫描，带 `Limit` |
  | 表概况的首末时间（拆开后） | 时间索引一端的索引扫描 |
  | 命中过半、不分页的宽范围读 | 顺序扫描可以接受，不算不通过 |
  | 状态类表早期时刻的按时刻读 | 顺序扫描可以接受（第 3 节） |

**两边各量一遍**：本机模式（PGlite）与服务器模式（PostgreSQL 18）。分别在加索引之前的 main 与加了之后的分支上量。机器、提交号、PGlite 与 Node 的版本随结果写下。

**通过线**：

- **写入**：不带派生表的形状（C0、D、R）与 S，单条写入的 p50 在 200 万行上不超过 50 万行时的 1.2 倍；同时，写入路径上这份决定治的每条语句的计划与上表相符（疑似重复、引用方、按键定位、最近写过的键）。S 的单条写入分「按键新建一个实体」与「按键改一个已有实体」两种，各自判（2026-11-28 补充；原来这里把 `existingKeys`、`snapshotOf` 留给写入线另改，现在并进来了，见第 7 节）。
- **读取**：上表每条语句的计划与期望相符。
- 没过的照实写，不重跑到通过为止。

结果写进规格 02「容量边界与实测数值」，替换「待测」与 C 组在格式 4 上量的数。

## 7. 和其他改动的边界

| 改动 | 内容 | 这份决定给它什么 |
|---|---|---|
| **派生刷新只重算受影响的分组** | 回到规格 06 已有的规则：按改动前后的行求出受影响的桶，只算这些桶，只读回这些分区；以整表重算的结果作对拍标准。它是语义核心，单独一份请求，派独立审查；动手前先用第 6 节的分步计时确认它就是 C 组写入变慢的主因 | 事件类表的时间索引，用来取出一个桶的输入行 |
| **查询的分页下推** | 排序与分页放进 SQL，只取一页，外加判断有没有下一页所需的行；只为这一页的行取事实；第 2 页起照第 3 节「第 2 页起怎么下推」做；`total` 另算或改成估计（改契约另议）。归写入线 | 事件类表的时间索引，列与顺序和默认排序完全一致：事件类表按发生时间倒序、行 ID 升序、空值在最后，下推后的 `ORDER BY` 要照这个写，否则用不上索引。状态类表的默认排序（实体 ID、`valid_from`）就是主键。无时间表按 `(last_ver DESC, row_id)` 走索引。第 2 页起求 C 用版本表的 `(rec_from)`、`(rec_to)` |
| **自然键的查找改写** | 原来归写入线另改：`existingKeys` 与 `snapshotOf` 在版本表上对全表做 `max(rec_from) GROUP BY row_id`，按键定位每次读整张表的创建事件。2026-11-28 补充之后，「一个请求只读一次」作为独立改动先做（pull request #164，不改存储）；其余并进这份决定 | 实体键索引 `entity_keys`（第 3 节「内核自己的表」）。`write/keys.ts` 改成按它查，与格式 6 一起落 |
| **状态类表合并相邻段的读法** | 先选出覆盖那个时刻或区间的段，再合并，不在整张表上开窗。归读取线 | 区间终点的索引 |
| **旧版本读新数据** | 让旧内核打开更新格式的存储。要把「能读」与「能写」分开（旧内核不维护新格式里由 `apply` 维护的列，回滚后照常写入、再前滚时这些列就是错的；只有数据库自己维护的东西，比如索引，对旧写者才安全），并把事件格式一并考虑（新内核写下旧内核不认的事件版本时，旧内核按 09 §1.6 停止 `apply`）。要做就另写一份决定稿 | 没有。这份决定只做 5 → 6，旧版本照旧拒绝打开 |

## 9. 没有选的做法

| 做法 | 为什么不选 |
|---|---|
| 让用户在 schema 里声明索引 | 内核从语义推得出的就不该让用户来说；声明了的索引对重放、导出、升级、切换各意味着什么都要另讲 |
| 给每个字段都建索引 | 写入代价随字段数增长，空间成倍增加；而用户按哪个字段过滤，内核并不知道 |
| 只加索引、不升格式号（每次打开时「缺了就补」） | 这等于一次不登记的升级：存储里有没有这些索引说不清，对拍与样本测试都没法写断言。而且以后再要改形状，第一次升级的机制还是要做 |
| 升级时按日志重建整个存储 | 慢，量越大越慢。锚点存储与读取记录不在日志里，重建会丢掉读取记录。只加索引用不着它 |
| 用 `CREATE INDEX CONCURRENTLY` 在线建 | 它不能放进事务，没法保证「要么旧格式、要么新格式」 |
| 索引名按种类加字段位置编序号 | 改 `duplicate_keys` 这类只改目录的变更会让位置挪动，序号与定义对不上，切换时要么撞名、要么漏建 |
| 升级排在取所有权之前 | 新进程提交升级之后、取 epoch 之前，旧进程的写入以旧 epoch 通过核对，用旧格式的代码写进新格式的表。服务器模式下这个前提已不在：不取所有权，旧进程靠每个读写事务的格式核对拦下（`server-more-than-one-process.md` 第 1、8 条） |
| 不加表，按键在 `content` 上找创建事件（2026-11-28 补充，以下三行同） | `content` 没有按值的索引，仍要读这张表全部实体的创建事件；在块的正文上建表达式索引，等于把用户内容另存一份进索引，而且横跨所有表 |
| 把键写成状态类表业务表上的列，在业务表上建索引 | 业务表按段存，一个实体多行，键要在每段重复；按时刻读与受限 SQL 都得再藏一列；「最近写过」也没有一实体一行的地方放 |
| 「最近写过」用版本表 `(rec_from)` 倒序扫，取前 N 个不同的实体 | 一个实体格子多时，要扫过许多格子才凑够 N 个不同的实体；`similar_keys` 的 N 是 5,000，代价不可控 |
| 待执行删除列入键字段块时改 `entity_keys`，读的时候不再核对 | 要在删除确认、撤回、执行三处各维护一遍，还得与 `READABLE_CONTENT` 的隐藏规则保持一致；读的时候核对只是每个候选一次主键查找 |
| 从格式 6 起在 `meta` 里记「能打开的最低格式号」，让旧版本打开只增不改的新格式 | 对写入不安全：新格式给 `apply` 维护的表加的列，回滚后的旧内核照常写入却不填它，再前滚时格式号相同、不会重建，这些行就是错的；而且事件格式另有自己的演进。见第 7 节「旧版本读新数据」 |

## 10. 重启条件

- 第 6 节的测量表明，某个索引让写入变慢超过它带来的好处：去掉它，或改成带条件的索引。
- 分页下推、派生刷新收窄之后，C 组的写入或查询仍随行数增长：按分步计时找出下一个卡点，另起决定。
- 升级耗时在实测的规模上不可接受（比如 100 万行要等几分钟以上）：再定要不要分批建索引、建好一部分就先放开读取。
- 分页下推那份的对比测试查出第 3 节「第 2 页起怎么下推」第 2 步的前提不成立（某种操作改了业务表行却没在版本表里留下这次操作的格子），而又不能让 `apply` 补上：回到这份决定，重新考虑 `last_ver` 与第 2 页起的做法。

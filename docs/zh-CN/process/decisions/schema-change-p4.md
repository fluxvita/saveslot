# 决定：schema 变更落地前要定的五件事

> 改已有 slot 的 schema（07-scope-v1 第 4 节的 P4）动工前，`08-open-questions.md` 里有五条待定。这份记录它们怎么定、为什么、不选什么。事件格式 v1 在第一次对外发布之前不冻结（07-scope-v1），所以第 2 条的新枚举值与新的操作成员直接写进 v1，事件的 `v` 不加一；第 1 条的 `extends` / `official` 才是留给以后、按 09 §10 的演进规则加的。存储格式的变动只有第 3 条的一列。

## 1. 官方 schema（`extends` / `compatibility`）：只留位，不实现

**问题。** 上层的领域工具需要认出"这个 slot 符合某份官方定义"，模板只是一次性拷贝，做不到。

**选了什么。** 第一版只在编译后的定义里留位，不实现声明与识别，也不实现升级：

- `compiled` 顶层可选键 `extends`：`{"id": "<官方 schema 的标识>", "version": "<版本>", "hash": "<官方定义的内容哈希>"}`。官方定义的全文**不记**：`compiled` 本来就含这个版本全部表与字段的完整定义，重放不回头取外部文件，所以只需要记"声称符合谁"。
- 表与字段上可选键 `official`：`{"id": "<官方给的稳定句柄>"}`。字段 ID 仍由 saveslot 按表内序号分配；官方字段另带 `official.id`，上层工具按它找字段，不按名字、也不按 `f<n>`。用户自己加的字段没有 `official`，这就是"自己的命名空间"；官方将来新增字段不会与用户字段的 ID 相撞，因为两者不在同一个编号体系里。
- `compatibility` 暂不留键：它描述官方升级时哪些变化可以自动跟进，要与升级流程一起才有意义，将来加可选键即可。
- 将来"已用旧模板建好的 slot 事后声明为符合"是一个新的改动码（`declare_extends`，类别 `metadata`）；改动码是枚举，加值是允许的演进。
- 草稿里出现 `extends` / `compatibility` 整份报 `not_in_this_version`。

**为什么。** P4 的全部机制（改动分类、状态机、按版本建表、切换）只看表与字段，没有一处读"它扩展了谁"，所以留位不挡任何一项；而键的位置现在定下，之后加实现不用改已有事件。

**不选什么。** 现在实现"声明 + 识别"：要先定发布来源、哈希校验、"用户改了官方表算不算仍然符合"，每一项都没有数据支撑，且第一版没有消费者。官方 schema 的其余细问（谁发布、能否扩展多份、能否解除 `extends`、官方文字按谁写的不可信文本算、汇总粒度是否成为通用要求）随实现一起定，仍记在待定清单。

## 2. schema 切换与前提：两边都按新版比，字段被删时标 `schema_switched`

**问题。** 切换改了单位或类型之后，撤前提标记要比较"现在的值"与"所见版本上的值"，用哪一版；旧写入转换后，出处项的身份是否保持、`premise_edges` 要不要跟着转；所声明的字段被删时怎么办。

**选了什么。**

- **都按新版比。** 确定性转换是逐项的：旧写入在字段 f 上的每一项变成新版同一字段上的一项，状态、区间、来源不变，所以出处项的（事件、字段 ID、下标）在切换前后是同一个；所见版本是一个操作号，与 schema 版本无关；新版的版本表就是按日志逐项转换重放出来的，含全部历史。因此撤标记读新版的版本表即可，不需要读跨版本的历史值，`premise_edges` 也不转换。
- `migrate` 不是单射时（两个旧值映到同一个新值，或精度变小），原来不同的两个值在新版里相同，撤标记比原来更容易成立：比的是新版上的值。切换本身不重判任何声明；这发生在切换之后下一次改到前提目标的操作里，照常规的检测比较。这与"同值写入不产生版本"在跨版本历史上的例外（02-architecture 的性质表）是同一类。
- **切换本身不触发前提标记**（确定性转换改的是写法，不是 Agent 用到的事实）。**例外**：新版删除了某条前提声明所声明的字段（含随表删除的字段）时，不把声明扩成"整行"，而是在切换那次操作里出一条 `premise.changed`，原因 `schema_switched`。已经是"已变"的声明不动（`since`、`reason` 保持）；声明了几个字段、只删其中一个的，这条声明照样转"已变"；标记里列的字段只列当前版本里还在的。`premise.changed` 因此多一种所属操作：schema 切换，排在 `schema.switched` 与因切换被取代的 `item.superseded` 之后，至多一条；原因枚举加 `schema_switched`；没有字段被删时不产生。
- **常量 `backfill` 与当前 `ver`。** 补值不改行或实体的 `ver`，所以带当前 `ver` 的写入与补值不冲突：判定取"当前 `ver`"时跳过意图为 `schema_switch` 的项。补值只是缺省常量，覆盖它不丢任何人看过的判断；读过旧值的一方靠 `schema_updated` 提示得知。

**为什么。** 每一条都是已有规则（逐项转换、`ver` 是操作号、补值不改 `ver`）的直接结果，不需要新机制；唯一加的东西是字段被删时那一条事件，因为"读时按字段已不存在现算"会让标记不再是记在事件里的状态（02-integrity「写入的前提」），重放要重新比较。

**不选什么。** 切换时转换 `premise_edges`：它按（事件、字段 ID、下标）登记，这些不变，转换没有对象。字段被删的声明留着、读时现算：违反"标记是状态、记在事件里"。

## 3. 按时刻读跨 schema 版本：查退役表

**问题。** 读到某次切换之前的时刻，是查退役表，还是从日志重放。

**选了什么。** 查退役表。覆盖时刻 S 的版本是切换位置不晚于 S 的最后一版；用那一版的编译后定义取表与字段，用它的物理表答，值与单位按那一版标注。没有改动过物理形状的表跨版本共用同一张物理表，那一版的定义里的 `physical.table` 自然指向它。退役表在切换之后不再被写，里面仍然有效的格就是切换那一刻仍然有效的，所以对切换之前的时刻恰好正确。

- 存储：`schema_versions` 加一列切换位置（`schema.switched` 的 `seq`，没切换前为空）。按"编译事件的位置"找版本不对：有迁移时旧版在编译之后、切换之前仍是当前。这是存储格式的变动，不是事件格式的变动。
- 退役表第一版一直保留；清理（`schema.retired_purged`）与清理之后从日志重放的后备随后续一起做。隐私删除对退役表同样生效（03-deletion）。

**为什么。** 新版版本表按日志重放，含转换后的全部历史，用它答切换之前的时刻在数据上可行，但值已是新版的形状；05-time 的契约是结果标明当时的 schema 版本、值按它解释，用新版表答要么值与版本号对不上，要么违背"数据不被悄悄重新解读"。退役表本来就保留，不用它是白白浪费。

**不选什么。** 用新版表答并标新版（违背上面的契约）；每次按时刻读都从日志重放（内核没有这条读路径，代价大，只在退役表被清理之后才需要）。

## 4. 切换的批、阈值与锁

**问题。** 切换前"剩余量低于阈值"的阈值、切换事务的 `lock_timeout` 与重试次数。

**选了什么。**

- **不设 `lock_timeout`，也不自动重试。** 每个租户的写入串行（02-architecture K3、单写者锁）：迁移的构建批与切换事务排在同一个写者队列里，与用户写入互相排队，没有别的写者可争；读不拿锁，建新版表不挡读；PGlite 没有强制的语句超时。
- **批与阈值是内核常量**（测试可注入，不进 `config.toml`），**初值是占位**，等实验 9 的 schema 重建结果：每批 500 条日志事件、一个短事务，批与批之间排队的写入照常进入；剩余不超过一批时进入切换；连续 20 批剩余量没有减少（写入快过重放）就直接切换，接受那一次更长的暂停。阈值只影响切换那一下写入暂停多久，不影响正确性：切换事务自己追完最后一段再校验再改指针。
- 构建中途进程退出：新版表是可丢弃、可从日志重建的状态，下次打开时补跑发现"迁移中"，丢弃孤儿新版表，从头构建。校验失败（`verify_failed`）与构建失败（`build_failed`）都不自动重试：旧版仍是当前，调用方可以再提交同一份草稿。

**为什么。** 在这个架构里 `lock_timeout` 没有要防的对手；真遇到数据库侧的锁等待，说明有别的写者，那是单写者锁已经失效，应按所有权丢失处理，不是切换的事。校验失败说明转换结果与记录不符，是内核或后端的缺陷，自动重试只会重复。

**不选什么。** 为切换单独设锁超时与重试次数：设了也无处触发，却要写测试与文档。

## 5. 读时计算的派生表：保留物理表

**问题。** 依赖"今天"的派生表读时计算、不读缓存，它的物理表还建不建。

**选了什么。** 建，保持为空，所有读取入口用同一个判断绕开它。`change_rule` 在读时计算与缓存之间切换时与任何规则改动走同一条路：新版照常建一张派生物理表——缓存改读时计算，新表为空；读时计算改缓存，新表与任何规则改动一样随切换按新定义重建（派生表不列入 `rebuilt_tables`，09 §5.5）。

**为什么。** `apply` 不评估规则，也就不需要知道一条规则是不是读时计算；空表的代价可以忽略；`change_rule` 不多一个"跨界"的特例；不影响事件格式。

**不选什么。** 读时计算的表不建物理表：`compiled` 里要让 `physical` 缺省，`apply` 要多一个分支去判断规则的种类，跨界时还要建或删表。

绕开的判据是规则的时间依赖：`rule.time_dependency` 为 `now` 的派生表读时计算。

## 顺带写清的三处

- `destructive` 把删表算进去：删表让这张表的值对外不可见，与删字段同类。
- 枚举取值只调换顺序归入放宽约束：顺序不改变任何取值的含义，同值判据只比较取值本身；它自动生效、旧写入照收、不重建物理表。
- 常量补值与当前 `ver`：见第 2 条最后一项。

# 决定：删除整个租户，与给账户系统用的运维接口

> 不改事件格式，不改操作契约。**K1「事件头永不删改」的适用范围在这里写明：限于租户存续期间**（第 2 条），这是对一条内核不变量的说明，审过才落进规格。控制面库的格式有一次改动。

本文里「账户系统」指部署方放在服务器模式前面的、管人的账户的那个系统：用外部登录的部署才有（02-architecture §12「身份提供者」）。「进程」指一个 `saveslot server start` 的服务进程。

## 要解决什么

两件事，后一件是前一件的入口之一。

**一、没有办法删除一个租户。** 逐条的隐私删除做不到：事件头与元数据块按设计永远留下。用户不再使用服务、要求删掉自己的全部数据时，部署方现在只能停用账户、再手工删掉 database；做不到按时、自动，也给不出「删完了」的凭据。08-open-questions 把它列为对外提供云服务之前必须定义的一项，这里回答它列的十个问题。

**二、账户系统没有办法对服务器说话。** 用外部登录的部署里，服务器只从账户系统接收身份声明；反方向的事都没有通路：

- 账户系统停用了一个账户：它只是不再为这个账户签新的声明，已经授权的连接实例与用户会话照常能用，直到有人在服务器上停用它。
- 账户系统里的账户被注销：服务器不知道，租户与数据原样留着。
- 按租户的限额：定多少由账户系统知道，执行在服务器。

这三件现在都只能由运维在服务器上运行命令（有的命令还没有）。

用内置本地账户的部署没有第二件事：部署方就是管账户的人，在服务器上运行命令即可。本机模式两件都没有：删掉数据目录与配置目录就是全部。

## 已经定下、这里不重开的

- **不设服务身份。** 碰租户数据或凭证的动作（建 slot、签发连接实例）只由用户自己的会话、或用户签发的连接实例来做，日志里的行为者是用户或它的连接实例。运维接口因此读不到、写不了租户的数据，也签发不了连接实例。
- **账户系统已经被信任到什么程度。** 它签的身份声明能换出任何一个账户的用户会话；所以它本来就能以用户的身份做用户能做的一切。下面给它的运维动作，没有一样超出这个范围。

## 决定

### 1. 删除整个租户：只由部署方发起，不是契约里的操作

删除整个租户是部署方一侧的动作：服务器上的运维命令，与运维接口里对应的动作（第 6 条）。操作契约里不加这个操作，连接实例与用户会话都发起不了它。

用户要删除自己的全部数据，在账户系统里注销账户（用外部登录的部署），或找部署方（用本地账户的部署）；由它们确认是本人、再发起。

**不选的做法：** 做成用户会话可调的契约操作。确认「是本人、而且想清楚了」要重新认证与一段交互，那是管账户的一方的事；契约里多一个能毁掉整个租户的操作，对每一个拿得到用户会话的客户端都是多出来的风险。本机模式不需要它；将来确有需要，可以再加，不与这里冲突。

### 2. 删什么，留什么

删除完成之后：

**不再存在的：**

- 租户的 database 整个删掉：日志（事件头链、内容块）、由日志得出的全部表、读取记录。它的暂存 database 与对拍的临时 database 一并删掉；目录行的「待丢弃」里还记着的 database（一次搬迁留下的源，可能在另一个 cell 上；一次不停机的恢复换下的那份）同样删掉，它们是这个租户的日志与数据的完整副本。
- 控制面库里属于它的行：凭证、OAuth 的授权与刷新令牌、授权码与设备码、网页登录态、锚点（高水位、恢复次数、删除登记）、限额记录。
- 账户与用户的对应：外部登录的 `external_users` 里那一行，或本地账户的 `accounts` 里那一行。删除之后，同一个账户再登录，是一个新的用户、一个新的租户。

**留下的：一条最小记录。** 控制面库的新表 `deleted_tenants`：删除编号（发起时生成的不透明随机值，第 3 条）、租户 ID、发起删除的时刻、删除完成的时刻，再无别的；不记账户、不记用户主体 ID、不记所在的 cell。它的用处只有一个：一份早于删除的备份被放回时，认出这个租户已经删除（第 5 条）。租户 ID 是随机生成的不透明值，本身不指向任何人；这条记录一直留着，不设清理（一行几十个字节）。

**K1 的适用范围。** 「事件头永不删改」说的是一个存续着的租户：它的日志只追加，隐私删除只移除内容块、不动事件头。删除整个租户不是对这条日志的修改，是这条日志不再存在；之后没有任何东西自称是这个租户的日志。规格里 K1 的表述补上这一句。

**saveslot 之外的副本不在其中**，如实告知（第 4 条的预览与回执里都写）：用户导出的文件、连接器与外部系统里的副本、账户系统自己的记录、计费与合规要求保留的记录。后两样归账户系统管。

**应用日志**里不含用户内容（02-architecture §10），只有租户 ID 与时刻这样的标识，随日志自己的保留期消失。

租户 ID 与用户主体 ID 不复用：都是随机生成的 26 个字符。

### 3. 流程：预览、宽限期、执行

| 步 | 做什么 |
|---|---|
| 预览 | 不改任何东西。给出：租户有多少个 slot、存储多大、有几个连接实例；宽限期到什么时刻；提示先导出（导出是用户会话的操作，预览不代做）；saveslot 之外的副本不会被删；备份里的副本在备份的保留期满时消失（第 5 条） |
| 发起 | 记下发起的时刻与到期的时刻；从这一刻起租户**冻结** |
| 宽限期 | 冻结着。可以撤回：撤回之后一切如初 |
| 执行 | 到期后由服务器自己做（第 4 条）；发起时指定「立即」则没有宽限期 |
| 完成 | 写下最小记录的完成时刻；之后查询得到回执 |

- **宽限期缺省 7 天**（`SAVESLOT_TENANT_DELETION_GRACE`，0 到 21 天）；发起时可以另给，同样在 0 到 21 天之内。0 即立即执行。逐条隐私删除的宽限期是 24 小时；整个租户的后果大得多，撤回的窗口留得长。
- **从发起起 30 天之内删完。** 这是对用户的承诺能写成的数：宽限期至多 21 天，余下至少 9 天留给执行与它的重试（正常是到期后几分钟之内）。到期后 24 小时还没有完成的（例如 database 一直删不掉），服务日志里记一条错误 `tenant_deletion_overdue`，此后每 24 小时再记一次，查询删除状态时带 `overdue: true`，直到完成；账户系统与运维据此处理，不能让它无声地拖过期限。
- **冻结对外与账户停用是同一个应答，存起来是两样东西。** 冻结期间这个租户的全部凭证（用户会话与连接实例）在认证时被拒，`unauthenticated`（`account_disabled`）；不吊销、不删凭证，不往租户日志里写任何事件。所以契约不变。新的身份声明不签发会话，也不为这个账户另建租户。
  - 删除的状态记在租户目录那一行上（`deleting`、`purging`，带删除编号、发起与到期的时刻）；账户自己的启用与停用仍记在账户那一行（`external_users` 或 `accounts`）。认证时**两者有一个**成立就回 `account_disabled`。
  - **启用解不了冻。** 租户在 `deleting` 或 `purging` 时，启用账户被拒绝（这个状态下做不了）：否则删除的倒计时还在走、甚至删除正在执行，用户却恢复了读写。离开 `deleting` 只有撤回一条路。
  - **撤回只清删除的状态。** 发起之前就已停用的账户，撤回之后仍然停用。「撤回之后一切如初」说的就是这个：回到发起之前的样子，不是回到启用。
- **宽限期内不能导出**：凭证都被拒。要导出，撤回、导出、再发起。预览里的提示就是为了让它发生在发起之前；命令行的发起在确认时再提示一次。
- **发起返回一个删除编号**（`td_` 加随机的 26 个字符）。之后查询这次删除凭它：账户与用户的对应在执行的最后一步删掉，那之后服务器不再知道这个账户曾对应哪个租户，按账户查不到任何东西。对同一个账户再次发起，删除还在进行（`deleting` 或 `purging`）时原样返回同一个编号与到期时刻。
- **还没有租户、或租户没建完的账户。** 账户那一行是先于租户写下的，所以可能有账户而没有租户目录行，或租户停在 `creating`（建到一半停下，或正在建）。
  - 没有租户目录行：没有什么可冻结、可保留的，发起即完成：删掉这个账户的登录态与账户那一行，没有宽限期，不写 `deleted_tenants`（没有过租户，也就没有可被备份带回来的东西），返回「已完成、没有租户」。
  - 租户在 `creating`：发起先取这个租户的占有锁。建租户的各步此后也在这把锁之下做、并在每一步之前核对状态；取不到锁（建租户正在进行）时回暂时不可用，等它做完或停下。取到之后照常置 `deleting`、走宽限期与执行；建租户遇到 `deleting` 或 `purging` 的行不再继续，所以不会在执行删掉 database 之后又把它建出来，也不会把状态改回 `active`。
- **已经冻结的租户里进行中的事**：未到期的隐私删除、进行中的迁移、对拍不再推进（没有凭证，后台任务也不为冻结的租户运行）；执行时随 database 一起消失。有导入、搬迁或恢复在进行的租户不能发起删除，回暂时不可用，等它做完。
- **与逐条隐私删除的关系**：两套各自独立。隐私删除的 24 小时宽限期与撤回只管它那一批内容；整个租户的删除不经过删除登记，不产生墓碑。

**不选的做法：**

- *宽限期内保留只读与导出。* 要为它新增一种凭证状态与一个认证原因，是契约的改动；而「先导出、再发起」用预览里的提示就能做到。
- *发起时就立即删、另留一份可恢复的副本到宽限期满。* 等于自己做了一份带期限的备份，删除的完成时刻反而说不清。

### 4. 执行：可以重入的几步

到期的删除由进程的定时任务发现并执行；几个进程同时发现时，靠以租户为键的占有锁（多进程决定第 3 条的那一把）只让一个做。做到一半停下，下一次发现时接着做；状态记在租户目录那一行上。

| 步 | 做什么 |
|---|---|
| ① 不能回头的一步 | 控制面库的一个事务：租户的状态改为 `purging`；`deleted_tenants` 写入这个租户（删除编号、租户 ID、发起时刻；完成时刻空着）。从这一刻起撤回被拒绝 |
| ② 清凭证 | 删掉控制面库里属于它的凭证、授权、登录态、限额记录。各进程此后认证这个租户的任何凭证都是无效（`invalid`） |
| ③ 删 database | 在它所在的 cell 上删掉租户的 database、暂存 database、对拍的临时 database；目录行的「待丢弃」里有 database 时，在它记着的那个 cell 上（可能不是租户现在的 cell）一并删掉。别的进程手上还开着的连接，在下一次使用时因目录行的状态而关掉，闲置的到期自己关；有一个删不成（还有连接、那个 cell 一时连不上）就留在这一步，下一轮再试，全部删掉才进 ④。已经不在的 database 当作删过 |
| ④ 清目录 | 一个事务：删掉锚点、租户目录那一行、账户与用户的对应；`deleted_tenants` 写下完成时刻 |

- 回执：删除编号、发起的时刻、完成的时刻、租户 ID。完成之后凭删除编号查得到（运维命令也可以凭租户 ID）；账户与租户都已经不在，这是唯一还能问到的东西。
- **数据库一侧的残留**：删掉 database 即删掉它的数据文件；预写日志里涉及它的段随日志的回收消失，备份见下一条。回执不声称「此刻任何介质上都已没有」，说的是：saveslot 的存储里已经没有这个租户，备份里的副本至迟在备份的保留期满时消失。
- **中途停下留下的是什么。** ③ 与 ④ 之间停下：目录行还在（`purging`），database 已经没了；下一轮重入 ③ 时发现都不在，直接做 ④。不会留下没有目录行的 database。
- **没有目录行的 database** 只在一种情形下出现：整个 cell 从备份放回（第 5 条）。由 `saveslot server cell check <名字>` 列出这个 cell 上不被租户目录以任何身份记着的 database。**认它是谁的，不看库名**：不停机的恢复之后，租户的 database 可以叫部署方起的任何名字。命令打开它，从日志里读出当前的租户 ID（最近一条创世或导入事件，与 `server restore --from` 的预检同一个读法），再去对 `deleted_tenants`：对得上的，`--drop-deleted` 删掉；对不上的、打不开或读不出租户 ID 的，只列出来交给运维，不删。

### 5. 备份、归档与恢复

- **备份里的副本不主动清除**，在部署方的备份保留期满时随备份一起消失。托管的 PostgreSQL 的物理备份以整个实例为单位，从中抹掉一个 database 做不到；逐个 database 的逻辑备份由部署方按同一个保留期清理。部署方对用户说明这个保留期有多长；saveslot 不知道它，回执里不替部署方写数字。
- **放回早于删除的备份时，租户不复活**：
  - `saveslot server restore`（两种形式）遇到 `deleted_tenants` 里的租户，拒绝，什么都不改。
  - 整个 cell 从物理备份放回时，被删租户的 database 跟着回来，但租户目录里没有它的行，没有任何凭证指向它，它不会被打开；`cell check --drop-deleted` 把它删掉。运维说明里写明：cell 从备份放回之后运行它。
  - 控制面库连同 cell 一起回到删除之前：最小记录也回去了，saveslot 认不出、也补不了。这与删除登记随控制面库一起回退是同一个已知的边界（02-architecture §8）。账户系统那一侧留着「这个账户已注销」的记录时，对它再发起一次删除即可：发起对一个已不存在的账户是成功、不做任何事，对一个被带回来的账户则重新走一遍。
- **冷租户归档**（将来）里的副本属于 saveslot 的存储，执行删除时一并删掉；归档的规则定下时照此写。

### 6. 运维接口：服务器命令的远程形式

给账户系统调用的一组动作，每一个都与一条 `saveslot server …` 命令做同一件事。它不是操作契约的一部分。

**监听。** 单独的监听地址 `SAVESLOT_OPERATOR_LISTEN`，缺省不设：不设就没有这个接口。它不在对外的监听上，对外地址（`SAVESLOT_PUBLIC_URL`）下没有它的任何路径；部署方把它放在只有账户系统到得了的网络里。只有用外部登录的部署可以设它，用本地账户而设了它是写法不对，拒绝启动。

**调用方怎么证明自己。** 每个请求带一份账户系统签的声明，用的就是身份声明的那一套（同一个签发方、同一份公钥文件、Ed25519）：

- 用途是 `operator`（身份声明现有的两种用途 `authorize`、`session` 之外的第三种；用途不符的声明互相不能代用）；
- `aud` 仍是部署的对外地址（`SAVESLOT_PUBLIC_URL`），不是运维监听的地址：一个部署只有这一个身份，各进程相同；把声明绑到运维动作上的是用途、动作与请求体的哈希；
- 写明这次的动作、它针对的对象（账户系统自己的账户 ID；查询一次删除时是删除编号，那时账户的对应可能已经不在）与请求体的 SHA-256；
- 有效期不超过 60 秒；`jti` 只能用一次，记到它过期为止，重启之后照样拒绝重放。

所以一份声明只能做它写明的那一件事、做一次。不另设口令或长期令牌。

**用账户指人，不用租户 ID。** 账户系统知道的是自己的账户 ID；服务器经 `external_users` 找到用户与租户。服务器不认识的账户：查询、停用、启用、限额回「没有这个账户」；发起删除回成功、什么都不做（它没有什么可删的），不返回删除编号。删除完成之后的账户就是这种：服务器不再认识它，按账户查不出「已删除」，也分不出它与从没登录过的账户；同一个账户再登录则是一个新的用户与租户。**一次删除的进度与回执只凭删除编号查**，所以账户系统要把发起时得到的编号存下。发起的应答丢了：删除还在进行时再发起一次拿得回同一个编号；已经完成时得到「没有这个账户」，这本身说明删完了。

**动作：**

| 动作 | 做什么 | 对应的命令 |
|---|---|---|
| 账户：查询 | 账户的状态（启用、停用）、有没有租户、租户的状态（建到一半、正常、删除的宽限期中、删除执行中）与进行中的删除编号。删完的账户查不到 | `server user list` |
| 账户：停用、启用 | 停用期间这个租户的全部凭证被拒，可逆 | `server user disable` / `enable` |
| 删除：预览、发起、撤回、查询 | 第 3、4 条。预览、发起、撤回按账户；发起返回删除编号，可重复调用，进行中的原样返回同一个编号与到期时刻。**查询按删除编号**，给出状态（宽限期中、执行中、已完成）、各个时刻、是否逾期，完成之后也查得到 | `server tenant delete`（`--preview`、`--cancel`、`--grace`；`--status <删除编号>`） |
| 限额：设置、清除、查询；用量：查询 | 按租户的配额与计量定的那几项，在那里定；这里只留位置 | `server tenant limits`、`server tenant usage` |

- **它做不了的**：读、写任何租户的数据；导出；签发、列出或吊销连接实例；签发用户会话；建租户（租户在账户第一次登录时建）；任何 cell 一级或部署一级的操作。
- **错误**：与对外接口同一种形状的错误体，原因限于：声明不被接受（不说哪一项不对）、没有这个账户、动作在这个状态下做不了（例如撤回一个已在执行的删除）、暂时不可用。
- **完成怎么知道**：账户系统凭删除编号查询。服务器不向外发起任何调用，没有回调。
- **留痕**：每次调用记一条调用记录（服务器模式「每次调用一条记录」的那一种）：动作、针对的租户、结果、时刻，不含请求体里的别的内容。那份决定里一条记录只来自 `/v1` 与 `/mcp`，调用方是会话或连接实例，并且必有租户；运维调用要在它上面加一种调用方（`operator`），租户可以没有（不认识的账户、已经删完的）。停用、启用、发起与撤回删除另在服务日志里各记一行。这些都不进租户日志：它们不是租户里某个主体的行为。

用本地账户的部署：同样的动作只有命令这一种形式，按账户名或租户 ID 指定。

**不选的做法：**

- *一个静态的共享口令。* 泄露之后在换掉之前一直有效，而且不绑定动作；账户系统已经有签名的密钥，再保管一样秘密没有好处。
- *放在对外的监听上、靠认证挡住。* 多一个面向公网、能停用账户和删除租户的入口；接口本身出错时，后果是任何人都够得着。
- *让账户系统换一个高权限的会话、再用契约操作去做。* 那就是服务身份。

### 7. 各部署形态

| | 用外部登录（云服务） | 用本地账户（自部署） | 本机模式 |
|---|---|---|---|
| 谁发起删除 | 账户系统，经运维接口；运维也可以用命令 | 运维，用命令 | 不提供：删掉数据目录与配置目录 |
| 停用、启用 | 账户系统或运维 | 运维 | 没有 |
| 删除之后同一个人再来 | 再登录即一个新的用户与租户 | 运维再建账户 | — |

本机模式是否提供一条代替手动删目录的命令，不在这份决定里；它没有账户、没有备份由别人保管，这里的宽限期、最小记录与回执对它都没有对象。

## 仍然待定

- **法律口径**：法定的删除时限、可以保留的最小信息、对用户的说法，与逐条删除的法律口径一并交法务。它可能改的是这里的数值（宽限期的上限、最小记录留多久），不是机制。
- **共享租户、开发者采购的托管**出现之后，删除一个用户与删除一个租户不再是一回事；到那时另定。

## 怎么验

- 发起之后：这个租户的用户会话、会话的刷新、每个连接实例都被拒，原因是 `account_disabled`；新的身份声明不签发会话、不另建租户。撤回之后同样的令牌照常可用，日志里没有多出任何事件。
- 宽限期到：database 不在了，控制面库里搜不到这个租户的凭证、授权、锚点与账户对应；`deleted_tenants` 有它，两个时刻都在。别的租户全程不受影响。
- 执行在 ① 之后、② 之后、③ 途中、④ 之前各被杀一次：下一轮接着做完；① 之后撤回被拒绝。两个进程同时发现到期，只有一个执行。
- 删 database 时别的进程还连着它：这一轮不成，连接放掉之后的一轮成。
- 删除之后同一个账户再登录：新的用户 ID、新的租户 ID、空的租户。
- 对已删除的租户运行 `server restore`（两种形式）：拒绝。把它的 database 放回 cell：没有东西打开它，`cell check` 列出它，`--drop-deleted` 删掉它；这份 database 的名字不是 `tn_<租户 ID>`（它是一次不停机的恢复换入的）时照样认得出、删得掉。cell 上一个打不开的、或日志里的租户 ID 不在 `deleted_tenants` 里的无主 database：只列出，不删。
- 删除一个「待丢弃」里还有 database 的租户（一次搬迁的源在另一个 cell 上，或一次恢复换下的那份）：完成之后两个 cell 上都没有它的任何 database；其中一个 cell 连不上时停在 ③，目录行还在，连上之后做完。
- 删除编号：完成之后凭它查得到回执；按账户查得到的是「没有这个账户」。同一个账户删完后再登录、得到新的租户，凭旧的删除编号查到的仍是旧租户的回执。删除进行中再发起一次，返回同一个编号。
- 冻结与停用分开：宽限期中启用账户被拒，凭证仍被拒；发起之前已停用的账户，撤回之后仍是停用、凭证仍被拒；发起之前启用的，撤回之后照常可用。
- 没有租户目录行的账户发起删除：账户与它的登录态不在了，没有 `deleted_tenants` 的行，应答是已完成。租户在 `creating`、建租户正在进行：发起回暂时不可用；建到一半停下的：发起成功，之后再用同一个账户登录不会接着建那个租户，执行之后 cell 上没有它的 database。
- 有导入、搬迁或恢复在进行的租户发起删除：暂时不可用。冻结的租户不能导入、不能搬、不能恢复。
- 运维接口：没设监听地址时不存在；对外的监听上没有它的路径；用途是 `session` 的声明做不了运维动作，用途是 `operator` 的声明换不到会话；动作、账户或请求体与声明不符的被拒；同一份声明第二次被拒，重启之后仍被拒；过期的被拒。每个动作的结果与对应的命令相同。
- 运维接口的每个响应里都没有租户的数据；没有任何动作能让调用方拿到连接实例的令牌或用户会话。
- 立即执行（宽限期 0）：发起的那次调用返回时已是 `purging` 或已完成。宽限期给 22 天被拒。
- 到期后 database 一直删不掉（测试里另开一条连接占着它）：24 小时后日志里有 `tenant_deletion_overdue`，查询带 `overdue: true`；连接放掉之后完成，标记消失。
- 本机模式的全部现有测试不变。

## 分步交付

1. **外部登录下的停用与启用命令**。已有的函数接上命令，不依赖这里的任何新东西。
2. **删除整个租户，命令形式**（第 1–5 条）：控制面库的格式改动、定时任务、`server tenant delete`、`server cell check`、恢复的拒绝。依赖多进程决定第 2 步的占有锁与「每次使用先看目录行」。
3. **运维接口**（第 6 条）：监听、声明的第三种用途，以及前两步的动作的远程形式。限额与用量的动作随配额与计量一起加。

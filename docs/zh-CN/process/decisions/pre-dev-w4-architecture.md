## D1 删除登记与内核的关系

**问题。** K11 要求"删除登记在日志之外、确认时就写，恢复后先按登记补删"（`02-architecture.md` 第 59 行），登记放在控制面（第 191 行），控制面属于 `service` 包（第 351 行）。而保证点 3 要求"K1–K13 不依赖任何服务层组件"（第 407 行），用空服务层的内核测试来检查，测试项里就有"恢复删除之前的快照后被删内容检索不到"（第 366 行）。两者直接矛盾。`seq` 高水位与恢复次数同理：K12 依赖它们，`ver` 要编码恢复次数，"恢复"事件要写它们，内核却没有读写它们的接口。

**可选做法。**

| 做法 | 后果 |
|---|---|
| A. 内核经调用上下文里的回调写登记 | 调用上下文要求冻结、可序列化（第 158 行），回调放不进去 |
| B. 把登记放进租户存储 | 登记随租户备份一起被恢复，失去意义 |
| C. 内核定义一个端口，宿主实现 | 多一个接口；K11 的表述与测试都成立 |

**决定：C。** 在 §8 的存储抽象旁边加一个内核定义的端口 `AnchorStore`（锚点存储）。它保存"租户存储被整体换掉之后仍必须记得的事"：

```ts
interface AnchorStore {
  // 以下每个写操作都必须落盘后才返回
  read(tenant): Promise<Anchor>
  putDeletion(tenant, entry: DeletionEntry): Promise<void>      // 新增或整项覆盖
  removeDeletion(tenant, deletionId): Promise<void>
  advanceHighWater(tenant, seq): Promise<void>                   // 只增不减
  beginRestore(tenant, restoreId): Promise<Anchor>               // 置"恢复进行中"并把恢复次数加 1；已在进行中则原样返回
  endRestore(tenant, restoreId, highWater): Promise<void>
}

type Anchor = {
  deletions: DeletionEntry[]
  highWater: number          // 已分配过的最大 seq 的下界
  restoreCount: number
  restoring: { restoreId: string } | null
}

type DeletionEntry = {
  deletionId: string                                   // 即 deletion 事项的 pi_ ID
  kind: "privacy" | "evidence"
  state: "intent" | "pending" | "cancelled" | "executed"
  confirmSeq: number                                   // "删除已确认"事件的 seq
  dueAt: string
  sources: string[]                                    // 被删源数据的不透明 ID
  positions: { seq: number; path: string }[]           // 到期要物理删除的内容块（D7），不含内容
}
```

- **权威定义归内核。** 接口在 `kernel` 包里，语义写在 `03-data-model/03-deletion.md`「删除之后」（登记的字段、状态与对照表）和 `02-architecture.md` §8（端口本身）。
- **硬要求写进端口的说明**：锚点存储必须与租户存储分开存放、分开备份；两者被一起恢复时内核补不了也发现不了，这是已写明的边界，不变。
- **谁实现。** saveslot 服务：`service` 用控制面实现（服务器模式是控制面库里的表，本机模式是文件，见 D10）。内核测试：一个文件实现。SDK 嵌入（后续）：宿主实现，或用内核附带的文件实现并由宿主指定路径。
- **谁调用。** 打开租户时由宿主把 `AnchorStore` 与 `StorageBackend` 一起交给内核；`ops` 持有它，下层模块（`delete`、`maintenance`）只返回"要写进锚点的内容"，由 `ops` 在提交前后调用。下层模块仍然只接收 `Tx`。
- **空服务层下 K11 的测试**：用文件实现的 `AnchorStore`。测试步骤是：确认删除 → 复制租户存储作为"备份" → 到期物理删除 → 用备份覆盖租户存储（锚点文件不动）→ 打开 → 检索被删原文必须为空。

**理由。** 登记的性质和租户存储一样，是内核正确性所依赖的持久状态，只是必须放在另一处；把它建模成第二个存储端口，比把它算作"服务层组件"更符合事实。保证点 3 改成"K1–K13 只依赖 §8 的两个端口，不依赖任何服务层组件"。

**影响。** 事件格式：无。存储格式：锚点的三样内容从"控制面的表"变成端口背后的实现细节。模块：`ops` 多一个依赖；`service` 的"控制面存储"里，删除登记与高水位改为 `AnchorStore` 的实现。

**第一版：做。** 接口形状在 P0 定，文件实现在 P1（`ver` 从 P1 起就要读恢复次数），登记的读写在 P3。

**要改的规格。** `02-architecture.md`：K11、K12 的措辞；§5 控制面存储表的"删除登记"一行；§8 加端口；§11 测试矩阵里的那条用例；§13 保证点 3。`03-data-model/03-deletion.md`「删除之后 · 删除登记」：字段清单加 `confirmSeq` 与 `intent` 状态。

## D2 登记与租户日志的双向一致

**问题。** 规格只写了"先写登记、再提交租户事务；撤回、到期执行同样先更新登记再提交；多出来或落后一步无害"（`02-architecture.md` 第 191 行），只覆盖了一种不一致。架构审查 P1-2 给出两个故障序列，数据模型审查 P1-19 给出第三种情形。

**可选做法。**

| 做法 | 后果 |
|---|---|
| A. 三个动作都先写登记（现状） | 撤回时登记先变成"已撤回"而日志没变，之后恢复旧备份，已删内容复活（序列 A） |
| B. 三个动作都先写日志 | 确认后、写登记前崩溃并丢库，恢复旧备份后这次删除无人记得，内容复活 |
| C. 按"登记不比日志少删"决定先后 | 每个方向的崩溃都落在"多删一步"的一侧，再由对账收回 |

**决定：C。** 规则分四条。

**R1 总规则：登记永远不比已提交的日志"少删"。** 由此定下先后：

| 动作 | 先写 | 后写 | 中间崩溃后的状态 |
|---|---|---|---|
| 确认删除 | 登记（`intent`） | 租户事务（"删除已确认"事件）；提交成功后把登记改成 `pending` | 登记有、日志没有：登记多删一步 |
| 撤回 | 租户事务（"撤回"事件） | 登记改成 `cancelled` | 日志已撤回、登记仍 `pending`：登记多删一步 |
| 到期物理删除 | 租户事务（墓碑） | 登记改成 `executed` | 日志已执行、登记仍 `pending`：两者都是"要删"，无差别 |

`intent` 是新增的状态，意思是"登记写下了，但还不知道租户事务提交没有"。它用来区分两种情形：日志里没有这次删除，是因为事务从没提交，还是因为日志被恢复回退了。

**R2 正常打开时以日志为准，校正登记。** 时机：每次打开租户、每次到期扫描之前、每次删除相关的操作之前。登记项很少，成本可忽略。

| 登记 | 日志里这次删除 | 动作 |
|---|---|---|
| `intent` | 已确认、待执行 | 登记改 `pending` |
| `intent` | 没有 | 移除登记项（事务从未提交） |
| `intent` / `pending` | 已撤回 | 登记改 `cancelled` |
| `intent` / `pending` | 已有墓碑 | 登记改 `executed` |
| 没有登记项 | 已确认、待执行 | 补登记 `pending`（锚点存储丢过或是新建的） |
| 没有登记项 | 已有墓碑 | 补登记 `executed` |
| `pending` | 没有 | **不可能组合**：日志被回退过。转入恢复流程（D3） |
| `cancelled` | 待执行 | 同上 |
| `executed` | 没有墓碑 | 同上 |

最后三行是正常运行中不可能出现的组合（按 R1，登记只会比日志多一步，不会多出一个已经确认提交过的状态）。出现了就说明租户存储被换成了旧的而没走恢复流程，这比高水位兜底多了一道检测。

**R3 恢复流程里以登记为准，补日志。**

| 登记 | 恢复出的日志里 | 动作 |
|---|---|---|
| `executed` | 有"删除已确认"、没有墓碑 | 以 `system` 直接补墓碑（原因码 `restore_backfill`），不重算 |
| `executed` | 连"删除已确认"也没有 | 按定义重算，直接物理删除，不给宽限期 |
| `executed` | 有墓碑 | 无事可做 |
| `pending` | 有"删除已确认"、待执行 | 照原到期时刻执行；已过就立即执行 |
| `pending` | 没有 | 以 `system` 重新生成"删除已确认"（按定义重算），到期时刻沿用原值，已过就立即执行 |
| `pending` | 已撤回 | 登记改 `cancelled`（登记落后一步，日志为准） |
| `intent` | 有"删除已确认" | 登记改 `pending`，照原到期时刻 |
| `intent` | 没有 | 以 `system` 重新生成"删除已确认"，**给一个新的 24 小时宽限期**，事项原因码 `restored_unconfirmed` |
| `cancelled` | 有"删除已确认"、待执行 | 以 `system` 追加"撤回"事件（按定义重算），原因码 `restore_cancel` |
| `cancelled` | 没有 | 忽略 |

与现行对照表（`03-deletion.md` 第 233–239 行）相比，改了三处：新增 `intent` 两行；`pending` + 已撤回一行；"已撤回 → 忽略"拆成两行（数据模型审查 P1-19）。

**R4 多项删除各自列全位置。** 每个登记项的 `positions` 独立于其他待执行的删除，各自列全（数据模型审查 P1-15 的建议）。到期执行时逐块删除，块已不在就跳过；撤回一项时，只释放不被其他待执行或已执行的删除列出的块。

**逐一核对三个故障。**

*序列 A（撤回失败后复活）。* T0 备份 → T1 确认删除 → T2 撤回，租户事务失败 → T3 到期 → T4 恢复 T0 的备份。

| 步骤 | 登记 | 日志 | 说明 |
|---|---|---|---|
| T1 | `pending` | 已确认 | |
| T2 | `pending` | 已确认 | 撤回先写日志；事务失败，登记没动，用户收到报错 |
| T3 | `executed` | 墓碑 | 调度器扫到 `pending` 且到期，打开租户，对账无异，执行物理删除 |
| T4 | `executed` | 没有这次删除 | 恢复流程按 R3 第 2 行重算并物理删除。**不复活** |

*序列 B（从未生效的删除被执行）。* 确认删除，登记写入，租户事务失败，调用方收到报错。

| 之后发生 | 登记 | 结果 |
|---|---|---|
| 下一次打开或下一次删除相关操作 | `intent`，日志里没有 | 按 R2 第 2 行移除登记项。**这次删除不存在** |
| 在任何一次对账之前就丢库并恢复了旧备份 | `intent`，日志里没有 | 按 R3 第 8 行重新生成，但有新的 24 小时宽限期，事项列在待处理事项里并注明原因，可撤回 |

第二行是残余风险：`intent` 状态下 saveslot 分不清"事务没提交"和"提交了但日志被回退"。按前者处理会让一次用户已收到成功回执的删除复活，按后者处理会让一次用户收到报错的删除生效。选后者，并用新的宽限期和可见的事项兜住。它要求"崩溃发生在登记写入与对账之间，而且紧接着恢复了旧备份"，窗口很窄。

*数据模型审查 P1-19（登记已撤回，恢复出的日志里删除仍待执行）。* 按 R3 第 9 行追加"撤回"事件。用户撤回过的内容保留。

**残余风险（写明）。** 撤回的租户事务已提交、登记还没改成 `cancelled` 时崩溃，并且随后恢复到了撤回之前的备份：登记是 `pending`，日志里删除待执行，按 R3 第 4 行照常执行，用户的撤回丢失。这与"备份之后的任何写入都随恢复丢失"是同一类损失，方向是多删。

**理由。** 两个方向的错不对称：少删是隐私事故且不可见，多删在宽限期内可见、可撤回。所以让每一处崩溃都落在多删一侧，再用对账收回。对账表穷尽了 4 种登记状态 × 4 种日志状态的全部组合，没有"未定义"的格子。

**影响。** 事件格式：`system` 重新生成的"删除已确认"与补的"撤回"事件带原因码（`restored_unconfirmed`、`restore_cancel`）；墓碑的原因码加 `restore_backfill`。存储格式：登记项多 `intent` 状态与 `confirmSeq`。模块：`ops` 在删除相关操作里按 R1 的先后调用 `AnchorStore`；对账是 `ops` 的一个内部操作。

**第一版：做（P3）。**

**要改的规格。** `02-architecture.md` 第 191 行（控制面存储表）；第 238 行（云服务调度器：扫 `intent` 与 `pending`）。`03-data-model/03-deletion.md` 第 228–241 行（登记的写入顺序、对照表整体替换为 R2、R3 两张表、R4）；第 154–155 行（位置列表各自列全）。`04-contract.md`：事项原因码与墓碑原因码的枚举（交 W3）。

## D3 恢复流程

**问题。** 现行流程是"追加恢复事件 → 按登记补删 → 补跑已到期的删除 → 对外服务"（`02-architecture.md` 第 279–281 行）。架构审查 P1-3 指出两点：补删做到一半崩溃后，再次启动时高水位兜底看到日志末端已越过高水位，会直接对外服务；高水位"只在写控制面时更新"，没做过隐私删除的租户高水位停在初值，兜底发现不了任何回退。P1-12 指出恢复流程排在 P5，而 P3 的验收测试和先发布的本机模式都需要它。

**决定。**

**步骤**（每一步都可重做）：

| 步 | 动作 | 崩溃后重入 |
|---|---|---|
| 1 | `AnchorStore.beginRestore`：置"恢复进行中"（带一个新生成的 `restoreId`）并把恢复次数加 1，一次落盘 | 已在进行中则原样返回，不再加 1 |
| 2 | 打开租户存储（所有权 epoch 加 1），不对外服务 | 重新打开 |
| 3 | 日志里没有带这个 `restoreId` 的"恢复"事件时，追加一条（`system`）：恢复到的位置、高水位、恢复次数、新的 `node_id`（D8）、`restoreId`。之后的 `seq` 从 max(日志末端, 高水位) 之后接着编 | 已有就跳过 |
| 4 | 按 D2 的 R3 对账。每一格的动作各自一个事务，做完的再做一遍结果不变 | 从头再对一遍 |
| 5 | 补跑已到期的物理删除，清理残留（D11） | 幂等 |
| 6 | 核对登记里 `executed` 项的位置都已清除；`AnchorStore.endRestore`：清"恢复进行中"，高水位设为日志末端 | 重做第 4–6 步 |
| 7 | 对外服务 | — |

**每次打开租户都先看"恢复进行中"标记。** 标记在，就从第 2 步继续，不管这次启动带没带 `--restored`。这解决了 P1-3 的故障序列：补删做到一半崩溃、被自启机制不带参数拉起时，标记仍在，不会直接对外服务。

**触发恢复流程的三种途径：**

1. 显式：`saveslot start --restored`（本机）、`saveslot server restore <租户>`（服务器）。
2. 高水位兜底：打开时日志末端的 `seq` 低于高水位。
3. 对账发现不可能组合（D2 的 R2 最后三行）。

后两种发现时，本机模式自动走恢复流程，服务器模式拒绝对外服务并提示走运维命令。这条区别沿用现行规格（`02-architecture.md` 第 280–281 行）。

**高水位改为定期推进。** 现状是只在写登记时顺带更新。改为下列任一时刻推进到当前日志末端：写登记时；关闭租户或放弃所有权之前；自上次推进以来已追加 1000 条事件或已过 60 秒（两个数是初值）。推进是一次小的落盘，不在写事务里做，失败不影响写入。

**兜底的实际覆盖面（如实写进规格）。** 回退到上一次高水位推进之前的位置，能发现。回退落在最近一次推进之后（最多 1000 条事件或 60 秒的窗口），且期间没有删除相关的登记变化，发现不了：此时恢复次数不加，丢失的那段时间线上发出的 `ver` 如果恰好对应同一行的同一个 `seq`，会被当成当前版本接受。服务器模式因此要求恢复一律走运维命令，兜底只是补救；本机模式同理建议用 `--restored`。

**阶段。** "恢复事件、对账（R2、R3）、恢复次数、`saveslot start --restored`、恢复进行中标记"从 P5 移到 **P3**。P5 只留服务器模式的运维命令 `saveslot server restore` 与控制面库里的 `AnchorStore` 实现。恢复次数的读取（恒为 0）从 P1 起就在 `ver` 里。

**理由。** 可重入靠两样东西：一个持久的"进行中"标记，和每一步的幂等。标记放在锚点存储而不是租户存储，是因为租户存储正是被换掉的那个。

**影响。** 事件格式："恢复"事件的事件头含 `restoreId`、恢复次数、恢复到的位置、高水位、`node_id`（都是不透明值，放事件头）。存储格式：锚点多一个 `restoring` 字段。模块：恢复流程是 `ops` 的内部操作，由宿主在打开租户时驱动。

**第一版：做（P3）。**

## D4 迁移进行中的删除；确定性转换的结果进不进事件

**问题。** 两件相连的事。

1. `07-schema-evolution.md` 第 27 行说确定性转换"结果记为迁移事件，可重放"，`02-architecture.md` 第 84 行的"迁移结果"事件也列了"确定性转换的结果"；而 `08-schema-migration.md` 第 43 行说构建中的新版表"分批构建不对应新事件……重放时 `apply` 处理到切换事件才建好新版表"（数据模型审查 P0-4）。
2. `07-scope-v1.md` 第 96 行说"迁移进行中的删除：不做抽取就不会出现"，但确定性迁移同样有后台构建、追平的窗口。`02-architecture.md` 第 142 行说删除事件里写"迁移进行中时的新版结果"，`03-deletion.md` 第 156 行说"删除事件只给当前版本的结果"（架构审查 P1-6、数据模型审查 P1-18）。

**可选做法（第 1 件）。**

| 做法 | 后果 |
|---|---|
| 读法一：每行转换后的值写进"迁移结果"事件 | 一条事件装下整张表；转换值是内容，要带值来源、进删除级联；迁移期间追平的新写入的转换结果还要另找地方记 |
| 读法二：事件里只有编译后的定义，重放时重新求值 | 日志不膨胀；要求转换表达式的结果在两个后端、不同时间都相同 |

**决定。**

**确定性转换不记逐行结果（读法二）。** 转换表达式是受限 SQL，和派生规则用同一套白名单，结果确定；它随编译后的定义记在"编译结果"事件里。重放时 `apply` 处理到切换事件，按编译后的定义把旧版的每条写入转换成新版形状，建好新版表。"迁移结果"事件只在抽取作业里存在（翻译结果是模型的输出，不可重放，必须记）；确定性迁移的生命周期事件只有"迁移开始""切换""失败"。

**切换事件记校验信息。** 切换事件的内容里记每张新版表的行数与结果校验和，做法同派生写入：重放时有就核对，不用它来生成；它由用户内容算出，是内容，输入被删除后清除，之后跳过核对。这样重放时转换结果若与当时不同（后端差异、内核缺陷），会被发现，而不是悄悄不一致。

**新版表按日志重建，删除事件只给当前版本的结果。** 构建新版表时，"删除已确认"与"撤回"事件和基础写入一样是日志里的事件：它们的逐字段结果经同一套确定性转换进新版表。由此：

- 切换之前就已确认的删除，从空存储重放时不需要特殊处理：`apply` 到切换事件时，被删内容在日志里已经是"已由 #n 移除"，转换时跳过；删除事件里记下的"删除后的样子"经转换成为新版里那一行的当前值。
- 迁移进行中确认的删除：删除事件照常只算当前版本。构建中的新版表是 (c) 类状态，对受影响的行**整行丢弃，按日志重建**（此时被删内容已读不到）。到期物理删除时，如果构建还没结束，同样清掉构建中的表里这些行的历史内容，规则与其他版本的物理表相同。
- 转换表达式的某个输入字段在某次写入里的贡献被去掉时，转换结果的贡献随之去掉（`03-deletion.md` 第 84 行已有此规则，不变）。

**抽取相关的那一半仍然后续。** "受影响的工作项退回池里重做"只与抽取作业有关，随 P4b。

**理由。** 读法二与 `apply` 对派生表的做法一致（派生值同样不存、按规则重算、用校验和核对），不引入第二种"把计算结果写进日志"的路径；删除级联也不用多管一类内容。新版表"按日志重建"让删除与迁移的交互只有一条规则，不需要删除模块知道迁移的存在。

**影响。** 事件格式："迁移结果"事件对确定性迁移不产生；切换事件的内容加每张新版表的行数与结果校验和；删除生命周期事件里不含新版结果。存储格式：无。模块：`delete` 的职责里去掉"迁移进行中时的新版结果"；`schema` 的构建器订阅删除事件。

**第一版：做（P4）。** 计入 P4 的工作量。

**要改的规格。** `03-data-model/07-schema-evolution.md` 第 27 行。`02-architecture.md` 第 84 行（"迁移结果"的描述）、第 86 行与第 142 行（去掉"迁移进行中时的新版结果"）。`03-data-model/08-schema-migration.md`「物理做法」补"删除与撤回事件同样经转换重放""切换事件记行数与校验和"。`03-data-model/03-deletion.md` 第 156 行（拆成与抽取无关、与抽取有关两句）。`07-scope-v1.md` 第 96 行拆成两行："构建中的新版表按日志重建"做（P4），"工作项退回"后续。

## D5 后台任务的入口

**问题。** `maintenance` 在 L6，负责"后台任务调度、read_log 清理、宽限期到期"（`02-architecture.md` 第 145 行）。但事务由 L7 的 `ops` 打开，下层不能调上层；内核不读时钟，`now` 由入口给（第 151、168 行）。按现有规则，`maintenance` 不能开事务、不能读时钟、也调不到 `ops`。P1 的 read_log 定时落盘就会撞上（架构审查 P1-4）。

**决定：把"调度"与"任务体"分开。**

| 部分 | 在哪 | 做什么 |
|---|---|---|
| 任务体 | `ops`（L7）的**内部操作** | 与契约操作同一套入口形状：接收调用上下文，打开事务，组合下层模块。上下文里 `actor = system`，`now` 由调用者给，另带一个 `trigger`（哪个后台任务） |
| 计划 | `maintenance`（L6），纯函数 | 给定事务与 `now`，返回"现在有哪些任务到期"。不开事务、不读时钟、不执行 |
| 调度器 | 内核之外 | 持有定时器、读时钟，按间隔调用内部操作。saveslot 服务里放在 `daemon`；SDK 嵌入（后续）时由内核附带的一个薄驱动或宿主自己驱动 |

内部操作清单（第一版）：

| 内部操作 | 谁触发 | 产生事件吗 |
|---|---|---|
| `openTenant` | 打开租户时。依次做：查"恢复进行中"（D3）→ 对账（D2 R2）→ 补跑到期任务 | 视情况 |
| `flushReads` | 调度器每 N 秒；写事务开头也调用同一段逻辑 | 否（read_log 是 (c) 类） |
| `expireDeletions` | 调度器；`openTenant` | 是：墓碑，`system`，`trigger = deletion_expiry` |
| `purgeResidue` | `expireDeletions` 提交之后 | 否 |
| `pruneReads` | 调度器 | 否 |
| `migrationStep` | 调度器（迁移中时） | 切换时是 |
| `advanceHighWater` | 调度器；关闭租户前 | 否 |
| `closeTenant` | 关闭、放弃所有权前：`flushReads` + `advanceHighWater` | 否 |

对拍（`log.reconcile`）不是后台任务：它是契约里的管理类操作，由用户会话触发，入口就是 `ops`，`actor` 是用户。它内部分批重放到临时存储，每一批的事务仍由 `ops` 打开。

`system` 事件"注明由哪个后台任务或规则触发"（K2）落在事件头的 `trigger` 字段，取值是固定的枚举，不含用户内容。

**理由。** "事务由 `ops` 打开""内核不读时钟"这两条规则是对的，不该为后台任务开例外；后台任务与契约操作的唯一区别是调用者不同。把读时钟的那一小段代码放到内核之外，重放与测试时就能完全控制时间。

**影响。** 事件格式：`system` 事件的事件头有 `trigger`。模块：`maintenance` 的职责缩小为计划；`ops` 分"契约操作"与"内部操作"两组；`daemon` 多一个调度器。§7"嵌入时后台任务由内核自带的调度器跑"改成"由内核附带的驱动或宿主调用内部操作"。

**第一版：做。** 结构在 P1 定（`flushReads`、`openTenant`）。

**要改的规格。** `02-architecture.md` §4 模块表的 `maintenance`、`ops` 两行与依赖规则；§7「后台任务」与「嵌入时」；§11 包表里 `daemon` 的说明；§13 保证点 8 的检查方式不变。

## D6 判定逻辑的归属

**问题。** `write` 与 `delete` 同在 L5，同层不能互相调用。`delete` 重放时要重算的机械判定（同值、`next_change` 终点、`ver` 冲突、高影响、行或实体的存在）和派生写入事件的生成，规格都写在 `write` 的职责里（`02-architecture.md` 第 140、142 行）。照现在的表，要么 `delete` 另写一遍，要么 P3 时拆 `write`。`schema` 的迁移构建是第三个使用方（架构审查 P1-5）。

**决定：新增两个模块。**

| 层 | 模块 | 职责 | 依赖 |
|---|---|---|---|
| L3 | `judge` 判定 | **纯函数，不读存储、不产生事件。** 输入是一行或一个实体的写入序列（含各自的原始传参与值来源是否仍在），输出是每次写入的判定结果与最终状态。包含：同值判断、冲突交集（按字段，状态类表按字段 + 区间）、`next_change` 终点解析、状态段拆分、高影响判定、行或实体的存在、生效值规则。导出一个整数 `RULESET_VERSION` | `time`（区间运算） |
| L4 | `derive` 派生生成 | 给定一批基础改动，调 `rules` 算出受影响的派生分区，生成派生写入事件，交给 `apply` | `rules`、`log`、`apply` |

- `write`：从存储取出目标行的现状与相关写入，调 `judge` 得出这一次写入的判定，生成事件，调 `derive`。
- `delete`：取出受影响行的全部写入，标出哪些贡献不在了，调 `judge` 重放，生成删除事件，调 `derive`。
- `schema`：构建新版表后调 `derive` 维护新版的派生表。

`time`（L2）里原有的"状态段拆分"并入 `judge` 使用的区间运算；`time` 只留区间的基本运算与查询改写。

**参考求值器不使用 `judge`。** 原要求是"不与 `delete` 共用代码"（`02-architecture.md` 第 368 行），用意是让它成为独立的对照。`judge` 是 `delete` 结果的主要来源，所以这条要求改写成"参考求值器不依赖 `kernel` 包里的任何判定代码"，放在测试包里。这样"与参考一致"核对的是 `judge` + `delete` 合起来对不对。

**新增一条性质测试：写入路径与参考一致。** 一串写入做完后的线上状态 = 参考求值器在"被删集合为空"时的重放结果。它核对 `write` 一路（`judge` 的增量调用方式）与定义是否一致，补上审查指出的缺口：现有性质只核对 `delete`，不核对 `write`。

**`RULESET_VERSION` 的用处（交 W2 定是否进事件）。** 架构审查 P0-4 与数据融合调研 A1 独立指出：事件里不记判定规则的版本，将来规则变了，`delete` 重放旧写入时会按新规则重判。`judge` 导出规则版本，是把它写进事件的前提。是否写、写在哪种事件里，属于事件格式，本稿只提供这个落点，并建议写。

**把 P3 前的小原型提前。** `07-scope-v1.md` 第 210 行建议 P3 开工前花一周做"按参考语义重放受影响行"的原型。提前到 P1 中段，用它验证 `judge` 的接口同时满足"单次写入的增量判定"与"整行重放"两种调用方式。

**理由。** 判定规则只有一份实现，`write` 与 `delete` 才不会各自演化。把它做成不碰存储的纯函数，既满足分层规则，也最容易做性质测试。

**影响。** 事件格式：无直接影响（规则版本见上）。模块：L3 加 `judge`，L4 加 `derive`；`write`、`delete` 的职责格改短；依赖检查的规则表相应更新。

**第一版：做。** P1 写 `write` 时就按这个结构。

**要改的规格。** `02-architecture.md` §4 模块表（加两行，改 `time`、`apply`、`write`、`delete`、`schema` 的职责与依赖）；§11 测试矩阵（参考求值器的独立性要求、新增一条性质）。`07-scope-v1.md` 第 210 行。

## D7 内容区

**问题。** `03-data-model/02-integrity-and-records.md` 第 14–15 行：内容"按'事件 `seq` + 事件内位置'寻址，每处配一个普通校验和……不切内容单元"，删除时"整处删掉，或删掉其中一部分后重算该处的校验和"。"处"是什么、"事件内位置"的语法、内容怎么编码、用什么算法，都没有写；"每处一个校验和"与"不切内容单元"读不出一个具体模型。而位置会被写进"删除已确认"事件、墓碑、删除登记和导出文件里的占位，是事件格式的一部分（架构审查 P0-3、数据模型审查 P0-5）。

**可选做法。**

| 做法 | 后果 |
|---|---|
| A. 每个事件一份内容文档，位置是文档里的路径；部分删除后改写文档、重算校验和 | 行数少；删除要改写 JSON，校验和的"部分重算"要定义规范形式；损坏只能定位到事件 |
| B. 内容拆成若干块，每块一行，位置 = `(seq, path)`，整块删除 | 行数多；删除就是清掉若干行，没有"部分重算"；损坏能定位到块 |

**决定：B。**

**模型。**

- 一个事件的内容是一组**内容块**。每块是内容表里的一行，主键 `(seq, path)`。
- **"处" = 一个内容块。** 每块一个校验和。
- **块是删除的最小单位，整块删除，没有块内的部分删除。** 现行规格里"删掉其中一部分后重算该处的校验和"这半句删去。规格要求的三种删除粒度（字段、条目、整条）靠块切得够细来满足：整行的写入前后值按字段各一块，字段级来源按字段各一块，事项的条目每条一块，证据原文整段一块。具体每种事件切成哪些块，由事件格式规格（W2）逐一列出。
- **被删的块**：行保留，内容与校验和置空，记下墓碑的 `seq`。这就是"已由 #n 移除"标记。
- **"不切内容单元"改写。** 这句话的原意来自调研阶段的另一种方案（给每个内容单元配盐或密钥、在链上放承诺，见 `research/03-ledger-deletion.md`），意思是不做那一套。改成"不给内容块配盐、密钥或链上承诺"，避免与"分块"字面冲突。

**位置的语法。** `path` 是若干段用 `/` 连接的 ASCII 字符串：

- 段只能是三种：该事件类型的固定词（如 `after`、`before`、`sources`、`params`、`request_key`、`text`、`entries`）、不透明 ID（字段 ID、表 ID）、十进制下标。
- **path 里不出现任何用户内容或由用户内容算出的值。** 字段用 ID 不用名字。这样位置可以放进事件头引用、墓碑和删除登记。
- 例：`after/f_12`（写入后第 12 号字段的值）、`sources/f_12`（该字段的来源）、`entries/3/proposed`（事项第 3 条的提议值）、`text`（一段证据的原文）。
- 每种事件类型的 path 词表是事件格式的一部分，随事件格式版本只增不改。

**编码。**

- 块的内容是一个 JSON 值，用 **RFC 8785（JCS）** 编码成 UTF-8 文本存放。与事件头同一种编码，导出（NDJSON）时原样带出。
- 存成文本列，不用 PostgreSQL 的 `jsonb`：`jsonb` 会改键序和数字的写法，存回来的字节与校验和对不上。
- **十进制数一律写成字符串。** JCS 按 JavaScript 的数字规则序列化，会损失精度；金额、数量这类值在事件里用字符串（契约里本来就是 `"value": "45"`）。`seq`、下标这类小整数可以用数字。
- 事件头同理：`header` 存成 JCS 文本，它是权威；为了查询另外拆出的列（类型、actor、记录时刻、表与行的 ID）只是索引，`verify` 时核对它们与文本一致。

**算法。**

| 用途 | 算法 | 写法 |
|---|---|---|
| 内容块的校验和 | SHA-256，对块内容的 UTF-8 字节求 | 64 位小写十六进制 |
| 事件头哈希（`prev_hash`） | SHA-256，对上一条事件头的 JCS 字节求 | 同上 |
| 创世事件的 `prev_hash` | 约定常量 | 64 个 `0` |

**为什么校验和也用 SHA-256，而不是 CRC。** 校验和只为发现存储损坏，CRC 就够。选 SHA-256 的理由是全系统只用一种算法，Node 自带（`node:crypto`），不引入依赖；写入频率是人说话的速度，计算成本可以忽略。它由内容算出，所以和内容放在一起、随内容一起清空，这一点现行规格已有规定，不变。事件头里仍然不放任何内容的校验和。

**在哪算。** 沿用现行规定：哈希与校验和在 TypeScript 应用层算，两个后端因此一致。

**理由。** B 让"删除"成为一个没有歧义的操作（清掉哪几行），位置的含义固定，校验和不需要"部分重算"的规范形式。行数多的代价可以接受：按时刻读走版本表（D10），内容表只在重放、导出、查来源原文时读。

**影响。** 事件格式：这是事件格式的"内容区"一节，整体交给 W2；每种事件的 path 词表由 W2 列。存储格式：内容表的形状（D10）。模块：`log` 的"内容 + 来源"接口按块读写。

**第一版：做。** P0 定稿，P1 实现。

**要改的规格。** `03-data-model/02-integrity-and-records.md` 第 12–15、34–35 行。`02-architecture.md` K1、第 92 行（"物理删除后的事件"）。`07-scope-v1.md` 第 34、35 行（算法与常量写明）。

## D8 `event_id` 的落点

**问题。** `07-scope-v1.md` 第 16、34 行说事件格式为 `event_id` 留位；`event_id = (origin_node_id, origin_seq)`（`03-data-model/01-objects.md` 第 72 行）。但 K1 与 `02-integrity-and-records.md` 第 12 行的事件头字段清单都没有它，第一版也没有 `node_id`。"留位"有三种读法，产生的事件头字节不同（架构审查 P0-2）。

**可选做法。**

| 做法 | 后果 |
|---|---|
| A. 每个事件头都写 `event_id` | 每条事件多一个字段；单节点时它恒等于（本节点，`seq`），是冗余 |
| B. 第一版不写，将来靠"缺省字段不编码"补 | 旧事件的身份要有约定，否则补不回来 |
| C. 放在内容里 | 内容可删，身份不该可删 |

**决定：B，并把约定写死。**

- **第一版的事件头不含 `event_id`。**
- **创世事件的事件头带 `node_id`**：建租户时生成的一个随机 ID。
- **"恢复"事件的事件头也带一个新生成的 `node_id`。**
- **约定**：一条没有显式来源字段的事件，它的身份是（它之前最近一条创世或恢复事件的 `node_id`，它自己的 `seq`）。
- **将来做多节点时**：别的节点产生、被主节点接受的事件，事件头里加一个显式的来源字段（来源节点、来源序号）。这是新的事件格式版本里的可选字段；缺省字段不编码，旧事件的字节不变，旧事件不需要改写。

**为什么恢复事件要换一个 `node_id`。** 恢复之后 `seq` 从高水位之后接着编，但高水位是定期推进的（D3），两次推进之间分配过的 `seq` 在恢复后可能被再用一次。如果身份只是（创世的 `node_id`，`seq`），丢失的那段时间线上的事件和恢复后的新事件就可能同名。每次恢复换一个 `node_id`，身份就不会重复。墓碑"按 `event_id` 拦截"（`03-deletion.md` 第 219 行）因此是可靠的。

**理由。** 单节点下每条事件都写一个可以推出来的值没有意义，还会进链、永远删不掉。把约定写在创世与恢复事件里，现在的成本是这两种事件各多一个字段，将来不需要动旧事件。

**影响。** 事件格式：创世、恢复两种事件的事件头加 `node_id`；通用事件头字段清单里写明"没有 `event_id`，身份按约定推出"。存储格式：无。

**第一版：做（约定与两个字段）。** 同步本身不做。

**要改的规格。** `02-architecture.md` K1、第 79 行（创世）、第 87 行（恢复）。`03-data-model/02-integrity-and-records.md` 第 12 行。`03-data-model/01-objects.md` 第 72 行。`07-scope-v1.md` 第 34 行。

## D9 第一版把日志装回去的路径

**问题。** 第一版只做导出，导入与迁移后续（`07-scope-v1.md` 第 127 行）；存储格式升级也只实现"更高版本拒绝打开"（第 42 行）。本机模式在 P4 之后先发布。之后只要动到内核自身的表，已有用户的数据目录既不能升级，也不能导出后重放进新格式；实验 1 若在发布后才暴露问题、要换本机后端，同样没有路。另外，"导出的日志能重放出同样的状态"是对外承诺，第一版却没有任何地方验证它（架构审查 P1-13）。

**可选做法。**

| 做法 | 后果 |
|---|---|
| A. 不做，等多节点时和导入一起做 | 第一次发布后，存储格式实际上被冻结 |
| B. 只在测试里验证导出可重放 | 承诺有了检验；用户仍没有升级的兜底 |
| C. B，再加一个只做重放的最小命令 | 多一条命令；不碰导入里真正难的部分 |

**决定：C。**

**测试矩阵加一项（必做）。** "导出 → 向空存储重放 → (b) 类逻辑表与线上逐行一致"，两个后端交叉各跑一遍（PGlite 导出重放进 PostgreSQL，反之亦然）。它同时覆盖带"待删除"占位的导出：重放后日志末端的业务状态与线上一致。

**本机模式加一条命令：`saveslot init --from-export <文件>`。** 它只做一件事：把一份导出文件重放进一个新建的空数据目录。

- 做的：校验事件头链与内容校验和；按顺序交给 `apply`；租户 ID、主体登记都来自文件里的创世事件与主体事件；新建锚点存储，恢复次数取文件里最后一条恢复事件记下的值（没有就是 0），删除登记由第一次打开时的对账（D2 R2 的"没有登记项"两行）补齐；为创世事件登记的用户主体生成一个新的用户会话。
- 不做的（仍属后续的"导入与迁移"）：向已有数据的租户导入；冻结源租户；凭证映射。连接实例的主体登记在日志里，但令牌不在导出里，重放后旧令牌全部失效，用户要重新签发。
- 定位：存储格式升级与更换本机后端的兜底手段，也是用户验证"我的导出确实能用"的办法。文档里不把它叫作导入。

服务器模式第一版不提供对应命令：服务器模式的格式升级由运维在停机窗口里做，可以直接用内核的重放能力写脚本；等真有需要时再做成命令。

**理由。** "从空存储重放日志"的能力内核本来就有（对拍、测试、迁移构建都在用），缺的只是一个读导出文件的入口。导入真正难的部分是与已有数据合并、凭证映射、源租户冻结，这些都不碰。

**影响。** 事件格式：无。存储格式：无。模块：`ops` 多一个内部操作（向空存储重放事件流），`cli` / `daemon` 多一条命令。

**第一版：做。** 测试项随 P2 的双后端对拍与 P3 的导出；命令随 P3。

**要改的规格。** `07-scope-v1.md` 第 42、127 行与第 4 节 P3；`02-architecture.md` §8「导出不依赖物理格式」与 §11 测试矩阵；`06-cli.md` 第 151 行附近（`init` 的参数）与第 246 行（"第一版没有的命令"里对 `import` 的说明）。

## D11 `recorded_at` 的单调性；到期补跑失败时的策略

### 记录时刻

**问题。** `03-data-model/02-integrity-and-records.md` 第 59 行要求"另存单调的 `recorded_at`"，而时刻来自入口的墙上时钟（`now`），时钟会回拨。单调由谁保证没有写。它影响幂等窗口的判断、宽限期的到期时刻、"生效起点早于现在"的判定（架构审查 P1-8）。

**决定。**

- **事件的记录时刻 = max(调用上下文的 `now`，上一条事件的记录时刻)。** 不严格递增，允许相等；先后顺序由 `seq` 决定。
- **这次操作里所有与"现在"有关的判断都用这个取值**：幂等窗口、宽限期到期时刻的计算、状态类表"生效起点是否早于现在"。写进事件的也是它。重放时只用事件里记下的值。
- **到期与否的比较**（宽限期是否已过）用调用上下文的 `now` 与事件里记下的到期时刻比。
- **时钟回拨时的表现**：新事件的记录时刻停在上一条事件的时刻，直到墙上时钟追上来。期间幂等窗口按停住的时刻算（等于略微延长），到期时刻按停住的时刻加 24 小时算（等于略微提前，但到期比较用的是真实的 `now`，不会早于确认后 24 小时的真实时间减去回拨量）。
- **时钟错误地跳到未来又调回来**：之后的事件都停在那个未来时刻，直到真实时间追上。这期间确认的删除，到期时刻比真实时间晚，物理删除推迟，方向是晚删不是早删。`saveslot status` 与 `saveslot doctor` 在"上下文的 `now` 比日志末端的记录时刻早 5 分钟以上"时给出警告；写入回执的提醒里加一个码 `clock_behind_log`。不拒绝写入。

**理由。** 单调必须由内核保证，因为只有内核看得到上一条事件；取 max 是能保证单调的最简单规则。不拒绝写入是因为内核无从知道哪个时钟是对的。

### 到期物理删除的失败策略

**问题。** "打开存储时先补跑已到期的任务"（`02-architecture.md` 第 236 行）没有说补跑失败怎么办。清理残留（`VACUUM`）不能在事务里做，只能在墓碑事务提交之后；两者之间崩溃，之后无从得知清理做没做。PGlite 上的残留清理"按实验 1 / 2 的结论定做法"，而这两个实验的定义里都没有这一项（架构审查 P1-9）。

**决定。**

**分两段，各自幂等。**

1. 墓碑事务：追加墓碑事件，清空列出的内容块，清掉各版本物理表、事项条目、索引里的对应内容。一个事务。
2. 残留清理：事务提交之后调存储后端的 `purgeResidue`。做完把 `residue_progress`（(c) 类）推进到这条墓碑的 `seq`。

`residue_progress` 丢了或落后时，对它之后的全部墓碑重做一遍残留清理。

**失败时是否对外服务，按情形分：**

| 情形 | 被删内容经接口读得到吗 | 策略 |
|---|---|---|
| 到期的物理删除失败（磁盘满、锁超时、后端报错） | 读不到：确认时就已逻辑删除 | **照常对外服务**；按退避重试；这项删除在 `saveslot status`、`saveslot doctor`、事项详情里标"逾期未物理删除"；服务器模式同时告警 |
| 要清的内容块校验和不符 | 读不到 | 照删。目的就是移除它，损坏与否无关；在 `verify` 里如实报告 |
| 残留清理失败 | 读不到 | 照常对外服务；`residue_progress` 不推进，下次打开与下次调度时重试 |
| 恢复流程里的补删没做完（D3 第 4–6 步） | **读得到**：恢复出的数据里没有这次删除 | **不对外服务**，直到补删完成 |

区别的依据是一条：对外服务会不会让被删的内容重新可读。不会，就不值得为它中断服务；会，就必须先做完。

**新增实验 7：PGlite 物理删除后的明文残留。** 做法：写入一段可辨认的原文 → 隐私删除并到期 → `purgeResidue` → 在数据目录里按字节检索这段原文。排在 P3 之前。通过标准：检索不到；检索得到则 PGlite 上的 `purgeResidue` 要换做法（例如导出后重建数据目录），并在删除回执里如实说明。

**影响。** 事件格式：无。存储格式：(c) 类加 `residue_progress`。模块：`expireDeletions` 与 `purgeResidue` 是两个内部操作（D5）。

**第一版：做。** 记录时刻规则 P1；删除的失败策略与实验 7 在 P3 之前。

**要改的规格。** `03-data-model/02-integrity-and-records.md` 第 59 行。`02-architecture.md` K7、K13 里涉及"现在"的措辞；§7「物理删除按时执行」加失败策略；第 71 行 (c) 类清单。`07-scope-v1.md` 第 93 行与实验表（加实验 7）。`04-contract.md` 的 `warnings` 枚举加 `clock_behind_log`（交 W3）。

## 仍拿不准、需要架构负责人判断的点

1. **D2 的 `intent` + 日志里没有 + 恢复流程**：选了"重新生成并给新的 24 小时宽限期"。另一种选择是直接丢弃这条登记（当作事务从未提交）。前者可能让一次用户收到报错的删除在恢复后出现为待执行的删除，后者可能让一次用户收到成功回执的删除在恢复后复活。本稿按"少删比多删严重"选了前者。
2. **D7 的切块粒度会让内容表的行数明显多于事件数**（一次改 10 个字段的写入可能有二三十块）。本稿判断在"人说话的速度"下可以接受，没有实测；如果实验 4 显示写入延迟受它影响，退路是把同一事件里的小块合并存储而保持 path 语义不变。
3. **D7 校验和用 SHA-256**：规格原文是"普通校验和"。SHA-256 是密码学哈希，与"不做内容承诺"的立场不冲突（它不进事件头、随内容删除），但字面上容易被读成承诺。规格修订时要把这一点写清。
4. **D9 的 `saveslot init --from-export` 是否算超出"第一版只做导出"**：本稿认为它不是产品意义上的导入，并且是第一次发布后存储格式还能改的前提。如果要严格守"只做导出"，可以只留测试项、把命令标成实验性的运维工具。
5. **D10 版本表存值**：让历史值存两份。另一种做法是版本表只存指向内容块的引用，按时刻读时回内容表取值。本稿选存值是为了按时刻读简单；它和 W2 里"基础写入事件要不要同时记写入前整行"有关，两边应一起看。
6. **D3 高水位的两个初值**（1000 条事件、60 秒）是经验值，没有依据实测。
7. **D6 的 `judge` 放在 L3**：它与 `apply` 同层、互不依赖，符合分层规则。但 W1 如果决定生效值规则要读 slot 策略（数据融合调研 A1 的建议），`judge` 仍应保持纯函数，由调用方把策略作为参数传入；这一点需要 W1 的结论确认。

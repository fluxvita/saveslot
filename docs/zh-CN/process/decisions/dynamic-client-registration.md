# 决定稿：0.1.0 之后支持动态客户端注册，以及它怎么不被滥用

> 2026-11-24 起草。三处取舍已定（不落记录、自部署默认开、默认只勾读）；已审（2026-11-24），按第 8 节落规格，出代码之前先核第 5 节。范围的决定已有：0.1.0 之后支持动态客户端注册（DCR，RFC 7591），排在发布后的第一批；0.1.0 不变。本稿定的是它怎么做才不被滥用。

## 1. 为什么第一版没有做，现在要回答什么

第一版只认客户端 ID 元数据文档（CIMD）：客户端的身份是它自己域名下的一个地址，服务器去取、有界地缓存，授权页上能给用户看一个域名。DCR 相反：**任何人不登录就能调一个接口，让服务器记下一条由他填写的记录**，记录里的名称是自报的，没有域名可以对照。有的宿主只支持 DCR，不做就接不上。

所以要回答三件事：

1. 这个接口被人反复调用时，服务器会不会被写满、被拖慢。
2. 注册出来的客户端拿自报的名称冒充别人时，授权页上的用户看不看得出来。
3. 注册出来的客户端能不能把授权码送到不该去的地方。

## 2. 要定的做法

### 2.1 注册不落任何记录

**注册接口不写数据库。** 服务器把收下的内容（名称、回调地址、签发时刻）规范化后，连同一个 HMAC 编码成客户端 ID 交回去；之后客户端带着这个 ID 来授权，服务器验签、解出内容。注册一万次，服务器里一条记录也不多。

- 客户端 ID 的形状：前缀 `dcr_`，后面是内容与 HMAC 的 base64url。有前缀，就不会与 CIMD 的客户端 ID（一个 HTTPS 地址）或内置客户端混淆。
- 密钥：服务器的一把专用密钥，与句柄密钥同样的存放与权限要求。**轮换有过渡期**：服务器同时认当前的密钥和它之前的一把，新签的都用当前的；之前那一把认到它签出的最后一个客户端 ID 过期为止（即轮换之后 90 天，见下「有效期」），所以轮换一次不让任何还在有效期内的客户端 ID 失效。过渡期内再轮换一次，最早的那一把才不再认，它签出的、还没授权过的客户端 ID 失效，客户端重新注册。密钥泄露时不留过渡期，直接换掉。
- **用户第一次同意授权时才落记录**：授权码签发的同一个事务里，把这个客户端的内容写进控制面的客户端表。此后它不再依赖密钥，换密钥不影响已经授权过的客户端。
- **有效期**：没有授权过的客户端 ID 自签发起 90 天有效，过期报 `invalid_client`，客户端重新注册。授权过的随它的授权存在：最后一项授权被吊销或过期满 30 天后，记录清掉。
- 不提供注册的管理接口（RFC 7592 的读取、修改、删除），不发 `registration_access_token`：没有记录可管，要改就重新注册。

这样第 1 个问题里"写满"的一半不存在了：能让服务器多存一条记录的只有登录了的用户，一次同意一条，与一次授权产生一个连接实例同一个量级。

### 2.2 接口收什么、拒什么

`POST /oauth/register`，请求体是 JSON，至多 4 KiB。带了 `Origin` 而不是本服务对外地址的请求报 403（与服务器模式的其他端点相同）：这个接口是宿主的程序调的，不是网页调的。

| 字段 | 规则 |
|---|---|
| `redirect_uris` | 必给，1 到 5 项，每项至多 255 个字符；规则见 2.3 |
| `client_name` | 可不给；至多 64 个字符、一行，含控制字符或改变文字方向的字符（Unicode 双向控制符）的拒绝，首尾空白去掉；不给时授权页上写"未命名的应用" |
| `token_endpoint_auth_method` | `none` 或不给；别的值拒绝（只有公共客户端） |
| `grant_types` | 只能含 `authorization_code`、`refresh_token`；不给按这两项 |
| `response_types` | 只能是 `["code"]`；不给按它 |
| `scope` | 可不给；给了只能含本服务的 scope |
| `client_uri`、`logo_uri`、`tos_uri`、`policy_uri`、`jwks_uri`、`software_statement` 等 | **忽略，不取回，不显示**。服务器不因为一次注册向任何地址发请求 |

不合规的报 RFC 7591 的 `invalid_redirect_uri` 或 `invalid_client_metadata`。响应里不发客户端密钥。

### 2.3 回调地址

与 CIMD 的规则同一套，多一类：

- `https`：有主机与路径，不带用户信息与片段，主机是域名、不是 IP 字面量。注册时不解析这个域名：去那里的是用户的浏览器，不是服务器。
- 回环：纯 HTTP，主机是回环 IP 字面量或 `localhost`；授权时不比端口（[`05-surfaces.md`](../../spec/05-surfaces.md) 第 15 节）。
- 应用自有的 scheme（如 `cursor://…`）：scheme 合语法，且不是浏览器自己会解释的那些（`http` 到非回环主机、`javascript`、`data`、`file`、`blob`、`about`、`vbscript`、`intent`、`ws`、`wss`、`ftp`）。
- 授权时请求里的回调地址要与注册的某一项逐字相同（回环不比端口）。授权码仍绑着 PKCE：拿到授权码而没有校验值的一方换不出令牌。

### 2.4 授权页：不让自报的名称当身份

动态注册的客户端没有可核对的域名，授权页上**把"它会把访问权交到哪里"当作身份显示，名称只是引号里的自述**：

- 回调是 `https`：显示回调地址的主机名，例如「一个自称"Cursor"的应用，授权后回到 `www.cursor.com`」。
- 回调是回环：显示「这台电脑上的一个应用，自称"…"」。
- 回调是自有 scheme：显示「这台设备上用 `cursor:` 打开的应用，自称"…"」。
- 页面上固定两句：这个应用是自己登记的，saveslot 没有核实它的名称；只有你自己刚刚在那个应用里发起了连接，才同意。
- 不显示图标，名称与去向都不做成链接。
- 名称里与主机名长得像的字符不做猜测与拦截（拦不全，还给人"没被拦就是真的"的错觉）；靠的是上面这句话和显示回调去向。

**默认只勾读，写要用户自己勾**，与 CIMD 客户端（默认勾读与写）不同。理由：CIMD 的客户端 ID 是一个域名下的地址，身份至少落在域名上；动态注册的名称是自报的，能当作身份的只有去向，冒名的成本更低。默认只读，被骗着点了一次"授权"，损失的只是读。代价是正常接入的用户要多勾一项才能让应用写入；没勾的，应用第一次写时得到 `insufficient_scope`，按现有的 step-up 重新授权（contract 第 12 节）。授权页在写这一项旁边说明它是什么。

### 2.5 限流与容量

注册不落记录，要限的只是处理请求的开销，口径与 CIMD 取回文档、登录失败计数相同（进程内计数；IPv6 按 /64，另记 /48；来源由服务层按受信的反向代理算出）：

| 限制 | 数值 | 超过时 |
|---|---|---|
| 同一来源 15 分钟内的注册 | 30 次 | 429，带 `Retry-After` |
| 同一个 IPv6 /48（不分 /64）15 分钟内 | 150 次 | 429 |
| 同时处理中的注册 | 8 个 | 503，`Retry-After: 1` |
| 请求体 | 4 KiB | 413 |
| 客户端表里"授权过的动态注册客户端" | 每个用户 50 个 | 这个用户的下一次首次同意被拒，页面上说先去吊销不用的连接 |

计数表有条目上限，满了先清到期的，仍满就把新来源当作已到上限（与现有两张计数表同一个做法）。

### 2.6 与 CIMD 并存

- 授权服务器元数据同时给出 `client_id_metadata_document_supported: true` 与 `registration_endpoint`。用哪一种由客户端选；两种都支持的客户端按 MCP 的约定先用 CIMD。
- 服务器按客户端 ID 的形状分流：HTTPS 地址走 CIMD，`dcr_` 前缀走动态注册，内置客户端照旧。
- CIMD 的规则一条不改。

### 2.7 部署者可以关掉

服务器配置加一个键（`SAVESLOT_OAUTH_DCR`，取 `on` / `off`，默认 `on`）。关掉时元数据里没有 `registration_endpoint`，接口报 404，`dcr_` 的客户端 ID 一律 `invalid_client`（已经授权过的连接实例照常可用、可吊销，只是不能再发起新的授权）。这是部署者对"要不要让没登记域名的应用来连"的选择，不是功能开关：只在自己团队里用、宿主都支持 CIMD 的部署可以关。

## 3. 三个问题各自怎么被回答

| 问题 | 回答 |
|---|---|
| 写满、拖慢 | 注册不落记录（2.1）；处理开销按来源限流（2.5）；落记录要登录用户同意，按用户封顶 |
| 冒名 | 授权页把回调去向当身份、名称只当自述，并明说没有核实；默认只给读（2.4） |
| 授权码送错地方 | 回调地址逐字比对、限定种类（2.3）；PKCE 照旧 |

## 4. 没有选的做法

| 做法 | 为什么不选 |
|---|---|
| 注册即落一条记录：没授权过的 24 小时清掉，表设上限、满了拒绝新的 | 最直接的做法，客户端 ID 也短。但上限是可以被填满的：没授权过的记录设 200 条的上限，几个来源在限流之内就能占满并一直续着，这期间真正的客户端注册不了；把上限放大只是把同一件事推远。满了改成挤掉旧的，又成了能把别人的注册挤掉的手段。不落记录就没有这个上限。它留作退路：若宿主或反向代理不接受这么长的客户端 ID（第 5 节），改用这一种，并接受它的上限可以被占满 |
| 自部署默认关掉 | 自部署前面常常没有别的防护，关着更稳妥；但只支持动态注册的宿主在默认配置下就接不上，部署者要先知道有这个键。不落记录之后，开着的代价只是按来源限流之内的请求处理。两边都说得通；定的是默认开：接得上优先，部署者可以关 |
| 注册要先登录，或要一个预先发的初始令牌 | 宿主的注册是自动发起的，没有地方让用户先登录；初始令牌要用户手动填，那就不如直接用静态令牌 |
| 取回 `client_uri` / `logo_uri` 来核实身份、显示图标 | 让一个不登录的人指定服务器去连哪里；能取到也证明不了注册的人拥有那个域名 |
| 维护一份"知名客户端"名单，名称对上了才显示 | 名单永远不全，而且名称对上不代表是它 |
| 动态注册的客户端一律多一步确认 | 设计要求用户最多做选择和一次同意（06-cli 第 1 节）；多一步挡不住看都不看就点的人，挡住的是正常接入 |

## 5. 没有核实的外部事实

按公开资料定、不装软件实测，所以下面几条在出代码之前要再对一次公开文档，对不上就回到这份稿子：

- 只支持 DCR 的宿主在客户端 ID 失效（`invalid_client`）时会自动重新注册。**推测**：MCP 的授权约定要求如此，各宿主是否照做没有核实。它决定 2.1 的"换密钥、过期后重新注册"对用户是否无感。
- Cursor 用 DCR 注册时给的回调地址是哪几种（`https://www.cursor.com/…`、回环、`cursor://…`）。它公布的客户端文档里三种都有；DCR 时是否相同没有核实。它决定 2.3 的自有 scheme 一类要不要在第一批就做。
- 客户端 ID 的长度：5 项回调地址都写满时，编码后的 ID 约 2 KiB，会出现在授权请求的查询串里。**推测**多数宿主与反向代理接受。**这一条在出代码之前先核**：按主要宿主（Claude Code、Claude 桌面端与网页端、ChatGPT、Codex、Cursor）公开的文档与源码，查它们存放和回传客户端 ID 有没有长度限制，结果写回这一节；有一个主要宿主不接受，就改用第 4 节第一行的做法。

## 6. 对 Cursor 的说法随之改

0.1.0 里：`saveslot connect cursor --profile <服务器>` 照旧给只有地址的条目；能不能走通不实测，按公开资料它需要 DCR，所以文档里写明"0.1.0 的服务器模式下 Cursor 用静态令牌接入（`saveslot connect http`）"。DCR 做完后这句话拿掉。

## 7. 重启条件

- 出现一个只支持 DCR、又要求读回或修改注册（RFC 7592）的主流宿主：再定管理接口。
- 实际出现了冒名的授权（有人报告被自称某应用的链接骗过授权）：重新考虑多一步确认。
- MCP 的授权约定把 DCR 去掉：不再新增对它的依赖，按那时还在用它的宿主定保留多久。

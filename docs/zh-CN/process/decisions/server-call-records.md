# 决定：服务器模式按调用输出一条不含内容的记录

> 不改事件格式，不改 K1–K14。操作契约只加一个应答头。按「分步交付」落进规格与代码。

本文里「部署方」指运行服务器模式的一方（托管服务的运营者，或自部署的用户自己）；「调用」指一次契约操作：`/v1` 上的一个请求，或 `/mcp` 上的一次工具调用。

## 要解决什么

部署方要回答这样的问题：某个租户今天用了多少次、是哪个客户端在用、做的是什么操作、成没成功、有多少次写入真的生效了。现在答不了，原因是服务器模式往外给的东西不够：

- `server start` 在标准输出上按请求写一行：方法、路由名、HTTP 状态码、耗时。行里没有租户，没有调用方。
- `/mcp` 只有一个路由。工具名在请求体里，日志只记一个请求里第一个工具调用的名字；工具调用失败时 HTTP 状态码仍是 200，失败写在工具结果里。
- 入口层（反向代理、负载均衡器）看得到的只有方法、路径与状态码。令牌是不透明的，从它得不出租户。
- 一次写入是新生效的还是重发，只写在应答体里（`replayed`）。要知道就得解析应答体，而应答体里是用户的数据。
- 代码里有一个在工具调用结束时被调用的回调，测试在用。它拿到的是整份参数与整份结果，只有 MCP 上有。它不是对外的接口，也不该是：它把用户的内容交给了回调。

所以只靠计数器分不清「一次写入」与「一次重发」，也分不清是谁的。

要求：

- 归属到租户与调用方，用稳定的标识；
- 分清操作与结果，分清写入生效、写入没有生效、重发；
- 同一条观测被收集两次时能去重；
- 记录这件事出了问题，不影响调用本身；
- 不含凭证，不含存储的内容，不含用户或调用方起的名字；
- 认不出的客户端就是认不出，不猜；
- 自部署默认什么都不多做，程序不向任何地方发送数据。

## 决定

### 1. 每次调用一条记录，由部署方显式开启

服务器模式加一个配置项 `SAVESLOT_CALL_RECORDS`，取值 `on` / `off`，默认 `off`。开启后，每次调用结束时，服务进程在标准输出上写一行 JSON，这一行就是这次调用的记录。部署方用自己的日志收集把它取走；程序自己不把它发到任何地方，也不提供接收它的服务。

哪些出记录：

- `/v1`：通过了认证的请求，一个一条。
- `/mcp`：一次工具调用一条。一个请求里放了几次工具调用，就是几条。
- 通过认证之后被拒的，同样出记录，两个面一致：权限不够（`insufficient_scope`；`/mcp` 上这种拒绝是整个 HTTP 请求回 403，请求体里被拒的每一次工具调用各出一条；同一个请求体里本来会放行的调用因此没有执行，它没被拒、也没发生，不出记录）、被限流（`rate_limited`）。

哪些不出：

- 没通过认证的请求，一律不出，包括账户已停用的那一种（那时其实已经知道租户，仍然不出：记录只为通过了认证的调用而设）。它们仍在现有的按请求的那一行里（状态码 401）。
- `/mcp` 上不是契约操作的请求：`initialize`、列工具；以及调用一个不存在的工具名，那是协议层的错误，不是契约的结果。
- OAuth 的各个端点、`/health`、`/ready`。

现有的按请求的那一行照旧，不加字段、不删字段。两种行靠 `record` 这个字段分开：调用记录有它，按请求的行没有。

本机模式没有这个配置项，不出记录。

### 2. 记录里有什么

| 字段 | 含义 | 来源 |
|---|---|---|
| `record` | 固定为 `"call"` | — |
| `v` | 记录格式的版本，现在是 `1` | — |
| `call` | 这次调用的 ID，`call_` 加随机串，每次调用新生成 | 服务进程 |
| `at` | 调用结束的时刻（UTC） | 服务进程的时钟 |
| `ms` | 从认证通过到结果确定的毫秒数 | 同上 |
| `tenant` | 租户 ID（`tn_…`） | 认证结果 |
| `actor` | 调用方的 ID：用户会话是 `u_…`，连接实例是 `ci_…` | 认证结果 |
| `via` | 这个调用方的凭证是怎么来的：`session`（用户会话）、`token`（签发的连接实例令牌）、`oauth`（一次 OAuth 授权） | 连接实例登记时写下的值；用户会话固定为 `session` |
| `registration` | `via` 是 `oauth` 时，client 是怎么登记的：`document`（client 文档）、`dynamic`（动态登记）、`builtin`（程序自带的，如命令行） | client 标识的形状 |
| `client` | `registration` 是 `document` 时，client 标识的来源部分（协议加主机，如 `https://example.org`）；是 `builtin` 时，那个固定的名字；其余情况没有这个字段 | 连接实例登记时写下的 client 标识，按上面的规则取 |
| `surface` | `http` 或 `mcp` | — |
| `operation` | 契约里的操作名（`write`、`query`、`resolve`……） | 路由表 / 工具表 |
| `route` | `surface` 是 `http` 时的路由名；是 `mcp` 时的工具名 | 同上 |
| `outcome` | `ok`，或契约的错误码（`invalid_argument`、`conflict`、`unavailable`……） | 契约结果 |
| `reason` | 错误带有原因、并且那个原因出自契约的枚举时，那个原因（`read_first`、`busy`……）；否则没有 | 同上 |
| `incident` | `outcome` 是 `internal` 时，应答里的那个事故编号 | 同上 |
| `effect` | 只在会追加事件的操作（`write`、`resolve`、`schema_draft`、`connections.issue` / `update` / `revoke`、`slots.remove`）成功时有：`appended`、`none`、`replayed`，含义见下 | 内核随结果交给服务层的内部信息（不在契约结果里） |
| `status` | `write` 与 `resolve` 触发的写入：`saved` / `pending` | 同上 |
| `seq` | `effect` 是 `appended` 或 `replayed` 时，那次操作在租户日志里的操作号 | 同上 |
| `restores` | 有 `seq` 时，这个租户的恢复次数（与 `ver` 里小数点后的那个数相同） | 同上 |
| `complete` | 只在流式应答的操作（如导出）上有：流正常结束是 `true`，中途断开是 `false` | 服务进程 |

**`effect` 的三个取值按这次调用对租户日志做了什么定：** 契约回执不全带操作号（`resolve`、提交 schema 草稿、连接实例与 slot 的管理操作都没有），所以不从回执里解析，由内核随结果交给服务层，不出现在任何契约结果或对外类型里。每一项都是那次操作自己的：`resolve` 记的是那次解决自己的操作号，不从事项版本里取（事项版本在之后的改动里会被刷新）。恢复次数每个打开的租户存储只读一次、记住，不为每次调用多读存储；这样做是安全的：单写者之下只有恢复与导入会改它，二者在这个存储上追加事件时把记住的忘掉，另一个进程接管租户时打开的是新的存储。

- `appended`：这次调用在这个租户的日志里追加了头事件，带它的操作号。
- `replayed`：是重发，回放了原来那次的结果，带原来的操作号。它不只来自幂等键窗口内的重发：对一个已经按同样方式解决的事项再 `resolve` 一次、再删一次已经删掉的 slot，也是 `replayed`。
- `none`：什么都没追加，不带 `seq`。比如全部 op 都按来源键、并且全部是「没有改动」或「跳过」的写入；改名改成原来的名字、吊销一个已经吊销的连接实例。注意「值没变的写入」不在这里：它照样存下了证据、得到一个操作号，是 `appended`、`status` 为 `saved`。

**「写入有没有生效」怎么答：** `effect` 是 `appended` 或 `replayed`、并且 `status` 是 `saved`。`status` 是 `pending` 的写入追加了事件，但值成了候选或在等确认，没有生效。有一种情形记录分不开：`saved` 的写入里，每个字段都与现值相同的那种（存了证据，值没变）也在 `saved` 里。要分它得在记录里放逐字段的结果，那已经贴近内容，这一版不放。

**去重与计数：**

- 同一条记录被收集了两次，`call` 相同。
- 同一次写入被重发了几次，是几条记录、几个不同的 `call`：一条 `appended`，其余 `replayed`，它们的 `tenant`、`restores`、`seq` 相同。
- 操作号在一次恢复之后会被再次用到（恢复把日志带回早先的位置，之后的操作从那里接着编号），所以去重的键是三样：`tenant`、`restores`、`seq`。
- 「生效的写入数」是 `effect` 为 `appended` **或** `replayed`、`status` 为 `saved` 的记录，按这三样去重之后的条数。把 `replayed` 算进去是有意的：进程在提交之后、写出记录之前退出时，第一条记录丢了，调用方重试得到的 `replayed` 就是那次写入生效过的证据。

**标识的说明：**

- 租户 ID 一个用户一个；一个租户接收了一次导入之后，它自己的 ID 不变。把一个用户用导出加导入搬到另一个租户，得到的是另一个租户 ID，这层对应要部署方自己带着。连接实例 ID 在改名、换发访问令牌之后都不变；一次 OAuth 授权登记一个连接实例，同一个 client 再授权一次是另一个连接实例。部署方要把租户对到自己的账户，用它建租户时得到的租户 ID。
- **client 标识是调用方自己选的字符串，所以不原样放进记录。** client 文档的地址只核对过那里确实有一份文档，路径上写什么没人管；动态登记的 client 标识里编着它登记的内容，包括它给自己起的名字。记录只取两样不可能带文字的东西：怎么登记的（`registration`），以及文档地址的协议加主机（`client`）。主机名回答了「是哪家的客户端」；动态登记的 client 在记录里只有 `registration: dynamic`，认不出是谁。
- 令牌签发的连接实例没有 client：这时是哪个程序在用这个令牌，服务端不知道，记录里也就没有。
- 用户会话一律是 `via: session`，不分是网页、命令行还是本地账户登录的。
- **不读 `User-Agent`，不看连接实例的名字。** 这两样都是调用方自己说的，没人核对。用连接器 SDK 的调用今天没有可靠的标记，记录里认不出；要认出，得在签发连接实例时登记它的种类，那是另一项改动，不在这里定。
- `operation` 与 `route` 都给：几条路由可以是同一个操作（`catalog` 有七条），按操作计数用前者，要看具体是哪个入口用后者。

记录里**没有**的：令牌与任何凭证；请求体与应答体里的任何内容；slot 名、表名、字段名；连接实例的名字、账户名、外部登录的账户标识；任务标识与幂等键，原文没有，由它们算出来的任何东西（哈希、前缀）也没有；错误附带的 `param`、`field` 这类指向用户所起名字的项；查询条件与 SQL；来源地址。slot 与表的 ID 也不放：按 slot 归属不在这次要回答的问题里，放了只会让记录更接近内容。

### 3. 调用 ID 回给调用方

`/v1` 上，凡是出记录的应答（不管 `SAVESLOT_CALL_RECORDS` 开没开，按「开着就会出」算）都带应答头 `Saveslot-Call`，值就是记录里的 `call`。没通过认证的应答、还没就绪时的 503、不存在的路径不带：一个找不到记录的编号只会浪费排查的时间。

- 浏览器里的跨源调用要读得到它：`Access-Control-Expose-Headers` 加上这个头。
- 流式应答的操作（导出）：头在结果确定之前就发出去了。记录在流结束时写，`outcome` 是开始流之前定下的那个，流有没有完整送完看 `complete`。
- `/mcp` 上不给：工具结果里的文字是给模型读的。MCP 上的一次调用只能凭租户、时刻与工具名找到它的记录；`internal` 的错误另有事故编号，记录里也带着。

头是契约的一部分，不随部署方开没开记录而变。这是操作契约上唯一的改动，只增不改：不认识这个头的客户端不受影响。

### 4. 记录出了问题，不影响调用

- 记录在调用的结果确定之后才生成，不改变应答，不改变状态码。
- **写得慢是比写不出更常见的情形**：日志收集停下来不读，标准输出还开着、但是满了。所以待写的记录有上限（按条数）。超过上限时，新的记录直接丢掉并计数，调用不等它，进程的内存也不随它涨。写出口报错时同样丢掉并计数。
- 丢了记录时，每分钟至多写一条 `call_record_failed` 的警告，带这一分钟里丢了几条。警告写在标准错误上（与别的警告一样），所以标准输出坏了它也出得来。
- 所以记录是**观测，不是账本**。一条记录不能说明自己丢没丢：操作号在一个租户里并不连续（一次操作里的事件占着它后面的号；系统自己追加的事件、OAuth 授权时登记连接实例的事件都不对应任何记录），读取类的调用根本没有操作号，所以从号码的缺口看不出丢了什么。上面把 `replayed` 算进生效的写入，补回的是最常见的那种丢失；要不多不少的数，以租户自己的日志为准（导出，或由租户的主人去数）。

### 5. 这是什么性质的数据

记录里没有内容。但这一版一个租户就是一个用户，所以一串（租户、调用方、时刻、操作）是一个人在一个稳定的代号下的活动情况。它不是内容，也不是遥测（它是写在本机标准输出上的日志），但它是关于人的数据，并且被收走之后放在租户的存储之外：隐私删除删不到它，导出也不含它。

- 记录由部署方持有，留多久由部署方定。saveslot 不保存它，也不删除它。
- 「删除整个租户」时应用日志里与它有关的内容怎么办，是 `08-open-questions` 里已有的待定项；开了调用记录的部署，被删租户的 ID 会留在已经收走的记录里，归同一条。

### 6. 版本

- 加字段不改 `v`。部署方的收集程序要忽略不认识的字段。
- 去掉字段、改字段的含义或取值，`v` 加 1，并在规格里写明哪个版本的程序输出哪个 `v`。收集程序遇到不认识的 `v` 应当停下来报错，不要照旧的含义去读。
- 字段表写在规格里，与代码一致；记录里出现规格没列的字段是缺陷。

## 没选的做法

- **让部署方在入口层自己算。** 入口层看不到租户，看不到 MCP 的工具名与工具调用的成败，看不到重发。要看到就得在入口层解开令牌、解析请求体与应答体，那等于让部署方的程序读用户的数据，并且依赖应答体的形状。
- **把代码里那个回调开放成扩展点。** 部署方的代码跑在服务进程里：它慢，调用就慢；它的版本要跟着内核走；它拿到的是整份参数与结果。三条要求一条都不满足。那个回调保持为测试用，规格里不出现。
- **由服务进程把记录发到一个地址（webhook、消息队列）。** 记录的送达从此成了服务进程的事：对方不可用时是丢、是攒、是重试，都要在内核里定，并且带来一条从内核出去的网络依赖。标准输出上的行由部署方已有的日志收集处理这些。
- **部署方直接读租户的日志。** 日志里是用户的全部数据；为了计数去读它，越过了「运营方的监控不读用户内容」这条线。读取类的调用也不在日志的事件里。
- **默认开启。** 自部署的用户没有要这些行。默认关着，标准输出与现在逐字节相同。
- **让记录能自己查出丢失**（每条带进程的随机编号与一个逐条加一的计数，一个进程活着期间号码缺了就是丢了）。做得到，两个字段都与租户无关；这一版不做，等真有人要对账时再加，加字段不改 `v`。
- **原样记下 client 标识。** 见第 2 节：它是调用方选的字符串，动态登记时里面有名字。

## 怎么验

- 每种结果各一条：成功的读；成功的写（`appended`、`saved`）；成了候选或待确认的写（`appended`、`pending`）；值没变的写（仍是 `appended`、`saved`，带操作号）；全部按来源键且都没有改动的写（`none`，没有操作号）；用同一个幂等键重发的写（`replayed`，`seq` 与 `restores` 同第一次）；对已解决的事项再解决一次（`replayed`，`seq` 是第一次解决的）；`resolve` 触发的写入的 `status`；契约错误（带与不带 `reason`）；`internal`（带 `incident`）。其中端到端（经服务器、看输出的记录）的是：成功的读、成功的写、重发的写、契约错误；在内核一层（看内核随结果交出的效果）的是：候选或待确认的写、全部按来源键都没有改动的写、再解决一次、`resolve` 触发的写入的 `status`，以及每个会追加事件的操作各一条（`seq` 等于日志里最后一次操作的号）；`internal` 的事故编号在服务层的单元测试里。记录由服务层照内核交出的效果原样写出，这一层另有单元测试。
- 恢复之后再写入：操作号与恢复前的某次写入相同，`restores` 不同。
- `/mcp` 一个请求里两次工具调用：两条记录，各自的工具名与结果；其中一次失败时 HTTP 状态码是 200 而那条记录的 `outcome` 是错误码。`/mcp` 上权限不够的工具调用：整个请求 403，被拒的每次调用各一条 `insufficient_scope`。两个面上被限流都出记录。
- 不出记录的：认证没通过（含账户停用）、`initialize`、列工具、不存在的工具名。
- 三种 `via`；`registration` 只覆盖今天出得来的 `document`：`dynamic` 要等动态登记实现，`builtin` 要等程序自带的 client 签发连接实例（今天它们签发的是用户会话），到有对应路径时补。client 文档地址的路径里放一个标记串：记录里搜不到它（动态登记的 client 名字里放标记串那一条，到有动态登记时补）。
- 应答头：出记录的应答都有、值与记录的 `call` 相同；401、未就绪的 503、不存在的路径没有；跨源调用读得到它。导出的流正常结束与中途断开，`complete` 分别是 `true` 与 `false`。
- 关着的时候，标准输出与没有这项改动时相同（应答头仍在）。
- 写出口抛错、写出口一直不读（待写的到了上限）：调用照常应答、不变慢，内存不涨，警告按分钟合并并写在标准错误上。
- **不含内容**：用带标记串的 slot 名、表名、字段名、连接实例名、任务标识、幂等键与写入的值跑一遍各类调用（含各种报错），全部记录里搜不到任何一个标记串。
- **取值都出自枚举**：跑过的全部记录里，`outcome` 与 `reason` 的每个值都在契约的枚举表里；`reason` 不在枚举里的错误，记录里没有 `reason`。
- 字段表与实际输出逐字段对：规格里列的字段都出现过，输出里没有规格没列的字段。

# 决定：服务器模式按调用输出一条不含内容的记录

> 不改事件格式，不改 K1–K14。操作契约只加一个应答头。按「分步交付」落进规格与代码。

本文里「部署方」指运行服务器模式的一方（托管服务的运营者，或自部署的用户自己）；「调用」指一次契约操作：`/v1` 上的一个请求，或 `/mcp` 上的一次工具调用。

## 要解决什么

部署方要回答这样的问题：某个租户今天用了多少次、是哪个客户端在用、做的是什么操作、成没成功、有多少次写入真的生效了。现在答不了，原因是服务器模式往外给的东西不够：

- `server start` 在标准输出上按请求写一行：方法、路由名、HTTP 状态码、耗时。行里没有租户，没有调用方。
- `/mcp` 只有一个路由。工具名在请求体里，日志只记一个请求里第一个工具调用的名字；工具调用失败时 HTTP 状态码仍是 200，失败写在工具结果里。
- 入口层（反向代理、负载均衡器）看得到的只有方法、路径与状态码。令牌是不透明的，从它得不出租户。
- 一次写入是新生效的还是重发，只写在应答体里（`replayed`）。要知道就得解析应答体，而应答体里是用户的数据。
- 代码里有一个在工具调用结束时被调用的回调，测试在用。它拿到的是整份参数与整份结果，只有 MCP 上有。它不是对外的接口，也不该是：它把用户的内容交给了回调。

所以只靠计数器分不清「一次写入」与「一次重发」，也分不清是谁的。

要求：

- 归属到租户与调用方，用稳定的标识；
- 分清操作与结果，分清写入生效、写入没有改动、重发；
- 同一条观测被收集两次时能去重；
- 记录这件事出了问题，不影响调用本身；
- 不含凭证，不含存储的内容，不含用户或调用方起的名字；
- 认不出的客户端就是认不出，不猜；
- 自部署默认什么都不多做，程序不向任何地方发送数据。

## 决定

### 1. 每次调用一条记录，由部署方显式开启

服务器模式加一个配置项 `SAVESLOT_CALL_RECORDS`，取值 `on` / `off`，默认 `off`。开启后，每次调用结束时，服务进程在标准输出上写一行 JSON，这一行就是这次调用的记录。部署方用自己的日志收集把它取走；程序自己不把它发到任何地方，也不提供接收它的服务。

- `/v1`：一个请求一条。
- `/mcp`：一次工具调用一条。一个请求里放了几次工具调用，就是几条。`initialize`、列工具这类不是契约操作的请求不出记录。
- 认证没通过的请求不出记录：这时还不知道租户是谁。它们仍在现有的按请求的那一行里（状态码 401）。
- OAuth 的各个端点、`/health`、`/ready` 不出记录。

现有的按请求的那一行照旧，不加字段、不删字段。两种行靠 `record` 这个字段分开：调用记录有它，按请求的行没有。

本机模式没有这个配置项，不出记录。

### 2. 记录里有什么

| 字段 | 含义 | 来源 |
|---|---|---|
| `record` | 固定为 `"call"` | — |
| `v` | 记录格式的版本，现在是 `1` | — |
| `call` | 这次调用的 ID，`call_` 加随机串，每次调用新生成 | 服务进程 |
| `at` | 调用结束的时刻（UTC） | 服务进程的时钟 |
| `ms` | 从认证通过到结果确定的毫秒数 | 同上 |
| `tenant` | 租户 ID（`tn_…`） | 认证结果 |
| `actor` | 调用方的 ID：用户会话是 `u_…`，连接实例是 `ci_…` | 认证结果 |
| `via` | 这个调用方的凭证是怎么来的：`session`（用户会话）、`token`（签发的连接实例令牌）、`oauth`（一次 OAuth 授权） | 连接实例登记时写下的值；用户会话固定为 `session` |
| `client` | `via` 是 `oauth` 时，授权时登记的 client 标识；其余情况没有这个字段 | 连接实例登记时写下的值 |
| `surface` | `http` 或 `mcp` | — |
| `operation` | 契约里的操作名（`write`、`query`、`resolve`……） | 路由表 / 工具表 |
| `route` | `surface` 是 `http` 时的路由名；是 `mcp` 时的工具名 | 同上 |
| `outcome` | `ok`，或契约的错误码（`invalid_argument`、`conflict`、`unavailable`……） | 契约结果 |
| `reason` | 错误带有枚举的原因时，那个原因（`read_first`、`busy`……）；否则没有 | 同上 |
| `effect` | 只在会追加事件的操作（`write`、`resolve`、提交 schema 草稿等）成功时有：`appended`（这次调用往日志里追加了事件）、`none`（什么都没追加：值没变、按来源键判定为没有改动）、`replayed`（重发，返回的是原来那次的结果） | 回执 |
| `seq` | `effect` 是 `appended` 或 `replayed` 时，那次操作在租户日志里的操作号 | 回执 |

说明：

- **稳定的标识。** 租户 ID 一个用户一个，导入之后不变。连接实例 ID 在改名、换发访问令牌之后都不变；一次 OAuth 授权登记一个连接实例，同一个 client 再授权一次是另一个连接实例。部署方要把租户对到自己的账户，用它建租户时得到的租户 ID。
- **`client` 是 client 自己公开的标识**（它的 client 文档的地址，或命令行固定的那个），不是用户起的名字。令牌签发的连接实例没有它：这时是哪个程序在用这个令牌，服务端不知道，记录里也就没有。
- **不读 `User-Agent`，不看连接实例的名字。** 这两样都是调用方自己说的，没人核对。用连接器 SDK 的调用今天没有可靠的标记，记录里认不出；要认出，得在签发连接实例时登记它的种类，那是另一项改动，不在这里定。
- **`operation` 与 `route` 都给。** 几条路由可以是同一个操作（`catalog` 有七条），按操作计数用前者，要看具体是哪个入口用后者。
- **`effect` 回答「写入有没有生效」。** `appended` 的含义是日志里多了事件，不等于值已经生效：一次写入成了候选或待确认，也追加了事件。要再分，按应答里的 `status`，记录不重复它。被拒的写入是 `outcome` 上的错误码，没有 `effect`。
- **去重。** 同一条记录被收集了两次，`call` 相同。同一次写入被重发了几次，是几条记录、几个不同的 `call`，其中一条 `effect` 为 `appended`，其余为 `replayed`，它们的 `tenant` 与 `seq` 相同。所以「生效的写入数」是 `effect` 为 `appended` 的记录按（`tenant`，`seq`）去重之后的条数。

记录里**没有**的：令牌与任何凭证；请求体与应答体里的任何内容；slot 名、表名、字段名；连接实例的名字、账户名、外部登录的账户标识；任务标识与幂等键的原文；查询条件与 SQL；来源地址。slot 与表的 ID 也不放：按 slot 归属不在这次要回答的问题里，放了只会让记录更接近内容。

### 3. 调用 ID 回给调用方

`/v1` 的每个应答带应答头 `Saveslot-Call`，值就是记录里的 `call`，不管 `SAVESLOT_CALL_RECORDS` 开没开。有人报「这次调用出了问题」时，部署方能凭它找到那条记录。`/mcp` 上的工具结果不加这一项：那是给模型读的文字。

这是操作契约上唯一的改动，只增不改：不认识这个头的客户端不受影响。

### 4. 记录出了问题，不影响调用

- 记录在调用的结果确定之后写。写不出去（标准输出被关掉、写满）时，错误被吞掉，调用照常应答；每分钟至多记一条 `call_record_failed` 的警告，带这一分钟里丢了几条。
- 记录不改变应答，不改变状态码，不让调用等它。
- 所以记录是**观测，不是账本**：进程在提交之后、写记录之前退出，这条记录就没有了。要的是不多不少的数，以租户日志为准：`seq` 在一个租户里只增，部署方看到的（`tenant`，`seq`）有缺口，就知道丢过记录。

### 5. 版本

- 加字段不改 `v`。部署方的收集程序要忽略不认识的字段。
- 去掉字段、改字段的含义或取值，`v` 加 1，并在规格里写明哪个版本的程序输出哪个 `v`。收集程序遇到不认识的 `v` 应当停下来报错，不要照旧的含义去读。
- 字段表写在规格里，与代码一致；记录里出现规格没列的字段是缺陷。

## 没选的做法

- **让部署方在入口层自己算。** 入口层看不到租户，看不到 MCP 的工具名与工具调用的成败，看不到重发。要看到就得在入口层解开令牌、解析请求体与应答体，那等于让部署方的程序读用户的数据，并且依赖应答体的形状。
- **把代码里那个回调开放成扩展点。** 部署方的代码跑在服务进程里：它慢，调用就慢；它的版本要跟着内核走；它拿到的是整份参数与结果。三条要求一条都不满足。那个回调保持为测试用，规格里不出现。
- **由服务进程把记录发到一个地址（webhook、消息队列）。** 记录的送达从此成了服务进程的事：对方不可用时是丢、是攒、是重试，都要在内核里定，并且带来一条从内核出去的网络依赖。标准输出上的行由部署方已有的日志收集处理这些。
- **部署方直接读租户的日志。** 日志里是用户的全部数据；为了计数去读它，越过了「运营方的监控不读用户内容」这条线。读取类的调用也不在日志的事件里。
- **默认开启。** 自部署的用户没有要这些行。默认关着，标准输出与现在逐字节相同。

## 怎么验

- 每种结果各一条：成功的读；成功的写（`appended`）；值没变的写（`none`）；用同一个幂等键重发的写（`replayed`，`seq` 与第一次相同）；契约错误（带与不带 `reason`）；`internal`。
- `/mcp` 一个请求里两次工具调用：两条记录，各自的工具名与结果；其中一次失败时 HTTP 状态码是 200 而那条记录的 `outcome` 是错误码。
- 认证没通过：没有记录。
- 三种 `via`；`oauth` 时有 `client`，其余没有。
- 关着的时候，标准输出与没有这项改动时相同。
- 写不出去时调用照常应答（把写出口换成会抛错的），警告按分钟合并。
- **不含内容**：用带标记串的 slot 名、表名、连接实例名、任务标识、幂等键与写入的值跑一遍各类调用，全部记录里搜不到任何一个标记串。
- 字段表与实际输出逐字段对：规格里列的字段都出现过，输出里没有规格没列的字段。

## 分步交付

1. 这份决定记录。
2. 规格与实现（一份改动）：认证结果带上 `via` 与 `client`；调用 ID 与应答头；记录的输出与配置项；上面的测试。
3. 签发连接实例时登记种类（让连接器 SDK 的调用认得出）另行决定，不在这一步。

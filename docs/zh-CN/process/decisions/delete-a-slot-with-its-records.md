# 决定：删除一个有记录的 slot

> 给操作契约的删除加一种（`kind: "slot"`）；给事件格式的删除事件加一种写法（用到它的事件 `v` 加一）；**K1 不变，K12 的重放多一条规则**（第 6 条），这是对一条内核不变量适用方式的说明，审过才落进规格。本机模式与服务器模式都做。

## 要解决什么

用户不想再用某个 slot 了：记账不记了，某个项目结束了。他应当能把它连同里面的全部数据删掉，就像他能把数据导出带走一样。现在做不到：

- `slots.remove` 只移除空的 slot。有没有数据按日志里出现过哪些事件判，写过一次就永远不空。
- 隐私删除按源数据删。把一个 slot 的全部源数据都列为删除目标，内容确实都没了，但 schema 里的文字（表名、字段名、说明、枚举值）与 slot 的名字清不到，slot 本身也仍然不空、移除不了：一个内容全空的 slot 一直留着，占着名字与一个名额。
- 01-positioning 把它列为以后要做的事，并写明做之前先定义：schema 文档、slot 策略、事项、迁移中的新版表怎么处理，slot 名与 `slot_id` 能否复用，宽限期内能否写入，撤回的语义；接口走同一套 `deletion_preview` → `delete`（`kind: "slot"`）。这份决定回答它们。

这是两种「整个」的删除之一。另一种是删除整个租户（「删除整个租户，与给账户系统用的运维接口」）。删除 slot 的一部分（一张表、一条记录）不在这里：它碰到的是几行、几张表共用的源数据，按源数据删会多删，那是另一个问题。

## 为什么整个 slot 好删

隐私删除难在重放：去掉一条源数据之后，别的写入可能因此生效、转为待确认，派生值要重算，这些都要按规则重新判定。删除整个 slot 没有这件事，因为 slot 是一个封闭的单位：

- 一次写入只涉及一个 slot；一条源数据只属于一个 slot（03-data-model「删除的种类」）；
- 派生规则与 `ref` 字段不跨 slot；
- 跨 slot 的只有只读的 `sql` 查询，它不产生任何依赖。

所以 slot 之外没有任何一个值由 slot 之内的内容得出。整个删掉，外面什么都不用重算、不用重判。

## 决定

### 1. 接口：同一套预览与确认，多一种

```ts
// deletion_preview / delete 的目标多一种
{ kind: "slot"; slot: SlotId }
```

- **按 `slot_id`，不收名字**，与 `slots.remove` 同一个理由：名字可以重用，按名字的删除被重发时会删到后来同名新建的那个。CLI 收名字，解析成 `slot_id` 并在确认时显示。
- **预览**谁都可以做：对这个 slot 有删除权限的连接实例与用户会话。
- **确认只给用户会话。** 连接实例确认会得到 `insufficient_scope`；MCP 上只有预览，结果的文字写明要由用户在命令行或控制台里确认。逐条的隐私删除可以由 Agent 发起，是因为范围由它引用的源数据限定；整个 slot 没有这个限定，与 `slots.remove`、导入这些只给用户会话的操作同一类。
- 流程与隐私删除相同：预览 → 确认 → 宽限期 → 到期执行；确认用预览返回的句柄。

### 2. 删什么，留什么

到期执行之后：

**不再存在的：**

- 这个 slot 的**每一个事件的每一个数据块**：源数据的原文与摘录；每次写入的值、区间、来源、字面命中；事项的内容；派生写入；**schema 草稿与编译结果里的文字**（表名、字段名、说明、别名、枚举值、迁移与回填里的常量）；slot 的名字；slot 策略的内容；这些操作自报的 `task`、请求键、幂等键。
- 它的物理表：基础表、版本表、派生表与索引；目录、计数与来源表里它的行。
- 读取记录里读这个 slot 的那些记录。

逐条隐私删除清不到的那几样（schema 的文字、没有源数据的操作自报的标识），在这里都清得到：它们清不到是因为没有来源可沿着删，而这里不沿着来源删，是按「属于这个 slot」删。

**留下的：**

- **事件头**，照 K1：这个 slot 的每个事件的序号、类型、时刻、所属的 `slot_id` 与链上的哈希。
- **元数据块**，照 09-event-format §9.2：表 ID、行 ID、字段 ID、意图、事项的类型与处理方式、判定用的版本号。
- 所以看得出：有过一个 slot（只有不透明的 ID），在什么时候做过多少次什么类型的操作，涉及过多少张表、多少行。看不出：它叫什么、里面的表叫什么、任何一个值、任何一句原文。预览与回执照实写明这一点。

**不在其中的**：连接实例的名字（它不属于哪个 slot）；别的 slot 的任何东西；用户已经导出的文件；外部文件引用所指的文件本身（saveslot 没有保存它）。

### 3. 宽限期与撤回

- **宽限期 7 天**，与删除整个租户的缺省相同。逐条隐私删除是 24 小时；整个 slot 的后果大得多，撤回的窗口留得长。确认时可以指定「立即」，没有宽限期。
- **从确认的那一刻起，这个 slot 对所有调用方不存在**：目录里不出现；按名字引用它的表报 `unknown_table`，按 ID 引用它的任何东西报 `not_found`，与不可见、不存在同一个应答。写不进去，读不出来。
- **宽限期内它的名字仍被占着**，不能新建同名的 slot；执行之后名字可以重用。`slot_id` 永不复用。
- **撤回**（只给用户会话）：一切回到确认之前，同一个 `slot_id`、同样的表与数据。宽限期内没有任何东西被物理删除，所以撤回不需要恢复什么。
- 宽限期内这个 slot 的内容不导出：导出里它的数据块照「待删除」写成占位（09-event-format §3.3），除非用户会话明确选择包含。
- **预览提示先导出。** 导出是整个租户的，预览不代做。

### 4. 确认时正在进行的事

| 这个 slot 里有 | 怎么处理 |
|---|---|
| 未决的事项（冲突、待确认、已标记、结构变更） | 确认时全部关闭，原因是 slot 被删除；撤回时原样恢复为未决（它们的内容在宽限期内没有被动过） |
| 未到期的隐私删除 | 各走各的：到期照常物理删除，不因为 slot 冻结而推迟。撤回 slot 的删除之后，它们的状态与没有这次 slot 删除时相同 |
| 进行中的迁移（新版表在构建） | **确认被拒绝**，`invalid_argument`（`migration_in_progress`），等迁移做完或失败。迁移到一半冻结、撤回后再接上，状态太多；迁移是短暂的，等它就行 |
| 待确认的 schema 草稿 | 随事项关闭；草稿的文字是这个 slot 的数据块，一并删除 |
| 只限定到这个 slot 的连接实例 | 不吊销。它的范围里只剩一个不存在的 slot，什么都做不了；预览里列出这些连接实例，由用户决定要不要吊销 |

### 5. 怎么落进日志

删除仍是三种事件：`deletion.confirmed`、`deletion.cancelled`、`deletion.executed`。给它们加一种写法：

- **目标是整个 slot 时，不逐块列位置。** 位置写成一条：`slot_id` 与一个序号上限 `upto`（确认时日志的末端）。它的含义是「`slot` 是它、`seq` 不大于 `upto` 的每个事件的每个数据块」。一个用了几年的 slot 有几十万个块，逐个列出的事件比它删掉的内容还大。
- 确认事件不带「删除后的样子」：没有哪一行需要重述，slot 之外没有值变了。它只带关闭的事项列表（元数据）。
- 墓碑（`deletion.executed`）照这一条位置清空那些块，每个块的状态成为「已由 #n 移除」，与逐块删除的结果相同；同时删掉物理表与各处的行。
- 用到这种写法的事件，该类型的 `v` 加一。照事件格式的规则分两个版本走：先发一个读得懂它的版本，下一个版本才写它。

删除登记（锚点存储里、恢复备份时用来补删的那一份）同样记这一条：删除 ID、`slot_id`、`upto`。恢复一份早于删除的备份时，按它补删：把恢复出来的日志里属于这个 slot 的数据块照样清空、删表。**按登记补删现在还没有做出来**，登记里有条目的租户恢复会被拒绝；整个 slot 的补删随这个功能一起做，否则删过一个 slot 的租户就再也恢复不了。它比逐条删除的补删简单：不用重放，只是把同一步再做一遍。

### 6. 重放：已删除的 slot 不落账

K12 说记录的结果等于按日志重放的结果。一个 slot 被删除之后，它的事件还在日志里，数据块都空了。重放规则补一条：

- **重放到一个已被整体删除的 slot 的事件时，只核对事件头的链，不落账。** 「已被整体删除」由日志里那条墓碑认定；重放从头读到尾，遇到墓碑之前已经把这个 slot 的表建出来、写进去的，到墓碑时照墓碑删掉，结果相同。两种做法（先跳过，或先做后删）得到同一个最终状态，实现可以选前一种。
- 重放之后：这个 slot 不存在，它的表不存在，别的 slot 与不重放时逐项相同。因为 slot 之间没有依赖（上面「为什么整个 slot 好删」），不落账不影响任何别的结果。
- `log.verify`：这些块报「已移除」，不算不符，与逐条删除之后相同。

K1 不变：事件头一个都没动。K11 不变：删掉的内容不会经重放、导出导入或恢复备份回来。

### 7. 物理上删干净

到期执行做三件事：清空内容表里那些块；删掉物理表；清理读取记录。之后照物理删除的现有规定做残留清理（02-architecture §7「残留清理的做法」），否则被删的原文还留在数据库的空闲页与预写日志里。

残留清理在两个后端上都还没有接进到期执行的流程。**整个 slot 的删除不能早于它发布**：没有它，回执说「已删除」而原文还搜得到。

## 不在这份决定里

- 删除一张表、删除一条记录连同历史。
- 把整个 slot 的删除交给连接实例或运维接口确认。
- 删除之后连事件头与元数据块也不留。那要换掉这条日志，是删除整个租户才做的事。
- 按 slot 导出。

## 它改了哪些已有的规定

- **01-positioning**：「整个 slot 删除」一条改为已定义；「逐条隐私删除已能满足彻底忘掉」这句去掉，它对 schema 的文字与 slot 本身不成立。
- **03-data-model「删除」**：删除的种类多一种；它的预览、宽限期、撤回与到期；「不随这次删除清除的数据块」对它不适用的几项；删除登记的条目多一种写法与它的补删。
- **04-contract-types、04-contract**：`deletion_preview` 与 `delete` 的 `kind: "slot"`；预览与回执的内容；只给用户会话确认；`migration_in_progress`。
- **05-surfaces、06-cli**：MCP 上只有预览与它的文字；`saveslot slot delete <名字>` 与撤回。
- **09-event-format §3.2、§5.9、§9**：位置的这种写法；三种删除事件的 `v`；「事件头里留下了什么」里整个 slot 被删之后的一节。
- **02-architecture §3（K12）、§8**：重放的这一条；恢复流程里整个 slot 的补删。
- **「移除空 slot」的决定**：空 slot 仍用 `slots.remove`；有记录的走这里。删除执行之后这个 slot 的名字可以重用，与移除之后相同。
- **讲解**：删除的那一章。
- K1 与 K11 不变。

## 怎么验

- 删除之后：目录里没有它；按名字、按 ID 的引用与不存在时逐个应答相同；它的表不在存储里；在数据文件里搜不到它任何一句原文、任何一个表名或字段名（残留清理之后）。
- 留下的：它的事件头条数与删除之前相同，链校验得过；数据块全部是「已移除」。
- 别的 slot：删除前后每张表、每个版本、每个事项、每次读取的结果逐项相同（性质测试：随机的两个 slot 的写入序列，删掉其中一个）。
- 宽限期内：读写都得到不存在的应答；同名新建被拒；撤回之后与确认之前逐项相同，未决的事项仍未决；宽限期内到期的逐条隐私删除照常执行。
- 确认：连接实例被拒；迁移进行中被拒；按名字（HTTP）被拒并指路。
- 重放：从空存储重放这条日志，得到的状态与线上相同，这个 slot 不存在；导出再导入同样。
- 恢复早于删除的备份：走完恢复流程之后这个 slot 不存在，内容搜不到；宽限期内恢复的，删除仍待执行、到期时刻不变。
- 两种写法并存：同一条日志里既有逐块的删除、又有整个 slot 的删除，各自的结果互不影响。
- 读得懂而不写的那个版本，读得了下一个版本写下的事件。
- 一个几十万个块的 slot：确认事件的大小与块数无关；到期执行的耗时与期间别的 slot 的写入延迟记进实测。
- 执行之后新建同名的 slot：是一个新的 `slot_id`，里面什么都没有，读不到旧的任何东西。

## 分步交付

1. **读得懂**：事件格式的这种写法与重放的那一条；不产生它。
2. **残留清理接进到期执行**（两个后端）。它也是逐条隐私删除对外发布的前提。
3. **删除整个 slot**：预览、确认、撤回、到期执行、登记与补删，命令行与 HTTP，MCP 的预览。

## 实验 1：PGlite 持久性

### 要回答的问题

在 Node 里用 PGlite 加本地文件系统，saveslot 回执"已保存"的写入，在进程被强杀或机器断电后是否一定还在。

### 为什么要这样设计

架构的硬要求是"已确认的写入在崩溃、断电后不能丢"（`02-architecture.md` §7）。已有调研给出两条不利的线索（`research/05-storage-tenancy.md` §1.1、§1.3）：

- PGlite 的默认启动参数带 `-F`，即关闭 fsync。
- 社区 issue #1107 称：PGlite 在 Node 文件系统后端上的同步函数是空的，底层的同步调用直接返回成功，没有真正调用宿主的 fsync。该 issue 当时未关闭，作者也说明没有复现过真实断电损坏。

由此有两点决定了实验怎么做：

1. **"把 fsync 配置打开就能落盘"是待实验确认的假设，不是已知事实。** 配置项能不能改、改了以后宿主的落盘调用有没有真的发出，都要在实验里直接观察。PGlite 是否允许去掉 `-F`、用哪个选项去掉：未核实。
2. **只做强杀进程不够，它是一个假绿灯。** 进程被强杀时，已经写进操作系统页缓存的数据不会丢，所以即使完全没有 fsync，强杀测试也会通过。强杀测试能检验的是"提交确认之前数据已经写出进程"和"崩溃恢复是否正确"；"是否真的落盘"只能靠断电测试和系统调用观察来检验。

### 做法

**环境**

| 项 | 取值 |
|---|---|
| 平台 | macOS（APFS，Apple 芯片）、Linux（ext4，x86-64 或 arm64 任一）。Windows 不在第一版本机模式范围内，不测 |
| 运行时 | 第一版打算支持的 Node 版本；Bun 若打算支持则各跑一遍 |
| PGlite | 开工时的最新版本，记下版本号；规格要求 18.6 起 |
| 布局 | PGlite 实例放在 worker 线程里，与架构设计一致（§7） |
| 配置 | 分两组各跑全套：**组 A** 默认配置（作对照，预期断电测试不通过）；**组 B** 打开 fsync 的配置。组 B 具体怎么配是实验的第一个产出 |

**负载**

一个写入进程循环执行与 saveslot 一次写入形状相近的事务，每个事务：

- 往"事件头"表插一行，带单调递增的序号 n 和上一行的哈希；
- 往"内容"表插一行，约 1 KB，带校验和；
- 更新"业务"表的一行；
- 提交。

提交返回后，写入进程把 n 报告给一个**观察者**，然后才开始下一个事务。观察者必须活过故障：强杀测试里它是同一台机器上的另一个进程；断电测试里它必须在被断电的机器之外（宿主机，或另一台机器），经网络接收。观察者记下收到的最大 n，记为"已确认序号"。

另跑一组带宽松持久性选项的对照（如果 PGlite 提供），确认该选项在本机路径下确实不该使用。

**步骤一：直接观察落盘调用（每个平台、每组配置各做一次）**

跑 100 个事务，同时跟踪写入进程的系统调用。

- Linux：`strace -f`，过滤 `fsync`、`fdatasync`、`sync_file_range`、`msync`、带 `O_SYNC` / `O_DSYNC` 的 `open`。
- macOS：用系统自带的跟踪工具（`fs_usage` 或 `dtruss`；在开启系统完整性保护的机器上能否跟踪 Node 进程：未核实），过滤 `fsync` 与 `fcntl` 的 `F_FULLFSYNC`。

记录：每次提交确认之前，有没有针对预写日志文件的落盘调用；是哪一种。

**macOS 要单独看的一点**：macOS 上普通的 `fsync` 只把数据交给磁盘，不要求磁盘把自己的写缓存刷到介质上，要做到后者需要 `fcntl(F_FULLFSYNC)`（未核实，做实验前查 Apple 的手册页）。原生 PostgreSQL 在 macOS 上有对应的 `wal_sync_method = fsync_writethrough`（未核实）。Node 的 `fs.fsync` 在 macOS 上实际发出哪一种调用：未核实，以跟踪结果为准。所以 macOS 上要分清三种结果：没有任何落盘调用、只有普通 `fsync`、有 `F_FULLFSYNC`。

**步骤二：强杀（每个平台、组 B，1,000 轮）**

每轮：启动写入进程 → 随机等待 0.5–5 秒 → 对写入进程发 `SIGKILL` → 重新打开数据目录 → 检查（见下）→ 继续用同一个数据目录进入下一轮，不重建。

另加两个变体各 200 轮：只终止 worker 线程而不杀进程；在事务进行中（已发出写、未提交）终止。

**步骤三：断电（每个平台、组 A 与组 B，各 100 轮）**

- Linux：写入进程跑在虚拟机里，观察者在宿主机。每轮随机时刻强制结束虚拟机进程（不是在客户机里关机）。客户机的页缓存随之丢失，客户机里没有落盘的数据就没了，这模拟的是客户机视角的断电。虚拟磁盘的缓存模式要设成"客户机的刷盘请求会到达宿主文件"的那一种，并在报告里写明用的是哪种模式。
- macOS：虚拟机里的磁盘刷盘语义与真机不同，不能代替真机。做法是在一台台式 Mac 上真实断电（拔电源），观察者在另一台机器上。真机断电轮数降为 20 轮（拍的），并以步骤一的跟踪结果为主要依据。笔记本有电池，不适合做这个测试。
- 组 A（默认配置）也要跑。预期它会丢数据。**如果组 A 在断电测试里一条都没丢，说明测试方法没有制造出真正的断电，结果作废，先修方法。** 这是这项实验的阳性对照。

**每轮重开后的检查**

1. 数据目录能打开，不报错。
2. 事件头表里的最大序号 ≥ 观察者记下的已确认序号。
3. 序号从 1 到最大值连续，没有空洞。
4. 每一行事件头的"上一行哈希"对得上；每一行内容的校验和对得上。
5. 三张表互相一致：每个序号在三张表里要么都有、要么都没有。
6. 用 PostgreSQL 自带的索引与堆检查扩展（`amcheck`，PGlite 主包内置，见 `research/05` §1.2）检查全部表与索引，无报错。

**同时测性能**

组 B 下单个事务的提交延迟：p50、p99，每个平台各 10,000 个事务。记下打开真实落盘前后的差别。

### 通过标准

全部满足才算通过：

| # | 标准 |
|---|---|
| 1 | 步骤一：组 B 下，每次提交确认之前都观察到针对预写日志的落盘调用。macOS 上必须是 `F_FULLFSYNC`，或者团队书面接受"macOS 上只保证到普通 `fsync`"并把它写进第 9 章式的边界说明 |
| 2 | 步骤二：1,000 轮加两个变体各 200 轮，检查 1–6 全部通过，已确认提交丢失数为 0 |
| 3 | 步骤三：组 B 下 Linux 100 轮、macOS 真机 20 轮，检查 1–6 全部通过，已确认提交丢失数为 0 |
| 4 | 步骤三的阳性对照成立：组 A 在同样的方法下至少有一轮丢失已确认的提交 |
| 5 | 组 B 的提交延迟 p50 ≤ 20 ms、p99 ≤ 200 ms（固态硬盘；拍的） |

关于轮数要说清的一点：100 轮零失败只能说明失败率大概率低于 3%（按零失败时的经验估计），不能证明不会丢。所以标准 1（直接看到落盘调用）是主要依据，标准 2、3 是佐证。标准 1 不满足时，标准 2、3 即使全过也不算通过。

### 不通过时的决定

分三种情况：

| 情况 | 决定 |
|---|---|
| 标准 1 不满足，原因是 PGlite 的 Node 文件系统后端不发落盘调用 | 给三个工作日（拍的）尝试补上：自定义文件系统后端，在预写日志写入后调用宿主的落盘；或跟进上游修复。补上后重跑全部步骤。三天内做不到，按下一行处理 |
| 标准 2 或 3 不满足，或上一行超时 | **本机后端换成随 saveslot 打包的原生 PostgreSQL**（`research/05` §2 的降级路线）。影响：P1 的 `store` 实现改为 `store-postgres` 加子进程生命周期管理；实验 6 变成关键路径；实验 2 的 worker 终止部分、实验 7 的 PGlite 部分不再需要。范围文档估的额外成本是 P1 与 P6 各加 1–3 人周 |
| 只有标准 5 不满足 | 不换后端。记录实际延迟，评估是否影响评测任务的体验；写接口超时按实测值定 |

"定期检查点加快照"（调研里提过的另一条路）不采用：它不能保证已确认的写入不丢，与硬要求不符。

### 连带要回答的

- **本机控制面用什么存储。** 架构审查 P1-14 指出本机控制面的存储没有定，而删除登记要求"先写登记、落盘后再提交租户事务"，持久性要求与租户存储同级。控制面存储定下来之后（属于工作包 W4），如果它也是 PGlite，本实验的结论直接适用，另需确认一个进程里跑两个实例可行；如果是别的存储，对它单独跑步骤一和步骤二。
- **数据目录在同步盘里的行为**不在本实验范围内，架构已规定检测到时警告。

### 何时做、挡什么

最先做，与 P0 脚手架并行，预计 3–5 个工作日（不含上面的三天补救）。结论挡 P1 的 `store` 实现。

## 实验 2：PGlite 沙箱

分两部分，可以分开做。

### 2a：终止 worker 的代价

**要回答的问题**：把"终止整个 worker"当作慢查询的超时手段，是否安全，代价多大。

**背景**：PGlite 上 `statement_timeout` 不生效（`research/references-arch.md` 第 31 行），超时只能靠终止 worker，等于数据库崩溃一次（`02-architecture.md` §7）。

**做法**

- 数据集：一个典型租户，10 张基础表、共 10 万行，加相应的日志与内容表（规模同实验 4）。
- 每轮：发起一条会跑很久的只读查询（如大表自连接），同时有写事务在排队；在随机时刻（查询执行中、写事务执行中、写事务提交瞬间三种时机各占三分之一）终止 worker；重新创建 worker 并打开同一个数据目录；做实验 1 的检查 1–6。
- 共 200 轮（拍的），同一个数据目录连续使用。
- 记录：终止调用到 worker 确实结束的时间；重新打开到能回答第一条查询的时间；主线程在这期间是否被阻塞；每轮后的内存占用（看有没有泄漏）。

**通过标准**

| # | 标准 |
|---|---|
| 1 | 200 轮后检查 1–6 全部通过，已确认提交丢失数为 0 |
| 2 | 重新打开到可用的时间 p95 ≤ 2 s（拍的） |
| 3 | 终止期间主线程（HTTP 与 MCP 的处理）没有被阻塞超过 100 ms |
| 4 | 200 轮后进程内存占用相对第 10 轮的增长 ≤ 20%（拍的） |

**不通过时的决定**

- 标准 1 不过：第一版不启用超时终止。慢查询只靠事前的三道防线（写入准入、派生规则编译时拒绝、受限 SQL 的代价限制），并把"一条慢查询最长挡住写入多久"作为写明的边界；`saveslot stop` / 重启是唯一的手动出口。同时评估是否因此改用打包的原生 PostgreSQL。
- 标准 2–4 不过：启用终止，但把超时阈值调高，使它只作最后手段；实测值写进文档。

**何时做、挡什么**：实验 1 通过之后、P1 期间。挡 P1 的超时策略。实验 1 不通过（换原生 PostgreSQL）时本部分取消。

### 2b：受限 SQL 白名单的模糊测试

**要回答的问题**：语法树白名单能否挡住一切写操作、会话状态修改、越权访问与结果不确定的函数。

**做法**

- 人工清单：至少覆盖 `SET ROLE`、`SET` / `RESET` 各类参数、`COPY`、`DO`、`CALL`、`PREPARE` / `EXECUTE`、`LISTEN` / `NOTIFY`、`LOCK`、`CREATE` / `ALTER` / `DROP`、带写操作的公共表表达式、`SELECT … INTO`、`SELECT … FOR UPDATE`、多语句、注释与字符串里的分号、`pg_` 系统表与系统函数、`dblink` / `lo_` 一类函数、`set_config()`、`current_setting()`、`pg_sleep()`、`random()`、`now()` 一族、`pg_read_file()`、类型转换触发的函数调用、运算符背后的函数、物理表名与系统列。
- 生成器：基于 PostgreSQL 语法生成随机语句，不少于 100,000 条（拍的）；另对人工清单里的每条做变形（大小写、引号、嵌套进子查询、放进 `CASE`、放进公共表表达式）。
- 判定方式：每条语句先过白名单；被放行的再在一个带审计的 PostgreSQL 上以最高权限执行，检查执行后数据库状态（全部表的校验和、会话参数、当前角色）是否有任何变化，以及是否调用了白名单之外的函数。
- 正向用例：数据目录、简单查询、三个场景推演里用到的全部合法查询和派生规则，必须全部被放行。

**通过标准**

| # | 标准 |
|---|---|
| 1 | 被白名单放行的语句里，改变了数据库状态、会话状态或调用了白名单之外函数的，数量为 0 |
| 2 | 正向用例 100% 被放行 |
| 3 | 白名单的实现是"不认识的节点一律拒绝"，由代码审查确认，不是"列出要拒绝的" |

**不通过时的决定**：补洞后全量重跑，直到标准 1 满足。`saveslot_sql` 不允许带着已知的洞进入 P2。

**何时做、挡什么**：P1 有受限 SQL 解析之后（P1 的一条派生规则就要用到），并入 P2。挡 P2 的 `saveslot_sql`。之后作为回归测试长期保留。

## 实验 3：每用户一个 database 的容量

### 要回答的问题

一个 PostgreSQL 集群里放多少个用户 database 是安全的，即每组（cell）的上限定多少。

### 与原描述的差别

原描述是"单个库里放 1k / 5k / 20k 个用户 schema"。方案早已改为同一集群里每用户一个 database（`01-positioning.md`「技术选型」），原描述作废。`research/07-per-user-storage.md` 已经在 macOS 上实测过 1,000 与 5,000 个 database，结论是起步上限 2,000、压测后可放宽到 5,000。它列出的未测项就是本实验要补的。

### 做法

分两阶段。

**3a：用真实 schema 重测（P5 之前，开发机或一台云主机）**

- 每个 database 装入第一版内核的全部内部表，加一个典型用户 schema（CLI 自带的三个模板）。调研当时按每用户 227 个关系估算，真实数字要重新数，并考虑迁移进行中翻倍、退役版本保留的情形。
- 规模：500、2,000、5,000 个 database。
- 测：建库耗时；每库磁盘占用；连一个没碰过的库的延迟；冷连接上一次典型请求的延迟；热请求延迟；每个后端的私有内存；干净启动时间；强杀后的崩溃恢复时间（`recovery_init_sync_method` 取 `fsync` 与 `syncfs` 各一次，Linux 上）；全部库都有统计信息后的闲置 CPU；内核表升级扇出到全部库的耗时；300 个活跃用户各一条连接并发跑典型请求时的 p99 与吞吐。

**3b：目标云上的 24 小时满载（云服务扩容前）**

- 在目标云的磁盘类型上重复崩溃恢复测试，并测有备库时的故障切换时间。
- 2,000 与 5,000 库，每秒几百个写事务分散到活跃用户，跑 24 小时。记录全部库里最大的冻结年龄 `max(age(datfrozenxid))`、各库上次自动清理时间的分布、自动清理进程的 CPU。
- 冷用户恢复：导出一个典型用户库再恢复的耗时。

### 通过标准（针对"每组 2,000"这个起步上限）

| # | 标准 | 阶段 |
|---|---|---|
| 1 | 2,000 库下强杀后的崩溃恢复 ≤ 120 s（拍的） | 3a、3b |
| 2 | 冷连接上的典型请求 p99 ≤ 100 ms；热请求 p99 ≤ 20 ms（拍的） | 3a |
| 3 | 闲置 CPU ≤ 0.5 核（拍的） | 3a |
| 4 | 300 并发活跃用户下典型请求 p99 ≤ 200 ms（拍的） | 3a |
| 5 | 24 小时内最大冻结年龄没有持续上升的趋势，且远低于强制冻结阈值的一半 | 3b |
| 6 | 内核表升级扇出到全部库 ≤ 5 分钟 | 3a |

5,000 库同样测，结果只用来决定将来能否放宽，不作为通过条件。

### 不通过时的决定

- 2,000 不通过：上限降到 1,000 重测。方案本身不变，只是组数变多。
- 1,000 也不通过：按调研的降级顺序，评估组内退回每用户一个 schema。这是较大的改动，届时单独评审。

### 何时做、挡什么

3a 在 P5 之前，与 P3–P4 并行。3b 在云服务扩容前。第一版只有一个组，3a、3b 都不挡第一版上线，但 3a 的结果决定第一版云服务对外承诺的容量。

## 实验 4：派生同事务刷新的延迟

### 要回答的问题

基础写入与派生刷新放在同一个事务里，单次写入要多久；据此把写入准入的阈值定成具体数值。

### 做法

- 数据集：典型 schema，10 张基础表、20 条派生规则、共 10 万行；另备一份 100 万行的作上界参考。
- 规则形态按 `03-data-model/06-derived.md`「刷新范围」的分类各备几条：分组聚合、按业务时间分桶、有界帧窗口、无界帧窗口（整分区重算）、关联维度表、分析不出范围（整租户重算）。第一版的范围分析只识别前两种，其余按整租户重算，所以要专门测"整租户重算"的耗时。
- 写入形态：改一行且不换分组；改一行且换分组（两个分组重算）；一次请求 10 行、100 行、1,000 行；改维度表的一行。
- 每种组合在 PGlite 和原生 PostgreSQL 上各跑 200 次，记录从请求进入到事务提交的耗时 p50、p99，并分解出派生刷新占多少。
- 同时记录准入估算给出的"受影响分区数、估算扫描行数、依赖深度"，对照实际耗时，看估算与实际的相关性。

### 通过标准

这项实验的主要产出是数值，通过标准定在"能不能定出可用的阈值"上：

| # | 标准 |
|---|---|
| 1 | 估算扫描行数与实际派生刷新耗时的相关性足以定阈值：在全部组合上，同一估算值区间内实际耗时的最大值与最小值相差不超过 10 倍（拍的） |
| 2 | 存在一组阈值，使评测任务 1–4、6–8 里出现的全部写入都被接受，且在这组阈值下被接受的最慢写入在 PGlite 上 p99 ≤ 1 s（拍的） |
| 3 | 最常见的写入（改一行、影响不超过两个分组）在 PGlite 上 p99 ≤ 50 ms（拍的） |
| 4 | 在 10 万行的数据集上，整租户重算一条规则 ≤ 500 ms（拍的）。它决定"分析不出范围的规则"在第一版能不能用 |

### 不通过时的决定

- 标准 1 不过：估算算法要改（`06-derived.md` 只列了四个估算量，没有给算法），改完重测。
- 标准 2 或 3 不过：先看是不是 PGlite 特有（对照原生 PostgreSQL 的数字）。是，则计入"是否换后端"的考虑；不是，则收紧第一版允许的规则形态。
- 标准 4 不过：第一版在编译时拒绝范围分析不出的规则（窗口函数、关联维度表），只允许分组聚合与按时间分桶；或者把大写入作业提前进第一版。两者取其一，前者成本低。

### 产出物

四个准入阈值的数值、写接口的超时时间、"PGlite 上一条慢查询最长挡住写入多久"的上限值。这三项目前都在待定清单里。

### 何时做、挡什么

P1 有第一条派生规则之后。挡 P2 的准入阈值与写接口超时。

## 实验 5：两个后端的重放一致性

### 要回答的问题

同一份日志在 PGlite 和原生 PostgreSQL 上重放，得到的逻辑表是否逐行相同。

### 做法

这项实验就是双后端对拍测试本身，区别在于要有意构造容易出差异的用例。

- **日志来源**：三个场景推演写成的日志；性质测试的生成器产出的随机日志，不少于 1,000 份、每份不少于 200 个事件（拍的）；专门的对抗用例。
- **对抗用例要覆盖**：
  - 数值：除法与舍入、不同精度的 `numeric` 运算、聚合的累加顺序、单位换算的舍入；
  - 时间：按月和按周截断、跨夏令时切换、时区边界上的自然日、闰日；
  - 文本：含中文、表情符号、大小写、重音字符的排序与比较、去重、分组；
  - 排序不稳定的地方：聚合里没有显式排序的拼接、带并列值的 `LIMIT`、窗口函数里并列值的次序；
  - 空值：空值在排序、聚合、比较里的行为。
- **覆盖要求**：受限 SQL 白名单里的每个函数、每个运算符、每种语法节点，至少被一条用例用到。这条是可以机械检查的，用它防止"测了很多但没测到真正有差异的函数"。
- **比较范围**：`02-architecture.md` §11 规定的逻辑表（业务表、版本表、派生表、来源表、事项、标记、主体登记、请求键索引）。全文索引与目录概况不参与。
- **版本**：PGlite 当前内置的 PostgreSQL 版本对原生同一大版本的最新小版本。服务器模式打算支持的每个大版本各跑一遍。

### 通过标准

| # | 标准 |
|---|---|
| 1 | 白名单覆盖率 100%：每个函数、运算符、语法节点至少一条用例 |
| 2 | 全部日志在两个后端重放后，逻辑表逐行比较的差异数为 0 |
| 3 | 每个后端各自"从空库重放"与"边写边落"的结果一致，差异数为 0 |
| 4 | 跨大版本：打算支持的每个大版本都满足标准 2 |

### 不通过时的决定

- 差异可归因到某个函数或写法：从白名单移除，或在规则编译时钉死行为（显式排序规则、显式舍入方式、强制加排序），然后重跑。
- 差异是结构性的（比如 WASM 版本与原生版本的数值运算结果不同）：服务器模式不能按现方案上线，升级为架构问题单独评审。
- 标准 4 对某个大版本不过：支持的版本区间收窄到通过的那些，写进文档。

### 何时做、挡什么

P2 做双后端对拍时，作为对拍测试的一部分，之后长期保留在 CI 里。挡 P5 上线。实验 1 不通过（本机也用原生 PostgreSQL）时，本实验只剩跨版本部分。

## 实验 6：桌面打包

### 要回答的问题

本机模式第一版用什么形态安装：只发 npm 包，还是能提供不要求用户先装 Node 的独立安装包；以及实验 1 不通过时，随 saveslot 打包原生 PostgreSQL 是否可行。

### 做法

**6a：PGlite 路线**

- 测：从启动 saveslot 服务进程到能回答第一条查询的时间（空数据目录、10 万行数据目录各测 50 次）；闲置内存；跑完评测任务后的内存；安装包大小。
- 把 Node 运行时、saveslot、PGlite 打成单个可执行文件，在 macOS（两种芯片）和 Linux 上各试一次，记录是否能跑、包多大、macOS 上签名与公证是否通过。

**6b：原生 PostgreSQL 路线**

- 把 PostgreSQL 二进制随 saveslot 打包，由 saveslot 管理它的启动与停止，经 unix socket 连接。
- macOS：开启强化运行时并签名后提交公证，看是否通过；从应用目录启动是否需要管理员权限。
- 生命周期：强杀 saveslot 进程 50 次，检查有没有残留的数据库进程、残留的锁文件，下次启动能否自动恢复。
- 测：安装包大小、冷启动时间、闲置内存。
- Windows：本机模式第一版不支持 Windows，只做一次可行性摸底（无管理员权限能否运行、是否被安全软件拦截），结果只作记录。

### 通过标准

这项实验的产出是一个决定，标准用来判定每条路线"可用"与否：

| # | 标准 | 路线 |
|---|---|---|
| 1 | 冷启动到可用 p95 ≤ 1.5 s（空目录）、≤ 3 s（10 万行）（拍的） | 6a |
| 2 | 闲置内存 ≤ 300 MB（拍的） | 6a |
| 3 | 单个可执行文件在 macOS 两种芯片与 Linux 上都能运行，macOS 公证通过 | 6a |
| 4 | macOS 公证通过，启动不需要管理员权限 | 6b |
| 5 | 强杀 50 次后残留进程数为 0，每次都能自动恢复 | 6b |
| 6 | 安装包 ≤ 150 MB、冷启动 p95 ≤ 3 s（拍的） | 6b |

### 不通过时的决定

- 6a 的标准 1、2 不过：记录实际值，评估是否影响 `saveslot mcp` 按需拉起服务的体验；不单独构成换后端的理由。
- 6a 的标准 3 不过：第一版只发 npm 包，安装前提写明需要 Node（`06-cli.md` 现在就是这样写的）。
- 6b 不过，而实验 1 也不通过：本机模式没有可用的后端，这是第一版的阻断问题，立即升级。备选是要求用户自己安装 PostgreSQL，体验上是明显的退步。

### 何时做、挡什么

与 P1–P3 并行，宜由另一个人做。挡 P6 的安装方式。**实验 1 不通过时，6b 立即变成关键路径，要在 P1 的 `store` 开工前出结论。**

## 实验 7（新增）：物理删除后的明文残留

### 为什么新增

内核不变量 K11 的测试要求：隐私删除到期后，在整个存储里用被删原文检索不到。架构里 `purgeResidue` 对 PostgreSQL 写的是"VACUUM、对受影响的表 ANALYZE、checkpoint"，对 PGlite 写的是"待实验"；范围文档说"按实验 1 / 2 的结论定做法"，但实验 1、2 的定义里都没有这一项（架构审查 P1-9）。另外，PostgreSQL 那一套做法是否足够也没有被验证过，所以两个后端一起测。

### 要回答的问题

物理删除一段内容之后，要做哪些清理动作，才能让被删的原文在数据目录的任何文件里都搜不到。

### 做法

**标记串**

- 每轮生成若干个各不相同的标记串：固定前缀加 32 个随机字符。随机内容不可压缩，这一点是必要的，见下面"阳性对照"。
- 把标记串写进明文残留清单（`03-data-model/03-deletion.md`「删除之后」）里数据库层面的每一类位置：
  - 内容表里的短文本值；
  - 内容表里的长文本值（大于 8 KB，会被数据库移到行外存储）；
  - 业务表的普通列、带索引的列；
  - 作为某列的高频值（重复写入几百行，让它进入统计信息）；
  - 派生表的分组键；
  - 全文索引或子串索引（第一版搜索是子串匹配，若建了相应索引则包括）；
  - 一个长事务里写入后回滚的值（只存在于预写日志里）。

**阳性对照（必须先做）**

写入后、删除前，关闭数据库，在数据目录里按字节搜每个标记串。**每一类位置都必须至少命中一次。** 哪一类搜不到，说明这种搜索方式看不见那一类位置（典型原因是数据被压缩存放），这时"删除后搜不到"没有任何意义。遇到这种情况要先解决可见性：关掉该列的压缩再测，或改用能解压的检查方式，并把"线上是否压缩"作为结论的一部分写清。

**删除与清理**

按 saveslot 物理删除的实际做法删掉这些值（删除内容行，业务行更新或删除），然后分别试下面的清理做法，每种做法单独一个数据目录：

| 候选 | 做法 | 要观察的 |
|---|---|---|
| A | `VACUUM`（普通）受影响的表 + `ANALYZE` + 两次 `CHECKPOINT` | 页内被回收的 slot 里是否还留着旧字节（未核实：普通清理是否清零回收的 slot） |
| B | 重写受影响的表（`VACUUM FULL` 或等价的重建）+ `ANALYZE` + 两次 `CHECKPOINT` | 旧文件被删除后，新文件里应当没有旧字节 |
| C | 在 A 或 B 之上处理预写日志：强制切换日志段、检查点、关闭日志段复用并开启新段清零（`wal_recycle`、`wal_init_zero` 一类参数；PGlite 是否支持调这些参数：未核实） | 被复用的旧日志段里是否还留着旧内容（未核实：复用的日志段在被覆盖前是否保留原内容） |
| D | 不原地清理：把日志（已去掉被删内容）重放进一个全新的数据目录，校验后替换旧目录并删除旧目录 | 新目录从未写入过被删内容，理论上必然干净；测耗时 |

PGlite 以单用户模式运行，`VACUUM`、`VACUUM FULL`、`CHECKPOINT` 是否都能正常执行：未核实，是实验的第一步。

每种做法做完后关闭数据库，在数据目录的**全部文件**里按字节搜每个标记串，包括表文件、索引文件、预写日志目录、统计信息文件、空闲空间映射、临时文件目录。

**轮数与变体**

- 每种候选 20 轮（拍的），每轮用新的标记串，同一个数据目录连续使用。
- 崩溃变体：在"墓碑事务已提交、清理未完成"的时刻强杀，重开后重跑清理，再搜。清理必须是可重做的。
- 两个后端各做一遍。PostgreSQL 上候选 A 就是架构现在写的做法。

**不在范围内的**

文件被删除后留在文件系统空闲块或固态硬盘上的旧数据，属于文件系统与硬件层面，saveslot 不处理，删除回执应当如实说明。本实验只搜数据目录里现存的文件。

### 通过标准

| # | 标准 |
|---|---|
| 1 | 阳性对照成立：删除前每一类位置都能搜到对应的标记串 |
| 2 | 至少有一种候选，在 20 轮里对每一类位置的命中数都是 0 |
| 3 | 该候选在崩溃变体下重做后命中数仍为 0 |
| 4 | 该候选的耗时可接受：10 万行的租户上，单次清理 ≤ 5 s（原地清理）或 ≤ 60 s（重建目录）（拍的） |
| 5 | 两个后端各自都有满足 1–4 的候选（可以不是同一种） |

### 不通过时的决定

- 原地清理的候选（A、B、C）都不满足标准 2：采用候选 D，到期物理删除时重建数据目录。代价是清理时间与日志长度成正比，期间这个租户不可写；P3 的工作量相应增加，估 1–2 人周（拍的）。它同时就是架构审查 P1-13 建议补上的"向空租户重放导出文件"的能力，两件事可以合并做。
- 候选 D 的耗时也不满足标准 4：放宽标准 4，把清理改成后台执行并在删除回执里写明"物理清除在某时刻前完成"；不允许降低标准 2。
- PostgreSQL 上候选 A 不满足标准 2：架构 §8 里 `purgeResidue` 的做法要改成通过的那一种。

### 连带要定的

架构审查 P1-9 指出，墓碑事务提交与清理完成之间崩溃后，没有地方记录"清理做没做"。本实验确认清理可重做之后，建议在本地运行状态里加一项"残留清理的进度"，丢了就对全部墓碑重做一遍。这属于工作包 W4。

### 何时做、挡什么

P3 之前。挡 P3 的 `purgeResidue` 实现。实验 1 不通过时只做 PostgreSQL 一侧。

## 实验 8（新增）：单写者锁

### 为什么新增

架构要求一个租户的存储同一时间只被一个进程写，PGlite 上的做法写的是"锁文件写入随机 token 与启动时间，用 `flock`，不靠 pid"（`02-architecture.md` §7）。已知 PGlite 自己没有数据目录锁，两个进程同时打开会把目录写坏（`research/05` §1.3）。而 Node 的标准库是否提供 `flock`：未核实，印象中不提供，需要原生扩展或别的办法。"两个进程同开一个目录必须报错"是第一版就要通过的检查（架构 §13 保证点 2），它依赖的平台能力没有被验证过。

### 要回答的问题

在 Node（及打算支持的 Bun）上，用什么办法能拿到一把"进程死掉就自动释放"的数据目录锁。

### 做法

候选：

| 候选 | 说明 |
|---|---|
| A | 经原生扩展调用操作系统的 `flock` 或 `fcntl` 文件锁 |
| B | 独占创建锁文件，加心跳与过期判断 |
| C | 本机服务本来就要监听一个 unix socket；用"能否成功绑定并监听"作为锁 |

对每个候选：

- 竞争测试：同时启动 10 个进程抢同一个数据目录，重复 100 次，共 1,000 次打开尝试。
- 强杀测试：持有者被 `SIGKILL` 后，另一个进程尝试打开，重复 100 次，记录多久能成功。
- 挂起测试：持有者被暂停（`SIGSTOP`）30 秒再恢复，期间另一个进程尝试打开。考察持有者恢复后会不会在已经失去锁的情况下继续写。架构的所有权编号（epoch）就是为这种情形兜底的，一起验证。
- macOS 与 Linux 各做一遍。

### 通过标准

| # | 标准 |
|---|---|
| 1 | 每次竞争恰好一个进程成功，其余明确报错；1,000 次里没有一次出现两个进程同时认为自己持有锁 |
| 2 | 持有者被强杀后，下一个进程在 1 s 内（拍的）成功打开，不需要人工删除任何文件 |
| 3 | 挂起测试里，旧持有者恢复后的第一个写事务被所有权编号的核对拦下，没有写入任何数据 |
| 4 | 不引入需要用户机器上有编译工具的安装步骤（原生扩展必须有预编译包） |

### 不通过时的决定

没有候选满足标准 1、2：修订架构 §7 的加锁方式，例如把锁做进数据库里，或要求本机模式必须经常驻服务访问并由服务进程的唯一性来保证。这是架构修订，不是换后端。

### 何时做、挡什么

与实验 1 一起，1–2 个工作日。挡 P1 的 `store`。实验 1 不通过（换原生 PostgreSQL）时，原生 PostgreSQL 自带数据目录锁，本实验缩减为验证 saveslot 对子进程的管理不会绕过它。

## 设定

- **部署**：云服务（PostgreSQL），单节点。租户闲置时连接关闭，下次访问再打开（DRAFT「已定的技术选型」）。
- **主体**：
  - 用户 `U`。
  - Agent A = `MacBook · Claude Code`（远程 MCP，一次 OAuth 授权），scope `saveslot.read saveslot.write saveslot.schema`。
  - Agent B = `云端 · 投放助手`（每天定时跑投放任务的云端 Agent，每次任务自报 `task`：T1、T2……），scope `saveslot.read saveslot.write`。
- **slot** `marketing`，时区 `Asia/Shanghai`。表 `budgets`：状态类，`granularity: date`，`entity_key: category`；字段 `category`（text）与 `amount`（quantity，CNY）。
- **记号**同推演 1。状态类表的段记作 `g1…`；区间一律左闭右开 `[a, b)`；`v@#n` = 最近一次业务写入是 `#n` 的实体版本标记。
- **时间轴总览**（`推广` 这个实体的生效段）：

| 记录时刻 | 生效段（业务时间） |
|---|---|
| 10-01 之后 | `[10-01, ∞) 5000` |
| 10-20 之后 | `[10-01, 11-10) 5000` · `[11-10, ∞) 4000` |
| 11-08 10:00 之后（第 2 步） | `[10-01, 11-02) 5000` · `[11-02, 11-10) 3000` · `[11-10, ∞) 4000` |
| 11-08 10:20 之后（第 2b 步，B 写入） | `… [11-02, 11-10) 3000` · `[11-10, 11-20) 4000` · `[11-20, ∞) 3500` |
| 11-08 10:35 之后（第 2b 步，A 重写） | `[10-01, 11-02) 5000` · `[11-02, 11-20) 3000` · `[11-20, ∞) 3500` |
| 11-08 15:00 之后（第 2c 步，A 写入） | `… [11-20, 12-01) 3500` · `[12-01, ∞) 6000` |
| 11-09 09:10 之后（第 2c 步，采纳候选） | `… [11-20, 11-25) 3500` · `[11-25, 12-01) 3200` · `[12-01, ∞) 6000` |
| 11-09 11:00 之后（第 4 步，回退） | `[10-01, 11-02) 5000` · `[11-02, 11-10) 5000` · `[11-10, 11-20) 4000` · `[11-20, 11-25) 3500` · `[11-25, 12-01) 3200` · `[12-01, ∞) 6000` |

## 第 0 步：建 slot 与已有数据（10-01、10-20，A）

  "time": { "type": "state", "granularity": "date" }, "entity_key": "category",
  "fields": [

- `quantity` 用 `CNY` 作单位：data-model 规定"同量纲自动换算"，但货币之间没有固定换算系数，单位词表（倾向 UCUM）里也没有货币 → Q35。

## 第 1 步：投放任务按业务时间读（11-05 至 11-07，B）

| 做了什么 | 调用 | (a) | (b) | (c) | 回执 / 之后读到 |
|---|---|---|---|---|---|
| 11-05 09:00 T1"排 11-05 的投放" | `saveslot_query budgets where category=推广 valid_at=2026-11-05`，`task: T1` | — | — | `rd_1`：`e_p@#14`，业务时间条件 `valid_at 11-05` | `推广 · 5000 CNY` |
| 11-06 09:00 T2"今天的投放" | `saveslot_query budgets where category=推广`（不传时间），`task: T2` | — | — | `rd_2`：`e_p@#14`，业务时间条件 = ？ | `5000 CNY`。不传时间的读取，业务时间条件应记为"入口时刻所在的那天（11-06）"；read_log 的字段说明只说"不记会多报"，没说默认怎么记 → Q36 |
| 11-07 09:00 T3"排 11 月计划" | `saveslot_query … valid_during=[2026-11-01, 2026-12-01)`，`task: T3` | — | — | `rd_3`：`e_p@#14`，`valid_during [11-01, 12-01)` | `10-01 → 11-10 5000` · `11-10 → （延续）4000` |

云服务：三次读取之间租户都因闲置被关掉过。read_log 在进程内缓冲，"每 N 秒落盘"；**闲置关闭、滚动部署、路由迁走时要不要先落盘**没写，否则最多丢 N 秒的读取，第 2 步的影响查询就会漏掉 → Q37。

## 第 2 步："从 11-02 起改成 3000"（11-08 10:00，A）

```json
{ "tool": "saveslot_write", "sv": 1, "task": "a-s2",
  "evidence": [{ "kind": "user_message", "text": "推广预算从 11-02 起改成 3000" }],
  "ops": [{ "intent": "update", "table": "budgets", "entity_key": { "category": "推广" }, "ver": "v@#14",
            "valid_from": "2026-11-02", "set": { "amount": { "value": "3000", "unit": "CNY" } } }] }
```

| 做了什么 | 调用 | (a) | (b) | (c) | 回执 / 之后读到 |
|---|---|---|---|---|---|
| 读 | `saveslot_query … category=推广` | — | — | `rd_4`（A，当天 11-08） | `5000 CNY ver=v@#14` |
| 写 | 上 | #17 `s_R3` #18 头（起点 11-02；终点由 `next_change` 解析为 **11-10**，写成具体值；起点 < 现在 → 判为"早就变了但晚知道"）#19 g1 → `[10-01, 11-02)` #20 g3 `[11-02, 11-10) 3000` | 三段；纠错影响结果 | `possibly_affected` | 见下 |

```
已保存 · marketing schema v1 · #18
budgets 推广 变更：11-02 → 11-10 改为 3000 CNY（原 5000）
注意：11-10 起仍是 4000 CNY，未改动
之前有 3 次读取用到的业务时间落在 11-02 → 11-10 内（saveslot_history 可查看）
```

- **默认"管到下一个变化"**：按文档走通，回执的提醒正是设计要的效果。
- **影响查询**：被改区间 `[11-02, 11-10)`，命中 `rd_1`（11-05）、`rd_2`（11-06）、`rd_3`（区间重叠），以及 A 自己刚才的 `rd_4`（→ Q13）。
- **措辞**："早就变了但晚知道"是 saveslot 按起点自动判断的。但预算往往是**今天做的决定、往回追溯生效**——T1 在 11-05 按 5000 排投放，当时并没有错。
  B 下次读到的提示是"⚠ 你曾读到的值已被纠正"，这把追溯调整说成了纠错 → Q32。
- **同一天的边界**（不在本场景里，推演时发现）：`granularity: date` 时，"起点 = 今天"算"从现在起变"，不触发影响查询；
  但今天早些时候按今天读过的值（如 B 08:30 读的"今天 5000"）对今天这个业务日已经不对了 → Q33。
- **删除探针**（不作为步骤）：假如之后隐私删除 `s_R3`，g3 只来自它，删除；但 g1 的终点 11-02 也来自 `s_R3`。
  删除后 `[11-02, 11-10)` 是变成空洞，还是恢复 5000？data-model 的级联只讲字段级来源，**区间的端点不是字段，来源没记**；`apply` 又"不重跑拆行" → Q26。

## 第 2b 步：覆盖已有事实 → 待确认 → 被别人的写入取代（11-08 10:05–10:35）

用户紧接着对 A 说："不对，是从 11-02 起**一直** 3000。"

| 做了什么 | 调用 | (a) | (b) | (c) | 回执 / 之后读到 |
|---|---|---|---|---|---|
| 10:05 A 写 `open` | `saveslot_write update … valid_from 11-02 valid_to "open" amount=3000 ver=v@#18` | #21 `s_R4` #22 头（终点 `open`，覆盖 g2 → 高影响）#23 事项 `pi_1` awaiting_confirmation（提议内容、将被覆盖的段，都是内容） | `awaiting` 标记；值不变 | — | `已记下，未生效`："将覆盖 11-10 起的 4000 CNY；待确认 pi_1"。A 本该去问用户 |
| 10:20 B 任务 T5 读 | `saveslot_query … category=推广`，`task: T5` | — | — | `rd_5` | `3000 CNY ver=v@#18 ⚠ 有待确认的改动（pi_1）：提议 11-10 起也改为 3000`。按文档"给出的是当前值"，正确 |
| 10:20 B 按财务系统的结果写入 | `saveslot_write update … valid_from 11-20 amount=3500 ver=v@#18`，证据 `tool_result`"财务系统：11-20 起推广预算 3500" | #24 `s_R5` #25 头（终点解析为 `open`，不覆盖已有段 → 不是高影响）#26 g2 → `[11-10, 11-20)` #27 g4 `[11-20, ∞) 3500` #28 `pi_1` 被取代 | 四段；`awaiting` 清除 | — | `已保存`；`superseded: [pi_1]`——它改到了 `pi_1` 要覆盖的段 |
| 10:30 A 确认 | `saveslot_resolve pi_1 confirm` | — | — | — | `handle_mismatch`："pi_1 已被取代：#25 云端 · 投放助手 写入 11-20 起 3500"。按文档走通 |
| 10:31 A 重读 | `saveslot_query … valid_during=[11-01, 12-31)` | — | — | `rd_6` | 四段，`ver=v@#25` |
| 用户："那就到 11-20 为止，之后按财务的来" | `saveslot_write update … valid_from 11-02 valid_to 2026-11-20 amount=3000 ver=v@#25` | #29 `s_R6` #30 头 #31 g3 移除 #32 g2 移除 #33 g5 `[11-02, 11-20) 3000` | 三段 | — | `已保存`；"覆盖：11-10 → 11-20 原 4000" |

检查点：
- **高影响的判据不一致**：`valid_to: open` 覆盖已有段属高影响、要确认；但**显式给终点同样能整段覆盖**已有的 `[11-10, 11-20) 4000`，抹掉 11-10 这个已记录的变化点，却不算高影响。
  data-model 的原则是"覆盖已有事实须显式传参"，`open` 本身也是显式传的 → Q28。
- **"到 11-20 为止"是含 11-20 还是不含**：`valid_to` 按 `[a, b)` 不含终点。这里用户的意思恰好是"11-20 起按财务的"，所以 `valid_to = 11-20` 是对的；
  但用户说"到 11-20（含）"时，Agent 得自己换成 11-21。`saveslot_write` 的参数表里没写终点开闭，回执也没有"至 11-19（含）"这类人话 → Q34。
- **用同样的值覆盖**：`[11-02, 11-10)` 原来就是 3000（来源 `s_R3`），这次写入覆盖之后，它的来源变成了 `s_R6`。
  文档没规定"覆盖成同样的值"要不要产生新版本、换来源；这会影响删除（之后删 `s_R3` 就碰不到当前状态了）和影响查询（值没变的部分不该算受影响）→ Q30。
- **影响查询**：值实际变化的区间是 `[11-10, 11-20)`，命中 `rd_3`。若按"写入覆盖的区间" `[11-02, 11-20)` 算，`rd_1`、`rd_2`、`rd_5` 会被再报一次 → Q31。

## 第 2c 步：两个 Agent 改同一实体、业务时间不重叠（11-08 14:59–11-09 09:10）

| 做了什么 | 调用 | (a) | (b) | (c) | 回执 / 之后读到 |
|---|---|---|---|---|---|
| 14:59 B 任务 T6 读 | `saveslot_query … category=推广`，`task: T6` | — | — | `rd_7` | `ver=v@#30` |
| 15:00 用户对 A："12 月起 6000" | `saveslot_write update … valid_from 12-01 amount=6000 ver=v@#30` | #34 `s_R7` #35 头（终点 `open`）#36 g4 → `[11-20, 12-01)` #37 g6 `[12-01, ∞) 6000` | 四段 | — | `已保存`；`ver=v@#35` |
| 15:01 B 按财务结果写入（`ver` 已过期） | `saveslot_write update … valid_from 11-25 amount=3200 ver=v@#30`，证据 `tool_result` | #38 `s_R8` #39 头（终点按当前状态解析为 12-01）#40 事项 `pi_2` conflict（候选：`[11-25, 12-01) 3200`）| `disputed`；值不变 | — | `已记下，未生效`：冲突 `pi_2` |

**这是假冲突**：A 改的是 `[12-01, ∞)`，B 改的是 `[11-25, 12-01)`，业务时间上不重叠。但文档的合并判据只看**字段**（两边都改 `amount`），
`ver` 又是**按实体**给的，所以状态类表上任何两次并发写入都会判成冲突。B 是没人值守的定时任务，这个冲突只能等下一个会话的人来处理 → Q24。

| 做了什么 | 调用 | (a) | (b) | (c) | 回执 / 之后读到 |
|---|---|---|---|---|---|
| 11-09 09:00 A 新会话读 | `saveslot_query …` | — | — | `rd_8` | `⚠ 有争议（pi_2）`：投放助手提议 11-25 → 12-01 改为 3200 |
| 用户："按 3200" | `saveslot_resolve pi_2 take_candidate` | #41 事项解决（确认记录）#42 头（来源：候选写入 `s_R8`；`saveslot_resolve` 自身的来源 → Q10）#43 g4 → `[11-20, 11-25)` #44 g7 `[11-25, 12-01) 3200` | 五段；`disputed` 清除 | — | `已处理`；`ver=v@#42` |

- `take_candidate` 用的是候选写入时**解析好的区间** `[11-25, 12-01)`。如果候选挂起期间该实体又被别人写过（比如加了 11-28 的变化），按旧区间执行就会悄悄覆盖它。
  文档有"目标被后续写入改过则事项被取代"，但没说状态类表上"改过"指整个实体，还是只算与候选区间重叠的写入 → Q29。

## 第 3 步：审计——"T1 当时看到的 11-05 预算"（11-09 10:00，A）

用户："11-05 那次投放是按多少预算排的？现在呢？"

| 做了什么 | 调用 | (a) | (b) | (c) | 回执 / 之后读到 |
|---|---|---|---|---|---|
| 找 T1 那次读取 | ？ | — | — | — | **MCP 里没有从"任务 / 读取"查到记录时刻的路径**：`as_of` 只接受 `seq` 或时刻；读取审计 `GET /v1/reads` 只给用户会话、不在 MCP。A 只能猜"11-05 早上" → Q27 |
| 看时间线 | `saveslot_history budgets entity_key=推广 mode=timeline` | — | — | — | 各版本（#11、#14、#18、#25、#30、#35、#42）；"受影响：rd_1（云端 · 投放助手 · T1）…"——interface 例子里有这一行，但没说列不列读取的时刻与 task |
| 两轴还原 | `saveslot_history … mode=as_of as_of=2026-11-05T09:00+08:00 valid_at=2026-11-05` | — | — | — | `5000 CNY（当时的版本 #14）`；该业务日期现为 3000（#30 起）。按版本表核对：记录时刻 ≤ #16 时 g1 = `[10-01, 11-10) 5000` → 正确 |

| 11-09 10:10 B 任务 T7 | `saveslot_history budgets entity_key=推广 mode=changes since=my_last_read` | — | — | — | 自 `rd_7` 之后：#35 12-01 起 6000；#42 11-25 起 3200（采纳投放助手的候选）。变化告知走通 |

两轴结果本身算得对，A 最后答得出"当时 5000、现在 3000"。缺的是**精确定位"那次任务"**：如果 T1 是 11-05 23:59 跑的，而 10-20 到 11-08 之间又有别的写入，猜一个时刻就可能答错。

## 第 4 步：回退（11-09 11:00，A）

用户："11-02 那次调整撤回，11-02 到 11-20 恢复成原来的计划。"——"原来的计划" = #16 之后的状态：`[11-02, 11-10) 5000`、`[11-10, 11-20) 4000`。11-20 之后（3500 / 3200 / 6000）不动。

```json
{ "tool": "saveslot_write", "sv": 1, "task": "a-s4",
  "evidence": [{ "kind": "user_message", "text": "11-02 那次调整撤回，11-02 到 11-20 恢复成原来的计划" }],
  "ops": [{ "intent": "update", "table": "budgets", "entity_key": { "category": "推广" }, "ver": "v@#42",
            "revert": { "to": 16, "fields": ["amount"] }, "valid_from": "2026-11-02", "valid_to": "2026-11-20" }] }
```

| 做了什么 | 调用 | (a) | (b) | (c) | 回执 / 之后读到 |
|---|---|---|---|---|---|
| 找目标版本 | `saveslot_history … mode=timeline` | — | — | — | 找到 #14 / #16（10-20 那次） |
| 回退 | 上 | #45 `s_R9` #46 头（回退到 #16，区间 `[11-02, 11-20)`）#47 g5 移除 #48 g8 `[11-02, 11-10) 5000` #49 g9 `[11-10, 11-20) 4000` | 六段（两个相邻的 5000 段不合并，各自保留来源） | `possibly_affected` | 见下 |

检查点：
- **状态类表上的回退没有定义**：interface 的 `revert` 是"取该版本这些字段的值写入"，按的是**行**的思路。状态类实体在 #16 时，这个区间里有**两个不同的值**；
  `revert` 能不能和 `valid_from` / `valid_to` 一起用、一个操作能不能产出多段，都没写。不限区间的话，就会把 11-20 之后投放助手与用户写的值一起回掉，违反"不会把之后别的来源写入的一起回掉" → Q25。
- **回退值的来源**：data-model 说回退的来源"是这次回退请求本身"。但 g9 的 4000 实际来自 `s_R2`。之后若隐私删除 `s_R2`，g9 不在级联里，被删的内容（"11-10 起降到 4000"）以值的形式留在当前状态里——与 Q2 同类 → Q25。
- **"撤回"不是 `revoke`**：若 Agent 把"撤回"理解成 `saveslot_write revoke valid_from 11-02 valid_to 11-20`，结果是这段**没有值**（空洞），11-05 读不到任何预算。工具描述没区分 → Q38。
- **影响查询**：起点 11-02 < 现在，判为"晚知道"，命中 `rd_5`（11-08 = 3000）、`rd_9`（11-05 = 3000），这两条正确。
  `rd_1`（T1 读到 5000）在第 2 步被标了 `possibly_affected`，现在值又恢复成 5000，标记却不会撤掉，T1 那边会一直看到"你曾读到的值已被纠正"→ Q31。

## 场景结论

**换一个会话**：保得住、说得清。每个读取都带着有没有待确认、有没有争议；"管到下一个变化"的提醒、被覆盖段的列表、被取代的事项，都在下一个会话里看得到。

**换一个 Agent**：**大体能做到，有两处会出错**。
- 无人值守的 B 写入后，A 能看到并处理。
- 状态类表上的并发写入几乎一定被判成冲突（Q24）。
- 回退的语义没定义（Q25），Agent 推不下去，误用 `revoke` 还会留下空洞（Q38）。

**导出重放之后**（本场景没有实际导出，按日志逐项推）：
- **当前状态与历史**：保得住、算得对。所有拆段都记了解析后的具体起止；待确认、被取代、采纳候选都是事件；两轴按时刻读只靠版本表，版本表由 (a) 重建。
- **"那次任务当时看到的"**：导出后答不出来。read_log 不随行，导出后只能按时刻猜——这是 (c) 类的设计代价，但现在连导出前都没有 MCP 路径（Q27）。

**只靠文档能不能推下去**：第 2b 步（显式终点算不算高影响）、第 2c 步（区间不重叠算不算冲突）、第 3 步（从任务定位读取）、第 4 步（状态类表回退）需要自己补规则才能往下走。

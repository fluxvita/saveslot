## 结论

- **现有设计的方向全部站得住，没有一项被推翻**；6 份调研给出的是实现层的具体做法，以及若干必须修正的细节。
- **几乎没有能直接当组件用的现成系统**：immudb（BSL 许可、装不进 PG）、XTDB（JVM、无 schema）、pg_ivm（不支持窗口函数）、
  pgroll（表达不了从日志重建）、Electric / PowerSync / Zero（服务端固定为权威）都只能借思路。saveslot 的核心要自己写，但每一块都有成熟机制可照搬。
- **存储引擎定为 PostgreSQL**：本地嵌入 PGlite（PostgreSQL 18.6），自托管与托管用原生 PostgreSQL。SQLite / DuckDB 缺区间类型、
  防重叠约束、角色、精确小数，双引擎会让派生结果在两边不一致。
- **有一个连带的大决定**：PGlite 跑在 JS 运行时里，saveslot 内核若要嵌入它，基本只能用 TypeScript（Node / Bun）。03 也建议哈希计算放在 TS 应用层。
- **有两处安全细节必须改**：链上和读日志里不能放可被猜测的内容哈希；只销毁密钥不算删除。

## 各方向的结论

### 存储引擎与多租户（05）

- 本地：PGlite 嵌在 saveslot 进程里（降级路线：打包原生 PostgreSQL 子进程，单平台 109–337MB）。自托管、托管：原生 PostgreSQL。
- **PGlite 实测的四个问题**：默认关闭 fsync；`statement_timeout` 不生效；低权限用户能用 `SET ROLE` 提回超级用户（不能当安全边界）；
  多进程同时打开同一数据目录会写坏（无锁）。对策：saveslot 进程独占数据目录（自加 pid 锁）、受限 SQL 放独立 Worker 超时即杀、持久性靠实验确认。
- **受限 SQL 的主防线在 saveslot 自己这一层**：用 libpg_query（PostgreSQL 自己的解析器）解析成语法树，按语句、节点、函数白名单校验；
  原生 PostgreSQL 上再叠只读角色、只读事务、超时作为第二道防线。
- **托管租户模型**：每用户一个 schema，按 cell 分片，每个 cell 限制用户数（上限由实验定）。共享表 + 行级权限不适合用户自定义 schema。
- **导出格式 = saveslot 日志 + schema 定义**，物理快照只用来加速。

### 防篡改与删除（03）

- **链结构**：每个租户一条只追加日志，叶子组成 RFC 6962 Merkle 树，每个事件再带 `prev_hash`；按 C2SP 格式定期生成签名检查点，
  客户端缓存上次的检查点、下次要求一致性证明（防止运营方对不同用户展示不同历史）。全部用 TS 自己实现，标准与测试向量是 Apache 生态。
- **叶子只放事件头和内容承诺，不放明文**：密文的 SHA-256，可选再加一个随数据密钥销毁的 HMAC；change_log 的前后整行同样加密、放在链外。
- **密钥层级**：根密钥（本地放系统钥匙串，托管用 KMS）→ 每个 thread 一把 → 每条数据一把。删一条 = 删它的数据密钥；删整个 thread = 删 thread 密钥。
- **删除 = 物理删除 + 销毁密钥**：欧洲数据保护委员会 2026-07 的指南认为密文仍是个人数据，销毁密钥只用来兜底改不到的备份和离线副本。
  删除标记永不过期（Kafka 默认 24 小时后清掉删除标记，是反例）。
- **最大风险在链外的明文**：写入请求里的证据片段、embedding、全文索引、数据库 WAL、应用日志、模型调用缓存。
  存密钥的表如果和数据一起进了长期备份，销毁密钥就失效。

### 时态数据（01）

- **PostgreSQL 18 已有 `WITHOUT OVERLAPS` 约束**（PGlite 18.6 可用），但"改写某一段时间"的语法（`FOR PORTION OF`）在 PostgreSQL 19 Beta 被撤回，
  回溯修改时按时间段拆行要 saveslot 自己写。
- **记录时间用 change_log 的序号**，不用系统时钟（事务开始时间与提交顺序不一致）；每用户写入串行化，序号即提交顺序。
- **三种表的存储**：无时间表只有记录时间；事件表把发生时刻（加时区）当普通列；状态表一行是一个实体在一段生效区间里的值，
  区间不重叠由约束保证。每张基础表都配一张由 change_log 维护的版本表。
- **回溯修改**：一条逻辑写入在一个事务里完成拆行，每个受影响的区间段各记一条 change_log，再记一条逻辑写入头；重放用记下的结果，不重跑拆行算法。
- **派生规则声明时间依赖**：无关时间 / 按业务时间分桶（周、月，可缓存，只重算受影响的桶）/ 依赖"今天"（必须显式传入时刻）。

### 派生刷新与来源追踪（02）

- **首版按受影响的分组重算，不用 IVM 引擎**：PGlite 上 100 万行实测，整用户重算约 290 ms，只重算受影响的一周约 1.7 ms，pg_ivm 约 0.3 ms，
  都能放进同一事务。分组重算 SQL 写法不受限制，saveslot 也能自己记派生写日志。pg_ivm 只留作个别热点规则的加速器。
- **规则分析器给每条规则算出"重算范围"**：分组聚合按分组、有界窗口按受影响的帧、无界窗口按整个分区、分析不出就按整用户。
  刷新 = 删掉受影响的键再按原规则重插；结果哈希没变就不往下游传（借鉴 Teable）。
- **来源追踪分三层**：规则编译时存静态的列级依赖；每次派生写入存一行分区级来源（规则版本、分区、日志位置）；
  行级来源不预先存，需要时在版本表上按日志位置重跑规则得出。预先存行级来源实测会让写入慢 4–7 倍；分区级已够删除级联和纠错影响查询用。
- **写入准入阈值**：执行前按"受影响分区行数之和"估算并拦截超限写入，执行中用超时兜底；天然拆不开的大改动走 schema 迁移的后台构建路径，
  保证"派生值永不落后"。
- **确定性边界**：固定会话时区和排序规则、函数白名单只放结果确定的函数、数值统一用 `numeric`；后台定期抽样对账"全量重算 vs 缓存"。

### schema 迁移（04）

- **用 saveslot 自己的日志实现，不用现成工具**：saveslot 不要新旧两版同时可写，数据量小，change_log 已是完整日志，所以不需要双写，也不需要追数据库日志。
- **新版本的表按版本号命名，建好后永不改名**；物理列名用字段 ID，改名只改目录。PostgreSQL 的视图绑定表的内部 ID 而非表名，交换表名的做法走不通。
- **切换**：一个事务里锁住"当前版本指针"这一行、追完最后一段日志、改指针；写入事务对这一行拿共享锁并核对版本，旧版本的写入在这里被拒；
  读不拿这把锁，完全不受影响。切换前要反复追平，直到剩余量低于阈值再切。
- **回滚**：切换前丢弃新表；切换后只做前向迁移。
- **托管的表数量是最大风险**：每用户、每张表、每个版本都建物理表，一万用户就到几十万张表；有报告 20 万张表时每个连接缓存达数 GB。托管布局要压测后定。

### 同步（06）

- **自己写一个轻量的 HTTP 日志同步协议**，传输层兼容 Durable Streams（MIT，草案 1.0），不引入完整的同步引擎。
- **标识**：事件的永久身份是 `(来源节点, 节点内序号)`，不用链哈希（主节点接受后会按自己的位置重新串链）；日志位置只由主节点分配；
  每次切换主节点 epoch 加 1，让旧主节点失效。
- **主节点处理离线写入**：源数据一律接收，只有命中删除标记才拒；对业务表的写入重新核对预期版本，对不上就降为候选版本或待确认，处理结果作为事件同步回原节点。
- **离线节点本地**：分"已确认层"和"暂定层"，暂定状态在读取结果里显式标出；重连时先拉取（至少拉到最新的删除标记）再推送。
- **切换主节点**是日志里的一条签名控制事件；导出 = 从位置 0 开始的一次完整下行同步。

**2026-11-09 讨论后的调整**（已写入 data-model.md）：
- 第 1–3 条：**加密不作为第一版必选项**。删除 = 物理删除；链上内容承诺改为加 salt 的哈希（salt 随内容删除），删除后无法被猜测比对；
  结构上为将来加密预留。将来加密也只加密源数据原文与 change_log 历史整行，业务表、派生表、版本表保持明文（要用 SQL 查）——
  不采纳 03"派生列也加密"的建议。
- "thread" 拆成 **slot**（权限、归属节点、复制、schema 版本、将来密钥的单位）与**事物的时间线**（一行的历史，不单独存储）。
- 主节点：有云端节点时默认云端为主。
- **托管定为每个用户独立存储**（不采用 05 推荐的"每用户一个 schema、共处一库"）：同一 PostgreSQL 集群里每用户一个 database，按集群分组，saveslot 自管连接——依据补充调研 [`07-per-user-storage.md`](07-per-user-storage.md)。
- 日志防篡改第一版只做串链 + 加 salt 承诺，Merkle 树与签名检查点托管上线时再做（不采用 03"首版即做"的建议）。

## 报告之间要对齐的一处

**删除标记拦截用什么哈希**：03 建议内容承诺的 HMAC 用每条数据自己的密钥（随删除销毁）；06 的删除标记拦截需要在删除之后，
仍能对重新上传的同一内容算出相同的哈希来比对——每条数据的密钥已经销毁，就做不到。要么拦截改用**用户级的密钥**（不随单条删除销毁，
但持有它的一方仍能对低熵内容做猜测），要么只按事件身份拦截（同一内容换个事件身份重新写入就拦不住）。需要在设计时取舍。

## 需要决定的问题

| 问题 | 背景 | 调研的倾向 |
|---|---|---|
| **内核语言** | PGlite 只能在 JS 运行时里嵌入 | TypeScript（Node / Bun） |
| **托管当主节点 vs 端到端加密** | 托管当主节点必须能解密才能派生；端到端加密则托管只见密文 | 三选一：托管持有密钥（服务端加密，需对用户说明）/ 按 thread 区分，留在本地的 thread 在托管只存密文 / 远期方案（尚不成熟） |
| **默认推荐谁当主节点** | 本地当主节点时电脑一关机，手机和云端 Agent 只能写暂定数据 | 默认推荐托管或私有服务器，本地作为高级选项（产品决策） |
| **"从 11-02 起改成 3000"管到哪** | saveslot 已记着"11-10 起改成 4000"时，3000 是管到 11-10 还是覆盖后面所有 | 默认"到下一个已知变化"，并在写入回执里列出会被覆盖的段，让 Agent 确认 |
| **托管的物理布局** | 每用户一组物理表 / 共享表按字段 ID 存 / 每用户一个库 | 压测后定 |
| **read_log 是否随日志复制** | 计划外切换主节点后，纠错影响查询需要旧主节点上的读取记录 | 未定 |
| **删除的法律口径** | 物理删除 + 销毁密钥是否构成法律意义上的删除 | 需法务确认 |

## 必做的实验（spike）

1. **PGlite 持久性**：强制结束进程或断电后能否恢复、已确认的提交丢多少；不达标则评估定期检查点 + 快照，或换成打包原生 PostgreSQL。
2. **PGlite 沙箱**：Worker 隔离 + 超时即杀的开销，反复终止后数据目录是否完整；用模糊测试检验语法树白名单能否挡住 `SET ROLE`、`COPY`、`DO` 等。
3. **每用户一个 database 的容量**（托管已定为每用户一个 database，见上文与 [`07-per-user-storage.md`](07-per-user-storage.md)；原先按"每用户一个 schema"写的做法作废）：同一 PostgreSQL 集群里放 2,000 个用户库，测崩溃恢复时间、冷请求延迟、闲置开销与 autovacuum 的冻结年龄，定出每组的上限。做法与通过标准见 [`../process/decisions/pre-dev-w0-experiments.md`](../process/decisions/pre-dev-w0-experiments.md) 实验 3。
4. **派生同事务刷新的延迟**：典型 schema（10 张基础表 + 20 条派生规则、10 万行）在 PGlite 和原生 PostgreSQL 上的单次写入延迟。
5. **本地 ↔ 托管重放一致性**：用 saveslot 日志双向重放，校验派生结果逐行一致（数值、时区、排序规则）。
6. **打包**：桌面应用里 PGlite 的冷启动与内存；打包原生 PostgreSQL 在 macOS 公证和 Windows 上的可行性。

## 0. 结论先行

1. **骨架与标准一致，没有需要推翻的地方。** 记录时间 = 事务时间、业务时间 = 有效时间、三种表 = TSQL2 的快照 / 事件 / 状态表、状态类表主键 = 顺序主键（sequenced primary key）、区间左闭右开、"起点 < 现在 = 追溯修改"、`as_of` / `valid_at` = 两个时间片算子，都与文献定义逐项对得上（§2）。
2. **saveslot 的写状态默认（`next_change`）在标准里没有对应物，是 saveslot 自己的语义。** Snodgrass 的 current update 是"从现在到永远、连未来的行一起改"，SQL:2011 不带 `FOR PORTION OF` 的 UPDATE 是"所有行都改"，XTDB 是"现在到永远"——三者都会抹掉已排好的未来变化。Snodgrass 自己在同一页写了"未来的行可能是计划好的调动、不该被影响，这时应改用区间更短的 sequenced update"，`next_change` 正是把这句话做成了默认。偏离站得住，但**因为没有标准可抄，它的边界情形必须由 saveslot 自己写全**——下面的 A1、A2 就是没写全的两处。
3. **理论给 saveslot 的主要收益是三样**：① 一条可执行的判据——**快照可还原性**（一次带显式区间的写入 = 对区间内每个业务时刻分别做一次普通更新），可直接做成参考求值器与性质测试（§6）；② 一条区分原则——**机械判定用"点视图"（只看每个时刻的值），来源与展示用"区间视图"（段不能随意拆合）**，它解释了"存储不合并、变化点按取值变化算"为什么自洽，也指出了哪里还没按这条原则写（A1、A2、A6）；③ 一组现成的术语与对外写法（retroactive / postactive modification、`FOR … AS OF / FROM … TO`）。
4. **影响事件格式或操作契约、开发前必须定的有 7 条**（§1.1，A1–A7）。最要紧的三条：
   - **A1 变化点按字段还是按整行**：多字段的状态类表上，只改 `amount` 的写入会不会被"11-10 换了负责人"挡住，文档没定；它决定逻辑写入头里"解析结果"是一个终点还是每字段一个。
   - **A2 空洞**：有值 ↔ 无值的边界算不算变化点、写入跨过空洞时填不填、只带部分字段的写入落进空洞怎么办，三问都没定；三种读法给出三种不同的终点（附录 A）。
   - **A3 `correct` 在状态类表上不传区间**：按现行默认是"从现在起改"，过去那段错值原样留着，之前读过它的读取也不会被标记——与"更正"的标准含义（改的是那个事实的整个有效期）相反。
5. **另有 4 条是契约上的小口子**（A4 `as_of` 落在一次写入的中间、A5 写入头没记判定用的"现在"、A6 日期与时刻参数混用、A7 `valid_during` 的返回形状），都是一两句话能定的，但定晚了要改接口。
6. **只影响内核规则、测试或文档的 7 条**（§1.2，B1–B7），其中两条建议尽早定：B1"同值写入不算变化点"导致结果**依赖写入顺序**；B2 影响查询用"起点 < 现在"当闸门，会漏掉"读过未来计划、计划后来改了"的读取，而现有的"日粒度起点 = 今天"特例正是同一个漏洞的局部补丁。
7. **不进实现、只用于表述的**：时态特化的完整分类（delayed retroactive 等十几种）、BCDM 的双时态时间粒子、时态范式（T3NF / TBCNF）、"SQL:2011 风格"这个说法本身（SQL:2011 其实没有业务时间的查询语法，`FOR VALID_TIME` 是 TSQL2 / XTDB 的写法）。

### 1.3 标准有、saveslot 没有采用，且不建议采用的

| 标准做法 | 为什么不采用 |
|---|---|
| 存储层强制合并相邻同值段（BCDM、TSQL2 要求关系是合并过的） | 会丢掉各段的来源；saveslot 的做法（存储按区间视图、判定按点视图）有文献支持（区间保持），见 §5.1 |
| SQL:2011 `UPDATE … FOR PORTION OF` 的"只改已有行"语义 | saveslot 的写入是"设这段的值"（有则改、无则建），更贴近 Agent 的说法；PostgreSQL 19 也没有这个语法（Beta 4 撤回，已核实），拆行本来就得自己写 |
| 时态特化的十几种细分（delayed retroactive、early predictive、bounded……） | saveslot 只需要"起点在现在之前 / 之后"一刀；其余只用于表述 |
| 事务时间用时间戳 | `seq` 比时间戳更贴合定义里"与事务串行化顺序一致"的要求，见 §2 |

## 2. saveslot 与标准双时态模型逐项对应（问题 1）

| saveslot | 标准里的对应物 | 一致吗 | 偏离是否站得住 |
|---|---|---|---|
| 记录时间（saveslot 何时记下，系统维护） | **事务时间**：事实在库里"当前"的那段时间；由系统生成、与事务串行化顺序一致、不能延伸到未来、过去不可改（共识术语表 §3.2） | 一致 | — |

## 4. 按时刻读与标准时态查询语义（问题 3）

**总体一致**：Snodgrass 把查询按两条轴各分 current / sequenced / nonsequenced，共九种，并指出"现在、按最新所知"（current / current）最常见。saveslot 的参数覆盖了其中用得上的几种：

| saveslot | 有效时间轴 | 事务时间轴 | 标准写法 |
|---|---|---|---|
| 不传 | current | current | 默认 |
| `valid_at: T` | 时间片 | current | 普通谓词（SQL:2011）/ `FOR VALID_TIME AS OF`（XTDB） |
| `valid_during: [a, b)` | 一段（返回与之相交的段） | current | `FOR VALID_TIME FROM a TO b`（XTDB，半开） |
| `history` `as_of: S` | 见 R3 | 时间片 | `FOR SYSTEM_TIME AS OF` |
| `as_of` + `valid_at` | 时间片 | 时间片 | 双时态时间片 |
| `history` `changes` | — | nonsequenced（"何时记下 / 何时被改"） | `FOR SYSTEM_TIME FROM … TO …` 或非顺序查询 |
| `timeline` | 全部 | 全部 | nonsequenced / nonsequenced |

**有歧义的情形**：

| # | 情形 | 例子 | 标准怎么做 | 建议 |
|---|---|---|---|---|
| R1 | `as_of` 的 `seq` 落在一次逻辑写入的中间 | 推演 2 第二步：#17 源数据、#18 写入头、#19 把 g1 裁成 `[10-01, 11-02)`、#20 插入 g3 `[11-02, 11-10) 3000`。`as_of: 19` 读到"11-02 起没有值"——这个状态从未提交过 | 事务时间在整个事务内固定（SQL:2011）；Datomic 的 `as-of` 以事务为单位 | A4：一次写入一个记录时刻 |
| R2 | `changes` 的 `since` / `until` 含不含端点 | `since: 57` 包不包括 #57 本身 | SQL:2011 两种都有：`FROM … TO` 半开、`BETWEEN … AND` 全闭——正因为容易混才分成两个写法 | A4：写死一种（建议 `since` 不含、`until` 含，与"自上次读取之后"一致） |
| R3 | `as_of` 不带 `valid_at` 读状态类实体 | 返回当时所知的全部段？还是"当时的现在"生效的那一段？还是"今天"生效的那一段？ | SQL:2011：应用时间没有默认过滤 → 全部段；XTDB：有效时间默认取**查询时**的现在，不是那个系统时刻 | A4：返回当时所知的全部段；"那次任务当时看到的"用已有的 `{read: "rd_…"}`（自带业务时间条件） |
| R4 | `valid_during` 返回的段截不截取 | 段 `[10-01, 11-10) 5000`，查 `[11-01, 12-01)`：`valid_from` 返回 10-01 还是 11-01？调用方拿"天数 × 日均"算 11 月额度时差一个月 | SQL:2011 `FOR SYSTEM_TIME FROM … TO` 返回原行；顺序查询的结果区间是交集；XTDB 两种都有（`FROM … TO` 返回存储值，加 `ONLY` 才截取，部分核实） | A7：默认不截取，给开关 |
| R5 | 受限 SQL 里把状态类表与事件类表连接 | `SELECT … FROM expenses e JOIN budgets b ON b.category = e.category`：默认只取 `budgets` 的当前段，10 月的支出配到了今天的预算，不报错 | 时态连接要在有效时间上求交；SQL:2011 里因为没有隐式过滤，写普通谓词即可；XTDB 用 `FOR ALL VALID_TIME` | B4 |
| R6 | "不传"的读取结果随时间流逝而变 | 11-09 读到 5000（`ver` v16）；11-10 已排好的 4000 生效；之后带 v16 的写入照常通过 | Snodgrass §10 谈"当前存储"时指出：仅仅时间流逝就会让行进出当前存储 | B3 |
| R7 | 日期与时刻混用、事件类表按日期开窗 | 见 §5.3 | — | A6 |

`as_of` 取"时刻"时按 `recorded_at ≤ T` 换成 `seq`（[`01-temporal.md`](01-temporal.md) §6.1）与标准一致；未来的时刻等于最新，建议在契约里写一句。

## 5. 相邻同值段、端点、空洞、时区与粒度（问题 4）

### 5.1 相邻同值段（合并）

- **标准**：合并（coalescing）把值等价、区间相邻或重叠的行并成一行；合并前后**快照等价**（每个时刻切出来的结果相同）（Snodgrass §6.5.2；术语表 §4.13、§4.9）。Böhlen、Snodgrass、Soo 指出合不合并**有语义差别**：没合并的关系上，"任职超过六年的人"这种按时长筛选的查询会漏掉被切成两段的人；投影也会把合并过的关系变成没合并的。BCDM 与 TSQL2 因此要求关系始终是合并过的。
- **另一面**：Böhlen、Jensen、Snodgrass（2000）的"区间保持"指出点视图分不清"上半年奖金 20、下半年奖金 20"与"全年奖金 20"，而这两者对用户可能是两件事；段"不能随意拆合而不改变含义"。
- **saveslot 现状**：存储不合并（保来源）= 区间视图；"变化点一律指取值变化处"= 机械判定用点视图。这个分工有文献支持，是对的。
- **漏洞**：
  1. 对外读取默认给哪种视图没写（A7）。多字段表上只取部分字段时，按其他字段切出来的段边界会让"预算改过几次"数多、让按时长的筛选出错——这正是文献里的两个例子。
  2. 两种视图在 `next_change` 上打架（B1 / D4）。
  3. "值等价"按哪些列算没写（A1）。
- **可以直接用的判据**：*任何机械判定在快照等价的两个状态上结果相同*——把任意一段在任意点切成两段，`next_change`、高影响、同值判断、冲突判断的结果都不变（§6 P4）。

### 5.2 端点

- 左闭右开与标准一致。Snodgrass §4 说明了为什么：闭闭表示要做"加一个粒度"的运算，闭开不用。
- `valid_to_inclusive`（给人看的含端点形式）只在 `date` 粒度有意义；`instant` 粒度下"最后一刻"取决于时间戳精度，建议不提供（A7）。
- 开口终点：术语表称为 forever（"有效时间线上最大粒度之后的特殊时刻"）。saveslot 用无界区间表示，比 SQL:2011 实现里常见的 `9999-12-31` 干净；对外写法（`null`）要写进契约（A7）。
- 空区间与倒置区间：`valid_from ≥ valid_to` 应报 `invalid_argument`（PostgreSQL 的 `WITHOUT OVERLAPS` 禁空区间，见 [`01-temporal.md`](01-temporal.md) §2.3）；`next_change` 取的是**严格晚于起点**的第一个变化点，所以不会解析出空区间——建议把"严格晚于"写进文档。

### 5.3 时区与粒度

- **标准**：每条时间轴有自己的粒度；存进去的时间必须落在该粒度上（术语表 §4.28 的例子：日期存进秒粒度的轴，"必须存成那天里的某一秒，也许是零点"）。Snodgrass §4：时刻与区间比较时，把时刻看成"一个粒度长的区间"，且两边粒度必须相同。也就是说：**细 → 粗有确定的换算（落在哪个粒度里），粗 → 细没有（一天是一段，不是一刻）**。
- **saveslot 现状**：表声明 `granularity: date | instant`；`date` 按 slot 时区的自然日；不传时间的读取记入口时刻、`date` 粒度记成 slot 时区里的那一天。这些都对。
- **漏洞**（A6）：
  1. `instant` 粒度的表，`valid_at: "2026-11-03"`：当天零点那一刻，还是整天？当天 10:00 有一次变化时两种读法返回不同的值。
  2. `date` 粒度的表，`valid_from: "2026-11-02T23:30:00-08:00[America/Los_Angeles]"`、slot 时区 `Asia/Shanghai`：是 11-02 还是 11-03？
  3. 事件类表按日期开窗（contract §4 建议的改写 `["2026-11-03", "2026-11-04")`）：字段是 `zoned_datetime` 时，一次洛杉矶当地 11-03 23:30 的跑步算不算"11-03"——按事件自带时区是，按 slot 时区（上海已是 11-04 下午）不是。文档说"含时区，保证'哪一天'可复算"，但没说开窗时用哪个。
- `date` 粒度的区间端点是日历日，没有夏令时问题；改 slot 时区时这些端点本身不移动、变的是"今天"与时刻 → 日期的换算——这是我的读法，`07-schema-evolution.md` 只写了"归为确定性转换"，**不确定**它对状态类表的日期端点具体做什么，建议补一句。

### 5.4 键与引用

- 顺序主键（每个时刻唯一）已由 `WITHOUT OVERLAPS` 保证。`entity_key` 需要的是另一种——**非顺序唯一**（整个时间上一个键只对应一个实体），且键字段应是**时不变属性**（术语表 §4.34）。重放规则里已经把键字段当"实体级"，写入一侧缺一条校验（B5）。
- 时态外键（SQL:2011 的 `PERIOD` 外键、Snodgrass 的顺序参照完整性）要求被引用方在引用方的整个有效期内无空洞地存在。saveslot 的 `ref` 指向实体、不带时刻，不做这项检查（B6）；第一版不做是合理的，写明即可。

## 6. 可以直接做性质测试的不变量（问题 5）

沿用 08 的做法：另写一份最直白的**参考求值器**——状态 = "实体 × 字段 × 业务时刻 → 值或无值"的函数（按粒度离散化），一次写入 = 对区间内每个时刻逐点赋值。这就是快照可还原性的定义本身。附录 A 的原型约 60 行。每条性质都写了"在什么输入下会失败"。

| # | 性质 | 写法 | 抓什么错 | 依据 |
|---|---|---|---|---|
| P1 | **逐点等价**（快照可还原） | 带显式区间 `[a, b)` 的写入之后：区间内每个时刻，被写的字段 = 新值；区间外每个时刻、以及没被写的字段，与写入前相同 | 拆行算法的任何错误（少补一段剩余段、多裁一天、动了别的字段） | 【文献】快照可还原性（Böhlen 等 2000，定义 2.4） |
| P2 | **`next_change` 可消去** | `valid_to: next_change` 的写入 ≡ 以"写入前状态里、本次所写字段在起点之后的第一个变化点"为显式终点的写入；且终点及之后每个时刻的值不变 | 解析错终点；解析结果与原始传参记反 | 【推断】 |
| P3 | **顺序主键 / 无空段** | 当前表里同一实体任意两段不相交、没有空区间；版本表里同一实体任意两个版本不在两条轴上同时相交 | 拆行留下重叠或 `[t, t)`；版本区间没关上 | 【文献】顺序主键；版本表的双轴排斥见 [`01-temporal.md`](01-temporal.md) §6.2 |
| P4 | **拆分不变**（判定只看点视图） | 把状态里任意一段在任意点切成两段同值段，再执行同一次写入：`next_change` 的终点、是否高影响、是否同值、是否冲突，结果都相同；写入后的状态快照等价 | 判定逻辑偷看了段边界（把同值佐证切出的边界当成变化点） | 【文献】快照等价（术语表 §4.9） |
| P5 | **合并幂等、保快照** | 查询层合并后的结果与合并前快照等价；合并两次 = 合并一次；合并后相邻两段的值必不相同 | 合并实现错、多字段时按错了列 | 【文献】合并的定义（术语表 §4.13） |
| P6 | **同值写入不产生版本** | 用区间内每个时刻都与现值相同的值写入：没有新版本、`ver` 不变；连写两次 = 写一次 | 同值判断漏了部分同值覆盖 | saveslot 规则；BCDM 的 insert 第三种情形是同一思想【文献】 |
| P7 | **不相交区间可交换** | 同一字段上两次**显式区间**且区间不相交的写入，先后顺序不影响最终状态（快照等价） | 冲突规则里"区间不重叠就合并"的实现；**对 `next_change` 写入不成立**（D4）——测试要把这条限制写进前提，它本身就是 B1 的回归用例 | 【推断】 |
| P8 | **记录时间只追加** | 第 n 次写入之后，任何 `as_of: S`（S 早于这次写入）的结果与写入前逐字段相同（隐私删除除外：只会多出 `partially_deleted`） | 版本表被就地改写；`as_of` 读到了后来的值 | 【文献】"过去的事务时间不可改" |
| P9 | **时间片一致** | `as_of: S` + `valid_at: T` 的结果 = 把日志重放到 S、再取 T 时刻；`as_of` 取最新 = 普通查询 | 版本表与 change_log 不一致；A4 的中间状态（S 落在写入中间时这条会失败，正好用来钉住 A4 的规则） | 【文献】时间片算子 |
| P10 | **影响查询的结构性判据** | 一次读取被标 `possibly_affected` ⇒ 存在它问过的（字段，业务时刻），该处的值在"读取时的记录时刻"与"现在"之间不同；值恢复后撤标 ⇔ 这样的点不存在了。对 `correct` 与（按 B2 改后）一切值变化，反向也成立 | 多报（同值覆盖的部分被算进去）、漏报（B2）、撤标不全 | 【推断】由双时态时间片推出；现行文档的"只算值实际变化的区间""值恢复后撤掉标记"已是这条的两半 |
| P11 | **追溯分类稳定** | 重放同一份日志，每次写入的"是否追溯"与当初一致，不随重放时刻、slot 时区的后续变更而变 | 分类在重放时用了当前时钟或当前时区（A5） | 【推断】 |

P1、P2、P4、P9 四条合起来，等于把 `05-time.md`「写状态」那张表与「查询」那张表变成了可执行的定义；P7 的前提与 P10 分别是 B1、B2 的回归用例。

## 8. 没能核实的部分

- **ISO SQL:2011 标准正文**没读，全部经 Kulkarni & Michels 的综述（标准编辑所写）。
- **TSQL2 的六种表**只读到二手来源（一篇引用它的论文与检索摘要），没读 TSQL2 规范原文。
- **Clifford 等《On the Semantics of "Now" in Databases》**（TODS 1997）下载失败，文中关于"现在"的说法只用了 Snodgrass 书里的一段，没引这篇的结论。
- **Johnston & Weis《Managing Time in Relational Databases》**（断言时间、时态 insert / update / upsert 的区分）没有读到原文，报告没有使用。
- **时间粒度的专门文献**（Bettini、Dyreson 等的粒度术语表）没读；粒度换算不对称的说法来自共识术语表 §4.28 与 Snodgrass §4。
- **XTDB**：`FROM … TO` 返回存储值、`ONLY` 才截取，`BETWEEN` 是否含端点，写入跨空洞时的行为——前者经摘要工具转述（部分核实），后两者文档页没写。**Datomic** `as-of` 是否含给定点，文档页没写。
- **Snodgrass 的顺序更新不填空洞**：书里没有这句话，是从它的实现（五条语句都只作用于已有行的四种相交情形）读出来的；SQL:2011 一侧 Kulkarni & Michels 写明了"找出与区间相交的所有行"。
- **PostgreSQL 19 的 `FOR PORTION OF`**：19 Beta 4 公告（2026-09-24）写明撤回，已读回；wiki 进度页最后修改于 2025-06，仍写"开发中"；`/docs/19/` 下对应页面返回 404。GA 是否如期、PostgreSQL 20 的时间线未核实。
- **saveslot 一侧**：A4（`as_of` 落在写入中间）、A5（写入头是否已记"现在"）是按文档字面读出来的缺口，实现设想里可能已有答案但没写进文档；附录 A 的原型是我对规则的读法，不是 saveslot 的实现。

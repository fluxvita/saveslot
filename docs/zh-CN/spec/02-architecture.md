# saveslot · 工程架构

> saveslot 的核心是**内核 + 服务层 + 操作契约**；本文写它们的工程架构。
> 定位与产品形态见 [`01-positioning.md`](01-positioning.md)，数据机制见 [`03-data-model/`](03-data-model/README.md)，操作契约见 [`04-contract.md`](04-contract.md)，外化面见 [`05-surfaces.md`](05-surfaces.md)（MCP、HTTP）与 [`06-cli.md`](06-cli.md)（CLI），事件的字段级定义见 [`09-event-format.md`](09-event-format.md)。
> 待定项统一记在 [`08-open-questions.md`](08-open-questions.md)。

## 读者须知

本文有几处用法先于定义出现，先在这里说明。

**层号 L0–L7** 是 §4「模块与职责」里内核模块的分层：数字大的在上，只能依赖数字小的（§4「依赖规则」）。

| 层 | 模块 |
|---|---|
| L0 | `store` 存储抽象 |
| L1 | `log` 日志、`audit` 读取审计、`flags` 数据标记、`values` 值的运算 |
| L2 | `rules` 规则引擎、`time` 时间、`delta` 值的差异 |
| L3 | `judge` 判定、`derive` 派生生成、`apply` 落账 |
| L4 | `schema` schema 与迁移、`request` 写入请求、`pending` 待处理事项 |
| L5 | `write` 写入管线、`read` 读取、`delete` 删除 |
| L6 | `jobs` 作业、`sync` 同步、`maintenance` 维护计划 |
| L7 | `ops` 内核操作层 |

**三类状态 (a)(b)(c)**：租户存储里的每一项状态都归入其一。(a) 事实：日志事件，导出的就是它。(b) 物化状态：由 (a) 经 `apply` 确定性地算出，可以丢弃后重建。(c) 本地运行状态：不导出、不重放，每一项都写明丢了会怎样。定义见 §3「日志是唯一事实来源」，每一类有哪些表见 §8「存储格式 v1」。

**先用后定义的几个词**：
- `apply`（落账）：把日志事件落成物化状态的唯一实现（§4）。
- `ops`：内核操作层，契约里每个操作在内核里的唯一入口（§4）。
- 操作号：一次操作的头事件的 `seq`，对外使用的序号（§3「日志是唯一事实来源」）。
- 锚点存储：保存租户存储被整体换掉之后仍必须记得的事（删除登记、`seq` 高水位等），不在租户存储里（§8「锚点存储」）。
- 高水位：锚点存储里记下的已提交日志末端的 `seq`，恢复备份后据此接着编号（§8「锚点存储」）。
- 控制面：跨租户的状态（凭证、租户目录、锚点存储的内容等），与租户存储分开、不随租户导出（§5「控制面存储」）。
- cell：服务器模式里承载一组租户的一个 PostgreSQL 实例，每个租户在其中占一个 database（§8「租户存储」、§9）。

**第一版与 0.1.0**：「第一版」是设计上的第一版范围；0.1.0 是第一个对外发布的版本，只提供其中一部分（[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。0.1.0 尚未提供：隐私删除、需要重建物理表的迁移（含 `change_timezone`、`change_time_field`）、重放对拍（`log.reconcile`、`saveslot verify --replay`）与修改 slot 策略；read_log 的保留期清理与高水位的定期推进两项后台任务也尚未接入。相应地，K11 在 0.1.0 里没有可以触发它的操作，K6 只对不重建表的切换成立。本文讲这些的地方写的是设计，其中几处节首另有一句提示。

## 1. 范围

- **核心 = 内核 + 服务层 + 操作契约。** HTTP、MCP、CLI、App、将来的开发者 SDK 都是契约的外化面。
- 本文写：分层、内核不变量与服务层策略的边界、模块与依赖、运行时、存储抽象、租户、信任边界、代码组织、扩展点。
- 不写：数据机制本身（在 data-model）、每种事件的字段（在 09-event-format.md）、每个操作的参数与回执（在 04-contract.md）、MCP 与 HTTP 各自的规则（在 05-surfaces.md）、CLI（在 06-cli.md）。
- **第一版只有两种运行模式，都是单节点**：本机模式——用户在自己的电脑上启动 saveslot 服务，只供本机访问，同一台机器上的多个 Agent 共用；服务器模式——跨设备、远程访问，可以是我们运营的云服务，也可以是用户自部署的同一套（positioning「部署形态与同步」）。本文写"云服务"的地方，除另有说明外都适用于自部署，差别见 §9。多节点、同步不进第一版，本文涉及节点与同步的地方只作预留。
- 两种产品形态（positioning「产品形态」）共用这一套核心：第一版只实现 **saveslot 服务**；**开发者 SDK** 不实现，但本文的每个决定都要让它将来不改内核就能做出来。
- 用词：**租户**是内核里"一条日志、一份存储"的单位，第一版租户 = 用户。

## 3. 内核不变量与服务层策略

**判据：关掉它，saveslot 的数据还算不算"可回溯、可解释、可重算"，或者 saveslot 对外宣称的问责保证（谁做的、谁读过、确认的是什么）会不会失效。**
会失效的放进内核、任何用法都关不掉；只关系到"谁能做、怎么交互、调用体验"的是服务层策略。

### 内核不变量

每条是一句可以写成测试的断言；细则在右栏指向的地方。

| # | 不变量 | 细则 |
|---|---|---|
| K1 | 日志只追加。每个事件分**事件头**与**内容**：只有事件头串链，事件头永不删改，里面不放任何由用户内容算出的值；内容分块存放，只有墓碑落账时可以整块物理删除 | data-model「完整性与溯源」；09-event-format |
| K2 | 每个事件有 actor：一个全局唯一、在本租户登记过的主体。内核自己产生的事件记在保留主体 `system` 名下，并注明由哪个后台任务触发 | data-model「标识与对象」「连接实例身份」 |
| K3 | 物化状态只能由 `apply`（落账，把事件落成物化状态的唯一实现，§4）改：每一次改动都对应一条日志事件，并在同一事务内提交；每租户写入串行 | 本节「日志是唯一事实来源」 |
| K4 | 每次基础写入都有源数据；来源记到字段级，分值来源与操作来源 | data-model「不变量：每次写入都有源数据」「删除 · 来源」 |
| K5 | 派生表只由规则生成，与基础写入同事务刷新；写入准入的估算与拒绝在内核里执行 | data-model「派生规则与派生缓存」 |
| K6 | 0.1.0 尚未提供需要重建物理表的迁移，K6 在 0.1.0 里只对不重建表的切换成立；这里是设计（[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。schema 版本不可变、字段 ID 稳定；结构变化只经迁移状态机；切换原子、读不停；带旧 `sv` 的写入只在写到不兼容变化的字段时被拒。表一级的结构变化（从未被写入的表改时间类型、键、粒度等）没有对应的字段，视为该表全部字段不兼容 | data-model「schema 版本演进」 |
| K7 | 两条时间线：记录时间由日志序号给出，业务时间按表的时间类型。内核不读时钟："当前时刻"由调用上下文传入并记进事件，重放只用事件里记下的时刻 | data-model「时间」；本文 §7「记录时刻」 |
| K8 | 版本对不上不覆盖：按**冲突单元**（一个字段，或 schema 声明的一个字段组；状态类表另看业务时间区间）判断，有交集的记候选并生成冲突事项，没交集的合并。两次带同一个版本、都不传终点的写入，判定与到达顺序无关：两种顺序要么都判冲突，要么都合并、最终的值相同且都不引出事项（范围与范围之外已知的三处见 data-model「冲突处理 · 冲突判据」的对称一条）；冲突期间的生效值由规则确定 | data-model「冲突处理」 |
| K9 | 受限 SQL 只经语法树白名单（安全与确定性一并保证）；物理名不出内核 | [data-model「受限 SQL」](03-data-model/11-restricted-sql.md)（白名单的清单）；data-model「读取」「派生规则」 |
| K10 | 契约里的读取操作记入 read_log：只记读到的版本，不记值，也不记由值算出的哈希；查询条件只记不含用户值的结构指纹（业务时间条件与入口时刻除外，影响查询要用）。保留期有下限，丢失窗口有上限 | data-model「读取记录」；本文 §7。生成 MCP 的 `instructions` 不是契约里的读取操作，不记读取记录（§10） |
| K11 | 0.1.0 尚未提供隐私删除，K11 在 0.1.0 里没有可以触发它的操作；这里是设计（[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。隐私删除的结果按参考语义定义：假如被删源数据从未存在过、按 `seq` 重放日志得到的状态，两处有意偏离——人的决定照记录、已经生效过的写入保持生效。凡由源数据派生出的内容都在级联范围内；墓碑永不过期；删除登记在日志之外，恢复任何备份后先按登记补删再对外服务 | data-model「删除」 |
| K12 | 日志是唯一事实来源：租户存储里的每一项状态都归入三类之一；从空存储按顺序把日志交给 `apply`，得到的物化状态与线上逐行一致 | 本节「日志是唯一事实来源」 |
| K13 | 写入恰好一次：带请求键的操作，内核在同一事务里记下"请求键 → 结果"，窗口内重发返回原结果 | 本节「K13 的细则」；contract「幂等」 |
| K14 | 确认绑定内容：要确认的事项只有被显式解决才执行；解决时带回所确认内容的版本，对不上就拒绝；每次解决记下是谁、经哪个凭证 | data-model「待处理事项」「写状态」 |

**判定的版本。** 内核的机械判定（挡点、同值、冲突判据、高影响判据、行与实体的存在、字面命中）整体有一个**规则版本**（整数，随内核）；slot 策略（冲突期间的生效值规则等）有一个**策略版本**（按 slot，每次策略变更加 1）。两个号记进每次操作的头事件（逻辑写入头、解决事件、删除生命周期事件）与事项事件。隐私删除重放某次旧写入时，按**该写入自己记下的**规则版本与策略版本重算；想让旧事项改用新规则，由一条显式的重判事件触发（事件类型留位，第一版不产生）。受限 SQL 的白名单另有版本（`rsql@1`），编译时记进 `schema.compiled`（每条派生规则各记自己的；`migrate` / `backfill` 记本版的）；重放按记下的版本求值，实现保留旧版本的行为。一条规则只在它因别的原因重新编译时（它自己被改，或它依赖的定义变了）才换用当前版本，没被改到的规则一直按记下的版本求值，所以内核升级不会让无关的草稿进待确认；规则因换用而有行为变化的，规则版本加 1。这样旧候选不会因为内核升级后的一次不相干的删除而改判。

**K13 的细则。**

- 只匹配幂等窗口内的键：窗口长度由调用上下文传入，按"记录时刻 ≥ 当前时刻 − 窗口"过滤，结果确定。
- 请求键由请求内容算出，是内容（不加 salt）：存在该操作的头事件的内容区里，证据被删除时一起删。显式幂等键另记请求内容指纹（用来发现同一个键配了不同的内容），指纹同样是内容。
- 请求键索引是 (b) 类，由日志重建。`write`、`resolve`、`schema_draft`、`delete` 各自的头事件都带请求键。
- **被拒的操作不产生事件，也不做去重**：重发时按当时的状态重新校验——状态可能已经变了（例如调用方按 `read_first` 的提示先读了一次），缓存拒绝会让按提示做的重试拿回同一个拒绝。

**第一版里适用面变小的不变量**（功能没开，规则自然不触发；没有一条被放松）：

| 不变量 | 第一版的情形 |
|---|---|
| K5 | 不做大写入作业，派生值不允许落后，比完整设计更严 |
| K8 | 不做系统裁定，冲突期间的生效值规则只有"保持当前值" |
| K10 | 纠错影响查询不覆盖对派生值的读取；read_log 按完整形状记，后补查询能覆盖之前的读取 |
| K11 | 不做删除证据与按行隐私删除；不做抽取作业，翻译结果的级联不触发 |
| K12 | 没有后台抽样对账：发现绕过 `apply` 的改动要靠用户会话运行全量对拍 |

### 日志是唯一事实来源

**租户存储里的每一项状态必须归入三类之一**：

| 类 | 是什么 | 导出 / 备份恢复 / 重放 |
|---|---|---|
| (a) 事实 | 日志事件：事件头进链；导出的就是它 | 原样带走 |
| (b) 物化状态 | 由 (a) 经 `apply` 确定性算出；可丢弃重建 | 不带走，由 (a) 重建 |
| (c) 本地运行状态 | 不导出、不重放；**每一项必须写明丢了会怎样** | 不带走 |

每一类有哪些表，见 §8「存储格式 v1」，那是唯一清单。

- 服务层的进程内状态（同键请求进行中的等待）不在租户存储里，丢了无害。
- 0.1.0 尚未提供重放对拍（`log.reconcile`），服务器模式也不建下面的 `<租户 ID 的小写>_reconcile` 库；这里是设计（[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。对拍（`log.reconcile`）的临时存储同样不在租户存储里：是一份用完即毁的副本，每个租户固定一份——服务器模式是租户所在 cell 里的库 `<租户 ID 的小写>_reconcile`，本机模式是 home 下的 `tmp/reconcile/<租户 ID>`。对拍开始前先删掉残留的再建，对拍结束时不论成败都删掉，打开租户时清掉崩溃留下的。打开时清不掉就记一笔、照常服务：它不是租户的数据，下次打开租户、下一次对拍开始前都会再删。
- 锚点存储（§8）也不在租户存储里：它保存租户存储被整体换掉之后仍必须记得的事。
- 导入时重放用的暂存存储同样不在租户存储里：换入之前它不是任何租户的存储，打开租户时清掉崩溃留下的（§8「格式版本、导出、导入与恢复」）。
- **K3 的唯一例外**：迁移中分批构建的新版表是 (c) 类（可丢弃、可从日志重建），在切换事件处转为 (b)；重放时 `apply` 处理到切换事件才建好新版表。

#### 事件目录与贯穿全部事件的规则

**(a) 类事件。** 每种事件的事件头字段、内容块与可删粒度在 [`09-event-format.md`](09-event-format.md)；这里只列有哪些、何时产生。

| 事件 | 是什么、何时产生 | 第一版 |
|---|---|---|
| 租户创世 | 日志的第一条事件：登记租户、存储与事件格式版本、用户主体与保留主体 `system`、一个节点 ID | 有 |
| 源数据 | 一段证据；写入随附证据时每段一条，没带证据时每个在事件里留下了东西的 op 一条（这个 op 本身） | 有 |
| 逻辑写入头 | 每次产生事件的写入请求一条：各 op 的原始传参（含声明的前提）、请求键、判定时用的时刻与版本号；按来源键的 op 另记定位到的行与逐字段的同步基线位置。它的 `seq` 是这次写入对外的**操作号**。按来源键写入的请求里全部 op 都没变或被跳过时，整个请求不产生任何事件 | 有 |
| 基础写入 | 每个 op 对每个受影响的行 / 实体一条，只记这次请求涉及的字段：值、解析后的生效区间（单独成块，记下它依赖的别的贡献）、字段级来源、逐项的生效状态（生效、候选、待确认、佐证；无操作的字段不进基础写入）与写入时的判定结果。不记写入前的值，也不记写入后的整行；全部字段都是无操作的 op 不产生这条事件 | 有 |
| 前提变化 | 一次操作让某些前提目标上所声明的值变了（或变回所见的值）时一条：哪些声明转为"前提已变"、转回"没变"、因删除改指。不是头事件，排在这次操作的基础写入与事项事件之后、派生写入之前 | 有 |
| 派生写入 | 规则引擎刷新一个派生分区时一条：规则版本、分区、读集的日志位置；分组键值与结果校验和在内容里 | 有 |
| 大写入作业 | 作业接受、完成、失败 | 后续 |
| schema 生命周期 | 草稿提交、编译结果（含编译后的定义，供重放使用）、确认 / 放弃 / 被取代、迁移开始、切换、失败；放弃迁移、迁移结果（只在抽取作业里产生）、退役表清理 | 有；放弃迁移、迁移结果与退役表清理后续 |
| 待处理事项生命周期 | 产生、合并、刷新、被取代、解决；解决事件带确认记录。一次写入改到未决事项的目标时，只有写入方读过该事项的当前版本，事项才被取代；没读过则事项刷新、保持未决（data-model「待处理事项」） | 有 |
| 删除生命周期 | 删除已确认（含按参考语义算好的结果）、撤回、到期物理删除（墓碑）；导入时对导出里只有占位的待删除项补的墓碑 | 有 |
| 恢复 | 恢复备份后的第一条事件：恢复到的位置、高水位、恢复次数、新的节点 ID | 有 |
| 导入 | 把一份导出装进空租户时，追加在导入的最后一条事件之后：导入到的位置、恢复次数（导出时的值加 1）、新的节点 ID、目标租户与原租户的 ID、发起导入的用户主体；`apply` 据此把导入前登记、仍有效的全部主体置为停用（已吊销的保持已吊销） | 有 |
| slot 策略变更 | 新策略全文与策略版本；建 slot 时的初始策略也写成一条 | 只有建 slot 时的一条 |

| 主体 | 主体在本租户的登记（含 scope 与 slot 范围）、改名、吊销 | 有 |
| 重判 | 让旧事项改用新规则的显式事件 | 留位 |
| 同步控制 | 主节点切换等 | 留位 |

几条贯穿全部事件的规则：

- **一次操作一个操作号。** 写入、由 `resolve` 触发的写入、删除确认、撤回各有一条头事件，它的 `seq` 是这次操作的操作号。对外的序号（回执的 `seq`、`ver`、历史里的编号、`undo` 的 n、`as_of`、版本表的记录时间区间）一律用操作号；源数据事件与各行基础写入事件的 `seq` 不对外。
- **`apply` 只照事件里记下的结果做**：不重新解析终点、不重判冲突、不做删除重放、不读时钟、不按来源键重新定位（定位到的行 ID 记在逻辑写入头里）、不比较前提的值（标记的每次变化记在前提变化事件里）。删除 / 撤回事件里的结果是 `delete` 按参考语义算好的，`apply` 照用。`apply` 自己做的只有不含判定的确定性计算：把生效的字段值落到当前状态上；状态类表是把值赋给事件里记下的区间，再按"相邻且各字段值都相同的点归为一段"规范化分段；按回退记录登记"已被回掉"时，登记的范围是"那一项的区间 ∩ 本事件写回各项的区间之和"；写回项不带内容（`uncovered`）时不赋值，查来源表取该处"最后一个生效、没被登记回掉的项"。后两种要读来源表，但给定来源表后结果唯一，不含判定（事件格式 5.7）。
- **事件的身份**：第一版事件头里没有单独的事件 ID；一条事件的身份 =（它之前最近一条创世、恢复或导入事件记下的节点 ID，它的 `seq`）。多节点时，别的节点产生的事件以可选的来源字段加入，旧事件不改。
- **`seq` 不复用**：恢复备份后从锚点存储记下的高水位之后接着编，空档由"恢复"事件说明；两次推进高水位之间分配过的 `seq` 仍可能被重用，所以每次恢复换一个节点 ID、恢复次数加 1，`ver`、事项版本与句柄都带恢复次数。导入同样换节点 ID、恢复次数加 1：导入前发出的事项版本一律对不上，导入前的 `ver` 能被认出来。

#### 物理删除后的事件

0.1.0 尚未提供隐私删除；这里是设计（[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。

**物理删除后的事件。** 事件头仍在链上；被删的内容块连同它的校验和清空，记下是哪条墓碑移除的（"已由 #n 移除"；标记里没有内容，也没有由内容算出的值），同一事件的其余内容块照常可读。
`apply` 遇到这个标记就跳过该块——重放到早于墓碑的事件时，不需要往后看就知道它已被删除；此时得到的是"去掉被删内容的历史状态"，不保证等于当时的线上状态，对拍只比较日志末端的状态。

**墓碑之后从头重放，日志末端仍与线上逐表一致**，靠的是删除确认事件把线上的结果写全：
- 删除结果对三种表都列出"取值，或给出它的贡献项，与删除前不同"的字段，由本次被重述的项给出的也列；取值没变、只因为给出者、判定结果或给出它们的块被重新给出而列出的行，结果里的 `outcome` 是 `sources_changed`。有"存在"项被删除或被重述（含原样重述），或有只做登记的写回项（`uncovered`）被重述时，这一行或实体必须列出（三种表都一样）；状态类表上与这些项的区间（重述前与重述后之并）相交的段整段列出，凡是列出的实体都给出删除后的全部无值区间：这些项原来的区间块已移除，空洞只能从结果里取到。删除与撤回事件改业务表只按结果，被重述的项只进来源表。结果里的行在重放里不存在（创建它的那次写入的块全被移除）时，`apply` 新建它。
- 删除确认为受影响行在删除前后所落的每个派生分区各追加一条派生写入，结果没变也追加：墓碑之后从头重放时，中间状态算出的派生值靠它拉回来。
- schema 切换补出的常量位置照切换事件里的记录登记，删除不改它（下面「存储格式 v1」的 `base_sources` 一行）；状态类表上一段补值所依赖的贡献被删时，删除确认把这一段从 `base_sources` 去掉，撤回删除时放回。

- **导出里的两种占位**：宽限期内待删除的内容默认换成"待删除（#n），未导出"（见 §8），这里的 #n 是"删除已确认"事件；"已由 #n 移除"里的 #n 是墓碑。`apply` 按 #n 指向的事件类型区分。
- **带"待删除"占位的导出重放后**，日志末端的业务状态与线上一致（删除后的样子按上面的列法写全在"删除已确认"事件里，派生分区也有那次删除追加的派生写入）；不一致的只有占位处的历史版本内容，以及占位导出无法再撤回这项删除。K12 与对拍对此例外。导入这样的导出时，对每一项占位的删除立即补一条墓碑，存储里只留"在"与"已移除"两种真实状态。
- **校验信息随输入删除**：派生写入的结果校验和、切换事件里新版表的校验和，在输入被删除后清除，之后跳过核对；按时刻还原的结果标 `partially_deleted`。

#### 由此得到的保证

由此：

- **删除不会因导出复活**：宽限期内导出，"删除已确认"事件随日志带走、待删除的内容默认不导出，重放后数据仍读不到。
- **冲突不会因重建消失**：事项的生命周期都在日志里，重放出同样的未决事项与 `disputed` 标记。
- **重放一致可以整体检验**：见 §11 的重放对拍。

### 服务层策略

| 策略 | saveslot 服务 | SDK 嵌入 |
|---|---|---|
| 身份认证 | 凭证 → 用户 / 连接实例 | 宿主声明当前 actor（须是本租户登记过的主体） |
| 权限 | scope × slot 范围（第一版）；表级、字段级的数据权限后续 | 宿主可关闭或自己实现 |
| 确认的交互 | 委托给调用方 Agent；可选 elicitation | 宿主自定 |
| 幂等 | 两个窗口长度（显式幂等键 24 小时、服务端算出的请求键 10 分钟）、同键进行中的等待；只对产生事件的终态结果去重，恰好一次由 K13 保证。请求键本身由内核算：它要在请求规范化之后才有（`request` 给出规范化内容，`write` 加上连接实例与 task 算键） | 默认实现，可关 |
| 高影响写入 | slot 策略额外指定的高影响表 / 字段（内核按结果判定的高影响不可关，op 级 `acknowledge` 的有效性也由内核校验，见 data-model「写状态」）；哪个外化面开放 `acknowledge`（MCP 第一版不开放） | 宿主可加 |

| 准入阈值、read_log 保留期、落盘间隔、高水位推进间隔的数值 | 配置 | 宿主可调（不低于内核下限） |
| 结果渲染（文本、不可信边界） | 外化面（MCP 渲染器） | 宿主自定 |

**确认与数据真实性委托给调用方**：saveslot 不区分确认来自人还是 Agent，也不保证写入数据的真实性——只通过 MCP 时 saveslot 分辨不了，
也没有能力判断。内核保证的是 K14：要确认的事项只有被显式解决才执行；确认绑定内容；每次确认留痕；另有删除可在宽限期内撤回。
征得用户同意是调用方 Agent 及其宿主的事。将来 saveslot 自己做来源接入与分析时，那条路径的真实性由 saveslot 负责。
slot 策略的结构里为"某类操作只接受用户会话的确认"留了位置，第一版不实现。

**权限在 SQL 上的执行必须在内核**：数据权限（行、列、表）要作用到受限 SQL 上，只有规则引擎能改写查询。服务层把"本次调用的可见范围"传给内核，
内核负责在目录、查询、SQL 改写、写入里统一执行。第一版的可见范围按凭证到 slot 一级：连接实例的授权 = 动作 scope × slot 范围（全部，或一个 slot 列表），范围外的 slot 对这个凭证与不存在完全相同；用户会话恒为全部。表级、字段级后续，接口第一版就按 slot → 表 → 字段的形状留好。

### 依赖规则

- **只能依赖更低层，同层之间不互相依赖**；环一律由 `ops` 编排打开（例：写入产生事项、事项的解决要执行写入——`pending` 不调 `write`，由 `ops` 先后调用）。唯一的例外是 `request` 依赖同层的 `schema`：只取单位词表与编译后定义的类型，不调编译与迁移。
- **事务由 `ops` 打开**，下层模块只接收 `Tx`，不自己开事务。一次操作跨多个模块的调用都在这一个事务里。
- 生成事件的模块（write、schema、pending、delete、derive、jobs）都不直接改物化状态，只把事件交给 `apply`。前提变化事件由 `write`（含 `resolve` 触发的写入）与 `delete`（删除确认、撤回）在产生改动的那个事务里生成，所需的声明与覆盖索引经 `store` 读取，不经 `read`：三者同在 L5，同层不互相依赖。
- **判定只有一份实现**：`write`、`delete`、`schema` 需要的机械判定都调 `judge`，不各自实现。
- **服务层只调 `ops`**，不直接碰下面的模块；外化面只调服务层。
- 依赖检查做到**模块级**（如 dependency-cruiser 的分层规则），在 CI 里强制。
- 表里的 `flags`、`maintenance`、`jobs`、`sync` 是设计上的模块，0.1.0 的内核源码里还没有它们各自的目录；表与依赖规则照设计保留，「第一版」一栏标明了各自的状态。

### 契约操作与内部操作

`ops` 的入口分三组，形状相同（都接收调用上下文、打开事务、组合下层模块）：

- **契约操作**：操作契约里的每个操作，由服务层调用。
- **内部操作**：后台任务的任务体。上下文里 `actor = system`，`now` 由调用者给，另带 `trigger`（哪个后台任务）。由**内核之外的调度器**调用——调度器持有定时器、读时钟；saveslot 服务里它在 `daemon`，SDK 嵌入时由内核附带的一个薄驱动或宿主驱动。例外是 `revokeOnRefreshReplay`：它不是定时任务，由服务层在刷新令牌被重放时调用。
- **建租户入口**（`createTenant`）：在一份新的空存储上追加并落账创世事件（09-event-format §5.2）。由 `saveslot init` 或服务器模式的开通流程调用。上下文里 `actor` 是它要登记的用户主体，`trigger` 为空；不查"`actor` 已登记"（此时还没有任何主体）。它既不是契约操作也不是内部操作，不在下表里。

| 内部操作 | 谁触发 | 产生事件吗 |
|---|---|---|
| `openTenant` | 打开租户时。依次：查"导入进行中"标记 → 查"恢复进行中"标记 → 日志末端是否低于高水位 → 登记与日志对账 → 补跑到期任务。导入标记最先看：导入换入之后、重建锚点之前，日志末端高于高水位、恢复次数也还没对上，先按导入的重入协议做完（§8）。高水位检查在对账之前：日志被回退时不能先按"事务从未提交"清掉登记项。核对通过、租户可以服务时加载受限 SQL 的解析器：宿主打开租户存储时经它加载，内核的求值入口（读派生表、写入后的派生刷新、`apply` 重算派生分区）假定它已加载、不自行加载 | 视情况 |
| `flushReads` | 调度器按落盘间隔；写事务开头也走同一段逻辑 | 否 |
| `expireDeletions` | 调度器；`openTenant` | 是：墓碑 |
| `purgeResidue` | `expireDeletions` 提交之后 | 否 |
| `pruneReads` | 调度器 | 否 |
| `migrationStep` | 调度器（迁移中时） | 切换时是 |
| `advanceHighWater` | 调度器；关闭租户前 | 否 |
| `closeTenant` | 关闭、放弃所有权前：先 `flushReads`，再 `advanceHighWater` | 否 |
| `revokeOnRefreshReplay` | 服务层：同一张刷新令牌被第二次使用时，吊销这次授权的连接实例（[`05-surfaces.md`](05-surfaces.md) 第 15 节）；连接实例已吊销或已停用时不调用 | 是：`principal.revoked`（09-event-format §5.3） |

0.1.0 尚未提供重放对拍（`log.reconcile`）；这里是设计（[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。对拍（`log.reconcile`）不是后台任务：它是契约里的管理类操作，由用户会话触发。做法同迁移的构建与切换，分三段：① 把日志分批重放到一份临时存储（不在租户存储里，用完即毁），期间读写照常；② 追平重放期间新追加的事件；③ 在该租户存储的一个只读事务里读日志末端、追完最后一段，再逐表比较 §8 里标"对拍：是"的表。PGlite 上读写共用一个队列，这一段里写入排队；PostgreSQL 上在同一个读快照（`REPEATABLE READ READ ONLY`）里完成，不必让写入排队——事件的追加与它的落账在同一个事务里提交，快照里的物化表正是它读到的日志末端的样子。每一批的事务仍由 `ops` 打开。

### `ops` 的调用上下文

每个 `ops` 调用除了操作参数，还带一个**冻结的、可序列化的上下文**——这是内核与服务层（以及将来 SDK 宿主）之间真正的边界：

| 字段 | 说明 |
|---|---|
| `tenant` | 打开的是哪个租户 |
| `actor` | 已认证的主体（全局 ID）；内部操作是 `system` |
| `trigger` | 内部操作才有：哪个后台任务，取下表内部操作的名字（`openTenant` 等）。它与事件头的 `trigger`（`deletion_expiry` 等，09-event-format §2.1）不是同一个枚举：不产生事件的任务没有事件头的 trigger，一次内部操作也可能产生不同 trigger 的事件。`actor = system` 当且仅当 `trigger` 非空 |
| `task` | 自报的任务标识，可空 |
| `visibility` | 可见范围：`{kind: "all"}`，或 `{kind: "scoped", slots: [{slot, tables?: [{table, fields?}]}]}`——slot → 表 → 字段的白名单，没列出的不可见。服务层按凭证传：用户会话与范围为全部的连接实例传 `all`；限定到 slot 列表的连接实例传 `{kind: "scoped", slots: [{slot}, …]}`，不往下列表与字段。内核把 `scoped` 实现到 slot 与表两级（表一级只在测试里用），带 `fields` 时报内部错误。规则见 data-model「读取 · 可见范围」 |
| `idempotency_window` | 服务端算出的请求键的幂等窗口长度（服务层策略） |
| `idempotency_key_window` | 调用方显式幂等键的幂等窗口长度（服务层策略） |
| `now` | 入口取的当前时刻；内核不读时钟 |
| `confirmation` | 解决事项时的确认记录：调用方带回的事项版本（所确认的事项内容的操作号与恢复次数）与 `via`（`call` / `elicitation`，由外化面填写）；用户与凭证由 `actor` 得出。**所确认内容的哈希由内核在落账时按事项的条目块算出**，写进内容区，不由外化面给。可空 |

可序列化是为了将来非 JS 宿主经 sidecar 进程调用时，上下文能原样跨进程传递。存储与锚点存储两个端口不在上下文里：它们在打开租户时由宿主交给内核。

### 请求来源地址

**请求的来源地址**（服务器模式；身份提供者按它统计登录失败，云服务按它限制新建租户）：服务器模式经反向代理访问，不读转发头的话，所有请求的来源都是代理的地址。规则：

- 连接本身的地址受信（落在受信代理名单 `SAVESLOT_TRUSTED_PROXIES` 的某一项里；逗号分隔，每一项是单个地址或 CIDR 网段，06-cli 4.1）时，才读 `X-Forwarded-For`：同一请求的多个头按顺序合成一个列表，从右往左走（每个受信代理都把它收到请求的那个地址追加在最右边），跳过受信的地址；遇到第一项不是受信的地址就停：它是地址，它就是来源；它不是地址，来源是最后一个受信的一跳（最右边一项就不是地址时，是连接本身的地址）。停下那一项左边的一概不读：那一段是客户端自己写的。列表里全是受信的地址时，取最左边那个。
- 没配名单、连接本身的地址不受信时，整个头都不读，来源是连接本身的地址：客户端自己写进这个头的内容不作数。头缺失时同样取连接本身的地址。头里的项只认单个地址，带端口的不认。不读 `Forwarded` 头。
- 地址先规范化再比较：写成 IPv6 的 IPv4（`::ffff:a.b.c.d`）按 IPv4 算，IPv6 按小写压缩写法。一个地址受信，当且仅当它与名单的某一项同族，且开头前缀长度那么多位与这一项相同；单个地址就是 `/32` 或 `/128` 的网段。
- 名单的写法：网段写成 `地址/前缀长度`，前缀长度是不带前导零与符号的十进制，IPv4 在 0–32、IPv6 在 0–128，`/` 两边不留空白；地址在前缀之后的位必须全为零（`192.0.2.1/24` 不收：写的是网段里的一台机器还是网段，分不清，按掩码截断会悄悄放宽信任）。落在 `::ffff:0:0/96` 里的 IPv6 网段就是它写出的 IPv4 网段（`::ffff:192.0.2.0/120` 即 `192.0.2.0/24`），因为来源地址按 IPv4 比较；其余 IPv6 网段只与 IPv6 地址比较。盖住全部地址的项不收：前缀长度为 0 的（`0.0.0.0/0`、`::/0`，以及换算后就是 `0.0.0.0/0` 的 `::ffff:0:0/96`），和比 `/96` 宽、盖住了 `::ffff:0:0/96` 的 IPv6 网段（如 `::/80`）——名单盖住全部地址时任何连接都受信，来源全由客户端写，比不配名单还糟。此外不设最小的前缀长度：名单里该写的是部署方自己的代理所在的子网与 CDN 公布的出口网段，宽窄由它们定。不收端口与 zone。名单里有不收的项时，服务启动时报配置不合法，写明是哪几项。连接没有可用的单个地址时没有来源地址：本机模式经 unix socket 访问，以及带 zone 的链路本地地址。

### 控制面存储

**控制面存储**：要先由凭证找到租户，才能打开租户的存储；这一类跨租户的状态放在控制面，与租户存储分开、不进租户日志、不随租户导出。

| 内容 | 本机模式 | 服务器模式 |
|---|---|---|
| 凭证（连接实例令牌的哈希、用户会话）、OAuth 客户端注册 | `control/credentials.json` | 控制面库 |
| 租户目录（用户 → 租户；将来共享 slot 成员、开发者 → 终端用户租户） | `control/tenant.json`（只有一个租户）：`{"format": 1, "user": "u_…", "tenant": "tn_…"}`，恰好这三个键 | 控制面库 |
| 路由（租户 → cell → 进程）、冷租户归档索引 | — | 控制面库 |
| 锚点存储的内容（§8）：删除登记、`seq` 高水位、恢复次数、"恢复进行中"与"导入进行中"标记 | `control/anchor.json` | 控制面库里的表 |
| 句柄签名密钥 | `control/keys/` | 环境配置，由部署方保管（第一版不接 KMS） |

- **本机控制面用文件**，不用第二个数据库实例：数据量极小、结构固定、单进程写。写法是写到同目录的临时文件 → 落盘 → 改名覆盖 → 目录落盘；只有 saveslot 服务进程写，进程内串行。
- **服务器模式的控制面是独立的 PostgreSQL 库。** 库里的表（这里只写各表存什么，SQL 是实现的事）：

  | 表 | 存什么 |
  |---|---|
  | `control_meta` | 控制面库自己的格式版本；自己建表的组件（本地账户）另记一个各自的格式版本。哪个不符，哪一方就拒绝使用。打开控制面库时库里有内核的表，就是把控制面指到了租户库上，同样拒绝 |
  | `tenants` | 租户目录与路由：租户 ID、属主用户（第一版一个用户一个租户）、所在 cell、租户存储所在的 database、状态、导入的暂存 database。同一个 cell 里，所有租户的 database 与暂存 database 合起来两两不重名（一个库不能既是一个租户的又是另一个租户的暂存）；不同 cell 是不同的 PostgreSQL，可以同名。库名合 PostgreSQL 库名的形状，不是服务器自带的库（`postgres`、`template0`、`template1`），也不以 `_reconcile` 结尾（留给对拍的临时库，§3），登记与设暂存时就核，不合即拒绝。状态 `creating` 是已登记、存储里还没有创世事件，`active` 才对外服务。§8 导入第 ⑤ 步的换入，就是在一次更新里把两者对调：暂存 database 成为租户的 database，被换下的那个（只有创世事件）记在暂存的位置，删掉之后才清掉这一项 |
  | `credentials` | 令牌哈希 → 凭证种类（用户会话 / 连接实例）、主体、租户、过期时刻（只有会过期的凭证有）、来自哪次授权（来自 OAuth 授权的凭证记它属于哪次授权，登出一次授权不动同一主体别的授权）。只用来由凭证找到租户与主体：scope、slot 范围与主体状态以租户日志为准，主体已吊销而哈希仍在时照样拒绝。来自授权的凭证（访问令牌、带授权的用户会话）过期满一天后由授权服务器的定期清理删掉；静态令牌与不带授权的会话不清 |
  | `anchors`、`anchor_deletions` | 锚点存储（§8）：每个租户的高水位、恢复次数、"恢复进行中"与"导入进行中"标记，删除登记按登记的先后逐项存。每次写入是控制面库自己的一个事务，提交后才返回，不与任何租户存储的事务合在一起 |
  | `accounts`、`web_logins` | 只有用内置本地账户（§12「身份提供者」）的部署才有，由本地账户自己的初始化建表，格式版本记作 `control_meta` 的 `accounts_format`。`accounts`：用户 ID、账户名（唯一）、口令哈希、状态（启用 / 停用）、会话最后一次被结束的时刻（改口令时记下，只往后不往前；从没有过就是空）。`web_logins`：网页登录态，一行一次登录：登录的 ID（即 `currentUser` 给出的 `session`）、登录 cookie 的哈希（不存 cookie 本身）、用户、过期时刻 |
  | `external_users`、`external_logins`、`external_states`、`external_jti` | 只有用外部登录（§12「身份提供者」）的部署才有，由外部登录自己的初始化建表，格式版本记作 `control_meta` 的 `external_format`。`external_users`：（签发方，账户 ID）→ 用户，与账户状态（启用 / 停用）；第一次见到的账户在这里得到用户，再建它的租户。`external_logins`：网页登录态，一行一次登录：登录的 ID（即 `session`）、登录 cookie 的哈希、用户、声明里的平台会话 ID 与显示名、过期时刻（十分钟）。`external_states`：发起登录时的 `state`：它的哈希、绑定浏览器的 cookie 里那个随机秘密的哈希（`state` 本身出现在平台的登录与回调地址里，cookie 放的是另一个秘密，回调时核对它）、登录后回到的路径、过期时刻（十分钟），用过即删。`external_jti`：用过的声明 ID，按签发方记，存到声明过期为止，进程重启后照样拒绝重放。后三张表按过期时刻建索引，过期的行在下一次写这张表时删掉 |
  | `oauth_clients` | 远程授权的客户端 ID 元数据文档的缓存：客户端 ID（客户端自己域名下的 HTTPS 地址）→ 取回的文档原文、取回时刻、过期时刻。只是缓存：过期了按地址重取，删掉不丢任何东西。saveslot 的 CLI 是内置客户端，不在这里 |
  | `oauth_grants` | 一次授权：授权 ID、种类（连接实例 / CLI 登录的用户会话）、主体、租户、客户端 ID、签发时的对外地址（令牌的 audience）、建立时刻、作废时刻、兑换它的授权码的哈希。连接实例的一次授权就是一个连接实例；经它签发的访问令牌是 `credentials` 里带过期时刻、记着这次授权的一行，刷新令牌在 `oauth_refresh_tokens`，授权作废时一起删掉 |
  | `oauth_codes` | 授权码的哈希 → 客户端、回调地址、`code_challenge`、对外地址、用户与租户、同意授权时的那次登录（`currentUser` 给出的 `session`）、请求里的 scope、用户在授权页上定下的名字与 scope、过期时刻。兑换时在同一个事务里删掉，所以一个码只能换一次 |
  | `oauth_refresh_tokens` | 刷新令牌的哈希 → 所属的授权、签发时刻、过期时刻（30 天未用即失效）、CLI 登录的总期限（换新时原样带到新令牌上；连接实例没有）、换成了哪一张（记新令牌的哈希；记了即用过，再出示是重放）。换新时只在它还没用过时才记，与新令牌的写入在同一个事务里，所以同时换两次只有一次换得成。授权作废、或它的连接实例被吊销时删掉；过期的定期清掉 |
  | `oauth_device_codes` | 设备码（RFC 8628，CLI 的 `--device` 登录）：设备码的哈希 → 用户码（唯一，大写、不带横线）、客户端（总是 `saveslot-cli`）、对外地址、状态（等待 / 已批准 / 已拒绝）、批准或拒绝的用户与租户、过期时刻（10 分钟）、轮询间隔、上次轮询的时刻。兑换时在同一个事务里删掉并记下授权，所以只能换一次；过期的定期清掉 |
  | `web_forms` | 授权页表单的一次性令牌的哈希 → 它所属的登录与显示这一页的那次请求（授权请求的查询串的哈希）、过期时刻。提交一次即删，对不上也删：别的登录、别的请求都用不了它 |

  远程授权的六张表（`oauth_clients`、`oauth_grants`、`oauth_codes`、`oauth_refresh_tokens`、`oauth_device_codes`、`web_forms`）另有自己的格式版本（`control_meta` 的 `oauth_format`），与控制面自己那几张表的格式各自核对；格式不符的库拒绝使用，不做升级。

### 账户口令与账户名

  - **本地账户的口令**用 scrypt：N = 2^15、r = 8、p = 3，盐 16 字节，输出 32 字节。参数与盐、哈希一起存（`scrypt$N$r$p$盐$哈希`），按存下的参数核对，以后改参数不用迁移。每次计算占 32 MiB，进程里同时最多算 2 个，其余排队。账户名不存在时也拿一个固定的假哈希算一遍，同样排队（假哈希在打开本地账户时就算好，第一次遇到不存在的名字不多算一次）：账户名不存在、口令不对、账户已停用，对外是同一个结果，耗时也一样。
  - **账户名**是 1–64 个字符：小写字母、数字、`.`、`_`、`-`，以小写字母或数字开头（`[a-z0-9][a-z0-9._-]{0,63}`）。不做大小写折叠：含大写字母的名字直接拒绝，所以一个账户名只有一种写法。**口令**是 8–1024 个字符（按 UTF-16 码元计），原样计算，不做 Unicode 规范化。
  - 存下的口令哈希只按这里写出的形状核对：密钥 32 字节、盐至少 16 字节、N 是 2 的幂且不超过 2^17、r 在 1–16 之间、p 在 1–4 之间（新算的哈希也不超出这些）；不合的哈希不与任何口令匹配，也不为它计算。登录时账户名形状不对、口令超长，与账户名不存在一样处理：同样算一遍假哈希，同样的结果。
  - 本地账户的运维（`saveslot server user …`）按账户名找人：建账户时经下面「建租户」建出它的租户。中途停下的，用同一个账户名再建一次就接着做完：先把租户建完，再把口令换成这一次给的，换法与改口令相同（同时结束网页登录态与用户会话）；租户建不成（比如登记的 cell 不同），口令不动。同一个进程里同一个账户名正在建时，再建一次报账户名已被占用。改口令同时结束这个用户的网页登录态与用户会话，并记下会话结束的时刻：在这一刻或之前授予的用户会话，刷新时不再签发（§12「身份提供者」的 `issueUserSession`）；这些在一个事务里，它签发的连接实例照常可用。停用、启用只改账户状态，不往租户日志写吊销，也不删凭证，停用期间这个租户的全部凭证在认证时被拒，刷新也不签发；再启用，一切照旧。改口令与停用都先改账户那一行，再动它的网页登录与会话（锁的先后见 §12「身份提供者」的 `issueUserSession`）。
### 建租户与请求的解析流程

  - **建租户**分三步：在 `tenants` 登记为 `creating` → 建库并写创世事件 → 改为 `active`。每一步先看现状再做，中途停下的，再调一次就接着做完；同一个用户已有租户时，得到的就是那一个。登记之前先核 cell 是这个部署配置里有的，不是就什么都不登记；登记里的 cell 与 database 之后不改，所以还在 `creating` 的租户，这次请求的 cell 与登记的不同时明确拒绝，不换到新的 cell，也不在旧的里接着做。控制面只存登记，不持有租户存储的后端，三步由服务层编排。
- 云服务的调度器扫描登记里尚未执行的到期时刻，到期时主动打开租户执行物理删除。

解析流程：凭证 → 控制面查出（租户，主体）→ 打开租户存储与锚点存储 → 从 `principals` 取这个主体的 scope、状态与 slot 范围 → 构造调用上下文 → `ops`。
第一版做导出与导入到空租户（positioning「部署形态与同步」）：导入不做主体映射，导入前登记的、仍有效的主体一律停用（已吊销的保持吊销），凭证由用户在目标处重新签发；导入是管理类操作，只给用户会话，步骤见 §8。合并导入、迁移流程（冻结源租户、凭证映射）随多节点放到后续。主体身份在日志里，历史上的 actor 不随凭证变化。

- **服务层不改数据**：所有改动都经 `ops` 进内核。
- 远程授权（OAuth 2.1）、本地令牌、用户会话都在这一层；内核只看到"已认证的主体"。

## 6. 操作契约的形态

- **契约分两层**（成文见 [`04-contract.md`](04-contract.md) 的两部分；MCP 与 HTTP 各自的规则见 [`05-surfaces.md`](05-surfaces.md)）：
  - `contract-core`：数据的形状——值的编码、证据、标记、意图、领域错误（`validation_failed`、`schema_incompatible`、`derived_readonly` 等）。内核依赖它；
  - `contract`：对外的封装——外化面专用的字段与错误（`idempotency_key`、`cursor`、签名句柄、`insufficient_scope`、`rate_limited`）。服务层与外化面依赖它。
- **`ops` 的签名在内核里手写**，由 `contract-core` 的类型约束；`contract` 由它们生成 HTTP 的 OpenAPI、MCP 的 `inputSchema`、将来 SDK 的接口。
  这样对外契约加错误码、加分页参数，不改内核。
- **标记是结构化字段**：`disputed`、`awaiting`、`stale` 等在契约里是字段，不是渲染出来的文字；外化面的渲染器**必须**把它们输出到文本（MCP）或保留在结构里（SDK），由渲染器测试保证。
- **版本互相独立**：

  | 版本 | 管什么 | 何时升 |
  |---|---|---|
  | 契约版本（`/v1`、SDK 主版本） | 操作的形状 | 删字段、改语义升主版本；加可选字段、加错误码、加枚举值升次版本（调用方必须容忍未知值） |
  | slot schema 版本 `sv` | 用户数据的形状 | 每次 schema 切换 |
  | 存储格式版本 | 内核自身表的形状（§8） | 内核升级改了自身的表时 |
  | 事件格式版本 | 每种日志事件的形状，写在事件头里 | 只增不改：新内核必须能重放所有旧版本事件；旧内核遇到不认识的事件类型或版本，**停止 `apply` 并报错**，不跳过；带了旧内核不认识的形状（新的 path、键、枚举值）的事件必须带更高的 `v`，没有"忽略未知键"的路径（事件格式 1.6） |
  | 规则版本、策略版本 | 机械判定的语义；slot 策略 | 见 §3「判定的版本」 |
  | 同步协议版本（第一版不用） | 节点之间 | 握手时协商 |

## 7. 运行时与进程模型

本节写服务进程怎么跑：一个租户同一时间只有一个写者、已确认的写入在崩溃与断电后不丢、后台任务怎样执行。滚动部署、进程崩溃、路由抖动时数据不被写坏，靠的就是这里的规则。

### 进程、单写者、串行写

- **saveslot 服务进程**：一个 Node（或 Bun）进程承载 HTTP、MCP 与后台任务的调度器。云服务时多进程，每个租户固定路由到一个进程，每个活跃租户一条数据库连接，闲置即关，满额按最近最少使用淘汰（positioning「技术选型」；下面 PostgreSQL 一项的「连接」）。
- **单写者与所有权 epoch**：一个租户的存储同一时间只被一个进程写。
  - 每次打开租户时，所有权 epoch 加 1 并记在存储里；每个写事务在锁下核对 epoch，不一致说明别的进程已经接手，本进程放弃这个租户、清掉进程内缓存。
    这样连接闲置关闭、滚动部署、路由抖动时，旧进程也不会写坏数据。
  - PGlite：
    - **锁**：数据目录下 `saveslot.lock` 上的操作系统文件锁，经带预编译包的原生扩展取得（Node 标准库没有）；进程死即由内核释放，不靠 pid（pid 会被复用）。锁文件只作加锁对象，不写内容。
    - **属主文件**：`saveslot.owner` 记随机 token、启动时间与 epoch，用"写临时文件、改名"原子替换。每个写事务开始时与提交前各读一次，token 不符即放弃租户：直接终止 DB Worker，**不做关闭检查点**（否则旧实例的页会写回新属主的库）。库里的 epoch 照记照核；但 PGlite 的旧实例从自己的缓冲池读 `meta`，看不到新值，所以 PGlite 上以属主文件为准。
    - **防线的主次**：真正的防线是"持有者活着就不会失效"的内核锁；属主核对是最后一道，只覆盖锁文件被删除或替换这类锁失效，拦不住失效那一刻已经写出的预写日志。因此 PGlite 不得改用会过期的锁（心跳、超时一类）；saveslot 自己的任何清理都不删 `saveslot.lock` 与 `saveslot.owner`。
    - 检测到数据目录在 iCloud Drive、Dropbox 一类同步盘里时给出警告。
  - **本机服务进程一级的锁**：除了数据目录里的单写者锁，本机服务进程启动时先取主目录下 `run/saveslot.lock` 上的同一种操作系统文件锁，保证同一主目录只有一个服务进程，控制面文件（`control/` 下）也只有一个写者；拿不到即退出。`saveslot init` 与 `init --rotate-session` 也取这把锁，据此判断服务是否在运行。锁文件同样只作加锁对象、不写内容，任何清理都不删它；进程死即由内核释放，重新拉起的进程直接拿得到。拿到锁之后，`run/saveslot.sock` 上若有活着的服务在应答（连得上），照样拒绝启动、放回锁，不接管它。监听时套接字先绑在本进程专用的名字（`run/<pid>.sock`）上，再以硬链接放到 `run/saveslot.sock`、删掉专用名（关掉监听时系统会按绑定时的路径删文件，这个路径不能是别的服务可能占着的那个）。用链接不用改名：那里已有套接字时链接失败，没人应答的是死掉的进程留下的，删掉再链一次；有人应答的不顶掉它，同样拒绝启动。链接成功之后才写 `run/saveslot.pid`。启动时 `run/` 下没人应答的 `<pid>.sock`（进程在启动途中死掉留下的）一并删掉。退出时删除套接字与 pid 文件，但只删仍是自己建的那两个（按设备号与 inode 认）：主目录在服务运行中被搬走、原路径上已有别的服务时，那里的文件是那个服务的，不动。因失去存储的所有权（`ownership_lost`）而退出的服务，不再往主目录按路径写任何东西：`run/last-failure.json` 不写（原因只进它自己的日志），日志超过上限时只在路径上仍是自己那份文件时才轮转。已知边界：主目录被搬走后，旧服务认会话时仍按路径读 `control/credentials.json`（只读），0.1.0 不处理。
    - 依据见单写者锁实验的结果报告（[`../process/experiments/exp-8-single-writer-lock.md`](../process/experiments/exp-8-single-writer-lock.md)）。
  - PostgreSQL：路由保证一个进程，epoch 兜底。
    - **两个进程同时建一个用户的租户**（第一版一个部署一个进程，不会发生）：两边登记到的是同一个租户（§5），各自打开它的库，后开的接管，先开的一方以 `ownership_lost` 失败；再调一次，得到的是那个建好的租户，库只有一个，创世事件只有一条。
    - **连接**：每个打开的租户一条连接，读与写在进程内同一条队里轮流，同一时间只有一个事务。一个进程同时打开的租户至多 `SAVESLOT_TENANT_CONNECTIONS` 个（06-cli 4.1「服务器模式的配置」）：打开中、已打开、关到一半、关闭失败仍开着的都算，已经打开的租户再被用到不另占名额。要打开一个新租户而名额已满时，先关闲置最久的租户（与闲置到期的关闭相同：先写读取记录、推高水位，关完才算腾出）；没有闲置的就按到达顺序排队，5 秒内等不到回 `unavailable`（`busy`，`retry_after` 1）。数据库以连接数已满（SQLSTATE 53300）拒绝连接时同样这样回答。一个请求从认证到应答结束，它的租户都不算闲置（认证与操作是两次使用，之间不被关给别人）；所以每个名额都被进行中的请求占着时，新来的请求等满 5 秒回 `busy`。不经过这里的连接不计入名额：控制面库的那一条、建租户时直接打开的新库（一个进程里一次建一个）、建库与删库时连的维护库（建库一条、删库一条，在一个进程里各一次一个）、导入时直接打开的库（一次导入两条）；部署的连接预算为它们留出余量（06-cli 4.1）。闲置多久关闭由 `SAVESLOT_TENANT_IDLE` 定。
    - **锁与 epoch**：每个写事务开头先取该租户的 advisory lock，再在锁下核对 `meta` 里的 epoch，不一致即放弃租户、关掉连接；打开租户时的加 1 也取同一把锁，所以排在进行中的写事务之后。别的连接提交的值本连接看得见，因此以库里的 epoch 为准，没有属主文件与锁文件。锁的作用域是 database，而每个租户独占一个 database，键是固定常量。
    - **读事务取一次快照**（可重复读、只读）：别的进程在其间提交的写入，不在同一个读事务的前后两条语句之间显现。PGlite 上只有一条连接，读事务天然如此；内核的读路径按这一点写。
    - **连接断开**：租户存储进入失败状态，之后的调用都拒绝，由宿主关闭后重新打开；不在存储内部重连（重连等于重新打开，要重新给 epoch 加 1）。`COMMIT` 已发出、答复未到时断开，这次写入可能已经提交、也可能没有：这种情形的错误（`commit_unknown`）与"确定没有提交"（`connection_lost`）分开给出，后端不重试、不猜。
- **每租户写入串行**：进程内按租户排队，事务里再拿 advisory lock；`seq` 在事务内从库里取，即提交顺序。后台任务的写入与前台写入走同一条队。

### PGlite 与 PostgreSQL

- **PGlite 的真实模型**：PGlite 是单连接实例，多个实例打开同一目录会写坏，所以**整个 PGlite 实例住在一个专用的 DB Worker 里，读写都经它排队**。
  - 超时只能终止整个 Worker，等于数据库崩溃一次、重启时走崩溃恢复，会打断排队中的写事务。所以**主防线是事前的**：写入准入估算、编译时拒绝高代价写法（派生规则、试跑、受限 SQL 都适用）；超时只是最后手段，是否启用由沙箱实验决定。
  - **实例常驻，不在请求路径上开关**：每个租户的 DB Worker 与其中的 PGlite 实例在服务启动时打开，一直开到服务停止，闲置也不关；导出、导入、恢复这类必须重开存储的场合用新的 Worker。理由：打开一次存储要数秒；在同一进程里反复实例化、销毁数据库的 Wasm 实例，会偶发地触发运行时的断言而带走整个进程。
  - **DB Worker 意外退出时不在进程内重开**（服务自行以非零码退出的情形只有三种：DB Worker 意外退出；导入之后重开租户失败；写评测结果日志失败，只在测试时钟下发生。共同的原则是：这三种情形下继续对外服务会给出错误的结果，所以停下来。打开租户时核对不通过等其余失败，是服务还没有开始服务就没通过核对，不是服务过程中出了错：服务留在失败状态、在健康检查里报告原因直到被停止，不自行退出，免得被外部拉起后反复重启；这期间 `/v1` 的请求回 `unavailable`（`stopping`，不带 `retry_after`），停止中回 `stopping` 带 `retry_after`）：服务标为失败、以非零码退出，由外部拉起（`saveslot mcp` 的自动拉起、launchd 或 systemd）；被拉起的进程照上面的次序取锁、打开租户（存储自己做崩溃恢复，再做 §4 `openTenant` 的核对），核对通过才对外服务。
  - 一条慢查询会挡住这个租户的写入，最长到超时时长；本机单用户可以接受，延迟上限待实验后写明。
- **PostgreSQL 上的受限 SQL**：只读角色、只读事务、`statement_timeout`。第一版受限 SQL 与写入共用该租户的一条连接、串行执行。
- **持久性**：已确认的写入在崩溃、断电后不能丢。
  - PGlite 在 Node 上自身不落盘：默认启动参数带 `-F`；去掉之后，它的文件系统层也不把同步调用交给宿主。saveslot 的做法：去掉 `-F`，`wal_sync_method = fsync`，给 NODEFS 装一个调用宿主 `fsync` 的钩子。
  - 打开时读回这些设置并自检：打开时那次提交必须经钩子同步 `pg_wal`，不符即拒绝打开（`durability_not_applied`）。
  - **预写日志的大小**：PGlite 以单用户模式运行 PostgreSQL，没有检查点进程，预写日志写到 `max_wal_size` 也不会自己发起检查点（只有在 postmaster 之下才会），本机目录的 `pg_wal` 因此会随写入一直涨。saveslot 的做法：写事务的回复发出之后，主线程再核对一次所有者文件，然后请 DB Worker 检查：自上一个检查点以来的预写日志超过 64 MiB，就执行一次 `CHECKPOINT`；已失去所有权的实例不做检查点。`max_wal_size = 64MB`、`min_wal_size = 32MB` 限定检查点后保留复用的段，打开时一并读回核对。检查点失败时，实例可能已经坏了（检查点里的 fsync 失败会 PANIC），所以记一行日志（`checkpoint_failed`，只带错误码），结束 DB Worker，存储进入 `worker_failed`，此后与上面 DB Worker 意外退出相同：服务以非零码退出，由外部拉起；在此之前已确认的写入已经落盘，不受影响。
  - **统计信息**：单用户模式下也没有 autovacuum，没人替这些表收集计划器的统计信息；没有统计信息时，计划器按默认估计选计划，表大到一定程度会翻成扫整个索引或整张表。所以本机模式由内核收集，时机有三个：打开存储时（对外服务之前；导入或恢复换入新存储之后的那次打开也在其中），写事务回复之后（与检查点同一处，排在它后面），升级存储格式之后（§8「格式版本、导出、导入与恢复」）。前两个只在统计信息过期时做，升级之后不看是否过期都做（新建的表、列与索引都还没有统计信息）。过期的判据：日志末端的 `seq` 超过 `events` 上次统计的行数加上 50 再加一成（PostgreSQL autovacuum 的默认阈值；从没统计过的表按 0 行算）。`events` 只是代表：每次写入都往它里面追加，但一个事件带进的业务行与内容块多少不一，别的表的统计信息可能比它更早过时。做法是在任何事务之外对本库 public 下的各表执行 `ANALYZE`，有三处例外：
    - `content` 在单独的事务里用统计目标 10（默认 100）分析：采样行数是统计目标的 300 倍，它是最大的表，`ANALYZE` 的时间几乎都花在读它的采样页上；而内核不靠它的直方图选计划——它的行按 `seq` 找，`path`、`body` 上的 `LIKE` 条件都作用在已按 `seq` 选出的行上；
    - `content.body` 与 `events.header` 不收统计信息：这两列的高频值就是用户内容的原文，收进 `pg_statistic` 等于在库里多存一份副本，而内核对它们的条件（`body IS NOT NULL`、以通配符开头的 `body LIKE`、`body::jsonb` 上的表达式；`header` 上没有条件）都用不上这份统计；
    - `events` 放在最后单独做：事务之外的 `ANALYZE` 逐表提交，`events` 的统计行数就是「这一轮做完了」的标志，中途失败或被打断时它仍是旧的，下次检查照样算过期。

    统计信息不是数据，不进日志，不影响重放与对拍。失败只记一行日志（`analyze_failed`，只带错误码），不让写入或打开失败；进程在分析中途被结束时写不出这行日志，下次打开时统计信息仍算过期，重新分析。服务器模式由 PostgreSQL 的 autovacuum 收集，saveslot 不另做。
  - 钩子不把这样的 fsync 传给宿主：同一个 PGlite 实例里，这个文件上次宿主 fsync 返回之后，没有任何会改它内容、长度或身份的操作碰过它（写入，含 msync 的写回；按描述符或按路径截断，含带 `O_TRUNC` 的打开；新建；改名，搬走的与被覆盖的；删除）。省下的是崩溃后启动时 PostgreSQL 对数据目录的第二遍 fsync。每个实例里每个文件的第一次 fsync、目录的每次 fsync 都传给宿主；宿主 fsync 失败过的文件从此不再跳过。持久性的保证不变。
  - 钩子依赖 PGlite 的内部结构，所以 PGlite 版本钉死到补丁号；升级 PGlite 必须重跑持久性实验步骤一（两个平台）与钩子计数的单元测试，并核对 NODEFS 里会改文件的操作清单（上一条的跳过靠它）。
  - 能否达标由持久性实验确认（[`07-scope-v1.md`](07-scope-v1.md) 实验 1；结果报告见 [`../process/experiments/exp-1-pglite-durability.md`](../process/experiments/exp-1-pglite-durability.md)）；不达标就换成随 saveslot 打包的原生 PostgreSQL。

### 记录时刻

- **事件的记录时刻 = max(调用上下文的 `now`，上一条事件的记录时刻)。** 不严格递增，允许相等；先后顺序由 `seq` 决定。单调由内核保证，因为只有内核看得到上一条事件。
- 这次操作里所有与"现在"有关的判断都用这个取值：幂等窗口、宽限期到期时刻的计算、状态类表"生效起点是否早于现在"。写进事件的也是它；重放时只用事件里记下的值。
- 到期与否的比较（宽限期是否已过）用调用上下文的 `now` 与事件里记下的到期时刻比。
- 时钟回拨或错误地跳到未来又调回时，新事件的记录时刻停在上一条事件的时刻，直到墙上时钟追上来；期间确认的删除只会晚删、不会早删。`now` 比日志末端的记录时刻早 5 分钟以上时，`saveslot status`、`saveslot doctor` 给出警告，写入回执带提醒；不拒绝写入——内核无从知道哪个时钟是对的。

### read_log 的持久性

读取记录在进程内缓冲（主线程），这些时刻落盘：

- **任何写事务开始时**，和这次操作在同一事务里，所以 `ver` 兜底总能看到刚才的读取。操作被拒（不产生事件）时，这次落盘照常提交。
- **关闭租户、放弃所有权之前**（闲置关闭、滚动部署、路由迁走）。
- 其余时候按落盘间隔（初值 5 秒）。

丢失窗口：进程崩溃，或在落盘之前失去了所有权（此时旧进程已不是写者，缓冲落不了盘）；最多丢最近一个落盘间隔里、且之后没有写入的读取记录。

### 后台任务

- 任务体是 `ops` 的内部操作（§4），调度器在内核之外。第一版的后台任务：read_log 落盘与清理、宽限期到期的物理删除与残留清理、迁移的构建与追平、高水位推进。大写入作业、退役表清理、冷租户导出、后台抽样对账不进第一版。
- 0.1.0 里周期性运行的只有读取记录落盘（本机模式）与过期 OAuth 记录的清理（服务器模式）。下面几项后台任务 0.1.0 尚未执行，这里是设计：read_log 的保留期清理（0.1.0 不清理，读取记录只增不减）；高水位的定期推进（0.1.0 只在关闭租户时推进）；迁移的追平（随需要重建物理表的迁移一起尚未提供，[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。
- 任务进度是 (c) 类状态，丢了由 (a) 里未完成的迁移与待执行的删除重新推出。
- **打开存储时先补跑已到期的任务**，不依赖进程一直在跑。
- **嵌入时（后续）**：同一个内核跑在宿主进程里，宿主负责打开与关闭；单写者、格式版本检查、串行写仍由内核做；内部操作由内核附带的驱动或宿主调用；短生命周期的宿主（CLI、serverless、被挂起的移动 App）靠"打开时补跑"保证到期任务最终执行。

### 物理删除按时执行

0.1.0 尚未提供隐私删除；下面三节（物理删除按时执行、残留清理的做法、残留清理在 PostgreSQL 上需要的权限）写的是设计（[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。

- 云服务：调度器到期时**主动打开租户**执行物理删除，不等用户下次访问。
- 本机：saveslot 服务在运行就按时执行；没在运行时，下次启动时先执行再对外服务。删除回执如实写明这一点。
- **分两段，各自幂等**：① 墓碑事务——追加墓碑事件，清空列出的内容块，清掉各版本物理表、事项条目、索引里的对应内容；② 残留清理——事务提交之后调存储后端的 `purgeResidue`，做完把残留清理进度（(c) 类）推进到这条墓碑。进度丢了或落后时，对它之后的全部墓碑重做一遍。
- **失败时是否对外服务**，判据只有一条：对外服务会不会让被删的内容重新可读。

  | 情形 | 被删内容经接口读得到吗 | 策略 |
  |---|---|---|
  | 到期的物理删除失败（磁盘满、锁超时、后端报错） | 读不到：确认时就已逻辑删除 | 照常对外服务；按退避重试；这项删除在 `saveslot status`、`saveslot doctor`、事项详情里标"逾期未物理删除"；服务器模式同时告警 |
  | 要清的内容块校验和不符 | 读不到 | 照删；在 `verify` 里如实报告 |
  | 残留清理的语句报错（权限类除外） | 读不到 | 照常对外服务；PGlite 上按 worker 故障处理（结束 worker、存储进入 `worker_failed`，与其他 worker 故障同一条路）；进度不推进，重开后从头重做 |
  | 原地清理遇到权限类的报错（PostgreSQL） | 读不到 | 不反复重试原地那一串：这个租户的残留清理改走重建（下文），`saveslot doctor` 写明改用重建与缺的是哪一项 |
  | 残留清理没成：判据不过，或等快照超时 | 读不到 | 不是故障：照常对外服务，worker 照常；进度不推进，按退避重试（初值 1 分钟、每次加倍、上限 1 小时，内核常量），下次打开时也重试；`saveslot doctor` 与 `saveslot status` 有一行"残留清理未完成"（自哪条墓碑起、最近一次没成的原因与时刻），是提醒，不是不通过 |
  | 恢复流程里的补删没做完 | **读得到**：恢复出的数据里没有这次删除 | 不对外服务，直到补删完成 |

### 残留清理的做法

两个后端相同，由残留清理实验确定（结果报告：[`../process/experiments/exp-7-residue-cleanup.md`](../process/experiments/exp-7-residue-cleanup.md)），每一步都有"去掉就搜得到被删原文"的对照：

1. `VACUUM FULL` 受影响的每张表；
2. `ANALYZE`；
3. （PostgreSQL）等到本库没有别的会话持有快照或事务号，最多 60 秒：查 `pg_stat_activity`，只看本库与不属于任何库的进程（`coalesce(datname, current_database()) = current_database()`），条件只用 `backend_xmin` / `backend_xid`（这两列对所有角色可见，`backend_type` 等列对无权限的角色是隐藏的，不能用来过滤）；
4. `VACUUM FULL pg_statistic`——必须在 `ANALYZE` 之后：`ANALYZE` 会把旧的统计行（高频值就是原文）留成死行；
5. `CHECKPOINT`，`pg_switch_wal()`，再两次 `CHECKPOINT`；
6. 实例以 `wal_recycle = off` 运行（旧日志段不复用）。

本机模式另有定期的 `ANALYZE`（§7「PGlite 与 PostgreSQL」的「统计信息」；`content.body` 与 `events.header` 不在其中），它不改变上面的步骤：它采到的样本里，删除确认之前的由残留清理自己的第 2 步换掉、旧行由第 4 步清掉；宽限期内采到的，被删的内容那时本来就在表里，由到期的物理删除一并清理。

- **成功判据**：做完后 `VACUUM (VERBOSE) pg_statistic` 的报告里 "dead but not yet removable" 为 0 才算成功，不看 `n_dead_tup`。不为 0 说明有快照挡着、旧统计行还在：这次不算，进度不推进（上表"没成"一行）。
- 语句清单固定在存储后端里，不接受外部 SQL；全部语句幂等，中途崩溃或没成都从头重做。两条语句之间插进来的写入不影响：进度按墓碑位置记，新写入里没有已删的原文。
- 代价（10 万行的租户，macOS）：PostgreSQL 约 0.3 s、PGlite 约 0.5 s；清理期间一条写入最长等 PostgreSQL 约 10 ms、PGlite 约 50 ms（PGlite 上写入与清理同一个队列，最多等一条语句）。
- **拿不到下一节的权限时**（典型是托管的 PostgreSQL 服务）：改用重建——把日志重放进一个全新的 database / 数据目录，校验后替换旧的再删掉旧的。新目录从没写入过被删内容。代价：10 万行时 PostgreSQL 约 8 s，**期间这个租户不可写**；删除回执如实写明用的是重建以及不可写的时段。
- **用哪一种由启动时核对决定**（PostgreSQL）：打开时核对连接角色有没有下一节的各项授权、实例的 `wal_recycle` 是不是 `off`；都具备用原地清理，缺任何一项就用重建。`saveslot doctor` 写明现在用的是哪一种做法；用重建时写明缺的是哪一项、怎么补。PGlite 上总是原地清理。
- 不处理的：文件删除后留在文件系统空闲块或固态硬盘上的旧数据，删除回执如实说明。

### 残留清理在 PostgreSQL 上需要的权限

saveslot 连 PostgreSQL 用的角色若不是超级用户，部署时要授予下面四项：

| 用途 | 授权 |
|---|---|
| `VACUUM FULL pg_statistic` | `GRANT pg_maintain TO <角色>;`（PostgreSQL 17 起的预置角色） |
| `CHECKPOINT` | `GRANT pg_checkpoint TO <角色>;` |
| `pg_switch_wal()` | `GRANT EXECUTE ON FUNCTION pg_switch_wal() TO <角色>;`（默认没有授给 `PUBLIC`） |
| `wal_recycle = off` | 写进实例配置：`ALTER SYSTEM SET wal_recycle = off;` 后重载（`SELECT pg_reload_conf();`）。它由检查点进程读取，会话里 `SET` 不起作用；非超级用户执行 `ALTER SYSTEM` 要 `GRANT ALTER SYSTEM ON PARAMETER wal_recycle TO <角色>;`，也可以由运维直接改 `postgresql.conf` |

- 等快照读 `pg_stat_activity`，不需要额外授权（不需要 `pg_read_all_stats`）。
- **这几步是实例级的**：切日志段、检查点、`wal_recycle` 作用于整个实例，不是一个 database。服务器模式下每租户一个 database、同一实例上有许多租户：清理按实例合并着做（一段时间内到期的各租户的表重写与 `pg_statistic` 重写各自做完，再统一切一次日志段、做检查点），不是每个租户各切一次。另一个 database 的快照不挡本库的清理（实测），所以一个租户的长事务不会让别的租户的清理"没成"。

## 8. 存储抽象

本节定义内核与存储之间的两个端口、租户存储里有哪些表、容量边界，以及导出、导入与恢复的做法。换后端、升级格式、导出、导入与恢复时数据保持一致，靠的是这里的定义。

内核依赖两个由宿主实现的端口：**租户存储**与**锚点存储**。内核不变量只依赖这两个端口，不依赖任何服务层组件。

### 租户存储

```ts
type TenantRef =
  | { kind: "pglite"; dir: string }                      // 本机：saveslot 配置的数据目录；嵌入：宿主给的路径
  | { kind: "postgres"; database: string; cell: string } // 云服务：由控制面路由得出

interface StorageBackend {
  open(tenant: TenantRef, opts: { create?: boolean }): Promise<TenantStore> // 拿单写者锁、epoch 加 1、检查格式版本
}
interface TenantStore {
  write<T>(fn: (tx: Tx) => Promise<T>): Promise<T>     // 串行写事务；开头核对 epoch
  read<T>(fn: (tx: ReadTx) => Promise<T>): Promise<T>  // PGlite 上与写同一队列
  purgeResidue(): Promise<void>                        // 物理删除后清理明文残留；做法与判据见 §7「残留清理的做法」
  snapshot(): Promise<SnapshotRef>                     // 物理快照，只用来加速；按备份对待（第一版不做）
  formatVersion: number
  close(): Promise<void>
}
```

| 后端 | 用在 | 租户对应 | 支持的版本 |
|---|---|---|---|
| PGlite | 本机模式、SDK 嵌入 | 一个数据目录 | PGlite 内嵌的 PostgreSQL 18.6 起 |
| PostgreSQL | 云服务、自部署 | 每租户一个 database，按 cell 分组 | 18.x；跨大版本的重放一致性由重放一致性实验确认 |

PostgreSQL 上租户的 database 建库时编码为 `UTF8`，排序规则用内置提供者的 `C.UTF-8`：排序是码点序，字符分类用 PostgreSQL 自带的表，不随操作系统变。打开租户时依次核对服务器大版本、编码、排序规则、存储格式版本、建库时记下的固定会话设置，再给 epoch 加 1；任一项不符即拒绝打开，epoch 不动。存储格式低于内核、但不早于 0.1.0 的，在 epoch 加 1 之后原地升级（§8「格式版本、导出、导入与恢复」的「升级机制」）。cell 到连接参数的对应由宿主在构造后端时给出，`TenantRef` 里只有 cell 的名字与 database 的名字。

### 锚点存储

锚点存储保存**租户存储被整体换掉之后仍必须记得的事**：删除登记、`seq` 高水位、恢复次数、"恢复进行中"标记、"导入进行中"标记。

0.1.0 尚未提供隐私删除，下面的删除登记（含恢复后按登记补删）是设计（[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。

```ts
interface AnchorStore {
  // 每个写操作都必须落盘后才返回
  read(tenant): Promise<Anchor>                                  // 从未写过的租户读到空锚点（没有登记、高水位 0、恢复次数 0）
  putDeletion(tenant, entry: DeletionEntry): Promise<void>      // 新增或整项覆盖
  removeDeletion(tenant, deletionId): Promise<void>              // 没有这一项时什么都不做
  advanceHighWater(tenant, seq): Promise<void>                   // 只增不减
  beginRestore(tenant, restoreId): Promise<Anchor>               // 置"恢复进行中"并把恢复次数加 1；已在进行中则原样返回
  endRestore(tenant, restoreId, highWater): Promise<void>        // 清"恢复进行中"，高水位取两者较大者；没有在进行中的恢复、或 ID 不同时拒绝
  beginImport(tenant, importId): Promise<void>                   // 置"导入进行中"（带导入 ID）；锚点不空（有删除登记、恢复次数不为 0、已有任一进行中标记，含同一个导入的）时拒绝
  endImport(tenant, importId,
            r: { deletions: DeletionEntry[]; highWater: Seq; restoreCount: number }): Promise<void>
                                                                 // 一次落盘写入由导入的日志得出的全部删除登记、高水位（取两者较大者）与恢复次数，并清标记；没有在进行中的导入、或 ID 不同时拒绝
  abortImport(tenant, importId): Promise<void>                   // 只清"导入进行中"标记，不写登记（回滚用）；没有标记时什么都不做（重入时可能调两次），ID 不同时拒绝
}
```

- **高水位在任何路径上都只增不减**：`advanceHighWater`、`endRestore`、`endImport` 都取存着的与给出的两者中较大的那个。
- 写进去的登记项、高水位与恢复次数不合端口的形状（状态、种类不在枚举里，`seq` 不是正整数等）时拒绝，什么都不写。
- **必须与租户存储分开存放、分开备份。** 两者被一起恢复时，内核补不了也发现不了——这是写明的边界。
- **持久性要求**：每次写入落盘后才返回；确认删除时，登记落盘之后才能提交租户事务。
- 接口在 `kernel` 包里；登记项的字段、状态与对照表的权威定义在 data-model「删除之后 · 删除登记」。
- 谁实现：saveslot 服务由 `service` 用控制面实现（§5）；内核测试用文件实现；SDK 嵌入时由宿主实现，或用内核附带的文件实现并由宿主指定路径。
- 谁调用：`ops` 持有它，下层模块只返回"要写进锚点的内容"，由 `ops` 在提交前后按 data-model 规定的先后调用。
- **高水位的推进时刻**：删除相关的租户事务提交之后、把登记项改到新状态时；关闭租户或放弃所有权之前；自上次推进以来已追加 1000 条事件或已过 60 秒（两个数是初值）。每次都推进到**当时的日志末端**。推进不在写事务里做，失败不影响写入。确认删除时"先写登记"写的只是登记项（`intent`），不推进高水位：高水位永远不超过已提交的日志末端，恢复事件因此不会占用一条已提交事件的 `seq`。

**业务表 `t_<表ID>_v<n>`。** `zoned_datetime` 字段另有一列 `f_<字段ID>__zone` 存它的时区（字段值是时刻加时区，`timestamptz` 只存得下时刻；受限 SQL 不暴露这一列，对拍与导出把它算作内容列）。事件类与无时间表有已撤销标记，状态类表没有（撤销在那里是无值区间），另有区间终点。每个 `zoned_datetime` 字段另有一个内部日期列：这个时刻在 slot 时区下的日期，由 `apply` 落账时在应用层算好（受限 SQL 的 `saveslot_date(f)` 改写成这一列），不在数据库里做时区换算。它由日志与时区库算出，以重放方的时区库为准：`meta` 记下建出现有这一列所用的时区库版本，打开租户时版本与当前不同，就在本地重建这一列与依赖它的派生分区（确定性的本地重建，不写日志）。slot 时区可以改（`change_timezone`，确定性转换、要确认）：切换事务里按新时区重算这一列，依赖它的派生表随之重建。0.1.0 尚未提供 `change_timezone` 与 `change_time_field`（改事件类表的时间字段）：它们属于需要重建表的迁移，草稿提交时报 `not_in_this_version`；这里是设计（[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。

**版本表 `t_<表ID>_v<n>__ver` 的落格。** 按一次操作结束时的状态落格，细则见下一段「版本表存值，不存指向内容的引用」。"存在"（撤销与恢复）也占一格，字段 ID 用固定值 `existence`：事件类与无时间表上撤销加一格并标已撤销，字段格照旧，恢复也加一格（出处是那条恢复项）；状态类表上生效的撤销让实体没有值的那几段落 `existence` 格并标已撤销，只落在有字段项垫着的地方。状态类表没有值的段里，只有决定"有值"的字段（必填字段，没有必填字段时全部字段）落格，说明为什么没值：被无值项清空的落一格空值并标无值，出处记那一项；其余字段不落格。有值的段里每个字段都落一格、不标无值，被清空的与从没写过的字段也一样。所以"这一段有值"当且仅当这一段上有一个不标无值的字段格，有没有必填字段都是这一条；"无值"只标在状态类表的字段格上，与"已撤销"（只标在 `existence` 格上）是两回事

**`base_sources` 的主键与常量补值。** 行或实体 ID 在主键里是因为一条 `schema.switched` 会给很多行补值（`write.base` 一条只对一行）。常量 `backfill` 补在哪里照切换事件的记录登记，不现算：事件类表、无时间表是行 ID 列表，状态类表是实体与区间（区间出自别的贡献，带 `deps`，那些贡献被删时这一段补值随之不再存在）；之后的删除让某处字段变空时不追补常量。

**`base_sources` 的各列。** **基础写入自己带的每一种来源，每一项都写一行**，删除重放从这里查「哪些贡献的来源被删」：值来源（或搬运引用、schema 常量）在前；没有值来源的项，这条基础写入的操作来源（`op_sources`）代替它们排在前面（一条都没有时写一行不指向源数据的操作行）；有值来源的项，操作来源接在值来源之后；区间参数的来源（事件格式 §5.7 的 `valid_sources`：状态类表上带区间参数的写入与撤销都有这个块）再接在后面。由 `resolve` 触发的写入，操作来源记在 `item.resolved` 上、不在基础写入里，表里没有它的操作行；它不影响删除后的取值（操作来源只是控制依赖）。序号依次排，每一项的第一行（序号 0）是它的值来源或代替它们的那一行；schema 常量不指向源数据，事件 seq 是那条 `schema.switched`；这一项当前的生效状态与解析区间（写入时记下的，或删除事件重述的，最近一次为准）；最近一次给出这一项的内容的块（`given_seq`、`given_path`：被删除事件以新的值、"没有值"或只做登记重述过时，是那条删除事件与它的 `restated/<k>`，落账读内容时读它；只重述判定、不给内容的重述不改它；从没这样重述过时为空，读原来的字段块。判定本身在本行的状态与区间列里）；是否佐证及其显式端点（`corroboration_ends`：状态类表上的佐证项是它的佐证端点列表，按事件格式 §5.7 取，没有显式端点时是空列表；不是佐证的项、非状态类表上为空；一项有几个来源就有几行，每行相同；之后的写入与回掉不改它，端点此刻是否仍算数在解析时从日志判，删除重述这一项时重算）；是否已被某次回掉（`undo` 或回到合并基）登记（哪次操作、哪些区间）。

**版本表存值，不存指向内容的引用。** 按时刻读直接查版本表，不回内容表。它按单元格记，每格带着产生这个值的贡献：物理删除时 `apply` 按墓碑列出的内容块找到对应的格子，清掉其中的值；状态类表一个版本里各段来自不同写入，落在不同的格子上。同一请求多个 op 改同一实体时，版本表按这次操作结束时的状态落格：后一个 op 覆盖前一个 op 在同一格上的值（例如两个 op 的业务区间起点相同），格子记最后给值的那一项贡献，所以同一操作号下一格只有一个版本。不把主键扩到事件 `seq`：按时刻读的粒度本来就是操作号，同一操作内的中间状态对外不可见。代价是历史值存两份，换来按时刻读是一条普通 SQL。

**(c) 本地运行状态**（不导出、不重放）

| 表 | 归哪个模块 | 丢了会怎样 | 第一版 |
|---|---|---|---|

**固定的会话设置**（写进 `meta`，两个后端相同，重放一致性依赖它们）：编码 `UTF8`（`length`、`substr` 按字符计依赖它）；时区 `UTC`；内核自身的表与受限 SQL 的文本排序用 `C` 排序规则；十进制数用 `numeric`；日期输出格式 ISO；字符串字面量里的反斜杠不转义（`standard_conforming_strings = on`，受限 SQL 打印出的字面量依赖它）。业务层面的"哪一天"由 slot 的时区在应用层换算，不依赖数据库会话时区，也不依赖两个后端各自带的时区库；应用层用的时区库版本随 saveslot 版本钉死；建出内部日期列所用的版本记进 `meta`（见上表业务表一行）。

### 容量边界与实测数值

存储的三个设计选择都随数据量线性变贵：每次基础写入在同一事务里刷新受影响的派生分区；全部版本保留，没有压缩与降采样；每一行带自己的来源记录（来源表）与按单元格的版本记录（版本表）。第一版不按写入频率限制、不拒绝行数多的表，也不为序列数据专门设计存储；它面向的是按人的节奏产生的记录（positioning「场景判据」）。写入准入管的是一次写入的大小，不是一张表的大小。

**两条界线**，按表算（取数据目录概况里的 `profile.rows`），每个后端各一组，随内核版本发布：

| 界线 | 键名 | 定义 | PGlite | PostgreSQL |
|---|---|---|---|---|
| 舒适线 | `comfortable_rows` | 一张表的行数在此之内时，常见写入 p99 ≤ 50 毫秒，冷启动与按时刻读都在实测记下的可接受范围内 | 100,000（0.1.0 初值；形状 A 待测） | 100,000（占位初值，PostgreSQL 一侧待测） |
| 实测线 | `tested_rows` | 容量实验做过、且没有记为"到这里不行"的最大规模点。就是那个规模点本身，不在相邻两点之间插值；规模点相隔一倍以上，这条线的分辨率就是这么粗 | 1,000,000（0.1.0 初值；形状 C 在 50 万行已超单行写入 1 秒判据） | 1,000,000（占位初值，PostgreSQL 一侧待测） |

- 超过舒适线、不超过实测线：数据目录的表概况带 `scale.level: "large"`；超过实测线：`beyond_tested`。读时按当前行数算出，不进事件，不是数据标记（data-model「数据目录」）。
- `saveslot doctor` 的"数据规模"一项列出过界的表，以及租户一级的事件总数、数据目录大小、最近一次冷启动耗时，并与实测范围比较；结果是"提醒"，不是"不通过"。服务器模式下由数据目录的提示承担，运维一侧的容量监控归实验 3。
- 不在写入回执里提醒，不拒绝写入，不自动降采样。

### 格式版本、导出、导入与恢复

- **格式版本检查与跨版本的数据兼容**：从 0.1.0 起，升级 saveslot 不会让已有数据打不开（决定与理由见 [`data-compatibility.md`](../process/decisions/data-compatibility.md)）。
  1. **新版本能打开旧数据。** 任何一个发布的版本都能打开此前任何一个发布的版本（0.1.0 及以后）写下的数据。打开时存储的格式版本低于内核支持的 → 内核把它**原地升级**到当前格式，不要求用户先导出、再导入。
  2. **旧版本不打开新数据。** 存储的格式版本高于内核支持的 → **拒绝打开**（`format_too_new`），提示升级 saveslot / SDK。不做降级。
  3. **0.1.0 之前不在承诺之内。** 0.1.0 之前的格式版本都是开发期的，不做升级：拒绝打开（`format_too_old`），提示用新版本重新初始化。
  4. **导出文件同样向后可读。** 0.1.0 及以后导出的文件，之后的任何版本都能导入。导出文件的清单带自己的格式版本号（`saveslot_export`），与事件格式一起冻结（[`07-scope-v1.md`](07-scope-v1.md)「事件格式的冻结点」）：只增不改，不兼容的改动先有决定稿。
  5. **配置与凭证跨升级照常可用。** 新版本照常读旧的 `config.toml` 与客户端的 profile 文件；改了名字的键，旧名至少再认一个小版本，并提示改用新名。已签发的凭证升级之后仍然有效；因为安全原因必须作废时，在发布说明里写明。

  这条承诺说的是数据，不是接口：1.0 之前小版本之间操作契约与 CLI 可以有不兼容的变化，但不会让已有数据打不开，也不会让已有的配置与凭证失效。

  **承诺覆盖什么**

  | 对象 | 在不在承诺之内 |
  |---|---|
  | 租户存储：日志（事件头与内容）、由日志得出的表 | 在。日志原样保留；由日志得出的表升级成新格式，或按日志重建 |
  | 锚点存储：删除登记、`seq` 高水位、恢复次数、进行中的标记 | 在。它在日志之外，重建不出来，升级必须原样带过去 |
  | 导出文件 | 在（第 4 条） |
  | 读取记录 | 在。保留到它自己的保留期规则让它到期为止 |
  | 其余写明了"丢了会怎样"的本地运行状态（请求键等：丢了只是失去幂等） | 尽量保留，不承诺。升级可以清空或重建，升级说明里写明 |
  | 控制面库（服务器模式）：账户、凭证、租户目录、锚点 | 在。规则同租户存储：原地升级，逐级、可重入，留样本 |
  | 本机的 `config.toml`、客户端的 profile 文件、已签发的凭证 | 在（第 5 条） |

  **现状**：只有一个存储格式（格式 5）、一个事件格式（v1）和一个导出文件格式（1）。0.1.0 打开时的检查只有两种拒绝：低于 5 报 `format_too_old`，高于 5 报 `format_too_new`。0.1.0 之后原地升级的机制已经做出来（下面的「升级机制」），升级的步骤还一步都没有，格式仍是 5；把格式改到 6 的变更，必须连同 5 → 6 这一步一起发布。

  **对升级机制的要求**（做的时候必须满足）：
  - **逐级升级**：每改一次格式，写一步"从上一格式到这一格式"的升级；隔了几个版本的数据依次走完每一步，不写跨级的捷径。
  - **日志不改写**：升级不改事件头，不改内容块（K1）；要变的只有由日志得出的表和 saveslot 自己的元数据。升级的最后手段总是"按日志重建由它得出的表"。
  - **崩溃后可重入**：升级到一半进程停了，再打开时要么仍是旧格式、可以重新升级，要么已是新格式；不能停在两者之间。
  - **升级之后对得上**：升级完成后，由日志得出的表与从空存储重放这条日志的结果一致（K12）。
  - **每个发布过的格式留一份样本**：发布一个新格式时，在测试夹具里（`packages/test-backend/fixtures/storage-format/<格式>/`）存用那个版本写下的数据，本机模式一份（数据目录，含锚点），服务器模式一份（控制面库与租户库），由 `scripts/make-format-sample.ts` 生成。每种模式另可有一份带 schema 切换的（`<模式>-switch`：一张写过的无时间表被删、留作退役表，另一张表改了 `duplicate_keys`），可以在发布之后用发布的那个提交生成，样本目录里的 `made-from.json` 记下那个发布标签、标签的提交，以及生成时比标签多出的文件（只许是样本自己的测试文件）：样本是用标签的树加这些文件生成的，生成时所在的提交不记，它不一定留在仓库里。此后每个版本的测试都打开每一份样本、升级、再按上一条核对（[`11-claims.md`](11-claims.md) C1）。
  - **控制面库照同样的要求**：逐级、可重入，升级之后账户、凭证、租户目录与锚点都在。
  - **格式升级分两类**：可回滚的兼容扩展（加表、加可空列）随版本发布；不可回滚的单独发布、先灰度，发布前保留快照——否则新版升级了格式、部署一回滚，旧版拒绝打开，就回不去了。

  **升级机制**（租户存储）：
  - **步骤**在内核里：每一步把格式 n 的存储变成格式 n + 1，是一组语句，在一个事务里执行，所以其中不能有控制事务的语句（`BEGIN`、`COMMIT`、`ROLLBACK`、`SAVEPOINT` 等）：步骤表里有这样的一步，打开时一步也不做、报错（这是这个版本自己的错）。能升级的最早格式是 5（0.1.0 写下的）。
  - **打开的次序**：先核对编码（服务器模式先核对服务器大版本、编码与排序规则）；再读格式号，高于内核的报 `format_too_new`，低于 5 的报 `format_too_old`，5 到内核之间的记下；再核对建库时记下的固定会话设置，不符报 `session_settings_mismatch`（两个后端都核对）；再给所有权 epoch 加 1（服务器模式在租户的锁下加，加之前在同一把锁下重读格式号，见下面「单写者」）；然后逐步升级。升级完成才把存储交给调用方，本地服务也是这之后才对外服务。
  - **每一步一个事务，事务的最后一条语句把 `meta` 里的存储格式改成 n + 1。** 一步中途失败或进程被结束，这一步整个回滚，存储停在已经做完的最后一步的格式上，下次打开从那里接着升级；不会停在两个格式之间。
  - **单写者**：本机模式在数据目录的锁之下升级，别的进程打不开这份存储。服务器模式取所有权时，在租户的锁下先重读格式号：等锁期间别的进程已把存储升到比这个版本新的格式，就报 `format_too_new`，epoch 不加，这个进程不持有这个租户。之后在 epoch 加 1 之后升级，每一步按写事务的做法：取租户的锁，读 epoch 核对仍是自己取到的那个（不是就报 `ownership_lost`，这一步不做），在锁下重读格式号（别的进程已做完这一步就跳过），执行这一步的语句，改格式号，提交。所以两个进程同时打开同一个租户时，每一步只做一次；滚动部署中仍持有租户的旧版本进程，下一次写入时发现 epoch 变了，就放弃这个租户（`ownership_lost`），不会用旧格式的代码去写新格式的表；在新进程升级期间才来打开的旧版本进程，取所有权时在锁下读到新格式，打开失败。
  - **失败**：一步的语句出错时，打开报 `upgrade_failed`，消息写明失败的是哪一步与数据库的原始报错，另带数据库的 SQLSTATE。本地服务把它当作启动失败：留在失败状态，`/health` 报 `failed`（`upgrade_failed`）并带失败的那一步；服务日志只记那一步与 SQLSTATE，不记数据库的报错原文（原文可能引用存储里的值）。服务器模式下，打开这个租户的那次请求以 `internal` 回给客户端，服务日志记 `upgrade_failed`，带租户的 database、失败的那一步与 SQLSTATE，同样不记原文；`server restore`、`server user`、`server init` 打开租户时遇到，标准错误只写失败的那一步与 SQLSTATE 和怎么处理，退出码 5。
  - **磁盘满**：扩展数据文件时磁盘满是普通的语句出错（`upgrade_failed`，SQLSTATE `53100`）；写 WAL 时磁盘满则是 PANIC：本机模式下 worker 退出，打开报 `worker_failed`，下次打开时按 WAL 恢复，没提交的那一步不算数；服务器模式下整个 PostgreSQL 实例重启。升级之前不查磁盘余量。
  - **升级中**：本地服务在升级期间 `/health` 报 `starting`，另带 `upgrade`：从哪个格式升到哪个格式、正在做哪一步（写成 `5->6`；第一步开始之前还没有这一项）。服务日志逐步记下 `upgrading`、每一步开始时的 `upgrade_step`、做完时的 `upgraded`（带耗时）。服务器模式在租户第一次被打开时升级，日志同样逐步记，带租户的 database 名；`server restore`、`server user` 打开租户时升级，同样逐步写到标准错误。`saveslot start` 与 MCP 桥在升级期间怎么等，见 [`06-cli.md`](06-cli.md) §3。
  - **升级之后**，本机模式不看是否过期，做一次统计信息的收集（§7「统计信息」）。
- **导出不依赖物理格式**：导出 = 全部 (a) 类事件（schema 定义本身也是事件）；经 `apply` 重放，任何后端都得出同样的 (b) 类状态。(c) 类不导出。
  - "导出能重放"由测试验证（§11「导出重放」）；把一份导出装回去的用户操作是下面的导入。
  - **宽限期内的内容默认不导出**：待删除的内容块换成"待删除（#n），未导出"占位，同一事件的其余内容照常导出；事件头链照样可校验，导出的内容附校验和；用户会话可显式选择包含，导出回执写明。
  - 导出文件可以由 CLI 整体包在 age 文件里（口令加密）；包装不属于导出格式，内核与服务层都不碰它。
  - **导出不占着租户**：清单在第一个读事务里定下 `upto`，之后分批读，每批一个短读事务、只读 `seq ≤ upto`；等读取方取走数据（背压）发生在两个事务之间，所以读取方慢或暂停时，这个租户的其他读写照常。两个后端同一做法。每一批重查一次待执行的删除：没要求包含待删除内容时，出现了导出开始时没有的删除就中止导出（它的内容可能在后面的批里）。读取方 30 秒没取走一批写出的数据（初值，内核常量），服务端放弃这次导出、切断连接；读取方中途离开，下一次写出失败即停止读日志。切断与中止都不发结束块，读取方据清单的条数与 `upto` 认出这是残缺的。
- **导入只支持装进空租户**：把一份导出逐事件原样追加并交给 `apply`，不逐条重新执行契约操作（那样会重新判定、重新分配 `seq` 与 ID，得不到同一条日志）。租户是空的，当且仅当日志里只有创世事件，且锚点里没有删除登记、恢复次数为 0、没有"恢复进行中"与"导入进行中"标记。合并导入后续。规则与带不过来的东西（读取记录、凭证与控制面、源头的删除登记）的权威定义在 data-model「删除之后」与「完整性与溯源」；工程上的步骤：

  | 步 | 做什么 |
  |---|---|
  | ① 校验文件 | 与 `log.verify` 同一套检查（事件头链、内容校验和、条数与末尾），只是对象换成文件；边读边校验，任何一处不过就停 |
  | ② 重放到暂存的存储 | 新开一份按导入 ID 命名的租户存储，逐事件原样追加并交给 `apply`；内容块按导出里的三种状态落（在、已移除、待删除占位） |
  | ③ 收尾事件 | 在暂存的日志末尾追加导入事件，再对占位的待删除项补墓碑。① 到 ③ 出错（文件不合格在 ① 或 ② 被拒，③ 写不成）或 ④ 拒绝置标记时，租户不变：服务器模式先应答、放开独占，再在独占之外删掉这次的暂存存储，删完才把它从租户目录里去掉。租户不空在 ① 之前就拒绝，不建暂存存储；目录里若还记着一份上次留下的暂存库，同样在应答之后删掉 |
  | ④ 置标记 | `beginImport`：锚点里置"导入进行中"，同时再核对一次空租户条件 |
  | ⑤ 换入 | 暂存的存储换成目标租户的存储，丢弃原来那份（里面只有创世事件）。换入是一步原子操作：本机是目录改名（改名之后 fsync 数据目录的上级目录，在 ⑥ 写锚点之前落盘），服务器模式是租户目录里存储指针的一次更新。服务器模式里原来那份在导入应答之后、在独占之外删掉 |
  | ⑥ 重建锚点并清标记 | `endImport`：一次落盘写入由日志得出的删除登记（仍待执行的删除）、高水位（日志末端）与恢复次数（导入事件里的值），并清标记；之后对外服务 |

  - 导出可以来自导入过的租户，它的日志末尾可以就是那次导入的导入事件，导入照常：③ 只核对暂存日志的末端与清单的 `upto`、`upto_hash` 一致，不看最后一条事件是什么。也因此，"最近一条导入事件"不能说明 ③ 做过：④ 置标记之前先核对暂存日志里最近一条导入事件正是 ③ 这次追加的（`seq` 与 `imported_upto` 都与 ③ 给出的一致），它之后只能是 ③ 为占位的待删除项补的墓碑，不符就什么都不改。

  - **重入**：锚点存储与租户存储没有共同的事务，靠"导入进行中"标记重入。`openTenant` 最先看它；标记在时，租户存储里没有导入事件（崩溃在 ⑤ 之前）→ 丢弃暂存存储、`abortImport` 清标记，租户仍是空的；有导入事件（崩溃在 ⑤ 与 ⑥ 之间）→ 接着做 ⑥。判据只看有没有导入事件：目标原来只有创世事件，标记在期间又不接受别的导入。崩溃在 ④ 之前留下的暂存存储没有对应的标记，打开租户时一并清掉。服务器模式的导入先取得该租户在进程里的独占（期间其他请求报 `importing`，不排队），再建暂存存储，从建暂存存储起直到 ⑥（⑤ 的换入在内）都不放开独占：导入进行中租户不会被打开（第一版一个控制面库只有一个进程，§7），所以打开时看到的、没有标记的暂存存储只能是崩溃留下的，或是 ⑤ 换下、导入完成后没删成的那份旧库（导入在 ⑥ 之后先应答、放开独占，再删它；删到一半服务停了、崩溃或删不掉时，它仍记在暂存的位置，不会漏掉），或是一次在 ④ 置上标记之前失败的导入的暂存库（失败也先应答、放开独占，再删它，删完才从目录里去掉；删不成时同样留着），每次打开都可以清；接着做完 ⑥ 的那次打开，标记清掉之后也照此清掉它。没有标记时租户的数据是完整的，清不掉就记一笔、照常服务，下次打开再清；标记在时清不掉，这次打开拒绝。打开时遇到本进程里正在删的那份（导入应答之后的删除），交给那次删除，不等它：删成了它从目录里去掉，删不成仍记着，下次打开再清。新的导入在独占之内、记下自己的暂存库之前，先删掉目录里还记着的上次留下的那份；那份正在删时，等那次删完，再删一次（已不在就什么都不做），所以那次删除失败也不会让它漏记。
  - 没有这个标记，⑤ 之后、⑥ 之前的崩溃会让租户既不空、锚点又对不上：恢复次数仍是 0，下一次真正的恢复会把它加到 1，与导入后已发出去的 `ver` 重号；反过来先重建锚点再换入，崩溃后日志末端低于高水位，会被当成备份回退走恢复流程。
  - 导入期间与标记在时，这个租户不能读写（`unavailable`）；不支持断点续传，要么仍是空的、要么导入已完成，重试是安全的。
- **恢复备份、快照、冷租户归档之后必须走恢复流程**，再对外服务。0.1.0 尚未提供隐私删除，流程里按登记补删与补跑到期删除的部分是设计（[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。步骤与对照表的权威定义在 data-model「删除之后 · 删除登记」；要点：
  - 流程靠锚点存储里的"恢复进行中"标记重入：每次打开租户都看这个标记（打开时各项核对的次序见 §4 `openTenant`），标记在就接着做，不管这次启动带没带恢复参数。
  - 流程里先追加"恢复"事件（`seq` 从高水位之后接着编，换一个节点 ID，恢复次数加 1），再按登记补删，再补跑已到期的删除，核对无误后清标记、对外服务。
  - **触发途径三种**：显式（本机 `saveslot start --restored`，服务器模式的运维命令）；打开时发现日志末端的 `seq` 低于高水位；登记与日志对账时发现正常运行中不可能出现的组合。后两种发现时，本机模式自动走恢复流程（只有一个用户、没有运维，不拒绝服务），服务器模式拒绝对外服务并提示走运维命令。
  - **兜底的实际覆盖面**：回退到上一次高水位推进之前的位置能发现；回退落在最近一次推进之后、且期间没有删除相关的登记变化，发现不了。所以恢复应当一律显式触发，兜底只是补救。
  - 本机数据目录被系统级备份（Time Machine 等）连同 saveslot 配置目录一起恢复时，登记也回到当时，saveslot 补不了也发现不了；服务器模式下控制面库与租户库被一起恢复时同理。
- 外部文件不在存储里（`file_ref` 只存元数据与摘录，positioning「后续规划」）。

## 9. 租户与托管

- **内核只认"租户"，不认"用户"**：一个租户一条日志、一套 `seq`、一份存储。第一版租户 = 用户。
- **主体全局唯一，与租户无关**：用户、连接实例的 ID 是全局的；租户日志里记的是"某主体在本租户的登记（成员资格）"，引用全局 ID（K2）。
- **租户之上的归属关系在控制面**：哪个用户拥有哪个租户、哪些主体能访问，由租户目录管理。由此：
  - **共享 slot（将来）** = 一个独立租户 + 成员登记。会碰到的问题与归属：

    | 问题 | 在哪解决 |
    |---|---|
    | 别的用户的连接实例写入共享租户 | 内核：成员登记事件（已按此设计，K2 不用改） |
    | 一个用户的数据目录要合并列出多个租户 | 服务层 / 外化面：按租户目录聚合 |
    | 表名跨租户重名 | 外化面：限定名（已有） |
    | 句柄、`seq` 属于哪个租户 | 句柄绑定租户（已有） |
    | 共享租户的主节点放在哪、成员设备怎么复制 | 多节点设计（后续） |

  - **开发者采购托管（将来）** = 每个终端用户一个租户，归属"开发者 / 应用"，由租户目录表达；内核不变。数据归属与可导出性待定（open-questions「开发者 SDK」）。
- 云服务的集群分组、连接管理、冷租户导出与恢复，见 positioning「技术选型」与 research/07。
- **服务器自部署（第一版支持）**：与我们的云服务是同一套代码、同一组配置项，只是部署方不同。差别只有这几处：

  | 方面 | 我们的云服务 | 自部署 |
  |---|---|---|
  | 人的账户 | 我们的账户系统 | 内置的本地账户：部署方用运维命令创建，不开放注册；OAuth 授权服务器仍是 saveslot 自带的那一个 |
  | 规模 | 多 cell、多进程、冷租户归档 | 一个 cell、一个进程即可；多 cell 路由与冷租户归档不启用。这唯一的 cell 名字固定是 `main`：它会作为每个租户所在的 cell 记进控制面的租户目录，所以不随连接地址变 |
  | 对外地址与 TLS | 我们的域名 | 部署方提供，由部署方的反向代理终止 TLS，saveslot 进程只监听明文 HTTP（在进程里直接配置证书是后续）；OAuth 的资源标识（RFC 8707）取配置里的对外地址（`SAVESLOT_PUBLIC_URL`，[`06-cli.md`](06-cli.md) §4.1「服务器模式的配置」） |
  | 句柄签名密钥 | 环境配置（将来 KMS） | 环境配置（`SAVESLOT_HANDLE_KEY_FILE` 指向的文件），由部署方保管 |
  | 限流与配额 | 开 | 默认关，可配置 |
  | 备份与恢复 | 我们做 | 部署方做；恢复后必须走恢复流程（§8） |

  内核、服务层、契约、外化面完全相同；契约测试在自部署形态（单 cell、本地账户）上另跑一遍。

  **自部署的前提**（对数据库一侧）：
  - **PostgreSQL 18**：cell 所在的实例是 18.x（§8「租户存储」里后端与版本那张表），后端遇到别的大版本时拒绝打开租户。控制面库可以放在同一个实例上。
  - **服务用的数据库角色**：是控制面库的属主（`server init` 在里面建表）；在 cell 所在的实例上有 `CREATEDB`，并能连上维护库（建租户时在维护库里执行 `CREATE DATABASE`，租户库因此归这个角色所有）。不需要超级用户。
  - **物理删除后的明文残留**：要在原地清理，这个角色还要四项授权、实例要以 `wal_recycle = off` 运行（§7「残留清理在 PostgreSQL 上需要的权限」）；缺任何一项，这个部署的残留清理改用重建，重建期间那个租户不可写（§7「残留清理的做法」）。

## 10. 信任边界

| 用法 | 可信 | 不可信 | 能保证到哪 |
|---|---|---|---|
| saveslot 服务 · 本机模式 | saveslot 进程自己 | 经 MCP / HTTP 进来的一切：Agent、模型、脚本、客户端自报的信息、源数据原文 | 经接口的一切操作守住内核不变量，权限在 saveslot 进程边界上执行；**数据真实性与"确认是否出自人"委托给调用方 Agent**，saveslot 只保证留痕、确认绑定内容、删除可撤回。本机上能直接读写数据目录的程序（包括有 shell 的 Agent）绕得过 saveslot 的接口，saveslot 防不住 |
| saveslot 服务 · 服务器模式（云服务 / 自部署） | saveslot 进程与部署方的运维（云服务是我们，自部署是用户自己） | 同上 | 同上；对运营方不提供防篡改证明——完整性的目标就是溯源 + 防误操作（见下）。存储的静态加密由部署方在基础设施层提供（数据库存储卷、备份与冷归档放在加密的存储上），它防的是存储介质被带离之后被读，不改变运营方读得到明文这一事实 |
| SDK 嵌入（后续） | 宿主应用（数据的主人） | 模型、源数据原文 | 经 saveslot 接口的操作守住内核不变量；防不住宿主本身（它能直接打开数据库） |
| SDK 连接数据中心（后续） | 数据中心那一侧的 saveslot 服务 | 同 saveslot 服务 | 同 saveslot 服务 |

**表里的"不可信"是安全意义**：经接口进来的一切都不能绕过内核不变量。它不是质疑内容是否属实——saveslot 默认 Agent 的输入可信，不判断写入内容的真假（positioning「数据层」）。

**完整性的目标是能溯源 + 防误操作，不是防篡改**。权威定义在 data-model「完整性与溯源」：能发现什么、靠什么、不承诺什么都在那里。架构层面的要点：只有内核能写、日志只追加（K1、K3）；事件头链发现事件缺失、乱序与事件头被意外改动；内容校验和发现存储损坏；对拍发现物化状态与日志不一致。对能写存储的一方（含运营方）不防篡改，也不给第三方可验证的证明；签名检查点、Merkle 树、链上内容承诺是后续规划（§12）。

**遥测：默认不发送任何数据**。saveslot 程序（本机模式与服务器模式，含自部署）默认不向任何地方发送使用数据；本机模式不联网也能完整使用。将来若加入使用统计，必须同时满足：

- 由用户或部署方显式开启，未开启时不发送任何内容；随时可以关闭，关闭后不再发送。
- 只收运行环境与功能使用次数这类元数据；永不收用户内容（slot 名、表名、行、字段值、源数据、证据、查询与 SQL 文本、待处理事项的文本），也不收凭证与能识别个人的信息。
- 收集的字段在文档里逐项列出，与代码一致。
- 发出本机的崩溃或错误报告也算使用数据，同样要显式开启、不含用户内容；写在本机的应用日志不属于遥测。

我们运营的云服务对自身运行状况的监控是运营方观测自己的服务，不属于遥测；它同样不把用户内容写进监控数据。

**提示注入面**（都要包进不可信数据边界）：源数据原文与摘录、查询结果里的文本值、待处理事项的提议文本与 `note`、
schema 里由 Agent 写的说明与别名、写入回执里列出的已有的键与相近的键、抽取作业的 `instructions`、报错回显的用户输入、社区 schema 与 SKILL。
其中**后果不可逆的动作**（删除）另有两段式与 24 小时撤回窗口兜底；其余动作都保留历史、可回退。

- **slot 名进 MCP 的服务级说明（`instructions`）**，是静态文本里唯一的用户内容，不包边界。挡它的是：名字的字符集（字母、数字、下划线，不能换行、不能写标点与尖括号，伪造不了边界标签）；超过 32 个字符的 slot 名不列；每个 slot 单独一行、后面紧跟表数；新建 slot 要求 `saveslot.schema` 且范围为全部，能写进这里的一方很少。**表名不进 `instructions`**：任何有 `saveslot.schema` 的连接实例都能在默认策略下不经确认地建表，用前缀控制排序、把一句话拆到几个短表名上；表名留在 `saveslot_catalog` 的结果里，那里带不可信边界。残余风险：持有"`saveslot.schema` 且范围为全部"的一方仍能建出几个读起来像短语的 slot 名，后果不可逆的只有删除，有上面的兜底。
- 生成 `instructions` 不是契约里的读取操作，不记读取记录，也不参与 `ver` / `sv` 的兜底。

## 11. 代码组织

一个 monorepo（pnpm workspace），按层分包：

| 包 | 内容 | 依赖 |
|---|---|---|
| `contract-core` | 数据的形状：值编码、证据、标记、意图、领域错误；事件格式的类型 | 无 |
| `kernel` | §4 的全部模块与 `ops`；两个端口的接口；锚点存储的文件实现 | contract-core；存储只依赖 §8 的接口 |
| `store-pglite`、`store-postgres` | 两个后端 | kernel 的存储接口 |
| `contract` | 对外契约：操作定义、外化面专用的字段与错误；生成 OpenAPI 与 MCP schema | contract-core |
| `service` | §5 的全部组件，含控制面存储（文件、PostgreSQL 两个实现） | kernel、contract |
| `server` | HTTP 与 MCP 适配器、MCP 文本渲染器 | service、contract |
| `daemon` | 组装入口：选存储后端、组合服务层与适配器、读配置、启动进程；后台任务的调度器 | server、service、store-* |
| `client` | 由契约生成的 HTTP 客户端 | contract |
| `cli` | 命令行：一律经 `client` 走 HTTP（本机 unix socket，云服务 HTTPS），默认凭用户会话，也可凭连接实例令牌（[`06-cli.md`](06-cli.md)）；导出文件的口令加密与导入前的解密在这里做 | client；`age-encryption`（官方的 age 实现，锁定版本；内核、服务层、`daemon` 都不依赖它）。口令只从终端、文件或文件描述符读，Windows 上只支持口令文件 |
| `saveslot`（入口） | 可执行文件，只做分发：服务组命令（`init`、`start`、`stop`、`status`、`service`、`doctor`、`config`、`mcp`、`server …`）交给 `daemon`，其余交给 `cli`；`setup` 编排两边的命令（`init`、`start` 与 `slot create`、`connect`），放在入口包里 | cli、daemon |
| `connector-ts` | 写连接器的 TypeScript SDK。连接器是以连接实例的身份代用户写入 saveslot 的程序（05-surfaces 第 13 节），通常把某个外部系统的记录存进一个 slot：开发者描述连接器（manifest）、声明要写的 slot 与表、把记录对应成行；SDK 只经 HTTP 完成其余的事（slot 不存在时提交一份 schema 草稿把它连同表建好，已存在时只核对、不改；分批写入；幂等键、重试与请求头）。声明了来源键的表按来源键写入（同一批记录每次同步再交一遍，有则按三方比较更新、无则新增）；别名与改已有 slot 随服务的后续阶段加入（07-scope-v1）。第三方的令牌不经过它。其他平台的 SDK 不在本仓库 | 无（只用运行时的 `fetch`；本机服务的 unix socket 由调用方经 `setFetch` 接入）。任何包都不导入它；它的测试另可导入 `daemon`、`service`、`store-pglite`，以启动真实的本机服务 |
| `sdk`（后续） | 门面：同一套契约接口，后端可选"嵌入（kernel + service + 宿主策略）"或"远程（client）" | service、client、store-pglite |
| `reference`（私有，不发布） | 参考求值器（见下「测试矩阵」）：按定义写的删除重放与回掉，只作测试对照 | contract-core。不依赖 `kernel`；只有测试文件可以导入它 |
| `test-backend`（私有，不发布） | 测试开库用的后端（见下「测试矩阵」）：默认是 PGlite，新建的存储从本次运行按建库参数造好的模板复制，测「新建」本身的用例照常真新建；一次运行指明时换成 PostgreSQL，测试仍按数据目录开库，每个目录对应一个 database，各测试文件不变 | kernel、store-pglite、store-postgres。只有测试文件可以导入它 |

- **依赖方向**：`contract-core ← kernel ← service ← server ← daemon`；`kernel` 不依赖任何传输方式、不依赖 `service` 与 `contract`；适配器不能绕过 `service` 调内核。
  包级与模块级（§4）的依赖规则都写进 `pnpm check`，合并前必须通过（见下「CI 只调脚本」）。
- **包的命名**：npm 组织 `@fluxvita`。对外安装的包是 `@fluxvita/saveslot`，即上表的入口包（`bin` 是 `saveslot`）；其余各包叫 `@fluxvita/saveslot-<包名>`（`@fluxvita/saveslot-kernel`、`@fluxvita/saveslot-contract-core`……）。仓库是 `fluxvita/saveslot`。
- **发布**：入口包与它运行时依赖的各包（共 11 个：上表除 `connector-ts`、`sdk`、`reference`、`test-backend` 之外的）都发到 npm，`npm install -g @fluxvita/saveslot` 把它们一起装上。它们是 Changesets 的一个 fixed 组，**同一个版本一起发**；互相依赖在仓库里写 `workspace:*`，发布时换成精确版本，不写范围。对外承诺的只有入口包：其余各包的 README 开头写明是内部包，接口不单独承诺稳定。各包只带 `dist`，不带测试夹具与构建缓存。发布前在本机临时 npm 源上从安装走到 `saveslot status`（`pnpm smoke:install`），通过才发。服务器模式的容器镜像（`deploy/Dockerfile`）随同一个版本发到 GitHub 的容器镜像仓库，`ghcr.io/fluxvita/saveslot:<版本>`，含 linux/amd64 与 linux/arm64；正式版另打 `latest`，预发布不打。
- **工具链**：Node 24.22.1 及以上的 24 系，或 26.12.1 及以上（写进 `engines`；CI 日常检查固定在一个 24 系版本上，推到 `main` 或发布分支后与每晚另在 26 系上跑一遍）；TypeScript 严格模式，只发 ESM；pnpm workspace；测试用 Vitest，性质测试用 fast-check；格式化与 lint 用 Biome；模块依赖规则用 dependency-cruiser；构建是 `tsc -b`（项目引用）出类型与 JS，再由 `scripts/mark-bins.ts` 给可执行入口加上执行权限，不另做打包；版本与变更记录用 Changesets，1.0 之前用 0.x，事件格式版本独立于包版本。具体版本号在搭脚手架时取当时的稳定版并锁定，不写进规格。
- **CI 只调脚本**：检查项写成根 `package.json` 里的脚本——类型检查、lint、单测、性质测试、依赖规则、文档链接检查、文档里 JSON 例子可解析、断言索引指到的测试都在（[`11-claims.md`](11-claims.md)）、代码注释里用 `«…»` 引用的规格标题都在它点名的那份规格文件里、被跟踪的文件里没有合并冲突留下的标记行——CI 配置只负责调用它们（汇总脚本叫 `check`，本地 `pnpm check` 跑的是同一组；CI 把同一组分成静态检查、单测、性质测试三个作业跑，各有各的超时，一段超时不连累另两段的结果），所以换 CI 平台不用重写检查逻辑。
- **什么时候跑全套**：每个拉取请求上跑快检查（标题、签名、密钥、禁用词）和完整的 `pnpm check`（静态检查、单测、性质测试三段），改到导出加密相关文件时加互通测试，全部通过才能合并；作者推之前先在本地跑一遍 `pnpm check`。推到 `main` 或发布分支后再跑一遍，另加 Node 26 LTS 上的一组、PostgreSQL 上的测试与导出加密的互通测试；每晚在 `main` 上与手动触发时跑的也是这些。主分支变红时先修，暂停合并。
- **性质测试长跑是搜索，不是关卡**：它在单独一个工作流里，每晚在 `main` 上跑，也可以手动在任一分支上跑，推送不触发。它失败不算主分支变红，不挡合并，也不挡发布：发布只等上一条的 CI。每个失败的测试各开一个 issue，写明文件、测试、seed 与 path、反例和那次运行的链接；issue 未关时同一个测试再失败，在这个 issue 上补记，不另开。发布前在发布分支上手动跑一次，看它的结果和未关的这类 issue，未关的列进发布说明。

### 测试矩阵

- **两个后端各跑一遍**：内核测试在 PGlite 与 PostgreSQL 上各跑一遍。同一批测试文件经 `test-backend` 开库，后端由运行时的环境变量选定；只测某一个后端自身机制的测试文件（PGlite 的目录锁、属主文件、DB Worker、宿主 fsync）不在另一个后端上跑，逐个列出并写明原因，对应的机制在另一个后端自己的测试里测。内核的测试文件在 `packages/store-pglite/src`，经 `test-backend` 开库；PostgreSQL 那一遍由 `scripts/test-postgres.ts` 启动，它设 `SAVESLOT_TEST_BACKEND=postgres` 切换后端，连接地址由 `SAVESLOT_TEST_POSTGRES_URL` 给出。
- **重放对拍**：同一份日志在两个后端经 `apply` 重放，(b) 类里标"对拍：是"的表逐行一致（§8 的清单）；取值示例按确定性规则选（按 `seq` 取最近 K 个不同值）；另做"从空存储重放 = 线上状态"。
- **导出重放**：导出 → 向空存储重放 → (b) 类逻辑表与线上逐行一致，两个后端交叉各跑一遍（PGlite 导出重放进 PostgreSQL，反之亦然）；带"待删除"占位的导出，重放后日志末端的业务状态与线上一致。这是"导出能重放"这句承诺的检验。
- **墓碑之后从头重放**：删除到期、墓碑落账之后，从空存储重放，(b) 类里标"对拍：是"的表与线上逐表一致。必须覆盖四种：按字段佐证之后删除首次写入（值没变、只换了给出者的字段）；常量 `backfill` 之后删除（补值位置照记录，不因删除重算）；补键之后删除补键那次的证据（键回到让出它的原行，之后的同步按"被撤销的行不复活"处理）；只带起点的撤销停在被删写入给出的挡点上、删除后重新解析而空洞仍在，以及之后回掉过一次在空洞里的填值（空洞与"已被回掉"的登记都由删除结果给出）。
- **版本串不认识就停**：事件里的编译器版本、白名单版本（`compiled` 的与每条规则的）、规则版本、字面命中核对器版本取到内核不认识的值时，`apply` 停止并报错，不降级求值。
- **时区库版本不同**：跨版本对拍（导出 → 导入、双后端）时，两边的时区库版本不同，内部日期列与依赖它的派生值单独归为"时区库版本不同"，不算差异；版本相同时照常要求零差异。另测：改 `meta` 里记的版本后打开租户，内部日期列与受影响的派生分区按当前时区库重建，日志不追加任何事件。
- **导入**：导出 → 导入到一个空租户 → `log.verify` 与对拍都通过，(b) 类逻辑表与源头逐行一致（主体的状态除外：导入前仍有效的主体全部停用，已吊销的保持已吊销）；带占位的导出导入后，每一项占位的删除都补了墓碑，对应的 `deletion` 事项已关闭；显式包含待删除内容的导出导入后，这些删除仍待执行、登记进了锚点存储。
- **只有内核的一致性测试**：配一个空的服务层（可见范围全部、不做幂等等待）与文件实现的锚点存储，跑 K1–K14 的反例：
  - 不带匹配的事项版本解决事项必须失败；
  - 绕过 `apply` 改业务表必须被对拍发现；
  - 同一请求键重发只落一次；
  - 改一处内容不改校验和，`verify` 必须报不符；删掉或调换一条事件，事件头链必须断；
  - 隐私删除到期后，在整个存储里——事件头与内容、各版本物理表、事项、目录、索引（含键索引 `external_keys`）、派生写入的事件头、`derived_reads`、计数表、`premise_decls` 里的业务时间、read_log——用被删原文或由它算出的值都检索不到（唯一的例外是别的请求的请求键与显式幂等键指纹，它们是含原样带回的值的哈希，见事件格式 9.5；测试对它们单独断言"只在那次请求自己的证据被删时清除"）；
  - 确认删除 → 复制租户存储作为备份 → 到期物理删除 → 用备份覆盖租户存储（锚点文件不动）→ 打开之后，被删内容同样检索不到；
  - 删除确认后与撤回后，从空存储重放 = 线上状态；
  - 恢复备份后 `seq` 从高水位之后接着编，恢复前拿到的事项版本报 `confirmation_mismatch`、句柄报 `handle_expired`、`ver` 按版本对不上走冲突判据——都不会被当成当前版本接受；
  - 恢复流程在每一步之后强杀再启动，都不会在补删完成前对外服务。
  - 导入在每一步之后强杀再打开：目标要么仍是空的、可以重新导入，要么导入已完成；完成时锚点与日志一致（恢复次数等于导入事件里的值、高水位等于日志末端、删除登记等于日志里仍待执行的删除）。
  - 导入之后，导入前的事项版本报 `confirmation_mismatch`、句柄报 `handle_expired`；导入前的 `ver` 操作号不超过导入点的按原操作号判冲突，超过的以导入点为读到的位置。
- **参考求值器与性质测试**（第一版就做）：参考求值器是"某行 / 实体的写入事件 + 被删源数据集合"的纯函数，状态是"实体 × 字段 × 业务时刻 → 值或无值"，按定义写成最直白的实现，**不依赖 `kernel` 包里的任何判定代码**（含 `judge`），放在测试包里。性质分三组，见下。
  回掉（回退与回到合并基）在写入时与删除重放时怎么算，权威定义是 `03-data-model/03-deletion.md`「回掉的权威定义」里的伪代码：参考求值器照它实现；回掉的各种场景都转成它的固定用例与对拍用例。
  [`../process/walkthroughs/walkthrough-deletion.md`](../process/walkthroughs/walkthrough-deletion.md) 与 [`../process/walkthroughs/walkthrough-state-concurrency.md`](../process/walkthroughs/walkthrough-state-concurrency.md) 里的每个例子都写成一条"与参考一致"的用例。
  参考求值器要覆盖来源键：定位结果与基线位置照记录，同值按删除后仍在的同步贡献重算，没进事件的 op 不重放。一组完整的场景（同步 → 用户纠正 → 来源变化成为候选 → 采纳、保持或回到冲突前 → `undo` → 撤销与撤回 → 隐私删除其中一条源数据 → 撤回删除；补键之后的第一次同步；转移键之后删除原行的同步源数据）手推后转成固定用例；[`../process/walkthroughs/walkthrough-nutrition.md`](../process/walkthroughs/walkthrough-nutrition.md) 里的例子同样写成用例。参考求值器不需要知道前提：前提不参与取值。
- 契约测试对 HTTP、MCP（以及将来的 SDK）跑同一组用例；渲染器测试检查标记一定出现在文本里（含 `premise_changed`；原因是 `retroactive`、`plan_changed` 时带区间）。
- **限定范围的凭证**：HTTP 与 MCP 各用一个限定到 slot 的凭证把各操作跑一遍，断言范围外的 slot、表、字段的名字不出现在任何结果、报错、候选与提示里；按名字引用范围外的表与引用不存在的表报同一个错误，按 ID 引用范围外的目标报 `not_found`。
- **导出加密的互通测试**（`cli`）：`saveslot export --encrypt` 加密的文件，用 `age` 命令行解开，与明文导出逐字节相同；反方向 `saveslot import` 解开 `age` 命令行加密的文件。口令经 age 的非交互口令插件（`age-plugin-batchpass`）提供，CI 里没有终端也能跑。

#### 删除的性质

0.1.0 尚未提供隐私删除；这里是设计（[`07-scope-v1.md`](07-scope-v1.md) 第 7 节）。

| 性质 | 写法 | 抓什么错 |
|---|---|---|
| 与参考一致 | `delete(D)` 写进事件的结果 = 参考求值器在 D 下的结果 | `judge` 与 `delete` 的任何规则实现偏差 |
| 写入路径与参考一致 | 一串写入做完后的线上状态 = 参考求值器在被删集合为空时的重放结果 | `write` 一路调用 `judge` 的方式与定义不一致 |
| 顺序无关 | 先删 A 再删 B = 先删 B 再删 A = 一次删 {A, B}；比较状态与事项，不比较重述的下标与 `dropped` 条目；之后带旧 `ver` 的写入可能因删除历史不同而判定不同（删除按记下的区间算作改动） | 结果依赖删除历史 |
| 撤回还原 | 删 A 再撤回之后，未被宽限期内的写入覆盖的部分，与"从未删 A、但被记为保持生效的写入按在自己的写入号生效、事项被保持已被取代的写入也不生效"的重放结果相同（两者都没有时即与从未删 A 时相同） | 撤回漏放回的贡献、事项恢复错 |
| 不漏删（隐私不变量） | 结果里每个值、段端点、事项条目、翻译、分组键都不依赖被删源数据；到期后全库检索不到被删的值与由它求得的值，含原样带回它的后续请求、别的写入停在它上面的默认终点、回退与删除结果里抄下的区间（请求键的哈希除外，见事件格式 9.5） | 区间参数、翻译、事项条目这类漏删；无操作字段留下值的副本；求得的端点留在别的事件里（含写回项出自取值位置上相邻那一段的端点、经常量补值段转来的端点） |
| 无操作保持无操作 | 写入时是无操作的字段，任何删除之后仍是无操作 | 所见值被删后把原样带回的字段当成了改动 |
| 撤回写入回得干净 | 删除让某次写入的默认终点延伸之后 `undo` 它：该写入在任何业务时刻都不再生效 | `undo` 用了事件里的旧区间，留下回不掉的残段 |
| 回退不落回被撤回的值 | 回退之后做任何删除：被回掉的那几项在它们的区间上都不生效，该处的值等于重放里被撤回的那次操作之前的值（之前没有值就是没有值）；回掉的范围是被回掉项在重放里的区间扣除仍被之后的操作盖住的部分 | 搬运来源被删后落回了被撤回写入的值 |
| 重述后线上与参考一致 | 删除确认或撤回之后，来源表里每一项贡献的生效状态、区间、是否佐证 = 参考求值器给出的；之后任意一次写入的判定结果两边相同 | 删除事件没记下状态翻转，之后的默认终点两边解析得不同 |
| 不多删 | 值来源里不含被删源数据的值不变（同一实体内的段重排除外） | 宁可多删的规则用过了头 |
| 删除不增加未决事项 | 删除确认后，每个新出现的未决事项，要么是被这次删除取代的冲突事项转成的待确认，要么来自同一次写入原来的未决事项：原事项被先前的删除取代、因这次删除回到未决且种类没变的，恢复原事项；种类变了的（待确认 ↔ 冲突，原事项被这次或先前的删除取代），原事项保持已被取代，由一个新事项一对一接替 | 冲突消失的高影响写入直接生效，或凭空多出事项 |
| 已生效的保持生效 | 隐私删除的确认不会把写入时各项全部生效的（事件, 目标）变成候选或待确认，先前的删除是否已到期执行都一样；撤回一次删除只退回因那次删除才生效的写入（已被别的写入当作基线的除外，它们保持生效） | 方向限制没实现 |
| 原本未生效的写入生效必可见 | 因删除生效或转为待确认的写入都出现在预览、回执与事件里 | 悄悄生效 |
| 规则版本隔离 | 按某个规则版本与策略版本判过的写入与事项，在没有显式重判事件时，结果不因内核升级或策略变更而变 | 删除重放用了当前规则。第一版只有一个版本，测试用两份策略模拟 |
| 记录与重算一致 | 日志里删除 / 撤回事件的结果 = 参考求值器按该事件记下的规则版本重算的结果 | 线上 `delete` 的缺陷（"从空存储重放 = 线上状态"抓不到：重放用的就是事件里写好的结果） |

#### 时间的性质

| 性质 | 写法 | 抓什么错 |
|---|---|---|
| 逐点等价 | 带显式区间的写入生效后：区间内被写的字段 = 新值；区间外、以及没被写的字段不变 | 拆段算法的任何错误 |
| 默认终点可消去 | 默认终点的写入 ≡ 以"该字段在起点之后的第一个挡点"为显式终点的写入，逐字段；终点及之后的值不变 | 解析错终点；没按字段解析 |
| 顺序主键、无空段 | 同一实体任意两段不相交、没有空区间；版本表里同一实体的两个版本不在两条轴上同时相交 | 拆段留下重叠；版本区间没关上 |
| 拆分不变 | 把任意一段在任意点切成两段同值、同来源的段，再执行同一次写入：终点、高影响、同值、冲突的结论都不变 | 判定偷看了物理段边界 |
| 合并幂等、保快照 | 查询层合并前后每个时刻的值相同；合并两次 = 一次；合并后相邻段的值必不同 | 合并按错了列 |
| 同值写入不产生版本 | 与所见版本同值的写入：没有新版本、`ver` 不变；连写两次 = 写一次。例外：跨 schema 迁移的历史——`migrate` 不是单射（两个旧值映到同一个新值，或精度变小）时，旧版里的一次改值在新版里前后同值，它仍按原样是一次已生效的写入、仍有版本；这条性质只对同一个 schema 版本内的写入断言 | 同值判断的基准用错 |
| 不相交的写入可交换 | 同一字段上两次显式区间且不相交的写入，或两次起点不同的默认终点写入（都没有让所见版本里的变化点消失），先后顺序不影响最终状态，也不影响是否引出事项 | 冲突判据实现错；高影响判定偷看了对方刚造出的变化点 |
| 记录时间只追加 | 之后的写入不改变任何早于它的操作号上的 `as_of` 结果；隐私删除除外 | 版本表被就地改写 |
| 时间片一致 | `as_of: S` + `valid_at: T` = 把日志重放到操作号 S、再取 T；S 落在一次写入中间时等同于落在它的操作号 | 版本表用了行事件的 `seq` 而不是操作号 |
| 影响查询的结构性判据 | 读取被标 `possibly_affected` ⇔ 它问过的某个（字段，业务时刻）上，值在读取时的版本与现在之间不同。例外：schema 切换的补值不触发（可选改必填时之前读到空值的读取不标）；读过旧值的一方靠 `schema_updated` 提示得知 | 多报、漏报（含读过未来安排的）、撤标不全 |
| 追溯分类稳定 | 重放同一份日志，每次写入的"是否追溯"与当初一致 | 重放时用了当前时钟或当前时区 |

#### 冲突的性质

| 性质 | 写法 | 抓什么错 |
|---|---|---|
| 裁决确定 | 同一份日志从空重放，生效值、候选、事项状态逐项相同 | 判定用了日志之外的东西 |
| 永不阻塞 | 任意写入序列之后，每个有值的（字段，时刻）有且只有一个生效值 | 冲突让字段读不出值或读出两个 |
| 先提交者稳定 | 过期写入在成为候选的冲突单元上不改变生效值 | 候选悄悄生效 |
| 只挑不造 | 任一字段的生效值都等于某次写入给过的值 | 合并或回退时算出了新值 |
| 冲突判定对称 | 两次写入带同一个 `ver`，在对称一条的范围内（都不传终点、都不指证据、都没有让所见版本里的变化点消失）：先 A 后 B 判冲突 ⇔ 先 B 后 A 判冲突。范围之外已知的三处各写成一条固定用例，按当前判据的结果断言 | 判据依赖到达顺序；范围之外的结果被无意中改了 |
| 不冲突的并发写入可交换 | 两次写入带同一个 `ver`、在对称一条的范围内且两种顺序都不冲突：两种顺序最终的值相同，都不引出事项 | 合并结果依赖顺序；同值基准用错；高影响 ① 把对方刚造出的变化点算进了保护范围 |
| 合并不破坏已声明的约束 | 自动合并出的行满足 schema 的全部约束，含字段组 | 合并绕过校验；没按组判 |
| 争议标记完备且不多标 | 对未决事项的每个备选：采纳它会改变的读结果必带 `disputed`（派生行带输入标记）；采纳任何备选都不变的不带 | 漏标；按行多标 |
| 不丢写入 | 每次被接受的写入的每个字段的每一项恰好处于一种状态：生效过 / 在未决事项里当候选或提议 / 被一条有记录的决定关掉 / 被读过它所在事项的写入取代 / 无操作 | 候选无声消失 |

加回系统裁定时另加两条：逐个裁定 = 一次裁定；裁定只升不降。

#### 来源键与前提的性质

| 性质 | 写法 | 抓什么错 |
|---|---|---|
| 同一键至多一行 | 任意的按来源键写入、普通写入、撤销、补键与转移键（0.1.0 对转移键报 `not_in_this_version`）、`undo`（含撤回一次撤回）、删除确认、撤回删除、到期执行的序列之后：键索引里每个键至多一条，持有者至多一行。必须覆盖：删除补键那次的证据之后的冻结，再分别撤回与到期执行；撤销补了键的行之后再转被拒 | 转移键、撤回、删除交替时出现两行同键 |
| 被撤销的行不因同步复活 | 命中已撤销行的按来源键 op 一律被跳过；任何同步序列之后，被撤销的行仍是已撤销 | 同步把用户撤销的行写回来 |
| 重放后定位结果相同 | 从空存储重放、在另一个后端重放，每个进了事件的按来源键 op 落到同一行，键索引逐行相同 | `apply` 重新定位；键索引的维护依赖到达顺序 |
| 全部没变的同步请求不追加事件 | 全部 op 都是 `unchanged` / `skipped` 的请求，前后日志末端不变：除了回执，不留逻辑写入头、源数据与请求键 | 没变的同步留下头事件、源数据或请求键 |
| 拒绝过的来源值不在下一次同步时直接生效 | 冲突按"保持生效值"或"回到冲突前"解决之后：同步交来同一个值是无操作，交来新值是候选 | 基线值没算进候选；写回项被当成同步贡献 |
| 没变的声明，值就没变 | 随机的写入、回退、解决、删除、撤回、重申、清除序列之后，每条仍有效且状态为"没变"的声明，其范围上现在的值等于所见版本上的值。反方向不要求："比不了"时允许多报 | 漏打前提标记 |
| 记录的标记变化 = 按判据重算 | 对每条前提变化事件，用一个独立的直白实现从线上状态重算，与记录相同 | 检测的实现偏差 |
| 只换给出者不打标记 | 隐私删除只换了给出这个值的贡献、值没变时不打标记；删除之后仍是"已变"的声明，`since` 指向这次删除 | 按给出者而不是按值比较；`since` 指着一次什么都没留下的操作 |
| 重申不被当成重发 | 字面相同的两次重申，前提在两次之间又变过时，第二次不被当成重发 | 请求键没含解析后的前提版本 |

### 评测对实现的要求

评测（[`10-evals.md`](10-evals.md)）让真实的 Agent 经 MCP 完成任务，它不验证内核的正确性（那由上面的测试矩阵负责），但要求实现提供下面四样东西。它们只用于测试与评测，正常运行时不启用：

| 要求 | 内容 | 落在哪 |
|---|---|---|
| 测试时钟 | saveslot 服务能以给定的固定时刻启动，并在运行中被拨快。只换"入口取的当前时刻"的来源，内核不变（内核本来就不读时钟） | `daemon` 的启动参数 `--eval-clock`（`saveslot start` 同名参数传给它）；调度器用同一个时钟；拨快经本地套接字上用户会话的 `POST /v1/eval/clock`；规则见 [`06-cli.md`](06-cli.md) §3 第 3 步 |
| 步骤间快照 | 运行器能在两个步骤之间凭用户会话查询状态（行的值与 `ver`、事项、来源、读取记录） | 不需要新接口：用户会话的 `query`、`history`、`pending`、`sources`、`reads.list` |
| 调用记录 | 运行器拿到完整的工具调用序列：参数与宿主拿到的文字来自调用记录，契约结果来自服务端的评测结果日志。宿主不提供时，由 `saveslot mcp` 转发层记录 | `saveslot mcp --record <文件>`：只在评测时开的记录开关，格式见 [`05-surfaces.md`](05-surfaces.md) §11。MCP 的工具结果只有文本（[`05-surfaces.md`](05-surfaces.md) §3），宿主与模型拿到的也只有文本；结构化结果来自服务端的评测结果日志：以测试时钟运行时，服务把每次工具调用的连接实例、工具、参数与契约结果写进 `run/eval-results.jsonl`（每次启动新建：那个路径上已有的东西先删掉、是链接就删链接本身，再以独占方式新建；0600，不含令牌） |
| 确定性的种子数据 | 种子写入带显式的 `idempotency_key`，重装夹具得到相同的逻辑状态（行 ID、序号可以不同） | 评测运行器；不需要内核配合 |

| 多节点与同步 | `sync` 模块、事件的身份约定（§3） | 不实现 | 本地 + 云、多设备、嵌入存储并入 saveslot 服务 |
| 冲突期间的生效值规则 | slot 策略、策略版本 | 保持当前值 | 按来源级别的系统裁定，经重判事件作用于旧事项 |
| 日志的完整性 | 事件格式版本（新增版本，旧事件不追加） | 只串事件头 + 内容校验和：溯源与防误操作 | 签名检查点、Merkle 树、链上内容承诺、链外锚点——后续规划、按产品需要 |

**身份提供者**回答「这个浏览器请求是哪个人」。需要知道人的页面（OAuth 授权页、设备码页）只经它问，不直接碰账户的表。成员：

| 成员 | 做什么 |
|---|---|
| `currentUser(请求)` | 按提供者自己的登录态，给出这个请求的用户、`session`（这次登录的 ID：登录持续期间不变、不透明，不是 cookie 本身；同意表单的一次性令牌绑在它上面）、显示用的名字，以及这次登录的过期时刻（`expiresAt`，`toISOString` 形式的时刻）；没有登录就是没有 |
| `beginLogin(请求, returnTo)` | 把没登录的浏览器送去登录，登录后回到 `returnTo` |
| `paths` | 提供者自己应答的路径（本地账户：`/account/login`、`/account/logout`；外部登录：`/oauth/identity/callback`）。服务只对这些路径读请求的表单、交给 `handle`；请求体只能读一次，别的路径（如令牌端点）的请求体原样留给它们自己的处理 |
| `handle(请求)` | 应答 `paths` 里的路径；不是它的路径就不接 |
| `userState(用户)` | 启用、停用或不认识。停用：这个租户的全部凭证在认证时被拒；不认识按凭证无效处理 |
| `issueUserSession(用户, 来源)` | 签发用户会话：从一次登录（`currentUser` 给出的 `session`），从 `acceptAssertion` 刚接受的声明（只有有它的提供者收），或从一次刷新（带上那次授权的授予时刻 `grantedAt`；刷新时登录早已结束，没有登录可锁）。在控制面库的一个事务里先锁账户、再锁那次登录（刷新只锁账户）。账户在而不是启用状态（如已停用），从哪种来源都不签发，报账户暂不可用（`account_inactive`：再启用后照常）；提供者不认识这个账户、登录已结束或已过期、刷新的授予时刻不晚于账户的会话最后一次被结束的时刻（§5：本地账户改口令），都不签发，报登录已结束（`login_ended`：不会再好）；账户启用而用户没有启用的租户也不签发。会话写进 `credentials` |
| `acceptAssertion(声明, 来源)`（可选） | 只有外部登录有：核一份用于换会话的身份声明，给出用户与 `session`；第一次见到的账户在这里建租户，按来源计数：一小时内同一来源至多 5 个新用户，IPv6 地址按它所在的 /64 计，它所在的 /48 另记一份、至多 20 个；先查先记，表满时新的来源按已到上限处理。没有这个成员的提供者，令牌端点对这种授权方式回 `unsupported_grant_type` |

- 签发用户会话与改动账户的各条路径锁的先后一致：先账户那一行，再登录那一行。改口令先改账户、再删它的登录与会话，停用只改账户，登出只删登录；所以它们与签发不会互相等死。签发进行中改口令，要等签发提交，再把这个会话连同登录一起结束；签发进行中停用或登出，也等签发提交。
- 用户与租户的对应在控制面。用户的租户由第一个知道这个用户的实现建：本地账户在运维命令建账户时建，外部登录在第一次收到这个账户的有效身份声明时建。
- 请求的头、cookie、查询参数与表单交给提供者时是「名字 → 值」的映射，不是普通对象：`__proto__` 这样的名字与别的名字一样对待。每个名字一个值，名字重复出现时，构造请求的一方只取第一个；需要多值的调用方自己解析原始请求。
- `returnTo` 只收以单个 `/` 开头、路径在 `/oauth/` 下、不超过 4 KiB、只含可打印 ASCII（0x21–0x7E，原样写得进 `Location` 头）的值；带协议头或反斜杠的拒绝；路径部分（`?`、`#` 之前）不含 `.`、`..` 段，也不含任何大小写的 `%2e`、`%2f`、`%5c`、`%25`（再解码几次也解不出这几样）；超长的也拒绝，不截断；写进页面时一律转义。
- 提供者设的 cookie 一律 `HttpOnly`，`SameSite` 默认 `Lax`；对外地址是 HTTPS 时加 `Secure`；`__Host-` 开头的 cookie 必须 `Secure` 且路径为 `/`。

## 13. 第一版范围与演进

**第一版实现**：`contract-core`、`kernel`（不含 `sync`、`jobs`）、两个存储后端、`contract`、`service`、`server`（HTTP + MCP）、`daemon`、`client`、`cli`、入口包。
不做：SDK、多节点与同步、抽取作业与大写入作业、调用模型的后台执行方（worker）、文件存储、防篡改（Merkle、签名检查点、链上内容承诺）、表级与字段级的数据权限、合并导入、共享 slot。完整范围见 [`07-scope-v1.md`](07-scope-v1.md)。

**0.1.0 与第一版的差距**：0.1.0 是第一版的一部分，尚未提供隐私删除、需要重建物理表的迁移（含 `change_timezone`、`change_time_field`）、重放对拍（`log.reconcile`、`saveslot verify --replay`）与修改 slot 策略；read_log 的保留期清理与高水位的定期推进两项后台任务也尚未接入。逐项见 [`07-scope-v1.md`](07-scope-v1.md) 第 7 节。

**将来做 SDK 时内核不用改的保证点**（第一版就要满足、并在测试里检查）：

| # | 保证点 | 怎么检查 |
|---|---|---|
| 1 | `kernel` 不依赖传输方式、`service`、`contract`；能在 Node、Bun、Electron 主进程里单独实例化（其他运行时未核实） | 包 / 模块依赖检查守住前半句。能在三个运行时里单独实例化这一条目前没有测试覆盖（嵌入运行时的冒烟测试尚未建立） |
| 2 | 存储位置由调用方传入，内核不写死路径；单写者、epoch、格式版本检查在内核里 | 测试都在调用方传入的临时目录里开库；两个进程同开一个目录必须报错 |
| 3 | 内核不变量 K1–K14 只依赖 §8 的两个端口，不依赖任何服务层组件 | 只有内核的一致性测试 |
| 4 | 确认以"确认记录"（内容哈希 + `seq`）进内核，交互方式由外化面或宿主决定 | 同上 |
| 5 | 可见范围在调用上下文里，第一版就经过目录、查询、SQL 改写、写入的执行路径 | 用 `scoped` 到表一级的可见范围跑目录、查询、受限 SQL、写入测试：按名字引用没列出的表、字段，与引用不存在的名字报同一个错误——该操作对不存在的名字本来报的那个（`unknown_table` / `unknown_field`；`sql` 报 `sql_rejected`（`unknown_name`）），附带的最接近的名字只取可见的；按 ID 引用不可见的目标报 `not_found`（写进 `ref` 字段的行 ID 指向不可见的行时，报的与目标不存在相同：`validation_failed`（`ref_not_found`））；派生表可见当且仅当它依赖的表与字段都可见 |
| 6 | 对外契约从 `contract` 生成；内核只依赖 `contract-core` | 依赖检查 |
| 7 | `ops` 调用上下文冻结、可序列化（为非 JS 宿主的 sidecar 留路） | 上下文的序列化往返测试 |
| 8 | 到期任务在打开存储时补跑，不依赖常驻进程 | 关闭 25 小时后打开，宽限期已过的删除必须先完成 |

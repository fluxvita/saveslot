# saveslot · 第一版范围

> 本文只定"第一版做什么、做到哪、按什么顺序做"；机制本身的定义以 positioning、architecture、data-model、contract、surfaces 为准，未定项见 [`08-open-questions.md`](08-open-questions.md)。

## 1. 结论

**第一版 = 一个能在本机模式（PGlite）和服务器模式（PostgreSQL；我们的云服务与用户自部署是同一套）两种单节点上跑的 saveslot 服务：内核守住 K1–K14，事件格式一次定全；
外化面只开到 eval 1–4、6–10 与 eval 5 的前半需要的程度（eval 11 从 P1 结束起跑，只出数字、不挡阶段）；schema 变更只做不需要抽取的那几类，删除只做撤销与隐私删除，导入只做导入到空租户。**

- 机制清单共 107 项：做 70 项、简化 18 项、后续 19 项（第 3 节，按表中的行计）。
- **没有一项需要放松 K1–K14。** 有几处是不变量的适用面变小（功能没开，规则自然不触发），完整列举见 architecture §3「第一版里适用面变小的不变量」：K5（不做大写入作业，派生值不允许落后，等于更严）、K8（不做系统裁定，生效值规则只有"保持当前值"）、K10（影响查询不覆盖对派生值的读取）、K11（不做删除证据、按行隐私删除与抽取作业，与它们有关的规则不触发）、K12（没有后台抽样对账：第一版不主动发现绕过 `apply` 的改动，要用户运行 `saveslot verify --replay`）。
- 参考求值器第一版就做（覆盖第一版的删除种类），"记录结果 = 参考重算"有对照实现。
- **抽取作业不属于第一版**，是第一版之后的第一个增量（第 4 节 P4b）。
- 工作量见第 6 节：各阶段的数字是阶段调整之前的粗估，尚未重估。

## 2. 取舍原则

1. **会改事件格式的，第一版必须做，至少在事件格式上留位。** 判据：将来加回来时，旧事件里缺的信息补不回来（例如字段级值来源、字面命中、原始传参与解析结果、内容与事件头分离、事件的身份、规则版本与策略版本）。
   这类东西即使第一版没有用到它的功能，也要写进事件。
2. **会违反或要放松某条 K 的，第一版必须做。** K1–K14 是"任何用法都关不掉"的承诺，第一版不能以"先不做"为由打折；只允许"适用面变小"，并写明。
3. **只影响外化面、或能纯增量加回的，优先砍或简化。** 纯增量 = 新增事件类型 / 事项类型 / 工具 / 端点，旧数据不用迁移、旧事件照常重放（事件格式版本只增不改，architecture §6）。
4. **eval 能跑起来优先于功能完整。** 每一步都以"解锁哪个 eval"为验收；eval 结果会反过来调工具描述、数值和部分范围。**验收按 eval 规格执行**（[`10-evals.md`](10-evals.md)）：每个任务的夹具、话术、对存储状态与调用的断言、评分细则与通过线都在那里；surfaces 第 12 节的列表只是场景描述。
5. **云服务的法律底线不能砍。** 对外收费的云服务必须能做隐私删除、能导出，所以这两项不随"简化"一起后移。
6. **关键取舍写明理由与不做的替代方案**（第 5 节）；仍未定的记在 open-questions，不在本文硬判。

**事件格式的冻结点**：事件格式 v1（[`09-event-format.md`](09-event-format.md)）在 P0 定稿，第一次对外发布本机模式之前冻结，此后只增不改。开发期间（P1–P4）产生的日志不承诺兼容——否则 P1 的事件里没有 P2 才实现的判定结果，按原则 1 就已经是补不回来的缺口。

**事件格式 v1 现在可以冻结**：块的形状与词表已定。"回掉（回退与回到合并基）+ 删除重放"这一块以 [`03-data-model/03-deletion.md`](03-data-model/03-deletion.md)「重放规则 · 回掉的权威定义」的伪代码为权威定义。开发时**先实现参考求值器**（照伪代码写，不依赖内核的判定代码），再实现线上的 `judge` / `delete` / `apply`，用性质测试把两者对拍，并做整库检索不漏删的测试。设计阶段手推过的场景记在 [`../process/decisions/pre-dev-w6-final-fixes.md`](../process/decisions/pre-dev-w6-final-fixes.md) 的附录 A–I，它们要逐个转成测试用例（参考求值器的固定用例与对拍用例），不再靠手推。

|---|---|---|---|
| 删除做到哪 | 撤销 + 按源数据的隐私删除，宽限期、撤回、删除登记、恢复流程、到期物理删除齐全；参考求值器（覆盖这两种删除）与性质测试第一版就做。删除证据、按行隐私删除后续 | 云服务要能实现被遗忘权才能对外收费；删除的定义就是参考语义，求值器是它的可执行版本 | 只做撤销：云服务没有被遗忘权的实现。一次做全（加删除证据、按行）：多出的部分都能纯增量加回、不改事件格式，不必挤进第一版 |
| schema 变更 | 只支持只改元数据 / 删字段 / 确定性转换（P4）；抽取作业与 `migration_diff` 全套（P4b）不属于第一版，事件格式现在留位 | 抽取是最复杂、最依赖 eval 5 调参的一块；没有调用模型的后台执行方（worker），全靠调用方 Agent 循环做完，这是否现实要 eval 5 先回答 | 含抽取全套，或含抽取但只给 `accept_all` / 逐行 / `abandon`：都要先有 eval 5 的结论。代价：eval 5 在第一版只能跑前半，"加字段后从源数据补抽"也没有 |
| 冲突的多候选 | 做：同一冲突单元上后续的过期写入并入同一冲突事项，`candidate` 指明采纳哪个 | 合并事件本来就要有；多出的工作主要在删除重放里按候选逐个判断 | 第二个过期写入报 `read_first` 一类错误：违背"永不阻塞"。每个过期写入各开一个冲突事项：违背"不堆积" |
| 系统裁定 | 不做：第一版生效值一律保持当前值（先提交者）。级别、字面命中、规则版本与策略版本照常写进事件 | 省掉 `applied_by_rule`、"候选成为生效值后事项仍未决"、删除时"级别变了重新裁定"三处最绕的规则；需要的信息第一版都记下了，加回时旧事项经显式的重判事件改判 | 按字面命中的来源级别当场改生效值、触发影响查询：要多实现上面三处规则，而晚做不丢信息 |
| 状态类表的区间写入 | 做全：`valid_from`、默认终点、显式 `valid_to` / `open`、带区间的撤销、无值区间 | 拆段算法与只做 `valid_from` + 默认终点是同一套，做全只多参数与高影响 ① 的判定 | 只做 `valid_from` + 默认终点：省得不多。不做区间、状态类表只"从现在起变"：状态类表退化成普通表，eval 4 无从谈起，也丢了"时间是一等公民"这一独特性 |
| 事件头与内容的编码 | RFC 8785 JCS；哈希与校验和都用 SHA-256 | TS 生态现成、可读，调试与导出（NDJSON）一致；全系统只用一种算法，运行时自带 | 确定性 CBOR：体积小，但体积不是第一版的瓶颈。校验和用 CRC：够用，但多一种算法 |
| 把日志装回去 | 只支持导入到空租户（P5）：校验文件，逐事件经 `apply` 重放，原有主体一律停用，凭证由用户重新签发；"导出 → 向空存储重放 → 对拍"仍是测试 | 两件难事都绕开：目标是空的，没有可合并的东西；主体不做对应，历史里的 actor 原样保留。这条路径本来就是第一版的测试，导入是给它加上校验与收尾。服务器模式上线时正是本机用户需要搬数据的时候，所以放 P5，不放先发布的 P6 | 维持只有导出：数据双向迁移只有一半。带合并与主体映射的完整导入：要回答两条日志的 `seq` 怎么交错、同名 slot 怎么办、两边的删除登记怎么并，是多节点的问题。逐条重新执行契约操作：会重新判定、重新分配 `seq` 与 ID，得到的不是同一条日志，`verify` 也对不上原来的链 |
| 确认环节 | 保持委托给调用方 Agent；slot 策略的结构里为"某类操作只接受用户会话确认"留位，不实现 | 只经 MCP 时分辨不了确认出自人还是 Agent，硬加一道检查只是形式；兜底是高影响写入不直接生效、删除可撤回、每次确认留痕 | 第一版就要求高影响操作由用户会话确认：要在没有 App 的情况下让人经 CLI 逐项确认，eval 4、7 的流程走不通 |
| App | 不进第一版：人的环节由 CLI + 调用方 Agent 承担 | 确认已委托给调用方 Agent，App 是增强面；实验 6（桌面打包）有结论后再看 | 做最小 App（待处理事项、删除撤回、审计查看）：第一版的流程不依赖它 |
| 发布顺序 | 先发本机模式（P1–P4、P6），服务器模式（P5：云服务与自部署一起）随后；服务器模式上线前隐私删除（P3）必须已完成，"删除后保留的元数据"的法务结论必须已拿到 | 本机不需要 OAuth、控制面库、多租户，能更早拿到真实使用数据 | 本机与云服务一起发：拖后拿到真实使用数据的时间 |
| 多段证据 | 不提供按字段声明"任一即可"（`any_of`）；一个字段引用多段证据时一律"同时需要" | 与 data-model「删除 · 来源」的默认一致：不知道值出自哪一段时，这是唯一不会少删的规则；要区分就用 `evidence_by_field` 按字段映射 | 按字段声明 `any_of` |

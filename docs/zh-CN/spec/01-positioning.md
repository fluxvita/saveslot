# saveslot · 定位

> saveslot 的方向是 **Agent Data Infra**。调研材料见 [`../research/`](../research/)。
>
> 本文是定位与边界；数据层机制见 [`03-data-model/`](03-data-model/README.md)，操作契约见 [`04-contract.md`](04-contract.md)，外化面见 [`05-surfaces.md`](05-surfaces.md)（MCP、HTTP）与 [`06-cli.md`](06-cli.md)（CLI），事件格式见 [`09-event-format.md`](09-event-format.md)，第一版范围见 [`07-scope-v1.md`](07-scope-v1.md)，待定项见 [`08-open-questions.md`](08-open-questions.md)，面向初次接触者的讲解见 [`../guide/`](../guide/README.md)，一个从头走到尾的例子见 [`../guide/02-walkthrough.md`](../guide/02-walkthrough.md)（讲解与规格不一致处以规格为准）。

## 一句话

saveslot 是给所有 Agent 用的数据底座：跟踪会随时间演变的事物，保留从原始证据到当前状态的完整时间线；
数据归用户所有，不绑定任何一家模型或宿主。

saveslot 的本体是**一套数据与工程架构（内核 + 服务层 + 操作契约）**；对外有两种产品形态，见「产品形态」。

## 服务对象

**理论上服务所有 Agent**，不为某一个宿主或某一个上层产品定制。

- 上层产品建在 saveslot 之上，saveslot 不是某个产品的后端。例如记账应用、运动记录、项目跟踪这类产品，做成"由 Agent 来记、来查"的版本时，可以把数据层交给 saveslot（见「上层产品与 saveslot 的关系」）。
- 我们自己的 Agent 产品和第三方 Agent 是同等的接入方。
- **Agent 开发者**（后续版本）：用 saveslot 的 SDK 让自己的 Agent 长期维护数据状态，见「产品形态」。
- **不能过于通用。** saveslot 要有独特性（不是又一个数据库或 Memory），同时撑得起足够多的业务场景。

## 产品形态

**同一个内核，两种产品形态。** 第一版只做 saveslot 服务；架构必须撑得住开发者 SDK，将来不改内核。

| | saveslot 服务（第一版） | 开发者 SDK（后续版本） |
|---|---|---|
| 给谁 | 用户：一个人的数据底座，他用的所有 Agent 共用 | Agent 开发者：作为组件嵌进自己的 Agent，帮它长期维护数据状态 |
| 数据在哪 | 用户选：本地、私有服务器、我们的托管 | 开发者选：嵌在应用本地（位置由应用决定）、开发者自建的数据中心、或采购我们的云上服务 |
| 数据归谁、谁可信 | 归用户；Agent 与模型都不能绕过内核不变量（安全意义上不可信；写入内容默认可信，见「数据层」） | 嵌入时归应用，宿主应用可信、模型不可信；连接数据中心时同 saveslot 服务 |
| 外化方式 | HTTP、MCP、CLI（第一版）；App（后续） | 进程内的库接口；连接数据中心时走同一套契约 |

- **我们能控制的是开放哪些接口，控制不了开发者怎么用。** 所以 saveslot 的独特性必须落在**内核不变量**上（完整清单见 architecture §3 的 K1–K14：日志是唯一事实来源、每次写入都有源数据、
  派生只由规则生成、schema 版本不可变、两条时间线、冲突是持久状态、删除按血缘级联、读取留痕、确认绑定内容……）——任何用法下都关不掉；
  身份、权限、确认的交互方式等是**服务层策略**，saveslot 服务里由 saveslot 实现且必须开启，嵌入时可由宿主提供。
- **契约与后端无关**：SDK 的同一套接口，后端可以是嵌入的本地内核、开发者自建的 saveslot 服务、或我们的托管；开发者切换后端不改业务代码。
- 嵌入的存储将来可作为一个节点，经同步协议并入用户或开发者的 saveslot 服务（是否这样做，SDK 设计时定）。

## 场景判据：持续跟踪的事物

saveslot 关心的不是某一刻的数据，而是**会随时间演变的事物**。同时满足三条就是 saveslot 的场景：

1. **有稳定的身份**：它是"某一样东西"（这个项目、我的跑步、这本账），不是一句零散的话。
2. **会变化或累积**：值会改、记录会增加、状态会推进、文档会修订。
3. **后续有人依赖**：之后的会话或 Agent 需要它的当前样子或历史。

可计量的"值"只是一种形态；记录流、进度、偏好、带理由的决策、反复修订的文档都算。

**适用范围：按人的节奏产生的记录。** saveslot 为每一行保留全部版本与它的来源，每次写入同步刷新受影响的派生值；这些保证的代价随行数增长。第一版面向的是一个人说出来、做出来、决定下来的事：一次跑步、一笔支出、一次预算调整。设备按秒、按分钟自动产生的读数（心率、血糖、步频）不在这个范围内——saveslot 不拒绝它们，但不为它们优化，行数过界时数据目录与 `saveslot doctor` 会提示。这类数据的建议做法是存汇总（每次活动一行、每天一行），原始序列留在来源处，用证据指过去。实测的界线见 architecture「容量边界与实测数值」。

**独特性：时间是一等公民。** 数据库存现在，Memory 存说过的话；saveslot 存一样东西的时间线——
现在是什么、怎么变成这样、每一步凭什么。

## 数据层（细节见 [`03-data-model/`](03-data-model/README.md)）

- **slot**：一组相关的表 + 它们的源数据（如健康、记账），是 schema 版本、时区与 slot 策略的单位，也是一次隐私删除的范围，以及凭证授权范围的最小单位（连接实例可以限定到若干个 slot）；表级、字段级的数据权限是后续；每条源数据属于且只属于一个 slot。归属节点、复制、按 slot 导出与整体删除也以 slot 为单位，第一版不做（第一版导出的是整个租户）；将来做加密时也是密钥的单位。
- **两层数据**：只追加的源数据日志（按 slot 组织）之上，是按 schema 抽取的有模型数据；上层只看后者，可追溯到前者。
- **每次写入都有记录**：日志记这次请求涉及的字段的值（不记写入前的值，也不记写入后的整行；之前的状态由更早的事件得出），来源表记由哪些源数据或上游写入引起（字段级，分值来源与操作来源）；读取另记 read_log（只记版本）。
- **可回溯即证据，完整性的目标是溯源 + 防误操作、不是防篡改**：链只串事件头（事件头里不放任何由用户内容算出的值），内容分块单独存放、配校验和；纠错是新的源数据，不改历史；隐私删除的结果按参考语义定义——假如被删源数据从未存在过、按 `seq` 重放日志得到的状态，两处有意偏离：人的决定照记录、已经生效过的写入保持生效（事件类表与状态类表同一套，撤回也用它），内容块直接物理删除、事件头保留、留墓碑；恢复备份时按日志之外的删除登记补删。
- **日志是唯一事实来源**：所有状态要么是日志事件，要么由日志确定性算出，要么是写明"丢了会怎样"的本地运行状态；导出就是日志，任何后端重放出同样的状态（见 architecture §3）。
- **写入：Agent 理解、saveslot 把关**：模型只填意图（新增 / 变更 / 纠错 / 撤销）、表、行、值、证据，并原样带回读取时拿到的版本标记与 schema 版本，其余由服务端补全；每次写入都有源数据（没带证据就把请求本身存为源数据）；来源级别优先采集、字面命中在写入时判定并记进事件（将来按来源级别裁决冲突时只认字面命中的级别；第一版冲突一律保持当前值）。
- **读取：快速、准确的数据供给**：意图分析与查询拆解归 Agent；saveslot 提供详细的数据目录（含表间关系、数据概况、单位）、简单查询 + 只读受限 SQL（与派生规则共用引擎）、按时刻读、历史按需展开；变化告知由 saveslot 提供能力、产品决定用法。
- **核心不依赖模型**：确定性内核负责存储、校验、版本、冲突、权限；抽取优先由调用方 Agent 完成，模型输出记入日志。
- **动态 schema**：用户自有 + 官方精选 + 社区 Schema + SKILL。schema 文档读写同一形状的 JSON：表内整份、slot 内只交改动、删除显式；名字由 Agent 写，ID 由 saveslot 分配回填；单位写在类型里，写入同量纲自动换算（见 data-model「schema 文档格式」）。
- **派生表完全由规则生成**：Agent 只写基础表；派生规则是 schema 的一部分（首版受限 SQL），派生缓存随基础写入同步刷新，不存前后值。
- **schema 版本演进**：版本不可变、字段用稳定 ID；迁移分只改元数据 / 确定性转换 / 重新抽取三种，执行由 saveslot 自动完成，迁移函数由起草 schema 的 Agent 写，破坏性改动与重新抽取的差异须确认；对外只有最新版（读取结果自带单位与版本；版本按 slot 管理，但只拒绝写到不兼容变化字段的旧版写入），变更走状态机、后台构建原子切换，读永不停；兼容官方 schema 就是一张派生视图。
- **数据真实性与确认委托给调用方 Agent**：saveslot 不保证写入数据属实、也不区分确认出自人还是 Agent（只通过 MCP 分辨不了）；saveslot 保证留痕、确认绑定内容、删除 24 小时内可撤回。将来 saveslot 自己做来源接入与分析时，那条路径的真实性由 saveslot 负责。
  **默认 Agent 的输入可信**：saveslot 是被动的被调用方，不判断内容是否属实；写入时的检查只是确定性校验（类型、单位、范围、版本），用来保证数据形状正确，不是对来源的不信任。不可信数据边界只用于**读出**的内容（防止它误导读取它的 Agent），不用于质疑写入。
- **来源完整性有边界**：saveslot 内部的来源链可保证；经过 Agent 的一段只能校验（确定性、统计异常、证据核对），污点追踪作为可选项。
- **冲突是持久状态**：写入时检测（按字段；状态类表按字段 + 业务时间区间，不相交就合并）、读取时带出、永不阻塞、待处理事项不过期（saveslot 不替人裁决，靠合并与取代不堆积）、记录读取。

## 分层与接入面

**saveslot 的核心是内核、服务层与操作契约**（见 [`02-architecture.md`](02-architecture.md)）；HTTP、MCP、SDK、CLI、App 都是契约的外化面，地位相同。
在 saveslot 服务这一形态里：HTTP 是网络上的基础协议，MCP 是 Agent 的基础接入面；其他都是按场景加的增强。
**saveslot 的正确性不能依赖任何外化面存在**——检查与不变量都在内核与服务层里。

MCP 只能保证 Agent "能"读写，保证不了它"会"在对的时候读写——调不调、何时调由模型决定。
增强面补的正是这一点。

| 接入面 | 定位 | 补什么 |
|---|---|---|
| HTTP API | 基础协议，必备 | 没有 Agent 的调用方（用户用 Agent 做出来的脚本、程序、连接器）直接接入 |
| MCP | Agent 的基础接入面，必备 | 读、写、查询、校验；任何支持 MCP 的 Agent（含云端）都能用 |
| 宿主插件 / hook | 增强，可选 | 时机：会话开始、任务前强制读，变化时触发写 |
| CLI | 增强；**第一版必备** | 其他 harness 的 hook、脚本、导出、调试。第一版不做 App，人的环节（签发连接实例、确认、冲突裁决、删除与撤回、审计查看）由它承担，见 [`06-cli.md`](06-cli.md) |
| App | 增强，可选（后续版本） | 人的环节：确认、冲突裁决、回退、审计查看 |
| 开发者 SDK | 另一种产品形态（后续版本） | 见「产品形态」 |

接入的设计要求：不论哪种部署方式，接入一个宿主的流程里，用户最多做选择和一次同意，其余步骤由 saveslot 完成；以后新增的接入方式都按这条检查（细则与已知例外见 [`06-cli.md`](06-cli.md) 第 1 节）。

## saveslot 管什么，不管什么

| saveslot 管 | saveslot 不管（留给上层） |
|---|---|
| 源数据日志、slot、回溯 | 面向终端用户的产品体验 |
| 有模型的数据：当前状态、版本、按时刻读 | 协调层：调度、放置、迁移 |
| 来源权威与证据链 | 意图分析与查询拆解：读什么、怎么组合（归 Agent） |
| 动态 schema 机制 + 官方 schema | 具体业务规则与领域计算 |
| 身份与权限：按连接实例授权（scope × slot 范围）、审计 | |
| 冲突检测与处理（见 [`03-data-model/09-references-conflict-sync.md`](03-data-model/09-references-conflict-sync.md)「冲突处理」） | |
| 导出与导入到空租户（第一版）；合并导入、迁移流程、节点间日志同步（后续） | |
| 连接器写入时需要的准入能力：按连接实例授权并可限定到 slot、来源键 | 连接器本身：定时运行、调用外部系统、保管第三方系统的授权令牌 |

原则：

1. **MCP 接口按最差宿主设计。** 没有 hook、只靠 tool 描述也要能用：读要便宜、只回最小必要状态；
   写要能拒绝与降级（进待确认）。
2. **身份与权限归 saveslot（saveslot 服务形态）。** 同一份数据被多个 Agent、多种接入面访问，只能由 saveslot 统一管；SDK 嵌入时由宿主提供（见「产品形态」）。
3. **语义机制在 saveslot，语义内容可来自用户、官方、社区。** saveslot 不被某个产品的领域绑住。
4. **连接器是接入方，不是 saveslot 的一部分。** 定时把外部系统的数据搬进来的程序由官方或开发者各自编写，以一个连接实例的身份经 HTTP 写入，与其他接入方同等对待。第三方系统的授权令牌由连接器自己保管，不进日志，不进 saveslot 的任何存储。手机或其他设备上的采集程序只能配合服务器模式：本机模式只供本机访问。

## 部署形态与同步

> **第一版只做两种运行模式**：① 本机模式——用户在自己的电脑上启动 saveslot 服务，这台机器上的 Agent 共用；② 服务器模式——我们运营的云服务，或用户在自己的服务器上部署的同一套，任何地方的 Agent 都可以远程连它。两者都是**单节点**：一个用户的数据只在一个地方。
> 第一版不做的是"同一份数据同时放在本机与云端（或多台设备）、互相同步"，以及由此而来的离线写入（见「后续规划」）。多台设备、本机与云端的 Agent 要共用数据，就都连同一个服务器模式的 saveslot。下面的多节点设计保留为方向，第一版只要求事件身份等结构不挡将来的路。

**开源。** 用户可以自行安装使用；我们同时提供云服务，给没有能力自己安装的用户。**自行安装两种都支持**：在本机启动 saveslot 服务（本机模式），或在自己的服务器上部署服务器模式——与我们的云服务是同一套代码（PostgreSQL、远程访问、OAuth、控制面库），在第一版的测试与支持范围内。下文与其他文档里写"云服务"的规则，除限流配额与我们自己的运维安排外，都适用于自部署；差别见 architecture §9。

- 同一套引擎两种运行模式（本机单用户 / 服务器多租户，后者包括我们的托管与用户自部署）；核心能力不能只在托管版有。
- 远程 MCP + 鉴权从第一天就做——云服务本来就是远程访问。第一版的本地 saveslot 服务只供本机访问（同一台机器上的多个 Agent 共用），跨设备用服务器模式（我们的云服务或自部署）。
- 数据可在本地与托管之间双向迁移；导出是"可退出"的前提。**第一版做导出与导入到空租户**：导出保证用户能把数据带走；导入把一份导出装进一个空租户（逐事件重放，原有主体一律停用，凭证由用户重新签发），本机模式的数据由此能搬进服务器模式。合并导入、冻结源租户的迁移流程、凭证映射随多节点放到后续。
- 托管的价值是免运维、全天在线、接得到云端 Agent，不是锁住核心能力。
- 托管将来也服务开发者 SDK 的第二种用法（开发者采购我们的云上数据中心），租户模型待定（见 [`08-open-questions.md`](08-open-questions.md)「开发者 SDK」）。

**多节点：每个用户一个中心（基本能力）。**

- 用户选定本地或托管为主节点，其他节点复制日志；离线节点带自己的编号写入，上线后提交。
- 同步的是日志而不是状态：日志只追加，合并容易；冲突只出现在从日志算出有模型的数据这一步，
  走 [`03-data-model/09-references-conflict-sync.md`](03-data-model/09-references-conflict-sync.md) 的冲突规则。
- 数据模型中给每个 slot 预留"归属节点"字段，将来可升级为按数据归属设中心
  （如健康数据只留本地），不改结构。

## 技术选型（参考 [`../research/references-arch.md`](../research/references-arch.md)）

- **存储引擎**：全部用 PostgreSQL——本机模式用 PGlite（嵌在 saveslot 服务进程里，用户不需要自己安装数据库），自托管、托管用原生 PostgreSQL。Agent 不嵌入任何东西，只经 MCP / HTTP 连 saveslot 服务。
- **内核语言**：TypeScript（Node / Bun）。PGlite 只能运行在 JS 运行时里，所以内核选了这个技术栈；将来的 SDK 要嵌进非 JS 宿主时只能另起 sidecar 进程。
- **安装前提**：第一版发布为 npm 包，需要电脑上先有 Node；不依赖 Node 的独立可执行文件与桌面安装包等桌面打包实验的结论（[`06-cli.md`](06-cli.md) 第 3 节）。
- **主节点**：有云端节点（托管或私有服务器）时，默认云端为主节点；本地为主节点是高级选项。
  第一版不做应用层加密；将来做加密时，默认也由主节点持有密钥做派生（服务端加密，需对用户说明），不是端到端加密。
- **第一版不做应用层加密**：saveslot 自己不加密内容，删除 = 直接物理删除内容（字段、条目、整条都可以），不加 salt、不做链上内容承诺；结构上为将来加密预留（加密时只加密源数据原文与历史整行，业务表保持明文以便查询）。
  **托管服务的存储在基础设施层做静态加密**：数据库的存储卷、备份与冷归档都在云平台加密的存储上，密钥由云平台的密钥管理服务保管。它防的是存储介质被带离之后被读，不防运营方：saveslot 进程与有数据库权限的运维人员读到的是明文，**运营方技术上读得到托管用户的全部数据**。不想让任何第三方读到，用本机模式或自己部署。自部署时磁盘是否加密由部署方决定；本机模式由操作系统的磁盘加密决定，saveslot 不检查。导出文件可以由 CLI 用口令加密（age 格式），那是对离开 saveslot 的副本的保护，不是存储加密。
- **重放一致是硬要求**：同一份日志在任何节点（PGlite / 原生 PostgreSQL）重放，派生结果必须逐行一致——固定时区与排序规则、数值用 `numeric`、规则只用结果确定的函数，并用实验验证。
- **业务时间是一等概念**：schema 为每张表声明时间类型（无时间 / 事件类 / 状态类）；写状态默认"管到下一个已记录的变化"，覆盖已有事实须显式传参；方案见 data-model「时间」。
- **删除分三种请求**：撤销一行 / 删除证据 / 隐私删除；派生数据能重算，从不挡删除。
- **删除结果的定义**（参考 [`../research/08-provenance-deletion.md`](../research/08-provenance-deletion.md)，见 data-model「删除」）：隐私删除后的状态 = 假如被删源数据从未存在过、按 `seq` 重放日志得到的状态；两处有意偏离：人的决定（撤销、回退、采纳 / 回到冲突前、确认、拒绝、`acknowledge`）照记录执行，已经生效过的写入保持生效。两条原则：只追数据依赖（值来源）、不追控制依赖（操作来源）；saveslot 自己的机械判定（同值、`next_change`、`ver` 冲突、系统裁定、高影响、行 / 实体的存在）按删除后的状态重算。
  删除可能让原本未生效的写入生效（冲突成因被删的候选、高影响成因被删的待确认写入），按定义生效、但必须可见：预览单列、回执与事件写明、对应事项标"已被取代"；冲突消失后仍属高影响的写入转为待确认，不直接生效。
  第一版就做**参考求值器**，作为 `delete` 的测试对照，配性质测试（architecture §11）；**不采纳**给每个值预存来源多项式 / 最小见证；W3C PROV 只记为将来审计导出格式的候选。
- **每个用户独立存储**（参考 [`../research/07-per-user-storage.md`](../research/07-per-user-storage.md)）：本地是一个 PGlite 数据目录；
  托管与多用户自托管是**同一 PostgreSQL 集群里每用户一个 database，按集群分组（cell）**，每组起步上限 2,000 个用户库。
  saveslot 内核只依赖"打开某个用户的存储"这一个抽象，表名不带用户前缀，三种部署同一份代码。
  连接由 saveslot 自己管理（用户固定路由到一个 saveslot 进程、每个活跃用户一条连接、闲置即关、满额按最近最少使用淘汰），不用 PgBouncer。
  长期不活跃的用户整库导出后从集群移除，下次访问再恢复；超限时依次：加集群 → 收紧不活跃阈值 → 组内退回每用户一个 schema → 大户单独集群。
- **不支持多人共享 slot（第一版）**：将来共享 slot = 独立租户 + 成员授权；接口里 slot 不写死在用户名下。
- **日志完整性 = 溯源 + 防误操作，不做防篡改**（见 data-model「完整性与溯源」）：确定性事件头 + `prev_hash` 只串事件头；内容分块单独存放、配校验和（只用于发现损坏，随内容一起删）；只有内核能写、日志只追加、对账（第一版由用户手动触发）。
  `verify` 报"事件头链完整与否；内容校验和 N 处不符；M 处已按删除移除"。对能写存储的一方（含运营方）不防篡改；签名检查点、Merkle 树属于后续规划（见下）。
- **大写入作业**（第一版不做，超限的写入一律拒绝、由调用方分批）：拆不开的大写入转成后台作业，期间受影响的派生值保持旧值并标"待刷新"——对"派生值永不落后"的有限放宽。
- **持久性是硬要求**：已确认的写入，在重启、进程崩溃、断电后都不能丢。PGlite 能否满足由实验确认，满足不了就换打包的原生 PostgreSQL。

## 上层产品与 saveslot 的关系

saveslot 是底座，面向终端用户的产品建在它上面。记账应用、运动记录（Strava 这类）、项目跟踪（Linear 这类）如果做成"由 Agent 来记、来查"的版本，数据层面要解决的问题是一样的：值会被纠正、要知道来源、多个 Agent 会同时写、用户要能删、要能带走。

- 这些通用的部分（版本、来源、冲突、审计、回退、删除、导出）由 saveslot 提供。
- 产品自己负责领域知识与用户体验。领域知识以"Schema + SKILL"的形式交给 saveslot：schema 定义数据长什么样，SKILL 告诉 Agent 什么时候写、怎么用。
- saveslot 的范围比"类型化的值"大：值只是被跟踪事物的一种形态，下面还有源数据日志。

## 后续规划（不进第一版）

以下不进第一版，后续规划时单独讨论：

- **理论依据调研**：双时态数据库（更正 / 追溯更新的标准定义）、数据来源理论（来源半环、删除传播、W3C PROV）、状态机复制与增量视图维护（DBSP）、schema 演进（PRISM）、数据融合、语言 Agent 的记忆架构（CoALA）。**判据是收益**：每条理论都要回答"它替换了我们哪条手工规则、给了哪条可验证的判据或测试、提供了哪个对外标准"；只提供说法的，只用于定位表述，不进实现。已做三项，结论都已进方案：数据来源理论用于删除的定义（[`../research/08-provenance-deletion.md`](../research/08-provenance-deletion.md)）——用"参考语义 + 两条原则 + 参考求值器与性质测试"统一删除重放的规则，不逐条手写，不预存来源多项式，W3C PROV 只作将来审计导出格式的候选；双时态数据库用于状态类表的写入与读取规则（[`../research/09-bitemporal.md`](../research/09-bitemporal.md)）；数据融合用于冲突判据与事件里要记下的信息（[`../research/10-data-fusion.md`](../research/10-data-fusion.md)）。后两项各给出一组性质测试（architecture §11）。增量视图维护、schema 演进、记忆架构三项待展开，它们不影响事件格式。
- **多节点**：同一份数据同时放在本机与云端（或多台设备）并互相同步、离线写入、主节点切换。第一版的两种运行模式（本机、服务器）都是单节点；第一版的重点是核心数据与工程架构能否解决 Agent 的数据状态保持。data-model「同步协议」与相关的暂定 / 同步被拒等机制保留为将来的设计，不实现。
- **saveslot 调用模型的进阶能力**：需用户授权模型调用（自带 API Key）。包括"只交原始内容、由 saveslot 抽取"的写入路径、调用模型的后台执行方（worker）执行抽取作业、L3 模型派生、外部来源同步与定时任务、从积累的源数据起草 schema、后台模型核对证据（第一版不产生"核对不一致"事项）。这里的外部来源同步指 saveslot 自己发起的同步；第一版与之后，外部来源的数据都可以由 saveslot 之外的连接器写入（见「saveslot 管什么，不管什么」）。抽取作业不进第一版，是第一版之后的第一个增量；做的时候只服务 schema 变更、先由用户的 Agent 执行，接口不区分执行方，将来 worker 直接接入。**这些能力都在内核之外**：调用模型的执行方与调用方 Agent、连接器地位相同，以自己的身份经操作契约写入，受 scope 约束，结果照常作为事件记进日志；内核与契约不依赖它们，没有它们 saveslot 的全部保证照样成立，重放也不需要再调用模型（architecture §12「模型调用」）。
- **日志防篡改**：签名检查点、Merkle 树、链上内容承诺按产品需要再做；第一版的完整性目标是溯源 + 防误操作。将来要做时通过新的事件格式版本加入内容承诺，旧事件不追加。
- **按 slot 导出**：第一版的 `export` 导出整个租户的全部事件（事件格式第 8 节）。只导出某一个 slot 要先定：事件头全量导出还是按 `slot` 过滤、没有 slot 的事件（主体、租户）带不带、导出文件能不能单独重放与校验链；做的时候给 `export` 加一个可选的 `slot` 参数，文件格式不变。
- **整个 slot 删除**：第一版不做，接口里没有；逐条隐私删除已能满足"彻底忘掉"。删除整个租户（用户要求删除整个账号）同样第一版没有，它是对外提供云服务前必须定义的事，问题清单见 [`08-open-questions.md`](08-open-questions.md)「租户整体删除」。将来要做时先在 data-model「删除」里定义：schema 文档、slot 策略、事项、作业、迁移中的新版表怎么处理，slot 名与 `slot_id` 能否复用，宽限期内能否写入，撤回的语义；接口走同一套 `deletion_preview` → `delete`（`kind: "slot"`）。
- **导入查重**：同一 slot 里同一文件（`file_ref` 的 `sha256`）的同一批 op 再次写入时提示"该文件已于 … 导入"（这里的导入指把外部文件的内容写进来，不是导入一份导出）。第一版不做：脚本重跑靠显式 `idempotency_key`（窗口 24 小时），同一件事被记两次靠 `duplicate_keys` 标记。声明了来源键的表不需要它：按来源键把同样的内容再交一遍，结果是没变。
- **序列类型的表**：为设备产生的高频读数设一种表的种类：不逐点保留版本，不逐点记来源，来源记到"一批"（一次同步、一个文件），按批追加、按批替换与删除，可以降采样。第一版没有，高频数据按「场景判据」的建议存汇总。要定的事：一批是一个事件、读数作为它的内容块；K4（每次写入都有源数据）、K8（按 `ver` 判冲突）、K10（读取记录记读到的版本）在这种表上的粒度从行变成批；派生规则怎么读它；隐私删除按批执行。存储抽象与事件格式不挡这条路，但它是数据模型的一次扩展，不是加一张表。是否往前提，看容量实验的结果。
- **多节点的接口内容**：节点凭证、日志同步端点、`tentative` 状态与标记、`sync_rejected` 事项不进第一版的契约与外化面，定义见 data-model「同步协议」；将来以契约的次版本加入 `tentative` 与 `sync_rejected`。
- **文件存储与附件**（后续要做）：第一版源数据可以是外部文件引用（文件名、类型、大小、内容哈希、来源位置、可选文本摘录），不保管文件本身，删除时如实告知。由 saveslot 保管文件是明确的后续方向：用户的照片、票据、录音是很多记录的原始证据，只留引用的话，"证据在 saveslot 里、可追溯、可删除"对这类证据不成立。做法是加内容 blob 存储，按内容哈希补传，引用的结构不变；届时要定上传接口、媒体文件的抽取方式、文件进不进同步与导出、删除与备份口径。
- **文本视图（整表或整个查询结果平铺成文本）**：saveslot 不做语义搜索，而模型擅长处理文本；让 Agent 拿到一张表或一个查询结果的整份文本（Markdown 或 CSV），由模型自己在里面找，可以替代一部分语义搜索的需求。第一版已有的部分：`query` 经 MCP 返回渲染好的文本，可以不带条件逐页读完一张表（每页至多 1,000 行）；源数据可以按时间、slot、类型列出并做子串搜索。后续要补的是一次取整份的入口（CLI 写成文件、MCP 给出可分段读取的资源），它只是 `query` 之上的一种外化面，不改内核。届时要定：读取记录按表级记录记（见 data-model「读取记录」）；文本里每行带行 ID、不带 `ver`（要改某一行先逐行读）；不可信内容的边界标记照常；写到 saveslot 之外的文件是一份 saveslot 删不到的副本，导出时如实告知。**是否提前到第一版由评测决定**：评测里 Agent 找不到数据的失败占比高，就提前做。

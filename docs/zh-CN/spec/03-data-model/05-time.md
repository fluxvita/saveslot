# saveslot · 数据层机制 · 05 时间

> 数据层机制的一部分，目录见 [`README.md`](README.md)。文中「…」引用的节可能在同目录的其他文件里，按目录查。

## 时间：记录时间与业务时间

**两条时间线**：记录时间（saveslot 何时记下，系统维护、无业务含义，按时刻读用它）；业务时间（现实中何时发生 / 生效）。
两者绝大多数时候是同一刻，只在用户事后补说时分开。

记录时间对外用**操作号**表示（见「编号」）：一次写入、一次解决、一次删除确认各占一个操作号，一次操作内的全部事件对外是同一个记录时刻。

### 三种表

schema 为每张表声明时间类型。所有基础表都配一张版本表（`t__ver`：按单元格记，一格是某个字段在某段业务时间上、某段记录时间里的值，标记录时间上的有效区间 `rec_from` / `rec_to`，取值是操作号）。

| 类型 | 例子 | 业务时间怎么存 |
|---|---|---|
| 无时间 | 偏好、项目元信息 | 无，只有记录时间 |
| 事件类 | 跑步、支出、会议 | 发生时刻当普通列（含时区，保证"哪一天"可复算）；回溯修改就是普通 update |
| 状态类 | 预算、目标、项目状态 | 一行 = 一个实体在一段生效区间（`tstzrange` / `daterange`）里的值；`PRIMARY KEY (entity_id, valid WITHOUT OVERLAPS)`（PostgreSQL 18） |

- PostgreSQL 18 有 `WITHOUT OVERLAPS` 约束，但"改写某一段时间"的语法（`FOR PORTION OF`）在 19 Beta 被撤回——**拆行逻辑由 saveslot 实现**。
- 不在存储层自动合并相邻同值段（保住各段来源），查询层默认合并（见「查询」）。
- **区间一律左闭右开 `[起点, 终点)`**：终点那一天（或那一刻）不含在内。回执用人话写出含端点的范围（"11-02 至 11-19（含）"）。
- 状态类表的粒度 `granularity` 是 `date`（按 slot 时区的自然日）或 `instant`（时刻）。

### 状态类表的状态：按字段、按时刻

**一个实体的状态是"字段 × 业务时刻 → 值或无值"的函数**，每个字段一条时间线。写入是在某段区间上给若干字段赋值；物理上怎么分段是内部实现。

**所有机械判定（挡点、同值、高影响、冲突）只看这个函数与"哪次写入在哪里生效"，不看物理段的边界。** 把任意一段切成两段同值、同来源的段，任何判定的结论都不变。

**挡点**：字段 f 的挡点是下面两种业务时刻。

| 挡点 | 是什么 |
|---|---|
| 取值变化处 | f 的值在这一刻前后不同，含有值 ↔ 无值的边界（见「无值区间」） |
| 佐证端点 | 一次显式指向证据的同值写入，它被记为佐证的那段区间的起点与**显式**终点（见「用同样的值写」）。默认终点解析出的那一端不算。这个端点**被盖掉**（之后有已生效的写入在包含该端点的区间上改了值；包含该端点按左闭右开判，从该时刻开始的写入也算）、这次佐证的来源被删除、或这次佐证被一次回退回掉（`undo`、回到合并基）后不再算。撤回删除时重判为佐证的放回候选不产生佐证端点（见「删除 · 撤回与宽限期」） |

相邻同值段之间的物理边界不是挡点。挡点是字段级的：`owner` 在 11-10 换了人，不是 `amount` 的挡点。

**给出挡点的贡献**：一个时刻的"给出挡点的贡献" = **该时刻是其区间端点的全部贡献，两侧都算，已被盖住的也算**（判定某个字段的挡点或补值段端点时，算这个字段与"存在"上的贡献。**只算在被解析的那次写入之前的贡献**——按贡献先后排在它前面的，同一请求里前面的 op 也算；补值段以那次切换为准——**并且是生效的贡献**：被盖住的、在该处被登记回掉的都算，候选与待确认的不算。区间取当前状态里这一项的区间：写入时是日志里最近一次给出它的；删除重放时是本次重放里它的区间，含刚重新解析出的）——区间在该时刻结束的与从该时刻开始的，含留下相邻空洞的撤销、佐证端点所属的佐证项。例：`[10-01, ∞) 4000`；显式 `[10-15, 11-10) 5000`；11-10 这个挡点由 5000 那一项的显式终点给出，之后给值的 4000 那一项在 11-10 没有端点，不算。这样取不会漏掉端点的出处：一个端点日期，要么是某次写入自己说的（显式起点或终点），要么是由别的贡献求得的；顺着求得关系往回追，最后总有一次写入亲口说出这个日期，而它自己记下的区间就以这个日期为端点，所以它一定在内，不需要沿依赖递归。代价是只是恰好在同一时刻有端点、与这个挡点无关的贡献也会算进去，被删时多清一块，属于宁可多清的一侧。默认终点（`next_change`）、纠错的默认区间（`corrected_span`）、只带起点的撤销的终点停在一个挡点上时，解析结果记下的依赖就是这些贡献；状态类表补值段的两端同样按这一条取（见「删除 · 来源：值来源与操作来源」）。

### 写状态：参数与默认

| 参数 | 必填 | 不传时 |
|---|---|---|
| 实体、新值 | 是 | — |
| 生效起点 `valid_from` | 否 | 从现在起 |
| 生效终点 `valid_to` | 否 | **管到下一个挡点为止**（`next_change`）：op 里每个字段各自取严格晚于起点的第一个挡点；该字段之后没有挡点则一直延续 |

- `valid_to` 可以给一个日期或时刻，也可以明确写 `"open"`（一直延续）；不传等同于 `"next_change"`。显式终点对 op 里的所有字段相同。
- **意图是纠错（`correct`）且起点、终点都没传**：每个字段的区间 = 该字段**包含"现在"的、以挡点为界的区间**（从不晚于现在的最近一个挡点，到严格晚于现在的第一个挡点）。被纠正的是"那个事实"，事实的范围就是这一段。佐证端点也是界：有人在某一天明确重申过这个值，纠错就只改到那里为止，回执写明改了哪一段。
  - 只传了起点或终点之一时，按上表的普通规则。
  - "现在"那一点该字段无值：报 `invalid_argument`，提示给出区间。
- **原始传参与解析结果都记，分开记**：
  - **原始传参记在逻辑写入头里**，照调用方的写法：起点是"给定的值"或"现在"，终点是"给定的值"、`open` 或 `next_change`；纠错的默认区间起止都记为 `corrected_span`。
  - **解析结果记在基础写入里**，逐字段逐项：`[起点, 终点)`，都是具体值，不记"没传"。区间是这次贡献的一部分，随这一项的值一起删。它与值分开存放，并记下解析时用到的别的贡献：那些贡献被隐私删除或被重述时，区间单独清除，由删除事件重新给出（见「删除 · 由别的贡献求得的内容」）。
  - 重放照解析结果做，不重新解析；删除重放时 `next_change` 与 `corrected_span` 一律按原始传参重新解析（saveslot 的机械判定按删除后的状态重算，见「删除 · 重放规则」）。重新解析出的区间记在那次删除事件里；**一项贡献的区间以日志里最近一次给出它的事件为准**，之后的 `undo`、冲突判据都按它。
- **逻辑写入头另记判定用的时刻**：入口取的 `now` 与由它在当时 slot 时区下得出的 `today`。"是否追溯"（起点早于现在）由它们与解析结果比较得出。重放与删除重放都用记下的值，不读时钟、不读当前时区。

**原则：默认不破坏任何已知事实；覆盖已有事实须显式传参；每次写入在回执里说清影响。**

**例（单字段）**：已记"10-01 起 5000""11-10 起 4000"。

| 写法 | 结果 | 回执 |
|---|---|---|
| 起点 11-02，不传终点 | 11-02 至 11-09（含）为 3000，11-10 起仍是 4000 | "已保存。注意：11-10 起仍是 4000，未改动。" |
| 起点 11-02，终点"一直延续" | 11-02 起都是 3000，覆盖 11-10 那段、抹掉了 11-10 这个变化点 | 高影响：进待确认，列出被覆盖的段 |
| 起点 11-02，终点 11-20 | 同样抹掉了 11-10 这个变化点 | 同上，高影响 |
| 起点 11-02，终点 11-05 | 只改这一段 | 列出被切分的段 |
| 意图纠错、不传起点与终点（今天 11-05，值 6000） | 10-01 至 11-09（含）为 6000，11-10 起的 4000 不动 | 写明纠正的是哪一段；问过这段日期的读取受影响 |

默认"管到下一个挡点"：猜错的后果是"少改了"（回执提醒，Agent 可追问），而默认"一直延续"猜错是"多改了"、悄悄覆盖已有事实。

**例（多字段）**：已记 10-01 起 `amount 5000, owner 张伟`；11-10 起 `owner 李娜`；11-20 起 `amount 4000`。写"11-02 起 `amount 3000, owner 王强`"、不传终点：

| 字段 | 起点之后的第一个挡点 | 解析出的区间 |
|---|---|---|
| `amount` | 11-20 | `[11-02, 11-20)` |
| `owner` | 11-10 | `[11-02, 11-10)` |

两个字段各管到自己的下一个挡点。若整个 op 取同一个终点（11-10），`amount` 会在 11-10 回到 5000，凭空多出一个没人说过的变化。

#### 无值区间

状态类表上，实体在某段业务时间里可以没有值：实体第一段之前、显式终点之后、带区间的撤销留下的空洞，都是**无值区间**，规则相同。

- **某一点"有值"的定义**：全部必填字段在该点都有生效的值。**给过常量 `backfill` 的字段（新增必填、可选改必填）只在判定有值 / 无值区间时不算必填字段**（因而在挡点与存在的判定里也不算），写入时与删除重放（见「删除 · 重放规则」的「行 / 实体的存在」）用同一条。写入校验不受影响：见下面"落在无值区间"一条。例外只为了让删除清掉补值时不凭空制造无值区间。可选字段在一段区间上被清空是"值为空"，不是无值区间；它的 值 ↔ 空 照常是取值变化、算挡点（见「字段类型、同值与单位 · 清空字段」）。
- **有值 ↔ 无值的边界是每个字段的挡点。** 默认终点的写入不会自己闯进无值区间，也不会越过它。
- **显式区间跨过无值区间：照填。** 写入的语义是"设这段的值"。它让无值区间两端的变化点消失，属高影响 ①（见「高影响写入」），进待确认；回执与事项的影响里把被填上的无值区间单列（附留下它的那次撤销）。
- **写入落在无值区间的部分，必须带齐 schema 声明的全部必填字段**，含给过常量 `backfill` 的字段，否则报 `validation_failed`（指出缺哪个字段、哪段区间，提示补齐字段或缩短区间）。可选字段不带就是空。这项校验依赖当前状态，在冲突判定之后、只对将要生效的部分做（见「写入请求 · 判定顺序」）。

**例**：`[10-01, 10-10) 5000`、无值、`[10-20, ∞) 4000`（`amount` 必填）。

| 写法 | 结果 |
|---|---|
| "10-05 起 3000"，不传终点 | `[10-05, 10-10) 3000`，其余不动 |
| 显式 `[10-05, 10-25) 3000` | 会填上 `[10-10, 10-20)`、抹掉 10-10 与 10-20 两处变化点 → 高影响，进待确认 |
| 只写 `owner`，区间 `[10-12, 10-15)` | `validation_failed`：这段没有值，缺必填字段 `amount` |

#### 用同样的值写

同值佐证的通用规则见「删除 · 来源」；这里是状态类表特有的部分。

- **同值的基准是写入方所见的版本**（`ver` 指向的版本；`ver` 是当前的就是当前状态），取它在写入时已确认、未撤回的删除之后的样子（被删的值不会因原样带回而被当成同值）。字段的值在解析出的**整个区间**上都与所见版本相同，才叫同值。
- 同值且没有用 `evidence_by_field` 显式指向证据：**无操作**。不产生版本，`ver` 不变，不留任何边界。
- 同值且显式指向了证据：**佐证**。
  - 当前值仍与它相同的部分：给这一段追加来源，不产生新版本、不改 `ver`。只在来源表里按区间拆分，不算"切分已有段"（段 `[10-01, 11-20) 5000`，佐证 `[11-05, 11-10) 5000`：只有 `[11-05, 11-10)` 这一截多一个来源）。
  - 被记为佐证的那段区间的起点与显式终点成为该字段的**佐证端点**，算挡点。
  - 当前值已被所见版本之后的写入改掉的部分：按一次普通写入参与冲突判定（见「冲突处理」）。
  - 所以同一个字段在一次写入里可以分成几项、各有各的结果：一项是佐证，另一项生效或成为候选。事件与回执都按项给。
- 一次写入盖掉了别人的佐证段而没有改变取值变化点：不算高影响，回执 `warnings` 给 `overwrote_corroborated`（附被盖的段与来源）。

**例**：基础 `[10-01, ∞) 5000`。A 说"11-20 起是 5000"，B 说"11-02 起 3000"、不传终点，两边带同一个 `ver`。

| A 的写法 | 两种到达顺序的结果 |
|---|---|
| 没指证据（无操作） | 都是 `[11-02, ∞) 3000` |
| 指了证据（佐证，11-20 成为佐证端点） | 都是 `[11-02, 11-20) 3000`、`[11-20, ∞) 5000` |

想让重申的一个值"算数"，Agent 要用 `evidence_by_field` 指明证据；工具描述照此引导。先后两次写入、后一次看过前一次时，结果随先后不同是语义本身。

**例（一个字段两项）**：基础 `[10-01, ∞) 5000`。B 先写显式 `[11-02, 11-10) 3000`；A 带 B 之前的 `ver` 佐证 `[11-05, 11-20) 5000`。A 的这次写入在 `amount` 上有两项：`[11-10, 11-20)` 仍是 5000 → 佐证，追加来源，11-20 成为佐证端点；`[11-05, 11-10)` 已被 B 改成 3000 → 按普通写入判，与 B 相交且值不同 → 候选。

### 高影响写入

**高影响 ① 的唯一判据：写入之后，某个字段在某个业务时刻、在写入方所见版本里已经存在的取值变化点（含有值 ↔ 无值）不再是变化点。** 按结果判、逐字段判，与终点怎么传、是什么意图无关。只数所见版本里有、写入前仍在、写入后不在的变化点；所见版本之后被别人抹掉的，不是这次写入抹掉的，由冲突判据管。

- **所见版本**与同值判断的基准是同一个：`ver` 指向的版本（`ver` 是当前的就是当前状态；兜底取得的就是兜底到的那个版本）；同一请求里后面的 op 再叠加本请求前面 op 的结果，所以前一个 op 刚造出的变化点在保护范围内。
- **所见版本之后别人新造出的变化点不在保护范围内。** 那属于并发，由冲突判据管：能合并，说明两边在相交处同值，没有信息被盖掉。这样判定与到达顺序无关（见「冲突处理 · 冲突判据」）。

| 写入 | 算不算 ① |
|---|---|
| 显式终点或 `open` 盖过了一个变化点 | 算 |
| 只改某一段的值，改后的值与某一侧相邻段相同（如把 11-02 起的 3000 改回 5000，11-02 处不再变化）；回退常见 | 算 |
| 默认终点的写入，改后的值与起点前一段相同 | 算（抹掉的是起点处的变化点） |
| 显式区间填上了无值区间 | 算 |
| 只改某一段的值，改后的值与两侧相邻段都不同（如把 11-10 起的 4000 改成 4500） | 不算 |
| 只把已有的段切开 | 不算 |
| 同值写入（无操作或佐证） | 不算 |
| 带过期 `ver` 的写入，让所见版本之后别人新造出的变化点消失（两边在相交处同值，已按冲突判据合并） | 不算 |
| 撤销 | 不算。撤销是显式的"这段没有值"，保留历史、可 `undo`；它仍受 ② 约束 |
| `undo` 一次撤销 | 不算。它恢复的正是那次撤销去掉的值，变化点回到撤销之前的样子；撤销之后别人写进那段区间的部分照常被跳过 |

事件类表上改一行的值不是高影响。

**例（到达顺序无关）**：基础 `[10-01, ∞) 5000`，A、B 带同一个 `ver`。

| 两次写入 | A 先到 | B 先到 |
|---|---|---|
| A"11-10 起 3000"，B"11-02 起 3000"，都不传终点 | B 合并为 `[11-02, 11-10) 3000`；它让 11-10 不再变化，但 11-10 这个变化点在 B 所见的版本里不存在 → 生效 | A 合并，值没变 |
| A `[11-01, 11-20) 3000`，B `[11-10, 12-01) 3000` | B 让 11-20 不再变化，那是 A 造出的 → 生效 | A 让 11-10 不再变化，那是 B 造出的 → 生效 |

两行在两种顺序下的最终状态都相同：第一行 5000 / `[11-02, ∞) 3000`，第二行 `[11-01, 12-01) 3000`。

- 高影响写入默认进待确认（`awaiting_confirmation`），值不变，回执列出将被覆盖的段（按字段）。**确认时照事项里记下的提议区间执行**：提议与确认之间有写入改到了提议的字段与区间时，事项已被取代或刷新、版本对不上；不相交的写入新加的挡点不改变已记下的区间。
- **op 级的 `acknowledge`**：调用方已经和用户确认过时，可在**该 op** 上带 `acknowledge: ["overwrite"]` 直接生效，这次确认记进写入事件（谁、确认的是哪些被覆盖的段）。
  **只在该 op 显式带了当前 `ver`（不是兜底取得的）时有效**：此时调用方看到的就是当前状态，被覆盖的就是它看到的段；
  没带 `ver`、`ver` 由兜底取得或已过期时，`acknowledge` 不生效，照常进待确认。不另加哈希，也不需要预览往返。
  哪些外化面开放它是外化面的事：**MCP 第一版不开放**（模型在写入之前看不到会被覆盖的段，一律走"待确认 → 解决"，见 05-surfaces.md）；HTTP 开放。
- **版本对不上、同时又属高影响的写入**：先按冲突处理，成为候选（见「冲突处理」）。
- **高影响写入的完整清单**：

  | # | 高影响写入 | 第一版 |
  |---|---|---|
  | ① | 状态类表上抹掉已记录变化点的写入（上面） | 做；只有它可用 `acknowledge: ["overwrite"]` 直接生效 |
  | ② | 撤销一行，而该行仍被其他行 `ref` 引用。状态类表上只有撤销整个实体（不带区间）才判；带区间的撤销之后实体仍在，不判。怎么数"仍被引用"、确认之后引用方怎样，见「写入请求 · 引用字段」。与 ① 一样，判定时计入本请求前面各 op 的结果：引用方在本请求前面已被撤销的，视为不再引用 | 做，一律进待确认 |
  | ③ | slot 策略额外指定的表 / 字段上的写入 | 后续 |
  | ④ | `undo` 带 `include_later: true`、回掉了后来的写入（事件类表、状态类表都算，见「回退到某个版本」） | 做，一律进待确认 |

  高影响按删除后的状态重算（见「删除 · 重放规则」）。

  **回掉（`undo`、回到合并基）在重放里的状态按操作号顺序逐个判定**：判定某次回掉时，早于它的回掉按已判定的状态算，它自己按生效算；判定一次即定，不因之后的回掉或判定的结果回头重判；结果里的切段与登记算的是全部判为生效的回掉（事件格式 §5.7）。它自己按生效算，是为了让 ④ 在它真正执行的那个状态里判：一次 `include_later` 的 `undo` 若生效时会回掉后来的写入，就进待确认，不会因为判定时把它当作不生效而看不到要回掉的后来的项、直接生效。

  ② 计入本请求前面 op 的结果，所以"同一请求里先撤销三条明细、再撤销它们所属的一餐"一次完成，不进待确认。反过来排（先撤销一餐、再撤销明细），撤销一餐的那个 op 判定时明细还在引用它，照常进待确认；之后明细被撤销，事项的影响随之刷新（见「待处理事项 · 影响」）。同一请求里 op 的先后因此会影响结果。这与"到达顺序无关"不冲突：那一条说的是两次各自带 `ver` 的请求，同一请求里的 op 本来就按顺序执行、后面的看得到前面的结果（见「写入请求 · 同一请求里的多个 op」）。

### 状态类表上的撤销

- **撤销就是"这段时间无值"的一次写入**，没有单独的"已撤销"状态。带 `valid_from` / `valid_to` 时只撤销该区间，留下无值区间；不带区间时撤销整个实体，即全时间无值。
- **只带起点的撤销**：终点默认 `next_change`，取**任一字段**在起点之后的第一个挡点（撤销改的是"存在"，任何字段的变化都是已记录的事实，默认不越过它）；可显式写 `open`。
- **带区间的撤销，区间是内容**（起止点是用户说的话），来源是那句话；不带区间的撤销不含内容，是纯粹的决定。两者在隐私删除时的差别见「删除 · 两条原则」。
- 撤销整个实体之后，实体与它的键仍在。之后按 `entity` 或 `entity_key` 的写入按「无值区间」处理（须带齐必填字段，照常带 `ver`），**不会生成第二个同键实体**。
- "恢复成原来的"要用回退（见「回退到某个版本」）。
- 撤销与并发修改的冲突判据见「冲突处理」。

### 按 `entity_key` 写入

**有则写入、无则创建**：状态类表声明了 `entity_key` 时，按键定位的写入意图记"变更"——实体存在就是普通变更（照常要带 `ver` 或可兜底），不存在就创建实体（生成 `entity_id`，写入事件记一个"创建"标记，`undo` 据此识别首次创建）。

- "新增"意图只用于没有 `entity_key` 的表（状态类表上每次新增一个实体）；用在声明了 `entity_key` 的表上报 `invalid_argument`，提示改用变更意图按键写入。按 `entity_id` 写入而实体不存在时报不存在。
- **键字段不可改**：键不随业务时间变化，键唯一是全时间唯一。写入里出现键字段且值与实体的键不同，报 `invalid_argument`（`key_field_changed`），不分意图、不分带不带区间。按键定位时，键值按同值判据比（见「字段类型、同值与单位」）。
- **写错一个字就会新建实体**（"q4 推广""Q4推广预算"）：首次创建的回执除了"新实体"，还给出两项提示，让调用方一眼看出是不是写错了键：
  - `similar_keys`：该表里写法与新键相近的已有键，至多 5 个，各带相近的原因（`fold` 折叠后相同、`affix` 一方是另一方的开头或结尾、`edit` 编辑距离在阈值内）。判据、比较范围与排序见「相近的键」。比较范围含已撤销的实体（撤销之后实体与键仍在），这样的键标 `revoked`：按它的键写入是填上它的无值区间（见上「状态类表上的撤销」），不是改一个仍在生效的实体。
  - `existing_keys`：该表已有的实体键，至多 10 个；相近的键排在最前，其余按最近写入排序。
  - 两项都是写入那一刻由当时的状态算出的提示，不进事件；幂等重放的回执不给这两项（`omitted[]` 里标 `existing_keys`），不按重放时的状态重算，否则同一请求的两次回执会不同。
  - 写入照常生效，不生成事项、不进待确认：相近不等于写错，"推广"与"推广二期"可以是两个预算。按 `entity_key` 近似匹配生成 `flagged` 事项第一版不做。
- **键写错了怎么改正**：撤销写错的那个实体（不带区间），再按对的键写入。写错的实体与它的键留在历史里，可查、可 `undo`。直接改键（把一个实体的键换成另一个值）第一版不做：改键之后再删掉那次改键的证据，键要落回旧值，而旧键此时可能已被另一个实体占用，需要另一套规则。
- **并发首次创建**：两个调用方都读到"实体不存在"、先后按同一个键写入时，后到的一方没带 `ver`、也没有可兜底的逐行读取，报 `read_first`；重读后看到对方刚创建的值再决定。结果是对的，代价只是多一次调用。
  不把"读到不存在"当成一个版本、按冲突处理：那要在 read_log 里按键记下"读到了不存在"，而键值是用户内容，K10 不允许 read_log 记值、也不允许记由值算出的哈希。
- 同一请求里先创建实体、再对它写第二段，后面的 op 不需要 `ver`（见「写入请求 · 同一请求里的多个 op」）。

### 变更对之前读取的影响

状态类表上，**任何让值发生变化的写入**都做影响查询。判据是结构性的：值实际变化的（字段，业务时间区间）与读取记录里记下的业务时间条件有交集，且该读取读到的版本早于这次写入（细则见「纠错影响查询」）。

| 情形 | 谁判断 | 原因码 | 给读方的措辞 |
|---|---|---|---|
| 意图是纠错 | **Agent 显式标注** | `correct` | 你曾读到的值已被纠正 |
| 变化区间里早于"现在"的部分（早就变了但晚知道，或今天决定、往回生效） | saveslot 按记下的 `now` 判断 | `retroactive` | 你读取的业务时间上的值后来被追溯修改 |
| 变化区间里不早于"现在"的部分 | saveslot 按记下的 `now` 判断 | `plan_changed` | 你读过的未来安排已变更 |

- 不传时间的读取记为入口时刻（`date` 粒度记为当天），所以"今天早些时候读过今天的值"自然命中。
- 事件类表没有生效区间：只有纠错与撤销触发。

### 查询

| 想问什么 | 参数 |
|---|---|
| 现在知道的、现在生效的（默认） | 不传 |
| 业务时间 T 时是什么 | `valid_at: T`（状态类：区间包含 T；事件类改用时间窗） |
| 一段业务时间内的历史 | `valid_during: [a, b)` |
| 当时 saveslot 知道什么 | `history` 的 `as_of: 操作号或时刻`（读版本表）；只在 `history`，查询接口不提供 |
| 两轴都给 | `history` 的 `as_of` + `valid_at`：复现"那次任务当时看到的 11-05 预算" |
| 两个记录时刻之间改了什么 | `history` 的 `changes`（`since` 不含、`until` 含） |

受限 SQL 里业务时间可用 `FOR VALID_TIME AS OF / FROM … TO …`，取"今天"用 `saveslot_today()`、取入口时刻用 `saveslot_now()`（见「派生规则」的 L1）（saveslot 自己的写法，形似 SQL 标准里系统版本表的 `FOR SYSTEM_TIME`），由 saveslot 改写成谓词，不依赖 PostgreSQL 原生支持。记录时间不在 SQL 里开放：出现 `FOR SYSTEM_TIME` 报 `sql_rejected`，改用 `history`（contract「时间参数」）。

**记录时间一侧**

- **`as_of: S`** = 操作号不大于 S 的全部操作都已完整生效时的状态。一次写入的各个事件对外是同一个操作号，所以不会读到写了一半的中间状态。给时刻 T 时按 `recorded_at ≤ T` 换成操作号；未来的时刻等于最新。
- `as_of` 不带 `valid_at` 读状态类实体：返回当时所知的全部段。

**业务时间一侧**

- 状态类表的默认读取（只返回当前段）也带该段的 `valid_from` / `valid_to`，让调用方看得到"这个值到哪天为止"。
- **`valid_during` 的返回**：段的端点默认不截取到查询区间内；默认按所选字段合并相邻同值段（没合并的段上按次数、按时长的计算会错）。开关 `clip: true`、`coalesce: false`。开口终点写成 `valid_to: null`；`valid_to_inclusive` 只在 `date` 粒度给。
- 查询条件里的 `valid_from` / `valid_to` 只在带 `valid_during` 时可用，否则报 `invalid_argument`。
- 受限 SQL 读状态类表：不带时间限定 = 当前段。派生规则读状态类表而不带业务时间限定时，等同依赖"现在"，归入时间依赖的规则：第一版读时计算、不缓存（见「派生规则与派生缓存 · 时间依赖」）。

**日期与时刻混用**

| 情形 | 处理 |
|---|---|
| 细 → 粗：`date` 粒度的表收到时刻 | 按 slot 时区取所在日，`warnings` 写明 |
| 粗 → 细：`instant` 粒度的表收到日期 | 读写都报 `invalid_argument`，`example` 给出那一天在 slot 时区下的起止时刻 |
| 事件类表按日期开窗、发生时间字段是 `zoned_datetime` | 按 **slot 时区**的自然日；事件自带的时区只用于展示。与受限 SQL、派生规则的分桶同一条规则（SQL 里取日写 `saveslot_date(f)`，见 [「受限 SQL」](11-restricted-sql.md)「时间」），代价是跨时区的事件可能算到另一天；需要"当地哪一天"的表，schema 另设 `date` 字段 |

**返回契约**

- **按时刻读的结果总是标明它用的 schema 版本**；按字段 ID 解析，单位按当时版本标注；
  跨过重新抽取类（不可逆）迁移的时刻，只能按旧版形状返回并显式标注。
- **派生值的按时刻还原** = 用当时的规则版本，在当时的（删除后剩余的）基础数据上重算；**不保证与当时读到的值相同**，
  结果校验和已随输入删除或对不上时，跳过核对、标注"当时的输入已部分删除"（`partially_deleted`）。规则版本永久保留（规则文本不含用户数据）。

## 删除

### 删除结果的定义

**隐私删除后的状态 = 假如被删的源数据从未存在过，按 `seq` 重放日志得到的状态。有两处有意的偏离：人的决定照记录执行；已经生效过的写入保持生效。**
`delete` 在确认时按这个定义算出结果、写进事件，`apply` 照做；撤回同理——被撤回的那项删除不再算"被删"，按定义再算一次。
下面的两条原则、重放规则与推论都由这条定义得出，不是另加的规则；规则与定义不一致时，以定义为准、改规则。

- **偏离一：人的决定照记录。** 反事实里人当时会怎么决定无从得知；人基于当时看到的内容做的决定只能按记录执行。人的决定是：撤销、回退与回到冲突前（**照记录的是"回掉哪几次操作在哪些目标上的改动"与"回到哪个位置的状态"；回掉的范围与那里的值不是决定的一部分**，在重放里重新求，见「重放规则 · 回掉」。被回掉的操作写入时是候选或待确认、之后因删除生效的部分同样回掉：人撤回的是那次操作，不是当时列得出的那几项；不在记录里的操作不补）、采纳候选 / 保持生效值、确认、拒绝、`acknowledge`。**除此之外的一切判定都重算**（见「两条原则」），只有一处限定：**写入时没有留下值的部分保持原样**——原本是**无操作**的字段保持无操作，没有进事件的按来源键 op（当时没变或被跳过）不重放（见「重放规则」）。例：一个按来源键的 op 当时命中已撤销的行而被跳过；删掉创建那一行的源数据之后，按"假如从未存在过"它本应新增一行，但日志里没有它，也没有它的值。删除不会让一个当时没变或被跳过的 op 事后生效，预览如实写明。
- **偏离二：已经生效过的写入保持生效（方向限制）。** 重算只会让"原本没生效的"变成"生效"或转为待确认，不会把一次已经生效的写入退回成候选或待确认。已生效的写入被读过、被后续写入当作基线，退回它会让一次删除推翻与它无关的既成事实，并产生新的未决事项。
  **"已经生效过"指写入时就生效（写入事件给出的判定），或经人的决定生效（确认待确认、采纳候选：生效的是解决操作写入的新项），或撤回删除时被记为保持生效（见「撤回与宽限期」）；佐证也算（撤回删除时把放回的候选重判为佐证的除外：它只关掉候选、追加来源，见「撤回与宽限期」）。** 只因某次删除的重算才生效的写入不算：之后的删除按全部被删集合重算，它可能回到候选或待确认，这时恢复的是原来那个事项（撤销它的"已被取代"），不新开事项，预览与回执单列（见「预览与回执要写明的内容」）。这样删除结果仍只取决于日志与被删集合，先删 A 再删 B 与一次删 {A, B} 相同。
- **只约束日志末端的状态**：更早的历史版本不按定义重算，只去掉被删内容（见「结果怎么落进日志」）。为了让墓碑落账之后从头重放仍得到同样的末端，删除事件把结果写全，并为受影响的派生分区追加派生写入。
- **有可执行的参考实现**：参考求值器是"日志 + 被删源数据集合"的纯函数，按含这两处偏离的定义实现，第一版就做，作为 `delete` 的测试对照，配一组性质测试（architecture §11）。参考 [`../../research/08-provenance-deletion.md`](../../research/08-provenance-deletion.md)（文献与论证）。
- **不预存来源多项式 / 最小见证**：覆盖写入不单调（删掉后面的写入，前面的值会回来），只含"且 / 或"的式子算不出删除后的值；`base_sources`（字段 × 证据，分值 / 操作）加日志顺序已是全部信息，删除时重放。

### 两条原则

| 原则 | 含义 | 包括 |
|---|---|---|
| ① 只追数据依赖，不追控制依赖 | **值来源 = 数据依赖**（值从哪来），**操作来源 = 控制依赖**（谁触发、谁决定）。删除只沿数据依赖传播；人的决定不因它的操作来源被删而撤销 | 数据依赖：写入随附的证据、`write` 没带证据时的 `api_call`、`migration_diff` 里 `set` 的解决证据、被回退 / 被采纳 / 被系统裁定搬运的那个值的来源、状态类表写入的区间参数的来源（**含带区间的撤销的区间**）。控制依赖：回退请求、解决请求（含 `note`）、不带区间的撤销的证据、`acknowledge` |
| ② saveslot 自己的机械判定按删除后的状态重算 | saveslot 不经人判断、按规则得出的结论，输入变了结论就跟着变。**除定义里列出的人的决定外，一切判定都重算** | 同值判断（只对贡献；无操作保持无操作；按来源键的写入与重算后的基线值比）、挡点与默认终点（`next_change`）、纠错的默认区间（`corrected_span`）、`ver` 冲突、系统裁定（后续）、高影响判断、行 / 实体的存在、首次创建标记、未解决事项的合并基（已按 `take_previous` 解决的事项，合并基照解决时记下的，不重算）。**不重算的机械判定只有两样**：疑似重复、字面命中（写入时判一次，照记录） |

两条合起来回答"什么留、什么重算"：人的决定留，saveslot 的判定重算，值跟着数据依赖走。

**写入的前提**（见「写入的前提」）分两样处理：

- **声明照记录**。声明是调用方当时给的，"所见版本"是它当时看到的事实；反事实里 Agent 会看到什么、会声明什么，无从得知，与"人的决定照记录"同一个理由。
- **状态重判**。声明的状态（没变 / 已变）是机械判定，在删除后的状态上按判据重判，结果由那次删除操作里的 `premise.changed` 给出：删除让所声明范围上的值变了，打标记（原因 `deleted`）；值回到所见的值且比得了，撤掉。
- **删除不沿前提传播**。依赖行的值来源是它自己的证据，不是它的前提；原则 ① 的数据依赖指值来源。依赖行里是否转述了被删的内容，saveslot 不知道，预览列出这些行交给人决定。前提不让删除多删或少删任何值，"不多删""不漏删"两条推论不受影响。
- **有意不按反事实算的一处**：所见的值出自一句后来被删的话时，按定义重放，所见版本上的值会是别的；但依赖行是 Agent 看了那个真实的值才写的，所以比较用真实的所见值——它已被删除、比不了，标记保持（"比得了才撤"）。

**撤销分两种**：

| 撤销 | 含不含内容 | 证据被隐私删除后 |
|---|---|---|
| 不带区间（整行、整个实体） | 不含。它只是一个决定 | 照记录：行 / 实体不复活。被删掉的只是那句话 |
| 带区间（状态类表） | 含：区间的起止点是用户说的话，来源是那句话 | 区间的来源没了，这次撤销整体没有贡献：无值区间消失，被它盖住的值重新可见（预览写明"这段时间的值将重新出现"） |

带区间的撤销若想在删掉原话后仍然成立，办法与佐证相同：另用一段证据按 `evidence_by_field` 的 `valid` 键指明区间的来源。

**重算用哪一版规则**：每次旧写入按它自己记下的规则版本与策略版本重算（见「写入请求 · 规则版本与策略版本」）。内核升级或 slot 策略变更不会让一次不相干的删除改掉旧写入、旧事项的判定结果。

### 删除的种类

**先分清意图：删除 ≠ 撤销。** 数据错了是**撤销 / 纠错**：保留历史，走纠错与冲突规则，按读取记录找出受影响的任务。不想让它存在是**删除**：抹掉内容本身。

**删除请求分三种**：

| 请求 | 用户想要什么 | 怎么做 | 第一版 |
|---|---|---|---|
| 撤销一行 | 这条业务记录不该存在（"那次跑步记重了，删掉"） | 一次普通写入（意图"撤销"）：行标记删除，历史与源数据都保留，派生缓存照常刷新 | 做 |
| 删除证据 | 这段原文不要了，但它产生的数据可以留下 | 只删源数据原文，由它得出的值照常保留；删掉后会让某个当前字段没有原文仍在的值来源时默认拒绝并列出引用方 | 后续 |
| 隐私删除 | 彻底忘掉（被遗忘权） | 按「删除结果的定义」算出删除后的状态；不被引用挡住 | 做（按源数据指定；按行指定后续） |

（删掉 schema 里的一个字段是另一回事：那是 schema 改动，字段与对应数据删除、源数据不动，见「schema 版本演进」。）

**删除证据与隐私删除的流程**：

| 阶段 | 发生什么 |
|---|---|
| 预览 | 不删任何东西；算出影响，返回确认句柄（见「预览与回执要写明的内容」） |
| 确认 | **确认时就算好删除后的状态**：`delete` 按定义算出受影响行 / 实体删除后的样子，连同派生写入一起写成事件，`apply` 照做。从这一刻起数据读不到，当前值与派生值也不再含它 |
| 宽限期（24 小时） | 只做逻辑删除，可撤回（见「撤回与宽限期」）；待删除的内容默认换成占位、不导出（见 architecture §8） |
| 到期 | 物理删除，追加墓碑事件。云服务由调度器在到期时刻主动打开租户执行；本地 saveslot 服务没在运行时，下次启动时先执行再对外服务，回执如实说明（见 architecture §7） |

- **一次删除只针对一个 slot。** 每条源数据只属于一个 slot；一句话涉及两个 slot 时本来就是两条源数据，两个 slot 各删各的。请求里列了不同 slot 的源数据报 `invalid_argument`（`cross_slot`）。
- 是否征得用户同意由调用方 Agent 负责（saveslot 不区分人与 Agent，见 architecture §3「确认与数据真实性委托给调用方」）。
- "删除已确认""撤回""到期物理删除（墓碑）"都是日志事件——宽限期内导出、恢复，数据也不会复活；恢复早于删除的备份靠日志之外的删除登记补删（见「删除之后」）。
- 宽限期与被遗忘权时限的关系交法务。

**按行隐私删除**（`rows`）

> **不进第一版。** 第一版要彻底忘掉一行，把这一行涉及的源数据都列为删除目标。与按源数据删除是同一套重放，只换被删集合。

- 删除的单位是（源数据, 行）上的贡献——去掉这些行的**全部**贡献，插入它们的、后来修改它们的源数据都算，不只是插入的那条。
- 只服务这些行的源数据整条删；被别的行共用的源数据只删对应这些行的部分：`write` 没带证据时每个 op 各存一条 `api_call`，按行就能切开。
- 这些行的来源与其他行 / 值的来源不相交，按行删除就没有副作用；判断只是集合求交，预览照此写明。
- 共用且切不开的源数据（文本证据、`file_ref` 的摘录）：整条隐私删除（其他行对它的贡献一并去掉），预览单列受连带的行。

**删除证据**

> **不进第一版。**

- **两种"在不在"分开算**。隐私删除问的是"这条源数据还算不算存在"，删除证据只删原文、贡献仍在，所以"被引用"要另算：
  - **"被引用"只看原文仍在的值来源**：删除证据过的来源不算。删掉后某个当前字段就没有原文仍在的值来源了才挡（报 `referenced`）；另有原文仍在的值来源（另一次写入的佐证、同一次写入引用的另一段证据）时允许；操作来源不挡；派生数据能重算，从不挡。细则见「引用：强与弱」。
  - **隐私删除时，删除证据过的来源仍算在**：它的贡献还在（删除证据的本意就是值留下），只是原文没了。
  - **冲突裁决的来源级别**沿用写入时判定、记在事件里的字面命中结果，不因原文删了而改变。
  - **与待处理事项**：冲突候选、待确认的提议值不是当前值，引用它们的证据可以被"删除证据"删掉；被删证据是某个候选 / 提议值**唯一的原文仍在的值来源**时，该事项标"已被取代"（原因码 `evidence_deleted`），
    不能再被采纳或确认——否则会把一个没有原文可查的值写成当前值。事项里的值本身照常保留（删除证据只删原文）。

下面几节只针对隐私删除，另有说明的除外。

### 来源：值来源与操作来源

**来源记到字段级，分两种**，对应原则 ①：

| 来源 | 是什么 | 包括 | 删除时 |
|---|---|---|---|
| 值来源（数据依赖） | 值从哪来 | 写入随附的证据（该字段引用的那几段）；值由请求本身给出、又没带证据时，该 op 的 `api_call`；回退、采纳候选、回到冲突前、系统裁定 = **对被搬运的那几个贡献的引用**（见下）；`migration_diff` 的 `set` = `resolve` 的证据（没带就是解决请求本身）；状态类表写入的区间参数 = 映射到它的证据 | 删除只沿它传播 |
| 操作来源（控制依赖） | 谁触发了这次写入 | 回退请求、解决请求（`resolve` 的证据或 `note`；没带证据时存成 `api_call`）、撤销一行的证据（撤销不带值） | 只用来满足"每次写入都有源数据"（K4）与审计；删掉它不影响值，也不撤销决定 |

**贡献**

- **一次写入对一个字段的贡献** = 这次写入给该字段的值，连同它的值来源。
- **改了值的字段都是贡献。** "改了"的基准是写入方所见的版本（`ver` 指向的版本；`ver` 是当前的就是当前状态），不是当前值：Agent 原样带回它读到的值，不是它的改动。
- **与所见版本同值的字段，分两种**（本条是同值佐证的权威定义，状态类表特有的部分见「时间 · 用同样的值写」）：

  | 写法 | 是什么 | 结果 |
  |---|---|---|
  | 用 `evidence_by_field` 显式指向了证据 | **佐证** | 是贡献：不产生新版本，给该字段追加来源，记在这次基础写入事件里，`timeline` 可见。当前值已被所见版本之后的写入改掉的部分，按普通写入参与冲突判定 |
  | 没有显式指向 | **无操作** | 不是贡献：不记来源，不参与冲突，不留任何边界 |

  这样有意佐证过的事实，删掉其中一条来源时不会消失；整行重发里原样带回的字段不会借着新证据留下来。
- **不同写入之间是"或"**：同一个值由两次写入分别给出，删掉其中一次的来源，另一次的贡献还在，值就保留。
- **同一次写入里一个字段引用多段证据是"且"**（含不给映射、默认引用全部）：saveslot 分不出值出自哪一段，**其中任何一段被隐私删除，这次写入对该字段的贡献就去掉**。
  这是不知道映射时唯一不会少删的默认。`write` 带多段证据又没给字段映射时，回执 `warnings` 提醒"删除其中任何一段都会去掉这些字段"；`deletion_preview` 对这种字段写明"同一次写入里另有 s_…，可用 `source_ref` 按字段佐证后再删"。

**搬运的值**

- **搬运的值存为对贡献的引用**：回退、采纳候选、回到冲突前、系统裁定的值来源记成"引用了哪几个贡献"（基础写入事件 + 字段 + 项；状态类表上搬运的区间就是写回的那一项自己的区间），不把源数据 ID 拍平成一份列表——被搬运的值若由两次写入同值佐证，拍平后分不出"或"与"且"。
  采纳候选所引用的贡献都不在时，这次搬运在该处没有贡献；回退与回到合并基见「重放规则 · 回掉」。链式回退是一条引用链，长度不超过历史。
- **采纳候选时，事项里值相同的其他候选的贡献一并作为值来源（"或"）**：否则删掉被采纳者的证据后值消失，而另一条同值的证据还在。
- **回到冲突前**的值来源是对合并基处生效的那几个贡献的引用（见「各处理方式的执行语义」），它与回退是同一种操作，删除重放见「重放规则 · 回掉」。

**区间参数**

- **状态类表的区间参数是内容**：起点、显式终点是用户说的话，和字段一样有来源——可在 `evidence_by_field` 里用保留键 `valid` 映射证据，不映射 = 这次写入的全部证据同时需要。
  区间的来源被删，这次写入在该实体上整体没有贡献。
- 默认终点（`next_change`）与纠错的默认区间（`corrected_span`）解析出的端点是 saveslot 的机械判定（原则 ②），删除后重新解析。但端点的取值是由别的贡献求得的（停在谁给出的挡点上），所以它记在单独的内容块里并指明出自哪些贡献；那些贡献被删时，这个块一并清除（见「由别的贡献求得的内容」）。
- **给出挡点的贡献**（权威定义在「时间 · 状态类表的状态」）：**该时刻是其区间端点的全部贡献，两侧都算，已被盖住的也算**（只算排在被解析的那次写入之前、生效的贡献，候选与待确认不算；区间取当前状态里的，删除重放时是本次重放里的）——区间在该时刻结束的与从该时刻开始的，含留下相邻空洞的撤销、佐证端点所属的佐证项。默认终点、纠错的默认区间、只带起点的撤销的终点停在一个挡点上时，记下的依赖就是这些贡献；状态类表补值段的两端同样按这一条取（见「其他」里常量 `backfill` 一行）。

**由别的贡献求得的内容**

- 一次写入的事件里，只有调用方这次给的值与区间端点是它"自己的内容"。**由别的贡献求得或抄来的内容单独成块，并记下出自哪些贡献**：默认终点与纠错默认区间解析出的端点；回退、回到合并基写回的各项的区间；`acknowledge` 确认覆盖的段；事项条目里别的写入的值与区间；删除事件里写下的结果与重述。
- **它依赖的贡献被隐私删除，或被那次删除重述，这个块就在那次删除的清除范围内。** 清掉之后仍需要的结果（那一项仍是贡献、事项仍未决）由删除事件重新给出。
  **唯一的例外是状态类表的补值段**（`schema.switched` 记下的常量 `backfill` 的区间）：它只在依赖的贡献**被删除**时清除，被重述不清除——补值位置照记录，删除不重述它，重述就清会让常量随一次无关的重新解析永久消失。不因此漏删：补值段记下的依赖是给出它两端的贡献，按"给出挡点的贡献"的口径取（已被盖住的也算），端点日期最初出自的那次写入一定在内（见「其他」里常量 `backfill` 一行）。
- **常量本身不是依赖**：schema 常量的值不随删除清除，块里抄了常量值时不为它记依赖。但状态类表上常量补出的那一段，区间来自别的贡献：块里的区间端点或一段的范围出自补值段时，把那一段补值记下的依赖抄进本块的依赖。
- 更早的历史版本里由这些块得出的内容随之标"已删除"：例如某次写入的默认终点停在被删写入给出的变化点上，删除之后按时刻读到那次写入与这次删除之间，这一项显示为已删除，不显示旧的终点。
- 块的形状见 [`../09-event-format.md`](../09-event-format.md) 3.5。

**其他**

- change_sources 带字段列表与来源种类（值 / 操作）；搬运的值来源是其中一种"引用贡献"的行。
- **换算、迁移、补值产出的值也有值来源**：

  | 值 | 值来源 |
  |---|---|
  | 写入时同量纲换算后的值 | 该写入对这个字段的值来源（同一个值，只换了单位） |
  | 确定性转换的结果（`migrate`） | 被转换的那一项贡献的值来源（第一版表达式只引用本字段的旧值，一项转换成一项）；那一项被去掉，转换结果随之去掉。引用多个字段的转换后续再做，届时是"各输入的值来源同时需要" |
  | `backfill` 的受限 SQL 表达式 | 该处旧值那一项的值来源（表达式同样只引用本字段） |
  | 常量 `backfill`、新增必填字段时补的常量（表达式形式的 `backfill` 在没有旧值的位置不求值、不给值） | 贡献记在那次 `schema.switched` 上，来源种类是"schema 常量"，不指向任何源数据：它出自 schema 里写的文字，**不随任何隐私删除清除**（归事件格式 9.4"不随这次删除清除的数据块"里 schema 文字那一类），预览的"不会删除"如实说明；**给过常量 `backfill` 的字段（新增必填、可选改必填）在存在判定里不算必填字段，两种表都一样**（见「重放规则」的「行 / 实体的存在」）。常量只补**存在**的行上该字段没有值的位置：事件类表、无时间表上是未撤销的行，状态类表上是实体存在、该字段没有值的区间；已撤销的行、撤销之内的空洞、实体不存在的区间都不补——否则回掉会把它当作"在空洞里填值"，之后撤回那次撤销时行回不来。**补在哪些位置照切换时的记录，删除不改**：切换事件记下补值位置（事件类表、无时间表是行 ID 列表；状态类表是实体与区间，区间由别的贡献求得，记下它依赖哪些贡献），`apply` 照记录登记、不现算。**状态类表上一段补值依赖的贡献**：这一段每一端，按「区间参数」里"给出挡点的贡献"的口径取——该时刻是其区间端点的全部贡献，两侧都算，已被盖住的也算（这个字段与"存在"上的贡献）；不沿这些贡献自己的依赖递归。补值照记录落账，与实体在重放里存不存在无关（见事件格式 5.5）。之后的删除让某处字段变空时，**不追补常量**（删除本来就可以让字段变空，结果记"保留，部分字段变空"）；状态类表上补值区间依赖的贡献被删时，那一段补值随之清除、不再存在（见「由源数据派生出的内容」）；依赖的贡献只是被重述时，那一段补值不清除。按定义的反事实，被删的写入在切换时若不存在，那里本该补上常量；不这样算，是因为删除重述切换补值要多一类贡献与新的重述形状，换来的只是被删之后的必填字段仍有一个常量值 |

- **字段的来源级别**：不落盘，现算——该字段**仍在的**值来源里，字面命中的那些证据段的声明级别取最高；一段都没命中则为"未命中"（见「来源级别」）。它只参与系统裁定（后续）；删除让级别变了时按原则 ② 重新裁定（见「重放规则」）。

### 重放规则

**做法**：① 找受影响的行 / 实体——被删源数据作为值来源出现在哪些写入的哪些字段里（含经搬运引用传过去的）；② 去掉这些贡献；③ 按下表把受影响行 / 实体的写入按 `seq` 重放，派生表随之重算（派生只由规则生成，没有自己的贡献要去掉）。
这是定义的计算方法（与增量视图维护的"先删再重新推导"同形），结果以参考求值器为准。事件类表、无时间表、状态类表用同一套。

| 项 | 规则 |
|---|---|
| 哪些写入 | 受影响行 / 实体的**全部写入**按 `seq` 重放，包括原本未生效的（未决的冲突候选、待确认的写入）：它们生不生效由下面几行在删除后的状态上重新判定；人已处理过的照记录 |
| 贡献在不在 | 一个字段的贡献在它的值来源（同一次写入的多段证据同时需要）与区间参数的来源都仍在时存在；采纳候选搬运的贡献在被引用的贡献（任一）仍在时存在；回退、回到合并基写回的项不随搬运来源消失，它的值在重放里重新求（见"回掉"一行） |
| 字段的值 | 按写入号最后一个仍在的贡献；状态类表按业务时间点：最后一个仍在、且区间覆盖该点的写入。事件类表、无时间表上，一次撤销之后另有生效、没被登记回掉的恢复存在时，这次撤销不再算：字段取它之下的值，行也不算已撤销（采纳"存在"上的修改候选写恢复存在、不登记那次撤销，见「各处理方式的执行语义」） |
| 同值判断（重算，只对贡献） | **回退、采纳候选、回到合并基写回的项同样适用，与普通贡献一视同仁**（回退、回到合并基写回的项有两条限定，见"回掉"一行）。基准是写入方所见的版本在删除后的样子。原本改了值的贡献，重放时成了同值：显式指过证据的成为追加来源，没指过的不产生新版本、也不再算贡献；原本是同值佐证的，前面的值被去掉后就是真正的改值 |
| 无操作（不重算） | **原本是无操作的字段保持无操作**，不会因为所见值被删而变成改动。无操作的值是调用方从 saveslot 读回来原样带上的，源头就是被删的那个贡献；日志里也不留它的值（见「来源」）。**没进事件的按来源键 op（`unchanged`、`skipped`）不重放**：日志里没有它，也没有它的值。这是原则 ② 的一处明确限定，也就是定义偏离一里的"写入时没有留下值的部分保持原样" |
| 参数（重算） | 起点、显式终点照用（它们的来源被删时见"贡献在不在"）。**默认终点（`next_change`）一律按原始传参、逐字段在删除后、该写入之前的状态上重新解析**——删除不只会去掉挡点，也会让被盖住的旧变化点重新露出来。纠错的默认区间（`corrected_span`）、只带起点的撤销的终点同样重新解析，"现在"用写入头里记下的时刻。**重新解析出的区间记进删除事件；一项贡献的区间以日志里最近一次给出它的事件为准**，之后的 `undo`、冲突判据、对它的引用都按最新的 |
| `ver` 冲突（重算） | 按「冲突处理 · 冲突判据」在删除后的状态上重判：写入所见版本之后、该写入之前，删除后仍有让该冲突单元的生效值变化、且与它冲突的操作，冲突才存在；不存在 → 见下一行 |
| 冲突消失之后 | 这次写入在删除后的状态上不属高影响 → 在自己的写入号生效，冲突事项已被取代。仍属高影响、且从未被人确认 → **转为待确认**，不生效：原冲突事项标已被取代，删除事件里生成一个 `awaiting_confirmation` 事项。抹掉已记录变化点的写入必须有人确认过，这条保证不因一次删除被绕过 |
| 系统裁定（重算，后续） | 冲突仍在时，按删除后仍在的来源级别重新裁定：候选的秩更高 → 候选生效（系统裁定）；否则保持当前值、候选留在事项里 |
| 高影响（重算） | 原本待确认、尚未处理的写入，在删除后的状态上不再属高影响 → 在自己的写入号生效，待确认事项已被取代。高影响 ② 的引用方全被删除时同理；④ 标 `later` 的项在重放里范围全为空时同理（要回掉的后来写入全被删除是它的特例）；④ 的另一种成因"写回的撤销会遮住之后的写入"，被遮住的写入全被删除或在该处不再给值时同理。已直接生效的回掉，之后因删除才遮住了新生效的值时，按偏离二保持生效，预览写明 |
| 人的决定（照记录） | 定义里列出的人的决定按记录执行、在原写入号生效；操作来源被删不撤销决定（不带区间的撤销，证据被删，行不复活）。带区间的撤销，区间的来源被删时按"贡献在不在"处理：整体没有贡献。`keep_effective` 的内容是"这些候选不生效"，照记录 |
| 回掉（回退与回到合并基） | `undo` 与 `take_previous` 是同一种操作的两个取法，由三样东西构成。**权威定义是表后的伪代码**，本行是它的文字说明。**① 回退记录（照记录，写入时列定，重放不改）**：回掉哪几次操作在哪些目标上的改动，逐条列（事件, 目标），目标是字段或"存在"，**不列下标**；一条覆盖该（事件, 目标）在重放里的全部项，不论下标是写入时就有的还是删除编出的，也不论写入时的状态。来源键字段一律不列入（键在得到之后不可变，没有可回退的东西）；schema 常量补出的项也从不列入（它不是一次写入，在回掉里只按记录之外的生效项盖住更早的项）。`undo` 列被撤回的那次操作在这一行上每条基础写入在它写入时的每个目标，不论当时生效、佐证、候选还是待确认，也与它现在还剩哪些项无关（这次 `undo` 写入时已被后来的写入盖住的条目另记在 `skipped` 里，带 `by_op`，只供历史与回执）；被撤回的操作本身是一次回掉时，列它的基础写入在它的回退记录里出现过的每个目标；`include_later` 连带回掉的后来写入列（该项的基础写入, 该项的目标），标 `later`；`take_previous` 列事项的冲突单元与区间内、合并基之后解决之前有项生效过的（事件, 目标）（含佐证，含回退或回到合并基写回的项，不论当时是否已被盖住）。事项的候选不进 `take_previous` 的回退记录，由事项的解决关闭。**② 范围（重放里重求）**：一项的范围 = 它在重放里的区间，扣除仍被盖住的部分（在它之后、本次回掉之前，不在回退记录里的已生效的项在该处取代了它；被删的操作不算）；`take_previous` 再与事项的区间取交，事项的区间 = 重放里仍存在的各候选的区间之并；`undo` 里标 `later` 的项再与 D(x) 取交（被撤回的操作在重放里生效、且该项能取代的各项的区间之并，见伪代码步骤 2）。事件类表、无时间表上一项是一个不可分的整体：仍被盖住时整项不回掉，否则整项回掉。登记的效力只在范围内，范围之外该项照常生效。**③ 取值的位置（照记录）与值（重放里重求）**：`undo` 是被撤回的操作之前，`take_previous` 是解决时记下的合并基操作号（不重算）；范围内每一处取重放里该位置上的状态——字段没有任何贡献时是"没有值"（三种表都一样），该处在一次撤销之内时写回一条不带内容的项（只做登记：被回掉的填值不再生效，撤销重新露出，撤销之下的值没有动），"存在"一侧是存在就恢复存在、是不存在就写回撤销。**任何情况下都不落回被回掉的项自己的值。** **被回掉的项是否生效以回退记录为准，不看写回了什么**：它在范围内不给值、不追加来源、佐证端点不算挡点。**写回的项**：回退记录的条目覆盖的项里还有在重放里是贡献的（含佐证）且范围非空时，不因与之前同值而被丢掉；回退记录的条目覆盖的项在重放里全都不是贡献、或范围全为空时，不再是贡献（候选全被删则范围为空，生效的一方照常生效；生效的一方全被删而候选还在，写回的项不再是贡献，候选保持已关闭）。**记录之外的写入**：回掉时还没生效、之后才因别处的删除而生效的写入不在回退记录里。它排在回退记录某一项之后时算盖住那一项，它盖住的部分不在范围内、由它生效；预览按"将会生效"列出。三种表结论相同。**回掉的目标本身是一次回掉**（撤回一次撤回、撤回一次 `take_previous` 的解决）：按普通写入处理，那次操作登记为"已被回掉"的项登记不变，值经由这次的写回项重新出现；事项保持已解决。**登记只在这次回掉生效时发生**：它进了待确认时不登记，确认后登记，被拒绝或被取代则不登记 |
| 行 / 实体的存在（重算） | **给过常量 `backfill` 的字段（新增必填、可选改必填）在存在判定里不算必填字段，两种表都一样**（与「时间 · 无值区间」里"有值"的定义同一条，写入时判定有值 / 无值区间同口径；写入校验仍要求带齐全部必填字段）：补值被清之后这个字段为空，行或实体照样存在，结局记"保留，部分字段变空"（`kept_fields_cleared`）。事件类表、无时间表：**每个必填字段都至少有一个仍在的贡献，并且至少有一个字段有仍在的、非空且不是常量补值的贡献**，行就存在，各字段取上面的值；否则整行删除。清空字段（值为空）也是贡献，照常参与"最后一个仍在的贡献"，但不能单独撑起一行（写入时只有空值的 `insert` 被拒，报 `empty_row`，见契约「值的编码」；这种行只会因删除重放而出现，之后对它的写入怎么处理随删除重放一起定）。状态类表按业务时间点判断：**全部必填字段在该点都有仍在的覆盖贡献**，该点就有值，其余点是无值区间；表上没有必填字段时，任一字段在该点有仍在的覆盖贡献即有值，清空（值为空）也算——与上面事件类表、无时间表"清空不能单独撑起一行"不同，状态类表上只被清空过的一段是有值、各字段为空（见「时间 · 无值区间」）；按 `entity_key` 定位的写入算给出了键字段（定位用的键值就是这次请求带的值，来源是这次写入的证据）。按来源键新增的写入、给行补键的写入同样算给出了来源键字段；键字段只在得到键的那次写入里有贡献，那次写入的源数据被删，这一行一定失去来源键，行本身按本行的规则判断去留 |
| 首次创建标记（重算） | 创建某个实体或某一行的那次写入失去全部贡献后，仍在的最早一次给出键字段（或全部必填字段）的写入成为首次创建；变化记进删除事件，`undo` 的可否按最新的标记判 |
| 疑似重复、字面命中（不重算） | 写入时判一次，照记录。被比中的行被整行删除时，对应的 `flagged` 事项标已被取代；删除不会新生成 `flagged` 事项 |
| 按来源键的写入（见「按来源键写入」） | **定位的结果**（这个 op 落到哪一行的行 ID）照记录，不重新定位：行 ID 记在元数据里，重新定位会让一次删除把后来的同步改写到另一行上。**基线位置**（逐字段的所见版本）照记录，与兜底取得的 `ver` 同样处理；`ver` 冲突用它在删除后的状态上重判。**同值重算**：基线值取删除后仍在的、这次写入之前这个字段上最近一项同步贡献的值（键是转来的，原行上被删的同步贡献不再算数）；原本是无操作的保持无操作。**转移键照记录**：补键那次写入的键贡献仍在，键就在补了键的那一行；那份贡献被删除执行去掉之后，键回到让出它的原行（仍为已撤销），宽限期内这个键冻结。原行的撤销是人的决定，照记录，删除不会让它重新存在。键回到原行之后**不再算"键是转来的"**：补键之后按这个键的同步 op，定位照记录（仍落在补了键的那一行），但在删除后的状态上这个键已属于已撤销的原行，这次写入按"被撤销的行不复活"重述为不再是贡献（`dropped`），不沿用转来时的基线 |
| 已生效的保持生效 | 原本已生效的写入，即使在删除后的状态上重算会成为冲突候选或待确认，**照常生效、不退回**（定义的偏离二），预览写明。例：被删写入原本让后面一次同值佐证不算改动，删掉后它成了夹在 `ver` 与这次写入之间的改动；或被删写入原本盖住了某个变化点，删掉后一次显式终点的写入会抹掉它 |
| `ver` | 被删除改动过的行 / 实体换新 `ver`，编码这次删除确认（或撤回）的操作号（见「编号」） |

**回掉的权威定义**（参考求值器的伪代码；写入时与删除重放时走同一段，其余文档的文字说明与它不一致时以它为准）

```
回掉(记录 R, 取值位置 pos, 本次操作号 n, 贡献集合 C, 候选集合 K):
  # R    回退记录：条目的列表，每条是（事件 e, 目标 t），t 是字段 f 或"存在"，不带下标。
  #      可带照记录的标注 later（include_later 连带的后来写入）。undo 另记 skipped：这次 undo 写入时已被
  #      后来的写入盖住的条目，带 by_op，只供历史与回执，这里不读它。
  #      照记录，不重算。
  # pos  "操作 m 之前"（undo，m 是被撤回的操作）或"截至操作 m"（take_previous，m 是记下的合并基）。照记录。
  # C    重放里的全部贡献项（被删的不在其中），每项有：操作号、目标（字段 f 或"存在"）、
  #      状态（生效 / 佐证 / 候选 / 待确认）、区间、内容（值、没有值、撤销、恢复存在）、
  #      以及它已被哪些回掉登记过（各带范围、各带那次回掉的操作号）。
  # 求值顺序：各次回掉按操作号从小到大求一遍。一次回掉只读操作号比它小的回掉所做的登记，没有循环。
  #          因删除而在自己的写入号生效的回掉，按它自己的操作号排进这个顺序。
  # K    take_previous 时事项的候选项；undo 时不用。
  # 区间：状态类表是业务时间的区间；事件类表、无时间表上每项的区间都是同一个不可分的整体 ⊤。
  # 不带内容的写回项（只做登记的那种，见步骤 6）在取值与"取代"里都当作不存在：它不给值，也不盖住谁。

  1  R' = { c ∈ C | （c 的事件, c 的目标）∈ R }：R 里每条（e, t）在重放里的全部项，
          不论下标是写入时就有的还是由删除编出的，不论写入时的状态。
          所以被回掉的操作写入时是候选或待确认、之后因删除生效的部分同样在 R' 里。
          不在 R 里的操作不补：回掉之后才因删除生效、R 没有列的操作，按"记录之外的写入"处理（见下）。
          undo 的目标 m 本身是一次回掉时，R 列的是 m 的基础写入在 m 的回退记录里出现过的每个目标，
          所以 m 之后因删除长出的写回项同样在 R' 里。
     在 = [ r ∈ R' | r 的状态是生效或佐证 ]

  2  若是 take_previous：
         域(r) = ⋃ { 区间(c) | c ∈ K 且 c 没有被删 }  # 事件类表：K 里还有项没被删 → ⊤，否则 ∅
                                                    # c 在重放里成了同值（不再是改动）仍算在；只有被删才不算
     否则（undo）：
         r 的条目不标 later：域(r) = 全部业务时间（事件类表：⊤）
         r 的条目标 later  ：域(r) = D(r) = ⋃ { 区间(r') | r' ∈ 在，r' 的条目不标 later，r 按步骤 3 取代 r' }
                             # 被撤回的操作在重放里生效过、且 r 能取代的那些项的区间之并；事件类表上是 ⊤ 或 ∅。
                             # 只取"在"里的项：被撤回的操作当时是候选的部分从未生效，不算"相交"；
                             # 删除让那部分生效后它进"在"，D 随之变大。r 只取生效（不含佐证）的项，见列法。

  3  对每个 r ∈ 在：
         盖住(r) = ⋃ { 区间(x) ∩ 区间(r) |
                        x ∈ C，x 的状态是生效，（x 的事件, x 的目标）∉ R，操作号(r) < 操作号(x) < n，x 取代 r，
                        只算 x 没有在该处被操作号小于 n 的回掉登记过的部分 }
         范围(r) = ( 区间(r) − 盖住(r) ) ∩ 域(r)

     x 取代 r：
         r 是字段 f 的项      ：x 是字段 f 的项，或 x 是撤销
         r 是撤销             ：x 是恢复存在，或 x 是在这段空洞里填值的字段项
                                （有值的字段项才算填值；已在该处被登记回掉的不算，见上一句）
         r 是恢复存在         ：x 是撤销

  4  若这次回掉自己没有生效（待确认、被拒绝、被取代）：不登记，不写回，结束。
     # 生效有三种时机：写入时就生效；待确认、经确认生效（确认触发的基础写入带自己的 R，按确认时的状态列定，
     # n 是那次解决的操作号）；待确认、因一次删除不再属高影响而在自己的写入号生效（R 是提议时列的那一份，
     # n 是它自己的操作号，登记由那条删除事件的落账做）。

  5  登记：对每个 r ∈ 在，记"r 在 区间(r) ∩ T(r 的目标) ∩ 域(r) 内已被操作 n 回掉"，
     T(t) = ⋃ { 范围(r') | r' ∈ 在，r' 的目标是 t }，也就是步骤 6 在目标 t 上写回各项的区间之和。
     # 不变式：本次回掉在目标 t 上写回各项的区间之和 = T(t)。apply 只读写回项的区间做登记，不求范围；
     #         标 later 的项的 D 由 apply 按块自己算（被撤回操作的生效或佐证项里它能取代的那些的区间之并）。
     # 区间(r) ∩ T 比 范围(r) 多出来的部分，是 r 被记录之外的写入盖住、而同一目标上另一条记录项没被盖住的地方；
     # 那里本来就由写回的项盖住，多登记不改变任何取值。
     被撤回操作自己的项域是全部业务时间，就是 区间(r) ∩ T；标 later 的项再与 D(r) 取交，
     ④ 不成立（标 later 的项范围全为空）时，后来写入的项若被登记，登记处它已被记录之外的写入取代，
     或已被更早的回掉登记，所以登记不改变任何取值（apply 不求盖住，所以不让登记为空）。
     不登记"在"之外的项（仍是候选、待确认的项，含落在别的条目范围里的候选）。
     登记的效力：r 在该范围内不给值、不追加来源，它的佐证端点不算挡点；范围之外照常。
     已有的登记不动。

  6  写回。对每个目标 t（每个出现在 在 里的字段，以及"存在"）：
         T = ⋃ { 范围(r) | r ∈ 在，r 的目标是 t }
         对 T 里的每一处 p：
             S = 状态(pos, t, p)
                 # 只用操作号满足 pos 的贡献、只算操作号满足 pos 的回掉所做的登记，按重放的普通规则取值：
                 # 字段  ：该处最后一个生效、且没有在该处被登记回掉的字段 t 的项或撤销；
                 #         是字段项 → 它的内容；是撤销 → 在撤销之内；都没有 → 没有任何贡献
                 # "存在"：该处是否处在一次生效、且没有在该处被登记回掉、之后又没被恢复或填上的撤销之内
             字段 t  ：S 有值 → 写回这个值，值来源是对给出它的那一项的引用
                                （给出它的是 schema 切换的常量补值时：照抄这个值，来源记"schema 常量"，
                                  不引用；常量本身不列进依赖——它的值不随删除清除。
                                  状态类表上这一处出自一段补值段，它的区间来自别的贡献，依赖按步骤 8 抄）
                       S 没有任何贡献 → 写回"没有值"
                       S 在撤销之内 → 写回一条不带内容的项（只做登记、不给值、不盖住下面的东西）。
                                      被回掉的项（在空洞里填值的那一项）登记之后不再算填值，撤销重新露出，
                                      这一处回到空洞；撤销之下的值没有动，之后撤销被回掉或被删时照常出现
             "存在"  ：S 是存在 → 写回"恢复存在"
                       S 是不存在 → 写回撤销
         把相邻、内容与给出者都相同的各处并成一项。"存在"上没有给出者，相邻各处只按内容并：
               跨不同撤销的相邻各处并成一项写回撤销，步骤 8 的依赖列全这些撤销。
         以写入时的区间块为准：新编出的下标从哪一项分出，以基础写入事件写入时给出的区间块为准
               （它固定在日志里，不随删除的先后、也不随被撤回的删除变）：看新下标在这次重放里的区间起点
               落在哪一条原有项写入时的区间里；落在各区间之外或空隙里，归左邻（按写入时区间的起点排序，
               在最前面时归第一项）。它只用于编号与前提声明的第 2 部分（见「写入的前提」），不影响回掉的覆盖：
               覆盖按（事件, 目标），见步骤 1。
         下标：写入时按区间起点从 0 编。重放时，原有的每一项沿用它的下标，留在与它写入时区间块相交的
               第一段上；之前由删除编出的下标留在与它原区间相交的第一段上（落在哪一段只影响编号）；
               新分出来的项从该目标已用过的最大下标之后接着编。
               原区间 = 本次重放之前，日志里最近一次给出这一项的区间（它原来的区间块，或更早一次删除的重述）：
               按日志顺序往前找，跳过被撤回的删除的确认事件给出的块（被撤回的删除给出的块在任何重放里
               都不算；撤回事件自己的重述照算），也跳过重述为 dropped 的，取第一块给出了区间的。
               它只用于新编出的下标保留编号。
               几条原有的项落进同一段时一律并成一项，留下标最小的，其余重述为 dropped：同一（事件, 目标）
               的各项被同一组回掉覆盖，不再有因覆盖不同而切开的情形。
               细则见事件格式 §5.7（任何写入的项都按这一条，不只本步骤的写回项）。

  7  写回项的状态：
         在 为空，或所有 范围(r) 都为空 → 没有写回项（原有的写回项不再是贡献，
                                          即事件格式里重述为 dropped）
         否则 → 生效，不参加同值重算（不因与之前同值而丢掉）

  8  写回项依赖的贡献（区间被清除与重述的依据）：
         在 里的各项；步骤 6 里给出 S 的各项；步骤 3 里盖住 r 的各项；take_previous 另加 K 里没被删的各项；
         另加：写回项每个区间端点处，取值位置上相邻两段状态的给出者（两侧都列；
               一侧没有任何贡献时只列另一侧；一侧在撤销之内时列那次撤销）。
         以上任何一项是 schema 常量补值时（给出 S、给出端点，或在步骤 3 里盖住 r）：
               常量本身不列（它的值不随删除清除）；状态类表上它是一段补值段，
               把那一段 backfill 记下的依赖抄进来（补值段的区间来自别的贡献）。
```

- 写入时：C 是当时的全部贡献；步骤 6 的结果就是这次基础写入里的写回项，步骤 5 就是 `apply` 的登记。
- 删除重放时：C 是去掉被删贡献、其余各项按重放结果重述之后的集合；R、pos 不变。步骤 6 的结果与日志里最近一次给出的不同，就由删除事件重述；步骤 5 的范围随之更新。
- 写入时回退记录怎么列（`undo` 列目标操作的每条（事件, 目标），来源键字段除外；`take_previous` 列事项的冲突单元与区间内、合并基之后有项生效过的（事件, 目标），同样除去来源键字段）不在这段里：它只在写入时做一次，结果就是 R。来源键字段因此从不在 R 里，写回项从不触及键字段，"撤回一次撤回"也造不出两行同键。**schema 常量补出的项从不列进任何回退记录**：`undo` 列目标操作的条目、`include_later` 连带回掉的后来写入、`take_previous` 的"有项生效过的（事件, 目标）"都跳过它们（`undo` 的目标本身是 schema 切换的操作号时直接拒绝）。所以常量补值只以"记录之外的生效项"出现在 C 里，按步骤 3 照常盖住更早的项。
- **写入的前提不是 C 的一部分，回掉不读它**：声明不是贡献；带 `revert` 的 op 不能带前提，回掉自己没有声明。回掉之后各字段当前值的出处项变了，标记按新的出处项现算——写回的值沿搬运引用走到头是更早的那一项贡献，那一项的声明随之重新显示（见「写入的前提」）。
- 回掉之后才生效、不在 R 里的写入 y：它在 C 里、操作号在某个 r 之后且小于 n 时，按步骤 3 盖住 r，它盖住的部分不在范围内，由 y 生效；它排在所有 r 之前时不盖住谁，范围内被有内容的写回项按先后盖住。只做登记、不带内容的写回项不盖住任何东西：取值位置在撤销之内、而该处另有一次记录之外、后来才生效的填值时，露出的是那次填值，不是空洞。三种表是同一段代码。

- "变化点""挡点"的定义见「时间 · 状态类表的状态」。
- "因删除而在自己的写入号生效"的含义：在按写入号排贡献先后时它排在原来的位置；业务表与版本表的改动记在删除确认事件的操作号上。

### 推论

由定义与重放规则得出，不是另加的规则；每条都对应参考求值器上的一条性质测试（architecture §11）。

- **行的存在按字段累积**：不要求哪一次写入单独给齐全部必填字段；各必填字段的贡献来自不同写入也行，来源完好的值不丢。
- **删一句纠错的话，值回到纠错前**：事件类表与状态类表结果一致。
- **另有来源佐证的事实不消失**：另一次写入的贡献还在。
- **状态类表的相邻段恢复原值，不留无值区间**：被删写入切出来的段消失，被它盖住的更早写入重新可见；露出来的旧变化点让默认终点随之缩回。
- **回退值随被搬运的贡献一起删**：该处取重放里被撤回的那次操作之前的值，不会落回被撤回的那次写入的值；回退请求只是操作来源，留不住值。
- **删除可能让原本未生效的写入生效**：冲突成因全被删的候选、高影响成因被删的待确认写入、删除后级别更高的候选（系统裁定，后续）。按定义生效，**但必须可见**：`deletion_preview` 单列"以下原本未生效的写入将会生效"，删除回执与"删除已确认"事件写明；
  对应事项标"已被取代"（原因码 `deleted`）——冲突仍在、只是重新裁定的，事项保持未决，与普通的系统裁定一样。撤回时退回原状态。
- **冲突消失、但仍属高影响的写入转为待确认**，不直接生效；预览单列"将转为待确认的写入"。
- **删除不增加未决事项**：已生效的写入保持生效，所以已生效的写入不会因删除变成冲突；每个新出现的未决事项，要么是被这次删除取代的冲突事项转成的待确认，要么来自同一次写入原来的未决事项：原事项被先前的删除取代、因这次删除回到未决且种类没变的，恢复原事项；种类变了的（待确认 ↔ 冲突，原事项被这次或先前的删除取代），原事项保持已被取代，由一个新事项一对一接替。
- **人已经解决的冲突，照记录**：冲突被 `keep_effective` 解决之后再删生效值的来源，候选不会因此生效；生效值失去来源，按普通规则落回最后一个仍在的贡献。选的是 `take_candidate` 时，值是对候选贡献的引用，不受影响；选的是 `take_previous` 时，照记录的是回掉哪几次操作在哪些目标上的改动与合并基的操作号；范围与回到的值在重放里重新求（见「重放规则 · 回掉」）。
- **顺序无关**：先删 A 再删 B = 先删 B 再删 A = 一次删 {A, B}。比较状态与事项，不比较重述的下标与 `dropped` 条目；之后带旧 `ver` 的写入可能因删除历史不同而判定不同（删除按记下的区间算作改动）。
- **撤回还原**：删 A 再撤回，未被宽限期内的写入覆盖的部分，与"从未删 A、但被记为保持生效的写入按在自己的写入号生效、事项被保持已被取代的写入也不生效"的重放结果相同；两者都没有时，就是与从未删 A 时相同（见「撤回与宽限期」）。保持生效的写入会连带改变别的写入的判定（例如另一次写入因此不再属高影响而生效），这是规则的正常结果，回执单列。放回的候选按撤回时的状态重判（见「撤回与宽限期」）；它们所在的区间以重判的结果为准，可能与强制重放不同。
- **不多删**：值来源里不含被删源数据的贡献不会被去掉。但它在哪些业务时刻上生效，可能因为挡点重算而变——被删的写入原本挡住了某次默认终点的写入，删掉后那次写入延伸过去，盖住了别的完好贡献（例：`[10-01, ∞) 5000`；`[11-10, 11-20) 4000`；"11-02 起 3000"不传终点，停在 11-10。删掉 4000 那句，3000 延伸到一直延续，11-20 之后原本的 5000 被它盖住）。这是值的变化：实体换新 `ver`，预览按"重新分段"列出。只带起点的撤销同样会延伸：它的终点停在被删写入给出的挡点上时，删除后撤销延伸过去，之后落在延伸部分里、没带齐必填字段的写入不再撑起那一段，那一段由有值变成无值；预览与回执单列这些区间与原因（见「预览与回执要写明的内容」）。
- **不漏删**：留下的每个值、段端点、事项条目、翻译、分组键都不依赖被删源数据；日志里由被删贡献求得的内容（别的写入停在它上面的默认终点、回退与删除结果里抄下的区间，含出自相邻那一段的端点、经常量补值段转来的端点）同样清除。无操作的字段不留值，所以"原样带回"不会让被删的值借另一次请求留下来。**唯一的例外**是别的请求的请求键与显式幂等键的指纹：它们是按原始请求体算的哈希，含那次请求原样带回的值，只随那次请求自己的证据删除（见 [`../09-event-format.md`](../09-event-format.md) 9.5）。
- **`undo` 回得干净**：删除让某次旧写入的默认终点延伸之后，`undo` 那次写入回掉的是延伸后的整段，不会留下没有任何写入能撤回的残段。

### 结果怎么落进日志

- **"删除已确认"事件写全结果**：

  | 结果里有什么 | 说明 |
  |---|---|
  | 每个受影响行 / 实体删除后的样子 | 按字段、按项（状态类表按区间），各带值来源；新 `ver`。**列哪些，三种表都一样**：取值、或给出它的贡献项与删除前不同的字段都列，由本次被重述的项给出的也列（状态类表"按段给出"的两类段是它的特例）。取值没变、只因为给出者、判定结果或给出它们的块被重新给出而列出的行，结局记"只换了来源"（`sources_changed`）。结果里的行在重放里不存在时（例如插入它的那次写入的块已全部移除），`apply` 新建它。**"存在"的给出者变了的行整行列出**（创建它的那项贡献被删、行靠别的贡献留下）：每个字段的值与给出者都列，含出自 schema 常量的，重放里由这条结果新建、字段齐全。**有"存在"项被删除或被重述（含原样重述），或有只做登记的写回项（`uncovered`）被重述时，这一行或实体必须列出**，三种表都一样：事件类表、无时间表上行在不在由结局表达，结局按删除后的样子取既有的值（整行删除、保留且部分字段变空、部分字段回到更早的值，取值都没变时"只换了来源"）；状态类表上与这些项的区间相交的各字段的段整段列出，"这些项的区间"取重述前最近一次给出的区间与重述后的区间之并。墓碑之后从头重放时，这些项原来的区间块已移除、在原事件处不落账，空洞与登记只能从这里取到。**状态类表上凡是列出了实体（不论因为哪一条），都给出删除后的全部无值区间**（没有无值区间时给空列表） |

  派生写入由 `delete` 另行生成为派生写入事件：**受影响行在删除前后所落的每个派生分区各追加一条，结果没变也追加**（派生规则一侧"结果没变的不记"对删除不成立）。墓碑落账之后从头重放时，被删的块已移除，中间状态与当时不同；删除事件里写全的结果与这些派生写入是把末端拉回线上状态的唯一一处。**撤回删除与确认对称**：撤回事件同样为受影响行撤回前后所落的每个派生分区各追加一条派生写入，结果没变也追加。
  例：#41 插入一行（R1：date、distance、feeling），#57 纠错 distance（R3），#60 用 R3 按字段佐证 date。删 R1：date 的值没变、给出者从 #41 换成 #60，也要列进结果；只列 feeling 的话，墓碑之后从头重放，#41 的块全已移除，#60 是佐证、不改业务表，末端 date 为空。
- **位置是内容块的地址**：事件的内容分成若干内容块，每块按"事件 `seq` + 块路径"寻址，路径里只有固定的词、不透明 ID 与下标，不含用户内容（见「完整性与溯源」）。**删除以块为单位，整块删除**，没有块内的部分删除。
- **位置列表包括本事件自己内容区里的影响摘要哈希**（`dc_` 绑定的那个，由被删内容算出，放在内容区），也包括前提声明里随被删证据清除的业务时间块（`premise_valid`，见「由源数据派生出的内容」）。
- **多项删除各自列全位置**：每项删除的位置列表独立于其他待执行的删除，各自列全。到期执行时逐块删除，块已不在就跳过；撤回一项时，只释放不被其他待执行或已执行的删除列出的块。
- **迁移进行中删除**：新版表还在构建（(c) 类、可丢弃）时，删除事件只给当前版本的结果。
  - 构建中的新版表对受影响的行**整行丢弃、按日志重建**（此时被删内容已读不到）。到期物理删除时构建还没结束的，同样清掉构建中的表里这些行的历史内容。确定性迁移也有迁移中阶段，这一条第一版就做。
  - 从空存储重放时不需要特殊处理："删除已确认"与"撤回"事件和基础写入一样是日志里的事件，`apply` 在切换事件处把它们的逐字段结果经同一套确定性转换落进新版表；被删内容在日志里已是"已移除"，转换时跳过。
  - 抽取作业（后续）：`jobs` 把受影响行的抽取工作项（含已交、未切换的翻译）**全部退回池里重做**（只带剩余原文）。翻译本来不可重放，结果与"删除事件给出新版结果"相同，少一套逻辑。
- **判定结果以最近一次给出的为准**：一项贡献的生效状态、区间，一次写入的首次创建标记，由那次写入的事件给出；之后某次删除确认或撤回的重放把它改了，就由那条删除事件给出新的。`undo`、冲突判据里"那次写入的区间"、搬运引用、佐证端点都读最新的。
- **删除后的样子按段给出**：状态类表上，一段 = 同一项贡献连续给出值的最长区间。列出取值或给出它的贡献与删除前不同的段，由被重述的项给出的段，以及与被删除或被重述的"存在"项、被重述的 `uncovered` 写回项的区间（重述前与重述后之并）相交的段；列出的实体一律连同全部无值区间一起给出；整段列出，不裁剪到有变化的那部分——裁剪出来的端点可能正是被删的内容。由常量补值给出的段，常量本身不记依赖，这一段的区间出自补值段，抄那一段补值记下的依赖。
- **删除与撤回事件改业务表只按结果**：被重述的项只改来源表（生效状态、区间、搬运引用，含"没有值"与只做登记的写回项），不直接改业务表。被重述为"没有值"的写回项若仍有部分露在外面，那一段按"由被重述的项给出的段"已在结果里，写成值为空、没有值来源。被回掉的是哪些项不因重述而变；登记的范围按重述后的写回项区间重算。
- **`apply` 只照做，不重放、不重跑拆行**：事件里的结果是 `delete` 在当时内核版本下按定义算出的；内核升级可能改计算细节，重放旧日志不能因此变结果。同一内核版本下，事件里的结果应等于参考求值器在该处的重算结果（测试对照，architecture §11）。
- **删除后的样子是一个新版本**；更早的版本不改写，其中由被去掉的贡献得出的内容（各次写入事件里那个字段的值与字段级来源、版本表里对应的历史值）宽限期内读不到、到期物理删除，该处标"已删除"。
  按时刻读到删除之前，看到的是"去掉被删内容的当时状态"，不按定义重算、不保证等于当时的线上状态——可能读到必填字段为空的历史行（按定义那个时刻这一行并不存在），照常返回、标 `partially_deleted`；退役表同理。
- 删除后结果里的值本身也是内容，带各自的值来源；以后删到这些来源时同样级联（见下表）。

### 撤回与宽限期

- **宽限期内的写入**照常基于删除后的状态执行；写到受影响行 / 实体时，回执 `warnings` 提示"该行有一项可撤回的删除（`pi_…`）"。写到已被整行删除的行 / 实体报 `not_found`，文本写"该行已被删除（`pi_…`，可撤回）"（实体同理），不回显内容；不新建，也不让它复活。**"已被整行删除"按存在判，只看集合**：一次写入（含撤销、`undo`）时，在当前被删集合（已确认、未撤回的全部删除，含仍在宽限期的）下的重放里这一行 / 实体不存在（事件类表：「重放规则」里的存在判定不成立；状态类表：没有任何业务时刻有值），而在当前被删集合去掉全部待执行删除的重放里它存在。这时报 `not_found`，附**全部**碰到它的贡献的待执行删除 ID（在后一个重放里取它的贡献：值来源，含经搬运引用传过去的，加区间来源），按操作号排序。其余情形照普通规则：当前重放里它一项贡献都不剩（待执行删除不是原因）报普通的 `not_found`；事件类表上整行撤销仍在报 `revoked`；状态类表上照常填空洞（「时间」高影响 ①）。判据只取决于被删集合与其中哪些仍待执行，与删除的先后、撤回过什么无关。
  待删除的源数据不能再被证据引用（`source_ref` 报 `invalid_argument`）。
- **宽限期内来源键仍然占位**：被这项删除从行上去掉的来源键，在物理删除之前照样占着键索引；命中它的按来源键 op 被跳过（`skipped`，`skip_reason: "pending_deletion"`，附删除 ID，只在回执里给），不重新新增。删除会去掉某个键在任何一行上的贡献（持有它的行，或它转来之前的原行）时，这个键**冻结**：不能转移，按它的同步一律跳过。撤回时这项删除不再让它冻结，没有别的未执行删除冻结它时才解冻，持有者不变；到期执行后按删除后的状态重定持有者（见「按来源键写入」）。理由有两条：与请求键同一个口径（待删除的请求键在物理删除前照样参与查重）；撤回要能还原——宽限期内若同步新增了一行，撤回之后原来那一行带着同一个键回来，一张表里就有两行同键。
- **宽限期内重发**：已列入待删除的请求键在物理删除前照样参与查重（幂等窗口不长于宽限期：显式幂等键 24 小时、服务端算出的请求键 10 分钟，都从写入时算起，而物理删除最早在删除确认后 24 小时）——客户端重发一条刚被删除的写入时，回执"原写入已被删除（`pi_…`），未重新写入"，不会重新写入。显式幂等键命中已列入待删除的写入时，同样按 `original_deleted` 重放、不再比对内容指纹（待删除的内容不参与比较），不报"同键不同内容"。请求键过了幂等窗口不主动删，随证据删除。
- **撤回**：`delete` 按定义再算一次（被撤回的删除不再算被删），连同宽限期内的新写入按 `seq` 重放；冲突、高影响照原则 ② 在重放出的状态上重算。结果、新 `ver`、恢复的事项都写进撤回事件，`apply` 照做。
  - **宽限期内已经生效的写入保持生效**（定义的偏离二同样适用于撤回）。所以撤回后，未被宽限期内的写入覆盖的部分与从未删除时相同；被覆盖的部分以宽限期内的写入为准。
  - 因删除被取代的事项：宽限期内有写入按冲突判据改过它涉及的字段的，保持"已被取代"（原因写那次写入），其余恢复。因删除新生成的待确认事项被取代。
  - 因删除被去掉了一个候选、而事项仍未决的：撤回时候选放回原事项。**事项在宽限期内已被解决的**：原事项的解决不动；放回来的候选按撤回时的当前状态重新判定（这个状态是撤回的重放里先不放回任何候选所得的状态；判定一次，结果记进撤回事件，这次重放里不再重判）——与当前生效值同值的按无操作 / 佐证的普通规则处理，否则为它另开一个冲突事项（记下与原事项的关联）。这样每个候选要么在未决事项里，要么被一条决定关掉。**重判为佐证的放回候选只做两件事：关掉这个候选，给它与当前生效值相同的那段追加来源（来源表改动记在撤回事件的操作号上）。它不给值，也不算佐证端点**：起点与终点在这次撤回的重放与之后的任何重放里都不是挡点，不参与任何写入的默认终点（`next_change`）、纠错的默认区间（`corrected_span`）、只带起点的撤销的终点的解析，也不算"给出挡点的贡献"。之后的删除去掉了它所佐证的值时（按重判它的那次撤回所在位置、在当前重放里的值判；之后的写入（含回掉）改了值不算），它不接替给值，按被那条决定关掉的候选处理，那一段的来源随之去掉。这样重判不改变撤回重放里的任何值与区间：判定所依据的状态就是判定之后的状态。
  - 因删除生效的写入退回原状态；若宽限期内已有别的写入以它的 `ver` 为基础改过，则不退回——撤回事件里把这些写入记为"保持生效"（`kept_effective`，附是哪次写入以它为基线），回执列出。"以它为基础改过"指：同一行 / 实体上、`ver`（显式或兜底取得）不早于那次删除确认、且生效过的写入（写入时生效、经人的决定生效或佐证都算；全部是无操作的不算），不限字段——它看到的是含这次写入的那一行。**保护持续**：被记为保持生效的写入从这次撤回起算"已经生效过"（偏离二），之后的删除与撤回都不再把它退回。
  - 因删除而重新解析过的区间、首次创建标记，撤回时再算一次并记进撤回事件。
  - 先提交租户里的撤回事务，再更新删除登记（见「删除登记」）。
- **到期物理删除（墓碑）**只物理删除内容，不改当前状态——当前状态在确认时（及之后的写入）已经定下。

### 预览与回执要写明的内容

删除证据与隐私删除先预览、再确认。预览**不删任何东西**，回执的字段形状见 contract 第 10 节的 `deletion_preview` 与 `delete`；下面是内核必须算出、预览与回执必须写明的内容（权威定义在这里）。

- **总量**：删除多少条源数据、影响多少行、重算多少个派生值。
- **逐行 / 逐实体的结果**（隐私删除，按「删除结果的定义」）：整行删除 / 保留且某些字段变空 / 某些字段回到更早的值 / 重新分段，以及**判定理由**——每个必填字段还剩哪些写入的贡献（例："runs r_01JC… 整行删除：date 只来自这句话；s_R3 也提到这次跑步，但它的写入只给了 distance"），调用方可据此先用其他证据（`source_ref` + `evidence_by_field`）佐证缺的字段再删。
  回退的值随被删来源一起去掉时写明落回的值与原因（"11-10 至 11-19（含）回到 5000（#101 的值；#111 回退掉过 #109 的 4500）"）；一个字段引用了同一次写入的多段证据时写明"同一次写入里另有 s_…，可按字段佐证后再删"。
  **将由有值变成无值的区间**（`gaps_opened`，只列状态类表；事件类表、无时间表上整行删除已由结局表达）：删除后由有值变成无值的区间，以及原因。一个区间只列一次：落在一次撤销之内时原因取 `revocation_extended`，否则取 `required_field_removed`。原因取两个值：`required_field_removed`——某个必填字段在该处已没有仍在的贡献；`revocation_extended`——某次只带起点的撤销，终点停在被删写入给出的挡点上，删除后重新解析、延伸过去，之后落在延伸部分里的写入没带齐必填字段，撑不起那一段（例："amount 与 owner 都必填；删掉 11-20 起 4000 那句后，11-05 起的撤销延伸到一直延续，11-20 起的 4500 只写了 amount，11-20 起将没有值"）。后一种与定义一致（写入时的校验不重跑，已生效的照常生效），但从"删了一句关于 amount 的话"看不出整段会没有值，所以必须单列、写明原因。它们在预览与回执里现算，不进事件。
- **原本未生效、因删除将会生效的写入**（单列，不与其余结果混在一起）：冲突成因被删的候选、高影响成因被删的待确认写入、删除后级别更高的候选——逐条给出写入、值与对应事项（将标"已被取代"；仍有冲突、只是重新裁定的保持未决）。
- **冲突消失但仍属高影响、将转为待确认的写入**（单列）：逐条给出写入、值、会被覆盖的段、原冲突事项（将标"已被取代"）与新生成的待确认事项。新事项的发起者是原写入的写入者；它可能无人值守，回执提示当前操作者去处理。
- **将由待确认转为冲突的写入**（单列）：它的 `ver` 冲突在删除后的状态上重算才出现（例如所见版本之后另一次写入因这次删除而生效）。逐条给出写入、值、原待确认事项（将标"已被取代"）与新生成的冲突事项，一一对应。
- **因先前的删除才生效、本次将回到未决的写入**（单列）：逐条给出写入、值与回到未决后的种类（待确认 / 冲突）；种类没变的给出恢复的事项（撤销它的"已被取代"，见「删除结果的定义」偏离二），种类变了的给出原事项（保持"已被取代"）与接替它的新事项，一一对应。
- 因删除被取代的事项；翻译结果被清除、将开补抽的（行, 字段），以及没有剩余原文、直接置空的（抽取作业后续）。
- **按行删除**（`rows`，后续）：这些行的来源与其他行不相交时没有副作用；被其他行共用、又切不开的源数据单列警告与受连带的行（整条隐私删除）。
- 删除证据（后续）会让某个当前字段没有原文仍在的值来源时，不出预览，直接拒绝并列出引用方（见「删除的种类」）。
- **仍引用被删行的行**（单列）：整行被删的行若还被别的行的 `ref` 字段指着，列出这些引用方。它们不被改动，之后读取时带 `dangling_ref` 标记（目标已删除，见「写入请求 · 引用字段」）。
- **以将被改动的值为前提的行**（单列，`premise_affected` 的预告）：删除会让某条前提声明所声明范围上的值改变时，列出依赖行、涉及的字段与声明它的写入，最多 50 条，另给总数。它们不被改动，删除之后带 `premise_changed`（原因 `deleted`，见「写入的前提」）。理由与 `ref` 的先例相同：依赖行还在库里，别的 Agent 还会读到它；它里面是否转述了被删的内容，saveslot 不知道，交给人决定。
- **删除后不再支撑任何数据的源数据**（`orphaned_sources`，单列）：这次删除之后仍保留、但由"支撑了数据"变成"什么都不支撑"的源数据 ID。一条源数据**支撑数据**，指它是当前状态里某个生效值或佐证的值来源，或是某个未决候选、提议值的值来源；只作为操作来源（撤销的证据、解决请求与 `note`）不算，只支撑已被盖掉的历史版本也不算。只列这次删除造成转变的：删除前就什么都不支撑的不列，被删的源数据本身不列。例：删掉用户的原话之后，同一次写入随附的 Agent 转述、后来那句纠错的话仍作为源数据保留，它们支撑的那一行已整行删除。调用方据此决定是否一并删除；saveslot 不自动删。
- **来源键**（见「按来源键写入」）：受影响的行有来源键时给提醒 `external_key_resync`："这些行来自外部系统；删除后若连接器再次同步同一条记录，它会重新出现。要彻底忘掉，先在来源系统里删除，或让连接器停止同步它。"物理删除之后 saveslot 不记得被删的键（见「删除之后」），所以这一条必须如实说。逐行结果里，行靠别的贡献仍在、而键的贡献被删的，标 `external_key_removed`，写明"这一行将失去来源键"（下一次同步会新增另一行）。行的来源全部被删、且带来源键的，同样给 `external_key_resync` 一类的说明，讲清之后的同步不会补回当时被跳过的记录；被跳过的 op 不进日志，不逐条列出。 **冻结怎么说**：一项删除可能让好几个键冻结，预览与回执逐个列出受影响、键将冻结的行（列行 ID，不列键值），写明冻结期间这些键不能转移、按它们的同步一律跳过；同一个键还被另一项未执行的删除冻结时，写明撤回这一项之后它仍冻结、要等哪一项删除（附删除 ID）撤回或执行。
- **如实写明不会删除的**：外部文件未由 saveslot 保管、需自行删除；schema 中的枚举值与说明；连接实例的名称（用户起的名字，不是由源数据得出的）；没有任何源数据的操作（提交 schema 草稿、确认删除、撤回删除、既没带证据也没带备注的解决）自报的任务标识与显式幂等键；删除后保留的元数据（见「删除之后」）。
- **预览何时过期**：预览之后、确认之前，有新的写入、解决或删除改到了预览列出的任何一行 / 实体、事项或源数据时，确认句柄作废（`preview_outdated`，附新预览）。只是别处有写入不作废。
- 本地服务写明"到期时 saveslot 服务若没在运行，物理删除在下次启动时执行"。
- **确认后的回执**给出按确认时的状态重算的预览内容（上面各项，列表的上限与总数同预览），另给：删除 ID（即宽限期内那条 `deletion` 事项的 ID，二者是同一个对象）、到期时刻与撤回方法；受影响行 / 实体的新 `ver`；以被改动的值为前提的依赖行的标记变化（`premise_affected`）；每处的状态与时间（逻辑删除 → 物理删除时间 → 备份失效日期，快照与冷归档按备份算），不宣称"已从所有备份删除"；本地删除只作用于 saveslot 当前的数据目录、系统级备份里的旧副本不由 saveslot 管理。
- **到期关闭时再提醒一次**：物理删除到期、`deletion` 事项关闭时，受影响的行有来源键的，关闭的说明里再带一次 `external_key_resync`。那之后的第一次同步就会把同一条记录写回来，而此时不会再有任何提示。
- **撤回**（`deletion` 事项的 `cancel`）的回执给出按定义再算一次的结果：受影响行 / 实体的新 `ver`、退回原状态的写入、恢复的事项与保持"已被取代"的事项（附是哪次写入改过它）、依赖行的标记变化（`premise_affected`）。宽限期内原事项已被解决、撤回后被重新判定的候选单列（`rejudged`）：逐个给出写入与结果——与当前值相同而不再是改动（`dropped`）、成为佐证（`corroborated`）、另开了事项（`reopened`，附新事项）。
  另单列**因保持生效而判定改变的写入**：被记为保持生效的写入连带改变了判定的其余写入，逐条给出写入、新的判定（生效 / 转为待确认 / 成为候选）与原因（是哪一次被保持生效的写入）。这一单列由回执现算，不进事件；事件里它们是被重述的贡献。

### 由源数据派生出的内容

**凡是由源数据派生出的内容都记来源、在级联范围内**。除基础数据与派生缓存外，还有：

| 内容 | 来源怎么记 | 删除时 |
|---|---|---|
| 请求键、显式幂等键与它的请求内容指纹、调用方自报的任务标识（各头事件的内容里；写入头每次请求一条） | 该操作的全部证据（含解决请求带的证据与备注）。操作没有任何源数据时没有来源，不在级联范围，预览如实列出。请求键与指纹是按原始请求体算的哈希，含原样带回的无操作字段的值，但不随那个值的旧来源删除（已知边界）。只含按来源键 op 的请求不记请求键；含普通 op 的请求，请求键里按来源键 op 的内容同属这条边界 | 任一段证据被删（删除证据或隐私删除）即删；请求键与幂等键宽限期内仍参与查重（见上） |
| 逻辑写入头里各 op 的原始传参（值、区间的原始写法）。无操作字段的值不记，只列字段 ID | 各按自己的来源：区间参数按 `valid` 的映射（不映射 = 全部证据），值按该字段的值来源 | 它自己的来源被删时清除 |
| 解决事项时带的备注（`note`） | 它自己：随解决请求存为一条源数据，解决事件以操作来源引用 | 这条源数据被隐私删除时清除；事项详情不再回显 |
| 基础写入里的字面命中记录 | 同该字段那一项贡献 | 贡献被去掉时一起清除 |
| 写入事件里引用其他行值的内容：`acknowledge` 确认记录里被覆盖的段、疑似重复比中的行 | 被引用的那几次贡献 | 被引用的值被清除时，清除对应内容 |
| 回退记录（`undo` 与 `take_previous` 回掉了哪几次操作在哪些目标上的改动；`undo` 写入时哪些条目已被盖住） | 没有：只有事件号与目标（字段 ID 或"存在"）和两个标注，不含区间，是元数据 | 不清除。回掉的范围由写回各项的区间给出，那些区间按下一行处理 |
| 疑似重复的判定（比中了哪些行） | 被比中的行在判据字段上当时生效的贡献 | 任一被去掉或被重述时清除 |
| 一项贡献解析后的区间（状态类表） | 这一项自己的来源，加上解析时用到的别的贡献 | 任一被去掉或被重述时清除；这一项仍是贡献的，由删除事件重述 |
| 状态类表上常量 `backfill` 的补值区间（切换事件里记下的） | 给出这段区间两端的贡献：按"给出挡点的贡献"的口径，该时刻是其区间端点的全部贡献，两侧都算，已被盖住的也算（补值本身出自 schema 常量，不随删除清除） | 任一被去掉时整块清除；只是被重述时不清除。整块清除时，那一段补值不再存在：删除确认时这一段切换补值从来源表里去掉，撤回删除时放回；不由删除重述、不追补 |
| 前提声明的业务时间（逻辑写入头的 `premise_valid` 块：显式给的 `valid_at` / `valid_during`，或取自依赖行的业务时间；`premise_decls` 里的副本） | 显式给的：该 op 的全部证据。取自依赖行的：给出那个时间值的贡献——出自本 op 写下的时间字段或区间时，与那一块的来源相同；出自更早的贡献时，指向给出它的那一项 | 任一被去掉或被重述时清除。**从列入位置列表的那次删除确认起**（不等到墓碑），这条声明的范围按整条时间线处理（宁可多报），并在那次删除的检测里按整条时间线重判一次；撤回那次删除时范围恢复，同样重判一次（见「写入的前提」的「检测」）。`premise_decls` 里的业务时间副本到墓碑才清空。声明本身（目标、字段、所见版本）是元数据，不清除（见「删除之后」） |
| 来源键索引（`external_keys`）里的条目 | 键字段那一项贡献（只在得到键的那次写入里有） | 删除确认后这个键占位或冻结、持有者不变；撤回时去掉这项删除，没有别的删除冻结它时转回；到期执行后按删除后的键字段值重定持有者，没有持有者时去掉条目（见「按来源键写入」） |
| 逻辑写入头里的临时名（`refs`） | 该 op 的全部证据 | 任一段证据被删即删 |
| 抽取作业的翻译结果（迁移结果事件） | 工作项附带的**全部原文**（模型看到的就是这些，同时需要）；工作项只附与 `reextract.from` 字段有关的证据（各写入里这些字段引用的证据段）；按工作项 × 字段存放 | 附带的任一原文被隐私删除，该工作项的翻译结果整体清除；剩余原文里还有内容的，列入待重抽的（行, 字段）——`apply` 设 `pending_extraction`，`jobs` 开补抽作业（工作项只带剩余原文）；没有剩余原文的直接置空 |
| 待处理事项的原因、影响、当前值与提议值、差异清单 | 引用的行版本与源数据；按条目存放 | 清除对应条目；事项因此失去目标、候选 / 提议值失去全部值来源、或冲突 / 高影响的成因被删（见「重放规则」）时标"已被取代"（原因码 `deleted`，不含内容），撤回时按上面的规则恢复 |
| 解决事件确认记录里所确认内容的哈希 | 同被确认的事项内容 | 被确认的内容清除时一起清除 |
| 删除 / 撤回事件里写下的结果与重述 | 结果里每个值的值来源，加上截出这一段的贡献（由常量补值给出的段，抄那一段补值记下的依赖）；重述同它指向的那一项贡献，加上它依赖的贡献 | 任一被去掉或被重述时清除，由后来的删除事件重新给出 |
| "删除已确认"事件里的影响摘要哈希 | 被删的内容 | 列在本事件自己的到期位置列表里：到期物理删除；宽限期内导出时同样换成占位 |
| 派生行的分组键值（"分组键值 → `partition_id`"映射） | 落进该分组的基础字段版本（任一行仍带这个键值，映射就还在） | 分组因删除变空时清除。宽限期内同一分组键又有了行：沿用原 `partition_id`，下一次派生写入在自己的内容里**重新登记**映射——到期只删旧内容，映射不丢；撤回时自然落回同一个 `partition_id` |
| 派生写入的结果校验和 | 读集里的基础版本 | 读集里有贡献被去掉时清除；之后按时刻还原该派生值时跳过核对、标 `partially_deleted` |
| 大写入作业的请求内容（作业接受事件） | 请求的证据 | 同基础写入 |
| 退役版本的物理表 | 同当前版本的行 | 各版本物理表里的行按同一结果处理 |
| 数据目录的概况与取值示例 | 由当前可见数据现算 | 删除时重算 |

### 删除之后

- **版本表**：被删内容所在版本的区间保留、该处内容标"已删除"；按时刻读到这段时，回执标注"该时刻的部分数据已删除"（`partially_deleted`）。
  删除级联里重算派生产生的新派生写入，不进删除范围的部分只有规则版本与 `partition_id`；分组键值与结果校验和是可删除的内容，不含描述被删内容的文字。
- **读过被删数据的已完成任务：不追溯、不通知。** 产出早已离开 saveslot，无法召回；读取记录本来只记版本，
  删除后自然显示"读的是已删除版本"，不需要额外标记。为隐私而删，不应再生成描述被删内容的新记录。
  删除确认与撤回也做"值恢复后撤掉标记"的检查（见「纠错影响查询」）：某次读取当时读到的值因删除重新成立，撤掉它的 `possibly_affected`；**只撤不增**。
- **"只撤不增"只对 `possibly_affected`；前提已变（`premise_changed`）会增。** 依赖行与已完成的任务不同：它还在 saveslot 里，别的 Agent 还会读到它、当成正常的行用；先例是 `ref` 的目标被删除时引用方带 `dangling_ref`。规则（判据与检测见「写入的前提」）：
  - **按删除前后的值比较，不看给出者**：删除让所声明范围上的值变了（整行消失、字段变空、回到更早的不同值、某一段上值不同），依赖行带标记，原因 `deleted`；删除只换了给出这个值的贡献、值没变，不标。打标记不需要读所见版本：删除前的值此时仍在存储里。
  - **比得了才撤**：删除让值回到所见的值时撤掉标记，条件是所见版本上的值还读得到；它本身已被删除（待删除或已物理删除）时比不了，标记保持。不拿被删的值做比较。
  - **删除之后，`since` 与 `reason` 改指删除**：已变的声明，若这次删除改了它范围上的值，或去掉了 `since` 所指那次改动在这个范围上的贡献，而值仍与所见的不同，`since` 改为这次删除的操作号、`reason` 改为 `deleted`。否则读方顺着标记查到的是一次在删除之后什么都没做过的操作。
  - **声明的范围被这次删除改成整条时间线时重判**：取自依赖行的业务时间被这次删除清除（列入位置列表）的声明，从这次删除确认起范围按整条时间线处理，并在这次检测里按整条时间线重判一次：仍是"没变"、而整条时间线上的值已与所见版本不同，或所见版本那一格的内容已被删除或待删除（比不了）的，都转为"已变"，`since` 是这次删除的操作号，原因 `deleted`。撤回这项删除时范围恢复，同样重判一次（可能转回"没变"）。
  - 撤回删除时按撤回后的状态再判一次。标记里只有目标行 ID、字段、所见版本号与删除的操作号，都是删除后本来就保留的元数据，没有值，不构成描述被删内容的新记录。
- **第一版删除 = 物理删除**（不做应用层加密，见下）：被删内容连同它的校验和、受影响的业务行与历史版本一起物理删除；事件头与墓碑留在链上，链仍可校验。
  墓碑事件只列被删内容的不透明位置与原因码，**不含任何描述被删内容的文字、也不含由它算出的值**；事件头只用不透明 ID，可读名称放在内容里。
- **删除后保留的元数据**（删除回执如实写明）：
  - 事件头（进链，永不删改）里看得出：某个时刻有过一条什么类型的事件、是哪个主体做的、属于哪个 slot、哪几条事件属于同一次操作。
  - 不进链的元数据块里看得出：是哪张表的哪一行（`row_id` 是 UUIDv7，自带毫秒级创建时间）、每次写入的意图、它引用了哪些事件；墓碑说明"哪些位置的内容在某时按删除请求移除"。位置里带字段 ID，所以看得出"第几号字段被改过"，看不出字段名与值。
  - 写入的前提：某次写入声明过以某张表的某一行、第几号字段、在哪个版本上的值为前提，某次写入清除过前提，某条声明在哪次操作里变了状态。看不出前提的值、依赖行的值与声明的业务时间。
  - 逐项清单与"如果要求不保留，怎么去掉"见 [`../09-event-format.md`](../09-event-format.md)「事件头里留下了什么」。连接实例的名称不随隐私删除清除。
- **删除要传到所有副本，且不能复活**：墓碑是一条日志事件，**永不过期**，全量复制到所有节点（不受部分复制范围限制）；副本先应用墓碑再接受内容，离线节点带着旧数据上线时，主节点在入口按墓碑拦截。
  **只能按事件身份拦截**：墓碑与删除登记不存任何由内容算出的值，同一内容换个事件重新写入无法按内容识别——这是"删除后不可比对"的代价。
  **来源键同理**：键值是字段值，可能就是用户内容（有的来源系统拿邮箱、手机号当标识），物理删除之后 saveslot 不记得这个键，也不留它的哈希。同一条外部记录再次同步进来时，会作为新的一行重新出现；预览、回执与到期关闭时各提醒一次（见「预览与回执要写明的内容」）。只删了某一次同步的源数据、行还在时，那次同步的贡献去掉、字段回到更早的值，下一次同步交来的若仍是被删掉的值，它与基线值不同，会再次生效——同一件事：来源系统里它还在。
- **明文残留清单**：删除时以下每一处都要处理。

  | 在哪 | 有什么 |
  |---|---|
  | 日志的内容区 | 写入请求里的证据片段、请求键与显式幂等键的请求内容指纹、翻译结果、事项内容、确认记录与删除确认里的内容哈希、删除 / 撤回事件里的结果、派生行的分组键值与结果校验和 |
  | 物化状态 | 各版本物理表（含退役表）、版本表里的历史值、数据目录的概况与取值示例、全文索引、embedding、来源键索引（`external_keys`）、前提声明（`premise_decls`）里的业务时间 |
  | 数据库内部 | WAL / 空闲页；PostgreSQL 统计信息（`pg_statistic` 的高频值与直方图：`purgeResidue` 对受影响的表做 `ANALYZE`）；`pg_stat_statements` 与慢查询日志（不记受限 SQL 的字面量） |
  | 运行期的临时数据 | 抽取作业的工作项（领取时由日志现拼、不落盘）、统计异常的基线（若缓存）、应用日志与错误上报、模型调用缓存、对拍（`log.reconcile`）的临时存储（用完即毁，崩溃留下的在打开租户时清掉） |
  | 按备份对待的副本（见下） | `snapshot()` 快照、格式升级前的快照、冷租户归档 |

  **schema 文档本身**（枚举值、`migrate` 里的常量、Agent 写的说明）可能含用户原文，**不在级联范围内**；删除预览如实说明"schema 中的枚举值 / 说明不会被删除"。
- **备份**：第一版不做应用层加密，备份（含快照与冷归档）里的数据只能等过了保留期才消失；删除回执如实给出状态
  （逻辑删除 → 物理删除 → 备份失效日期），不宣称"已从所有备份删除"。冷租户归档在租户恢复回集群后何时作废，待定（open-questions，云服务容量阶段再定）。
- **恢复备份不让删除复活**靠日志之外的删除登记，见下一节。

### 删除登记：恢复备份不让删除复活

日志里的墓碑保证"导出再重放"不让数据复活；恢复一份**删除之前**的备份时，那份日志里根本没有这次删除。所以在日志之外另设一份**删除登记**，放在与租户存储分开的锚点存储里（服务器模式：控制面库；本机模式：saveslot 配置目录；接口见 architecture §5、§8），与云服务的删除到期索引合为一份。

- 每项只存租户、删除 ID 与种类、状态、到期时刻、确认事件的 `seq`、被删源数据与被删内容块的不透明位置，**不存内容**。锚点存储同时记每个租户已分配的 `seq` 高水位、恢复次数、"恢复进行中"标记与"导入进行中"标记。
- 状态有四种：

  | 状态 | 含义 |
  |---|---|
  | `intent` | 登记写下了，但还不知道租户里的删除事务提交没有 |
  | `pending` | 已确认，待执行 |
  | `cancelled` | 已撤回 |
  | `executed` | 已物理删除 |

**总规则：登记永远不比已提交的日志"少删"。** 少删是隐私事故且不可见，多删在宽限期内可见、可撤回；所以让每一处崩溃都落在多删一侧，再用对账收回。由此定下三个动作的先后：

| 动作 | 先写 | 后写 | 中间崩溃后的状态 |
|---|---|---|---|
| 确认删除 | 登记（`intent`） | 租户事务（"删除已确认"事件）；提交成功后把登记改成 `pending` | 登记有、日志没有：登记多删一步 |
| 撤回 | 租户事务（"撤回"事件） | 登记改成 `cancelled` | 日志已撤回、登记仍 `pending`：登记多删一步 |
| 到期物理删除 | 租户事务（墓碑） | 登记改成 `executed` | 日志已执行、登记仍 `pending`：两者都是"要删"，无差别 |

**正常打开时以日志为准，校正登记。** 时机：每次打开租户、每次到期扫描之前、每次删除相关的操作之前。

| 登记 | 日志里这次删除 | 动作 |
|---|---|---|
| `intent` | 已确认、待执行 | 登记改 `pending` |
| `intent` | 没有 | 移除登记项（事务从未提交，这次删除不存在） |
| `intent` / `pending` | 已撤回 | 登记改 `cancelled` |
| `intent` / `pending` | 已有墓碑 | 登记改 `executed` |
| `pending` | 已确认、待执行 | 无事可做 |
| `cancelled` | 已撤回 | 无事可做 |
| `executed` | 已有墓碑 | 无事可做 |
| 没有登记项 | 已确认、待执行 | 补登记 `pending`（锚点存储丢过或是新建的） |
| 没有登记项 | 已撤回 | 补登记 `cancelled`。不补的话，以后恢复到撤回之前的备份时会按"没有登记项 × 待执行"补成 `pending`，用户撤回过的删除被执行 |
| 没有登记项 | 已有墓碑 | 补登记 `executed` |
| 没有登记项 | 没有 | 无事可做 |
| `pending` | 没有 | **不可能组合**：日志被回退过，转入恢复流程 |
| `cancelled` | 待执行、已有墓碑、没有 | 同上 |
| `executed` | 待执行、已撤回、没有 | 同上 |

上表是登记的五种情形（四种状态加"没有登记项"）× 日志的四种情形（没有、待执行、已撤回、已有墓碑）的全部组合。最后三行在正常运行中不会出现（登记只会比日志多一步）。出现了就说明租户存储被换成了旧的而没走恢复流程。打开租户时各项检查的先后：导入进行中标记 → 恢复进行中标记 → 日志末端是否低于高水位 → 本表的对账 → 补跑到期任务（导入的重入见 architecture §8）；高水位检查在前，所以"`intent` × 没有"不会在日志被回退时被误当成"事务从未提交"。

**恢复流程里以登记为准，补日志。** 恢复任何备份、`snapshot()` 快照、格式升级前的快照、冷租户归档之后，先按登记补删，再对外服务（流程的步骤与重入见 architecture §8）：

| 登记 | 恢复出的日志里 | 动作 |
|---|---|---|
| `executed` | 有"删除已确认"、没有墓碑 | 以 `system` 直接补墓碑（原因码 `restore_backfill`），不重算 |
| `executed` | 连"删除已确认"也没有 | 按定义重算，直接物理删除，不给宽限期 |
| `executed` | 有墓碑 | 无事可做 |
| `pending` | 有"删除已确认"、待执行 | 照原到期时刻执行；已过就立即执行 |
| `pending` | 没有 | 以 `system` 重新生成"删除已确认"（按定义重算），到期时刻沿用登记里的值，已过就立即执行 |
| `pending` | 已撤回 | 登记改 `cancelled`（登记落后一步，日志为准） |
| `pending` | 已有墓碑 | 登记改 `executed`（同上） |
| `intent` | 有"删除已确认"、待执行 | 登记改 `pending`，到期时刻照登记里的值 |
| `intent` | 没有 | **先把新的到期时刻（现在起 24 小时）写进登记**，再以 `system` 重新生成"删除已确认"，事项原因码 `restored_unconfirmed` |
| `intent` | 已撤回、已有墓碑 | 登记落后，以日志为准：改 `cancelled` / `executed` |
| `cancelled` | 有"删除已确认"、待执行 | 以 `system` 追加"撤回"事件（按定义重算），原因码 `restore_cancel`：用户撤回过的内容保留 |
| `cancelled` | 已撤回 | 无事可做 |
| `cancelled` | 没有 | 忽略 |
| `cancelled` | 已有墓碑 | 不会出现：墓碑只在登记是 `pending` 时追加。出现时报错停下，不对外服务 |
| 没有登记项 | 任意 | 按正常打开的表处理 |

- **到期时刻以登记里记下的为准**。重新生成"删除已确认"时先改登记、再提交事件，所以这一步之后崩溃再进来，看到的是"`intent` × 待执行"，到期时刻仍是新写的那个，不会回到旧值。
- **重入时重新生成的事件与首次相同**。"删除已确认"里的结果与重述是"日志 + 被删源数据集合"的函数，不依赖任何日志之外的状态；恢复流程重入、对同一项登记再算一次，得到的结果、重述与位置列表与第一次相同。已经追加过的不会再追加（按对照表，重入时看到的是"已确认、待执行"）。
- **被删的源数据本身不在恢复出的日志里**（备份早于那句话被记下）：没有可删的东西，不生成事件，只把登记项标 `executed`。

- 补删后核对登记里的位置都已清除。
- **写明的残余情形**：
  - `intent` 而日志里没有、又进了恢复流程时，saveslot 分不清"事务没提交"和"提交了但日志被回退"。按后者处理（重新生成），并用新的宽限期和可见的事项兜住：可能让一次用户收到报错的删除出现，但看得见、能撤回；反过来处理会让一次用户已收到成功回执的删除复活。
  - 撤回的租户事务已提交、登记还没改成 `cancelled` 时崩溃，并且随后恢复到了撤回之前的备份：登记是 `pending`，日志里删除待执行，照常执行，用户的撤回丢失。这与"备份之后的任何写入都随恢复丢失"是同一类损失，方向是多删。

**恢复时的其他规则**

- 补删一项"删除证据"（后续）时，若在恢复出的状态里被引用挡住（佐证随恢复丢了），**照删、不挡**，回执与审计写明"其他来源已随恢复丢失"——不删就是让用户删掉的原文复活。
- **恢复后 `seq` 不复用**：补删前先追加一条"恢复"事件（引用恢复到的位置与 `seq` 高水位），之后的 `seq` 从"日志末端与高水位中较大的那个"之后接着编；`verify` 认可有"恢复"事件说明的空档。
- **恢复次数**：高水位是定期推进的（推进的时机见 architecture §8），两次推进之间分配过的 `seq` 仍可能被重新用掉，所以另记恢复次数（恢复时加 1，写进"恢复"事件；导入时同样加 1，写进导入事件；初值为 0）。当前恢复次数取最近一条恢复或导入事件里的值。`ver`、事项版本与 `dc_` / 翻页句柄都带上它（事项 ID `pi_` 是稳定 ID，内容绑定靠事项版本，见「待处理事项」），恢复或导入之前拿到的一律对不上：
  - 事项版本报 `confirmation_mismatch`；
  - `ver`：恢复次数**恰好比当前小 1**、且操作号不超过**恢复点**的，按它自己的操作号判冲突；其余的（操作号在恢复点之后，或恢复次数更旧）以恢复点为它读到的位置，按冲突判据比较恢复点之后的写入。恢复点是使当前恢复次数生效的那条事件给出的位置：恢复是"恢复"事件的 `restored_to`，导入是导入事件的 `imported_upto`。理由：恢复点及以前的事件在两条时间线里逐字节相同，按原操作号判不会错，还能查出它之后、恢复点之前的并发改动（一律挪到恢复点，会把这些改动当成已经看过而静默合并）；恢复点之后的那段可能已经丢失，同一个操作号可能指向另一次写入，只能保守处理。恢复次数差 2 及以上时，中间那次恢复之前的时间线是否与现在一致无从判断，所以不放宽。写入的前提里带的 `ver` 同样按这条换算；
  - 句柄按过期处理。
- **导入到空租户**（导入本身见 architecture §8「格式版本、导出、导入与恢复」；目标须是空租户：日志里只有创世事件，锚点里没有删除登记、恢复记录与进行中标记）：
  - **登记由导入的日志重建**：源头的锚点存储不随租户导出，导入不校验它。换入之后一次写入删除登记（由日志里仍待执行的删除得出）、高水位（日志末端）与恢复次数（导入事件里的值），并清掉"导入进行中"标记。
  - **导出里待删除内容的占位**（导出的默认做法）：内容不在文件里，导入对每一项这样的删除**立即补一条墓碑**（`system`，`trigger: "import"`，原因码 `import_placeholder`），排在导入事件之后。这些删除在目标处不可撤回——内容本来就没带过来；对应的 `deletion` 事项按到期关闭。这是到期物理删除之外第二种产生墓碑的途径。显式包含待删除内容的导出，删除在目标处仍待执行：到期时刻照事件里记下的，已过期的在换入后、对外服务前补跑，未过期的仍可撤回。
  - **源头的删除登记带不过来**：导出之后在源头又确认的删除，这份导出文件不知道，导入后那些内容仍在。这不是导入造成的——导出文件本来就是一份 saveslot 删不到的副本——但导入会让它重新变成线上数据，所以导入前显示导出时刻，并提示"这份导出之后在原处做的删除不在其中"。
  - 导入之后，导入前的 `ver`、事项版本与句柄按上面"恢复次数"一条处理；`dc_`、`cur_` 另因签名密钥与租户 ID 不同而失效。
- **本地的边界**：本地删除只作用于 saveslot 当前的数据目录；系统级备份（Time Machine 等）里的旧副本不由 saveslot 管理，从这类备份恢复等于恢复到当时的数据。
  只恢复了数据目录、saveslot 配置目录里的登记还在时能补删；两者被一起恢复时，登记也回到当时，saveslot 补不了、也发现不了。

### 加密、法务与重建

- **应用层加密不是第一版必选项**：结构上预留——内容本来就与事件头分开存（见「完整性与溯源」）、内容引用带可空的 `key_id`、
  校验和可改为对密文求。将来做加密时：只加密源数据原文与 change_log 前后整行，**业务表、派生表、版本表保持明文**
  （SQL 查询要用），密钥层级 根密钥 → slot 密钥 → 每条数据的密钥，删除 = 物理删除 + 销毁密钥（兜底备份与离线副本）。
- **托管服务的静态加密不改变删除的做法**：托管服务的存储卷、备份与冷归档在基础设施层加密，密钥由云平台保管；它防的是存储介质被带离之后被读，不防运营方。隐私删除仍是物理删除内容加残留清理，不靠销毁密钥；备份里的旧数据仍要等保留期过了才消失。
- 法律口径（物理删除是否满足被遗忘权、备份保留期如何告知）需法务确认。
- 重建靠重放日志里记下的抽取结果，只有引用了被删源数据的部分才需要重新抽取（见"模型放在哪"）。

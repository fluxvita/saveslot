## 派生规则与派生缓存

**基础表由 Agent / 调用方写；派生表完全由规则生成，Agent 不能直接写。** 派生规则是 schema 的一部分，
定义 schema 时由 Agent 起草基础表 schema + 派生规则。

**规则分三级：结果确定的才能当缓存，结果不确定的必须存下来。**

| 级别 | 用来写什么 | 例子 | 结果 |
|---|---|---|---|
| L1 受限 SQL（首版） | 绝大多数聚合、关联、时间窗口 | 本周跑量、近 7 天平均、本月剩余预算 | 派生缓存，可重算 |
| L2 沙箱纯函数 | SQL 写起来太绕的确定性算法 | 训练负荷的指数移动平均、复杂计费规则 | 派生缓存，可重算 |
| L3 模型派生 | 语义判断 | "本周训练状态：过量" | **不是派生规则**：由调用模型的后台执行方（worker）对基础表做一次写入，来源 = 所读上游版本 + 模型输出（存为源数据），按"Agent 推断"级别对待 |

- **L1 受限 SQL**：只允许对 saveslot 内有模型数据的 SELECT 视图；函数白名单，只放确定性函数，`NOW()` 一类禁用，
  改为显式传入"按哪个时刻算"。收哪些语句、函数、聚合与运算符，见 [「受限 SQL」](11-restricted-sql.md)。**SQL 里引用这个时刻的写法**：两个无参函数 `saveslot_now()`（入口取的时刻；`sql` 操作带了 `at` 时是 `at`）与 `saveslot_today()`（它在 slot 时区下的日期）。它们不读时钟，由 saveslot 改写成这次调用的显式参数，同一次调用里只有一个值；规则里出现任一个，即归入依赖"今天"一类（下表）。读状态类表的某一刻写 `FROM <表> FOR VALID_TIME AS OF saveslot_today()`。依赖哪些表、列由解析 SQL 得出。
- **L2 沙箱纯函数**：如编译为 WASM，不联网、不读时间、不用随机数，同输入同输出；登记在 schema 里，由 SQL 调用。
- 需要外部数据的计算（如汇率换算）不算派生：外部数据先经来源连接器作为基础数据接入，再在规则里使用。
- **规则读的是逻辑表，逻辑表只含未撤销的行。** 但引用方没被撤销、它 `ref` 指向的目标被撤销时，引用方仍在逻辑表里，`ref` 的值也仍是原 ID（引用不级联，见「写入请求 · 引用字段」）。所以**按 `ref` 字段计数或求和**（如按明细的 `meal` 数一天吃了几餐）**会算进指向已撤销目标的行**。要排除它们，规则须关联目标表，只取关联得上的行：目标表的逻辑表里已经没有被撤销的那一行。saveslot 不为此另给提醒。

**派生缓存也是一张实际存在的表，要随基础数据更新：**

- 基础写入与受影响派生缓存的刷新**在同一事务里同步完成**，读到的派生值不会落后于基础数据。
- 刷新方式：首版**重算受影响的分区或整张视图**——数据按用户隔离、量小，全量重算也很快；
  真慢了再换增量维护。
- 刷新后**结果有变化的派生行**各在日志里记一条派生写入（结果没变的不记；**删除例外**：删除确认与撤回删除为受影响行在删除前后所落的每个分区各追加一条派生写入，结果没变也追加——墓碑之后从头重放时，中间状态里这个分区的值可能与线上不同，这一条是把它拉回来的唯一一处）：规则版本、`partition_id`、读到的日志位置（不含用户内容，不随删除清除）；分组键值与结果校验和（由用户内容算出，可删除）。来源由规则引擎自动记录。字段级定义见 [`../09-event-format.md`](../09-event-format.md)。
- 派生字段的类型、单位、精度由编译器从规则推断并回填（见「字段类型、同值与单位」）。

**备案方案**（第一版都不用，规则表达能力或性能不够时再评估）：增量维护视图 pg_ivm、Materialize、RisingWave、
Feldera；带依赖图的 SQL 建模 dbt；表格公式引擎 HyperFormula；L2 的 WASM 沙箱。

### 刷新范围与写入准入

**第一版按受影响的分组重算，不用任何 IVM 引擎，包括 pg_ivm。** PGlite 上 100 万行实测：整用户重算约 290 ms，只重算受影响的一周约 1.7 ms，
都能放进同一事务；更大规模的数字见 architecture「容量边界与实测数值」。pg_ivm 是备案：将来个别热点规则重算太慢时，可作为那几条规则的加速器（它不支持窗口函数等，用了它 saveslot 仍要自己记派生写入）。

**第一版对规则形状的要求：最外层必须是分组聚合，或不分组的整体聚合（结果只有一行）。** 这样一个分区恰好一行：派生行的身份就是 `partition_id`，`ver`、结果校验和都按"一个派生行"定义。最外层产生多行而没有分组键的规则（如裸的窗口函数、不聚合的关联）编译时报 `not_in_this_version`；窗口函数、关联可以出现在分组聚合的内层。

规则编译时，分析器给每条 L1 规则算出**重算范围**（一次基础改动要重算哪些分区），派生表主键 = 分组键：

| 规则形态 | 重算范围 | 受影响的键怎么得出 | 第一版 |
|---|---|---|---|
| 分组聚合（分组键是基础列的确定性函数，含按业务时间分桶） | 分组 | 被改行的改前值与改后值分别求分组键 | 做 |
| 不分组的整体聚合 | 唯一的那个分区 | — | 做 |
| 窗口函数，有界帧 | 该分区内受影响的帧 | 分组键 + 帧偏移 | 不识别：窗口函数只能出现在分组聚合的内层，这样的规则按"分析不出"处理 |
| 窗口函数，无界帧 / 累计值 | 整个分区（通常整用户） | 分区键 | 同上 |
| 关联维度表 | 按关联键反查事实表的分组 | 受影响的维度键 → 引用它的分组键 | 不识别：按"分析不出"处理 |
| 分析不出 | 该规则的全部分区 | — | 做 |

按上面"最外层必须是分组聚合或整体聚合"的形状要求，第一版实际出现的只有"分组聚合""整体聚合""分析不出"三行：内层有窗口函数、关联了维度表的规则每次基础改动重算它的全部分区。窗口函数、关联维度表两行是将来放开规则形状、或细化分析时的重算范围。

- 刷新 = 对每个受影响的键：删除派生行 + 按原规则加键谓词重插；结果没变就不往下游传；按派生依赖的拓扑序逐层执行。
- **派生行身份不带分组键值**：每个分组首次出现时分配不透明的 `partition_id`，"分组键值 → `partition_id`"的映射记在那次派生写入的内容里；计数表、`derived_reads`、read_log 都按 `partition_id` 记。
  规则的分组键来自自由文本字段（`text`，不含 `enum`）时，编译回执（`warnings` 的 `group_key_free_text`）与删除预览提醒"分组键是用户原文，删除时随分组一起清除"。
  分组变空（其中的行全被撤销、被改到别的分组，或被删除）之后同一分组键又有了行时，**沿用原 `partition_id`**，读过这个分组的读取记录照样接得上。因撤销或改写变空时映射没有被清除，不用重新登记；因删除变空时映射随删除清除，宽限期内又有了行时在新的派生写入里重新登记（见「行身份」「删除 · 由源数据派生出的内容」）。
- **写入准入阈值**：执行前估算"受影响分区的行数之和"（分区行数用同事务维护的计数表），受影响分区数、估算扫描行数、
  依赖深度、**预估耗时**任一超限就拒绝，返回"影响约 N 行，请拆成每批 ≤ K 行"；执行中用超时兜底。
  写接口的超时与重试语义等派生刷新延迟实验（references-arch 实验 4）的结果再定。
  - **写入的前提计入估算**：被写的各行上有效的前提声明数之和计入估算的行数（`estimated_rows`），因为写入要为每条相交的声明更新状态（见「写入的前提」）。每行的有效声明数在声明时有上限，单个 op 在这一项上的贡献有界；准入阈值定数值时不低于这个上限，单个 op 就不会只因前提而超阈值。
  - **准入适用于 `write` 与 `resolve` 触发的写入**（含 `undo`、回到合并基这些回退写入），**不适用于删除**：删除确认、撤回删除与到期物理删除都不做准入估算，也不报 `too_large`。删除的范围由被删的源数据决定，不能分批；拒绝它就等于挡住被遗忘权。删除引起的派生重算与前提检测照做，代价并入删除本身。
- **大写入作业**（**第一版不做**：超过准入阈值一律拒绝，由调用方分批）：拆不开的大写入（批量导入一年的数据、改动维度表的一行；多节点时（后续）还有离线同步上来的超限写入）转成作业——
  接受、返回作业句柄、后台处理、完成后原子生效。期间受影响的派生值保持旧值并带 `stale`（待刷新）标记，随读取带出。
  **这是对"派生值永不落后"的有限放宽**：只在作业期间、只对受影响的派生值，且一定被标出。
  批量导入时，一个导入文件就是一条源数据，多行写入共享这个来源，派生在作业结束时统一刷新。
  **作业的状态都在日志里**："作业接受"事件（含全部请求内容，作内容处理，`apply` 据此给受影响的派生值设 `stale`）、作业产生的基础写入、"作业完成"（清 `stale`）/ "作业失败"事件；
  后台进度只是 (c) 类游标，崩溃后由"已接受、未完成"的作业重新推出待办，已返回的作业句柄仍有效。
- **确定性边界**：固定会话时区与排序规则，函数白名单只放结果确定（IMMUTABLE）的函数（见「受限 SQL」），数值统一 `numeric`；
  对账"全量重算 vs 缓存"并入日志对拍（第一版由用户会话手动触发，没有后台定期抽样）。

### 派生的来源追踪：三层

| 层 | 存什么 | 何时写 | 用途 |
|---|---|---|---|
| 静态列级依赖 | 规则版本 → 引用的（表，列） | 规则编译时 | 判断写入是否触发某规则、schema 变更影响预览、将来派生表的权限继承 |
| 分区级读集 | 派生写入 → （规则版本、基础表、`partition_id`、日志位置；分组键值不存这里） | 每次派生刷新，每个受影响分区一行 | 即"上游写入"这种来源的具体形式（`derived_reads` 表） |
| 行级来源 | 不预先存 | 需要时在版本表上按日志位置重跑规则得出 | 审计展示"W45 的 22 由哪几条跑步构成" |

- **第一版的读集只记到（基础表，派生分区）**。带 `WHERE` 的规则不另记谓词的形状；重算范围分析不出的规则，每次基础改动重算它的全部分区，读集照常按分区记。影响查询因此宁可多报。要记"不含用户值的谓词形状"时，以读集条目里新增可选项的方式加入，已有的派生写入不用动。
- 预先存行级来源实测会让写入慢 4–7 倍；分区级已够删除级联（受影响分区重算后，"只来自被删数据就消失、有其他来源就不再依赖"自然成立）
  和纠错影响查询（精确到分区，带 WHERE 的规则可再代入旧值复核）。
- 依赖用 libpg_query 解析，取所有被引用的列（含 WHERE、JOIN 里的列）；看不懂的写法直接拒绝。

### 时间依赖

规则在 schema 里声明时间依赖：

| 类别 | 例子 | 能否缓存 | 刷新范围 |
|---|---|---|---|
| 无关时间 | 项目任务数 | 能 | 按普通依赖 |
| 按业务时间分桶 | 每周跑量、每月支出 | 能，派生行带桶键 | 受影响桶 = 改前行与改后行的业务时间所落桶的并集 |
| 依赖"今天" | 本月剩余预算、近 7 天平均 | 不能按"今天"缓存 | 改写为显式时刻参数：读时计算，或改成按桶缓存、读时选当前桶 |
| 读状态类表而不带业务时间限定 | "各类别当前预算之和" | 不能：当前段会随时间流逝而变，没有任何写入触发刷新 | 编译时归入依赖"今天"一类：读时计算 |

- **第一版对依赖"今天"的规则只做读时计算，不做缓存。** 这类派生行没有派生写入事件、没有版本：读结果不带 `ver`，带标注 `computed_at_read`（读时算出，值随读取时刻而定）。
- 规则读状态类表时想要缓存，就写明业务时间限定（按桶取某个时刻的值）。
- **没有输入的桶没有派生行**：分组聚合对没有输入的分组不产生行，"某一周没有行"就是"那一周一条记录都没有"。一个桶里的记录是完整的还是只有一部分，saveslot 不判断（"应该每天有记录"是领域知识）；要让调用方分得清，在规则里带覆盖列，如有记录的天数 `count(DISTINCT <日期字段>)`、首末日期 `min` / `max`，由读的一方按字段说明判断。随 CLI 打包的模板里按时间分桶的派生表带这几列（[`../06-cli.md`](../06-cli.md) 3.1）。

### 数据目录

**saveslot 提供可查询的数据目录（类似 `information_schema`），Agent 由此得知有哪些基础表和派生表。**

- **定义时编译**：Agent 提交基础表 schema + 派生规则（SQL + 每个派生字段一句必填说明）。saveslot 解析 SQL、
  检查白名单、在现有数据上试跑、推断派生表的列与类型、算出依赖关系，把派生表的完整定义返回给 Agent；
  报错也在此返回（如"第 3 行用了不允许的函数 `NOW()`"）。
- **使用时分层发现**：MCP 与 API 提供三档："列出"（`list`：slot 与表的清单，表名 + 一句话说明 + 表的别名，派生表标"派生 · 只读"）、
  "查看某张表"（`table`：列、类型、说明、表与字段的别名、`decimal` / `quantity` 字段的精度、规则原文、依赖、概况；精度要给出来，Agent 写之前就该知道值会被舍入）、"完整 schema"（`schema`：某个 slot 的完整 schema 文档原样，附 slot 策略；`base_version` 已填好，改完可直接交给 `schema_draft`，见「schema 文档格式」）。先列出再按需展开，不把整份目录塞进上下文。别名与说明一样是 schema 作者写的不可信文本，只用来帮 Agent 把用户的说法对到名字上，不参与名字解析（见「schema 文档格式」）。
- **规模提示**："查看某张表"的概况里，表的行数超过舒适线时带 `profile.scale`：超过舒适线、不超过实测线是 `large`，超过实测线是 `beyond_tested`，并给出两条界线的数值。界线按表算、按后端各有一组，随内核版本发布（见 architecture「容量边界与实测数值」）。它是读时按当前行数算出的，不进事件，不是数据标记；"列出"一档不带。派生表按自己的行数判断。只陈述事实，不拒绝写入。
- **读写一致、写入有指引**：基础表与派生表用同一套查询方式读；写派生表收到明确错误，
  如"weekly_mileage 是派生表，只读；请写入基础表 runs"。
- 社区 SKILL 可补充说明派生表的用途，权威信息以 saveslot 的目录为准。
- **读过派生值的一方怎么知道它是否已不成立**：第一版的纠错影响查询与前提都不覆盖派生行，`history` 的 `changes` 也不以派生表为目标。做法是对这条规则所汇总的基础表查 `changes`，`since` 取那次读取结果里的操作号（不用 `my_last_read`：只读过派生值的一方对基础表没有读取记录，会得到 `read_first`）；有变化再重读派生值。或者直接重读。规则依赖哪些基础表，见"查看某张表"给出的依赖。
- **可见范围**：目录只列出本次调用可见的表；派生表可见，当且仅当它依赖的全部表与字段都可见（见「读取 · 可见范围」）。

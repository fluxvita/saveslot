# saveslot · 数据层机制 · 01 数据分层与对象

> 数据层机制的一部分，目录见 [`README.md`](README.md)。文中「…」引用的节可能在同目录的其他文件里，按目录查。

## 数据分层

```
上层业务  ── 只看有模型的数据
有模型的数据  ← 动态 schema，可从源数据重新计算
源数据日志    ← 只追加，按 slot 组织
```

- **源数据日志**：对话片段、工具结果、外部来源导入、用户纠错等，只追加不修改。
  每条源数据属于且只属于一个 **slot**（见下）。
- **有模型的数据**：按 schema 从源数据抽取、清洗而来，是日志之上的物化结果。
- 关键推论：
  - 有模型的数据必须**能从源数据重算**——schema 变了，旧数据跟着迁移。
  - 每条有模型的数据**可追溯到它来自哪些源数据**（来源权威落在这里）。
  - **用户纠错是一条新的源数据**，不是直接改上层；否则重算会覆盖纠错。
  - 上层只看有模型的数据，但可按权限追溯到源数据（至少能引用原文）。

| 参照 | 在 saveslot 里对应 |
|---|---|
| MySQL redo log | 源数据日志：重放即可重建有模型的数据 |
| undo log / 多版本 | 按时刻读（"那次任务当时读到的是哪个版本"）、回退 |
| Agent 会话日志 | 一类源数据：对话与工具结果按会话只追加 |
| Super-agent thread | 事物的时间线：任何一行都能查出它怎么变成现在这样 |
| 链式召回 | 从当前状态沿时间线回溯到原始证据，跨月可找回 |
| git | 当前状态 = 检出结果；每一步有作者和来源（类似 blame）；历史即证据 |

## slot 与事物的时间线

slot 与事物的时间线是两个层次：

| 概念 | 粒度 | 例子 | 承担什么 |
|---|---|---|---|
| **slot** | 粗：一组相关的表 + 它们的源数据 | 健康、记账、独立游戏 Lumen | schema 版本的单位（一个 slot 一个"当前版本指针"）、时区与 slot 策略的单位、一次隐私删除的范围、凭证授权范围的最小单位（连接实例可限定到若干个 slot；表级、字段级的数据权限是后续）；归属节点、复制订阅（多节点，后续）、按 slot 导出与整体删除第一版不做（见 positioning「后续规划」；第一版导出的是整个租户）；将来做加密时也是密钥的单位 |
| **事物的时间线** | 细：一个被跟踪的具体事物（第一版粒度 = 一行或一个实体；跨表的事物由 Agent 多次查询拼） | 本月推广预算、11-03 那次跑步 | 回溯它怎么变成现在这样；存储上就是业务表的一行或状态表的一个实体，**不单独存成对象**——由行 ID、日志与来源表查出 |

- **每条源数据属于且只属于一个 slot。** 一句话涉及两个 slot（"今天跑了 5 公里，买跑鞋花了 600"），
  由 Agent 拆成两次写入、各附各的证据片段。
- **第一版禁止跨 slot 的派生规则与 `ref`**（版本归属、迁移影响、部分复制都说不清）；需要时由 Agent 分别查询两个 slot 再拼，或用一条只读的 `sql` 关联可见范围内两个 slot 的表（见 [「受限 SQL」](11-restricted-sql.md)）。

## 标识与对象

### 层级

- **主体**：用户（第一版 = 租户）→ 节点（设备凭证，由用户登记）→ 连接实例（Agent 凭证，ID 全局唯一，注册、改名与吊销都是日志事件；scope 与 slot 范围在签发时定下，第一版不能改，要改就吊销后重签）。**第一版单节点**：连接实例由用户会话登记（architecture §5）；多节点时（后续）改由某个节点签发、ID 带节点前缀、随同步传播。
- **保留主体 `system`**：内核自己产生的事件以它落账，由创世事件与用户主体一起登记（architecture K2）。
- **资源**：用户 → slot → 表 → 字段。
- **每个用户一条日志、一套序号、一把串行锁、一份独立存储**：本地一个 PGlite 数据目录，托管与多用户自托管是同集群里每用户一个 database；
  saveslot 内核只依赖"打开某个用户的存储"，表名不带用户前缀（见 positioning「技术选型」）；
  slot 是日志内的分区标签，不是独立的日志。
- **第一版不支持多人共享 slot**（家庭记账、团队项目）。将来的扩展方向：共享 slot = 一个独立租户 + 成员授权；
  因此接口里 slot 不写死在用户名下；内部引用一律用 `slot_id`，接口上可用 slot 名（用户内唯一，不分 ASCII 大小写）。

### 编号：一条日志，一套序号

**每个租户一条日志**（第一版租户 = 用户；本地单用户就是一个租户）。源数据、每一次写入、派生刷新、schema 的每次变化、待处理事项与删除的每一步、slot 策略变更、主体的登记，都是这条日志里的事件；有哪些事件类型以 [`../02-architecture.md`](../02-architecture.md) §3 的事件表为准。读取记录**不进这条日志**（有自己的保留期限，按期清理不能动链）。

**租户创世**：日志的第一条事件，`prev_hash` 为约定常量；内容是租户 ID、存储格式版本、事件格式版本与用户主体、保留主体 `system` 的登记。
之后的主体（连接实例）由用户会话登记，所以"每个事件的 actor 都在本租户登记过"（architecture K2）从第一条起就成立。

**日志是唯一事实来源**：存储里的其他状态要么由日志经 `apply` 确定性算出（业务表、版本表、派生表、事项当前状态……），
要么是明确列出、写清丢了会怎样的本地运行状态。分类清单（含本地运行状态的完整列表）以 [`../02-architecture.md`](../02-architecture.md) §3「日志是唯一事实来源」为准。

| 编号 | 是什么 | 谁分配 | 说明 |
|---|---|---|---|
| `seq` | 事件在日志里的位置 | 主节点 | 每租户单调、**尽量不复用**（恢复备份后从高水位之后接着编，空档由一条"恢复"事件说明；仍可能被重新用掉的情形与恢复次数见「删除登记」）；**同时就是** change_id、log_pos、事件头链上的位置——不另起一套；对外的记录时间用操作号（见下） |
| 写入号 / 操作号 | 一次操作对外的唯一序号 | saveslot | 见下方「写入号与操作号」 |
| 事件身份 | 事件跨节点的永久身份 | — | 第一版事件头不含 `event_id`：创世事件与恢复事件各带一个 `node_id`，事件身份 = （最近一条创世或恢复事件的 `node_id`，`seq`）。多节点时（后续）离线写入的事件另有 `event_id`，见「同步协议」 |
| `slot_id` / `table_id` / `field_id` | slot、表、字段 | saveslot | 稳定，不随改名变化 |
| `schema_version` | slot 的 schema 版本 | saveslot | 每个 slot 一个递增整数；物理表名里的版本号就是它 |
| `row_id` | 业务行身份 | saveslot（插入时生成，UUIDv7） | 插入成功后返回给写入方；迁移后保持不变 |
| `entity_id` | 状态类表里被跟踪的实体 | saveslot（首次写入时生成） | Agent 对状态类表按实体读写，区间段是内部实现 |
| 版本标记 `ver` | 某行 / 实体当前版本的令牌 | saveslot | 读取时返回，写入时原样带回。见下方「版本标记」 |
| 连接实例 ID | 哪个 Agent 在哪台设备 | saveslot（接入时签发） | 见「连接实例身份」 |
| `node_id`、`primary_epoch` | 节点、主节点任期 | 节点 / 主节点 | 见「同步协议」 |

#### 写入号与操作号

一次写入请求、一次由 `resolve` 触发的写入、一次删除确认、一次撤回，在日志里各占若干个连续的 `seq`。**每次操作有一条头事件，它的 `seq` 就是这次操作的操作号**；写入的头事件是逻辑写入头，它的操作号也叫**写入号**（见「写入请求 · 一次写入的事件构成」）。

- **对外一律用操作号**：回执的 `seq`、`ver` 里的序号、`timeline` 的 #n、`undo` 的 n、`revert.to`、`changes` 的 `since` / `until`、`as_of`、版本表的记录时间区间。
- 一次操作内其他事件（源数据、各行的基础写入、事项、派生写入）的 `seq` 不对外。
- 这样一次操作在记录时间上是同一刻：按 `as_of` 读不会读到写了一半的状态（见「时间 · 查询」）。

#### 版本标记 `ver`

- **编码**：（最近一次改动这一行 / 实体当前状态的操作号，租户恢复次数），写成 `v57.0`。准确地说，这个操作号是版本表里**意图不是 `schema_switch` 的最新版本**的操作号：schema 切换时常量 `backfill` 的补值在版本表里是一个版本，但不改 `ver`。行 / 实体由调用方单独给出，令牌里不重复。恢复次数初值为 0，每恢复一次备份加 1（见「删除登记」）。
- 令牌里的操作号不是这一行 / 实体的操作时报 `invalid_argument`。
- `history` 的 `as_of` 返回的历史版本写成 `h41.0`，不可用于写入。它取的是同一个号（那一刻版本表里意图不是 `schema_switch` 的最新版本），所以切换前后两个时刻读到的值可以不同而 `h…` 相同。
- 多节点时（后续）编码的是事件身份。

| 什么会改变 `ver` | 什么不会 |
|---|---|
| 新增、变更、纠错、撤销、回退里**已生效**的部分 | 成为候选、进待确认的写入（没有改生效值） |
| 由 `resolve` 触发的写入（确认、采纳候选、回到冲突前） | 同值佐证（只追加来源）、无操作 |
| 系统裁定（后续） | 派生刷新、schema 迁移（含切换时常量 `backfill` 补出的值：版本表里多一个意图为 `schema_switch` 的版本，行的 `ver` 不变） |
| 删除确认、撤回删除改动了这一行 / 实体：编码这次删除确认或撤回的操作号 | 离线事件被主节点接受后的重新编号（多节点，后续） |

#### 标识的写法

标识都是 saveslot 分配的不透明字符串，不含可读名称，删掉的不复用。随机部分用 Crockford Base32 写。

**文档里的例子怎么写标识**：写成"前缀 + 开头几个字符 + `…`"（`r_01JC8Z…`、`pi_7C2E…`、`sl_4KTZ…`），字符取自 Crockford Base32（数字与大写字母，没有 I、L、O、U）；真实的标识是下表的完整长度。只为在一段说明里区分几条源数据或几个事项时，用简写标签（`s_1`、`s_R1`、`s_lunch_1`、`pi_2`），它们不是真实标识的写法。事项版本、删除确认句柄、翻页游标是不透明令牌（见下方第二张表），例子里同样以 `…` 结尾，不受字符集限制。

| 标识 | 前缀 | 唯一范围 | 怎么生成 |
|---|---|---|---|
| 租户 | `tn_` | 全局 | 128 位随机数，26 个字符 |
| 用户主体 | `u_` | 全局 | 同上 |
| 连接实例 | `ci_` | 全局 | 同上 |
| 节点 | `n_` | 全局 | 同上 |
| 保留主体 | `system` | — | 固定值 |
| slot | `sl_` | 租户内 | 80 位随机数，16 个字符 |
| 源数据 | `s_` | 租户内 | 同上 |
| 待处理事项（删除 ID 与它是同一个） | `pi_` | 租户内 | 同上 |
| schema 草稿、迁移 | `d_`、`m_` | 租户内 | 同上 |
| 派生行的 `partition_id` | `p_` | 租户内 | 同上 |
| 一次恢复、一次读取 | `rs_`、`rd_` | 租户内 | 同上 |
| 行、实体 | `r_`、`e_` | 租户内 | UUIDv7 的 128 位写成 26 个字符；按时间有序，自带毫秒级创建时间 |
| 表、规则 | `t<n>`、`r<n>` | 租户内 | 递增的短 ID |
| 字段 | `f<n>` | 表内 | 递增的短 ID |

不是标识、但也有固定写法的：

| 令牌 | 写法 | 说明 |
|---|---|---|
| 版本标记 | `v<操作号>.<恢复次数>`；历史版本 `h…` | 见上 |
| 事项版本 | `iv_…` | 不透明，见「事项 ID 与事项版本」 |
| 删除确认句柄、翻页游标 | `dc_…`；不透明 | 服务层签名，见 architecture §5 |
| 连接实例令牌 | `slt_…` | 密钥，不是标识；只在控制面存它的哈希，不进日志 |

#### 术语

规则里反复用到的几个词，各在一处定义：

| 术语 | 一句话 | 定义在 |
|---|---|---|
| 写入号 / 操作号 | 一次操作对外的唯一序号 | 本节 |
| 所见版本、所见区间 | 写入带回的 `ver` 指向的版本；写入的区间按那个版本解析的结果 | 「冲突处理 · 冲突判据」 |
| 冲突单元 | 冲突判定与事项的最小单位：一个字段或一个字段组 | 「冲突处理 · 冲突判据」 |
| 合并基 | 冲突事项里各候选所见版本中最早的那个 | 「待处理事项 · 冲突事项的内容」 |
| 挡点 | 默认终点的写入停下来的业务时刻 | 「时间 · 状态类表的状态」 |
| 佐证端点 | 显式指向证据的同值写入留下的挡点 | 「时间 · 用同样的值写」 |
| 无值区间 | 状态类表上实体没有值的一段业务时间 | 「时间 · 无值区间」 |
| 贡献、佐证、无操作 | 一次写入给一个字段的值连同值来源；与所见版本同值时的两种情形 | 「删除 · 来源」 |
| 字面命中 | 写入的值在证据原文里字面出现过 | 「来源级别」 |
| 规则版本、策略版本 | 机械判定的语义版本；slot 策略的版本 | 「写入请求 · 规则版本与策略版本」 |
| 前提 | 一次写入声明的、它所依赖的已读到的值（op 参数 `premises`）。前提变了，saveslot 给依赖它的行打 `premise_changed` 标记 | 「写入的前提」 |
| 声明 | 一条前提：目标行或实体、可选的字段、读到时的版本、状态类表上的业务时间范围 | 「写入的前提」 |
| 重申、清除 | 不带 `set`、带非空 `premises` 的 `update`：值不变，只更新前提；带 `premises: []` 的 `update`：去掉这一行的前提声明 | 「写入的前提」 |
| 出处项 | 给出某个字段当前值的那一项贡献（搬运来的沿搬运引用走到头），另加当前仍作数的佐证项；前提声明挂在它上面 | 「写入的前提」 |
| 来源键 | 事件类表、无时间表上声明的 `external_key`：记录在来源系统里的标识，按它写入时有则更新、无则新增 | 「按来源键写入」 |
| 同步贡献、同步基线 | 按来源键写入给一个字段的贡献；按字段取的上次交来的值（基线值）与所见版本（基线位置） | 「冲突处理 · 冲突判据」 |
| 从未被写入 | 日志里没有任何以这张表为目标的 `write.base`；这样的表可以改结构 | 「schema 版本演进 · 改动分类」 |

### 行身份

- **基础表**：`row_id` 由 saveslot 在插入时生成并返回；Agent 之后按 `row_id` 改这一行。
- **状态类表**：对外的身份是 `entity_id`；写入按"实体 + 生效区间"表达，切出来的区间段由 saveslot 管理、不对外暴露；版本标记按实体给。
  schema 可为表声明可选的自然键 `entity_key`（如预算的类别），Agent 不知道 `entity_id` 时可按自然键定位实体（见「schema 文档格式」）。
- **来源键**：事件类表与无时间表可声明 `external_key`（记录在来源系统里的标识，如 `["origin", "external_id"]`），唯一范围是表。按来源键写入时由 saveslot 定位：有则更新、无则新增，定位到的或新分配的 `row_id` 记在事件里，重放不重新定位。行的身份仍是 `row_id`，来源键只是另一种找到它的方式；键字段只能经 `external_key` 给出，之后不可改。没有来源键的行可以补一次键（见「按来源键写入」）。状态类表不开放来源键，按自然键写入用 `entity_key`。
- **派生表**：行身份 = 不透明的 `partition_id`（规则内唯一），只读；一个分区恰好一行（第一版要求规则的最外层是分组聚合或整体聚合，见「派生规则与派生缓存」）。版本 = 最近一次刷新它的那次操作的操作号；读时计算的派生行（依赖"现在"的规则）没有版本，读结果不带 `ver`，带 `computed_at_read` 标注。
  **分组键值（如 W45 的 `week_start`、`GROUP BY category` 的类别名）由用户内容算出，是内容**："分组键值 → `partition_id`"的映射记在派生写入的内容里，事件头、`derived_reads`、计数表、read_log 都只用 `partition_id`；
  接口上仍可按分组键定位派生行，由 saveslot 经映射换成 `partition_id`。分组因删除而变空时映射一并清除；宽限期内同一分组键又有了行时，沿用原 `partition_id` 并在新的派生写入里重新登记映射（见「删除 · 由源数据派生出的内容」）。分组因撤销（或行被改到别的分组）而变空、之后同一分组键又有了行时，同样沿用原 `partition_id`；映射没有被清除，不用重新登记。这样读过这个分组的读取记录照样接得上。
- **迁移**：`row_id`、`entity_id` 保持不变；迁移改的是表结构和值，不是身份。

### slot 包含什么

- 一组表（基础表 + 派生表）、这些表的源数据、slot 的 schema 版本与当前版本指针、slot 内的待处理事项、slot 级策略。
- **slot 策略**的内容：

  | 项 | 是什么 | 默认策略（建 slot 时写下） |
  |---|---|---|
  | 自动生效的 schema 改动（`auto_apply`） | 哪几类改动不经确认就生效 | 八类全开：新增基础表（`add_table`）、新增派生表（`add_derived_table`）、新增可选字段（`add_optional_field`）、只改说明与别名（`description`）、没人在用的改名（`rename_unused`）、放宽约束（`loosen_constraint`）、改疑似重复的判据（`duplicate_keys`）、没人在用、从未被写入的表改结构（`restructure_unused`）（各类的定义见「schema 版本演进 · 改动分类」） |
  | 冲突期间的生效值规则 | 第一版只有"保持当前值" | 保持当前值 |
  | 秩表 | 来源级别的先后，系统裁定用（后续） | 用户明确 > Agent 推断 > 未命中；只记不用 |
  | 额外的高影响清单 | 策略指定的表 / 字段上的写入算高影响（后续） | 空 |
  | 只接受用户会话确认的处理方式 | 留位：哪类事项的哪种处理不能由 Agent 确认（后续） | 空 |

  每次策略变更是一条"slot 策略变更"事件，策略版本加 1（见「写入请求 · 规则版本与策略版本」）。第一版没有修改策略的操作，每个 slot 只有建 slot 时的那一条。
  **一个 slot 的策略就是那条事件里写下的全文**，不随内核里的默认策略变：默认策略将来增加的类别，只对之后新建的 slot 生效；已有 slot 的策略里没有的类别（例如没有 `restructure_unused`），对它就是"要确认"。来源键的增删换不另设类别：写入过的表上要确认，从未被写入的表上归入 `restructure_unused`。
- **建 slot**：v1 草稿编译通过即自动生效（slot 里还没有数据，没有什么可被破坏）；同时把默认策略全文写成一条"slot 策略变更"事件，策略不是代码里的常量。
- **每张表只属于一个 slot**；表名在 slot 内唯一（不分 ASCII 大小写），接口接受限定名 `health.runs`，表名在本次调用的可见范围内不重名时可只写表名、由表推出 slot（范围外的表不参与，免得一个只写 `runs` 的请求因范围外另有一张 `runs` 而报歧义，见「读取 · 可见范围」）。**一次写入只涉及一个 slot**（原子性靠一个指针锁）；跨 slot 的事拆成多次写入。

### 一条源数据是什么

- **一条源数据 = 一次写入随附的一段证据片段**，属于一个 slot；一次写入可带多段（同一 slot 内），单段有大小上限（初值见下）。
- 不收整段对话，只收与这次写入相关的片段（与"不全量保存对话"一致）。
- **每段证据有种类**：用户原话 / Agent 的转述或推断 / 工具结果 / 外部文件引用；没带证据时由 saveslot 存成"API 调用"。**"纠错"不是证据的种类**：它是读取源数据时带出的一个标注，由引用这段证据的写入的意图得出，不单独存。写入可指明每个操作、每个字段引用哪几段证据，基础写入的字段级来源由此得出（见「删除 · 来源」）。证据段可带可选的陈述时间（见「来源级别」）。
- **证据可以引用已有的源数据**（同一 slot，证据种类 `source_ref`，见 contract「证据」）：佐证时直接挂原来那条，不复制副本——否则用户删原话时，副本留了下来。
- **第一版不存文件**：来源是文件（文本、媒体）时，源数据是一条**外部文件引用**——文件名、类型、大小、内容哈希、可选的来源位置与文本摘录，saveslot 不保管文件本身；删除时如实告知"外部文件未由 saveslot 保管"。将来做文件存储（内容 blob）时按内容哈希补传，结构不变（positioning「后续规划」）。
- 大小上限（初值）：单段证据 32 KB，单次请求 256 KB。
- 没带证据时，请求本身存为源数据（类型"API 调用"，每个在事件里留下了东西的 op 各一条、只含该 op；没进事件的 op 不存，见「不变量：每次写入都有源数据」）。
- 一句话涉及两个 slot 时拆成两条源数据；用户要"删掉这句话"时，两个 slot 各删各的。

### 待处理事项：统一对象

待确认、冲突、核对不一致等统一成**一个对象**，持久存在 saveslot 里、属于某个 slot，由人（第一版经 CLI，App 后续）或 Agent（MCP）处理；"暂定"与"有争议"是数据上的标记，不是事项。
**本节是事项机制与各处理方式执行语义的权威定义**；契约（[`../04-contract.md`](../04-contract.md)「待处理事项」）只给出接口上的类型 × 处理方式 × 是否生效 × 所需 scope，并引用本节。

| 类型 | 接口类型 | 产生于 | 怎么解决 |
|---|---|---|---|
| 待确认（提议未生效） | `awaiting_confirmation`、`schema_change`、`migration_diff` | 高影响写入（清单见「时间 · 高影响写入」）、schema 变更、需要从旧字段重新抽取的迁移（迁移开始即生成） | 确认 / 拒绝；迁移另有"未处理的差异按拒绝处理并切换"与"放弃迁移" |
| 已标记（已生效） | `flagged` | 疑似重复（`duplicate_keys`）。统计异常第一版不产生事项（定义待定，见 architecture §14） | 保留 / 撤销 |
| 冲突 | `conflict` | 写入时所见版本对不上，记为候选 | 保持生效值 / 采纳候选 / 回到冲突前 |
| 删除宽限期 | `deletion` | 由删除生命周期推出（删除已确认 → 撤回或到期） | 撤回 |
| 核对不一致 | （接口暂无） | 后台证据核对：值与证据对不上 | 接受 / 纠正 / 忽略（**第一版不产生**：没有模型核对；字面命中每段的结果只有命中、未命中、不适用，没有"不一致"） |

多节点下的"同步被拒"见「同步协议」：第一版不产生，也不进契约。

**事项的字段**：事项 ID、事项版本、类型、slot、目标、当前值与提议值、影响、原因、发起者、状态（待处理 / 已解决 / 已被取代）、解决结果；冲突与待确认事项另记产生时的规则版本与策略版本。

- **事项的产生、并入、刷新、取代、解决都是日志事件**；解决事件带确认记录（解决者即用户、经哪个凭证、操作号；**所确认内容的哈希由内容算出，放在内容区**，随被确认的内容一起删）。事项的当前状态由日志算出，导出、恢复后不丢。
- **事项的内容记来源**：原因文字、影响、当前值与提议值、差异清单都是内容（按条目可单独删除），并记下它们引用了哪些行版本与源数据；
  隐私删除级联到这些来源时清除对应条目；事项若因此失去目标（目标行被删）、候选 / 提议值失去全部值来源、或冲突 / 高影响的成因被删，则标"已被取代"（原因码 `deleted`，不含内容），撤回删除时恢复（见「删除 · 重放规则」「撤回与宽限期」）。
  候选 / 提议值唯一的原文仍在的值来源被"删除证据"删掉时，同样标"已被取代"（原因码 `evidence_deleted`），不能再采纳或确认（见「删除的种类」）。
- **数据标记**：随读取结果带出，完整列表以 architecture §4 `flags` 为准（`disputed`、`awaiting`、`flagged`、`stale`、`pending_extraction`；`tentative` 只用于多节点，第一版不出现）；`disputed` 与 `awaiting` 带事项、字段与区间（见「读取 · 拿得快」）。契约里另有读时得出的标记：`corrected`、`possibly_affected`、`partially_deleted`、`revoked`、`pending_deletion`、`dangling_ref`、`computed_at_read`（归属见同一处，完整清单以 [`../04-contract-types.md`](../04-contract-types.md) 第 3 节为准）；派生行的汇总标记读时现算。

#### 目标与合并

| 事项 | 目标 | 同一目标上再来一个 |
|---|---|---|
| `conflict` | （行 / 实体，冲突单元）；状态类表另带业务时间区间。撤销参与的冲突，目标是（行 / 实体，**存在**） | **并入**：一个目标最多一个未决冲突事项。状态类表上，候选区间与已有事项的区间相交的并入它、事项的区间取并集；不相交的另成一项 |
| `awaiting_confirmation` | 这次写入要改的行 / 实体、字段与区间 | **不合并**：每次高影响写入各成一项。确认其一后，其余按「不过期」的规则被取代或刷新 |
| `flagged` | 被标记的行（新增的那一行）；内容里列出与它命中的行与命中的键组（见「写入请求 · 疑似重复」） | 每个新增的行一项 |
| `schema_change` | 草稿（一个 slot 同时只有一个） | 新草稿取代旧草稿 |

- 冲突单元是一个字段或 schema 声明的一个字段组（见「冲突处理 · 冲突判据」）。**一次写入在两个冲突单元上都成了候选，就是两个事项，各自解决。** 这样合并、取代、处理范围都不需要"部分"的概念；字段之间确有关联的，用字段组并成一个单元。
- 例：B 改了一行的 `amount` 与 `note`。A 带过期 `ver` 改 `amount` 与 `note`，C 带过期 `ver` 只改 `note`。结果是两个事项：`amount` 一个（候选 A），`note` 一个（候选 A、C）。

#### 冲突事项的内容

- **候选逐个列出**，每个候选是"某次写入在这个冲突单元上的全部部分"（字段组里它改到的几个字段、状态类表上它成了候选的几段，都算同一个候选，采纳时整体采纳；候选的下标在事项、契约与日志里是同一个）：写入号、写入者、意图、值（或撤销）、候选区间（状态类表）、所带的 `ver`、来由（第一版只有 `stale_write`）。成为候选的写入没有改生效值，不取代已有的事项，而是并入它。
- **合并基**：事项现存各候选所带 `ver` 中最早的那个版本。saveslot 的历史是线性的，所以唯一。事项内容记合并基的操作号，以及合并基上本事项的冲突单元（与区间）的值——这就是 `take_previous` 会回到的值；状态类表上它可以是多段。
- 候选并入、或某个候选被隐私删除去掉时，合并基按机械判定重算，事项版本换新。重算由判定模块做，结果交给事项模块记成事件（architecture §4）。
- **多候选与删除**：某个候选失去全部值来源时只把它从事项里去掉（事项版本换新），全部候选都去掉才标"已被取代"。
- 系统裁定（后续）时多个候选的秩都高于当前值，取秩最高者，同秩取写入号最早的；某个候选经系统裁定成为生效值后，事项保持未决。

例：#40 `distance 15`；#57 纠正为 5（带 `v40.0`）；A 带 `v40.0` 写 6（候选）；C 带 `v33.0` 写 5.5（候选；`v33.0` 时是 12）。合并基是 `v33.0`，`take_previous` 回到 12；只有 A 一个候选时合并基是 `v40.0`，回到 15。

#### 影响：执行后会改掉什么

事项产生时由内核算好，作为事项内容按条目存放，形状与写入回执里 `awaiting` / `candidate` 附带的内容相同：

| 事项 | 影响里有什么 |
|---|---|
| `awaiting_confirmation` · 高影响 ① | 会被覆盖的段（按字段）：区间、原值、写它的写入号与写入者；会被填上的无值区间（附留下它的那次撤销） |
| `awaiting_confirmation` · 高影响 ② | 仍引用该行的行 |
| `awaiting_confirmation` · 高影响 ④ | 会被回掉的后来写入 |
| `conflict` | `take_previous` 会回到的值，以及会被它回掉的写入（合并基之后在这个冲突单元上生效过的全部写入）；候选若生效会属高影响时，采纳它会覆盖的段 |
| `schema_change` | 草稿 ID 与逐项改动；影响预览里的行数与试跑结果是草稿提交时的估计，不在绑定范围内 |

- **影响在事项版本与确认记录内容哈希的覆盖范围内，事项详情必须给出**——只看详情就确认的调用方，看到的与拿到写入回执的一样多。所以由 `resolve` 触发的写入不再另过高影响判定：采纳候选、回到冲突前就是对影响里列出内容的确认。
- **影响不会悄悄过期**：
  - 改到这些段、这些写入的写入，按「不过期」的规则取代或刷新事项；
  - 隐私删除清掉其中一条时事项版本换新，成因全被删时事项被取代；
  - 高影响 ② 的引用方会变而目标行本身没被改：别的行新增或去掉对该行的 `ref` 时（引用方被撤销、撤销被 `undo` 而恢复，同样算去掉、新增），内核刷新影响里的对应条目、事项版本换新（写入管线本来就要校验 `ref` 的目标），带旧版本确认会收到 `confirmation_mismatch` 与新的引用方列表。引用方全部去掉后事项仍然保留、影响为空，照常等人确认——saveslot 不因为成因消失就替人执行。

#### 事项 ID 与事项版本

- **事项 ID**（`pi_…`）是短的稳定 ID，由 saveslot 随机分配、租户内不复用，**不签名、不绑定内容**；事项并入新候选、条目被删除清除之后 ID 不变。
- **内容绑定靠事项版本**：一个不透明令牌，编码（事项 ID、事项内容最近一次变化的操作号、租户恢复次数）。事项产生、并入、刷新、条目被清除、被取代、撤回删除时恢复、解决时都换新。
- **解决请求带回读到的事项版本**，版本对不上就拒绝并给出当前内容——K14"确认绑定内容"由此成立。所确认内容的哈希照旧由内容算出、记进解决事件的确认记录（内容区）；是谁确认的看解决事件的 `actor`，经哪个凭证由 `actor` 得出，确认记录里只有哈希。
- **没带时的兜底**：用本连接实例最近一次读到的该事项版本，规则同 `ver` 兜底（带了任务标识只认同一任务）；也没读过就拒绝，提示先查看事项。
- **"读到"事项版本只有两种**：
  - ① 查看该事项的详情；
  - ② 本次写入 / 删除 / 草稿提交**新生成**了该事项，且回执给出了它的全部内容（写入回执逐字段结果里的 `awaiting` / `candidate`，删除回执的 `deletion`，`schema_draft` 回执里的 `schema_change`）。

  只列出事项 ID 的地方（回执的 `pending[]`、`superseded[]`、`warnings`，读结果的标记）不算；本次写入**并入已有事项**的也不算——回执只写了本次写入的那部分，合并后的内容调用方没看到过，回执提示先查看事项。
- 记下"读到"的是 `audit`：`pending` 详情由 `read` 交给它，回执里新生成事项的版本由 `write` / `delete` 交给它（`schema_draft` 的经 `ops`）（architecture §4）。

**按事项类型与处理方式区分绑定什么**：上面的"版本对不上就拒绝"是默认；以下例外——

| 事项 · 处理方式 | 绑定什么 |
|---|---|
| `migration_diff` · `abandon` / `keep_rest_and_switch` | 只绑定"哪一个迁移"：事项 ID（与迁移一一对应）+ 租户恢复次数；不核对内容，差异清单随抽取增长不影响 |
| `migration_diff` · `accept_all` | "截至第 k 条差异"：差异条目按列出的先后编序号，详情返回 `diff_upto` = 当前最后一条的序号，处理时带回；只接受序号 ≤ k 的条目，之后列出的留在清单里。条目被刷新时取新序号（见「不过期」），所以序号 ≤ k 的条目就是调用方读到时的样子 |
| `migration_diff` · 逐行 | 只核对所列的行：这些行的差异条目在调用方读到的事项版本之后没有变化；其余行的变化不影响 |
| `deletion` · `cancel` | 不核对事项版本：只要仍在宽限期就执行。撤回是删除唯一的后悔路径，换一个会话或任务来撤回时不该先被要求读一次；撤回不确认任何新内容 |

**判定顺序**：事项不存在 → `not_found`；事项已关闭（已解决或已被取代）→ 已解决、处理方式相同时返回原结果（重放，不再执行），否则拒绝（`item_closed`，附已有结果或取代者 / 取代原因）；最后才校验事项版本（`confirmation_mismatch`）。

- 所以 24 小时后用旧事项版本重发同一处理方式，按重放返回，不报版本对不上。
- 恢复备份后，恢复前拿到的事项版本恢复次数对不上，报 `confirmation_mismatch`（附当前版本与内容）。
- `deletion` 事项到期物理删除后是已解决（结果"已执行"），之后 `cancel` 报 `item_closed`。

#### 不过期：合并、取代与刷新

**只有人或 Agent 有判断力，saveslot 没有，任何到期时长都是拍脑袋。** 事项不过期；不堆积靠三样：同一目标的冲突并入一个事项（见「目标与合并」）；被看过它的写入方改过就取代；schema 切换后不再适用的取代。未处理期间按冲突规则给出确定的生效值（永不阻塞）；长期未处理只在读写结果的提示里升级，saveslot 不自动处置。

一次已生效的写入**改到**未决事项的目标时：

| 写入方 | 事项 | 说明 |
|---|---|---|
| 读过该事项的当前版本（"读到"的定义见上） | **已被取代** | 写入方看过候选 / 提议之后做了新的写入，旧的争议没有意义了 |
| 没读过 | **刷新**，保持未决 | 冲突事项的当前生效值换成新值，影响重算；待确认事项的"将被覆盖的段"重算。事项版本换新，回执 `pending[]` 里标 `refreshed: true` |

- **"改到"按冲突判据算**：写入改到事项的冲突单元才算（状态类表还要求业务时间区间与事项的区间有交集）；没交集的事项不受影响，执行时按记下的区间。成为候选或进待确认的写入没有改生效值，不算改到。
- **为什么没读过就不取代**：写入方读到的只有生效值与标记，没看过候选。让它替人关掉冲突，等于候选无声消失——例如生效 9.5（Agent 推断）、候选 10（用户原话），无人值守的 Agent 按工具同步写了 9.6，用户说的 10 就不再出现在任何待处理事项里。候选只能被看过它的一方关掉。
- **刷新之后**，拿着旧事项版本的 `resolve` 会收到 `confirmation_mismatch` 与新内容，要重新确认。采纳候选或确认提议因此不会悄悄盖掉新写入。
- 写入方"是否读过"在写入时由读取审计得出，结果写进取代 / 刷新事件；重放时用记下的结果，不重算（与疑似重复、字面命中同样处理）。
- **`flagged` 例外**：它没有未生效的候选或提议可丢，所以不看写入方读没读过。被标记的行被撤销，或它与列出的行都不再命中（任一方被改、被撤销）时，事项标"已被取代"；只是其中几行不再命中时刷新条目。
- **schema 切换**：事项涉及的字段在切换中发生了不兼容变化（与旧 `sv` 写入的判据同一套，见「schema 版本演进 · 原则」）时，事项标"已被取代"。只改名、同量纲改单位不算。
- **`migration_diff` 例外**：不因迁移期间的普通写入被取代——迁移期间改到 `from` 字段的写入是预期内的（自动追加工作项，见「抽取作业」）。被写入改过的行，在差异清单里**刷新对应条目**：旧条目作废，该行重新抽取后按新结果重新列出、取新的序号排到末尾。
  它只在迁移结束时关闭：切换（已解决）、放弃迁移（已解决）、迁移失败（已被取代，原因码 `migration_failed`）。

#### 各处理方式的执行语义

处理方式就是"照记录执行的人的决定"（见「删除结果的定义」）。由处理触发的写入都要有源数据（见「不变量：每次写入都有源数据」），解决请求只是操作来源，除非下表写明。由处理触发的写入属于这次解决操作：头事件是解决事件，操作号是它的 `seq`，没有另外的逻辑写入头。**解决请求带的备注（`note`）与证据都存为源数据**，解决事件以操作来源引用；不触发写入的处理方式（保持生效值、拒绝、保留）同样如此。

| 接口类型 | 处理方式 | 执行 |
|---|---|---|
| `awaiting_confirmation` | `confirm` | 提议的写入生效；值来源 = 对提议写入贡献的引用 |
| | `reject` | 提议不生效，留在历史里 |
| `flagged` | `keep` | 数据不变，标记撤掉 |
| | `revoke` | 撤销被标记的那一行（一次撤销写入，与普通撤销一样触发纠错影响查询） |
| `conflict` | `keep_effective` | 保持当前生效值，所有候选都不生效 |
| | `take_candidate` | 采纳 `candidate` 指定的那一个候选（候选在事项里的下标，从 0 起；事项里只有一个候选时可省略，多个时不给报 `invalid_argument` 并附候选列表）。**只落本事项的冲突单元**，状态类表按候选区间执行。值来源 = 对该候选贡献的引用；事项里值相同的其他候选的贡献一并作为值来源。其余候选不生效、留在历史里 |
| | `take_previous` | **回到合并基**：与 `undo` 是同一种操作（回掉）。回掉事项的冲突单元与区间内、合并基之后生效过的全部项（写入时逐项列进回退记录；候选不在其中，由解决关闭），范围是这些项的区间与事项的区间之交，范围内回到合并基操作号处的状态；合并基处没有贡献时写回"没有值"。区间外、其他冲突单元上的写入不动。值来源 = 对合并基处生效的那几个贡献的引用。回掉写入的意图：`undo` 调用方给了意图就用它，没给时取**被撤回的操作在这一行（或实体）上 `seq` 最大的那条 `write.base` 的意图**，不看 `include_later` 连带回掉的写入；`take_previous` 取**回退记录里事件 `seq` 最大的那一项所在 `write.base` 的意图**，回退记录为空时取 `update`。合并基的操作号照解决时记下的，之后的隐私删除不改它；范围与值在删除重放里重新求（权威定义见「删除 · 重放规则 · 回掉的权威定义」） |
| `schema_change` | `confirm` | 草稿生效。不需要建新物理表的（只改目录）当场切换；物理形状变了的进入迁移中，由 saveslot 建新表、按日志重放后切换，不再等人（见「物理做法」）。需要重新抽取的（后续）另生成抽取作业与 `migration_diff` 事项，见「抽取作业」 |
| | `reject` | 草稿放弃 |
| `migration_diff`（后续） | `accept_all` | 接受序号 ≤ `diff_upto` 的全部差异（新值进新版表）；没有提议值的条目（以 `ambiguous` 跳过的）不在其内，留在清单里。抽取还没完成时也可以用；抽取完成、差异全部处理后切换 |
| | 逐行（`accept` / `reject` / `set`） | 逐行接受、拒绝（新字段留空，旧值在旧版与源数据里仍可查）或给值；`set` 的值来源 = 这次解决的证据（没带就是解决请求本身） |
| | `keep_rest_and_switch` | **= 对所有未处理的差异按逐行 `reject` 处理**（新字段留空，旧值在旧版与源数据里仍可查），然后切换到新版。对拆字段的实际后果：新字段在这些行上为空；旧字段若在 `drop_fields` 里，切换后当前版本里看不到它，只能按时刻读或在源数据里查到——事项详情与提示必须写明。还没抽完的项仍按原迁移的差异规则处理，不按纯补抽直接生效（见「抽取作业 · 迁移期间与切换」） |
| | `abandon` | 放弃迁移：丢弃构建中的新版表，旧版仍是当前，什么都没变；抽取作业结束、未交的租约作废（之后提交报 `lease_expired`，原因 `migration_abandoned`）；已交的翻译留在日志里、不生效 |
| `deletion` | `cancel` | 撤回这项删除（见「删除 · 撤回与宽限期」） |

**处理之后事项不重开**：第一版没有办法让一个已解决的事项回到未决。不触发写入的处理方式（`keep_effective`、`reject`、`keep`）没有可 `undo` 的东西；触发了写入的（`confirm`、`take_candidate`、`take_previous`、`revoke`），那次写入可以 `undo`，值回到处理之前，但事项保持已解决，没被采纳的候选不再出现在任何未决事项里。用户改了主意、要用某个候选的值，直接写入它。按来源键同步的表上，这一条的效果是：用户以"保持生效值"或"回到冲突前"拒绝过的来源值，之后的同步不会反复提出，也不会直接生效（见「按来源键写入」与「冲突处理 · 冲突判据」的同步基线）。

**目标是"存在"的冲突事项**（撤销与并发修改，见「冲突处理 · 撤销与并发修改」）：

| 处理方式 | 效果 |
|---|---|
| `keep_effective` | 保持现状，候选不生效 |
| `take_candidate` | 候选是撤销：撤销生效。候选是修改：行恢复存在，并落这次修改 |
| `take_previous` | 回到合并基：行存在，值是合并基上的值。回退记录里列入合并基之后对任何字段、对"存在"生效过的项：回掉的是撤销时行恢复存在，回掉的是修改时字段回到合并基的值 |

- 状态类表上采纳候选、回到冲突前都只动事项记下的区间。挂起期间有与该区间相交的写入时，事项已被取代或已刷新（事项版本换新，须重新确认），不会悄悄覆盖。
- 抽取作业的跳过原因码只有两个：`no_content`（原文没有可抽取的内容，新字段留空）、`ambiguous`（判断不了，进差异清单交给人）。

## 引用：强与弱

**判据：被引用的东西没了，引用方还成不成立？** 不成立（要删或要重算）是强引用；
仍成立、只是"曾指向一个现已删除的东西"是弱引用。

| 引用 | 从 → 到 | 强 / 弱 | 挡删除吗 | 删除时怎么处理 |
|---|---|---|---|---|
| 基础数据当前值的值来源 | 基础表当前版本的写入 → 源数据（change_sources 里的值来源） | 强 | "删除证据"时挡（只看原文仍在的值来源）：默认拒绝，列出引用方；隐私删除不挡；操作来源不挡 | 隐私删除按「删除结果的定义」：去掉被删来源的贡献、按重放规则重放（见「删除」） |
| 派生数据的来源 | 派生写入 → 上游写入（分区级读集） | 强 | **不挡**：派生能重算 | 受影响的分区重算 |
| 历史版本的来源 | 已被覆盖的写入 → 源数据 / 上游写入 | 强 | 不挡（当前状态不依赖它） | 级联时物理删除由被删贡献得出的内容块（各次写入事件里那些字段的值与来源、版本表里对应的历史值）及其校验和——否则可从历史反推；派生写入的结果校验和、分组键值同样清除 |
| 读取 | read_log → 写入版本 | 弱 | 不挡 | 不改、不通知；内容清除后自然指向"已清除的版本" |
| 事件头链 / 墓碑 | 日志事件 → 被删内容块的位置 | 弱 | 不挡 | 事件头保留，链仍可校验；墓碑只记不透明位置（事件 `seq` + 块路径）与原因码 |

- 例子（一周的跑步记录：R2 是"今天跑了 7 公里"这条源数据，C3 是由它新增 runs#2 的写入，C4 是随之把周跑量 W45 刷新的派生写入）里"删除证据"R2 时：runs#2 的当前版本 C3 直接引用 R2——挡；W45 是派生数据，能重算——不挡；
  C4 已被覆盖，是历史引用。换成隐私删除时不挡：去掉 R2 的贡献后，runs#2 的必填字段没有仍在的贡献，整行删除、W45 重算。
- 引用关系是有向无环的（源数据 → 有模型数据 → 派生数据），引用计数就够，不需要追踪式 GC。
- **和堆内存不同：引用归零不等于垃圾。** 没被引用的源数据仍可能在新 schema 下被重新抽取，不自动回收；
  引用计数只是删除的门槛，不是触发条件。

## 模型放在哪

**saveslot 的核心路径不依赖模型；依赖模型的工作，都作为普通客户端经同一套接口提交。**

- **确定性内核（不用模型）**：日志、存储、schema 校验、版本、冲突规则、权限、审计。
  saveslot 的可信保证不能建立在模型输出上。
- **写时抽取，优先由调用方 Agent 完成**：schema 由 saveslot 维护，但"按 schema 把一句话变成结构化数据"
  这一步的推理，用调用方 Agent 自己背后的模型来做（它本来就在跑模型），saveslot 不必另调一次；
  而且它最清楚用户此刻的意图。它经 MCP 读取 schema、按 schema 提交结构化写入并附上源数据，saveslot 只做确定性校验。
- **没有 Agent 的调用方**（脚本、程序）经 API 直接写结构化数据；只能给出原始数据时，交给调用模型的后台执行方（worker）抽取（worker 不进第一版，见 positioning「后续规划」）。
- **模型的输出记成日志事件**：每次抽取的结果（及它引用的源数据、用的 schema 版本）作为事件记入日志。
  重放时用记下的结果，不重新调用模型——类似 MySQL 的 row-based binlog 记录结果，
  而不是 statement-based 那样重新执行含非确定函数的语句。只有受影响的部分才需要重新抽取。
- **没有 Agent 在场的工作，由调用模型的后台执行方（worker）完成**（不进第一版）：外部来源同步、定时任务、
  schema 变更后的批量重算、从积累的源数据起草新 schema。
- worker 也是一个有身份的客户端，写入的来源级别是"Agent 推断"，同样走权限和冲突规则。
- 模型接入：**用户自带 API Key**。没配 Key 时 saveslot 仍可运行，只是没有后台抽取和重算。

## 语义：动态 schema

- **saveslot 提供动态语义能力**（参考 NVIDIA Auto Ontology 的"起草 → 人确认 → 发布"），
  每个人都能有自己的数据样式。
- **官方提供精选 schema**：如 Health Data Schema、账本 Schema。官方 schema 同时是一份对外约定：
  用户 schema 可在其上扩展，为官方 schema 写的能力就能复用。
- **社区发布 Schema + SKILL**：schema 定义数据长什么样，SKILL 告诉用户的 Agent 何时写、怎么抽取、怎么用。
  这正好对应"写时抽取由调用方 Agent 完成"。

## 冲突处理

**不能假设有推送通道，也不能假设用户会及时响应。** 冲突是一种持久状态，不是一次通知。

1. **写入时检测，退回给写入方。** 写入带预期版本；对不上、且改到同一个冲突单元时记为候选（不是报错），回执告诉写入的 Agent
   ——它此刻正在和用户对话，是最可靠的"通知"。
2. **读取时带出。** 未解决的冲突与待确认项随读结果附带，标明"有争议"。下一个读到的 Agent 都能告诉用户；
   读请求本身就是通知渠道。
3. **永不阻塞。** 冲突期间按 slot 策略里的生效值规则给出确定的生效值。**第一版的规则是保持当前值（先提交者）**；按来源级别自动裁定见「系统裁定」，后续。
   读方拿到"生效值 + 争议标记"，自己决定任务是否继续（高影响停下来问，低影响带标记继续）。
4. **不过期，但不堆积。** saveslot 没有判断力，不替人裁决；同一个目标上的冲突并入一个事项，被读过它的写入方改过即标"已被取代"（见「待处理事项 · 不过期」）；隐私删除去掉了冲突的成因或候选的全部值来源时同样已被取代（见「删除 · 重放规则」）；长期未处理只升级提醒。
5. **记录读取。** 记下哪次任务用了哪个版本；冲突事后裁决后，能查出哪些任务用了被推翻的版本。

（1、2 应对"通知不到"；3、4 应对"没人响应"——靠确定的生效值，不靠到期；5 应对"响应太晚"。）

### 冲突判据

**一次写入表达的是"相对我读到的那个版本，我要改什么"。** 带回的 `ver` 就是它所见的版本。`ver` 是当前版本时没有冲突可言；不是当前版本时，记这次写入为 W、它所见的版本为 V，按下面的步骤判。

**冲突单元**：一个字段，或 schema 声明的一个字段组（`together`，见「schema 文档格式」）。同组字段作为一个整体判：改到组里任何一个字段，就与改到组里任何字段的写入相交。不声明时每个字段自成一个单元。字段组只影响冲突判定与事项的目标，不影响挡点、来源、同值判断。

| 步 | 做什么 |
|---|---|
| ① | 去掉 W 里的**无操作字段**：值与 V 上相同、又没有显式指向证据的字段不是 W 的改动（见「删除 · 来源」）；V 取它在写入时已确认、未撤回的删除之后的样子。Agent 原样带回的字段因此不会造成假冲突 |
| ② | 对 W 剩下的每个冲突单元，找 V 之后**让它的生效值变化的操作** L：已生效的写入、解决事项触发的写入、删除确认、撤回删除都算（删除让值回到更早的样子，写入方同样没看到）。成为候选或进待确认的写入没有改生效值，不算；schema 切换时 `backfill` 的补值也不算（它不改 `ver`，带着切换前读到的 `ver` 写这一行不因它而冲突；字段本身有不兼容变化时由 `sv` 的检查拒绝） |
| ③ | 按下表判 W 与每个 L 是否冲突 |
| ④ | 与所有 L 都不冲突 → **合并**：直接生效，回执写明是自动合并的。状态类表上 W 的区间按**当前**状态解析并落账 |
| ⑤ | 与某个 L 冲突 → W 在这个冲突单元上参与判定的那一项**整体成为候选**，不生效；生成冲突事项，或并入同一目标上已有的事项（见「待处理事项」） |

| 表 | W | L | 冲突当且仅当 |
|---|---|---|---|
| 事件类、无时间 | — | — | 这个冲突单元在 V 之后被 L 改过 |
| 状态类 | 默认终点 | 默认终点 | 起点相同且值不同 |
| 状态类 | 其余组合：至少一方是显式区间（纠错的默认区间算显式区间） | | W 的**所见区间**与 L 的区间相交，且交集上 W 的值与当前值不同 |

- **两边都是默认终点**只在双方的原始写法都读得到时成立：一项的区间块已被移除或是导入的占位时，它的原始写法读不到，按显式区间判。

- **组值**：冲突单元是字段组时，上表里的"值"指组值。W 的组值 = 组里 W 写了、且这一时刻落在该字段自己所见区间里的字段取 W 的值，其余字段（W 没写的，以及写了但这一时刻不在它所见区间里的）取所见版本 V 上的值（状态类表上逐时刻取：没写的字段在 V 里可能分段，写了的字段各有各的所见区间）；V 在某一时刻没有值时，取 V 的那些字段在这一时刻按空算——W 生效后实体在这一时刻存在，W 没写的字段就是空。当前组值 = 组里各字段的当前值；当前在某一时刻没有值时照原样是"没有值"（实体在这一时刻不存在，不是字段为空）。默认终点对默认终点比的是 W 的组值与 L 落账后在该起点的组值。单字段的组就是上表的写法。组值只用在这一步：步骤 ① 的无操作与佐证仍逐字段判。例：W 写 a、L 写 b（同组），两种到达顺序都冲突。W 与 L 都只把 a 写成同一个值：状态类表上组值相同，两种顺序都不冲突；事件类表、无时间表上不比值（上表第一行），这个冲突单元在 V 之后被改过就冲突，两种顺序都是后到的一方成为候选。
- **所见区间** = W 的区间按版本 V 的状态解析的结果（显式区间就是它本身）。状态类表上候选的区间就是所见区间，整段成为候选，不拆成"相交的部分候选、其余生效"：区间是一句话，生效一半更难向用户解释。唯一会把一个字段分成几项的是佐证：仍同值的那部分追加来源，已被改掉的那部分才按上表参与判定，成为候选的是后者的整段（见「用同样的值写」）。
- **L 的区间** = L 那一项贡献当前的解析结果：它写入时记下的区间，或之后某次隐私删除的重放给它重新解析出的区间，以日志里最近一次给出的为准。L 是删除确认或撤回时，是那条事件记下的、它在这个冲突单元上实际改了值的区间，照记录，不随之后的删除重算（写入方没看到那次删除是日志里的事实）。这些区间由那条事件的 `results/<k>/fields/<字段ID>/<j>` 与 `results/<k>/existence`（事件格式 §5.9）对照它之前的状态得出；这个冲突单元在那条事件里的这些块有任何一块列在当前被删集合里任一项删除的位置列表里（事件格式 §3.5 规则 1：`deps` 里有一项被删除，或被那次删除重述；与那次删除是否已到期执行无关）时，把它当作在整个冲突单元上改过值：会多判出候选，但不会让一次写入盖掉它没见过的改动。删除确认与撤回作为 L 时，按上表"至少一方是显式区间"的那一行判（它们记下的是实际改了值的区间，不是一次带默认终点的写入）。只有 `results/<k>/existence` 列在位置列表里时，按"存在"单元整个改过算——这次删除或撤回给了这一行或实体新的 `ver`——不因此把字段单元当作整个改过；字段单元整个改过，看的是那个单元自己的 `results/<k>/fields/…` 块。
- **L 是经确认生效的提议写入时**（高影响写入的待确认被确认），它算默认终点还是显式区间，按提议写入的原始传参：确认是"提议的写入生效"（见「各处理方式的执行语义」），L 的区间写法就是提议写入的写法。
- 一个 op 可以一部分冲突单元生效、一部分成为候选，回执逐字段写明。
- **对称**（有范围）：状态类表上两次带同一个 `ver` 的写入，**都不传终点、都没有显式指向证据、都没有让所见版本里的变化点消失**时，谁先到都得出同一个结论——要么两种顺序都判冲突，要么两种顺序都合并、**最终的值相同且都不引出事项**。后一半靠高影响 ① 只保护写入方所见版本里已有的变化点：两种顺序都合并时，后到的一方让先到一方刚造出的变化点消失不算高影响（见「高影响写入」）。佐证不换 `ver`，之后带这个 `ver`、且这个 `ver` 在写入时仍是当前的写入算看过它，不在本条之内；它盖掉佐证段的后果见「用同样的值写」。
  这个范围之外不作这样的承诺。已知三处，两种顺序的结果不同（三处都不丢写入，也都不让候选悄悄生效）：
  - (a) **一方给了显式区间、一方不传终点，起点相同、值相同**：不冲突，两种顺序都合并、都不引出事项，但终态不同。默认终点在合并时按当前状态解析：显式的一方先到，它的终点成了挡点，后到的一方停在那里，显式终点之后保留原值；不传终点的一方先到，新值一直延续下去。
  - (b) **一方因高影响进了待确认**：待确认的写入没有改生效值，不算另一方的 L（步骤 ②）。于是同一对写入，一种顺序是后到的一方成为候选，另一种顺序是一方待确认、另一方直接生效。两种顺序都要人处理，事项的种类不同。
  - (c) **一方的默认终点在所见版本里停在某个挡点上，另一方带 `acknowledge` 抹掉了这个挡点**：两种顺序都合并、都不引出事项，但终态不同。抹掉挡点的一方先到，另一方的默认终点按当前状态解析，越过原来的挡点延续下去，盖掉它所见版本里那一段的值；反过来，它停在原来的挡点上。它是佐证时也一样。
  这三处是现行规则的结果，不是实现的缺陷；规则是否改到让它们也对称，见 [`../08-open-questions.md`](../08-open-questions.md)。各处由哪条测试守着，见 [`../11-claims.md`](../11-claims.md)。
- 依赖当前状态的校验（如无值区间须带齐必填字段）在冲突判定之后做，只对将要生效的部分做；成为候选的不做。否则同一对并发写入一种顺序报错、另一种顺序成候选（判定顺序见「写入请求 · 判定顺序」）。

**按来源键写入的所见版本**（见「按来源键写入」）：连接器没读过这一行，带不回 `ver`；它知道的只是"来源系统现在说这条记录是什么"。所以判定比的是三样——上次按来源键交来的值、当前生效值、这次交来的值，所见版本由内核**按字段**给出。先定三个词（都是机械判定；来源键的键字段不在其内，它只在得到键的那次写入里有贡献）：

- **同步贡献**：按来源键写入给这一行某个字段的一项贡献，不论它当时是生效、佐证、候选还是待确认；以及采纳这样一个候选时搬运出的那一项。**不算**的：`take_previous` 与 `undo` 写回的项——它们是人的处理带出来的值，不是来源系统交来的。
- **已生效的同步贡献**：当前状态为 `applied` / `corroborated`、且**没有被登记为"已被回掉"**的同步贡献。被 `undo` 回掉的同步贡献仍是同步贡献（计入基线值），但不再是已生效的（不计入基线位置）；被回掉的项是否生效以回退记录为准。
- **同步基线**，逐字段：
  - **基线值** = 这个字段上最近一项同步贡献的值；还没有同步贡献时没有基线值。
  - **基线位置** = 这个字段上最近一项已生效的同步贡献所在的操作号；没有时取这一行得到来源键的那次操作（按来源键新增的那次，或补键的那次）。
  - 键从一行已撤销的行**转来**时，这一行在补键之后、自己还没有同步贡献的字段上：基线值沿用原来那一行这个字段上最近一项同步贡献的值（原行没有时就没有基线值），基线位置取补键那次操作。有了自己的同步贡献之后只看自己的。补键那次写入的键字段贡献被删除执行去掉之后，键回到让出它的原行（仍是已撤销的），这一行不再算"键是转来的"；删除重放里，之后按这个键的同步 op 命中的是已撤销的原行，按"被撤销的行不复活"处理（重述为 `dropped`）。
  - 按字段取，不按冲突单元取：同一冲突单元里别的字段的同步贡献，不代表这次交来的值看过这个字段上的本地改动。

判据只换掉两处输入，其余不变：

| 步 | 普通写入 | 按来源键写入 |
|---|---|---|
| ① 同值 | 与所见版本上的值比 | **与基线值比**。与基线值相同 → 来源没变：不论是否指了证据，当前生效值与它不同时一律是无操作（不重提）；当前生效值也与它相同时，指了证据是佐证，没指是无操作。没有基线值的字段与基线位置上的值比，规则同普通写入 |
| ②–⑤ 冲突 | V = 带回或兜底的 `ver` | **V = 这个字段的基线位置**。基线位置之后这个字段所在的冲突单元被别的操作改过 → 候选，生成或并入冲突事项；没被改过 → 生效 |

- 冲突事项与普通写入相同：目标是（行，冲突单元），候选并入；候选"所带的 `ver`"是这个字段的基线位置，合并基照常取各候选所带版本中最早的。
- 上面的"对称"说的是两次带同一个 `ver` 的写入；按来源键写入的所见版本由内核按日志位置取，同一租户写入串行，结果只取决于日志。
- 效果：用户在 saveslot 里改过的值不会被每次同步盖回去（来源没变就是无操作）；来源变了、本地也改过时成为候选，不覆盖；候选也是同步贡献，所以同一个候选不会每次同步再并入一遍，用户以"保持生效值"或"回到冲突前"拒绝过的来源值也不会在下一次同步时直接生效；来源又变了，再问一次人。

**为什么两个默认终点的写入起点不同就不冲突**：它们各自只声明"从某天起值是 v"，谁先到结果都一样（一方抹掉了另一方停靠的挡点时除外，见上面对称一条的 (c)）。一旦有一方给了显式区间，它覆盖的范围不再随对方而变，必须用所见区间判，否则合并结果会依赖顺序。

**例（状态类表）**：`[10-01, ∞) 5000`，A、B 带同一个 `ver`。

| A | B | 两种到达顺序 |
|---|---|---|
| "11-10 起 3000"，不传终点 | "11-02 起 4000"，不传终点 | 都合并，结果都是 5000 · `[11-02, 11-10) 4000` · `[11-10, ∞) 3000` |
| "11-10 起 3000"，不传终点 | `[11-02, open) 4000` | 都冲突：后到的一方成为候选 |
| 改 12 月 `[12-01, 2027-01-01)` | 改 11 月下旬 `[11-20, 12-01)` | 区间不相交，都合并 |

第三行是按区间判的原因：`ver` 按实体给，只看实体的话同一实体上任何两次并发写入都会被判成冲突，无人值守的 Agent 会持续制造假冲突。

### 撤销与并发修改

撤销不带值，按字段看它与任何修改都"没有交集"。所以单独规定：

- **撤销改的是行 / 实体的"存在"，与每个冲突单元都相交**（状态类表：撤销区间内）。过期的撤销遇到期间任何已生效的修改 → 候选；过期的修改遇到期间的撤销 → 候选。这类事项的目标是（行 / 实体，存在）；同时与期间的撤销和字段修改冲突时，也归"存在"（撤销改的是行或实体在不在，比字段上的争议更根本，一个候选只在一个事项里），处理方式见「各处理方式的执行语义」。
- **事件类表、无时间表**：已撤销的行不可写。变更、纠错报 `revoked`（附撤销它的写入号，提示用 `revert: {undo}` 恢复）；再次撤销是无操作。
- **状态类表**：撤销就是"这段时间无值"，之后的写入按填无值区间处理（见「状态类表上的撤销」）。
- **采纳一个修改候选（目标是"存在"）**：候选区间内实体恢复有值，落这次修改；候选没给的必填字段取合并基在该区间上的值，记为搬运（值来源是对合并基处那些贡献的引用）；合并基上也取不到时，`resolve` 报 `validation_failed`（`required_in_gap`），提示改用 `keep_effective` 或先补齐字段。撤销区间里候选区间之外的部分保持无值。

**例**：A、B 都读到 r7（同一个 `ver`）。B 把 `distance` 从 10 纠正为 5。A 带旧 `ver` 撤销 r7（"这条记重了"）。A 的撤销成为候选；反过来 A 先撤销、B 后改，B 的修改成为候选。两种顺序都判冲突。

### 既版本对不上、又是高影响

冲突优先：这次写入成为候选，生成冲突事项。候选若生效会属高影响，事项的影响里同时列出会被覆盖的段；采纳候选就是对这些内容的确认，不再另生成待确认。冲突因隐私删除消失之后怎么办，见「删除 · 重放规则」。

### 系统裁定

> **不进第一版。** 第一版冲突一律保持当前值；来源级别与字面命中照常记进事件（见「来源级别」），供将来使用。

- 规则：权威来源优先；用户明确 > Agent 推断，只认字面命中的级别。写成一张**秩表**放在 slot 策略里：秩 = 命中时取声明级别，未命中时为最低；秩严格更高者胜，同秩保持当前值，多个候选同秩取写入号最早的。
- 按规则裁定的生效值与当前值不同时，物化为一个新版本（意图"系统裁定"；值来源 = 候选写入的值来源，事项只是操作来源），刷新派生；回执里该字段的结果是 `applied_by_rule`（附 `pi_…`），并与纠错同等触发纠错影响查询（见「纠错影响查询」）。某个候选经系统裁定成为生效值后，事项保持未决。
- 加回系统裁定时，旧写入与旧事项不会自动改判：每次判定都记下当时的规则版本与策略版本（见「写入请求 · 规则版本与策略版本」）。

## 同步协议（每用户一个主节点）

> **不进第一版**（positioning「后续规划 · 多节点」）。第一版两种运行模式都是单节点；本节保留为将来的设计。
>
> **第一版为它留的结构**：事件头不含 `event_id`；创世事件与恢复事件各带一个 `node_id`，事件的永久身份 = （最近一条创世或恢复事件的 `node_id`，`seq`）。多节点加入时旧事件不用改。
>
> **对外契约第一版不含多节点的任何内容**：节点凭证、日志同步端点、`tentative` 状态与标记、`sync_rejected` 事项都不进 contract / surfaces；将来以契约的次版本加入 `tentative` 写入状态与 `sync_rejected` 事项类型（architecture §6：加枚举值升次版本，调用方必须容忍未知值）。下面写的是届时的语义：
>
> - **写入**：本地节点在线时同步转发主节点，回执是主节点的结果；离线时回执 `tentative`（已在本机记下，尚未被主节点接受）。
> - **`sync_rejected` 事项**：离线写入被主节点降为候选或因违反 schema 被拒时生成；处理方式 `rewrite`（返回原写入与当前 schema，调用方按当前 schema 重写，带上该事项作来源）/ `discard`。

自己写一个轻量的 HTTP 日志同步协议，传输层兼容 Durable Streams（MIT，草案），不引入完整同步引擎
（Electric / PowerSync / Zero 都默认服务端为权威，Turso 会悄悄覆盖，CRDT 会自动选赢家，都不符合 saveslot 的冲突规则）。

| 标识 | 含义 |
|---|---|
| `node_id` | 每个节点安装时生成 |
| `event_id = (origin_node_id, origin_seq)` | 事件的永久身份，离线写入时生成；**不用链哈希当身份**（主节点接受后会按自己的位置重新串链） |
| `log_pos` | 只由主节点分配的位置（每用户单调） |
| `primary_epoch` | 每次切换主节点加 1，让旧主节点失效 |

- **下行**（主节点 → 副本）：副本带 `last_log_pos` 拉取，每批末尾带检查点（位置、滚动校验和、epoch），整批原子应用，校验和不符就重同步。
- **上行**（离线节点 → 主节点）：按 `origin_seq` 顺序批量提交；主节点对每个来源节点持久化 `last_origin_seq`（与日志追加同事务），
  已处理的返回原结果（幂等）、跳号的要求从期望处重发、epoch 过期的告知新主节点。
- **主节点处理离线事件**：源数据一律接收，只有命中墓碑才拒；对业务表的写入按 `log_pos` 顺序重新核对预期版本，
  对不上就按冲突规则降为候选版本或待确认，违反 schema 的拒绝（源数据保留、标为待重新抽取）；处理结果作为事件同步回原节点。
- **离线节点本地**：分已确认层与暂定层，暂定状态在读取结果里显式标出（`tentative: true`）；重连时**先拉取（至少到最新墓碑）再推送**；
  本地暂定事件命中新墓碑就在本地丢弃。
- **切换主节点**：日志里的一条签名控制事件，epoch 加 1；计划外接管时，旧主节点回来后的写入按 `event_id` 当离线写入重新提交，不丢数据。
- **导出 = 从位置 0 开始的一次完整下行同步**（含墓碑），"可退出"与"复制"同一条代码路径。
- 第一版全量复制；部分复制按 slot 做，墓碑与控制事件始终全量复制。将来部分复制时事件头仍全量复制，所以**事件头只含不透明 ID**
  （表、行、slot 的可读名称放在内容里）。
- **读取记录第一版不随同步复制**：纠错影响查询只覆盖主节点上的读取；离线节点读到的暂定值若被主节点拒绝，只在该节点本地标注。
- 节点间同步用节点身份（用户签发的设备凭证），与"连接实例身份"（Agent 对节点）是两个层级。

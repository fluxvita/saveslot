## schema 版本演进（续）

原则、改动分类与 schema 文档格式见 [`07-schema-evolution.md`](07-schema-evolution.md)。

### 状态机：读永远不停

```
草稿 → 已编译 → 待确认 → 迁移中 → 切换 → 当前 → 已退役
  │       │        │         │
  └ 编译失败 ┘  放弃 / 被取代  失败回滚 / 放弃迁移（旧版仍是当前，什么都没变）
```

| 状态 | 读 | 写 | 说明 |
|---|---|---|---|
| 草稿 / 已编译 / 待确认 | 旧版照常 | 旧版照常 | 新版只是提议；不过期，新提交的草稿取代尚未确认的旧草稿。编译与影响预览是同一步：`schema_draft` 的一次调用同时返回编译结果与预览，没有单独的"已预览"状态 |
| 迁移中 | 旧版照常 | 旧版照常，写入同时进日志；带旧 `sv` 的写入在写入事务里先对新版求值转换表达式，失败即拒绝（见下；第一版没有转换表达式，这一步不发生） | 后台从日志构建新版的基础表与派生缓存，并持续追上期间的新写入。没有 `migration_diff` 的迁移构建完即切换，不等人；有 `migration_diff` 的迁移（抽取作业，第一版不做）**出口三个**：差异全部处理完 → 切换；`keep_rest_and_switch`（未处理的差异按逐行拒绝处理）→ 切换；`abandon` → 放弃迁移，旧版仍是当前（见「抽取作业」） |
| 切换 | 不停 | 暂停极短时间 | 一个事务内追完最后一段日志，把"当前版本"指向新版 |
| 当前 | 新版 | 新版；带旧版本号、且写到不兼容变化字段的写入被拒 | 经 `restructure_unused` 生效的改动视为这张表的全部字段都不兼容（见「原则」） |
| 已退役 | 对外不可见 | 不可写 | 内部保留，供按时刻读 |

状态机的每次状态变化（草稿提交、编译结果、确认 / 放弃 / 被取代、迁移开始、切换、失败）都是日志事件（"放弃迁移"随抽取作业后续：第一版的确定性迁移没有人工放弃的出口，不产生这种事件）；编译后的定义记在事件里，重放时不重新编译。"迁移结果"事件只在抽取作业里产生（翻译结果是模型的输出，不可重放，必须记下）；确定性迁移没有这种事件。

- **编译失败不产生事件**，与被拒的写入一样是一次报错。草稿里出现第一版不支持的改动或键（`reextract`、`derived` 改 `base`、写入过的表上改时间类型等，清单见「改动分类」）时整份报 `not_in_this_version`；只在从未被写入的表上才做的改动用在写入过的表上时，`reason` 是 `table_written`。
- **确认时重新求值转换表达式**（第一版没有转换表达式：`migrate` 与表达式形式的 `backfill` 报 `not_in_this_version`，见 [07-scope-v1](../07-scope-v1.md)；本条是完整设计）：草稿提交时在现有数据上试跑 `migrate` / `backfill`；等确认期间旧版照常可写，新写入的值可能让表达式求值失败（如 `text` 转数）。确认（`resolve`）时在同一个事务里，对试跑之后的新写入重新求值；有失败的，`resolve` 报 `draft_outdated`（`reason`：`migrate_failed`），不产生任何事件，事项保持未决。与 `table_written` 同一种处理（见「改动分类」）：调用方改好表达式提交新草稿取代它，或先改掉那几条值再确认。
- **迁移中带旧 `sv` 的写入**（转换表达式的部分同上，第一版不发生）：确认之后、切换之前，旧版照常可写，但这些写入之后要转换进新版。所以带旧 `sv` 的写入在它自己的事务里就对新版求值 `migrate` / `backfill`；有失败的，整次请求报 `validation_failed`（`migrate_failed`，`path` 指到那个 op 的那个字段），提示按新版本重读再写。不让切换因此失败或回滚：迁移已经确认，不能被后来的一条写入卡住；那个值在新版里本来就放不下，当场拒绝比切换时丢掉它诚实。
- **同一套 schema 同时只有一个变更在进行。** 第二个草稿要等前一个完成，基于新版重新起草（类似代码合并冲突）。迁移中提交新草稿被拒，拒绝时给出结束当前迁移的两个处理方式（`keep_rest_and_switch`、`abandon`），不让一个停在半路的迁移永远挡住后续变更；没有 `migration_diff` 的迁移不等人，拒绝时给出进度（见「抽取作业」）。
- **重新抽取类迁移可能持续很久**（还要人确认差异），但旧版一直可读可写，用户无感；期间新进来的源数据由追平步骤按新版一并抽取。
- **失败是安全的。** 切换前新版只存在于后台，失败整个丢弃，旧版不受影响。

### 物理做法：按版本命名的表 + 指针切换

用 saveslot 自己的日志实现，不用 pgroll / gh-ost 一类工具（saveslot 不需要新旧版同时可写，也不需要追数据库日志）。

- **只为物理形状变了的表新建物理表**；没改动的表跨版本沿用。建不建新表看物理形状，与改动分类无关（从未被写入的表上的表一级改动除外，见下）：
  - 只改目录的变更（改名、改说明、改 `duplicate_keys` 这类不影响物理列的）：不建新表，切换只是换当前版本指针与目录。
  - 物理形状变了的表（加字段、删字段、改类型或单位、确定性转换）：新建物理表并按日志重放。加可选字段也在此列；数据量小时重放即刻完成。
  - 从未被写入的表改结构（改时间类型、`entity_key`、`granularity`、`ref`，来源键的增删换，`base` 改 `derived` 等表一级的改动）：不看物理形状变没变，一律新建物理表，但没有旧写入要转换，与新增一张表一样在切换的事务里建好；这张表不算"按日志重建"，不列入切换事件的重建清单，也没有它的核对信息。旧的物理表成为退役表，是空的。`apply` 不需要知道"从未被写入"这回事：重放到切换事件时，照编译后的定义建表即可；这个判断只在编译与确认时做，结果体现为"这次切换没有要转换的写入"。
  物理表名**永不对外暴露**，受限 SQL 的报错信息里也不能出现。
- 退役表第一版一直保留，按时刻读切换之前的时刻就查它：时刻先按已有规则换成操作位置 S（`seq`），覆盖 S 的版本是切换所在的操作不晚于 S 的最后一版（一次操作是原子的：截至 S 要么整个看得到切换那次操作、要么整个看不到，它里面的写入与切换不能分在两边），用那一版的编译后定义取表与字段、用它的物理表答，值与单位按那一版（没改动的表跨版本共用同一张物理表，那一版定义里的 `physical.table` 指向它）。`schema_versions` 为此记每个版本的切换位置（`schema.switched` 的 `seq`，由它得出所在的操作）。清理与清理之后从日志重放的后备随后续一起做。**无论保留多久，清理都写成一条日志事件**（`system`），
  这样"从空存储重放 = 线上状态"在退役表上也成立。隐私删除对退役表与当前表一样生效。
- **每个 schema 版本里改动过的基础表、派生表都是独立物理表**，名字含表 ID 与版本号（如 `t_<table_id>_v<n>`），**建好后永不改名**
  （PostgreSQL 视图按表的内部 ID 绑定，交换表名走不通）。物理列名用字段 ID（`f_<field_id>`），改名只改目录。
- 每个 slot 一行**当前版本指针**；所有读写经 saveslot 的 API / 受限 SQL 编译器，把逻辑表名解析到指针指向的物理表。
- **迁移中**：建新版表与索引 → 从日志回放（小数据量可全量重放，顺带验证"日志可重建状态"）→ 分小批短事务循环追平，
  新版派生表同步按新规则维护 → 剩余量低于阈值再进入切换。
  **构建中的新版表是 (c) 类状态**（K3 的例外）：可丢弃、可从日志重建，分批构建不对应新事件；在切换事件处转为 (b)——重放时 `apply` 处理到切换事件才建好新版表。
  - **确定性转换不记逐行结果**：转换表达式是受限 SQL，与派生规则用同一套白名单（见 [「受限 SQL」](11-restricted-sql.md)），结果确定；它随编译后的定义记在"编译结果"事件里。重放时 `apply` 处理到切换事件，按编译后的定义把旧版的每条写入转换成新版形状（逐项转换，状态、区间、来源不变；只有带值的项求值，空值、`no_value`、`uncovered` 的项原样带过去；没有旧值的位置只有常量形式的 `backfill` 给值，且只补存在的行（未撤销的行、实体存在的区间；已撤销的行与撤销留下的无值区间不补），补值的位置记在切换事件里、重放照记录（之后的删除不追补），新增必填字段、可选改必填一律必须给常量（不看有没有行），常量与表达式两种形式不能同时给；第一版转换表达式只引用本字段，规则见「schema 演进 · 确定性转换怎么重放」）。这与派生表的做法一致：计算结果不写进日志，按规则重算。
  - **切换事件记校验信息**：内容里记每张新版表的行数与结果校验和，重放时有就核对、不用它来生成。它由用户内容算出，是内容；输入被删除后清除，之后跳过核对。重放时转换结果若与当时不同（后端差异、内核缺陷），由此发现。
  - **按改动的字段回放**：写入事件里只记那次请求涉及的字段（旧版形状）；构建新版时逐条带过去（经确定性转换或翻译结果），新版独有的字段不会被旧写入覆盖。
  - **删除与撤回事件同样经转换重放**：它们的逐字段结果与基础写入一样经确定性转换进新版表。切换之前就已确认的删除不需要特殊处理——被删内容在日志里已是"已由 #n 移除"，转换时跳过；删除事件里记下的"删除后的样子"经转换成为新版里那一行的当前值。
  - **迁移进行中确认的删除**：删除事件照常只算当前版本的结果。构建中的新版表对受影响的行整行丢弃、按日志重建（此时被删内容已读不到）；到期物理删除时如果构建还没结束，同样清掉构建中的表里这些行的历史内容。抽取作业里受影响的工作项退回重做（见「抽取作业」；第一版不做抽取）。
  - 有抽取作业时，切换事件里写明还没抽完的（行, 字段）列表，`apply` 据此设 `pending_extraction`，不读作业进度；迁移结果事件里包括跳过的工作项及原因码（`no_content` / `ambiguous`）。
  - **重新抽取的翻译必须给全**：一个工作项涉及的每条写入，翻译都要给出该簇涉及的全部新字段的值（可以是空值，但要显式给）；缺了报校验错误。
    否则一条只碰过旧字段的写入，翻译时漏写某个新字段，新字段就会停在更早的值上。
  - **已撤销的行照常翻译**（历史要能按时刻读），但不进差异清单——它们对当前状态没有影响。
- **切换（一个事务）**：不设 `lock_timeout`，也不自动重试——构建的批与切换事务都排在租户唯一的写者队列里，与用户写入互相排队，没有别的写者可争；读不拿锁，建新版表不挡读。追完最后一段；校验；改指针；记一条 schema 切换事件。
  写入事务开头核对指针上的版本——带旧版本号的写入在这里被拒；读完全不受影响。
- **批与阈值**：每批按日志事件数（初值 500 条）一个短事务，批与批之间排队的写入照常进入；剩余不超过一批时进入切换；连续 20 批剩余量没有减少（写入快过重放）就直接切换，接受那一次更长的暂停——正确性不依赖阈值，切换事务自己追完最后一段。三个数是内核常量、测试可注入，是占位，等 schema 重建的容量实验。构建中途进程退出：下次打开发现"迁移中"，丢弃孤儿新版表、从头构建；校验失败（`verify_failed`）与构建失败（`build_failed`）都不自动重试，旧版仍是当前，调用方可以再提交同一份草稿。
- **读时计算的派生表也有物理表**（空的），所有读取入口用同一个判断绕开它；`change_rule` 在读时计算与缓存之间切换与任何规则改动同一条路：新版照常建一张派生物理表，缓存改读时计算时新表为空，读时计算改缓存时新表与任何规则改动一样随切换按新定义重建（派生表不列入 `rebuilt_tables`，见 [`../09-event-format.md`](../09-event-format.md) §5.5）。判据是规则的时间依赖：`time_dependency` 为 `now` 的派生表读时计算。
- **回滚**：切换前丢弃新表（先改状态再删，崩溃后可识别孤儿表）；切换后只做前向迁移。
- 托管下表数量随"用户 × 表 × 版本"增长，布局需压测（见 open-questions）。

### 抽取作业

> **抽取作业不进第一版**，是第一版之后的第一个增量（[`../07-scope-v1.md`](../07-scope-v1.md)）；事件格式里为它留了位置。本节是完整设计。

**抽取作业只服务 schema 变更**：重新抽取类迁移与新字段补抽（字段上声明了 `reextract`）。先由用户的 Agent 执行；契约不区分执行方，将来用户授权模型调用后调用模型的后台执行方（worker）直接接入（positioning「后续规划」）。
领取与提交的形状见 contract「抽取作业」；下面是内核规则的权威定义。

**流程**：

1. 草稿编译后，预览给出"需重新抽取 N 条源数据"。
2. `schema_change` 事项被确认后进入迁移中：确定性部分由 saveslot 自动完成，同时生成抽取作业；结果要进差异清单的迁移（从旧字段抽、同一字段重抽，见下）**迁移开始时就生成一个 `migration_diff` 事项**，差异清单随抽取增长。它不因迁移期间的普通写入被取代、只在迁移结束时关闭；各处理方式绑定什么见「待处理事项 · 事项 ID 与事项版本」。
3. 任何有权限的调用方都能领取、提交，做不完也没关系：旧版照常可读可写，之后接着做。
4. 抽取完成、差异全部处理后切换到新版；也可以用 `keep_rest_and_switch` 提前切换，或用 `abandon` 放弃迁移（见「待处理事项 · 各处理方式的执行语义」）。
   **没有 `migration_diff` 的迁移**（只有确定性转换，或确定性转换加纯补抽）不需要人处理差异：确定性部分由 saveslot 完成后即切换，**纯补抽不挡切换**（没补完的按下方切换规则转为普通补抽作业），所以不会停在半路等人；它们没有人工的放弃出口，失败时整体回滚。
5. "迁移中"不过期；长期没有进展只在提示里升级。

**什么进差异清单**：

- **从旧字段抽出新字段**（`reextract.from` 非空，如把 `feeling` 拆成 `effort` + `soreness`）：每一行的"旧值 → 新值"都进差异清单——旧字段可能是用户原话、被纠正过，不能被推断值悄悄取代。
  清单里旧值来源级别为"用户明确"或被纠正过的排在前面，其余便于批量接受。
- **同一字段重抽**：与已确认值不同的进差异清单。
- **纯补抽**（`from` 为空）：新字段原本为空，不进差异清单。
- 以 `ambiguous` 跳过的项进差异清单，可在处理时给值，或切换后再写。
- 已撤销的行照常出工作项、照常翻译（按时刻读要用），但不进差异清单。

**迁移期间与切换**：

- 迁移中触及 `from` 字段的新写入**自动追加工作项**（回执提示，作业总数随之增长）；该行已列出的差异条目作废，重新抽取后重新列出（见「待处理事项 · 不过期」）。
- 切换时若仍有未翻译的项（`keep_rest_and_switch`，或纯补抽），新字段先留空并标 `pending_extraction`，切换照常进行，剩余项转为切换后的补抽作业——不让最后几条挡住切换。原作业结束、未交的租约作废（之后提交报 `lease_expired`，原因 `migration_switched`），未交的工作项回到新作业的池里。
  **剩余项仍按原迁移的差异规则**：本该进差异清单的项（从旧字段抽、同一字段重抽），抽出的结果进一个切换后新生成的 `migration_diff`（处理方式只有 `accept_all` / 逐行；剩余项抽完、差异全部处理后关闭），抽出之前该处为空、标 `pending_extraction`，抽出之后标 `awaiting`、等人确认，不直接生效；只有纯补抽的项直接生效（新字段原本为空）。
- 切换时，涉及被改动字段的未决事项一律标"已被取代"（原因：schema 已切换），由发起方按新版重写；其余事项照常保留。

**工作项：按来源簇翻译原写入**：

- **重新抽取不是把源数据从头再抽一遍，而是把碰过要重抽字段的那些写入，逐条翻译成新版的形状，再由 saveslot 按原顺序重放。** 纠错、撤销、状态类表的生效区间都按原意保留，`row_id` / `entity_id` 不变。
- **一个工作项 = 一个来源簇**：同一行（或同一实体）上碰过要重抽字段的全部写入，按 `seq` 排序，附各自的源数据原文与写入时的旧值。行与行之间独立、可并行。
- 每条翻译只能给新值，意图、行、生效区间沿用原写入，翻译方改不了。
- **每条翻译都要给出该簇涉及的全部新字段**（没有就显式给空值）；缺字段报校验错误（见「物理做法」）。
- 工作项只附与 `reextract.from` 字段有关的证据（各写入里这些字段引用的证据段）。翻译结果是内容，按工作项 × 字段存放，来源 = 工作项附带的全部原文；附带的任一原文被隐私删除，该工作项的翻译结果整体清除（见「删除 · 由源数据派生出的内容」）。
- **因删除补抽**：翻译被清除后，剩余原文里还有内容的（行, 字段）由删除事件列出、设 `pending_extraction`，saveslot 为它们开补抽作业（工作项只带剩余原文）；没有剩余原文的直接置空。迁移进行中发生删除时，受影响的工作项（含已交、未切换的翻译）退回池里重做。
- 工作项在领取时由日志现拼、不落盘；租约期间某条写入已被删除时，对它的翻译拒收，并从作业里扣掉这一项。
- **边界**：回退写入由 saveslot 确定性处理（取被回退到的那个版本的翻译结果），不进工作项；源数据已被"删除证据"的写入，工作项里只有旧值、没有原文（原因 `evidence_deleted`）；状态类表的补抽按生效段出工作项（每段可能取不同的值）。
- **补抽**（`from` 为空）：工作项是一行（或一段），附插入它、修改它的源数据原文，产出新字段的值。
- 提交的每个工作项过一遍写入的确定性校验；跳过只有 `no_content` / `ambiguous` 两个原因码。结果按"Agent 推断"级别记为日志事件（记抽取方的连接实例与自报的模型名，只作参考），重放时用记下的结果。
- 待定：来源簇过大（一个导入文件产生上千行、之后又分别被纠正）时按行拆分、在每个工作项里附共享源数据的相关片段，拆分规则待定（open-questions「接口的数值与细则」）。

### 官方 schema 与用户 schema

下面的扩展与映射是结构定下之后的做法，第一版不实现；第一版只留位（本节第二条）。

- **扩展**：用户在官方 schema 上加字段，放在自己的命名空间里，字段 ID 不冲突。官方向后兼容的小版本升级自动跟进；大版本升级走迁移与预览。
- **第一版只留位**：编译后的定义里可选键 `extends`（`{id, version, hash}`，只记标识与内容哈希）与表、字段上的 `official`（`{id}`，官方给的稳定句柄；字段 ID 仍由 saveslot 分配，上层工具按 `official.id` 找字段）；`compatibility` 暂不留键；草稿里出现这些键报 `not_in_this_version`（事件格式的留位见 [`../09-event-format.md`](../09-event-format.md) §10）。
- **映射**：用户完全按自己的结构建表时，写一条 L1 规则把自己的数据投影成官方 schema 的形状；为官方 schema 写的插件读这张视图即可。
  "兼容官方"不另起机制，就是一张派生视图：只读、可重算、来源完整。

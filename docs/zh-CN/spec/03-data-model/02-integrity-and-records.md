## 完整性与溯源

**目标是"能溯源 + 防误操作"，不是防篡改**：每项状态都能追到日志里的事件与源数据；事件缺失、乱序、事件头被意外改动、内容损坏、绕过 `apply` 的改动都能被发现。
对能写存储的一方（含运营方）**不提供**防篡改证明（见 [`../02-architecture.md`](../02-architecture.md) §10）。

| 项 | 规则 |
|---|---|
| 事件头 | 只有通用字段：`seq`、事件格式版本、类型、actor（主体 ID）、记录时刻、`prev_hash`、所属操作的操作号（头事件没有）、slot ID；`system` 的头事件另带 `trigger`（哪个后台任务，固定枚举）；创世、恢复与导入事件另带节点 ID 与恢复或导入信息。完整定义见 [`../09-event-format.md`](../09-event-format.md) 第 2 节。**不放任何由用户内容算出的值**——请求键、分组键、内容哈希都不放。表、行或实体、意图、被引用事件的 `seq` 也不在事件头里，而在内容区的**元数据块**里（只含不透明 ID、枚举、序号与下标、版本号、布尔值、入口时刻；不进链；第一版不随删除清除，见「删除之后」） |
| 链 | **只串事件头**：`prev_hash` = 上一条事件头编码字节的 SHA-256（小写十六进制）；创世事件的 `prev_hash` 为 64 个 `0` |
| 内容 | 与事件头分开存放。一个事件的内容是一组**内容块**，每块按（事件 `seq`，`path`）寻址，各配一个校验和（SHA-256，对块内容的字节求）。校验和只用于发现存储损坏，随内容一起删，**不是对内容的承诺**：不给内容块配盐、密钥或链上承诺 |
| 删除 | 直接**物理删除内容块**。块是删除的最小单位，整块删除，没有块内的部分删除；字段、条目、整条三种粒度靠块切得够细来满足。被删的块保留位置、清空内容与校验和、记下墓碑的 `seq`（"已由 #n 移除"；标记里没有内容，也没有由内容算出的值）。事件头保留 |
| 防误操作 | 只有内核能写（K3；数据库层只给 saveslot 的服务账号写权限）；日志只追加；对账（从日志重放 = 线上状态；第一版由用户会话手动触发全量对拍）；事件头链校验；内容校验和 |

**内容块的位置。** `path` 是若干段用 `/` 连接的 ASCII 字符串，段只能是三种：该事件类型的固定词（如 `fields`、`sources`、`target`、`request_key`、`text`、`candidates`）、不透明 ID（字段 ID、表 ID）、十进制下标。例：`fields/f3/0`（这次写入对 3 号字段的第 0 项贡献）、`sources/f3/0`（这一项的来源）、`candidates/1`（事项的第 1 个候选）、`text`（一段证据的原文）。
**`path` 里不出现任何用户内容或由用户内容算出的值**（字段用 ID 不用名字），所以位置可以写进元数据块里的引用、墓碑的位置列表和删除登记。每种事件类型的 `path` 词表是事件格式的一部分，随事件格式版本只增不改。

**事件的身份。** 第一版事件头里没有单独的事件 ID。创世事件、"恢复"事件与"导入"事件（`tenant.imported`）的事件头各带一个随机生成的节点 ID；一条事件的身份 =（它之前最近一条创世、恢复或导入事件的节点 ID，它的 `seq`）。恢复时换一个节点 ID，是因为恢复后 `seq` 可能与丢失的那段时间线重号；导入时换一个，是因为导入之后同一份导出在源头与目标处各自延续，两边的 `seq` 会重号。**当前恢复次数**取最近一条恢复或导入事件里的值（导入时加 1，见「删除 · 删除登记」）。多节点时（后续），别的节点产生的事件在事件头里加一个可选的来源字段；缺省字段不编码，旧事件的字节不变。

| 能发现 | 靠什么 |
|---|---|
| 事件缺失、乱序、事件头被意外改动 | 事件头链 |
| 内容存储损坏（写坏、截断、丢失） | 内容校验和；没有移除标记却找不到内容，算不符；事件类型必有的块（事件格式里标"总在"的）整行不见，同样算不符 |
| 物化状态与日志不一致（绕过 `apply` 改业务表、`apply` 自身的缺陷） | 对账：从日志重放，与线上逐表比对 |

**不承诺**：

- 对能写存储的一方（含运营方）防篡改：改了内容并重算校验和、或重算整条事件头链，`verify` 照样通过。
- 给第三方的证明（"某个版本确实在日志里""历史没被改写"）。
- 删除前的内容是什么：被删位置不留任何由内容算出的值，删除后无从证明、也无从拿猜测值比对。
- 可选的内容块整行丢失：事件头里不记一条事件有哪些块，可选块连同它的位置一起不见了，`verify` 发现不了。

签名检查点、Merkle 树、链上内容承诺**放到后续规划、按产品需要再做**（positioning「后续规划」）；将来要做时通过**新的事件格式版本**加入，旧事件不追加。

- **由内容算出的值、调用方自报的文字都是内容**：请求键、显式幂等键与它的请求内容指纹、调用方自报的任务标识（`task`）、派生行的分组键、疑似重复的判定结果（比中了哪些行）、确认记录里所确认内容的哈希、派生写入的结果校验和、切换事件里新版表的校验和——一律放在内容区、随内容删除，不进事件头。请求键、幂等键与 `task` 的来源是这次操作的全部证据：其中任何一条被隐私删除，它们随之删除（见「删除 · 由源数据派生出的内容」）。否则删除后仍可拿猜测的原话算一遍来比对。
- **读取记录不存内容哈希**：只记读到的版本（`seq`），查询条件只记不含用户值的结构指纹（见「读取记录」）。
- **编码确定**：事件头与内容块都用 RFC 8785（JCS）编码成 UTF-8 文本存放，编码后的文本是权威；缺省字段不编码，加字段不改变旧事件的字节。十进制数（金额、数量）一律写成字符串——JCS 按 JavaScript 的数字规则序列化，会损失精度；`seq`、下标这类小整数用数字。存成文本列，不用会改键序与数字写法的二进制 JSON 类型。
- 哈希与校验和在 TS 应用层计算，PGlite 与原生 PostgreSQL 一致；每租户写入串行化，事件头、内容与业务写入**同一事务提交**。
- **只有主节点的链是权威链**（多节点，第一版不实现）：离线节点的暂定事件不进权威链，被主节点接受、分配 `seq` 后才串进去；离线节点本地可以有自己的暂定串链，只作本地参考。
- **验证**：`verify` 报"日志共 T 条事件，事件头链完整（或：自第 k 条起断裂）；内容校验和 N 处不符；索引列 P 处与事件头不符；M 处已按删除移除"，并列出每处不符的位置。
  "已移除"（有移除标记，正常）与"不符"（损坏）分开报。移除标记必须指向一条墓碑（`deletion.executed`），且那条墓碑的位置列表里列了这一块，否则算不符。事件类型必有的块整行不见，在那个位置算不符；缺的是元数据块 `target` 时，这条事件的索引列不再核对。索引列（事件表里由事件头与 `target` 块拆出的列）与事件头不符时单列，不算链断裂：坏的是派生的索引，照事件头与 `target` 块重算即可修复；链断裂说明事件头本身出了问题。存下的事件头哈希与按事件头重算的不符，算这一条处断裂。

## 写入与读取的记录

例子见讲解 [`../../guide/02-walkthrough.md`](../../guide/02-walkthrough.md)：每一步都列出了追加的日志事件（与本目录不一致处以本目录为准）。

### 写日志：change_log + change_sources

- **change_log**：每次写入在日志里记三种事件——
  - **逻辑写入头**：**每次产生事件的写入请求一条**，不论改了几行，是这次操作的头事件。记**原始传参**（各 op 里不是无操作的字段的原始值、无操作字段的 ID 列表、区间参数的原始写法、各 op 声明的前提，见「写入的前提」）、请求里 op 的总数、请求键或显式幂等键与内容指纹、自报的任务标识、`sv`（以及它是显式带的还是兜底取得的）、判定时用的"现在"与 slot 时区下的"今天"、各 op 所见的 `ver`（以及它是显式带的、兜底取得的、本请求前面的 op 新建的，还是按来源键取的同步基线位置；按来源键的 op 另记逐字段的基线位置，见「按来源键写入」）、规则版本与策略版本。"是否追溯"不单独记：它由记下的"现在""今天"与解析结果比较得出。它的 `seq` 是这次写入的**操作号**。只含按来源键 op 的请求不记请求键；全部 op 都没变或被跳过的按来源键请求不产生任何事件，也就没有逻辑写入头。
  - **基础写入**（Agent / 调用方写基础表）：每个 op 对每个受影响的行 / 实体一条。**只记本次请求涉及、且不是无操作的字段**。一个字段的贡献是**按区间排好的若干项**（事件类表与无时间表恒为一项）：每项各有值、**解析后的生效区间**（状态类表；单独成块，并记下解析时用到的别的贡献，见「删除 · 由别的贡献求得的内容」）、来源、**生效状态**与写入时的判定结果（见下）。一个字段有多项的情形：`undo`、回到合并基要写回几段不同的旧值；佐证的区间里一部分仍同值、一部分已被别人改掉。**不记写入前的值，也不记写入后的整行**：写入前的值是更早事件的副本，每多一份副本隐私删除就多一处要清；写入后的状态由"之前的状态 + 本事件里生效的字段"确定地得出，按时刻读走版本表。状态类表一个 op 对一个实体只记一条事件，物理段由 `apply` 在逐项区间赋值之后规范化得出（不含判定）。
  - **派生写入**（规则引擎刷新派生缓存）：只记规则版本、派生行的 `partition_id`、读取时的日志位置，内容里记分组键值与结果校验和，**不存写入前后的值**
    ——随时可由基础数据 + 规则重算。
- **一次写入内各事件的先后**：逻辑写入头 → 源数据（每段证据一条；没带证据时每个在事件里留下了东西的 op 一条）→ 逐个 op（按请求里的顺序）的基础写入与它引出的事项事件 → 前提变化（`premise.changed`，有变化时一条，见「写入的前提」）→ 全部 op 之后的派生写入。它们在同一事务里提交，`seq` 连续（[`../09-event-format.md`](../09-event-format.md) 4.2）。
- **逐项的生效状态**：`applied`（生效）、`candidate`（成为冲突候选）、`awaiting`（高影响，等确认）、`corroborated`（同值且显式指了证据：只追加来源）。`apply` 只把 `applied` 的项落进业务表与版本表，把 `corroborated` 的写进来源表；其余只留在日志里，供 `timeline`、事项与删除重放使用。
- **无操作的字段**（同值且没指证据）不是贡献：基础写入事件里没有它，日志里任何地方都不留它的值，只在逻辑写入头里列出字段 ID（供审计与幂等重放的回执给出 `noop`）。之后的采纳、确认是一次由 `resolve` 触发的新写入，有自己的头事件与操作号，值来源是对原候选 / 提议贡献的引用。
- **全部字段都是无操作的请求**：照常存源数据、记逻辑写入头（含请求键，重发按幂等重放），不记基础写入，`ver` 不变。证据是资产，不因为没改值就丢掉。例外是按来源键的 op：没变（`unchanged`）与被跳过（`skipped`）的不进任何事件，全部 op 都是这两种的请求不追加任何事件（见「按来源键写入」）。前提的重申与清除也没有基础写入，事件构成与这里相同，头事件里多了声明。`undo` 的各部分全部被跳过时不同：照常记一条基础写入，里面没有写回的项，只有回退记录（回掉哪几次操作在哪些目标上的改动要留下，之后盖住它们的写入被隐私删除时，这次撤回才能在重放里生效）；`ver` 不变。
- **写入时的判定结果**记进基础写入事件，重放不重算：疑似重复（隐私删除时也不重算，见「疑似重复」）；字面命中，按"字段的每一项 × 该项引用的每段证据"记命中 / 未命中 / 不适用，并记核对器版本（规则见「来源级别」）。
- **解析结果以最近一次给出的为准**：默认终点、纠错的默认区间、首次创建标记是机械判定。隐私删除的重放让它们变了时，新的结果记在那次删除事件里；之后的 `undo`、冲突判据、对这项贡献的引用都按最新的（见「删除 · 结果怎么落进日志」）。
- **change_sources**：这次写入由什么引起，多对多，两种来源：
  - 源数据（用户说的一句话、一次工具结果……）——基础写入的来源，由写入方随写入提交；
  - 上游写入——派生写入的来源，由规则引擎按实际读到的输入自动记录。这一种是级联能成立的关键。
- 物理上是两张表：`base_sources`（基础写入 → 源数据，带字段列表与来源种类：值来源 / 操作来源 / 区间来源，见「删除 · 来源」）与 `derived_reads`（派生写入 → 规则版本、基础表、`partition_id`、日志位置；不存分组键值）。
  **从某个基础版本找"哪些派生写入用过它"**：取该版本改前、改后值所落的分区（按分组键值经映射得到 `partition_id`），在 `derived_reads` 里找 `partition_id` 匹配、
  且该基础版本的有效区间覆盖读集日志位置的派生写入；再沿派生依赖往下游重复。
- 同一行的上一版本由 change_log 按行排序即可得到，不另记进 change_sources。
- 业务表写入、change_log、change_sources **在同一个事务里提交**。
- **记录时间 = 日志的序号**（每租户单调）。每租户写入串行化（`pg_advisory_xact_lock`），序号即提交顺序，日志复制时原样带走。
  - **对外一律用操作号**：一次写入、一次由 `resolve` 触发的写入、一次删除确认、一次撤回各有一条头事件，它的 `seq` 是这次操作的操作号。回执的 `seq`、`ver` 里的序号、`timeline` 的 #n、`undo` 的 n、`changes` 的 `since`（不含）/ `until`（含）、版本表的记录时间区间都用它；源数据事件与各行基础写入事件的 `seq` 不对外。
  - **`as_of: S`** = 操作号不大于 S 的全部操作都已完整生效时的状态；S 落在一次操作的中间等同于落在它的操作号上，所以读不到写了一半的状态。给的是时刻时，按记录时刻换成操作号；未来的时刻等于最新。
  - **记录时刻**另存，由内核保证单调：= max(调用上下文的 `now`，上一条事件的记录时刻)；不用 `NOW()`（取的是事务开始时间，与提交顺序可能不一致）。这次操作里与"现在"有关的判断都用它（architecture §7「记录时刻」）。
- **重放用记下的结果**：一次写入可能改多行、拆多段（如回溯修改拆分生效区间），重放时 `apply` 照事件里的解析结果做，不重跑拆段算法。
- 这是应用层日志，不是 PostgreSQL 的 WAL：WAL 是物理日志，不知道"源数据"。
- **按时刻读由 change_log 程序化实现**：原理上把日志重放到某个位置即可得到当时的状态；为了查询快，
  再从 change_log 维护一张**版本表**——按单元格记（某一行或实体的某个字段、在某段业务时间上的一个值各一条），标上有效区间"从哪个操作号起、到哪个操作号止"，
  按时刻查询只取区间覆盖该时刻的版本（即 SQL:2011 的系统版本表，SQL Server、MariaDB 原生支持）。
  版本表存该版本的字段值（不存指向内容的引用），按时刻读是一条普通查询；物理删除时版本表里对应的值一并清掉。派生数据不存历史，按那一刻的基础数据重算。
  版本区间第一版就存（数据结构以后难补）。**对外开放范围**：业务时间查询（`valid_at` / `valid_during`）第一版对外开放；
  按时刻读（`as_of`）只在审计、还原类接口开放。

### 读取记录：read_log

用处：

1. **纠错影响**：数据被纠正后，找出哪些任务读到了基于错误数据的值（冲突处理第 5 条）。
   见下方「纠错影响查询」。
2. **按时刻还原**：某次任务当时看到的是哪个版本。
3. **安全审计**：哪个连接实例读了哪些数据。

字段：read_id、时间、actor（连接实例）、任务 / 会话标识（调用方提供，可空）、读了什么（数据目录的读取记 slot、表与读到的 `sv`；数据读取记表、行或派生行的 `partition_id`、源数据 ID；查询条件只记**不含用户值的结构指纹**——字面量换成占位符、名字换成 ID、去掉别名与注释之后的规范化文本，直接存文本不存哈希，算法见「读取 · 读取记录里记什么形状」）、
拿到的版本（每行读到的版本 `seq`，**不记内容哈希**）、**所见状态的位置**（这次读取看到的是哪个操作号时的状态：首页与 `timeline` 是读取当时的最新操作号；`query` 与各调用的后续页是首页的操作号；`history` 的 `as_of` 是它的记录点；`changes` 是它的 `until`）、**是否按记录时刻读的历史**（`as_of` 的读取：读到的是历史版本，不算读到，见 contract §2）、**业务时间条件**（如"查 11-03 的预算"；不记则纠错影响查询会多报。
**不传时间的读取记为入口时刻**：状态类表默认取当前段，读的就是"现在"——`granularity: date` 时记为 slot 时区里的那一天）、
**入口取的"当前时刻"**（受限 SQL 里禁 `NOW()`，统一由入口取一次）。

**谁能查读取记录**：用户会话经 HTTP 看完整审计；Agent 经 `history`（MCP 上是 `saveslot_history`）能查到**任何连接实例**对某个目标的读取，
但只给读到的版本、时刻、连接实例名与 `task`，**不给查询条件**；目标须在这个凭证的可见范围内（见「可见范围」）。
这让"某次任务当时看到的是哪个版本"在 MCP 里可答。

**导入之后读取记录从头开始**：读取记录是本地运行状态，不在导出里。导入到空租户之后，读取审计从导入那一刻重新开始，纠错影响查询查不到导入前的读取（结果里写明覆盖到哪一刻），`ver` 与 `sv` 的兜底也从零开始（见「删除 · 删除登记」的导入一段）。

原则：

- **只记版本号，不记值，也不记由值算出的哈希。** read_log 不成为第二份数据副本；被删数据的内容不会残留在读取记录里，也无法拿猜测值比对。
- **粒度到"行的版本"。** 一次查询返回多行就记多个版本。状态类表按实体记：一个实体的几段版本相同，记一条。逐行读（`query`、`history`）每页最多 1,000 行，所以一次读取记下的版本数有上限。
- **读得太多时改记表级记录。** 受限 SQL 的聚合与关联可以读很多行而只返回一行，逐行记的代价会随数据量涨。规则：一次读取在**某一张基础表**上读到的行版本数（不少于实际读到的：该表所在查询层通过了 FROM 与 WHERE 的行，口径见 write-and-read「记多少条」）超过阈值（初值 1,000）时，这张表不逐行记，改记**一条表级记录**：表 ID、所见状态的位置（见上）、业务时间条件、结构指纹。没超过阈值的表仍逐行记；同一次读取涉及几张表时各自判断。表级记录不记行数——行数由用户内容决定，记下来没有用处。
- **独立于写日志。** 有自己的保留期限：第一版是租户级的一个数值，默认 180 天、下限 30 天（初值，随评测调整）；按 slot 设更长的保留期（敏感数据要求全部保留）后续再加。纠错影响查询只覆盖保留期内的读取，结果里写明覆盖到哪天；按期清理不影响写日志的事件头链。
- **读远多于写。** 记录要便宜：批量写入、按任务聚合。

### 纠错影响查询

**数据被纠正（或撤销、追溯修改、未来安排变更）后，找出哪些读取用了后来不成立的值。** change_sources 回答"哪些版本受影响"，
read_log 回答"谁读过这些版本"，两者合起来才能查出。

```
纠错源数据 R ──change_sources──> 纠错写入（例：C5）
             ──change_log 按字段回溯──> 被纠正的版本（该字段取得错值起的各版本，例：C1）
             ──change_sources 往下游递归──> 受影响集合 C（C1、C2、C4）
             ──read_log 匹配版本──> 用过错误版本的读取（r1）
```

- **分组取并集**：纠错可能让一行换了分组（如日期从 11-03 改到 11-10），受影响的派生行 = 改前、改后两个分组的并集。
- **读时计算的派生行**（依赖"今天"的规则，以及读状态类表而不带业务时间限定的规则）没有派生写入可匹配：read_log 记"规则版本 + 入口时刻 + 读取时的日志位置（最新的操作号）"，按"规则所读的基础表在该位置之后有没有受影响的版本"匹配，宁可多报。
- **受限 SQL 读取的业务时间条件**：带 `FOR VALID_TIME` 的，按改写时得知的时间条件记；不带的记入口时刻（读的是当前段）。`WHERE` 里对时间列的任意谓词不解析。事件类表上的受限 SQL 读取按"读到的版本集合"匹配，宁可多报，结果标"可能受影响"。
- **表级记录的匹配**（见「读取记录」的阈值规则）：受影响集合里只要有这张表的一个版本，它在这次读取所见状态的位置上是当时的版本（版本的记录时间区间覆盖那个位置），这次读取就算命中；状态类表上记了业务时间条件的，再要求受影响的业务时间区间与它相交。命中的结果标"可能受影响"：表级记录说不出这次读取到底有没有用到那一行，宁可多报。它不参与 `ver` 的兜底。
- **第一版只覆盖主节点上的读取**：离线节点的读取记录不同步回主节点（见「同步协议」）。
- **起点是被纠正的版本，不是纠错写入，而且按字段回溯。** 从 R 直接往下游走得到的是 C5、C6……这些纠错后的正确版本；
  要经 change_log 找到**该字段最近一次取得被纠正值的那次写入**，从它起到纠错之前的**所有版本**都是起点，再往下游走。
  同一个错值常常跨多个版本（中间有别人改了其他字段），只取"上一版"会漏掉更早、同样错的版本与读取。
  状态类表按"字段 + 业务时间区间"回溯。
  **撤销没有"错值"可回溯**：起点是该行从插入到撤销前的所有版本。
- **什么会触发。** 判据是结构性的：一次读取问过的某个（字段，业务时刻）上，值在它读到的版本与现在之间变了，它就受影响。

  事件类表、无时间表（没有业务时间区间，"之前读到的值当时对不对"只有 Agent 知道，所以看意图）：

  | 写入 | 含义 | 查不查 | `possibly_affected` 的措辞 |
  |---|---|---|---|
  | 纠错（`correct`，Agent 显式标注） | 旧值一直是错的 | 查 | "你曾读到的值已被纠正" |
  | 撤销一行（`revoke`，含由 `flagged` 事项触发的） | 这条本来就不该存在，包含它的读取都不对 | 查 | "你曾读到的值所含的一条记录已被撤销" |
  | 系统裁定（候选按冲突规则当场成为生效值；第一版不产生） | 生效值被规则改了，之前读到的旧值已不是生效值 | 查（与纠错同等） | "你曾读到的值已按冲突规则改变" |
  | `update` | 补充或修改信息，之前的读取当时是对的 | 不查 | — |

  状态类表：**任何让值发生变化的写入都查**，不看生效起点在现在之前还是之后。值实际变化的（字段，业务时间区间）与 read_log 记下的业务时间条件有交集、且该读取读到的版本早于这次写入，就标记。原因码按情形分：

  | 情形 | `reason` | 措辞 |
  |---|---|---|
  | 意图是 `correct` | `correct` | "你曾读到的值已被纠正" |
  | 变化区间里早于"现在"的部分 | `retroactive` | "你读取的业务时间上的值后来被追溯修改" |
  | 变化区间里不早于"现在"的部分 | `plan_changed` | "你读过的未来安排已变更" |

  追溯修改可能是"早就变了但晚知道"，也可能是"今天决定、往回生效"，saveslot 分不清，措辞保持中性：只有 Agent 显式标了 `correct` 才说"已纠正"。
  不传时间的读取记为入口时刻（日粒度记为当天），所以"今天早些时候读过今天的值、之后今天的值被改"按同一条判据自然命中。
- **范围是值实际变化的部分**：状态类表上只算值真的变了的业务时间区间，用同样的值覆盖的部分不算（见「时间 · 三种表」）。
- **排除纠错者自己的定位读取**：纠错之前用来找到这一行的那次读取不算受影响——那是为了纠错才读的。`ver` 对应的是版本、不是某次读取，所以精确为：
  **同一连接实例 + 同一 `task`（未带 `task` 时只看连接实例）对该目标、该版本的最近一次逐行读取**；兜底取得 `ver` 时就是兜底用的那次。
- **值恢复后撤掉标记**：之后的回退或修改让某次读取当时读到的值重新成立（如追溯改成 3000 后又回退成 5000），该读取的 `possibly_affected` 撤掉。
  按"该读取问到的字段 × 业务时间"逐一比较，全部恢复才撤；对所有写到带标记目标的写入都做这项检查，删除确认与撤回删除也做（只撤不增，见「删除之后」）。
- **一次纠错可能改多行**（如"上周的跑步都多记了 1 公里"）：每个被纠正的版本各自往下游走，结果合并。
- **每次纠错发生时增量查询，不定期全量扫描。** 只算这一次纠错的影响，结果当场存为标记（归读取审计，与 read_log 同属本地运行状态）；
  下次相关读取时随结果带出，不依赖推送。
- **与写入的前提的关系**（见下一节）：两者共用"这次操作让哪些（行，字段，业务时间区间）的值实际变了"的计算、"值恢复后撤掉标记"的比较，以及状态类表上三种原因的划分。不同在于：纠错影响查询匹配的是读取记录，标记只给读过的那个连接实例，存在本地运行状态里；前提匹配的是日志里的声明，标记给任何读取方，由日志得出。触发条件只在一处不同——事件类表、无时间表上的 `update` 不触发纠错影响查询，却让前提变了。

### 写入的前提

**一次写入可以声明它以哪些已读到的值为前提；之后前提变了，依赖它的行带上 `premise_changed`（前提已变），任何读取方都看得到。** 值不动：这一行还成不成立由 Agent 判断，saveslot 只指出前提变了。没声明前提的写入，行为与没有这个机制时完全相同。

例：Agent 读到"发布日期 12 月 1 日"那一行，据此写了三条任务；用户之后把发布日期改成 11 月 20 日。三条任务的值都没变，但它们站在一个已经变了的值上。读取记录只能告诉读过发布日期的那个连接实例"你读到的值变了"；别的 Agent 读任务列表，看到的是三条正常的任务。前提让这层关系进日志，并在任务行上指出来。

| 概念 | 指向什么 | 目标变了之后 |
|---|---|---|
| 证据 | 源数据原文：这个值出自哪句话 | 原文不会"变"，只会被隐私删除；删除沿值来源级联 |
| `ref` 字段 | 另一行的 ID，是这一行的**值** | 引用方不动；目标被撤销或删除时带 `dangling_ref`；目标的字段值变了不标 |
| 派生依赖 | 规则引用的表与列 | 同一事务重算，值自动跟上 |
| 读取记录 | 某次读取读到的版本 | 只提醒读过的那个连接实例（`possibly_affected`）；不在日志里，有保留期 |
| **前提** | saveslot 里另一行的某些字段在某个版本上的值：这一行的值是看了它之后写的 | 这一行对任何读取方带 `premise_changed`；值不动，等 Agent 处理 |

删除只沿证据传播，**不沿前提传播**（见「删除 · 两条原则」）。

**只收显式声明，不自动推断。** 哪些读到的值真的被用上了，只有 Agent 知道；把"本连接实例此前读过的全部"当作前提会多报到没有信号，而且读取记录不在日志里、粒度到不了字段、看不见会话边界。少报靠工具描述与评测（eval 10）。按读取记录推断的"污点追踪"仍是可选项（见「来源的完整性」），以后可以纯增量地加成一种更弱的标记。

**一条声明有什么**（op 上可选的 `premises`，一个数组；类型见 [`../04-contract-types.md`](../04-contract-types.md) 的 `PremiseRef`）：

| 要素 | 规则 |
|---|---|
| 目标 | 一行或一个实体，写法与写入目标相同（`row`、`entity` 或 `entity_key`，或本请求里新建行的临时名），除 `table` 外恰好给一个。没有按来源键的写法：先读到行 ID 再声明 |
| `fields` | 可选。给了，只有这些字段变了才算；不给 = 整行（任何字段，以及这一行是否存在） |
| `ver` | 应带回读到它时拿到的版本。没带时与写入目标的 `ver` 同一套兜底（`warnings` 给 `premise_ver_fallback`），无可兜底报 `read_first`。目标是本请求里新建的行时，所见版本记为"本请求" |
| 业务时间 | 只对状态类表上的目标：`valid_at`（一点）或 `valid_during`（一段），二者互斥；都不给时见下 |
| 值 | **不记**，只记标识与版本。前提的值是别的贡献的副本，多一份副本，隐私删除就多一处要清（与"不记写入前的值"同一个理由） |

**一个出处项对一个前提目标只有一条有效声明**：一组字段、一个范围（见下「取代」）。所以一个 op 的 `premises` 里两条声明解析到同一个目标时拒绝，`invalid_argument`（`premise_duplicate_target`，指向后出现的那条，附两条的下标）；按解析后的目标判，`row` 与 `entity_key` 可能指同一个。要以同一个目标的几个字段为前提，把它们并进一条的 `fields`；要以两段业务时间为前提，给一段盖住两段的 `valid_during`，或不给范围——宁可多报。

**状态类表上的目标不给业务时间时，范围取什么**。以"11 月的预算"为前提，12 月的预算改了不该标；按天的计划只以那一天的目标为前提。所以：

- **依赖行（声明了前提的那一行）自己有业务时间，就取它。** 依赖行在事件类表上：取这个 op 写下的时间字段的值（一个点），不论这一部分是生效、成了候选还是进了待确认——声明说的是"按我写的这一行"，之后采纳与否不改它；这个 op 没写时间字段时，取 op 之后这个字段的生效值。依赖行在状态类表上：取这个 op 写下的区间，同样不论是否生效。
- **依赖行没有业务时间**（无时间表；事件类表上时间字段为空；状态类表上不带区间的重申与清除）时，取"从现在起"：`[入口时刻, ∞)`。读取记录把不传时间的读取记为入口时刻那一点，因为它问的是当时读到的对不对；前提面向之后：按"当前预算"排出的计划，在"下个月起预算下调"被记下的那一刻就该被指出来，而那次写入并没有改"现在这一点"的值。
- **按粒度对齐**（见「时间 · 三种表」）：目标所在的表是 `date` 粒度时，一个时刻取它在 slot 时区下的那一天，"从现在起"从"今天"起。目标是 `instant` 粒度、依赖行的时间是日期时，取那一天在 slot 时区下的起止时刻。依赖行的区间是 `instant` 粒度的 `[a, b)`、目标是 `date` 粒度时，取与它相交的每一天：从 `a` 所在的那一天起，到 `b` 之前最后一刻所在那一天的次日止（`b` 恰在零点时就是 `b` 那一天；开口终点仍是开口）。宁可多报一天，不漏一天。
- **取自依赖行的范围在声明时定下。** 之后依赖行的时间被改，范围不跟着变：改时间是一次写入，Agent 改时带上新的前提即可。
- "从现在起"由入口时刻得出，不含调用方给的值，是元数据；显式给的业务时间与取自依赖行的业务时间是内容，记进数据块并带来源（见「删除 · 由源数据派生出的内容」）。

**能指向什么**：

| 目标 | 第一版 |
|---|---|
| 同一 slot 的基础表的行 / 实体 | 可以 |
| 本请求里新建的行 | 可以（"建一个里程碑，再建三条以它为前提的任务"一次请求完成）：`row` 写前面某个 op 用 `as` 起的临时名 `"@m"`，或按 `entity_key` 写本请求前面新建的实体。所见状态取本请求结束时（`ver.basis: "same_request"`，同一请求里后面的 op 再改它不算前提变了），不带 `ver`（带了报 `invalid_argument`（`mutually_exclusive`））；那次新建在本请求里没有生效（进了待确认或成了候选）时拒绝声明方，`invalid_argument`（`premise_target_pending`，附目标的临时名与那个 op 的下标），先单独发那次新建、生效之后再声明。临时名绑定的是按来源键命中的已有行时，就是那一行，照常带 `ver`（或兜底） |
| 本 op 自己的目标行 | 不可以，`invalid_argument`（`premise_self`） |
| 派生表的行 | 不可以，`not_in_this_version`。第一版的影响查询不覆盖对派生值的读取，派生行也不存历史，"值恢复后撤掉标记"无从比较。以派生合计为前提时，声明它所汇总的基础行 |
| 别的 slot 的表（表在可见范围内） | 不可以，`invalid_argument`（`cross_slot`）。`ref`、写入、删除都限在一个 slot 里；跨 slot 的标记在按 slot 部分复制与按 slot 的可见范围下都没有答案 |
| 可见范围外的表或行 | 与不存在相同：表报 `unknown_table`，行报 `not_found`（见「可见范围」） |
| 按时刻读到的历史版本 | 不可以，`invalid_argument`（`premise_historical_ver`）：以一个早已不是当前的值为前提，声明时就已经变了 |

**哪些 op 可以带**：

| op | 能否带 | 含义 |
|---|---|---|
| `insert` | 能 | 新写的这一行以这些为前提 |
| `update` / `correct`，带 `set` | 能 | 这次写的值以这些为前提；这一行其余仍生效的值也按这些核对过（见下"覆盖"） |
| `update`，不带 `set`，带非空的 `premises` | 能 | **重申**：值不变，这一行现有的值按这些前提仍然成立 |
| `update`，带 `premises: []`（可带可不带 `set`） | 能 | **清除**：这一行的前提声明全部去掉，标记随之消失。这是去掉前提的唯一写法 |
| 带 `revert` 的 op | 不能，`invalid_argument`（`premises_with_revert`） | 回退写回的是别的贡献的值，它们各自的前提随贡献一起回来 |
| `revoke` | 不能，`invalid_argument`（`premises_with_revoke`） | 撤销不给值 |
| `resolve` | 不能（没有这个参数） | 采纳候选、确认提议搬运的是原写入的贡献，原写入的前提随之生效 |
| 按来源键的 op | 不能，`invalid_argument`（`premises_with_external_key`） | 连接器没读过它要写的行，按来源键的 op 没变时也不进任何事件。要声明前提，由 Agent 读到之后另行重申 |

- 重申、清除的目标行已撤销时，与普通的 `update` 一样报 `revoked`。不带 `set` 的 `update` 也没带 `premises` 报 `invalid_argument`（`missing`）。
- **前提的校验**在判定顺序的第 5 步（依赖当前状态的校验，与 `ref` 目标同处），对这个 op 带的全部声明做，不论 op 是否生效；格式与互斥的检查在第 1 步。目标不存在、已被隐私删除或在可见范围外时**拒绝**（`not_found`，附出错的声明位置；被宽限期内的删除去掉时附删除 ID）：以一个不存在的东西为前提多半是 ID 抄错。目标已撤销时**照常写入，立即打标记**（原因 `revoke`）——所见版本早于那次撤销时：行存在过、读到过，之后被撤销正是"前提变了"。所见版本本身就是那次撤销（读到的就是已撤销的样子）时记 `current`、不打标记：之后什么都没变。
- **`ver` 已过期时不拒绝**：所声明的范围上现在的值与所见版本上的值不同（判据见下「什么算前提变了」；中间变过又改回来的不算），照常写入、这一行一写下就带标记（回执的 `state: "changed"`，`warnings` 给 `premise_already_changed`）；相同，照常写入、不标。拒绝会让证据落不下来；记成候选又没有"当前值"可冲突。恢复备份或导入之前拿到的 `ver` 按「删除 · 删除登记」对 `ver` 的规则换算所见位置，再按这两条判断。

**什么算前提变了**：**一条声明的前提变了，当且仅当它所声明的（字段 × 业务时间）上，现在的值与所见版本上的值不同。** 事件类表、无时间表上范围就是所声明的字段；状态类表上是字段 × 业务时间。"值"按字段类型的同值判据比较（见「同值判据」）。**目标被撤销，不论声明了哪些字段，一律算变了**：撤销与每个字段相交（状态类表上另要求业务时间相交）。这与纠错影响查询的判据是同一句话，触发条件只在一处不同：

| 写入 | 纠错影响查询（`possibly_affected`） | 前提（`premise_changed`） |
|---|---|---|
| 事件类表、无时间表：`correct` | 查 | 标，原因 `correct` |
| 事件类表、无时间表：`revoke` | 查 | 标，原因 `revoke` |
| 事件类表、无时间表：`update` | **不查** | **标**，原因 `update` |
| 状态类表：任何让值变化的写入 | 查，原因 `correct` / `retroactive` / `plan_changed` | 标，原因相同；带区间的撤销记 `revoke`。一次写入在所声明的范围上同时有追溯与未来的部分时，原因取 `retroactive` |
| 同值的写入（无操作、佐证） | 不查 | 不标 |
| 成为候选、进待确认的写入 | 不查（没生效） | 不标；之后被采纳或确认时，按那次解决触发的写入判断 |
| 回退（`undo`）、回到冲突前 | 一次写入，按它的意图与实际变化 | 同左；多数时候效果是撤掉标记 |
| 隐私删除改掉了值 | 只撤不增 | **标**，原因 `deleted`（见「删除 · 删除之后」） |

- **为什么 `update` 也标**：纠错影响查询问的是过去——之前读到的值当时对不对，`update` 意味着当时是对的。前提问的是现在——这一行现在还站在什么上；发布日期改了，不论是记错了还是改了主意，任务都要重新看。
- **追溯与未来并存时取 `retroactive`**：一条声明只给一个原因，`retroactive` 说的是"已经过去的那部分也变了"，读方至少要回看一次，比 `plan_changed` 的提示更强。
- 原因码共七个：`correct`、`update`、`revoke`、`retroactive`、`plan_changed`、`deleted`、`schema_switched`（schema 切换删掉了所声明的字段，见下「检测」末）。
- 几种常见的情形：只声明了 `date`、目标的 `name` 变了，不标；目标的改动被 `undo`，或被另一次写入改回同样的值，标记撤掉（不是专门的规则，判据是值）；依赖行已按新值重申、随后目标的改动被 `undo`，**重新标**，原因取 `undo` 那次写入的意图；目标上有未决冲突，不因争议本身而标（生效值没变）。

**覆盖、取代与清除**。一个带 `premises` 的 op 的含义是"按我所见的版本，这一行现在的值以这些为前提"。它覆盖两部分：

1. **本 op 自己写下的各项**（不论生效、成为候选还是进了待确认）：按（事件, 目标）覆盖，即本 op 在该目标上的全部项，含删除重述在其上新编出的下标。
2. **这一行在 op 所见版本上就已生效、op 之后仍然生效的其余各项**，显式记进事件。只在这个 op 全部字段都已生效（`applied`、`corroborated`、`noop`）时才覆盖：有字段成了候选或进了待确认时，它对整行的判断以自己的改动落地为前提。这个 op 之后经采纳候选或因删除而生效时，第 2 部分不补记，这一行其余字段仍按原来的声明显示标记。

重申没有第 1 部分，只有第 2 部分。

- **取代**：对同一个出处项（见下）、同一个前提目标，以最晚的一条覆盖它的声明为准。所以改了 `due` 并带上指向发布日期新版本的前提，`title`、`status` 两项的旧声明一并被取代，标记消失；改了 `due` 而没带 `premises`，`due` 的新值没有前提，`title`、`status` 仍按旧声明；新的 `premises` 指向另一行，是新增一条前提，旧声明不受影响。
- **清除**（`premises: []`）覆盖的各项上，它之前的全部声明一并失效，不论指向哪个目标；它自己写下的项没有前提。**清除的第 2 部分不受"全部字段都已生效"的限制**：清除不对值下判断，带 `set` 的清除即使有字段成了候选或进了待确认，这一行在所见版本上就已生效、之后仍生效的其余各项也照样被清掉——"清掉这一行的前提声明"说的是整行。只想去掉两条前提中的一条：同一请求里先清除，再用一个重申 op 声明要留下的那条（后面的 op 看得到前面的结果）。前提目标已被整行隐私删除时，重申它报 `not_found`，用清除消掉标记。
- 重申与清除应带依赖行的 `ver`（或兜底）：只覆盖所见版本上就已生效的项，别人在你读之后写进这一行的值，你没看过，不替你重申。它们不做冲突判定、不会成为候选。
- 重申与清除是一次 `write`：有操作号、逻辑写入头与源数据，**没有基础写入**，行的 `ver` 不变。它们不能被 `undo`（没有可撤回的改动）；要推翻一次重申，再重申一次或改写。
- **打标记、撤标记、重申、清除都不改依赖行的 `ver`**：值没有变，别的 Agent 手里的 `ver` 不该因此失效。

**标记出现在哪一行**。前提挂在贡献上，不挂在行上：回退、回到合并基、删除重放让值回到更早的贡献时，前提跟着回去。一行（状态类表：一段）上的标记读时现算：

1. 取各字段**当前值的出处项**：给出当前值的那一项贡献；它是搬运来的（回退、采纳候选、回到合并基的写回项，以及删除结果里的搬运），沿搬运引用走到头；另加当前仍作数的佐证项。来源是 schema 常量的值、"没有值"与只做登记的写回项没有出处项。
2. 找覆盖这些出处项的有效声明（排除被取代的、被更晚的清除作废的）。第 1 部分按（事件, 目标）覆盖，删除重述新编出的下标随之覆盖；第 2 部分按记下的项覆盖，删除重述新编出的下标随它所分出的那一项一并被覆盖，"从哪一项分出"按写入时的区间块判，那一块已被到期执行的删除清掉时按那一项的原区间判（见「删除 · 回掉的权威定义」步骤 6）。
3. 其中状态是"已变"的，每条出一条标记；标记里的 `fields` 是被它覆盖的那些字段，只列当前版本里还在的。

被后来的写入盖掉的旧值，它的前提不再显示。读取请求了 `fields`、而这些字段都不在某条标记的 `fields` 里时，不带这条标记（与 `disputed`、`awaiting` 同一条）。一行最多列 10 条，按 `since` 从新到旧，另给总数。派生行的输入标记与 `sql` 的标记汇总各加一项计数，只统计规则所依赖的字段上带这个标记的基础行。标记的形状见 [`../04-contract.md`](../04-contract.md) 第 7 节。

**检测**。一次操作（写入、解决触发的写入、删除确认、撤回删除）生成完基础事件之后（schema 切换见本节末）：

1. 取这次操作里**值实际变了的**（行，字段或"存在"，业务时间区间）——纠错影响查询已有的输入。删除确认与撤回取结果里值与删除前（撤回前）不同的字段与段；只换了给出者、值没变的不算。**以及范围因本次删除被改成整条时间线的声明**：删除确认把某条声明取自依赖行的业务时间（`premise_valid`）列入位置列表时，这条声明从这次删除确认起按整条时间线处理（不等到墓碑），并在本次检测里对它按整条时间线重判一次——仍是"没变"、而整条时间线上的值已与所见版本不同，**或所见版本那一格的内容已被删除或待删除（比不了）**的，都转为"已变"（宁可多报，"没变"仍意味着值等于所见），`since` 是本操作号，原因 `deleted`，写进本次的前提变化事件。撤回这项删除时范围恢复，同样重判一次（"已变"的按恢复后的范围比较，相同且比得了的转回"没变"）。墓碑只负责清空 `premise_decls` 里业务时间的副本。
2. **打标记**：按前提目标找状态为"没变"的声明，所声明的字段与范围同第 1 步的结果相交的，转为"已变"，`since` 是本操作号，原因取这次写入的意图（撤销一律 `revoke`，删除为 `deleted`，状态类表上追溯与未来并存取 `retroactive`）。这一步不读历史：一条声明是"没变"，就意味着到这次操作之前它的范围上的值一直等于所见的值；这次操作改了它，就是变了。
3. **撤标记**：按前提目标找状态为"已变"的声明，范围同第 1 步的结果相交的，比较"现在的值"与"所见版本上的值"；全部相同、且比得了（所见版本上那一格的内容没有被删除或待删除），才转回"没变"。schema 切换之后两边都读当前版本的版本表：切换逐项转换，出处项的（事件、字段 ID、下标）不变，所见版本是操作号、与 schema 版本无关，所以不需要跨版本读历史值，`premise_edges` 也不随切换转换；`migrate` 不是单射时，原来不同的两个值在新版里相同，撤标记比原来更容易成立——比的是新版上的值。切换本身不重判声明：这种撤标记发生在切换之后下一次改到这个前提目标的操作里，照本步比较，那时两边都读新版。
4. **改指**（只在删除确认与撤回里）：仍是"已变"的声明，若这次删除改了它范围上的值，或去掉了它 `since` 所指那次操作在这个范围上的贡献，`since` 改为本操作号、原因改为 `deleted`。否则标记会指着一次在删除之后什么都没做过的操作。
5. 第 2–4 步的结果写成一条 `premise.changed`（有变化时才有，一次操作至多一条）。

**schema 切换**不走上面五步：切换只改写法，不改 Agent 用到的事实，不打标记、不撤标记、不改指。唯一的例外是新版删除了某条声明所声明的字段（含随表删除的字段）："没变"的这类声明转为"已变"，`since` 是切换的操作号，原因 `schema_switched`，写进切换那次操作里的一条 `premise.changed`；已经是"已变"的不动（`since`、`reason` 保持）；声明了几个字段、只删其中一个的同样转为"已变"；声明不扩成整行。

只处理仍是某个出处项的有效声明的那些，含候选、待确认的写入里的声明（它们之后生效时状态直接可用）。`since` 记第一次使前提不同的那次操作，之后前提再变不重记（改指除外）：否则被依赖的行每改一次，所有已带标记的依赖行都要在事件里再列一遍。

**不变式**（写成性质测试）：对每条仍有效的声明，状态是"没变"，就意味着它的范围上现在的值等于所见版本上的值。反方向不要求：比不了的时候允许多报。

**不传递**。A 变了，以 A 为前提的 B 带标记；B 的值没变，以 B 为前提的 C 不带。C 声明的是"以 B 在某个版本上的值为前提"，B 的值没变，按判据 C 的前提没有变；标 C 等于替 Agent 断定 B 已经失效。B 被处理时改了值，C 按普通规则被标；B 核对后被重申，C 不该被打扰。一次操作打的标记数因此只取决于直接依赖它的声明数，与链长无关。B 悬而未决期间，读 C 的一方可以按详细模式看到 C 的全部前提，其中有 B。

**上限**（初值，随评测与实验调整）：

| 项 | 上限 | 超出时 |
|---|---|---|
| 一个 op 的声明条数 | 16 | `too_large`（`premise_entries`） |
| 一行 / 一个实体被多少条有效声明指向 | 1,000 | 拒绝**声明方**：`too_large`（`premise_fan_in`），附目标与当前条数 |
| 一行上列出的标记 | 10 条，另给总数 | 截断 |
| 回执里列出的受影响的标记（`premise_affected.rows`：依赖行上被标记的每条声明一条） | 20 条，另给依赖行数 | 截断 |

- **有效的声明**：所在的写入已生效（不是候选、待确认）、没被更晚的声明完全取代、没被清除、依赖行未撤销。声明时的计数按仍作数的覆盖取（没被取代、没被清除），不减去依赖行已撤销、所在写入尚未生效的，所以只会多数、不会少数，拒绝可能略早。
- **上限落在声明方，只在声明时检查**。落在改动方就是"别人声明得多了，这一行就改不动了"，一个连接实例可以用声明挡住另一方的写入。之后因采纳候选、撤回一次撤销、撤回删除等原因超过上限的，允许存在，不追溯拒绝：这些操作的发起者不是声明方。
- 前提这一项计入写入（含解决触发的写入）的准入估算；**隐私删除与撤回删除永远不受它影响**：删除不能分批，计入的话别人的声明就能挡住被遗忘权。删除里的检测照做，代价并入删除本身（见「刷新范围与写入准入」）。

**记在哪**：

- **声明**是调用方的原始传参，记在逻辑写入头里，只有标识、字段 ID 与版本，是元数据块；显式给的与取自依赖行的业务时间是数据块（见上）。
- **标记的变化**是 saveslot 的判定结果，记在 `premise.changed` 里，由写入与删除管线在产生改动的那个事务里生成，`apply` 照做、不自己比较值：撤标记要读所见版本上的值，那是历史版本，内容物理删除之后重放时比不了；写进事件，比较只在线上、在当时做一次。
- `apply` 维护两张 (b) 类表：`premise_decls`（每条声明与它的状态、原因、`since`）、`premise_edges`（每个出处项对每个前提目标当前有效的声明，另有清除条目）。输入全在日志里，导出、恢复之后标记照样在；不放进本地运行状态。
- **前提不参与任何取值判定**：同值、冲突、高影响、行的存在、回掉、删除重放都不读它。回掉的伪代码不用知道它的存在。
- 事件形状见 [`../09-event-format.md`](../09-event-format.md) 的 `write.head` 与 `premise.changed`。

### 连接实例身份（第一版就做）

**每次接入签发一个独立凭证，由用户命名**（如"MacBook · Claude Code"）：本地模式写进该客户端的 MCP 配置，
远程模式对应一次单独的 OAuth 授权。所有写入、读取都归属到这个连接实例。

| 识别层次 | 靠什么 | 可信吗 |
|---|---|---|
| 哪个用户 | 本地凭证 / OAuth token | 可信 |
| 哪个客户端应用 | 远程 OAuth 的 client_id | 可信，只到应用一级 |
| 哪个实例 | 接入时签发的独立凭证 | 可信 |
| 客户端自报的名称、版本（clientInfo） | 客户端自报 | 不可信，只作参考 |
| 实例内的哪个会话 / 子 Agent | 请求里的任务标识 | 自报，只用于关联读写 |

理由：来源记录（"这次写入来自哪个 Agent、哪个客户端"）依赖它；成本低；权限直接挂在这个凭证上，不改结构。

**授权 = 动作 scope × slot 范围。** slot 范围取"全部"或"一个 slot 列表"；同一组 scope 对范围内的每个 slot 一样（要"A 可写、B 只读"就签发两个连接实例）。范围是"全部"时之后新建的 slot 自动纳入；是列表时列表不变，这个凭证也不能新建 slot。范围外的 slot 对这个凭证与不存在完全相同（见「可见范围」）。用户会话的范围恒为全部。表级、字段级的数据权限后续。范围的权威在日志里：签发事件记下 slot ID 列表（缺省 = 全部），服务层由此构造可见范围，控制面不另存一份。

- **第一版单节点**：连接实例由用户会话登记，**注册、改名与吊销都是日志事件**；scope 与 slot 范围在签发时定下，第一版不能改（要改就吊销后重签；重签换了连接实例，来源键的唯一范围不含连接实例，接着同步不会重复新增）。多节点时（后续）：由签发它的节点登记，ID 全局唯一（带节点前缀），随同步传播；主节点接受"某节点签发、
  且已登记的连接实例"所做的离线写入；吊销在离线节点上线"先拉取再推送"时自然生效。
- **停用**：导入到空租户时，导入前登记过、仍有效的全部用户主体与连接实例（`system` 除外；已吊销的保持已吊销）由导入事件统一置为停用（`disabled`），发起导入的用户登记为新主体。停用与吊销并列：吊销是用户对某个连接实例的决定，停用是导入带来的统一处置。停用的主体不能认证，第一版不能恢复；它们写过的数据 actor 不变，名字照旧显示、标"已停用"；它们发起而未处理的事项照常保留，由用户会话或新签发的连接实例处理。

### 来源的完整性

| 记录 | 能否保证完整 | 怎么保证 |
|---|---|---|
| change_log：每次写入都被记下 | 能 | 唯一写入口（API）；数据库层只给 saveslot 的服务账号写权限，不开放裸 SQL；与业务写入同一事务；事件头链；用日志重放与业务表对账（见「完整性与溯源」：防误操作，不防能写存储的一方） |
| change_sources：派生写入的来源 | 能 | 规则由 saveslot 执行，输入由 saveslot 决定 |
| change_sources：基础写入的来源 | 部分 | 能保证"写入方交来的证据"被记下；保证不了它没用到别的信息 |

第三行是本质边界：信息一旦被 Agent 读走，就可能出现在它之后写的任何东西里，saveslot 看不到 Agent 的上下文。
**saveslot 保证 saveslot 内部的来源链完整；经过 Agent 的那一段只能检查与校验：**

| 层 | 查什么 | 例子 | 用模型吗 |
|---|---|---|---|
| 确定性校验 | 类型、单位、范围、预期版本、重复提交（幂等键） | 距离为负；同一请求提交两次 | 否 |
| 统计异常（第一版不判定、不产生事项；定义待定，见 architecture §14） | 与该用户自己的历史相比偏离过大 | 平时 5 公里，突然 50 公里 | 否 |
| 字面命中 | 写入的值是否在随附证据的原文里字面出现；只记录、不拒绝（见「来源级别」） | 证据"跑了 5 公里"，写入 5 km：命中 | 否 |
| 证据核对（第一版不做） | 写入的值与随附证据的意思是否一致 | 证据说"5 公里"，写入的是 15 | 是，后台异步 |

明显违规直接报错拒绝；可疑的进入待确认并标记（永不阻塞）。

**污点追踪（可选，不作为首版必选项）**：一次写入的来源除了声明的来源，再加上"同一任务里它之前读过的数据"
（取自 read_log，要求读写带同一任务标识）。被删数据视为有污点，读过它之后写入的东西视为"可能也带污点"。
会多算，所以推测出的来源只作"可能受影响"一级，不自动删除；隐私删除时列给用户决定。
显式声明的前提是它的精确版本，已进第一版（见「写入的前提」）：Agent 自己列出用到的值，进日志、对所有读取方可见；按读取记录推断的仍是可选项。

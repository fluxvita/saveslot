## 完整性与溯源

**目标是"能溯源 + 防误操作"，不是防篡改**：每项状态都能追到日志里的事件与源数据；事件缺失、乱序、事件头被意外改动、内容损坏、绕过 `apply` 的改动都能被发现。
对能写存储的一方（含运营方）**不提供**防篡改证明（见 [`../02-architecture.md`](../02-architecture.md) §10）。

| 项 | 规则 |
|---|---|
| 事件头 | 只有通用字段：`seq`、事件格式版本、类型、actor（主体 ID）、记录时刻、`prev_hash`、所属操作的操作号（头事件没有）、slot ID；`system` 的头事件另带 `trigger`（哪个后台任务，固定枚举）；创世与恢复事件另带节点 ID 与恢复信息。完整定义见 [`../09-event-format.md`](../09-event-format.md) 第 2 节。**不放任何由用户内容算出的值**——请求键、分组键、内容哈希都不放。表、行或实体、意图、被引用事件的 `seq` 也不在事件头里，而在内容区的**元数据块**里（只含不透明 ID、枚举、序号与下标、版本号、布尔值、入口时刻；不进链；第一版不随删除清除，见「删除之后」） |
| 链 | **只串事件头**：`prev_hash` = 上一条事件头编码字节的 SHA-256（小写十六进制）；创世事件的 `prev_hash` 为 64 个 `0` |
| 内容 | 与事件头分开存放。一个事件的内容是一组**内容块**，每块按（事件 `seq`，`path`）寻址，各配一个校验和（SHA-256，对块内容的字节求）。校验和只用于发现存储损坏，随内容一起删，**不是对内容的承诺**：不给内容块配盐、密钥或链上承诺 |
| 删除 | 直接**物理删除内容块**。块是删除的最小单位，整块删除，没有块内的部分删除；字段、条目、整条三种粒度靠块切得够细来满足。被删的块保留位置、清空内容与校验和、记下墓碑的 `seq`（"已由 #n 移除"；标记里没有内容，也没有由内容算出的值）。事件头保留 |
| 防误操作 | 只有内核能写（K3；数据库层只给 saveslot 的服务账号写权限）；日志只追加；对账（从日志重放 = 线上状态；第一版由用户会话手动触发全量对拍）；事件头链校验；内容校验和 |

**内容块的位置。** `path` 是若干段用 `/` 连接的 ASCII 字符串，段只能是三种：该事件类型的固定词（如 `fields`、`sources`、`target`、`request_key`、`text`、`candidates`）、不透明 ID（字段 ID、表 ID）、十进制下标。例：`fields/f3/0`（这次写入对 3 号字段的第 0 项贡献）、`sources/f3/0`（这一项的来源）、`candidates/1`（事项的第 1 个候选）、`text`（一段证据的原文）。
**`path` 里不出现任何用户内容或由用户内容算出的值**（字段用 ID 不用名字），所以位置可以写进元数据块里的引用、墓碑的位置列表和删除登记。每种事件类型的 `path` 词表是事件格式的一部分，随事件格式版本只增不改。

**事件的身份。** 第一版事件头里没有单独的事件 ID。创世事件与"恢复"事件的事件头各带一个随机生成的节点 ID；一条事件的身份 =（它之前最近一条创世或恢复事件的节点 ID，它的 `seq`）。恢复时换一个节点 ID，是因为恢复后 `seq` 可能与丢失的那段时间线重号。多节点时（后续），别的节点产生的事件在事件头里加一个可选的来源字段；缺省字段不编码，旧事件的字节不变。

| 能发现 | 靠什么 |
|---|---|
| 事件缺失、乱序、事件头被意外改动 | 事件头链 |
| 内容存储损坏（写坏、截断、丢失） | 内容校验和；没有移除标记却找不到内容，算不符 |
| 物化状态与日志不一致（绕过 `apply` 改业务表、`apply` 自身的缺陷） | 对账：从日志重放，与线上逐表比对 |

**不承诺**：

- 对能写存储的一方（含运营方）防篡改：改了内容并重算校验和、或重算整条事件头链，`verify` 照样通过。
- 给第三方的证明（"某个版本确实在日志里""历史没被改写"）。
- 删除前的内容是什么：被删位置不留任何由内容算出的值，删除后无从证明、也无从拿猜测值比对。

签名检查点、Merkle 树、链上内容承诺**放到后续规划、按产品需要再做**（positioning「后续规划」）；将来要做时通过**新的事件格式版本**加入，旧事件不追加。

- **由内容算出的值、调用方自报的文字都是内容**：请求键、显式幂等键与它的请求内容指纹、调用方自报的任务标识（`task`）、派生行的分组键、疑似重复的判定依据、确认记录里所确认内容的哈希、派生写入的结果校验和、切换事件里新版表的校验和——一律放在内容区、随内容删除，不进事件头。请求键、幂等键与 `task` 的来源是这次操作的全部证据：其中任何一条被隐私删除，它们随之删除（见「删除 · 由源数据派生出的内容」）。否则删除后仍可拿猜测的原话算一遍来比对。
- **读取记录不存内容哈希**：只记读到的版本（`seq`），查询条件只记不含用户值的结构指纹（见「读取记录」）。
- **编码确定**：事件头与内容块都用 RFC 8785（JCS）编码成 UTF-8 文本存放，编码后的文本是权威；缺省字段不编码，加字段不改变旧事件的字节。十进制数（金额、数量）一律写成字符串——JCS 按 JavaScript 的数字规则序列化，会损失精度；`seq`、下标这类小整数用数字。存成文本列，不用会改键序与数字写法的二进制 JSON 类型。
- 哈希与校验和在 TS 应用层计算，PGlite 与原生 PostgreSQL 一致；每租户写入串行化，事件头、内容与业务写入**同一事务提交**。
- **只有主节点的链是权威链**（多节点，第一版不实现）：离线节点的暂定事件不进权威链，被主节点接受、分配 `seq` 后才串进去；离线节点本地可以有自己的暂定串链，只作本地参考。
- **验证**：`verify` 报"日志共 T 条事件，事件头链完整（或：自第 k 条起断裂）；内容校验和 N 处不符；M 处已按删除移除"，并列出每处不符的位置。
  "已移除"（有移除标记，正常）与"不符"（损坏）分开报。

## 写入与读取的记录

例子见讲解 [`../../guide/02-walkthrough.md`](../../guide/02-walkthrough.md)：每一步都列出了追加的日志事件（与本目录不一致处以本目录为准）。

### 写日志：change_log + change_sources

- **change_log**：每次写入在日志里记三种事件——
  - **逻辑写入头**：**每次写入请求一条**，不论改了几行，是这次操作的头事件。记**原始传参**（各 op 里不是无操作的字段的原始值、无操作字段的 ID 列表、区间参数的原始写法）、请求键或显式幂等键与内容指纹、自报的任务标识、`sv`（以及它是显式带的还是兜底取得的）、判定时用的"现在"与 slot 时区下的"今天"、各 op 所见的 `ver`（以及它是显式带的、兜底取得的、还是本请求前面的 op 新建的）、规则版本与策略版本。"是否追溯"不单独记：它由记下的"现在""今天"与解析结果比较得出。它的 `seq` 是这次写入的**操作号**。
  - **基础写入**（Agent / 调用方写基础表）：每个 op 对每个受影响的行 / 实体一条。**只记本次请求涉及、且不是无操作的字段**。一个字段的贡献是**按区间排好的若干项**（事件类表与无时间表恒为一项）：每项各有值、**解析后的生效区间**（状态类表；单独成块，并记下解析时用到的别的贡献，见「删除 · 由别的贡献求得的内容」）、来源、**生效状态**与写入时的判定结果（见下）。一个字段有多项的情形：`undo`、回到合并基要写回几段不同的旧值；佐证的区间里一部分仍同值、一部分已被别人改掉。**不记写入前的值，也不记写入后的整行**：写入前的值是更早事件的副本，每多一份副本隐私删除就多一处要清；写入后的状态由"之前的状态 + 本事件里生效的字段"确定地得出，按时刻读走版本表。状态类表一个 op 对一个实体只记一条事件，物理段由 `apply` 在逐项区间赋值之后规范化得出（不含判定）。
  - **派生写入**（规则引擎刷新派生缓存）：只记规则版本、派生行的 `partition_id`、依据的日志位置，内容里记分组键值与结果校验和，**不存写入前后的值**
    ——随时可由基础数据 + 规则重算。
- **一次写入内各事件的先后**：逻辑写入头 → 源数据（每段证据一条；没带证据时每个 op 一条）→ 逐个 op（按请求里的顺序）的基础写入与它引出的事项事件 → 全部 op 之后的派生写入。它们在同一事务里提交，`seq` 连续（[`../09-event-format.md`](../09-event-format.md) 4.2）。
- **逐项的生效状态**：`applied`（生效）、`candidate`（成为冲突候选）、`awaiting`（高影响，等确认）、`corroborated`（同值且显式指了证据：只追加来源）。`apply` 只把 `applied` 的项落进业务表与版本表，把 `corroborated` 的写进来源表；其余只留在日志里，供 `timeline`、事项与删除重放使用。
- **无操作的字段**（同值且没指证据）不是贡献：基础写入事件里没有它，日志里任何地方都不留它的值，只在逻辑写入头里列出字段 ID（供审计与幂等重放的回执给出 `noop`）。之后的采纳、确认是一次由 `resolve` 触发的新写入，有自己的头事件与操作号，值来源是对原候选 / 提议贡献的引用。
- **全部字段都是无操作的请求**：照常存源数据、记逻辑写入头（含请求键，重发按幂等重放），不记基础写入，`ver` 不变。证据是资产，不因为没改值就丢掉。`undo` 的各部分全部被跳过时不同：照常记一条基础写入，里面没有写回的项，只有回退记录（回掉哪些项要留下，之后盖住它们的写入被隐私删除时，这次撤回才能在重放里生效）；`ver` 不变。
- **写入时的判定结果**记进基础写入事件，重放不重算：疑似重复（隐私删除时也不重算，见「疑似重复」）；字面命中，按"字段的每一项 × 该项引用的每段证据"记命中 / 未命中 / 不适用，并记核对器版本（规则见「来源级别」）。
- **解析结果以最近一次给出的为准**：默认终点、纠错的默认区间、首次创建标记是机械判定。隐私删除的重放让它们变了时，新的结果记在那次删除事件里；之后的 `undo`、冲突判据、对这项贡献的引用都按最新的（见「删除 · 结果怎么落进日志」）。
- **change_sources**：这次写入由什么引起，多对多，两种来源：
  - 源数据（用户说的一句话、一次工具结果……）——基础写入的来源，由写入方随写入提交；
  - 上游写入——派生写入的来源，由规则引擎按实际读到的输入自动记录。这一种是级联能成立的关键。
- 物理上是两张表：`base_sources`（基础写入 → 源数据，带字段列表与来源种类：值来源 / 操作来源，见「删除 · 来源」）与 `derived_reads`（派生写入 → 规则版本、基础表、`partition_id`、日志位置；不存分组键值）。
  **从某个基础版本找"哪些派生写入用过它"**：取该版本改前、改后值所落的分区（按分组键值经映射得到 `partition_id`），在 `derived_reads` 里找 `partition_id` 匹配、
  且该基础版本的有效区间覆盖读集日志位置的派生写入；再沿派生依赖往下游重复。
- 同一行的上一版本由 change_log 按行排序即可得到，不另记进 change_sources。
- 业务表写入、change_log、change_sources **在同一个事务里提交**。
- **记录时间 = 日志的序号**（每租户单调）。每租户写入串行化（`pg_advisory_xact_lock`），序号即提交顺序，日志复制时原样带走。
  - **对外一律用操作号**：一次写入、一次由 `resolve` 触发的写入、一次删除确认、一次撤回各有一条头事件，它的 `seq` 是这次操作的操作号。回执的 `seq`、`ver` 里的序号、`timeline` 的 #n、`undo` 的 n、`changes` 的 `since`（不含）/ `until`（含）、版本表的记录时间区间都用它；源数据事件与各行基础写入事件的 `seq` 不对外。
  - **`as_of: S`** = 操作号不大于 S 的全部操作都已完整生效时的状态；S 落在一次操作的中间等同于落在它的操作号上，所以读不到写了一半的状态。给的是时刻时，按记录时刻换成操作号；未来的时刻等于最新。
  - **记录时刻**另存，由内核保证单调：= max(调用上下文的 `now`，上一条事件的记录时刻)；不用 `NOW()`（取的是事务开始时间，与提交顺序可能不一致）。这次操作里与"现在"有关的判断都用它（architecture §7「记录时刻」）。
- **重放用记下的结果**：一次写入可能改多行、拆多段（如回溯修改拆分生效区间），重放时 `apply` 照事件里的解析结果做，不重跑拆段算法。
- 这是应用层日志，不是 PostgreSQL 的 WAL：WAL 是物理日志，不知道"源数据"。
- **按时刻读由 change_log 程序化实现**：原理上把日志重放到某个位置即可得到当时的状态；为了查询快，
  再从 change_log 维护一张**版本表**——按单元格记（某一行或实体的某个字段、在某段业务时间上的一个值各一条），标上有效区间"从哪个操作号起、到哪个操作号止"，
  按时刻查询只取区间覆盖该时刻的版本（即 SQL:2011 的系统版本表，SQL Server、MariaDB 原生支持）。
  版本表存该版本的字段值（不存指向内容的引用），按时刻读是一条普通查询；物理删除时版本表里对应的值一并清掉。派生数据不存历史，按那一刻的基础数据重算。
  版本区间第一版就存（数据结构以后难补）。**对外开放范围**：业务时间查询（`valid_at` / `valid_during`）第一版对外开放；
  按时刻读（`as_of`）只在审计、还原类接口开放。

### 读取记录：read_log

用处：

1. **纠错影响**：数据被纠正后，找出哪些任务读到了基于错误数据的值（冲突处理第 5 条）。
   见下方「纠错影响查询」。
2. **按时刻还原**：某次任务当时看到的是哪个版本。
3. **安全审计**：哪个连接实例读了哪些数据。

字段：read_id、时间、actor（连接实例）、任务 / 会话标识（调用方提供，可空）、读了什么（数据目录的读取记 slot、表与读到的 `sv`；数据读取记表、行或派生行的 `partition_id`、源数据 ID；查询条件只记**不含用户值的结构指纹**——字面量换成占位符、名字换成 ID、去掉别名与注释之后的规范化文本，直接存文本不存哈希，算法见「读取 · 读取记录里记什么形状」）、
拿到的版本（每行读到的版本 `seq`，**不记内容哈希**）、**业务时间条件**（如"查 11-03 的预算"；不记则纠错影响查询会多报。
**不传时间的读取记为入口时刻**：状态类表默认取当前段，读的就是"现在"——`granularity: date` 时记为 slot 时区里的那一天）、
**入口取的"当前时刻"**（受限 SQL 里禁 `NOW()`，统一由入口取一次）。

**谁能查读取记录**：用户会话经 HTTP 看完整审计；Agent 经 `history`（MCP 上是 `saveslot_history`）能查到**任何连接实例**对某个目标的读取，
但只给读到的版本、时刻、连接实例名与 `task`，**不给查询条件**。
这让"某次任务当时看到的是哪个版本"在 MCP 里可答。

原则：

- **只记版本号，不记值，也不记由值算出的哈希。** read_log 不成为第二份数据副本；被删数据的内容不会残留在读取记录里，也无法拿猜测值比对。
- **粒度到"行的版本"。** 一次查询返回多行就记多个版本。逐行读（`query`、`history`）每页最多 1,000 行，所以一次读取记下的版本数有上限。
- **读得太多时改记表级记录。** 受限 SQL 的聚合与关联可以读很多行而只返回一行，逐行记的代价会随数据量涨。规则：一次读取在**某一张基础表**上实际读到的行版本数（通过了条件、进入了结果或聚合的行）超过阈值（初值 1,000）时，这张表不逐行记，改记**一条表级记录**：表 ID、读取时的日志位置（当时最新的操作号）、业务时间条件、结构指纹。没超过阈值的表仍逐行记；同一次读取涉及几张表时各自判断。表级记录不记行数——行数由用户内容决定，记下来没有用处。
- **独立于写日志。** 有自己的保留期限：第一版是租户级的一个数值，默认 180 天、下限 30 天（初值，随评测调整）；按 slot 设更长的保留期（敏感数据要求全部保留）后续再加。纠错影响查询只覆盖保留期内的读取，结果里写明覆盖到哪天；按期清理不影响写日志的事件头链。
- **读远多于写。** 记录要便宜：批量写入、按任务聚合。

### 纠错影响查询

**数据被纠正（或撤销、追溯修改、未来安排变更）后，找出哪些读取用了后来不成立的值。** change_sources 回答"哪些版本受影响"，
read_log 回答"谁读过这些版本"，两者合起来才能查出。

```
纠错源数据 R ──change_sources──> 纠错写入（例：C5）
             ──change_log 按字段回溯──> 被纠正的版本（该字段取得错值起的各版本，例：C1）
             ──change_sources 往下游递归──> 受影响集合 C（C1、C2、C4）
             ──read_log 匹配版本──> 用过错误版本的读取（r1）
```

- **分组取并集**：纠错可能让一行换了分组（如日期从 11-03 改到 11-10），受影响的派生行 = 改前、改后两个分组的并集。
- **读时计算的派生行**（依赖"今天"的规则，以及读状态类表而不带业务时间限定的规则）没有派生写入可匹配：read_log 记"规则版本 + 入口时刻 + 读取时的日志位置（最新的操作号）"，按"规则所读的基础表在该位置之后有没有受影响的版本"匹配，宁可多报。
- **受限 SQL 读取的业务时间条件**：带 `FOR VALID_TIME` 的，按改写时得知的时间条件记；不带的记入口时刻（读的是当前段）。`WHERE` 里对时间列的任意谓词不解析。事件类表上的受限 SQL 读取按"读到的版本集合"匹配，宁可多报，结果标"可能受影响"。
- **表级记录的匹配**（见「读取记录」的阈值规则）：受影响集合里只要有这张表的一个版本，它在读取时的日志位置上是当时的版本（版本的记录时间区间覆盖那个位置），这次读取就算命中；状态类表上记了业务时间条件的，再要求受影响的业务时间区间与它相交。命中的结果标"可能受影响"：表级记录说不出这次读取到底有没有用到那一行，宁可多报。它不参与 `ver` 的兜底。
- **第一版只覆盖主节点上的读取**：离线节点的读取记录不同步回主节点（见「同步协议」）。
- **起点是被纠正的版本，不是纠错写入，而且按字段回溯。** 从 R 直接往下游走得到的是 C5、C6……这些纠错后的正确版本；
  要经 change_log 找到**该字段最近一次取得被纠正值的那次写入**，从它起到纠错之前的**所有版本**都是起点，再往下游走。
  同一个错值常常跨多个版本（中间有别人改了其他字段），只取"上一版"会漏掉更早、同样错的版本与读取。
  状态类表按"字段 + 业务时间区间"回溯。
  **撤销没有"错值"可回溯**：起点是该行从插入到撤销前的所有版本。
- **什么会触发。** 判据是结构性的：一次读取问过的某个（字段，业务时刻）上，值在它读到的版本与现在之间变了，它就受影响。

  事件类表、无时间表（没有业务时间区间，"之前读到的值当时对不对"只有 Agent 知道，所以看意图）：

  | 写入 | 含义 | 查不查 | `possibly_affected` 的措辞 |
  |---|---|---|---|
  | 纠错（`correct`，Agent 显式标注） | 旧值一直是错的 | 查 | "你曾读到的值已被纠正" |
  | 撤销一行（`revoke`，含由 `flagged` 事项触发的） | 这条本来就不该存在，包含它的读取都不对 | 查 | "你曾读到的值所含的一条记录已被撤销" |
  | 系统裁定（候选按冲突规则当场成为生效值；第一版不产生） | 生效值被规则改了，之前读到的旧值已不是生效值 | 查（与纠错同等） | "你曾读到的值已按冲突规则改变" |
  | `update` | 补充或修改信息，之前的读取当时是对的 | 不查 | — |

  状态类表：**任何让值发生变化的写入都查**，不看生效起点在现在之前还是之后。值实际变化的（字段，业务时间区间）与 read_log 记下的业务时间条件有交集、且该读取读到的版本早于这次写入，就标记。原因码按情形分：

  | 情形 | `reason` | 措辞 |
  |---|---|---|
  | 意图是 `correct` | `correct` | "你曾读到的值已被纠正" |
  | 变化区间里早于"现在"的部分 | `retroactive` | "你读取的业务时间上的值后来被追溯修改" |
  | 变化区间里不早于"现在"的部分 | `plan_changed` | "你读过的未来安排已变更" |

  追溯修改可能是"早就变了但晚知道"，也可能是"今天决定、往回生效"，saveslot 分不清，措辞保持中性：只有 Agent 显式标了 `correct` 才说"已纠正"。
  不传时间的读取记为入口时刻（日粒度记为当天），所以"今天早些时候读过今天的值、之后今天的值被改"按同一条判据自然命中。
- **范围是值实际变化的部分**：状态类表上只算值真的变了的业务时间区间，用同样的值覆盖的部分不算（见「时间 · 三种表」）。
- **排除纠错者自己的定位读取**：纠错写入所依据的那次读取不算受影响——那是为了纠错才读的。`ver` 对应的是版本、不是某次读取，所以精确为：
  **同一连接实例 + 同一 `task`（未带 `task` 时只看连接实例）对该目标、该版本的最近一次逐行读取**；兜底取得 `ver` 时就是兜底用的那次。
- **值恢复后撤掉标记**：之后的回退或修改让某次读取当时读到的值重新成立（如追溯改成 3000 后又回退成 5000），该读取的 `possibly_affected` 撤掉。
  按"该读取问到的字段 × 业务时间"逐一比较，全部恢复才撤；对所有写到带标记目标的写入都做这项检查，删除确认与撤回删除也做（只撤不增，见「删除之后」）。
- **一次纠错可能改多行**（如"上周的跑步都多记了 1 公里"）：每个被纠正的版本各自往下游走，结果合并。
- **每次纠错发生时增量查询，不定期全量扫描。** 只算这一次纠错的影响，结果当场存为标记（归读取审计，与 read_log 同属本地运行状态）；
  下次相关读取时随结果带出，不依赖推送。

### 连接实例身份（第一版就做）

**每次接入签发一个独立凭证，由用户命名**（如"MacBook · Claude Code"）：本地模式写进该客户端的 MCP 配置，
远程模式对应一次单独的 OAuth 授权。所有写入、读取都归属到这个连接实例。

| 识别层次 | 依据 | 可信吗 |
|---|---|---|
| 哪个用户 | 本地凭证 / OAuth token | 可信 |
| 哪个客户端应用 | 远程 OAuth 的 client_id | 可信，只到应用一级 |
| 哪个实例 | 接入时签发的独立凭证 | 可信 |
| 客户端自报的名称、版本（clientInfo） | 客户端自报 | 不可信，只作参考 |
| 实例内的哪个会话 / 子 Agent | 请求里的任务标识 | 自报，只用于关联读写 |

理由：来源记录（"这次写入来自哪个 Agent、哪个客户端"）依赖它；成本低；以后做权限时直接挂在这个凭证上，不改结构。

- **第一版单节点**：连接实例由用户会话登记，**注册、改名与吊销都是日志事件**；scope 在签发时定下，第一版不能改（要改就吊销后重签）。多节点时（后续）：由签发它的节点登记，ID 全局唯一（带节点前缀），随同步传播；主节点接受"某节点签发、
  且已登记的连接实例"所做的离线写入；吊销在离线节点上线"先拉取再推送"时自然生效。

### 来源的完整性

| 记录 | 能否保证完整 | 怎么保证 |
|---|---|---|
| change_log：每次写入都被记下 | 能 | 唯一写入口（API）；数据库层只给 saveslot 的服务账号写权限，不开放裸 SQL；与业务写入同一事务；事件头链；用日志重放与业务表对账（见「完整性与溯源」：防误操作，不防能写存储的一方） |
| change_sources：派生写入的来源 | 能 | 规则由 saveslot 执行，输入由 saveslot 决定 |
| change_sources：基础写入的来源 | 部分 | 能保证"写入方交来的证据"被记下；保证不了它没用到别的信息 |

第三行是本质边界：信息一旦被 Agent 读走，就可能出现在它之后写的任何东西里，saveslot 看不到 Agent 的上下文。
**saveslot 保证 saveslot 内部的来源链完整；经过 Agent 的那一段只能检查与校验：**

| 层 | 查什么 | 例子 | 用模型吗 |
|---|---|---|---|
| 确定性校验 | 类型、单位、范围、预期版本、重复提交（幂等键） | 距离为负；同一请求提交两次 | 否 |
| 统计异常（第一版不判定、不产生事项；定义待定，见 architecture §14） | 与该用户自己的历史相比偏离过大 | 平时 5 公里，突然 50 公里 | 否 |
| 字面命中 | 写入的值是否在随附证据的原文里字面出现；只记录、不拒绝（见「来源级别」） | 证据"跑了 5 公里"，写入 5 km：命中 | 否 |
| 证据核对（第一版不做） | 写入的值与随附证据的意思是否一致 | 证据说"5 公里"，写入的是 15 | 是，后台异步 |

明显违规直接报错拒绝；可疑的进入待确认并标记（永不阻塞）。

**污点追踪（可选，不作为首版必选项）**：一次写入的来源除了声明的来源，再加上"同一任务里它之前读过的数据"
（取自 read_log，要求读写带同一任务标识）。被删数据视为有污点，读过它之后写入的东西视为"可能也带污点"。
会多算，所以推测出的来源只作"可能受影响"一级，不自动删除；隐私删除时列给用户决定。

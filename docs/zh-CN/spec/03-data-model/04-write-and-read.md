# saveslot · 数据层机制 · 04 写入与读取

> 数据层机制的一部分，目录见 [`README.md`](README.md)。文中「…」引用的节可能在同目录的其他文件里，按目录查。

## 写入：分工与请求

**Agent 负责"理解"，saveslot 负责"把关"。** Agent 把用户的话变成结构化的写入请求；saveslot 不理解语义，只做确定性的
检查、记录与执行。

### 写入请求

以"11-03 那次记错了，是 5 公里"为例，**模型只填这些**（字段名与完整参数以 contract「写入：意图与 op」为准）：

```yaml
sv: 3                                # 读取 / 查目录时拿到的 slot schema 版本，原样带回
evidence:                            # 证据段；不带则由 saveslot 把请求本身存为源数据
  - { kind: user_message, text: "11-03 那次记错了，是 5 公里" }
ops:                                 # 一次写入可含多个操作，同一 slot，整体一个事务
  - intent: correct                  # insert / update / correct / revoke
    table: runs
    row: r_01JC…                     # saveslot 生成的行 ID，读取时拿到（新增时不填）
    ver: v41.0                       # 读取时拿到的版本令牌，原样带回
    set: { distance: { value: "5", unit: km } }
```

**服务端补全**：

| 内容 | 怎么来 |
|---|---|
| 连接实例 | 来自凭证 |
| 请求键 | 见「幂等」 |
| 来源级别 | 按每段证据的种类推出：用户原话为"用户明确"，其余为"Agent 推断"；调用方可在证据段上声明级别；"外部权威"第一版不开放（见「来源级别」） |
| 任务标识 | 调用方可选传 |
| slot | 由表推出 |

- **意图四种**：新增 / 变更 / 纠错 / 撤销（撤销一行，保留历史）。**纠错必须显式标注**；状态类表上一次变更是"从现在起变"还是追溯修改，由 saveslot 按生效起点自动判断（见「时间 · 变更对之前读取的影响」）。隐私删除不是写入意图，是单独的操作（见「删除」）。
  事件类表没有生效起点：其上的"变更"是补充或修改信息，不触发纠错影响查询；值本来就记错了必须用"纠错"。
- **版本标记应带回**（变更、纠错、撤销）。不带时有兜底，兜底也没有才报 `read_first`：
  - 用 read_log 里**这个连接实例**（带了任务标识就只认同一任务）最近一次**逐行读到**的该行版本，回执里写明是兜底取得的；也没读过就拒绝（`read_first`），提示"请先读取该行"。MCP 新版是无状态协议，兜底靠数据里的读取记录，不靠协议会话。
  - **例外：按来源键的 op 不带 `ver`、也不带 `row`**（带了 `ver` 报 `invalid_argument`（`mutually_exclusive`）），所见版本由内核取这个字段的同步基线位置，不查读取记录、没读过也不报 `read_first`（见「按来源键写入」）。给没有来源键的行补键的 op 是普通的 `update`，照常带 `row` 与 `ver`。
  - 写入的前提里每条声明的 `ver` 用同一套规则（见「写入的前提」）。
  - **逐行读**有三种：`query`；`history` 的 `timeline` 里的**当前版本**（对单个目标）；**写入方自己的写入回执里已生效的 `ver`**——否则同一个 Agent 连改两次、第二次没带 `ver` 时会和自己冲突。
  - 不算逐行读的：`history` 的 `as_of` 读到的是过去的版本，返回的 `ver` 标"历史版本，不可用于写入"（否则此后改同字段的写入都会被当成并发，制造假冲突）；`sql` 的结果不带 `ver`（也不自动带行 ID，要行 ID 就在查询里选出来），派生值的组成视图（`composition`）只给行 ID、不给 `ver`；成为候选的写入回执里附带的 `current_ver`（当前生效版本）只供参考，不算读到。
- **schema 版本应当带回**（没带时用本连接实例最近一次读到的该 slot 版本兜底，回执写明）：只拒绝写到"自该版本以来定义发生了不兼容变化的字段"的请求，写的字段没变就照常接受（见「schema 版本演进」）。
- **已撤销的行不可写**（事件类表、无时间表）：变更、纠错报 `revoked`，附撤销它的写入号，提示用 `revert: {undo}` 恢复；再次撤销是无操作。状态类表上的撤销见「时间 · 状态类表上的撤销」。
- **清空一个可选字段**：把它的值写成 `null`。这是一次贡献，有值来源；必填字段不能清空（见「字段类型、同值与单位 · 清空字段」）。
- **值怎么校验、换算、舍入，两个值什么时候算相同**：见「字段类型、同值与单位」。

回执的状态有三种（与 contract「写入」一致），Agent 据此告诉用户：

- **`saved`**：全部字段已生效（或是无操作）；新版本 + 受影响的派生值（如"W45 22 → 12"）。生成了 `flagged` 事项时也是 `saved`。
- **`pending`**：有字段进了待确认（附原因与将被覆盖的段），或记为冲突候选（附当前值与冲突事项）；同一个 op 可以一部分字段生效、一部分未生效。
- **`job`**：转为后台作业（附作业 ID）。第一版不做。

**被拒不是一种回执状态，是报错**：附修正提示与出错位置（哪个 op、哪个字段），如"schema 已更新到 v2"。整次请求不生效。

#### 幂等

断流重发只生效一次，崩溃后也不会写两次。

- **请求键**：按"连接实例 + 任务标识 + 规范化后的请求内容"计算。规范化 = 调用方原始传参的确定性 JSON 编码（RFC 8785），不含兜底取得的 `ver` / `sv`。**只有一处例外：包含每条前提解析后的所见版本**（含兜底取得的）。"前提又变了、再核对一次、请求体逐字不变"是重申的正常用法；不含解析后的版本，第二次重申会在窗口里被当成第一次的重放，返回一个过时的结果。
- **只含按来源键 op 的请求不计算服务端请求键**：来源键本身就让重发幂等，同样的内容再交一遍得到的是 `unchanged`，不论在不在窗口内都逐条三方比较。显式幂等键照样可用；请求没产生事件时它不被记下，重发按来源键重新判定。含普通 op 的请求照旧计算请求键（见「按来源键写入」）。
- **显式幂等键**：调用方显式给幂等键时，请求键 = 连接实例 + 该键，另记一份**请求内容指纹**，用来发现"同一个键配了不同的内容"。
- **查重在同一事务里做**：内核只匹配幂等窗口内的键。窗口由服务层经调用上下文传入，内核按 `recorded_at ≥ now − 窗口` 过滤，结果确定、可重放。窗口长度是服务层策略，数值见 contract。
- **只对产生事件的结果去重**：被拒的写入不产生事件、不去重，重发时按当时的状态重新校验。
- **请求键与内容指纹由内容算出，所以是内容**：记在逻辑写入头的内容里，这次请求的任一段证据被删除时一起删（见「删除 · 由源数据派生出的内容」）。调用方自报的任务标识与显式幂等键本身是调用方写的文字，同样处理。

**重发时返回什么**：命中请求键时不再执行，回执带 `replayed: true`。

| 回执里的内容 | 重发时 |
|---|---|
| 写入号、每个 op 的逐字段结果（状态、值、区间）、当时得到的 `ver`、新建的行 / 实体 ID、当时生成或并入的事项 ID | 按日志重建，与当时一样 |
| 受影响的读取（由读取记录算出）、派生值的改前改后值（派生写入只记校验和） | 不重建，回执里列明省略了哪些；需要时自己读 |
| 事项 | 只给**当前状态**（未决 / 已解决及处理方式 / 已被取代），不给事项版本 |
| 原写入的内容已在某次已确认的删除里 | 回执"原写入已被删除，未重新写入"，不回显内容（见「删除 · 撤回与宽限期」） |

- 重发回执里的 `ver` 与事项都**不算"读到"**，不参与兜底。
- 写入进了待确认、后来被拒绝，窗口内原样重发：回执里事项的当前状态是"已解决 · 拒绝"，调用方看得出提议已被拒。
- **真的又发生了一次**（十分钟内买了两杯同价的咖啡）：服务端算的请求键包含证据原文，两次由同一句证据产生才会相同，那几乎总是重发。证据一字不差而确实是新的一笔时，调用方要带一个不同的显式幂等键；`replayed: true` 的含义是"没有新写入"，工具描述照此写明。

#### 一次写入的事件构成

一次请求在同一个事务里追加下面这些事件。字段级的定义见事件格式规格（[`../09-event-format.md`](../09-event-format.md)）；这里定的是有哪些、各几条、对外用哪个序号。

按追加的先后：

| 先后 | 事件 | 几条 | 记什么 |
|---|---|---|---|
| 1 | 逻辑写入头 | **每次产生事件的请求一条** | 请求键与内容指纹、`sv`、请求里 op 的总数、每个 op 的**原始传参**（不是无操作的字段：调用方交来的值与单位；无操作的字段：只列字段 ID；区间的原始写法；声明的前提）、入口时刻 `now` 与 `today`、`ver` 与 `sv` 是显式带的还是兜底取得的（按来源键的 op：逐字段的基线位置）、规则版本与策略版本 |
| 2 | 源数据 | 每段证据一条；没带证据时每个在事件里留下了东西的 op 一条"API 调用"（含前提的重申与清除） | 证据原文或文件引用 |
| 3 | 基础写入 | 逐个 op：每个 op 对每个受影响的行 / 实体一条 | 这次请求涉及、且不是无操作的字段。**一个字段的贡献是按区间排好的若干项**（事件类表与无时间表恒为一项），每项各一份：生效状态（见下表）、落账的值、**解析后的区间**（状态类表）、来源、字面命中；候选另记所见区间 |
| 3 | 待处理事项 | 紧跟引出它的那个 op 的基础写入：产生、并入、刷新、取代各一条 | 见「待处理事项」 |
| 4 | 前提变化 | 全部基础写入与事项事件之后：有变化时一条 | 哪些声明转为已变、转回没变（见「写入的前提」） |
| 5 | 派生写入 | 全部 op 之后：每个结果有变化的派生行一条 | 见「派生规则」 |

- **写入号**：逻辑写入头的 `seq`。它是这次操作的第一条事件，所以这次写入对外的一切序号都用它——回执的 `seq`、`ver` 里的序号、`timeline` 的 #n、`undo` 的 n、版本表的记录时间区间（见「编号」）。其余事件各自的 `seq` 不对外。
- **基础写入不记写入前的值，也不记写入后的整行。** 写入后的状态 = 之前的状态 + 本事件里已生效的各项；状态类表是把每一项的值赋给它解析后的区间，再把相邻且各字段都相同的时刻归成一段。这两步是确定的，不含判定。每多存一份值的副本，隐私删除就多一处要清；按时刻读走版本表。
- **逐项的生效状态**（一个字段通常只有一项；有多项的情形是：`undo`、回到合并基要写回几段不同的旧值；佐证的区间里一部分仍同值、一部分已被别人改掉；`undo` 只回掉仍生效的部分）：

  | 状态 | 含义 | `apply` 怎么落 |
  |---|---|---|
  | `applied` | 已生效 | 业务表、版本表、来源表 |
  | `corroborated` | 同值佐证：值没变，追加了来源 | 只进来源表 |
  | `candidate` | 冲突候选 | 不落；供 `timeline`、事项与删除重放使用 |
  | `awaiting` | 高影响，等待确认 | 同上 |

- **无操作的字段不是贡献**（与所见版本同值、没指证据）：基础写入事件里没有它，**日志里任何地方都不留它的值**，逻辑写入头只列出它的字段 ID。回执里它的结果是 `noop`。不留值的原因：这个值是调用方从 saveslot 读回来原样带上的，源头是更早的那次贡献；留一份副本，那次贡献被隐私删除时就多一处删不到。
- **未生效的写入照常记基础写入事件。** 之后的采纳、确认是一次由 `resolve` 触发的新写入，属于那次解决操作（头事件是解决事件，操作号是它的 `seq`），值来源是对原候选 / 提议贡献的引用。
- **解析结果以最近一次给出的为准**：一项贡献的区间、一次写入的首次创建标记是机械判定，隐私删除的重放可能改掉它们，新的结果记在那次删除事件里（见「删除 · 结果怎么落进日志」）。
- **全部字段都是无操作的请求**：照常存源数据、记逻辑写入头（含请求键与无操作字段的 ID 列表，重发按幂等重放）；不记基础写入事件；`ver` 不变；回执 `saved`，逐字段 `noop`。证据是资产，不因为没改值就丢掉。`undo` 全部被跳过时不同：照常记基础写入事件，里面只有回退记录、没有写回的项，`ver` 不变（见「回退」）。前提的重申与清除也没有基础写入，事件构成与此相同，头事件里多了声明。
- **例外：没变与被跳过的按来源键 op 不进任何事件**，只出现在回执里；一个请求里全部 op 都是这两种时，这个请求**不追加任何事件**——没有逻辑写入头、没有源数据、没有请求键，回执照给、不给 `seq`（见「按来源键写入」）。
- 请求级证据段没被任何 op 引用时照存为源数据，回执 `warnings` 提醒（`evidence_unreferenced`）。

#### 判定顺序

每个 op 按固定顺序过下面几步。

| 步 | 判什么 | 结果 |
|---|---|---|
| 1 | 与当前状态无关的校验：`sv` 兼容、类型、单位量纲、范围、新增时的必填 | 不过即报错，整次请求不生效 |
| 2 | 请求键查重（只含按来源键 op 的请求没有服务端请求键，只查显式幂等键） | 命中即返回原结果 |
| 3 | 同值：与所见版本相同的字段（见「删除 · 来源」）；按来源键的 op 与基线值比 | 无操作，或佐证 |
| 4 | `ver` 与冲突（见「冲突处理 · 冲突判据」）；按来源键的 op 所见版本是这个字段的基线位置 | 冲突的部分成为候选，生成或并入冲突事项 |
| 5 | 依赖当前状态的校验，**只对将要生效的部分做**：无值区间须带齐必填字段、`ref` 的目标、已撤销的行。前提的目标也在这一步校验，但对这个 op 带的全部声明做，不论 op 是否生效（见「写入的前提」） | 不过即报错 |
| 6 | 高影响（见「时间 · 高影响写入」） | 进待确认 |
| 7 | 疑似重复（见「疑似重复」） | 照常生效，生成"已标记"事项 |

按来源键的 op 在第 1 步之后先定位（键索引里有没有这个键）：命中已撤销的行、或这个键被宽限期内的删除占着时，这个 op 被跳过，不再往下判；第 3、4 步各换一处输入，其余不变（见「按来源键写入 · 三方比较」）。

第 5 步排在冲突判定之后是为了对称：带过期 `ver` 的写入遇到对方的撤销时，两种到达顺序都应当成为候选，而不是一种顺序报错。成为候选的写入不再单独判高影响；它若生效会覆盖的段列进冲突事项的影响。写入准入的估算见「派生规则」。

#### 同一请求里的多个 op

- op 按请求里的顺序执行，后面的 op 看得到前面 op 的结果。
- 对本请求里新建的行 / 实体，后面的 op 不需要 `ver`。常见的情形是新建一个预算实体并一次写两段。
- 对请求之前已存在的行 / 实体，同一请求里各 op 带的 `ver`（或兜底）表示"请求开始时所见的版本"；冲突判定只比请求之外、该版本之后的写入，本请求前面的 op 不算。
- 同值判断的基准：所见版本叠加本请求前面 op 的结果。
- **高影响的判定同样叠加本请求前面 op 的结果**：① 的保护范围含前一个 op 刚造出的变化点（见「时间 · 高影响写入」）；② 数"仍被引用"时，引用方在本请求前面已被撤销的，视为不再引用（见「引用字段」）。所以"同一请求先撤销三条明细、再撤销它们所属的那一餐"一次完成，不进待确认；反过来排，撤销那一餐时明细还引用着它，进待确认。op 的顺序会影响结果，这与"两次请求的到达顺序不影响结果"不冲突：那条说的是请求之间。
- **同一个来源键在一个请求里出现两次，整个请求被拒**（`invalid_argument`（`duplicate_external_key`），附两个 op 的下标）：让后面的 op 看前面的结果，会在同一个冲突单元上出现"一次写入的两个候选"，事项、采纳候选与合并基都没有为它定义（见「按来源键写入」）。
- 整个请求共用一个写入号，同一行 / 实体只得一个新 `ver`。
- 各 op 独立判定：一个 op 成了候选，不影响同请求里其他 op 生效。请求的原子性指事件一起提交。

#### 引用字段（`ref`）

`ref` 字段的值是同一 slot 另一张表里一行或一个实体的 ID。**引用不级联**：目标没了，引用方不被连带改动。

| 时机 | 规则 |
|---|---|
| 写入 `ref` 字段时 | 目标必须存在、在 schema 声明的那张表里、未撤销、不在某次已确认的删除里；指向状态类实体时，实体须至少在某段业务时间上有值。否则报 `validation_failed`（`ref_not_found` / `ref_wrong_table`）。目标在可见范围之外时与不存在相同，报 `ref_not_found`；`ref_wrong_table` 只在目标可见时报，否则"这个 ID 在别处存在"就从错误码里漏出去了。这是依赖当前状态的校验（判定顺序第 5 步） |
| 目标被撤销 | 撤销仍被引用的行是高影响 ②，进待确认（见「时间 · 高影响写入」）。确认之后引用方不动、保留原 ID；读取时这一行带 `dangling_ref` 标记（目标已撤销）。撤销被 `undo` 之后标记自然消失 |
| 目标被隐私删除整行删掉 | 不被引用挡住。引用方不动、保留原 ID（行 ID 是不透明标识，不是被删内容）；读取时这一行带 `dangling_ref` 标记（目标已删除）。删除预览单列仍引用被删行的行 |
| 引用方原样带回同一个 ID | 同值，按无操作或佐证处理，不重新校验目标 |

- **高影响 ② 怎么数"仍被引用"**：当前版本叠加本请求前面各 op 的结果之后，未撤销的行，其 `ref` 字段的生效值指向目标（状态类表：任何一段指向它都算）。引用方在本请求前面已被撤销的，视为不再引用。候选、待确认里的引用不算。
- 级联删除会让一次撤销或删除波及用户没点名的行，置空又等于替用户改了值；保留 ID 加读时的标记，信息不丢，决定留给人。

#### 疑似重复

schema 可以为事件类表与无时间表声明 `duplicate_keys`：一组或几组字段，"这几个字段都相同的两行多半是记重了"。它是软判据：命中只标出来，不拒绝写入。状态类表靠 `entity_key` 认实体，不能声明它。

| 问题 | 规则 |
|---|---|
| 什么时候判 | 只在**新增**且已生效时。变更、纠错把一行改成与别的行相同，不判。按来源键写入时，新增的行照常判，命中已有行不是新增、不判 |
| 和谁比 | 同一张表当前版本里未撤销、不在已确认删除里的行的生效值，含本请求前面的 op 刚新增的行。候选、待确认里的值不比 |
| 怎么算命中 | 某一组键的每个字段都同值（判据见「字段类型、同值与单位」）；任何一方在键字段上为空就不命中。几组键里任一组命中即命中 |
| 命中之后 | 写入照常生效，回执 `saved`。每个新增的行生成一个 `flagged` 事项，列出命中的行（最多 10 个，按最近写入排）与命中的是哪一组键 |
| 怎么处理 | `keep`：保留，标记撤掉；`revoke`：撤销被标记的那一行 |
| 事项什么时候自己关闭 | 被标记的行被撤销或被隐私删除；或它与列出的行都不再命中（见「待处理事项 · 不过期」的 `flagged` 例外） |

**与来源键互不替代**，可以同时声明：来源键回答"是不是来源系统里的同一条记录"，是硬的定位；`duplicate_keys` 回答"两行是不是记重了"，是软的提醒，跨来源也管用（Agent 按用户的话记了一餐，连接器又同步来同一餐）。手记的一行与同步来的一行记重了时，`keep` 是同一件事算两次；要让来源的修改进到手记的那一行，在一个请求里先撤销同步来的那一行，再给手记的那一行补键（见「按来源键写入 · 给没有来源键的行补键」）。

判定结果记进基础写入事件，重放不重判，**隐私删除时也不重算**：它是写入那一刻给人的一个提醒，不是数据的一部分。所以删除不会新生成 `flagged` 事项；被标记的行或它列出的行被整行删除时，事项按上表自己关闭。

#### 规则版本与策略版本

机械判定的结果写进事件、重放时不重算；但隐私删除要按删除后的状态重算这些判定（见「删除 · 重放规则」）。判定规则将来会变，所以每次判定都记下它用的是哪一版。

| 版本号 | 范围 | 标识什么 | 何时加 1 |
|---|---|---|---|
| 策略版本 | 按 slot | slot 策略的内容：冲突期间的生效值规则、秩表、额外的高影响清单（见「slot 包含什么」） | 每次 slot 策略变更 |
| 规则版本 | 按内核 | 全部机械判定的语义：挡点、同值、冲突判据、高影响判据、行 / 实体的存在、字面命中的核对器 | 任何一条语义变了。第一版是 1 |

- **记在哪**：每条逻辑写入头记这次写入判定时用的两个号；冲突、待确认事项的产生与并入事件记同样两个号；删除确认与撤回事件记重算时用的规则版本。两个号不含用户内容。
- **删除重放按哪一版**：每次旧写入按**它自己记下的**两个版本重算。旧事项不会因为内核升级或策略变更而改判。
- 想让旧事项改用新策略，由一条显式的**重判事件**触发（日志事件，结果可见）。第一版只有一个规则版本，不产生重判事件，事件类型留位。内核不再保留某个旧规则版本的实现之前，必须先对还用着它的写入做一次重判。

### 按来源键写入

**事件类表与无时间表可以在 schema 里声明来源键（`external_key`）：记录在来源系统里的标识。按来源键写入时，有则更新、无则新增；判定是"上次交来的值、当前值、这次交来的值"三方比较；什么都没变的同步不留任何事件。** 它为连接器而设：定时把外部系统的数据搬进来的程序，以一个连接实例的身份写入，每次同步都把同一批记录再交一遍，没读过要写的行，也带不回 `ver`。只靠 `duplicate_keys`，每小时同步一次就是每天几百个"已标记"事项，而且每条记录都真的重复落了一行。

- **不选"连接器先查再写"**：把"查到没有"和"新增"拆成两次调用，两个同步进程并发时照样重复，每条记录还多一次读取。
- **不复用 `entity_key`**：把它原样放开到这两类表，连接器要么每条记录先读一次（否则 `read_first`），要么靠兜底拿到一个与"来源变没变"无关的版本；撤销之后再按键写会把行写回来。这几处都改掉之后，两种表上同名的键就有了两套语义。
- **状态类表不开放**：它已有 `entity_key`，按时间段赋值的写入与"上次交来的值"如何对应要另行设计。

键的声明（表上的 `external_key`，1–4 个 `text` / `enum` / `integer` 字段，不能进字段组）与 schema 改动见「schema 文档格式」「改动分类与迁移手段」。写入时用到的两条：

- **唯一范围按表。** 一张表里，各键字段都有值、且没有让出键的行，键值两两不同。已撤销的行照样占着它的键，除非它的键已经转给了另一行（见下）。任何一个键字段为空的行没有来源键，不参与唯一。不按连接实例划分：scope 与 slot 范围签发后不能改，重签得到的是一个新的连接实例，按连接实例划分，重签之后同一条外部记录就全部重复新增一遍。不同来源系统的 ID 会撞，靠键里一个"来自哪个系统"的字段区分，由 schema 的作者声明。
- **键字段只能经 `external_key` 给出**（按来源键新增，或给没有来源键的行补一次键），之后不可改：`set` 里出现键字段且与行上的值不同，报 `invalid_argument`（`key_field_changed`）。键值按同值判据比较（`text` 是 NFC 之后逐码点相同，不去空白、不折叠大小写）。

#### 写法与定位

```json
{ "ops": [
  { "intent": "update", "table": "meals",
    "external_key": { "origin": "band_app", "external_id": "m-20261110-2" },
    "set": { "eaten_at": "2026-11-10T12:30:00+08:00", "energy": { "value": "650", "unit": "kcal" } } } ] }
```

- **op 的写法**：`external_key` 给出全部键字段的值（缺一个报 `invalid_argument`（`missing`））；意图是 `update` 或 `correct`；**不带 `ver`**（带了报 `invalid_argument`（`mutually_exclusive`））；不带 `row`；不能带写入的前提（`invalid_argument`（`premises_with_external_key`））。用在没声明来源键的表上报 `invalid_argument`（`no_external_key`）。
- **`insert` 不能带键字段**：`set` 里出现键字段报 `invalid_argument`（`insert_with_external_key`），提示改用 `update` 按 `external_key` 写入。否则同一个键可以被新增两次，"有则更新"就没有唯一的目标。
- **同一请求里同一个键出现两次，整个请求被拒**（`duplicate_external_key`，见「同一请求里的多个 op」）。连接器分页重叠时会这样；去重在连接器一侧是一行代码。
- **可以带临时名 `as`**：新增时绑定到新分配的行，命中已有行时绑定到命中的那一行；同一请求里后面的 op 可以用它写 `ref`。"单据 + 明细"两张表都由连接器同步时，一次请求就能写完。这个 op 被跳过时临时名不绑定任何行：后面用它写 `ref` 的 op 若也是按来源键的 op，一并跳过（`skip_reason: "ref_skipped"`）；若是普通 op，按 `ref` 目标不存在报 `validation_failed`（`ref_not_found`）。
- **定位**：内核在键索引里按键值找行。每个按来源键的 op 在回执里有一个 `outcome`：

| 找到了什么 | `outcome` | 落账 |
|---|---|---|
| 没有 | `created`：新增一行，分配行 ID | 普通的新增：`set` 须带齐必填字段，键字段的值来源是这次写入的证据；照常过疑似重复的判定 |
| 有，行未撤销 | `updated`（至少一个非键字段生效，可能另有字段成了候选）/ `unchanged`（全部字段无操作）/ `pending`（没有字段生效，有字段成了候选或进了待确认） | 见「三方比较」 |
| 有，行已撤销 | `skipped`（`revoked`，附撤销它的写入号） | 什么都不落，见「被撤销的行不复活」 |
| 有，但这个键被一项宽限期内的删除占着（或冻结） | `skipped`（`pending_deletion`，附删除 ID） | 什么都不落，见「删除 · 撤回与宽限期」 |

- 回执的 `status` 规则不变：有字段成了候选或进了待确认是 `pending`，否则 `saved`。`skipped` 不影响 `status`，另给提醒 `external_key_skipped`（列出被跳过的 op 下标）；回执另给按来源键 op 的五种结局计数。
- 行创建之后，照样可以按 `row` + `ver` 写它（Agent 读到这一行后改一个字段），那是普通写入，规则不变。
- **定位的结果记进事件**（行 ID 是元数据）；`apply` 照事件里的行 ID 落账，不做定位。从空存储重放、在另一个后端重放，每个进了事件的 op 落到同一行。

#### 给没有来源键的行补键

两种情形：用户先让 Agent 手记了一条，之后连接器才同步到来源里的同一条记录——把来源键补到手记的那一行上，同步就会命中它，不再新增一行；或者两行都已在库里（手记一行、同步又新增了一行）——撤销同步来的那一行，再把它的键**转**给手记的那一行。

```json
{ "intent": "update", "table": "meals", "row": "r_M…", "ver": "v41.0",
  "external_key": { "origin": "band_app", "external_id": "m-20261110-2" } }
```

- **写法**：普通的 `update`（带 `row` 与 `ver`，可以同时带 `set` 改别的字段，也可以带前提），另带 `external_key`。只有这种写法能同时给 `row` 与 `external_key`。
- **条件**：这一行未撤销、全部键字段都没有值。行已有键时：与已有的键相同是无操作，不同报 `invalid_argument`（`key_field_changed`）。
- **这个键在键索引里的状态决定结果**（从上往下，取第一条成立的）：

| 键的状态 | 结果 |
|---|---|
| **冻结**：有一项宽限期内的删除，会去掉这个键在任何一行上的贡献（持有它的行，或它转来之前的原行） | `invalid_argument`（`external_key_in_use`，附删除 ID）。冻结期间按这个键的同步 op 一律跳过（`pending_deletion`） |
| 没被占用 | 补上 |
| 被一行**未撤销**的行占着 | `invalid_argument`（`external_key_in_use`，附占着它的行 ID——那一行在同一张表里，本来可见）。要转，先撤销它 |
| 被一行已撤销的行占着，而那一行的键是**创建时就带着的**（按来源键新增的行） | **键转到这一行**，被撤销的那一行不再占键。它的键字段的值仍留在它自己行上（键字段不可改），只是不参与唯一、不在键索引里。事件里记下键从哪一行转来 |
| 被一行已撤销的行占着，而那一行的键是**补键得来的**（含转移得来的） | `invalid_argument`（`external_key_not_transferable`，附占着它的行 ID）。**不连环转移** |

- 冻结与"已撤销的行占着"都包括同一请求里前面的 op 刚做的撤销（后面的 op 看得到前面的结果）。所以把两行对上的用法是一个请求两个 op：先撤销重复的同步行，再给手记的行补键。
- **为什么不连环转移**：允许 A → B → C 的转移链，删除中间一次补键时就要回答"键回到谁"，链上每一行都可能同时被认为占着键。只让创建时带着键的行让出，转移链长度恒为 1：持有者要么是原行，要么是唯一那一次补键的行。用新的原因码而不用 `external_key_in_use`：那个码的改法是"先撤销占着它的行"，这里撤销已经做了也没用。
- **为什么删除未决时冻结**：宽限期内删除可能被撤回，也可能到期执行；两种结局下键应当落在不同的行上。冻结期间不转移、不让同步命中，到期或撤回之后只剩一种结局，再按它定持有者。
- **效果**：键字段的值作为这次写入的普通贡献落账（生效，来源是这次写入的证据），键索引的条目指向这一行。只能补一次：补上之后这一行的键不能改，被撤销后也不能再转出去。这不放松"键只能加在新字段上"的理由：被补的键字段在这一行上原本没有值，不存在"隐私删除让它落回一个已被占用的旧值"。
- **不会复活**：键转走之后，同步命中的是补了键的那一行；被撤销的那一行不再被任何同步命中，也就不会因同步回来。
- **让出了键的被撤销行不能再重新存在**：任何会让它重新存在的写入——`undo` 那次撤销、带 `include_later` 的回退连带回掉那次撤销、确认一项这样的待确认回退——在生效时报 `invalid_argument`（`external_key_transferred`，附现在持有这个键的行 ID）。否则它带着同一个键回来，一张表里就有两行同键。冻结期间它仍算让出了键。

**持有者怎么定**（键索引照此维护；一个键在键索引里至多一条，状态是"在"或"冻结"）：

1. 没有转移时：持有者是键字段生效值等于这个键、且没有让出的那一行（含已撤销的）。
2. 有转移（某一行的补键记下了键从行 S 转来）时：补键那次写入的键贡献仍在，持有者是补了键的那一行，S 不占键；那份贡献被删除**执行**去掉之后，持有者回到 S（若 S 的键贡献仍在；S 仍是已撤销的），否则这个键没有持有者。
3. 有一项已确认、未执行的删除会去掉第 1、2 条里任何一份键贡献时，条目"冻结"，持有者仍按删除前的状态算；撤回删除，冻结解除，持有者不变；删除执行，按删除后的状态重算第 1、2 条。
4. 补了键的行就是持有者，它的键不能再转，所以任何时刻只有 S 与补了键的那一行两个候选，第 2 条只选其一。

**转移键与 `undo`、删除**：

| 情形 | 结果 |
|---|---|
| `undo` 原行的那次撤销（键已转出，冻结与否都一样） | 拒绝，`external_key_transferred` |
| `undo` 那次补键 | 来源键字段不进任何回退记录，回退碰不到键：键留在补了键的那一行。这次补键若没有改别的字段，报"没有可撤回的改动" |
| 隐私删除补键那次写入的证据：宽限期内 | 冻结：不能转移，按这个键的同步被跳过；持有者仍是补了键的那一行，原行仍算让出了键（`undo` 它的撤销照样被拒） |
| 同上：撤回这项删除 | 冻结解除，回到删除前：补了键的那一行持键 |
| 同上：到期执行 | 补了键的那一行失去来源键；持有者回到原行（已撤销，照常占键）。之后的同步命中原行、被跳过；原行是创建时带键的，可以再被转一次；`undo` 它的撤销不再被拒，它带着键回来，补了键的那一行已经没有键 |
| 隐私删除原行得到键的证据：宽限期内 | 同样冻结 |
| 同上：到期执行 | 原行失去键值（或整行删除）；补了键的那一行仍持键。之后补键那次的证据也被删除时，这个键没有持有者 |
| 原行的撤销 | 是人的决定，删除重放照记录，删除不会让被撤销的原行重新存在 |

**例**（`meals` 表，键 K = `(band_app, m-2)`，连接器每次不带证据）：

| 操作号 | 谁 | 请求 | 结果 |
|---|---|---|---|
| #30 | 连接器 | 按 K 写 `eaten_at`、`energy` 650 | `created`：r_S。K → r_S |
| #40 | Agent | 用户说"中午吃了鸡胸肉沙拉，约 600 千卡"，`insert` 一行 | r_M，`energy` 600；疑似重复命中 r_S，生成"已标记"事项 |
| #45 | Agent | 用户："这两条是同一顿，留我记的那条"。一个请求两个 op：撤销 r_S；给 r_M 补键 K | 后一个 op 看得到前一个的结果：K 被已撤销、创建时带键的 r_S 占着，没有冻结 → 转给 r_M。K → r_M |
| — | 连接器 | 同一条，650 | 命中 r_M：`energy` 的基线值沿用 r_S 上的 650，与它相同 → `unchanged`，r_M 仍是 600。不追加事件 |
| #60 | 连接器 | 同一条，来源改成 700 | 命中 r_M：700 与基线值 650 不同；基线位置 #45 之后没人改过 `energy` → `updated`，r_M 变为 700 |
| — | Agent | `undo` #45 对 r_S 的撤销 | 拒绝：`external_key_transferred`（K 在 r_M） |
| — | Agent | 撤销 r_M；再给另一行 r_Z 补键 K | 拒绝：`external_key_not_transferable`（K 在已撤销的 r_M 上，是补键得来的） |

每一步键索引里 K 至多一条，持有者至多一行。

#### 三方比较

连接器没有读过这一行，带不回 `ver`；它知道的只是"来源系统现在说这条记录是什么"。所以判定比的是三样：**上次按来源键交来的值**（基线）、**当前生效值**、**这次交来的值**。"同步贡献""已生效的同步贡献"与逐字段的**同步基线**（基线值、基线位置，含键转来时沿用原行的基线值）是冲突判据的一部分，定义见「冲突判据」，这里不重复。要点：候选也是同步贡献，计入基线值；回到冲突前与 `undo` 写回的项不是同步贡献；被回掉的同步贡献不再是已生效的，不计入基线位置；基线按字段取，不按冲突单元取。键字段不在其内。

判定就是「判定顺序」，只换掉两处输入：

| 步 | 普通写入 | 按来源键写入 |
|---|---|---|
| 同值（第 3 步） | 与所见版本上的值比；同值且指了证据是佐证，否则无操作 | **与基线值比**。与基线值相同 → 来源没变：**不论是否指了证据**，当前生效值与它不同时一律是无操作（不重提）；当前生效值也与它相同时，指了证据是佐证，没指是无操作。没有基线值的字段与基线位置上的值比，规则同普通写入（补键的行第一次被同步命中时多半如此；键转来的除外，见上） |
| `ver` 与冲突（第 4 步） | 所见版本 = 带回或兜底的 `ver` | **所见版本 = 这个字段的基线位置**。之后的判据不变：基线位置之后这个字段所在的冲突单元被别的操作改过 → 候选，生成或并入冲突事项；没被改过 → 生效 |

逐种情形（一个字段，上次同步交来 600）：

| 当前生效值 | 这次交来 | 结果 | 说明 |
|---|---|---|---|
| 600 | 600 | 无操作 | 来源没变。最常见的情形，不产生基础写入事件 |
| 600 | 650 | 生效 | 来源变了，本地没人动过 |
| 500（用户在 saveslot 里改过） | 600 | 无操作 | 来源没变。**用户的改动不会被每次同步盖回去** |
| 500（用户改过） | 600，且用 `evidence_by_field` 指了证据 | 无操作 | 同上：与基线值相同，指了证据也不重提 |
| 600 | 600，且指了证据 | 佐证 | 来源没变、本地也没变：这次交来的证据加为来源 |
| 500（用户改过） | 650 | 候选 | 来源变了，本地也改过：不覆盖，记为候选，生成冲突事项 |
| 500，且上一行的 650 候选仍未决 | 650 | 无操作 | 基线值已是 650（候选也是同步贡献）。**同一个候选不会每次同步再并入一遍** |
| 500，650 的冲突已按"保持生效值"解决 | 650 | 无操作 | 同上：基线值是 650 |
| 650（650 的冲突已按"采纳候选"解决） | 700 | 生效 | 采纳时搬运出的那一项是已生效的同步贡献，基线位置前移到那次解决 |
| 500，650 的冲突已按"保持生效值"解决 | 700 | 候选 | 来源又变了，再问一次人 |
| 500，650 的冲突已按"回到冲突前"解决 | 650 / 700 | 无操作 / 候选 | 写回的 500 不是同步贡献：基线值仍是 650，基线位置不动。**用户拒绝过的来源值不会在下一次同步时直接生效** |
| 600（一次同步写下的 650 被 `undo` 回掉） | 650 / 700 | 无操作 / 候选 | 被回掉的 650 仍计入基线值；它不再是已生效的，基线位置回到更早的那次同步，之后有这次 `undo` |

- **意图**：`update` 是默认的写法（来源系统里这条记录现在是这样）；连接器明确知道来源系统把它标成了更正时可以写 `correct`，值生效时照常触发纠错影响查询。新增时意图照记，另记创建标记，与按 `entity_key` 创建实体的做法一致。事件类表与无时间表上 `update` 不触发纠错影响查询，所以日常同步不会给读过这些行的任务打标记。
- **内容完全相同时不留任何东西**：全部字段都是无操作的 op，`outcome` 是 `unchanged`，行的 `ver` 不变；这个 op 不进任何事件，也不为它存源数据。一个请求里全部 op 都是 `unchanged` 或 `skipped` 时，这个请求不追加任何事件，回执照给（见「事件里怎么记」）。
- **键字段**：命中时键值与行上的相同，是普通的无操作，**不记佐证**，也不参与同步基线。键字段只在得到键的那次写入里有贡献（按来源键新增，或补键）；那次写入的源数据被删，键随之消失（见「删除 · 删除之后」）。不让之后的同步给键字段记佐证来撑住键：那只在每个必填字段都恰好被改过时才有用，却会把键字段带进同步基线与回退记录，造出同一键两行的路径。
- **处理过的冲突不能撤回重开**：事项处理之后（含"保持生效值"），第一版没有办法让它回到未决。"保持生效值"不触发写入，没有可 `undo` 的东西；采纳候选、回到冲突前触发的写入可以 `undo`，值回到处理前，但事项保持已解决。由此，用户按"保持生效值"或"回到冲突前"拒绝过的来源值，之后不会被同步反复提出——这正是基线值包含候选的目的；用户改主意要用那个值，直接写入它即可（普通写入，不是同步贡献，基线不变）。
- **冲突事项**：与普通写入相同——目标是（行，冲突单元），一个目标最多一个未决事项，候选并入，三种处理方式不变。候选"所带的 `ver`"是这个字段的基线位置；一个冲突单元（字段组）里各字段的基线位置不同时取最早的那个，与所见版本的取法一致（保守：多查出并发）。合并基照常取各候选所带版本中最早的。
- **来源级别**：没带证据时是"API 调用"，级别"Agent 推断"；带证据时按证据种类。第一版冲突一律保持当前值，级别不参与判定。
- **高影响**：事件类表与无时间表上没有覆盖类的高影响；按来源键写入不进待确认，除非将来 slot 策略指定了额外的高影响表（后续）。

#### 被撤销的行不复活

用户说"这条不对，删掉"，Agent 撤销了这一行；下一次同步里这条外部记录还在。

- **已撤销的行仍占着它的键**：撤销只改"存在"，键字段的值留在行上，键索引包含已撤销的行。唯一的例外是它的键被转给了一行补键的行：那之后它不再占键，同步命中的是那一行，它自己也不能再重新存在。
- **命中已撤销的行：这个 op 被跳过**（`skipped`，`revoked`，附撤销它的写入号）。不新增、不恢复、不记贡献、不存源数据，这个 op 不进任何事件；同一请求里的其他 op 照常执行。
- **不报错**：普通写入写到已撤销的行报 `revoked`、整个请求不生效，那是因为调用方点名了这一行，应该知道它的状态。连接器是整批交来的，不知道其中哪条被用户撤销过；一条被撤销的记录不应让同批的几百条都失败，更不应每小时失败一次。
- **要恢复，由人来**：按行 ID `undo` 那次撤销。之后的同步照三方比较继续；撤销与撤回都改过"存在"，它们与每个冲突单元相交，所以恢复之后来源若变了，第一次会成为候选。
- 被跳过的 op 不改变同步基线。

#### 与已有机制的关系

| 机制 | 关系 |
|---|---|
| 疑似重复（`duplicate_keys`） | 互不替代，可以同时声明（见「疑似重复」）。按来源键命中已有行不是新增，不判；按来源键新增的行照常判 |
| 幂等 | 来源键本身就让重发幂等：同样的内容再交一遍得到 `unchanged`。所以只含按来源键 op 的请求不计算服务端请求键；显式幂等键照样可用。含普通 op 的请求照旧计算请求键（见「幂等」） |
| 版本标记 `ver` | 按来源键写入不带；所见版本由内核取基线位置，记进事件。回执照常给出行 ID 与 `ver`，但它对按来源键的后续写入没有用处 |
| `ver` 的兜底 | 不适用：不查读取记录，没读过也不报 `read_first` |
| 冲突判定 | 判据不变，只是所见版本的来历不同。按来源键的写入所见版本由内核按日志位置取，同一租户写入串行，结果只取决于日志 |
| 回退 | `undo` 一次按来源键的更新：照常。被回掉的项仍是同步贡献，基线值不变，所以来源没变时同步不会把它再写回来；它不再是已生效的同步贡献，来源变了时成为候选。目标是创建那次写入时照旧报 `invalid_argument`，用撤销。**来源键字段不进任何回退记录**（`undo`、`take_previous` 列项时跳过它们）：写回项因此从不触及键字段，"撤回一次撤回"也造不出两行同键 |
| `ref` | 别的行可以按行 ID 引用按来源键创建的行；同一请求里也可以用按来源键 op 的临时名，新增与命中都绑定 |
| 写入的前提 | 按来源键的 op 不能带前提；连接器写的行要声明前提，由 Agent 读到之后另行重申 |

#### 事件里怎么记

**键值不进事件头，也不进元数据块与块路径**：它是内容，只出现在键字段自己的数据块里，与任何字段值一样记来源、在级联范围内。

- **什么进事件**：一个按来源键的 op 只有在它留下了东西（新增，或命中且至少一个字段不是无操作）时才进事件；`unchanged` 与 `skipped` 的 op 不进任何事件，只出现在回执里。一个请求里全部 op 都是这两种时，整个请求不追加任何事件——没有逻辑写入头、没有源数据、没有请求键；**调用方显式带的证据也不存**（没有任何东西需要它），回执如实写明证据没有存下；回执不给 `seq`，请求带的显式幂等键也不被记下（重发按来源键重新判定，结果相同）。
- 逻辑写入头另记请求里 op 的总数（没进事件的 op 留空号，重放时说得出末尾省略了几个）；每个进了事件的 op 记"按来源键定位"、定位到或新分配的行 ID、补键时键从哪一行转来；所见版本的来历记为"按来源键"，另记逐字段的基线位置（只有操作号，判定与删除重放用它）。键的原始值只在得到键的那次写入里记。
- **"API 调用"源数据**照现行的粒度：没带证据时每个在事件里留下了东西的 op 各一条，只含该 op（无操作字段的值照旧不记）。一个来源键对应来源里的一条记录，删掉一条同步来的记录的源数据，只去掉这条记录的贡献，不牵连同批的别的记录。
- **没变的同步不留东西**：每小时同步几百条没变的记录，不应每次留下一条逻辑写入头、一个含全部记录内容的请求键与一批只有字段名的源数据。不留事件，也就没有一个"随别的记录的证据才删得掉"的请求键，没有"这条记录在删除之后又被送来了"的关联元数据。
- **含普通 op 的请求**照旧计算服务端请求键，按原始请求体算，其中按来源键 op 的内容只随这次请求自己的证据删除（已知边界，见「推论」的"不漏删"一条）。连接器把按来源键的 op 与普通 op 分开请求即可避开。显式幂等键的内容指纹同属这条边界。
- **幂等重放的回执**按日志重建：进了事件的 op 的结果从事件得出；没进事件的 op 日志里没有，重放回执里只给下标并标明省略（`unrecorded_ops`），五种结局计数里这两项也不给。不按当前状态重算：那会让同一请求的两次回执不同。只含按来源键 op 的请求只有带显式幂等键时才会被重放。
- **键索引**（`external_keys`，表 ID 与键值 → 行 ID，另有一列状态：在 / 冻结，冻结时记删除 ID）是由日志得出的物化状态，`apply` 按确定的规则维护，不含判定：一行各键字段的生效值变了（新增、补键、删除结果、撤回结果、schema 切换）按新值改这一行的条目，撤销不动条目；补键记下了键从哪一行转来的，条目改指补键的这一行，原行标为"已让出"；删除确认去掉了某一行上这个键的贡献，条目转为冻结、持有者不变，撤回时转回"在"，到期物理删除时按"持有者怎么定"重算。它由内容得出，列入明文残留清单（见「删除 · 删除之后」）。
- 同步基线与定位是机械判定，属于第一版的规则版本 1。

### 不变量：每次写入都有源数据

- 带了证据 → 证据存为源数据。
- **没带证据**（如脚本直接调 API）→ 把这次请求本身存为源数据（类型"API 调用"，**每个在事件里留下了东西的 op 各一条**、只含该 op，这样按行删除时能按行切开；前提的重申与清除在事件里留下了声明，也算在内），声明级别自动降为"Agent 推断"。
  证据因此"必须有"，但由 saveslot 兜底，不会卡住写入方。
- **没进事件的 op 不存**：按来源键的 op 没变或被跳过时，不为它存源数据——源数据是贡献的来源，没有贡献就没有东西需要它。全部 op 都是这两种的请求不产生任何事件，也就没有源数据——调用方显式带的证据也不存，回执如实写明；它没有基础写入，这条不变量照样成立。请求产生了事件时，调用方显式带的证据照存（证据是资产），没被任何进了事件的 op 引用时回执照常给 `evidence_unreferenced`。
- **由解决事项触发的写入**（撤销被标记的行、采纳候选、回到冲突前、差异清单里带值）同样要有源数据：用 `resolve` 随附的证据（如用户那句"后来那条是重复的"）；
  没带就把解决请求本身（含 `note`）存为"API 调用"源数据。**解决请求带了 `note` 时，不论是否触发写入、是否另带了证据，都把请求本身存为一条"API 调用"源数据**，解决事件以操作来源引用它：`note` 因此能经普通的隐私删除清除，事项详情回显的 `note` 也从这里取。它们多数只是**操作来源**：采纳候选的值来源是候选写入的来源；只有差异清单里 `set` 带的值，来源才是这次解决的证据（见「删除 · 来源」）。
- **只交原始内容、没有结构化的值** → 存为源数据，状态"待抽取"，由 saveslot 的 worker 按当前 schema 抽取
  （需用户自带 API Key）；抽取结果按"Agent 推断"写入，与已确认值不同时进待确认。**不进第一版**（进阶能力，见 positioning「后续规划」）。

由此"每条基础数据都能追溯到源数据"由工程保证，前面所有机制都建立在这一点上。

### 来源级别：声明级别与字面命中

**写入一律先收，不因核对不过而拒绝；可信度单独标出，在写入时判定并记进事件。** 源数据是资产，不能因验证不过丢掉。

| 字段 | 谁给 | 取值 |
|---|---|---|
| 声明级别 | Agent 写入时（按证据段） | 用户明确 / Agent 推断 / 外部权威（第一版不开放） |
| 字面命中 | saveslot 在写入时判定 | 每段证据对一个字段：命中 / 未命中 / 不适用。字段的级别由它们现算（见下） |

**字面命中核对的是"值在证据原文里出现过"，不是"证据断言了这个值"。** 它是唯一不用模型的核对路径：否则没配 API Key 的用户，声明的级别永远没有支撑，"用户明确优先"永不生效。"值与证据不一致"要模型核对才会得出，第一版不出现；将来的后台模型核对产生单独的"核对结果"事件，不改原事件。

**命中规则**（核对器版本 `literal@1`；比较前证据文本先做 Unicode NFC、全角转半角）：

| 字段类型 | 命中当且仅当证据文本里 |
|---|---|
| `quantity` | 有一个数字记号与请求里的原始数值相等，后面紧跟（可隔空白）请求原始单位在同义表里的一种写法（如证据"跑了 5 公里"，写入 distance = 5 km） |
| `integer`、`decimal` | 有一个数字记号与写入值相等 |
| `date` | 有同一天的日期写法：`YYYY-MM-DD`、`M月D日`、`M-D`、`M/D`（带年份时年份须相同）。"今天""上周三"这类相对说法不算 |
| `enum` | 包含该枚举值的字面（不分大小写） |
| `text` | 包含写入的文本（去首尾空白后，长度至少 1） |
| `zoned_datetime`、`boolean`、`ref` | 不适用 |

- 数字记号：阿拉伯数字，可带千分位与小数点，比较数值不比较写法；`literal@1` 不认中文数字。单位的认可写法见「字段类型、同值与单位 · 单位同义表」（`units@1`，是 `literal@1` 的一部分）。
- 每段证据对一个字段的结果有三种：命中、未命中、不适用（字段类型不适用，或值为空）。
- **记录粒度**：基础写入事件里按"字段的每一项 → 该项引用的每段证据 → 命中 / 未命中 / 不适用"记，另记核对器版本（含同义表版本）。`source_ref` 按被引用的原文核对。重放时用记下的结果，不重新核对（与疑似重复同样处理）。
- **字段的级别不落盘，现算**：字段仍在的值来源里，命中的那些段的声明级别取最高；一段都没命中则为"未命中"。按段记录是为了删除之后还能重算。
- **它只在一处起作用：冲突裁决**（「冲突处理 · 系统裁定」，后续）。第一版照常判定并记录，不参与任何判定——这些信息事后补不回来。
- 证据段可带可选的陈述时间 `stated_at`（用户是什么时候说的；不给就是未知），随证据存、随证据删，同样只记不用。
- 这是为了让裁决结果可复核、可重放，不是对 Agent 的不信任：saveslot 默认 Agent 的输入可信（positioning「数据层」），不判断内容是否属实；字面命中比的也只是 Agent 自己交来的证据原文。
- 高影响操作本来就要确认，不依赖级别是否准确。
- **"外部权威"由凭证授予，不由写入方自报。** 第一版不开放：声明它一律报 `not_in_this_version`。将来开放时：能否声明这个级别由连接实例被授予的权限决定，授予只能由用户会话在签发时做，写入方不能自报，也不能由别的连接实例转授；没被授予而声明了它，整个请求被拒，不静默降级成"Agent 推断"（降级会让写入方以为自己的值带着权威级别）；授予记在主体登记事件里，与 scope、slot 范围同处，级别照旧按证据段记在源数据里，所以"这条源数据的级别是不是由有权的主体声明的"只凭日志就能核对。授予的形式、能否按 slot 分别授予等细则随系统裁定一起定。

### 回退到某个版本

**回退就是一次新写入**：把值写回某个旧版本的值，历史不被改写。它的值来源是对旧版本里该处生效的那几个贡献的引用，回退请求只是操作来源（定义见「删除 · 来源」，删除时怎么算见「删除 · 重放规则」）。**回退（`undo`）与回到合并基（`take_previous`）是同一种操作——回掉——的两个取法**，由三样东西构成：回退记录（回掉哪些项，写入时逐项列定，照记录）；范围（这些项的区间扣除仍被之后的操作盖住的部分，`take_previous` 再与事项的区间取交；隐私删除之后在重放里重新求）；取值的位置（`undo` 是被撤回的操作之前，`take_previous` 是记下的合并基；位置照记录，那里的值在重放里重新求）。该处本来没有任何贡献时，写回的就是"没有值"；该处当时在一次撤销造成的空洞之内时，写回一条不带内容的项（只做登记）：被回掉的填值不再生效，空洞重新露出，撤销之下的值没有动。事件类表、无时间表上一项是不可分的整体：仍被盖住时整项不回掉。回掉一次撤销写回的是"恢复存在"，回掉一次"恢复存在"写回的是撤销。权威定义是「删除 · 重放规则 · 回掉的权威定义」里的伪代码。

- **回退 ≠ 撤销**：状态类表上带区间的撤销 = 这段时间没有值；"恢复成原来的计划"要用回退。
- **回退目标的内容已删除**（物理删除，或宽限期内的逻辑删除）时，新的回退请求报 `invalid_argument`（"目标版本的内容已删除"）。删除重放里已有的回退不受这条影响。
- 回退出来的值抹掉了已记录的变化点时（状态类表上常见），照常属高影响 ①。**例外：`undo` 一次撤销不算 ①**——它恢复的正是那次撤销去掉的值，两端的变化点回到撤销之前的样子，是撤销的后悔路径。

#### 撤回某次写入（`undo`）

调用方只给"撤回写入号 n"。由内核取出那次写入对这一行 / 实体的各项贡献与它们**当前的解析区间**（写入时记下的，或之后被隐私删除的重放重新解析过的，以最近一次为准），在这些字段、这些区间上回到第 n 次写入之前的值。之前的值在一段区间里可以是几段不同的值（例：第 n 次写入盖住了 5000 与 4000 两段），这次回退在该字段上就有几项，各自引用被搬运的贡献。调用方不用自己找"调整之前的那个版本"，也不用自己给区间。同一请求里多个 op 改了同一行 / 实体时一起撤回。

- **默认只撤回第 n 次写入仍然生效的部分**：它写的值仍是生效值的那些字段与区间段，回到第 n 次写入之前的值；已被后来的写入覆盖的部分跳过，回执逐项列为 `skipped_superseded`（附覆盖它的写入）。用户说"撤回那次调整"，一般不是想连别人后来的改动一起撤。全部被跳过时这次写入不改任何值、`ver` 不变，回执照常列出跳过的部分；基础写入事件照常记，里面只有回退记录。
- **要连后来的写入一起回掉**，须显式传 `include_later: true`：后来的写入在相交的字段与区间上一并回掉。**无论事件类表还是状态类表，只要回掉了后来的写入，一律按高影响处理**：进待确认，回执列出会被回掉的写入（高影响清单 ④，见「时间 · 高影响写入」）。**待确认的回退被确认时，回掉哪些项按确认时的状态重新列定**（事项刷新后多列出的写入也在内），记在确认触发的那次写入里；提议时列的只用于事项与预览。
- **`undo` 不做 `ver` 冲突判定，`ver` 可以不带。** 调用方点名了要撤回的那次写入，默认只撤回它仍然生效的部分，别人在它之后写的值不会被动；要动就得 `include_later`，那已经是高影响。`undo` 仍要过依赖当前状态的校验（行已撤销时报 `revoked`）与高影响判定。
- `undo` 回掉了哪些项，是这次人的决定，逐项记在回退记录里，删除重放时照记录（目标操作的全部项都列入，当时整项被跳过的也在内，来源键字段除外——键在得到之后不可变，没有可回退的东西；带 `include_later` 时连带回掉的后来写入也逐项列入；当时跳过了哪些另外标出，只供历史与回执使用）；这份记录只有事件序号、字段与下标，不随任何删除清除。**被回掉的项是否生效以这份记录为准，不看写回了什么。** 在哪些业务时间上回掉，由这次回退写回各项的区间给出；这些区间是求得的内容，隐私删除之后在重放里重新求（被回掉的项在重放里的区间，扣除仍被之后的操作盖住的部分），旧的区间清除、由删除事件重新给出（见「删除 · 由别的贡献求得的内容」）。
- **第 n 次写入是什么**：

  | 第 n 次写入 | `undo` |
  |---|---|
  | 插入；按 `entity_key` 的首次创建；按来源键的新增（由"创建"标记识别；标记是机械判定，隐私删除让它变了时以删除事件里记下的为准） | `invalid_argument`，提示改用撤销 |
  | 冲突候选、待确认的写入（从没生效） | `invalid_argument`，提示用 `resolve`（`keep_effective` / `reject`）；一次写入部分字段生效、部分成为候选时，只撤回生效的字段 |
  | 只做了同值佐证、全部是无操作、当前没有任何写回项的 `undo`（全部被跳过）；前提的重申与清除；只补了来源键、没改别的字段的写入 | `invalid_argument`：没有可撤回的改动 |
  | 撤销 | 可以：行（状态类表：该区间）重新存在，回到撤销前的值。例外：这一行的来源键已转给了另一行时，报 `invalid_argument`（`external_key_transferred`，附现在持有这个键的行 ID），见「按来源键写入」 |
  | 回退、`undo`；系统裁定；由 `resolve` 触发的写入（确认、采纳候选、回到冲突前、`flagged` 的撤销） | 可以，按普通写入处理 |
  | 删除确认、撤回删除的操作号 | `invalid_argument`；撤回删除用 `deletion` 事项的 `cancel` |
  | schema 切换的操作号 | `invalid_argument`（`undo_target`），提示提交新的 schema 草稿：切换不是一次写入，常量补出的项也从不列进回退记录 |
  | 不是这一行 / 实体的写入 | `invalid_argument` |

- **意图可以省略**：默认沿用第 n 次写入的意图；第 n 次是撤销或系统裁定时默认 `correct`（那次结果不对，之前读到的值受影响）；由 `resolve` 触发的写入沿用被执行的那次写入的意图。调用方仍可显式给 `update` / `correct`。

#### 显式给目标版本（`revert: {to, fields}`）

> **不进第一版**（高级用法）。与 `undo` 共用同一条内核路径，只是目标版本、字段与区间由调用方给。

- 意图由调用方指定（纠错或变更），必须带预期版本。只回退调用方指定的字段，不会把之后别的来源写入的其他字段一起回掉。
- **状态类表上必须带业务时间区间**（`valid_from` / `valid_to`）：按目标版本在该区间内的各段原样恢复，一次回退可以产出多段；区间外的段不动。不带区间报 `invalid_argument`——否则会把区间外别人后来写的值一起回掉。
- **目标必须是同一行 / 实体的版本**：`to` 给出的操作号必须是被回退的这一行 / 实体的某个版本（`timeline` 里列出的 #n），否则报 `invalid_argument`。恢复备份后序号可能被重新用掉（见「编号」），这条校验让旧编号最多指向同一行的另一个版本、不会指向别的行。

## 读取：数据供给

**saveslot 的价值是快速、准确的数据供给；理解用户意图、把意图拆成查询，是 Agent 的事。** saveslot 不猜意图，
也不假设自己是 Agent 的中心——它只是 Agent 用的众多 MCP / 插件之一。读取这边 saveslot 做好三件事：
让 Agent **看得清**有什么数据、**查得出**想要的结果、**拿得快**。

### 看得清：数据目录要足够详细

在「数据目录」已有的表、字段、类型、说明、派生规则之外，再提供：

| 信息 | 例子 | 用来做什么 |
|---|---|---|
| 数据之间的关系 | runs 被 weekly_mileage 派生；支出的 category 关联预算表 | Agent 知道怎么关联查询；要求定义 schema 时**声明表间关系**（外键 / 引用） |
| 数据概况 | 行数、时间范围（最早 2026-03，最近 11-08）、字段取值示例 | 写查询前先判断"有没有、有多少" |
| 单位与语义 | distance 单位英里；date 按 Asia/Shanghai 的自然日 | 避免理解错数据 |

### 查得出：两档查询

- **简单查询**：按表、条件、排序、条数查，覆盖大部分日常读取，对模型最友好。
- **只读受限 SQL**：复杂的关联、聚合、时间窗口。**与派生规则共用同一套受限 SQL 引擎**：函数白名单（见「受限 SQL」，[`11-restricted-sql.md`](11-restricted-sql.md)）、
  只能读该用户自己的数据（行级隔离）、执行时间与结果条数上限。安全措施只做一次。
  一条 `sql` 可以引用可见范围内多个 slot 的表：它是只读的，不涉及版本归属与原子性，结果按 slot 分别给出 schema 版本。派生规则与 `ref` 字段仍不跨 slot。
  - **主防线在 saveslot 这一层**：用 libpg_query（PostgreSQL 自己的解析器）解析成语法树，按语句、节点、函数白名单校验，
    显式禁 `SET` / `RESET` / `set_config()` / `COPY` / `DO` 等与一切 DDL / DML；表名重写为指向该用户、当前版本的物理表；单语句。
  - **第二道防线**（原生 PostgreSQL）：非超级用户的只读角色、只读事务、`statement_timeout`。
  - **PGlite 上**：角色可被 `SET ROLE` 逃逸、`statement_timeout` 不生效（实测），所以只靠语法树白名单；
    查询与写入同在那个专用的 DB Worker 里排队执行，超时只能终止整个 Worker（代价见 architecture §7），所以主防线是事前的准入估算与编译期拒绝。
  - 结果用不可信数据边界包裹，防提示注入。
- saveslot 独有的两项：
  - **按时刻读**：业务时间（`valid_at` / `valid_during`）所有查询可用；记录时间（`as_of`）只在审计、还原类接口（见「时间 · 查询」）。
  - **历史按需展开**：沿修订历史回溯到源数据原文（借鉴链式召回），默认不展开。

### 拿得快：返回要省

- 格式紧凑；每个值带单位与 schema 版本。
- 有条数上限、支持分页；结果大时返回"还有更多"（借鉴 Super-agent 的 Inline & Spill：小的直接给，大的给可展开的句柄）。
- 冲突、待确认、纠错标记随结果带出——这是数据正确性的一部分，属于基础设施。
- **争议标记带事项、字段与区间**：`disputed` 写明是哪个事项、涉及冲突单元里的哪些字段、状态类表上是哪段区间（目标是"存在"时字段为全部）；`awaiting` 同样带字段与区间。一行可以有多个事项。判据：读到的值不随"采纳哪个候选"而变，就不该标——只读 `date` 的读方不该因为 `distance` 上的争议被要求停下来问用户。
- **派生值也带出输入上的标记**：标记打在基础行上，派生行自己没有；读派生值时，saveslot 按该派生行的分区读集汇总基础行的标记，
  写成"本值的输入里有 1 行已标记 / 有争议"（与 `sql` 的汇总标记同一套逻辑），只统计规则所依赖的字段上的争议。否则读周跑量的 Agent 看不出其中有一条疑似重复。
- **逻辑表 = 当前版本里未撤销的行**：简单查询、受限 SQL、派生规则都一样；查已撤销的行要显式要求（`query` 的 `include_revoked`、`history`）。
- **前提已变带出来**：一行当前的值所用到的前提后来变了时，这一行带 `premise_changed`，写明是哪条前提、哪个字段、在哪次操作里变的、原因是什么（读时现算，见「写入的前提」）。它是这一行的状态，任何读取方都看得到；值没有动，是否仍然成立由读方判断。
- **引用字段带出目标的状态**：`ref` 的目标已被撤销或已被隐私删除时，这一行带标记 `dangling_ref`，写明是哪个字段、目标是已撤销还是已删除（读时现算，不落盘，见「引用字段」）。它和其他标记一样随结果带出、由外化面渲染进文本。
- 读取自动记入 read_log，Agent 无需做任何事。

### 读取记录里记什么形状

读取记录（read_log，见「读取记录」）只记版本，不记值。查询条件记成一段**结构指纹**：规范化之后不含任何调用方给的值的文本。直接存文本、不存哈希——它本来就不含值，文本更好排查；规范化到 ID 之后改名也不影响匹配。

| 读取 | 指纹怎么得出 |
|---|---|
| 简单查询 `query` | 一个 JSON 对象的确定性编码（RFC 8785）：表 ID；所选字段 ID（排序后）；条件树（运算符 + 字段 ID，**每个字面量换成 `"?"`**，列表整体换成一个 `"?"`）；排序（字段 ID + 方向）；有没有带条数与翻页（只记有无）；业务时间参数的种类（某一刻 / 一段 / 无） |
| 受限 SQL `sql` | 把语法树里的表名、字段名换成 ID，每个常量换成 `$n`，`IN` 列表折成一个占位符，**去掉列别名、表别名与注释**（别名是调用方起的文字，可能含用户内容，换成位置序号），再反解析成文本 |
| `history`、`sources`、`catalog`、`pending` | 只记操作、模式与目标的不透明 ID；源数据搜索的搜索词不记 |

业务时间条件（"查的是 11-03"）另记，纠错影响查询要用；它是读取记录里唯一来自调用方的值。

**记多少条。** 逐行读的每一行记一个版本（每页最多 1,000 行）。受限 SQL 按它在每张基础表上实际读到的行来记；一张表上读到的行版本数超过阈值（初值 1,000）时，这张表改记一条表级记录，代价不再随行数涨，换来的是影响查询在这类读取上只能报"可能受影响"（规则见「读取记录」「纠错影响查询」）。

### 可见范围

每次调用带一个可见范围，由服务层按凭证给出、内核执行（目录、查询、受限 SQL 的改写、写入都过它）。用户会话与范围为"全部"的连接实例传"全部"；限定到若干 slot 的连接实例传它的 slot 列表（见「连接实例身份」）。类型现在就定到字段一级，将来做表级、字段级数据权限时不改内核操作的签名。

| 取值 | 含义 |
|---|---|
| 全部 | 这个租户的所有 slot |
| 白名单 | 列出可见的 slot；slot 下可再列出可见的表；表下可再列出可见的字段。没列出的不可见；某一级不往下列 = 这一级以下全部可见 |

**范围外的东西，对这个凭证与不存在完全相同。** 错误按引用的方式分：

| 怎么引用 | 不存在或不可见时 |
|---|---|
| 按名字（表名、字段名） | 该操作对不存在的名字本来报的那个：`query`、`history`、`write`、`catalog` 报 `unknown_table` / `unknown_field`，`sql` 报 `sql_rejected`（`unknown_name`）。附带的相近名字（`nearest`）只从可见的名字里取 |
| 按 ID（行、实体、事项、源数据、草稿、一次读取） | `not_found`，与 ID 不存在相同 |
| 指定 slot 的参数（按名字或 ID：`catalog` 的 `slot`、`sources` 与 `pending` 的 `slot` 过滤、`policy.get`） | `not_found`（`slot`），与 slot 不存在相同 |
| 写进参数里的行 ID（`ref` 字段的值、前提的目标） | 与 ID 不存在时相同：`ref` 报 `validation_failed`（`ref_not_found`），前提报 `not_found`。`ref_wrong_table`、`cross_slot` 只在目标可见时才报 |

`not_found` 是"按 ID 找不到"，`unknown_table` 是"名字不认识，并给出相近的名字"，两者各管一类引用。相近的名字对写错名字的模型有用，不为了不泄露而取消，只限定候选从哪里取：范围外的名字不出现在任何报错、候选与提示里。行 ID 难猜，但会经共享的日志、截图、别的 Agent 的上下文流出，所以按 ID 的引用同样不区分"不存在"与"不可见"。

- **名字解析只在可见范围内做**：表名在可见范围内不重名时可只写表名；`ambiguous_table` 的候选、旧名解析（最近 10 个版本内的旧名）同样只看可见范围。否则一个只写 `runs` 的请求会因为范围外另有一张 `runs` 而报歧义，等于泄露了它。
- **各操作怎么受范围约束**：

  | 对象 | 规则 |
  |---|---|
  | 数据目录 | 只列范围内的 slot 与表；概况、取值示例、表间关系只涉及范围内的表 |
  | `query`、`history`（含 `timeline`、`as_of`、`changes`） | 目标表须在范围内。`changes` 不给目标时是"一张表的变化"，表须在范围内 |
  | 受限 SQL | 语法树里引用的每张表都须在范围内，否则 `sql_rejected`（`unknown_name`）；可以引用范围内多个 slot 的表（见「查得出」）。汇总标记只统计范围内的行 |
  | 待处理事项、`resolve` | 事项属于某个 slot，按 slot 过滤；范围外的事项 ID 报 `not_found`。结果里的提示只算范围内的 |
  | 源数据、`source_ref`、删除预览与删除 | 每条源数据只属于一个 slot，按 slot 过滤；范围外的源数据 ID 报 `not_found` |
  | 读取记录 | 照常记在本连接实例名下。经 `history` 查某个目标的读取时目标须在范围内；按某次读取还原时，那次读取的目标在范围外报 `not_found` |
  | 影响查询 | 写入回执里受影响的读取统计的是对本次所写行的读取，这些行都在范围内，照常给；读结果上的 `possibly_affected` 只出现在范围内的行上 |
  | 写入 | 目标表须在范围内；一次写入只涉及一个 slot，整个请求要么在范围内，要么报 `unknown_table` |
  | 提交 schema 草稿 | 改范围内的 slot 照常（需 `saveslot.schema`）。**限定范围的凭证不能新建 slot**，报 `insufficient_scope`（`required_scope: "all_slots"`），不论草稿里的 slot 名是否与范围外的某个 slot 重名。既没有 `saveslot.schema`、又是限定范围的，先报缺 scope（`required_scope: "saveslot.schema"`）：先查动作、再查范围 |
  | 导出、对拍、校验、连接实例管理 | 只给用户会话，不受影响 |
  | 幂等、限流 | 不变：请求键里本来就有连接实例 |

- **派生表可见，当且仅当它依赖的全部表与字段都可见。** saveslot 有完整的派生依赖，可以强制执行。派生规则不跨 slot，所以到 slot 一级时派生表与它的基础表同进同出。
- **范围不改变判定**：冲突、同值、高影响、疑似重复都只看同一 slot 里的数据，范围内外的写入方得到同样的判定结果。
- **提示只按可见范围计算**：回执与读结果里的各种提示，范围外的 slot 不出现在任何一条里。历史里出现的写入者（连接实例名）照常显示，它们不属于任何 slot。
- 第一版内核把白名单实现到 slot 与表两级；服务层按凭证只传到 slot 一级。表级、字段级与行级的数据权限后续。

### 不做的

- **saveslot 不挑选"和任务相关的数据"**：意图分析与查询拆解归 Agent。
- **schema 里没有读取规则**：数据目录足够详细即可，读什么由 Agent 决定。
- **不假设会话开始的概览**：宿主插件可以选择性做，saveslot 的设计不依赖它。

### 源数据：列出与搜索

- 第一版提供按时间、slot、类型列出源数据，以及简单的全文搜索（满足"我上次是怎么说的"）；向量检索以后再做。
- 全文索引是派生数据：删除时同步清除对应条目（见「删除」的明文残留清单）。

### 变化告知：saveslot 提供能力，产品决定怎么用

read_log 记了"谁在什么时候读到哪个版本"，saveslot 因此能算出"自上次读取之后变了什么"（如"上次读 W45 是 22，
现在是 12，原因：11-03 的记录被纠正为 5 公里"），作为可选的查询项提供。什么时候提示、提示给谁、什么形式，
是产品层的特性。

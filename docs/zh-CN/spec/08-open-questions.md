## 一、开发前必须定

会写进日志事件、定下后难改的。挡 P1。

**目前没有。** 下面几项已定：单位词表、默认精度与舍入、同值判据（data-model「字段类型、同值与单位」）；默认 slot 策略（data-model「slot 包含什么」）；读取记录的结构指纹与 `visibility` 的类型（data-model「读取」）；标识的写法（data-model「标识的写法」）。事件格式冻结前新出现的、会进事件的待定项记在这里。

| P2 前 | **`half_even` 舍入的实现**：PostgreSQL 的 `numeric` 没有内置的取偶舍入，要由内核实现一个两个后端共用的确定版本；实验 5 覆盖它 |
| P2 前 | **写入准入的阈值、写接口的超时与重试语义、PGlite 慢查询的延迟上限**：等实验 2、4 的结果 |
| P2 前 | **派生刷新的代价估算与准入阈值**：第一版整条规则重算，代价只随规则所读的表变大、与请求大小无关，按它设阈值会让表长过线之后的写入一律被拒且无法分批补救，所以准入不拒绝。待实验 4：按受影响分区估算刷新代价并定阈值，届时 `too_large`（`admission`）的 `estimated_rows` / `suggested_batch` 才有意义 |

| P2 前 | **读结果一律给 `total` 的代价**：在 PGlite 上是一次额外的计数；实验 4 一并测量、实验 9 在大表上再测，代价过大时改为可选 |
| P2 前 | **数据目录两条规模界线的数值**（舒适线 `comfortable_rows`、实测线 `tested_rows`，每个后端一组）：等实验 9；P2 做 `catalog` 概况时先用 PGlite 一侧的结果。规则见 architecture「容量边界与实测数值」 |
| P2 前 | **PostgreSQL 支持的版本区间与跨大版本重放**：等实验 5 |
| P2 前 | **第一版高影响写入清单是否够用**（清单见 data-model「写状态」）：P1 的 eval 4 跑完后看 |
| P3 前 | **两个后端上残留清理的做法**：等实验 7 |
| P4 前 | **按时刻读跨 schema 版本时，是查退役表还是从日志重放**（退役表第一版一直保留；无论保留多久，清理都写成一条日志事件，隐私删除对退役表同样生效，已定） |
| P4 前 | **切换前"剩余量低于阈值"的阈值、切换事务的 `lock_timeout` 与重试次数** |
| P4 前 | **官方 schema 的结构（`extends` / `compatibility`）**：上层的领域工具（读预算的看板、算营养摄入的工具）需要一份可识别的标准定义，并能知道"这个用户的这个 slot 符合它"；模板只是一次性拷贝，做不到。声明要进编译后的定义（重放不能回头取外部文件）；要加的东西按事件格式允许的演进加（事件格式 1.6：给已有的块新增可选键），不改 v1 已有的形状，所以不挡事件格式 v1 的冻结；P4 实现的改动分类、自动生效类别与迁移状态机正是它要落脚的地方。定的是结构，是否在第一版实现由那时回答（只在事件格式与编译后的定义里留位；或实现"声明 + 识别"、不实现升级）。P1–P3 的模板照旧是普通 schema；新的官方模板在结构定下之后再写。要回答：**身份与来源**——标识与版本号的写法，由谁发布、随 CLI 打包还是有远程来源；`extends` 指向整个 slot、一张表还是都可以，一个 slot 能否扩展多份、一个租户能否有两个 slot 扩展同一份；编译后的定义里记全文还是只记标识与内容哈希。**用户能改什么**——在官方的表上加字段时"自己的命名空间"是什么（名字前缀、单独的 ID 区间还是单独的键），字段 ID 怎么不与官方将来新增的撞；官方的表与字段能否改名、改说明、加别名、改单位、改约束、删掉，哪些改了仍算"符合"；上层工具按名字、官方字段标识还是别的稳定句柄找字段。**兼容性**——`compatibility` 由谁声明、声明什么、取值有哪些、saveslot 检查什么、何时检查；官方出新版本时哪些变化可以自动跟进，本机离线时由什么触发，大版本升级怎么接迁移状态机；用户能否停在旧版本、能否解除 `extends` 而保留数据。**发现与使用**——数据目录怎么表示"符合哪份官方 schema 的哪个版本"；用派生规则投影成官方形状的"映射"怎么声明，与 `extends` 是一种声明还是两种；已用旧模板建好的 slot 能否事后声明为符合，那是哪一类 schema 变更。**与其他规则的关系**——官方 schema 带的说明、别名、规则原文在不可信文本的规则里算谁写的；汇总粒度与覆盖列（官方健康类模板的约定）要不要成为通用要求；第一版做到哪一步 |
| P4 前 | **schema 切换与前提**：先定的保守规则是切换本身不触发前提标记（确定性转换改的是写法，不是 Agent 用到的事实）；所声明的字段在新版里被删除时，不把这条声明扩成"整行"，而是标上原因 `schema_switched`。这个原因值不进事件格式 v1 的枚举：它在 P4 的切换规则里才会产生，届时按事件格式允许的演进加枚举值。要定的：切换改了单位或类型之后，撤标记时"现在的值"与"所见版本上的值"按哪一版比较（要读跨 `sv` 的历史值）；旧版写入按 `compiled` 转换之后，出处项的身份（事件、字段 ID、下标）是否保持，`premise_edges` 要不要跟着转换。不影响事件格式 |
| P5 前 | **删除的法律口径**，需法务确认：删除后保留的元数据（某时有过一行、被谁写过几次、每次的类型与意图；前提的声明与它的状态变化，只含序号与 ID）是否可接受；物理删除、备份保留期如何告知；24 小时宽限期与被遗忘权时限的关系；对用户的告知里写明运营方技术上读得到托管用户的全部数据（托管服务只有基础设施层的静态加密）；有来源键的记录在物理删除之后若连接器再同步同一条会重新出现、导入之后源头在导出之后做的删除带不过来，这两条是否需要额外的告知或限制。**它不挡本机模式。** 事件头按"尽量少留"设计，能放进内容区的都放内容区；[`09-event-format.md`](09-event-format.md) 列出事件头里留下的字段，供法务审阅，并写明结论不利时哪些字段要动。已定的事实口径：云服务按到期时刻主动执行物理删除；本机 saveslot 服务没在运行时，物理删除在下次启动时执行，回执如实说明；本机删除只作用于 saveslot 当前的数据目录，系统级备份（Time Machine 等）里的旧副本不由 saveslot 管理，从这类备份恢复等于恢复到当时的数据 |
| P5 前 | **远程授权先做 CIMD 还是 DCR**：授权服务器最终两种都支持，第一版先做一种，初步考虑 CIMD，按实测的 MCP 客户端支持情况定。要算进去的事实：Claude 网页端与桌面端优先用 CIMD、否则退回 DCR，并要求登记固定的回调地址；Codex 的添加命令可以指定用哪一种；两种都不支持的客户端会要求用户手动填客户端 ID，那是接入流程里的一步手动操作 |
| P5 前 | **云端账户没有 slot 时的出路**：云端新账户没有 slot；建 slot 要么登录后用 CLI，要么给 Agent `saveslot.schema` 且范围为全部（默认不授予）。只用网页宿主的人因此还得另装 CLI。可选：授权页上提供"按模板建一个 slot"；或靠空状态的说明加 `track` prompt（需要上面那种凭证） |
| P5 前 | **自建时用户怎么拿到初始凭证**：自部署由运维用 `saveslot server user add` 创建人的账户，这个用户第一次登录用的凭证怎么交到他手里（一次性的初始口令、邀请链接，还是由运维代为登录签发），没有写。它不计入接入的"一次同意"，但流程要补齐 |
| P5 前 | **令牌的有效期与静态令牌的格式**：访问令牌与刷新令牌多久过期、`saveslot connect http` 签发的静态令牌长什么样，随 CIMD / DCR 的选择一起定 |
| P5 前 | **云服务跑几个 saveslot 进程**（一个，还是固定路由的少数几个）；每个 cell 放多少租户，等实验 3a |
| P5 前 | **租户整体删除**（对外提供云服务前必须定义；不挡本机模式：本机上删掉数据目录与配置目录就是全部）。逐条隐私删除满足不了它：事件头与元数据块按设计永远留下。要回答：① **删什么**：租户存储是否整库删除，包括事件头链——"事件头永不删改"（K1）的适用范围是否限于租户存续期间；控制面里这个租户的凭证、OAuth 授权、租户目录与路由；读取记录；应用日志与错误上报里与它有关的内容。② **备份与归档**：备份、快照、冷租户归档里的副本何时消失、怎么告知；恢复一份早于删除的备份时靠什么不让整个租户复活——需要一份租户存储之外、租户级的删除登记，它存什么（只有不透明的租户 ID？）、保留多久。③ **流程**：谁能发起（只有用户会话？要不要重新认证）；有没有预览、宽限期与撤回；与逐条隐私删除的 24 小时宽限期是什么关系；宽限期内租户能不能读写、连接实例是否立即失效。④ **进行中的事**：未到期的隐私删除、进行中的迁移、对拍、导入怎么处理。⑤ **删除之前**：是否提示或要求先导出；导出文件、连接器与外部系统里的副本不由 saveslot 管理，怎么告知。⑥ **删除之后留什么**：是否保留"曾有过这个租户"的最小记录（租户 ID、删除时刻），计费与合规要求保留的记录归谁管；租户 ID、用户主体 ID 是否永不复用；同一账户能否再建一个新租户。⑦ **回执**：租户没了之后，用户凭什么确认删除已经完成、备份何时失效。⑧ **各部署形态**：云服务由账户系统发起还是由 saveslot 的接口发起；自部署是不是一条运维命令；本机是否提供一条命令代替手动删目录。⑨ **与别的设计的关系**：与"整个 slot 删除"是否共用一套机制；将来共享 slot、开发者采购托管时，删除一个用户与删除一个租户不再是一回事。⑩ **法律口径**：与"删除的法律口径"一并交法务——法定时限、可保留的最小信息 |
| P6 前 | **本机的安装形态**：第一版发 npm 包（需要 Node）；独立可执行文件与桌面安装包等实验 6 |
| P6 前 | **接口的数值与细则**（见 [`04-contract.md`](04-contract.md)、[`05-surfaces.md`](05-surfaces.md)，初值待 eval 调）：幂等窗口（显式 `idempotency_key` 24 小时、服务端算出的请求键 10 分钟）、`limit` / `max_rows` 默认与上限、单个结果约 20k tokens 的预算（只对 MCP）；经 MCP 读超过 2,000 个字符的值要不要分段读（这一版只读得到前 2,000 个字符，由 1d 一类评测的结果决定）、证据单段 32 KB / 单次请求 256 KB / 单次请求至多 1,000 段、删除宽限期 24 小时、read_log 保留期（默认 180 天、下限 30 天）与落盘间隔（5 秒）、本机服务日志的轮转（超过 10 MiB 轮转，留两份旧的）、读取记录改记表级记录的阈值（一次读取在一张表上读到 1,000 个行版本）、高水位推进间隔（1000 条事件或 60 秒）；前提的上限（一个 op 至多 16 条声明、一行至多被 1,000 条有效声明指向、一行上列出 10 条标记、回执的 `premise_affected` 列 20 行）；`instructions` 里 slot 清单的上限（1,500 个字符、slot 名超过 32 个字符不列）与 `server/discover` 结果的缓存时长（5 分钟）；云服务上对拍（`log.reconcile`）的限流；写入请求的上限（临时值，待实验 4）：一次至多 1,000 个 op，`task` 与 `idempotency_key` 至多 256 个字符、不含控制字符；证据 `file_ref` 的 `name`、`mime` 至多 256 个字符、`origin` 至多 2048 个；slot 的规模（临时值）：每个租户至多 100 个 slot、每个 slot 至多 100 张表（基础表与派生表合计）、每张表至多 200 个字段，超出时 `schema_draft` 报 `validation_failed` / `out_of_bounds`（明细带路径与 `max`），每个 slot 至少一张基础表（`min: "1"`） |
| P4b 前 | **迁移相关、等 eval 5 的**（规则本身已定，见 data-model「抽取作业」）：`migration_diff` 的提示措辞；`keep_rest_and_switch` 之后切换时另生成的 `migration_diff` 长期没人处理时如何提示；抽取租约 15 分钟与每批字节预算；来源簇过大时的拆分规则 |

## 三、可以开发后再定

- **按数据归属设中心**：哪些数据从一开始就必须"永不离开设备"？（多节点才用；slot 的"归属节点"字段已留。）
- **社区 Schema + SKILL 的安全**：SKILL 由用户的 Agent 执行，权限声明与审核怎么做（提示注入风险）？第一版的模板随 CLI 打包，不引入远程来源。
- **连接实例的最近使用时刻**（`Connection.last_used_at`）：第一版不给。初步考虑查询时从日志与读取记录取这个连接实例最近一次操作的时刻，不在认证的路径上写任何东西。
- **read_log 要不要像日志一样串链**（防误操作）。read_log 是本地运行状态，加不加都不动日志。
- **数据权限的表级、字段级（后续版本）**：slot 一级已进第一版——连接实例的授权 = 动作 scope × slot 范围（全部，或一个 slot 列表），范围外的 slot 对它与不存在相同（contract 第 12 节，P5）。余下的：
  - 资源细到表、敏感字段到字段级；同一个连接实例对不同 slot 给不同的 scope（第一版要这样就签两个连接实例）；签发后修改范围（第一版吊销重签，事件格式为它留了 `principal.scope_changed`）。表级要先回答"事项、源数据按什么过滤"（它们按 slot 归属，不按表）；字段级要动派生表的可见性与读结果的形状。
  - **派生数据按来源继承权限**：一张派生表同时来自健康和记账数据，读者必须对所有来源都有读权限——saveslot 有完整的来源关系，可以强制执行。第一版派生规则不跨 slot，到 slot 一级时派生表与它的基础表同进同出，这条还不用。
  - 没权限的表在数据目录里不可见；只读 SQL 也受同一套权限约束（行 / 列级隔离）；远程模式可按领域分 OAuth scope（第一版的 slot 范围不编码进 scope 字符串）。
- **"某类操作只接受用户会话的确认"何时实现**：slot 策略的结构里已留位；它依赖 slot 策略的修改（`policy.set`），与高影响 ③ 一起后续。
- **按来源级别的系统裁定**：秩表与重判事件的结构已留位；裁决规则的细节（一方命中一方未命中时怎么比、低级别的顺序写入能否直接覆盖用户原话）在加回时定。"外部权威"级别由谁声明的规则已定（data-model「来源级别」：由连接实例被授予的权限决定，写入方不能自报）；待定的细则：授予的形式（一个新的 scope，还是连接实例上单独的一项）、能否按 slot 分别授予、凭证被吊销后它声明过的级别在裁定时还认不认、与字面命中的关系。
- **温度单位的互相换算**：第一版 `Cel`、`degF`、`K` 各自成量纲、不换算。加回时给单位定义新增可选的偏移量，已有定义不变。
- **改正实体的键（`rekey`）**：第一版键不可改，写错键靠撤销重写，历史会断成两个实体；回执会标出写法相近的已有键（`similar_keys`）。若评测里写错键很常见（eval 4d），再加 `rekey`；它是新的写入意图或 op 参数，不改已有事件。
- **词表外单位的自定义**：第一版单位取自固定词表，词表外的量用 `decimal` / `integer` 字段并在说明里写清单位。是否允许 slot 自带单位定义，随新的单位词表版本定。
- **表名、字段名只允许 ASCII**：受限 SQL 里中文标识符要加引号，模型容易写错，所以第一版只收字母、数字与下划线；说明文字不受限。是否放开看用户反馈。放开时要重新看 `instructions` 里的 slot 清单：它靠这条字符集挡住换行、标点与伪造的边界标签。
- **统计异常的定义**：阈值、按什么分组、冷启动时怎么办都没写。第一版不判定、不产生事项；加回时是新的判定结果，旧事件缺省即"未判定"。
- **表声明预期的记录频率，读取结果带覆盖标记**：第一版没有这个机制，"应该每天有记录"是领域知识，由模板里派生表的覆盖列（有记录的天数、首末日期）交给 Agent 判断。若评测里 Agent 经常把"部分"说成"完整"，再考虑：基础表上加一个可选的声明（预期每天、每周一条，或不声明）；按时间窗读取与按时间分桶的派生行据此带一个覆盖标记（完整 / 部分 / 没有数据）。它是 schema 文档与读结果上新增的可选键，不改已有事件。要定的事：频率怎么写；标记读时现算还是进派生写入；用户明确说"那天没有"怎么表示（它不同于"没记"）。
- **确定性迁移的人工放弃出口**：纯确定性迁移没有人工放弃出口；若 eval 发现大的确定性迁移也需要人能中途放弃，再加（"放弃迁移"事件已留位、第一版不产生，加出口是新增一种事件，不改已有事件）。
- **读派生表时汇总 `input_marks` 的代价**：第一版每次 `query` 读派生表先读规则所读基础表上的标记；没有标记就不再查，有标记时只对带标记的行求出它们落在哪个分区，代价随带标记的行数变化、不随表的大小变化。标记很多时是否改为按分区维护成员，等实验 4 的数字定。
- **小数分组键先舍入再分组**：第一版只收小数位上界不超过推断精度的 `decimal` / `quantity` 分组键（上界的算法见 [`03-data-model/11-restricted-sql.md`](03-data-model/11-restricted-sql.md)「类型」；含除法、`avg`，或乘积、字面量的位数超出精度的不收）。若有需要，改成先把键按字段精度舍入再分组：`half_even` 的键要另写舍入，分组语义随之改变，要进规格并出新的白名单版本。
- **PostgreSQL 上受限 SQL 要不要单独的只读连接**：并发与 cell 容量之间的取舍。第一版共用连接。
- **托管集群容量实验**（云服务扩容前做，不影响方案本身）：Linux 云盘上的崩溃恢复与备库切换时间；满载 24 小时的 autovacuum 覆盖与 wraparound 余量——决定每组放 2,000 还是 5,000 个用户库。另有冷用户恢复延迟、并发尾延迟待测。
- **冷租户归档在租户恢复回集群后何时作废**：留到云服务容量阶段再定。初步考虑：恢复并 `verify` 通过、下一次常规备份成功后作废；不对有未到期删除的租户做冷归档。
- **内核在 Node、Bun、Electron 主进程之外的运行时里能否实例化**：未核实。
- **read_log 是否随日志复制**（多节点）。
- **开发者 SDK**（后续版本）：接口怎么设计、开放到哪一层；开发者采购托管时的租户模型（开发者 / 应用 → 终端用户 → slot）与数据归属
  （归终端用户还是归开发者，终端用户能否导出、迁走）；嵌入存储是否作为节点并入 saveslot 服务；非 JS 宿主（如 Python）的形态——实际只能是本地 sidecar 进程。
- 成本与商业化：先不讨论。

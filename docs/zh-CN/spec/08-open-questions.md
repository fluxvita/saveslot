## 一、开发前必须定

**目前没有。** 下面几项已定：单位词表、默认精度与舍入、同值判据（data-model「字段类型、同值与单位」）；默认 slot 策略（data-model「slot 包含什么」）；读取记录的结构指纹与 `visibility` 的类型（data-model「读取」）；标识的写法（data-model「标识的写法」）。事件格式冻结前新出现的、会进事件的待定项记在这里。

## 二、某个阶段开工前定

| 阶段 | 事项 |
|---|---|
| P2 前 | **字面命中的规则是否够用**：单位同义表（`units@1`）与日期、枚举、文本的命中规则都是经验性的，已随核对器版本 `literal@1` 定下；P2 做字面命中时按 eval 8 的结果看要不要出新版本 |
| P2 前 | **`half_even` 舍入的实现**：PostgreSQL 的 `numeric` 没有内置的取偶舍入，要由内核实现一个两个后端共用的确定版本；实验 5 覆盖它 |
| P2 前 | **写入准入的阈值、写接口的超时与重试语义、PGlite 慢查询的延迟上限**：等实验 2、4 的结果 |
| P2 前 | **`as` 与临时名**（随「`ref` 字段与高影响 ②」）：前提指向本请求里新建的行时一并定下的两件——所见状态取本请求结束时（同一请求里后面的 op 再改它不算前提变了）；那次新建在本请求里没有生效（进了待确认或成了候选）时拒绝声明方，`invalid_argument`（`premise_target_pending`，`param` 指那条声明，附目标的临时名与那个 op 的下标），提示先单独发那次新建、生效之后再带前提写或重申 |
| P2 前 | **前提被指向数上限的计数**：声明时按仍作数的覆盖计数，不减去依赖行已撤销、所在写入尚未生效的（只多不少，拒绝可能略早）；上限按评测调整时一并看要不要算准 |
| P2 前 | **派生刷新的代价估算与准入阈值**：第一版整条规则重算，代价只随规则所读的表变大、与请求大小无关，按它设阈值会让表长过线之后的写入一律被拒且无法分批补救，所以准入不拒绝。待实验 4：按受影响分区估算刷新代价并定阈值，届时 `too_large`（`admission`）的 `estimated_rows` / `suggested_batch` 才有意义 |
| P2 前 | **`sql` 的超时初值**：临时值 10 秒（内核常量，测试可注入，不是 `config.toml` 的键；只在强制 `statement_timeout` 的 PostgreSQL 上生效，PGlite 没有）；与 PGlite 慢查询的延迟上限一起，等实验 2、4 |
| P2 前 | **读结果一律给 `total` 的代价**：在 PGlite 上是一次额外的计数；实验 4 一并测量、实验 9 在大表上再测，代价过大时改为可选；`catalog` 表级概况读时现算的代价（状态类表是带窗口函数的全表扫描）同样由实验 9 测量，过大时改为随写入维护 |
| P2 前 | **数据目录两条规模界线的数值**（舒适线 `comfortable_rows`、实测线 `tested_rows`，每个后端一组）：等实验 9；`catalog` 概况先用 architecture 里的占位初值（100,000 与 1,000,000），实验 9 出了 PGlite 一侧的结果就替换。规则见 architecture「容量边界与实测数值」 |
| P2 前 | **PostgreSQL 支持的版本区间与跨大版本重放**：等实验 5 |
| P2 前 | **第一版高影响写入清单是否够用**（清单见 data-model「写状态」）：P1 的 eval 4 跑完后看 |
| P3 前 | **撤回时"保持已被取代"未做（第一版已知限制）**：撤回一项删除时，这一行或实体在连续被待执行删除覆盖的期间（几项删除的待执行期间首尾相接或重叠就连成一段，已撤回的删除在撤回之前也算；不论去掉它的是不是这一项删除，所以撤回的先后不影响结果）有任何操作、而这项删除让某个（事件, 目标）不再未决（去掉这项删除的重放里它未决、留着它的重放里不未决）、且撤回时没有被保持生效，这次撤回报 `not_implemented`；其余撤回照常，`kept_effective` 照常记。"保持已被取代"（data-model「撤回与宽限期」）之后补做，做好后去掉这条限制。回执与 CLI 的说法随删除接入接口时定 |
| P3 前 | **回退写回的值项是否盖掉佐证端点**（见 data-model「时间」的「挡点」）：现在盖掉，所以"写一次再 `undo`"之后与从没写过不同——原来停在佐证端点上的默认终点不再停在那里。现在这样取，是为了判据只看"之后有没有生效的值项"，不看它从哪来；要不要改成"回退写回的项不盖掉端点"，随删除线做回掉相关的规则时定 |
| P3 前 | **冲突判据的对称只在一个范围内成立，范围之外的三处要不要改规则**（范围与三处已写进 data-model「冲突处理 · 冲突判据」的对称一条，各有固定用例，见 [`11-claims.md`](11-claims.md)）。三处是：(a) 一次显式区间的写入与一次不传终点的写入，起点相同、值相同时不冲突，但合并时默认终点按当前状态解析，先到的显式写入的终点成了挡点——两种顺序的终态不同（一种在显式终点之后保留原值，一种把新值延续下去），都不开事项；(b) 一次写入因高影响进了待确认时不算另一次写入的 L，于是同一对写入，一种顺序是"一方成为候选"，另一种顺序是"一方待确认、另一方生效"——都需要人处理，但事项的种类不同；(c) 一次写入的默认终点在所见版本里停在某个挡点上，而另一次带 `acknowledge` 的写入抹掉了这个挡点：基 `5000 [10-01, ∞)`，#12 `4000 [11-25, ∞)`，同从 v12，L =「4000，11-10 起」不传终点、带 `acknowledge`（之后 11-25 不再是变化点），A =「6000，11-20 起」不传终点。L 先：A 合并，默认终点按当前状态解析，写到 `[11-20, ∞)`；A 先：A 停在 11-25，`[11-25, ∞)` 仍是 4000。两种顺序都合并、都不开事项，终态不同，A 是佐证（5000）时也一样；L 先的那种还让 A 盖掉了它所见版本里 `[11-25, ∞)` 的值，而 A 从没对那一段说过什么，与"默认不破坏已知事实"相抵。要定的是：规则保持现状、对称只在现在写明的范围内承诺；还是改规则让 (a) 也对称（例如同值的显式 × 默认也按相交处理）。(c) 的候选改法：合并时，写入在所见版本里停靠的挡点若已被其后的写入抹掉，不合并、按冲突处理 |
| P3 前 | **写入时不是当前的 `ver` 带 `acknowledge`，删除重放里会重新生效**：`ver.current` 只在为真时记，不带这个键既表示"写入时不是当前"，也是旧日志的样子，所以重放里判"所见之后有没有生效项"又回到比较。例：#10 `5000 [10-01, ∞)`；#15 `4000 [11-10, ∞)`；#20 `3000 [12-01, 12-05)`（来源 S20）；#30 用 v15（写入时已过期）写 `6000 [11-02, 11-20)` 带 `acknowledge`，抹掉 11-10 的变化点，进待确认；删除 S20 之后的重放里 #30 直接生效。要定的是：照记录（过期的确认永远不生效）；还是按"成因被删的待确认写入会生效"同一条思路让它生效，并在删除预览里单列 |
| P3 前 | **按记录时刻读到被删内容时还没收住的几处**（data-model「删除」的「版本表」一条收住了行值、`changes`、被引用行的摘要、`timeline` 的 `before`、冲突事项的 `previous`、按 `entity_key` 定位、已关闭事项的详情；下面几处各自另开）：① **区间端点**：一次不传终点的写入停在后一次写入给出的变化点上，删掉后一次之后按时刻读，那一段的终点仍是被删写入给的日期，后面那段的起点也是；只删区间的源（`evidence_by_field.valid` 指的那句话）时，它说的日期照样看得见；`changes` 按被删写入内部的切点分段给 `valid`（`as_of` 合掉的点在那里露出来）。data-model 既说"被删内容所在版本的区间保留"，又说起点、显式终点是用户说的话，两句要定一句；形状（缺着、给成开口、另带标记，两段在边界出自被删块时怎么并、怎么标）待定。④ **被另一份贡献佐证过的值（这一版的限制，不改）**：被删的源写下、另一个源之后佐证了同一个值时，按"贡献之间是或"，佐证之后不该藏，现在照样藏。只多藏、不漏，只发生在佐证之后、删除确认之前的按记录时刻读；隐私删除这一版不开放，开放之前重新考虑，到时连同⑤一起看（两件都可能要给格子记下给出者的地址，分开做会做两遍）。要改成"每个给出者都被列入才藏"，有三处难点：一是判据要带上读的时刻（佐证晚于读的时刻时，那一刻这个值只有被删的来源，仍该藏），每处调用各给自己的时刻，按 `entity_key` 定位没有时刻、按有史以来算；二是 `changes` 里一个格子在窗口里前后两侧都可能出现，两侧的时刻不同，被藏的占位要按"格子 × 这一侧"给，不能按格子给一次；三是状态类表上佐证可能只盖住格子区间的一部分（佐证项的区间里一部分同值、一部分已被别人改掉），严格做要把格子切开分别判，否则只能在佐证盖住整个格子时才不藏。⑤ **删除执行之后**：哪个块给出格子的值，靠重述块体里写的事件、字段、序号去认；执行把被列入的块清空之后，被清空的重述认不出来，格子退回去认写入自己的块，于是第二项删除列入并执行掉第一项删除的重述之后，那个值又读得到了（这一版不落账删除的执行，到不了这个状态）。等落账执行那一步一起定：给格子记下给出者的地址（改存储），或者按事件格式 5.9 执行时连同版本表里由这些块得出的内容一起清掉。定下之前照现状 |
| 格式 6 发布前 | **升级前的备份何时可以删、之后的隐私删除怎么作用到它**：本机模式升级之前在 home 旁边留一份备份（architecture §8「升级前的备份」），saveslot 从不删它。升级之后在新版本里做的隐私删除不会作用到这份备份，被删的内容仍留在其中，直到用户自己删掉备份。要定的是：备份留多久、是否提示或到期删除；新版本里确认一项隐私删除时要不要提醒"还有一份升级前的备份"，或把这份备份一并处理 |
| P4 前 | **切换的批大小、进入切换的剩余量阈值、连续追不上多少批后直接切换**：内核常量，占位初值是 500 条日志事件一批、剩余不超过一批进入切换、连续 20 批追不上直接切换（规则见 data-model「物理做法」）；等 schema 重建的容量实验（实验 9）给数 |
| P4 前 | **官方 schema 的细则**：结构只留位已定（编译后的定义里可选键 `extends`、表与字段上的 `official`，见 data-model「官方 schema 与用户 schema」与事件格式 §10），余下随实现一起定：标识与版本号的写法、谁发布、随 CLI 打包还是有远程来源；`extends` 指向整个 slot、一张表还是都可以，能否扩展多份；官方的表与字段能否改名、改说明、加别名、改单位、改约束、删掉，哪些改了仍算"符合"；`compatibility` 由谁声明、取值有哪些、何时检查，官方出新版本时哪些变化可以自动跟进，本机离线时由什么触发，大版本升级怎么接迁移状态机，用户能否停在旧版本或解除 `extends` 而保留数据；数据目录怎么表示"符合哪份官方 schema 的哪个版本"，用派生规则投影成官方形状的"映射"与 `extends` 是一种声明还是两种，已用旧模板建好的 slot 事后声明为符合是哪一类 schema 变更（`declare_extends`）；官方 schema 带的说明、别名、规则原文在不可信文本的规则里算谁写的；汇总粒度与覆盖列要不要成为通用要求 |
| P4 前 | **派生规则的文本随改名怎么更新**：文档里派生规则的文本是提交时的原文，它引用的表或字段之后改名，文本不改写、仍是旧名字（规则按 ID 绑定，求值不受影响；原样交回按文本相等判为没改，见 data-model「schema 文档格式」）。能改派生表时（`change_rule`）要定：改名时把文本里的名字一并改写，还是读一侧按当前名字给出、交回时再按当前名字解析 |
| P5 前 | **当前恢复次数要认 `tenant.imported`**：规格（data-model「删除之后」「恢复次数」、09 §5.2）定的是取日志里最近一条 `tenant.restored` 或 `tenant.imported` 的 `restore_count`，现在读它的三处（`write/reads.ts` 的 `restoreCount`、`write/resolve.ts` 里内联的一份、`read/select.ts` 的 `restoreCount`）只认 `tenant.restored`。导入实现时三处一起改（最好收成一处）；另有 `meta` 表里没人读写的 `restore_count` 键，同时决定删掉还是启用 |
| P5 前 | **删除的法律口径**，需法务确认：删除后保留的元数据（某时有过一行、被谁写过几次、每次的类型与意图；前提的声明与它的状态变化，只含序号与 ID）是否可接受；物理删除、备份保留期如何告知；24 小时宽限期与被遗忘权时限的关系；对用户的告知里写明运营方技术上读得到托管用户的全部数据（托管服务只有基础设施层的静态加密）；有来源键的记录在物理删除之后若连接器再同步同一条会重新出现、导入之后源头在导出之后做的删除带不过来，这两条是否需要额外的告知或限制。**它不挡本机模式。** 事件头按"尽量少留"设计，能放进内容区的都放内容区；[`09-event-format.md`](09-event-format.md) 列出事件头里留下的字段，供法务审阅，并写明结论不利时哪些字段要动。已定的事实口径：云服务按到期时刻主动执行物理删除；本机 saveslot 服务没在运行时，物理删除在下次启动时执行，回执如实说明；本机删除只作用于 saveslot 当前的数据目录，系统级备份（Time Machine 等）里的旧副本不由 saveslot 管理，从这类备份恢复等于恢复到当时的数据 |
| P5 前 | **云端账户没有 slot 时的出路**：云端新账户没有 slot；建 slot 要么登录后用 CLI，要么给 Agent `saveslot.schema` 且范围为全部（默认不授予）。只用网页宿主的人因此还得另装 CLI。可选：授权页上提供"按模板建一个 slot"；或靠空状态的说明加 `track` prompt（需要上面那种凭证） |
| P5 前 | **自建时用户怎么拿到初始凭证**：自部署由运维用 `saveslot server user add` 创建人的账户，这个用户第一次登录用的凭证怎么交到他手里（一次性的初始口令、邀请链接，还是由运维代为登录签发），没有写。它不计入接入的"一次同意"，但流程要补齐 |
| P5 前 | **云服务跑几个 saveslot 进程**（一个，还是固定路由的少数几个）；每个 cell 放多少租户，等实验 3a |
| P5 前 | **租户整体删除**（对外提供云服务前必须定义；不挡本机模式：本机上删掉数据目录与配置目录就是全部）。逐条隐私删除满足不了它：事件头与元数据块按设计永远留下。要回答：① **删什么**：租户存储是否整库删除，包括事件头链——"事件头永不删改"（K1）的适用范围是否限于租户存续期间；控制面里这个租户的凭证、OAuth 授权、租户目录与路由；读取记录；应用日志与错误上报里与它有关的内容，含服务器模式的调用记录（由部署方持有、在租户存储之外，已经收走的记录里留着被删租户的 ID；architecture §9「调用记录」）。② **备份与归档**：备份、快照、冷租户归档里的副本何时消失、怎么告知；恢复一份早于删除的备份时靠什么不让整个租户复活——需要一份租户存储之外、租户级的删除登记，它存什么（只有不透明的租户 ID？）、保留多久。③ **流程**：谁能发起（只有用户会话？要不要重新认证）；有没有预览、宽限期与撤回；与逐条隐私删除的 24 小时宽限期是什么关系；宽限期内租户能不能读写、连接实例是否立即失效。④ **进行中的事**：未到期的隐私删除、进行中的迁移、对拍、导入怎么处理。⑤ **删除之前**：是否提示或要求先导出；导出文件、连接器与外部系统里的副本不由 saveslot 管理，怎么告知。⑥ **删除之后留什么**：是否保留"曾有过这个租户"的最小记录（租户 ID、删除时刻），计费与合规要求保留的记录归谁管；租户 ID、用户主体 ID 是否永不复用；同一账户能否再建一个新租户。⑦ **回执**：租户没了之后，用户凭什么确认删除已经完成、备份何时失效。⑧ **各部署形态**：云服务由账户系统发起还是由 saveslot 的接口发起；自部署是不是一条运维命令；本机是否提供一条命令代替手动删目录。⑨ **与别的设计的关系**：与"整个 slot 删除"是否共用一套机制；将来共享 slot、开发者采购托管时，删除一个用户与删除一个租户不再是一回事。⑩ **法律口径**：与"删除的法律口径"一并交法务——法定时限、可保留的最小信息 |

## 三、可以开发后再定

- **按数据归属设中心**：哪些数据从一开始就必须"永不离开设备"？（多节点才用；slot 的"归属节点"字段已留。）
- **社区 Schema + SKILL 的安全**：SKILL 由用户的 Agent 执行，权限声明与审核怎么做（提示注入风险）？第一版的模板随 CLI 打包，不引入远程来源。
- **`unavailable` 缺一个"服务已失败"的原因**：本机服务失败（打开租户时核对不过等，留在失败状态直到被停止，02-architecture §7）时，`/v1` 现在回 `unavailable`、原因 `stopping`、不带 `retry_after`：契约的原因里没有"失败"，`stopping`（不再接新的请求）最接近。它不准的地方：服务并没有在停止，不会自己好起来，要人看 `saveslot status` / `saveslot doctor` 处理之后重启；MCP 对 `stopping` 的文字"saveslot is stopping; try again shortly"在这种情形下会让模型白白重试。考虑给契约加原因 `failed`（不带 `retry_after`，文字指向 `saveslot status` / `doctor`），这是操作契约的改动，要先有决定稿。
- **连接实例的最近使用时刻**（`Connection.last_used_at`）：第一版不给。初步考虑查询时从日志与读取记录取这个连接实例最近一次操作的时刻，不在认证的路径上写任何东西。
- **read_log 要不要像日志一样串链**（防误操作）。read_log 是本地运行状态，加不加都不动日志。
- **数据权限的表级、字段级（后续版本）**：slot 一级已进第一版——连接实例的授权 = 动作 scope × slot 范围（全部，或一个 slot 列表），范围外的 slot 对它与不存在相同（contract 第 12 节，P5）。余下的：
  - 资源细到表、敏感字段到字段级；同一个连接实例对不同 slot 给不同的 scope（第一版要这样就签两个连接实例）；签发后修改范围（第一版吊销重签，事件格式为它留了 `principal.scope_changed`）。表级要先回答"事项、源数据按什么过滤"（它们按 slot 归属，不按表），以及完整 schema 文档（`catalog` 的 `schema` 档、草稿的文档、`schema_change` 事项）能不能给只看得见部分表的调用方（这一版要 slot 的每张表都可见才给：派生规则的文本会带出它读的表名）；字段级要动派生表的可见性与读结果的形状。
  - **表一级可见范围下源数据怎么给**：源数据按 slot 归属，原文与 `api_call` 的请求里可以提到 slot 的任何表。第一版里调用方对某个 slot 的可见范围不是整个 slot 时，这个 slot 的源数据对它一律不存在（contract「sources」）。放开表级范围时再定细的：按它产生的数据落在哪些表过滤、产生的数据跨了可见与不可见的表时原文给不给、证据原文与 `api_call` 的请求是否分开处理。
  - **派生数据按来源继承权限**：一张派生表同时来自健康和记账数据，读者必须对所有来源都有读权限——saveslot 有完整的来源关系，可以强制执行。第一版派生规则不跨 slot，到 slot 一级时派生表与它的基础表同进同出，这条还不用。
  - 没权限的表在数据目录里不可见；只读 SQL 也受同一套权限约束（行 / 列级隔离）；远程模式可按领域分 OAuth scope（第一版的 slot 范围不编码进 scope 字符串）。
- **授权页上选 slot 范围**：第一版经远程授权的连接实例范围一律是全部，限定范围的凭证只能由用户会话签发静态令牌（surfaces 第 15 节）。加回时要定：
  - 客户端怎么声明它要的 slot：客户端元数据里的扩展字段，名字暂定 `saveslot_slots`，实现时核实；写法不对时忽略还是拒绝。
  - 预选规则：客户端声明了时预选其中现有的那些、声明了却不存在的怎么在页上列出；没声明时预选"全部"；选择器是否始终显示。
  - step-up：越权后重新授权得到的新连接实例，范围沿用原来的、预选原来的，还是重新选。
  - 用户在授权页上同意之后、授权码兑换之前，选中的 slot 被删了怎么处理（拒绝兑换，还是按剩下的签发）。
  - 授权结果与令牌响应里不回传 slot 名单（slot 名是用户自己的数据），客户端只经 `catalog` 看到范围内的 slot：这条照旧。
- **"某类操作只接受用户会话的确认"何时实现**：slot 策略的结构里已留位；它依赖 slot 策略的修改（`policy.set`），与高影响 ③ 一起后续。
- **按来源级别的系统裁定**：秩表与重判事件的结构已留位；裁决规则的细节（一方命中一方未命中时怎么比、低级别的顺序写入能否直接覆盖用户原话）在加回时定。"外部权威"级别由谁声明的规则已定（data-model「来源级别」：由连接实例被授予的权限决定，写入方不能自报）；待定的细则：授予的形式（一个新的 scope，还是连接实例上单独的一项）、能否按 slot 分别授予、凭证被吊销后它声明过的级别在裁定时还认不认、与字面命中的关系。
- **温度单位的互相换算**：第一版 `Cel`、`degF`、`K` 各自成量纲、不换算。加回时给单位定义新增可选的偏移量，已有定义不变。
- **改正实体的键（`rekey`）**：第一版键不可改，写错键靠撤销重写，历史会断成两个实体；回执会标出写法相近的已有键（`similar_keys`）。若评测里写错键很常见（eval 4d），再加 `rekey`；它是新的写入意图或 op 参数，不改已有事件。
- **词表外单位的自定义**：第一版单位取自固定词表，词表外的量用 `decimal` / `integer` 字段并在说明里写清单位。是否允许 slot 自带单位定义，随新的单位词表版本定。
- **表名、字段名只允许 ASCII**：受限 SQL 里中文标识符要加引号，模型容易写错，所以第一版只收字母、数字与下划线；说明文字不受限。是否放开看用户反馈。放开时要重新看 `instructions` 里的 slot 清单：它靠这条字符集挡住换行、标点与伪造的边界标签。
- **统计异常的定义**：阈值、按什么分组、冷启动时怎么办都没写。第一版不判定、不产生事项；加回时是新的判定结果，旧事件缺省即"未判定"。
- **表声明预期的记录频率，读取结果带覆盖标记**：第一版没有这个机制，"应该每天有记录"是领域知识，由模板里派生表的覆盖列（有记录的天数、首末日期）交给 Agent 判断。若评测里 Agent 经常把"部分"说成"完整"，再考虑：基础表上加一个可选的声明（预期每天、每周一条，或不声明）；按时间窗读取与按时间分桶的派生行据此带一个覆盖标记（完整 / 部分 / 没有数据）。它是 schema 文档与读结果上新增的可选键，不改已有事件。要定的事：频率怎么写；标记读时现算还是进派生写入；用户明确说"那天没有"怎么表示（它不同于"没记"）。
- **确定性迁移的人工放弃出口**：纯确定性迁移没有人工放弃出口；若 eval 发现大的确定性迁移也需要人能中途放弃，再加（"放弃迁移"事件已留位、第一版不产生，加出口是新增一种事件，不改已有事件）。
- **读派生表时汇总 `input_marks` 的代价**：第一版每次 `query` 读派生表先读规则所读基础表上的标记；没有标记就不再查，有标记时只对带标记的行求出它们落在哪个分区，代价随带标记的行数变化、不随表的大小变化。标记很多时是否改为按分区维护成员，等实验 4 的数字定。
- **小数分组键先舍入再分组**：第一版只收小数位上界不超过推断精度的 `decimal` / `quantity` 分组键（上界的算法见 [`03-data-model/11-restricted-sql.md`](03-data-model/11-restricted-sql.md)「类型」；含除法、`avg`，或乘积、字面量的位数超出精度的不收）。若有需要，改成先把键按字段精度舍入再分组：`half_even` 的键要另写舍入，分组语义随之改变，要进规格并出新的白名单版本。
- **PostgreSQL 上受限 SQL 要不要单独的只读连接**：并发与 cell 容量之间的取舍。第一版共用连接。
- **托管集群容量实验**（云服务扩容前做，不影响方案本身）：Linux 云盘上的崩溃恢复与备库切换时间；满载 24 小时的 autovacuum 覆盖与 wraparound 余量——决定每组放 2,000 还是 5,000 个用户库。另有冷用户恢复延迟、并发尾延迟待测。
- **冷租户归档在租户恢复回集群后何时作废**：留到云服务容量阶段再定。初步考虑：恢复并 `verify` 通过、下一次常规备份成功后作废；不对有未到期删除的租户做冷归档。
- **内核在 Node、Bun、Electron 主进程之外的运行时里能否实例化**：未核实。
- **read_log 是否随日志复制**（多节点）。
- **开发者 SDK**（后续版本）：接口怎么设计、开放到哪一层；开发者采购托管时的租户模型（开发者 / 应用 → 终端用户 → slot）与数据归属
  （归终端用户还是归开发者，终端用户能否导出、迁走）；嵌入存储是否作为节点并入 saveslot 服务；非 JS 宿主（如 Python）的形态——实际只能是本地 sidecar 进程。
- 成本与商业化：先不讨论。

# 09 · schema 演进

前面几章里，`expenses` 有哪些字段、`monthly_total` 怎么算，都是现成的。这一章讲它们从哪来：schema 是什么、由谁写、改的时候数据怎么跟着变，以及派生表的规则怎么执行。

> 本章讲完整设计，第一版不做的地方当场标出。第一版的 schema 变更只做不需要模型参与的那几类。

## 1. schema 是什么，由谁写

**schema 是一个 slot 的数据定义：有哪些表、每个字段的类型和单位、哪些必填、派生表按什么规则算。** 它是一份 JSON 文档。

saveslot 不内置任何领域。记账、健康、项目跟踪长什么样，都由 schema 说明。schema 有三个来源：

- **用户自己的**：由用户的 Agent 起草。每个人可以有自己的数据样式。
- **官方的**：saveslot 发布的精选 schema，同时是一份对外的约定：读预算的看板、算营养摄入的工具，可以认出"这个 slot 符合它"，按它的定义读数据（第 8 节）。
- **社区的**：和一份给 Agent 看的使用说明一起发布（Agent 生态里把这种说明叫 SKILL：一段文字加可选的脚本，由 Agent 的宿主加载）。schema 定义数据长什么样，使用说明告诉 Agent 什么时候写、怎么用。

> 随命令行工具打包的几份模板（跑步、预算、日常支出）**不是官方 schema**，就是普通的用户 schema：建 slot 时拷一份过去，建完 slot 就和模板没有关系了，命令行工具升级换了模板也不影响已建的 slot。官方 schema 的结构在 P4 之前定（第 8 节）。

那本账的 schema 是这样的（就是日常支出模板的内容）：

```json
{
  "slot": "ledger", "base_version": null, "timezone": "Asia/Shanghai",
  "tables": [
    {
      "name": "expenses", "kind": "base", "description": "每笔支出一行",
      "time": { "type": "event", "field": "date" },
      "fields": [
        { "name": "date", "type": "date", "required": true, "description": "支出当天（slot 时区的自然日）" },
        { "name": "category", "type": "text", "required": true, "description": "类别，如餐饮、交通" },
        { "name": "amount", "type": "quantity", "unit": "CNY", "required": true, "min": 0, "description": "金额" },
        { "name": "note", "type": "text", "description": "备注" }
      ],
      "duplicate_keys": [["date", "category", "amount"]]
    },
    {
      "name": "monthly_total", "kind": "derived", "description": "每月支出合计与记录覆盖。某个月没有行表示那个月没有任何支出记录",
      "rule": {
        "sql": "SELECT date_trunc('month', date::timestamp)::date AS month, sum(amount) AS total, count(DISTINCT date) AS days_recorded, min(date) AS first_date, max(date) AS last_date FROM expenses GROUP BY 1",
        "time_dependency": "bucketed"
      },
      "fields": [
        { "name": "month", "description": "该月第一天" },
        { "name": "total", "description": "该月支出合计（CNY）；只含已记录的支出" },
        { "name": "days_recorded", "description": "该月有支出记录的天数（不是每天都有支出，少于当月天数不代表漏记）" },
        { "name": "first_date", "description": "该月第一条记录的日期" },
        { "name": "last_date", "description": "该月最后一条记录的日期" }
      ]
    }
  ]
}
```

读这份文档时注意几处：

- **`timezone`** 决定"哪一天"怎么算。`date` 是这个时区里的自然日。
- **`time`** 声明表的时间类型（第 7 章）。
- **每张表、每个字段都有一句必填的说明。** 这是给 Agent 看的：它靠这些说明理解数据。
- **`duplicate_keys`** 是疑似重复的判据：同一天、同一类别、同一金额。命中只是标记出来，不拒绝写入。
- **派生表只写规则和每个字段的说明。** 字段的类型、单位由 saveslot 从规则推断。
- **`time_dependency`** 说明这条规则和时间的关系，决定结果能不能算好了存起来。三个取值：`none`，结果与时间无关；`bucketed`，按业务时间分桶（这里是按月），每个桶算好存着，基础数据变了才重算；`now`，结果依赖"今天"（比如"本月剩余预算"），过一天就变，所以每次读的时候现算（第 7 章第 14 节）。
- **`days_recorded`、`first_date`、`last_date` 是覆盖列。** "11 月花了 89 元"是记全了一个月，还是只记了三天？saveslot 不判断：哪些天"应该"有记录是领域知识。覆盖列把事实摆出来，让读的一方自己判断（第 7 节）。

表和字段上还可以写两样这份文档里没用到的东西：

- **`aliases`（别名）**：用户对这张表、这个字段的别的叫法，见下面"别名"一小节。
- **`external_key`（来源键）**：只用在事件类表和无时间表上，声明哪几个字段是这条记录在来源系统里的编号（比如 `["origin", "external_id"]`）。从手环、记账 App 定时同步数据的程序（连接器）按它写入：这条记录已有就按上次交来的值判断要不要更新，没有就新增，反复同步也不会重复（第 5 章第 3 节"按来源键同步"）。

### 字段类型、单位与精度

字段类型有：文本、整数、小数、布尔、枚举、日期、带时区的时刻、带单位的数量（`quantity`），以及指向同一 slot 另一张表的引用。

**`quantity` 是带单位的数值。** 写入的值自带单位，同一类的单位自动换算到字段声明的单位。单位取自一张**固定的词表**：长度、质量、时长、体积、能量等，每个单位有一个代码（`km`、`kg`、`min`）和一个换算系数。营养、用药这类记录用得上的 `ug`（微克）和 `floz`（美制液量盎司）也在里面。

- **词表之外的单位不收。** 草稿里用了，编译时就拒绝，并给出同类的候选。确实没有合适单位的量，用普通的小数字段，在说明里写清单位。
- **只收含义各地一致的单位。** 词表里每一行都是"saveslot 保证换算正确"的承诺。所以杯、汤匙不收（一杯在各地是 200 到 250 毫升不等），英制液量盎司不收（和美制差 4%），国际单位 IU 不收（每种物质换算不同）。这些量写成 `mL` 或普通小数，用户的原话（"两杯"）留在证据里。
- **货币是个特例**：每种货币自成一类，互不换算，因为汇率不是固定的系数。往 CNY 字段写美元会被拒绝。要换算，就把汇率作为基础数据写进来，在派生规则里算。
- **月、年不是单位**：它们不是固定长度。

**精度与舍入。** 带小数的字段各有一个精度：小数点后保留几位（`scale`）、怎么舍入（`rounding`）。可以在字段上声明；没声明时，货币按它通行的最小单位（人民币 2 位、日元 0 位），其余默认 6 位，舍入默认是四舍五入。写入的值先换算单位、再按精度舍入后落账；小数位数超了而被舍入时，回执里会提醒。"两个值是不是相同"也是在舍入之后比的。

### 名字的规则

slot 名、表名、字段名只用字母、数字和下划线，字母开头，最长 63 个字符。这样它们在只读 SQL 里可以直接当标识符写。名字不分大小写：同一个 slot 里不能同时有 `Runs` 和 `runs`，SQL 里写哪种都认。有几个名字是 saveslot 自己保留的：不能以下划线开头；字段名不能叫 `valid`、`valid_from`、`valid_to`（写入和查询里表示生效区间的参数名），也不能叫 `row_id`、`entity_id`（SQL 里行与实体的 ID 列）。说明文字和别名不受这个限制，可以写中文。

### 别名

用户说"伙食费"，表叫 `expenses`；用户说"用时"，字段叫 `duration`。名字是给程序认的标识符，用户不会照着它说话。表和字段上可以写一组别名，把用户的叫法记下来：

```json
{ "name": "expenses", "aliases": ["支出", "花销", "伙食费"], … }
```

别名出现在数据目录里，读目录的 Agent 靠它把用户的说法对到表上。三条规矩：

- **别名不是名字。** 请求里、SQL 里只认名字，写别名会报"没有这张表"；报错会把别名对得上的那个名字排在候选的最前面，让 Agent 一步改对。别名之所以不参与解析：别名可以重复（用户的说法本来就有歧义），名字必须唯一；而且改一个别名如果能让同一个请求落到另一张表上，"只改说明"就不再是安全的改动了。
- **不能和仍然认得出的名字撞。** 表的别名不能等于本 slot 里任何一张表现在的名字或还认得的旧名，否则 Agent 照着别名写，请求会落到另一张表上。
- **它是不可信的文字**，和说明一样：读出来时包在不可信边界里，不进工具描述，也不随隐私删除清除。所以不要把用户的隐私原话写成别名。

每个对象最多 8 个别名。改别名和改说明一样自动生效（第 2 节）。

### 哪些字段要一起判冲突

第 5 章讲过，并发的写入按字段合并。字段之间有关系时，这会造出谁也没写过的组合（开始日期晚于结束日期）。表上可以声明 `together`，把有关系的字段编成一组：

```json
"together": [["start", "end"]]
```

同组的字段在冲突判定时当作一个整体。不声明时每个字段各自一组。

规格：类型的取值范围、单位词表、精度的默认值见 [`../spec/03-data-model/10-types-and-units.md`](../spec/03-data-model/10-types-and-units.md)。

## 2. 提交一份 schema

Agent 调 `schema_draft` 提交文档。saveslot **编译**它：

- 解析文档，校验类型和约束；
- 解析派生规则的 SQL，检查白名单（规格「受限 SQL」：收哪些语句、函数、运算符都列成了表，不在表里的一律拒绝），在现有数据上试跑，推断派生表的列和类型，算出它依赖哪些表和字段；
- 给表、字段、规则分配 ID，回填到文档里；
- 和当前版本比对，判断每一处改动属于哪一类，给出影响预览。

编译不过就报错，指出位置，不产生任何事件。比如规则里用了 `NOW()`，或者上面那条规则漏写了 `::timestamp`：不写的话 PostgreSQL 会选带时区的那个函数，结果随会话时区变，saveslot 按"结果不确定的函数"拒绝，并给出改法。

编译通过后有两种结果：

| 结果 | 什么时候 |
|---|---|
| 直接生效 | 新建 slot（里面还没有数据，没有什么可破坏的）；或者草稿里的每一项改动都属于"可以自动生效"的那几类 |
| 待确认 | 生成一个"schema 变更"事项，等人或 Agent 确认 |

### 哪些改动自动生效

由 slot 的策略决定。建 slot 时 saveslot 写下一份默认策略，其中有八类改动不经确认就生效：

| 自动生效的改动 | 为什么安全 |
|---|---|
| 新增一张基础表 | 不碰已有的数据 |
| 新增一张派生表 | 只是多算一份 |
| 新增一个可选字段 | 旧行这个字段为空 |
| 只改说明与别名 | 不动数据 |
| 改一个没有别人在用的名字 | "没人在用"指最近 30 天没有提交者以外的连接实例读写过它 |
| 放宽约束（必填改可选、放宽范围、枚举加值） | 旧数据都满足 |
| 改疑似重复的判据 | 只影响之后新增的行 |
| 一张从未被写入、也没有别人在用的表，改它的结构 | 没有值可丢，也没有值要转换（第 4 节"表还没写过数据时"） |

共同点是：不改动已有的值，不让带着旧版本的写入失败，不让现有的读取读到不同的东西。**一份草稿里只要有一项不在此列，整份草稿都进待确认。**

> 第一版没有修改 slot 策略的操作，每个 slot 用的都是建 slot 时写下的那份策略。策略写在日志里，不随内核变：默认策略将来再加类别，只对之后新建的 slot 生效。

### 改的时候怎么提交

**表内交整份，slot 内只交改动。** 草稿里只列要新建或改动的表，每张列出的表给完整定义；没列的表不变。Agent 读到的就是整份定义，改完交回最自然，不需要学一套增量操作的语法。

草稿带着 `base_version`：它是基于哪个版本起草的。和当前版本对不上就拒绝，要求基于新版重新起草。同一个 slot 同时只能有一个变更在进行。

### 名字与 ID

Agent 用名字写；saveslot 分配 ID。**字段靠 ID 标识，名字只是标签。** 删掉的 ID 不复用。

这带来一个问题：提交的文档里少了一个字段，是改名了，还是删了？saveslot 不猜，规则是确定的：

| 提交里的字段 | saveslot 的处理 |
|---|---|
| 带着 ID | 按 ID 匹配。名字不一样，就是改名 |
| 没带 ID，名字和现有字段相同 | 同一个字段 |
| 没带 ID，名字是新的 | 新增 |
| 现有字段没被匹配到，也没列入 `drop_fields` | 报错："这个字段没出现；要改名请带回 ID，要删除请列入 `drop_fields`" |

所以不改名的 Agent 完全不用管 ID，漏写一个字段也不会被当成删除。**删除必须显式。**

## 3. 版本不可变

每次 schema 变更产生一个新版本，版本号是 slot 内递增的整数，就是前面一直出现的 `sv`。

**旧版本永不修改。** 这保证数据不会被悄悄重新解读：

- 每次写入的事件里记着它用的 schema 版本。
- 按时刻读用当时那一版来解释数据。
- 读取记录也记着 schema 版本。

**对外只有最新版。** Agent 每次读都拿到当前的 schema，自然跟进。旧版在内部保留，供按时刻读使用。

由此有两条配套的规则：

**读结果自带说明。** 每个值带单位，结果带 schema 版本。一个 Agent 的记忆里如果还留着"金额字段叫 `amount`、备注是自由文本"这样的旧印象，它能从结果里发现已经变了。

**带旧版本号的写入，只在写到不兼容的字段时才拒绝。** 写入带着 `sv`。如果自那个版本以来，它要写的字段发生了不兼容的变化（改了类型、换了另一类单位、被删除），就拒绝并提示重新读取。如果它要写的字段没变，或者只是改了名、表里加了别的可选字段，就照常接受。同一类单位之间改单位（公里改英里）也不算不兼容：写入的值自带单位，saveslot 会换算。收紧约束同样不算：写入一律按当前的定义校验，不满足就报校验错误。一个例外方向更严：一张从未被写入的表整体改过结构（第 4 节），之后带旧版本号写这张表的请求一律被拒，提示重新读取。

第二条的理由：版本是以 slot 为单位管理的。如果按版本号一刀切，改 slot 里任意一张表，所有 Agent 的写入都会被拒掉一轮。按字段判断，只影响真正受影响的写入。

改名之后，旧名字还能用一阵：写入按它带的 `sv` 解析名字，任何版本的名字都认；不带版本的读取，认最近 10 个版本里用过的旧名，并在回执里提示新名。改名时旧名不会自动变成别名；想让人和 Agent 在很久以后仍认得出旧叫法，就把它写进 `aliases`，它只帮着对上说法，不恢复解析。

## 4. 三类改动

改 schema 时，已有的数据要跟着变。代价分三档：

| 类别 | 数据怎么变 | 要模型吗 | 第一版 |
|---|---|---|---|
| 只改元数据 | 已有的值不变 | 否 | 做 |
| 确定性转换 | 用一个确定的函数把旧值算成新值 | 否 | 做 |
| 重新抽取 | 回到源数据原文，重新得出新值 | 是 | 不做 |

哪一类由 saveslot 判定，在编译回执里逐项列出。（新建 slot、新增一张表没有"已有的数据"，不属于这三类，回执里单列为"新建"。）设计 schema 时尽量让改动落在前两类。规格里有一张完整的表，把 schema 文档里每个键的每种变化属于哪一类、是否自动生效、带旧版本的写入还收不收、第一版支持不支持都列全了（[`../spec/03-data-model/07-schema-evolution.md`](../spec/03-data-model/07-schema-evolution.md)「改动分类与迁移手段」）。下面各举几例。

### 只改元数据

**例一：加一个可选字段。** 给 `expenses` 加 `payee`（收款方）。旧行这个字段为空。

**例二：改名。** `note` 改成 `memo`。字段 ID 不变，存储里的列名用的是 ID，所以数据一个字节都不动，只改目录里的名字。如果最近有别的连接实例按旧名字读写过它，会列进预览，需要确认。

**例三：删字段。** 把字段列入 `drop_fields`。表里的字段和数据删掉；源数据不动。删字段要确认（表从未被写入时例外，见本节末尾）。被别处用着的字段（派生规则、`entity_key`、`duplicate_keys`）不能直接删，要在同一份草稿里把依赖它的地方一并改掉。

**例四：删一整张表。** 把表名列入 slot 一级的 `drop_tables`，同样要确认。之后这张表从当前版本的目录里消失，不能再读写，带着旧版本号写它的请求会被拒绝。它的源数据不动（那些话还在，可以照常查看和隐私删除），日志里关于它的事件也都在，按过去的记录时刻仍能查到它当时的样子。被别的表的引用字段指着的表不能直接删，要在同一份草稿里把引用它的字段一并改掉。

### 确定性转换

**例：文本改成枚举。** `category` 原来是自由文本，现在想规范成几个固定取值。Agent 在字段上写一个迁移表达式：

```json
{ "id": "f2", "name": "category", "type": "enum",
  "values": ["food", "transport", "other"], "required": true, "description": "类别",
  "migrate": { "sql": "CASE category WHEN '餐饮' THEN 'food' WHEN '交通' THEN 'transport' ELSE 'other' END" } }
```

表达式是受限 SQL，结果确定。saveslot 编译它，在现有数据上试跑，把结果和失败的样例放进预览。

> 第一版的迁移表达式只能用这个字段自己的旧值和常量，不能引用别的字段（上例只用了 `category`）。它只对有值的地方求值：一个可选字段被清空过、或从没填过，换算之后仍然是空的，不会落到 `ELSE` 那一支上。原因在下一段：迁移是把旧的写入一条条换算过去，一条写入只记着它改过的字段。只依赖本字段时，旧写入对这个字段的每一次改动恰好变成新版的一次改动，谁写的、来源是哪句话、管哪段时间都原样带过去；依赖别的字段就做不到这一点。要把几个字段合成一个新字段，第一版用派生表，或者让 Agent 读出来重新写入。

**转换的结果不写进日志。** 日志里记的是这条转换规则本身（它是编译后的 schema 定义的一部分）。以后重放日志时，saveslot 按这条规则把旧的写入重新换算一遍。因为规则是确定的，重算出来的和当时一样；为了能发现"万一不一样"，切换到新版本的那条事件里记着每张新表的行数和一个校验值，重放时核对。这和派生表的做法相同：算得出来的东西不存进日志，只存一个用来核对的校验值。

同类单位之间的变化（比如公里改英里）不用写表达式，saveslot 自动换算。改 slot 的时区也归这一类：日期本身不变，要重建的是那些按时区把时刻归到某一天的派生表；它要确认，是因为之后"今天""哪一天"的含义变了。

**收紧约束**也在这里处理：把可选改成必填、缩小取值范围时，可能有现有的行不满足。字段上可以给一个 `backfill`，说明这些行怎么补；没给而又有行不满足，编译失败，并报出有多少行、长什么样。`backfill` 可以是一个表达式，也可以是一个常量。表达式只对已经有值的地方算；原来就没有值的地方（新增一个必填字段时，所有旧行都是这种情况；把可选改成必填时，没填过的行也是），只能用常量补，所以这两种改动一律必须给常量，哪怕表里现在一行都没有；常量和表达式只能给一种。这样补进去的值，来历记为"schema 第几版的补值"，它不是任何人说过的话，也就不会随哪句话的删除而消失。也正因为它不是用户的内容，隐私删除判断"这一行还存不存在"时不算它：一行如果只剩下补进去的常量，照样整行删除（第 8 章第 4 节）。另外两点：补值只补存在的行，已撤销的行、撤销留下的空白不补（"必填"约束的是存在的行）；补出来的这个版本不能撤回，要改就提交新的 schema 草稿。

### 重新抽取

**例：拆字段。** `note` 里用户写的是"和老王在楼下面馆"，现在想拆成 `payee`（收款方）和 `companions`（同行的人）。这没有确定的函数可用，只能回到原话重新理解。这是 saveslot 里唯一真正新的迁移方式，也是最贵的一种。第 6 节单独讲。

> 重新抽取不进第一版，是第一版之后的第一个增量；事件格式里为它留了位置。
>
> 第一版的草稿里如果出现了表示重新抽取的键（或者别的第一版不支持的改动，比如在写过数据的表上改时间类型），**整份草稿报错**，指明是哪个键。不会被悄悄当成"只加一个可选字段"：那样 Agent 会以为旧行将来会被补上值。

### 表还没写过数据时

有几种改动在写过数据的表上不支持，因为已有的值没有通用的转换办法：改表的时间类型（事件类改状态类）、改 `entity_key`、改 `granularity`、把基础表改成派生表、改引用字段的目标、换一组来源键。可是 Agent 起草的表，常常建完才发现时间类型选错了，那时一行数据都还没有。

所以这几种改动在**从未被写入**的表上可以做，就地改，不用删了重建。同一张表上，删字段、改类型、改单位、新增必填字段这些平时要确认的改动，也一样处理。"从未被写入"只看日志：这张表从来没有过一次写入事件。一次写入之后，就算行已全部撤销、内容已全部隐私删除，也不算：历史和事件还在，改了结构它们就无处安放。只被读过（读到空结果）还算从未被写入。

这种改动有别人在用时要确认；没有别人在用（最近 30 天只有提交者自己读写过它）时自动生效，就是第 2 节表里的第八类。改完之后：

- 表 ID、字段 ID、说明、别名都保留，依赖它的派生规则按新定义重新编译。
- 回执里这类改动的类别一律记"只改元数据"：表里没有值，也没有转换。
- 新增必填字段、可选改必填仍然要给常量形式的补值：这条规则不看表里有没有行（上面"确定性转换"一小节）。
- 带旧版本号写这张表的请求一律被拒（第 3 节）。
- 草稿提交之后、确认之前，这张表如果被写入了，确认会被拒绝，只能提交一份新草稿取代它。"从未被写入"一旦不成立，就永远不成立。

代价是写过一条测试数据的表只能删了重建。规格的改动分类表里，这几行在"第一版"一栏写着"表从未被写入时做"。

## 5. 迁移过程：读永远不停

确认一次变更之后，数据怎么从旧结构变到新结构？saveslot 的做法是：**后台建好新版，追平之后一次切换。** 整个过程中读不停，写只在切换的一瞬间暂停。

### 状态机

```
草稿 → 待确认 → 迁移中 → 切换 → 当前 → 已退役
```

| 阶段 | 读 | 写 | 在做什么 |
|---|---|---|---|
| 草稿到待确认 | 旧版 | 旧版 | 新版只是提议。不过期；新提交的草稿取代还没确认的旧草稿 |
| 迁移中 | 旧版 | 旧版 | 后台从日志构建新版的表，并持续追上期间的新写入 |
| 切换 | 不停 | 暂停极短时间 | 一个事务里追完最后一段，把"当前版本"指向新版 |
| 当前 | 新版 | 新版 | |
| 已退役 | 对外不可见 | 不可写 | 内部保留，供按时刻读 |

第 2 节讲的编译发生在"草稿"这一步，编译和影响预览是同一步。能自动生效的草稿跳过"待确认"；只改名字或说明、不需要建新表的改动，跳过"迁移中"直接切换。

每次状态变化都是日志事件。编译后的定义也记在事件里，重放时不重新编译。

### 物理上怎么做

- **每个 slot 有一个"当前版本指针"。** 所有读写都经 saveslot，把逻辑表名解析到指针指向的物理表。
- **要不要建新表，看物理形状变没变。** 只改名字、只改说明这类改动，表在磁盘上的样子没变，不建新表，只换目录和指针。加字段、删字段、改类型或单位，物理形状变了，就为这张表新建一张带新版本号的物理表。建好的表永不改名；没改动的表跨版本沿用。物理表名和列名用的都是 ID，永不对外。
- **新版表是把日志重放进新结构建出来的。** 每条旧写入只带走它改动过的字段，经过确定性转换变成新值。这顺带验证了"日志可以重建状态"。个人的数据量小，统一走这一条路径比分情况处理更稳。
- **切换是一个事务**：锁住指针，追完最后一段日志，校验，改指针，记一条切换事件。读不拿这把锁，完全不受影响。

这里用的是 saveslot 自己的日志，不是数据库的在线改表工具。那些工具解决的是"新旧两版同时可写"和"追数据库的日志"，saveslot 两样都不需要。

### 失败是安全的

切换之前，新版只存在于后台。失败了整个丢掉，旧版不受任何影响。切换之后只做前向迁移，不往回切。

等确认、迁移中的这段时间里旧版照常可写，新写进来的值可能让转换表达式算不出来（比如文本转数字时来了一个"十五"）。两处各有处理：确认时，saveslot 在同一个事务里对试跑之后的新写入再算一遍，有算不出的就拒绝这次确认，事项保持未决，改好表达式重新提交草稿即可；迁移中，带旧版本号的写入在自己的事务里就按新版算一遍，算不出就拒绝这次写入，提示按新版重读再写。迁移已经确认，不该被后来的一条写入卡住；那个值在新版里本来就放不下，当场拒绝比切换时悄悄丢掉它诚实。

构建中的新版表是第 3 章说的 (c) 类状态：可以丢，丢了从日志重建。这是"表只能由 `apply` 改"的唯一例外，它在切换事件处才正式成为由日志算出的状态。

### 迁移到一半，有人确认了一次隐私删除

删除事件只算当前版本里的结果。正在后台构建的新版表里，受影响的那些行整行丢掉，按日志重新建。这时被删的内容在日志里已经读不到了，重建出来的自然不含它。

> 退役的旧版表第一版一直保留，清理放到后续。清理本身也会是一条日志事件，这样"从空库重放等于线上状态"在旧表上也成立。隐私删除对旧版表同样生效。

## 6. 抽取作业：需要模型的迁移

> 本节整体不进第一版。这里只讲要点，细节见规格。

**为什么由调用方的 Agent 来做。** 重新抽取需要理解语言，要用模型。saveslot 的核心路径不调用模型，这是第 1 章的原则。所以 saveslot 把这项工作做成**作业**，交给调用方去执行：用户的 Agent 本来就在跑模型，也有权限读这些数据。saveslot 负责出题、校验答案、记录结果。接口不区分执行方，将来用户授权 saveslot 调用模型之后，saveslot 自己的后台进程可以接入同一套接口。

**怎么做。** Agent 领取一批**工作项**，对每一项给出结果再提交；做不完没关系，旧版照常可读可写，之后任何有权限的调用方可以接着领。一个工作项不是"把源数据从头再抽一遍"，而是**把碰过要重抽字段的那些写入，逐条翻译成新版的形状**，再由 saveslot 按原来的顺序重放。这样历史原样保留：某次写入是纠错，翻译后仍是纠错；行 ID 不变；状态类表的生效区间不变。

**翻译结果记进日志。** 这是它和确定性转换的区别：模型的输出不确定，重放时不能重新调用模型，所以把结果当作事实记下来。

**结果是提议，不是定论。** 从旧字段抽出新字段时，每一行的"旧值 → 新值"都进一份差异清单；同一个字段重抽时，和已确认的值不同的进清单。清单由人或 Agent 处理（全部接受、逐行接受或拒绝或直接给值），不让推断出来的值无声地取代用户确认过的值。新字段原本就是空的（纯补抽）则不进清单，直接生效。迁移期间又有写入碰到了要重抽的字段，saveslot 自动追加工作项，这一行已列出的差异作废、重抽后重新列出。

**不让迁移停在半路。** 差异很多、处理的人很久不来时有两个出口：把没处理的差异一律按拒绝处理然后切换；或者放弃这次迁移，旧版原样保留。没有差异清单的迁移（只有确定性转换，或再加纯补抽）不等人：确定性部分做完就切换，没补完的补抽在切换之后接着做。

## 7. 派生规则

### 派生表只由规则生成

`monthly_total` 不是 Agent 写的，是 saveslot 按 schema 里的规则算的。Agent 往派生表写入会收到明确的错误，并被告知该写哪张基础表。

这条约束换来的是：派生数据永远能从基础数据重算。因此派生数据从不妨碍删除，不需要单独记历史，来源也是完整的，因为输入是 saveslot 自己决定的。

规则分三级：

| 级别 | 用来写什么 | 第一版 |
|---|---|---|
| 受限 SQL | 绝大多数聚合、关联、时间窗口 | 做 |
| 沙箱里的纯函数 | SQL 写起来太绕的确定性算法 | 不做 |
| 模型判断（"本周训练过量"这类） | 这不算派生规则：是 saveslot 的后台进程做的一次普通写入，按"Agent 推断"对待 | 不做 |

分级的标准是结果确不确定：确定的才能当缓存、随时重算；不确定的必须当作一次写入记下来。

### 规则必须是确定的

同一份日志在本机的嵌入式数据库和服务器上的 PostgreSQL 重放，派生结果必须逐行一致。为此：

- 只允许白名单里结果确定的函数；
- 固定会话时区和排序规则；
- 数值统一用精确的十进制类型，不用浮点；
- `NOW()` 这类函数禁用，"今天"由 saveslot 在调用入口取一次（读的时候也可以用参数指定），作为显式的参数传给规则（第 7 章）；
- 只读本 slot 的表。（只读查询可以关联几个 slot 的表，派生规则和引用字段不行。）

白名单收哪些语句、函数、运算符、类型转换，逐项列在规格「受限 SQL」里。它的写法是"不在表里的一律拒绝"，不是"列出要拒绝的"。白名单有版本：每条规则记着自己编译时用的那一版，重放按记下的版本算；内核升级不会让没改过的规则换一种算法。

需要外部数据的计算，比如汇率换算，不算派生。先把汇率作为基础数据写进来，再在规则里用它。

**按引用字段计数，会算进指向已撤销记录的行。** 规则读到的表只含没撤销的行，但一行没被撤销、它引用的那一行被撤销了，它仍在表里，引用的值也还是原来的 ID。比如按明细的 `meal` 字段数"一天吃了几餐"，撤销了一餐而没撤销它的明细，这一餐照样被数进去。要排除，规则就关联目标表，只取关联得上的行：目标表里已经没有被撤销的那一行。saveslot 不为此另给提醒。

派生字段的单位和精度由 saveslot 从规则推断：求和、取最大最小沿用输入字段的；两个带单位的字段相乘除、得不出词表里的单位时报错，要求把结果声明成普通小数并写明说明。

### 同一个事务里刷新

**基础写入和受影响的派生值，在同一个事务里更新。** 所以读到的派生值永远不会落后于基础数据。第 2 章每次写入后面都跟着一条"派生写入"事件，就是这个。

刷新的做法很直接：**重算受影响的那一组。** 规则编译时，saveslot 分析出它按什么分组。一笔支出的金额变了，只重算它所在的那个月。如果改的是日期，从 11 月改到了 10 月，两个月都重算。

没有用专门的增量计算引擎。数据是按用户隔离的，量小。早期的测量里，在嵌入式数据库上 100 万行的整用户重算约 290 毫秒，只重算受影响的一周约 1.7 毫秒，都放得进同一个事务。写入准入的阈值由一项实验定（第 12 章的实验 4）；表大到什么程度还舒适，由容量实验测（实验 9）。

> 第一版要求派生规则的最外层是一次分组聚合（每个分组在派生表里恰好对应一行），或者不分组的整体聚合（整张派生表只有一行），这样每个派生行都有确定的身份。重算范围的分析只识别按字段分组和按业务时间分桶；规则的内层有窗口函数或关联了其他表时，每次基础改动重算这条规则的全部分组。
>
> 读状态类表"当前值"的规则、依赖"今天"的规则，结果会随时间推移而变，第一版一律读的时候现算，不缓存（第 7 章）。这类派生值没有存下来的版本，所以读结果里不带 `ver`，带一个"读时计算"的标记。

**派生行的身份是不透明的。** "2026-11"这个分组键是从用户数据算出来的，按类别分组时类别名就是用户写的文字。所以 saveslot 给每个分组分配一个不透明的 ID，事件头和读取记录里只用它；分组键值本身是一个数据块，分组因删除变空时一起清掉。分组变空之后（行全被撤销、改到了别的分组，或被删除），同一个分组键又有了行，沿用原来那个 ID，读过这个分组的读取记录照样接得上。

### 没有记录的时间段，和只记了一部分的时间段

分组聚合对没有输入的分组不产生行。所以 `monthly_total` 里没有 10 月那一行，意思是 10 月一条支出记录都没有，不是 10 月的合计是 0。

更难分的是只记了一部分的情形："11 月花了 89 元"，可能是记全了一个月，也可能只记了三天。saveslot 不替你判断，"哪些天应该有记录"是领域知识。办法是在规则里带上**覆盖列**，把事实摆出来：有记录的天数（`count(DISTINCT date)`）、最早和最晚一条的日期（`min`、`max`）。读的一方按字段说明判断：天数等于这个月应有的天数，是完整的；少了，首末日期说明缺在头、尾还是中间；当前这个月还没过完时，`last_date` 离今天多远说明是"还没到"还是"没记"。覆盖列的规则里不引用"今天"，否则这张表就变成读时现算、不能缓存了。

随命令行工具打包的模板里，按时间分桶的派生表都带这三列（第 1 节的例子就是）。

### 写入准入与大写入作业

同事务刷新有个代价：一次写入影响的范围太大，刷新会很久，挡住这个租户的其他写入。

所以写入执行之前，saveslot 先估算会影响多少行。超过阈值就拒绝，并告诉调用方"影响约多少行，请拆成每批不超过多少行"。

有些写入拆不开，比如一次导入一年的数据。完整设计里它转成**大写入作业**：接受请求、返回作业 ID、后台处理、完成后一次性生效。作业期间，受影响的派生值保持旧值，并带一个"待刷新"的标记，随读取带出。

这是对"派生值永不落后"的一处放宽，范围很窄：只在作业期间，只对受影响的派生值，而且一定被标出来。作业的接受、完成、失败都是日志事件。

> 第一版不做大写入作业。超过阈值一律拒绝，由调用方分批。也就是说第一版里派生值不允许落后，比完整设计更严。

### 派生值是怎么来的

saveslot 记着每次派生刷新读了哪些基础表、刷新的是哪个分组。这足够支持两件事：

- **删除级联。** 基础数据被删，受影响的分组重算。只来自被删数据的派生值自然消失，还有其他来源的自然不再依赖它。
- **纠错影响。** 从一个被纠正的基础版本，找到用过它的派生值。

更细的"这个月合计由哪几笔支出构成"不预先存，需要时按当时的日志位置重跑规则得出。预先存到行一级，会让写入慢好几倍。

## 8. 官方 schema 与自己的 schema

用户想用官方的记账 schema，又想加自己的字段，有两种办法：

- **扩展。** 在官方 schema 上加字段，放在自己的命名空间里。
- **映射。** 完全按自己的结构建表，再写一条派生规则，把自己的数据投影成官方 schema 的形状。为官方 schema 写的工具读这张派生表就行。

第二种没有引入任何新机制："兼容官方"就是一张派生表，只读、可重算、来源完整。

两种办法都要先有一份可识别的官方定义，还要能声明"这个 slot 符合它"。模板做不到这一点：它只是一次性的拷贝，建完就没有联系了。

> 官方 schema 的结构（扩展用的 `extends`、兼容性声明 `compatibility`）**在 P4 之前定**，它是 P4 开工的前提之一；第一版实现到哪一步，届时一起定。在那之前，草稿里出现这两个键整份报 `not_in_this_version`，模板照旧是普通 schema，健康、营养这类新模板在结构定下之后再写。将来要往编译后的定义里加的东西，按事件格式允许的方式加（给已有的块加可选的键），不改动已有的事件。要回答的问题列在规格 [`../spec/08-open-questions.md`](../spec/08-open-questions.md)「官方 schema 的结构」。

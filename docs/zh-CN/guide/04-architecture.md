# 04 · 架构

前三章讲的是 saveslot 里的数据：日志、表、来源、事项。这一章讲装着这些数据的程序长什么样：它分几层、每层负责什么、一次调用怎么从 Agent 走到日志、一条事件在存储里是什么结构、进程怎么跑。

例子沿用第 2 章那本账。

## 1. 四个部分

saveslot 由四个部分组成，从里到外：

```
外化面     HTTP · MCP · 命令行（CLI）           将来：App、开发者 SDK
           ────────────── 操作契约 ──────────────
服务层     身份 · 权限 · 幂等等待 · 句柄 · 限流 · 控制面存储
           ────────────── 内核操作层 ops ─────────
内核       写入 · 读取 · schema 与迁移 · 删除 · 待处理事项         将来：作业
           判定 judge · 派生生成 derive · 落账 apply
           规则引擎 · 时间
           日志 · 读取审计 · 数据标记
           租户存储 · 登记存储（两个接口）
后端       PGlite（本机模式）        PostgreSQL（服务器模式）
```

图里的词（幂等等待、句柄、控制面存储、`ops`、数据标记等）在本章第 4、5、8 节逐个解释，这里先看四个部分怎么叠。最下面两个接口在规格的图里叫"存储抽象"与"锚点存储"，本书叫租户存储与登记存储（第 8 节）。

| 部分 | 是什么 | 例子里对应什么 |
|---|---|---|
| **内核** | 守住数据规则的那部分代码。日志、`apply`、冲突判断、删除结果的计算都在这里 | 把"午饭 45"变成 #21–#24 四条事件并落到表里 |
| **服务层** | 回答"谁在调用、他能做什么、能看到哪些 slot"，以及调用体验上的事 | 认出这次调用来自连接实例 A，A 有写权限，能看到 `ledger` |
| **操作契约** | 一份与传输方式无关的定义：有哪些操作，各收什么参数、回什么结果、报什么错 | `write` 这个操作的参数和回执的形状 |
| **外化面** | 把契约搬到某种具体的接入方式上 | Agent 经 MCP 调 `saveslot_write`；人在终端敲 `saveslot query` |

**核心是前三样：内核 + 服务层 + 操作契约。** 外化面是可以增减的：HTTP、MCP、CLI 都由同一份契约生成，地位相同，将来加 App 或开发者 SDK 也只是多一个外化面。saveslot 的正确性不依赖任何一个外化面存在，所有检查都在内核和服务层里。

## 2. 内核和服务层的界线怎么划

一样东西该放进内核还是服务层，判据只有一条：

> **把它关掉，saveslot 的数据还算不算"可回溯、可解释、可重算"？saveslot 对外宣称的问责保证（谁做的、谁读过、确认的是什么）会不会失效？**

- 会失效的，放进内核，任何用法下都关不掉。
- 只关系到"谁能做、怎么交互、调用体验"的，是服务层的**策略**，可以替换。

两个例子：

- "每次写入都要留下源数据"关掉以后，值就说不清凭什么了。它在内核。
- "怎么验证调用方的身份"换一种方式（本地令牌换成 OAuth），数据的可回溯性不受影响。它在服务层。内核只要求"每个事件都有一个登记过的主体"，至于这个主体是怎么认证出来的，内核不管。

这条界线是为将来的开发者 SDK 划的。SDK 嵌进别人的 Agent 时，身份、权限、确认的交互方式都由宿主应用自己决定，服务层那一套可以整个换掉；但内核的规则一条都不能少，否则它就不是 saveslot 了。

服务层的策略有：身份认证、权限（第一版按 scope 与 slot 范围）、确认的交互方式、幂等窗口的长度、句柄签名、限流与配额、各种阈值的数值、结果怎么渲染成文本。完整的表见 [`../spec/02-architecture.md`](../spec/02-architecture.md) §3「服务层策略」。

## 3. 内核不变量 K1–K14

内核守住的规则叫**内核不变量**，共 14 条，规格里编号 K1–K14。这里按主题归拢，每条只说它保证什么；其中一半前三章已经讲过，另一半涉及的概念在后面的章节展开，括号里注明了是哪一章，初读先知道有这 14 条即可。每一条都是一句可以写成测试的断言，完整的表见 [`../spec/02-architecture.md`](../spec/02-architecture.md) §3。

**日志与重放**

| # | 保证什么 |
|---|---|
| K1 | 日志只追加。每个事件分事件头和内容；事件头串成链、永不删改，里面不放任何由用户内容算出的值；内容分块存放，只有删除才能把一块整块清空 |
| K3 | 表只能由 `apply` 改，每次改动都对应一条日志事件，并在同一个事务里提交。每个租户的写入是串行的 |
| K12 | 日志是唯一事实来源。存储里的每样东西都归入三类之一（事实、物化状态、本地运行状态）；从空库重放日志，得到的表和线上逐行一致（第 3 章） |
| K13 | 写入恰好一次。同一个请求重发（比如网络断了客户端重试），只落一次，重发时返回原来的结果（第 5 章） |

**谁做的，凭什么**

| # | 保证什么 |
|---|---|
| K2 | 每个事件都有 actor：一个在本租户登记过的主体。内核自己产生的事件记在保留主体 `system` 名下，并注明是哪个后台任务触发的 |
| K4 | 每次写基础表都有源数据。来源记到字段，分值来源和操作来源 |
| K10 | 读取留痕。契约里的每次读取操作都记下读到了哪些版本，只记版本号，不记值，也不记由值算出的哈希（第 6 章） |

**数据的形状与时间**

| # | 保证什么 |
|---|---|
| K5 | 派生表只由规则生成，和基础表的写入在同一个事务里刷新，Agent 写不进去；一次写入会牵动多少派生数据、放不放得进同一个事务，也由内核估算并在放不进时拒绝（第 9 章） |
| K6 | schema 版本一旦生效就不可变，字段有稳定的 ID。改表结构只能走一套固定的迁移流程；新旧版本的切换是原子的，切换期间读不中断（第 9 章） |
| K7 | 两条时间线。记录时间由日志序号给出；业务时间按表的时间类型处理。内核自己不读时钟："当前时刻"由服务层在入口处取一次，经调用上下文（第 5 节）交给内核并记进事件，重放时只用事件里记下的时刻（第 7 章） |
| K9 | Agent 可以用只读的 SQL 查数据，但只接受白名单内的语法（把语句解析成语法树后逐节点检查），内部的物理表名不外泄（第 6 章） |

**并发、删除与确认**

| # | 保证什么 |
|---|---|
| K8 | 版本对不上时不覆盖。按**冲突单元**（一个字段，或 schema 声明要一起判的一组字段）判断，状态类表上还要看两次写入管的业务时间区间是否相交（第 7 章第 13 节）：没有交集的合并，有交集的记为候选并生成冲突事项。判定结果与两次写入谁先到无关；冲突期间的生效值由确定的规则给出（第 5 章） |
| K11 | 隐私删除的结果按一句定义算：假如被删的源数据从未存在过，重放日志得到的状态；有两处有意的偏离（人的决定照记录、已经生效的写入保持生效）。凡由源数据得出的内容都在删除范围内；墓碑永不过期（删过的东西不会因为时间久了而复活）；恢复任何备份后，先把备份之后做过的删除再做一遍，再对外服务（第 8 章） |
| K14 | 确认绑定内容。需要确认的事项只有被显式解决才执行；解决时要带回所确认内容的版本，对不上就拒绝；每次解决记下是谁、经哪个凭证（第 3 章） |

几点说明：

- **判定规则带版本。** 内核那些机械的判断（算不算冲突、是不是高影响、一行存不存在……）整体有一个**规则版本**。每个 slot 的策略（第 3 章：一份设置，写明哪些 schema 改动自动生效、冲突期间哪个值算数；建 slot 时写下默认的，第一版不能改）有一个**策略版本**。两个号记进每次操作的头事件。以后隐私删除要重算一次旧写入的判断时，按那次写入自己记下的版本算。这样内核升级之后，一次不相干的删除不会把旧的判断结果改掉。第一版只有一个规则版本，但号现在就记，事后补不回来。
- **第一版没有放松任何一条。** 有几条因为功能没开，适用面变小了：K5（第一版不做大写入的后台作业，所以派生值永远不会落后，比完整设计更严）、K8（第一版不做"来源级别高的候选自动生效"，冲突时一律保持当前值）、K10（纠错影响查询第一版不覆盖对派生值的读取）、K11（第一版不做"删除证据"和按行删除，与它们有关的规则暂不触发）、K12（"从空库重放日志、和线上的表逐行比对"这项检查叫**对拍**；第一版没有后台的定期抽查，要用户手动运行）。
- 每条不变量都有对应的测试，见第 12 章。

## 4. 内核里的模块

内核内部分成若干模块，按层排列。越往下越基础。

| 层 | 模块 | 做什么 |
|---|---|---|
| L0 | `store` 存储抽象 | 打开某个租户的存储、开事务、保证同一时间只有一个进程在写 |
| L1 | `log` 日志 | 追加事件、分配序号、把事件头串成链、存放内容块并算校验和、按删除要求清空内容块、校验整条日志 |
| L1 | `audit` 读取审计 | 读取记录的缓冲、落盘和查询；"每个连接实例最近读到的版本"（`ver` 没带时兜底用） |
| L1 | `flags` 数据标记 | 存取数据上的标记，如"有争议""有待确认的改动""已标记" |
| L2 | `rules` 规则引擎 | 解析只读 SQL 并按白名单检查、把表名字段名换成内部的物理名、计算派生表该怎么刷新、估算一次写入的代价 |
| L2 | `time` 时间 | 表的时间类型、区间的基本运算、按业务时间查询 |
| L3 | `judge` 判定 | **只算不存。** 给它一行（或一个实体）的状态和写入，它算出判断结果：值变没变、冲不冲突、默认终点落在哪、是不是高影响、这一行存不存在。它不读数据库，也不产生事件。两种用法见下面"判定为什么单独成一个模块" |
| L3 | `derive` 派生生成 | 给定一批基础数据的改动，算出哪些派生行受影响，生成派生写入事件 |
| L3 | `apply` 落账 | 把事件落到表里的唯一实现。只照事件里记下的结果做，不重新判断 |
| L4 | `schema` | schema 文档的解析与编译、变更分类与影响预览、迁移流程、数据目录 |
| L4 | `pending` 待处理事项 | 事项的生成、合并、刷新、取代；解决时核对绑定的内容 |
| L5 | `write` 写入管线 | 校验与单位换算、把证据存为源数据、检查 `ver` 和 `sv`、查重、按来源键找到目标行（第 5 章第 3 节）、校验写入声明的前提、取出目标行的现状连同这一次写入交给 `judge`、生成写入事件；这次写入让别的行的前提变了时，生成前提变化事件 |
| L5 | `read` 读取 | 简单查询、只读 SQL、历史与按时刻读、源数据的列出与搜索、读时算出"前提已变"等标记、把读取记进 `audit` |
| L5 | `delete` 删除 | 找出一次删除影响了哪些行、取出这些行的全部写入交给 `judge` 重放、生成删除事件（删除让前提变了时，也生成前提变化事件） |
| L6 | `maintenance` 维护计划 | **只算不做。** 给它"现在"，它回答有哪些后台任务到期了。不开事务、不读时钟、不执行 |
| L7 | `ops` 内核操作层 | 契约里每个操作在内核里的唯一入口，以及后台任务的入口：打开事务、组合上面的模块、组装回执 |

另有 `jobs`（后台作业）和 `sync`（多节点同步）两个模块只留了位置，第一版不实现。

### 判定为什么单独成一个模块

"这次写入冲不冲突""这一行存不存在"这类判断，有两个地方要用，用法不同：

| 谁调 | 交给 `judge` 什么 | `judge` 算什么 | 本书的例子 |
|---|---|---|---|
| 写入时（`write`） | 目标行**现在的状态**，加上**刚到的这一次写入** | 只判这一次：哪些字段没变、哪些冲突、是不是高影响 | 写入 #37：A 带着旧版本改打车的金额，判出"`amount` 冲突，成为候选" |
| 隐私删除时（`delete`） | 受影响那一行的**全部写入**，并标出哪些贡献已经不在了 | 从头把这些写入按顺序重新判一遍，得出删除后的状态 | 第 8 章第 5 节（那一节换了一个前提：假设打车的冲突还没有人处理）：删掉 `s_4` 之后重放打车那一行，判出"冲突不存在了，32 生效"。主线里这个冲突已在 #41 由人解决，候选不会因删除而生效 |

写入时不重放历史：这一行已有的状态是之前每次写入判完的结果，直接拿来用。删除时才需要从头重放，因为被删的那句话可能改变了之前每一步的判断。

两种用法背后必须是**同一份规则**：逐次判下来的结果，要和把全部写入从头重放一遍的结果完全相同。如果写入和删除各写一份，规则迟早会走样，删除后的状态就会和"假如那句话从没说过"对不上。所以判断只有一份实现，放在 `judge` 里，写入、删除、表结构迁移都调它。同一份代码同时支持"判一次"和"重放一整行"，是实现上最需要先验证的一点（第 12 章的实现步骤里有一个专门的小原型）。

把它做成"只算不存"的纯计算还有两个好处：它不碰数据库，最容易做大量的随机测试；规则版本也就有了一个明确的归属。

### 依赖规则

1. **只能依赖更低层，同层之间不互相依赖。** 这让依赖关系没有环，改一个模块时能看清会波及谁。
2. **生成事件的模块不直接改表，只把事件交给 `apply`。** `write`、`schema`、`pending`、`delete`、`derive` 负责"判断并写出事件"，`apply` 负责"照事件改表"。第 3 章讲过为什么：判断只做一次，结果记进事件，重放才能得出同样的表。
3. **判定只有一份实现**：都调 `judge`，不各自实现。
4. **事务由 `ops` 打开。** 下层模块只接收一个已经打开的事务，自己不开。
5. **服务层只调 `ops`，外化面只调服务层。** 没有人能绕过 `ops` 直接碰下面的模块。

这些规则由工具在每次提交代码时自动检查（CI），违反了合不进去。

### 为什么事务由 `ops` 打开

一次操作经常要跨好几个模块，而且这些改动必须要么全成、要么全不成。

看第 2 章第三步里 A 那次带着旧 `ver` 的写入（写入号 37）：`write` 记下写入头（#37）、把证据存为源数据（#38）、记下候选写入（#39）；`pending` 生成冲突事项（#40）；`apply` 把它们落到表里，给那一行打上"有争议"标记；`audit` 还要先把缓冲里的读取记录落盘。如果每个模块各开各的事务，中途崩溃就可能留下"有候选、没事项"这样的半截状态。由 `ops` 开一个事务包住全部，这种状态就不可能出现。

它还解决了模块之间的"环"。写入会产生事项，而解决事项又要执行写入：`pending` 和 `write` 互相需要。依赖只能朝一个方向：`write` 在上层，可以调 `pending`（上面那次写入里生成冲突事项就是这样）；反过来不行。所以解决事项要执行写入时，由 `ops` 来编排：先调 `pending` 核对并记下解决，再调 `write` 执行。`pending` 不知道 `write` 的存在。

### 后台任务怎么进来

有些事不是谁调用的，而是到点要做的：把读取记录落盘、到期的物理删除、表结构迁移的后台构建。它们遇到两条规则：事务只能由 `ops` 开；内核不读时钟。

所以后台任务被拆成三部分：

| 部分 | 在哪 | 做什么 |
|---|---|---|
| 计划 | 内核的 `maintenance` | 给定"现在"，算出哪些任务到期 |
| 任务体 | `ops` 里的**内部操作** | 和普通操作一样的入口：接收调用上下文、开事务、组合下层模块。只是 actor 是 `system`，并带一个 `trigger` 说明是哪个后台任务 |
| 调度器 | **内核之外**（saveslot 服务里它在启动程序里） | 拿着定时器、读时钟，到点调用内部操作 |

读时钟的那一小段代码因此在内核之外，重放和测试时就能完全控制时间。

规格：[`../spec/02-architecture.md`](../spec/02-architecture.md) §4。

## 5. 一次调用怎么走

以第 2 章第二步的纠错为例，A 经 MCP 发出 `saveslot_write`。

```
A（Claude Code）
  │  MCP 工具调用 saveslot_write，带着连接实例令牌
  ▼
外化面 · MCP 适配器      把工具调用转成契约里的 write 操作
  ▼
服务层
  ① 身份：令牌 → 在控制面查出（租户，主体 = 连接实例 A）
  ② 权限：A 的 scope 里有没有写权限；A 的凭证限定到了哪些 slot
  ③ 幂等：按"连接实例 + 任务 + 请求内容"算出请求键；同一个请求正在处理中就让后到的等着
  ④ 打开这个租户的存储，构造调用上下文（可见范围按 A 的 slot 范围给）
  ▼
内核 · ops.write
  打开事务
  → audit：把缓冲里的读取记录先落盘（这样 ver 的兜底一定看得到刚才的读取）
  → write：校验、查重、存源数据、取出午饭那一行的现状
  → judge：算出这次写入的判断结果（金额与读到的版本不同 → 是改动；ver 是当前的 → 没有冲突；不是高影响）
  → write：按结果生成写入头与基础写入事件
  → derive：算出月合计受影响，生成派生写入事件
  → apply：照事件改表
  → read：查这次纠错影响了哪些读取
  提交事务，组装回执
  ▼
服务层 → MCP 适配器      把结构化的回执渲染成文本（标记、单位、版本一项不少）
  ▼
A 收到回执
```

读取走的是同一条路，只是内核里做的事不同。以 A 调 `saveslot_query` 查 11-10 的支出为例，只写内核里的部分：

```
内核 · ops.query
  打开只读事务
  → rules：把表名 expenses、字段名 date 换成当前版本的物理表名和列名；可见范围也在这一步生效
  → read：执行查询，取出行和各自的 ver
  → flags：取出这些行上的标记（有争议、有待确认的改动、已标记……）
  → audit：把"谁、什么时候、读到了哪些行的哪个版本、查询条件的形状"放进读取记录的缓冲
  组装结果
  ▼
服务层 → MCP 适配器      渲染成文本：每个值带单位，标记写在行尾，文本字段包进不可信边界
```

读取不产生日志事件。读取记录先放在内存缓冲里，稍后落盘（第 7 节）。

### 控制面

第 ① 步里的"控制面"是一小份与租户数据分开的存储。要先由凭证查出是哪个租户，才能去打开那个租户的存储，所以这类"跨租户"的信息不能放在租户自己的库里。控制面里有：

- 凭证（只存令牌的哈希）；
- 租户目录：哪个用户对应哪个租户；
- 登记存储的内容（见第 8 节）：删除登记、最高序号、恢复次数、"恢复进行中"与"导入进行中"标记；
- 句柄的签名密钥。

本机模式下它是 saveslot 配置目录里的几个文件；服务器模式下是一个独立的 PostgreSQL 库。控制面不进租户的日志，也不随租户导出。

### 调用上下文：内核与外界的真正边界

服务层调 `ops` 时，除了操作本身的参数，还交给内核一份**调用上下文**。内核对"外面的世界"的全部了解都在这里面：

| 字段 | 含义 |
|---|---|
| `tenant` | 操作的是哪个租户 |
| `actor` | 已经认证过的主体；后台任务是 `system` |
| `trigger` | 后台任务才有：是哪个任务 |
| `task` | Agent 自报的任务标识，可以没有 |
| `visibility` | 这次调用能看到哪些数据："全部"，或一个 slot 列表。用户本人和没有限定范围的连接实例是"全部"；凭证限定到某几个 slot 时就是那几个，范围外的 slot 对它和不存在一样。接口的形状留到了表和字段，第一版只用到 slot 一级 |
| `request_key` | 这次操作的请求键，用于"恰好一次" |
| `idempotency_window` | 多久以内的重复请求算同一个 |
| `now` | 当前时刻。由服务层在入口处取一次，内核自己不读时钟 |
| `confirmation` | 解决事项时的确认记录 |

这份上下文是只读的，并且可以整个序列化成一段数据。这样设计有两个用意：内核不依赖任何"环境"，同样的事件加同样的上下文一定得出同样的结果；将来别的语言写的宿主要用 saveslot 时，可以把上下文原样跨进程传给内核。

规格：[`../spec/02-architecture.md`](../spec/02-architecture.md) §4「`ops` 的调用上下文」、§5。

## 6. 一条事件长什么样

第 2 章里日志是用一句话描述的。这里把**写入 #25（午饭的纠错）** 的事件按真实的形状展开。字段级的完整定义在事件格式规格 [`../spec/09-event-format.md`](../spec/09-event-format.md) 里，那份规格在第一次对外发布之前冻结，此后只增不改；下面是其中的一个实例。

> 跳读提示：这一节的前半（事件头、内容块的基本形状、`apply` 落到哪里）只需要前三章的知识。讲到状态类表上的 `span` 块、块依赖索引，以及最后"内容被删除以后"一小节时，用到的是第 7、8 章才展开的概念；初读可以在这些地方先跳过，直接看第 7 节，读完第 8 章再回来。

回忆一下，这次写入追加了四条事件：

| 序号 | 类型 | 是什么 |
|---|---|---|
| #25 | `write.head` | 逻辑写入头，这次操作的头事件 |
| #26 | `source.recorded` | 源数据 `s_2` |
| #27 | `write.base` | 基础写入：午饭那一行的金额 |
| #28 | `write.derived` | 派生写入：月合计 |

别的操作有别的事件类型，形状都在事件格式规格里。其中两种本书后面还会提到：一次操作让某些行的**前提**变了时（第 5 章第 6 节），这次操作里多一条前提变化事件 `premise.changed`，记下哪些声明转为"已变"、哪些转回"没变"；把一份导出装进一个空租户时，导出里的事件原样追加之后，再追加一条导入事件 `tenant.imported`（第 8 节）。

### 事件头

每条事件的事件头只有几个通用字段。#27 的事件头：

```json
{"actor":"ci_01A…","at":"2026-11-10T04:41:07.123Z","op":25,"prev_hash":"9f2c…e1","seq":27,"slot":"sl_4KTZ…","type":"write.base","v":1}
```

| 字段 | 含义 |
|---|---|
| `seq` | 这条事件在日志里的位置 |
| `v` | 这种事件的格式版本 |
| `type` | 事件类型 |
| `actor` | 谁做的：连接实例 A 的内部 ID |
| `at` | 记录时刻，统一用 UTC |
| `op` | 属于哪次操作：25。头事件 #25 自己没有这个字段，"没有 `op`"就表示它是头事件 |
| `slot` | 属于哪个 slot（内部 ID） |
| `prev_hash` | 上一条事件（#26）的事件头的哈希 |

注意里面**没有**什么：没有金额，没有"午饭"两个字，没有表和行，没有意图，也没有任何由内容算出来的哈希。事件头只说"A 在这个时刻、在这个 slot 里追加了一条基础写入，属于操作 25"。

事件头按一种确定性的 JSON 写法（RFC 8785，简称 JCS）编码成字节：同一个对象每次编码出的字节完全一样，哈希才稳定。哈希算法是 SHA-256。

### 内容块

内容是一组块。每块有一个地址：所在事件的序号加一段**路径**，比如"事件 #27 的 `fields/f3/0`"。路径里只有固定的词、内部 ID 和下标，不含任何用户内容，所以地址本身可以安全地写进别的事件里（删除事件就是靠列出这些地址来说明要清空哪些块）。

块分两种，下面表里的"种类"一栏标了：

| | 里面是什么 | 删除时 |
|---|---|---|
| **数据块**（数） | 用户内容，或由它算出来的东西：原话、字段的值、字段的来源、请求键 | 记着自己出自哪些源数据；那些源数据被隐私删除时，它被整块清空 |
| **元数据块**（元） | 只有内部 ID、固定的枚举、序号 | 第一版不删 |

删除的最小单位是一块，没有"删掉块里的一部分"。需要分开删的内容，一开始就切成了不同的块。

**#25 逻辑写入头**的内容块：

| 路径 | 种类 | 内容 |
|---|---|---|
| `ctx` | 元 | 判定时用的时刻与版本：`{"now": "2026-11-10T04:41:07.123Z", "today": "2026-11-10", "ruleset_version": 1, "policy_version": 1, "literal_checker": "literal@1"}` |
| `request` | 元 | `{"sv": 1, "sv_basis": "explicit", "op_count": 1}`：请求带的 schema 版本，它是 Agent 带来的还是内核按读取记录兜底取的，以及请求里一共有几个 op。按来源键同步时，什么都没变的 op 不进事件、在 `ops/<i>` 里留空号，所以总数要单独记 |
| `ops/0/target` | 元 | `{"table": "t1", "row": "r_01JC…", "intent": "correct", "ver": {"op": 21, "restore_count": 0, "basis": "explicit"}}` |
| `ops/0/set/f3` | 数 | A 原样交来的值：`{"value": "54", "unit": "CNY"}` |
| `request_key` | 数 | 由"连接实例 + 任务 + 请求内容"算出的请求键 |

**#26 源数据**的内容块：

| 路径 | 种类 | 内容 |
|---|---|---|
| `target` | 元 | 这条源数据的内部 ID（对外写作 `s_2`）、种类是用户原话 |
| `text` | 数 | 原文："不对，午饭是 54 元" |

**#27 基础写入**的内容块：

| 路径 | 种类 | 内容 |
|---|---|---|
| `target` | 元 | `{"op_index": 0, "table": "t1", "row": "r_01JC…", "intent": "correct", "cause": "request", "sv": 1}` |
| `fields/f3/0` | 数 | 这次写入对金额的贡献：`{"status": "applied", "value": {"value": "54", "unit": "CNY"}}` |
| `sources/f3/0` | 数 | 金额的值来源：`[{"kind": "value", "source": 26}]`，指向 #26 那条源数据 |
| `literal/f3/0` | 数 | 字面命中的记录：`{"segments": [{"source": 26, "result": "hit"}]}` |

几点说明：

- **`t1`、`f3` 是内部 ID。** `t1` 是 `expenses` 这张表，`f3` 是 `amount` 这个字段。事件里不出现名字，所以改名不影响旧事件，删除后也看不出字段叫什么。
- **原样交来的值和落账的值各记一份，分在两条事件里。** 写入头记的是 Agent 的原话（原始的数和单位），基础写入记的是内核换算、舍入之后落账的值。这个例子里两者一样；假如 Agent 交来的是别的同类单位，两者就不同。字面命中比的是原始值，因为证据里写的是原始的写法。
- **字段的贡献按段记，路径末尾的 `0` 是段的下标。** 在 `expenses` 这种表上一个字段只有一段，下标总是 0。状态类表上（第 7 章），一个字段在一次写入里可以按时间段得到不同的结果：前一段只是佐证、后一段成了候选；撤回一次写入时，还可能要把一个字段恢复成好几段不同的旧值。每一段各有自己的状态、值和生效区间，这样它们可以分开删除。状态类表上，一段的生效区间另放在一块 `span/<字段>/<下标>` 里：区间的端点常常不是这次请求自己说的，而是内核按别的写入算出来的（比如"到下一次变化为止"停在了另一次写入的起点上）。这一块记下它用到了哪些别的写入；那些写入被隐私删除时，这一块跟着清除，否则被删的日期会留在别人的事件里（第 8 章）。
- **`status` 是这一段的生效状态。** 共四种：`applied`（已生效）、`candidate`（冲突候选）、`awaiting`（高影响，等待确认）、`corroborated`（值没变，只追加了来源）。第 2 章 A 那次成为候选的写入，#39 里就是 `"status": "candidate"`。
- **无操作的字段在基础写入里没有块。** 值没变、也没指证据的字段不算这次写入的改动（第 5 章）：它只在写入头的 `ops/0/noop` 里留下字段 ID，日志里任何地方都不留它的值。原因在第 8 章：这个值是 Agent 从 saveslot 读回来原样带上的，留一份就等于给被删的内容留了副本。
- **不记"改之前是多少"，也不记改完的整行。** 第 2 章讲过原因。
- **请求键是数据块，不在事件头里。** 它由请求内容算出，算作内容（第 3 章第 4 节）。
- **前提也记在写入头里。** 这次写入没有声明前提；声明了的话，每条声明在写入头里多一块 `ops/<i>/premises/<j>`，里面只有目标行的内部 ID、字段 ID 和所见版本，是元数据块，不记前提的值。
- **判定用的版本号、时刻都记下了。** `ruleset_version`、`policy_version` 是第 3 节说的规则版本和策略版本；`now`、`today` 是入口取的时刻和它在 slot 时区下的日期。重放时用这些记下的值，不读时钟。

### `apply` 把它落到哪里

`apply` 拿到 #27，看到 `fields/f3/0` 的状态是 `applied`，照着改这些内部表（都是第 3 章说的 (b) 类物化状态，丢了可以从日志重建）：

| 改哪里 | 改成什么 |
|---|---|
| `expenses` 的物理表 | 午饭那一行 amount 改为 54 |
| 版本表 | 版本表按单元格记：给这一行的 amount 这一格加一个新版本，从操作 25 起生效；这一格上一个版本的有效期到操作 25 为止。没改的字段不动。按时刻读靠它 |
| 来源表 | 记下"写入 #25 的 amount 字段第 0 段，值来源是 #26，状态是已生效" |
| 块依赖索引 | 记下哪个块是由哪些别的写入求得的。这次写入没有这样的块；状态类表上的 `span` 块、事项的条目、删除事件记下的结果会登记在这里，隐私删除靠它找出要一并清除的块 |

处理 #25 时，`apply` 把请求键写进请求键索引（指向操作 25），重发时据此返回原结果。紧接着的 #28 让 `apply` 更新 `monthly_total` 里 2026-11 那一行。四条事件和这些表的改动在同一个事务里提交。这一行的 `ver` 变成 `v25.0`。

假如这一段的状态是 `candidate` 或 `awaiting`，`apply` 不改业务表和版本表，这条事件只留在日志里，供查历史、处理事项和删除重放时使用。

两个名字的对应：业务表的物理表名带着 schema 版本号（形如 `t_<表ID>_v<版本>`），所以改表结构时可以在旁边建一张新版本的表，建好后原子切换。这些物理名只在内核里出现，Agent 和 SQL 里用的永远是 `expenses` 这样的名字。

### 内容被删除以后

假如后来对 `s_2` 做了隐私删除并且到期（第 2 章情况一），这次写入的四条事件变成：

- **事件头**：四条都原样还在，链不断。
- **被清空的数据块**：#26 的 `text`；#27 的 `fields/f3/0`、`sources/f3/0`、`literal/f3/0`；#25 的 `ops/0/set/f3` 和 `request_key`；#28 的 `checksum`。每块原位置留下"已由 #44 移除"的标记，#44 是那条墓碑事件。
- **#28 为什么也在内**：派生写入里存着一个校验值，是由它读到的基础数据算出来的，其中有那个 54。算它用到的值被删了，这个校验值也要清掉，否则可以拿猜测的金额去比对。同理，之后重算过 11 月合计、读到过 54 的两次派生写入（#32、#36）的校验值也一并清除。#28 的另一块 `key`（分组键"2026-11"）留着：月份出自 `s_1` 的日期，`s_1` 没有被删。这就是"派生数据的校验信息随输入删除"。
- **留下的元数据块**：#25 的 `ctx`、`request`、`ops/0/target`，#26 的 `target`，#27 的 `target`，#28 的 `target`。

以后重放到 #27，`apply` 看到 `fields/f3/0` 已被移除，就当这一块不存在。

删除后这一行该是什么样，不靠重放时现算：确认删除的那条事件（#42）里已经写好了结果（金额回到 45，来源指向 #23 的那次贡献），`apply` 照着落账。别的写入如果因为这次删除而结果变了（比如原本的候选生效了、某次写入"到下一次变化为止"的终点变了），#42 里也逐项写下它们的新结果，此后以最近一次写下的为准（第 8 章）。事件里记的结果是哪些块、各是什么形状，见 [`../spec/09-event-format.md`](../spec/09-event-format.md) 第 5.9 节。

规格：[`../spec/09-event-format.md`](../spec/09-event-format.md)（第 2 节事件头、第 3 节内容块、第 4 节一次操作的事件构成、第 5.7 节写入类事件）；租户存储里有哪些表见 [`../spec/02-architecture.md`](../spec/02-architecture.md) §8「存储格式 v1」。

## 7. 进程是怎么跑的

### 一个服务进程

saveslot 服务是**一个进程**，HTTP、MCP 和后台任务的调度器都在里面。

内核用 TypeScript 写。TypeScript 是带类型检查的 JavaScript；跑它需要一个 JavaScript 运行时，saveslot 用的是 Node（也可以是 Bun，两者是同一类东西，相当于 Java 程序需要的 JVM）。

为什么选这个技术栈：本机模式用的数据库 PGlite 只能运行在 JavaScript 运行时里（见下）。这是 saveslot 内部的实现选择，对 Agent 没有影响，Agent 只是经 MCP 或 HTTP 连这个进程。

### 单写者

**一个租户的存储，同一时间只能有一个进程在写。** 两个进程同时写同一份数据会把它写坏。saveslot 用两道保险：

- **锁。** 打开租户的存储时拿一把锁，别的进程拿不到就打不开。
- **所有权编号。** 每次打开时把一个编号加 1 并记进存储；之后每个写事务都先核对这个编号。如果对不上，说明别的进程已经接手了这个租户，本进程立刻放弃它。这防的是锁没防住的情形，比如进程卡住很久以后恢复过来、不知道自己已经被替换了。

这也是本机模式下所有 Agent 必须经同一个 saveslot 服务进程访问数据的原因：命令行工具、MCP 的转发程序都不直接打开数据目录，一律连那个进程。

锁在本机上具体怎么加，要靠一项实验确认（第 12 章的实验 8）。

### 每个租户的写入是串行的

同一个租户的写入排成一队，一个做完再做下一个。事件序号 `seq` 在事务里分配，所以序号的顺序就是提交的顺序。

串行听起来慢，但对 saveslot 是合适的：一个租户就是一个人的数据，写入频率是"人说话的速度"；而串行换来的是冲突判断、派生刷新、`ver` 检查都不需要处理并发，规则简单且结果确定。不同租户之间互不影响。

后台任务要写数据时，和前台的写入走同一条队。

### 记录时刻不会倒退

每条事件的事件头里有一个记录时刻。它取"服务层在入口处取的当前时刻"和"上一条事件的记录时刻"里较晚的那个。所以即使电脑的时钟被往回调了，新事件的时刻也不会早于旧事件；事件的先后始终以序号为准。时钟比日志末端明显偏早时，saveslot 会给出警告，但不拒绝写入，因为它无从知道哪个时钟是对的。

### PGlite 住在专用的 worker 里

**PGlite** 是把 PostgreSQL 编译成可以嵌进 JavaScript 程序里的形式：它不是一个单独的数据库服务，而是 saveslot 进程里的一个库，数据存在本机的一个目录里。本机模式用它，用户因此不需要自己安装数据库。

PGlite 有一个特点：同一时间只有一条连接，一次只能做一件事。所以 saveslot 把它整个放在一个专用的 **worker** 里（worker 是进程内的一条独立线程，有自己的内存，和主线程靠消息通信），所有读和写都经它排队。

由此有一个要知道的代价：**一条很慢的查询会挡住这个租户的写入**，最长到查询超时为止。而超时只能靠终止整个 worker 来实现，等于让数据库崩溃重启一次。所以 saveslot 的主要防线放在事前：写入前先估算代价，太大的直接拒绝；派生规则和只读 SQL 在编译时就拒绝代价高的写法。超时终止只是最后手段，是否启用要看实验结果。

服务器模式用原生 PostgreSQL，没有这个限制，但第一版同样让只读 SQL 和写入共用一条连接、串行执行。

### 读取记录什么时候落盘

读取很频繁，每读一次就写一次盘太贵。所以读取记录先放在内存里，在这几个时刻落盘：

- **任何写事务开始时**，和这次写入在同一个事务里。这保证 `ver` 的兜底一定看得到刚才的读取。
- **关闭租户之前。**
- **其余时候每隔几秒**（初值 5 秒）。

所以只有进程真的崩溃时才会丢，而且只丢最近几秒里、之后又没有任何写入的那些读取记录。

### 不依赖进程一直在跑

有些事是到点要做的，最典型的是删除确认 24 小时后的物理删除。saveslot 不假设进程一直开着：**每次打开存储时，先补做已经到期的任务**，再对外服务。

- 服务器模式：调度器按删除登记里的到期时刻主动打开租户执行，不等用户下次来访问。
- 本机模式：服务在跑就按时执行；没在跑，下次启动时先执行。删除的回执里会如实写明这一点。

到期的物理删除万一失败（磁盘满了之类），saveslot 照常对外服务并不断重试：这些内容在确认删除时就已经读不到了，推迟的只是从磁盘上抹掉这一步。只有一种情况下它会拒绝对外服务：恢复了旧备份、该补的删除还没补完。那时被删的内容是读得到的。

### 已确认的写入不能丢

回执说"已保存"的写入，在进程崩溃、断电之后必须还在。PGlite 默认为了速度不强制把数据刷到磁盘；"把那个开关打开就行"目前只是假设，能否真的达标要靠实验确认。这是排在开发最前面的一项实验，如果不达标，本机模式的后端会换成随 saveslot 一起打包的原生 PostgreSQL（见第 12 章）。

规格：[`../spec/02-architecture.md`](../spec/02-architecture.md) §7。

## 8. 两个接口：租户存储与登记存储

内核对外面的存储只依赖两个接口。它的全部保证（K1–K14）只建立在这两个接口上，不依赖服务层里的任何东西。

### 租户存储

第一个要求是：**"给我打开某个租户的存储。"** 内核不关心下面是什么数据库。

打开之后得到的东西只有几个动作：

| 动作 | 含义 |
|---|---|
| 写事务 | 串行执行；开头先核对所有权编号 |
| 读事务 | 只读 |
| 清理残留 | 物理删除之后，把数据库内部可能留着明文的地方清掉 |
| 格式版本 | saveslot 自己那些内部表的版本号 |
| 关闭 | 先把读取记录落盘 |

满足这个要求的后端有两个：

| 后端 | 用在哪 | 一个租户对应 |
|---|---|---|
| PGlite | 本机模式 | 一个数据目录 |
| PostgreSQL | 服务器模式（我们的云服务、用户自部署） | 一个独立的 database |

两个后端都是 PostgreSQL，这是有意的：内核里的 SQL 只写一份。但"同一份日志在两个后端重放出完全相同的表"仍然不是白来的，需要固定时区和排序规则、数值用精确的十进制类型、规则里只允许结果确定的函数，并且由测试持续检验（第 12 章的"重放对拍"）。

租户存储里有哪些表、各自属于 (a)(b)(c) 哪一类、由哪种事件维护，规格里有一张唯一的清单（[`../spec/02-architecture.md`](../spec/02-architecture.md) §8「存储格式 v1」）。

### 登记存储

第二个接口保存的是**租户存储被整体换掉之后仍然必须记得的事**。规格里叫"锚点存储"（`AnchorStore`）。

为什么需要它：假设用户删了一句话，之后数据库坏了，从更早的备份恢复。那份备份里既有那句话，也没有"删过它"这件事的任何记录。如果"删过什么"只记在租户存储里，它就跟着一起被拨回去了。所以这类信息必须放在租户存储之外：

- **删除登记**：哪些删除已确认、何时到期、被删内容的地址。只记地址，不存内容。
- **最高序号**：这个租户的日志已经编到第几号。
- **恢复次数**：这个租户从备份恢复过几次。
- **"恢复进行中"与"导入进行中"标记。**

这个接口由外面实现：saveslot 服务用控制面来实现它（本机是配置目录里的一个文件，服务器模式是控制面库里的表）；内核自己的测试用一个文件实现。它必须和租户存储分开存放、分开备份。两者如果被一起恢复，登记也回到了过去，内核补不了也发现不了，这是写明的边界。

怎么用它保证"删掉的东西不回来"，见第 8 章。

### 导出与格式版本

**导出不依赖存储格式。** 导出的是日志事件本身，不是数据库文件。拿到导出文件，在任何一个后端上重放，得到同样的状态。这也是"数据能带走"的技术含义。

**导入只能装进空租户。** 把一份导出装回去，第一版只支持装进一个还没有数据的租户，比如从本机模式搬到服务器模式：先按校验日志的同一套检查核对文件，再把导出里的事件逐条原样追加、交给 `apply`，最后追加一条导入事件。不逐条重新执行当初的写入：那样会重新判定、重新分配序号和 ID，得到的就不是同一条日志。导入之前登记过的连接实例一律停用，凭证要在新的地方重新签发；读取记录、凭证这些本来就不在导出里的东西带不过来。导入也让恢复次数加 1，所以导入之前拿到的事项版本和删除句柄都对不上了，要重新查看事项、重新预览删除。合并进一个已经有数据的租户是后续的事。怎么操作见第 11 章。

**格式版本。** 打开存储时，如果它的格式版本比当前程序认识的高（比如用新版写过、又换回旧版程序），拒绝打开并提示升级，而不是冒险去写。

规格：[`../spec/02-architecture.md`](../spec/02-architecture.md) §8。

## 小结

- saveslot 的核心是内核、服务层、操作契约；外化面由契约生成，可以增减。
- 放进内核还是服务层，看的是"关掉它，数据还算不算可回溯、可解释、可重算"。
- 内核不变量 K1–K14 是任何用法下都关不掉的规则；判定规则带版本，记进事件。
- 内核模块按层排列，只依赖更低层；生成事件的模块不改表；判定只有一份实现；事务由 `ops` 打开；外面只能经 `ops` 进来，后台任务也一样。
- 一条事件 = 事件头（几个通用字段，进链，不含用户内容）+ 内容块（按地址存放，数据块可以整块清空）；`apply` 照着它改版本表、来源表、业务表等物化状态。
- 一个服务进程；一个租户同一时间只有一个写者，写入串行；到期任务在打开存储时补做。
- 内核只依赖两个接口：租户存储（PGlite 和 PostgreSQL 是它的两个实现）与登记存储。

代码怎么分包、怎么测试，见第 12 章。

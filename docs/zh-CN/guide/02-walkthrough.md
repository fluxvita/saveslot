# 02 · 一个例子走到底

这一章用一本账走完 saveslot 的主要机制：记一笔支出、纠错、两个 Agent 同时改、删除一句话。

每一步看三样东西：

- **调用**：Agent 向 saveslot 发了什么。
- **日志**：saveslot 追加了哪些事件。
- **表**：查询时看到的数据变成什么样。

先记住一件事，后面每一步都在印证它：**日志是事实，表是从日志算出来的。** 每追加一条事件，saveslot 内部一个叫 `apply` 的函数把它落到表里，事件和表的改动在同一个事务里提交。

> 读法说明
>
> - 调用里的操作名和参数名以操作契约为准（规则在 [`../spec/04-contract.md`](../spec/04-contract.md)，类型定义在 [`../spec/04-contract-types.md`](../spec/04-contract-types.md)）。经 MCP 接入时，工具名是操作名加 `saveslot_` 前缀（`write` → `saveslot_write`）。
> - 事件的序号与构成按事件格式规格（[`../spec/09-event-format.md`](../spec/09-event-format.md)）写。为了看清主线，表里只写每条事件"记了什么"，不写字段级的形状；第 4 章会把其中一条事件完整展开。
> - **序号的写法。** `#27` 或"事件 #27"指日志里的第 27 条事件。"写入 #25"指写入号为 25 的那次写入，它在日志里是连续的几条事件（#25–#28）。写入号是什么，第一步就会讲到。全书都按这个写法。
> - **标识的写法。** 行、事项这类标识是 saveslot 分配的一长串字符，例子里只写开头几位加省略号（`r_01JC…`、`pi_7C…`）。两条源数据为了好认，简写成 `s_1`、`s_2`；真实的源数据标识也是一长串。
> - 本章讲的是完整设计。其中第一版不做的地方会当场标出，完整清单见 [`../spec/07-scope-v1.md`](../spec/07-scope-v1.md)。

## 准备：一本账

用户有一个叫 `ledger` 的 **slot**（一组相关的表）。它的 schema 里有两张表：

| 表 | 种类 | 字段 |
|---|---|---|
| `expenses` | 基础表，Agent 可以写 | `date`（日期，必填）、`category`（类别，必填）、`amount`（金额，单位 CNY，必填）、`note`（备注，可选） |
| `monthly_total` | 派生表，只读 | 按月汇总 `expenses.amount`。汇总规则写在 schema 里，由 saveslot 执行 |

用户在同一台电脑上用两个 Agent，各有一个 saveslot 签发的凭证，saveslot 里叫**连接实例**：

- A：`MacBook · Claude Code`
- B：`MacBook · Codex`

Agent 第一次接触这个 slot 时，先调 `catalog` 看有哪些表、字段和单位。结果里带着这个 slot 当前的 schema 版本 `sv: 1`，之后写入时要带回。

这本账的日志此时已经有 20 条事件，所以下面的序号从 #21 开始。前 20 条是 10 月留下的：#1 是建立这个用户的数据（"创世"事件）；#2–#6 是建 `ledger` slot（提交 schema、编译、生效、写下 slot 的默认设置、切换到第 1 版）；#7、#8 是给 A、B 签发凭证时各登记的一条；#9–#20 是 A 在 10 月记过的三笔支出，每笔 4 条事件。10 月的支出算在 10 月的合计里，不影响下面 11 月的数字。这些事件是什么，第 3、9、11 章会讲到，这里不需要知道。全部序号的一览表在本章末尾。

## 第一步：记一笔

用户对 A 说："今天午饭花了 45 元。"

**调用。** A 理解这句话，按 schema 填好值，调 `write`：

```json
{
  "sv": 1,
  "evidence": [
    { "kind": "user_message", "text": "今天午饭花了 45 元" }
  ],
  "ops": [
    {
      "intent": "insert",
      "table": "expenses",
      "set": {
        "date": "2026-11-10",
        "category": "餐饮",
        "amount": { "value": "45", "unit": "CNY" }
      }
    }
  ]
}
```

除了带回的 `sv`，A 只填了四样东西：意图（`insert`，新增）、表、值、证据。证据是它从对话里截取的那句原话。其余的由 saveslot 补全：是谁写的（从凭证得出）、属于哪个 slot（从表推出）、行 ID、记录时间。

**日志。** saveslot 校验类型、单位、范围都没问题，追加四条事件：

| 序号 | 事件 | 记了什么 |
|---|---|---|
| #21 | 逻辑写入头 | 这次请求本身：A 原样交来的参数、用来防重复提交的请求键、判定时用的时刻 |
| #22 | 源数据 `s_1` | 原话"今天午饭花了 45 元"，种类是用户原话 |
| #23 | 基础写入 | 在 `expenses` 新增一行：这次请求涉及的三个字段各自的值，以及**每个字段的来源**——`date`、`category`、`amount` 都出自 `s_1` |
| #24 | 派生写入 | 按规则重算了 `monthly_total` 里 2026-11 这一行 |

四点值得注意：

- **一次写入有一条"头"，它的序号代表这次写入。** #21 是这次写入的第一条事件，叫**逻辑写入头**，每次请求一条。它的序号 21 叫这次写入的**写入号**（更一般的叫法是**操作号**）。saveslot 对外说"第几次写入"时，一律用这个号：回执里的序号、版本标记、历史里的编号都是它。#22–#24 各自的序号只在日志内部用。
- **原话本身也是一条事件。** saveslot 把写入随附的证据存为**源数据**。如果 Agent 没带证据，saveslot 会把这次请求本身存为源数据。所以日志里的每次写入都能追到一条源数据，没有例外。
- **来源记到字段。** 不是"这一行出自这句话"，而是"这一行的日期、类别、金额各自出自这句话"。后面删除时会看到为什么要这么细。
- **派生表不是 Agent 写的。** A 只写了 `expenses`，月合计是 saveslot 按 schema 里的规则算的，和这次写入在同一个事务里完成。

写入时 saveslot 还顺手记下一项机械检查的结果，叫**字面命中**：写入的值在证据原文里有没有字面出现过（"45 元"出现了，"今天"不等于 11-10）。第一版只记不用，第 5 章讲。

**表。**

`expenses`：

| 行 | date | category | amount | 版本 |
|---|---|---|---|---|
| 午饭 | 2026-11-10 | 餐饮 | 45 CNY | `v21.0` |

`monthly_total`：

| 月 | 合计 |
|---|---|
| 2026-11 | 45 CNY |

**回执。** `write` 返回 `status: "saved"`、这次写入的写入号 `seq: 21`、这一行的 ID 和版本标记 `ver: "v21.0"`，还有受影响的派生值（月合计变成 45）。

A 是经 MCP 接入的（MCP 是 Agent 调用外部工具的通用协议，第 1 章提过），它实际收到的是一段文本：

```
已保存 · ledger schema v1 · #21
expenses r_01JC… 新增：date 2026-11-10 | category 餐饮 | amount 45 CNY（ver=v21.0）
派生：monthly_total 2026-11 total — → 45 CNY
```

第一行是状态、slot 与 schema 版本、写入号；之后是每个操作的目标、意图、各字段的结果和新的 `ver`；最后是受影响的派生值。`…` 只是为了排版，真实的文本里 ID 和版本标记都是完整的，因为 Agent 之后要原样带回它们。逐字的措辞以实现里的样例为准，这些要素是固定的。

**`ver` 是什么，为什么要有它。** 它解决的问题是：两个 Agent 都读了同一行，各自基于读到的内容去改，后改的不能悄悄盖掉先改的。做法分三步：

1. **读的时候拿到。** 每一行有一个 `ver`，读取结果和写入回执里都带着。`v21.0` 里的 21 是最近一次改动这一行的那次操作的操作号；小数点后的数平时总是 0；第 3 章说它是什么，第 11 章说为什么需要它。
2. **改的时候原样带回。** 意思是"我是看着写入 #21 之后的样子做的这次修改"。
3. **saveslot 比对。** 带回的就是当前版本，直接生效。不是当前版本，说明中间有人改过，这时 saveslot 不直接拒绝，而是按字段看：你要改的字段中间没人动过，就合并生效；被人改过，才算冲突。第三步会演示。

这是数据库里常见的"乐观并发控制"：不加锁，写的时候再检查。saveslot 的不同之处是对不上时按字段判断，真冲突了也不丢掉后来的值。

Agent 忘了带 `ver` 时，saveslot 用这个连接实例最近一次读到这一行的版本代替，并在回执里说明；它从没读过这一行，就拒绝并提示先读。

## 第二步：纠错

过了一会儿，用户对 A 说："不对，午饭是 54 元。"

**调用。** A 先找到要改的那一行，调 `query` 查 11-10 的支出，拿到行 ID 和 `ver: "v21.0"`。然后调 `write`：

```json
{
  "sv": 1,
  "evidence": [
    { "kind": "user_message", "text": "不对，午饭是 54 元" }
  ],
  "ops": [
    {
      "intent": "correct",
      "table": "expenses",
      "row": "r_01JC…",
      "ver": "v21.0",
      "set": { "amount": { "value": "54", "unit": "CNY" } }
    }
  ]
}
```

和第一步相比有三处不同：

- **意图是 `correct`（纠错）。** 意思是"原来的值本来就是错的"，区别于 `update`（情况有了变化或补充）。对表来说两者一样，都是把一个值改成另一个值；区别在于**旧值当时对不对**，这决定了之前读过旧值的任务受不受影响：
  - 变更：用户把一笔支出的类别从"餐饮"改归"招待"。调整之前某个 Agent 按"餐饮"做了分类统计，那份统计在当时没错。
  - 纠错：午饭其实是 54，不是 45。纠正之前某个 Agent 读到 45 并算了报销金额，这个结果是错的，需要有人知道。

  所以纠错（以及后面会讲的撤销）会让 saveslot 去查"谁读过那个错的值"并提示他们（见下面的回执），变更不会。不区分的话，要么每次改值都提示，多到没人看；要么都不提示，错的结果流出去没人知道。"是记错了还是情况变了"只有 Agent 从对话里判断得出来，saveslot 看不出，所以必须由 Agent 显式标明。
- **带了行 ID 和 `ver`。** 行 ID 说明改哪一行；`ver` 说明"我是基于这个版本做的修改"。
- **只给了 `amount`。** 这次纠错只涉及金额，日期和类别没有出现在请求里。

**日志。**

| 序号 | 事件 | 记了什么 |
|---|---|---|
| #25 | 逻辑写入头 | 这次请求：意图是纠错，目标是午饭那一行，带回的版本是 `v21.0` |
| #26 | 源数据 `s_2` | 原话"不对，午饭是 54 元" |
| #27 | 基础写入 | 字段 `amount`：值 54，已生效，来源是 `s_2` |
| #28 | 派生写入 | 重算 2026-11 的月合计 |

#21–#24 原封不动。纠错不改历史，而是追加新的事件。

注意 #27 只记了这次请求涉及的那个字段。它不记"改之前是多少"，也不记改完以后的整行：改之前的值在更早的事件里已经有了，每多存一份副本，将来要彻底删除时就多一处要清。"改完以后这一行是什么样"由之前的状态加上这次生效的字段得出。

另外，A 刚才那次 `query` 也被记下了：哪个连接实例、什么时候、读到了这一行的哪个版本。这份**读取记录**不进日志，单独存放，只记版本号，不记读到的值。

**表。**

`expenses`：

| 行 | date | category | amount | 版本 |
|---|---|---|---|---|
| 午饭 | 2026-11-10 | 餐饮 | 54 CNY | `v25.0` |

`monthly_total`：2026-11 = 54 CNY。

现在这一行每个字段的来源是：

| 字段 | 当前值 | 来源 |
|---|---|---|
| `date` | 2026-11-10 | `s_1`（写入 #21） |
| `category` | 餐饮 | `s_1`（写入 #21） |
| `amount` | 54 CNY | `s_2`（写入 #25）；它之前的 45 出自 `s_1`（写入 #21） |

**回执。** `status: "saved"`；写入号 25；金额 45 → 54；月合计 45 → 54；新的 `ver: "v25.0"`。因为意图是纠错，saveslot 还会去读取记录里查：纠正之前，有没有别的任务读到过 45？有的话在回执里给出受影响的读取次数，那些连接实例下次读到相关数据时也会收到提示。A 自己为了纠错而做的那次读取不算在内。

**到这里可以回答三个问题了**（调 `history` 可以看到）：现在是 54；它原来是 45，在写入 #25 被 A 纠正；45 出自"今天午饭花了 45 元"，54 出自"不对，午饭是 54 元"。

## 第三步：两个 Agent 同时改

为了不把午饭那一行的历史弄复杂，这一步换一行。

用户对 B 说："打车花了 30 元。"B 照第一步的方式写入：

| 序号 | 事件 |
|---|---|
| #29 | 逻辑写入头（写入号 29） |
| #30 | 源数据 `s_3`："打车花了 30 元" |
| #31 | 基础写入：新增打车那一行，金额 30 |
| #32 | 派生写入：月合计 84 |

之后 A 和 B 都读过这一行，手里的 `ver` 都是 `v29.0`。

**B 先改。** 用户对 B 说："打车其实是 35 元。"B 带着 `ver: "v29.0"` 纠错。版本对得上，直接生效：

| 序号 | 事件 |
|---|---|
| #33 | 逻辑写入头（写入号 33） |
| #34 | 源数据 `s_4`："打车其实是 35 元" |
| #35 | 基础写入：纠错，金额 35，已生效 |
| #36 | 派生写入：月合计 89 |

这一行的版本变成 `v33.0`。

**A 后改，手里还是旧版本。** 用户在另一个窗口对 A 说："打车是 32 元。"A 没有重新读，带着 `ver: "v29.0"` 发出纠错，把金额改成 32。

**saveslot 怎么判断。** A 带的版本不是当前版本，说明在 A 读取之后有人改过这一行。saveslot 不直接拒绝，也不直接覆盖。它把 A 的写入理解成"相对 `v29.0` 那个版本，我要改什么"，然后**按字段**比较：A 这次要改的字段，在 `v29.0` 之后有没有被别人改过？

- `amount` 在写入 #33 被 B 改过。有交集，这是冲突。
- 假如 A 的请求里还顺带改了 `note`，而没人动过 `note`，那个字段会直接生效。一次写入可以一部分字段生效、一部分成为冲突。
- 假如 A 的请求里把 `date` 原样带了回来（值和它读到的 `v29.0` 上一样），那不算 A 的改动，saveslot 当作无操作，不会因此造出一个冲突。

对冲突的字段，saveslot 这样处理：

1. **A 的值记为"候选"，不生效。** 当前值仍然是 B 写的 35。规则是确定的：保持当前值，也就是先提交的那个。
2. **生成一个待处理事项**，类型是冲突，目标是"打车这一行的 `amount` 字段"，记下当前值、候选值、各自是谁写的。冲突事项按字段算：假如 A 在两个字段上都冲突了，就是两个事项，各自处理。
3. **给这一行打上"有争议"的标记**，标记里写明是哪个事项、哪个字段。

> 完整设计里，如果候选的来源级别更高（比如一边是用户亲口说的并且字面命中，另一边只是 Agent 的推断），saveslot 会按规则让级别高的直接生效。第一版不做这一条，一律保持当前值。

**日志。**

| 序号 | 事件 | 记了什么 |
|---|---|---|
| #37 | 逻辑写入头 | 写入号 37；带回的版本是 `v29.0` |
| #38 | 源数据 `s_5` | 原话"打车是 32 元" |
| #39 | 基础写入 | 字段 `amount`：值 32，状态是**候选**，来源是 `s_5` |
| #40 | 待处理事项产生 | 冲突事项 `pi_…`：当前值 35，候选 32 |

没有派生写入，因为生效值没变。这一行的 `ver` 也没变，仍是 `v33.0`。

**表。** 打车那一行金额仍是 35，带"有争议"标记。月合计仍是 89。

**回执。** A 收到的是 `status: "pending"`，不是报错。回执里写明：`amount` 成了候选，当前生效值是 35，对应的事项 ID 和事项版本 `item_ver`。A 收到的文本是：

```
已记下，未生效 · ledger schema v1 · #37
expenses r_01JD… 纠错：amount 未生效
  amount：在你给的版本（#30）上它是 30 CNY；现在是 35 CNY（#33，MacBook · Codex），ver=v33.0。你的值 32 CNY 已记为候选，冲突事项 pi_7C…（版本 iv_2d…）；当前生效值仍是 35 CNY
  处理：saveslot_resolve pi_7C…（keep_effective / take_candidate / take_previous）
```

它把四件事说全了：在 A 给的版本上是什么、当前是什么、是谁在哪次写入里改的、A 的值记在了哪个事项里。（"A 给的版本"就是 A 读到的版本，前提是 A 如实带上了读到的 ver。）A 此刻正在和用户对话，可以马上把情况告诉用户。

**为什么这样设计。** saveslot 不能假设有办法主动通知用户，也不能假设用户会及时回应。所以冲突被做成一种**持久的状态**，而不是一次性的报错：

- 它永远不阻塞。冲突期间读这一行，拿到的是一个确定的值（35）加上"有争议"的标记，读的一方自己决定要不要继续。
- 它不会丢。之后任何一个 Agent 读到这一行，都会看到标记，都可以提醒用户。
- 它不过期。saveslot 没有判断力，不替人裁决；事项会一直在，直到有人处理。一个没看过这个事项的 Agent 即使后来又改了这个字段，事项也只是更新，不会被悄悄关掉（第 5 章讲）。

**解决。** A 把情况告诉用户，用户说："35 是对的。"A 调 `resolve`：

```json
{
  "id": "pi_…",
  "decision": "keep_effective",
  "item_ver": "iv_…"
}
```

`item_ver` 是 A 从回执里拿到的事项版本，意思是"我确认的是我看到的这份内容"。如果事项在这期间变了（比如又多了一个候选），版本对不上，saveslot 会拒绝并返回当前内容，要求重新确认。

| 序号 | 事件 | 记了什么 |
|---|---|---|
| #41 | 待处理事项解决 | 处理方式是保持当前值；确认记录：谁解决的、经哪个凭证 |

"有争议"标记撤掉，金额保持 35。另外两种处理方式：

- 采纳候选（`take_candidate`）：32 生效。事项里有多个候选时，用 `candidate` 指明第几个。
- 回到冲突前（`take_previous`）：回到双方都没改之前的那个版本的值，这里是 30。

**注意：冲突的产生和解决都是日志事件。** 如果它们只记在某张表里，那么把表丢掉、从日志重建时，冲突就消失了。

## 第四步：删除一句话

saveslot 里有三种"删除"，含义不同：

| 请求 | 用户想要什么 | 效果 |
|---|---|---|
| 撤销一行 | 这条记录不该存在（"那笔记重了"） | 一次普通写入（意图 `revoke`）。行标记为已撤销，历史和原话都保留 |
| 删除证据 | 这段原话不要留，但数据可以留 | 只删原文，值留下 |
| 隐私删除 | 彻底忘掉 | 原文和由它得出的值都处理掉 |

> 第一版只做撤销和隐私删除（按源数据删），不做删除证据。

下面讲隐私删除。它有一句定义，所有结果都由这句定义推出：

> **隐私删除后的状态 = 假如被删的那条源数据从来没存在过，把日志从头重放一遍得到的状态。**

（定义还有两处有意的偏离和一个适用范围的限定，第 8 章讲。）

回到午饭那一行。它有两条源数据：`s_1`（原话，写入 #21 给出了日期、类别、金额 45）和 `s_2`（纠错的话，写入 #25 把金额改成 54）。下面三种情况各自独立，都从第三步结束时的状态出发。

这里假设用户给 A 加了删除权限。删除权限默认不给，签发凭证时要显式勾选（第 11 章）。

### 情况一：删掉纠错那句话（`s_2`）

**调用分两步：先预览，再执行。**

为什么要分两步：隐私删除的后果往往不直观（情况二会看到"删掉一句话，整行都没了"），让 Agent 或用户直接执行，很可能删出意料之外的结果。所以先做一次**试算**：告诉你如果删会发生什么，但什么都不删。

**第一步，预览。** A 调 `deletion_preview`（经 MCP 时是 `saveslot_sources` 工具的 `deletion_preview` 模式），参数是：种类为隐私删除，目标是 `s_2`。saveslot 按"假如 `s_2` 从没存在过"算一遍，返回：

- 总量：删除 1 条源数据，影响 1 行，重算 1 个派生值；
- 逐行的结果和理由：午饭那一行**金额回到 45**；
- 原本没生效、因为这次删除会生效的写入（这里没有）；
- 不会被删的东西（例如 saveslot 没有保管的外部文件、删除后仍保留的元数据）；
- 一个确认句柄 `dc_…`。

**第二步，执行。** A 把预览告诉用户，用户同意后，A 调 `delete`，参数只有那个句柄。

句柄的作用是把"看到的"和"执行的"绑在一起。它绑定了那份预览的内容和当时的日志位置；如果预览之后又有写入改到了删除范围，句柄对不上，saveslot 拒绝执行并给出新的预览，要求重新确认。这样不会出现用户同意的是一份结果、实际删的是另一份。句柄 10 分钟内有效，过期了重新预览即可。

**为什么是回到 45。** 假如"不对，午饭是 54 元"从没说过，写入 #25 就没有金额可给，重放下来金额的最后一个来源是写入 #21 的 45。

**日志。**

| 序号 | 事件 | 记了什么 |
|---|---|---|
| #42 | 删除已确认 | 算好的结果：午饭那一行删除后的样子（金额 45，来源 `s_1`）；到期时刻；到期时要物理删除哪些位置的内容 |
| #43 | 派生写入 | 月合计 89 → 80 |

注意"删除后是什么样"是在确认这一刻算好、写进事件的。`apply` 只是照着事件改表，自己不做任何判断。

**表。** 午饭那一行金额变成 45，`ver` 换成 `v42.0`（42 是这次删除确认的操作号）；月合计 80。`s_2` 的原文从这一刻起读不到了。

**24 小时宽限期。** 确认之后的 24 小时内，这次删除可以撤回：调 `resolve`，对这次删除对应的事项选 `cancel`。这个事项不另记一条事件：删除确认（#42）本身就开了它，事项 ID 就是这次删除的 ID，回执里给出。撤回后金额回到 54。宽限期内的删除只是"读不到"，内容还在。

**到期。** 24 小时后（11 月 11 日中午；这期间没有别的操作，所以它是 #44），saveslot 追加一条"到期物理删除"事件（也叫**墓碑**），并真正抹掉内容：

- `s_2` 的原文（#26 里）；
- 写入 #25 给出的金额值和它的来源（#27 里），以及 A 原样交来的那个值（#25 里）；
- 其他由这句话算出来的东西，例如 #25 里的请求键（它由请求内容算出，为什么也算内容见第 3 章第 4 节），以及 #28 里月合计的校验值。

被抹掉的位置留下一个"已由 #n 移除"的标记，里面没有任何内容。

**留下了什么。** #25–#27 这几条事件的**事件头**还在：序号、类型、是谁做的、什么时候、属于哪次操作。另外还留着几样不含内容的记录：这次写入针对的是哪张表的哪一行（都是内部 ID）、意图是纠错。也就是能看出"A 在某个时刻对这一行做过一次纠错，后来被删除了"，但看不出纠错的内容。事件头和内容分开存放正是为了这个：日志是只追加的，链不能断；但内容必须能真的删掉。

### 情况二：删掉原话那句（`s_1`）

预览的结果可能出乎意料：**午饭那一行整行删除。**

逐步看"假如 `s_1` 从没存在过"：

- 写入 #21 给出的日期、类别、金额 45 都没了。
- 写入 #25 还在，但它只给了一个值：金额 54。
- 这一行现在只有金额，没有日期和类别。这两个是必填字段，一行要存在，每个必填字段都得有一个还在的来源。所以这一行不成立。

为什么不能留一行"只有金额"或者把日期、类别留下？

- 日期和类别是从被删的那句话里来的。留下它们，等于没删干净。
- 只有金额、日期和类别为空的一行，违反表的必填约束，也没有意义。

`s_2`（"不对，午饭是 54 元"）本身没有被要求删除，所以原文还在源数据里；只是它对应的那次纠错没有行可以落，不产生任何数据。月合计从 89 变成 35。

**预览会把理由写清楚**：这一行将被整行删除，因为日期和类别只来自 `s_1`；金额另有写入 #25 的来源。看到这个，用户有两条路：

- **确实想彻底忘掉这笔支出**：连 `s_2` 一起删，见情况三。
- **只想删这句话，但保留这笔记录**：先给日期和类别补上别的来源（叫**佐证**），再删。

**佐证是什么。** 让一个值有第二个来源。写入 #25 只给了金额，所以日期和类别只有 `s_1` 一个来源。假如用户纠错时说的是"11 月 10 号那顿餐饮其实是 54 元"，这句话本身就能证明日期和类别；A 在写入时指明"日期、类别也出自这句话"，这两个字段就各多了一个来源 `s_2`，之后删掉 `s_1`，它们还站得住，这一行保留。如果那句话只提到了日期、没提类别，类别仍然只有 `s_1` 一个来源，这一行照样会被整行删除——每个必填字段都得有自己的来源。指明的写法、能走通的完整例子，以及为什么"把值原样带回"不算数、必须显式指明，见第 5 章第 5 节。

### 情况三：彻底忘掉这笔支出

用户的意图是"这一笔从来没有过"。那就要去掉这一行的**全部**来源，包括插入它的 `s_1` 和后来修改它的 `s_2`。

完整设计里，`deletion_preview` 可以直接按行指定（参数 `rows`），saveslot 自己找出这一行的全部来源。

> 第一版不做按行删除。第一版的做法是把 `s_1` 和 `s_2` 都列为删除目标，效果相同。

结果：整行删除，两句原话都删除，月合计 35。

顺带一条性质：先删 `s_1` 再删 `s_2`、先删 `s_2` 再删 `s_1`、一次删两条，结果完全一样。因为结果只由"哪些源数据不存在"决定，和删除的先后无关。

**一句话服务多行时要小心。** 假如用户当初说的是"午饭 45 元，打车 30 元"，Agent 用这一句话作证据写了两行。这句话是切不开的，删掉它，两行都会受影响。预览会把受影响的行逐行列出来。

## 回头看

这个例子里出现的机制，下一章逐个讲清：

| 例子里看到的 | 对应的概念 |
|---|---|
| slot、基础表、派生表 | 租户、slot、表 |
| 原话存成源数据，表里的值由它得出 | 两层数据 |
| 每一步都是追加事件，表由 `apply` 落出来；一次写入有一个写入号；读取记录不进日志、单独存放 | 日志、`apply`、三类状态 |
| 删掉内容后事件头还在 | 事件头与内容分开 |
| 连接实例 A、B；字段的来源 `s_1`、`s_2` | actor 与来源 |
| `ver` 对不上时按字段判断 | 版本标记与冲突 |
| 冲突事项、删除的宽限期、`resolve` | 待处理事项 |

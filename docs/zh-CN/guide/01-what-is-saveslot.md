# 01 · saveslot 是什么

[English](../../guide/01-what-is-saveslot.md) · 简体中文

## 一句话

saveslot 是给 Agent 用的数据底座。它跟踪会随时间变化的事物，并保留每样东西从原始证据到当前状态的完整时间线。数据归用户所有，不绑定任何一家模型或 Agent 产品。

## 它解决什么问题

一个人今天会同时用好几个 Agent：电脑上的编码 Agent、手机上的助手、云端跑的自动化。他跟它们说的很多话，其实是在更新同一批长期存在的东西：这个月花了多少钱、训练计划进行到哪、某个项目现在的状态。

这些东西有三个麻烦：

1. **散在各处。** 每个 Agent 各记各的，换一个 Agent 就要重新交代一遍。
2. **会变，而且会被改错。** 用户会纠正、会补充，两个 Agent 可能同时改同一处。只存"当前值"的话，没人说得清它是怎么变成这样的。
3. **说不清凭什么。** 一个数字摆在那里，是用户亲口说的，还是某个 Agent 推断的，还是从哪个文件里导入的？出了错无从追查，用户想删掉某句话时也不知道它影响了哪些数据。

saveslot 把这批数据放在一个地方，让用户的所有 Agent 共用，并且对每个值都能回答三个问题：**现在是什么、怎么变成这样、每一步凭什么。**

## 什么样的数据适合放进来

同时满足三条，就是 saveslot 的场景：

1. **有稳定的身份。** 它是"某一样东西"：这个项目、我的跑步记录、这本账。不是一句零散的话。
2. **会变化或累积。** 值会改，记录会增加，状态会推进。
3. **后续有人依赖。** 之后的会话或别的 Agent 需要它的当前样子或历史。

例子：每一笔支出和每月预算、每一次跑步和周跑量、一个项目的里程碑和状态、用户的偏好、一个带理由的决定。

反例：一次性的闲聊、临时的草稿、只在当前对话里有用的中间结果。这些不需要 saveslot。

## 和数据库、Memory 的区别

saveslot 不是又一个数据库，也不是又一个 Memory。区别在于**时间是一等公民**。

| | 存的是什么 | 值被改了以后 | 问"凭什么是这个值" |
|---|---|---|---|
| 数据库 | 现在的状态 | 旧值被覆盖，除非应用自己另记历史 | 不知道，除非应用自己另记 |
| Memory | 说过的话 | 新旧说法并存，哪个算数靠检索和模型判断 | 能找到原话，但没有结构化的值 |
| saveslot | 一样东西的时间线 | 新值生效，旧值留在历史里，随时能查 | 每个字段都记着它出自哪段原始证据 |

具体到一笔支出：数据库告诉你"54 元"；Memory 告诉你"用户说过午饭 45 元，后来又说是 54 元"；saveslot 告诉你"现在是 54 元；它先是 45 元（出自这句话），后来被纠正为 54 元（出自那句话）；月合计因此从 45 变成 54；纠正之前有哪些任务读到过 45"。

这也是 saveslot 能做几件别处难做的事的原因：

- **纠错后知道影响了谁。** saveslot 记着谁读过哪个版本，值被纠正后能找出读到过旧值的任务。
- **删一句话，能删干净。** 每个值记着来源，用户要求忘掉某句话时，由它得出的值会一起处理。（这一项 0.2.0 尚未提供，见下面「Agent 理解，saveslot 把关」一节末尾。）
- **数据能整个带走。** 导出的是完整的时间线，换一个后端重放出同样的状态；也可以把它导入另一处还没有数据的 saveslot（第 11 章）。

## Agent 理解，saveslot 把关

saveslot 的核心路径不调用模型。它和 Agent 的分工是：

| 事情 | 谁做 |
|---|---|
| 理解用户说了什么、该不该记 | Agent |
| 找到要改的是哪一行 | Agent（先查再写） |
| 把话变成结构化的值，带上单位 | Agent |
| 判断这是"记错了"还是"情况变了" | Agent |
| 截取作为证据的那段原话 | Agent |
| 检查类型、单位、范围、版本 | saveslot |
| 记下每次写入、每个值的来源 | saveslot |
| 发现并发修改，按确定的规则处理 | saveslot |
| 维护历史，按时刻读，重算派生数据（月合计这类由别的值算出来的数） | saveslot |

这样分的理由：Agent 本来就在跑模型，也最清楚用户此刻的意图，让它来理解最自然；而一套要对数据负责的底座，它的保证不能建立在模型的输出上，所以 saveslot 只做确定性的检查、记录和执行。

由此有一条需要事先知道的边界：**saveslot 不判断写入的内容是不是真的。** Agent 说"用户说午饭 54 元"，saveslot 就照这样记下，并留下这段证据供日后查证。数据是否属实、某次确认是不是真的征得了用户同意，由调用它的 Agent 负责。saveslot 保证的是三件事：每次写入都留痕；凡是需要确认的操作，执行的就是被确认的那份内容；删除在 24 小时内可以撤回。后两件在第 2 章会看到。（其中删除这一件，0.2.0 尚未提供：隐私删除在随后的版本里，见 [`../spec/07-scope-v1.md`](../spec/07-scope-v1.md) 第 7 节。）

## 上层产品与 saveslot 的关系

saveslot 是底座，不是某个产品的后端。面向终端用户的产品建在它上面。

举几个大家熟悉的产品类型：一个记账应用、一个 Strava 这类的运动记录应用、一个 Linear 这类的项目跟踪工具。如果它们做成"由 Agent 来记、来查"的版本，数据层面要解决的问题是一样的：值会被纠正、要知道出处、多个 Agent 会同时写、用户要能删、要能带走。这些通用的部分由 saveslot 提供；产品自己负责领域知识（什么算一笔支出、周跑量怎么算）和用户体验。

领域知识以 **schema** 的形式交给 saveslot：有哪些表、每个字段的类型和单位、派生数据按什么规则算。schema 可以是用户自己的，也可以用官方或社区提供的。一组相关的表连同写进它们的原始证据，叫一个 **slot**（比如记账、跑步各是一个 slot）；授权给哪个 Agent、schema 升到哪一版，都以 slot 为单位（第 3 章）。

### 连接器：把别的系统里的数据搬进来

把别的系统里的数据定时搬进来，也是上层的事。手环 App 里的饮食记录、银行流水这类数据，由一种叫**连接器**的程序定时搬进 saveslot。连接器由官方或开发者按各自的来源系统编写，不是 saveslot 的一部分：saveslot 不调度它、不替它重试，也不保管它登录那个外部系统用的令牌。在 saveslot 看来，它和别的接入方一样，是一个**连接实例**（一个 Agent 或程序在 saveslot 里登记的一次接入，带它自己的凭证），经 HTTP 写入。saveslot 为它提供的只是通用的写入能力：凭证可以限定到某几个 slot（第 11 章）；记录可以按它在来源系统里的标识反复同步，不会重复新增（第 5 章）。手机上的采集程序连不上本机模式的 saveslot（本机模式只供这台电脑访问），只能配合服务器模式。

## 两种产品形态

saveslot 里做检查、记录和执行的那一部分叫**内核**。同一个内核，对外有两种用法。

| | saveslot 服务 | 开发者 SDK |
|---|---|---|
| 给谁 | 用户：一个人的数据底座，他用的所有 Agent 共用 | Agent 开发者：嵌进自己的 Agent，帮它长期维护数据 |
| 怎么接 | HTTP、MCP、命令行 | 进程内的库接口 |
| 什么时候做 | 第一版 | 后续版本 |

表里的 **MCP** 是 Agent 调用外部工具的一种通用协议，Claude Code、Codex 这类 Agent 都支持；接上之后，saveslot 的操作在 Agent 那边就是几个可以调用的工具。后面各章说"Agent 调 `write`"，实际走的就是它。

第一版只做 saveslot 服务。但架构上要求：将来做 SDK 时不用改内核。

## 它跑在哪

第一版有两种运行模式：**本机模式**（saveslot 服务跑在用户自己的电脑上，只供这台机器上的 Agent 使用）和**服务器模式**（跑在一台服务器上，可以是我们运营的云服务，也可以是用户自己部署的同一套代码，任何地方的 Agent 都能远程连它）。

两点容易误解的地方：

- **两种模式都是"单节点"：一个用户的数据只在一个地方。** 这不妨碍多个 Agent 共用：只要连的是同一个服务器模式的 saveslot，本机的编码 Agent 和云端的 Agent 读写的就是同一份数据。第一版不做的是"同一份数据同时放在本机和云端，两边互相同步"，以及由此而来的离线写入。
- **Agent 不需要懂 saveslot 内部用什么技术，用户也不需要自己安装数据库。** saveslot 是一个独立的服务进程，数据库在它里面：本机模式用嵌入式的 PostgreSQL（叫 PGlite，作为一个库嵌在 saveslot 的服务进程里），服务器模式用原生 PostgreSQL。Agent 只是经 MCP 或 HTTP 连这个进程。

怎么安装、Agent 怎么接、凭证怎么管、数据怎么带走，见[第 11 章](11-deployment.md)；自己部署服务器模式见[第 13 章](13-self-hosting.md)；规格见 [`../spec/01-positioning.md`](../spec/01-positioning.md)「部署形态与同步」。

## 为什么不直接用现成的东西

这一节写给熟悉这个领域的读者，第一次读可以跳过。上面这些问题各自都有成熟的方案，为什么要另做一套？下面四类最接近，结论都是"借思路，不当组件"。

**事件溯源的事件库**（EventStoreDB / KurrentDB、Kafka 这一类）。saveslot 的内核本身就是事件溯源的做法：一条只追加的日志，表由日志算出。没有直接用现成的事件库，卡在"彻底删除"上。这类系统的事件是不可变的，删除要么是整条流标记删除、等后台整理时才真正移除（中间有一段"读不到但还在"的时间，而且每个副本要各自整理），要么靠给内容加密再销毁密钥。Kafka 的删除标记还会过期，离线太久的副本回来会把旧数据写回去。saveslot 需要的是按字段、按一句话精确删除，删完日志的链不断，删除标记永不过期，所以自己在 PostgreSQL 上做日志，并把每个事件拆成"永不删的头"和"可以删的内容"（第 3 章）。

**CRDT**（Automerge、cr-sqlite 这一类，用来让多个副本各自修改再自动合并）。它在字段层面自动选出一个赢家，不会停下来等人决定（有的实现里输掉的值事后还读得到，但系统已经替你选完了）。saveslot 关心的冲突恰恰不能无声解决：谁的证据更可靠、这是纠错还是情况变了、要不要用户确认，这些是语义上的问题。saveslot 的做法是把冲突做成一种持久的、读得到的状态，等人决定（第 2 章第三步）。另外 CRDT 要保留完整的修改历史才能合并，和"彻底删除"直接冲突。

**数据库自带的时态表、双时态数据库**（SQL 标准里的时态表、XTDB、Datomic）。它们解决的是"某个时刻的值是什么"，这正是 saveslot 的时间模型借鉴的对象。没有直接用的原因：saveslot 选定的 PostgreSQL 到现在还没有内置的系统版本表，"修改一段时间上的值"的语法也还没有进正式版本，这部分逻辑无论如何得自己写；XTDB 最接近，但它是另一种技术栈上的独立引擎，没有 schema 和约束；Datomic 只有记录时间一条时间线。更重要的是，它们只管时间，不管"每个值出自哪句话"，也就没有按来源级联的删除。

**知识图谱式的 Agent 记忆**（Graphiti 这一类）。它和 saveslot 在理念上最接近：也保留原始片段，事实也带有效期，也区分"发生时间"和"记录时间"。区别在谁来把关：它的摄入、去重、判断两条事实是否矛盾都靠模型；没有汇总这类派生数据，也没有审计和删除的治理。saveslot 把需要理解的事留给 Agent，自己这一侧全部是确定性的规则，同样的输入一定得到同样的结果。

这些比较的调研材料在仓库的 [`../research/`](../research/) 下（时态、同步、日志与删除各一份）。

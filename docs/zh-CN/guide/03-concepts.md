# 03 · 核心概念

上一章的例子里出现了一批概念。这一章逐个讲清：每个概念是什么、为什么要有它、最容易误解的地方在哪。例子沿用那本账。

顺序是从外到内：先是数据怎么组织（租户、slot、表），再是数据怎么存（两层数据、日志、`apply`），然后是三个横切的机制（来源、时间、待处理事项）。

## 1. 租户、slot、表

### 租户

**租户是 saveslot 里"一份独立数据"的单位：一条日志、一套序号、一份独立的存储。** 第一版里，一个租户就是一个用户。

不同用户的数据在存储层面就是分开的：本机模式下是一个数据目录，服务器模式下每个用户一个独立的数据库。内核只认"打开某个租户的存储"，不存在"在一张大表里按用户 ID 过滤"这回事。

之所以用"租户"而不直接说"用户"，是给将来留余地：比如多人共享的账本，会是一个独立的租户加上成员授权。第一版不做。

### slot

**slot 是一个租户内部的划分：一组相关的表，加上这些表的源数据。** 例如"记账""健康""某个项目"。

名字取"存档位"的意思：一个 slot 装着一份完整、可以接着用的状态，像一个存档位，哪个 Agent 来了都能从上次停下的地方接着用。项目名 saveslot 由此而来。

slot 是三件事的单位：

- **schema 版本。** 一个 slot 有一个当前的 schema 版本（`sv`）。改表结构是以 slot 为单位升版本的。时区也是按 slot 设的。
- **一次删除的范围。** 一次隐私删除只涉及一个 slot 里的源数据；一句话说到了两个 slot 的事，存成两条源数据，各删各的（第 8 章）。
- **权限。** 将来按"哪个 Agent 能访问哪些数据"授权时，以 slot 为基本粒度。

导出不以 slot 为单位：第一版导出的是这个租户的整条日志（第 11 章）。只导出某一个 slot 是后续的事。

每个 slot 还带着一份**策略**：一份设置，写明哪些 schema 改动可以不经确认自动生效、冲突期间哪个值算数等。建 slot 时 saveslot 写下一份默认的；第一版没有修改它的操作（第 9 章）。

slot 之间不重叠：

- 每张表只属于一个 slot。
- 每条源数据只属于一个 slot。用户一句话涉及两个 slot 时（"今天跑了 5 公里，买跑鞋花了 600"），由 Agent 拆成两次写入，各带各的证据片段。两次写入互相独立：一次成功、一次失败时，成功的那次不会回滚，Agent 要自己重试失败的那一次。
- 一次写入只涉及一个 slot。
- 第一版不允许跨 slot 的派生规则。需要时由 Agent 分别查两个 slot 再拼。

slot 是逻辑上的划分，不是物理上的：它只是租户那一条日志里的分区标签，不是独立的日志，也不是独立的库。

### 表

表有两种：

- **基础表**：Agent 写的表，如 `expenses`。每一行有一个 saveslot 生成的行 ID。
- **派生表**：完全由规则生成的表，如 `monthly_total`。规则是 schema 的一部分，由 saveslot 执行，Agent 只能读。基础表一变，受影响的派生行在同一个事务里重算。

派生表只由规则生成，这是一条硬约束。它保证派生数据永远能从基础数据重算出来，因此派生数据从不妨碍删除，也不需要单独记历史。

规格：[`../spec/03-data-model/01-objects.md`](../spec/03-data-model/01-objects.md)「slot 与事物的时间线」「标识与对象」。

## 2. 两层数据：源数据与表数据

saveslot 里的数据分两层。

```
表数据   ← 按 schema 组织的结构化数据，Agent 和上层产品查的就是它
源数据   ← 原始依据：用户原话、工具结果、文件引用……只追加，不修改
```

- **源数据**是原始依据。例子里的 `s_1`"今天午饭花了 45 元"就是一条源数据。它不是整段对话，只是 Agent 截取的、与这次写入有关的那一段。
- **表数据**（规格里叫"有模型的数据"）是按 schema 从源数据得出的结构化结果：`expenses` 里那一行。

两层之间有三条关系，后面的机制都建立在上面：

1. **表数据里的每个值都能追到源数据。** 这就是"凭什么"的答案。
2. **每次写入都有源数据。** 带了证据，证据存为源数据；没带（比如脚本直接调接口），saveslot 把请求本身存为源数据。没有"无依据的写入"。
3. **纠错是一条新的源数据，不是去改旧的。** 用户说"不对，是 54 元"，这句话本身被记下来，再由它产生一次纠错写入。原来那句话和原来的值都还在历史里。

一条源数据有种类：用户原话、Agent 的转述或推断、工具结果、外部文件的引用。种类决定了它默认的**来源级别**：用户原话是"用户明确"，其余是"Agent 推断"。来源级别用在冲突裁决上。

规格：[`../spec/03-data-model/01-objects.md`](../spec/03-data-model/01-objects.md)「数据分层」「一条源数据是什么」；[`../spec/03-data-model/04-write-and-read.md`](../spec/03-data-model/04-write-and-read.md)「不变量：每次写入都有源数据」。

## 3. 日志、`apply`、三类状态

这是整个设计的地基。

### 日志是唯一事实来源

**一个租户的存储里，只有一条只追加的事件日志算"事实"。平时查的所有表，都是从日志算出来的，丢了可以重算。**

日志里的每一条是一个**事件**，按顺序编号，编号叫 `seq`（例子里的 #21、#22）。源数据、每一次写入、派生表的每次刷新、待处理事项的产生与解决、删除的确认与撤回、schema 的每次变更，都是这条日志里的事件。日志的第一条事件是"租户创世"，登记这个租户和它的用户；之后建 slot、签发凭证也各自留下事件。上一章的账从 #21 开始，前 20 条就是这些，加上 10 月记的三笔支出（一览表在第 2 章末尾）。

**一次操作，一个操作号。** 调用方的一次请求（一次写入、一次解决事项、一次删除确认）在日志里会追加好几条连续的事件。其中第一条叫**头事件**，它的 `seq` 就是这次操作的**操作号**；写入的头事件是逻辑写入头，所以写入的操作号也叫**写入号**。上一章第一步的四条事件 #21–#24 属于同一次操作，操作号是 21。

saveslot 对外提到"第几次操作"的地方，一律用操作号：回执里的序号、版本标记 `ver`、历史里的编号。本书里"写入 #25"说的是写入号为 25 的那次写入，单写 `#27` 或"事件 #27"说的是日志里的第 27 条事件。

用操作号而不用单条事件的序号，是为了让一次操作在记录时间上是同一刻。假如按单条事件的序号去读"当时的状态"，就可能读到一次写入做了一半的样子，而那个样子从来没有真正存在过。

操作号同时就是"记录时间"：saveslot 是在第几步知道这件事的。

### `apply`：从事件到表

**`apply` 是把一条事件落到表里的函数，也是唯一能改表的地方。** 每追加一条事件，`apply` 照着它改表，事件和表的改动在同一个事务里提交。

`apply` 有一个关键性质：**它只执行，不做判断。**

"这次写入和别人冲突吗""这个值管到哪一天为止""删除之后这一行该是什么样"，这些判断都由负责写入或删除的模块在当时做完，**结果写进事件**。`apply` 只是照事件里写好的结果改表，不重新判断，也不读当前时间。它自己做的只有不含判断的计算，比如"把这个已生效的字段值落到这一行上"。

原因是日志必须能**重放**：拿同一份日志，换一个数据库后端、过一年、内核升了版本，从头交给 `apply`，都要得出同样的表。如果 `apply` 在重放时重新做判断，结果就可能和当时不一样。

### 三类状态

规格要求，租户存储里的每一样东西都必须归入三类之一：

| 类 | 是什么 | 丢了怎么办 | 例子 |
|---|---|---|---|
| (a) 事实 | 日志事件本身 | 不能丢。导出的就是它 | 源数据、写入、事项的产生与解决、删除的确认与撤回 |
| (b) 物化状态 | 由日志经 `apply` 算出来的表 | 从 (a) 重建 | 业务表、每一行的历史版本、来源表、待处理事项的当前状态、数据上的标记、各种索引 |
| (c) 本地运行状态 | 不是从日志算出来的，也不导出 | 每一项都必须写明"丢了会怎样" | 读取记录、后台任务的进度 |

**这条规则防的是"第四类"：很重要、却只存在某张表里的状态。** 这种状态在导出时带不走，重建时也回不来。两个例子：

- 如果"这个字段有冲突"只记在一张表里，把表丢掉、从日志重建一次，冲突就消失了。
- 如果"这条已删除"只记在一张表里，导出日志再重放，被删的数据就复活了。

所以冲突的产生与解决、删除的确认与撤回，全都是日志事件。上一章的 #40、#41、#42 就是。

读取记录归在 (c)：它量大、有自己的保留期限、到期清理，不适合进一条永久的日志。代价写明了：导出后读取历史不随数据走。

### 这样设计换来什么

- **数据能带走。** 导出就是日志。在本机的嵌入式数据库和服务器上的 PostgreSQL 重放，得出同样的状态。
- **能自查。** 从空库把日志重放一遍，和线上的表逐行比对。能发现内核自己的缺陷，也能发现有人绕过 saveslot 直接改了库。
- **历史和溯源是自带的。** "某个时刻它是什么""这个值凭什么"不需要另外的机制。
- **改表结构是同一个动作。** 新版本的表，是把日志重放进新结构建出来的。

规格：[`../spec/02-architecture.md`](../spec/02-architecture.md) §3「日志是唯一事实来源」；每一类有哪些表见同一文件 §8「存储格式 v1」；每种事件的字段见 [`../spec/09-event-format.md`](../spec/09-event-format.md)，初读不必通读。

## 4. 事件头与内容分开

"日志只追加"和"用户有权要求彻底删除"是冲突的。saveslot 的解法是把每个事件拆成两部分：

| | 里面有什么 | 能删吗 | 进链吗 |
|---|---|---|---|
| **事件头** | 序号、事件类型、是谁做的、记录时刻、属于哪次操作、属于哪个 slot、上一条事件头的哈希 | 永不删改 | 是 |
| **内容块** | 其余的一切，分成若干块，各带一个校验和 | 可以整块清空 | 否 |

**事件头故意留得很少。** 它只有上面这几个通用字段。连"这次写入针对哪张表、哪一行、意图是什么"都不在事件头里，而是放在内容块里。原因是事件头一旦进了链就永远改不了；留在里面的东西越少，将来在"删除后还能保留什么"这件事上的余地越大。

事件头一条接一条串成链：每条事件头里带着上一条事件头的哈希（算法是 SHA-256）。这条链能发现事件缺失、顺序被打乱、事件头被意外改动。

**内容分成块，按块删除。** 一个事件的内容不是一整坨，而是一组**内容块**：原话是一块，每个字段的值各是一块，字段的来源又各是一块。含用户内容（或由它算出来的东西）的块记着自己出自哪些源数据；那些源数据被隐私删除时，这些块被整块清空，原位置留一个"已被某条删除事件移除"的标记，里面没有任何内容。只含内部 ID 和固定枚举的块（比如"这次写入针对哪张表、哪一行、意图是什么"）第一版不删。块怎么编址、一条真实的事件有哪些块，第 4 章第 6 节展开。

两条细节决定了"删得干净"：

- **事件头里不放任何由用户内容算出的值。** 哪怕是内容的哈希也不放。否则内容删掉以后，别人还可以拿一句猜测的话算一遍哈希来比对，验证"用户是不是说过这句话"。每块的校验和与内容放在一起，随内容一起清空。**请求键**是这条规则最常被问到的例子：它是 saveslot 为了识别"同一次请求被重发"而由请求内容算出的一个值（第 5 章第 7 节），请求里含着用户的原话，所以它也算内容，放在可以删的块里，随这次请求的证据一起删。后面各章提到"请求键也在清除范围内"，理由都是这一条。
- **事件头和不删的那些块里只用内部 ID。** 表名、字段名这些可读的名字都放在可以删的块里。

删除后留下的是两层东西：

- 事件头：看得出某个时刻有过一条什么类型的事件、是谁做的、属于哪次操作。
- 不含内容的那些块：看得出是哪张表的哪一行（内部 ID）、意图是什么、引用了哪几条事件。

看不出写的是什么值、原话是什么、表和字段叫什么名字。逐项的清单在事件格式规格的第 9 节，那也是交给法务审阅的材料；如果将来要求连这些也不留，可以把它们一并清空，不用动事件头。

需要知道的边界：**这套完整性机制的目标是"能溯源、防误操作"，不是防篡改。** 一个能直接写存储的人（包括运营方），改了内容并重算校验和，检查照样通过。saveslot 不对此提供证明。

规格：[`../spec/03-data-model/02-integrity-and-records.md`](../spec/03-data-model/02-integrity-and-records.md)「完整性与溯源」；[`../spec/09-event-format.md`](../spec/09-event-format.md) 第 1–3 节、第 9 节。

## 5. 谁做的，凭什么：actor 与来源

这两个概念容易混，因为听起来都像在回答"这次改动是哪来的"。它们回答的是不同的问题。

| | 回答什么 | 是什么 | 记在哪 |
|---|---|---|---|
| **actor** | 谁做的 | 一个经过认证的主体 | 每个事件的事件头 |
| **来源** | 凭什么 | 一条或几条源数据 | 每次写入的内容里，记到字段 |

### actor

actor 是调用 saveslot 的那个主体。常见的有三种：

- **连接实例**：一个 Agent 的一次接入。每次接入由 saveslot 签发一个独立的凭证，由用户命名，例如"MacBook · Claude Code"。例子里的 A 和 B 是两个连接实例。
- **用户会话**：用户本人，经命令行等给人用的入口操作时。
- **`system`**：saveslot 内核自己产生的事件（比如到期执行物理删除）记在这个保留主体名下。

actor 是从凭证得出的，调用方不能自己填。

### 来源

来源说的是：这次写入的依据是哪条源数据。它记到**字段**一级，并且分两种。

- **值来源**：字段的值是从它来的。例子第一步，日期、类别、金额的值来源都是 `s_1`。
- **操作来源**：它触发了这次写入，但没有提供任何值。

操作来源的典型情形是撤销。用户说"把午饭那笔撤销"，Agent 调 `write`，意图是 `revoke`，带上行 ID 和这句话作为证据。这次写入没有任何字段值，只是把行标记为已撤销。这句话记为操作来源：它说明这次撤销是凭什么发生的，但没有哪个值出自它。类似的还有回退到旧版本、解决一个待处理事项时带的证据。

### 三点容易误解的地方

**第一，操作来源不是"操作者"。** 操作者是 actor。操作来源和值来源一样，指的是一条源数据（一句话、一次请求），只是它在这次写入里起的作用是"触发"而不是"提供值"。

**第二，来源的种类不是原话自身的属性，而是按"哪次写入、哪个字段"记的。** 同一句话可以两种都是。用户说"把午饭那笔撤销，另外晚饭花了 80 元"：

- 对撤销午饭的那次写入，这句话是操作来源；
- 对新增晚饭那一行，这句话是金额的值来源。

**第三，"这句话证明了哪些字段"由 Agent 声明，saveslot 照着记。** saveslot 不理解语义。规则是：

- 一次写入里**改了值**的字段，以这次写入可见的证据为值来源。Agent 可以用 `evidence_by_field` 把不同字段指向不同的证据段。"改没改"是和 Agent 读到的那个版本比，不是和当前值比。
- **值没变**的字段分两种。Agent 用 `evidence_by_field` 显式指向了证据的，叫**佐证**：算这次写入的贡献，给该字段追加一个来源，不产生新版本。没有指明的，叫**无操作**：整行重发里原样带回的字段就是这种，不记来源。

第二条的道理在上一章讲过：Agent 手里没变的值，往往只是从 saveslot 读回来的，源头是更早的那句话；不能因为它出现在一次新请求里，就算作新证据的贡献。

### 为什么要分两种来源

为了删除时算得对。隐私删除只沿**值来源**传播：一句话被删，由它提供的值要处理；但它只是"触发"过的写入不受影响。

具体到撤销：用户说"撤销午饭那笔"，之后又要求删掉这句话。删除沿值来源找受影响的值，找不到任何由这句话提供的值，所以行的状态不变，仍然是已撤销。被删掉的只是这句话本身。如果不分两种来源，删掉这句话就会让那一行"复活"，等于替用户撤回了一个他做过的决定。

### 小结：可回溯落在字段上

前面几节合起来是一句话：**saveslot 的"可回溯"不是落在行上，而是落在字段上。** 分三层看：

- **来源和历史按字段记。** 一行的每个字段各有自己的来源、自己的变更历史。午饭那一行的日期出自 `s_1`，金额出自 `s_2`，两者互不相干。
- **冲突按字段（或声明要一起判的一组字段）判。** A 改备注、B 改金额，不算冲突；两个人改了同一个字段才算（第 5 章）。
- **撤回按操作发起，按字段执行；隐私删除同样落到字段。** 撤回一次写入，回掉的是它改过的那几个字段里仍然生效的部分，别人后来改过的字段不动。删掉一句话，受影响的是由它提供值的那几个字段，同一行里出自别的话的字段留着（第 8 章）。

所以"这一行是怎么来的"在 saveslot 里没有单一的答案，要问的是"这一行的这个字段是怎么来的"。

### 边界：来源准不准，取决于 Agent 声明得准不准

saveslot 保证的是：Agent 交来的证据被完整记下，saveslot 内部的来源链（比如派生数据出自哪些基础数据）是完整的。它保证不了 Agent 在写入时没有用到别的信息，也发现不了 Agent 把一个字段指向一句其实没提到它的话。

两种声明不当的后果不对称：

- Agent **少声明**（该佐证的没佐证）：删除时偏向多删。上一章情况二里那一行被整行删除就是这样。
- Agent **乱声明**：记下的来源不反映事实。这属于"数据真实性由调用方 Agent 负责"的范围。

saveslot 这一侧只有一项机械检查，叫**字面命中**：写入的值在证据原文里有没有字面出现过。它不拒绝任何写入，第一版只把结果记下来（第 5 章第 5 节）。

规格：[`../spec/03-data-model/03-deletion.md`](../spec/03-data-model/03-deletion.md)「来源：值来源与操作来源」；[`../spec/03-data-model/02-integrity-and-records.md`](../spec/03-data-model/02-integrity-and-records.md)「连接实例身份」「来源的完整性」；[`../spec/03-data-model/04-write-and-read.md`](../spec/03-data-model/04-write-and-read.md)「来源级别」。

## 6. 版本标记与读取记录

这两样东西让 saveslot 能发现并发修改、能在纠错后找出受影响的人。

**版本标记 `ver`。** 每一行有一个当前版本的令牌，读取时返回，修改时原样带回。它写成 `v21.0` 这样：前一个数是最近一次改动这一行的那次操作的操作号，后一个数是租户从备份恢复过的次数。saveslot 据此知道"你是基于哪个版本做的修改"，这个版本叫这次写入的**所见版本**。对不上时不直接拒绝，而是按字段比较：你要改的字段在那之后没被别人动过，就合并生效；被动过，才算冲突（上一章第三步）。

`ver` 只在这一行的生效值变了的时候变；完整的清单在第 5 章第 3 节。

slot 的 schema 版本 `sv` 是同样的用法：读的时候拿到，写的时候带回。

**读取记录（read_log）。** saveslot 自动记下每次读取：哪个连接实例、什么时候、读到了哪些行的哪个版本。它只记版本号，不记读到的值，所以不会变成第二份数据副本，被删的内容也不会残留在里面。

它有三个用处：

- **纠错影响。** 一个值被纠正后，查出哪些任务读到过旧值。
- **按时刻还原。** 某次任务当时看到的是哪个版本。
- **兜底。** Agent 写入时忘了带 `ver`，saveslot 用这个连接实例最近一次读到的版本代替，并在回执里写明。

读取记录有保留期限，到期清理。所以纠错影响查询只能覆盖保留期内的读取，结果里会写明覆盖到哪一天。第 6 章展开。

规格：[`../spec/03-data-model/02-integrity-and-records.md`](../spec/03-data-model/02-integrity-and-records.md)「读取记录」「纠错影响查询」。

## 7. 时间：两条时间线，三种表

这里只建立基本概念，细节留给第 7 章。

### 两条时间线

- **记录时间**：saveslot 是什么时候记下这件事的。对外用操作号表示。
- **业务时间**：这件事在现实中是什么时候发生或生效的。

大多数时候两者是同一刻。它们分开的时候，是用户事后才说：11 月 12 号告诉 Agent"其实 11 月 2 号起餐饮预算就降到 3000 了"。记录时间是 11-12，业务时间是 11-02。

两条时间线对应两种不同的问题：

- "11 月 5 号那天的预算是多少？"问的是业务时间。
- "上周那次任务跑的时候，saveslot 认为 11 月 5 号的预算是多少？"两条时间线都问到了。

### 三种表

schema 为每张表声明它的时间类型。

| 类型 | 一行是什么 | 例子 | 业务时间怎么体现 |
|---|---|---|---|
| 无时间 | 一个没有时间含义的事实 | 偏好、项目的基本信息 | 没有 |
| 事件类 | 一件发生过的事 | 一笔支出、一次跑步 | 发生时刻是表里的一个普通字段 |
| 状态类 | 一样东西在一段时间里的值 | 月度预算、目标、项目状态 | 每个值带一段生效区间 |

例子里的 `expenses` 是事件类表：`date` 就是一个普通字段。

状态类表的差别在于，Agent 读写的单位不是"行"，而是**实体**（比如"餐饮预算"这样一个被跟踪的东西）加上**生效区间**。"餐饮预算 10 月 1 日起 5000，11 月 10 日起 4000"是同一个实体的两段。区间怎么切、怎么存，由 saveslot 管理。

写状态类表时有一条默认规则值得先知道：**不指定终点时，新值只管到下一个已记录的变化为止。** 已经记了"11 月 10 日起 4000"，现在写"11 月 2 日起 3000"，结果是 11-02 到 11-09 为 3000，11-10 起仍是 4000。这样默认的理由是：猜错的后果是"少改了"，回执会提醒；而如果默认一直延续，猜错的后果是悄悄覆盖掉一个已经记下的事实。会抹掉已记录变化的写入属于**高影响写入**，默认不直接生效，要先确认（下一节的"待确认"事项）。

规格：[`../spec/03-data-model/05-time.md`](../spec/03-data-model/05-time.md)。

## 8. 待处理事项

有些事 saveslot 自己决定不了，需要人或 Agent 来判断。saveslot 把这些事统一成一种对象，叫**待处理事项**。

| 类型 | 什么时候产生 | 数据生效了吗 | 可以怎么处理 |
|---|---|---|---|
| 冲突 | 一次写入带回的版本不是当前版本，而且它要改的字段在那之后被别人改过 | 按规则给出一个确定的生效值 | 保持当前值 / 采纳候选 / 回到冲突前 |
| 待确认 | 高影响写入 | 没有，等确认 | 确认 / 拒绝 |
| 已标记 | 疑似重复的记录 | 已生效，只是被标出来 | 保留 / 撤销 |
| schema 变更 | 不能自动生效的表结构改动 | 没有，等确认 | 确认 / 拒绝 |
| 删除宽限期 | 一次已确认的删除，24 小时内 | 已经读不到，尚未物理删除 | 撤回 |

（另有一种与表结构迁移有关的事项，留到第 9 章。）

它们共有四条性质。

**持久。** 事项属于某个 slot，存在 saveslot 里，产生、合并、刷新、取代、解决都是日志事件。不依赖推送，不依赖某个会话还开着。

**不阻塞。** 事项未处理期间，读写照常进行。读到相关数据时，结果里带着标记（"有争议""有提议尚未生效""已标记"），标记写明是哪个事项、涉及哪些字段，读的一方自己决定怎么办。只读日期的一方，不会因为金额上的争议被要求停下来。

**不过期，也不会被悄悄关掉。** saveslot 没有判断力，任何"多久之后自动处理"的时长都是拍脑袋，所以它不替人裁决。事项不会堆积，靠的是：

- 冲突事项按字段算，同一行同一个字段上最多一个未决的冲突事项，后来的冲突并入它。
- 之后有写入改到了事项涉及的字段时，分两种情况。写入方**看过这个事项的详情**：事项标为"已被取代"，因为它看过候选之后做了新的决定。写入方**没看过**：事项只是**刷新**（当前值换成新值）并保持未决。

第二条的道理：读数据的一方看到的只有生效值和一个标记，没看过候选是什么。假如生效值是 Agent 推断的 9.5，候选是用户亲口说的 10，一个无人值守的 Agent 按外部工具同步写了 9.6；如果这样就把事项关掉，用户说过的 10 就不再出现在任何待处理事项里了。候选只能被看过它的一方关掉。

**确认绑定内容。** 处理事项时，调用方要带回它读到的事项版本（`item_ver`）。如果事项内容在这期间变了，版本对不上，saveslot 拒绝并返回当前内容。这保证"确认的就是执行的"：不会出现用户同意的是一份内容、实际执行的是另一份。删除的确认句柄 `dc_` 是同一个思路。

谁来处理？人（第一版经命令行）或 Agent（经 MCP）都可以。saveslot 分辨不了一次确认究竟出自人还是 Agent；是否真的征得了用户同意，由调用方 Agent 负责。saveslot 负责的是把每次确认是谁做的、确认的是什么内容记下来。

规格：[`../spec/03-data-model/01-objects.md`](../spec/03-data-model/01-objects.md)「待处理事项：统一对象」；[`../spec/04-contract.md`](../spec/04-contract.md) 第 6 节。

## 小结

把这一章压成几句话：

- 一个租户一条只追加的日志，日志是唯一的事实；表由 `apply` 从日志算出，可以丢弃重建。
- 存储里的每样东西要么是事件，要么能从事件算出，要么写明了丢了会怎样。
- 一次操作在日志里是几条连续的事件，对外只有一个操作号。
- 事件分事件头和内容块：事件头只有几个通用字段，串成链、永不删改；内容按块存放，可以整块清空。
- 每次写入都有源数据；每个字段记着来源；来源分"提供了值"和"只是触发"两种，由 Agent 声明。
- actor 回答"谁做的"，来源回答"凭什么"。
- 两条时间线：saveslot 何时记下，现实中何时发生。
- saveslot 决定不了的事成为待处理事项：持久、不阻塞、不过期、不会被没看过它的写入关掉、确认绑定内容。

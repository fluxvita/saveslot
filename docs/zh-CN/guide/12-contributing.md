## 1. 代码怎么分包

整个项目放在一个仓库里，分成若干个包（这种组织方式叫 monorepo；包之间的依赖由工具 pnpm 管理）。每个包对应第 4 章的一层。

| 包 | 里面是什么 | 依赖谁 |
|---|---|---|
| `contract-core` | 数据的形状：值怎么编码、证据、标记、意图、领域错误；事件格式的类型 | 无 |
| `kernel` | 内核的全部模块和 `ops`（第 4 章第 4 节）；租户存储与登记存储两个接口；登记存储的文件实现 | `contract-core`；存储只依赖接口 |
| `store-pglite`、`store-postgres` | 两个存储后端 | `kernel` 里的存储接口 |
| `contract` | 对外的契约：操作定义、幂等、分页、句柄、凭证相关的字段和错误 | `contract-core` |
| `service` | 服务层：身份、权限、幂等等待、句柄、限流、控制面存储（文件和 PostgreSQL 两个实现） | `kernel`、`contract` |
| `server` | HTTP 和 MCP 两个适配器，以及把结果渲染成文本的渲染器 | `service`、`contract` |
| `daemon` | 组装入口：选后端、把服务层和适配器拼起来、读配置、启动进程；后台任务的调度器 | `server`、`service`、两个后端 |
| `client` | 契约的 HTTP 客户端 | `contract` |
| `cli` | 命令行工具，一律经 `client` 走 HTTP | `client` |
| `saveslot`（入口） | 可执行文件，只做分发：管进程的命令交给 `daemon`，其余交给 `cli` | `cli`、`daemon` |
| `connector-ts` | 写连接器用的 TypeScript SDK，和脚本一样经 HTTP 调用服务；不发布 | 无（它的测试会起真的本机服务，用到 `daemon`、`service`、`store-pglite`） |
| `reference` | 参考求值器（第 2 节），只给测试用 | `contract-core` |
| `test-backend` | 测试打开存储用的后端：PGlite，按需换成 PostgreSQL；只给测试用 | `kernel`、两个后端 |

包之外还有两个目录，都不发布：`evals/` 放评测任务的数据与运行工具（第 2 节"评测"），`experiments/` 放各项实验的程序（第 3 节"必做的实验"）。

第一版不含开发者 SDK 的包，也不含 `kernel` 里的同步模块和作业模块。0.2.0 里 HTTP 与 MCP 的接口描述、HTTP 客户端都不是由契约生成的：客户端里每个操作对应哪条路由是手写的。

### 依赖方向

```
contract-core ◀── kernel ◀── service ◀── server ◀── daemon
      ▲                         ▲
      └──── contract ───────────┘
                 ▲
              client ◀── cli
```

箭头指向被依赖的一方。三条硬规则：

1. **`kernel` 不依赖任何传输方式，也不依赖 `service` 和 `contract`。** 它只认 `contract-core` 里的数据形状和两个接口（租户存储、登记存储）。这保证内核可以被单独拿出来，嵌进别的程序（将来的 SDK）。
2. **适配器不能绕过 `service` 直接调内核。** 身份和权限检查因此不可能被跳过。
3. **契约分两层是有意的。** `contract-core` 是数据本身的形状，内核依赖它；`contract` 是对外的包装（分页参数、幂等键、外层错误码）。这样对外接口加一个分页参数、加一个错误码，不用动内核。

包之间和内核模块之间的依赖规则都由工具检查，是 `pnpm check` 的一部分，合并前必须通过，违反了合不进去。

### 想改某样东西，去哪个包

| 想改的 | 去哪 |
|---|---|
| 一条判定规则（冲突怎么判、算不算高影响、一行存不存在） | `kernel` 的 `judge`。它是唯一的一份实现，写入时"判一次"和删除时"重放一整行"用的都是它（第 4 章第 4 节）；改了语义要升规则版本；同时改规格和参考求值器 |
| 写入或删除的流程（校验、取数据、生成事件） | `kernel` 里的 `write`、`delete` |
| 一种事件里记什么 | 先改事件格式规格；类型在 `contract-core`；`kernel` 里生成它的模块和 `apply` |
| 一个操作的参数或回执 | 先改契约的类型定义；数据形状在 `contract-core`，对外封装在 `contract`，内核里的入口在 `kernel` 的 `ops` |
| MCP 工具的描述、回执的文本措辞 | `server` 里的渲染器 |
| 一条命令行命令 | `cli` |
| 认证方式、限流 | `service` |
| 某个数据库后端的行为 | `store-pglite` 或 `store-postgres` |

规格：[`../spec/02-architecture.md`](../spec/02-architecture.md) §11。

## 2. 测试各防什么

saveslot 的很多承诺是"无论如何都成立"这一类的，这类承诺只能靠专门设计的测试来守。下面每一种测试都对应一类具体的错。

### 两个后端各跑一遍

内核的测试在 PGlite 和 PostgreSQL 上各跑一遍。

**防什么：** 某段逻辑只在一个后端上是对的。两个后端虽然都是 PostgreSQL，但版本、运行方式不同，行为可能有细微差别。

### 重放对拍

把同一份日志分别在两个后端上从头交给 `apply` 重放，然后逐行比较得到的表。另外再做一种："从空库重放"得到的表，要和线上一直运行下来的表逐行一致。

**防什么：**

- 重放结果依赖了日志之外的东西，比如当前时间、数据库的默认时区、排序规则。这类错平时看不出来，换个环境重放才暴露。
- `apply` 以外的地方改了表。
- 两个后端对同一条派生规则算出不同的数。

这是"日志是唯一事实来源"这句话的直接检验。哪些表参与比较，在存储格式的表清单里逐张标了；全文索引和数据目录里的概况统计可以重建，但不要求逐行一致。

### 导出重放

导出 → 重放进一个空库 → 和原来的表逐行比对。两个后端交叉各做一遍：PGlite 上导出的重放进 PostgreSQL，反过来也做。带"待删除"占位的导出也要测：重放后当前的业务状态和线上一致。

**防什么：** "数据能带走"成了空话。导入到空租户（`saveslot import`，第 11 章第 6 节）靠的也是这一点。

### 只有内核的一致性测试

给内核配一个"空的服务层"（任何人都能看到全部数据、不做幂等等待）和一个文件实现的登记存储，然后针对每一条内核不变量（K1–K14）写**反例**：故意做一件违反它的事，断言一定失败或一定被发现。例如：

| 故意做的事 | 必须发生的结果 |
|---|---|
| 不带匹配的事项版本去解决一个待处理事项 | 失败 |
| 绕过 `apply` 直接改业务表 | 对拍发现不一致 |
| 同一个请求键发两次 | 只落一次 |
| 改一处内容但不改校验和 | 日志校验报不符 |
| 删掉或调换一条事件 | 事件头链断裂 |
| 隐私删除到期后，在整个存储里搜被删的原文或由它算出的值 | 哪里都搜不到：事件头、内容、各版本的表、事项、目录、索引、读取记录 |
| 确认删除、把租户的数据复制一份当备份、等到期物理删除、再用备份盖回去（登记不动），然后打开 | 被删内容仍然搜不到 |
| 恢复备份后，用恢复之前拿到的版本标记、事项版本、句柄 | 都不会被当成当前版本接受 |
| 恢复流程每做完一步就强杀进程再启动 | 补删完成之前绝不对外服务 |

**防什么：** 两件事。一是不变量本身被实现坏了。二是不变量悄悄依赖了服务层：既然测试里服务层是空的，不变量还成立，就说明它确实只靠内核和那两个接口。后者是将来做 SDK 时"内核不用改"的保证。

### 参考求值器与性质测试

第 8 章讲过，隐私删除的结果是按一句定义算的。真正执行的代码为了效率只重算受影响的行，逻辑相当复杂。所以另外写一个**参考求值器**：一个纯函数，输入是"某一行的全部写入事件 + 被删的源数据集合"，输出是这一行应该是什么样。它把状态看成"每个字段在每个业务时刻的值"，按定义用最直白的方式实现，不追求效率，**不使用内核里的任何判定代码**（包括 `judge`）。它在 `packages/reference` 里，只依赖 `contract-core`，只有测试能引用它。

被删的集合为空时，它算出的就是"一串写入做完之后应该是什么样"。所以它不只对照删除，也对照写入、时间和冲突的规则。

规则里最绕的一块是"撤回某次写入、回到冲突前"遇上隐私删除时怎么算。这一块在规格里直接给了参考求值器的伪代码，作为权威定义（[`../spec/03-data-model/03-deletion.md`](../spec/03-data-model/03-deletion.md)「重放规则 · 回掉的权威定义」）。实现时先照它写出参考求值器，再让线上的实现和它对拍。设计阶段手推过的场景记在 [`../process/decisions/pre-dev-w6-final-fixes.md`](../process/decisions/pre-dev-w6-final-fixes.md) 的各个附录里，每一个都应当转成测试用例。

性质测试的做法是：不写几个固定的例子，而是让程序随机生成大量的写入和删除序列，检查一组性质是否每次都成立。性质分三组，完整的表在 [`../spec/02-architecture.md`](../spec/02-architecture.md) §11：

| 组 | 例子 | 抓什么错 |
|---|---|---|
| 删除（第 8 章第 10 节列了全部） | 与参考一致；顺序无关；不漏删；不多删；已生效的保持生效；无操作保持无操作；回退不落回被撤回的值；重述后线上与参考一致；记录与重算一致 | 删除的规则实现偏了；隐私上的漏网之鱼；删过头 |
| 时间 | 默认终点的写入，等同于以"该字段的下一个挡点"为显式终点的写入；把一段数据在内部切成两段，任何判断的结论不变；`as_of` 不会读到一次写入的中间状态 | 终点解析错、没按字段解析；判断偷看了内部怎么分段；版本表用错了序号 |
| 冲突 | 在规格写明的范围内（两次写入带同一个版本、都不传终点、都不指证据、都没有抹掉读到的变化点）：先 A 后 B 判冲突，当且仅当先 B 后 A 也判冲突；不冲突的，两种顺序结果相同。范围之外已知的三种情形各有一条固定用例；每次被接受的写入都有下落，候选不会无声消失 | 判定依赖到达顺序；合并结果依赖顺序；事项被没看过它的写入关掉 |

其中"记录与重算一致"值得多说一句。"从空库重放 = 线上状态"这个测试抓不到删除算错的情形，因为重放用的就是事件里记下的那个结果，错的结果会被忠实地重放出来。所以需要一个独立的实现来对照。

规格里有两份场景推演（删除的、状态类表并发的，都在 `docs/zh-CN/process/walkthroughs/` 下），其中的每个例子都会写成一条"与参考一致"的用例。

### 契约测试与渲染器测试

- **契约测试：** 同一组用例对 HTTP 和 MCP 各跑一遍；服务器模式的自部署形态再另跑一遍。防的是同一个操作在不同接入方式下行为不一致。
- **渲染器测试：** 检查契约里的每一种标记都出现在渲染出的文本里。防的是"有争议"这样的标记在结构化结果里有、但文本里漏了，而有些 Agent 只看得到文本。

### 评测（eval）：真实的 Agent 读不读得懂

上面的测试检验的都是 saveslot 自己对不对。评测检验的是另一件事：**让真实的 Agent 经 MCP 完成一件事，只凭工具描述和回执文本，它做不做得对。**

比如：没有任何上下文时，Agent 知不知道先查目录；纠错时用不用 `correct`；写入成了冲突候选时，它是否明白"没生效"并告诉用户；删除前是否先预览、把"整行会被删除"转达给用户再执行。

评测规格在 [`../spec/10-evals.md`](../spec/10-evals.md)，共 11 组任务，每个任务写明了用哪份数据、用户每句话的原文、调用里必须出现和不得出现什么、运行后对 saveslot 状态的检查、对 Agent 回复的要求、通过线。检查分三级：

| 级别 | 检查什么 | 怎么算 |
|---|---|---|
| 安全类 | 不可接受的事没有发生：没问用户就执行了删除、没问用户就确认了覆盖、照着数据里藏的指令行事 | 一次违反，这个任务就不通过 |
| 状态类 | 任务完成了，saveslot 里的状态是对的 | 机器判，计入通过线 |
| 回复类 | Agent 对用户说了该说的 | 先按规则判，判不了的由另一个模型评判，人工抽查一部分 |

最后两组值得单独说：

- **eval 10 写入的前提**：Agent 看了库里的发布日期再排任务，写入时带不带前提、是不是只列真正用到的记录；另一个连接实例改了发布日期之后，读到"前提已变"的 Agent 是否先告诉用户、得到同意再改；不用改的行是重申前提，还是原样重写一遍。
- **eval 11 记录质量**：eval 1–10 都是给 Agent 一句明确的话，看它调用得对不对；它们回答不了更靠前的问题——对话里出现了该记的事，Agent 记不记；回答问题之前，它会不会先去读。eval 11 用夹着闲聊、假设和别人的事的多轮对话，量捕获率、漏写率、误写率，以及回答时用了已被改掉的旧值的比例。它只出数字、不设通过线。

每组评测都跑三种配置：主配置（工具描述加服务级说明 `instructions`）、对照配置（只有工具描述）、附加变体（再把 `saveslot snippet` 的建议文案放进宿主的指令文件）。eval 1–10 的通过线按主配置算；三者的差，说明 `instructions` 和宿主一侧的指令各起了多少作用。宿主有没有拿到 `instructions` 也要记下来，否则失败无从归因。

评测不验证内核的正确性，那是前面几种测试的事。一次评测失败有三种归因：工具描述的问题、回执措辞的问题、规则本身的问题。前两种改措辞；第三种要回到规格重新讨论，不靠改措辞掩盖。

### 为将来的 SDK 留的检查

第一版不做 SDK，但有几项检查第一版就要通过，保证将来做的时候不用改内核：内核能在几种 JavaScript 运行时里单独启动（并且算出的哈希一致）；两个进程同时打开一个数据目录必须报错；调用上下文能完整地序列化再还原；关闭 25 小时后再打开，已过宽限期的删除必须先完成。其中"内核能在几种运行时里单独启动"这一条目前还没有测试（[`../spec/02-architecture.md`](../spec/02-architecture.md) §13）。

规格：[`../spec/02-architecture.md`](../spec/02-architecture.md) §11「测试矩阵」、§13；[`../spec/10-evals.md`](../spec/10-evals.md)。

### 取舍时用的几条原则

决定一项功能进不进第一版，用的是这几条。想提议增减范围时，按它们来论证：

1. **会改事件格式的，第一版必须做，至少留位。** 判据是：将来加回来时，旧事件里缺的信息还补不补得回来。比如字段级的来源、字面命中、规则版本，事后补不了，所以第一版就要记，哪怕用到它们的功能第一版没有。
2. **会放松某条内核不变量的，第一版必须做。** 只允许"适用面变小"（功能没开，规则自然不触发），不允许打折。
3. **只影响外化面、或者能纯增量加回来的，优先砍。** 纯增量指的是：新增一种事件、一个工具、一个端点，旧数据不用迁移。
4. **能跑评测优先于功能完整。**
5. **云服务的法律底线不能砍。** 隐私删除和导出因此不后移。

### 必做的实验

有几件事纸面上定不下来，要靠实验。每项实验都写了客观的通过标准和"不通过时怎么办"，标准在实验开始前可以调，不在看到结果之后改。

| 实验 | 问的是什么 | 结论会影响什么 |
|---|---|---|
| 1 PGlite 持久性 | 进程被强杀或断电后，已确认的写入会不会丢 | 不达标就把本机后端换成打包的原生 PostgreSQL |
| 8 单写者锁 | 两个进程同时打开一个数据目录，是否恰好一个成功 | 锁的实现方式 |
| 2 PGlite 沙箱 | 终止 worker 的代价有多大；SQL 白名单挡不挡得住各种绕过 | 慢查询的超时策略 |
| 4 派生刷新的延迟 | 写入时同事务重算派生表，典型数据量下要多久 | 写入准入的阈值 |
| 9 容量边界 | 三种数据形状（按人的节奏的 1 万到 100 万条事件、十年的汇总健康数据、分钟级的序列读数）在两个后端上：写入延迟、日志与存储多大、打开数据与从头重放要多久、导出与删除的耗时、内存。只出数字，逐个规模点往上做到"到这里不行" | 数据目录与 `saveslot doctor` 的两条规模界线；快照要不要提前做；高频读数要不要单设一种表 |
| 5 重放一致性 | 同一份日志在 PGlite 和 PostgreSQL（含不同大版本）上重放，结果是否逐行一致 | 服务器模式能否上线 |
| 7 物理删除后的残留 | 删除并清理之后，在数据目录的文件里按字节搜被删的原文，搜不搜得到 | 残留清理的做法 |
| 6 桌面打包 | PGlite 的启动时间和内存；打包原生 PostgreSQL 是否可行 | 本机的安装方式 |
| 3 每用户一个库的容量 | 一个数据库集群里放多少个用户库是安全的 | 云服务每组服务器放多少用户；不挡第一版上线 |

实验 1 的设计里有一点值得知道：只做"强杀进程"的测试是不够的。进程被杀时，已经交给操作系统的数据还在内存缓存里，不会丢，所以即使完全没有落盘也能通过。实验因此要直接观察落盘的系统调用，并且做真实的断电；还要求默认配置在同样的测试里必须丢数据，否则说明测试方法没有制造出真正的断电。

目前最大的两个不确定性：实验 1 还没做的断电步骤；以及隐私删除按定义重放受影响行的实现难度。

规格：[`../spec/07-scope-v1.md`](../spec/07-scope-v1.md)。它的第 3 节是逐项的机制清单（九十余项，每项标了做、简化还是后续，在哪个阶段，以及对哪条不变量有影响），想知道某个功能第一版有没有，查那里。

### 改设计时要同步什么

设计改动不是只改一处。下面是一份检查清单：

| 改了什么 | 还要看哪里 |
|---|---|
| 一条数据规则 | `03-data-model/` 里的权威定义；它对应的内核不变量（`02-architecture.md` §3）；如果改了判定的语义，规则版本要加 1；事件格式里受影响的字段；契约里受影响的参数、结果、错误码；外化面的文本；第一版范围里对应的那一行；参考求值器与性质测试 |
| 事件里记什么 | `09-event-format.md`（只增不改）；它是元数据块还是数据块、数据块的来源是什么、删除时怎么级联（`03-data-model/03-deletion.md`「由源数据派生出的内容」）；`apply` 据此改哪些表 |
| 新增一种存下来的状态 | 归入三类之一，加进 `02-architecture.md` §8 的表清单；如果是 (c) 类，写明"丢了会怎样" |
| 一个操作的形状 | `04-contract-types.md`；`04-contract.md` 里的规则；MCP 与 HTTP 的对应（`05-surfaces.md`）；命令行（`06-cli.md`）；和事件格式共用的枚举，两边要同名 |
| 工具描述、参数说明、服务级说明 `instructions`、prompts 或回执措辞 | `05-surfaces.md`；过一遍下面的检查；重跑相关的评测（`10-evals.md`），`instructions` 改了要看 eval 11 主配置与对照配置的差 |
| 第一版做不做某项 | `07-scope-v1.md` 的机制清单，并写明对不变量的影响 |
| 留下了没定的事 | 记进 `08-open-questions.md`。它是唯一的待定清单，别的文档只指向它 |
| 讲解里讲到的内容 | 本目录对应的章节 |

**改工具描述、参数说明、`instructions`、prompts 时要过的检查。** 这几样是"静态文本"：只有 saveslot 的发布者能写，经过评审，所以可以写"什么情况下该用"。回执、报错、提示这些"动态文本"紧挨着存下来的不可信数据，只陈述事实和可用的下一步，不指挥模型（要求先征得用户同意的那几处除外）。改静态文本时逐条检查（完整的在 `05-surfaces.md` 4.3）：

1. 以用户的意图为条件（"用户问到自己的记录时"），不写无条件的要求（"每次对话开始时都调用"）。
2. 写清什么时候不用：闲聊、假设、没有对应的表时不写入。
3. 只谈 saveslot 自己的工具：不提别的服务的工具，不要求优先于别的工具，不改写宿主或用户给模型的指令，不要求模型对用户隐瞒什么。
4. 只提这个凭证用得了的工具：指向别的工具的句子，只在那个工具也在清单里时出现。
5. 不含任何存下来的用户内容：表或字段的说明、别名、取值、原文都不进来；唯一的例外是 `instructions` 里的 slot 名。
6. 顺序依赖写成条件句（"改已有的记录前先读它"），不写成"必须先调用 X"。
7. 要紧的话放在开头：`instructions` 的前 512 个字符自成一体，全文和每个工具描述都不超过 4,096 个字符。

模型看得到的文字一律用白话，标识符照规格写；第一版是英文；规格规定内容，实现里的英文是实际发出的文字。

两条写作上的约定：

- **方案文档只写方案。** 日期、第几轮修订、是谁在哪次审查里提的，这些过程信息写进 `docs/zh-CN/process/`，不进方案文档。
- **涉及删除的改动，用例子对照定义。** 每个例子并排给出"按定义应该是什么"和"按规则推出来是什么"，两者不一致就是规则有问题。

### 推演：检验设计的办法

提出一个新场景或一条新规则时，最有效的检验是走一遍推演：选一个具体场景，每一步写清 Agent 发了什么调用、日志追加了哪些事件、哪些表变了、本地运行状态有什么变化、下一个会话读到什么，然后对照 K1–K14 逐条检查。凡是"两个 Agent 谁先到结果都该一样"的地方，两种顺序都推一遍。第 2 章就是一个简化的推演。

## 5. 还没定的事

全部未定事项集中在 [`../spec/08-open-questions.md`](../spec/08-open-questions.md)。读规格时看到"待定"，指的都是那里。它按"什么时候必须定"分成三组：

| 组 | 含义 | 例子 |
|---|---|---|
| 开发前必须定 | 会写进日志事件、定下后难改的。这一组在内核开发开始前应当清空 | 目前没有：都已定下，事件格式已在 0.1.0 冻结 |
| 某个阶段开工前定 | 写明了是哪个阶段 | 写入准入的阈值与各种超时、两条规模界线的数值（等实验结果）；切换的批大小与阈值、官方 schema 的细则（P4 前）；删除的法律口径、租户整体删除（P5 前） |
| 可以开发后再定 | 后续版本的设计，或不影响已有事件的 | 表级、字段级的数据权限；"只接受用户本人确认"的开关何时实现；按来源级别的自动裁决的细则；开发者 SDK；社区 schema 的安全 |

想找一个可以参与讨论的切入点，可以从这份清单的后两组开始。

## 小结

- 代码按层分包，依赖只能从外向内；内核不依赖任何传输方式和服务层，只依赖两个存储接口。
- 每种测试对应一类具体的错：双后端、重放对拍、导出重放、内核不变量的反例、参考求值器与三组性质测试、契约与渲染器测试；评测检验的是真实的 Agent 读不读得懂。
- 第一版分步实现，每步以能跑通的评测为验收；事件格式在 0.1.0 冻结，此后只增不改；0.2.0 提供哪些见 `07-scope-v1.md` 第 7 节。
- 规则的权威定义在 `03-data-model/`，事件的形状在 `09-event-format.md`，对外的形状在 `04-contract-types.md`；改设计时按清单同步；未定事项只记在一处。

# 11 · 部署与接入

[English](../../guide/11-deployment.md) · 简体中文

这一章回答实际使用的问题：saveslot 装在哪、Agent 怎么连上它、人怎么操作它、凭证怎么管、数据怎么带走、备份恢复后要注意什么。

## 1. 两种运行模式

第一版有两种运行模式。两种都是**单节点**：一个用户的数据只在一个地方。

| | 本机模式 | 服务器模式 |
|---|---|---|
| 装在哪 | 用户自己的电脑 | 一台服务器：我们运营的云服务，或用户自己部署 |
| 谁能连 | 只有这台机器上的 Agent 和程序 | 任何地方的 Agent，经网络 |
| 数据库 | PGlite（嵌在 saveslot 进程里，数据在本机的一个目录） | 原生 PostgreSQL，每个用户一个独立的 database |
| 用户数 | 一个 | 多个，互相隔离 |
| 适合 | 只在一台电脑上用；数据不想离开本机 | 多台设备共用；要接云端的 Agent；希望全天在线 |

两种模式跑的是同一个内核、同一套规则。核心能力不会只在某一种里有。

### 容易误解的一点：单节点不等于"本地和云端不能共用"

只要部署了服务器模式，本机的编码 Agent、另一台电脑上的 Agent、云端跑的 Agent 都连同一个服务，读写的是同一份数据。这是第一版让多设备共用数据的办法。

第一版不做的是另一件事：**同一份数据同时放在本机和云端两个地方，两边互相同步。** 由此带来的两点实际影响：

- 连服务器模式时，断网就用不了。
- 本机模式的数据只有本机能访问。本机模式和服务器模式是两份互不相通的数据，第一版不在它们之间同步。要从本机搬到服务器，做法是一次性的导出、再导入到服务器上一个空的账户里（第 6 节）。

### 云服务和自部署的差别

服务器模式的两种部署是同一套代码、同一组配置项，差别只在部署方是谁：

| 方面 | 我们的云服务 | 用户自部署 |
|---|---|---|
| 人的账户 | 我们的账户系统 | 内置的本地账户：由部署的人用运维命令创建，不开放注册 |
| 对外地址与证书 | 我们的域名 | 部署方自己提供 |
| 密钥保管 | 我们 | 部署方 |
| 限流与配额 | 开 | 默认关，可配置 |
| 备份与恢复 | 我们做 | 部署方做，恢复后必须走恢复流程（见第 6 节） |
| 规模 | 多组服务器 | 一个进程、一个数据库集群即可 |

自己部署要准备什么、怎么初始化和建账户，见第 13 章。

### 平台支持

本机模式第一版只支持 macOS 和 Linux，Windows 放在后面。

## 2. Agent 怎么连

Agent 经 **MCP** 连 saveslot（第 1 章介绍过：Agent 调用外部工具的一种通用协议，Claude Code、Codex 这类 Agent 都支持）。接上以后，Agent 的工具列表里会多出一组 `saveslot_` 开头的工具。

### 第一版开放的 10 个工具

| 工具                      | 读 / 写 | 做什么                                                |
| ----------------------- | ----- | -------------------------------------------------- |
| `saveslot_catalog`      | 读     | 看有哪些 slot、表、字段、单位                                     |
| `saveslot_query`        | 读     | 按条件查数据，返回每行的 `ver`                                 |
| `saveslot_sql`          | 读     | 只读 SQL，用于关联和聚合                                     |
| `saveslot_history`      | 读     | 看一样东西怎么变成现在这样，或某个过去时刻的样子                           |
| `saveslot_sources`      | 读     | 列出、搜索、读取源数据；删除前的影响预览也在这里（它的 `deletion_preview` 模式） |
| `saveslot_pending`      | 读     | 列出待处理事项，看某一项的详情                                    |
| `saveslot_write`        | 写     | 写入：新增、变更、纠错、撤销                                     |
| `saveslot_resolve`      | 写     | 处理一个待处理事项                                          |
| `saveslot_schema_draft` | 写     | 提交 schema 草稿（建 slot、改表结构；第一版先开建 slot）                 |
| `saveslot_delete`       | 写     | 执行一次已预览的删除（0.2.0 尚未提供）                              |

完整设计里还有两个与"重新抽取"有关的工具，随那部分功能后做。

Agent 调用工具后收到的是一段文本。它长什么样，前面有三份实例：第 2 章第一步的写入回执、第三步"成为候选"的回执，第 6 章第 3 节的查询结果。

几条设计上的考虑，接入方值得知道：

- **按最差的 Agent 设计。** 只依赖"调用工具、拿回文本"这一最基本的能力。Agent 的宿主不支持弹窗确认、不支持结构化结果，流程照样走得通。
- **工具列表按权限裁剪。** 一个只有读权限的连接实例，工具列表里根本没有写工具。六个读工具总在，因为每个连接实例都有读权限。连接实例只看得到某几个 slot 时，工具列表不变，范围外的 slot 在任何结果和报错里都不出现（第 4 节）。
- **标记一定出现在文本里。** "有争议""有待确认的改动"这些标记在契约里是结构化字段，渲染成文本时一个都不会漏。有些宿主只把文本交给模型，所以不能只放在结构化结果里。
- **ID 和版本标记一律完整给出。** 模型要原样带回它们，所以文本里不缩写。
- **读回来的文字包着不可信边界。** 见第 10 章第 6 节。
- **结果有长度预算。** 一个工具结果的文本最多 10 万字符。能翻页的结果（查询的行、事项列表、历史）在预算处截断，截断点就是下一页的起点，不漏行；不能翻页的结果超了预算会报错并提示怎么缩小，不会悄悄截掉一半。
- **调用了第一版还没实现的功能**，统一得到 `not_in_this_version` 这个错误，写明是哪个参数或操作。
- **管理类操作不进 MCP。** 签发凭证、读取审计、日志校验与对拍、导出、导入只给人用，走命令行或 HTTP。

### 接上之后，Agent 怎么知道什么时候该用 saveslot

工具接上了，不等于 Agent 会在对的时候用它：用户说"今天跑了 5 公里"，Agent 得知道这该记下来；用户问"这个月跑了多少"，得知道先去查。MCP 本身只保证 Agent "能"读写（第 10 章第 2 节）。saveslot 在三处给它提示，都不需要用户做什么：

| 在哪 | 给谁看 | 写什么 |
|---|---|---|
| 服务级说明（MCP 里叫 `instructions`） | 模型；宿主连上 saveslot 时取得 | saveslot 是什么；用户问到自己的记录时先查再答；用户说出属于某张表的新事实、或指出记错了时写入，提问、假设、闲聊时不写；回执写着"待确认"时先告诉用户；最后列出这位用户的 slot 名和每个 slot 有几张表 |
| 每个工具的描述 | 模型 | 这个工具什么时候用、什么时候改用别的 |
| 快捷入口（MCP 里叫 prompts） | 人：宿主通常显示成斜杠命令，如 Claude Code 里菜单显示 `/saveslot:overview`，直接输入是 `/mcp__saveslot__overview` | 三个：看一下有什么（`overview`）、逐项处理待处理事项（`pending`）、开始记录一类新的事情（`track`） |

几点要知道：

- **按凭证生成。** 只读的连接看到的说明里没有"什么时候写"，换成"这个连接是只读的"；范围外的 slot 不列；没有改 schema 权限的看不到 `track`。
- **只列 slot 名和表数，不列表名。** 表名由 Agent 用 `saveslot_catalog` 去查（为什么见第 10 章第 6 节）。新建的 slot 不会另发通知，以 `saveslot_catalog` 为准。
- **只写"在什么情况下用"。** 不写"每次对话都先调用"这类无条件的要求，并写明什么时候不用。写得太宽，Agent 会把随口一句话记下来；写得太窄，该记的会漏掉。两头各有多少，由评测来量（第 12 章 eval 11）。
- **有的宿主不把服务级说明交给模型，或者不支持快捷入口。** 那样只剩工具描述，流程照样走得通，只是 Agent 主动用 saveslot 的时候可能少一些。想更稳，可以把一段建议文案放进宿主自己的指令文件（Claude Code 的 `CLAUDE.md`、Codex 的 `AGENTS.md`）：`saveslot snippet <宿主>` 打印文案和该放在哪。这一步是可选的，由你自己放；saveslot 不写这些文件，理由和第 5 节"不改宿主的配置文件"相同。
- **第一版这些文字是英文的。** 它们是写给模型读的，模型照样用你的语言回答你。

### 本机模式怎么接

本机的 saveslot 服务不监听网络端口，只监听一个本机的套接字文件（unix socket），文件权限只允许当前系统用户访问。好处是别的用户连不上、网络上的人连不上、浏览器里的网页也打不到它。

Agent 的宿主一般不会直接连套接字文件，所以 saveslot 提供一个小的转发程序 `saveslot mcp`：宿主把它当作一个普通的 MCP 服务启动，它把消息转给本机的 saveslot 服务。

```
Claude Code ──启动──▶ saveslot mcp ──套接字──▶ saveslot 服务 ──▶ 数据目录
Codex       ──启动──▶ saveslot mcp ──套接字──▶     （同一个进程）
```

两个 Agent 各启动一个 `saveslot mcp`，但背后是同一个 saveslot 服务进程、同一份数据。如果 saveslot 服务没在运行，`saveslot mcp` 会先把它拉起来。

### 服务器模式怎么接

Agent 的宿主直接走远程 MCP，地址形如 `https://<域名>/mcp`。授权用 OAuth：宿主打开授权页，用户在页上确认这次接入的名字和权限，点一次"授权"，这个 Agent 就成了一个连接实例。

授权页上每一项都有默认值：名字取宿主自报的名称，权限是读 + 写；不改就只点一次。这样授权出来的连接实例能看到全部 slot（含以后新建的）。要一个只碰某几个 slot 的凭证（比如连接器），在命令行里用 `saveslot connect http --profile <名字> --slots …` 签发静态令牌。一次授权就是一个连接实例；之后在命令行里用 `saveslot connections list` 能看到它，改名、吊销照常。

宿主那一侧的添加命令同样由 `saveslot connect <宿主> --profile cloud` 打印出来（自部署换成它的 profile）。这条命令里没有令牌，凭证由宿主自己走 OAuth 取得，所以加 `--apply` 时由 saveslot 代为执行。只有网页界面的宿主（Claude 网页端、ChatGPT 这类）没有命令可执行，要在它的界面里手动填地址：这一步 saveslot 消不掉。

### 没有 Agent 的程序：HTTP

脚本、自己写的程序可以直接调 HTTP 接口，路径以 `/v1` 开头，请求和回执就是契约里定义的 JSON。HTTP 和 MCP 由同一份契约生成，能做的事基本一样；差别主要是 HTTP 不做文本渲染、不按长度截断结果，并且开放管理类操作。

这类调用方里有一种值得单独说：**连接器**，即定时把某个外部系统（手环、记账 App）的数据搬进 saveslot 的程序。它不是 saveslot 的一部分，由官方或开发者各自编写；saveslot 不调度它，也不替它保管外部系统的授权令牌。它以一个连接实例的身份经 HTTP 写入，和别的接入方同等对待。saveslot 为它准备的只有三样通用能力：凭证可以只限定到它负责的那个 slot（第 4 节）；表上可以声明来源键，同一条记录反复同步不会重复新增（第 9 章）；分批写入的重发识别。凭证这样取得：

```
$ saveslot connect http --name "手环 · 连接器" --slots health
```

手机或别的设备上的采集程序只能配合服务器模式：本机模式只供本机访问，别的设备连不上。走不了 OAuth 的脚本和连接器连服务器模式时，用 `saveslot connect http --profile cloud` 由用户会话签发一个静态令牌，同样按权限和 slot 范围限定、可吊销。

写脚本时要注意一点：写入返回成功，不等于"已生效"。回执里的 `status` 可能是 `saved`（已保存），也可能是 `pending`（已记下但未生效，比如成了冲突候选）。脚本必须看这个字段。

规格：[`../spec/05-surfaces.md`](../spec/05-surfaces.md)（`instructions` 与工具描述在第 9 节，prompts 在 10.1，远程授权在第 15 节）；凭证与 slot 范围见 [`../spec/04-contract.md`](../spec/04-contract.md) 第 12 节。

## 3. 人怎么用：命令行

第一版不做图形界面的 App。人要做的事都经**命令行工具** `saveslot` 来做，或者交代给 Agent 去做。

人用命令行做的事：

| 做什么 | 命令 |
|---|---|
| 一条命令完成上手：初始化、启动、建第一个 slot、接入本机装着的 Agent | `saveslot setup` |
| 分步：初始化、启动、停止本机服务，看状态 | `saveslot init`、`saveslot start`、`saveslot stop`、`saveslot status` |
| 逐项自检（服务、权限、同步盘、各宿主里的条目、数据规模） | `saveslot doctor` |
| 建 slot | `saveslot slot create`；也可以让 Agent 经 `saveslot_schema_draft` 起草、你同意后建（默认签发的连接实例就能这样做） |
| 给 Agent 签发、查看、吊销凭证 | `saveslot connect`、`saveslot connections list / revoke` |
| 打印建议放进宿主自定义指令的文案 | `saveslot snippet` |
| 处理待处理事项 | `saveslot pending`、`saveslot pending show`、`saveslot pending resolve` |
| 删除与撤回（0.2.0 尚未提供） | `saveslot delete`、`saveslot delete cancel` |
| 查数据、看历史 | `saveslot query`、`saveslot history`、`saveslot sql`、`saveslot sources` |
| 看谁读过什么 | `saveslot reads` |
| 校验、对拍 | `saveslot verify`、`saveslot verify --replay` |
| 导出（可选口令加密）、导入到空的账户 | `saveslot export`、`saveslot import` |

三点设计值得知道：

- **命令行不做业务写入。** 没有 `saveslot write`。写入需要把一句话变成意图、行、值和证据，这是 Agent 的事。人想改数据，对 Agent 说，那句话就是证据。
- **命令行不直接碰数据目录。** 除了初始化那一次，所有命令都经 saveslot 服务。这样单写者和读取留痕都不会被绕过。
- **确认时绑定的是人刚看到的那一份。** 处理事项时，命令行先把详情展示出来，再用展示时拿到的事项版本去执行；删除时用的是刚展示的那份预览的句柄。删除的确认要求输入完整的 `delete`，不接受按一下 `y`。

规格：[`../spec/06-cli.md`](../spec/06-cli.md)。

## 4. 凭证、连接实例与权限

### 两类凭证

| 凭证 | 谁持有 | 能做什么 |
|---|---|---|
| **用户会话** | 人 | 一切，包括签发和吊销连接实例、读取审计、导出 |
| **连接实例** | 一个 Agent、一个脚本或一个连接器 | 按签发时给的权限，在签发时给的 slot 范围里 |

每个 Agent 的每次接入都有自己的连接实例，由用户命名，建议写成"设备 · Agent"，例如"MacBook · Claude Code"。这个名字会出现在历史、事项的发起者和读取审计里。第 2 章的 A 和 B 就是两个连接实例。

给每个 Agent 单独的凭证，是"谁做的"能说清的前提：两个 Agent 共用一个凭证，它们的读写就分不开了。

### 四种权限

权限在签发连接实例时选定，按动作分四种，规格里叫 scope：

| 权限 | 允许 | 默认 |
|---|---|---|
| `saveslot.read` | 全部读操作，含删除预览 | 每个连接实例都必须有 |
| `saveslot.write` | 写入；处理与写入有关的事项 | 给 |
| `saveslot.schema` | 提交 schema 草稿；处理 schema 变更事项 | 不给，要显式勾选 |
| `saveslot.delete` | 执行删除；撤回删除（0.2.0 尚未提供） | 不给，要显式勾选 |

命令行签发时用 `--scope` 调整。两种写法，不能混用：

- 在默认（读 + 写 + 新建 slot）上增减：`--scope +delete`、`--scope -schema`、`--scope -write`。不让 Agent 建 slot 就是 `--scope -schema`，只读的连接实例就是 `--scope -write,-schema`。scope 在签发时定下：之前签发的连接实例要获得建 slot 的能力，重新 `connect`。
- 完整列出：`--scope read,write,schema`，列出的就是全部。

去掉读权限是用法错误：没有读权限的连接实例什么都做不了，也没法先读再写。

### 能看到哪些 slot

签发时还可以限定这个连接实例能看到哪几个 slot。**授权 = 权限 × slot 范围**：同一组权限对范围里的每个 slot 都一样。

```
$ saveslot connect http --name "手环 · 连接器" --slots health
```

- **不限定就是全部 slot，包括以后新建的。** 限定成一个列表时，之后别人新建的 slot 不纳入。
- **范围外的 slot 对它和不存在完全一样。** 目录里没有，按名字引用会报"没有这个 slot / 这张表"，和真的不存在报同一个错误；提示、候选里也不出现它们的名字。这样它连"还有别的 slot"都看不出来。
- **限定了范围的连接实例不能新建 slot。** 建出来的 slot 不在它的列表里，它自己都看不见。先由你建好，再签发限定到它的凭证。
- **要"A 可写、B 只读"，就签发两个连接实例。**
- 第一版能限定到 slot 为止；某张表、某个字段只给某个 Agent 看，是后续版本的事。

典型的用法是给连接器：它只该碰自己负责的那个 slot。`saveslot setup` 签发的都是范围为全部的连接实例，要限定就用 `saveslot connect --slots` 单独签发。

需要知道的限制：

- **权限和 slot 范围签发后都不能改。** 要改就吊销重签。
- **令牌只显示一次。** saveslot 只保存它的哈希。丢了就吊销重签。
- **吊销立即生效。** 令牌外泄时这是收回权限的手段。吊销只是让这个凭证之后的请求被拒，不删除任何东西：它写过的数据还在，记的仍是它的名字，显示时名字后标"已吊销"；它发起而还没处理的事项（冲突、待确认等）照常留着，由用户或别的有权限的连接实例处理。吊销之后它的名字**仍然占用**，不能再签发同名的连接实例：历史里同一个名字只指一个主体。

### 只有用户会话能做的事

签发、改名、吊销连接实例；查看读取审计；日志校验与对拍；导出；导入。

理由很直接：能签发凭证的 Agent 可以给自己任意权限；审计的对象正是各个 Agent，被审计的一方不该能读全部审计；导出是一次拿走全部数据，这是用户的权利，不是 Agent 的；导入决定了这个账户里有什么、谁的凭证还有效。

### 本机上的一个边界

本机模式下，用户会话的凭证是用户主目录里的一个文件。一个有 shell 权限的 Agent（能在终端里执行命令的那种）读得到它，也能直接运行 `saveslot` 命令，这时它做的事都记在用户名下，和真人操作分不开。saveslot 防不住这一类程序。

如果希望有 shell 的 Agent 也留下自己的痕迹，给它一个连接实例令牌，让它带着这个令牌运行命令行工具。

## 5. 上手流程（本机模式）

### 一条命令

从零到第一个 Agent 能用，装好之后只要一条命令：

```
$ npm install -g @fluxvita/saveslot
$ saveslot setup
[1/5] 已创建 ~/.saveslot（0700）
[2/5] saveslot 服务已在后台启动 · pid 4211
[3/5] 用哪个模板建第一个 slot？（空格选择，回车确认；可以不选）
      [ ] running   跑步记录 → slot health
      [x] spending  日常支出 → slot ledger
      [ ] budget    预算 → slot plan
      已建 slot ledger · schema v1 · 2 张表（expenses、monthly_total）
[4/5] 接入哪些宿主？
      [x] Claude Code（claude 2.x，/usr/local/bin/claude）
      [x] Codex（codex 0.x，/opt/homebrew/bin/codex）
      [ ] Cursor（没有添加命令，需要手动粘贴配置：saveslot connect cursor）
[5/5] 将为每个宿主签发一个连接实例（scope saveslot.read saveslot.write），并执行：
        claude mcp add saveslot --scope user -e SAVESLOT_TOKEN=<令牌> -- /usr/local/bin/saveslot mcp
        codex mcp add saveslot --env SAVESLOT_TOKEN=<令牌> -- /usr/local/bin/saveslot mcp
      执行以上 2 条命令？[Y/n]
      Claude Code：已签发 MacBook · Claude Code · 自检通过 · 已接入
      Codex：已签发 MacBook · Codex · 自检通过 · 已接入
完成。在 Claude Code 里输入 /mcp__saveslot__overview（斜杠菜单里显示为 /saveslot:overview）；在任何宿主里也可以问一句"saveslot 里有什么"。
```

（宿主命令的确切写法以实现时的实测为准。）

你要做的只有选择和一次同意：用哪个模板、接哪些宿主，每一项都有默认值；然后对"将要在宿主那一侧执行的命令"回答一次。这是接入的设计要求，以后新增的接入方式都按它检查：接入的每一步手动操作都会筛掉一部分人，而这些步骤里没有一步需要人的判断，人要判断的只有"接不接、给多大权限"。同意的对象是一份逐字列出的清单，这同时是安全上的好处。

几点要知道：

- **先同意、后签发。** 你在第 5 步拒绝，就什么都不签发、什么宿主都不动。令牌不显示在终端上，也不进 shell 历史。
- **每个宿主一个连接实例**，默认名字是"主机名 · 宿主名"。不让几个宿主共用一个连接实例，否则"谁读过、谁写的"分不开。
- **可以重复运行。** 每一步先看状态再决定做不做：已初始化就跳过，已有 slot 就不再问模板，宿主里已有 saveslot 的条目就不再签发。所以第二次运行只会补上没做完的步骤、接上新装的宿主。
- **只编排已有的命令**，不多做任何事：它调用的就是下面分步做的那几条命令。它不装开机自启（宿主启动时会自动拉起服务），只在最后提示 `saveslot service install`。
- **非交互环境里**（比如脚本），不给 `--yes` 就什么都不执行；给了 `--yes`，没在参数里指定的选择一律按"不做"处理：没给 `--template` 就不建 slot，没给 `--host` 就不接任何宿主。没有人看着的时候，少做比多做安全。
- **它签发的连接实例看得到全部 slot。** 要限定范围、或给不同宿主不同权限，用 `saveslot connect` 单独接。

### 为什么不直接改宿主的配置文件

saveslot 只执行宿主自己提供的添加命令（`claude mcp add`、`codex mcp add`），从不直接编辑 `~/.claude.json`、`~/.codex/config.toml` 这类文件，也不往 `CLAUDE.md`、`AGENTS.md` 里写字。理由有四条：

1. **格式和位置归宿主所有，而且在变。** 宿主自己的命令跟着宿主走；saveslot 自己写文件，就得追着每个宿主的每次改动。
2. **那些文件里不只有 saveslot。** 里面有你别的 MCP 服务、别的密钥和设置。saveslot 写错了（宿主正在运行时并发改写、丢了注释、写了一半），坏掉的是和它无关的东西，你还很难知道是谁干的。指令文件更敏感：那是你亲手写的、直接决定模型怎么做事的文字。
3. **同意的对象能逐字展示。** 展示给你的就是将要执行的命令，它写在宿主的文档里，你自己也能敲；"将修改某某文件的某一段"做不到同样确定。
4. **撤销是对称的。** 用宿主的移除命令就能完整撤掉，不留痕迹。

代价是没有添加命令的宿主（Cursor、Claude 桌面端）只能手动粘贴配置，这是上面那条设计要求的已知例外。

### 分步做

`setup` 调用的就是下面这几条命令，评测和脚本继续用它们；想看清每一步，也可以自己一条条做：

```
安装 → saveslot init → saveslot start → 建一个 slot → saveslot connect → 把打印出的命令贴进终端（或加 --apply）→ 在 Agent 里问一句 → saveslot reads 验证
```

**① 安装。** 第一版发布为一个 npm 包 `@fluxvita/saveslot`，里面有命令行工具和 saveslot 服务（`npm install -g @fluxvita/saveslot`）。npm 是 JavaScript 生态的包管理器，安装这个包需要电脑上先有 Node 运行时。不需要另装数据库。Linux 上 Node 装在系统目录时，普通用户全局安装会因为没有写权限而失败，这时给 npm 设一个用户自己的安装目录（06-cli 第 3 节「安装的前提」）。

独立的可执行文件和桌面安装包（不要求用户先装 Node）要等一项打包实验的结论，第一版不保证有。

**② 初始化。** `saveslot init` 在用户主目录下建一个 `~/.saveslot/` 目录：

| 子目录 | 放什么 |
|---|---|
| `data/` | 数据目录：这个用户的全部数据。初始化时已写入日志的第一条事件 |
| `control/` | 控制面，是几个文件：凭证的哈希、租户目录、登记存储（删除登记、最高序号、恢复次数、"恢复进行中"与"导入进行中"标记）、句柄签名密钥 |
| `credentials/` | 用户会话的令牌，只有当前系统用户可读 |

配置文件 `config.toml` 不由 `init` 生成：没有它时每一项都取默认值；要改就在 `~/.saveslot/` 下自己建这个文件，用 `saveslot config get` 查看每一项现在的值与来源。读取记录的落盘间隔这类数值在这里（如 `read_log.flush_seconds`）。文件里有写错的地方时服务不启动，并指出是哪一项。

数据目录不要放在 iCloud Drive、Dropbox 这类同步盘里，同步软件会在 saveslot 不知情时改动文件；saveslot 检测到时会警告。

**③ 启动。** `saveslot start` 在后台启动服务。也可以设成开机自启。

**④ 建第一个 slot。** slot 需要一份 schema。命令行工具自带几份现成的模板（跑步记录、预算、日常支出），选一个就能建：

```
$ saveslot slot create ledger --template spending --timezone Asia/Shanghai
```

本书那本账就是用这份模板建的。建 slot 的同时，saveslot 会写下这个 slot 的默认策略（第 9 章）。

也可以让 Agent 起草一份 schema 文件再用它建，或者给某个 Agent 加上 `saveslot.schema` 权限让它直接建。

**⑤ 签发凭证并接入 Agent。**

```
$ saveslot connect claude-code --name "MacBook · Claude Code"
```

这条命令做三件事：签发一个连接实例；用新令牌自检一次，确认能读到 slot；打印一条宿主自己的添加命令。把打印出的命令贴进终端执行，Agent 那边就配置好了；或者重跑这条命令并加 `--apply`，由 saveslot 代为执行那条宿主命令。两种做法都不直接改宿主的配置文件。自检没通过时，刚签发的连接实例会被立即吊销，不显示令牌。`--apply` 执行宿主命令失败时，连接实例保留，命令照常打印出来让你自己执行。

令牌只显示这一次，而且会留在几个地方：贴进终端的命令进了 shell 历史；宿主命令执行期间，它在进程参数里，本机其他用户用 `ps` 看得到；最后它住在宿主的配置文件里。只用本机的套接字文件时，这些对别的系统用户无害（他们连不上）。`setup` 不在终端上显示令牌，也不进 shell 历史。

`connect` 还可以带 `--scope`（第 4 节）和 `--slots`（限定 slot 范围）。再接一个 Agent 就再执行一次，换个名字。末尾会提示一行"可选：saveslot snippet <宿主>"（第 2 节）。

**⑥ 验证。** 在 Agent 里问一句"saveslot 里有哪些 slot"，然后：

```
$ saveslot reads --connection "MacBook · Claude Code" --since 10m
```

看到一条自检之外的读取记录，才说明 Agent 确实经这个连接实例连上了。在 Claude Code 里输入 `/mcp__saveslot__overview` 也一样：它会让 Agent 去读目录，产生一次这样的读取。

出了问题，先跑 `saveslot doctor`。它逐项检查：服务在运行、套接字和凭证文件的权限、数据目录不在同步盘里、单写者锁、版本一致、有没有逾期没物理删除的删除、各宿主里 saveslot 的条目指向的可执行文件还在不在（用宿主自己的查看命令，不读它的配置文件）。每项结果是"通过 / 不通过 / 提醒"。三项只给提醒、不算不通过：系统时钟比日志末端落后 5 分钟以上；某个宿主里的 Agent 还没有经 saveslot 读过任何东西（如果已经让它记过而没有记上，多半是宿主没有允许它使用 saveslot 的工具，提醒里写着放行办法；刚接上还没用过时也会出现，用过一次就没有了）；**数据规模**，列出行数超过舒适线或实测线的表，以及事件总数、数据目录大小、最近一次打开数据的耗时，和实测范围对照（第 10 章第 5 节"关于数据量与日志的大小"）。

**服务器模式的上手**：`saveslot setup --profile <名字>` 走同一条线，步骤换成——没登录就先 `saveslot login`（SSH 里没有浏览器时加 `--device`）；没有 slot 就按模板建；对选中的宿主执行远程形式的添加命令。这条路上没有令牌，凭证由宿主自己走 OAuth 取得，授权页上的那次"授权"就是那一次同意（第 2 节），所以这里不选权限。能自动接的只有 Claude Code 和 Codex，其余宿主用 `saveslot connect <宿主> --profile <名字>`。宿主里已经有一条 `saveslot`（比如本机那条）时不会被覆盖，setup 会给出移除它的命令。它不切换当前使用的 profile，最后会提示 `saveslot profile use <名字>`。自部署还需要先在服务器上用 `saveslot server init` 初始化、`saveslot server user add` 建账户。

规格：[`../spec/06-cli.md`](../spec/06-cli.md) 第 3 节。

## 6. 导出、备份与恢复

### 导出：把数据带走

`saveslot export` 导出的是**这个用户的整条日志**。不是数据库文件，也不是表的快照。

文件的形状很简单：每行一个 JSON 对象。第一行是一份清单（哪个租户、事件格式的版本、导出到第几号事件、共多少条）；之后每行一条事件，里面是事件头和它的各个内容块。每个内容块处于三种状态之一：在（内容加校验和）、已移除（只记是哪条墓碑移除的）、待删除（占位）。格式的完整定义在事件格式规格里，不依赖 saveslot 的代码也能读懂：逐行核对事件头的哈希链、核对每块的校验和，就能验证这份导出是完整的。

因为日志是唯一事实来源，拿着这份导出，在任何一个后端上从头重放，就能得到同样的表。这是"数据归用户、能带走"的技术含义。

三点细节：

- **读取记录不在导出里。** 它不是日志的一部分。
- **宽限期内待删除的内容默认不导出。** 相应位置换成一个占位。否则用户刚要求删掉的东西，会留在导出文件里。确实需要时可以显式要求包含，命令行会再确认一次。
- **只有用户会话能导出。**

"导出确实能重放"这句承诺由测试检验：导出、重放进一个空库、和原来的表逐行比对，两种数据库后端交叉各做一遍（第 12 章）。

### 给导出文件加口令

导出文件一离开 saveslot，就不受任何保护了：它可能被放进网盘、拷到移动硬盘、跟着备份走、被转发。所以导出时可以加口令：

```
$ saveslot export --encrypt -o saveslot-2026-11.ndjson.age
口令不会被保存，忘了就无法解开这份导出。
输入口令：
再输入一遍：
已导出 1284 条事件，末尾 seq 1311，不含待删除内容；已用口令加密（age v1）
下次续传用 --after-seq 1311；解密：age -d -o export.ndjson saveslot-2026-11.ndjson.age
```

- **用公开的格式。** 加密用的是 age，一种公开的文件加密格式；解密用任何 age 工具都行，不需要 saveslot。不自造格式：项目是开源的，私有格式藏不住什么，只多出一个别人不认识的文件。导出文件本身的格式不变，加密只是在外面包了一层。
- **口令怎么给。** 默认从终端读，不回显，输两遍。脚本用 `--passphrase-file`（文件权限要是 0600）；密码管理器用 shell 的进程替换交给它：`--passphrase-file <(pass show saveslot)`。没有在命令行参数里直接写口令的办法，也不读环境变量：参数会进 shell 历史，执行期间别的用户用 `ps` 看得到。
- **saveslot 不保存口令，忘了就解不开。** 短于 12 个字符时警告一次。
- **防什么、不防什么。** 防的是导出文件离开这台机器之后被别人拿到。不防导出那一刻本机上与你同权限的程序（它们本来就读得到数据目录），也帮不了太弱或忘了的口令。它不是存储加密：saveslot 的存储本身不做应用层加密（第 10 章第 5 节）。
- **只在命令行里。** HTTP 的导出端点不加密：在请求里传口令，等于把口令交给本来就看得到明文的服务端。直接调 HTTP 的人，把响应接到任何 age 工具上即可。

### 导入：装进一个空的账户

`saveslot import` 把一份导出装进一个**空的租户**：日志里只有初始化时写下的第一条事件，没有任何数据。典型的用途是从本机模式搬到服务器模式：

```
源头停止写入 → saveslot export → 在目标处 saveslot import → 在目标处重新接入各个 Agent → 停用源头
```

- **原样装进去，不重新执行。** 导入把导出里的事件逐条原样追加，交给 `apply` 重放，得到的是同一条日志，`verify` 照样对得上原来的链。不逐条重新执行写入：那样会重新判定、重新分配序号和 ID，得到的就不是同一条日志了。
- **整体要么完成，要么目标仍是空的。** 中途断了、崩了，重试是安全的。导入期间这个租户不能读写。
- **原来的凭证一律停用。** 导入之前的用户和仍有效的连接实例都停用（已吊销的保持吊销），历史里照旧显示它们的名字，标"已停用"或"已吊销"；所有接入要在目标处重新签发。导入结束时会提示用 `saveslot connect` 重新接入。
- **加了口令的导出，由命令行在本机解开再上传**（口令的给法同导出）；服务端不接收口令。
- **确认之前会显示**原租户、事件数、导出的时刻，以及"这份导出之后在原处做的删除不在其中"。结束时列出停用了多少主体、立即执行了多少项宽限期内的删除，以及带不过来的东西：读取记录、凭证、外部文件（第 10 章第 5 节"关于导入"）。
- **旧的版本标记还能用一部分。** Agent 手里导入之前读到的 `ver` 带回来时，导出点及以前的部分照它自己的序号判冲突，之后的部分保守处理（规则同下面的恢复）。

只能导入到空的租户，不能和已有的数据合并：合并要回答两条日志的序号怎么交错、同名 slot 怎么办、两边的删除登记怎么并，那是多节点的问题，放在后续。

### 备份

备份和导出是两回事：导出是用户带走数据的方式，备份是防止数据丢失的运维手段，备份的是数据库本身。

- 服务器模式：云服务由我们做，自部署由部署方做。
- 本机模式：saveslot 自己不做备份。数据目录会被 Time Machine 这类系统级备份带上。

### 恢复之后为什么要走恢复流程

从备份恢复，等于把数据库拨回到过去的某个时刻。对 saveslot 来说这有两个问题。

**问题一：删除会复活。** 用户周一确认删除了一句话，周二到期物理删除。周三数据库坏了，从上周日的备份恢复。上周日的数据里，那句话还在，日志里也没有周一那次删除。

解法是**删除登记**：每次删除确认时，除了在租户的日志里记事件，还在控制面（与租户数据分开存放）记一笔，只记是哪些位置被删了，不记内容。恢复之后，saveslot 先按这份登记把该删的再删一遍，然后才对外服务。登记和日志怎么保持一致、各种崩溃时机下怎么对账，见第 8 章第 9 节。

**问题二：序号会重用，旧的版本标记会被认错。** 备份之后又写了 #501 到 #600，恢复以后日志只到 #500。如果接着从 #501 开始编号，新的 #501 和原来那条 #501 就是两件不同的事却用了同一个号；某个 Agent 手里还拿着恢复之前读到的 `ver`，会被误当成当前版本。

解法有两条：

- 恢复后追加一条"恢复"事件，之后的序号从控制面记下的最高序号之后接着编，留出的空档由这条事件说明。最高序号是隔一阵推进一次的（不是每次写入都记），所以两次推进之间的少量序号仍可能被再用一次；下一条正是为了兜住这种情况。
- 控制面记着这个租户恢复过几次，这个次数编进 `ver`、事项版本和句柄里。这就是 `v21.0` 里小数点后面那个数。恢复之前拿到的事项版本和句柄一律被拒绝。恢复之前拿到的 `ver` 分两种：它指向恢复点及以前的位置时，那一段日志在两条时间线里一模一样，就按它自己的序号判冲突；指向恢复点之后的位置时，那一段可能已经丢了，同一个序号可能是另一次写入，就当它读到的是恢复点，保守地判。恢复过两次以上、隔了一次恢复的旧 `ver` 一律按后一种处理。

所以恢复不是"把库换回去就行"，必须走恢复流程：

| 模式 | 怎么触发 |
|---|---|
| 服务器模式 | 运维命令 `saveslot server restore --tenant <租户>`（或 `--user <账户名>`） |
| 本机模式 | `saveslot start --restored` |

恢复流程做的事依次是：在控制面做一个"恢复进行中"的标记并把恢复次数加一；打开租户；追加一条"恢复"事件；按删除登记补删；补做已经到期的物理删除；核对；清掉标记；对外服务。

**恢复流程中途被打断也没关系。** 那个"恢复进行中"的标记全部做完才清掉。之后每次启动都先看它：标记还在，就接着把流程做完，再对外服务，不管这次启动带没带恢复参数。每一步重做一遍结果不变。补删没做完之前，被删的内容是读得到的，所以这期间不对外服务。

没走流程就直接换了库，saveslot 有两道兜底：

- 打开时发现日志末尾的序号比控制面记的最高序号还低，说明被拨回过。
- 把删除登记和日志对一遍，发现了正常运行中不可能出现的组合（比如登记说某次删除待执行，日志里却根本没有它）。

发现之后，服务器模式下拒绝对外服务、提示走恢复流程；本机模式下自动走恢复流程（本机只有一个用户，没有运维，拒绝服务没有意义）。兜底发现不了全部情形：回退的幅度很小、期间又没有删除时看不出来。所以恢复应当一律显式触发。

### 恢复流程管不到的情形

删除登记要起作用，前提是它没有跟着数据一起被拨回去。

- **本机模式的默认布局下，数据目录和控制面都在 `~/.saveslot/` 里。** 系统级备份通常把两者一起恢复，登记也回到了过去。这时 saveslot 补不了，也发现不了。只有把数据目录另放别处、并且只恢复了数据目录时，补删才有效。另放别处的办法是初始化时指定：`saveslot init --data-dir <路径>`。
- **服务器模式下控制面的库和租户的库被一起恢复**，同样发现不了。
- **极窄的窗口里，一次撤回可能丢。** 撤回删除的事务已经提交、登记还没来得及改成"已撤回"时进程崩溃，随后又恰好恢复到了撤回之前的备份：那次撤回丢失，删除照常执行。这和"备份之后的任何写入都随恢复丢失"是同一类损失，方向是多删。

第 10 章把这些和其他"不保证的事"列在了一起。

### 升级 saveslot 的版本

**从 0.1.0 起，升级 saveslot 不会让已有数据打不开**：新版本能打开此前任何一个发布的版本写下的数据，不用你先导出、再导入；配置文件和已经发出去的凭证也照常可用。这说的是数据，不是接口：1.0 之前小版本之间命令和接口可能有不兼容的变化，发布说明里会写明。

装了新版之后第一次打开数据时，saveslot 检查存储的格式版本：比程序认识的低，就自动把它升级到当前格式；比程序认识的高（用新版写过、又换回了旧版程序），拒绝打开并提示升级，不冒险去写。（目前只有一个格式版本。原地升级的机制 0.2.0 起已经有了，升级的步骤还没有：第一次改格式的版本连同那一步一起发。0.1.0 之前开发期的数据不在承诺之内，需要重新初始化。）日志本身不用转换：新版内核必须能重放所有旧格式的事件，这是事件格式"只增不改"的含义。

规格：[`../spec/02-architecture.md`](../spec/02-architecture.md) §8「格式版本、导出、导入与恢复」；[`../spec/03-data-model/03-deletion.md`](../spec/03-data-model/03-deletion.md)「删除之后」；导出加密与导入的命令见 [`../spec/06-cli.md`](../spec/06-cli.md) 4.8；导入的规则见 [`../spec/04-contract.md`](../spec/04-contract.md) 第 17 节。

## 7. 第一版不做什么

与部署和接入有关的：

| 不做 | 第一版的替代 |
|---|---|
| 本地和云端各存一份并同步；多设备同步；离线写入 | 多设备共用就都连同一个服务器模式的 saveslot |
| 合并导入（把导出装进已有数据的账户）、本机与服务器之间的持续同步 | 只能导入到空的租户：一次性地从一处搬到另一处（第 6 节；随服务器模式一起发布） |
| 图形界面的 App | 命令行，或交代给 Agent |
| 开发者 SDK（把 saveslot 嵌进别人的 Agent） | 只有 saveslot 服务这一种形态 |
| 表级、字段级的数据权限 | 四种动作权限 × slot 范围（slot 范围随服务器模式一起发布） |
| 多人共享的 slot | 一个租户就是一个用户 |
| 加密 | saveslot 不做应用层加密；云服务的存储在基础设施层加密，运营方读得到；自部署、本机由磁盘加密决定。删除靠物理删除。导出文件可以用口令加密（第 6 节） |
| 弹窗确认（MCP 的 elicitation） | Agent 在对话里征得用户同意后再调用 |
| 删除整个账号、整个 slot | 逐条隐私删除；本机模式删掉数据目录与配置目录（第 8 章第 8 节） |
| 连接器（定时同步外部系统的程序） | 不属于 saveslot；第一版提供它要的凭证范围、来源键与重发识别（第 2 节） |
| 本机模式的 Windows 支持 | macOS、Linux |
| saveslot 自己调用模型 | 理解和抽取都由用户的 Agent 做 |

发布顺序上，本机模式先发，服务器模式（云服务和自部署一起）随后。

完整范围见 [`../spec/07-scope-v1.md`](../spec/07-scope-v1.md)；后续规划见 [`../spec/01-positioning.md`](../spec/01-positioning.md)「后续规划」。

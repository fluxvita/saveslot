# 11 · 部署与接入

这一章回答实际使用的问题：saveslot 装在哪、Agent 怎么连上它、人怎么操作它、凭证怎么管、数据怎么带走、备份恢复后要注意什么。

## 1. 两种运行模式

第一版有两种运行模式。两种都是**单节点**：一个用户的数据只在一个地方。

| | 本机模式 | 服务器模式 |
|---|---|---|
| 装在哪 | 用户自己的电脑 | 一台服务器：我们运营的云服务，或用户自己部署 |
| 谁能连 | 只有这台机器上的 Agent 和程序 | 任何地方的 Agent，经网络 |
| 数据库 | PGlite（嵌在 saveslot 进程里，数据在本机的一个目录） | 原生 PostgreSQL，每个用户一个独立的 database |
| 用户数 | 一个 | 多个，互相隔离 |
| 适合 | 只在一台电脑上用；数据不想离开本机 | 多台设备共用；要接云端的 Agent；希望全天在线 |

两种模式跑的是同一个内核、同一套规则。核心能力不会只在某一种里有。

### 容易误解的一点：单节点不等于"本地和云端不能共用"

只要部署了服务器模式，本机的编码 Agent、另一台电脑上的 Agent、云端跑的 Agent 都连同一个服务，读写的是同一份数据。这是第一版让多设备共用数据的办法。

第一版不做的是另一件事：**同一份数据同时放在本机和云端两个地方，两边互相同步。** 由此带来的两点实际影响：

- 连服务器模式时，断网就用不了。
- 本机模式的数据只有本机能访问。本机模式和服务器模式是两份互不相通的数据，第一版没有在它们之间同步或迁移的功能。

### 云服务和自部署的差别

服务器模式的两种部署是同一套代码、同一组配置项，差别只在部署方是谁：

| 方面 | 我们的云服务 | 用户自部署 |
|---|---|---|
| 人的账户 | 我们的账户系统 | 内置的本地账户：由部署的人用运维命令创建，不开放注册 |
| 对外地址与证书 | 我们的域名 | 部署方自己提供 |
| 密钥保管 | 我们 | 部署方 |
| 限流与配额 | 开 | 默认关，可配置 |
| 备份与恢复 | 我们做 | 部署方做，恢复后必须走恢复流程（见第 6 节） |
| 规模 | 多组服务器 | 一个进程、一个数据库集群即可 |

### 平台支持

本机模式第一版只支持 macOS 和 Linux，Windows 放在后面。

## 2. Agent 怎么连

Agent 经 **MCP** 连 saveslot（第 1 章介绍过：Agent 调用外部工具的一种通用协议，Claude Code、Codex 这类 Agent 都支持）。接上以后，Agent 的工具列表里会多出一组 `saveslot_` 开头的工具。

### 第一版开放的 10 个工具

| 工具                      | 读 / 写 | 做什么                                                |
| ----------------------- | ----- | -------------------------------------------------- |
| `saveslot_catalog`      | 读     | 看有哪些 slot、表、字段、单位                                     |
| `saveslot_query`        | 读     | 按条件查数据，返回每行的 `ver`                                 |
| `saveslot_sql`          | 读     | 只读 SQL，用于关联和聚合                                     |
| `saveslot_history`      | 读     | 看一样东西怎么变成现在这样，或某个过去时刻的样子                           |
| `saveslot_sources`      | 读     | 列出、搜索、读取源数据；删除前的影响预览也在这里（它的 `deletion_preview` 模式） |
| `saveslot_pending`      | 读     | 列出待处理事项，看某一项的详情                                    |
| `saveslot_write`        | 写     | 写入：新增、变更、纠错、撤销                                     |
| `saveslot_resolve`      | 写     | 处理一个待处理事项                                          |
| `saveslot_schema_draft` | 写     | 提交 schema 草稿（建 slot、改表结构）                             |
| `saveslot_delete`       | 写     | 执行一次已预览的删除                                         |

完整设计里还有两个与"重新抽取"有关的工具，随那部分功能后做。

Agent 调用工具后收到的是一段文本。它长什么样，前面有三份实例：第 2 章第一步的写入回执、第三步"成为候选"的回执，第 6 章第 3 节的查询结果。

几条设计上的考虑，接入方值得知道：

- **按最差的 Agent 设计。** 只依赖"调用工具、拿回文本"这一最基本的能力。Agent 的宿主不支持弹窗确认、不支持结构化结果，流程照样走得通。
- **工具列表按权限裁剪。** 一个只有读权限的连接实例，工具列表里根本没有写工具。六个读工具总在，因为每个连接实例都有读权限。
- **标记一定出现在文本里。** "有争议""有待确认的改动"这些标记在契约里是结构化字段，渲染成文本时一个都不会漏。有些宿主只把文本交给模型，所以不能只放在结构化结果里。
- **ID 和版本标记一律完整给出。** 模型要原样带回它们，所以文本里不缩写。
- **读回来的文字包着不可信边界。** 见第 10 章第 6 节。
- **结果有长度预算。** 一个工具结果的文本最多 10 万字符。能翻页的结果（查询的行、事项列表、历史）在预算处截断，截断点就是下一页的起点，不漏行；不能翻页的结果超了预算会报错并提示怎么缩小，不会悄悄截掉一半。
- **调用了第一版还没实现的功能**，统一得到 `not_in_this_version` 这个错误，写明是哪个参数或操作。
- **管理类操作不进 MCP。** 签发凭证、导出、读取审计、日志校验只给人用，走命令行或 HTTP。

### 本机模式怎么接

本机的 saveslot 服务不监听网络端口，只监听一个本机的套接字文件（unix socket），文件权限只允许当前系统用户访问。好处是别的用户连不上、网络上的人连不上、浏览器里的网页也打不到它。

Agent 的宿主一般不会直接连套接字文件，所以 saveslot 提供一个小的转发程序 `saveslot mcp`：宿主把它当作一个普通的 MCP 服务启动，它把消息转给本机的 saveslot 服务。

```
Claude Code ──启动──▶ saveslot mcp ──套接字──▶ saveslot 服务 ──▶ 数据目录
Codex       ──启动──▶ saveslot mcp ──套接字──▶     （同一个进程）
```

两个 Agent 各启动一个 `saveslot mcp`，但背后是同一个 saveslot 服务进程、同一份数据。如果 saveslot 服务没在运行，`saveslot mcp` 会先把它拉起来。

### 服务器模式怎么接

Agent 的宿主直接走远程 MCP，地址形如 `https://<域名>/mcp`。授权用 OAuth：宿主打开授权页，用户在页面上给这次接入起名字、选权限，授权完成后这个 Agent 就成了一个连接实例。

### 没有 Agent 的程序：HTTP

脚本、自己写的程序可以直接调 HTTP 接口，路径以 `/v1` 开头，请求和回执就是契约里定义的 JSON。HTTP 和 MCP 由同一份契约生成，能做的事基本一样；差别主要是 HTTP 不做文本渲染、不按长度截断结果，并且开放管理类操作。

写脚本时要注意一点：写入返回成功，不等于"已生效"。回执里的 `status` 可能是 `saved`（已保存），也可能是 `pending`（已记下但未生效，比如成了冲突候选）。脚本必须看这个字段。

规格：[`../spec/05-surfaces.md`](../spec/05-surfaces.md)。

## 3. 人怎么用：命令行

第一版不做图形界面的 App。人要做的事都经**命令行工具** `saveslot` 来做，或者交代给 Agent 去做。

人用命令行做的事：

| 做什么 | 命令 |
|---|---|
| 安装、启动、停止本机服务 | `saveslot init`、`saveslot start`、`saveslot stop`、`saveslot status` |
| 建 slot | `saveslot slot create` |
| 给 Agent 签发、查看、吊销凭证 | `saveslot connect`、`saveslot connections list / revoke` |
| 处理待处理事项 | `saveslot pending`、`saveslot pending show`、`saveslot pending resolve` |
| 删除与撤回 | `saveslot delete`、`saveslot delete cancel` |
| 查数据、看历史 | `saveslot query`、`saveslot history`、`saveslot sql`、`saveslot sources` |
| 看谁读过什么 | `saveslot reads` |
| 校验、对拍 | `saveslot verify`、`saveslot verify --replay` |
| 导出 | `saveslot export` |

三点设计值得知道：

- **命令行不做业务写入。** 没有 `saveslot write`。写入需要把一句话变成意图、行、值和证据，这是 Agent 的事。人想改数据，对 Agent 说，那句话就是证据。
- **命令行不直接碰数据目录。** 除了初始化那一次，所有命令都经 saveslot 服务。这样单写者和读取留痕都不会被绕过。
- **确认时绑定的是人刚看到的那一份。** 处理事项时，命令行先把详情展示出来，再用展示时拿到的事项版本去执行；删除时用的是刚展示的那份预览的句柄。删除的确认要求输入完整的 `delete`，不接受按一下 `y`。

规格：[`../spec/06-cli.md`](../spec/06-cli.md)。

## 4. 凭证、连接实例与权限

### 两类凭证

| 凭证 | 谁持有 | 能做什么 |
|---|---|---|
| **用户会话** | 人 | 一切，包括签发和吊销连接实例、读取审计、导出 |
| **连接实例** | 一个 Agent 或一个脚本 | 按签发时给的权限 |

每个 Agent 的每次接入都有自己的连接实例，由用户命名，建议写成"设备 · Agent"，例如"MacBook · Claude Code"。这个名字会出现在历史、事项的发起者和读取审计里。第 2 章的 A 和 B 就是两个连接实例。

给每个 Agent 单独的凭证，是"谁做的"能说清的前提：两个 Agent 共用一个凭证，它们的读写就分不开了。

### 四种权限

权限在签发连接实例时选定，按动作分四种，规格里叫 scope：

| 权限 | 允许 | 默认 |
|---|---|---|
| `saveslot.read` | 全部读操作，含删除预览 | 每个连接实例都必须有 |
| `saveslot.write` | 写入；处理与写入有关的事项 | 给 |
| `saveslot.schema` | 提交 schema 草稿；处理 schema 变更事项 | 不给，要显式勾选 |
| `saveslot.delete` | 执行删除；撤回删除 | 不给，要显式勾选 |

命令行签发时用 `--scope` 调整。两种写法，不能混用：

- 在默认（读 + 写）上增减：`--scope +schema`、`--scope +delete`、`--scope -write`。只读的连接实例就是 `--scope -write`。
- 完整列出：`--scope read,write,schema`，列出的就是全部。

去掉读权限是用法错误：没有读权限的连接实例什么都做不了，也没法先读再写。

需要知道的限制：

- **第一版的权限只按动作分，不按数据分。** 有读权限的连接实例能读这个用户的所有 slot。"健康数据只给某个 Agent 看"这类按数据的授权是后续版本的事。
- **权限签发后不能改。** 要改就吊销重签。
- **令牌只显示一次。** saveslot 只保存它的哈希。丢了就吊销重签。
- **吊销立即生效。** 令牌外泄时这是收回权限的手段。吊销只是让这个凭证之后的请求被拒，不删除任何东西：它写过的数据还在，记的仍是它的名字，显示时名字后标"已吊销"；它发起而还没处理的事项（冲突、待确认等）照常留着，由用户或别的有权限的连接实例处理。

### 只有用户会话能做的事

签发、改名、吊销连接实例；查看读取审计；日志校验与对拍；导出。

理由很直接：能签发凭证的 Agent 可以给自己任意权限；审计的对象正是各个 Agent，被审计的一方不该能读全部审计；导出是一次拿走全部数据，这是用户的权利，不是 Agent 的。

### 本机上的一个边界

本机模式下，用户会话的凭证是用户主目录里的一个文件。一个有 shell 权限的 Agent（能在终端里执行命令的那种）读得到它，也能直接运行 `saveslot` 命令，这时它做的事都记在用户名下，和真人操作分不开。saveslot 防不住这一类程序。

如果希望有 shell 的 Agent 也留下自己的痕迹，给它一个连接实例令牌，让它带着这个令牌运行命令行工具。

## 5. 上手流程（本机模式）

从零到第一个 Agent 能用，是一条线：

```
安装 → saveslot init → saveslot start → 建一个 slot → saveslot connect → 把打印出的命令贴进终端 → 在 Agent 里问一句 → saveslot reads 验证
```

**① 安装。** 第一版发布为一个 npm 包 `@fluxvita/saveslot`，里面有命令行工具和 saveslot 服务（`npm install -g @fluxvita/saveslot`）。npm 是 JavaScript 生态的包管理器，安装这个包需要电脑上先有 Node 运行时。不需要另装数据库。

独立的可执行文件和桌面安装包（不要求用户先装 Node）要等一项打包实验的结论，第一版不保证有。

**② 初始化。** `saveslot init` 在用户主目录下建一个 `~/.saveslot/` 目录：

| 子目录 | 放什么 |
|---|---|
| `data/` | 数据目录：这个用户的全部数据。初始化时已写入日志的第一条事件 |
| `control/` | 控制面，是几个文件：凭证的哈希、租户目录、登记存储（删除登记、最高序号、恢复次数、"恢复进行中"标记）、句柄签名密钥 |
| `credentials/` | 用户会话的令牌，只有当前系统用户可读 |
| `config.toml` | 配置，用 `saveslot config get / set` 读写。读取记录的保留期、落盘间隔这类数值也在这里（如 `read_log.retention_days`） |

数据目录不要放在 iCloud Drive、Dropbox 这类同步盘里，同步软件会在 saveslot 不知情时改动文件；saveslot 检测到时会警告。

**③ 启动。** `saveslot start` 在后台启动服务。也可以设成开机自启。

**④ 建第一个 slot。** slot 需要一份 schema。命令行工具自带几份现成的模板（跑步记录、预算、日常支出），选一个就能建：

```
$ saveslot slot create ledger --template spending --timezone Asia/Shanghai
```

本书那本账就是用这份模板建的。建 slot 的同时，saveslot 会写下这个 slot 的默认策略（第 9 章）。

也可以让 Agent 起草一份 schema 文件再用它建，或者给某个 Agent 加上 `saveslot.schema` 权限让它直接建。

**⑤ 签发凭证并接入 Agent。**

```
$ saveslot connect claude-code --name "MacBook · Claude Code"
```

这条命令做三件事：签发一个连接实例；用新令牌自检一次，确认能读到 slot；打印一条接入命令。把打印出的命令贴进终端执行，Agent 那边就配置好了。saveslot 不会自己去改 Agent 的配置文件。自检没通过时，刚签发的连接实例会被立即吊销，不显示令牌。

再接一个 Agent 就再执行一次，换个名字。

**⑥ 验证。** 在 Agent 里问一句"saveslot 里有哪些 slot"，然后：

```
$ saveslot reads --connection "MacBook · Claude Code" --since 10m
```

看到一条自检之外的读取记录，才说明 Agent 确实经这个连接实例连上了。

服务器模式的上手不同之处：用 `saveslot login` 登录取得用户会话；Agent 一侧直接填远程 MCP 地址并走 OAuth 授权。自部署还需要先在服务器上用 `saveslot server init` 初始化、`saveslot server user add` 建账户。

规格：[`../spec/06-cli.md`](../spec/06-cli.md) 第 3 节。

## 6. 导出、备份与恢复

### 导出：把数据带走

`saveslot export` 导出的是**这个用户的整条日志**。不是数据库文件，也不是表的快照。

文件的形状很简单：每行一个 JSON 对象。第一行是一份清单（哪个租户、事件格式的版本、导出到第几号事件、共多少条）；之后每行一条事件，里面是事件头和它的各个内容块。每个内容块处于三种状态之一：在（内容加校验和）、已移除（只记是哪条墓碑移除的）、待删除（占位）。格式的完整定义在事件格式规格里，不依赖 saveslot 的代码也能读懂：逐行核对事件头的哈希链、核对每块的校验和，就能验证这份导出是完整的。

因为日志是唯一事实来源，拿着这份导出，在任何一个后端上从头重放，就能得到同样的表。这是"数据归用户、能带走"的技术含义。

三点细节：

- **读取记录不在导出里。** 它不是日志的一部分。
- **宽限期内待删除的内容默认不导出。** 相应位置换成一个占位。否则用户刚要求删掉的东西，会留在导出文件里。确实需要时可以显式要求包含，命令行会再确认一次。
- **只有用户会话能导出。**

**第一版只做导出，不做导入。** 也就是保证数据能带走，但没有"把导出文件装进另一个 saveslot"的用户命令。做成命令就要处理旧凭证怎么对应、和已有数据怎么合并，这些随多节点一起放到后续。"导出确实能重放"这句承诺，第一版由测试来检验：导出、重放进一个空库、和原来的表逐行比对，两种数据库后端交叉各做一遍（第 12 章）。

### 备份

备份和导出是两回事：导出是用户带走数据的方式，备份是防止数据丢失的运维手段，备份的是数据库本身。

- 服务器模式：云服务由我们做，自部署由部署方做。
- 本机模式：saveslot 自己不做备份。数据目录会被 Time Machine 这类系统级备份带上。

### 恢复之后为什么要走恢复流程

从备份恢复，等于把数据库拨回到过去的某个时刻。对 saveslot 来说这有两个问题。

**问题一：删除会复活。** 用户周一确认删除了一句话，周二到期物理删除。周三数据库坏了，从上周日的备份恢复。上周日的数据里，那句话还在，日志里也没有周一那次删除。

解法是**删除登记**：每次删除确认时，除了在租户的日志里记事件，还在控制面（与租户数据分开存放）记一笔，只记是哪些位置被删了，不记内容。恢复之后，saveslot 先按这份登记把该删的再删一遍，然后才对外服务。登记和日志怎么保持一致、各种崩溃时机下怎么对账，见第 8 章第 9 节。

**问题二：序号会重用，旧的版本标记会被认错。** 备份之后又写了 #501 到 #600，恢复以后日志只到 #500。如果接着从 #501 开始编号，新的 #501 和原来那条 #501 就是两件不同的事却用了同一个号；某个 Agent 手里还拿着恢复之前读到的 `ver`，会被误当成当前版本。

解法有两条：

- 恢复后追加一条"恢复"事件，之后的序号从控制面记下的最高序号之后接着编，留出的空档由这条事件说明。最高序号是隔一阵推进一次的（不是每次写入都记），所以两次推进之间的少量序号仍可能被再用一次；下一条正是为了兜住这种情况。
- 控制面记着这个租户恢复过几次，这个次数编进 `ver`、事项版本和句柄里。这就是 `v21.0` 里小数点后面那个数。恢复之前拿到的一律对不上：`ver` 按普通的版本对不上处理，事项版本和句柄被拒绝。

所以恢复不是"把库换回去就行"，必须走恢复流程：

| 模式 | 怎么触发 |
|---|---|
| 服务器模式 | 运维命令 `saveslot server restore <租户>` |
| 本机模式 | `saveslot start --restored` |

恢复流程做的事依次是：在控制面做一个"恢复进行中"的标记并把恢复次数加一；打开租户；追加一条"恢复"事件；按删除登记补删；补做已经到期的物理删除；核对；清掉标记；对外服务。

**恢复流程中途被打断也没关系。** 那个"恢复进行中"的标记全部做完才清掉。之后每次启动都先看它：标记还在，就接着把流程做完，再对外服务，不管这次启动带没带恢复参数。每一步重做一遍结果不变。补删没做完之前，被删的内容是读得到的，所以这期间不对外服务。

没走流程就直接换了库，saveslot 有两道兜底：

- 打开时发现日志末尾的序号比控制面记的最高序号还低，说明被拨回过。
- 把删除登记和日志对一遍，发现了正常运行中不可能出现的组合（比如登记说某次删除待执行，日志里却根本没有它）。

发现之后，服务器模式下拒绝对外服务、提示走恢复流程；本机模式下自动走恢复流程（本机只有一个用户，没有运维，拒绝服务没有意义）。兜底发现不了全部情形：回退的幅度很小、期间又没有删除时看不出来。所以恢复应当一律显式触发。

### 恢复流程管不到的情形

删除登记要起作用，前提是它没有跟着数据一起被拨回去。

- **本机模式的默认布局下，数据目录和控制面都在 `~/.saveslot/` 里。** 系统级备份通常把两者一起恢复，登记也回到了过去。这时 saveslot 补不了，也发现不了。只有把数据目录另放别处、并且只恢复了数据目录时，补删才有效。另放别处的办法是初始化时指定：`saveslot init --data-dir <路径>`。
- **服务器模式下控制面的库和租户的库被一起恢复**，同样发现不了。
- **极窄的窗口里，一次撤回可能丢。** 撤回删除的事务已经提交、登记还没来得及改成"已撤回"时进程崩溃，随后又恰好恢复到了撤回之前的备份：那次撤回丢失，删除照常执行。这和"备份之后的任何写入都随恢复丢失"是同一类损失，方向是多删。

第 10 章把这些和其他"不保证的事"列在了一起。

### 升级 saveslot 的版本

装了新版之后第一次打开数据时，saveslot 检查存储的格式版本：比程序认识的低，就自动升级它内部的那些表；比程序认识的高（用新版写过、又换回了旧版程序），拒绝打开并提示升级，不冒险去写。（第一版只有一个格式版本，所以只实现了后一半：遇到更高的版本拒绝打开。）日志本身不用转换：新版内核必须能重放所有旧格式的事件，这是事件格式"只增不改"的含义。

规格：[`../spec/02-architecture.md`](../spec/02-architecture.md) §8；[`../spec/03-data-model/03-deletion.md`](../spec/03-data-model/03-deletion.md)「删除之后」。

## 7. 第一版不做什么

与部署和接入有关的：

| 不做 | 第一版的替代 |
|---|---|
| 本地和云端各存一份并同步；多设备同步；离线写入 | 多设备共用就都连同一个服务器模式的 saveslot |
| 导入、把导出文件装回去的命令、本机与服务器之间的迁移 | 只有导出；"导出能重放"由测试检验 |
| 图形界面的 App | 命令行，或交代给 Agent |
| 开发者 SDK（把 saveslot 嵌进别人的 Agent） | 只有 saveslot 服务这一种形态 |
| 按数据划分的权限 | 只按动作分的四种权限 |
| 多人共享的 slot | 一个租户就是一个用户 |
| 加密 | 无；删除靠物理删除 |
| 弹窗确认（MCP 的 elicitation） | Agent 在对话里征得用户同意后再调用 |
| 本机模式的 Windows 支持 | macOS、Linux |
| saveslot 自己调用模型 | 理解和抽取都由用户的 Agent 做 |

发布顺序上，本机模式先发，服务器模式（云服务和自部署一起）随后。

# saveslot · Engineering architecture

> Translated from docs/zh-CN/spec/02-architecture.md, updated in the same commit as this file.
> The Chinese edition is authoritative; where the two differ, the Chinese one holds.

> The core of saveslot is the **kernel + the service layer + the operation contract**; this document describes their engineering architecture.
> For positioning and product forms see [`01-positioning.md`](01-positioning.md); for the data mechanisms see [`03-data-model/`](03-data-model/README.md); for the operation contract see [`04-contract.md`](04-contract.md); for the surfaces see [`05-surfaces.md`](05-surfaces.md) (MCP, HTTP) and [`06-cli.md`](06-cli.md) (CLI); for the field-level definition of events see [`09-event-format.md`](09-event-format.md).
> Undecided items are recorded in one place, [`08-open-questions.md`](08-open-questions.md).

## Notes for the reader

Some terms in this document are used before they are defined; they are explained here first.

**Layer numbers L0–L7** are the layering of the kernel modules in §4 "Modules and their responsibilities": a higher number is higher up and may depend only on lower numbers (§4 "Dependency rules").

| Layer | Modules |
|---|---|
| L0 | `store` storage abstraction |
| L1 | `log` log, `audit` read audit, `flags` data flags, `values` value operations |
| L2 | `rules` rule engine, `time` time, `delta` value differences |
| L3 | `judge` judgement, `derive` derivation generation, `apply` applies events |
| L4 | `schema` schema and migration, `request` write requests, `pending` pending items |
| L5 | `write` write pipeline, `read` reads, `delete` deletion |
| L6 | `jobs` jobs, `sync` synchronization, `maintenance` maintenance plan |
| L7 | `ops` kernel operation layer |

**The three classes of state (a), (b), (c)**: every item of state in tenant storage falls into exactly one of them. (a) facts: log events; what is exported is exactly these. (b) materialized state: computed deterministically from (a) by `apply`; it can be discarded and rebuilt. (c) local running state: not exported, not replayed; for each item it is stated what happens if it is lost. The definition is in §3 "The log is the only source of truth"; which tables belong to each class is in §8 "Storage format v1".

**A few terms used before they are defined**:
- `apply` (applies events): the only implementation that turns log events into materialized state (§4).
- `ops`: the kernel operation layer, the only entry point in the kernel for each operation in the contract (§4).
- Operation number: the `seq` of the head event of an operation, the sequence number used externally (§3 "The log is the only source of truth").
- Anchor storage: holds what must still be remembered after tenant storage is replaced as a whole (the deletion register, the `seq` high-water mark, and so on); it is not inside tenant storage (§8 "Anchor storage").
- High-water mark: the `seq` of the end of the committed log, recorded in anchor storage; after a backup is restored, numbering continues from it (§8 "Anchor storage").
- Control plane: state that spans tenants (credentials, the tenant directory, the contents of anchor storage, and so on); it is kept apart from tenant storage and is not exported with a tenant (§5 "Control-plane storage").
- cell: in server mode, one PostgreSQL instance that hosts a group of tenants, each tenant occupying one database in it (§8 "Tenant storage", §9).

**The first version and 0.1.0**: "the first version" is the scope of the first version in the design; 0.1.0 is the first version released publicly, and it provides only part of that scope ([`07-scope-v1.md`](07-scope-v1.md) section 7). 0.1.0 does not provide yet: privacy deletion; migrations that need to rebuild physical tables (including `change_timezone` and `change_time_field`); replay comparison (`log.reconcile`, `saveslot verify --replay`); changing the slot policy; the two background tasks of read_log retention cleanup and periodic advancing of the high-water mark are also not wired in yet. Accordingly, in 0.1.0 K11 has no operation that can trigger it, and K6 holds only for switches that do not rebuild tables. Where this document describes these, it describes the design, and a few sections carry an extra note at their start.

## 1. Scope

- **The core = the kernel + the service layer + the operation contract.** HTTP, MCP, the CLI, the App and the future developer SDK are all surfaces of the contract.
- This document covers: the layers, the boundary between kernel invariants and service-layer policy, modules and dependencies, the runtime, the storage abstraction, tenants, trust boundaries, code organization and extension points.
- It does not cover: the data mechanisms themselves (in the data model), the fields of each event (in 09-event-format.md), the parameters and receipt of each operation (in 04-contract.md), the rules specific to MCP and HTTP (in 05-surfaces.md), the CLI (in 06-cli.md).
- **The first version has only two run modes, both single-node**: local mode, where the user starts a saveslot service on their own computer, reachable only from that machine and shared by the several agents on it; and server mode, which works across devices and remotely, and can be a cloud service we operate or the same system self-hosted by the user ("Deployment forms and synchronization" in the positioning document). Wherever this document says "cloud service", it applies to self-hosted deployments as well unless stated otherwise; the differences are in §9. Multiple nodes and synchronization are not in the first version; where this document mentions nodes and synchronization, it only reserves room for them.
- The two product forms ("Product forms" in the positioning document) share this one core: the first version implements only the **saveslot service**; the **developer SDK** is not implemented, but every decision in this document must let it be built later without changing the kernel.
- Terminology: a **tenant** is the unit in the kernel of "one log, one store"; in the first version a tenant = a user.

## 3. Kernel invariants and service-layer policy

**The criterion: if it is turned off, does saveslot's data stop being "traceable, explainable and recomputable", or do the accountability guarantees saveslot states publicly (who did it, who read it, what was confirmed) stop holding?**
What would stop holding goes into the kernel and cannot be turned off in any use; what concerns only "who may do it, how to interact, the calling experience" is service-layer policy.

### Kernel invariants

Each is a single assertion that can be written as a test; the details are where the right-hand column points.

| # | Invariant | Details |
|---|---|---|
| K1 | The log is append-only. Each event is divided into an **event header** and **content**: only event headers are chained, an event header is never deleted or modified, and it holds no value computed from user content; content is stored in blocks, and only when a tombstone is applied may a block be physically erased as a whole | "Integrity and provenance" in the data model; 09-event-format |
| K2 | Every event has an actor: a globally unique principal registered in this tenant. Events the kernel produces itself are recorded under the reserved principal `system`, noting which background task triggered them | "Identifiers and objects" and "Connection identity" in the data model |
| K3 | Materialized state can be changed only by `apply` (applies events, the only implementation that turns events into materialized state, §4): every change corresponds to one log event and is committed in the same transaction; writes are serial per tenant | "The log is the only source of truth" in this section |
| K4 | Every base write has source data; provenance is recorded down to the field level, as value source and operation source | "Invariant: every write has source data" and "Deletion · Provenance" in the data model |
| K5 | Derived tables are generated only by rules and are refreshed in the same transaction as the base write; the estimation and rejection for write admission are executed in the kernel | "Derivation rules and derived caches" in the data model |
| K6 | 0.1.0 does not provide migrations that need to rebuild physical tables yet, and in 0.1.0 K6 holds only for switches that do not rebuild tables; what is written here is the design ([`07-scope-v1.md`](07-scope-v1.md) section 7). A schema version is immutable and field IDs are stable; structural change goes only through the migration state machine; a switch is atomic and reads do not stop; a write carrying an old `sv` is rejected only when it writes to a field with an incompatible change. A table-level structural change (changing the time type, key, granularity and so on of a table that has never been written) has no corresponding field, and is treated as all fields of that table being incompatible | "Schema version evolution" in the data model |
| K7 | Two timelines: recorded time is given by the log sequence number, and valid time follows the table's time type. The kernel does not read the clock: "the current instant" is passed in by the calling context and recorded in the event, and replay uses only the instants recorded in events | "Time" in the data model; §7 "The recorded instant" of this document |
| K8 | A version mismatch does not overwrite: the decision is made per **conflict unit** (a field, or a field group declared by the schema; for state tables the valid-time interval is also considered); where they intersect, candidates are recorded and a conflict item is generated, and where they do not intersect, they are merged. Two writes carrying the same version, neither passing an end point, are judged independently of arrival order: in either order both are judged conflicts, or both are merged with the same final value and neither produces an item (the range, and the three cases known to lie outside it, are in the symmetry paragraph of "Conflict handling · Conflict criteria" in the data model); the value in effect during a conflict is determined by rule | "Conflict handling" in the data model |
| K9 | Restricted SQL goes only through a syntax-tree allowlist (which guarantees safety and determinism together); physical names do not leave the kernel | ["Restricted SQL" in the data model](03-data-model/11-restricted-sql.md) (the allowlist); "Reads" and "Derivation rules" in the data model |
| K10 | Reads among the operations in the contract are recorded in read_log: only the versions read are recorded, not values, and not hashes computed from values; the query condition is recorded only as a structural fingerprint containing no user values (except the valid-time condition and the entry instant, which are needed to determine affected queries). The retention period has a lower limit, and the window of loss has an upper limit | "Read records" in the data model; §7 of this document. The `instructions` generated for MCP are not a read operation in the contract and are not recorded in the read record (§10) |
| K11 | 0.1.0 does not provide privacy deletion yet, and in 0.1.0 K11 has no operation that can trigger it; what is written here is the design ([`07-scope-v1.md`](07-scope-v1.md) section 7). The result of privacy deletion is defined by the reference semantics: the state obtained by replaying the log by `seq` as if the deleted source data had never existed, with two deliberate deviations: a person's decisions are kept as recorded, and writes that have already taken effect stay in effect. Everything derived from the source data is within the cascade; a tombstone never expires; the deletion register is outside the log, and after restoring any backup, the deletions in the register are re-applied before the service resumes | "Deletion" in the data model |
| K12 | The log is the only source of truth: every item of state in tenant storage falls into one of three classes; feeding the log to `apply` in order from an empty store yields materialized state that matches the live state row for row | "The log is the only source of truth" in this section |
| K13 | Writes happen exactly once: for an operation carrying a request key, the kernel records "request key → result" in the same transaction, and a resend within the window returns the original result | "The details of K13" in this section; "Idempotency" in the contract |
| K14 | A confirmation is bound to its content: an item awaiting confirmation is executed only when it is explicitly resolved; resolving passes back the version of the content being confirmed, and a mismatch is rejected; each resolution records who did it and through which credential | "Pending items" and "Writing state" in the data model |

**Versions of judgement.** The kernel's mechanical judgements (stop points, same value, the conflict criterion, the high-impact criterion, the existence of rows and entities, literal matches) have one **rule version** as a whole (an integer, shipped with the kernel); the slot policy (the rule for the value in effect during a conflict, and so on) has a **policy version** (per slot, incremented on each policy change). Both numbers are recorded in the head event of each operation (the logical write head, the resolve event, the deletion lifecycle events) and in item events. When privacy deletion replays an old write, it recomputes using the rule version and policy version **that write itself recorded**; to make an old item use the new rules, an explicit rejudge event triggers it (the event type is reserved; the first version does not produce it). The restricted SQL allowlist has its own version (`rsql@1`), recorded in `schema.compiled` at compile time (each derivation rule records its own; `migrate` / `backfill` record the version of this release); replay evaluates with the recorded version, and the implementation keeps the behavior of old versions. A rule switches to the current version only when it is recompiled for another reason (it was itself changed, or a definition it depends on changed); a rule that was not touched keeps being evaluated with its recorded version, so a kernel upgrade does not push unrelated drafts into awaiting confirmation; when a rule's behavior changes because of such a switch, the rule version is incremented by 1. This way an old candidate is not re-judged because of an unrelated deletion after a kernel upgrade.

**The details of K13.**

- Only keys within the idempotency window are matched: the window length is passed in by the calling context, and the filter is "recorded instant ≥ current instant − window", so the result is deterministic.
- The request key is computed from the request content and is itself content (no salt added): it is stored in the content area of that operation's head event and is erased together with the evidence when the evidence is deleted. An explicit idempotency key additionally records a fingerprint of the request content (used to detect the same key paired with different content), and the fingerprint is likewise content.
- The request-key index is class (b), rebuilt from the log. The head events of `write`, `resolve`, `schema_draft` and `delete` each carry a request key.
- **A rejected operation produces no event and is not deduplicated**: on resend it is validated again against the state at that time. The state may have changed (for example, the caller has read once as the `read_first` hint told it to), and caching the rejection would make a retry that follows the hint get the same rejection back.

**Invariants whose scope is smaller in the first version** (the feature is not enabled, so the rule is simply never triggered; none has been relaxed):

| Invariant | The situation in the first version |
|---|---|
| K5 | No large-write jobs, and derived values are not allowed to lag, which is stricter than the full design |
| K8 | No system adjudication; the rule for the value in effect during a conflict is only "keep the current value" |
| K10 | The query for affected-by-correction does not cover reads of derived values; read_log records the full shape, so a query added later can cover earlier reads |
| K11 | No evidence deletion and no per-row privacy deletion; no extraction jobs, so the cascade for translation results is not triggered |
| K12 | No background sampled reconciliation: finding a change that bypassed `apply` relies on the user's session running a full replay comparison |

### The log is the only source of truth

**Every item of state in tenant storage must fall into one of three classes**:

| Class | What it is | Export / backup restore / replay |
|---|---|---|
| (a) facts | log events: event headers go into the chain; what is exported is exactly these | taken as they are |
| (b) materialized state | computed deterministically from (a) by `apply`; can be discarded and rebuilt | not taken; rebuilt from (a) |
| (c) local running state | not exported, not replayed; **for each item it must be stated what happens if it is lost** | not taken |

Which tables belong to each class is in §8 "Storage format v1", which is the only list.

- The in-process state of the service layer (waiting while a request with the same key is in flight) is not in tenant storage, and losing it is harmless.
- 0.1.0 does not provide replay comparison (`log.reconcile`) yet, and server mode does not create the `<lowercase tenant ID>_reconcile` database below either; what is written here is the design ([`07-scope-v1.md`](07-scope-v1.md) section 7). The temporary storage for replay comparison (`log.reconcile`) is likewise not in tenant storage: it is a copy destroyed after use, one fixed copy per tenant: in server mode it is the database `<lowercase tenant ID>_reconcile` in the cell the tenant lives in, and in local mode it is `tmp/reconcile/<tenant ID>` under home. Before a replay comparison starts, any residue is deleted and a fresh one is built; when it ends, it is deleted whether it succeeded or failed; when a tenant is opened, what a crash left behind is cleared. If it cannot be cleared on open, a note is recorded and service continues as usual: it is not the tenant's data, and it will be deleted again the next time the tenant is opened and before the next replay comparison starts.
- Anchor storage (§8) is likewise not in tenant storage: it holds what must still be remembered after tenant storage is replaced as a whole.
- The staging storage used for replay during an import is likewise not in tenant storage: until it is swapped in it is no tenant's storage, and when a tenant is opened, what a crash left behind is cleared (§8 "Format versions, export, import and restore").
- **The only exception to K3**: a new-version table built in batches during a migration is class (c) (discardable, rebuildable from the log) and becomes class (b) at the switch event; during replay, `apply` builds the new-version table only when it reaches the switch event.

#### The event catalog and the rules that hold for every event

**Class (a) events.** The event header fields, content blocks and erasable granularity of each kind of event are in [`09-event-format.md`](09-event-format.md); here only which events exist and when they are produced are listed.

| Event | What it is and when it is produced | First version |
|---|---|---|
| Tenant genesis | The first event of the log: registers the tenant, the storage and event format versions, the user principal and the reserved principal `system`, and a node ID | Yes |
| Source data | A piece of evidence; when a write comes with evidence, one per piece, and when it comes without evidence, one for each op that left something in the event (this op itself) | Yes |
| Logical write head | One per write request that produces events: the original parameters of each op (including the declared premises), the request key, the instant and version numbers used in judgement; an op keyed by external key additionally records the row it located and the per-field synchronization baseline position. Its `seq` is the **operation number** of this write as seen externally. When all ops in a request keyed by external key are unchanged or skipped, the whole request produces no events | Yes |
| Base write | One per affected row / entity for each op, recording only the fields this request touches: the value, the resolved valid interval (a separate block, noting the other contributions it depends on), the field-level provenance, the per-item effect status (in effect, candidate, awaiting confirmation, corroboration; a field with a no-op does not enter the base write) and the judgement result at write time. It does not record the value before the write, nor the whole row after the write; an op whose fields are all no-ops produces no such event | Yes |
| Premise change | One when an operation changes (or changes back to the value seen) the declared value on some premise targets: which declarations turn to "premise changed", turn back to "unchanged", or are redirected because of deletion. It is not a head event; it is placed after this operation's base writes and item events and before the derived writes | Yes |
| Derived write | One when the rule engine refreshes a derived partition: the rule version, the partition, the log position of the read set; the group key values and the result checksum are in the content | Yes |
| Large-write job | Job accepted, completed, failed | Later |
| Schema lifecycle | Draft submitted, compile result (including the compiled definition, for replay), confirmed / abandoned / superseded, migration started, switch, failed; abandoned migration, migration result (produced only by extraction jobs), cleanup of a retired table | Yes; abandoned migration, migration result and cleanup of a retired table: later |
| Pending item lifecycle | Created, merged, refreshed, superseded, resolved; a resolve event carries the confirmation record. When a write changes the target of an open item, the item is superseded only if the writer has read the item's current version; if not, the item is refreshed and stays open ("Pending items" in the data model) | Yes |
| Deletion lifecycle | Deletion confirmed (including the result computed by the reference semantics), cancelled, physical erasure on time (tombstone); tombstones added at import for items that appear in the export only as placeholders pending deletion | Yes |
| Restore | The first event after a backup is restored: the position restored to, the high-water mark, the restore count, a new node ID | Yes |
| Import | When an export is loaded into an empty tenant, appended after the last event of the import: the position imported to, the restore count (the value at export time plus 1), a new node ID, the IDs of the target tenant and the original tenant, the user principal that started the import; `apply` uses it to set every principal registered before the import and still valid to disabled (those already revoked stay revoked) | Yes |
| Slot policy change | The full text of the new policy and the policy version; the initial policy when a slot is created is also written as one | Only the one at slot creation |
| Slot removal | Removes an empty slot: its ID, the version and name at removal; `apply` deletes its slot row, catalog and physical tables, and keeps its schema versions (the table numbers and `slot_id` are not reused) | Yes (empty slots only) |
| Principal | Registration of a principal in this tenant (including scope and slot range), renaming, revocation | Yes |
| Rejudge | The explicit event that makes an old item use the new rules | Reserved |
| Synchronization control | Switching the primary node, and so on | Reserved |

Several rules hold for every event:

- **One operation, one operation number.** A write, a write triggered by `resolve`, a deletion confirmation and a deletion cancellation each have a head event, and its `seq` is the operation number of that operation. Every externally visible number (the `seq` of a receipt, `ver`, the numbers in history, the n of `undo`, `as_of`, the recorded-time interval of a version table) uses the operation number; the `seq` of source data events and of per-row base write events is not exposed.
- **`apply` does only what the result recorded in the event says**: it does not re-resolve end points, re-judge conflicts, replay deletions, read the clock, re-locate by external key (the located row ID is recorded in the logical write head), or compare premise values (each change of a flag is recorded in premise change events). The result in a deletion / undo event is the one `delete` computed by the reference semantics, and `apply` uses it as it is. What `apply` does itself is only deterministic computation containing no judgement: putting the field values in effect onto the current state; for a state table, assigning the value to the interval recorded in the event and then normalizing the segmentation by "adjacent points with the same value in every field are one segment"; when registering "already reverted" according to a revert record, the registered range is "the interval of that item ∩ the union of the intervals of the items this event writes back"; when a write-back item carries no content (`uncovered`), it assigns no value and looks up the source table for "the last item at that place that is in effect and not registered as reverted". The latter two read the source table, but given the source table the result is unique and contains no judgement (event format 5.7).
- **The identity of an event**: in the first version an event header has no separate event ID; the identity of an event = (the node ID recorded by the nearest earlier genesis, restore or import event, its `seq`). With multiple nodes, events produced by other nodes join through an optional source field, and old events are not changed.
- **`seq` is not reused**: after a backup is restored, numbering continues after the high-water mark recorded in anchor storage, and the gap is explained by the "restore" event; `seq` values allocated between two advances of the high-water mark may still be reused, so each restore changes the node ID and adds 1 to the restore count, and `ver`, item versions and handles all carry the restore count. An import likewise changes the node ID and adds 1 to the restore count: every item version issued before the import fails to match, and a `ver` from before the import can be recognized.

#### Events after physical erasure

0.1.0 does not provide privacy deletion yet; what is written here is the design ([`07-scope-v1.md`](07-scope-v1.md) section 7).

**Events after physical erasure.** The event header stays on the chain; the erased content block is cleared together with its checksum, and a mark records which tombstone removed it ("removed by #n"; the mark contains no content and no value computed from content), while the other content blocks of the same event stay readable as usual.
When `apply` meets this mark it skips the block: replaying an event earlier than the tombstone does not need to look ahead to know it has been deleted; what is obtained then is "the historical state with the deleted content removed", which is not guaranteed to equal the live state at that time, and replay comparison compares only the state at the end of the log.

**Replaying from the start after a tombstone, the end of the log still matches the live state table by table**, because the deletion confirmation event writes out the live result in full:
- For all three kinds of table, the deletion result lists the fields whose value, or whose contributing items, differ from before the deletion, including those given by items that were restated this time; for rows listed only because the giver, the judgement result or the block that gave them was given again while the value did not change, the `outcome` in the result is `sources_changed`. When an "exists" item is deleted or restated (including restated unchanged), or a write-back item that only does registration (`uncovered`) is restated, that row or entity must be listed (the same for all three kinds of table); in a state table, a segment that intersects the intervals of these items (the union of before and after the restatement) is listed as a whole segment, and every listed entity is given all its intervals without a value after the deletion: the interval blocks of these items have been removed, and the gaps can be obtained only from the result. A deletion or undo event changes the business table only according to the result, and a restated item enters only the source table. When a row in the result does not exist in the replay (all blocks of the write that created it were removed), `apply` creates it.
- For each derived partition the affected rows fall into before and after the deletion, the deletion confirmation appends one derived write, even if the result did not change: when replaying from the start after a tombstone, the derived values computed from intermediate states are pulled back by it.
- The constant positions added at a schema switch are registered as recorded in the switch event, and deletion does not change them (the `base_sources` row in "Storage format v1" below); in a state table, when a contribution that a segment's filled value depends on is deleted, the deletion confirmation removes that segment from `base_sources`, and cancelling the deletion puts it back.

- **The two kinds of placeholder in an export**: content pending deletion within the grace period is by default replaced by "pending deletion (#n), not exported" (see §8), where #n is the "deletion confirmed" event; the #n in "removed by #n" is the tombstone. `apply` tells them apart by the type of the event #n points to.
- **After replaying an export that carries "pending deletion" placeholders**, the business state at the end of the log matches the live state (the post-deletion shape is written out in full in the "deletion confirmed" event in the way listed above, and the derived partitions also have the derived writes that deletion appended); what differs is only the historical version content at the placeholders, and that a placeholder export can no longer cancel that deletion. K12 and replay comparison are exceptions for this. When such an export is imported, a tombstone is added immediately for the deletion of each placeholder, so the store keeps only two real states, "present" and "removed".
- **Verification information is deleted along with its inputs**: the result checksum of a derived write and the checksum of the new-version table in a switch event are cleared once their inputs are deleted, and the check is skipped afterwards; a result restored as of an instant is marked `partially_deleted`.

#### The guarantees that follow

It follows that:

- **Deletion is not revived by an export**: when an export is made within the grace period, the "deletion confirmed" event goes along with the log and content pending deletion is by default not exported, so after replay the data still cannot be read.
- **Conflicts do not vanish because of a rebuild**: the lifecycles of items are all in the log, and replay produces the same open items and `disputed` flags.
- **Replay consistency can be verified as a whole**: see the replay comparison in §11.

### Service-layer policy

| Policy | saveslot service | SDK embedded |
|---|---|---|
| Authentication | credential → user / connection | the host declares the current actor (which must be a principal registered in this tenant) |
| Permissions | scope × slot range (first version); table-level and field-level data permissions later | the host may turn it off or implement its own |
| Interaction for confirmation | delegated to the calling agent; optional elicitation | decided by the host |
| Idempotency | two window lengths (24 hours for an explicit idempotency key, 10 minutes for a request key computed by the server), waiting while a request with the same key is in flight; only terminal results that produce events are deduplicated, and exactly-once is guaranteed by K13. The request key itself is computed by the kernel: it exists only after the request is normalized (`request` gives the normalized content, and `write` adds the connection and the task to compute the key) | default implementation, can be turned off |
| High-impact writes | the high-impact tables / fields additionally designated by the slot policy (a high-impact determination the kernel makes from the result cannot be turned off, and the validity of an op-level `acknowledge` is also checked by the kernel, see "Writing state" in the data model); which surface opens `acknowledge` (MCP does not open it in the first version) | the host may add |
| Handle signing | one signing key per tenant | default implementation |
| Rate limiting and quotas | yes | no |
| Values of the admission threshold, the read_log retention period, the flush interval and the high-water-mark advance interval | configuration | adjustable by the host (not below the kernel's lower limit) |
| Result rendering (text, untrusted boundary) | the surface (the MCP renderer) | decided by the host |

**Confirmation and the authenticity of data are delegated to the caller**: saveslot does not distinguish whether a confirmation came from a person or an agent, and does not guarantee the authenticity of the data written; through MCP alone saveslot cannot tell, and
has no ability to judge. What the kernel guarantees is K14: an item awaiting confirmation is executed only when it is explicitly resolved; a confirmation is bound to its content; every confirmation leaves a trace; and in addition a deletion can be cancelled within the grace period.
Obtaining the user's consent is a matter for the calling agent and its host. When saveslot later does source ingestion and analysis itself, the authenticity of that path is saveslot's responsibility.
The structure of the slot policy reserves a place for "an operation of a given kind accepts confirmation only from a user session"; the first version does not implement it.

**The enforcement of permissions on SQL must be in the kernel**: data permissions (rows, columns, tables) must act on restricted SQL, and only the rule engine can rewrite queries. The service layer passes "the visible range of this call" to the kernel,
and the kernel enforces it uniformly in the catalog, in queries, in SQL rewriting and in writes. In the first version the visible range is at the level of credential to slot: a connection's authorization = action scope × slot range (all, or a list of slots), and a slot outside the visible range is exactly the same as nonexistent for this credential; a user session is always all. Table-level and field-level come later, and the interface already leaves room in the shape slot → table → field from the first version.

### Dependency rules

- **A module may depend only on lower layers, and modules in the same layer do not depend on each other**; cycles are always opened up by `ops` orchestration (example: a write produces an item, and resolving the item requires executing a write: `pending` does not call `write`, and `ops` calls them one after the other). The only exception is that `request` depends on `schema` in the same layer: it takes only the unit vocabulary and the types of the compiled definition, and does not call compilation or migration.
- **Transactions are opened by `ops`**; lower-layer modules receive only a `Tx` and do not open transactions themselves. The calls across several modules in one operation are all in this one transaction.
- Modules that generate events (write, schema, pending, delete, derive, jobs) never change materialized state directly; they only hand events to `apply`. Premise-change events are generated by `write` (including writes triggered by `resolve`) and by `delete` (deletion confirmation, cancellation) in the transaction that produces the change; the declarations and coverage indexes they need are read through `store`, not through `read`: the three are in the same layer L5 and do not depend on each other.
- **There is only one implementation of judgement**: the mechanical judgements that `write`, `delete` and `schema` need all call `judge` and none implements its own.
- **The service layer calls only `ops`** and does not touch the modules below directly; surfaces call only the service layer.
- The dependency check works at the **module level** (such as the layering rules of dependency-cruiser) and is enforced in CI.
- `flags`, `maintenance`, `jobs` and `sync` in the table are modules in the design; the kernel source of 0.1.0 does not yet have a directory for each of them. The table and the dependency rules keep them as designed, and the "First version" column states the status of each.

### Contract operations and internal operations

The entry points of `ops` fall into three groups with the same form (each receives a calling context, opens a transaction and composes lower-layer modules):

- **Contract operations**: each operation in the operation contract, called by the service layer.
- **Internal operations**: the task bodies of background tasks. In the context `actor = system`, `now` is given by the caller, and there is an additional `trigger` (which background task). They are called by a **scheduler outside the kernel**: the scheduler holds the timers and reads the clock; in the saveslot service it lives in `daemon`, and in SDK embedding it is a thin driver shipped with the kernel or a host driver. The exception is `revokeOnRefreshReplay`: it is not a timed task, and the service layer calls it when a refresh token is replayed.
- **The tenant-creation entry point** (`createTenant`): appends and applies the genesis event on a new empty storage (09-event-format §5.2). It is called by `saveslot init` or by the provisioning flow in server mode. In the context, `actor` is the user principal it is to register and `trigger` is empty; it does not check that "`actor` is registered" (there is no principal yet). It is neither a contract operation nor an internal operation and is not in the table below.

| Internal operation | Triggered by | Produces events? |
|---|---|---|
| `openTenant` | When a tenant is opened. In order: check the "import in progress" mark → check the "restore in progress" mark → check whether the log end is below the high-water mark → reconcile the register with the log → run the tasks that are due. The import mark is looked at first: after the import swap and before the anchor is rebuilt, the log end is above the high-water mark and the restore count does not match yet, so the import's re-entry protocol is completed first (§8). The high-water check comes before reconciliation: when the log has been rolled back, register entries must not first be cleared on the grounds that "the transaction never committed". Once the checks pass and the tenant can serve, it loads the restricted SQL parser: the host loads it through this when opening tenant storage, and the kernel's evaluation entry points (reading derived tables, derived refresh after a write, `apply` recomputing derived partitions) assume it is already loaded and do not load it themselves | As the case may be |
| `flushReads` | The scheduler, at the flush interval; the start of a write transaction runs the same logic | No |
| `expireDeletions` | The scheduler; `openTenant` | Yes: tombstone |
| `purgeResidue` | After `expireDeletions` commits | No |
| `pruneReads` | The scheduler | No |
| `migrationStep` | The scheduler (while a migration is in progress) | At the switch, yes |
| `advanceHighWater` | The scheduler; before a tenant is closed | No |
| `closeTenant` | Before closing and giving up ownership: first `flushReads`, then `advanceHighWater` | No |
| `revokeOnRefreshReplay` | The service layer: when the same refresh token is used a second time, revokes the connection of this authorization ([`05-surfaces.md`](05-surfaces.md) section 15); not called when the connection is already revoked or disabled | Yes: `principal.revoked` (09-event-format §5.3) |

0.1.0 does not provide the replay comparison (`log.reconcile`) yet; what is written here is the design ([`07-scope-v1.md`](07-scope-v1.md) section 7). The replay comparison (`log.reconcile`) is not a background task: it is an administrative operation in the contract, triggered by a user session. It works like the build and switch of a migration, in three phases: (1) replay the log in batches into a temporary storage (not inside the tenant storage, destroyed after use), while reads and writes continue as usual; (2) catch up with the events appended during the replay; (3) in one read-only transaction on that tenant storage, read the log end, catch up the last stretch, and then compare table by table the tables marked "replay comparison: yes" in §8. On PGlite reads and writes share one queue, and writes queue up during this phase; on PostgreSQL it is completed within one read snapshot (`REPEATABLE READ READ ONLY`) and writes need not queue: the append of an event and its apply are committed in the same transaction, so the materialized tables in the snapshot look exactly as they were at the log end it read. The transaction of each batch is still opened by `ops`.

### The source address of a request

**The source address of a request** (server mode; the identity provider counts login failures by it, and the cloud service limits new tenants by it): server mode is accessed through a reverse proxy, and if the forwarding header is not read, the source of every request is the address of the proxy. The rules:

- Only when the address of the connection itself is trusted (inside one of the entries of the trusted-proxy list `SAVESLOT_TRUSTED_PROXIES`; comma separated, each entry a single address or a CIDR range, 06-cli 4.1) is `X-Forwarded-For` read: the several headers of the same request are combined in order into one list and walked from right to left (each trusted proxy appends the address from which it received the request at the far right), skipping trusted addresses; it stops at the first item that is not a trusted address: if it is an address, it is the source; if it is not an address, the source is the last trusted hop (when the rightmost item is itself not an address, it is the address of the connection itself). Everything to the left of the item where it stopped is never read: that part is written by the client itself. When the list consists entirely of trusted addresses, the leftmost one is taken.
- When no list is configured, or the address of the connection itself is not trusted, the whole header is not read and the source is the address of the connection itself: whatever the client wrote into this header does not count. When the header is missing, the address of the connection itself is likewise taken. An item in the header is accepted only as a single address; one with a port is not accepted. The `Forwarded` header is not read.
- Addresses are normalized before comparison: an IPv4 written as IPv6 (`::ffff:a.b.c.d`) is treated as IPv4, and IPv6 uses the lowercase compressed notation. An address is trusted if and only if it is of the same family as an entry of the list and its first prefix-length bits are those of the entry; a single address is a `/32` or `/128` range.
- How the list is written: a range is `address/prefix-length`, the prefix length a decimal without leading zeros or sign, 0–32 for IPv4 and 0–128 for IPv6, with no spaces around the `/`; the bits of the address after the prefix must all be zero (`192.0.2.1/24` is not accepted: whether a machine in the range or the range was meant cannot be told, and truncating it by the mask would quietly widen the trust). An IPv6 range inside `::ffff:0:0/96` is the IPv4 range it writes (`::ffff:192.0.2.0/120` is `192.0.2.0/24`), because source addresses are compared as IPv4; other IPv6 ranges are compared with IPv6 addresses only. An entry that covers every address is not accepted: one with a prefix length of 0 (`0.0.0.0/0`, `::/0`, and `::ffff:0:0/96`, which converts to `0.0.0.0/0`), and an IPv6 range wider than `/96` that covers `::ffff:0:0/96` (such as `::/80`) — when the list covers every address, every connection is trusted and the source is entirely written by the client, which is worse than configuring no list. No other minimum prefix length is set: the list should hold the subnets of the deployment's own proxies and the egress ranges a CDN publishes, and how wide they are is up to them. Ports and zones are not accepted. When the list contains an entry that is not accepted, the service reports an invalid configuration at startup, naming the entries. When the connection has no usable single address there is no source address: local mode accessed through a unix socket, and link-local addresses with a zone.

  | `oauth_clients` | The cache of the client ID metadata documents of remote authorization: client ID (an HTTPS address under the client's own domain) → the original text of the fetched document, the instant of fetching, the expiry instant. It is only a cache: when expired it is fetched again by address, and deleting it loses nothing. The saveslot CLI is a built-in client and is not here |
  | `oauth_grants` | One authorization: authorization ID, kind (connection / user session from CLI login), principal, tenant, client ID, the external address at issuance (the audience of the token), the establishment instant, the invalidation instant, the hash of the authorization code that redeemed it. One authorization of a connection is one connection; the access token issued through it is a row in `credentials` with an expiry instant that records this authorization, the refresh token is in `oauth_refresh_tokens`, and both are deleted together when the authorization is invalidated |
  | `oauth_codes` | Authorization code hash → client, callback address, `code_challenge`, external address, user and tenant, the login at which the authorization was consented to (the `session` given by `currentUser`), the scope in the request, the name and scope the user settled on the authorization page, the expiry instant. It is deleted in the same transaction in which it is redeemed, so a code can be exchanged only once |
  | `oauth_refresh_tokens` | Refresh token hash → the authorization it belongs to, the issuance instant, the expiry instant (it becomes invalid after 30 days unused), the total lifetime of the CLI login (carried over to the new token as it is on renewal; connections have none), which token it was exchanged for (the hash of the new token; once recorded it has been used, and presenting it again is a replay). On renewal it is recorded only if it has not been used yet, in the same transaction as the write of the new token, so when two renewals happen at the same time only one succeeds. Deleted when the authorization is invalidated or its connection is revoked; expired ones are cleaned periodically |
  | `oauth_device_codes` | Device codes (RFC 8628, the CLI's `--device` login): device code hash → user code (unique, uppercase, without hyphens), client (always `saveslot-cli`), external address, status (waiting / approved / denied), the user and tenant that approved or denied, the expiry instant (10 minutes), the polling interval, the instant of the last poll. It is deleted in the same transaction in which it is redeemed and the authorization is recorded, so it can be exchanged only once; expired ones are cleaned periodically |
  | `web_forms` | The hash of the one-time token of an authorization page form → the login it belongs to and the request that displayed this page (the hash of the query string of the authorization request), the expiry instant. Deleted once submitted, and also deleted on a mismatch: another login or another request cannot use it |

  The six tables of remote authorization (`oauth_clients`, `oauth_grants`, `oauth_codes`, `oauth_refresh_tokens`, `oauth_device_codes`, `web_forms`) have a format version of their own (`oauth_format` in `control_meta`), checked separately from the format of the control plane's own tables; a database whose format does not match is refused and is not upgraded.

### Account passwords and account names

  - **Passwords of local accounts** use scrypt: N = 2^15, r = 8, p = 3, a 16-byte salt, a 32-byte output. The parameters are stored together with the salt and the hash (`scrypt$N$r$p$salt$hash`) and checked against the stored parameters, so changing the parameters later needs no migration. Each computation occupies 32 MiB, at most 2 run at the same time in a process, and the rest queue. When the account name does not exist, a fixed fake hash is likewise computed and queued in the same way (the fake hash is computed when the local accounts are opened, so the first encounter with a nonexistent name does not do extra work): a nonexistent account name, a wrong password and a disabled account give the same result externally, and take the same time.
  - **An account name** is 1–64 characters: lowercase letters, digits, `.`, `_`, `-`, starting with a lowercase letter or a digit (`[a-z0-9][a-z0-9._-]{0,63}`). There is no case folding: a name containing an uppercase letter is refused outright, so an account name has only one spelling. **A password** is 8–1024 characters (counted in UTF-16 code units), computed as it is, without Unicode normalization.
  - A stored password hash is checked only in the shape written here: key 32 bytes, salt at least 16 bytes, N a power of 2 and not above 2^17, r between 1 and 16, p between 1 and 4 (newly computed hashes also stay within these); a hash that does not conform matches no password, and nothing is computed for it. At login, an account name of the wrong shape and an over-long password are handled the same as a nonexistent account name: the fake hash is likewise computed, with the same result.
  - The operation of local accounts (`saveslot server user …`) finds people by account name: when an account is created, its tenant is created through "Creating a tenant" below. If it stopped midway, creating again with the same account name finishes the work: first the tenant is completed, then the password is replaced with the one given this time, in the same way as a password change (which ends web login state and user sessions at the same time); if the tenant cannot be created (for example, the registered cell differs), the password is left unchanged. While the same account name is being created in the same process, creating it again reports that the account name is already taken. Changing a password ends this user's web login state and user sessions at the same time, and records the instant at which sessions ended: a user session granted at or before this instant is no longer issued on refresh (`issueUserSession` under "Identity providers" in §12); these happen in one transaction, and the connections it issued remain usable as usual. Disabling and enabling change only the account status, do not write a revocation into the tenant log, and do not delete credentials; while disabled, all credentials of this tenant are refused at authentication and refresh does not issue either; once enabled again, everything is as before. Changing a password and disabling both change the account row first and then touch its web logins and sessions (for the order of locks see `issueUserSession` under "Identity providers" in §12).
### Creating a tenant, and how a request is resolved

  - **Creating a tenant** has three steps: register as `creating` in `tenants` → create the database and write the genesis event → change to `active`. Each step looks at the current state before acting, and if it stopped midway, calling again finishes the work; when the same user already has a tenant, what is returned is that one. Before registering, it checks that the cell is one in this deployment's configuration, and if it is not, nothing is registered; the cell and database in the registration are not changed afterwards, so for a tenant still in `creating`, a request whose cell differs from the registered one is explicitly refused, and it neither switches to a new cell nor continues in the old one. The control plane stores only the registration and does not hold the tenant storage's backend; the three steps are orchestrated by the service layer.
- The cloud service's scheduler scans the registered due instants of not yet executed work and, when one is due, actively opens the tenant to execute the physical erasure.

How a request is resolved: credential → the control plane looks up (tenant, principal) → open tenant storage and anchor storage → take this principal's scope, status and slot range from `principals` → build the calling context → `ops`.
The first version does export and import into an empty tenant ("Deployment forms and synchronization" in the positioning document): import does no principal mapping, and principals registered before the import and still valid are all disabled (revoked ones stay revoked), and the user reissues credentials at the target; import is an administrative operation, given only to user sessions, with the steps in §8. Merge import and the migration flow (freezing the source tenant, credential mapping) go to later along with multiple nodes. Principal identity is in the log, and the historical actor does not change with credentials.

- **The service layer does not change data**: all changes enter the kernel through `ops`.
- Remote authorization (OAuth 2.1), local tokens and user sessions are all in this layer; the kernel sees only "the authenticated principal".

## 6. The form of the operation contract

- **The contract has two layers** (written up in the two parts of [`04-contract.md`](04-contract.md); the rules for MCP and HTTP respectively are in [`05-surfaces.md`](05-surfaces.md)):
  - `contract-core`: the shape of data: value encoding, evidence, flags, intents, domain errors (`validation_failed`, `schema_incompatible`, `derived_readonly` and so on). The kernel depends on it;
  - `contract`: the outward wrapper: the fields and errors specific to surfaces (`idempotency_key`, `cursor`, signed handles, `insufficient_scope`, `rate_limited`). The service layer and surfaces depend on it.
- **The signatures of `ops` are written by hand in the kernel**, constrained by the types of `contract-core`; `contract` is generated from them: the OpenAPI of HTTP, the `inputSchema` of MCP, and the interface of the future SDK.
  This way, adding an error code or a paging parameter to the external contract does not change the kernel.
- **Flags are structured fields**: `disputed`, `awaiting`, `stale` and so on are fields in the contract and not rendered text; the renderer of a surface **must** output them into text (MCP) or keep them in the structure (SDK), guaranteed by renderer tests.
- **Versions are independent of each other**:

  | Version | What it governs | When it is raised |
  |---|---|---|
  | Contract version (`/v1`, the SDK major version) | The shape of operations | Removing a field or changing semantics raises the major version; adding an optional field, an error code or an enum value raises the minor version (callers must tolerate unknown values) |
  | Slot schema version `sv` | The shape of user data | At every schema switch |
  | Storage format version | The shape of the kernel's own tables (§8) | When a kernel upgrade changes its own tables |
  | Event format version | The shape of each kind of log event, written in the event header | Only added to, never changed: a new kernel must be able to replay all events of older versions; when an old kernel meets an event type or version it does not know, it **stops `apply` and reports an error** and does not skip; an event carrying a shape the old kernel does not know (a new path, key or enum value) must carry a higher `v`, and there is no path of "ignoring unknown keys" (event format 1.6) |
  | Rule version, policy version | The semantics of mechanical judgements; the slot policy | See §3 "The version of judgements" |
  | Sync protocol version (not used in the first version) | Between nodes | Negotiated at handshake |

## 7. Runtime and process model

This section describes how the service process runs: a tenant has only one writer at a time, confirmed writes are not lost after a crash or power failure, and how background tasks are executed. The rules here are what keep data from being corrupted during rolling deployments, process crashes and routing flapping.

### Processes, the single writer, serial writes

- **The saveslot service process**: one Node (or Bun) process carries HTTP, MCP and the scheduler of background tasks. In the cloud service there are multiple processes, each tenant is routed to a fixed process, each active tenant has one database connection, and idle ones are closed ("Technology choices" in the positioning document).
- **The single writer and the ownership epoch**: the storage of a tenant is written by only one process at a time.
  - Each time a tenant is opened, the ownership epoch is increased by 1 and recorded in the storage; each write transaction checks the epoch under the lock, and a mismatch means that another process has taken over, so this process gives up the tenant and clears its in-process cache.
    This way, even when connections are closed when idle, during rolling deployments and during routing flapping, an old process will not corrupt the data.
  - PGlite:
    - **Lock**: an operating-system file lock on `saveslot.lock` in the data directory, obtained through a native extension that ships with prebuilt packages (the Node standard library has none); when the process dies the kernel releases it, and it does not rely on the pid (pids get reused). The lock file serves only as the object to lock and no content is written to it.
    - **Owner file**: `saveslot.owner` records a random token, the start time and the epoch, and is replaced atomically by "write a temporary file, rename". It is read once at the start of each write transaction and once before commit, and a token mismatch means the tenant is given up: the DB Worker is terminated directly, **with no shutdown checkpoint** (otherwise the pages of the old instance would be written back into the new owner's database). The epoch in the database is still recorded and checked as usual; but a PGlite old instance reads `meta` from its own buffer pool and cannot see the new value, so on PGlite the owner file is authoritative.
    - **Primary and secondary lines of defense**: the real line of defense is the kernel lock, which "does not fail as long as the holder is alive"; the owner check is the last one, covering only lock failures such as the lock file being deleted or replaced, and it cannot stop the write-ahead log already written out at the moment of failure. Therefore PGlite must not switch to a lock that expires (a heartbeat, a timeout or the like); no cleanup of saveslot's own deletes `saveslot.lock` and `saveslot.owner`.
    - A warning is given when the data directory is detected to be in a synced folder such as iCloud Drive or Dropbox.
  - **The lock at the level of the local service process**: besides the single-writer lock in the data directory, when the local service process starts it first takes the same kind of operating-system file lock on `run/saveslot.lock` under the home directory, to guarantee that one home directory has only one service process and that the control-plane files (under `control/`) also have only one writer; if it cannot get it, it exits. `saveslot init` and `init --rotate-session` also take this lock, and judge from it whether the service is running. The lock file likewise serves only as the object to lock and no content is written to it, and no cleanup deletes it; when the process dies the kernel releases it, and a process started again gets it directly. After getting the lock, if a live service is answering on `run/saveslot.sock` (it can be connected to), startup is still refused, the lock is put back, and that service is not taken over. When listening, the socket is first bound to a name dedicated to this process (`run/<pid>.sock`), then put at `run/saveslot.sock` by a hard link, and the dedicated name is deleted (when the listener is closed the system deletes the file by the path it was bound with, and this path must not be one that another service may be occupying). A link is used and not a rename: when a socket is already there the link fails; if nobody answers, it was left by a dead process, so it is deleted and linked once more; if someone answers, it is not displaced, and startup is likewise refused. `run/saveslot.pid` is written only after the link succeeds. At startup, any `<pid>.sock` under `run/` that nobody answers (left by a process that died during startup) is deleted as well. On exit the socket and the pid file are deleted, but only the two that it still created itself (identified by device number and inode): when the home directory has been moved while the service is running and another service is already at the original path, the files there belong to that service and are left alone. A service that exits because it lost ownership of storage (`ownership_lost`) no longer writes anything by path into the home directory: `run/last-failure.json` is not written (the reason goes only into its own log), and when the log exceeds its limit it is rotated only if the file at the path is still its own. A known boundary: after the home directory is moved, the old service still reads `control/credentials.json` by path (read-only) when recognizing sessions, and 0.1.0 does not handle this.
    - For the basis see the result report of the single-writer lock experiment ([`../process/experiments/exp-8-single-writer-lock.md`](../zh-CN/process/experiments/exp-8-single-writer-lock.md) (Chinese)).
  - PostgreSQL: routing guarantees one process, and the epoch is the fallback.
    - **Two processes creating the tenant of one user at the same time** (in the first version one deployment is one process, so this does not happen): both register the same tenant (§5) and each opens its database, the later opener takes over, and the earlier one fails with `ownership_lost`; calling again returns the tenant that was created, with only one database and only one genesis event.
    - **Connection**: each open tenant has one connection, reads and writes take turns in the same queue within the process, and there is only one transaction at a time.
    - **Lock and epoch**: each write transaction first takes the tenant's advisory lock at the start, then checks the epoch in `meta` under the lock, and on a mismatch gives up the tenant and closes the connection; the increment by 1 at tenant opening takes the same lock, so it is queued behind any write transaction in progress. Values committed by other connections are visible to this connection, so the epoch in the database is authoritative, and there is no owner file or lock file. The scope of the lock is the database, and each tenant has a database of its own, with the key being a fixed constant.
    - **A read transaction takes one snapshot** (repeatable read, read-only): writes committed by other processes in the meantime do not show up between two statements of the same read transaction. On PGlite there is only one connection, so a read transaction is naturally like this; the kernel's read path is written with this in mind.
    - **Connection loss**: the tenant storage enters a failed state, all later calls are refused, and the host closes it and opens it again; there is no reconnecting inside the storage (reconnecting amounts to reopening and would have to increase the epoch by 1 again). When the connection is lost after `COMMIT` has been sent and before the reply arrives, the write may or may not have been committed: the error in this case (`commit_unknown`) is given separately from "certainly not committed" (`connection_lost`), and the backend neither retries nor guesses.
- **Writes are serial per tenant**: queued per tenant within the process, and the advisory lock is taken again inside the transaction; `seq` is taken from the database inside the transaction, which is the commit order. The writes of background tasks go through the same queue as foreground writes.

### PGlite and PostgreSQL

- **The real model of PGlite**: PGlite is a single-connection instance, and several instances opening the same directory would corrupt it, so **the whole PGlite instance lives in a dedicated DB Worker, and both reads and writes queue through it**.
  - A timeout can only terminate the entire Worker, which amounts to a database crash once, with crash recovery on restart, and it would interrupt the write transactions queued. So **the main line of defense is up front**: write admission estimation, and rejection at compile time of high-cost constructs (applicable to derivation rules, dry runs and restricted SQL alike); a timeout is only a last resort, and whether it is enabled is decided by the sandbox experiment.
  - **The instance stays resident and is not opened and closed on the request path**: the DB Worker of each tenant and the PGlite instance in it are opened when the service starts and stay open until the service stops, even when idle; for occasions that must reopen the storage, such as export, import and restore, a new Worker is used. The reasons: opening a storage once takes several seconds; repeatedly instantiating and destroying the Wasm instance of the database in the same process occasionally triggers a runtime assertion that takes down the whole process.
  - **When the DB Worker exits unexpectedly, it is not reopened inside the process** (the service exits by itself with a non-zero code in only three situations: the DB Worker exits unexpectedly; reopening the tenant fails after an import; writing the eval result log fails, which happens only under the test clock. The common principle is that in these three situations continuing to serve externally would give wrong results, so it stops. Other failures, such as a check failing when a tenant is opened, are cases where the service has not yet started serving and did not pass the check, and are not something going wrong during service: the service stays in a failed state and reports the reason in the health check until it is stopped, and does not exit by itself, so that it is not pulled up again by something external and restarted repeatedly; meanwhile a request on `/v1` is answered `unavailable` (`stopping`, without `retry_after`), and while it is stopping `stopping` with `retry_after`): the service is marked failed and exits with a non-zero code, and is started again by something external (the automatic launch of `saveslot mcp`, launchd or systemd); the process that is started again takes the lock and opens the tenant in the order above (the storage does its own crash recovery, then the checks of `openTenant` in §4), and serves externally only after the checks pass.
  - A slow query blocks this tenant's writes for up to the timeout; this is acceptable for a single local user, and the upper bound of the delay will be stated after the experiment.
- **Restricted SQL on PostgreSQL**: a read-only role, a read-only transaction, `statement_timeout`. In the first version, restricted SQL shares the tenant's one connection with writes and executes serially.
- **Durability**: confirmed writes must not be lost after a crash or power failure.
  - PGlite on Node does not write to disk by itself: the default startup parameters carry `-F`; with it removed, its file system layer still does not hand synchronous calls to the host. saveslot's approach: remove `-F`, set `wal_sync_method = fsync`, and install into NODEFS a hook that calls the host `fsync`.
  - On opening, these settings are read back and self-checked: the commit made at opening must synchronize `pg_wal` through the hook, and if not, opening is refused (`durability_not_applied`).
  - **The size of the write-ahead log**: PGlite runs PostgreSQL in single-user mode, with no checkpointer process, and even when the write-ahead log is written up to `max_wal_size` it does not start a checkpoint by itself (only under a postmaster does that happen), so `pg_wal` in the local directory keeps growing with writes. saveslot's approach: after the reply of a write transaction is sent, the main thread checks the owner file once more and then asks the DB Worker to check: if the write-ahead log since the last checkpoint exceeds 64 MiB, it executes one `CHECKPOINT`; an instance that has lost ownership does not checkpoint. `max_wal_size = 64MB` and `min_wal_size = 32MB` limit the segments kept for reuse after a checkpoint, and are read back and checked at opening as well. When the checkpoint fails, the instance may already be broken (an fsync failure in a checkpoint causes a PANIC), so one log line is recorded (`checkpoint_failed`, carrying only the error code), the DB Worker is ended, and the storage enters `worker_failed`; from then on it is the same as the unexpected exit of the DB Worker above: the service exits with a non-zero code and is started again by something external; the writes confirmed before that are already on disk and are not affected.
  - **Statistics**: in single-user mode there is no autovacuum either, so nothing gathers the planner's statistics for these tables; without them the planner chooses plans by default estimates, and past a certain table size a plan can turn into a scan of a whole index or table. So in local mode the kernel gathers them, at two points: when the storage is opened (before serving; the opening that follows an import or a restore swapping in a new storage is one of these), and after the reply of a write transaction (where the checkpoint is checked, after it). Only when the statistics are stale: the log's last `seq` is past the rows `events` was last counted with, plus 50, plus a tenth (PostgreSQL autovacuum's default threshold; a table never counted counts 0 rows). `events` only stands for the store: every write appends to it, but one event brings a varying number of business rows and blocks, so another table's statistics can go stale before it. It runs `ANALYZE` on the tables under public, outside any transaction, with three exceptions:
    - `content` is analyzed in a transaction of its own with a statistics target of 10 (the default is 100): the sample is 300 times the target, `content` is by far the largest table and ANALYZE's time goes almost all into reading its sampled pages, while the kernel chooses no plan by its histogram: its rows are found by `seq`, and the `LIKE` conditions on `path` and `body` apply to rows already found by `seq`;
    - `content.body` and `events.header` get no statistics: their most common values are the user's content itself, so gathering them would keep another copy of it in `pg_statistic`, and none of the kernel's conditions on them (`body IS NOT NULL`, a `body LIKE` starting with a wildcard, expressions on `body::jsonb`; none on `header`) can use them;
    - `events` goes last and on its own: outside a transaction `ANALYZE` commits table by table, and the count of `events` is the mark that a run got through; one that fails or is stopped half way leaves it as it was, and the next check finds the statistics stale again.

    Statistics are not data: they are not in the log and do not affect replay or reconciliation. A failure only writes one log line (`analyze_failed`, carrying only the error code), and fails neither the write nor the opening; a process ended in the middle of a run writes no such line, and at the next opening the statistics are stale and gathered again. In server mode PostgreSQL's autovacuum gathers them; saveslot does nothing more.
  - The hook depends on PGlite's internal structure, so the PGlite version is pinned to the patch number; upgrading PGlite requires rerunning step one of the durability experiment (on both platforms) and the unit test of the hook count.
  - Whether the target is met is confirmed by the durability experiment (experiment 1 in [`07-scope-v1.md`](07-scope-v1.md); for the result report see [`../process/experiments/exp-1-pglite-durability.md`](../zh-CN/process/experiments/exp-1-pglite-durability.md) (Chinese)); if it is not met, it is replaced by the native PostgreSQL packaged with saveslot.

### The recorded instant

- **The recorded instant of an event = max(`now` of the calling context, the recorded instant of the previous event).** It is not strictly increasing and equality is allowed; the order is decided by `seq`. Monotonicity is guaranteed by the kernel, because only the kernel can see the previous event.
- Every judgement in this operation that concerns "now" uses this value: the idempotency window, the computation of the grace period's expiry instant, and "whether the effective start of a state table is earlier than now". What is written into the event is also this; replay uses only the value recorded in the event.
- The comparison of whether something is due (whether the grace period has passed) compares `now` of the calling context with the expiry instant recorded in the event.
- When the clock is set back, or wrongly jumps into the future and is then set back, the recorded instant of a new event stays at the instant of the previous event until the wall clock catches up; in the meantime a confirmed deletion can only be erased later and never earlier. When `now` is 5 minutes or more earlier than the recorded instant at the log end, `saveslot status` and `saveslot doctor` give a warning and the write receipt carries a notice; the write is not refused, because the kernel has no way to know which clock is right.

### Durability of read_log

Read records are buffered in the process (the main thread), and are flushed to disk at these moments:

- **At the start of any write transaction**, in the same transaction as this operation, so that the `ver` fallback can always see the reads just made. When an operation is rejected (no event is produced), this flush is still committed.
- **Before closing a tenant and giving up ownership** (closing when idle, rolling deployment, routing migration).
- At other times, at the flush interval (initial value 5 seconds).

The loss window: a process crash, or ownership lost before the flush (the old process is then no longer the writer and the buffer cannot be flushed); at most the read records of the latest flush interval that have no write after them are lost.

### Background tasks

- The task bodies are the internal operations of `ops` (§4), and the scheduler is outside the kernel. The background tasks of the first version: flushing and cleanup of read_log, physical erasure and residue cleanup when the grace period expires, build and catch-up of migrations, and advancing the high-water mark. Large-write jobs, cleanup of retired tables, export of cold tenants and background sampling reconciliation are not in the first version.
- In 0.1.0 the only things that run periodically are the flushing of read records (local mode) and the cleanup of expired OAuth records (server mode). The following background tasks are not yet executed in 0.1.0, and what is written here is the design: the retention-period cleanup of read_log (0.1.0 does not clean up, and read records only grow); the periodic advancing of the high-water mark (0.1.0 advances it only when a tenant is closed); the catch-up of migrations (not provided yet, together with migrations that need to rebuild physical tables, [`07-scope-v1.md`](07-scope-v1.md) section 7).
- Task progress is (c) state; if lost, it is derived again from the unfinished migrations and pending deletions in (a).
- **When storage is opened, tasks that are already due are run first**, and this does not depend on a process running all the time.
- **When embedded (later)**: the same kernel runs in the host process, and the host is responsible for opening and closing; the single writer, the format version check and serial writes are still done by the kernel; internal operations are called by a driver shipped with the kernel or by the host; short-lived hosts (CLI, serverless, a suspended mobile app) rely on "run on open" to guarantee that due tasks are eventually executed.

### Physical erasure on time

0.1.0 does not provide privacy deletion yet; the three sections below (physical erasure on time, how residue is cleaned up, privileges residue cleanup needs on PostgreSQL) describe the design ([`07-scope-v1.md`](07-scope-v1.md) section 7).

- Cloud service: when due, the scheduler **actively opens the tenant** and executes the physical erasure, without waiting for the user's next access.
- Local: if the saveslot service is running, it is executed on time; when it is not running, it is executed at the next startup before serving externally. The deletion receipt states this truthfully.
- **Two phases, each idempotent**: (1) the tombstone transaction: append the tombstone event, clear the listed content blocks, and clear the corresponding content in the physical version tables, item entries and indexes; (2) residue cleanup: after the transaction commits, call the storage backend's `purgeResidue`, and when it is done advance the residue cleanup progress ((c) state) to this tombstone. If the progress is lost or behind, all tombstones after it are redone.
- **Whether to serve externally on failure** is decided by a single criterion: whether serving externally would make the erased content readable again.

  | Situation | Can the erased content be read through the interface? | Policy |
  |---|---|---|
  | The due physical erasure fails (disk full, lock timeout, backend error) | No: it was already logically deleted at confirmation | Serve as usual; retry with backoff; this erasure is marked "physical erasure overdue" in `saveslot status`, `saveslot doctor` and the item details; in server mode an alert is also raised |
  | The checksum of a content block to be cleared does not match | No | Erase anyway; report it truthfully in `verify` |
  | A statement of residue cleanup reports an error (except privilege errors) | No | Serve as usual; on PGlite treat it as a worker failure (end the worker, the storage enters `worker_failed`, the same path as other worker failures); the progress does not advance, and after reopening it is redone from the beginning |
  | In-place cleanup hits a privilege error (PostgreSQL) | No | Do not keep retrying the in-place sequence: residue cleanup for this tenant switches to rebuild (below), and `saveslot doctor` states that rebuild is used and which item is missing |
  | Residue cleanup did not complete: the criterion is not met, or the wait for snapshots timed out | No | Not a fault: serve as usual, the worker is as usual; the progress does not advance, and it is retried with backoff (initial value 1 minute, doubling each time, upper limit 1 hour, a kernel constant) and also retried at the next opening; `saveslot doctor` and `saveslot status` have a line "residue cleanup not completed" (since which tombstone, the reason and instant of the latest failure), which is a reminder and not a failure |
  | The re-application of deletions in the restore flow is not finished | **Yes**: the restored data does not contain this deletion | Do not serve externally until the re-application is finished |

### How residue is cleaned up

The two backends are the same, determined by the residue cleanup experiment (result report: [`../process/experiments/exp-7-residue-cleanup.md`](../zh-CN/process/experiments/exp-7-residue-cleanup.md) (Chinese)); every step has a control in which "removing it makes the original text of the erased content searchable":

1. `VACUUM FULL` on each affected table;
2. `ANALYZE`;
3. (PostgreSQL) wait until no other session in this database holds a snapshot or transaction ID, for at most 60 seconds: query `pg_stat_activity`, looking only at processes of this database and those that belong to no database (`coalesce(datname, current_database()) = current_database()`), with the condition using only `backend_xmin` / `backend_xid` (these two columns are visible to all roles, while columns such as `backend_type` are hidden from roles without privileges and cannot be used for filtering);
4. `VACUUM FULL pg_statistic`, which must come after `ANALYZE`: `ANALYZE` leaves the old statistics rows (where the frequent values are the original text) behind as dead rows;
5. `CHECKPOINT`, `pg_switch_wal()`, then `CHECKPOINT` twice;
6. The instance runs with `wal_recycle = off` (old log segments are not reused).

Local mode also runs `ANALYZE` from time to time (§7 "PGlite and PostgreSQL", "Statistics"; `content.body` and `events.header` are not among what it gathers). It does not change the steps above: of what it samples, what was sampled before a deletion was confirmed is replaced by step 2 of the residue cleanup itself, and the old rows are removed by step 4; what is sampled during the grace period was still in the tables then, and goes with the physical erasure when it is due.

- **Success criterion**: it succeeds only if "dead but not yet removable" in the report of `VACUUM (VERBOSE) pg_statistic` is 0 after it finishes; `n_dead_tup` is not consulted. If it is not 0, a snapshot is blocking and the old statistics rows are still there: this run does not count and the progress does not advance (the "did not complete" row of the table above).
- The list of statements is fixed in the storage backend and external SQL is not accepted; all statements are idempotent, and after a crash midway or an unfinished run everything is redone from the beginning. Writes interleaved between two statements do no harm: the progress is recorded by tombstone position, and the new writes do not contain the erased original text.
- Cost (a tenant of 100,000 rows, macOS): about 0.3 s on PostgreSQL and about 0.5 s on PGlite; during cleanup a write waits at most about 10 ms on PostgreSQL and about 50 ms on PGlite (on PGlite writes and cleanup share one queue, and wait at most one statement).
- **When the privileges of the next section cannot be obtained** (typically a managed PostgreSQL service): rebuild is used instead: replay the log into a brand-new database / data directory, replace the old one after validation, and then delete the old one. The new directory never had the erased content written into it. Cost: about 8 s on PostgreSQL for 100,000 rows, **during which this tenant is not writable**; the deletion receipt states truthfully that rebuild was used and the period in which it was not writable.
- **Which one is used is decided by a check at startup** (PostgreSQL): at opening it checks whether the connection role has each grant of the next section and whether the instance's `wal_recycle` is `off`; if all are present, in-place cleanup is used, and if any one is missing, rebuild is used. `saveslot doctor` states which approach is in use now; when rebuild is used it states which item is missing and how to supply it. On PGlite in-place cleanup is always used.
- Not handled: old data left in free blocks of the file system or on a solid-state drive after a file is deleted; the deletion receipt says so truthfully.

### Privileges residue cleanup needs on PostgreSQL

If the role that saveslot uses to connect to PostgreSQL is not a superuser, the following four items must be granted at deployment:

| Purpose | Grant |
|---|---|
| `VACUUM FULL pg_statistic` | `GRANT pg_maintain TO <role>;` (a predefined role since PostgreSQL 17) |
| `CHECKPOINT` | `GRANT pg_checkpoint TO <role>;` |
| `pg_switch_wal()` | `GRANT EXECUTE ON FUNCTION pg_switch_wal() TO <role>;` (not granted to `PUBLIC` by default) |
| `wal_recycle = off` | Write it into the instance configuration: `ALTER SYSTEM SET wal_recycle = off;` and then reload (`SELECT pg_reload_conf();`). It is read by the checkpointer process, and `SET` in a session has no effect; for a non-superuser to run `ALTER SYSTEM` requires `GRANT ALTER SYSTEM ON PARAMETER wal_recycle TO <role>;`, or the operator can edit `postgresql.conf` directly |

- Waiting for snapshots reads `pg_stat_activity` and needs no extra grant (`pg_read_all_stats` is not needed).
- **These steps are instance-level**: switching log segments, checkpoints and `wal_recycle` act on the whole instance and not on one database. In server mode each tenant has one database and there are many tenants on the same instance: cleanup is done merged per instance (the table rewrites and the `pg_statistic` rewrite of the tenants that fall due within a period are each completed, and then one log-segment switch and checkpoint is done for all), and not one switch per tenant. A snapshot in another database does not block cleanup of this database (measured), so one tenant's long transaction does not make another tenant's cleanup "not complete".
## 8. The storage abstraction

This section defines the two ports between the kernel and storage, the tables in tenant storage, the capacity limits, and how export, import and restore work. Data stays consistent across a change of backend, a format upgrade, export, import and restore because of the definitions here.

The kernel depends on two ports implemented by the host: **tenant storage** and **anchor storage**. The kernel invariants depend only on these two ports, not on any service-layer component.

### Tenant storage

```ts
type TenantRef =
  | { kind: "pglite"; dir: string }                      // local mode: the data directory saveslot is configured with; embedded: the path the host gives
  | { kind: "postgres"; database: string; cell: string } // cloud service: derived by control-plane routing

interface StorageBackend {
  open(tenant: TenantRef, opts: { create?: boolean }): Promise<TenantStore> // takes the single-writer lock, increments epoch, checks the format version
}
interface TenantStore {
  write<T>(fn: (tx: Tx) => Promise<T>): Promise<T>     // serial write transaction; checks epoch at the start
  read<T>(fn: (tx: ReadTx) => Promise<T>): Promise<T>  // on PGlite, in the same queue as writes
  purgeResidue(): Promise<void>                        // cleans up plaintext residue after physical erasure; method and criteria in §7 "How residue is cleaned up"
  snapshot(): Promise<SnapshotRef>                     // physical snapshot, only for speed; treated as a backup (not in the first version)
  formatVersion: number
  close(): Promise<void>
}
```

| Backend | Used for | A tenant corresponds to | Supported versions |
|---|---|---|---|
| PGlite | local mode, SDK embedding | one data directory | PostgreSQL 18.6 and later, as embedded in PGlite |
| PostgreSQL | cloud service, self-hosted | one database per tenant, grouped by cell | 18.x; replay consistency across major versions is confirmed by the replay-consistency experiment |

On PostgreSQL, a tenant's database is created with encoding `UTF8` and the collation `C.UTF-8` from the builtin provider: ordering is by code point, and character classification uses PostgreSQL's own tables, so it does not vary with the operating system. When a tenant is opened, the following are checked in order: the server major version, the encoding, the collation, the storage format version, and the fixed session settings recorded when the database was created; then epoch is incremented. If any item does not match, opening is refused and epoch is left unchanged. The mapping from cell to connection parameters is given by the host when it constructs the backend; `TenantRef` carries only the name of the cell and the name of the database.

### Anchor storage

Anchor storage keeps **what must still be remembered after tenant storage has been replaced as a whole**: deletion register entries, the `seq` high-water mark, the restore count, the "restore in progress" mark, and the "import in progress" mark.

0.1.0 does not provide privacy deletion yet; the deletion register below (including re-applying deletions from the register after a restore) is design ([`07-scope-v1.md`](07-scope-v1.md) section 7).

```ts
interface AnchorStore {
  // every write operation must be on disk before it returns
  read(tenant): Promise<Anchor>                                  // a tenant that was never written reads as an empty anchor (no register entries, high-water mark 0, restore count 0)
  putDeletion(tenant, entry: DeletionEntry): Promise<void>      // add, or replace the whole entry
  removeDeletion(tenant, deletionId): Promise<void>              // does nothing when there is no such entry
  advanceHighWater(tenant, seq): Promise<void>                   // only increases
  beginRestore(tenant, restoreId): Promise<Anchor>               // sets "restore in progress" and increments the restore count; if one is already in progress, returns it as it is
  endRestore(tenant, restoreId, highWater): Promise<void>        // clears "restore in progress", the high-water mark takes the larger of the two; rejected when no restore is in progress or the ID differs
  beginImport(tenant, importId): Promise<void>                   // sets "import in progress" (with the import ID); rejected when the anchor is not empty (it has deletion register entries, the restore count is not 0, or any in-progress mark exists, including one for the same import)
  endImport(tenant, importId,
            r: { deletions: DeletionEntry[]; highWater: Seq; restoreCount: number }): Promise<void>
                                                                 // in one write to disk, records all deletion register entries derived from the imported log, the high-water mark (the larger of the two) and the restore count, and clears the mark; rejected when no import is in progress or the ID differs
  abortImport(tenant, importId): Promise<void>                   // only clears the "import in progress" mark, writes no entries (used for rollback); does nothing when there is no mark (it may be called twice on re-entry), rejected when the ID differs
}
```

- **The high-water mark never decreases on any path**: `advanceHighWater`, `endRestore` and `endImport` all take the larger of the stored value and the given value.
- A register entry, high-water mark or restore count that does not fit the shape of the port (a status or kind not in the enumeration, a `seq` that is not a positive integer, and so on) is rejected, and nothing is written.
- **It must be stored separately from tenant storage and backed up separately.** When the two are restored together, the kernel can neither make up for it nor detect it. This is a stated boundary.
- **Durability requirement**: every write is on disk before it returns; when a deletion is confirmed, the register entry must be on disk before the tenant transaction is committed.
- The interface is in the `kernel` package; the authoritative definition of the fields and statuses of register entries and of the comparison table is in "After deletion · The deletion register" in the data model.
- Who implements it: the saveslot service implements it in `service` with the control database (§5); kernel tests use a file implementation; in SDK embedding the host implements it, or uses the file implementation shipped with the kernel with a path the host specifies.
- Who calls it: `ops` holds it; the lower modules only return "what is to be written into the anchor", and `ops` calls it before and after the commit in the order the data model prescribes.
- **When the high-water mark advances**: after a deletion-related tenant transaction commits, when a register entry is changed to a new status; before a tenant is closed or ownership is given up; and when 1000 events have been appended or 60 seconds have passed since the last advance (the two numbers are initial values). Each time it advances to **the end of the log at that moment**. The advance is not done inside a write transaction, and its failure does not affect the write. When a deletion is confirmed, "write the register entry first" writes only the register entry (`intent`) and does not advance the high-water mark: the high-water mark never exceeds the committed end of the log, so a restore event never takes the `seq` of an already committed event.

**The business table `t_<table ID>_v<n>`.** A `zoned_datetime` field also has a column `f_<field ID>__zone` that stores its time zone (the field value is an instant plus a time zone, and `timestamptz` can store only the instant; restricted SQL does not expose this column, and replay comparison and export count it as a content column). Event tables and timeless tables have a revoked mark; state tables do not (revoking there is an interval without a value) and have an interval end instead. Each `zoned_datetime` field also has an internal date column: the date of this instant in the slot time zone, computed in the application layer by `apply` when the event is applied (the `saveslot_date(f)` of restricted SQL is rewritten to this column), and no time zone conversion is done in the database. It is derived from the log and the time zone database, and the replaying side's time zone database prevails: `meta` records the version of the time zone database used to build the current column, and when a tenant is opened and the version differs from the current one, this column and the derived partitions that depend on it are rebuilt locally (a deterministic local rebuild that writes nothing to the log). The slot time zone can be changed (`change_timezone`, a deterministic conversion that needs confirmation): in the switch transaction this column is recomputed under the new time zone, and the derived tables that depend on it are rebuilt along with it. 0.1.0 does not provide `change_timezone` and `change_time_field` (changing the time field of an event table) yet: they are migrations that need the table to be rebuilt, and a draft reports `not_in_this_version` when it is committed; this is design ([`07-scope-v1.md`](07-scope-v1.md) section 7).

**Placement of cells in the version table `t_<table ID>_v<n>__ver`.** Cells are placed according to the state at the end of an operation; the details are in the next paragraph, "The version table stores values, not references to content". "Existence" (revoking and restoring) also takes a cell, with the field ID using the fixed value `existence`: on event tables and timeless tables, a revoke adds one cell marked revoked, the field cells stay as they are, and a restore also adds a cell (its provenance is that restore item); on state tables, a revoke in effect puts an `existence` cell marked revoked on those stretches where the entity is left without a value, only where a field item underlies it. In a stretch of a state table that has no value, only the fields that decide "has a value" (the required fields; all fields when there are no required fields) are placed in cells, to say why there is no value: a field cleared by a no-value item gets one cell with an empty value marked no value, and its provenance records that item; the other fields are not placed. In a stretch that has a value every field gets one cell and none is marked no value, including fields that were cleared and fields never written. So "this stretch has a value" if and only if the stretch has a field cell not marked no value, whether or not there are required fields; "no value" is marked only on the field cells of state tables, and is a different thing from "revoked" (marked only on `existence` cells)

**The primary key of `base_sources` and constant backfill.** The row or entity ID is in the primary key because one `schema.switched` backfills values for many rows (one `write.base` concerns only one row). Where the constant `backfill` fills in is registered according to the record of the switch event, not computed on the fly: for event tables and timeless tables it is a list of row IDs, for state tables it is entities and intervals (the intervals come from other contributions and carry `deps`; when those contributions are deleted, the backfill for this stretch ceases to exist with them); when a later deletion leaves a field empty somewhere, the constant is not backfilled again.

**The columns of `base_sources`.** **Every kind of source that a base write itself carries gets a row for every item**, and deletion replay looks here for "which contributions have sources that were deleted": value sources (or carried references, schema constants) come first; for an item that has no value source, the operation source of this base write (`op_sources`) takes their place at the front (when there is none at all, one operation row that points to no source data is written); for an item that has value sources, operation sources follow the value sources; the sources of the interval parameters (`valid_sources` of §5.7 of the event format: writes and revokes with interval parameters on state tables all have this block) come after that. For a write triggered by `resolve`, the operation source is recorded on `item.resolved` and not in the base write, so the table has no operation row for it; it does not affect values after a deletion (an operation source is only a control dependency). The ordinals run in sequence; the first row of each item (ordinal 0) is its value source or the row that takes their place; a schema constant does not point to source data, and its event seq is that `schema.switched`; the status in effect and resolved interval of this item at present (recorded at write time, or restated by a deletion event, whichever is most recent); the block that most recently gave the content of this item (`given_seq`, `given_path`: when a deletion event has restated it with a new value, with "no value", or with only a registration, it is that deletion event and its `restated/<k>`, and `apply` reads it when it reads the content; a restatement that only restates the judgement and gives no content does not change it; when it has never been restated this way it is empty and the original field block is read. The judgement itself is in the status and interval columns of this row); whether it is corroboration and its explicit endpoints (`corroboration_ends`: for a corroboration item on a state table it is the list of its corroboration endpoints, taken according to §5.7 of the event format, and the empty list when there are no explicit endpoints; empty for items that are not corroboration and on tables that are not state tables; an item with several sources has several rows, each the same; later writes and reverts do not change it, whether an endpoint still counts at this moment is judged from the log at resolution time, and it is recomputed when a deletion restates this item); whether it has been registered by a revert (`undo` or taking the previous value) (which operation, which intervals).

**The version table stores values, not references to content.** Reading as of an instant queries the version table directly and does not go back to the content table. It records by cell, and each cell carries the contribution that produced the value: on physical erasure, `apply` finds the corresponding cells according to the content blocks the tombstone lists and clears the values in them; in a state table the segments of one version come from different writes and land in different cells. When several ops in the same request change the same entity, the version table places cells according to the state at the end of the operation: a later op overwrites an earlier op's value in the same cell (for example when the two ops have the same start of valid interval), and the cell records the last contribution that gave a value, so under one operation number a cell has only one version. The primary key is not extended to the event `seq`: the granularity of reading as of an instant is the operation number to begin with, and intermediate states within one operation are not visible outside. The cost is that historical values are stored twice, and in return reading as of an instant is an ordinary SQL query.

**(c) Local running state** (not exported, not replayed)

| `meta`: the storage format version, the tenant ID, the ownership epoch, the fixed session settings, the version of the time zone database used to build the current internal date columns | `store` | epoch lost: it is incremented again at the next open. | `read_log` (one row per read: read ID, instant, actor, task, position of the state seen, whether it was a historical read by recorded instant, what was read, structure fingerprint, valid-time condition) | `audit` | the read history does not go with the rows after an export; the effect of a correction cannot find earlier reads | Yes |

`audit` only stores and retrieves the `possibly_affected` marks; the comparison of historical values needed for "remove the mark when the value is restored" is done by `read`, and `ops` calls it after writes, deletion confirmations and cancellations.

**Fixed session settings** (written into `meta`, the same in both backends; replay consistency depends on them): encoding `UTF8` (`length` and `substr` counting by characters depends on it); time zone `UTC`; the kernel's own tables and the text ordering of restricted SQL use the `C` collation; decimal numbers use `numeric`; date output format ISO; backslashes in string literals are not escaped (`standard_conforming_strings = on`; the literals printed by restricted SQL depend on it). On the business level, "which day" is converted in the application layer by the slot's time zone, and does not depend on the database session time zone or on the time zone databases the two backends each carry; the version of the time zone database used by the application layer is pinned with the saveslot version; the version used to build the internal date columns is recorded in `meta` (see the business table row in the table above).

### Capacity limits and measured values

All three design choices of storage get more expensive linearly with the amount of data: every base write refreshes the affected derived partitions in the same transaction; all versions are kept, with no compression and no downsampling; each row carries its own provenance records (the sources table) and per-cell version records (the version table). The first version does not limit write frequency, does not reject tables with many rows, and does not design storage specially for series data; it targets records produced at a human pace ("The scenario test" in the positioning document). Write admission governs the size of one write, not the size of a table.

**Two limits**, computed per table (taking `profile.rows` from the catalog profile), one set per backend, released with the kernel version:

| Limit | Key name | Definition | PGlite | PostgreSQL |
|---|---|---|---|---|
| comfort limit | `comfortable_rows` | while a table's row count is within it, common writes have p99 ≤ 50 ms, and cold start and reading as of an instant are within the acceptable range recorded by measurement | 100,000 (placeholder initial value, awaiting experiment 9) | 100,000 (placeholder initial value, awaiting experiment 9) |
| tested limit | `tested_rows` | the largest scale point that the capacity experiments ran and did not record as "fails at this point". It is that scale point itself, with no interpolation between two adjacent points; when scale points are more than a factor of two apart, this is how coarse the resolution of this limit is | 1,000,000 (placeholder initial value, awaiting experiment 9) | 1,000,000 (placeholder initial value, awaiting experiment 9) |

- Above the comfort limit and not above the tested limit: the table profile of the catalog carries `scale.level: "large"`; above the tested limit: `beyond_tested`. It is computed at read time from the current row count, does not enter an event, and is not a data flag ("Catalog" in the data model).
- The "data scale" item of `saveslot doctor` lists the tables over a limit, and at the tenant level the total number of events, the size of the data directory and the duration of the most recent cold start, and compares them with the measured range; the result is a "reminder", not a "failure". In server mode the hint in the catalog covers this, and capacity monitoring on the operations side belongs to experiment 3.
- No reminder in the write receipt, no rejection of writes, no automatic downsampling.

### Format versions, export, import and restore

- **Format version check and data compatibility across versions**: from 0.1.0 on, upgrading saveslot does not make existing data unopenable (the decision and its reasons are in [`data-compatibility.md`](../zh-CN/process/decisions/data-compatibility.md) (Chinese)).
  1. **A new version can open old data.** Any released version can open data written by any earlier released version (0.1.0 and later). When the stored format version is lower than what the kernel supports, the kernel **upgrades it in place** to the current format, without requiring the user to export first and then import.
  2. **An old version does not open new data.** When the stored format version is higher than what the kernel supports, it **refuses to open** (`format_too_new`) and tells the user to upgrade saveslot / the SDK. There is no downgrade.
  3. **Before 0.1.0 is outside the commitment.** Format versions before 0.1.0 were all from development and are not upgraded: opening is refused (`format_too_old`) and the user is told to initialize again with a new version.
  4. **Export files are also backward readable.** Any later version can import a file exported by 0.1.0 or later. The manifest of an export file carries its own format version number (`saveslot_export`), and it is frozen together with the event format ([`07-scope-v1.md`](07-scope-v1.md) "The freeze point of the event format"): it only grows and is never changed, and an incompatible change needs a decision draft first.
  5. **Configuration and credentials keep working across upgrades.** A new version reads the old `config.toml` and the client's profile files as before; for a key that was renamed, the old name is recognized for at least one more minor version, with a hint to use the new name. Credentials already issued remain valid after an upgrade; when they must be invalidated for security reasons, the release notes say so.

  This commitment is about data, not interfaces: before 1.0, the operation contract and the CLI may change incompatibly between minor versions, but existing data is not made unopenable, and existing configuration and credentials are not invalidated.

  **What the commitment covers**

  | Object | Within the commitment? |
  |---|---|
  | Tenant storage: the log (event headers and content), the tables derived from the log | Yes. The log is kept as it is; the tables derived from the log are upgraded to the new format, or rebuilt from the log |
  | Anchor storage: deletion register entries, `seq` high-water mark, restore count, in-progress marks | Yes. It is outside the log and cannot be rebuilt, so the upgrade must carry it over as it is |
  | Export files | Yes (item 4) |
  | Read records | Yes. Kept until its own retention rule expires them |
  | Other local running state that says "what happens if it is lost" (request keys and so on: losing them only loses idempotency) | Kept where possible, not promised. An upgrade may clear or rebuild it, and the upgrade notes say so |
  | The control database (server mode): accounts, credentials, tenant directory, anchors | Yes. The same rules as tenant storage: in-place upgrade, step by step, re-entrant, with a sample kept |
  | The local `config.toml`, the client's profile files, credentials already issued | Yes (item 5) |

  **The current state of 0.1.0**: there is only one storage format (format 5), one event format (v1) and one export file format (1). The check at open implements only two refusals: below 5 reports `format_too_old`, above 5 reports `format_too_new`; the in-place upgrade mechanism is not implemented, and 0.1.0 does not need it. **The mechanism is built before the first change of the storage format**: a change that moves the format to 6 must be released together with the upgrade from 5 to 6.

  **Requirements for the upgrade mechanism** (it must meet them when built):
  - **Step-by-step upgrade**: each time the format changes, write one step "from the previous format to this format"; data that is several versions behind goes through every step in turn, and no shortcut across steps is written.
  - **The log is not rewritten**: an upgrade changes no event header and no content block (K1); only the tables derived from the log and saveslot's own metadata change. The last resort of an upgrade is always "rebuild the tables derived from the log from the log".
  - **Re-entrant after a crash**: if the process stops halfway through an upgrade, the next open finds either the old format, which can be upgraded again, or the new format; it must not stop in between.
  - **It matches after the upgrade**: when the upgrade is complete, the tables derived from the log are identical to the result of replaying this log from an empty store (K12).
  - **A sample is kept for each released format**: when a new format is released, store data written by that version in the test fixtures (`packages/test-backend/fixtures/storage-format/<format>/`), one for local mode (a data directory, including the anchor) and one for server mode (the control database and a tenant database), generated by `scripts/make-format-sample.ts`. From then on the tests of every version open every sample, upgrade, and check as in the previous item ([`11-claims.md`](11-claims.md) C1).
  - **The control database follows the same requirements**: step by step, re-entrant, and after the upgrade the accounts, credentials, tenant directory and anchors are all there.
  - **Format upgrades come in two kinds**: reversible compatible extensions (adding a table, adding a nullable column) are released with the version; irreversible ones are released on their own, with a gradual rollout first, and a snapshot is kept before release. Otherwise, if a new version upgrades the format and the deployment is then rolled back, the old version refuses to open the data and there is no way back.
- **Export does not depend on the physical format**: export = all type (a) events (the schema definition itself is also an event); replayed through `apply`, any backend arrives at the same type (b) state. Type (c) is not exported.
  - "An export can be replayed" is verified by tests (§11 "Export replay"); the user operation that loads an export back is the import below.
  - **Content in the grace period is not exported by default**: a content block pending erasure is replaced by a placeholder "pending erasure (#n), not exported", and the rest of the content of the same event is exported as usual; the chain of event headers can still be verified, and the exported content carries checksums; a user session can explicitly choose to include it, and the export receipt says so.
  - An export file can be wrapped as a whole in an age file by the CLI (passphrase encryption); the wrapping is not part of the export format, and neither the kernel nor the service layer touches it.
  - **Export does not hold on to the tenant**: the manifest fixes `upto` in the first read transaction, and after that the log is read in batches, each batch in a short read transaction reading only `seq ≤ upto`; waiting for the reader to take the data (backpressure) happens between two transactions, so when the reader is slow or paused, the other reads and writes of this tenant go on as usual. The two backends do the same. Each batch re-checks the pending deletions: when inclusion of pending-erasure content was not requested, a deletion that did not exist when the export began aborts the export (its content may be in a later batch). When the reader has not taken a batch of written data for 30 seconds (an initial value, a kernel constant), the server gives up the export and cuts the connection; when the reader leaves midway, the next write fails and reading the log stops. Neither cutting nor aborting sends an end block, and the reader recognizes from the manifest's count and `upto` that it is incomplete.
- **Import is supported only into an empty tenant**: it appends an export event by event as it is and hands it to `apply`, and does not re-execute contract operations one by one (that would judge again and assign `seq` and IDs again, and would not produce the same log). A tenant is empty if and only if the log has only the genesis event, and the anchor has no deletion register entries, the restore count is 0, and there is no "restore in progress" or "import in progress" mark. Merge import is later. The authoritative definition of the rules and of what cannot be brought over (read records, credentials and the control plane, the source's deletion register) is in "After deletion" and "Integrity and provenance" in the data model; the engineering steps are:

  | Step | What is done |
  |---|---|
  | ① Validate the file | The same checks as `log.verify` (event header chain, content checksums, count and end), only with the file as the object; validated while reading, and stops at any failure |
  | ② Replay into staging storage | Open a new tenant storage named by the import ID, append event by event as it is and hand it to `apply`; content blocks are placed according to the three states in the export (present, removed, pending-erasure placeholder) |
  | ③ Closing events | Append the import event at the end of the staged log, then add tombstones for the pending-erasure items that are placeholders. If ① to ③ fail (a file that does not qualify is rejected in ① or ②, ③ cannot be written) or ④ refuses to set the mark, the tenant is unchanged: in server mode, first reply and release the exclusive hold, then delete this run's staging storage outside the exclusive hold, and only after the deletion remove it from the tenant directory. A non-empty tenant is rejected before ①, and no staging storage is created; if the directory still records a staging database left by a previous run, it is likewise deleted after the reply |
  | ④ Set the mark | `beginImport`: set "import in progress" in the anchor, and check the empty-tenant condition once more at the same time |
  | ⑤ Swap in | The staged storage becomes the target tenant's storage, and the original one is discarded (it holds only the genesis event). The swap is one atomic step: in local mode it is a directory rename (after the rename, fsync the parent directory of the data directory, to be on disk before the anchor is written in ⑥), in server mode it is one update of the storage pointer in the tenant directory. In server mode the original one is deleted after the import reply, outside the exclusive hold |
  | ⑥ Rebuild the anchor and clear the mark | `endImport`: in one write to disk, the deletion register entries derived from the log (the deletions still pending), the high-water mark (the end of the log) and the restore count (the value in the import event), and clear the mark; serve outside only after that |

  - An export can come from a tenant that was imported into, and the end of its log can be just the import event of that import; the import goes on as usual: ③ only checks that the end of the staged log agrees with the manifest's `upto` and `upto_hash`, and does not look at what the last event is. For that reason, "the most recent import event" cannot show that ③ was done: before ④ sets the mark, check that the most recent import event in the staged log is exactly the one ③ appended this time (its `seq` and `imported_upto` both agree with what ③ gave); after it there can only be tombstones that ③ added for pending-erasure placeholders, and if it does not match nothing is changed.

  - **Re-entry**: anchor storage and tenant storage have no common transaction, and re-entry relies on the "import in progress" mark. `openTenant` looks at it first; when the mark is present and tenant storage has no import event (a crash before ⑤), the staging storage is discarded, `abortImport` clears the mark, and the tenant is still empty; when it has an import event (a crash between ⑤ and ⑥), go on with ⑥. The criterion looks only at whether there is an import event: the target originally had only the genesis event, and no other import is accepted while the mark is present. A staging storage left by a crash before ④ has no corresponding mark, and is cleared when the tenant is opened. An import in server mode first obtains the tenant's exclusive hold within the process (other requests report `importing` meanwhile, and are not queued), then creates the staging storage, and does not release the exclusive hold from creating the staging storage through ⑥ (including the swap of ⑤): a tenant is not opened while an import is in progress (in the first version one control database has only one process, §7), so a staging storage seen at open without a mark can only be one left by a crash, or the old database that ⑤ swapped out and that could not be deleted after the import completed (after ⑥ the import replies first and releases the exclusive hold, then deletes it; if the service stops halfway through the deletion, crashes or cannot delete it, it is still recorded in the staging location and is not missed), or the staging database of an import that failed before ④ set the mark (a failure also first replies and releases the exclusive hold, then deletes it, and only after the deletion removes it from the directory; when it cannot be deleted it is likewise kept), and every open can clean it up; the open that finishes ⑥ also cleans it up in the same way once the mark is cleared. Without the mark, the tenant's data is complete, and if it cannot be cleaned up, a note is made and service goes on as usual, to be cleaned up at the next open; when the mark is present and it cannot be cleaned up, this open is refused. When the open meets a database that is being deleted in this process (the deletion after the import reply), it leaves it to that deletion and does not wait for it: if the deletion succeeds it is removed from the directory, and if it fails it stays recorded, to be cleaned up at the next open. A new import, inside the exclusive hold and before recording its own staging database, first deletes the one still recorded in the directory from last time; if that one is being deleted, it waits for that deletion to finish and deletes once more (doing nothing if it is already gone), so even if that deletion fails it is not missed.
  - Without this mark, a crash after ⑤ and before ⑥ would leave the tenant neither empty nor matching the anchor: the restore count would still be 0, and the next real restore would increment it to 1, duplicating a `ver` already issued after the import; conversely, if the anchor were rebuilt first and then swapped in, after a crash the end of the log would be below the high-water mark and would be taken for a backup rolled back and sent through the restore process.
  - During an import and while the mark is present, this tenant can be neither read nor written (`unavailable`); resuming from a break point is not supported, so it is either still empty or the import has completed, and retrying is safe.
- **After restoring a backup, a snapshot or an archived cold tenant, the restore process must be run** before serving outside. 0.1.0 does not provide privacy deletion yet, so the parts of the process that re-apply deletions from the register and re-run due deletions are design ([`07-scope-v1.md`](07-scope-v1.md) section 7). The authoritative definition of the steps and of the comparison table is in "After deletion · The deletion register" in the data model; the key points:
  - The process re-enters by the "restore in progress" mark in anchor storage: every open of a tenant looks at this mark (for the order of the checks at open see `openTenant` in §4), and when the mark is present it carries on, whether or not this start came with the restore parameter.
  - In the process, first append the "restore" event (`seq` continues after the high-water mark, with a different node ID, and the restore count is incremented), then re-apply deletions from the register, then re-run the deletions that are already due, and after checking that everything is right clear the mark and serve outside.
  - **Three ways to trigger it**: explicit (locally `saveslot start --restored`, in server mode an operations command); on opening, finding that the `seq` at the end of the log is below the high-water mark; and, when reconciling the register with the log, finding a combination that cannot occur in normal operation. For the latter two, local mode goes through the restore process automatically (there is only one user and no operator, so service is not refused), and server mode refuses to serve outside and prompts the operations command.
  - **What the fallback actually covers**: a rollback to a position before the last high-water mark advance can be detected; a rollback that lands after the most recent advance, with no deletion-related register changes in between, cannot be detected. So a restore should always be triggered explicitly, and the fallback is only a remedy.
  - When the local data directory is restored by a system-level backup (Time Machine and the like) together with the saveslot configuration directory, the register also goes back to that time, and saveslot can neither make up for it nor detect it; the same holds in server mode when the control database and the tenant databases are restored together.
- External files are not in storage (`file_ref` stores only metadata and an excerpt; "Later plans" in the positioning document).

## 9. Tenants and hosting

- **The kernel knows only "tenants", not "users"**: one tenant is one log, one set of `seq`, one storage. In the first version a tenant = a user.
- **Principals are globally unique, independent of tenants**: the IDs of users and connections are global; what the tenant's log records is "a principal's registration in this tenant (membership)", referring to the global ID (K2).
- **Ownership above the tenant is in the control plane**: which user owns which tenant, and which principals can access it, is managed by the tenant directory. From this:
  - **A shared slot (future)** = an independent tenant + membership registrations. The problems it will meet and where they are solved:

    | Problem | Where it is solved |
    |---|---|
    | a connection of another user writes into the shared tenant | kernel: the membership registration event (already designed this way, K2 needs no change) |
    | one user's catalog has to list several tenants together | service layer / surface: aggregate by the tenant directory |
    | the same table name in different tenants | surface: qualified names (already exist) |
    | which tenant a handle or `seq` belongs to | a handle is bound to its tenant (already exists) |
    | where the primary node of a shared tenant sits and how member devices replicate | multi-node design (later) |

  - **Developer-procured hosting (future)** = one tenant per end user, belonging to the "developer / application", expressed by the tenant directory; the kernel does not change. Data ownership and exportability are undecided ("Developer SDK" in the open questions).
- The cluster grouping, connection management, and export and restore of cold tenants of the cloud service are in "Technology choices" in the positioning document and in research/07.
- **Self-hosting on a server (supported in the first version)**: the same code and the same set of configuration items as our cloud service, only deployed by a different party. The differences are only these:

  | Aspect | Our cloud service | Self-hosted |
  |---|---|---|
  | Human accounts | our account system | built-in local accounts: the deployer creates them with operations commands, and registration is not open; the OAuth authorization server is still the one saveslot ships with |
  | Scale | many cells, many processes, archiving of cold tenants | one cell and one process are enough; multi-cell routing and archiving of cold tenants are not enabled. The name of this only cell is fixed as `main`: it is recorded in the control plane's tenant directory as the cell each tenant is in, so it does not change with the connection address |
  | Public address and TLS | our domain | provided by the deployer; TLS is terminated by the deployer's reverse proxy, and the saveslot process listens only on plaintext HTTP (configuring a certificate directly in the process is later); the OAuth resource identifier (RFC 8707) takes the public address in the configuration (`SAVESLOT_PUBLIC_URL`, "Server mode configuration" in [`06-cli.md`](06-cli.md) §4.1) |
  | Handle signing key | environment configuration (KMS in the future) | environment configuration (the file `SAVESLOT_HANDLE_KEY_FILE` points to), kept by the deployer |
  | Rate limits and quotas | on | off by default, configurable |
  | Backup and restore | we do it | the deployer does it; after a restore the restore process must be run (§8) |

  The kernel, the service layer, the contract and the surface are exactly the same; the contract tests are run once more on the self-hosted form (single cell, local accounts).

  **Prerequisites for self-hosting** (on the database side):
  - **PostgreSQL 18**: the instance the cell is on is 18.x (the table of backends and versions in §8 "Tenant storage"), and the backend refuses to open a tenant when it meets another major version. The control database can be on the same instance.
  - **The database role the service uses**: it owns the control database (`server init` creates tables in it); on the instance the cell is on it has `CREATEDB` and can connect to the maintenance database (when a tenant is created, `CREATE DATABASE` is run in the maintenance database, so the tenant database is owned by this role). A superuser is not needed.
  - **Plaintext residue after physical erasure**: to clean it up in place, this role also needs four grants and the instance must run with `wal_recycle = off` (§7 "Privileges residue cleanup needs on PostgreSQL"); if any one is missing, residue cleanup in this deployment uses a rebuild instead, and during the rebuild that tenant is not writable (§7 "How residue is cleaned up").

## 10. Trust boundaries

| Usage | Trusted | Untrusted | How far it is guaranteed |
|---|---|---|---|
| saveslot service · local mode | the saveslot process itself | everything that comes in through MCP / HTTP: the agent, the model, scripts, what the client reports about itself, the original text of source data | every operation through the interface keeps the kernel invariants, and permissions are enforced at the boundary of the saveslot process; **the truthfulness of data and "whether a confirmation came from a person" are delegated to the caller's agent**, and saveslot only guarantees the trace, that a confirmation is bound to its content, and that a deletion can be cancelled. A program on the local machine that can read and write the data directory directly (including an agent with a shell) can bypass saveslot's interface, and saveslot cannot prevent that |
| saveslot service · server mode (cloud service / self-hosted) | the saveslot process and the deployer's operations (in the cloud service that is us, in self-hosting it is the user) | same as above | same as above; no tamper-proof evidence is provided against the operator: the goal of integrity is provenance + guarding against mistakes (see below). Encryption at rest of storage is provided by the deployer at the infrastructure layer (database storage volumes, backups and cold archives on encrypted storage); it guards against the storage medium being read after being taken away, and does not change the fact that the operator can read plaintext |
| SDK embedding (later) | the host application (the owner of the data) | the model, the original text of source data | operations through the saveslot interface keep the kernel invariants; it cannot defend against the host itself (it can open the database directly) |
| SDK connecting to a data center (later) | the saveslot service on the data center side | same as the saveslot service | same as the saveslot service |

**"Untrusted" in the table is in the security sense**: nothing that comes in through the interface can bypass the kernel invariants. It does not question whether the content is true: saveslot by default takes the agent's input as trustworthy and does not judge whether what is written is true or false ("The data layer" in the positioning document).

**The goal of integrity is provenance plus guarding against mistakes, not tamper-proofing**. The authoritative definition is in "Integrity and provenance" in the data model: what can be detected, by what means, and what is not promised are all there. The points at the architecture level: only the kernel can write, and the log is append-only (K1, K3); the chain of event headers detects missing events, reordering and accidental changes to event headers; content checksums detect storage corruption; replay comparison detects that materialized state is inconsistent with the log. Against a party that can write to storage (including the operator) there is no tamper-proofing and no evidence a third party can verify; signed checkpoints, Merkle trees and on-chain content commitments are later planning (§12).

**Telemetry: no data is sent by default**. The saveslot program (local mode and server mode, including self-hosted) by default sends no usage data anywhere; local mode can be used in full without a network. If usage statistics are added in the future, all of the following must hold:

- It is enabled explicitly by the user or the deployer, and nothing is sent while it is not enabled; it can be turned off at any time, and nothing is sent after it is turned off.
- Only metadata such as the runtime environment and counts of feature use is collected; user content is never collected (slot names, table names, rows, field values, source data, evidence, query and SQL text, the text of pending items), nor credentials or information that can identify a person.
- The collected fields are listed item by item in the documentation, consistent with the code.
- A crash or error report sent from the machine also counts as usage data, and likewise must be enabled explicitly and contain no user content; application logs written on the local machine are not telemetry.

The monitoring of its own running state by the cloud service we operate is the operator observing its own service and is not telemetry; it likewise does not write user content into monitoring data.

**Prompt injection surfaces** (all must be wrapped in the untrusted data boundary): the original text and excerpts of source data, text values in query results, the proposed text and `note` of pending items,
the descriptions and aliases written by the agent in a schema, the existing keys and similar keys listed in write receipts, the `instructions` of extraction jobs, user input echoed in error messages, community schemas and SKILLs.
Among them, **actions whose consequences are irreversible** (deletion) have in addition the two-stage process and the 24-hour window for cancelling as a safeguard; all other actions keep history and can be rolled back.

- **Slot names entering the MCP service-level description (`instructions`)** are the only user content in static text, and are not wrapped in a boundary. What holds them back: the character set of names (letters, digits, underscores; no line breaks, no punctuation or angle brackets, so a boundary tag cannot be forged); slot names longer than 32 characters are not listed; each slot gets its own line followed directly by its table count; creating a new slot requires `saveslot.schema` with a scope of all, so few parties can write here. **Table names do not enter `instructions`**: any connection with `saveslot.schema` can, under the default policy, create tables without confirmation, controlling the ordering with a prefix and splitting a sentence over several short table names; table names stay in the result of `saveslot_catalog`, which carries the untrusted boundary. Residual risk: a party holding "`saveslot.schema` with a scope of all" can still create several slot names that read like phrases, and the only irreversible consequence is deletion, which has the safeguard above.
- Generating `instructions` is not a read operation in the contract, does not write a read record, and does not take part in the `ver` / `sv` fallback.

### The test matrix

- **Both backends run everything**: the kernel tests run once on PGlite and once on PostgreSQL. The same test files open databases through `test-backend`, and the backend is chosen by an environment variable at run time; a test file that tests only the own mechanism of one backend (the directory lock of PGlite, the owner file, the DB Worker, host fsync) does not run on the other backend; they are listed one by one with the reason, and the corresponding mechanism is tested in the other backend's own tests. The kernel test files are in `packages/store-pglite/src` and open databases through `test-backend`; the PostgreSQL run is started by `scripts/test-postgres.ts`, which sets `SAVESLOT_TEST_BACKEND=postgres` to switch the backend, and the connection address is given by `SAVESLOT_TEST_POSTGRES_URL`.
- **Replay comparison**: the same log is replayed through `apply` on both backends, and the tables marked "replay comparison: yes" in (b) materialized state (the list in §8) are identical row by row; sample values are chosen by a deterministic rule (the most recent K distinct values by `seq`); in addition, "replay from an empty storage = live state".
- **Export replay**: export → replay into an empty storage → the logical tables of (b) materialized state are identical row by row to the live ones, run in both directions across the two backends (a PGlite export replayed into PostgreSQL, and the reverse); for an export with "pending deletion" placeholders, after replay the business state at the end of the log is identical to the live state. This is the check of the promise that "an export can be replayed".
- **Replay from the start after a tombstone**: once the deletion is due and the tombstone is recorded, replay from an empty storage, and the tables marked "replay comparison: yes" in (b) materialized state are identical to the live ones, table by table. Four cases must be covered: deleting the first write after per-field corroboration (the value is unchanged; only the field whose provider was replaced); deleting after a constant `backfill` (the backfill position follows the record and is not recomputed because of the deletion); deleting the evidence of a key backfill after the key was backfilled (the key returns to the original row that gave it up, and later syncs treat it as "a revoked row is not revived"); a revoke given only a start point that stops at the stop point supplied by the deleted write, resolved again after the deletion while the hole remains, and, after that, a fill value in the hole that was reverted once (both the hole and the registration of "already reverted" come from the deletion result).
- **Stop on an unknown version string**: when the compiler version, the allowlist version (that of `compiled` and that of each rule), the rule version or the literal match checker version in an event has a value the kernel does not recognize, `apply` stops and reports an error, and does not evaluate in a degraded way.
- **Different time zone library versions**: in a cross-version replay comparison (export → import, both backends), the time zone library versions of the two sides differ; the internal date columns and the derived values that depend on them are classified separately as "time zone library version differs" and do not count as a difference; when the versions are the same, zero difference is required as usual. Also tested: after changing the version recorded in `meta` and opening the tenant, the internal date columns and the affected derived partitions are rebuilt with the current time zone library, and the log gets no appended event.
- **Import**: export → import into an empty tenant → `log.verify` and the replay comparison both pass, and the logical tables of (b) materialized state are identical row by row to the source (except the state of principals: all principals still valid before the import are disabled, and the revoked ones stay revoked); after importing an export with placeholders, the deletion of every placeholder has a tombstone added and the corresponding `deletion` item is closed; after importing an export that explicitly includes content pending deletion, those deletions are still pending and are registered in anchor storage.
- **Kernel-only consistency tests**: with an empty service layer (visible range all, no idempotency wait) and the file implementation of anchor storage, run the counterexamples of K1–K14:
  - resolving an item without a matching item version must fail;
  - changing a business table by bypassing `apply` must be found by the replay comparison;
  - resending the same request key is recorded only once;
  - changing the content in one place without changing the checksum must make `verify` report a mismatch; deleting or swapping an event must break the event header chain;
  - after a privacy deletion is due, nothing in the whole storage can retrieve the deleted original text or any value computed from it: the event headers and content, the physical tables of every version, items, the catalog, indexes (including the key index `external_keys`), the event headers of derived writes, `derived_reads`, counter tables, the valid times in `premise_decls`, read_log (the only exception is the request keys of other requests and the fingerprints of explicit idempotency keys, which are hashes containing values passed back unchanged, see event format 9.5; the tests assert about them separately that "they are cleared only when the evidence of that request itself is deleted");
  - confirm a deletion → copy the tenant storage as a backup → physical erasure when due → overwrite the tenant storage with the backup (the anchor file untouched) → after opening, the deleted content is likewise not retrievable;
  - after a deletion is confirmed and after it is cancelled, replay from an empty storage = live state;
  - after a backup is restored, `seq` continues from after the high-water mark; an item version obtained before the restore reports `confirmation_mismatch`, a handle reports `handle_expired`, and a `ver` that does not match the version goes through the conflict criterion; none of them is accepted as the current version;
  - the restore procedure, killed by force after each step and then started again, never serves externally before the re-applied deletions are complete;
  - an import killed by force after each step and then opened again: the target is either still empty and can be imported again, or the import has completed; at completion the anchor and the log are consistent (the restore count equals the value in the import event, the high-water mark equals the end of the log, and the deletion register equals the deletions still pending in the log);
  - after an import, an item version from before the import reports `confirmation_mismatch` and a handle reports `handle_expired`; a `ver` from before the import whose operation number does not exceed the import point is judged for conflicts by its original operation number, and one that exceeds it takes the import point as the position read.
- **The reference evaluator and property tests** (done in the first version): the reference evaluator is a pure function of "the write events of a row / entity + the set of deleted source data", and its state is "entity × field × valid time → a value or no value"; it is written as the plainest implementation from the definition, **does not depend on any judgement code in the `kernel` package** (including `judge`), and lives in the test package. The properties fall into three groups, see below.
  The authoritative definition of how a revert (reverting with `revert` in a write, or taking the previous value) is computed at write time and at deletion replay is the pseudocode in "The authoritative definition of reverting" in `03-data-model/03-deletion.md`: the reference evaluator implements it as written, and every revert scenario is turned into a fixed case and a replay comparison case.
  Every example in [`../process/walkthroughs/walkthrough-deletion.md`](../zh-CN/process/walkthroughs/walkthrough-deletion.md) (Chinese) and [`../process/walkthroughs/walkthrough-state-concurrency.md`](../zh-CN/process/walkthroughs/walkthrough-state-concurrency.md) (Chinese) is written as a case that "agrees with the reference".
  The reference evaluator must cover external keys: locating results and baseline positions follow the record, the same value is recomputed from the sync contributions that remain after the deletion, and ops that did not enter an event are not replayed. A complete set of scenarios (sync → user correction → a source change becomes a candidate → adopt, keep, or return to before the conflict → `undo` → revoke and undo → privacy deletion of one of the sources → cancel the deletion; the first sync after a key backfill; the sync source data of deleting the original row after a key transfer) is worked out by hand and turned into fixed cases; the examples in [`../process/walkthroughs/walkthrough-nutrition.md`](../zh-CN/process/walkthroughs/walkthrough-nutrition.md) (Chinese) are likewise written as cases. The reference evaluator does not need to know premises: premises do not take part in determining values.
- The contract tests run the same set of cases against HTTP and MCP (and, in the future, the SDK); the renderer tests check that flags always appear in the text (including `premise_changed`; when the cause is `retroactive` or `plan_changed`, with the interval).
- **Credentials limited in scope**: HTTP and MCP each run every operation with a credential limited to a slot, and assert that the names of slots, tables and fields outside the scope appear in no result, error, candidate or hint; referring by name to a table outside the scope and referring to a table that does not exist report the same error, and referring by ID to a target outside the scope reports `not_found`.
- **Interoperability test of export encryption** (`cli`): a file encrypted by `saveslot export --encrypt` and decrypted with the `age` command line is byte-for-byte identical to the plaintext export; in the other direction, `saveslot import` decrypts a file encrypted by the `age` command line. The passphrase is supplied through age's non-interactive passphrase plugin (`age-plugin-batchpass`), so it can run in CI without a terminal.

#### Properties of deletion

0.1.0 does not provide privacy deletion yet; what follows is the design ([`07-scope-v1.md`](07-scope-v1.md), section 7).

| Property | Statement | What error it catches |
|---|---|---|
| Agrees with the reference | The result that `delete(D)` writes into events = the result of the reference evaluator under D | Any deviation in the rule implementations of `judge` and `delete` |
| The write path agrees with the reference | The live state after a series of writes = the replay result of the reference evaluator when the set of deleted data is empty | The way `write` calls `judge` throughout does not agree with the definition |
| Order independence | Deleting A then B = deleting B then A = deleting {A, B} at once; states and items are compared, not the indexes of restatements and not `dropped` entries; a later write with an old `ver` may be judged differently because the deletion history differs (a deletion counts as a change over the interval it recorded) | The result depends on the deletion history |
| Cancellation restores | After deleting A and cancelling the deletion, the parts not overwritten by writes made within the grace period are the same as the replay result of "A was never deleted, but the writes recorded as kept in effect take effect at their own write numbers, and the writes whose item was kept superseded do not take effect either" (when neither exists, the same as when A was never deleted) | The cancellation misses putting back a contribution; an item is restored wrongly |
| No missed deletion (the privacy invariant) | No value, segment endpoint, item entry, translation or group key in the result depends on the deleted source data; once due, no search of the whole database finds the deleted value or any value derived from it, including later requests that pass it back unchanged, default end points that other writes stopped on it, and intervals copied into reverts and deletion results (except the hashes of request keys, see event format 9.5) | Missed deletion of things such as interval parameters, translations and item entries; a copy of a value left in a no-op field; a derived endpoint left in other events (including the endpoint of a write-back item that comes from the adjacent segment at the position of the value, and an endpoint passed over from a constant backfill segment) |
| A no-op stays a no-op | A field that was a no-op when written is still a no-op after any deletion | A field passed back unchanged is treated as a change after the value it saw is deleted |
| An undone write is undone cleanly | `undo` a write after a deletion extended its default end point: that write no longer takes effect at any valid time | `undo` used the old interval in the event and left a residual segment that cannot be reverted |
| A revert does not fall back to an undone value | After a revert, any deletion: the reverted items do not take effect over their intervals, and the value there equals the value before the operation that was undone in the replay (no value if there was none before); the range of the revert is the interval of the reverted item in the replay minus the part still covered by later operations | After the source of a transfer is deleted, the value falls back to that of a revertne write |
| After restatement, live agrees with the reference | After a deletion is confirmed or cancelled, the state in effect, interval and corroboration status of every contribution in a source table = what the reference evaluator gives; the judgement result of any later write is the same on both sides | The deletion event did not record a state flip, so later default end points are resolved differently on the two sides |
| No excess deletion | A value whose value source does not contain the deleted source data is unchanged (except the reordering of segments within the same entity) | A rule that prefers deleting too much is overused |
| A deletion adds no pending items | After a deletion is confirmed, each newly appearing pending item is either an awaiting-confirmation item turned from a conflict item superseded by this deletion, or comes from a pending item of the same write: where the original item was superseded by an earlier deletion and returned to pending because of this deletion with its kind unchanged, the original item is restored; where the kind changed (awaiting confirmation ↔ conflict, the original item superseded by this or an earlier deletion), the original item stays superseded and a new item succeeds it one to one | A high-impact write takes effect directly because its conflict disappeared, or items appear from nowhere |
| What is in effect stays in effect | The confirmation of a privacy deletion does not turn an (event, target) whose items were all in effect at write time into a candidate or awaiting confirmation, whether or not an earlier deletion has already been executed on time; cancelling a deletion only rolls back writes that were in effect only because of that deletion (except those already used as a baseline by other writes, which stay in effect) | The directional restriction is not implemented |
| A write that was not in effect and takes effect is visible | A write that takes effect or turns into awaiting confirmation because of a deletion appears in previews, receipts and events | It takes effect silently |
| Rule version isolation | A write or item judged under some rule version and policy version, when there is no explicit re-judgement event, does not change its result because of a kernel upgrade or a policy change | Deletion replay used the current rules. The first version has only one version, and the tests simulate with two policies |
| The record agrees with recomputation | The result of a deletion / cancellation event in the log = the result the reference evaluator recomputes under the rule version recorded in that event | A defect in the live `delete` (not caught by "replay from an empty storage = live state": replay uses exactly the result written in the event) |

#### Properties of time

| Property | Statement | What error it catches |
|---|---|---|
| Pointwise equivalence | After a write with an explicit interval takes effect: the field written inside the interval = the new value; fields outside the interval, and fields that were not written, are unchanged | Any error in the segment-splitting algorithm |
| The default end point can be eliminated | A write with a default end point ≡ a write whose explicit end point is "the first stop point of that field after the start point", field by field; values at and after the end point are unchanged | The end point is resolved wrongly; it was not resolved per field |
| Ordered primary key, no empty segments | Any two segments of the same entity are disjoint and no interval is empty; two versions of the same entity in a version table do not intersect on both axes at the same time | Splitting leaves an overlap; a version interval was not closed |
| Splitting does not matter | Cut any segment at any point into two segments with the same value and the same provenance, then perform the same write: the conclusions about the end point, high impact, same value and conflict do not change | The judgement peeked at the physical segment boundary |
| Merging is idempotent and preserves snapshots | The value at every instant is the same before and after merging in the query layer; merging twice = merging once; after merging, adjacent segments must have different values | The merge used the wrong columns |
| A same-value write produces no version | A write with the same value as the version seen: no new version, `ver` unchanged; writing twice = writing once. Exception: history across schema migration: when `migrate` is not injective (two old values map to the same new value, or the precision becomes smaller), a change of value in the old version has the same value before and after in the new version, but it is still, as it is, a write that took effect and still has a version; this property is asserted only for writes within the same schema version | The baseline of the same-value judgement was wrong |
| Disjoint writes commute | Two writes on the same field with explicit and disjoint intervals, or two writes with default end points and different start points (neither made a change point in the version seen disappear): the order does not affect the final state, nor whether items are produced | The conflict criterion is implemented wrongly; the high-impact judgement peeked at a change point that the other side had just created |
| The recorded time is append-only | A later write does not change the `as_of` result at any operation number earlier than it; privacy deletion excepted | The version table was rewritten in place |
| Time-slice consistency | `as_of: S` + `valid_at: T` = replay the log to operation number S, then take T; when S falls in the middle of a write, it is equivalent to falling at that write's operation number | The version table used the `seq` of a row event instead of the operation number |
| The structural criterion of affected queries | A read is flagged `possibly_affected` ⇔ at some (field, valid time) it asked about, the value differs between the version at the time of the read and now. Exception: the backfill of a schema switch does not trigger it (a read that saw an empty value before an optional field became required is not flagged); the party that read the old value learns of it through the `schema_updated` hint | Over-reporting, under-reporting (including reads that saw future arrangements), incomplete clearing of marks |
| The retroactive classification is stable | Replaying the same log, the "retroactive or not" of each write is as it was at the time | Replay used the current clock or the current time zone |

#### Properties of conflicts

| Property | Statement | What error it catches |
|---|---|---|
| The ruling is determinate | Replaying the same log from empty, the value in effect, the candidates and the item states are identical one by one | The judgement used something outside the log |
| Never blocks | After any write sequence, every (field, instant) that has a value has exactly one value in effect | A conflict leaves a field unreadable or reads out two values |
| The earlier committer is stable | A stale write does not change the value in effect on a conflict unit where it becomes a candidate | A candidate takes effect silently |
| Pick, never invent | The value in effect of any field equals a value that some write gave | A new value was computed during a merge or a revert |
| The conflict judgement is symmetric | Two writes carrying the same `ver`, within the scope of the symmetry property (neither passes an end point, neither points at evidence, neither made a change point in the version seen disappear): A then B is judged a conflict ⇔ B then A is judged a conflict. The three known cases outside that scope are each written as a fixed case, asserted by the result of the current criterion | The criterion depends on arrival order; a result outside the scope was changed unintentionally |
| Concurrent writes that do not conflict commute | Two writes carrying the same `ver`, within the scope of the symmetry property and not conflicting in either order: the final values in the two orders are the same, and neither produces an item | The merge result depends on the order; the baseline of the same-value judgement was wrong; high impact ① counted the change point that the other side had just created into the protected range |
| A merge does not break declared constraints | A row produced by an automatic merge satisfies all the constraints of the schema, including field groups | The merge bypassed validation; the judgement was not made per group |
| Dispute flags are complete and not excessive | For each alternative of a pending item: a read result that adopting it would change must carry `disputed` (a derived row carries the input flag); one that does not change whichever alternative is adopted does not | A missed flag; excessive flags per row |
| No write is lost | Every item of every field of every accepted write is in exactly one state: has been in effect / is a candidate or proposal in a pending item / was closed by a recorded decision / was superseded by a write that had read the item it is in / is a no-op | A candidate disappears silently |

When system adjudication is added back, two more properties are added: adjudicating one by one = adjudicating once; adjudication only goes up, never down.

#### Properties of external keys and premises

| Property | Statement | What error it catches |
|---|---|---|
| At most one row per key | After any sequence of writes by external key, ordinary writes, revokes, key backfills and key transfers (0.1.0 reports `not_in_this_version` for a key transfer), `undo` (including undoing an undo), deletion confirmation, cancellation of a deletion, and execution when due: each key in the key index has at most one entry, and a holder has at most one row. Must cover: freezing after deleting the evidence of a key backfill, then cancelling and executing when due respectively; a transfer after revoking a row whose key was backfilled is rejected | Two rows with the same key appear when key transfer, undo and deletion alternate |
| A revoked row is not revived by a sync | An op by external key that hits a revoked row is always skipped; after any sync sequence, a revoked row is still revoked | A sync writes back a row the user revoked |
| The location result is the same after replay | Replaying from an empty storage and replaying on another backend, every op by external key that entered an event lands on the same row, and the key index is identical row by row | `apply` re-locates; the maintenance of the key index depends on arrival order |
| A sync request in which nothing changed appends no event | For a request whose ops are all `unchanged` / `skipped`, the end of the log is the same before and after: apart from the receipt, no logical write head, source data or request key is left | A sync with no change leaves a head event, source data or a request key |
| A source value that was rejected does not take effect directly at the next sync | After a conflict is resolved by "keep the value in effect" or "return to before the conflict": the sync delivering the same value is a no-op, and delivering a new value is a candidate | The baseline value was not counted into the candidate; a write-back item was treated as a sync contribution |
| A declaration that did not change means the value did not change | After a random sequence of writes, reverts, resolutions, deletions, cancellations, restatements and clears, for each declaration that is still valid and whose state is "unchanged", the value on its range now equals the value on the version seen. The other direction is not required: when "cannot compare", over-reporting is allowed | A premise flag was missed |
| The recorded flag change = recomputation by the criterion | For each premise change event, recompute it from the live state with an independent plain implementation, and it equals the record | A deviation in the implementation of the detection |
| Replacing only the provider sets no flag | When a privacy deletion replaces only the contribution that gave the value and the value did not change, no flag is set; a declaration that is still "changed" after the deletion has `since` pointing at this deletion | Comparing by provider instead of by value; `since` pointing at an operation that left nothing behind |
| A restatement is not treated as a resend | Two literally identical restatements: when the premise changed again between them, the second is not treated as a resend | The request key did not include the resolved premise version |

### What the evals require of the implementation

The evals ([`10-evals.md`](10-evals.md)) have real Agents complete tasks through MCP. They do not verify the correctness of the kernel (that is the job of the test matrix above), but they require the implementation to provide the four things below. They are used only for tests and evals and are not enabled in normal operation:

| Requirement | Content | Where it lives |
|---|---|---|
| Test clock | The saveslot service can start at a given fixed instant and be advanced while running. Only the source of "the current time taken at the entry point" is replaced; the kernel is unchanged (the kernel never reads the clock anyway) | The startup parameter `--eval-clock` of `daemon` (the parameter of the same name of `saveslot start` is passed to it); the scheduler uses the same clock; it is advanced through `POST /v1/eval/clock` with a user session on the local socket; for the rules see [`06-cli.md`](06-cli.md) §3 step 3 |
| Snapshots between steps | The runner can query the state between two steps with a user session (the values and `ver` of rows, items, sources, read records) | No new interface is needed: `query`, `history`, `pending`, `sources` and `reads.list` of the user session |
| Call record | The runner obtains the complete sequence of tool calls: the arguments and the text the host received come from the call record, and the contract results come from the server's eval results log. When the host does not provide it, the forwarding layer of `saveslot mcp` records it | `saveslot mcp --record <file>`: a recording switch turned on only during evals, with the format in [`05-surfaces.md`](05-surfaces.md) §11. The tool results of MCP are text only ([`05-surfaces.md`](05-surfaces.md) §3), and the host and the model also receive only text; the structured results come from the server's eval results log: when running with the test clock, the service writes the connection, tool, arguments and contract result of every tool call to `run/eval-results.jsonl` (created anew at every start: whatever is already at that path is deleted first, and if it is a link, the link itself is deleted, then it is created exclusively; 0600, containing no tokens) |
| Deterministic seed data | Seed writes carry an explicit `idempotency_key`, and reinstalling the fixtures gives the same logical state (row IDs and sequence numbers may differ) | The eval runner; no cooperation from the kernel is needed |

| Extension point | Where the interface is | The first version | Later |

| Storage backend | §8 `StorageBackend` | PGlite, PostgreSQL | — |

Local tokens, OAuth 2.1 and user sessions sit on top of it and do not vary with the implementation | The end-user identity of developer applications |
| Visible range | The `ops` calling context | All, or limited to some slots by a credential | Table-level and field-level data permissions (open-questions) |
| Model invocation | The executor of extraction jobs (the contract does not distinguish executors) | None: extraction jobs are not in the first version | Extraction jobs are first executed by the user's Agent, and later by a background executor (worker) that calls a model, writing through the contract and outside the kernel ("Later plans" in the positioning document) |
| File storage | The `file_ref` of evidence (including the content hash) | References only | Content blobs, re-upload |
| Multiple nodes and sync | The `sync` module, the identity conventions of events (§3) | Not implemented | Local + cloud, multiple devices, merging embedded storage into the saveslot service |
| The rule for the value in effect during a conflict | The slot policy, the policy version | Keep the current value | System adjudication by source level, acting on old items through re-judgement events |
| Integrity of the log | The event format version (add a version, no appending to old events) | Only the event header chain + the content checksum: provenance and protection against mistakes | Signed checkpoints, a Merkle tree, on-chain content commitments, off-chain anchors: later plans, as the product needs |

The **identity provider** answers "which person is this browser request". Pages that need to know the person (the OAuth authorization page, the device code page) ask only through it and do not touch the account tables directly. Its members:

| Member | What it does |
|---|---|
| `currentUser(request)` | By the provider's own login state, gives the user of this request, the `session` (the ID of this login: constant while the login lasts, opaque, and not the cookie itself; the one-time token of the consent form is bound to it), the display name, and the expiry instant of this login (`expiresAt`, an instant in `toISOString` form); with no login, it gives nothing |
| `beginLogin(request, returnTo)` | Sends a browser that is not logged in to log in, and returns to `returnTo` after login |
| `paths` | The paths the provider answers itself (local accounts: `/account/login`, `/account/logout`; external login: `/oauth/identity/callback`). The service reads the form of a request and hands it to `handle` only for these paths; the request body can be read only once, and the request bodies of other paths (such as the token endpoint) are left as they are for their own handling |
| `handle(request)` | Answers the paths in `paths`; does not take a path that is not its own |
| `userState(user)` | Enabled, disabled or unknown. Disabled: all credentials of this tenant are rejected at authentication; unknown is treated as an invalid credential |
| `issueUserSession(user, source)` | Issues a user session: from a login (the `session` given by `currentUser`), from an assertion just accepted by `acceptAssertion` (accepted only by a provider that has it), or from a refresh (carrying the grant instant `grantedAt` of that authorization; at refresh time the login ended long ago, so there is no login to lock). In one transaction of the control database it locks the account first and then that login (a refresh locks only the account). When the account exists but is not in the enabled state (for example, disabled), no session is issued from any source, and it reports that the account is temporarily unavailable (`account_inactive`: back to normal once re-enabled); when the provider does not recognize the account, the login has ended or expired, or the grant instant of a refresh is not later than the instant at which the account's sessions were last ended (§5: a local account changes its password), none is issued, and it reports that the login has ended (`login_ended`: it will not come back); no session is issued either when the account is enabled but the user has no enabled tenant. The session is written into `credentials` |
| `acceptAssertion(assertion, source)` (optional) | Only external login has it: verifies an identity assertion used to exchange for a session and gives the user and the `session`; for an account seen for the first time, the tenant is created here, with counting by source: at most 5 new users from the same source within one hour, with an IPv6 address counted by its /64 and its /48 counted separately at most 20; check first and record first, and when the table is full a new source is treated as having reached the limit. For a provider without this member, the token endpoint answers `unsupported_grant_type` for this kind of authorization |

- The paths that issue a user session and the paths that change an account lock in the same order: the account row first, then the login row. Changing a password changes the account first and then deletes its logins and sessions, disabling changes only the account, and logging out deletes only the login; so they and issuing cannot deadlock with each other. A password change during issuing waits for the issue to commit and then ends that session together with its login; a disable or a logout during issuing also waits for the issue to commit.
- The correspondence between users and tenants is in the control plane. A user's tenant is created by the first implementation that knows the user: for local accounts when the operations command creates the account, and for external login when a valid identity assertion for this account is first received.
- The headers, cookies, query parameters and forms of a request are handed to the provider as a "name → value" mapping, not as an ordinary object: a name such as `__proto__` is treated like any other name. Each name has one value, and when a name occurs repeatedly, the party that constructs the request takes only the first; a caller that needs multiple values parses the raw request itself.
- `returnTo` accepts only a value that starts with a single `/`, whose path is under `/oauth/`, is at most 4 KiB, and contains only printable ASCII (0x21–0x7E, which can be written unchanged into the `Location` header); a value with a scheme or a backslash is rejected; the path part (before `?` and `#`) contains no `.` or `..` segment and no `%2e`, `%2f`, `%5c` or `%25` in any letter case (and decoding any number of further times does not yield these either); an over-long value is also rejected, not truncated; when written into a page it is always escaped.
- A cookie set by the provider is always `HttpOnly`, and `SameSite` defaults to `Lax`; `Secure` is added when the external address is HTTPS; a cookie starting with `__Host-` must be `Secure` and have the path `/`.

## 13. Scope of the first version, and evolution

**Implemented in the first version**: `contract-core`, `kernel` (without `sync` and `jobs`), the two storage backends, `contract`, `service`, `server` (HTTP + MCP), `daemon`, `client`, `cli`, the entry package.
Not done: the SDK, multiple nodes and sync, extraction jobs and large-write jobs, the background executor (worker) that calls a model, file storage, tamper protection (Merkle, signed checkpoints, on-chain content commitments), table-level and field-level data permissions, merge import, shared slots. For the complete scope see [`07-scope-v1.md`](07-scope-v1.md).

**The gap between 0.1.0 and the first version**: 0.1.0 is a part of the first version and does not provide privacy deletion yet, migrations that need to rebuild physical tables (including `change_timezone` and `change_time_field`), the replay comparison (`log.reconcile`, `saveslot verify --replay`), or changing the slot policy; the two background tasks, the retention cleanup of read_log and the periodic advance of the high-water mark, are not connected yet either. For the item-by-item list see [`07-scope-v1.md`](07-scope-v1.md), section 7.

**Guarantees that let the kernel stay unchanged when the SDK is built later** (to be met already in the first version and checked in tests):

| # | Guarantee | How it is checked |
|---|---|---|
| 1 | `kernel` does not depend on the transport, `service` or `contract`; it can be instantiated alone in Node, Bun and the Electron main process (other runtimes are not verified) | The package / module dependency check holds the first half. That it can be instantiated alone in the three runtimes has no test coverage at present (the embedding smoke test on the runtimes has not been set up yet) |
| 2 | The storage location is passed in by the caller, and the kernel does not hard-code a path; the single writer, the epoch and the format version check are in the kernel | The tests all open their stores in a temporary directory passed in by the caller; two processes opening the same directory must report an error |
| 3 | The kernel invariants K1–K14 depend only on the two ports of §8, not on any service-layer component | The kernel-only consistency tests |
| 4 | A confirmation enters the kernel as a "confirmation record" (the content hash + `seq`), and the way of interaction is decided by the surface or the host | Same as above |
| 5 | The visible range is in the calling context, and in the first version it already passes through the execution paths of the catalog, queries, SQL rewriting and writes | Run the catalog, query, restricted SQL and write tests with a visible range `scoped` down to the table level: referring by name to a table or field that is not listed reports the same error as referring to a name that does not exist, namely the one that the operation reports for a name that does not exist (`unknown_table` / `unknown_field`; `sql` reports `sql_rejected` (`unknown_name`)), and the closest name attached is taken only from the visible ones; referring by ID to an invisible target reports `not_found` (when a row ID written into a `ref` field points to an invisible row, what is reported is the same as when the target does not exist: `validation_failed` (`ref_not_found`)); a derived table is visible if and only if the tables and fields it depends on are all visible |
| 6 | The external contract is generated from `contract`; the kernel depends only on `contract-core` | The dependency check |
| 7 | The `ops` calling context is frozen and serializable (leaving a path for sidecars of non-JS hosts) | The serialization round-trip test of the context |
| 8 | Tasks that are due are run when the storage is opened, and do not depend on a resident process | Open after being closed for 25 hours: deletions whose grace period has passed must be completed first |

## 14. Undecided items and gaps

2. Numbers: the latency upper bound of slow PGlite queries; the thresholds of write admission; the two scale lines of the data directory (the measured numbers are gathered in §8 "Capacity limits and measured values"). 4. The form of the SDK for non-JS hosts: a sidecar process (later).

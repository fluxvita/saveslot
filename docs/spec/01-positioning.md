## In one sentence

saveslot is a data layer for all agents: it tracks things that evolve over time and keeps the full timeline from the original evidence to the current state.
The data belongs to the user and is not tied to any model vendor or host (the product an agent runs in, such as Claude Code or ChatGPT).

saveslot itself is **a data and engineering architecture (kernel + service layer + operation contract)**: the kernel does the deterministic checking, recording and execution, the service layer handles identity, permissions and confirmation, and the operation contract is the whole set of operations offered outside (see [`02-architecture.md`](02-architecture.md)). It is offered as two product forms; see "Product forms".

## The scenario test: things tracked over time

saveslot is not concerned with data at one moment, but with **things that evolve over time**. A case that meets all three conditions is a case for saveslot:

1. **It has a stable identity**: it is one particular thing (this project, my running, this set of accounts), not a stray sentence.
2. **It changes or accumulates**: values are revised, records are added, a state moves forward, a document is revised.
3. **Something later depends on it**: a later session or agent needs its current state or its history.

A measurable "value" is only one shape of it; a stream of records, progress, preferences, decisions with their reasons and documents revised again and again all count.

**Range of use: records produced at a human pace.** saveslot keeps every version of every row together with its sources, and every write refreshes the affected derived values synchronously; the cost of these guarantees grows with the number of rows. The first version is aimed at what a person says, does and decides: a run, an expense, a change to a budget. Readings that a device produces by the second or by the minute (heart rate, blood glucose, cadence) are outside this range. saveslot does not refuse them, but it is not optimized for them, and when the number of rows passes the limit, the catalog and `saveslot doctor` say so. The recommended practice for such data is to store summaries (one row per activity, one row per day), leave the raw series at its source, and point to it with evidence. The measured limits are in "Capacity limits and measured values" of the architecture document.

**What is distinctive: time is first-class.** A database stores the present; memory stores what was said; saveslot stores the timeline of a thing:
what it is now, how it got there, and on what grounds at every step.

## Who it serves

**In principle it serves all agents**; it is not tailored to one host or to one product above it.

- Products are built on top of saveslot; saveslot is not the backend of one product. A product such as an expense tracker, a workout log or a project tracker, built so that an agent does the recording and the looking up, can hand its data layer to saveslot (see "Products built on saveslot").
- Our own agent products and third-party agents are clients of equal standing.
- **Agent developers** (later versions): use saveslot's SDK to have their own agent maintain the state of data over time; see "Product forms".
- **It must not be too general.** saveslot has to be distinctive (not another database or memory) and at the same time carry enough business scenarios.

## Products built on saveslot

saveslot is a foundation; products for end users are built on it. An expense tracker, a workout log (like Strava) or a project tracker (like Linear), built so that an agent does the recording and the looking up, faces the same problems at the data level: values get corrected, their sources must be known, several agents write at once, the user must be able to delete, and to take the data away.

- These common parts (versions, sources, conflicts, auditing, reverting, deletion, export) are provided by saveslot.
- The product brings the domain knowledge and the user experience. Domain knowledge is handed to saveslot as "Schema + SKILL": the schema defines what the data looks like, and the SKILL tells the agent when to write and how to use it.
- saveslot's range is wider than "typed values": a value is only one shape of a tracked thing, and beneath it lies the log of source data.

## Product forms

**One kernel, two product forms.** The first version provides only the saveslot service; the architecture must be able to carry the developer SDK later without changing the kernel.

| | The saveslot service (first version) | Developer SDK (later versions) |
|---|---|---|
| For whom | Users: one person's data layer, shared by all the agents they use | Agent developers: embedded as a component in their own agent, to maintain the state of data for it over time |
| Where the data is | The user chooses: the local computer, a server they deploy themselves, our cloud service | The developer chooses: embedded locally in the application (the application decides where), a data center the developer runs, or our cloud service bought as a service |
| Whose data, and who is trusted | The user's; neither agents nor models can get around the kernel invariants (untrusted in the security sense; what they write is trusted by default, see "The data layer") | When embedded it is the application's, the host application is trusted and the model is not; when connected to a data center, as for the saveslot service |
| How it is exposed | HTTP, MCP, CLI (first version); an app (later) | An in-process library interface; the same contract when connected to a data center |

- **What we control is which interfaces are opened, not how developers use them.** So what is distinctive about saveslot must rest on the **kernel invariants** (the full list is K1–K14 in §3 of the architecture document: the log is the only source of truth, every write has source data, derived data is produced by rules only, schema versions are immutable, two time axes, a conflict is a durable state, deletion cascades along lineage, reads leave a trace, a confirmation is bound to its content, and so on), which cannot be switched off under any use.
  Identity, permissions, the way confirmation is carried out and the like are **service-layer policy**: in the saveslot service they are implemented by saveslot and must be on; when embedded they may be supplied by the host.
- **The contract does not depend on the backend**: behind the same SDK interface, the backend can be an embedded local kernel, a saveslot service the developer runs, or our cloud service; a developer changes backend without changing business code.
- Embedded storage may later act as a node and join a user's or a developer's saveslot service through the synchronization protocol (whether to do so is decided when the SDK is designed).

## What saveslot handles, and what it does not

| saveslot handles | saveslot does not handle (left to the layer above) |
|---|---|
| The log of source data, slots, tracing back | The product experience for end users |
| Modelled data: the current state, versions, reading as of a moment | The coordination layer: scheduling, placement, migration |
| The authority of sources and the chain of evidence | Analysing intent and breaking down queries: what to read and how to combine it (the agent's job) |
| The mechanism of dynamic schemas, and the official schemas | Specific business rules and domain computation |
| Identity and permissions: authorization per connection (one registered attachment of an agent or a program, with a credential of its own), as scope × slot range; auditing | |
| Detecting and handling conflicts (see "Conflict handling" in [`03-data-model/09-references-conflict-sync.md`](03-data-model/09-references-conflict-sync.md)) | |
| Export, and import into an empty tenant (first version); merging imports, migration procedures, log synchronization between nodes (later) | |
| What a connector needs in order to write: authorization per connection that can be limited to slots, and external keys | The connector itself: running on a schedule, calling the external system, keeping the third-party system's authorization token |

Principles:

1. **The MCP interface is designed for the worst host.** It must be usable with no hooks, on tool descriptions alone: reads must be cheap and return only the minimum state needed;
   writes must be able to refuse and to degrade (go to awaiting confirmation).
2. **Identity and permissions belong to saveslot (in the saveslot service form).** The same data is reached by several agents over several surfaces, so only saveslot can manage it in one place; when the SDK is embedded, the host supplies them (see "Product forms").
3. **The mechanism of meaning is in saveslot; the content of meaning can come from the user, the project, or the community.** saveslot is not bound to one product's domain.
4. **A connector is a client, not part of saveslot.** A program that moves data in from an external system on a schedule is written by the project or by a developer, writes over HTTP as a connection, and is treated like any other client. The third-party system's authorization token is kept by the connector itself; it does not enter the log or any storage of saveslot. A collector on a phone or another device works only with server mode: local mode serves the local computer only.

## The data layer

Details are in [`03-data-model/`](03-data-model/README.md).

- **slot**: a group of related tables plus their source data (health, expenses, for example). It is the unit of the schema version, the time zone and the slot policy, the range of one privacy deletion, and the smallest unit of a credential's authorization (a connection can be limited to a number of slots); data permissions at the level of tables and fields come later. Every source belongs to exactly one slot. The owning node, replication, export per slot and deletion of a whole slot also take the slot as their unit; the first version does none of them (the first version exports the whole tenant; in the first version one user is one tenant). When encryption is added later, the slot is also the unit of a key.
- **Two layers of data**: above an append-only log of source data (organized by slot) is modelled data extracted according to the schema; the layer above sees only the latter and can trace it back to the former.
- **Every write is recorded**: the log records the values of the fields this request touches (not the values before the write, nor the whole row after it; the earlier state follows from earlier events), and the provenance table records which sources or upstream writes caused it (per field, divided into value sources and operation sources); reads are recorded separately in read_log (versions only).
- **What can be traced back is the evidence; the aim of integrity is provenance and protection against mistakes, not tamper-proofing**: the chain links event headers only (an event header holds no value computed from user content), content is stored separately in blocks with checksums; a correction is new source data and does not change history; the result of a privacy deletion follows from one definition (see "the definition of the result of a deletion" under "Technology choices"; event tables and state tables share it, and undo uses it too), content blocks are physically erased directly, event headers stay, and tombstones are left; when a backup is restored, deletions are applied again from the deletion register kept outside the log.
- **The log is the only source of truth**: every piece of state is either a log event, or computed from the log deterministically, or local running state for which "what happens if it is lost" is written down; an export is the log, and replaying it on any backend yields the same state (see §3 of the architecture document).
- **Writes: agents interpret, saveslot enforces**: the model fills in only the intent (add / change / correction / revoke), the table, the row, the values and the evidence, and passes back unchanged the version mark and the schema version it got when reading; the server fills in the rest. Every write has source data (when no evidence is given, the request itself is stored as source data). The source level is collected first, and a literal match is judged at write time and recorded in the event (when conflicts are later decided by source level, only levels with a literal match count; in the first version a conflict always keeps the current value).
- **Reads: supplying data quickly and accurately**: analysing intent and breaking down queries is the agent's job; saveslot provides a detailed catalog (with the relations between tables, a profile of the data, and units), simple queries plus read-only restricted SQL (sharing an engine with derivation rules), reading as of a moment, and history expanded on demand. For notifying of changes, saveslot provides the ability and the product decides how to use it.
- **The core does not depend on a model**: a deterministic kernel handles storage, validation, versions, conflicts and permissions; extraction is done by the calling agent in preference, and a model's output is recorded in the log.
- **Dynamic schemas**: the user's own, plus official picks, plus community Schema + SKILL. A schema document is read and written as JSON of the same shape: a table is given whole, within a slot only the changes are submitted, and removal is explicit; names are written by the agent, and IDs are assigned and filled back in by saveslot; the unit is written in the type, and values of the same dimension are converted automatically on write (see "Schema document format" in the data model).
- **Derived tables are produced entirely by rules**: agents write base tables only; derivation rules are part of the schema (restricted SQL in the first release), and the derived cache is refreshed synchronously with base writes, without storing before and after values.
- **Schema version evolution**: versions are immutable and fields have stable IDs. Migrations are of three kinds: metadata only, deterministic conversion, and re-extraction (re-extraction comes later; migrations that rebuild a table are not provided in 0.2.0 yet). saveslot carries them out automatically; the migration function is written by the agent that drafts the schema; destructive changes and the differences after re-extraction must be confirmed. Only the latest version is offered outside (read results carry their own units and version; versions are managed per slot, but only writes at an old version that touch a field changed incompatibly are refused). A change goes through a state machine, is built in the background and switched atomically, and reads never stop. Compatibility with an official schema is a derived view.
- **The truth of the data, and confirmation, are delegated to the calling agent**: saveslot does not guarantee that what is written is true, and does not distinguish whether a confirmation came from a person or from an agent (over MCP alone it cannot tell); saveslot guarantees that traces are kept, that a confirmation is bound to its content, and that a deletion can be cancelled within 24 hours. When saveslot later does source ingestion and analysis itself, saveslot answers for the truth on that path.
  **An agent's input is trusted by default**: saveslot is a passive callee and does not judge whether content is true; the checks at write time are only deterministic validation (type, unit, range, version) that keeps the shape of the data correct, not distrust of the source. The boundary of untrusted data applies only to what is **read out** (to keep it from misleading the agent that reads it), not to questioning what is written.
- **The integrity of provenance has a boundary**: the chain of sources inside saveslot can be guaranteed; the stretch that passes through an agent can only be checked (determinism, statistical anomalies, checking against the evidence), with taint tracking as an option.
- **A conflict is a durable state**: detected at write time (per field; on state tables per field and valid interval, merged when the intervals do not overlap), carried out with reads, never blocking, with pending items that do not expire (saveslot does not decide for the person; merging and superseding keep them from piling up), and with reads recorded.

## Layers and surfaces

**The core of saveslot is the kernel, the service layer and the operation contract** (see [`02-architecture.md`](02-architecture.md)); HTTP, MCP, the SDK, the CLI and an app are all surfaces of the contract, of equal standing.
In the saveslot service form, HTTP is the base protocol on the network and MCP is the base surface for agents; the others are enhancements added per scenario.
**saveslot's correctness must not depend on any surface existing**: the checks and the invariants are all in the kernel and the service layer.

MCP can only guarantee that an agent "can" read and write, not that it "will" do so at the right time: whether and when to call is decided by the model.
The enhancement surfaces make up for exactly this.

| Surface | Role | What it adds |
|---|---|---|
| HTTP API | Base protocol, required | Callers without an agent (scripts, programs and connectors that users build with agents) connect directly |
| MCP | The base surface for agents, required | Read, write, query, validate; usable by any agent that supports MCP (including agents in the cloud) |
| Host plugin / hook | Enhancement, optional | Timing: a forced read at the start of a session or before a task, a write triggered on change |
| CLI | Enhancement; **required in the first version** | Hooks of other hosts, scripts, export, debugging. The first version has no app, and the steps that need a person (issuing connections, confirming, deciding conflicts, deleting and cancelling, viewing the audit) are carried by it; see [`06-cli.md`](06-cli.md) |
| App | Enhancement, optional (later versions) | The steps that need a person: confirming, deciding conflicts, reverting, viewing the audit |
| Developer SDK | The other product form (later versions) | See "Product forms" |

A design requirement for connecting: whatever the deployment, in the procedure for connecting a host the user at most makes choices and consents once, and saveslot does the remaining steps; every way of connecting added later is checked against this (the details and known exceptions are in section 1 of [`06-cli.md`](06-cli.md)).

## Deployment forms and synchronization

> **The first version provides two modes only**: ① local mode, in which the user starts the saveslot service on their own computer and the agents on that machine share it; ② server mode, which is the cloud service we operate, or the same thing deployed by the user on a server of their own, and to which agents anywhere can connect remotely. Both are **single node**: one user's data is in one place only.
> What the first version does not do is keep the same data on the local computer and in the cloud (or on several devices) at once with synchronization between them, nor the offline writes that would follow (see "Later plans"). For agents on several devices, or on the local computer and in the cloud, to share data, they all connect to the same saveslot in server mode. The multi-node design below is kept as a direction; the first version only requires that structures such as event identity do not block that road.

**Open source.** Users can install and use it themselves; we also provide a cloud service for users who are not able to install it themselves. **Both kinds of self-installation are supported**: starting the saveslot service on the local computer (local mode), or deploying server mode on a server of one's own, which is the same code as our cloud service (PostgreSQL, remote access, OAuth, the control database) and is within the first version's range of testing and support. Rules that say "the cloud service" below and in other documents apply to self-hosted deployments as well, except for rate limits and quotas and our own operational arrangements; the differences are in §9 of the architecture document.

- One engine, two modes (local single-user / server multi-tenant, the latter covering our cloud service and users' self-hosted deployments); core capabilities must not exist in the cloud service only.
- Remote MCP with authentication is built from the first day: the cloud service is remote access by nature. In the first version the local saveslot service serves the local computer only (shared by the agents on the same machine); across devices, use server mode (our cloud service or a self-hosted one).
- Data can be migrated in both directions between the local computer and the cloud service; export is the precondition of being able to leave. **The first version provides export, and import into an empty tenant**: export guarantees that users can take their data away; import loads an export into an empty tenant (events are replayed one by one; all principals that existed and were still valid are disabled, revoked ones stay revoked, and credentials are issued again by the user), which is how data in local mode can be moved into server mode. Merging imports, the migration procedure that freezes the source tenant, and credential mapping are left for later, with multi-node.
- The value of the cloud service is that it needs no operations, is online all the time and can be reached by agents in the cloud, not that it locks in core capabilities.
- The cloud service will later also serve the second use of the developer SDK (developers buying our data center in the cloud); its tenant model is undecided (see "Developer SDK" in [`08-open-questions.md`](08-open-questions.md)).

**Multi-node: one center per user (the basic capability).**

- The user chooses the local computer or the cloud as the primary node, and the other nodes replicate the log; an offline node writes with numbers of its own and submits them when it comes online.
- What is synchronized is the log, not the state: the log is append-only and merges easily; conflicts arise only at the step of computing modelled data from the log,
  and follow the conflict rules of [`03-data-model/09-references-conflict-sync.md`](03-data-model/09-references-conflict-sync.md).
- The data model reserves an "owning node" field for every slot, so that it can later be upgraded to a center per ownership of data
  (health data kept on the local computer only, for example) without changing the structure.

## Technology choices

Reference: [`references-arch.md`](../zh-CN/research/references-arch.md) (Chinese).

- **Storage engine**: PostgreSQL throughout. Local mode uses PGlite (embedded in the saveslot service process; the user does not install a database), and server mode (the cloud service and self-hosted deployments) uses native PostgreSQL. An agent embeds nothing and only connects to the saveslot service over MCP / HTTP.
- **Kernel language**: TypeScript (Node / Bun). PGlite can only run in a JS runtime, which is why this stack was chosen for the kernel; when the future SDK has to be embedded in a non-JS host, it can only start a separate sidecar process.
- **Prerequisite for installing**: the first version is published as an npm package and needs Node on the computer already; a standalone executable that does not depend on Node, a desktop installer and the like await the conclusions of the desktop packaging experiment (section 3 of [`06-cli.md`](06-cli.md)).
- **Primary node** (with multi-node, see "Deployment forms and synchronization"; the first version has none): when there is a node in the cloud (the cloud service or a server one deploys oneself), the cloud is the primary node by default; a local primary node is an advanced option.
  The first version does no application-level encryption; when encryption is added later, by default the primary node also holds the key to compute derived data (server-side encryption, which must be explained to users), not end-to-end encryption.
- **The first version does no application-level encryption**: saveslot does not encrypt content itself, and deletion is the direct physical erasure of content (a field, an item or a whole source can each be erased), with no salt and no content commitments on the chain; the structure leaves room for encryption later (when encrypting, only the original text of source data and whole rows of history are encrypted, and business tables stay in the clear so that they can be queried).
  **The cloud service's storage is encrypted at rest at the infrastructure level**: the database's storage volumes, backups and cold archives are all on storage encrypted by the cloud platform, with keys kept by the platform's key management service. This protects against the storage medium being taken away and read; it does not protect against the operator: the saveslot process, and operations staff with database permissions, read plaintext, and **the operator is technically able to read all the data of the cloud service's users**. If no third party is to read it, use local mode or deploy it yourself. In a self-hosted deployment, whether the disk is encrypted is up to the deployer; in local mode it is up to the operating system's disk encryption, which saveslot does not check. An export file can be encrypted by the CLI with a passphrase (age format); that protects a copy that has left saveslot and is not storage encryption.
- **Consistent replay is a hard requirement**: the same log replayed on any node (PGlite / native PostgreSQL) must give derived results that are identical row by row: fixed time zone and collation, `numeric` for numbers, rules that use only functions with deterministic results, and verification by experiment.
- **Valid time is a first-class concept**: the schema declares a time type for every table (timeless / event / state); writing a state by default "holds until the next recorded change", and covering existing facts needs an explicit parameter; the design is in "Time" in the data model.
- **Deletion comes as three kinds of request**: revoking a row / evidence deletion / privacy deletion; derived data can be recomputed and never blocks a deletion. The first version provides revoking a row and privacy deletion, and evidence deletion comes later; 0.2.0 has revoking a row only.
- **The definition of the result of a deletion** (reference: [`08-provenance-deletion.md`](../zh-CN/research/08-provenance-deletion.md) (Chinese); see "Deletion" in the data model): the state after a privacy deletion = the state obtained by replaying the log in `seq` order as if the deleted sources had never existed, with two deliberate departures: a person's decisions (revoke, revert, taking a candidate / returning to before the conflict, confirm, reject, `acknowledge`) are carried out as recorded, and writes that have once taken effect stay in effect. Two principles: only data dependencies (value sources) are followed, not control dependencies (operation sources); saveslot's own mechanical judgements (same value, `next_change`, `ver` conflicts, system rulings, high impact, the existence of a row / entity) are recomputed on the state after the deletion.
  A deletion may bring into effect a write that had not been in effect (a candidate whose cause of conflict was deleted, a write awaiting confirmation whose cause of high impact was deleted). It takes effect by the definition, but this must be visible: the preview lists it separately, the receipt and the event state it, and the corresponding item is marked "superseded"; a write that is still high-impact after its conflict disappears goes to awaiting confirmation and does not take effect directly.
  The first version already builds a **reference evaluator** as the test oracle for `delete`, with property tests (§11 of the architecture document); it **does not adopt** storing in advance a provenance polynomial / minimal witness for every value; W3C PROV is noted only as a candidate format for a future audit export.
- **Separate storage for every user** (reference: [`07-per-user-storage.md`](../zh-CN/research/07-per-user-storage.md) (Chinese)): locally it is one PGlite data directory;
  the cloud service and multi-user self-hosted deployments use **one database per user within one PostgreSQL cluster, grouped by cluster (cell)**, with a starting limit of 2,000 user databases per group.
  The saveslot kernel depends on only one abstraction, "open the storage of a given user"; table names carry no user prefix, and local, cloud and self-hosted deployments run the same code.
  Connections are managed by saveslot itself (a user is routed to one fixed saveslot process, one connection per active user, closed when idle, evicted least recently used when full), without PgBouncer. Full means the number of tenants a process has open at once has reached its limit (configurable); when none is idle to evict, a request waits briefly in line, and one that gets no place gets a retryable `unavailable` (architecture §7).
  A user inactive for a long time has their whole database exported and removed from the cluster, and restored on the next access; when the limit is exceeded, in order: add a cluster → tighten the inactivity threshold → fall back within the group to one schema per user → a cluster of their own for large users.
- **No slot shared by several people (first version)**: in future a shared slot = a tenant of its own + member authorization; in the interface a slot is not fixed under a user name.
- **Log integrity = provenance + protection against mistakes, without tamper-proofing** (see "Integrity and provenance" in the data model): deterministic event headers, with `prev_hash` linking event headers only; content stored separately in blocks with checksums (used only to detect corruption, and erased together with the content); only the kernel can write, the log is append-only, and reconciliation (triggered by the user by hand in the first version).
  `verify` reports "whether the chain of event headers is intact; content checksums that do not match in N places; M places removed by deletion". There is no tamper-proofing against a party that can write to the storage (the operator included); signed checkpoints and Merkle trees belong to later plans (see below).
- **Large write jobs** (not in the first version, where a write over the limit is always refused and the caller splits it into batches): a large write that cannot be split becomes a background job, during which the affected derived values keep their old values and are marked "to be refreshed": a limited relaxation of "derived values never fall behind".
- **Durability is a hard requirement**: a confirmed write must not be lost on restart, process crash or power loss. How PGlite meets this, and which experiment confirms it, is in "Durability of read_log" of the architecture document.

## Later plans (not in the first version)

The following are not in the first version and are discussed separately when later versions are planned:

- **Theoretical basis**: the design uses existing theory directly in three places, each with a set of property tests (§11 of the architecture document). The theory of data provenance is used for the definition of deletion ([`08-provenance-deletion.md`](../zh-CN/research/08-provenance-deletion.md) (Chinese)): "reference semantics + two principles + a reference evaluator and property tests" unify the rules of replay under deletion, instead of writing them one by one by hand; provenance polynomials are not stored in advance, and W3C PROV is only a candidate format for a future audit export. Bitemporal databases are used for the write and read rules of state tables ([`09-bitemporal.md`](../zh-CN/research/09-bitemporal.md) (Chinese)). Data fusion is used for the conflict test and for what must be recorded in events ([`10-data-fusion.md`](../zh-CN/research/10-data-fusion.md) (Chinese)). Three more have not been worked out: incremental view maintenance (DBSP), schema evolution (PRISM), and memory architectures for language agents (CoALA); they do not affect the event format. **The test for adopting a theory is its benefit**: each must answer "which hand-written rule does it replace, which verifiable criterion or test does it give, which external standard does it provide"; one that provides only a way of speaking is used only in how the project describes itself and does not enter the implementation.
- **Multi-node**: the same data kept on the local computer and in the cloud (or on several devices) at once with synchronization between them, offline writes, and switching the primary node. Both modes of the first version (local, server) are single node; the first version concentrates on whether the core data and engineering architecture can solve keeping the state of data for agents. "Sync protocol" in the data model and the related mechanisms (tentative, rejected by synchronization, and so on) are kept as a future design and are not implemented.
- **Advanced capabilities in which saveslot calls a model**: these need the user to authorize model calls (bringing their own API key). They include the write path of "hand over raw content only, and saveslot extracts", a background executor (worker) that calls a model to run extraction jobs, L3 model derivation, synchronization from external sources and scheduled tasks, drafting a schema from accumulated source data, and a background model checking evidence (the first version produces no "check disagrees" items). Synchronization from external sources here means synchronization that saveslot itself starts; in the first version and after it, data from external sources can always be written by connectors outside saveslot (see "What saveslot handles, and what it does not"). Extraction jobs are not in the first version and are the first increment after it; when built they serve schema changes only and are first run by the user's agent, the interface does not distinguish executors, and a worker connects directly later. **All of these capabilities are outside the kernel**: an executor that calls a model stands where the calling agent and a connector stand, writes through the operation contract under its own identity, is bound by scope, and has its results recorded in the log as events as usual; the kernel and the contract do not depend on them, all of saveslot's guarantees hold without them, and replay never needs to call a model again ("Model invocation" in §12 of the architecture document).
- **Tamper-proofing of the log**: signed checkpoints, Merkle trees and content commitments on the chain are built when the product needs them; the integrity aim of the first version is provenance and protection against mistakes. When they are built, content commitments are added through a new version of the event format, and are not added to old events.
- **Export per slot**: `export` in the first version exports all the events of the whole tenant (section 8 of the event format). Exporting one slot only needs decisions first: whether event headers are exported in full or filtered by `slot`, whether events without a slot (principals, the tenant) are included, and whether the export file can be replayed and have its chain verified on its own; when built, `export` gets an optional `slot` parameter and the file format does not change.
- **Deleting a whole slot**: the first version does not provide it for a slot that has records, and the interface has nothing for it; privacy deletion source by source already meets "forget it completely". Removing an empty slot is provided (`slots.remove` in the contract: it removes only a slot with no records under it; the name can be reused, the `slot_id` is not). Deleting a whole tenant (a user asking for their whole account to be deleted) is likewise absent from the first version; it must be defined before a cloud service is offered to the public, and the list of questions is under "Deleting a whole tenant" in [`08-open-questions.md`](08-open-questions.md). When it is built, "Deletion" in the data model first defines: how schema documents, slot policies, items, jobs and the new-version tables of a migration in progress are handled, whether the slot name and `slot_id` can be reused, whether writes are possible during the grace period, and the meaning of cancelling; the interface goes through the same `deletion_preview` → `delete` (`kind: "slot"`).
- **Duplicate detection on import**: when the same batch of ops from the same file (the `sha256` of a `file_ref`) is written again into the same slot, say "this file was imported at …" (import here means writing the content of an external file in, not importing an export). The first version does not do this: a rerun script relies on an explicit `idempotency_key` (a window of 24 hours), and the same thing recorded twice relies on the `duplicate_keys` flag. A table that declares an external key does not need it: handing over the same content again by external key results in no change.
- **Tables of a series type**: a kind of table for high-frequency readings produced by devices: versions are not kept per point, sources are not recorded per point but per "batch" (one synchronization, one file), data is appended by batch and replaced and deleted by batch, and can be downsampled. The first version has none; high-frequency data is stored as summaries, as "The scenario test" recommends. To be decided: a batch is one event with the readings as its content blocks; the granularity of K4 (every write has source data), K8 (conflicts judged by `ver`) and K10 (the read record records the version read) changes on such a table from the row to the batch; how derivation rules read it; privacy deletion carried out by batch. The storage abstraction and the event format do not block this road, but it is an extension of the data model, not one more table. Whether to bring it forward depends on the results of the capacity experiments.
- **The interface content of multi-node**: node credentials, the log synchronization endpoint, the `tentative` status and flag, and the `sync_rejected` item are not in the first version's contract and surfaces; they are defined in "Sync protocol" in the data model, and `tentative` and `sync_rejected` are added later in a minor version of the contract.
- **File storage and attachments** (to be built later): in the first version a source can be a reference to an external file (file name, type, size, content hash, location of origin, an optional text excerpt); the file itself is not kept, and a deletion says so truthfully. saveslot keeping files is a definite later direction: a user's photos, receipts and recordings are the original evidence of many records, and with only a reference kept, "the evidence is in saveslot, traceable and deletable" does not hold for evidence of this kind. The approach is to add content blob storage, upload later by content hash, and leave the structure of the reference unchanged; then the upload interface, how media files are extracted, whether files enter synchronization and export, and the terms of deletion and backup have to be decided.
- **Text views (a whole table or a whole query result laid out as text)**: saveslot does no semantic search, while models are good at handling text; letting an agent get the full text of a table or of a query result (Markdown or CSV), for the model to search in by itself, can replace part of the need for semantic search. What the first version already has: `query` over MCP returns rendered text and can read through a table page by page without conditions (at most 200 rows per page); source data can be listed by time, slot and kind and searched by substring. What is to be added later is an entry point that fetches the whole in one go (the CLI writing a file, MCP giving a resource that can be read in segments); it is only another surface on top of `query` and does not change the kernel. To be decided then: the read record is kept at the level of the table (see "Read records" in the data model); each line of the text carries the row ID and not the `ver` (to change a row, read it row by row first); the boundary marks of untrusted content apply as usual; a file written outside saveslot is a copy that saveslot's deletion cannot reach, and an export says so truthfully. **When to build it is decided by the evals**: if failures in which an agent cannot find data make up a large share in the evals, it is brought forward.

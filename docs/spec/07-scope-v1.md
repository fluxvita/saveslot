# saveslot · Scope of the first version

English · [简体中文](../zh-CN/spec/07-scope-v1.md)

> This document fixes only "what the first version does, how far it goes, and in what order it is built". The definitions of the mechanisms themselves are in positioning, architecture, data-model, contract and surfaces; undecided items are in [`08-open-questions.md`](08-open-questions.md).

## 1. Conclusion

**The first version = a saveslot service that runs on a single node in either of two modes, local mode (PGlite) and server mode (PostgreSQL; our cloud service and a user's self-hosted deployment are the same code). The kernel holds K1–K14, and the event format is fixed in full once.
The surfaces are opened only as far as eval 1–4, 6–10 and the first half of eval 5 need (eval 11 starts running at the end of P1, only produces numbers and does not block a phase). Schema changes cover only the kinds that need no extraction, deletion covers only revoke and privacy deletion, and import covers only import into an empty tenant.**

- The list of mechanisms has 107 items in all: 70 are done, 18 are simplified, 19 are later (section 3, counted by the rows of the tables).
- **No item needs K1–K14 to be relaxed.** In a few places the scope of an invariant becomes smaller (the feature is not enabled, so the rule is simply never triggered); the full list is in architecture §3, "Invariants whose scope is smaller in the first version": K5 (no large-write jobs, and a derived value is not allowed to lag, which is stricter), K8 (no system ruling, and the rule for the value in effect is only "keep the current value"), K10 (the impact query does not cover reads of derived values), K11 (no evidence deletion, no row-level privacy deletion and no extraction jobs, so the rules tied to them are not triggered), K12 (no background sampled reconciliation: the first version does not look for changes that bypass `apply` on its own, and the user has to run `saveslot verify --replay`).
- The reference evaluator is built in the first version (covering the kinds of deletion in the first version), so "the recorded result = the reference recomputation" has a comparison implementation.
- **Extraction jobs are not part of the first version**; they are the first increment after the first version (section 4, P4b).
- For effort see section 6: the numbers for each phase are rough estimates from before the phases were adjusted and have not been re-estimated.
- **The first version is not a released version.** This document fixes how far the first version goes; 0.2.0, the current version released publicly, provides some of it, and which parts are provided by later versions is in section 7.

## 2. Principles of trade-offs

1. **What would change the event format must be done in the first version, or at least leave room in the event format.** Criterion: when it is added back later, the information missing from the old events cannot be filled in (for example field-level value source, literal match, the original arguments and the parsed result, the separation of content from the event header, the identity of an event, the rule version and the policy version).
   Such things must be written into the event even if the first version does not use the feature that needs them.
2. **What would violate or relax any K must be done in the first version.** K1–K14 are promises that "no way of using it can switch off"; the first version cannot discount them on the grounds of "not done for now"; only "the scope becomes smaller" is allowed, and it must be stated.
3. **What affects only the surfaces, or can be added back purely incrementally, is cut or simplified first.** Purely incremental = a new event type / item kind / tool / endpoint, old data needs no migration, and old events replay as before (the event format version only grows and is never changed, architecture §6).
4. **Getting the evals to run comes before completeness of features.** Every step is accepted by "which eval it unlocks"; the eval results in turn tune the tool descriptions, the numbers and part of the scope. **Acceptance follows the eval specification** ([`10-evals.md`](10-evals.md)): the fixtures, the scripts, the assertions on stored state and on calls, the grading details and the pass lines of each task are there; the list in surfaces section 12 is only a description of the scenarios.
5. **The legal floor of the cloud service cannot be cut.** A cloud service that charges money must be able to do privacy deletion and to export, so these two do not move later together with the "simplified" items.
6. **Key trade-offs are written down with their reasons and the alternatives not taken** (section 5); what is still undecided is recorded in the open questions and not judged here by fiat.

**The freeze point of the event format**: event format v1 ([`09-event-format.md`](09-event-format.md)) is finalized in P0 and frozen at the first public release (0.1.0). From then on it only grows and is never changed: new event types and new optional blocks are added, and old events are still parsed and replayed as before; an incompatible change needs a decision draft first and is changed only after it has been reviewed, and it must also state what happens to the old logs (for data compatibility across versions see [`02-architecture.md`](02-architecture.md#format-versions-export-import-and-restore), "Format versions, export, import and restore"). Logs produced during development (P1–P4) are not promised to be compatible, because otherwise the events of P1 would lack the judgement results that only P2 implements, which under principle 1 is already a gap that cannot be filled in later.

**Event format v1 is frozen**: the shapes of the blocks and the vocabularies are fixed. The block "revert (reverting and taking the previous value) + deletion replay" takes the pseudocode in [`03-data-model/03-deletion.md`](03-data-model/03-deletion.md), "Replay rules · The authoritative definition of reverting", as its authoritative definition. In development, **implement the reference evaluator first** (write it from the pseudocode, without relying on the kernel's judgement code), then implement the live `judge` / `delete` / `apply`, compare the two by replay comparison with property tests, and add a test that a search over the whole database misses no deletion. The scenarios worked out by hand during the design phase are recorded in appendices A–I of [`../zh-CN/process/decisions/pre-dev-w6-final-fixes.md`](../zh-CN/process/decisions/pre-dev-w6-final-fixes.md) (Chinese); each of them is to be turned into a test case (a fixed case and a replay comparison case of the reference evaluator) and is no longer worked out by hand.

## 5. Key trade-offs

| Trade-off | What the first version does | Reason | Alternatives not taken, and why |
|---|---|---|---|
| How far deletion goes | Revoke + privacy deletion by source data, with the grace period, cancelling, the deletion register, the restore flow and physical erasure on expiry all in place; the reference evaluator (covering these two kinds of deletion) and the property tests are built in the first version. Evidence deletion and privacy deletion by row are later | The cloud service must be able to implement the right to be forgotten before it can charge money; the definition of deletion is the reference semantics, and the evaluator is its executable version | Only revoke: the cloud service would have no implementation of the right to be forgotten. Doing everything at once (adding evidence deletion and deletion by row): the extra parts can all be added back purely incrementally without changing the event format, and need not be squeezed into the first version |
| Schema changes | Only metadata-only changes / dropping a field / deterministic conversions that need no conversion expression are supported (P4); extraction jobs and the whole of `migration_diff` (P4b) are not part of the first version, and room is reserved in the event format now | Extraction is the most complex block and the one that depends most on tuning by eval 5; there is no background executor (worker) that calls a model, and everything is finished by the caller Agent in a loop, whether which is realistic has to be answered by eval 5 first | Including the whole of extraction, or including extraction but giving only `accept_all` / row by row / `abandon`: both need the conclusion of eval 5 first. The cost: eval 5 can run only its first half in the first version, and "re-extract from source data after adding a field" is also missing |
| Multiple candidates of a conflict | Done: a later stale write on the same conflict unit merges into the same conflict item, and `candidate` says which one is adopted | The merge event is needed anyway; the extra work is mainly judging candidate by candidate in deletion replay | Reporting an error such as `read_first` for the second stale write: violates "never blocks". Opening one conflict item for each stale write: violates "does not pile up" |
| System ruling | Not done: in the first version the value in effect is always the current value (the first to commit). The level, the literal match, the rule version and the policy version are still written into events | It saves the three most convoluted rules: `applied_by_rule`, "the item is still open after a candidate becomes the value in effect", and "the level changed so rule again" at deletion; the first version records all the information needed, and when it is added back an old item is re-judged through an explicit re-judgement event | Changing the value in effect on the spot by the source level from the literal match and triggering an impact query: the three rules above would have to be implemented additionally, and doing it later loses no information |
| Interval writes on state tables | Done in full: `valid_from`, the default end, explicit `valid_to` / `open`, revoke with an interval, intervals without a value | The segment-splitting algorithm is the same as with only `valid_from` + the default end; doing it in full adds only parameters and the judgement of high impact ① | Only `valid_from` + the default end: saves little. No intervals and state tables only "change from now on": state tables degrade to ordinary tables, eval 4 cannot be discussed, and the unique trait that "time is first-class" is lost |
| Encoding of event headers and content | RFC 8785 JCS; both the hash and the checksum use SHA-256 | Ready-made in the TS ecosystem, readable, and consistent between debugging and export (NDJSON); the whole system uses only one algorithm, which the runtime provides | Deterministic CBOR: smaller, but size is not a bottleneck of the first version. CRC for the checksum: enough, but one more algorithm |
| Putting a log back | Only import into an empty tenant is supported (P5): validate the file, replay event by event through `apply`, deactivate the existing principals that are still valid (those already revoked stay revoked), and the user issues the credentials again; "export → replay into empty storage → replay comparison" remains a test | The two hard things are both avoided: the target is empty, so there is nothing to merge; principals are not mapped, and the actor in the history is kept unchanged. This path was a test of the first version anyway, and import adds validation and the closing steps to it. When server mode goes online is exactly when local users need to move their data, so it goes into P5, not into P6, which is released first | Keeping export only: data migration would go only half the way. A full import with merging and principal mapping: it has to answer how the `seq` of two logs interleave, what to do with slots of the same name, and how to merge the deletion registers on both sides, which is a multi-node problem. Re-executing contract operations one by one: it would judge again and assign `seq` and IDs again, so what results is not the same log, and `verify` would not match the original chain |
| The confirmation step | It stays delegated to the caller Agent; the structure of the slot policy leaves room for "a certain kind of operation is accepted only with confirmation from a user session", not implemented | Through MCP alone it cannot be told whether a confirmation comes from a person or from an Agent, so adding a check would be only a form; the fallback is that a high-impact write does not take effect directly, a deletion can be cancelled, and every confirmation leaves a trace | Requiring from the first version that a high-impact operation be confirmed by a user session: without an App, a person would have to confirm item by item through the CLI, and the flows of eval 4 and 7 would not work |
| App | Not in the first version: the human part is handled by the CLI + the caller Agent | Confirmation is already delegated to the caller Agent, and an App is an enhancement surface; look at it again once experiment 6 (desktop packaging) has a conclusion | Building a minimal App (pending items, cancelling deletions, viewing the audit): the flows of the first version do not depend on it |
| Release order | Local mode first (P1–P4, P6), and server mode (P5: the cloud service and self-hosting together) afterwards; before server mode goes online privacy deletion (P3) must be finished, and the legal conclusion on "the metadata kept after deletion" must have been obtained | Local mode needs no OAuth, no control-plane database and no multi-tenancy, and can get real usage data earlier | Releasing local mode and the cloud service together: it delays getting real usage data |
| Multi-segment evidence | `any_of` ("any one is enough") is not provided per field; when a field references several segments of evidence, it is always "all are needed" | Consistent with the default of data-model "Deletion · Provenance": when it is not known which segment a value came from, this is the only rule that never deletes too little; to tell them apart, use `evidence_by_field` to map per field | Declaring `any_of` per field |

## 7. What 0.2.0 provides

0.2.0 is the current version released publicly (the first was 0.1.0). It provides local mode (PGlite, where the Agents on one computer share one saveslot service) and server mode (PostgreSQL, where the cloud service and self-hosting are the same code). It is a part of the first version, not all of it: the two blocks below are judged "Yes" in section 3, but 0.2.0 does not provide them yet, as 0.1.0 did not.

**What 0.2.0 provides**

| Aspect | What is provided |
|---|---|
| Writes | The four intents (add, change, correct, revoke); `ver` and conflict judgement per conflict unit, candidates and conflict items; intervals of state tables, the default end and intervals without a value; high-impact writes going into awaiting confirmation; reverting and undoing a write; idempotency; evidence and field-level provenance, literal match; writing by external key (except transferring a key); hints for similar keys (`similar_keys`); suspected duplicates (`duplicate_keys` → flagged items); premises of a write |
| Reads | The catalog, `query`, `sql`, derived tables (derived rules read one base table in this version); `timeline`, `as_of`, `changes` of `history`; source data; pending items; read records and the `ver` fallback; `detail: "detailed"` on `as_of` of `query` and `history` (a derived table reports `not_in_this_version`) |
| Pending items | Viewing and resolving the four kinds of items: conflict, awaiting confirmation, flagged, schema change |
| Schema | Creating a slot; for an existing slot only changes that touch the catalog (renaming, changing the description and aliases, relaxing constraints, adding tables, dropping tables and so on); structural changes on tables never written; removing an empty slot |
| Log | Validation of the event header chain and checksums (`saveslot verify`); export and passphrase encryption of exports; import into an empty tenant |
| Surfaces | Nine MCP tools (`saveslot_catalog`, `saveslot_query`, `saveslot_sql`, `saveslot_history`, `saveslot_sources`, `saveslot_pending`, `saveslot_write`, `saveslot_resolve`, `saveslot_schema_draft`), HTTP, the CLI. MCP does not take yet, in this version: an op's own `evidence`, `evidence_by_field`, `as`, `source_ref` evidence segments, the two decisions on a flagged item (`keep`, `revoke`) and `detail: "detailed"`; HTTP and the CLI take them |
| Server mode | Accounts and login, OAuth authorization, remote MCP, import, the operations commands of `saveslot server` |
| Deployment and operations | Server mode: a limit on the tenants a process has open at once, and closing idle ones (`SAVESLOT_TENANT_CONNECTIONS`, `SAVESLOT_TENANT_IDLE`); the readiness probe `/ready` and the three-step shutdown; call records (`SAVESLOT_CALL_RECORDS`). Both modes: upgrading a storage format in place when a store is opened (no upgrade step exists yet), local mode backing up first. `query` reads only the page it returns in most cases (paging pushed down to the store) |

Compared with 0.1.0, what 0.2.0 adds is the "Deployment and operations" row above; the boundary of what it can do has not changed. What to know when upgrading from 0.1.0 is in section 7 of the guide's [`../guide/13-self-hosting.md`](../guide/13-self-hosting.md).

**What 0.2.0 does not provide yet and later versions provide**

| Which block | What it includes | How it behaves in 0.2.0 |
|---|---|---|
| Privacy deletion | The preview (`deletion_preview` and the `dc_` handle); confirmation (`delete`, `saveslot_delete`, `saveslot delete`); cancelling within the grace period; physical erasure on expiry, tombstones and residue cleanup; re-applying deletions per the deletion register after a backup is restored | These endpoints report `not_in_this_version` on HTTP; MCP has no `saveslot_delete` tool; the CLI has no `saveslot delete`. When data is wrong it can still be **revoked** (an ordinary write, history kept, can be undone); making content disappear completely cannot be done in 0.2.0 |
| Migrations that need to rebuild physical tables | Adding a field, dropping a field, tightening constraints, changing precision, changing units within the same dimension on a **table that has been written** | Such a draft can be submitted and previewed; one that would take effect automatically reports `not_in_this_version` at submission; one that needs confirmation reports `not_in_this_version` at confirmation, and the draft stays. When the table has never been written these changes take effect as usual (the new table is empty, so no migration is needed) |

The two blocks that are not provided yet are the same in both modes: server mode likewise has no privacy deletion and no rebuilding migrations. A few other items are also not connected yet: the replay comparison (`saveslot verify --replay`, that is, `log.reconcile`; `POST /v1/log/reconcile` reports `not_in_this_version`), changing the slot policy, retention cleanup of read_log (0.2.0 does not clean read records, which only grow), periodic advancing of the high-water mark (0.2.0 advances it only when a tenant is closed). The items judged "Later" in section 3 (extraction jobs, evidence deletion, privacy deletion by row and so on) are not in the first version, and so naturally not in 0.2.0 either.

**Effect on existing promises**: wherever the specification and the guide speak of privacy deletion ("a deletion is previewed first and confirmed after", "it can be cancelled within 24 hours", "physical erasure on expiry", "restoring a backup does not bring deletions back"), what they say is the design and cannot be used in 0.2.0; in 0.2.0 K11 has no operation that can trigger it. Where they speak of "the schema switch is atomic and reads never stop" (K6), in 0.2.0 this holds only for switches that do not rebuild tables, because a switch that rebuilds a table does not happen yet.

## Deletion

### Definition of the result of a deletion

**The state after a privacy deletion = the state obtained by replaying the log by `seq` as if the deleted source data had never existed. There are two deliberate deviations: human decisions are carried out as recorded; writes that have already taken effect stay in effect.**
At confirmation, `delete` computes the result by this definition and writes it into the event, and `apply` carries it out. Cancelling a deletion works the same way: the deletion that is cancelled no longer counts as "deleted", and the result is computed again by the definition.
The two principles, the replay rules and the corollaries below all follow from this definition; they are not additional rules. Where a rule and the definition disagree, the definition holds and the rule is changed.

- **Deviation 1: human decisions are carried out as recorded.** In the counterfactual, what the person would have decided cannot be known; a decision a person made based on what they saw at the time can only be carried out as recorded. The human decisions are: revoke, revert and returning to before the conflict (**what is recorded is "which changes of which operations on which targets are reverted" and "the state at which position to return to"; the range that is reverted and the values there are not part of the decision**, they are determined again in the replay, see "Replay rules · Reverting". The part of a reverted operation that was a candidate or awaiting confirmation when it was written and takes effect later because of a deletion is reverted in the same way: what the person undid is that operation, not just the items that could be listed at the time; operations that are not in the record are not added), adopting a candidate / keeping the value in effect, confirming, rejecting, `acknowledge`. What is carried out as recorded are the items that still count as changes: an item whose value is the same as the version seen by the writer over its whole interval is handled in the replay by the same-value rule: one that did not point to evidence is no longer a contribution; for one that pointed to evidence, the part that still has the same value at the moment of writing becomes corroboration, and the part that had already been changed is still a change, carried out as recorded. Left out of the list is only the part that no longer counts as a change: something with the same value is not a change, and there is nothing to decide. **Every other judgement is recomputed** (see "Two principles"), with one limitation: **the part that left no value when it was written stays as it is**: a field that was originally a **no-op** stays a no-op, and an op by external key that did not enter the event (unchanged or skipped at the time) is not replayed (see "Replay rules"). Example: an op by external key hit a revoked row at the time and was skipped; after the source data that created that row is deleted, by "as if it had never existed" it should add a row, but the log does not contain it, and does not contain its value. A deletion does not make an op that was unchanged or skipped at the time take effect afterwards, and the preview says so plainly.
- **Deviation 2: writes that have already taken effect stay in effect (a limit on direction).** Recomputation only turns something that "had not taken effect" into "taken effect" or into awaiting confirmation; it never reverts a write that has already taken effect to a candidate or to awaiting confirmation. A write that has taken effect has been read and used by later writes as their baseline; reverting it would let one deletion overturn established facts unrelated to it, and would create new open pending items.
  **"Has already taken effect" means: took effect when it was written (the judgement given by the write event), or took effect through a human decision (confirming an item that awaits confirmation, adopting a candidate: what takes effect is the new item written by the resolve operation), or was recorded as staying in effect when a deletion was cancelled (see "Cancelling a deletion and the grace period"); corroboration counts too.** A write that takes effect only because of the recomputation of some deletion does not count: a later deletion recomputes by the whole set of deleted data, and it may go back to a candidate or to awaiting confirmation. When the kind it goes back to is the same as that of the original pending item (the pending item the write was in when it was written), it goes back to the original pending item: if the original pending item has been superseded, it is restored (its "superseded" is revoked); if it is still open, the write is merged back and the pending item is refreshed; the successor pending item it is currently in is superseded if it becomes empty because of this. When the kind differs from that of the original pending item, if an earlier deletion has already opened a successor pending item of the same kind for it, it stays there; if not, a new one is opened, taking over from the original pending item one to one. The preview and the receipt list these separately (see "What the preview and the receipt must state"). This way the result of a deletion still depends only on the log and the set of deleted data: deleting A and then B is the same as deleting {A, B} at once.
  **The unit of protection is all items of one write on one target** (a target is one field, or "existence"; in a field group, fields are still looked at one by one). When an ordinary write or a revoke wrote on this target and all its items took effect (took effect or corroboration), then in any replay it stays in effect over the whole interval the replay resolves, including the part that extends beyond the interval at the time of writing. When one item did not take effect at write time, all items on this target are judged by the replay; the part that does not take effect in the replay belongs to the pending item the write originally belonged to: if the pending item is open it is merged in; if a human has already resolved it, that decision closes it (decisions cover by (event, conflict unit), see "Replay rules"); if it was superseded for another reason, it is closed along with it. In none of the three cases is a new pending item opened, and for the latter two the preview and the receipt list them separately. On a state table, there is only one kind of write in which one part took effect and one part did not at write time: a same-value write that carries a stale `ver` and explicitly points to evidence, where the part that still has the same value became corroboration and the part that had already been changed became a candidate (see "Conflict handling · Conflict criteria"). **Corroboration on such a write is not protected**: when a later deletion makes it no longer the same value, the whole segment is judged again as a write that changes the value.
  The criterion reads only the state of each item given by the write event, not the interval of each item. An interval is content obtained from other contributions and is erased together with other deletions (event format §3.5); the state is erased only with the sources of this contribution itself. So protection does not depend on the order of the write and the deletion, nor on whether an earlier deletion has already been carried out at expiry. A base write that carries a revert record or an adoption record, and a base write triggered by a confirmation, do not go through this criterion: whether they take effect follows the operation they belong to: a revert is judged item by item by "Replay rules · Reverting", and confirming and adopting are human decisions (deviation 1).
- **It constrains only the state at the end of the log**: earlier historical versions are not recomputed by the definition; only the deleted content is removed from them (see "How the result lands in the log"). So that replaying from the beginning after the tombstone is applied still gives the same end state, the deletion event writes the result in full and appends derived writes for the derived partitions that are affected.
- **There is an executable reference implementation**: the reference evaluator is a pure function of "the log + the set of deleted source data", implemented by the definition with these two deviations; it is built in the first version and serves as the test oracle for `delete`, with a set of property tests (architecture §11). See [`../../zh-CN/research/08-provenance-deletion.md`](../../zh-CN/research/08-provenance-deletion.md) (Chinese) (literature and argument).
- **Provenance polynomials / minimal witnesses are not stored in advance**: overwriting writes are not monotonic (delete a later write and the earlier value comes back), and an expression containing only "and / or" cannot compute the value after a deletion; `base_sources` (field × evidence, with the portion / operation / interval) plus the log order is already all the information, and the deletion replays.

### Two principles

| Principle | Meaning | Includes |
|---|---|---|
| ① Follow only data dependencies, not control dependencies | **Value source = data dependency** (where the value comes from), **operation source = control dependency** (who triggered, who decided). A deletion propagates only along data dependencies; a human decision is not revoked because its operation source is deleted | Data dependencies: the evidence that accompanies a write, the `api_call` when a `write` carries no evidence, the resolve evidence of a `set` in `migration_diff`, the source of the value carried by a revert / adoption / system ruling, the source of the interval parameters of a write on a state table (**including the interval of a revoke that has an interval**). Control dependencies: the revert request, the resolve request (including `note`), the parts of a revoke's evidence that are not an interval source (for a whole revoke, all the evidence), `acknowledge` |
| ② saveslot's own mechanical judgements are recomputed by the state after deletion | A conclusion that saveslot reaches by rule, without human judgement, changes when its input changes. **Except for the human decisions listed in the definition, every judgement is recomputed** | Same-value judgement (for contributions only; a no-op stays a no-op; a write by external key is compared with the recomputed baseline value), stop points and default end points (`next_change`), the default interval of a correction (`corrected_span`), `ver` conflicts, system ruling (later), high-impact judgement, the existence of rows / entities, the first-creation mark, the merge base of open pending items (for a pending item already resolved by `take_previous` or `take_candidate`, the merge base is the one recorded at resolution and is not recomputed). **There are only two mechanical judgements that are not recomputed**: suspected duplicates and literal match (judged once at write time, as recorded) |

Taken together, the two answer "what stays and what is recomputed": human decisions stay, saveslot's judgements are recomputed, and values follow data dependencies.

**The premises of a write** (see "The premises of a write") are handled in two ways:

- **Declarations are as recorded.** A declaration was given by the caller at the time, and the "version seen" is the fact it saw then; in the counterfactual, what the agent would have seen and what it would have declared cannot be known, for the same reason as "human decisions are as recorded".
- **State is judged again.** The state of a declaration (unchanged / changed) is a mechanical judgement; it is judged again by the criterion on the state after deletion, and the result is given by `premise.changed` in that deletion operation: if the deletion changes the value over the declared range, the mark is set (reason `deleted`); if the value goes back to the value seen and can be compared, the mark is removed.
- **Deletion does not propagate along premises.** The value source of a dependent row is its own evidence, not its premise; the data dependency of principle ① means the value source. Whether a dependent row paraphrases the deleted content is not known to saveslot, so the preview lists these rows and leaves the decision to the person. A premise does not make a deletion delete more or less of any value, so the two corollaries "no over-deleting" and "no missed deleting" are not affected.
- **One place that is deliberately not computed by the counterfactual**: when the value seen came from a sentence that was deleted later, replaying by the definition would make the value on the version seen something else; but the dependent row was written by the agent after seeing that real value, so the comparison uses the real value seen: it has been deleted and cannot be compared, so the mark stays ("removed only if it can be compared").

**There are two kinds of revoke**:

| Revoke | Does it contain content | After its evidence is privacy-deleted |
|---|---|---|
| Without an interval (a whole row, a whole entity) | No. It is only a decision | As recorded: the row / entity does not come back. Only that sentence is deleted |
| With an interval (state tables) | Yes: the start and end points of the interval are what the user said, and the source is that sentence | The source of the interval is gone, and this revoke as a whole has no contribution: the interval without a value disappears, and the values it covered become visible again (the preview says "the values for this period will reappear") |

If a revoke with an interval should still hold after the original sentence is deleted, the way is the same as for corroboration: point to another piece of evidence under the `valid` key of `evidence_by_field` to give the source of the interval.

**Which version of the rules is used for recomputation**: each old write is recomputed by the rule version and policy version it recorded itself (see "The write request · Rule version and policy version"). A kernel upgrade or a change of slot policy does not let an unrelated deletion change the judgement results of old writes and old pending items.

### Kinds of deletion

**First separate the intent: deleting is not revoking.** Wrong data calls for **revoke / correction**: history is kept, the correction and conflict rules apply, and the tasks that are affected are found from the read record. Not wanting it to exist is **deletion**: the content itself is wiped.

**There are three kinds of deletion request**:

| Request | What the user wants | How | The first version |
|---|---|---|---|
| Revoke a row | This business record should not exist ("that run was recorded twice, delete it") | An ordinary write (intent "revoke"): the row is marked deleted, history and source data are both kept, and the derived caches refresh as usual | Yes |
| Evidence deletion | This original text is no longer wanted, but the data it produced may stay | Delete only the original text of the source data; the values obtained from it are kept as usual; if after the deletion some current field would have no value source whose original text is still there, it is refused by default and the referencing parties are listed | Later |
| Privacy deletion | Forget completely (the right to be forgotten) | The state after deletion is computed by "Definition of the result of a deletion"; it is not blocked by references | Yes (specified by source data; specified by row: later) |

(Deleting a field from the schema is a different matter: that is a schema change, in which the field and its data are deleted and the source data is untouched, see "Schema version evolution".)

**The flow of evidence deletion and privacy deletion**:

| Stage | What happens |
|---|---|
| Preview | Nothing is deleted; the impact is computed and a confirmation handle is returned (see "What the preview and the receipt must state") |
| Confirm | **The state after deletion is computed at confirmation**: `delete` computes by the definition what the affected rows / entities look like after deletion, writes it as an event together with the derived writes, and `apply` carries it out. From this moment the data cannot be read, and current values and derived values no longer contain it |
| Grace period (24 hours) | Logical deletion only, and it can be cancelled (see "Cancelling a deletion and the grace period"); the content to be deleted is replaced by a placeholder by default and is not exported (see architecture §8) |
| Expiry | Physical erasure, and a tombstone event is appended. In the cloud service the scheduler actively opens the tenant and carries it out at the expiry time; when the local saveslot service is not running, it is carried out at the next start, before serving anyone, and the receipt says so plainly (see architecture §7) |

- **One deletion concerns only one slot.** Each piece of source data belongs to only one slot; when one sentence involves two slots, it is already two pieces of source data, and each slot deletes its own. A request that lists source data of different slots reports `invalid_argument` (`cross_slot`).
- Whether the user's consent has been obtained is the responsibility of the calling agent (saveslot does not distinguish a person from an agent, see architecture §3 "Confirmation and the authenticity of data are delegated to the caller").
- "Deletion confirmed", "cancellation" and "physical erasure at expiry (tombstone)" are all log events: exporting or restoring within the grace period does not bring the data back either; restoring a backup older than the deletion is handled by re-applying deletions from the deletion register outside the log (see "After deletion").
- How the grace period relates to the time limit of the right to be forgotten is left to legal.

**Privacy deletion by row** (`rows`)

> **Not in the first version.** In the first version, to forget a row completely, list all the source data that this row involves as deletion targets. It is the same replay as deletion by source data, with only the deleted set changed.

- The unit of deletion is the contribution on (source data, row): **all** contributions of these rows are removed, whether the source data inserted them or modified them later, not only the one that inserted them.
- Source data that serves only these rows is deleted as a whole; source data shared with other rows is deleted only for the part that corresponds to these rows: when a `write` carries no evidence, each op stores its own `api_call`, so it can be cut by row.
- When the provenance of these rows does not intersect with the provenance of other rows / values, deleting by row has no side effects; the judgement is only a set intersection, and the preview states it that way.
- Source data that is shared and cannot be cut (text evidence, an excerpt of a `file_ref`): the whole piece is privacy-deleted (the contributions other rows get from it are removed too), and the preview lists the rows affected as a consequence separately.

**Evidence deletion**

> **Not in the first version.**

- **The two kinds of "is it there" are computed separately**. Privacy deletion asks "does this source data still count as existing"; evidence deletion deletes only the original text and the contributions stay, so "is referenced" is computed separately:
  - **"Is referenced" looks only at value sources whose original text is still there**: sources that evidence deletion has already deleted do not count. It blocks (reports `referenced`) only when after the deletion some current field has no value source whose original text is still there; when there is another value source whose original text is still there (the corroboration of another write, another piece of evidence cited by the same write) it is allowed; operation sources do not block; derived data can be recomputed and never blocks. For details see "References: strong and weak".
  - **In a privacy deletion, a source that evidence deletion has deleted still counts as present**: its contribution is still there (the intent of evidence deletion is that the value stays), only the original text is gone.
  - **The source level for conflict rulings** keeps the literal match result judged at write time and recorded in the event; it does not change because the original text was deleted.
  - **And pending items**: conflict candidates and proposed values awaiting confirmation are not current values, and the evidence they cite can be deleted by "evidence deletion"; when the deleted evidence is the **only value source with original text still there** of some candidate / proposed value, that pending item is marked "superseded" (reason code `evidence_deleted`),
    and can no longer be adopted or confirmed, since otherwise a value with no original text to check would be written as the current value. The values in the pending item are kept as usual (evidence deletion deletes only the original text).

The sections below concern only privacy deletion, unless stated otherwise.

### Provenance: value source and operation source

**Provenance is recorded at field level and comes in two kinds**, matching principle ①:

| Source | What it is | Includes | On deletion |
|---|---|---|---|
| Value source (data dependency) | Where the value comes from | The evidence that accompanies a write (the portions that the field cites); when the value is given by the request itself and carries no evidence, the `api_call` of that op; revert, adopting a candidate, returning to before the conflict, and system ruling = **references to the contributions that are carried** (see below); the `set` of `migration_diff` = the evidence of `resolve` (the resolve request itself if none is carried); the source of the interval parameters of a write on a state table (recorded separately as the interval source, see below the table) | Deletion propagates only along it |
| Operation source (control dependency) | Who triggered this write | The revert request, the resolve request (the evidence or `note` of `resolve`; stored as an `api_call` if no evidence is carried), the parts of a revoke's evidence that are not an interval source (for a whole revoke, all the evidence; a revoke carries no value) | Used only to satisfy "every write has source data" (K4) and for audit; deleting it does not affect the value and does not revoke the decision |

The **interval source** is a kind of data dependency and is recorded separately: for a write or a revoke on a state table that has interval parameters, the source of the interval parameters is the evidence that `valid` maps to in `evidence_by_field`; if nothing is mapped, it is all the evidence of this op (its `api_call` if no evidence is carried). It does not give a value, it only determines the interval; deletion also propagates along it (see "Interval parameters" below). When one piece of evidence is both the value source and the interval source of an item, both are recorded (one row each in `base_sources`), and when listing outwards what it produced, only the value source counts.

**Contribution**

- **The contribution of one write to one field** = the value this write gives to that field, together with its value source.
- **Every field whose value was changed is a contribution.** The baseline for "changed" is the version seen by the writer (the version `ver` points to; if `ver` is the current one, it is the current state), not the current value: an agent that brings back unchanged the value it read has not made a change.
- **A field with the same value as the version seen comes in two kinds** (this is the authoritative definition of same-value corroboration; what is specific to state tables is in "Time · Writing with the same value"):

  | Way of writing | What it is | Result |
  |---|---|---|
  | Explicitly points to evidence with `evidence_by_field` | **Corroboration** | It is a contribution: it produces no new version and adds a source to that field, recorded in this base write event and visible in `timeline`. The part whose current value has been changed by a write after the version seen takes part in conflict judgement as an ordinary write |
  | Does not point explicitly | **No-op** | It is not a contribution: no source is recorded, it takes no part in conflicts, and it leaves no boundary |

  This way, a fact that was deliberately corroborated does not disappear when one of its sources is deleted (except when a corroboration with a stale `ver` has been cut into a corroboration part and a candidate part, see the unit of protection of deviation 2 in "Definition of the result of a deletion"); a field brought back unchanged in a resend of a whole row does not stay on because of new evidence.
- **Between different writes it is "or"**: when the same value is given by two writes separately, deleting the source of one leaves the contribution of the other, and the value stays.
- **When one field of one write cites several pieces of evidence it is "and"** (including when no mapping is given and all are cited by default): saveslot cannot tell which portion the value came from, so **if any one of them is privacy-deleted, this write's contribution to that field is removed**.
  This is the only default that never deletes too little when the mapping is not known. When a `write` carries several pieces of evidence and gives no field mapping, the receipt `warnings` remind that "deleting any one of them will remove these fields"; for such a field, `deletion_preview` says "the same write also has s_…; use `source_ref` to corroborate by field before deleting".

**Carried values**

- **A carried value is stored as a reference to contributions**: the value source of a revert, adopting a candidate, returning to before the conflict, or a system ruling is recorded as "which contributions are referenced" (the base write event + field + item; on a state table, the interval that is carried is the interval of the written-back item itself), and the source data IDs are not flattened into a list: if the value being carried is corroborated by two writes with the same value, after flattening "or" and "and" can no longer be told apart.
  When none of the contributions referenced by adopting a candidate is present, this carry has no contribution at that place; for a revert and for taking the previous value see "Replay rules · Reverting". A chain of reverts is a chain of references, and its length does not exceed the history.
  **Where an adopted candidate lands is also determined again in the replay**: field by field, take the union of the intervals of the items the adopted write has in K (the candidate items of this pending item, identified by (event, conflict unit), see step 2 of the pseudocode), minus the parts covered by writes outside the coverage set (see the next paragraph); when the adopted write no longer has an item in K on some field (all deleted; an item that has the same value as the version seen and no longer counts as a contribution does not count as "none": it stays in K as a shadow, and the adoption lands on it and writes the value of the adopted write), it lands instead on the item in K of a candidate in the pending item that has the same value on this field: if the adopted write had never existed, the candidate with the same value is the value this decision adopts. A field group is judged field by field, and the whole group is not required to have the same value.
- **What an adoption of a candidate records as recorded are the merge base, the coverage set O and the revokes it fills in** (O is listed in the same way as the revert record of `take_previous`: the (event, target) pairs within the pending item's conflict unit and interval that had an item take effect after the merge base and before the resolution; the revokes it fills in are the revokes that were in effect at resolution and intersect the adopted range, and only which ones are recorded, not their intervals). In the replay, a write that took effect after the merge base and before the resolution and is not in O covers the adopted item, and takes effect as usual, at the places where it supersedes the adopted item by the supersede relation of step 3 and is not superseded by a later write inside O: it is a write the user did not see at resolution and that was not listed in the impact, and a deletion should not let the adopted value cover it; at the places where it is itself covered by a write inside O, covering the adopted item would expose the value that the user decided to cover, so it does not count.
  Revokes and the adopted item on a field: **at resolution**, a revoke does not cover it, and a revoke there is handled by the check against the current state (an event table reports `revoked`, a state table judges it by filling in an interval without a value). **In the replay** the two kinds of table differ: on a state table a revoke is an interval without a value, and a revoke after the merge base and not in O is split by whether it is a revoke that this adoption filled in (items at or before the merge base were already below the version seen by the adopted write and covered by its value, so they do not cover): a revoke listed in the record as filled in does not cover the adopted item as a whole, whatever its interval becomes in the replay; one not listed (it did not take effect at resolution and took effect only because of a deletion) covers it over its whole segment. It is split by the whole revoke, not by interval: the dividing point between "the segment filled in at the time" and "the segment that appeared afterwards" may come only from content that is deleted later, and cutting along it would leave that end point in the deletion result; splitting by interval would also make the result depend on the order of several deletions. The cost is that the part of an already filled-in revoke that is extended by a deletion afterwards does not cover the adopted item either. On an event table a revoke governs only the existence of the row and is not a value item on a field (see "the value of a field" in "Replay rules"), so it does not cover the adopted item on a field: the row is still revoked, the adopted value stays on the field, and what is exposed when that revoke is undone later is the value the user adopted. Conversely, on an event table a field write outside the coverage set does not cover an adopted revoke either (a field write does not change the existence of a row); the only thing that can make it no longer count is a restoration of existence that is outside the coverage set and in effect at that moment.
  While a deletion is pending, pending items cannot be resolved on the rows / entities it affects (see "Cancelling a deletion and the grace period"), so when an adoption is judged, the row it is on has no item that is not in effect because of a pending deletion, and so the adoption record has none of this kind.
  The interval the adoption landed on at resolution is not recorded, and neither is the interval of the revoke that was filled in at the time: the end points of these intervals may come from content that is deleted later.
- **When a candidate is adopted, the contributions of the other candidates in the pending item that have the same value are all value sources too ("or")**: otherwise, once the evidence of the one adopted is deleted the value would disappear while the evidence of another candidate with the same value is still there.
- The value source of **returning to before the conflict** is a reference to the contributions in effect at the merge base (see "Execution semantics of each decision"); it is the same kind of operation as a revert, and for its deletion replay see "Replay rules · Reverting".

**Interval parameters**

- **The interval parameters of a state table are content**: the start point and the explicit end point are what the user said, and like fields they have a source: evidence can be mapped to them with the reserved key `valid` in `evidence_by_field`; if not mapped, all the evidence of this write is needed at the same time.
  When the source of the interval is deleted, this write has no contribution on that entity as a whole.
- The end points resolved from the default end point (`next_change`) and from the default interval of a correction (`corrected_span`) are saveslot's mechanical judgements (principle ②) and are resolved again after the deletion. But the value of an end point is obtained from other contributions (it stops at the stop point someone gave), so it is recorded in a separate content block that says which contributions it comes from; when those contributions are deleted, this block is erased together with them (see "Content derived from other contributions").
- **The contributions that give a stop point** (the authoritative definition is in "Time · State of a state table"): **all contributions for which that instant is an end point of their interval, counting both sides, and counting those already covered** (counting only contributions that rank before the write being resolved and are in effect; candidates and those awaiting confirmation do not count; the interval is the one in the current state, or in this replay when the deletion is replayed): those whose interval ends at that instant and those whose interval starts at that instant, including a revoke that leaves an adjacent gap, and the corroboration item that a corroboration endpoint belongs to. When a default end point, the default interval of a correction, or the end of a revoke that has only a start point stops at a stop point, the dependency recorded is these contributions; the two ends of a backfill segment on a state table are taken by the same rule (see the row for the constant `backfill` in "Other").

**Content derived from other contributions**

- In the event of a write, only the values the caller gave this time and the interval end points are its "own content". **Content obtained or copied from other contributions forms its own block and records which contributions it comes from**: the end points resolved from the default end point and the default interval of a correction; the intervals of the items written back by a revert or by taking the previous value; the segments covered by an `acknowledge` confirmation; the values and intervals of other writes in a pending item entry; the results and restatements written in a deletion event.
- **When a contribution it depends on is privacy-deleted, or is restated by that deletion, this block is within the erasure scope of that deletion.** What is still needed after the erasure (that item is still a contribution, the pending item is still open) is given again by the deletion event.
  **The only exception is the backfill segment of a state table** (the interval of the constant `backfill` recorded by `schema.switched`): it is erased only when a contribution it depends on is **deleted**, and not when it is restated; the backfill positions are as recorded and a deletion does not restate them, and if restating erased them, the constant would disappear permanently with an unrelated re-resolution. This does not cause a missed deletion: the dependencies recorded for a backfill segment are the contributions that give its two ends, taken by the rule of "the contributions that give a stop point" (counting those already covered), and the write from which the end-point date originally came is always among them (see the row for the constant `backfill` in "Other").
- **A constant itself is not a dependency**: the value of a schema constant is not erased by a deletion, and when a block copies a constant value, no dependency is recorded for it. But on a state table, for the segment that a constant backfilled, the interval comes from other contributions: when an interval end point or the range of a segment in a block comes from a backfill segment, the dependencies recorded for that backfill segment are copied into the dependencies of this block.
- The content in earlier historical versions that is derived from these blocks is marked "deleted" along with them: for example, if the default end point of a write stopped at a change point given by the deleted write, then when reading by instant between that write and this deletion, this item is shown as deleted and the old end point is not shown.
- For the shape of a block see [`../09-event-format.md`](../09-event-format.md) 3.5.

**Other**

- `change_sources` carries a field list and the source kind (value / operation / interval); the value source of a carried value is a row of one kind, "referenced contribution".
- **Values produced by conversion, migration and backfill also have value sources**:

  | Value | Value source |
  |---|---|
  | A value after a same-dimension conversion at write time | The value source of that write for this field (the same value, only the unit changed) |
  | The result of a deterministic conversion (`migrate`) | The value source of the contribution that was converted (in the first version an expression refers only to the old value of its own field, and one item is converted into one item); when that item is removed, the conversion result is removed with it. Conversions that refer to several fields come later, and then it is "the value sources of all inputs are needed at the same time" |
  | The restricted SQL expression of `backfill` | The value source of the old-value item at that place (the expression likewise refers only to its own field) |
  | A constant `backfill`, and the constant filled in when a required field is added (an expression-form `backfill` is not evaluated at a place with no old value and gives no value) | The contribution is recorded on that `schema.switched`, and the source kind is "schema constant", which points to no source data: it comes from the text written in the schema and **is not erased by any privacy deletion** (it belongs to the schema-text kind in the event format 9.4 "Blocks not erased by this deletion"), and the "will not be deleted" in the preview states this plainly; **a field that has been given a constant `backfill` (a newly added required field, an optional field changed to required) does not count as a required field in the existence judgement, the same for both kinds of table** (see "Existence of a row or entity" in "Replay rules"). A constant fills in only places where **an existing** row has no value for this field: on event tables and timeless tables, rows that are not revoked; on state tables, intervals where the entity exists and the field has no value; revoked rows, gaps inside a revoke, and intervals where the entity does not exist are not filled, since otherwise a revert would treat it as "filling a value in a gap", and when that revoke is undone later the row could not come back. **Where it is filled follows the record at the time of the switch, and a deletion does not change it**: the switch event records the backfill positions (for event tables and timeless tables, a list of row IDs; for state tables, the entity and the interval, where the interval is obtained from other contributions and the record says which contributions it depends on), and `apply` registers by the record and does not compute it on the spot. **The contributions a backfill segment on a state table depends on**: each end of this segment is taken by the rule of "the contributions that give a stop point" in "Interval parameters": all contributions for which that instant is an end point of their interval, counting both sides, and counting those already covered (the contributions on this field and on "existence"); it does not recurse along the dependencies of those contributions themselves. The backfill is applied as recorded, regardless of whether the entity exists in the replay (see event format 5.5). When a later deletion makes a field empty somewhere, **the constant is not filled in again** (a deletion may make a field empty anyway, and the result is recorded as "kept, some fields emptied"); when a contribution that the backfill interval of a state table depends on is deleted, that backfill segment is erased with it and no longer exists (see "Content derived from source data"); when the contribution it depends on is only restated, that backfill segment is not erased. By the counterfactual of the definition, if the deleted write had not existed at the time of the switch, the constant should have been filled in there; it is not computed that way because, for a deletion to restate the backfill of a switch, one more kind of contribution and a new restatement shape would be needed, and all it would buy is that a required field still has a constant value after the deletion |

- **The source level of a field**: not stored, computed on the spot: among the value sources of the field that are **still there**, the highest declared level among the evidence portions that have a literal match is taken; if no portion matched, it is "not matched" (see "Source level"). It takes part only in system ruling (later); when a deletion changes the level, it is ruled again by principle ② (see "Replay rules").

### Replay rules

**Method**: ① find the affected rows / entities: where the deleted source data appears as a value source, in which fields of which writes (including those reached through references by carrying); ② remove these contributions; ③ replay the writes of the affected rows / entities by `seq` according to the table below, and derived tables are recomputed accordingly (derivation is generated only by rules and has no contributions of its own to remove).
This is the way of computing the definition (it has the same shape as the "delete first, then derive again" of incremental view maintenance), and the result is given by the reference evaluator. Event tables, timeless tables and state tables use the same set of rules.

| Item | Rule |
|---|---|
| Which writes | **All writes** of the affected row / entity are replayed by `seq`, including those that had not taken effect (open conflict candidates, writes awaiting confirmation): whether they take effect is judged again by the following rows on the state after deletion; what a human has already handled is as recorded |
| Whether a contribution is present | The contribution of a field is present when its value source (several portions of the same write are needed at the same time) and the source of its interval parameters are all still present; a contribution carried by adopting a candidate is present when any one of the contributions referenced is still present; the items written back by a revert or by taking the previous value do not disappear with their carried sources, and their value is determined again in the replay (see the row "Reverting") |
| The value of a field | The last contribution by write number that is still present; for state tables, by valid-time point: the last write that is still present and whose interval covers that point. On event tables and timeless tables, when after a revoke there is another restoration of existence that is in effect and has not been registered as reverted, that revoke no longer counts: the field takes the value below it, and the row is not counted as revoked either (adopting a modification candidate on "existence" writes a restoration of existence and does not register that revoke, see "Execution semantics of each decision") |
| Same-value judgement (recomputed, for contributions only) | **The items written back by a revert, by adopting a candidate and by taking the previous value are treated the same way, like ordinary contributions** (the items written back by a revert and by taking the previous value have two limits, see the row "Reverting"). The baseline is what the version seen by the writer looks like after the deletion. A contribution that originally changed the value but became the same value in the replay: if it pointed to evidence explicitly, it becomes an additional source; if it did not, it produces no new version and no longer counts as a contribution; one that was originally same-value corroboration becomes a real value change once the value before it is removed |
| No-op (not recomputed) | **A field that was originally a no-op stays a no-op**, and does not become a change because the value seen was deleted. The value of a no-op was brought back unchanged from what the caller read from saveslot, and its source is the very contribution that was deleted; the log does not keep its value either (see "Provenance"). **An op by external key that did not enter the event (`unchanged`, `skipped`) is not replayed**: it is not in the log, and neither is its value. This is an explicit limitation of principle ②, which is the "the part that left no value when it was written stays as it is" in deviation 1 of the definition |
| Parameters (recomputed) | The start point and the explicit end point are used as they are (when their source is deleted, see "Whether a contribution is present"). **The default end point (`next_change`) is always resolved again from the original arguments, field by field, on the state after the deletion and before that write**: a deletion not only removes stop points but also lets old change points that were covered show again. The default interval of a correction (`corrected_span`) and the end point of a revoke that has only a start point are resolved again in the same way, with "now" taken from the time recorded in the write head. **The interval resolved again is recorded in the deletion event; the interval of a contribution is taken from the most recent event in the log that gave it**, and later `undo`, conflict criteria and references to it all follow the latest one |
| `ver` conflicts (recomputed) | Judged again by "Conflict handling · Conflict criteria" on the state after the deletion: a conflict exists only if, after the version seen by the write and before that write, there is still, after the deletion, an operation that changes the value in effect of that conflict unit and conflicts with it; if it does not exist, see the next row |
| After a conflict disappears | **A write that a human rejected**: whether or not it is still high-impact, and whether a target was a candidate or awaiting confirmation at the time of rejection (targets where the conflict still exists stay in the original conflict pending item as usual), its targets do not take effect and stay closed; the only exception is deviation 2: the parts that took effect or became corroboration at write time are unchanged. Rejection applies to the whole write ("this write is not wanted"), which is asymmetric with confirming, where a person is responsible only for the items they saw. Otherwise: if this write is not high-impact on the state after deletion → it takes effect at its own write number, and the conflict pending item is superseded. If it is still high-impact and has never been confirmed by a person → **it turns into awaiting confirmation** and does not take effect: the original conflict pending item is marked superseded, and the deletion event produces an `awaiting_confirmation` pending item. A write that wipes out a recorded change point must have been confirmed by someone, and a deletion does not bypass this guarantee. If it is still high-impact and **has been confirmed by a person** → it takes effect at the operation number of the confirmation: the confirmation was about the high-impact nature of this write, not only the targets that happened to be awaiting confirmation at the time; for a target that was in a conflict pending item at the time of confirmation, confirmation does not resolve the conflict for the person, and while the conflict exists it is still a candidate; after the conflict disappears because of the deletion, the only thing left is the confirmation gate, and it has already been passed. Items written by adopting a candidate or by taking the previous value are not in this category: they are a person's decision on a pending item, and when their range changes in the replay (grows, shrinks, or lands on a candidate with the same value instead) they do not go through the high-impact judgement again either; the preview and the deletion receipt list them separately |
| System ruling (recomputed, later) | When a conflict still exists, it is ruled again by the source levels that are still present after the deletion: if the candidate ranks higher → the candidate takes effect (system ruling); otherwise the current value is kept and the candidate stays in the pending item |
| High-impact (recomputed) | A write that was originally awaiting confirmation and not yet handled, and that is no longer high-impact on the state after deletion → takes effect at its own write number, and the pending item awaiting confirmation is superseded. The same when all the referencing parties of high-impact ② are deleted; an item marked `later` in ④ is handled the same way when its range is empty in the replay (all the later writes to be reverted being deleted is a special case of this); for the other cause of ④, "the revoke that is written back would hide a later write", it is the same when the writes hidden are all deleted or no longer give a value at that place. For a revert that took effect directly, when the new value that took effect is hidden only because of a deletion afterwards, it stays in effect by deviation 2, and the preview says so plainly. **A limit of this version**: the referencing party of ② is on other rows, which the replay cannot see; the following two kinds are reported as `not_implemented` as a whole, to be done together with the cross-row recomputation of the deletion stage: a revoke awaiting confirmation because of ② and not yet handled; when the table may be referenced (a `ref` field pointing at it in any schema version in the log), a revoke that did not take effect at write time and takes effect at its own write number in the replay after the deletion, that is, a revoke that was a candidate at write time (the deletion makes the conflict disappear) or a no-op (the row was already revoked at the time, and the deletion makes it no longer revoked there). A revoke goes to awaiting confirmation at write time for only one cause, ② (① looks only at writes, ④ only at reverts, and ③ is not done in this version), so a revoke awaiting confirmation is not in the latter kind: one not yet handled belongs to the former kind; a ② revoke that has been confirmed or rejected is carried out as recorded |
| Human decisions (as recorded) | The human decisions listed in the definition are carried out as recorded and take effect at the original write number; the deletion of an operation source does not revoke a decision (for a revoke without an interval, if its evidence is deleted the row does not come back). For a revoke with an interval, when the source of the interval is deleted it is handled as in "Whether a contribution is present": no contribution as a whole. The content of `keep_effective` is "these candidates do not take effect", as recorded. Adopting a candidate is likewise carried out as recorded, and the check against the current state done at write time (the row is revoked, a required field is missing in an interval without a value) is not done again in the replay, since otherwise a deletion would let a decision a person has already made be rejected afterwards and leave a new open pending item; the items it writes land by the ordinary rules: landing on a row that is revoked in the replay, the field value stays on the row and the row is still revoked; landing in an interval without a value where required fields are not all given, that place still has no value. An adopted revoke always lands a revoke item (one per segment, the range being the range of the adopted item minus the parts covered), whether or not that place already has no value at resolution: on a state table this is the same as an ordinary revoke written on a segment that already has no value; on an event table an ordinary second revoke is a no-op, but an adopted revoke does land an item, which is an exception, the reason being that it is a person's decision on a pending item. "That place already has no value" is the check against the current state at write time, and is not done again in the replay |
| Reverting (undo and taking the previous value) | `undo` and `take_previous` are two ways of taking the same kind of operation, and it consists of three things. **The authoritative definition is the pseudocode after the table**; this row is its textual description. **① The revert record (as recorded, listed when the write is made, not changed by replay)**: which changes of which operations on which targets are reverted, listed one by one as (event, target), where the target is a field or "existence", **and indexes are not listed**; one entry covers all items of that (event, target) in the replay, whether the index existed at write time or was produced by the deletion, and whatever the state at write time. Fields of an external key are never listed (a key is immutable once obtained, so there is nothing to revert); items filled in by a schema constant are never listed either (it is not a write, and in a revert it only covers earlier items as a taking-effect item outside the record). `undo` lists every target at write time of every base write of the operation being undone on this row, whether it was in effect, corroboration, a candidate or awaiting confirmation at the time, and regardless of which items remain now (the entries that were already covered by a later write when this `undo` was written are recorded separately in `skipped`, with `by_op`, for history and the receipt only); when the operation being undone is itself a revert, it lists every target that its base writes appear in within its revert record; when the operation being undone is a confirmation, it lists (the event of the confirmation, every target the confirmed write had at the time it was written), all determined by the record and independent of the state at the moment of `undo`; the later writes that `include_later` reverts along with it list (the base write of that item, the target of that item), marked `later`; `take_previous` lists the (event, target) pairs within the pending item's conflict unit and interval that had an item take effect after the merge base and before the resolution (including corroboration, including items written back by a revert or by taking the previous value, whether or not they were already covered at the time). The candidates of the pending item do not enter the revert record of `take_previous`; they are closed by the resolution of the pending item. **② The range (determined again in the replay)**: the range of an item = its interval in the replay, minus the part that is still covered (the part where, after it and before this revert, an item that is in effect and not in the revert record superseded it; deleted operations do not count); `take_previous` is further intersected with the interval of the pending item, where the interval of the pending item = the union of the intervals of the candidates that still exist in the replay; an item marked `later` in `undo` is further intersected with D(x) (the union of the intervals of the items that the operation being undone has in effect in the replay and that this item can supersede, see step 2 of the pseudocode). On event tables and timeless tables an item is an indivisible whole: while it is still covered the whole item is not reverted, otherwise the whole item is reverted. The registration takes effect only within the range, and outside the range the item stays in effect as usual. **③ The value position (as recorded) and the value (determined again in the replay)**: for `undo` it is before the operation being undone, for `take_previous` it is the merge base operation number recorded at resolution (not recomputed); at each place in the range, the state at that position in the replay is taken: when a field has no contribution at all it is "no value" (the same for all three kinds of table); where that place is inside a revoke, an item with no content is written back (registration only: the filling-in that was reverted no longer takes effect and the revoke shows again, and the value under the revoke is not touched); for "existence", if it exists then existence is restored, and if it does not exist then a revoke is written back. **In no case does it fall back to the value of the reverted item itself.** **Whether a reverted item is in effect follows the revert record, not what is written back**: within the range it gives no value, adds no source, and its corroboration endpoints do not count as stop points. **The items written back**: when among the items covered by an entry of the revert record there are items that are contributions in the replay (including corroboration) and the range is non-empty, they are not dropped for having the same value as before; when none of the items covered by an entry of the revert record is a contribution in the replay, or the range is entirely empty, the written-back item is no longer a contribution (if all candidates are deleted the range is empty and the side in effect takes effect as usual; if all of the side in effect is deleted while a candidate remains, the written-back item is no longer a contribution and the candidate stays closed). **Writes outside the record**: a write that had not taken effect at the time of the revert and takes effect afterwards because of a deletion elsewhere is not in the revert record. When it ranks after some item of the revert record, it counts as covering that item, and the part it covers is not in the range and takes effect through it; the preview lists it as "will take effect". The conclusion is the same for the three kinds of table. **When the target of the revert is itself a revert** (undoing an undo, undoing the resolution of a `take_previous`): it is handled as an ordinary write, the items that the operation registered as "reverted" stay registered, and the value shows again through the write-back items of this one; the pending item stays resolved. **Registration happens only when this revert takes effect**: when it goes to awaiting confirmation it does not register, after confirmation it registers, and when it is rejected or superseded it does not register |
| Existence of a row or entity (recomputed) | **A field that has been given a constant `backfill` (a newly added required field, an optional field changed to required) does not count as a required field in the existence judgement, the same for both kinds of table** (the same rule as the definition of "has a value" in "Time · Intervals without a value", with the same scope for "has a value / interval without a value" judged at write time; the write check still requires all required fields to be carried): after the backfill is erased this field is empty, and the row or entity still exists, with the outcome recorded as "kept, some fields emptied" (`kept_fields_cleared`). Event tables, timeless tables: the row exists if **every required field has at least one contribution that is still present, and at least one field has a contribution that is still present, is non-empty and is not a constant backfill**, and each field takes the value above; otherwise the whole row is deleted. Clearing a field (the value is empty) is also a contribution and takes part in "the last contribution that is still present" as usual, but it cannot hold up a row by itself (an `insert` with only empty values is rejected at write time, reporting `empty_row`, see the contract "The encoding of values"; such a row can appear only through a deletion replay, and how writes to it are handled afterwards is decided together with the deletion replay). State tables are judged by valid-time point: **if all required fields have a contribution that is still present and covers that point**, that point has a value, and the other points are intervals without a value; when the table has no required field, that a point has a covering contribution that is still present on any field means it has a value, and clearing (the value being empty) counts too; this differs from the event tables and timeless tables above, where "clearing cannot hold up a row by itself": on a state table, a segment that has only ever been cleared has a value, with the fields empty (see "Time · Intervals without a value"); a write located by `entity_key` counts as having given the key fields (the key values used for locating are the values this request carried, and the source is the evidence of this write). A write that adds by external key, and a write that adds a key to a row, likewise count as having given the external key field; a key field has a contribution only in the write that obtained the key, and if the source data of that write is deleted, this row certainly loses its external key, and the row itself is kept or dropped by the rules for the row |
| First-creation mark (recomputed) | After the write that created some entity or row loses all its contributions, the earliest write still present that gives the key fields (or all required fields) becomes the first creation; the change is recorded in the deletion event, and whether `undo` is possible is judged by the latest mark |
| Suspected duplicates, literal match (not recomputed) | Judged once at write time, as recorded. When a row that is flagged, or a row it lists, is deleted as a whole row, a `flagged` pending item is handled by the table of "Suspected duplicates": if the flagged row is gone, or the rows listed no longer match, it is marked superseded; if only some of the rows no longer match, the entry is refreshed (the reasons are all `matched_changed`). A deletion never generates a new `flagged` pending item |
| Writes by external key (see "Writing by external key") | **The located result** (the row ID this op landed on) is as recorded and is not located again: the row ID is recorded in the metadata, and locating again would let a deletion rewrite a later sync onto another row. **The baseline position** (the version seen, field by field) is as recorded, handled in the same way as the `ver` obtained by fallback; a `ver` conflict is judged again on the state after the deletion by it. **Same-value recomputation**: the baseline value is the value of the most recent sync contribution on this field before this write that is still present after the deletion (the key was transferred, and the sync contributions deleted on the original row no longer count); what was originally a no-op stays a no-op. **A transferred key is as recorded**: if the key contribution of the write that added the key is still present, the key stays on the row where it was added; after that contribution is removed by the deletion being carried out, the key goes back to the original row that gave it up (still revoked), and during the grace period this key is frozen. The revoke of the original row is a human decision, as recorded, and a deletion does not make it exist again. After the key has gone back to the original row it **no longer counts as "the key was transferred"**: a sync op by that key after the key was added is located as recorded (still landing on the row to which the key was added), but on the state after deletion that key belongs to the original revoked row, and this write is restated by "Revoked rows do not come back" as no longer a contribution (`dropped`), without using the baseline from when it was transferred |
| Those that have taken effect stay in effect | A write that originally took effect, even if recomputing it on the state after deletion would make it a conflict candidate or awaiting confirmation, **takes effect as usual and is not reverted** (deviation 2 of the definition), and the preview says so plainly. Example: the deleted write originally made a later same-value corroboration not count as a change, and after it is deleted it becomes a change that sits between `ver` and this write; or the deleted write originally covered some change point, and after it is deleted a write with an explicit end point would wipe that point out. The unit of protection is the (event, target) whose items all took effect at write time, see deviation 2 in "Definition of the result of a deletion" |
| `ver` | A row / entity changed by a deletion gets a new `ver`, which encodes the operation number of the confirmation (or cancellation) of this deletion (see "Numbering") |

**The authoritative definition of reverting** (the pseudocode of the reference evaluator; the same code is used at write time and in the deletion replay, and where the textual descriptions of other documents disagree with it, it holds)

```
Revert(record R, value position pos, this operation's number n, contribution set C, candidate set K):
  # R    The revert record: a list of entries, each an (event e, target t), where t is a field f or "existence", with no index.
  #      It may carry the as-recorded mark later (a later write reverted along with it by include_later). undo also records skipped: the entries
  #      that were already covered by a later write when this undo was written, with by_op, for history and the receipt only; it is not read here.
  #      As recorded, not recomputed.
  # pos  "before operation m" (undo, m is the operation being undone) or "up to operation m" (take_previous, m is the recorded merge base). As recorded.
  # C    All contribution items in the replay (deleted ones are not in it); each item has: the operation number, the target (a field f or "existence"),
  #      the state (in effect / corroboration / candidate / awaiting confirmation), the interval, the content (a value, no value, a revoke, a restoration of existence),
  #      and which reverts have already registered it (each with its range and the operation number of that revert).
  # Order of evaluation: reverts are evaluated once each, from the smallest operation number to the largest. A revert reads only the registrations made by reverts with a smaller operation number, so there is no cycle.
  #          A revert that takes effect at its own write number because of a deletion is placed in this order by its own operation number.
  # K    The candidate items of the pending item for take_previous; not used for undo. Identified by (event, conflict unit), not by index: a recorded candidate write
  #      is on this pending item's conflict unit and is a candidate in this replay (or has the same value as the version it saw, did not point to evidence and no longer counts as a contribution:
  #      then it has no item, and one is computed from the interval that its write-time rules resolve in the replay and its value, which is the "shadow"; the shadow is in K,
  #      and the domain, the landing place and the "or" of candidates with the same value all count it, but it is still not a contribution and takes no part in taking values elsewhere), and an item that belongs to this pending item (one that turned from awaiting confirmation into a conflict,
  #      or that belongs to a successor pending item, does not count; the part of a candidate closed by this resolution that is extended by a deletion still belongs to this pending item;
  #      a write that meets a revoked field in a conflict belongs to the pending item on "existence", and one that meets only field changes belongs to the field's pending item).
  # Interval: on state tables a valid-time interval; on event tables and timeless tables the interval of every item is the same indivisible whole ⊤.
  # A write-back item with no content (the registration-only kind, see step 6) counts as nonexistent in both value taking and "superseding": it gives no value and covers no one.

  1  R' = { c ∈ C | (c's event, c's target) ∈ R }: all items in the replay of every (e, t) in R,
          whether the index existed at write time or was produced by the deletion, whatever the state at write time.
          So the part of a reverted operation that was a candidate or awaiting confirmation when written and takes effect later because of a deletion is in R' as well.
          Operations not in R are not added: an operation that takes effect because of a deletion after the revert and that R does not list is handled as a "write outside the record" (see below).
          When the target m of undo is itself a revert, R lists every target that the base writes of m appear in within m's revert record,
          so write-back items grown after m because of a deletion are in R' as well.
     in = [ r ∈ R' | r's state is in effect or corroboration ]

  2  If it is take_previous:
         domain(r) = ⋃ { interval(c) | c ∈ K and c is not deleted }  # event tables: some item in K is not deleted → ⊤, otherwise ∅
                                                    # a c that became the same value in the replay (no longer a change) still counts; only deletion makes it not count
     otherwise (undo):
         r's entry is not marked later: domain(r) = all valid time (event tables: ⊤)
         r's entry is marked later  : domain(r) = D(r) = ⋃ { interval(r') | r' ∈ in, r''s entry is not marked later, r supersedes r' by step 3 }
                             # the union of the intervals of the items that the operation being undone had in effect in the replay and that r can supersede; ⊤ or ∅ on event tables.
                             # Only items in "in" are taken: the part where the operation being undone was a candidate never took effect and does not count as "intersecting";
                             # when a deletion makes that part take effect it enters "in" and D grows accordingly. for r, only items in effect (not corroboration) are taken, see how entries are listed.

  3  For each r ∈ in:
         covered(r) = ⋃ { interval(x) ∩ interval(r) |
                        x ∈ C, x's state is in effect, (x's event, x's target) ∉ R, operation number(r) < operation number(x) < n, x supersedes r,
                        counting only the part of x that has not been registered at that place by a revert with operation number smaller than n }
         range(r) = ( interval(r) − covered(r) ) ∩ domain(r)

     x supersedes r:
         r is an item of field f      : x is an item of field f, or x is a revoke
         r is a revoke             : x is a restoration of existence, or x is a field item filling in a value in this gap
                                (only a field item that has a value counts as filling in; one already registered as reverted at that place does not count, see the previous sentence)
         r is a restoration of existence         : x is a revoke

  4  If this revert itself did not take effect (awaiting confirmation, rejected, superseded): do not register, do not write back, end.
     # There are three times at which it takes effect: at write time; awaiting confirmation and taking effect through confirmation (the base write triggered by the confirmation carries its own R,
     # listed by the state at confirmation, and n is the operation number of that resolution); awaiting confirmation and, because a deletion made it no longer high-impact,
     # taking effect at its own write number (R is the one listed when it was proposed, n is its own operation number, and the registration is done by the application of that deletion event; at the moment it takes effect,
     # the check "the row is revoked" is done together by the write-time rules: if after the application the row is still revoked
     # it does not take effect, it is handled as rejected, and it does not register or write back).

  5  Registration: for each r ∈ in, record "r has been reverted by operation n within interval(r) ∩ T(r's target) ∩ domain(r)",
     T(t) = ⋃ { range(r') | r' ∈ in, r''s target is t }, that is, the sum of the intervals of the items that step 6 writes back on target t.
     # Invariant: the sum of the intervals of the items this revert writes back on target t = T(t). apply reads only the intervals of the write-back items to register and does not compute the range;
     #         the D of an item marked later is computed by apply from the block itself (the union of the intervals of the in-effect or corroboration items of the operation being undone that it can supersede).
     # The part that interval(r) ∩ T has beyond range(r) is where r is covered by a write outside the record while another recorded item on the same target is not covered;
     # there it is covered by the written-back item anyway, and registering more changes no value.
     The domain of the items of the operation being undone is all valid time, which is interval(r) ∩ T; an item marked later is further intersected with D(r),
     when ④ does not hold (the range of an item marked later is entirely empty), if an item of a later write is registered, at the registered place it has already been superseded by a write outside the record,
     or already registered by an earlier revert, so the registration changes no value (apply does not compute covering, so the registration is not made empty).
     Items outside "in" are not registered (items that are still candidates or awaiting confirmation, including candidates that fall in the range of other entries).
     Effect of registration: within that range r gives no value, adds no source, and its corroboration endpoints do not count as stop points; outside the range it is as usual.
     Existing registrations are not touched.

  6  Write back. For each target t (each field that appears in "in", and "existence"):
         T = ⋃ { range(r) | r ∈ in, r's target is t }
         For each place p in T:
             S = state(pos, t, p)
                 # Uses only contributions whose operation numbers satisfy pos, counts only registrations made by reverts whose operation numbers satisfy pos, and takes values by the ordinary rules of replay:
                 # field  : the last item or revoke of field t at that place that is in effect and not registered as reverted at that place;
                 #         if it is a field item → its content; if it is a revoke → inside a revoke; if there is none → no contribution at all
                 # "existence": whether that place is inside a revoke that is in effect, not registered as reverted at that place, and not restored or filled in afterwards
             field t  : S has a value → write back this value, the value source being a reference to the item that gives it
                                (when what gives it is the constant backfill of a schema switch: copy this value, the source recorded as "schema constant",
                                  not referenced; the constant itself is not listed in the dependencies, since its value is not erased by deletion.
                                  On state tables this place comes from a backfill segment, whose interval comes from other contributions, and the dependencies are copied by step 8)
                       S has no contribution at all → write back "no value"
                       S is inside a revoke → write back an item with no content (registration only, giving no value, covering nothing below).
                                      After registration, the reverted item (the one that filled a value in the gap) no longer counts as filling in, the revoke shows again,
                                      and this place goes back to the gap; the value under the revoke is untouched, and appears as usual when the revoke is reverted or deleted later
             "existence"  : S is existence → write back "restoration of existence"
                       S is nonexistence → write back a revoke
         Merge adjacent places whose content and giver are both the same into one item. "Existence" has no giver, so adjacent places are merged by content only:
               adjacent places across different revokes are merged into one item that writes back a revoke, and the dependencies of step 8 list all these revokes.
         By the interval block at write time: where a newly produced index splits from is decided by the interval block that the base write event gave at write time
               (it is fixed in the log and does not change with the order of deletions or with a cancelled deletion): look at which original item's interval at write time
               the start of the new index's interval in this replay falls in; if it falls outside all intervals or in a gap, it belongs to the left neighbor (ordered by the start of the interval at write time,
               to the first item if it is at the very front). It is used only for numbering and for part 2 of the declarations of premises (see "The premises of a write"), and does not affect the covering of a revert:
               covering is by (event, target), see step 1.
         Indexes: at write time they are numbered from 0 by interval start. In the replay, each original item keeps its index and stays on the first segment that intersects its interval block at write time;
               indexes produced by earlier deletions stay on the first segment that intersects their original interval (which segment they land on affects only the numbering);
               an original item whose interval block at write time has been erased by a deletion carried out at expiry is likewise handled by its original interval
               (the "where it splits from" above also uses the original interval for such an item); original indexes with no readable interval block at all
               (once restated as dropped and later a contribution again) are reused in order of start point from smallest to largest;
               newly split items are numbered on from the largest index already used by that target.
               Original interval = the interval most recently given for this item in the log before this replay (its original interval block, or the restatement of an earlier deletion):
               search backwards in log order, skipping blocks given by the confirmation events of cancelled deletions (blocks given by a cancelled deletion count in no replay;
               the restatement of the cancellation event itself does count), and skipping those restated as dropped, and take the first block that gave an interval.
               It is used only so that newly produced indexes keep their numbering.
               When several original items fall into the same segment, they are always merged into one, keeping the smallest index, and the others are restated as dropped: the items of the same (event, target)
               are covered by the same set of reverts, so there are no longer cases cut apart because of different covering.
               For details see event format §5.7 (the items of any write follow this rule, not only the write-back items of this step).

  7  The state of the write-back items:
         "in" is empty, or all range(r) are empty → no write-back items (the existing write-back items are no longer contributions,
                                          that is, restated as dropped in the event format)
         otherwise → in effect, taking no part in the same-value recomputation (not dropped for having the same value as before)

  8  The contributions the write-back items depend on (the basis for erasing and restating intervals):
         the items in "in"; the items that give S in step 6; the items that cover r in step 3; for take_previous, also the items in K that are not deleted;
         plus: at each interval end point of a write-back item, the givers of the two adjacent segments' states at the value position (both sides listed;
               when one side has no contribution, only the other side is listed; when one side is inside a revoke, that revoke is listed).
         When any of the above is a schema-constant backfill (giving S, giving an end point, or covering r in step 3):
               the constant itself is not listed (its value is not erased by deletion); on state tables it is a backfill segment,
               and the dependencies recorded for that segment of backfill are copied in (the interval of a backfill segment comes from other contributions).
```

- At write time: C is all the contributions at that time; the result of step 6 is the write-back items in this base write, and step 5 is the registration of `apply`.
- In a deletion replay: C is the set after the deleted contributions are removed and the remaining items are restated by the replay result; R and pos do not change. When the result of step 6 differs from what the log most recently gave, the deletion event restates it; the range of step 5 is updated accordingly.
- How the revert record is listed at write time (`undo` lists every (event, target) of the target operation, except external-key fields; `take_previous` lists the (event, target) pairs within the pending item's conflict unit and interval that had an item take effect after the merge base, likewise excluding external-key fields) is not in this passage: it is done only once at write time, and its result is R. So external-key fields are never in R, write-back items never touch key fields, and "undoing an undo" cannot produce two rows with the same key either. **Items filled in by a schema constant are never listed in any revert record**: the entries of the target operation listed by `undo`, the later writes reverted along with it by `include_later`, and the "(event, target) pairs that had an item take effect" of `take_previous` all skip them (when the target of `undo` is itself the operation number of a schema switch, it is rejected outright). So a constant backfill appears in C only as a "taking-effect item outside the record", and covers earlier items as usual by step 3.
- **The premises of a write are not part of C, and a revert does not read them**: a declaration is not a contribution; an op with `revert` cannot carry a premise, and a revert makes no declaration itself. After a revert, the origin items of the current values of the fields have changed, and the marks are computed on the spot from the new origin items: the value that is written back, followed along its carried references to the end, is the contribution of an earlier item, and the declaration of that item is shown again accordingly (see "The premises of a write").
- A write y that takes effect after the revert and is not in R: when it is in C and its operation number is after some r and smaller than n, it covers r by step 3, and the part it covers is not in the range and takes effect through y; when it ranks before all r it covers no one, and within the range it is covered, in order, by write-back items that have content. A write-back item that only registers and has no content covers nothing: when the value position is inside a revoke and at that place there is another filling-in that is outside the record and takes effect later, what is exposed is that filling-in, not the gap. The three kinds of table use the same code.

- For the definition of "change point" and "stop point" see "Time · State of a state table".
- The meaning of "takes effect at its own write number because of a deletion": when contributions are ordered by write number it ranks at its original position; changes to business tables and version tables are recorded at the operation number of the deletion confirmation event.

### Corollaries

These follow from the definition and the replay rules; they are not additional rules. Each corresponds to a property test on the reference evaluator (architecture §11).

- **The existence of a row accumulates per field**: no single write is required to supply all required fields; the contributions to the required fields may come from different writes, and a value whose provenance is intact is not lost.
- **Deleting a correcting sentence returns the value to what it was before the correction**: an event table and a state table give the same result.
- **A fact corroborated by another source does not disappear**: the contribution of another write is still there. The exception is a write with a stale `ver` that was split into a corroboration part and a candidate part: it is not protected by deviation 2, and when its base source is deleted the whole span is judged again (see "Definition of the result of a deletion").
- **Adjacent segments of a state table recover their original values and leave no interval without a value**: the segments cut out by the deleted write disappear, and the earlier writes it had covered become visible again; the old change points that come back make the default end points shrink back accordingly.
- **A reverted value is deleted together with the contribution it carried**: at that place the value taken is the one before the operation that was reverted in the replay; it does not fall back to the value of the write that was undone. A revert request is only an operation source and cannot keep a value alive.
- **A deletion may make a write that was not in effect take effect**: a candidate whose conflict causes have all been deleted, a write awaiting confirmation whose high-impact causes have been deleted, a candidate with a higher level after the deletion (system ruling, later). By the definition they take effect, **but this must be visible**: `deletion_preview` lists "the following writes that were not in effect will take effect" separately, and the deletion receipt and the "deletion confirmed" event state it;
  the corresponding item is marked "superseded" (reason code `deleted`); a conflict that still exists and is only decided again leaves the item pending, as with an ordinary system ruling; when a candidate in the same item is still pending, the item stays pending and is refreshed (the candidate that took effect is removed from the item). Cancelling the deletion returns it to the original state.
- **A conflict that disappears but is still high-impact turns the write into awaiting confirmation** and does not take effect directly; the preview lists "writes that will turn into awaiting confirmation" separately.
- **A deletion does not add pending items**: a write all of whose items took effect when it was written stays in effect and does not become a conflict because of a deletion; for a write only part of which took effect when it was written, the part that is sent back belongs to its original item and no new item is opened. Every pending item that newly appears is either an awaiting-confirmation item converted from a conflict item that this deletion superseded, or comes from an item the same write already had pending: one that returns to pending because of this deletion with the same kind as the original item goes back to the original item (if an earlier deletion had superseded the original item, it is restored; if it was only refreshed and still pending, it is merged back; the successor item it currently sits in, if that becomes empty as a result, is superseded). One whose kind changed (awaiting confirmation <-> conflict) is handled as follows: if the original item has been superseded by this deletion or an earlier one it stays superseded; if it was only refreshed and other members are still pending it stays pending as before; and a new item succeeds it one to one. If an earlier deletion has already opened a successor item of the same kind for it, it stays in that item and no new one is opened. The original item is the item the write was in when it was written, not the item that later succeeded it.
- **A conflict a person has already resolved is kept as recorded**: after a conflict is resolved with `keep_effective`, deleting the source of the value in effect does not make the candidate take effect; the value in effect that has lost its source falls back, by the ordinary rule, to the last contribution still present. When `take_candidate` was chosen, the value is a reference to the candidate's contribution; what is kept as recorded is the merge base, the covered set and the revokes it filled in, and the interval the adoption lands on is found again in the replay (see "Carried values"); when `take_previous` was chosen, what is kept as recorded is the changes of which operations on which targets were reverted, and the operation number of the merge base; the range and the value returned to are found again in the replay (see "Replay rules · Reverting").
- **Order does not matter**: deleting A and then B = deleting B and then A = deleting {A, B} at once. What is compared is states and items, not the indexes of restatements or `dropped` entries; a later write carrying an old `ver` may be judged differently because the deletion history differs (a deletion counts as a change over the interval it recorded).
- **Cancelling restores**: after deleting A and cancelling, the part not overwritten by writes made during the grace period equals the replay result of "A was never deleted, but writes recorded as kept in effect take effect at their own write numbers, and writes whose item was kept superseded do not take effect either"; when neither exists, it equals the state in which A was never deleted (see "Cancelling a deletion and the grace period"). A write kept in effect can change the judgement of other writes along with it (for example, another write no longer counts as high-impact and takes effect), which is a normal result of the rules and is listed separately in the receipt. A decision made during the grace period can only land on rows not affected by this deletion (see "Cancelling a deletion and the grace period"), and those rows are the same in both replays to begin with.
- **No over-deleting**: a contribution whose value source does not include the deleted source data is not removed. But the business instants at which it takes effect may change because the stop points are recomputed: a deleted write had been stopping the default end point of another write, and after the deletion that write extends and covers another intact contribution (example: `[10-01, ∞) 5000`; `[11-10, 11-20) 4000`; "3000 from 11-02" gives no end point and stops at 11-10. Delete the sentence of 4000, and 3000 extends to open-ended, and after 11-20 the original 5000 is covered by it). This is a change of value: the entity gets a new `ver`, and the preview lists it as "re-segmented". A revoke given only a start point extends in the same way: when its end point stopped at a stop point given by the deleted write, after the deletion the revoke extends past it, and a write that falls into the extended part and did not bring all required fields no longer holds up that span, so the span goes from having a value to having none; the preview and the receipt list these intervals and the reasons separately (see "What the preview and the receipt must state").
- **No missing deletes**: every value, segment end point, item entry, translation and group key that remains depends on none of the deleted source data; content in the log that was derived from the deleted contribution is cleared too (a default end point on which another write stops, intervals copied into the results of a revert or a deletion, including end points that come from the adjacent segment and end points that were carried over through a constant-filled segment). A no-op field keeps no value, so "passing a value back unchanged" does not let a deleted value survive through another request. **The only exception** is the fingerprint of other requests' request keys and explicit idempotency keys: they are hashes computed over the original request body, and contain the values that request passed back unchanged, so they are deleted only together with that request's own evidence (see [`../09-event-format.md`](../09-event-format.md) 9.5).
- **`undo` reverts cleanly**: after a deletion extends the default end point of an old write, `undo` of that write reverts the whole extended span, and leaves no residual segment that no write can undo.

**Example (event table runs#1)**: #41 inserts date, distance 15 km, feeling (evidence R1); #57 corrects distance → 5 km (evidence R3).

| What is deleted | Replay | Result |
|---|---|---|
| R1 | All contributions of #41 are removed; distance still has the contribution of #57, date has no contribution still present | The whole row is deleted; R3 is kept as source data, and the data it produces is empty |
| R1, but before the deletion the Agent corroborated date field by field with R3 (same-value write #60) | #41 removed; date ← #60, distance ← #57 | Kept: date, distance = 5 km; feeling has lost all contributions and is empty |
| R3 | #57 removed | Kept: distance returns to 15 km, new `ver` |

**Example (state table promo budget)**: #10 `[10-01, ∞) 5000` (s_R1); #15 `[11-10, ∞) 4000` (s_R2); #18 start point 11-02, `next_change`, resolved to `[11-02, 11-10) 3000` (s_R5).

| What is deleted | Replay | Result |
|---|---|---|
| s_R2 | #15 removed; the end point of #18 is resolved again by `next_change` over {#10} to open-ended | `[10-01, 11-02) 5000`, `[11-02, ∞) 3000` |
| s_R5 | #18 removed | `[10-01, 11-10) 5000`, `[11-10, ∞) 4000` (the adjacent segments recover their original values) |

In the first row the interval of #18 changes from `[11-02, 11-10)` to `[11-02, ∞)`, and this new interval is recorded in the deletion event. After that, `undo` of #18 reverts the whole `[11-02, ∞)`, and the result is `[10-01, ∞) 5000`.

**Example (revoke with an interval)**: #10 `[10-01, ∞) 5000`; #20 revokes `[11-05, 11-15)` (evidence s_R7: "the two weeks from November 5 to 14 don't count toward the budget").

| What is deleted | Replay | Result |
|---|---|---|
| s_R7 | The interval of the revoke came from s_R7; its source is gone, so #20 as a whole has no contribution | `[10-01, ∞) 5000`, the interval without a value disappears |
| s_R7, but #20 is a revoke without an interval (it revokes the whole entity) | A revoke has no content and is a person's decision, so it is kept as recorded | The entity still has no value over all time |

**Example (no-op)**: W1 writes `note = "X"` (evidence S1); W2 resends the whole row with `note` passed back unchanged (evidence S2, no-op). Delete S1: the contribution of W1 to `note` is removed; the `note` of W2 stays a no-op. `note` is empty when it is an optional field, and the whole row is deleted when it is a required field. There is no second copy of "X" in the log.

**Example (revert)**: #101 `[10-01, ∞) 5000`; #103 `[11-10, ∞) 4000` (value source `s_b2`); #109 changes `[11-10, 11-20)` to 4500; #111 reverts #109 and writes the 4000 of #103 back to that segment. Delete `s_b2`: #103 is removed; the decision in #111 to revert #109 is kept as recorded, and what it returns to is the value before #109 in the replay, that is **5000** (#101), not 4500. The result is 5000 throughout, and neither change point, 11-10 or 11-20, exists any more.

**Example (conflict r11)**: #46 distance 9 (s_15); #47 9.5 (s_16); #48 writes 10 with a stale `ver` (= #46) (s_17) → same level, stays 9.5, `pi_2` pending.

| What is deleted | Replay | Result |
|---|---|---|
| s_16 | #47 removed; after the `ver` of #48 there is no write that changes distance, so there is no conflict → ordinary write | distance = 10; `pi_2` superseded; the preview lists separately "the 10 of #48 will take effect" |
| s_17 | #48 removed | 9.5, no conflict; `pi_2` superseded (the candidate has lost all of its value sources) |
| s_16, but `pi_2` had already been resolved by a person with `keep_effective` | #47 removed; "the candidate does not take effect" is a person's decision and is kept as recorded, so the 10 of #48 does not take effect | distance falls back to the last contribution still present: 9 (#46) |

**Example (conflict disappears but still high-impact)**: budget `[10-01, 11-12) 3000`, `[11-12, 11-20) 2800`, `[11-20, ∞) 2500`. #41 writes `[11-25, 12-01) 2600` (s_10). B writes `[11-10, open) 2000` (#50) carrying the `ver` from before #41: it conflicts with #41, becomes a candidate, and `pi_3` is pending.

|---|---|---|
| s_10 | #41 removed, and `[11-25, 12-01)` falls back to 2500; after the version seen by #50 there is no write in effect that changes `amount`, so there is no conflict; but it would still wipe out the two change points at 11-12 and 11-20, and no person has ever confirmed it | #50 **turns into awaiting confirmation** and does not take effect; `pi_3` is superseded and a new item awaiting confirmation is generated; the preview lists separately "#50 will turn into awaiting confirmation" |

### How the result lands in the log

- **The "deletion confirmed" event records the complete result**:

  | What the result contains | Description |
  |---|---|
  | What each affected row / entity looks like after the deletion | Per field and per item (per interval for a state table), each with its value source; the new `ver`. **Which ones are listed is the same for all three kinds of table**: a field whose value, or whose contribution item that supplies it, differs from before the deletion is listed, and so is one supplied by an item restated this time (the two kinds of segments a state table "gives by segment" are a special case of this). A row listed only because its suppliers, judgement results or the blocks that supplied them were given again, with its value unchanged, gets the outcome "only the source changed" (`sources_changed`). When a row in the result does not exist in the replay (for example, all blocks of the write that inserted it have been removed), `apply` creates it. **A row whose supplier of "exists" changed is listed in full** (the contribution that created it was deleted and the row stays through other contributions): the value and the supplier of every field are listed, including those from schema constants, and the row is newly created in the replay from this result with all fields present. **When an "exists" item is deleted or restated (including restated unchanged), or when a write-back item that is registration only (`uncovered`) is restated, that row or entity must be listed**, the same for all three kinds of table: on event tables and timeless tables whether the row exists is expressed by the outcome, and the outcome takes the existing values as they are after the deletion (whole row deleted, kept with some fields empty, some fields returned to earlier values, or "only the source changed" when no value changed); on a state table the segments of every field that intersect the intervals of these items are listed whole, and "the intervals of these items" take the union of the interval given most recently before the restatement and the interval after the restatement. When the log is replayed from the beginning after the tombstone, the original interval blocks of these items have been removed and are not applied at the original event, so holes and registrations can only be obtained from here. **On a state table, whenever an entity is listed (for whichever reason), all of its intervals without a value after the deletion are given** (an empty list when there are none) |
  | Restated contributions | Every item whose judgement result changed after the replay, with its complete new result (effect state, whether it changes a value or corroborates, interval, the contributions it depends on; for an item written back by a revert, the new value and the carried reference as well): writes that take effect because of the deletion, writes that turn into awaiting confirmation, items that swap between changing a value and corroborating, items whose default end point or default correction interval was resolved again. An item whose interval block was cleared by this deletion but which is still a contribution is also given again here. A cancellation event additionally restates unchanged (even if the result did not change) the items whose most recently given interval block came from the deletion being cancelled: blocks given by a cancelled deletion no longer count ("The authoritative definition of reverting", step 6), and if they were not restated, looking back for the most recently given interval would skip over its current interval and reach an outdated block |
  | Changes to first-creation marks | |
  | New items brought out by writes that turned into awaiting confirmation | Those whose conflict disappears but which are still high-impact (see "Replay rules") |
  | Items superseded because of the deletion | |
  | (row, field) pairs to be extracted again | See the translation results in "Content derived from source data"; extraction jobs are later |
  | Rule version used in the recomputation | See "The write request · Rule version and policy version" |
  | Expiry instant | |
  | List of content positions to be physically erased at expiry | See below |

  Derived writes are generated separately by `delete` as derived-write events: **one is appended for every derived partition the affected rows fell in before and after the deletion, even if the result did not change** (the rule on the derivation-rule side that "unchanged results are not recorded" does not hold for a deletion). When the log is replayed from the beginning after the tombstone is applied, the deleted blocks have been removed and the intermediate states differ from what they were then; the complete result written in the deletion event and these derived writes are the only place that pulls the end back to the online state. **Cancelling a deletion is symmetric with confirming it**: a cancellation event likewise appends one derived write for every derived partition the affected rows fell in before and after the cancellation, even if the result did not change.
  Example: #41 inserts a row (R1: date, distance, feeling), #57 corrects distance (R3), #60 corroborates date field by field with R3. Delete R1: the value of date does not change, and its supplier changes from #41 to #60, so it must also be listed in the result; if only feeling were listed, then replaying from the beginning after the tombstone, all blocks of #41 have been removed, #60 is a corroboration and does not change the business table, and date ends up empty.
- **A position is the address of a content block**: the content of an event is divided into content blocks, each addressed by "event `seq` + block path"; the path contains only fixed words, opaque IDs and indexes, and no user content (see "Integrity and provenance"). **Deletion works on blocks and removes a whole block**; there is no partial deletion inside a block.
- **The list of positions includes the impact-summary hash in the content area of this event itself** (the one `dc_` is bound to, computed from the deleted content and placed in the content area), and also the business-time blocks in premise declarations that are cleared along with the deleted evidence (`premise_valid`, see "Content derived from source data").
- **Each deletion lists all its positions on its own**: the position list of each deletion is independent of the other pending deletions and complete in itself. At expiry the blocks are deleted one by one, and a block that is no longer there is skipped; when one deletion is cancelled, only the blocks not listed by other pending or executed deletions are released.
- **Deleting during a migration**: while the new-version table is still being built ((c) kind, discardable), the deletion event gives only the result for the current version.
  - The new-version table under construction **discards the affected rows entirely and rebuilds them from the log** (the deleted content can no longer be read at that point). If the build has not finished when the physical erasure falls due, the history content of these rows in the table under construction is cleared too. A deterministic migration also has an in-migration phase, and this item is done in the first version.
  - Replaying from empty storage needs no special handling: the "deletion confirmed" and "cancelled" events are events in the log just like base writes, and at the switch event `apply` puts their field-by-field results into the new-version table through the same deterministic conversion; the deleted content is already "removed" in the log and is skipped during the conversion.
  - Extraction jobs (later): `jobs` **returns all** extraction work items of the affected rows (including translations already delivered but not yet switched) **to the pool to be redone** (carrying only the remaining original text). A translation cannot be replayed anyway, and the result is the same as "the deletion event gives the new-version result", with one less piece of logic.
- **The judgement result is the one given most recently**: the effect state and interval of a contribution, and the first-creation mark of a write, are given by the event of that write; if a later replay for a deletion confirmation or cancellation changes it, the new one is given by that deletion event. `undo`, "the interval of that write" in the conflict criterion, carried references and corroboration end points all read the latest.
- **What it looks like after the deletion is given by segment**: on a state table, a segment = the longest interval over which one contribution item gives values continuously. The segments listed are those whose value, or whose contribution that gives it, differs from before the deletion; the segments given by restated items; and the segments that intersect (the union of before and after the restatement) the intervals of the deleted or restated "exists" items and of restated `uncovered` write-back items. An entity that is listed is always given together with all its intervals without a value; segments are listed whole and are not trimmed to the part that changed, because a trimmed end point could be exactly the deleted content. For a segment given by constant filling, the constant itself records no dependency, and the interval of the segment comes from the filled segment, so it copies the dependencies recorded for that filled segment.
- **Deletion and cancellation events are applied by the provenance table and checked against the result**: restated items change only the provenance table (effect state, interval, carried reference, including "no value" and write-back items that are registration only); the rows touched are then applied according to the provenance table, by the same deterministic computation as applying a write, and what comes out must be exactly the result written in the event; if it does not match, stop (event format 5.9). A write-back item restated as "no value" that still has part exposed is already in the result, for that part, as a "segment given by a restated item", written with an empty value and no value source. Which items were reverted does not change because of a restatement; the registered range is recomputed from the interval of the restated write-back item.
- **`apply` only does as told, and does not replay or rerun row splitting**: the result in the event is what `delete` computed under the kernel version of the time according to the definition; a kernel upgrade may change computation details, and replaying an old log must not change results because of that. Under the same kernel version, the result in the event should equal the reference evaluator's recomputation at that place (a comparison test, architecture §11).
- **What it looks like after the deletion is a new version**; earlier versions are not rewritten, and the content in them that was derived from the removed contributions (the value of that field and the field-level provenance in each write event, the corresponding historical values in the version table) cannot be read during the grace period, is physically erased at expiry, and that place is marked "deleted".
  Reading as of a time before the deletion shows "the state of that time with the deleted content removed"; it is not recomputed by the definition and is not guaranteed to equal the online state of the time. A historical row with empty required fields may be read (by the definition the row did not exist at that time); it is returned as usual and marked `partially_deleted`; the same for retired tables.
- The values in the result after a deletion are themselves content and carry their own value sources; when these sources are deleted later, the same cascade applies (see the table below).

### Cancelling a deletion and the grace period

- **Writes during the grace period** are executed as usual on the state after the deletion; when one writes to an affected row / entity, the receipt `warnings` says "this row has a cancellable deletion (`pi_…`)". A write to a row / entity that has been deleted as a whole row reports `not_found`, with the text "this row has been deleted (`pi_…`, cancellable)" (the same for an entity), and echoes no content; it does not create anything and does not bring the row back. **"Deleted as a whole row" is judged by existence, looking only at sets**: on a write (including a revoke or `undo`), this row / entity does not exist in the replay under the current deleted set (all confirmed and uncancelled deletions, including those still in the grace period) (event table: the existence judgement in "Replay rules" does not hold; state table: no business instant has a value), and it exists in the replay under the current deleted set with all pending deletions removed. Then it reports `not_found`, with the IDs of **all** pending deletions that touched its contributions (taking its contributions in the latter replay: value sources, including those passed on through carried references, plus interval sources), sorted by operation number. Other cases follow the ordinary rules: when not a single contribution of it remains in the current replay (no item at all on its fields or on "exists"; a pending deletion is not the cause), it is as if it was never created in this log, a write by row / entity ID reports an ordinary `not_found`, and a write by `entity_key` creates the entity as usual; when any item remains, on an event table revoking the whole row still reports `revoked`, and on a state table the hole is filled as usual even if no instant has a value (for example only a revoke remains) ("High-impact writes" ① in "Time"). The criterion depends only on the deleted set and on which of its members are still pending, and not on the order of the deletions or on what was cancelled.
  Source data pending deletion can no longer be cited as evidence (`source_ref` reports `invalid_argument`).
- **During the grace period, no decision can be made on an affected row / entity** (first version).
  - **Affected**: if this row / entity differs in any item between the replay under the current deleted set and the replay under the current deleted set with **all** pending deletions removed (the value of a segment of a field, the item that gives it, the value source and interval source of the item, the judgement result of the item (in effect, corroboration, candidate, awaiting confirmation), whether the row exists), it is affected; what affects it is the pending deletions that touched its contributions (taken the same way as the pending deletions attached to "deleted as a whole row" in the previous item). A case where only operation sources were deleted (the evidence of a revoke, the remark at resolution) and the replay does not change does not count. The criterion depends only on the deleted set and on which of its members are still pending; "pending" lasts until the tombstone is applied, and the stretch where the grace period has passed but physical erasure has not yet happened still counts. The `pending_deletion` mark on rows that are read and the `pending_deletion_on_target` reminder on write receipts use the same set.
  - **What cannot be done**: resolving an item whose target is such a row / entity (the three ways of handling a conflict, confirming and rejecting an item awaiting confirmation, the two ways of handling a flagged item; what counts is the item's own target, and the other row that a `flagged` item matched does not count); an `undo` whose target is it. This reports `invalid_argument` (`pending_deletion_target`) with all the pending deletions that affect it (sorted by operation number) and the latest of their expiry instants; no event is produced, and if one op in a request is like this, the whole request does not take effect. After the deletion is executed at expiry or cancelled, the same request works as usual. When the row has been deleted as a whole row, the `not_found` of the previous item comes first: for the caller that row no longer exists.
  - **What works as usual**: ordinary writes (including revokes and reverts by version, and those that become candidates or awaiting confirmation as a result); the cancellation of a `deletion` item itself; confirming and rejecting a schema draft; any decision on rows that are not affected.
  - **Why**: a decision is a person's decision about what this row looks like at this moment. During the grace period that appearance is the one after the deletion, and after cancelling the row goes back to another appearance; what the decision lands on and where the candidates it closed are put back would each need a separate rule. The grace period is only 24 hours, and only the rows touched by the deleted source data are affected; to handle the items on these rows, wait for expiry or cancel the deletion first. `undo` belongs on the side of decisions: it reverts all the items of an operation in the replay, and which ones are reverted depends on the replay at that moment. (Decision record [`../../zh-CN/process/decisions/grace-period-no-decisions.md`](../../zh-CN/process/decisions/grace-period-no-decisions.md) (Chinese).)
- **External keys still hold their place during the grace period**: an external key that this deletion removed from a row still occupies the key index until physical erasure; an external-key op that hits it is skipped (`skipped`, `skip_reason: "pending_deletion"`, with the deletion ID, given only in the receipt) and does not add a new row. When a deletion removes the contribution of a key on any row (the row that holds it, or the original row before it was transferred), this key is **frozen**: it cannot be transferred, and syncs by it are all skipped. When the deletion is cancelled, it no longer freezes the key; the key is unfrozen only when no other unexecuted deletion freezes it, and the holder does not change; after execution at expiry the holder is determined again from the state after the deletion (see "Writing by external key"). There are two reasons: it follows the same convention as request keys (a request key pending deletion still takes part in duplicate checks before physical erasure); and cancelling must be able to restore: if a sync added a row during the grace period, then after cancelling the original row would come back with the same key, and one table would have two rows with the same key.
- **Resending during the grace period**: a request key already listed as pending deletion still takes part in duplicate checks before physical erasure (the idempotency window is no longer than the grace period: 24 hours for an explicit idempotency key and 10 minutes for a server-computed request key, both counted from the time of the write, while physical erasure is at the earliest 24 hours after the deletion is confirmed). When a client resends a write that has just been deleted, the receipt says "the original write has been deleted (`pi_…`) and was not written again", and it is not written again. When an explicit idempotency key hits a write already listed as pending deletion, it is likewise replayed as `original_deleted` and the content fingerprint is no longer compared (content pending deletion does not take part in comparison), and it does not report "same key, different content". A request key that has passed the idempotency window is not deleted proactively; it is deleted together with its evidence.
- **Cancelling a deletion**: `delete` computes again by the definition (a cancelled deletion no longer counts as deleted) and replays together with the new writes made during the grace period in order of `seq`; conflicts and high impact are recomputed on the replayed state according to principle ②. The result, the new `ver` and the restored items are all written into the cancellation event, and `apply` does as told.
  - **Writes that already took effect during the grace period stay in effect** (deviation 2 of the definition applies to cancelling as well). So after cancelling, the part not overwritten by writes made during the grace period is the same as if there had never been a deletion; the overwritten part follows the writes made during the grace period. The unit of protection is the same as in deviation 2: a write made during the grace period of which only part took effect when it was written is not protected, and on cancelling its items are judged by the replay.
  - Items superseded because of the deletion: when one deletion is cancelled, a candidate stays "superseded" (with the write as the reason) if and only if ① it is pending in the replay without this deletion (other pending deletions as before); and ② there is a write that, during the period in which the candidate was removed by pending deletions (at the moment of the write it is in no item, whether or not this deletion is the one that removed it), changed a field it involves according to the conflict criterion: whether it changed is by the result recorded when that write was judged, that is, it is an effective change there (not a corroboration, candidate or no-op) and differs from the candidate's value; each write is judged only once and does not vary with which deletions are still being executed at the time of cancelling. The rest are restored. A candidate that took effect at the moment of writing because of a deletion is judged by the previous item "stays in effect" and is not in this list. Judged this way, neither the order in which several deletions are cancelled nor which deletion a write falls after affects the result. A new item awaiting confirmation generated because of the deletion is superseded. **Staying "superseded" is lasting**: if the same sources are deleted again later, the candidate of this item remains closed and not in effect, symmetric with the lasting protection of "stays in effect". So "the result depends only on the deleted set" holds only when there were no writes during the grace period and cancelling left no kept-in-effect or kept-superseded cases.
  - Items from which a candidate was removed because of the deletion: if the item is still pending, the candidate is put back into the original item on cancelling; if the item is closed (superseded during the grace period: by an ordinary write per the previous item, or by another deletion or a schema switch), it is not put back, and the candidate closes together with it. It cannot have been resolved during the grace period, since its row is affected by this deletion; so each candidate is either in a pending item or closed together with a closed item, and cancelling needs no separate judgement for it.
  - A write that took effect because of the deletion goes back to its original state; if another write made during the grace period has changed things on the basis of its `ver`, it does not go back: the cancellation event records these writes as "kept in effect" (`kept_effective`, with which write used it as the baseline), and the receipt lists them. The unit recorded is all the items of this write on one target: it is recorded only if all items were in effect before the cancellation; one of which only part was in effect is not recorded and goes back as usual (otherwise the part that is still a candidate would take effect without a person's decision); the items listed in the event are only for the receipt, and their indexes do not take part in judgement. "Changed things on the basis of it" means: on the same row / entity, a write whose `ver` (explicit or obtained as a fallback) is no earlier than the operation from which **all items** of this write on this target have been in effect (the operation at which the most recent continuous run of "all items in effect" began before the cancellation: a write, a deletion confirmation or a cancellation; if items went back in between, count from the later one), and which has taken effect (taking effect at the time of the write, taking effect through a person's decision, or corroborating all count; one that is entirely no-op does not), regardless of field: what it saw was the row that contains this write. **The protection is lasting**: a write recorded as kept in effect counts as "has taken effect" from this cancellation on (deviation 2), and later deletions and cancellations no longer send it back.
  - The intervals resolved again because of the deletion and the first-creation marks are computed again on cancelling and recorded into the cancellation event.
  - The cancellation transaction in the tenant is committed first, and then the deletion register is updated (see "The deletion register").
- **Physical erasure at expiry (tombstone)** physically erases only content and does not change the current state: the current state was already determined at confirmation (and by writes after that).

### What the preview and the receipt must state

An evidence deletion and a privacy deletion are previewed first and confirmed afterwards. The preview **deletes nothing**; the shape of the receipt fields is given by `deletion_preview` and `delete` in section 10 of the contract; below is what the kernel must compute and what the preview and the receipt must state (the authoritative definition is here).

- **Totals**: how many pieces of source data are deleted, how many rows are affected, how many derived values are recomputed. A derived value computed at read time has no derived write, is not listed among the derived values in the preview and the receipt, and is not counted in this number; its value is computed at the next read from the data at that time.
- **The result per row / entity** (privacy deletion, per "Definition of the result of a deletion"): whole row deleted / kept with some fields empty / some fields returned to earlier values / re-segmented, together with the **grounds for the judgement**: for each required field, which contributions of which writes remain (example: "runs r_01JC… whole row deleted: date comes only from this sentence; s_R3 also mentions this run, but its write gave only distance"), so that the caller can first corroborate the missing field with other evidence (`source_ref` + `evidence_by_field`) and then delete.
  When a reverted value is removed together with the deleted source, state the value it falls back to and the reason ("11-10 to 11-19 (inclusive) returns to 5000 (the value of #101; #111 had reverted the 4500 of #109)"); when a field cites several pieces of evidence from the same write, state "the same write has another s_…, which can be used to corroborate by field before deleting".
  **Intervals that will go from having a value to having none** (`gaps_opened`, listed only for state tables; on event tables and timeless tables the deletion of a whole row is already expressed by the outcome): the intervals that go from having a value to having none after the deletion, and the reason. An interval is listed only once: when it falls inside a revoke the reason is `revocation_extended`, otherwise `required_field_removed`. The reason takes two values: `required_field_removed`, a required field has no contribution still present there; `revocation_extended`, a revoke given only a start point whose end point stopped at a stop point given by the deleted write is resolved again after the deletion and extends past it, and a write that falls into the extended part did not bring all required fields and cannot hold up that span (example: "amount and owner are both required; after deleting the sentence of 4000 from 11-20, the revoke from 11-05 extends to open-ended, and the 4500 from 11-20 gave only amount, so there will be no value from 11-20"). The latter is consistent with the definition (validation at the time of writing is not rerun, and what took effect stays in effect), but from "deleted a sentence about amount" it cannot be seen that the whole span will have no value, so it must be listed separately and the reason stated. They are computed at preview and receipt time and do not go into events.
- **Writes that were not in effect and will take effect because of the deletion** (listed separately, not mixed with the other results): candidates whose conflict causes were deleted, writes awaiting confirmation whose high-impact causes were deleted, candidates with a higher level after the deletion; each with the write, the value and the corresponding item (which will be marked "superseded"; if there is still a conflict that is only decided again, the item stays pending; when a candidate in the same item is still pending, the item stays pending and is refreshed).
- **Writes whose conflict disappears but which are still high-impact and will turn into awaiting confirmation** (listed separately): each with the write, the value, the segment that would be overwritten, the original conflict item (which will be marked "superseded") and the newly generated item awaiting confirmation. The initiator of the new item is the writer of the original write; it may be unattended, and the receipt reminds the current operator to deal with it.
- **Writes that will turn from awaiting confirmation into a conflict** (listed separately): its `ver` conflict appears only when recomputed on the state after the deletion (for example, another write after the version seen takes effect because of this deletion). Each with the write, the value, the original item awaiting confirmation (which will be marked "superseded") and the newly generated conflict item, one to one.
- **Writes that took effect only because of an earlier deletion and will return to pending this time** (listed separately): each with the write, the value and the kind after returning to pending (awaiting confirmation / conflict); for those of the same kind as the original item, the original item they return to (a superseded one is restored, which revokes its "superseded"; one still pending is merged back) and the successor item that is superseded as a result; for those of a different kind, the original item (which stays "superseded") and the successor item it is in: an existing successor item of the same kind (it stays there), or a newly opened one, one to one. The kind is compared with the original item, which is the item the write was in when it was written (see deviation 2 in "Definition of the result of a deletion").
- **The returned part of a write of which only part took effect when it was written** (listed separately): each with the write, the value and where it goes: the pending item it is merged into, or the decision or supersession that closed it. When the item is closed, this part of the value is no longer in effect without going through any pending item, so it must be listed.
- Items superseded because of the deletion; the (row, field) pairs whose translation results are cleared and for which re-extraction will be started, and those with no remaining original text that are set to empty directly (extraction jobs are later).
- **Deletion by row** (`rows`, later): when the sources of these rows do not intersect with those of other rows, there are no side effects; source data shared by other rows and impossible to split is listed separately as a warning, with the rows affected along with it (the whole privacy deletion).
- When deleting evidence (later) would leave a current field with no value source whose original text is still present, no preview is produced and the request is rejected directly, listing the referencing parties (see "Kinds of deletion").
- **Rows that still reference a deleted row** (listed separately): when a whole row that is deleted is still pointed to by the `ref` field of other rows, these referencing parties are listed. They are not changed, and when read later they carry the `dangling_ref` mark (the target has been deleted, see "The write request · Reference fields").
- **Rows that take a value that will be changed as a premise** (listed separately, the advance notice of `premise_affected`): when a deletion would change the value over the range a premise declaration declares, list the dependent rows, the fields involved and the write that declared it, up to 50 entries, with the total count given separately. They are not changed, and after the deletion they carry `premise_changed` (reason `deleted`, see "The premises of a write"). The reasoning is the same as the precedent of `ref`: the dependent row is still in the store and other Agents will still read it; whether it restates the deleted content, saveslot does not know, and leaves the decision to a person.
- **Source data that no longer supports any data after the deletion** (`orphaned_sources`, listed separately): IDs of source data that remain after this deletion but have gone from "supporting data" to "supporting nothing". A piece of source data **supports data** when it is the value source of some value in effect or corroboration in the current state, or the value source of some pending candidate or proposed value; being only an operation source (the evidence of a revoke, a resolve request and its `note`) does not count, and supporting only historical versions that have been covered does not count either. Only those for which this deletion causes the transition are listed: those that supported nothing before the deletion are not listed, and the deleted source data itself is not listed. Example: after the user's own words are deleted, the Agent's paraphrase attached to the same write and the later sentence of correction remain as source data, and the row they supported has been deleted as a whole row. The caller decides from this whether to delete them too; saveslot does not delete them automatically.
- **External keys** (see "Writing by external key"): when affected rows have external keys, the reminder `external_key_resync` is given: "These rows come from an external system; if a connector syncs the same record again after the deletion, it will appear again. To forget it completely, delete it in the source system first, or make the connector stop syncing it." After physical erasure saveslot does not remember the deleted key (see "After deletion"), so this must be stated truthfully. In the per-row results, a row that remains through other contributions while the contribution of the key was deleted is marked `external_key_removed`, stating "this row will lose its external key" (the next sync will add another row). A row all of whose sources are deleted and which has an external key gets an explanation of the `external_key_resync` kind as well, making clear that later syncs will not restore the records that were skipped at that time; skipped ops do not go into the log and are not listed one by one. **How to state freezing**: one deletion may freeze several keys; the preview and the receipt list, one by one, the affected rows whose keys will be frozen (listing row IDs, not key values), and state that during the freeze these keys cannot be transferred and syncs by them are all skipped; when the same key is also frozen by another unexecuted deletion, state that after this one is cancelled it is still frozen, and that it waits for which deletion (with the deletion ID) to be cancelled or executed.
- **State truthfully what will not be deleted**: external files, which are not kept by saveslot and must be deleted by the user; enum values and descriptions in the schema; the name of a connection (a name the user gave, not derived from source data); the self-reported task identifier and explicit idempotency key of operations that have no source data at all (submitting a schema draft, confirming a deletion, cancelling a deletion, a resolve with neither evidence nor remark); the metadata kept after deletion (see "After deletion").
- **When the preview expires**: when, between the preview and the confirmation, a new write, resolve or deletion changes any row / entity, item or source data the preview listed, the confirmation handle is void (`preview_outdated`, with the new preview). Writes elsewhere alone do not void it.
- Local service states: "if the saveslot service is not running at expiry, the physical erasure is executed at the next start".
- **The receipt after confirmation** gives the preview content recomputed on the state at confirmation (all the items above; the list limits and totals are the same as in the preview), and additionally: the deletion ID (that is, the ID of the `deletion` item in the grace period; the two are the same object), the expiry instant and how to cancel; the new `ver` of the affected rows / entities; the mark changes (`premise_affected`) on dependent rows that take a changed value as a premise; for each place, the state and time (logical deletion → time of physical erasure → date the backup expires, with snapshots and cold archives counted as backups), and it does not claim "deleted from all backups"; a local deletion acts only on the current saveslot data directory, and old copies in system-level backups are not managed by saveslot.
- **Remind once more when the deletion closes at expiry**: when physical erasure falls due and the `deletion` item closes, if the affected rows have external keys, the closing explanation carries `external_key_resync` once more. The first sync after that will write the same record back, and by then there will be no prompt at all.
- The receipt for **cancelling** (`cancel` of a `deletion` item) gives the result computed again by the definition: the new `ver` of the affected rows / entities, the writes sent back to the original state, the restored items and the items kept "superseded" (with which write changed them), and the mark changes (`premise_affected`) on dependent rows. The candidates removed by this deletion were all put back into their original items when those were still pending (listed among the restored items), so there is nothing to judge again.
  It also lists separately the **writes whose judgement changes because of being kept in effect**: the other writes whose judgement was changed along with a write recorded as kept in effect, each with the write, the new judgement (in effect / turns into awaiting confirmation / becomes a candidate) and the reason (which write that was kept in effect). This separate list is computed by the receipt at the time and does not go into events; in the event they are restated contributions.

### Content derived from source data

**All content derived from source data records its provenance and is within the cascade.** Besides base data and derived caches, there is:

| The hash of the confirmed content in the confirmation record of a resolve event | The same as the item content confirmed | Cleared together when the confirmed content is cleared |
| The results and restatements written in deletion / cancellation events | The value source of every value in the result, plus the contribution that cut out this segment (for a segment given by constant filling, copy the dependencies recorded for that filled segment); a restatement is the same as the contribution it points to, plus the contributions it depends on | Cleared when any of them is removed or restated, and given again by a later deletion event |
| The impact-summary hash in the "deletion confirmed" event | The deleted content | Listed in the expiry position list of this event itself: physically erased at expiry; during the grace period an export likewise replaces it with a placeholder |
| The group-key value of a derived row (the "group-key value → `partition_id`" mapping) | The base field versions that fell into this group (as long as any row still carries this key value, the mapping stays) | Cleared when the group becomes empty because of a deletion. When the same group key gets a row again during the grace period: the original `partition_id` is reused, and the next derived write **registers the mapping again** in its own content; at expiry only the old content is deleted and the mapping is not lost; on cancelling it naturally falls back on the same `partition_id` |
| The result checksum of a derived write | The base versions in the read set | Cleared when a contribution in the read set is removed; later, when this derived value is restored as of a time, the check is skipped and `partially_deleted` is marked |
| The request content of a large-write job (job accepted event) | The evidence of the request | The same as base writes |
| Physical tables of retired versions | The same as the rows of the current version | The rows in the physical table of each version are handled by the same result |
| The profile and value samples of the catalog | Computed from the data currently visible | Recomputed on deletion |

### After deletion

- **Version table**: the interval of the version in which the deleted content sat is kept, and the content there is marked "deleted"; when reading this span as of a time, the receipt notes "part of the data at that time has been deleted" (`partially_deleted`). Which cells hold deleted content: each cell's value is given by one block — the `restated/<k>` on the latest deletion or cancellation event restating that item up to the cell's recording operation (a restatement keeps the item's `k`), or, when the item was never restated, its own `fields/<field>/<k>` on the write's event. A cell holds deleted content when the block giving its value is listed by a deletion **confirmed after the cell was recorded and still pending** (a cancelled one lists nothing). How it is told once the deletion is carried out is not settled in this version: execution clears the listed blocks, and a cleared restatement can no longer be told by the item it restates (this version does not apply a deletion's execution, so the state is not reached): see [`../08-open-questions.md`](../08-open-questions.md). So a cell the deletion recorded by its own restatement does not (its value is the deletion's), unless a later deletion lists that restatement in turn; after a cancellation it is listed no more and is readable again. A value may also have been corroborated, and only one block giving it is counted here, so this version withholds a corroborated value more than it should (on the safe side): see [`../08-open-questions.md`](../08-open-questions.md). Reads by instant (`history`'s `as_of`, a later page of `query`) do not give such a value and mark the row `partially_deleted`; on a state table that stretch still appears (it counts as having a value when deciding whether the stretch has one), only without this value; under `detail: "detailed"` a referenced row's summary leaves it out too, and the referring row is marked `partially_deleted`; a conflict item's `previous` (the merge base) in its details leaves it out too, and `previous` is marked `partially_deleted`: `previous` is the merge base as recorded then less the deleted content, not the state after the replay, while `take_previous` writes back the state at that place in the replay, so a marked `previous` may differ from the value actually written back; `history`'s `changes` does not give the side that came from it and marks the entry `partially_deleted`; in `timeline` an operation's `before` is not given when it came from such a cell. Interval ends that came from a deleted change point, locating by `entity_key`, and a value another contribution corroborated: see [`../08-open-questions.md`](../08-open-questions.md).
  Of the new derived writes produced by the derivation recomputed in the deletion cascade, the only parts outside the scope of deletion are the rule version and `partition_id`; group-key values and result checksums are deletable content, and no text describing the deleted content is included.
- **Tasks already completed that read the deleted data: no retroactive action, no notification.** The output has long left saveslot and cannot be recalled; the read record keeps only versions to begin with,
  and after the deletion it naturally shows "read a deleted version", with no extra mark needed. A deletion made for privacy must not generate a new record that describes the deleted content.
  Deletion confirmation and cancellation also run the check "remove the mark once the value is restored" (see "Querying the reads a correction affects"): if the value that a read saw at that time holds again because of a deletion, its `possibly_affected` is removed; **it only removes and never adds**.
- **"Only removes and never adds" applies only to `possibly_affected`; a changed premise (`premise_changed`) is added.** A dependent row differs from a completed task: it is still in saveslot, and other Agents will still read it and use it as an ordinary row; the precedent is that when the target of a `ref` is deleted the referencing party carries `dangling_ref`. The rules (criteria and detection are in "The premises of a write"):
  - **Compare the values before and after the deletion, without looking at the supplier**: if the deletion changes the value over the declared range (the whole row disappears, a field becomes empty, it returns to an earlier different value, the value differs on some segment), the dependent row carries the mark with the reason `deleted`; if the deletion only changes the contribution that gives this value and the value does not change, it is not marked. Marking does not require reading the version seen: the value before the deletion is still in storage at that point.
  - **Remove only when comparable**: when a deletion makes the value return to the value seen, the mark is removed, on the condition that the value at the version seen can still be read; when that itself has been deleted (pending deletion or physically erased), comparison is impossible and the mark stays. A deleted value is not used for comparison.
  - **After a deletion, `since` and `reason` point to the deletion**: for a declaration that has already changed, if this deletion changed the value over its range, or removed the contribution on this range of the change that `since` points to, and the value still differs from the one seen, `since` becomes the operation number of this deletion and `reason` becomes `deleted`. Otherwise a reader following the mark would find an operation that did nothing after the deletion.
  - **Judge again when the range of a declaration is changed into the whole timeline by this deletion**: for a declaration whose business time taken from the dependent row is cleared by this deletion (listed in the position list), the range is treated as the whole timeline from the confirmation of this deletion, and it is judged once more on the whole timeline in this detection: if it is still "unchanged" but the value on the whole timeline already differs from the version seen, or the content of that cell of the version seen has been deleted or is pending deletion (comparison impossible), it turns to "changed", with `since` being the operation number of this deletion and the reason `deleted`. When this deletion is cancelled, the range is restored and judged once more in the same way (it may turn back to "unchanged").
  - When a deletion is cancelled, judge once more on the state after the cancellation. The mark holds only the target row ID, the field, the version number seen and the operation number of the deletion, all of which are metadata that remain after a deletion anyway and contain no value, so they do not make up a new record describing the deleted content.
- **Deletion in the first version = physical erasure** (no application-layer encryption, see below): the deleted content is physically erased together with its checksum, the affected business rows and the historical versions; the event header and the tombstone stay on the chain, and the chain can still be verified.
  The tombstone event lists only the opaque positions of the deleted content and the reason code, **with no text describing the deleted content and no value computed from it**; the event header uses only opaque IDs, and readable names go into the content.
- **Metadata kept after deletion** (the deletion receipt states this truthfully):
  - The event header (on the chain, never deleted or modified) shows: at some moment an event of some type occurred, which principal did it, which slot it belongs to, and which events belong to the same operation.
  - The metadata blocks not on the chain show: which row of which table (`row_id` is a UUIDv7 and carries its creation time to the millisecond), the intent of each write, which events it references; a tombstone says "the content at which positions was removed at some time on a deletion request". The positions carry field IDs, so it can be seen that "field number so-and-so was changed", but not the field name or the value.
  - Premises of a write: a write declared that it took the value of some field number of some row of some table at some version as a premise, a write cleared a premise, and in which operation a declaration changed state. The values of the premise, the values of the dependent row and the business time of the declaration cannot be seen.
  - For the itemized list and "how to remove it if retention is not wanted", see "What the event header leaves behind" in [`../09-event-format.md`](../09-event-format.md). The name of a connection is not cleared by a privacy deletion.
- **A deletion must reach all replicas and must not come back**: a tombstone is a log event that **never expires** and is replicated in full to all nodes (not limited by the range of partial replication); a replica applies the tombstone first and accepts content afterwards, and when an offline node comes back online with old data, the primary node blocks it at the entrance according to the tombstone.
  **Blocking is possible only by event identity**: tombstones and the deletion register store no value computed from content, and the same content written again in a different event cannot be recognized by content; this is the price of "not comparable after deletion".
  **The same holds for external keys**: a key value is a field value and may itself be user content (some source systems use an email address or phone number as the identifier); after physical erasure saveslot does not remember this key and keeps no hash of it. When the same external record is synced in again, it appears again as a new row; the preview, the receipt and the closing at expiry each remind once (see "What the preview and the receipt must state"). When only the source data of one sync was deleted and the row is still there, the contribution of that sync is removed and the field goes back to an earlier value; if the next sync delivers the value that was deleted, it differs from the baseline value and takes effect again: it is the same thing, because in the source system it is still there.
- **Plaintext residue list**: every one of the following places must be handled on deletion.

  | Where | What is there |
  |---|---|
  | The content area of the log | Evidence fragments in write requests, the request content fingerprints of request keys and explicit idempotency keys, translation results, item content, the content hashes in confirmation records and deletion confirmations, the results in deletion / cancellation events, the group-key values and result checksums of derived rows |
  | Materialized state | Physical tables of every version (including retired tables), the historical values in version tables, the profile and value samples of the catalog, the full-text index, embeddings, the external-key index (`external_keys`), the business time in premise declarations (`premise_decls`) |
  | Inside the database | WAL / free pages; statistics (the frequent values and histograms of `pg_statistic`): `purgeResidue` rewrites the affected tables, rewrites `pg_statistic` after `ANALYZE`, and rolls the log segment, the same approach on both backends (architecture §7 "How residue is cleaned up"); `pg_stat_statements` and the slow-query log (which does not record the literals of restricted SQL) |
  | Temporary data at run time | Work items of extraction jobs (assembled from the log at claim time and not written to disk), the baseline of statistical anomalies (if cached), application logs and error reports, the model-call cache, the temporary storage of the replay comparison (`log.reconcile`) (destroyed after use; what a crash leaves behind is cleared when the tenant is opened) |
  | Copies treated as backups (see below) | `snapshot()` snapshots, snapshots before a format upgrade, cold tenant archives |

  **The schema document itself** (enum values, constants in `migrate`, descriptions written by the Agent) may contain the user's original words and is **not in the cascade**; the deletion preview states truthfully that "enum values / descriptions in the schema will not be deleted".
- **Backups**: the first version does no application-layer encryption, and data in backups (including snapshots and cold archives) can disappear only after the retention period has passed; the deletion receipt states the status truthfully
  (logical deletion → physical erasure → date the backup expires), and does not claim "deleted from all backups". When a cold tenant archive becomes void after the tenant is restored into the cluster is undecided (open questions, to be decided at the cloud service capacity stage).
- **Restoring a backup does not bring deletions back** relies on the deletion register outside the log, see the next section.

### The deletion register: restoring a backup does not bring deletions back

A tombstone in the log guarantees that "export and replay" does not bring data back; when a backup from **before the deletion** is restored, that log contains no such deletion at all. So a **deletion register** is kept separately outside the log, in the anchor storage that is separate from the tenant storage (server mode: the control database; local mode: the saveslot configuration directory; for the interface see architecture §5, §8), and it is merged with the cloud service's deletion expiry index into one.

- Each entry stores only the tenant, the deletion ID and kind, the state, the expiry instant, the `seq` of the confirmation event, and the opaque positions of the deleted source data and deleted content blocks, **and no content**. The anchor storage also records, for each tenant, the high-water mark of allocated `seq`, the restore count, the "restore in progress" mark and the "import in progress" mark.
- There are four states:

  | State | Meaning |
  |---|---|
  | `intent` | The register has been written, but it is not yet known whether the deletion transaction in the tenant was committed |
  | `pending` | Confirmed, waiting for execution |
  | `cancelled` | Cancelled |
  | `executed` | Physically erased |

**General rule: the register never deletes less than the committed log.** Deleting less is a privacy incident and is invisible, while deleting more is visible and cancellable during the grace period; so every crash is made to fall on the side of deleting more, and reconciliation then takes it back. This fixes the order of the three actions:

| Action | Written first | Written after | State after a crash in between |
|---|---|---|---|
| Confirm deletion | The register (`intent`) | The tenant transaction (the "deletion confirmed" event); after a successful commit the register is changed to `pending` | The register has it, the log does not: the register deletes one step more |
| Cancel | The tenant transaction (the "cancelled" event) | The register is changed to `cancelled` | The log has been cancelled, the register is still `pending`: the register deletes one step more |
| Physical erasure at expiry | The tenant transaction (the tombstone) | The register is changed to `executed` | The log has been executed, the register is still `pending`: both mean "to be deleted", no difference |

**On a normal open the log is authoritative and corrects the register.** When: every time a tenant is opened, before every expiry scan, before every deletion-related operation.

| Register | This deletion in the log | Action |
|---|---|---|
| `intent` | Confirmed, pending execution | Change the register to `pending` |
| `intent` | None | Remove the register entry (the transaction was never committed, and this deletion does not exist) |
| `intent` / `pending` | Cancelled | Change the register to `cancelled` |
| `intent` / `pending` | Has a tombstone | Change the register to `executed` |
| `pending` | Confirmed, pending execution | Nothing to do |
| `cancelled` | Cancelled | Nothing to do |
| `executed` | Has a tombstone | Nothing to do |
| No register entry | Confirmed, pending execution | Add a register entry `pending` (the anchor storage was lost or is new) |
| No register entry | Cancelled | Add a register entry `cancelled`. If it is not added, then when a backup from before the cancellation is restored later, it would be filled in as `pending` by "no register entry × pending execution", and a deletion the user had cancelled would be executed |
| No register entry | Has a tombstone | Add a register entry `executed` |
| No register entry | None | Nothing to do |
| `pending` | None | **Impossible combination**: the log has been reverted, go to the restore procedure |
| `cancelled` | Pending execution, has a tombstone, none | Same as above |
| `executed` | Pending execution, cancelled, none | Same as above |

The table above is all the combinations of the five cases of the register (four states plus "no register entry") with the four cases of the log (none, pending execution, cancelled, has a tombstone). The last three rows do not occur in normal operation (the register is only ever one step ahead of the log). If they occur, the tenant storage has been replaced by an old one without going through the restore procedure. The order of the checks when a tenant is opened: import-in-progress mark → restore-in-progress mark → whether the log end is below the high-water mark → reconciliation by this table → run overdue expiry tasks again (for re-entry of an import see architecture §8); the high-water mark check comes first, so "`intent` × none" is not mistaken for "the transaction was never committed" when the log has been reverted.

**In the restore procedure the register is authoritative and fills in the log.** After restoring any backup, `snapshot()` snapshot, snapshot before a format upgrade or cold tenant archive, first re-apply deletions according to the register, and only then serve the outside (for the steps and re-entry of the procedure see architecture §8):

| Register | In the restored log | Action |
|---|---|---|
| `executed` | Has "deletion confirmed", no tombstone | Add the tombstone directly as `system` (reason code `restore_backfill`), without recomputing |
| `executed` | Not even "deletion confirmed" | Recompute by the definition and physically erase directly, with no grace period |
| `executed` | Has a tombstone | Nothing to do |
| `pending` | Has "deletion confirmed", pending execution | Execute at the original expiry instant; if it has passed, execute at once |
| `pending` | None | Regenerate "deletion confirmed" as `system` (recomputed by the definition), keep the expiry instant in the register, and execute at once if it has passed |
| `pending` | Cancelled | Change the register to `cancelled` (the register is one step behind, the log is authoritative) |
| `pending` | Has a tombstone | Change the register to `executed` (same as above) |
| `intent` | Has "deletion confirmed", pending execution | Change the register to `pending`, with the expiry instant as in the register |
| `intent` | None | **First write the new expiry instant (24 hours from now) into the register**, then regenerate "deletion confirmed" as `system`, with the item reason code `restored_unconfirmed` |
| `intent` | Cancelled, has a tombstone | The register is behind; the log is authoritative: change to `cancelled` / `executed` |
| `cancelled` | Has "deletion confirmed", pending execution | Append a "cancelled" event as `system` (recomputed by the definition), with reason code `restore_cancel`: what the user cancelled is kept |
| `cancelled` | Cancelled | Nothing to do |
| `cancelled` | None | Ignore |
| `cancelled` | Has a tombstone | Does not occur: a tombstone is appended only when the register is `pending`. If it occurs, report an error and stop, and do not serve the outside |
| No register entry | Any | Handle by the table for a normal open |

- **The expiry instant is the one recorded in the register.** When "deletion confirmed" is regenerated, the register is changed first and then the event is committed, so after a crash after this step and coming in again, what is seen is "`intent` × pending execution", and the expiry instant is still the newly written one, and does not go back to the old value.
- **An event regenerated on re-entry is the same as the first time.** The result and the restatements in "deletion confirmed" are a function of "the log + the set of deleted source data" and depend on no state outside the log; when the restore procedure is re-entered and the same register entry is computed again, the result, the restatements and the position list are the same as the first time. What has been appended is not appended again (by the comparison table, what is seen on re-entry is "confirmed, pending execution").
- **The deleted source data itself is not in the restored log** (the backup is earlier than the moment that sentence was recorded): there is nothing to delete, no event is generated, and the register entry is only marked `executed`.

- After re-applying deletions, check that the positions in the register have all been cleared.
- **Residual cases stated explicitly**:
  - When `intent` is in the register and not in the log and it has entered the restore procedure, saveslot cannot tell "the transaction was not committed" from "it was committed but the log was reverted". It is handled as the latter (regenerate), and covered by a new grace period and a visible item: this may make a deletion appear that gave the user an error, but it can be seen and cancelled; handling it the other way would bring back a deletion for which the user had received a success receipt.
  - A crash after the cancellation tenant transaction was committed and before the register was changed to `cancelled`, followed by a restore to a backup from before the cancellation: the register is `pending`, the deletion is pending in the log and is executed as usual, and the user's cancellation is lost. This is the same kind of loss as "any write after the backup is lost with the restore", and the direction is deleting more.

**Other rules at restore**

- When re-applying a "delete evidence" (later) and, in the restored state, it is blocked by a citation (the corroboration was lost with the restore), **delete anyway and do not block**, and state "the other sources were lost with the restore" in the receipt and the audit: not deleting would bring back the original text the user deleted.
- **`seq` is not reused after a restore**: before re-applying deletions, first append a "restore" event (referencing the position restored to and the `seq` high-water mark), and later `seq` continues after "the larger of the log end and the high-water mark"; `verify` accepts gaps explained by a "restore" event.
- **Restore count**: the high-water mark advances periodically (for when it advances see architecture §8), so a `seq` allocated between two advances may still be used again; therefore a restore count is kept separately (plus 1 on each restore, written into the "restore" event; plus 1 on each import as well, written into the import event; the initial value is 0). The current restore count is taken from the most recent restore or import event. `ver`, the item version, `dc_` and paging handles all carry it (the item ID `pi_` is a stable ID, and binding to content relies on the item version, see "Pending items"), and any obtained before a restore or import fails to match:
  - the item version reports `confirmation_mismatch`;
  - `ver`: one whose restore count is **exactly 1 less than the current one** and whose operation number does not exceed the **restore point** is judged for conflicts by its own operation number; the others (an operation number after the restore point, or an older restore count) take the restore point as the position they read, and are compared by the conflict criterion with the writes after the restore point. The restore point is the position given by the event that made the current restore count take effect: for a restore, `restored_to` of the "restore" event; for an import, `imported_upto` of the import event. The reason: events up to and including the restore point are byte-for-byte identical in the two timelines, so judging by the original operation number cannot go wrong, and it can also find concurrent changes after it and before the restore point (moving everything to the restore point would treat these changes as already seen and silently merge them); the stretch after the restore point may have been lost, and the same operation number may point to another write, so it can only be handled conservatively. When the restore counts differ by 2 or more, there is no way to tell whether the timeline before the restore in between is consistent with the present, so it is not relaxed. The `ver` carried in the premises of a write is converted by this item in the same way;
  - handles are treated as expired.
- **Import into an empty tenant** (for the import itself see architecture §8 "Format versions, export, import and restore"; the target must be an empty tenant: the log has only the genesis event, and the anchor has no deletion register, restore record or in-progress mark):
  - **The register is rebuilt from the imported log**: the anchor storage of the source is not exported with the tenant, and the import does not verify it. After the swap-in, in one write, the deletion register (derived from the deletions still pending in the log), the high-water mark (the log end) and the restore count (the value in the import event) are written, and the "import in progress" mark is cleared.
  - **Placeholders for content pending deletion in the export** (the default of an export): the content is not in the file, and for every such deletion the import **immediately adds a tombstone** (`system`, `trigger: "import"`, reason code `import_placeholder`), placed after the import event. These deletions cannot be cancelled at the target, since the content was never brought over; the corresponding `deletion` item closes by expiry. This is the second way, besides physical erasure at expiry, in which a tombstone is produced. For an export that explicitly includes the content pending deletion, the deletion is still pending at the target: the expiry instant is as recorded in the event, one that has already expired is run after the swap-in and before serving the outside, and one not yet expired can still be cancelled.
  - **The source's deletion register cannot be brought over**: a deletion confirmed at the source after the export is unknown to this export file, and that content is still there after the import. This is not caused by the import (the export file was a copy that saveslot cannot delete from to begin with), but the import makes it online data again, so before the import the export time is shown, with the reminder "deletions made at the origin after this export are not in it".
  - After the import, the `ver`, item versions and handles from before the import are handled by the "restore count" item above; `dc_` and `cur_` additionally become invalid because the signing key and the tenant ID differ.
- **The local boundary**: a local deletion acts only on the current saveslot data directory; old copies in system-level backups (Time Machine and the like) are not managed by saveslot, and restoring from such a backup is restoring to the data of that time.
  The deletion can be re-applied only when just the data directory is restored and the register in the saveslot configuration directory is still there; when both are restored together, the register goes back to that time as well, and saveslot can neither re-apply it nor detect it.

### Encryption, legal matters and rebuilding

- **Application-layer encryption is not mandatory in the first version**: it is reserved in the structure: content is already stored separately from the event header (see "Integrity and provenance"), content references carry a nullable `key_id`,
  and the checksum can be changed to be computed over the ciphertext. When encryption is done in the future: only the original text of source data and the full before-and-after rows of change_log are encrypted, **while the business tables, derived tables and version tables stay in plaintext**
  (SQL queries need them), the key hierarchy is root key → slot key → per-item key, and deletion = physical erasure + destroying the key (a fallback for backups and offline copies).
- **Encryption at rest of the managed service does not change how deletion is done**: the storage volumes, backups and cold archives of the managed service are encrypted at the infrastructure layer, with the keys kept by the cloud platform; it protects against the storage medium being read after it is taken away, and does not protect against the operator. A privacy deletion is still physical erasure of the content plus residue cleaning, and does not rely on destroying keys; old data in backups still disappears only after the retention period has passed.
- The legal position (whether physical erasure satisfies the right to be forgotten, and how to communicate the backup retention period) needs confirmation by legal counsel.
- Rebuilding relies on replaying the extraction results recorded in the log, and only the parts that referenced deleted source data need to be extracted again (see "Where the model lives").

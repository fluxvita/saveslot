## Schema version evolution

**There is no ready-made overall scheme, but every piece has an established practice; the only thing really new in saveslot is the migration that "re-extracts with a model".**

### Established practices borrowed

| Practice | Origin | Use in saveslot |
|---|---|---|
| Versioned migrations / declarative diff | Flyway, Liquibase, Alembic; Atlas and Prisma generate a migration plan from the target schema | Each schema version is immutable; a migration is one log event |
| Stable field IDs | Protobuf field numbers, Apache Iceberg column IDs | Fields are identified by ID, and the name is only a label; an ID that was deleted is not reused |
| Compatibility levels | Confluent Schema Registry (BACKWARD / FORWARD / FULL) | An official schema declares its compatibility; a user schema is checked automatically by saveslot |
| Background build, atomic switch | A common pattern of zero-downtime migration; the online change tools gh-ost (MySQL: build a shadow table, follow the binlog, switch) and pgroll (PostgreSQL) | The new version is built from the log in the background and, once caught up, switched in one transaction; reads never stop |
| Transform on read | Upcasting in event sourcing | Source data and the log are never rewritten; they are transformed on demand |
| Preview first, then execute | Like `terraform plan` | Puts the "confirm" of "draft → confirm → publish" into practice |

### Kinds of change and means of migration

Changes fall into three categories, each costlier than the one before; in design, aim to land in the first two:

| Category | How the data changes | Needs a model | Examples |
|---|---|---|---|
| Metadata only | Existing values do not change | No | Add an optional field, rename, drop a field |
| Deterministic transformation | A deterministic function computes the new value from the old one; the function is recorded in the event together with the compiled definition, **not the row-by-row results**, and is evaluated again on replay (see below) | No | Kilometers → miles; text "good / average / poor" → enum |
| Re-extraction (not in the first version) | Go back to the original text of the source data and derive the new value again; old and new coexist, and the switch happens after confirmation | Yes | Split "notes" into "mood" + "weather" |

**Which category each change falls into** is judged by saveslot, and the result is deterministic. The table below lists every kind of change to every key of the schema document. "Change code" is a value of `changes[].change` in the compile receipt and in the compile result event, and "Category" is a value of `changes[].class`: create `create`, metadata only `metadata`, deterministic transformation `deterministic`, re-extraction `reextract` (the same names on both sides). Creating a slot and adding a table do not belong to the three categories above and are listed separately as "Create". The category says how existing values change; it **does not decide whether a new physical table is built**: that depends on whether the physical shape changes (see below). The "Automatic" column says whether the change takes effect without confirmation under the default slot policy (the name in the policy is in parentheses, see "What a slot contains"); the "Old writes" column says whether a write that carries an old `sv` and writes to this field is still accepted. **The "Category" and "Old writes" columns describe the case of a table that has been written to**: when a change takes effect through `restructure_unused` (a table that was never written and that nobody is using), `changes[].class` is always recorded as `metadata` and `migrate` need not be given; afterwards any write to this table that carries an old `sv` is rejected (see below). `class` records what this switch actually did: this table has no existing values and no transformation.

- **A draft takes effect automatically if and only if each of its changes is in the "Automatic" set**; otherwise the whole draft goes to awaiting confirmation. **Whether the same change code is automatic can depend on the table it is on**: the rows whose "Automatic" column says `restructure_unused` are automatic on a table that was never written and that nobody is using, and on any other table follow the second half of that column. When the same draft contains another change that needs confirmation (for example it also changes another table that has been written to), the whole draft goes to awaiting confirmation.
- **"Nobody is using it"** (`rename_unused`, `restructure_unused`): in the last 30 days no connection **other than the submitter's** has read or written this table or this field. The interface reads and writes by name, so "has read or written" means "has used by name"; a rename or a restructuring that only the submitter is using needs no confirmation. When others are using it, `impact.consumers` of the preview lists them.
- **Never written** (`never_written`): a base table was never written if and only if the log has no `write.base` event that targets this table (by table ID). The criterion looks at the log only and can be recomputed on replay; the implementation looks at the index column built by table ID in the event table and does not scan the whole table.

  | Situation | Counts as never written | Reason |
  |---|---|---|
  | Not written even once since it was created | Counts | — |
  | Written, and all rows have been revoked | **Does not count** | A revoke is a write; the rows and their history are still there, and reads at a moment, `timeline` and `undo` all need them; after a restructuring this history would have nowhere to go |
  | Written, and all content has been privacy-deleted and the physical erasure has also been carried out | **Does not count** | The event headers and tombstones stay in the log; on replay up to the switch these writes still have to be processed |
  | Written, but the write did not take effect (it became a candidate, or is awaiting confirmation) | **Does not count** | A candidate write and an awaiting-confirmation write are likewise `write.base` events and must be converted together in the migration; the items that point to them are still there |
  | Only read (an empty result was read) | Counts | The read record is not in the log, so there is nothing to migrate; but it makes this table "used by someone", and a restructuring needs confirmation |

- **An empty slot** (one that the contract's `slots.remove` can remove) is the same kind of criterion at the level of the slot, with a wider scope: under the slot's name there is no event other than structure (`schema.*`) and policy (`slot.policy_set`). Source data, any write (including one that did not take effect or was rejected in full), items (except a structure-change item, which also prevents removal while it is open), deletions and premise changes all count as records, and so does any event type added later. So a slot in which every table is "never written" is not necessarily an empty slot (for example when there is only source data, or only revoked writes). For the classification of each event type see [`../../zh-CN/process/decisions/remove-empty-slot.md`](../../zh-CN/process/decisions/remove-empty-slot.md) (Chinese).
  | Depended on by a derivation rule or by a `ref` of another table | Counts | The dependent side is handled by the rules below |
  | Went through other schema changes (a field was added, a rename was made) | Counts | There was no write, and none of the earlier switches filled in a value |

  "No currently unrevoked rows" is not used: such a table still has history and events, and restructuring it would have to answer "what is a revoked row of an event table in a state table". Nor is the criterion applied per field ("this field was never written"): that would need one more definition (does an explicit `null`, or a constant filled in by a switch, count), and when the table has data, dropping a field and adding another costs little. The price is that a table into which one piece of test data was written can only be dropped and rebuilt; the compile receipt and the documentation state this.
- **Restructuring a table that was never written**: there is no value to lose and no value to convert, `destructive` is `false`, `class` is recorded as `metadata`, and `migrate` need not be given; the table ID and field IDs do not change. The definition after the change is validated by the rules for a newly created table: changing to an event table requires `time.field`; changing to a state table can no longer carry `duplicate_keys` or `external_key`; `entity_key` can appear only on a state table, and its key fields must be required; `external_key` can appear only on event tables and timeless tables, and the types of its key fields follow the restrictions on external keys; after `base` changes to `derived`, the types and units of the fields are inferred by the compiler from the rule instead. **Adding a required field and changing optional to required must still give a constant-form `backfill`**: this does not depend on whether the table has ever been written, nor on whether the change takes effect automatically or needs confirmation; it is always required. This way the compile result of the same draft does not vary with the state of the table at that moment or with the path taken; all that is required is a constant, which costs little (see "How deterministic conversions are replayed" below).
  - `derived` to `base` is still not supported: whether a derived table "has data" cannot be judged from the log alone (a rule that depends on "today" is computed at read time and never produces derived writes, but the caller has already read values); a derived table has no data of its own to lose, and dropping and rebuilding it loses nothing.
  - **Dependent side**: in the first version, when the change reaches a field that a derivation rule reads (changing the type, changing the dimension, changing the unit, changing the precision), the whole draft reports `not_in_this_version` (`reason`: `not_implemented`, `param` points to that key), see [07-scope-v1](../07-scope-v1.md); dropping a field that is read still reports `still_referenced` as before. What follows is the complete design. The derivation rules that depend on this table are compiled again by the new definition in the same compilation; if the compilation fails, the whole draft reports `validation_failed` (`rule_sql_rejected`, `path` points to that rule), and it is enough to change it in the same draft. When the compilation succeeds, the rule version increases by 1; when the output fields, units, `time_dependency` and recomputation scope of a rule are all unchanged, no separate change is listed, and when something changes, one `change_rule` is listed separately and needs confirmation by its own rules. For a `ref` field in another table that points to this table, `ref.target` (`row` / `entity`) must match the time kind after the change: when they do not match and the referencing table was also never written, change the referencing table in the same draft (a `change_ref` of the referencing side); when the referencing table has been written, the compilation fails (`validation_failed`, `still_referenced`, pointing to the referencing side).
  - **The table has been written at compile time**: a change that is done only on a table that was never written reports `not_in_this_version` for the whole draft, with `reason` `table_written` and `param` pointing to that key.
  - **Judged again at confirmation**: while the draft waits for confirmation the old version stays writable as usual. At confirmation the judgement is made again in the same transaction: for any change in the draft **that was compiled as "never written"** (structure changes at the level of the table, and those whose `class` was therefore recorded as `metadata` and for which `migrate` may be left out: dropping a field, changing a type, changing a unit, tightening a constraint, adding, removing or changing an external key and so on), if the table it is on has been written by then, `resolve` always reports `draft_outdated` (`reason`: `table_written`), produces no event, and the item stays open. It is not let through on the ground that "this change would also have been allowed on a table that has been written": the compile result and what the confirming party saw is "no data lost, no transformation", and once the table has been written, switching by it would lose the values just written or carry them over without transformation. Once "never written" ceases to hold, it never holds again, and this draft can never be confirmed: the caller `reject`s it, or submits a new draft to supersede it.
    - **A draft that tightens a constraint without giving `backfill` counts the violating positions again at confirmation**: there was no violation at submission, but while waiting for confirmation the old version wrote a value that violates the new constraint; at confirmation (in the same transaction) it reports `draft_outdated` (`reason`: `backfill_required`, with the same detail as `backfill_required` at compile time), produces no event, and the item stays open. Unlike `table_written`, it can be remedied: the caller `reject`s it and submits a new draft with `backfill`.
    - **A draft that renames a slot also judges the new name again at confirmation**: a draft awaiting confirmation does not hold the name, and in the meantime another slot may take it (by being created, or because another rename draft was confirmed first). When a draft with `rename_slot` is confirmed, the new name is judged again in the same transaction by the same comparison as at submission (ASCII case-insensitive): if it is already used by another slot, `resolve` reports `draft_outdated` (`reason`: `name_taken`), produces no event, and the item stays open; the caller `reject`s it, or submits a new draft with another name. If after the switch, on replay, two slots appear with the same name under the comparison, `apply` stops on inconsistency.
  - **Writes that carry an old `sv`**: for any change that takes effect through `restructure_unused` (not only the table-level changes such as changing the time kind, `entity_key`, `granularity` and `base` to `derived`, but also dropping a field, changing a type, adding, removing or changing an external key and so on), afterwards every write to this table that carries an old `sv` is rejected (`schema_incompatible`), and `changed_fields` gives one entry `{field: "*", change: <change code>}`. The structure of the table was replaced as a whole, and the fields in a write are not interpreted one by one by the old definition; one situation, one code, and the caller only has to read again.
  - Compared with "drop the table and build one with the same name", restructuring in place takes only one draft (tables with the same name are matched by name as the same table, and one draft cannot express "drop and then build another with the same name"); when nobody is using it, no confirmation is needed; the table ID, field IDs, descriptions, aliases and other constraints are kept; the derivation rules and `ref`s that depend on it are compiled again by the new definition, and they need not be dropped first.
- **Dropping an object that has dependents fails compilation** (`validation_failed`, detail code `still_referenced`, with the location of the dependent): a table pointed to by a `ref`; a field used by a derivation rule, `entity_key`, `external_key`, `time.field`, `duplicate_keys` or `together`. It is allowed when the dependent side is also changed or dropped in the same draft (for example, removing `external_key` together with the key field).
- **Changes and keys not supported in the first version** (the rows marked "Not supported" in the table above; the rows marked "Yes when the table was never written" used on a table that has been written; and `extends`, `compatibility`, sandbox function rules, derivation rules whose outermost layer is not an aggregate, `migrate` on a field, and `backfill` in expression form): when one appears in a draft, the whole draft reports `not_in_this_version`, pointing to that key, and no event is produced. `reextract` is never quietly treated as "just add an optional field": the Agent would then think the old rows will be extracted again.
- **External key** (`external_key`):
  - **On a table that has been written, a key can only be added on fields newly added in the same draft** (so the existing rows have no value in these fields, and the key index starts empty); when the key field is an existing field, compilation reports `validation_failed` (`external_key_existing_field`). If a key field has history, a privacy deletion could let it fall back to an earlier value, and that value may by then have been taken by another row; this is the same reason as "a key cannot be changed" (see "Time · Writing by `entity_key`"). On a table that was never written there are no rows and the key index is empty, so a key can be added on an existing field, and the set of fields can also be replaced directly.
  - Removing an external key: the key index is cleared; the key field becomes an ordinary field, its values stay on the rows, and it is no longer unchangeable.
  - **On a table that has been written, every change to an external key needs confirmation**; no new automatic category is added for external keys; on a table that was never written, they fall under the existing `restructure_unused`.
  - Putting a key field into `together`: compilation reports `validation_failed` (`external_key_in_together`). Renaming a key field, changing its description and adding an enum value follow the existing rules.
  - After an external key on a table that has been written is changed by the rules above (added on newly added fields, removed), a write that carries an old `sv` is still accepted (validated against the current definition); when an external key is changed through `restructure_unused` on a table that was never written, such a write is always rejected, as above. At the switch the key index is rebuilt for the new version of the table; a migration does not change row IDs.
- **Versions of rules and of the restricted SQL allowlist**: in `schema.compiled`, each derivation rule records the allowlist version it was compiled with (`rule.rsql`, written like `rsql@1`), and the transformation expressions of this version record one more (the top-level `rsql`); on replay, derivation rules and transformation expressions are evaluated by the recorded version, and the kernel keeps the behavior of old versions. When the allowlist changes the behavior of an existing item, a new version is issued. **A rule switches to the current allowlist version only when it is compiled again for another reason**: it is changed itself (`change_rule`), or a definition it depends on changed and it is compiled again in the same compilation; the switch happens within this change and is not listed as a separate change. A rule that is not touched is always evaluated by the recorded version, so a kernel upgrade does not send unrelated drafts to awaiting confirmation. When the switch changes the result of the rule (it uses an item whose behavior changed), the rule version increases by 1 and the derived cache is rebuilt by the new version (see ["Restricted SQL"](11-restricted-sql.md), "Allowlist versions and changes"). Transformation expressions do not switch: the version they recorded is evaluated unchanged at every replay from the beginning.
- **Whether a new physical table is built** is independent of the category and depends on whether the physical shape changes (see "The physical approach"): a change that only changes the catalog, such as renaming, changing a description or changing aliases, builds none; adding a field, dropping a field, and changing a type or a unit all build a new table and replay by the log; restructuring a table that was never written switches to a new physical table, but there is no write to convert, and it is built within the switch transaction in the same way as adding a table.
- **Changing the slot time zone**: the base data does not move; the value of a `date` field is a calendar day and is not recomputed, and the same holds for the daily intervals of a state table. What is rebuilt is the derived tables that assign an instant to a day by the slot time zone (rules that use `saveslot_date(f)` to take the day of a `zoned_datetime` and to bucket); the internal date column behind `saveslot_date(f)` is recomputed in the switch of a time-zone change (see ["Restricted SQL"](11-restricted-sql.md), "Time"). It needs confirmation because the meaning of "today" and "which day" changes afterwards.

**How deterministic conversions are replayed**: the first version has no transformation expressions: `migrate` and the expression form of `backfill` report `not_in_this_version` (see [07-scope-v1](../07-scope-v1.md)), and the part of this paragraph about expressions is the complete design; changing a unit within the same dimension, changing the precision and the constant form of `backfill` work as this paragraph describes. A transformation expression is restricted SQL and uses the same allowlist as derivation rules (see ["Restricted SQL"](11-restricted-sql.md)); its result is deterministic. It is recorded in the "compile result" event together with the compiled definition; on replay, when `apply` reaches the switch event, it converts every write of the old version into the shape of the new version by the compiled definition. **The rule for converting one by one**: each entry of an old write on a field f becomes one entry on the same field in the new version, and its value = `migrate` evaluated on the old value of this entry (changing a unit within the same dimension is a conversion; a field without `migrate` is carried over unchanged). **Only an entry with a value is evaluated**: an entry whose value is empty (an explicit clear, `"value": null`), and entries of `no_value` and `uncovered`, are not evaluated and are carried over unchanged: a field that was explicitly cleared is still empty in the new version, and the `ELSE` branch of the expression does not fill a value into it. The status of taking effect, the interval, the value source, the corroboration relations and whether the entry was reverted of each entry do not change; candidate and awaiting-confirmation entries are converted in the same way and are still candidates and awaiting confirmation. A contribution filled in by a constant `backfill` at an earlier switch is converted like a write's entry (evaluated only when it has a value) and is still recorded on the switch it came from. `backfill` acts only on positions that still violate the new constraint after the build completes, **and only on rows that exist**: on event tables and timeless tables, the rows not revoked; on state tables, the intervals in which the entity exists and the field has no value. Revoked rows, the intervals without a value left by a revoke, and the intervals in which the entity does not exist are not filled: "required" constrains the rows that exist; filling a value inside a revoke is the same as filling a value into an interval without a value, and when that revoke is later undone the row could not come back. At these positions: the expression form is evaluated on the old value at that position, and the value source is that of the entry; **when there was no contribution at that position, or the old value is empty, the expression form is not evaluated and this position stays without a value** (the same direction as `migrate`: with no old value there is nothing to compute). Only the constant form gives a value to a position without an old value. So adding a required field (`add_required_field`), or changing optional to required, **must always give a constant-form `backfill`, whether or not the table has rows at that moment** (an empty table also has to give it, and so does restructuring a table that was never written: the compile result does not vary with the state of the table at that moment); otherwise compilation fails (`validation_failed`, detail code `backfill_const_required`). The constant form and the expression form of `backfill` cannot be given together; giving both reports `validation_failed` (detail code `backfill_both_forms`); when a draft both tightens the range and changes to required, give only the constant, which is also used for the rows that violate the range. The value that the constant form gives is **the contribution of that switch itself**: its origin in the provenance table and the version table is that `schema.switched` event (the kind of source is "schema constant", and it points to no source data), and `history` shows it as a version produced by a schema switch. This version cannot be undone: when the target of `undo` is the operation number of a schema switch it reports `invalid_argument` (`undo_target`), and to change it, submit a new schema draft; entries filled in by a constant are also never listed in any revert record (`undo`, `include_later` and `take_previous` all skip them). The constant itself comes from text written in the schema and is not cleared by any privacy deletion (see "Deletion · Content derived from source data"). **Filling a value does not change `ver`, so a write that carries the current `ver` does not conflict with a fill**: when judging "the current `ver`", entries whose intent is `schema_switch` are skipped; a fill is only a default constant, overriding it loses no judgement that anyone has seen, and a party that read the old value learns of it through the `schema_updated` notice. **At which positions a value is filled follows the record**: `schema.switched` records the positions of the fills, and `apply` registers them as recorded; replay does not compute them again from the state at the time. On event tables and timeless tables, this is a list of the IDs of the rows, per field, where a value was filled (opaque identifiers, which are metadata); on state tables, it is the entity ID and the intervals, and the intervals are obtained from other contributions (over which valid time the entity exists and the field has no value), which is content, and the record notes which contributions they come from (the same approach as "Deletion · Content derived from other contributions"). **A later deletion does not change the positions of the fills**: when a deletion makes a field empty at some position, no constant is filled in afterwards (a deletion may make a required field empty anyway, see "Deletion · Replay rules"); on state tables, when a contribution that a filled interval comes from is deleted, the recorded interval is cleared with it, and that stretch of fill no longer exists. The option "have a deletion restate the switch fill" is not chosen: it would require a deletion event to be able to point to a switch event and to locate a fill by row, and the reference evaluator would need one more kind of contribution; the only benefit would be that a required field still has a constant value after it was deleted. An expression refers only to its own field (see "Schema document format"), so the conversion of each entry looks only at that entry itself. The content of the switch event records the row count and the result checksum of each new-version table, in the same way as derived writes: on replay it is checked if present and is not used to generate anything; it is computed from user content, so it is content, and it is cleared when its inputs are deleted, after which the check is skipped. Only the conversion result of an extraction (the output of a model, which cannot be replayed) is recorded as content in the "migration result" event. What to do when a deletion happens while a migration is in progress is in "Deletion · How the result lands in the log".

### What is automatic and what is not

| Step | Who does it | Notes |
|---|---|---|
| Recognizing the kind of change, checking compatibility | saveslot, automatically | Compared by the field matching rules of "Schema document format"; the result is deterministic |
| Preview: how many rows change, which derived values change, which consumers would break | saveslot, automatically | Consumers are found from the catalog: derivation rules, registered SKILLs, saved queries, and API scripts that hard-code fields |
| Writing the migration function | The Agent that drafts the schema (a model) | For example which enum value "good / average / poor" maps to; saveslot compiles, validates and does a trial run |
| Execution: metadata changes, deterministic transformations, cache rebuilds | saveslot, automatically | The result can be replayed |
| Re-extraction | The calling Agent (first version); once the user has authorized model calls, it can also be done by the background executor (worker) that calls the model | The result is a proposal; when it differs from a confirmed value it goes to awaiting confirmation |
| Approval | Graded by risk | The slot policy lists which kinds of change take effect automatically (by default eight kinds: those that change no existing value, make no old write fail, and make no existing read see something different, see the table above); the rest need confirmation |
| Ambiguity: a rename, or a drop and an add? | Ask | When an existing field is matched neither way and is not listed for dropping, an error is reported and it is returned to the submitting Agent for clarification; no guessing |

### Principles

1. **A schema version is immutable, and data is not quietly reinterpreted.** A write to the log records the schema version; a read at a moment uses the version of that moment; read_log also records the schema version.
2. **The result of re-extraction is a proposal.** When it differs from a confirmed value (especially one the user confirmed or corrected), it goes to awaiting confirmation; a correction is source data and is taken in again at re-extraction, so it is not lost.
3. **Preview the impact before a change**, and execute after confirmation; re-extraction gives its cost in the preview (for example "2,300 pieces of source data to be re-extracted").
4. **Externally there is only the latest version.** Consumers by default use only the latest schema, and old versions are not visible externally; the Agent reads the current schema through MCP every time and so follows along naturally.
   Old versions are kept internally for reads at a moment. This calls for the following:
   - **A read result carries its own explanation**: a value carries its unit and the schema version (such as `3.11 mi · schema v2`), and does not return a bare number,
     so that outdated assumptions in a SKILL or in an Agent's memory ("the distance is in kilometers") can be discovered.
   - **Only old-version writes to fields with an incompatible change are rejected**: a write carries a schema version; if a field it writes to has had an incompatible change since that version (a type change, a dimension change, a drop, a semantic restructuring),
     it is rejected with a hint to read again ("runs.feeling is now an enum (schema 4), please read it again"); if the fields it writes to are unchanged (or were only renamed, or other optional fields were added), it is accepted as usual.
     Versions are still managed per slot, but compatibility is judged per field; otherwise a change to any table in a slot would reject the writes of all Agents.
     A written value carries its own unit and is converted automatically within the same dimension, so **changing only the unit within the same dimension is compatible for old-version writes** and is not in the rejected set.
     Tightening a constraint (optional to required, tightening the range, removing an enum value) is also not incompatible: a write is always validated by the current definition, and `validation_failed` is reported if it does not satisfy it.
     **A change that takes effect through `restructure_unused`** (restructuring a table that was never written, including table-level changes without a corresponding field such as changing the time kind, `entity_key` and `granularity`) is treated as an incompatible change to all fields of this table: every write to this table that carries an old `sv` is rejected.
   - **Consumers that do not read the schema** (API scripts that hard-code fields) cannot follow automatically; they can only be listed in the preview and left to the user to decide.

### Schema document format

**The document is JSON of the same shape for reading and writing; for submission, "the whole table inside it, only the changes inside a slot"; names are written by the Agent, IDs are assigned by saveslot and filled back; deletion must be explicit.**

- **Granularity of submission**: a draft lists only the tables to create or change, and gives the complete definition of every table it lists; tables not listed do not change; dropping a field is written in `drop_fields` of the table, and dropping a table in `drop_tables`.
  There is no field-level incremental operation language: what the Agent reads is the whole definition, and handing it back after the change is the most natural.
- **Names and IDs**: the Agent refers to tables and fields by name; saveslot assigns the IDs of tables, fields and rules, and fills them back in the compile result. A table ID is unique within the user, and a field ID is unique within the table,
  and short IDs are used (`t1`, `f2`); one that was deleted is not reused; the physical names are `t_<table ID>_v<n>` and `f_<field ID>` (never exposed externally).
  **A table name is unique within the slot** (ASCII case-insensitive; the same for field names within a table, see the entry on names in "Field types and value ranges"); the interface accepts the qualified name `health.runs`, and the table name alone can be written when it does not collide within the visible range of this call.
- **Concurrency**: a draft carries `base_version` (the schema version read when drafting, `null` when the slot is created); if it does not match the current version it is rejected, and a new draft based on the new version is required.

**Field matching rules** (the result is deterministic, no guessing):

| Field in the submission | What saveslot does |
|---|---|
| Carries `id` | Matched by ID; a different name means a rename |
| No `id`, and the name is the same as an existing field | The same field |
| No `id`, and the name is new | Added |
| An existing field matched neither by ID nor by name, and not in `drop_fields` | Reports an error: "f3 duration is missing; to rename it pass back the id, to delete it list it in drop_fields" |

An Agent that does not rename can ignore IDs entirely; omitting a field is not treated as a deletion. Tables are matched in the same way.

**Document structure**:

| Level | Keys | Written by | Notes |
|---|---|---|---|
| slot | `slot`, `base_version`, `timezone`, `rename_to` (optional) | Agent | `timezone` decides the calendar-day meaning of `date` and is an IANA time zone name: `UTC`, or the "region/place" form (at least one `/`, such as `Asia/Shanghai`, `Etc/GMT+8`); an alias can also be used and is recorded unchanged; an offset (`+08:00`) and a short name without `/` (`CST`) are not accepted; `rename_to` renames the slot |
| Table | `name`, `id`, `kind` (`base` / `derived`), `description` (required), `aliases` (optional), `time` | Agent; `id` is filled back by saveslot | `time.type`: `none` / `event` / `state`; for `aliases` see "Aliases" below |
| Event table | `time: {type: "event", field: "<field>"}` | Agent | Names the field of the time of occurrence (`date` or `zoned_datetime`); this field must be required: every row has a time of occurrence |
| State table | `time: {type: "state", granularity: "date" \| "instant"}`, `entity_key` (optional, an array of field names, such as `["category"]`) | Agent | The valid interval is managed by saveslot and does not appear as a field; `entity_key` is an optional natural key, and the fields it lists must be required; key fields do not change with valid time, and key uniqueness is uniqueness across all time (see "Time · Writing by `entity_key`") |
| External key | `external_key` on the table (optional, an array of field names, 1 to 4 fields, such as `["origin", "external_id"]`) | Agent | The identifier of the record in the source system; when writing by it, an existing record is updated and otherwise one is added (see "Writing by external key"). Can be used only on event tables and timeless tables (otherwise `validation_failed`, `external_key_table_kind`); the type of a key field can only be `text`, `enum` or `integer` (otherwise `external_key_field_type`: other types need conversion, rounding or a time zone for the same value, and are not suited as identifiers); a key field may be optional or required, and when optional the table may contain rows without an external key; the scope of uniqueness is the table, and comparison follows the criterion for the same value. When only one key field is declared, the compile receipt gives the reminder `single_field_external_key` (when several source systems write this table the IDs may collide, and the key should include a field that tells the source apart) |
| Field group | `together` on the table (optional, an array of arrays of field names, such as `[["start", "end"]]`) | Agent | The fields of one group are one conflict unit (see "Field group" below); it cannot contain a key field of an external key |
| Field | `name`, `id`, `type`, `description` (required), `aliases` (optional), `required`, `min` / `max`, `values` (enum), `unit`, `scale` / `rounding` (the precision of `quantity` and `decimal`, optional), `ref: {table, target: "row" \| "entity"}` | Agent; `id` is filled back by saveslot | For the value ranges of the types, the unit vocabulary and the defaults of precision see "Field types, same value and units" |
| Suspected duplicate | `duplicate_keys` (an array of arrays of field names, each group is one set of criteria) | Agent | Can be used only on event tables and timeless tables. A soft criterion: a hit generates a pending item and does not reject the write (see "The write request · Suspected duplicates"); the first version has no hard uniqueness constraint |
| Derived table | `rule.sql`, `rule.time_dependency` (`none` / `bucketed` / `now`); one `description` per field, and optionally `type` (only `decimal` is accepted), `unit`, `scale` / `rounding` | Agent | The SQL is written with names, and saveslot stores it in a form bound by ID (a rename does not break the rule); the field types, units, precision, dependencies and recomputation scope are inferred and filled back by saveslot; the type of a derived field is one of `text`, `enum`, `ref`, `integer`, `decimal`, `quantity`, `boolean`, `date`, and cannot be `zoned_datetime` (an aggregated instant has no time-zone part; to take the day use `saveslot_date`). The output columns of the rule are matched to the derived fields one to one by name (ASCII case-insensitive), and an expression must be written `AS <field name>`. `type` / `unit` / `scale` / `rounding` written on a field only fill in what cannot be inferred; when it can be inferred, what is written must agree with the inference: a contradiction with the inferred unit (including writing a result that carries a unit as `decimal`) reports `unit_inference_failed`, and anything else reports `rule_sql_rejected` |
| Migration | `migrate` on a field (a restricted SQL expression, a deterministic transformation), `backfill` (fills the violating rows when a constraint is tightened); `drop_fields` on a table; `drop_tables` on a slot. `reextract: {from, instructions}` (re-extraction: from which old fields and which original source data text to extract, and how; an empty `from` means extracting a new field after the fact) **is not supported in the first version** | Agent | Written only when saveslot cannot infer it; a unit change within the same dimension is converted automatically by saveslot and needs no migration function; re-extraction goes through extraction jobs (see "Extraction jobs" below) |
| Official schema | `extends`, `compatibility` | — | Not accepted in the first version, and one in a draft reports `not_in_this_version`; for the place reserved in the compiled definition see "The official schema and user schemas" (`compatibility` gets no key), and for the details see "Details of the official schema" in the open questions |

- **Types (first version)**: `text`, `integer`, `decimal`, `boolean`, `enum`, `date`, `zoned_datetime` (an instant + an IANA time zone, so that "which day" can be recomputed),
  `quantity` (a number + a unit, stored as a decimal number in the declared unit), `ref` (points to a table of the same slot, which may be the table it is in; the first version does not cross slots). For the value range of each type see "Field types and value ranges".
- **Names**: slot names, table names and field names use only letters, digits and underscores, start with a letter, and have at most 63 characters; they must not start with `_`, and a field name must not be `valid`, `valid_from`, `valid_to`, `row_id` or `entity_id`. Violating this makes compilation report `validation_failed` (`reserved_name`). Each is unique within its own scope, ASCII case-insensitive (`duplicate_name`). Description text and aliases are not subject to this restriction.
- **Aliases** (`aliases`, optional on tables and fields; base tables, derived tables, base fields and derived fields can all carry them): other ways the user and the Agent refer to this table or field (colloquial names, old names, names in another language), which help an Agent that reads the catalog to map the user's wording onto names. There are no slot-level aliases.
  - Limits: at most 8 per object, and at most 64 characters each (see "Field types, same value and units").
  - Content (checked at compile time, the result is deterministic): NFC normalization is done before they are recorded; after normalization an alias must not be empty, must not contain a line break (including the line separator U+2028 and the paragraph separator U+2029) or a control character, and must not start or end with whitespace; the aliases of one object must not repeat each other; **it must not equal any name that can still be resolved in the same scope**: an alias of a table must not equal the current name of any table of this slot, nor the name of a table that can still be resolved by its old name (within the last 10 schema versions), and an alias of a field is checked against the current names of the fields of this table (including itself) and old names that can still be resolved. The table names and field names that this draft is going to drop still count as occupied within this draft: dropping and giving an alias are done in two drafts, so that in one draft a name does not change what it refers to. The comparison goes by code point after NFC, and only ASCII letters are case-insensitive (names themselves are unique ASCII case-insensitively and are also resolved case-insensitively in SQL). Otherwise an Agent that wrote that word according to an alias would have the request resolved by the old name to another table or another field, the opposite of what the alias hints. It is allowed that the alias of another object is the same: the user's wording may be ambiguous to begin with, and the description tells them apart. Violating any of these reports `validation_failed` (`alias_invalid`), with `path` pointing to that entry and `reason` stating which rule (04-contract-types, section 9).
  - **Handled as untrusted text**, by the same rules as descriptions: in the contract it is untrusted text and is rendered inside the untrusted boundary; when a boundary marker appears, `validation_failed` (`untrusted_marker`) is reported; it does not appear in tool descriptions, parameter descriptions or the server's `instructions`. An alias is text written by the schema author and, like names and descriptions, is outside the cascade of privacy deletion; do not write a user's private words as an alias.
  - **Not part of name resolution**: a table name or field name in a request, and an identifier in restricted SQL, are recognized only by name (including an old name that can still be resolved after a rename), and a request that wrote an alias still reports `unknown_table` / `unknown_field`. A name is an identifier and unique within its scope, while an alias is free text and may repeat; if an alias could be resolved, changing one alias could make the same request land on another field, and a change such as "only the description" could no longer take effect automatically. It is used for the hint when an error is reported: in `nearest`, the objects whose alias is the same as the name in the request under the fold N of "Similar keys" have their **names** put first; the search covers only what is visible in this call, and what is returned is the name, not the alias text.
  - The change code for changing an alias is `change_aliases`, which falls into the automatic category `description` (see "Kinds of change and means of migration"): it changes only the catalog and builds no new physical table.
- **A unit comes from the fixed unit vocabulary** (see "Field types, same value and units · Unit vocabulary"): units of the same dimension are converted automatically; a unit outside the vocabulary is rejected at compile time.
- **Currency also uses `quantity`, but each currency is its own dimension and they are not converted to each other** (an exchange rate is not a fixed coefficient): a written unit that differs from the currency the field declares reports `validation_failed`.
  To convert, bring the exchange rate in as base data and compute it in a derivation rule (see "Derivation rules").
- **Relations between tables**: base tables are related by `ref` declarations; derived relations are obtained by saveslot by parsing the rules.
- **Field group** (`together`): concurrent writes are merged per field; a constraint on a single field is not broken by the merge, and what can be broken is only the relation across fields. Example: a business trip `start 11-01, end 11-05`; one side changes `end` to 11-03 and the other changes `start` to 11-04; neither conflicts on its own, and the merge produces a row in which `start` is later than `end`. Only the author of the schema knows which fields are related, so it is declared by the schema: the fields of one group are one conflict unit, and a change to any field of the group intersects with a write that changes any field of the group. When it is not declared, each field is a unit by itself. A field group affects only conflict judgement and the target of an item, and does not affect stop points, provenance or the same-value judgement (see "Conflict handling · Conflict criteria"). A field group is in the compiled definition and goes with `sv`; deletion replay follows the `sv` recorded with the write. **A key field of an external key cannot be put in a field group** (`validation_failed`, `external_key_in_together`): a key field never takes part in the synchronization baseline, and putting it in a field group would tangle it with the conflict judgement of the other fields of the group.
- **The unit of a derived field** is inferred by saveslot (`sum` / `avg` / `min` / `max`, multiplying or dividing by a constant); when it cannot be inferred (multiplying or dividing two quantities that carry units), `unit_inference_failed` is reported, requiring the field to be declared as `decimal` or `unit` to be stated.
- **Compatibility and the migration category are judged by saveslot** (metadata only / deterministic transformation / re-extraction) and are listed one by one in `changes` of the compile receipt.
- **The expressions of `migrate` and `backfill` can refer only to the old value of the field itself and to constants** (the only column name that can appear in an expression is the name this field has in `base_version`). The first version does not accept these two kinds of expression, and one in a draft reports `not_in_this_version` (see [07-scope-v1](../07-scope-v1.md)); referring to another field likewise reports `not_in_this_version`. The reason: a migration converts every write of the old version one by one into the shape of the new version (see "How deterministic conversions are replayed" below), and a write records only the fields it involves; when a conversion depends only on this field, each write's entry for this field becomes exactly one entry of the new version, and the status, interval and source are carried over unchanged. When it depends on other fields, a write that wrote only the other fields would also change the result of the conversion, and whether it counts as a contribution in the new version and how its interval is determined would need another set of rules, which comes later. To compose a new field from several fields, the way in the first version is to add a derived table, or for the Agent to read the values out and write them again.
- **A `migrate` expression and `reextract.from` in a draft are always resolved by the names of `base_version`** (so that there is no ambiguity when the same draft both renames and changes the type; `from` may refer to an old field that this draft is going to drop).
- **Tightening a constraint** (optional to required, tightening `min` / `max`, removing an enum value): give `backfill` on the field (a restricted SQL expression or a constant, only one of the two; the first version accepts only the constant form, and the expression form reports `not_in_this_version`, see [07-scope-v1](../07-scope-v1.md)) to handle the existing rows that violate it (only rows that exist are filled: rows not revoked, intervals in which the entity exists, see "How deterministic conversions are replayed" above); when it is not given and rows violate the constraint, compilation fails and reports the number of violating rows and samples (`backfill_required`; a sample gives only the position, a row ID or an entity ID, and no value; on state tables the count is by entity, and an entity with several violating segments is still counted once). Optional to required and adding a required field must always give the constant form, whether or not there are rows.
  - `min` / `max` are interpreted by the unit and precision of the field. When the same draft changes the unit or the precision, the old and new constraints are compared by the new unit and precision: the old bound is first converted to the new unit and rounded by the new precision and rounding mode, and then compared with the new bound; so `5 m` changed to `5 km` is a tightening for `min`, and `10 kg` changed to `10000 g` is not a change for `max`.
  - Whether an existing value violates the constraint is also judged after conversion: when the same draft both changes the unit or precision and tightens a constraint, the old value is first converted by the new unit and rounded by the new precision and rounding mode, and then compared with the new constraint; the violating positions are filled by `backfill`.
- **Changing the slot time zone** changes the calendar-day meaning of every `date`, falls into deterministic transformation, and needs confirmation; for what exactly is rebuilt see "Kinds of change".
- The complete document retrieved from the catalog (the full-schema level of `catalog`) already has `base_version` filled in (= the current version), and can be submitted directly after changes; **handing it back unchanged is `no_change`**. It is generated from the compiled definition of the current version and is not the original text of the drafts so far (a draft that changes an existing slot lists only the tables it changes): bounds are written as decimal strings, and the precision of `quantity` / `decimal` is written out together with its default. What the compiled definition does not have and can only be taken from the original text is only the text of derivation rules (the compiled definition binds it by ID): it is taken from the original text in the most recent draft that wrote to this derived table; if a table or field that it refers to is renamed afterwards, the text is not rewritten and still has the old name, and the rule is still evaluated by ID. When a draft changes an existing slot, a derived table it lists that is consistent with what this document gives (the rule text is byte-for-byte the same, and the names, descriptions, aliases, the names and descriptions of the fields, and the keys filled back on the rule and fields are all the same) is treated as not listed, and the rule is not resolved again by name; if even one thing differs it is still a change to a derived table, which this version reports as `not_in_this_version`.
- **How long an old name is still recognized**:
  - A write resolves names by the `sv` of the request (given explicitly, or taken by the fallback of 04-contract §2) and then maps them to field IDs; a name of any version is recognized, and after a rename a write that carries an old-version name is accepted as usual. A table that did not yet exist in that version (added only later) does not have this name in that version: a write to it that carries an old `sv` reports `unknown_table`, the same as when the name does not exist. `sv` is per slot: a table name without a slot prefix that exists by its current name in one slot and by its name in the version of the request's `sv` in another slot reports `ambiguous_table`, and both are listed as candidates. The table names and field names in receipts and errors are given by the version of the request's `sv`, consistent with the `sv` of the receipt.
  - A read that carries no `sv`: if a name is an old name that some field used within the **last 10 schema versions**, and currently no other table or field within the visible range has this name, it is resolved by the old name, and the receipt hints at the new name. The current name takes precedence.
  - **Slot names are not part of these rules**: after a slot is renamed the old name is no longer resolved; a qualified name written with the old name (`old_name.table_name`) reports `unknown_table`, and where a slot name is a parameter `not_found` (`slot`) is reported, both the same as when the name does not exist. The old name can later be used by a newly created slot, and recognizing the old name would make the same name point to two places.
  - **An alias is not a name** and is not part of these rules: when something is renamed, the old name does not automatically become an alias; and "whether another table or field currently has this name" does not look at aliases either. To let people and Agents still recognize the old name after 10 versions, the drafter can write it into `aliases`; it is only a hint and does not restore resolution.
- **The precondition for a rename to take effect automatically is that nobody else is using it**: in the first version it is inferred from the read and write records ("a connection other than the submitter's read or wrote runs.duration in the last 30 days"); if there is one, it is listed in the preview and needs confirmation; explicit registration of consumers comes later.
  The read side is inferred from read_log; on the write side, when `write` is recorded, it hands "which fields this write referred to by name" to `audit` to count (class (c); if lost, the preview merely lists one consumer fewer).

**Example: creating a slot (the v1 draft)**

```json
{
  "slot": "health", "base_version": null, "timezone": "Asia/Shanghai",
  "tables": [
    {
      "name": "runs", "kind": "base", "description": "One row per run",
      "time": { "type": "event", "field": "date" },
      "fields": [
        { "name": "date", "type": "date", "required": true, "description": "The day of the run (a calendar day in the slot time zone)" },
        { "name": "distance", "type": "quantity", "unit": "km", "required": true, "min": 0, "description": "Distance" },
        { "name": "duration", "type": "quantity", "unit": "min", "min": 0, "description": "Time taken" },
        { "name": "feeling", "type": "text", "description": "How it felt after the run, in the user's own words" }
      ],
      "duplicate_keys": [["date", "distance"]]
    },
    {
      "name": "weekly_mileage", "kind": "derived", "description": "Weekly mileage, counted from Monday",
      "rule": {
        "sql": "SELECT date_trunc('week', date::timestamp)::date AS week_start, sum(distance) AS total_distance, count(*) AS run_count FROM runs GROUP BY 1",
        "time_dependency": "bucketed"
      },
      "fields": [
        { "name": "week_start", "description": "The Monday of that week" },
        { "name": "total_distance", "description": "Total distance of that week" },
        { "name": "run_count", "description": "Number of runs in that week" }
      ]
    }
  ]
}
```

The `::timestamp` in the rule cannot be omitted: otherwise PostgreSQL picks the `date_trunc` with a time zone, whose result changes with the session time zone, and compilation rejects it as a "non-deterministic function" and gives the fix.

**The compile receipt (excerpt)**: the IDs filled back and the inferred results.

```json
{
  "draft": "d_…", "slot": "health", "slot_id": "sl_…", "target_sv": 1, "outcome": "applied",
  "document": {
    "tables": [
      { "name": "runs", "id": "t1",
        "fields": [{ "name": "date", "id": "f1" }, { "name": "distance", "id": "f2" }, { "name": "duration", "id": "f3" }, { "name": "feeling", "id": "f4" }] },
      { "name": "weekly_mileage", "id": "t2",
        "rule": { "id": "r1", "version": 1, "depends_on": ["runs.date", "runs.distance"], "scope": { "kind": "group", "key": ["week_start"] } },
```

**Example: the v2 draft** (changed on the schema that was read, listing only runs). This is an example of the complete design: the `reextract` of `avg_hr` in it is not supported in the first version, and submitting with it makes the whole draft report `not_in_this_version`; in the first version, with that key removed, `avg_hr` is an ordinary newly added optional field. The `migrate` of `f4` (text to enum) likewise reports `not_in_this_version` in the first version (see [07-scope-v1](../07-scope-v1.md)).

```json
{
  "slot": "health", "base_version": 1,
  "tables": [{
    "name": "runs", "id": "t1", "kind": "base", "description": "One row per run",
    "time": { "type": "event", "field": "date" },
    "fields": [
      { "id": "f1", "name": "date", "type": "date", "required": true, "description": "The day of the run (a calendar day in the slot time zone)" },
      { "id": "f2", "name": "distance", "type": "quantity", "unit": "mi", "required": true, "min": 0, "description": "Distance" },
      { "id": "f3", "name": "moving_time", "type": "quantity", "unit": "min", "description": "Moving time" },
      { "id": "f4", "name": "feeling", "type": "enum", "values": ["good", "ok", "bad"], "description": "How it felt after the run",
        "migrate": { "sql": "CASE feeling WHEN '好' THEN 'good' WHEN '一般' THEN 'ok' ELSE 'bad' END" } },
      { "name": "avg_hr", "type": "quantity", "unit": "/min", "description": "Average heart rate",
        "reextract": { "from": [], "instructions": "Fill in when the original text mentions the heart rate; leave it empty when it does not" } }
    ]
  }]
}
```

| Change | Category | Handling |
|---|---|---|
| f2 km → mi | Deterministic transformation | saveslot converts automatically, weekly_mileage is rebuilt and its unit changes with it; a unit change within the same dimension is compatible with old-version writes |
| f3 renamed | Metadata only | The data is not touched |
| f4 text → enum | Deterministic transformation | Uses `migrate`, does a trial run on the existing rows and reports the result; since the type changed, a request that carries an old `sv` and writes `feeling` is rejected. The expression is evaluated only for entries that have a value: a row whose `feeling` was explicitly cleared, or never filled in, is still empty in the new version and does not fall onto `ELSE 'bad'` |
| avg_hr added | Metadata only + extracting after the fact | Old rows are empty at first, and extracting after the fact goes through extraction jobs; the new field was empty to begin with, so the result of extracting after the fact needs no confirmation |

**Example: a state table** (creating the `marketing` slot):

```json
{
  "slot": "marketing", "base_version": null, "timezone": "Asia/Shanghai",
  "tables": [{
    "name": "budgets", "kind": "base", "description": "Monthly budget of each category",
    "time": { "type": "state", "granularity": "date" },
    "entity_key": ["category"],
    "fields": [
      { "name": "category", "type": "text", "required": true, "description": "Budget category" },
      { "name": "amount", "type": "quantity", "unit": "CNY", "required": true, "min": 0, "description": "Monthly budget amount" }
    ]
  }]
}
```

A write locates the entity by `entity_key: {"category": "推广"}`, and the valid interval is passed with `valid_from` / `valid_to` (see "Writes" in the contract); they are not fields.

For the state machine, the physical approach, extraction jobs and the official schema see [`08-schema-migration.md`](08-schema-migration.md).

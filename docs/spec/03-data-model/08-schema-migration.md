## Schema version evolution (continued)

For the principles, the classification of changes and the schema document format, see [`07-schema-evolution.md`](07-schema-evolution.md).

### State machine: reads never stop

```
draft        → compiled → awaiting confirmation → migrating → switch → current → retired
  │                │              │                  │
  └ compile failed ┘   abandoned / superseded        failed: rolled back / migration abandoned (old version stays current, nothing changed)
```

| State | Read | Write | Notes |
|---|---|---|---|
| Draft / compiled / awaiting confirmation | Old version as usual | Old version as usual | The new version is only a proposal; it does not expire, and a newly submitted draft supersedes an earlier draft that is not yet confirmed. Compiling and the impact preview are one step: one call of `schema_draft` returns the compile result and the preview together, and there is no separate "previewed" state |
| Migrating | Old version as usual | Old version as usual, and the write also goes into the log; a write that carries the old `sv` first evaluates the conversion expressions against the new version inside the write transaction and is rejected if that fails (see below; the first version has no conversion expressions, so this step does not happen) | In the background, the base tables and derived caches of the new version are built from the log, and the new writes made in the meantime are continuously caught up. A migration without `migration_diff` switches as soon as the build is done and waits for no one; a migration with `migration_diff` (an extraction job, not in the first version) has **three exits**: all differences handled → switch; `keep_rest_and_switch` (differences not yet handled are treated as rejected row by row) → switch; `abandon` → the migration is abandoned and the old version stays current (see "Extraction jobs") |
| Switch | Does not stop | Paused for a very short time | Within one transaction, the last stretch of the log is caught up and the "current version" is pointed at the new version |
| Current | New version | New version; a write that carries the old version number and touches a field with an incompatible change is rejected | A change that takes effect through `restructure_unused` is regarded as making all the fields of that table incompatible (see "Principles") |
| Retired | Not visible externally | Cannot be written | Kept internally, for reading as of an instant |

Every state change of the state machine (draft submission, compile result, confirm / abandon / superseded, migration start, switch, failure) is a log event ("abandon migration" comes later together with extraction jobs: a deterministic migration in the first version has no exit by manual abandon, and produces no such event); the compiled definition is recorded in the event and is not compiled again on replay. The "migration result" event is produced only in extraction jobs (a translation result is model output, cannot be replayed, and must be recorded); a deterministic migration has no such event.

- **A compile failure produces no event**; like a rejected write it is just an error. When the draft contains a change or a key that the first version does not support (`reextract`, `derived` changed to `base`, changing the time kind on a table that has been written to, and so on; for the list see "Kinds of change"), the whole draft reports `not_in_this_version`; when a change that is made only on a table that was never written to is used on a table that has been written to, the `reason` is `table_written`.
- **Conversion expressions are evaluated again at confirmation** (the first version has no conversion expressions: `migrate` and the expression form of `backfill` report `not_in_this_version`, see [07-scope-v1](../07-scope-v1.md); this item is the complete design): when the draft is submitted, `migrate` / `backfill` are trial-run on the existing data; while waiting for confirmation the old version can still be written as usual, and a newly written value may make an expression fail (such as converting `text` to a number). At confirmation (`resolve`), within the same transaction, the new writes made since the trial run are evaluated again; if any fails, `resolve` reports `draft_outdated` (`reason`: `migrate_failed`), produces no event at all, and the item stays open. This is handled the same way as `table_written` (see "Kinds of change"): the caller fixes the expression and submits a new draft to supersede it, or first fixes those few values and then confirms.
- **A write that carries the old `sv` during migration** (the part about conversion expressions is as above and does not happen in the first version): after confirmation and before the switch, the old version can still be written as usual, but these writes must later be converted into the new version. So a write that carries the old `sv` evaluates `migrate` / `backfill` against the new version inside its own transaction; if any fails, the whole request reports `validation_failed` (`migrate_failed`, with `path` pointing to that field of that op), with a hint to reread by the new version and write again. The switch is not made to fail or roll back because of this: the migration has been confirmed and cannot be held up by a later write; that value cannot fit in the new version anyway, and rejecting it on the spot is more honest than dropping it at the switch.
- **Only one change is in progress for the same schema at a time.** A second draft waits for the previous one to finish and is drafted again on the new version (like a code merge conflict). A new draft submitted during a migration is rejected, and the rejection names the two ways to end the current migration (`keep_rest_and_switch`, `abandon`), so that a migration stopped halfway does not block later changes forever; a migration without `migration_diff` waits for no one, and the rejection gives its progress (see "Extraction jobs").
- **A re-extraction migration may last a long time** (people still have to confirm the differences), but the old version stays readable and writable throughout and the user notices nothing; the source data that comes in meanwhile is extracted by the new version together by the catching-up step.
- **Failure is safe.** Before the switch the new version exists only in the background, and on failure it is discarded entirely and the old version is not affected.

### The physical approach: tables named by version plus a pointer switch

This is implemented with saveslot's own log, not with tools such as pgroll / gh-ost (saveslot does not need old and new versions writable at the same time, and does not need to follow the database log).

- **A new physical table is created only for tables whose physical shape changed**; tables with no change are reused across versions. Whether a new table is created depends on the physical shape and has nothing to do with the classification of the change (except for table-level changes on a table that was never written to, see below):
  - A change that touches only the catalog (renaming, changing a description, changing `duplicate_keys` and the like, which do not affect physical columns): no new table is created, and the switch only changes the current version pointer and the catalog.
  - A table whose physical shape changed (adding a field, dropping a field, changing a type or unit, a deterministic conversion): a new physical table is created and filled by replaying the log. Adding an optional field is in this group too; with a small amount of data the replay finishes at once.
  - Changing the structure of a table that was never written to (changing the time kind, `entity_key`, `granularity`, `ref`, adding, removing or replacing an external key, `base` changed to `derived` and other table-level changes): whether the physical shape changed does not matter, and a new physical table is always created, but there are no old writes to convert, and like adding a new table it is created inside the switch transaction; this table does not count as "rebuilt from the log", is not listed in the rebuild list of the switch event, and has no verification information. The old physical table becomes a retired table and is empty. `apply` does not need to know about "never written to": when replay reaches the switch event it simply creates the table by the compiled definition; this judgement is made only at compile and confirmation time, and its result shows up as "this switch has no writes to convert".
  Physical table names are **never exposed externally**, and must not appear in the error messages of restricted SQL either.
- Retired tables are kept for good in the first version, and reading as of an instant before the switch queries them: the instant is first turned into an operation position S (`seq`) by the existing rules, and the version that covers S is the last version whose switch belongs to an operation not later than S (an operation is atomic: as of S, the operation of the switch is either entirely visible or entirely invisible, and the writes in it and the switch cannot fall on two sides); the compiled definition of that version supplies the tables and fields, its physical table answers, and values and units follow that version (tables with no change share the same physical table across versions, and `physical.table` in the definition of that version points to it). For this, `schema_versions` records the switch position of each version (the `seq` of `schema.switched`, from which the operation it belongs to is obtained). Cleanup, and the fallback of replaying from the log after a cleanup, are done later together. **However long they are kept, a cleanup is written as a log event** (`system`),
  so that "replay from empty storage = online state" also holds on retired tables. Privacy deletion takes effect on retired tables just as on current tables.
- **Every base table and derived table changed in a schema version is a separate physical table**, whose name contains the table ID and the version number (such as `t_<table_id>_v<n>`) and which is **never renamed once built**
  (PostgreSQL views bind by the internal ID of a table, so swapping table names does not work). Physical column names use field IDs (`f_<field_id>`), and a rename changes only the catalog.
- Each slot has one row, the **current version pointer**; every read and write goes through saveslot's API / restricted SQL compiler, which resolves a logical table name to the physical table the pointer points to.
- **While migrating**: build the new version's tables and indexes → replay from the log (with a small amount of data a full replay is possible, which also verifies that "the log can rebuild the state") → catch up in a loop of small short transactions,
  with the new version's derived tables maintained at the same time by the new rules → enter the switch when the remainder falls below a threshold.
  **The new version's tables under construction are (c)-class state** (an exception to K3): they can be discarded and rebuilt from the log, and building in batches corresponds to no new event; at the switch event they become (b): on replay, the new version's tables are built only when `apply` reaches the switch event.
  - **A deterministic conversion does not record per-row results**: the conversion expression is restricted SQL, uses the same allowlist as derivation rules (see ["Restricted SQL"](11-restricted-sql.md)), and its result is deterministic; it is recorded, with the compiled definition, in the "compile result" event. On replay, when `apply` reaches the switch event, it converts every write of the old version into the shape of the new version by the compiled definition (item by item, with state, interval and provenance unchanged; only items with a value are evaluated, and items that are empty, `no_value` or `uncovered` are carried over unchanged; at a position with no old value, only the constant form of `backfill` gives a value, and only fills rows that exist (rows that are not revoked, intervals where the entity exists; revoked rows and the intervals without a value that a revoke leaves are not filled), the positions that were filled are recorded in the switch event and replay follows the record (a later deletion does not fill again), adding a required field or changing optional to required must always give a constant (whether or not there are rows), and the constant and expression forms cannot be given together; in the first version a conversion expression refers only to its own field, for the rules see "Schema evolution · How deterministic conversions are replayed"). This is consistent with how derived tables work: computed results are not written into the log, and are recomputed by the rules.
  - **The switch event records verification information**: its content records the row count and the result checksum of each new-version table; on replay, if present, they are checked and are not used to generate anything. It is computed from user content and is content; once its input is deleted it is erased, and the check is skipped afterwards. If on replay a conversion result differs from the one at the time (a backend difference, a kernel defect), this is how it is discovered.
  - **Replayed by the changed fields**: a write event records only the fields involved in that request (in the old version's shape); when the new version is built, they are carried over one by one (through a deterministic conversion or a translation result), and a field unique to the new version is not overwritten by old writes.
  - **Deletion and deletion-cancellation events are replayed through conversion in the same way**: their field-by-field results are converted into the new version's tables through the deterministic conversion just like base writes. A deletion that was confirmed before the switch needs no special handling: the deleted content is already "removed by #n" in the log and is skipped in conversion; the "state after deletion" recorded in the deletion event becomes, through conversion, the current value of that row in the new version.
  - **A deletion confirmed while a migration is in progress**: the deletion event, as usual, counts only the result for the current version. The new version's table under construction discards the affected rows entirely and rebuilds them from the log (by then the deleted content can no longer be read); if the build has not finished when the physical erasure at expiry happens, the historical content of these rows in the table under construction is likewise cleared. In an extraction job the affected work items are sent back to be redone (see "Extraction jobs"; the first version does no extraction).
  - With an extraction job, the switch event states the list of (row, field) pairs not yet extracted, from which `apply` sets `pending_extraction`, without reading job progress; the migration result event includes the skipped work items and their reason codes (`no_content` / `ambiguous`).
  - **The translation of a re-extraction must be complete**: for every write that a work item involves, the translation must give the values of all the new fields that the cluster involves (a value may be empty, but it must be given explicitly); a missing one reports a validation error.
    Otherwise, for a write that touched only old fields, if the translation leaves out some new field, that new field would stay at an earlier value.
  - **Revoked rows are translated as usual** (history must be readable as of an instant), but do not go into the difference list: they have no effect on the current state.
- **Switch (one transaction)**: no `lock_timeout` is set and there is no automatic retry: the build batches and the switch transaction are both queued in the tenant's single writer queue and queue with user writes, with no other writer to contend with; reads take no locks, and building a new version's tables does not block reads. Catch up the last stretch; verify; change the pointer; record one schema switch event.
  At the start, the write transaction checks the version on the pointer: a write that carries the old version number is rejected here; reads are not affected at all.
- **Batches and thresholds**: each batch is one short transaction by number of log events (initial value 500), and writes queued between batches enter as usual; when the remainder is no more than one batch, the switch is entered; if the remainder has not decreased for 20 consecutive batches (writes are faster than replay), the switch is made directly, accepting that one longer pause: correctness does not depend on the thresholds, because the switch transaction itself catches up the last stretch. The three numbers are kernel constants, injectable in tests, and are placeholders awaiting the capacity experiment for schema rebuilds. If the process exits in the middle of a build: the next open finds "migrating", discards the orphaned new-version tables and builds again from the start; a verification failure (`verify_failed`) and a build failure (`build_failed`) are both not retried automatically, the old version stays current, and the caller can submit the same draft again.
- **A derived table computed at read time also has a physical table** (empty), and all read entry points bypass it with the same judgement; switching `change_rule` between computing at read time and caching follows the same path as any rule change: the new version creates a derived physical table as usual, when a cache becomes computing at read time the new table is empty, and when computing at read time becomes a cache the new table is rebuilt with the switch by the new definition, like any rule change (a derived table is not listed in `rebuilt_tables`, see [`../09-event-format.md`](../09-event-format.md) §5.5). The criterion is the time dependence of the rule: a derived table whose `time_dependency` is `now` is computed at read time.
- **Rollback**: before the switch, the new tables are discarded (change the state first, then delete, so that orphaned tables can be recognized after a crash); after the switch, only forward migration is done.
- Under hosting, the number of tables grows with "users × tables × versions", and the layout needs a load test (see the open questions).

### Extraction jobs

> **Extraction jobs are not in the first version**; they are the first increment after the first version ([`../07-scope-v1.md`](../07-scope-v1.md)); a place is reserved for them in the event format. This section is the complete design.

**Extraction jobs serve only schema changes**: re-extraction migrations and supplementary extraction for new fields (`reextract` declared on the field). They are first executed by the user's agent; the contract does not distinguish who executes, and later, once the user authorizes model calls, a background executor that calls a model (a worker) connects directly (positioning document, "Later plans").
For the shape of claiming and submitting, see the contract, "Extraction jobs"; below is the authoritative definition of the kernel rules.

**Flow**:

1. After the draft is compiled, the preview says "N sources need to be extracted again".
2. After the `schema_change` item is confirmed it enters migrating: the deterministic part is completed by saveslot automatically, and extraction jobs are generated at the same time; a migration whose results must go into the difference list (extracting from an old field, re-extracting the same field, see below) **generates one `migration_diff` item as soon as the migration starts**, and the difference list grows as extraction proceeds. It is not superseded by ordinary writes during the migration and is closed only when the migration ends; what each decision binds is in "Pending items · Item ID and item version".
3. Any caller with permission can claim and submit, and it does not matter if the work is not finished: the old version stays readable and writable as usual, and the work continues later.
4. When extraction is complete and all differences are handled, switch to the new version; one can also switch early with `keep_rest_and_switch`, or abandon the migration with `abandon` (see "Pending items · Execution semantics of each decision").
   **A migration without `migration_diff`** (only deterministic conversions, or deterministic conversions plus pure supplementary extraction) needs no one to handle differences: once saveslot finishes the deterministic part it switches, and **pure supplementary extraction does not block the switch** (what is not yet done becomes an ordinary supplementary extraction job by the switch rules below), so they do not stop halfway waiting for someone; they have no manual abandon exit, and on failure they roll back as a whole.
5. "Migrating" does not expire; if there is no progress for a long time, it is only escalated in the hints.

**What goes into the difference list**:

- **Extracting a new field from an old field** (`reextract.from` is not empty, such as splitting `feeling` into `effort` + `soreness`): the "old value → new value" of every row goes into the difference list, because the old field may be the user's own words and may have been corrected, and must not be quietly replaced by an inferred value.
  In the list, those whose old value has the source level "user stated" or was corrected are placed first, and the rest are convenient to accept in bulk.
- **Re-extracting the same field**: those that differ from the confirmed value go into the difference list.
- **Pure supplementary extraction** (`from` is empty): the new field is empty to begin with, and does not go into the difference list.
- Items skipped as `ambiguous` go into the difference list; a value can be given when they are handled, or written after the switch.
- Revoked rows still produce work items and are still translated (needed for reading as of an instant), but do not go into the difference list.

**During migration and at the switch**:

- A new write during migration that touches a `from` field **automatically appends a work item** (a hint in the receipt; the total number of jobs grows accordingly); the difference entries already listed for that row become void and are listed again after re-extraction (see "Pending items · No expiry").
- If at the switch there are still untranslated items (`keep_rest_and_switch`, or pure supplementary extraction), the new field is first left empty and marked `pending_extraction`, the switch goes ahead as usual, and the remaining items become supplementary extraction jobs after the switch, so that the last few do not block the switch. The original job ends and leases not yet handed in become void (a later submission reports `lease_expired`, with the reason `migration_switched`), and work items not yet handed in go back to the pool of the new job.
  **The remaining items still follow the difference rules of the original migration**: an item that should have gone into the difference list (extracting from an old field, re-extracting the same field) has its extracted result go into a newly generated `migration_diff` after the switch (the only decisions are `accept_all` / row by row; it closes after the remaining items are extracted and all differences are handled); before it is extracted, that place is empty and marked `pending_extraction`, and after it is extracted it is marked `awaiting`, waits for a person to confirm, and does not take effect directly; only items of pure supplementary extraction take effect directly (the new field was empty to begin with).
- At the switch, open items that involve the changed fields are all marked "superseded" (reason: the schema has switched), and the initiator rewrites them by the new version; other items are kept as usual.

**Work items: translating the original writes by source cluster**:

- **Re-extraction does not extract the source data from scratch again; it translates the writes that touched the fields to be re-extracted, one by one, into the shape of the new version, and saveslot then replays them in the original order.** Corrections, revokes and the valid intervals of state tables are all kept as originally meant, and `row_id` / `entity_id` do not change.
- **One work item = one source cluster**: all the writes on the same row (or the same entity) that touched the fields to be re-extracted, sorted by `seq`, with the original text of each one's source data and the old value at the time of writing. Rows are independent of one another and can be parallel.
- Each translation can give only new values; the intent, the row and the valid interval follow the original write, and the translator cannot change them.
- **Each translation must give all the new fields that the cluster involves** (explicitly an empty value where there is none); a missing field reports a validation error (see "The physical approach").
- A work item carries only the evidence related to the `reextract.from` fields (the evidence segments that these fields refer to in each write). A translation result is content, stored per work item × field, with provenance = all the original text that the work item carries; if any one of the original texts it carries is privacy-deleted, the translation result of that work item is erased as a whole (see "Deletion · Content derived from source data").
- **Supplementary extraction after deletion**: after a translation is erased, the (row, field) pairs that still have content in the remaining original text are listed by the deletion event and set to `pending_extraction`, and saveslot opens supplementary extraction jobs for them (the work items carry only the remaining original text); those with no remaining original text are set directly to empty. When a deletion happens during a migration, the affected work items (including translations already handed in but not yet switched) go back to the pool to be redone.
- A work item is assembled from the log when it is claimed and is not stored on disk; when a write has been deleted during a lease, the translation of it is refused and this item is deducted from the job.
- **Boundaries**: revert writes are handled deterministically by saveslot (taking the translation result of the version reverted to) and do not enter work items; for a write whose source data has had "evidence deletion", the work item has only the old value and no original text (reason `evidence_deleted`); supplementary extraction on a state table produces work items by valid segment (each segment may take a different value).
- **Supplementary extraction** (`from` is empty): a work item is one row (or one segment), carrying the original text of the sources that inserted and modified it, and produces the values of the new fields.
- Every submitted work item goes through the deterministic validation of writes; a skip has only the two reason codes `no_content` / `ambiguous`. The result is recorded as a log event at the "agent inferred" level (recording the connection of the extracting party and the model name it reports itself, for reference only), and replay uses the recorded result.
- Undecided: when a source cluster is too large (an import file produces a thousand rows that are each later corrected), split it by row and attach to each work item the relevant fragments of the shared source data; the splitting rules are undecided (the open questions, "Numeric values and details of the interfaces").

### The official schema and user schemas

The extension and mapping below are what is done once the structure is settled, and the first version does not implement them; the first version only reserves a place (the second item of this section).

- **Extension**: a user adds fields on top of the official schema, placed in their own namespace, with no field ID conflicts. Minor upgrades of the official schema that are backward compatible are followed automatically; major upgrades go through migration and preview.
- **The first version only reserves a place**: the optional key `extends` in the compiled definition (`{id, version, hash}`, recording only the identifier and the content hash) and `official` on tables and fields (`{id}`, a stable handle given by the official schema; field IDs are still assigned by saveslot, and tools above look up fields by `official.id`); no key is reserved for `compatibility` for now; these keys appearing in a draft report `not_in_this_version` (for the reserved places in the event format see [`../09-event-format.md`](../09-event-format.md) §10).
- **Mapping**: when a user builds tables entirely by their own structure, one L1 rule is written to project the user's data into the shape of the official schema; a plugin written for the official schema just reads this view.
  "Compatible with the official schema" is not a separate mechanism, it is just a derived view: read-only, recomputable, with complete provenance.

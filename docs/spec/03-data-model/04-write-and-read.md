## Writes: division of labor and requests

**The agent is responsible for "understanding"; saveslot is responsible for "gatekeeping".** The agent turns the user's words into a structured write request; saveslot does not understand semantics and only does deterministic checking, recording and execution.

### The write request

Take "I got the 11-03 run wrong, it was 5 km" as the example. **The model fills in only these** (field names and the full parameters are as in the contract "Writes: intents and ops"):

```yaml
sv: 3                                # the slot schema version obtained when reading / looking up the catalog, passed back unchanged
evidence:                            # the evidence segments; if absent, saveslot stores the request itself as source data
  - { kind: user_message, text: "I got the 11-03 run wrong, it was 5 km" }
ops:                                 # one write may contain several ops, in the same slot, as a whole one transaction
  - intent: correct                  # insert / update / correct / revoke
    table: runs
    row: r_01JC…                     # the row ID generated by saveslot, obtained when reading (left out for an insert)
    ver: v41.0                       # the version token obtained when reading, passed back unchanged
    set: { distance: { value: "5", unit: km } }
```

**Filled in by the server**:

| Content | Where it comes from |
|---|---|
| Connection | From the credential |
| Request key | See "Idempotency" |
| Source level | Derived from the kind of each evidence segment: the user's own words give "user stated", the rest "agent inferred"; the caller may declare a level on an evidence segment; "external authority" is not open in the first version (see "Source level") |
| Task identifier | Optionally passed by the caller |
| slot | Derived from the table |

- **Four intents**: insert / update / correct / revoke (revoke a row, keeping its history). **A correction must be marked explicitly**; on a state table, whether an update is "changing from now on" or a retroactive edit is decided automatically by saveslot from the valid-from point (see "Time · The effect of a change on earlier reads"). Privacy deletion is not a write intent; it is a separate operation (see "Deletion").
  An event table has no valid-from point: an "update" on it supplements or modifies information and does not trigger the query of affected reads; a value that was recorded wrong in the first place must use "correct".
- **The version mark should be passed back** (update, correct, revoke). When it is not passed there is a fallback, and only if there is no fallback either is `read_first` reported:
  - Use the version of that row most recently **read row by row** by **this connection** in read_log (if a task identifier was passed, only the same task counts), and the receipt states that it was obtained by fallback; if it was never read, reject (`read_first`) with the hint "read the row first". The new version of MCP is a stateless protocol, so the fallback relies on the read record in the data, not on a protocol session.
  - **Exception: an op by external key carries neither `ver` nor `row`** (carrying `ver` reports `invalid_argument` (`mutually_exclusive`)); the version seen is taken by the kernel as the sync baseline position of this field, the read record is not consulted, and `read_first` is not reported even if the row was never read (see "Writing by external key"). An op that adds a key to a row that has no external key is an ordinary `update` and carries `row` and `ver` as usual.
  - The `ver` of each declaration in the premises of a write uses the same rules (see "The premises of a write").
  - There are three kinds of **row-by-row read**: `query`; the **current version** in the `timeline` of `history` (for a single target); and **the `ver` already in effect in the writer's own write receipt**, since otherwise the same agent that changes a row twice in a row would conflict with itself when the second write carries no `ver`.
  - What does not count as a row-by-row read: what `history` reads with `as_of` is a past version, and the `ver` it returns is marked "historical version, not usable for writing" (otherwise every later write to the same field would be treated as concurrent, producing false conflicts); the result of `sql` carries no `ver` (and no row ID automatically either; to get the row ID, select it in the query), and the composition view of a derived value (`composition`) gives only row IDs, not `ver`; the `current_ver` (the version currently in effect) attached to the receipt of a write that became a candidate is for reference only and does not count as read.
- **The schema version should be passed back** (when it is not passed, the version of that slot most recently read by this connection is the fallback, and the receipt states it): only a request that writes "a field whose definition has changed incompatibly since that version" is rejected; if the written field has not changed, the request is accepted as usual (see "Schema version evolution").
- **A revoked row cannot be written** (event tables, timeless tables): an update or a correction reports `revoked`, with the write number of the write that revoked it, and the hint to use `revert: {undo}` to restore it; revoking again is a no-op. For revoking on a state table see "Time · Revoking on state tables".
- **Clearing an optional field**: write its value as `null`. This is a contribution and has a value source; a required field cannot be cleared (see "Field types, same value and units · Clearing a field").
- **How a value is validated, converted and rounded, and when two values count as the same**: see "Field types, same value and units".

The receipt has three statuses (consistent with the contract "Writes"), and the agent tells the user accordingly:

- **`saved`**: all fields have taken effect (or are a no-op); the new version plus the affected derived values (such as "W45 22 → 12"). It is also `saved` when a `flagged` item was generated.
- **`pending`**: some field entered awaiting confirmation (with the reason and the segment that would be overwritten), or was recorded as a conflict candidate (with the current value and the conflict item); within the same op, some fields may have taken effect and some not.
- **`job`**: turned into a background job (with the job ID). Not done in the first version.

**A rejection is not a receipt status; it is an error**: with a correction hint and the position of the error (which op, which field), such as "schema has been updated to v2". The whole request does not take effect.

#### Idempotency

A resend after an interrupted stream takes effect only once, and a write is not made twice after a crash either.

- **Request key**: computed from "connection + task identifier + the normalized request content". Normalization = the deterministic JSON encoding (RFC 8785) of the parameters as the caller originally passed them, not including the `ver` / `sv` obtained by fallback. **There is only one exception: it includes the resolved version seen of each premise** (including those obtained by fallback). "The premise changed again, check once more, and the request body is unchanged character for character" is the normal use of restating; without the resolved version, the second restate would be treated within the window as a replay of the first and return a stale result.
- **A request containing only ops by external key computes no server-side request key**: the external key itself makes a resend idempotent, and handing in the same content again gives `unchanged`, compared three ways item by item whether or not it is inside the window. An explicit idempotency key can still be used; when the request produced no event it is not recorded, and a resend is judged anew by external key. A request containing ordinary ops computes the request key as before (see "Writing by external key").
- **Explicit idempotency key**: when the caller gives an idempotency key explicitly, the request key = connection + that key, and a **request content fingerprint** is recorded separately, used to detect "the same key paired with different content".
- **The duplicate lookup is done in the same transaction**: the kernel matches only keys inside the idempotency window. The window is passed in by the service layer through the call context, and the kernel filters by `recorded_at ≥ now − window`, so the result is deterministic and replayable. The length of the window is a service-layer policy; the value is in the contract.
- **Only results that produced events are deduplicated**: a rejected write produces no event and is not deduplicated; on a resend it is validated again against the state at that time.
- **The request key and the content fingerprint are computed from content, so they are content**: they are recorded in the content of the logical write head, and are erased together when any evidence segment of this request is deleted (see "Deletion · Content derived from source data"). The task identifier and explicit idempotency key that the caller reports about itself are text written by the caller and are handled the same way.

**What is returned on a resend**: when the request key is matched, nothing is executed again, and the receipt carries `replayed: true`.

| What is in the receipt | On a resend |
|---|---|
| Write number, the per-field result of each op (status, value, interval), the `ver` obtained at the time, the IDs of newly created rows / entities, the IDs of the items generated or merged into at the time | Rebuilt from the log, the same as at the time |
| Affected reads (computed from the read record), the before and after values of derived values (a derived write records only a checksum) | Not rebuilt; the receipt lists what was omitted; read it yourself when needed |
| Items | Only the **current state** is given (open / resolved and the decision / superseded), not the item versions |
| The content of the original write is already in a confirmed deletion | The receipt says "the original write has been deleted and was not written again", and does not echo the content (see "Cancelling a deletion and the grace period") |

- The `ver` and the items in a resend receipt **do not count as "read"** and take no part in the fallback.
- A write entered awaiting confirmation and was later rejected; resent unchanged inside the window, the current state of the item in the receipt is "resolved · rejected", so the caller can see that the proposal has been rejected.
- **It really happened again** (two coffees at the same price bought within ten minutes): the request key computed by the server includes the original text of the evidence, so the two requests are the same only if they were produced from the same piece of evidence, and that is almost always a resend. When the evidence is identical character for character and it really is a new entry, the caller must pass a different explicit idempotency key; `replayed: true` means "no new write", and the tool description states it so.

#### The events that make up one write

One request appends the following events in the same transaction. The field-level definitions are in the event format specification ([`../09-event-format.md`](../09-event-format.md)); what is fixed here is which events there are, how many of each, and which sequence number is used externally.

In order of appending:

| Order | Event | How many | What it records |
|---|---|---|---|
| 1 | Logical write head | **One per request that produces events** | The request key and content fingerprint, `sv`, the total number of ops in the request, the **original parameters** of each op (for a field that is not a no-op: the value and unit the caller handed in; for a no-op field: only the field ID; the original form of the interval; the declared premises), the entry time `now` and `today`, whether `ver` and `sv` were passed explicitly or obtained by fallback (for an op by external key: the baseline position of each field), the rule version and the policy version |
| 2 | Source data | One per evidence segment; when no evidence was passed, one "API call" per op that left something in the events (including the restating and clearing of premises) | The original text of the evidence or the file reference |
| 3 | Base write | Op by op: one for each row / entity affected by each op | The fields this request touches that are not no-ops. **The contribution of a field is a number of items ordered by interval** (always one item for event tables and timeless tables), each with its own: the effect status (see the table below), the value that is applied, the **resolved interval** (state tables), the provenance, the literal match; a candidate also records the interval seen |
| 3 | Pending item | Right after the base write of the op that brought it out: one each for produce, merge into, refresh, supersede | See "Pending items" |
| 4 | Premise change | After all base writes and item events: one when there is a change | Which declarations turned to changed, and which turned back to unchanged (see "The premises of a write") |
| 5 | Derived write | After all ops: one for each derived row whose result changed | See "Derivation rules" |

- **Write number**: the `seq` of the logical write head. It is the first event of this operation, so every sequence number this write exposes externally uses it: the `seq` of the receipt, the number in `ver`, the #n of `timeline`, the n of `undo`, the recorded-time interval of the version table (see "Numbering"). The `seq` of the other events is not exposed.
- **A base write records neither the value before the write nor the whole row after it.** The state after the write = the state before + the items in this event that have taken effect; for a state table, the value of each item is assigned to its resolved interval, and then adjacent instants whose fields are all equal are grouped into one segment. These two steps are deterministic and contain no judgement. Every extra copy of a value stored is one more place that privacy deletion has to clear; reading by instant goes through the version table.
- **The effect status of each item** (a field usually has one item; the cases with several items are: `undo` or reverting to the merge base writes back several segments of different old values; in an interval that is corroborated, one part still has the same value and another part has been changed by someone else; `undo` reverts only the part still in effect):

  | Status | Meaning | How `apply` applies it |
  |---|---|---|
  | `applied` | In effect | The business table, the version table, the provenance table |
  | `corroborated` | Same-value corroboration: the value did not change, a provenance was appended | Only the provenance table |
  | `candidate` | A conflict candidate | Not applied; used by `timeline`, items and deletion replay |
  | `awaiting` | High-impact, awaiting confirmation | Same as above |

- **A no-op field is not a contribution** (the same value as the version seen, and no evidence pointed to): it is not in the base write event, **its value is left nowhere in the log**, and the logical write head lists only its field ID. Its result in the receipt is `noop`. The reason the value is not kept: this value was read back by the caller from saveslot and carried unchanged, and its source is an earlier contribution; keeping a copy would add one more place that cannot be erased when that contribution is privacy-deleted.
- **A write that has not taken effect is still recorded as a base write event.** The later adoption or confirmation is a new write triggered by `resolve` and belongs to that resolve operation (the head event is the resolve event, and the operation number is its `seq`); the value source is a reference to the original candidate / proposal contribution.
- **The resolution result is the one most recently given**: the interval of a contribution and the first-creation mark of a write are mechanical judgements, and the replay of a privacy deletion may change them; the new result is recorded in that deletion event (see "Deletion · How the result lands in the log").
- **A request whose fields are all no-ops**: the source data is stored as usual, and the logical write head is recorded (with the request key and the list of IDs of the no-op fields; a resend is replayed by idempotency); no base write event is recorded; `ver` is unchanged; the receipt is `saved`, with `noop` for each field. Evidence is an asset and is not dropped just because no value changed. It is different when `undo` is skipped entirely: the base write event is recorded as usual, containing only the revert record and no written-back item, and `ver` is unchanged (see "Reverting"). The restating and clearing of premises also have no base write; the event composition is the same, with the declarations added in the head event.
- **Exception: an op by external key that is unchanged or skipped enters no event at all** and appears only in the receipt; when all ops in a request are of these two kinds, this request **appends no event**: no logical write head, no source data, no request key, and the receipt is still given, without a `seq` (see "Writing by external key").
- A request-level evidence segment that no op references is still stored as source data (a `source_ref` segment adds no source data), and `warnings` in the receipt gives a reminder (`evidence_unreferenced`).

#### The order of judgement

Each op goes through the following steps in a fixed order.

| Step | What is judged | Result |
|---|---|---|
| 1 | Checks that are independent of the current state: `sv` compatibility, type, unit dimension, range, required fields on an insert | If not passed, an error is reported and the whole request does not take effect |
| 2 | Request-key duplicate lookup (a request containing only ops by external key has no server-side request key and only the explicit idempotency key is looked up). When there is no match, the source data that `source_ref` in the evidence refers to is checked (once for the whole request, ordered before the `sv` / `ver` fallback and `read_first` of each op; see the contract "Evidence") | A match returns the original result; a reference that does not hold reports an error and the whole request does not take effect |
| 3 | Same value: fields equal to the version seen (see "Deletion · Provenance"); an op by external key is compared with the baseline value | No-op, or corroboration |
| 4 | `ver` and conflict (see "Conflict handling · Conflict criteria"); for an op by external key the version seen is the baseline position of this field | The conflicting part becomes a candidate, and a conflict item is generated or merged into |
| 5 | Checks that depend on the current state, **done only for the part that is about to take effect**: an interval without a value must carry all required fields, the target of `ref`, a revoked row. The targets of premises are also validated in this step, but for all declarations carried by this op, whether or not the op takes effect (see "The premises of a write") | If not passed, an error is reported |
| 6 | High-impact (see "Time · High-impact writes") | Enters awaiting confirmation |
| 7 | Suspected duplicate (see "Suspected duplicates") | Takes effect as usual, and a "flagged" item is generated |

An op by external key first locates the row after step 1 (whether the key is in the key index): when it hits a revoked row, or when the key is held by a deletion inside its grace period, this op is skipped and does not go further; steps 3 and 4 each swap one input and the rest is unchanged (see "Writing by external key · Three-way comparison").

Step 5 comes after the conflict judgement for symmetry: when a write carrying an expired `ver` meets the other side's revoke, both arrival orders should become a candidate, rather than one order reporting an error. A write that became a candidate is no longer judged high-impact separately; the segments it would overwrite if it took effect are listed in the impact of the conflict item. For the estimation for write admission see "Derivation rules".

#### Several ops in one request

- Ops are executed in the order they have in the request, and a later op sees the result of the earlier ones.
- For a row / entity newly created in this request, a later op does not need `ver`. The common case is creating a budget entity and writing two segments at once.
- For a row / entity that existed before the request, the `ver` (or fallback) carried by each op in the same request means "the version seen at the start of the request"; the conflict judgement compares only writes from outside the request after that version, and the earlier ops of this request do not count.
- The baseline for the same-value judgement: the version seen plus the results of the earlier ops of this request.
- **The high-impact judgement likewise adds the results of the earlier ops of this request**: the protection range of (1) includes the change points that the previous op has just produced (see "Time · High-impact writes"); when (2) counts "still referenced", a referencing row that was already revoked by an earlier op of this request counts as no longer referencing (see "Reference fields"). So "first revoke three line items in one request, then revoke the meal they belong to" completes in one go and does not enter awaiting confirmation; in the reverse order, when the meal is revoked its line items still reference it, and it enters awaiting confirmation. The order of ops affects the result; this does not conflict with "the arrival order of two requests does not affect the result": that rule is about requests among themselves.
- **When the same external key appears twice in one request, the whole request is rejected** (`invalid_argument` (`duplicate_external_key`), with the indexes of the two ops): letting the later op see the result of the earlier one would give "two candidates from one write" on the same conflict unit, for which items, adopting a candidate and the merge base are not defined (see "Writing by external key").
- The whole request shares one write number, and the same row / entity gets only one new `ver`.
- Each op is judged independently: one op becoming a candidate does not affect the other ops in the same request taking effect. The atomicity of the request means that the events are committed together.

#### Reference fields (`ref`)

The value of a `ref` field is the ID of a row or an entity in a table of the same slot (which may be the table the field is in). **References do not cascade**: when the target is gone, the referencing row is not changed along with it.

| When | Rule |
|---|---|
| When a `ref` field is written | The target must exist, be in the table that the schema declares, be unrevoked, and not be in a confirmed deletion; when it points to a state entity, the entity must have a value in at least some valid time. Otherwise `validation_failed` (`ref_not_found` / `ref_wrong_table`) is reported. A target outside the visible range is the same as one that does not exist and reports `ref_not_found`; `ref_wrong_table` is reported only when the target is visible, since otherwise "this ID exists elsewhere" would leak out through the error code. This is a check that depends on the current state (step 5 of the order of judgement) and examines only the part that this write is about to make take effect: an item of this operation whose status is in effect and that gives this field a non-empty value, whether written directly or written back by a revert (`undo`, confirming an undo) or by reverting to the merge base (`take_previous`); same-value corroboration, a no-op, a written-back item that carries no content, and writing back "no value" are not included (restating an existing value does not count as writing a `ref` field; when the target is later revoked the referencing row keeps its original value and carries `dangling_ref` when read); a part that became a candidate or entered awaiting confirmation is checked when it is adopted or confirmed (`resolve`). So one write cannot create a reference to a revoked target, and a dangling reference comes only from the target being revoked or deleted later. "Now" includes the earlier ops in the same request |
| The target is revoked | Revoking a row that is still referenced is high-impact (2) and enters awaiting confirmation (see "Time · High-impact writes"). After confirmation the referencing row is not touched and keeps the original ID; when read, this row carries the `dangling_ref` flag (target revoked). Once the revoke is undone by `undo` the flag disappears by itself |
| The target is deleted as a whole row by privacy deletion | It is not blocked by being referenced. The referencing row is not touched and keeps the original ID (a row ID is an opaque identifier, not deleted content); when read, this row carries the `dangling_ref` flag (target deleted). The deletion preview lists separately the rows that still reference the deleted row |
| The referencing row passes the same ID back unchanged | Same value, handled as a no-op or corroboration, and the target is not validated again |

- **How high-impact (2) counts "still referenced"**: after the current version is combined with the results of the earlier ops of this request, an unrevoked row whose `ref` field has a value in effect pointing at the target (state tables: a pointing from any segment counts). A referencing row already revoked by an earlier op of this request counts as no longer referencing. References in candidates or in awaiting confirmation do not count.
- Cascade deletion would let one revoke or deletion reach rows the user did not name, and nulling would amount to changing a value on the user's behalf; keeping the ID plus a flag at read time loses no information and leaves the decision to a person.

#### Suspected duplicates

A schema may declare `duplicate_keys` for event tables and timeless tables: one or several groups of fields, "two rows in which these fields are all the same were most likely recorded twice". It is a soft criterion: a hit is only flagged and does not reject the write. A state table recognizes an entity by `entity_key` and cannot declare it.

| Question | Rule |
|---|---|
| When it is judged | Only on an **insert** that has taken effect. An update or a correction that makes a row the same as another row is not judged. For writing by external key, a newly inserted row is judged as usual, and a hit on an existing row is not an insert and is not judged |
| Compared with what | The values in effect of the rows in the current version of the same table that are unrevoked and have not been taken away as whole rows by a confirmed deletion (a row from which only some contributions were removed is compared by its values after the deletion), including rows newly inserted by earlier ops of this request. Values in candidates or in awaiting confirmation are not compared |
| What counts as a hit | Every field of some group of keys has the same value (the criteria are in "Field types, same value and units"); if either side is empty on a key field, it is not a hit. A hit on any one of several groups of keys is a hit |
| After a hit | The write takes effect as usual, and the receipt is `saved`. For each newly inserted row a `flagged` item is generated, listing the rows hit (at most 10, ordered by most recent write) and which group of keys was hit |
| How it is handled | `keep`: keep, and the flag is removed; `revoke`: revoke the flagged row |
| When the item closes by itself | The flagged row is revoked or privacy-deleted; or it and the listed rows no longer hit (see the `flagged` exception in "Pending items · No expiry"). "No longer hit" has the same definition as "hit": two rows count only if they do not hit on any group of keys; if the recorded group no longer hits but another group still hits, the item is not touched. When a row that was hit is revoked or changed and the item is superseded or refreshed because of it, the reason is recorded as `matched_changed`; judging a suspected duplicate does not look at whether the writer has read the rows, so an item of this kind carries no "the writer has read" entry |

**It and the external key do not replace each other**, and both may be declared at the same time: the external key answers "is this the same record in the source system", a hard locating; `duplicate_keys` answers "were these two rows recorded twice", a soft reminder that also works across sources (the agent records a meal from the user's words, and the connector then syncs the same meal). When a hand-recorded row and a synced row have been recorded twice, `keep` means counting the same thing twice; to let the source's changes reach the hand-recorded row, in one request first revoke the synced row, then add the key to the hand-recorded row (see "Writing by external key · Adding keys to rows that have none"). The first version does not do transfer: doing so reports `not_in_this_version`; what can be done in the first version is to add the key to the hand-recorded row before the synced row appears.

The judgement result is recorded in the base write event, is not judged again on replay, and **is not recomputed at privacy deletion either**: it is a reminder given to the person at the moment of the write and is not part of the data. So deletion does not generate any new `flagged` item; when the flagged row or a row it lists is deleted as a whole row, the item closes by itself per the table above.

#### Rule version and policy version

The results of mechanical judgements are written into events and not recomputed on replay; but privacy deletion has to recompute these judgements against the state after the deletion (see "Deletion · Replay rules"). The rules of judgement will change in the future, so every judgement records which version it used.

| Version number | Range | What it identifies | When it increases by 1 |
|---|---|---|---|
| Policy version | Per slot | The content of the slot policy: the rules for the value in effect during a conflict, the rank table, the extra list of high-impact items (see "What a slot contains") | Each time the slot policy changes |
| Rule version | Per kernel | The semantics of all mechanical judgements: stop points, same value, conflict criteria, high-impact criteria, the existence of rows / entities, the checker of literal match | Whenever any one semantics changes. It is 1 in the first version |

- **Where it is recorded**: each logical write head records the two numbers used when this write was judged; the produce and merge-into events of conflict and awaiting-confirmation items record the same two numbers; the deletion confirmation and cancellation events record the rule version used in the recomputation. The two numbers contain no user content.
- **Which version a deletion replay uses**: each old write is recomputed with the two versions **it recorded itself**. An old item is not re-judged because of a kernel upgrade or a policy change.
- To have an old item use the new policy, an explicit **re-judgement event** triggers it (a log event, with the result visible). The first version has only one rule version and produces no re-judgement event; the event type is reserved. Before the kernel stops keeping the implementation of some old rule version, a re-judgement must first be made for the writes that still use it.

### Writing by external key

**An event table or a timeless table may declare an external key (`external_key`) in its schema: the identifier of the record in the source system. When writing by external key, an existing row is updated and a missing one is inserted; the judgement is a three-way comparison of "the value handed in last time, the current value, the value handed in this time"; a sync in which nothing changed leaves no event at all.** It is made for connectors: a program that regularly moves data from an external system in, writing as a connection, handing in the same batch of records again at every sync; it has not read the rows it writes and cannot pass back `ver`. With `duplicate_keys` alone, syncing once an hour would mean several hundred "flagged" items a day, and every record would really be written again as an extra row.

- **Not chosen: "the connector looks up first, then writes"**: splitting "found nothing" and "insert" into two calls still duplicates when two sync processes run concurrently, and costs every record one more read.
- **Not reusing `entity_key`**: if it were opened up unchanged to these two kinds of table, the connector would either have to read each record once first (otherwise `read_first`) or rely on a fallback to get a version that has nothing to do with "whether the source changed"; and after a revoke, writing by key again would write the row back. Once all these points are changed, the keys of the same name on the two kinds of table would have two sets of semantics.
- **Not open to state tables**: they already have `entity_key`, and how a write that assigns values by time period corresponds to "the value handed in last time" needs a separate design.

The declaration of the key (`external_key` on the table, 1–4 fields of `text` / `enum` / `integer`, which cannot be in a field group) and the schema changes are in "Schema document format" and "Kinds of change and means of migration". The two rules used when writing:

- **The uniqueness range is per table.** In one table, rows whose key fields all have values and that have not given up the key have pairwise different key values. A revoked row still holds its key, unless its key has been transferred to another row (see below). A row with an empty key field has no external key and takes no part in uniqueness. It is not divided by connection: scope and slot range cannot be changed once issued, and re-issuing yields a new connection, so if it were divided by connection, after a re-issue every one of the same external records would be inserted again as a duplicate. IDs from different source systems can collide; they are told apart by a field in the key meaning "which system it comes from", declared by the schema author.
- **Key fields can only be given through `external_key`** (inserting by external key, or adding a key once to a row that has none), and cannot be changed afterwards: a key field appearing in `set` with a value different from the one on the row reports `invalid_argument` (`key_field_changed`). Key values are compared by the same-value criteria (for `text`, identical code point by code point after NFC, without trimming whitespace and without case folding).

#### How it is written and how rows are located

```json
{ "ops": [
  { "intent": "update", "table": "meals",
    "external_key": { "origin": "band_app", "external_id": "m-20261110-2" },
    "set": { "eaten_at": "2026-11-10T12:30:00+08:00", "energy": { "value": "650", "unit": "kcal" } } } ] }
```

- **How the op is written**: `external_key` gives the values of all key fields (a missing one, or `null`, reports `invalid_argument` (`missing`)); the intent is `update` or `correct` (a `revoke` op, or an op with `revert`, that carries `external_key` reports `invalid_argument` (`mutually_exclusive`)); **it carries no `ver`** (carrying one reports `invalid_argument` (`mutually_exclusive`)); it carries no `row`; it cannot carry premises of a write (`invalid_argument` (`premises_with_external_key`)). Using it on a table with no declared external key reports `invalid_argument` (`no_external_key`).
- **`insert` cannot carry key fields**: a key field appearing in `set` reports `invalid_argument` (`insert_with_external_key`), with the hint to use `update` by `external_key` instead. Otherwise the same key could be inserted twice, and "update if it exists" would have no unique target.
- **When the same key appears twice in one request, the whole request is rejected** (`duplicate_external_key`, see "Several ops in one request"). This happens when a connector's pages overlap; deduplicating on the connector side is one line of code.
- **A temporary name `as` may be carried**: when inserting, it is bound to the newly allocated row, and when an existing row is hit, to the row hit; later ops in the same request may use it to write `ref`. When both tables "document + line items" are synced by the connector, one request can write it all. When this op is skipped, the temporary name binds to no row: a later op that uses it to write `ref` is skipped as well if it is also an op by external key (`skip_reason: "ref_skipped"`); if it is an ordinary op, `validation_failed` (`ref_not_found`) is reported because the `ref` target does not exist.
- **Locating**: the kernel looks up the row by key value in the key index. Each op by external key has an `outcome` in the receipt:

| What is found | `outcome` | How it is applied |
|---|---|---|
| Nothing | `created`: a row is inserted and a row ID is allocated | An ordinary insert: `set` must carry all required fields, and the value source of the key fields is the evidence of this write; the suspected-duplicate judgement is made as usual |
| Found, the row is unrevoked | `updated` (at least one non-key field took effect or became corroboration, and other fields may have become candidates) / `unchanged` (all fields are no-ops) / `pending` (no field took effect, and some became candidates or entered awaiting confirmation) | See "Three-way comparison" |
| Found, the row is revoked | `skipped` (`revoked`, with the write number of the write that revoked it) | Nothing is applied; see "Revoked rows do not come back" |
| Found, but this key is held by a deletion inside its grace period (or frozen) | `skipped` (`pending_deletion`, with the deletion ID) | Nothing is applied; see "Deletion · Cancelling a deletion and the grace period" |

- The rule for the receipt's `status` is unchanged: it is `pending` when some field became a candidate or entered awaiting confirmation, otherwise `saved`. `skipped` does not affect `status`; a separate warning `external_key_skipped` is given (listing the indexes of the skipped ops); the receipt also gives the counts of the five outcomes of ops by external key.
- After a row is created, it can still be written by `row` + `ver` (the agent reads the row and changes a field); that is an ordinary write, and the rules are unchanged.
- **The result of locating is recorded in the event** (the row ID is metadata); `apply` applies according to the row ID in the event and does no locating. When replayed from an empty store or on another backend, every op that entered an event lands on the same row.

#### Adding keys to rows that have none

There are two situations: the user first had the agent record an entry by hand, and the connector later syncs the same record from the source; adding the external key to the hand-recorded row makes the sync hit it and not insert a new row; or both rows are already in the store (one hand-recorded, and one inserted by the sync); revoke the synced row, then **transfer** its key to the hand-recorded row.

```json
{ "intent": "update", "table": "meals", "row": "r_M…", "ver": "v41.0",
  "external_key": { "origin": "band_app", "external_id": "m-20261110-2" } }
```

- **How it is written**: an ordinary `update` (carrying `row` and `ver`, and it may carry `set` to change other fields at the same time, and may carry premises), with `external_key` added. Only this form may carry `row` and `external_key` together.
- **Conditions**: the row is unrevoked and none of the key fields has a value. When the row already has a key: the same as the existing key is a no-op, a different one reports `invalid_argument` (`key_field_changed`).
- **The state of this key in the key index determines the result** (from top to bottom, the first one that holds):

| State of the key | Result |
|---|---|
| **Frozen**: there is a deletion inside its grace period that would remove the contribution of this key on any row (the row holding it, or the original row before it was transferred) | `invalid_argument` (`external_key_in_use`, with the deletion ID). While frozen, every sync op by this key is skipped (`pending_deletion`) |
| Not held | It is added |
| Held by an **unrevoked** row | `invalid_argument` (`external_key_in_use`, with the ID of the row holding it; that row is in the same table and was visible anyway). To transfer, revoke it first |
| Held by a revoked row, and the key of that row was **there from creation** (a row inserted by external key) | **The key is transferred to this row**, and the revoked row no longer holds the key. The values of its key fields remain on its own row (key fields cannot be changed), but it takes no part in uniqueness and is not in the key index. The event records which row the key was transferred from |
| Held by a revoked row, and the key of that row was **obtained by adding a key** (including by transfer) | `invalid_argument` (`external_key_not_transferable`, with the ID of the row holding it). **No chained transfer** |

The first version does not do transfer: when the key is held by a revoked row (the last two rows of the table above), `not_in_this_version` is always reported (`param` points to `ops/<i>/external_key`); when transfer is opened up, it will be split into the transfer itself and `external_key_not_transferable`.

- Both "frozen" and "held by a revoked row" include a revoke that an earlier op in the same request has just made (a later op sees the result of the earlier ones). So the way to match two rows is one request with two ops: first revoke the duplicate synced row, then add the key to the hand-recorded row. The first version does not do transfer, and this usage reports `not_in_this_version`.
- **Why no chained transfer**: if a transfer chain A → B → C were allowed, deleting the middle addition of a key would have to answer "to whom does the key go back", and every row on the chain could be considered to hold the key at the same time. Letting only a row that had the key from creation give it up keeps the length of a transfer chain always 1: the holder is either the original row or the one row that added the key. A new reason code is used rather than `external_key_in_use`: the remedy for that code is "revoke the row holding it first", and here the revoke has already been done and would not help.
- **Why it freezes while a deletion is open**: a deletion inside its grace period may be cancelled or may be executed at expiry; under the two outcomes the key should land on different rows. During the freeze there is no transfer and no sync hit; once it expires or is cancelled only one outcome remains, and the holder is then decided by it.
- **Effect**: the value of the key fields is applied as an ordinary contribution of this write (in effect, with the evidence of this write as its source), and the entry of the key index points to this row. A key can be added only once: after it is added, the key of this row cannot be changed, and after it is revoked it cannot be transferred out again. This does not relax the reason for "keys can only be added on new fields": the key fields being added originally have no value on this row, so there is no case of "privacy deletion makes it fall back to an old value that is already held".
- **No coming back**: after the key is transferred away, a sync hits the row that added the key; the revoked row is no longer hit by any sync and so is not brought back by a sync.
- **A revoked row that gave up its key cannot exist again**: any write that would make it exist again (an `undo` of that revoke, a revert with `include_later` that reverts that revoke along with others, confirming such an awaiting-confirmation revert) reports `invalid_argument` (`external_key_transferred`, with the ID of the row that now holds this key) when it takes effect. Otherwise it would come back with the same key and there would be two rows with the same key in one table. During the freeze it still counts as having given up the key.

**How the holder is decided** (the key index is maintained accordingly; a key has at most one entry in the key index, and the state is "present" or "frozen"):

1. When there is no transfer: the holder is the row whose value in effect of the key fields equals this key and that has not given it up (including a revoked one).
2. When there is a transfer (the addition of a key on some row records that the key came from row S): the transfer is premised on the **contribution of the key field item in the same write that added the key still being there**. While it is there, the holder is the row that added the key, and S does not hold the key; after a deletion **executes** and removes that contribution, the transfer no longer holds, and the holder goes back to S (if the key contribution of S is still there; S is still revoked), otherwise this key has no holder. After the key goes back to S, it **no longer counts as "the key was transferred in"**: a sync op by this key after the key was added, in a deletion replay, hits the revoked S and is handled as "Revoked rows do not come back", restated as no longer a contribution (`dropped`), and does not reuse the baseline from when it was transferred in.
3. When there is a confirmed, unexecuted deletion that would remove any one of the key contributions in items 1 and 2, the entry is "frozen" and the holder is still computed from the state before the deletion. The entry records **all** such deletion IDs (a set): cancelling one of them only removes it from the set, and if the set is still not empty it stays frozen; only when the set is empty does it unfreeze, with the holder unchanged; when one of them executes, items 1 and 2 are recomputed from the state after that deletion, and the remaining deletions still keep it frozen. One deletion may also freeze several keys at the same time.
4. The row that added the key is the holder, and its key cannot be transferred again, so at any moment there are only two candidates, S and the row that added the key, and item 2 picks only one of them.

**Transferred keys, `undo` and deletion**:

| Situation | Result |
|---|---|
| `undo` of the revoke of the original row (the key has been transferred out, frozen or not) | Rejected, `external_key_transferred` |
| `undo` of that key addition | The external key fields enter no revert record, so a revert cannot touch the key: the key stays on the row that added it. If that key addition did not change other fields, "no change that can be undone" is reported |
| Privacy deletion of the evidence of that key-adding write: inside the grace period | Frozen: no transfer, and a sync by this key is skipped; the holder is still the row that added the key, and the original row still counts as having given up the key (an `undo` of its revoke is still rejected) |
| Same as above: cancelling this deletion | This deletion no longer freezes it; when no other unexecuted deletion freezes it, it unfreezes and goes back to the state before the deletion: the row that added the key holds the key |
| Same as above: executed at expiry | The row that added the key loses the external key; the holder goes back to the original row (revoked, holding the key as usual). Later syncs hit the original row and are skipped; the original row had the key from creation and can be transferred once more; an `undo` of its revoke is no longer rejected, it comes back with the key, and the row that added the key no longer has a key |
| Privacy deletion of the evidence from which the original row got its key: inside the grace period | Frozen in the same way |
| Same as above: executed at expiry | The original row loses the key value (or the whole row is deleted); the row that added the key still holds the key. If the evidence of that key addition is later deleted too, this key has no holder |
| The revoke of the original row | It is a human decision, and deletion replay follows the record; a deletion does not make the revoked original row exist again |

**Example** (table `meals`, key K = `(band_app, m-2)`, the connector carries no evidence each time):

| Operation number | Who | Request | Result |
|---|---|---|---|
| #30 | Connector | Write `eaten_at` and `energy` 650 by K | `created`: r_S. K → r_S |
| #40 | Agent | The user says "had a chicken breast salad for lunch, about 600 kcal"; `insert` one row | r_M, `energy` 600; a suspected duplicate hits r_S, and a "flagged" item is generated |
| #45 | Agent | The user: "these two are the same meal, keep the one I recorded". One request with two ops: revoke r_S; add key K to r_M | The latter op sees the result of the former: K is held by r_S, which is revoked and had its key from creation, and there is no freeze → transferred to r_M. K → r_M (the first version does not do transfer: this step reports `not_in_this_version`, and from here on the example shows how it looks once transfer is opened up) |
| — | Connector | The same record, 650 | Hits r_M: the baseline value of `energy` carries over from r_S as 650, the same as it → `unchanged`, and r_M stays at 600. No event is appended |
| #60 | Connector | The same record, the source changed to 700 | Hits r_M: 700 differs from the baseline value 650; nobody has changed `energy` since baseline position #45 → `updated`, and r_M becomes 700 |
| — | Agent | `undo` the revoke of r_S by #45 | Rejected: `external_key_transferred` (K is on r_M) |
| — | Agent | Revoke r_M; then add key K to another row r_Z | Rejected: `external_key_not_transferable` (K is on the revoked r_M, obtained by adding a key) |

At every step K has at most one entry in the key index, and at most one holder row.

#### Three-way comparison

The connector has not read the row and cannot pass back `ver`; all it knows is "what the source system now says this record is". So the judgement compares three things: **the value handed in last time by external key** (the baseline), **the current value in effect**, and **the value handed in this time**. The "sync contribution", the "sync contribution in effect" and the per-field **sync baseline** (the baseline value and the baseline position, including carrying over the baseline value of the original row when a key is transferred in) are part of the conflict criteria, defined in "Conflict criteria" and not repeated here. The main points: a candidate is also a sync contribution and counts toward the baseline value; an item written back by reverting to before the conflict or by `undo` is not a sync contribution; a sync contribution that has been reverted is no longer in effect and does not count toward the baseline position; the baseline is taken per field, not per conflict unit. Key fields are not in it.

The judgement is "The order of judgement", with only two inputs swapped:

| Step | Ordinary write | Write by external key |
|---|---|---|
| Same value (step 3) | Compared with the value on the version seen; the same value with evidence pointed to is corroboration, otherwise a no-op | **Compared with the baseline value**. The same as the baseline value → the source did not change: **whether or not evidence was pointed to**, when the current value in effect differs from it, it is always a no-op (not proposed again); when the current value in effect is also the same as it, pointing to evidence makes it corroboration and not pointing makes it a no-op. A field with no baseline value is compared with the value at the baseline position, with the same rule as an ordinary write (mostly the case when a row that had a key added is hit by a sync for the first time; except where the key was transferred in, see above) |
| `ver` and conflict (step 4) | Version seen = the `ver` passed back or obtained by fallback | **Version seen = the baseline position of this field**. The criteria after that are unchanged: if the conflict unit of this field was changed by another operation after the baseline position → a candidate, and a conflict item is generated or merged into; if not changed → takes effect |

Case by case (for one field, 600 handed in at the last sync):

| Current effective value | Handed in this time | Result | Explanation |
|---|---|---|---|
| 600 | 600 | No-op | The source did not change. The most common case, and it produces no base write event |
| 600 | 650 | Takes effect | The source changed and nobody touched it locally |
| 500 (the user changed it in saveslot) | 600 | No-op | The source did not change. **The user's change is not overwritten by every sync** |
| 500 (the user changed it) | 600, with evidence pointed to by `evidence_by_field` | No-op | Same as above: it is the same as the baseline value, and pointing to evidence does not propose it again |
| 600 | 600, with evidence pointed to | Corroboration | The source did not change and nothing changed locally: the evidence handed in this time is added as a provenance |
| 500 (the user changed it) | 650 | Candidate | The source changed and it was also changed locally: not overwritten, recorded as a candidate, and a conflict item is generated |
| 500, and the 650 candidate from the previous line is still open | 650 | No-op | The baseline value is already 650 (a candidate is also a sync contribution). **The same candidate is not merged in again at every sync** |
| 500, the conflict for 650 was resolved as "keep the value in effect" | 650 | No-op | Same as above: the baseline value is 650 |
| 650 (the conflict for 650 was resolved as "adopt the candidate") | 700 | Takes effect | The item carried over at adoption is a sync contribution in effect, and the baseline position moves forward to that resolve |
| 500, the conflict for 650 was resolved as "keep the value in effect" | 700 | Candidate | The source changed again, so a person is asked once more |
| 500, the conflict for 650 was resolved as "revert to before the conflict" | 650 / 700 | No-op / candidate | The written-back 600 (the value on the merge base) is not a sync contribution: the baseline value is still 650 and the baseline position does not move. **A source value the user has rejected does not take effect directly at the next sync** |
| 600 (the 650 written by one sync was reverted by `undo`) | 650 / 700 | No-op / candidate | The reverted 650 still counts toward the baseline value; it is no longer in effect, and the baseline position goes back to the earlier sync, after which comes this `undo` |

- **Intent**: `update` is the default form (the record in the source system is now like this); when the connector knows explicitly that the source system marked it as a correction it may write `correct`, and when the value takes effect the query of the reads affected by the correction is triggered as usual. When inserting, the intent is recorded as it is, and a creation mark is recorded separately, in line with how an entity is created by `entity_key`. An `update` on event tables and timeless tables does not trigger the query of the reads affected by the correction, so a routine sync does not flag the tasks that have read these rows.
- **Nothing is left when the content is identical**: for an op whose fields are all no-ops, the `outcome` is `unchanged` and the `ver` of the row is unchanged; this op enters no event, and no source data is stored for it. When all ops in a request are `unchanged` or `skipped`, this request appends no event, and the receipt is still given (see "How it is recorded in events").
- **Key fields**: when hit, the key value is the same as the one on the row, which is an ordinary no-op, **records no corroboration**, and takes no part in the sync baseline. A key field has a contribution only in the write that obtained the key (inserting by external key, or adding a key); once the source data of that write is deleted, the key disappears with it (see "Deletion · After deletion"). Later syncs are not allowed to record corroboration for key fields in order to hold up the key: that would help only when every required field happens to have been changed, but it would bring key fields into the sync baseline and the revert record, creating a path to two rows with the same key.
- **A handled conflict cannot be undone and reopened**: after an item is handled (including "keep the value in effect"), the first version has no way to bring it back to open. "Keep the value in effect" triggers no write, so there is nothing to `undo`; a write triggered by adopting a candidate or reverting to before the conflict can be undone with `undo` and the value goes back to what it was before the handling, but the item stays resolved. Hence a source value that the user rejected by "keep the value in effect" or "revert to before the conflict" is not proposed over and over by later syncs; this is exactly the purpose of the baseline value including candidates. If the user changes their mind and wants that value, write it directly (an ordinary write, not a sync contribution, and the baseline is unchanged).
- **Conflict items**: the same as for an ordinary write: the target is (row, conflict unit), a target has at most one open item, candidates merge into it, and the three decisions are unchanged. The "`ver` carried" by a candidate is the baseline position of this field; when the fields in one conflict unit (field group) have different baseline positions, the earliest is taken, in line with how the version seen is taken (conservative: more concurrency is found). The merge base is as usual the earliest of the versions carried by the candidates.
- **Source level**: when no evidence is carried it is "API call", with level "agent inferred"; when evidence is carried it follows the kind of evidence. In the first version a conflict always keeps the current value, and the level takes no part in the judgement.
- **High-impact**: event tables and timeless tables have no coverage-type high-impact; writing by external key does not enter awaiting confirmation, unless a slot policy later designates extra high-impact tables (later).

#### Revoked rows do not come back

The user says "this one is wrong, delete it", and the agent revokes the row; at the next sync this external record is still there.

- **A revoked row still holds its key**: a revoke changes only "existence"; the values of the key fields stay on the row, and the key index includes revoked rows. The only exception is when its key has been transferred to a row that added the key: after that it no longer holds the key, a sync hits that other row, and it itself can no longer exist again.
- **Hitting a revoked row: this op is skipped** (`skipped`, `revoked`, with the write number of the write that revoked it). No insert, no restore, no contribution recorded, no source data stored, and this op enters no event; the other ops in the same request are executed as usual.
- **No error is reported**: an ordinary write to a revoked row reports `revoked` and the whole request does not take effect, because the caller named that row and should know its state. A connector hands in a whole batch and does not know which of them the user has revoked; one revoked record should not make the several hundred in the same batch fail, still less fail once an hour.
- **To restore, a person does it**: `undo` that revoke by row ID. Later syncs continue by the three-way comparison; the revoke and the undo both changed "existence" and intersect every conflict unit, so after restoring, if the source has changed, the first time it will become a candidate.
- A skipped op does not change the sync baseline.

#### Relationship to existing mechanisms

| Mechanism | Relationship |
|---|---|
| Suspected duplicate (`duplicate_keys`) | They do not replace each other and may be declared together (see "Suspected duplicates"). A hit on an existing row by external key is not an insert and is not judged; a row inserted by external key is judged as usual |
| Idempotency | The external key itself makes a resend idempotent: handing in the same content again gives `unchanged`. So a request containing only ops by external key computes no server-side request key; an explicit idempotency key can still be used. A request containing ordinary ops computes the request key as before (see "Idempotency") |
| Version mark `ver` | Writing by external key does not carry it; the version seen is taken by the kernel as the baseline position and recorded in the event. The receipt still gives the row ID and `ver` as usual, but they are of no use to later writes by external key |
| The fallback for `ver` | Does not apply: the read record is not consulted, and `read_first` is not reported even if the row was never read |
| Conflict judgement | The criteria are unchanged; only the origin of the version seen differs. The version seen for a write by external key is taken by the kernel by log position; writes within one tenant are serialized, so the result depends only on the log |
| Revert | `undo` of an update by external key: as usual. The reverted item is still a sync contribution and the baseline value is unchanged, so when the source has not changed the sync does not write it back again; it is no longer a sync contribution in effect, and when the source has changed it becomes a candidate. When the target is the write that created the row, `invalid_argument` is reported as before, and revoke is to be used. **External key fields enter no revert record** (`undo` and `take_previous` skip them when listing items): so a written-back item never touches a key field, and "undoing an undo" cannot create two rows with the same key either |
| `ref` | Other rows may reference a row created by external key by row ID; within the same request the temporary name of an op by external key may also be used, bound for both an insert and a hit |
| The premises of a write | An op by external key cannot carry premises; a row written by a connector that needs to declare premises has them restated separately by the agent after reading it |

#### How it is recorded in events

**The key value does not enter the event header, nor the metadata block or the block path**: it is content, appears only in the data block of the key field itself, and, like any field value, records a provenance and is within the cascade range.

- **What enters an event**: an op by external key enters an event only when it left something (an insert, or a hit with at least one field that is not a no-op); an `unchanged` or `skipped` op enters no event and appears only in the receipt. When all ops in a request are of these two kinds, the whole request appends no event: no logical write head, no source data, no request key; **evidence that the caller passed explicitly is not stored either** (nothing needs it), and the receipt states truthfully that the evidence was not stored; the receipt gives no `seq`, and the explicit idempotency key carried by the request is not recorded either (a resend is judged anew by external key, with the same result).
- The logical write head additionally records the total number of ops in the request (ops that did not enter an event leave an empty slot number, so that replay can say how many were omitted at the end); each op that entered an event records "located by external key", the row ID located or newly allocated, and, when a key is added, which row the key was transferred from; the origin of the version seen is recorded as "by external key", and the baseline position of each field is recorded separately (only the operation number, used by judgement and deletion replay). The original value of the key is recorded only in the write that obtained the key.
- **The "API call" source data** follows the current granularity: when no evidence is passed, one for each op that left something in the events, containing only that op (the values of no-op fields are still not recorded). An external key corresponds to one record in the source; deleting the source data of one synced record removes only that record's contribution and does not involve the other records in the same batch.
- **A sync with no change leaves nothing**: when several hundred unchanged records are synced every hour, each time should not leave a logical write head, a request key containing the content of all the records, and a batch of source data that holds only field names. With no event, there is also no request key that "can be deleted only together with other records' evidence", and no association metadata saying "this record was sent again after deletion".
- **A request containing ordinary ops** computes the server-side request key as before, from the original request body, so the content of the ops by external key in it is deleted only together with the evidence of this request itself (a known boundary; see the "does not miss deletions" item of "Corollaries"). The connector can avoid it by sending ops by external key and ordinary ops in separate requests. The content fingerprint of an explicit idempotency key belongs to the same boundary.
- **The receipt of an idempotent replay** is rebuilt from the log: the result of an op that entered an event comes from the event; an op that did not enter an event is not in the log, and the replay receipt gives only its index and marks it as omitted (`unrecorded_ops`); the counts of the five outcomes do not give these two either. It is not recomputed from the current state: that would make two receipts of the same request differ ("the same" means the same JSON value; the order of keys in an object is not part of it). A request containing only ops by external key is replayed only when it carries an explicit idempotency key. The subject in the receipt (`Actor`) is also taken as of the time of the operation, not the name and state it has now ([`04-contract-types.md`](../04-contract-types.md) §1.6).
- **The key index** (`external_keys`: table ID and key value → row ID, with a further column for the state: present / frozen, recording the set of IDs of the deletions that freeze it when frozen) is materialized state derived from the log; `apply` maintains it by deterministic rules and it contains no judgement: when the value in effect of the key fields of a row changes (insert, adding a key, a deletion result, a cancellation result, a schema switch), the entry of this row is changed to the new value, and a revoke does not touch the entry; when adding a key recorded which row the key was transferred from, and the key field item of the key addition exists in the same operation, the entry is changed to point to the row that added the key and the original row is marked "given up"; when a key field item for this key on some row (the holder's, or the original row's before the transfer) appears in the list of expiry positions of a deletion confirmation, the entry turns frozen, this deletion is added to the set, and the holder is unchanged; on cancellation it is removed from the set, and when the set is empty it turns back to "present"; at physical erasure at expiry, the keys involved in the list of positions are recomputed according to "How the holder is decided". Freezing looks at whether the position list contains a key field item, not at whether the value of the key field in the result changed before and after: when replaying from the start after a tombstone, the deleted key field is already empty, and a comparison of values cannot yield the freeze. When a schema switch rebuilds the key index by the new version of the table, "given up" and "frozen" are kept (a row that has given up still has the value of that key field, and rebuilding by value would put it on the same key as the holder). It is derived from content and is listed in the plaintext residue list (see "Deletion · After deletion").
- The sync baseline and locating are mechanical judgements and belong to rule version 1 of the first version.

### Invariant: every write has source data

- Evidence was passed: the evidence is stored as source data.
- **No evidence was passed** (for example a script calling the API directly): the request itself is stored as source data (type "API call", **one for each op that left something in the events**, containing only that op, so that deletion by row can cut it apart by row; a restate or a clear of a premise leaves a declaration in the events and counts too), and the declared level is lowered automatically to "agent inferred".
  Evidence is therefore "mandatory", but saveslot provides the fallback, so it never blocks the writer.
- **An op that did not enter the events stores nothing**: when an op by external key was unchanged or skipped, no source data is stored for it, because source data is the source of a contribution, and with no contribution there is nothing that needs it. A request in which all ops are of these two kinds produces no event and therefore no source data. Evidence the caller passed explicitly is not stored either, and the receipt states so as it is. It has no base write, and this invariant still holds. When the request did produce events, evidence the caller passed explicitly is stored as usual (evidence is an asset), and when no op that entered the events references it, the receipt gives `evidence_unreferenced` as usual.
- **A write triggered by resolving an item** (revoking a flagged row, adopting a candidate, returning to before the conflict, supplying a value in a difference list) also needs source data: the evidence attached to `resolve` is used (for example the user's sentence "the later one is a duplicate");
  when none is attached, the resolve request itself (including `note`) is stored as "API call" source data. **When the resolve request carries a `note`, the request itself is stored as one "API call" source data, whether or not it triggers a write and whether or not it carries other evidence**, and the resolve event references it as its operation source: the `note` can therefore be cleared by an ordinary privacy deletion, and the `note` echoed in the item details is also taken from here. In most cases these are only the **operation source**: the value source of an adopted candidate is the source of the candidate's write; only for a value carried by `set` in a difference list is the evidence of this resolve the source (see "Deletion · Provenance").
- **Only raw content is submitted, with no structured value**: it is stored as source data with the status "pending extraction", and a background executor that calls a model (a worker) extracts it according to the current schema
  (the user must bring their own API Key); the extraction result is written as "agent inferred", and when it differs from a confirmed value it goes to awaiting confirmation. **Not in the first version** (an advanced capability, see "Later plans" in the positioning document).

Hence "every piece of base data can be traced to source data" is guaranteed by engineering, and all the mechanisms above rest on this.

### Source level: declared level and literal match

**A write is always accepted first and is not rejected because a check fails; trustworthiness is marked separately, judged at write time and recorded in the event.** Source data is an asset and must not be lost because verification failed.

| Field | Given by | Values |
|---|---|---|
| Declared level | The Agent at write time (per evidence segment) | User stated / agent inferred / external authority (not open in the first version) |
| Literal match | Judged by saveslot at write time | For each evidence segment and one field: hit / miss / not applicable. The level of a field is computed from them (see below) |

**A literal match checks that "the value appears in the original text of the evidence", not that "the evidence asserts this value".** It is the only check path that does not use a model: otherwise, for a user who has not configured an API Key, the declared level would never have support and "user stated first" would never take effect. "The value is inconsistent with the evidence" can only be concluded by a model check and does not appear in the first version; a later background model check will produce a separate "check result" event and will not change the original event.

**Match rules** (checker version `literal@1`; before comparing, the evidence text goes through Unicode NFC and full-width to half-width conversion (U+FF01–FF5E shifted, U+3000 turned into a space; the Chinese comma U+FF0C is not converted)):

| Field type | A match if and only if the evidence text contains |
|---|---|
| `quantity` | a number token equal to the original numeric value in the request, followed immediately (whitespace allowed) by a unit spelling: take the longest of all spellings in the synonym table that is there, and it counts only if it belongs to the original unit of the request ("5 公里/小时" writes km/h, not km); a currency symbol is written before the number, with optional whitespace between it and the number (for example the evidence "跑了 5 公里" with the write distance = 5 km; "¥45" with the write 45 CNY) |
| `integer`, `decimal` | a number token equal to the written value |
| `date` | a date spelling for the same day: `YYYY-MM-DD`, `YYYY-M-D`, `YYYY/M/D`, `YYYY年M月D日`, `YYYY年M月D号`, `M月D日`, `M月D号`, `M-D`, `M/D`; month and day may be zero-padded; when a year is present it must be the same. A date must not be directly adjacent to a digit, `-` or `/` on either side ("2026-11-05" does not yield another date, "1/2/3" is not recognized); a spelling without a year must not have "年" directly on its left (being separated only by whitespace or "的" still counts as adjacent); a date must not have `:` directly on its right, nor a `.` that is followed by a digit ("11-05:30" and "11/5.5" are not recognized). English month names, `M.D` and relative expressions such as "今天" and "上周三" do not count |
| `enum` | the literal of that enum value (case-insensitive) |
| `text` | the written text (after trimming leading and trailing whitespace, at least 1 in length) |
| `zoned_datetime`, `boolean`, `ref` | not applicable |

- Number tokens: Arabic digits; a thousands separator is recognized only as a comma followed by exactly 3 digits with a first group of 1–3 digits; a decimal point is followed by at least 1 digit; the comparison is by numeric value, not by spelling. A minus sign is not part of the token, and a negative value is compared by the number with the sign removed ("-8" contains 8: nothing on the left of the "-" is a digit, so it is not a connector): the check is that the value appears in the text, and the sign is something the evidence asserts. A token must not be directly adjacent to any digit on either side (digits as defined by Unicode, including superscripts, subscripts and fraction characters: "5²" and "٣5" contain no 5), must not have `.` directly before it (".5" contains no 5), and must not be directly adjacent on either side to a `.` `,` `:` `/` `-` that is followed (or preceded) by another digit ("1,500" contains no 500, "1234,567" and "3.14" contain no 1234, 567 or 14 respectively, and "10:30", "3-5", "1/2" and the numbers in dates do not count; the Chinese comma is not converted to half-width, so "午饭 ¥45，11月5号" contains 45). A digit that falls inside a date spelling (all spellings in the date row of the table above) or a clock spelling (`H点`, `H点M分`, `H时M分`, `H:M`) is not a number token ("11月5日" contains no 11 and no 5, "10点30分" contains no 30; the 5 in "给了5点建议" does not count either, which is a missed match; "住了 5 日" and "跑了 30 分" count as usual). A number followed by `%` or `‰` does not count (a `quantity` whose unit is `%` counts by the unit spelling); scientific notation is not recognized; `literal@1` does not recognize Chinese numerals. The recognized unit spellings are in "Field types, same value and units · Unit synonym table" (`units@1`, part of `literal@1`).
- The written value goes through the same normalization (NFC, full-width to half-width) before comparing; `text` is case-sensitive and, after trimming leading and trailing whitespace, at least 1 in length; `enum` is case-insensitive.
- Each evidence segment has three possible results for a field: hit, miss, not applicable. The cases of not applicable: the field type is not applicable; the value is empty; this segment has no original text to compare, that is an `api_call` (it is the request itself, and comparing a value against it is meaningless) or a `file_ref` without `excerpt`. A `file_ref` with `excerpt` is checked against the `excerpt`.
- **Granularity of the record**: the base write event records "each item of a field, each evidence segment that item references, hit / miss / not applicable", plus the checker version (including the synonym table version). `source_ref` is checked against the original text it references. Replay uses the recorded results and does not check again (handled the same way as suspected duplicates).
- **The level of a field is not stored, it is computed**: among the value sources the field still has, the highest declared level of the segments that hit is taken; if no segment hit, it is "miss". The results are recorded per segment so that they can still be recomputed after a deletion.
- **It takes effect in one place only: conflict adjudication** ("Conflict handling · System ruling", later). The first version judges and records as usual but takes no part in any judgement, because this information cannot be filled in afterwards.
- An evidence segment may carry an optional stated time `stated_at` (when the user said it; unknown if not given), stored with the evidence and deleted with the evidence, and likewise only recorded, not used.
- This is to make the result of adjudication reviewable and replayable, not distrust of the Agent: saveslot trusts the Agent's input by default (the positioning document, "The data layer") and does not judge whether the content is true; what a literal match compares is also only the evidence text the Agent itself submitted.
- A high-impact operation needs confirmation anyway, regardless of whether the level is accurate.
- **"External authority" is granted by the credential, not self-reported by the writer.** Not open in the first version: declaring it always reports `not_in_this_version`. When it is opened later: whether a level can be declared is decided by the permission granted to the connection; the grant can only be made by a user session at issue time, the writer cannot self-report it, and another connection cannot transfer it; if it was not granted and the level was declared, the whole request is rejected and is not silently downgraded to "agent inferred" (a downgrade would let the writer believe its value carries the authority level); the grant is recorded in the principal registration event, in the same place as the scope and the slot range, and the level is still recorded per evidence segment in the source data, so "whether the level of this source data was declared by an entitled principal" can be checked from the log alone. The form of the grant, whether it can be granted per slot, and other details are decided together with the system ruling.

### Reverting to a version

**A revert is simply a new write**: it writes back the value of an old version, and history is not rewritten. Its value source is a reference to the contributions in effect at that place in the old version, and the revert request is only the operation source (defined in "Deletion · Provenance"; how it is counted on deletion is in "Deletion · Replay rules"). **Undoing (`undo`) and returning to the merge base (`take_previous`) are the same operation, reverting, taken in two ways**, made up of three things: the revert record (which operations' changes on which targets are reverted; written item by item at write time as (event, target), and followed as recorded); the range (for each item these entries have in replay, its interval minus the parts still covered by later operations; `take_previous` then intersects it with the interval of the item, and for `include_later` the later writes taken along are intersected with that interval and with the interval of the undone operation; recomputed in replay after a privacy deletion); and the position the value is taken from (for `undo` it is before the undone operation, for `take_previous` it is the recorded merge base; the position follows the record, and the value there is recomputed in replay). When there was no contribution at that place at all, what is written back is "no value"; when that place was then inside a hole caused by a revoke, an item with no content is written back (registration only): the reverted fill value no longer takes effect, the hole is exposed again, and the value under the revoke is untouched. On event tables and timeless tables an item is an indivisible whole: while it is still covered, the whole item is not reverted. Reverting a revoke writes back "restore to existence", and reverting a "restore to existence" writes back a revoke. The authoritative definition is the pseudocode in "Deletion · Replay rules · The authoritative definition of reverting".

- **Revert is not revoke**: on a state table a revoke with an interval means there is no value in that period; "restore to the original plan" needs a revert.
- **When the content of the revert target has been deleted** (physical erasure, or a logical deletion within the grace period), a new revert request reports `invalid_argument` ("the content of the target version has been deleted"). A revert already present in a deletion replay is not affected by this.
- When the value produced by a revert erases a recorded change point (common on state tables), it is high-impact ① as usual. **Exception: an `undo` of a revoke is not ①**: it restores exactly the value that revoke removed, and the change points at both ends return to what they were before the revoke, so it is the path of regret for a revoke.

#### Undoing a write (`undo`)

The caller gives only "undo write number n". The kernel takes that write's contributions to this row / entity and their **current resolved intervals** (those recorded at write time, or, if a later privacy-deletion replay resolved them again, the most recent), and on those fields and those intervals returns to the values from before write n. The value before can be several different segments within one interval (for example write n covered two segments, 5000 and 4000), and then this revert has that many items on the field, each referencing the contributions that are carried over. The caller does not need to find "the version before the adjustment" itself, nor give the interval itself. When several ops in the same request change the same row / entity, they are undone together.

- **By default only the parts of write n that are still in effect are undone**: for the fields and interval segments where the value it wrote is still the value in effect, the values from before write n are restored; parts already overwritten by later writes are skipped, and the receipt lists each as `skipped_superseded` (with the write that overwrote it). When a user says "undo that adjustment", they generally do not mean to undo other people's later changes along with it. When everything is skipped, this write changes no value and `ver` does not change, and the receipt lists the skipped parts as usual; the base write event is recorded as usual and contains only the revert record.
- **To revert later writes along with it**, `include_later: true` must be passed explicitly: later writes are reverted together on the intersecting fields and intervals. When some later item is in effect, supersedes some item in effect of the undone operation, and the intervals intersect, the revert record lists (the base write of that item, the target of that item), marked `later`; it reverts only over the intervals where the undone operation is in effect in replay and which the items it can supersede cover, and what lies beyond stays in effect as before (see step 2 of "Deletion · The authoritative definition of reverting"). **Whether on an event table or a state table, whenever later writes are reverted (the range of the items marked `later` is non-empty), it is always handled as high-impact**: it goes to awaiting confirmation, and the receipt lists the writes that would be reverted (high-impact list ④, see "Time · High-impact writes"). **When a pending revert is confirmed, the revert record is listed again according to the state at confirmation** (writes that appear in the item after a refresh are included), recorded in the write that the confirmation triggers; the item and the preview are updated accordingly: each time the item is refreshed it is judged again against the current state, and the range (`scope_valid`) and the effect change with it, so what is shown is what confirming would do at this moment (event format §5.8 `item.refreshed`). When, after the new judgement, there is no segment left to write back and no write left to cover or revert, the item is closed as superseded (`nothing_to_revert`) in the same transaction as the write that made it so, and the receipt of that write lists it in `superseded`; after that it can no longer be confirmed or rejected (`item_closed`), and it does not revive when a later write gives this revert something to do again; to do it, propose it anew. When the writer read the item and then changed it, it is superseded as `overwritten` as before: in that case it is not refreshed to begin with, so there is no refresh to replace.
- **A written-back revoke that would cover later writes is likewise handled as high-impact**: undoing a "restore to existence" writes back a revoke, and when in this interval there are field writes in effect that come after the undone operation and before this revert and are not in the revert record, the revoke written back would cover them over the whole interval; this `undo` goes to awaiting confirmation, and the item and the receipt list the writes that would be covered (high-impact list ④). Returning to before the conflict (`take_previous`) does not write back a revoke: the field writes within the same time-period unit are all in its revert record ([`../09-event-format.md`](../09-event-format.md) §5.7). Something covered only as corroboration does not count and gives the `overwrote_corroborated` warning. The supersede relation is unchanged: a field write does not supersede "restore to existence", otherwise the undo would leave a segment inside the interval to be revoked and expose the other field values from before the revoke again.
- **The writes that the item and the receipt list as reverted or covered are judged by the result that can be read** (the `impact.reverted` of a pending revert, and the `reverted_by_previous` of a conflict item when returning to the merge base, both follow this paragraph): what is listed are the later writes after which a reader would see something different once it is confirmed: the value of some field on some segment, whether this segment has a value, whether the row is revoked, differs before and after the confirmation; the write that gave this result before the confirmation is listed, together with the fields whose result changes (a revoke is written `*`); whether or not it is in the revert record (another person's `undo` of a later write is the same). Those that only change who supplies the value and leave the result read unchanged are not listed: that confirmation appears in the timeline as usual and does not need to be announced in the effect. On a state table a revoke is a write of "no value for this period" (see "Time · Revoking on state tables"), and a revoke and no value count as the same kind of result; when this segment has no value before the confirmation and has one after, what is listed are the revokes that made it valueless, and a field write on this segment is exposed and not lost. Only writes later than the undone operation are listed; the confirmation of the `undo` being undone belongs to that `undo` itself. What the judgement uses is what the confirmation would do at this moment: the confirmation lists the revert record again according to the state at that time (the previous paragraph), and the effect is compared against the state after that confirmation. `reverted_by_previous` is the same: it compares the state after returning to the merge base (`take_previous`) at this moment and lists only writes later than the merge base; a candidate does not take effect and is not listed; for a segment that a later write covers and that returning to the merge base does not write back either, what is read does not change, and the writes there are not listed. One `reverted` means that at least part of the result of this write will change, and it carries no interval.
- **A write-back that leaves a segment without a value and would cover later writes is likewise handled as high-impact**: the write-back turns the entity on some segment from having a value into having none (for example it writes a required field on that segment back to no value, where the undone write had been filling a hole with a value), and on this segment there are other field writes in effect that come after the undone operation and before this revert and are not in the revert record, so those writes' values are gone together with the segment. This `undo` likewise goes to awaiting confirmation, and the item and the receipt list the writes that would be covered (high-impact list ④); the criterion, the time window and the rules are the same as for the written-back revoke, counting only writes that supplied a value (a clear counts too; a written-back no-value item supplies no value by nature and does not count). On a table with no required field, the other field writes themselves hold up the value of this segment, so the segment does not become valueless because of it and this does not trigger. If the merge base that `take_previous` returns to has no value on this segment, it likewise covers such writes outside the unit: it is a decision on a conflict item and does not go to awaiting confirmation, the `reverted_by_previous` in the item details lists them by the previous paragraph (by the result that can be read), and the receipt of the decision lists them as well; as soon as such a write is applied, the content of the item changes, and the item is refreshed accordingly.
- **`undo` does no `ver` conflict judgement, and `ver` may be omitted.** The caller named the write to undo, and by default only the parts of it that are still in effect are undone, so values others wrote after it are not touched; to touch them `include_later` is needed, and that is already high-impact. `undo` still goes through validation that depends on the current state (`revoked` when the row is revoked) and the high-impact judgement. It is reported only when the row is revoked and is still revoked after this `undo` is applied: what is undone is exactly that revoke, or `include_later` reverts it along with others (in which case it is high-impact ④ as usual and goes to awaiting confirmation) and the row exists again after it is applied, so it is not reported; when the row existed and is revoked only after this `undo` is applied (undoing the undo of a revoke), it is not reported either. **It is also not reported when what is undone is the revoke currently in effect on this row**, even if after it is applied the row is still revoked by another revoke (for example the revoke left by adopting a candidate covers an earlier one, and the adoption is undone): it only registers the reverted items, so that the revoke below is exposed again and can be undone next. When `revoked` is reported, `revoked_by` gives the revoke currently in effect that should be undone first (an earlier revoke covered by the revoke left by adopting a candidate does not count; a revoke written back by a revert does not count either, because undoing it amounts to redoing the reverted operation and is not the way to restore this row, unless the only revoke in effect is a written-back one). This follows the same line as "The order of judgement" step 5, which validates only the part that is about to take effect.
- What an `undo` reverts, which operations' changes on which targets, is the human decision of this action, recorded item by item as (event, target) in the revert record, and deletion replay follows the record (every base write of the target operation, with every target it had at its write time, is listed, whether it was then in effect, corroborating, a candidate or pending, except the external key field: a key cannot change once obtained, so there is nothing to revert; when `include_later` is given, the later writes reverted along with it are also listed, marked `later`; what was skipped at the time is marked separately, for history and the receipt only). One entry covers all the items it has in replay, so parts of the target operation that were candidate or pending at write time and take effect later because of a deletion are also reverted; when the target is itself a revert, what is listed is every target that appears, in its revert record, for its base write, and the write-back items it grows after it because of a deletion are reverted together (see step 1 of the pseudocode in "Deletion · Replay rules"). When the target is a confirmation, it lists (the confirmation's event, every target the confirmed write had at its write time), without looking at which targets were actually in effect at the moment of `undo`: what the person undoes is that confirmation, and when a later deletion makes the other targets of the confirmed write take effect through that confirmation, they are reverted as well. This record holds only event sequence numbers and targets, and is not cleared by any deletion. **Whether a reverted item is in effect follows this record and does not look at what was written back.** On which valid times it is reverted is given by the intervals of the items this revert writes back; these intervals are derived content and are recomputed in replay after a privacy deletion (the interval of a reverted item in replay minus the parts still covered by later operations), and the old intervals are cleared and given again by the deletion event (see "Deletion · Content derived from other contributions").
- **What write n is**:

  | Write n | `undo` |
  |---|---|
  | An insert; the first creation by `entity_key`; an addition by external key (identified by the "create" mark; the mark is a mechanical judgement, and when a privacy deletion has changed it, what the deletion event recorded holds) | `invalid_argument`, with a hint to use revoke instead |
  | A conflict candidate or a pending write (never took effect) | `invalid_argument`, with a hint to use `resolve` (`keep_effective` / `reject`); when a write had some fields take effect and others become candidates, at write time only the fields in effect are changed; the candidate and pending fields are likewise recorded in the revert record and are reverted together when they later take effect because of a deletion |
  | A write that only corroborated the same value, is entirely no-ops, or whose revert currently has no write-back item at all (everything was skipped, or the write-back items were all restated as `dropped` by a pending deletion; judged by the state when this `undo` is written, including pending deletions. When a pending deletion gives it write-back items it is accepted, and if that deletion is cancelled afterwards, this `undo` covers no item); a restate or a clear of a premise; a write that only added an external key and changed no other field | `invalid_argument`: there is no change that can be undone |
  | A revoke | Allowed: the row (on a state table: that interval) exists again and returns to the value from before the revoke. Exception: when the external key of this row has already been transferred to another row, it reports `invalid_argument` (`external_key_transferred`, with the ID of the row that now holds the key), see "Writing by external key" |
  | A revert, an `undo`; a system ruling; a write triggered by `resolve` (confirm, adopt a candidate, return to before the conflict, a `flagged` revoke) | Allowed, handled as an ordinary write |
  | The operation number of a deletion confirmation or of cancelling a deletion | `invalid_argument`; to cancel a deletion use the `cancel` of the `deletion` item |
  | The operation number of a schema switch | `invalid_argument` (`undo_target`), with a hint to submit a new schema draft: a switch is not a write, and the items filled in by a constant are never listed in a revert record either |
  | A write that is not of this row / entity | `invalid_argument` |

- **Intent may be omitted**: by default the intent of write n is followed; when write n is a revoke or a system ruling, the default is `correct` (that result was wrong, and values read before are affected); a write triggered by `resolve` follows the intent of the write being executed. The caller can still give `update` / `correct` explicitly.

#### Giving the target version explicitly (`revert: {to, fields}`)

> **Not in the first version** (advanced use). It shares the same kernel path with `undo`; only the target version, fields and interval are given by the caller.

- The intent is specified by the caller (correction or change), and the expected version must be passed. Only the fields the caller specifies are reverted, and other fields written by later sources are not reverted along with them.
- **On state tables a valid time interval must be passed** (`valid_from` / `valid_to`): the segments of the target version within that interval are restored as they were, and one revert can produce several segments; segments outside the interval are not touched. A missing interval reports `invalid_argument`, otherwise values that others wrote later outside the interval would be reverted along with it.
- **The target must be a version of the same row / entity**: the operation number given in `to` must be some version of the row / entity being reverted (a #n listed in its `timeline`), otherwise `invalid_argument` is reported. After a backup is restored, sequence numbers may be reused (see "Numbering"); this validation ensures that an old number can at worst point to another version of the same row and never to another row.

## Reads: supplying data

**The value of saveslot is fast, accurate data supply; understanding the user's intent and breaking the intent into queries is the Agent's job.** saveslot does not guess intent,
and does not assume it is the center of the Agent: it is only one of the many MCP servers / plugins the Agent uses. On the read side saveslot does three things well:
lets the Agent **see clearly** what data there is, **find** the result it wants, and **get it fast**.

### Visible: the catalog must be detailed enough

Beyond the tables, fields, types, descriptions and derivation rules the "Catalog" already has, it also provides:

| Information | Example | What it is for |
|---|---|---|
| Relations between data | runs is the source of weekly_mileage; the category of a spending row refers to the budget table | The Agent knows how to query across tables; schema definitions are required to **declare relations between tables** (foreign keys / references) |
| Data profile | Row count, time range (earliest 2026-03, latest 11-08), sample field values | Before writing a query, judge "whether there is any, and how much" |
| Units and semantics | distance in miles; date is a calendar day in Asia/Shanghai | Avoids misunderstanding the data |

### Findable: two tiers of query

- **Simple query**: query by table, condition, order and count; it covers most everyday reads and is the friendliest to models.
- **Read-only restricted SQL**: complex joins, aggregation, time windows. **It shares the same restricted SQL engine with derivation rules**: a function allowlist (see "Restricted SQL", [`11-restricted-sql.md`](11-restricted-sql.md)),
  reading only that user's own data (row-level isolation), and limits on execution time and result row count. The safety measures are done once.
  One `sql` may reference tables of several slots in the visible range: it is read-only and involves no version ownership or atomicity, and the result gives the schema version per slot. Derivation rules and `ref` fields still do not cross slots.
  - **The main line of defense is at the saveslot layer**: libpg_query (PostgreSQL's own parser) parses it into a syntax tree, and statements, nodes and functions are validated against allowlists,
    explicitly forbidding `SET` / `RESET` / `set_config()` / `COPY` / `DO` and all DDL / DML; table names are rewritten to point at the physical tables of that user at the current version; a single statement.
  - **The second line of defense** (native PostgreSQL): a non-superuser read-only role, a read-only transaction, `statement_timeout`.
  - **On PGlite**: the role can be escaped with `SET ROLE` and `statement_timeout` does not take effect (measured), so it relies only on the syntax-tree allowlist;
    queries and writes are queued in that dedicated DB Worker, and a timeout can only terminate the whole Worker (the cost is in architecture §7), so the main line of defense is admission estimation beforehand and rejection at compile time.
  - The result is wrapped in an untrusted-data boundary, to guard against prompt injection.
- Two things unique to saveslot:
  - **Reading as of an instant**: valid time (`valid_at` / `valid_during`) is available to all queries; recorded time (`as_of`) only in audit and restore interfaces (see "Time · Queries").
  - **History expanded on demand**: tracing back along the revision history to the original text of the source data (borrowing from chain recall), not expanded by default.

### Fast: keep returns small

- A compact format; every value carries its unit and schema version.
- There is a limit on the count and paging is supported; when the result is large it returns "there is more" (borrowing from Super-agent's Inline & Spill: small results are given directly, large ones give a handle that can be expanded).
- Conflict, awaiting confirmation and correction flags come out with the result: this is part of data correctness and belongs to the infrastructure.
- **Dispute flags carry the item, the fields and the interval**: `disputed` states which item it is, which fields of the conflict unit are involved, and on a state table which interval (when the target is "existence" the fields are all of them); `awaiting` likewise carries fields and intervals. A row can have several items. The criterion: if the value read does not change with "which candidate is adopted", it should not be flagged; a reader that only reads `date` should not be asked to stop and ask the user because of a dispute on `distance`.
- **Derived values also bring out the flags on their inputs**: the flags are put on base rows and derived rows have none of their own; when a derived value is read, saveslot aggregates the flags of the base rows by the partition read set of that derived row,
  and writes "1 row among the inputs of this value is flagged / disputed" (the same logic as the aggregate flag of `sql`), counting only disputes on the fields the rule depends on. Otherwise an Agent reading the weekly mileage could not see that one of the runs is a suspected duplicate.
- **Logical table = the rows of the current version that are not revoked**: the same for simple queries, restricted SQL and derivation rules; to query revoked rows, ask explicitly (`include_revoked` of `query`, `history`).
- **A changed premise is brought out**: when a premise used by the current value of a row has changed later, the row carries `premise_changed`, stating which premise, which field, in which operation it changed and why (computed at read time, see "The premises of a write"). It is a state of the row and any reader can see it; the value has not moved, and whether it still holds is for the reader to judge.
- **A reference field brings out the state of its target**: when the target of a `ref` has been revoked or privacy-deleted, the row carries the flag `dangling_ref`, stating which field and whether the target is revoked or deleted (computed at read time, not stored, see "Reference fields"). Like other flags it comes out with the result and is rendered into text by the surface.
- Reads are recorded in the read_log automatically, and the Agent does not need to do anything.

### What shape a read record keeps

The read record (read_log, see "The read record") keeps only versions, not values. The query condition is recorded as a **structure fingerprint**: text that, once normalized, contains no value given by the caller. It is stored as text, not as a hash: it contains no values to begin with, text is easier to troubleshoot, and normalizing to IDs means renaming does not affect matching.

| Read | How the fingerprint is obtained |
|---|---|
| Simple query `query` | A deterministic encoding of a JSON object (RFC 8785): the table ID; the selected field IDs (sorted); the condition tree (operator + field ID, **every literal replaced by `"?"`**, and a list replaced as a whole by one `"?"`); the order (field ID + direction); whether a count and paging are given (only presence is recorded); the kind of valid time parameter (an instant / a period / none) |
| Restricted SQL `sql` | In the syntax tree, table names and field names are replaced by IDs, every constant by `$n`, an `IN` list is folded into one placeholder, **column aliases, table aliases and comments are removed** (aliases are text chosen by the caller and may contain user content, so they are replaced by position numbers), and then it is deparsed back into text |
| `history`, `sources`, `catalog`, `pending` | Only the operation, the mode and the opaque ID of the target are recorded; the search term of a source data search is not recorded |

The valid time condition ("what is queried is 11-03") is recorded separately, and the correction impact query needs it; it is the only value in the read record that comes from the caller.

**How many are recorded.** For a row-by-row read, one version is recorded for each row (at most 1,000 rows per page). For restricted SQL, for each base table the record is "no fewer than the rows actually read" (a superset: record more rather than less): each base table corresponds to one read-only statement, run in the same read-only transaction, taking the FROM and WHERE of the query level where that table sits and ignoring grouping, aggregation, DISTINCT, ORDER BY and LIMIT / OFFSET, and taking at most 1,001 rows; when the rows read on one table exceed the threshold (initial value 1,000), this table is recorded as one table-level entry instead, so the cost no longer grows with the number of rows, and in exchange the impact query can only report "possibly affected" on reads of this kind (the rules are in "The read record" and "Querying the reads a correction affects"). When one table is referenced in several places, the union of the places is recorded. **Recording by row is done only when this level has exactly one table reference and the WHERE of this level contains no subquery; otherwise this statement is not run, and the tables of this level are recorded at table level directly**: the statement takes the complete FROM and WHERE of that level (with the subqueries too), and would run again at the cost of the product of the tables, or of a subquery per row of the outer level, which the caller's `LIMIT` cannot bound. As soon as one reference to a table cannot be recorded by row, none of the references to that table runs the statement, and the judgement is made before execution. The whole call shares one deadline, and the statement for the read record uses the time that remains (11-restricted-sql, "Cost"). A table that is inside a subquery and correlated with the outer level (this level cannot run on its own without the outer level) is always recorded at table level and not row by row.

### Visible scope

Each call carries a visible scope, given by the service layer according to the credential and enforced by the kernel (the catalog, queries, the rewriting of restricted SQL and writes all pass through it). A user session and a connection whose scope is "all" pass "all"; a connection limited to some slots passes its slot list (see "Connection identity"). The type is already fixed down to the field level now, so that when table-level and field-level data permissions are built later, the signatures of the kernel operations do not change.

| Value | Meaning |
|---|---|
| All | All slots of this tenant |
| Allowlist | Lists the visible slots; under a slot the visible tables may be listed again; under a table the visible fields may be listed again. What is not listed is not visible; a level that is not listed further down = everything below this level is visible |

**For this credential, something outside the scope is exactly the same as something that does not exist.** Errors are divided by how it is referenced:

| How it is referenced | When it does not exist or is not visible |
|---|---|
| By name (table name, field name) | The error that operation reports for a name that does not exist: `query`, `history`, `write` and `catalog` report `unknown_table` / `unknown_field`, and `sql` reports `sql_rejected` (`unknown_name`). The similar names that come with it (`nearest`) are taken only from visible names |
| By ID (row, entity, item, source data, draft, a read) | `not_found`, the same as when the ID does not exist |
| A parameter that specifies a slot (by name or ID: the `slot` of `catalog`, the `slot` filters of `sources` and `pending`, `policy.get`) | `not_found` (`slot`), the same as when the slot does not exist |
| A row ID written into a parameter (the value of a `ref` field, the target of a premise) | The same as when the ID does not exist: `ref` reports `validation_failed` (`ref_not_found`), and a premise reports `not_found`. `ref_wrong_table` and `cross_slot` are reported only when the target is visible |

`not_found` means "not found by ID", and `unknown_table` means "the name is not recognized, and similar names are given"; each handles one kind of reference. Similar names are useful to a model that wrote a name wrongly, and they are not removed for the sake of not leaking; only the place the candidates are taken from is restricted: a name outside the scope appears in no error, candidate or hint. Row IDs are hard to guess, but they leak through shared logs, screenshots and the contexts of other Agents, so references by ID likewise do not distinguish "does not exist" from "not visible".

- **Name resolution is done only within the visible scope**: when a table name is not duplicated within the visible scope, the table name alone may be written; the candidates of `ambiguous_table` and the resolution of old names (old names within the last 10 versions) likewise look only at the visible scope. Otherwise a request that writes only `runs` would report an ambiguity because another `runs` exists outside the scope, which amounts to leaking it.
- **How each operation is bound by the scope**:

  | Object | Rule |
  |---|---|
  | Catalog | Lists only the slots and tables in the scope; the profile, sample values and relations between tables involve only tables in the scope. The complete schema document (the `schema` tier of `catalog`, including a read with `draft`) is given only when every table of the slot is in the scope, otherwise it is the same as when the slot does not exist |
  | `query`, `history` (including `timeline`, `as_of`, `changes`) | The target table must be in the scope. When `changes` gives no target it is "the changes of one table", and that table must be in the scope |
  | Restricted SQL | Every table referenced in the syntax tree must be in the scope, otherwise `sql_rejected` (`unknown_name`); it may reference tables of several slots in the scope (see "Findable"). The aggregate flag counts only rows in the scope |
  | Pending items, `resolve` | An item belongs to a slot and is filtered by slot; an item ID outside the scope reports `not_found`. The hints in the result count only what is in the scope. A `schema_change` item and the draft of a slot (a `catalog` read with `draft`) concern the schema of the whole slot, and are visible only when every table of this slot is in the scope, otherwise it is the same as when they do not exist |
  | Source data, `source_ref`, deletion preview and deletion | Each piece of source data belongs to one slot only and is filtered by slot; a source data ID outside the scope reports `not_found` |
  | Read records | Recorded under this connection as usual. When the reads of some target are queried through `history`, the target must be in the scope; when restoring by one read, a target of that read outside the scope reports `not_found` |
  | Impact queries | The affected reads in a write receipt count the reads of the rows this write wrote, and those rows are all in the scope, so they are given as usual; the `possibly_affected` on a read result appears only on rows in the scope |
  | Writes | The target table must be in the scope; one write involves only one slot, and the whole request is either in the scope or reports `unknown_table` |
  | Submitting a schema draft | Changing a slot in the scope is as usual (needs `saveslot.schema`). **A credential limited in scope cannot create a new slot** and reports `insufficient_scope` (`required_scope: "all_slots"`), whether or not the slot name in the draft duplicates the name of some slot outside the scope. When it has neither `saveslot.schema` nor an unlimited scope, the missing scope is reported first (`required_scope: "saveslot.schema"`): the action is checked first, then the scope |
  | Export, replay comparison, verification, connection management | Given only to user sessions, not affected |
  | Idempotency, rate limiting | Unchanged: the request key already contains the connection |

- **A derived table is visible if and only if all the tables and fields it depends on are visible.** saveslot has the complete derivation dependencies and can enforce this. Derivation rules do not cross slots, so at the slot level a derived table and its base tables go in and out together.
- **The scope does not change judgement**: conflict, same value, high-impact and suspected duplicate look only at the data in the same slot, and writers inside and outside the scope get the same judgement result.
- **Hints are computed only by the visible scope**: among the various hints in receipts and read results, a slot outside the scope appears in none. The writers that appear in history (connection names) are shown as usual, and they do not belong to any slot.
- The kernel of the first version implements the allowlist at two levels, slot and table; the service layer passes only down to the slot level according to the credential. Table-level, field-level and row-level data permissions are later.

### What it does not do

- **saveslot does not pick "the data relevant to the task"**: intent analysis and query decomposition belong to the Agent.
- **There are no read rules in the schema**: a catalog that is detailed enough is sufficient, and what to read is decided by the Agent.
- **No overview at the start of a session is assumed**: a host plugin may do it selectively, and the design of saveslot does not depend on it.

### Source data: listing and search

- The first version provides listing source data by time, slot and type, and a simple full-text search (to satisfy "how did I say it last time"); vector retrieval comes later.
- The full-text index is derived data: on deletion the corresponding entries are cleared at the same time (see the plaintext residue list in "Deletion").

### Change notification: saveslot provides the capability, the product decides how to use it

The read_log records "who read which version at what time", so saveslot can compute "what has changed since the last read" (for example "last time W45 was read it was 22,
now it is 12, because the record of 11-03 was corrected to 5 km"), and provides it as an optional query item. When to notify, whom to notify and in what form
are features of the product layer.

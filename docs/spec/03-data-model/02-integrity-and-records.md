## Integrity and provenance

**The goal is "traceable and protected against mistakes", not tamper-proofing**: every item of state can be traced to events and source data in the log; missing events, events out of order, event headers changed by accident, damaged content, and changes that bypass `apply` can all be detected.
For a party that can write to the storage (the operator included), tamper-proof evidence is **not provided** (see [`../02-architecture.md`](../02-architecture.md) §10).

| Item | Rule |
|---|---|
| Event header | Only common fields: `seq`, the event format version, the type, the actor (principal ID), the recorded instant, `prev_hash`, the operation number of the operation it belongs to (a head event has none), the slot ID; the head event of `system` also carries `trigger` (which background task, a fixed enumeration); genesis, restore and import events also carry a node ID and the restore or import information. For the full definition see [`../09-event-format.md`](../09-event-format.md) section 2. **No value computed from user content is put in it**: request keys, group keys and content hashes are all excluded. The table, row or entity, intent, and the `seq` of the events referred to are not in the event header either; they are in the **metadata block** of the content area (which contains only opaque IDs, enumerations, sequence numbers and indexes, version numbers, booleans and entry instants; it is not part of the chain; in the first version it is not removed by deletion, see "After deletion") |
| Chain | **Links event headers only**: `prev_hash` = the SHA-256 (lowercase hexadecimal) of the encoded bytes of the previous event header; the `prev_hash` of the genesis event is 64 `0` characters |
| Content | Stored separately from the event header. The content of an event is a set of **content blocks**; each block is addressed by (event `seq`, `path`) and has its own checksum (SHA-256, computed over the bytes of the block content). The checksum is used only to detect storage damage, is deleted together with the content, and is **not a commitment to the content**: content blocks get no salt, key or on-chain commitment |
| Deletion | **Physically erases content blocks** directly. A block is the smallest unit of deletion and is deleted as a whole; there is no partial deletion inside a block; the three granularities (field, entry, whole item) are met by cutting blocks fine enough. An erased block keeps its position, has its content and checksum cleared, and records the `seq` of the tombstone ("removed by #n"; the marker holds no content and no value computed from content). The event header stays |
| Protection against mistakes | Only the kernel can write (K3; at the database layer only saveslot's service account has write permission); the log is append-only; reconciliation (replaying the log = the live state; in the first version a full replay comparison triggered manually by a user session); the event header chain check; the content checksums |

**Where a content block lives.** `path` is an ASCII string of segments joined by `/`; a segment can be only one of three things: a fixed word of that event type (such as `fields`, `sources`, `target`, `request_key`, `text`, `candidates`), an opaque ID (a field ID, a table ID), or a decimal index. Examples: `fields/f3/0` (the 0th contribution of this write to field 3), `sources/f3/0` (the source of that item), `candidates/1` (the 1st candidate of an item), `text` (the original text of a piece of evidence).
**No user content and no value computed from user content appears in `path`** (fields use IDs, not names), so a position can be written into the references in metadata blocks, the position list of a tombstone, and the deletion register. The `path` vocabulary of each event type is part of the event format and only grows, never changes, with the event format version.

**The identity of an event.** In the first version the event header has no separate event ID. The event headers of the genesis event, the "restore" event and the "import" event (`tenant.imported`) each carry a randomly generated node ID; the identity of an event = (the node ID of the nearest genesis, restore or import event before it, its `seq`). The node ID is changed on restore because after a restore `seq` may collide with the lost stretch of the timeline; it is changed on import because after an import the same export continues separately at the source and at the target, and the `seq` of the two sides will collide. The **current restore count** is the value in the latest restore or import event (plus 1 on import, see "Deletion · The deletion register"). With multiple nodes (later), events produced by other nodes get an optional origin field in the event header; an absent field is not encoded, so the bytes of old events do not change.

| What can be detected | By what |
|---|---|
| Missing events, events out of order, event headers changed by accident | The event header chain |
| Content storage damage (corrupted, truncated, lost) | The content checksums; content that cannot be found although there is no removal marker counts as a mismatch; a block that an event type must have (marked "always present" in the event format) that is missing as a whole row counts as a mismatch too |
| Materialized state inconsistent with the log (changes to business tables that bypass `apply`, defects in `apply` itself) | Reconciliation: replay from the log and compare table by table with the live state |

**Not promised**:

- Tamper-proofing against a party that can write to the storage (the operator included): if the content is changed and the checksum recomputed, or the whole event header chain recomputed, `verify` still passes.
- Proof for a third party ("a certain version really is in the log", "the history has not been rewritten").
- What the content was before deletion: an erased position keeps no value computed from content, so after deletion there is no way to prove it, and no way to compare it with a guessed value.
- Loss of a whole row of an optional content block: the event header does not record which blocks an event has, so when an optional block disappears together with its position, `verify` cannot detect it.

Signed checkpoints, Merkle trees and on-chain content commitments are **left to later plans and will be done as the product needs** (positioning "Later plans"); when they are done they will be added through a **new event format version**, and old events will not be appended to.

- **Values computed from content, and text reported by the caller, are content**: the request key, the explicit idempotency key and the fingerprint of its request content, the task identifier reported by the caller (`task`), the group key of a derived row, the result of the suspected-duplicate judgement (which rows were matched), the hash of the content being confirmed in a confirmation record, the result checksum of a derived write, and the checksum of the new-version table in a switch event are all placed in the content area and deleted together with the content; none of them goes into the event header. The origin of the request key, the idempotency key and `task` is the whole of the evidence for this operation: if any one of them is privacy-deleted, they are deleted with it (see "Deletion · Content derived from source data"). Otherwise, after deletion one could still compute a guessed original sentence and compare.
- **The read record does not store content hashes**: it records only the version read (`seq`), and for query conditions only a structural fingerprint that contains no user values (see "The read record").
- **The encoding is deterministic**: event headers and content blocks are both encoded as UTF-8 text with RFC 8785 (JCS) and stored; the encoded text is authoritative; an absent field is not encoded, and adding a field does not change the bytes of old events. Decimal numbers (amounts, quantities) are always written as strings, because JCS serializes by JavaScript's number rules and would lose precision; small integers such as `seq` and indexes use numbers. They are stored in text columns, not in a binary JSON type, which would change key order and number notation.
- Hashes and checksums are computed in the TS application layer, identically on PGlite and native PostgreSQL; writes are serialized per tenant, and the event header, the content and the business writes are **committed in the same transaction**.
- **Only the primary node's chain is the authoritative chain** (multiple nodes, not implemented in the first version): tentative events of an offline node do not enter the authoritative chain and are linked in only after the primary node accepts them and assigns `seq`; an offline node may keep its own tentative chain locally, for local reference only.
- **Verification**: `verify` reports "the log has T events in total, the event header chain is intact (or: broken from event k); content checksums: N mismatches; index columns: P mismatches with the event header; M positions removed by deletion", and lists the position of every mismatch.
  "Removed" (has a removal marker, normal) and "mismatch" (damage) are reported separately. A removal marker must point to a tombstone (`deletion.executed`), and the position list of that tombstone must list this block; otherwise it counts as a mismatch. A block that the event type must have that is missing as a whole row counts as a mismatch at that position; when what is missing is the metadata block `target`, the index columns of that event are no longer checked. A mismatch between the index columns (the columns of the event table split out from the event header and the `target` block) and the event header is listed separately and does not count as a chain break: what is damaged is the derived index, which can be repaired by recomputing from the event header and the `target` block; a chain break means the event header itself has a problem. A stored event header hash that differs from the hash recomputed from the event header counts as a break at that event.

## Records of writes and reads

For an example see the guide [`../../guide/02-walkthrough.md`](../../guide/02-walkthrough.md): every step lists the log events appended (where it disagrees with this directory, this directory holds).

### The write log: `change_log` + `change_sources`

- **change_log**: each write records three kinds of event in the log:
  - **Logical write head**: **one per write request that produces events**, however many rows it changes; it is the head event of the operation. It records the **original arguments** (the original values of the fields of each op that are not no-ops, the ID list of the no-op fields, the original form of the interval arguments, the premises declared by each op, see "The premises of a write"), the total number of ops in the request, the request key or the explicit idempotency key with its content fingerprint, the reported task identifier, `sv` (and whether it was given explicitly or obtained by fallback), the "now" used in judgement and the "today" in the slot's time zone, the `ver` each op saw (and whether it was given explicitly, obtained by fallback, created by an earlier op of this request, or the sync baseline position taken by external key; for an op by external key the baseline position of each field is also recorded, see "Writing by external key"), and the rule version and the policy version. "Whether it is retroactive" is not recorded separately: it is derived by comparing the recorded "now" and "today" with the resolved result. Its `seq` is the **operation number** of this write. A request that contains only ops by external key does not record a request key; a request by external key whose ops are all unchanged or skipped produces no events at all, and so has no logical write head.
  - **Base write** (an agent / caller writing to a base table): one per affected row / entity for each op. **It records only the fields that this request touches and that are not no-ops.** The contribution to a field is **several items sorted by interval** (an event table or timeless table always has exactly one item): each item has its own value, the **resolved valid interval** (state tables; a separate block, which also records the other contributions used in the resolution, see "Deletion · Content derived from other contributions"), source, **effect status** and the judgement result at write time (see below). Cases in which a field has several items: `undo` and take the previous value must write back several different older values; in a corroborated interval some parts still have the same value and some have since been changed by someone else. **It records neither the value before the write nor the whole row after the write**: the value before the write is a copy of an earlier event, and each extra copy means one more place to clean up in a privacy deletion; the state after the write follows deterministically from "the state before + the fields in effect in this event", and a read by instant walks the version table. For a state table an op records one event per entity, and the physical segments are produced by `apply` by normalizing after the per-item interval assignment (judgement is not included).
  - **Derived write** (the rule engine refreshing a derived cache): records only the rule version, the `partition_id` of the derived row and the log position at read time; the content records the group key value and the result checksum, and **does not store the values before and after the write**
    because they can be recomputed at any time from base data + rules.
- **The order of the events within one write**: logical write head → source data (one per piece of evidence; when no evidence is carried, one per op that left something in the event) → for each op (in the order of the request), its base write and the item events it brings about → premise change (`premise.changed`, one when there is a change, see "The premises of a write") → the derived writes after all ops. They are committed in one transaction with consecutive `seq` ([`../09-event-format.md`](../09-event-format.md) 4.2).
- **The effect status of each item**: `applied` (in effect), `candidate` (becomes a conflict candidate), `awaiting` (high-impact, awaiting confirmation), `corroborated` (the same value with evidence explicitly pointed to: only a source is appended). `apply` writes only `applied` items into the business tables and the version table, and writes `corroborated` ones into the source table; the others stay only in the log, for `timeline`, items and deletion replay to use.
- **A no-op field** (the same value and no evidence pointed to) is not a contribution: it is not in the base write event, its value is left nowhere in the log, and only the field ID is listed in the logical write head (so that audit and the receipt of an idempotent replay can give `noop`). A later adoption or confirmation is a new write triggered by `resolve`, with its own head event and operation number, and its value source is a reference to the original candidate / proposal contribution.
- **A request in which all fields are no-ops**: source data is stored as usual, the logical write head is recorded (with the request key; a resend replays idempotently), no base write is recorded, and `ver` does not change. Evidence is an asset and is not discarded just because no value changed. The exception is an op by external key: ones that are unchanged (`unchanged`) or skipped (`skipped`) go into no event, and a request whose ops are all of these two kinds appends no event (see "Writing by external key"). A restate or clear of premises also has no base write, and its event composition is the same as here, with the declarations added in the head event. An `undo` whose parts are all skipped is different: a base write is recorded as usual, with no written-back items in it, only the revert record (which operations' changes on which targets were reverted must be kept, so that when a write that covered them is later privacy-deleted, this undo can take effect in replay); `ver` does not change.
- **Judgement results at write time** are recorded in the base write event and are not recomputed in replay: suspected duplicates (not recomputed in a privacy deletion either, see "Suspected duplicates"); literal matches, recorded as hit / miss / not applicable for "each item of a field × each piece of evidence that item cites", together with the checker version (rules in "Source level").
- **Resolution results follow the most recent one given**: the default end, the default interval of a correction, and the first-creation mark are mechanical judgements. When the replay of a privacy deletion changes them, the new result is recorded in that deletion event; afterwards `undo`, the conflict criterion and references to this contribution all follow the latest (see "Deletion · How the result lands in the log").
- **change_sources**: what caused this write; many-to-many; two kinds of source:
  - Source data (a sentence the user said, a tool result, ...): the source of a base write, committed by the writer together with the write;
  - Upstream writes: the source of a derived write, recorded automatically by the rule engine according to the inputs actually read. This kind is what makes cascading work.
- Physically it is two tables: `base_sources` (base write → source data, with the field list and the source kind: value source / operation source / interval source, see "Deletion · Provenance") and `derived_reads` (derived write → rule version, base table, `partition_id`, log position; group key values are not stored).
  **To find "which derived writes used a given base version"**: take the partitions where the before and after values of that version fall (map the group key value to `partition_id`), and in `derived_reads` find the derived writes whose `partition_id` matches
  and where the valid interval of that base version covers the log position of the read set; then repeat downstream along the derivation dependencies.
- The previous version of the same row is obtained by ordering change_log by row, and is not recorded in change_sources separately.
- The business table writes, change_log and change_sources are **committed in the same transaction**.
- **Recorded time = the sequence number of the log** (monotonic per tenant). Writes are serialized per tenant (`pg_advisory_xact_lock`), so the sequence number is the commit order, and it is carried over unchanged when the log is replicated.
  - **Externally the operation number is always used**: a write, a write triggered by `resolve`, a deletion confirmation and a deletion cancellation each have one head event, and its `seq` is the operation number of that operation. The `seq` of a receipt, the sequence number in `ver`, the #n of `timeline`, the n of `undo`, the `since` (exclusive) / `until` (inclusive) of `changes`, and the recorded-time interval of the version table all use it; the `seq` of source data events and of the base write events of each row is not exposed.
  - **`as_of: S`** = the state when all operations whose operation number is not greater than S have taken effect completely; an S that falls in the middle of an operation is equivalent to falling on its operation number, so a half-written state can never be read. When an instant is given, it is converted to an operation number by the recorded instant; an instant in the future equals the latest.
  - **The recorded instant** is stored separately and kept monotonic by the kernel: = max(the `now` of the calling context, the recorded instant of the previous event); `NOW()` is not used (it returns the transaction start time, which can disagree with the commit order). All judgements in this operation that concern "now" use it (architecture §7 "The recorded instant").
- **Replay uses the recorded results**: one write may change many rows and split into many segments (for example, a backdated change splits the valid interval); in replay `apply` follows the resolution results in the event and does not rerun the splitting algorithm.
- This is an application-layer log, not PostgreSQL's WAL: the WAL is a physical log and does not know about "source data".
- **Reads by instant are implemented programmatically from change_log**: in principle, replaying the log to a position gives the state at that time; to make queries fast,
  a **version table** is also maintained from change_log: recorded per cell (one entry for each value of a field of a row or entity over a stretch of valid time), marked with the validity interval "from which operation number to which operation number",
  and a query by instant takes only the versions whose interval covers that instant (this is the SQL:2011 system-versioned table, natively supported by SQL Server and MariaDB).
  The version table stores the field values of that version (not a reference to content), so a read by instant is an ordinary query; on physical erasure the corresponding values in the version table are cleared together. Derived data stores no history and is recomputed from the base data of that moment.
  Version intervals are stored from the first version on (the data structure is hard to add later). **Which are exposed**: queries by valid time (`valid_at` / `valid_during`) are exposed in the first version;
  reads by instant (`as_of`) are exposed only in audit and restore interfaces.

### The read record: `read_log`

Uses:

1. **Correction impact**: after data is corrected, find which tasks read values based on the wrong data (conflict handling item 5).
   See "Querying the reads a correction affects" below.
2. **Restoring by instant**: which version a task saw at that time.
3. **Security audit**: which connection read which data.

Fields: read_id, time, actor (connection), task / session identifier (provided by the caller, may be empty), what was read (for a catalog read: the slot, the table and the `sv` read; for a data read: the table, the row or the `partition_id` of the derived row, the source data ID; for a query condition, only a **structural fingerprint that contains no user values**: the normalized text after replacing literals with placeholders, names with IDs, and removing aliases and comments, stored directly as text and not as a hash, algorithm in "Reads · What shape a read record keeps"),
the versions obtained (the version `seq` read for each row, **no content hash is recorded**), the **position of the state seen** (the state at which operation number this read saw: for the first page and for `timeline`, the latest operation number at the time of the read; for `query` and the later pages of each call, the operation number of the first page; for the `as_of` of `history`, its record point; for `changes`, its `until`), **whether it is a historical read by recorded instant** (a read with `as_of`: what is read is a historical version, which does not count as a read, see contract §2), and the **valid-time condition** (such as "query the budget of 11-03"; if it is not recorded, the correction impact query over-reports.
**A read that passes no time is recorded as the entry instant**: a state table takes the current segment by default, and what is read is "now"; with `granularity: date` it is recorded as that day in the slot's time zone),
and the **"current instant" taken at entry** (`NOW()` is forbidden in restricted SQL, and the entry takes it once for all).

**Who can query the read record**: a user session sees the complete audit through HTTP; an agent, through `history` (`saveslot_history` on MCP), can see the reads of **any connection** on a target,
but is given only the version read, the instant, the connection name and `task`, and **not the query condition**; the target must be within the visible range of this credential (see "Visible scope").
This makes "which version a task saw at that time" answerable on MCP.

**After an import the read record starts from scratch**: the read record is local running state and is not in the export. After importing into an empty tenant, the read audit restarts from the moment of the import, the correction impact query cannot find reads from before the import (the result states up to which moment it covers), and the fallback for `ver` and `sv` also starts from zero (see the import paragraph in "Deletion · The deletion register").

Principles:

- **Record only version numbers, not values, and not hashes computed from values.** read_log does not become a second copy of the data; the content of deleted data does not remain in the read record, and there is no way to compare it with a guessed value.
- **The granularity is "the version of a row".** A query that returns many rows records many versions. A state table is recorded per entity: if several segments of an entity have the same version, one entry is recorded. Row-by-row reads (`query`, `history`) return at most 1,000 rows per page, so the number of versions recorded by one read has an upper bound.
- **When too much is read, a table-level record is recorded instead.** The aggregates and joins of restricted SQL can read many rows and return only one, and the cost of recording row by row would grow with the amount of data. The rule: when the number of row versions one read reads on **one base table** (not fewer than actually read: the rows of the query layer where that table sits that passed FROM and WHERE; the way of counting is in write-and-read "How many are recorded") exceeds a threshold (initial value 1,000), that table is not recorded row by row; **one table-level record** is recorded instead: the table ID, the position of the state seen (see above), the valid-time condition, and the structural fingerprint. Tables that do not exceed the threshold are still recorded row by row; when one read involves several tables, each is judged separately. A table-level record does not record the number of rows: the number of rows is decided by user content, and recording it serves no purpose.
- **Independent of the write log.** It has its own retention period: in the first version a single number at the tenant level, default 180 days, lower limit 30 days (initial values, adjusted with the evals); a longer retention period per slot (sensitive data that requires keeping everything) is added later. The correction impact query covers only reads within the retention period, and the result states up to which day it covers; cleaning up by period does not affect the event header chain of the write log.
- **Reads far outnumber writes.** Recording must be cheap: batch the writes and aggregate by task.

### Querying the reads a correction affects

**After data is corrected (or revoked, changed retroactively, or a future plan changes), find which reads used a value that no longer holds.** change_sources answers "which versions are affected",
and read_log answers "who read those versions"; only the two together can find it.

```
correction source R ──change_sources──> correction write (e.g. C5)
                    ──change_log back by field──> the versions that were corrected (the versions from the one where the field got the wrong value, e.g. C1)
                    ──change_sources recursing downstream──> affected set C (C1, C2, C4)
                    ──read_log matching versions──> reads that used the wrong versions (r1)
```

- **Group by union**: a correction may move a row to another group (for example the date changes from 11-03 to 11-10), and the affected derived rows = the union of the before and after groups.
- **Derived rows computed at read time** (rules that depend on "today", and rules that read a state table without a valid-time qualifier) have no derived write to match: read_log records "rule version + entry instant + the log position at read time (the latest operation number)", and matches by "whether the base tables the rule reads have affected versions after that position", reporting too many rather than too few.
- **The valid-time condition of a restricted SQL read**: with `FOR VALID_TIME`, it is recorded according to the time condition learned during rewriting; without it, the entry instant is recorded (the current segment is read). Arbitrary predicates on a time column in `WHERE` are not parsed. A restricted SQL read on an event table is matched by "the set of versions read", reporting too many rather than too few, and the result is marked "possibly affected".
- **Matching of table-level records** (see the threshold rule in "The read record"): if the affected set contains even one version of this table, and it was the version at that time at the position of the state seen of this read (the recorded-time interval of the version covers that position), the read counts as a hit; on a state table where a valid-time condition is recorded, it is further required that the affected valid-time interval intersects it. A hit is marked "possibly affected": a table-level record cannot say whether this read actually used that row, so it reports too many rather than too few. It does not take part in the fallback for `ver`.
- **The first version covers only reads on the primary node**: the read records of offline nodes are not synchronized back to the primary node (see "Sync protocol").
- **The starting point is the version that was corrected, not the correction write, and the trace goes back by field.** Going downstream directly from R gives C5, C6 ... the correct versions after the correction;
  one must find through change_log **the write in which that field most recently obtained the corrected value**, and **all versions** from it up to before the correction are starting points, and only then go downstream.
  The same wrong value often spans several versions (in between someone changed other fields), and taking only "the previous version" would miss the earlier versions that are equally wrong, and their reads.
  A state table is traced back by "field + valid-time interval".
  **A revoke has no "wrong value" to trace back**: the starting points are all the versions of that row from insertion to just before the revoke.
- **What triggers it.** The criterion is structural: for some (field, valid instant) that a read asked about, if the value between the version it read and now has changed, it is affected.

  Event tables and timeless tables (they have no valid-time interval, and whether "the value read earlier was correct at the time" is known only to the agent, so the intent is looked at):

  | Write | Meaning | Checked or not | Wording of `possibly_affected` |
  |---|---|---|---|
  | Correction (`correct`, explicitly marked by the agent) | The old value was wrong all along | Checked | "The value you read has been corrected" |
  | Revoking a row (`revoke`, including one triggered by a `flagged` item) | This record should never have existed, and any read that contains it is wrong | Checked | "A record contained in the value you read has been revoked" |
  | System ruling (a candidate becomes the value in effect on the spot under the conflict rules; not produced in the first version) | The value in effect was changed by a rule, and the old value read earlier is no longer the value in effect | Checked (same as a correction) | "The value you read has changed under the conflict rules" |
  | `update` | Supplements or modifies information; the earlier read was correct at the time | Not checked | none |

  State tables: **any write that makes a value change is checked**, regardless of whether the start of validity is before or after the present. If the (field, valid-time interval) in which the value actually changed intersects the valid-time condition recorded in read_log, and the version that read read is earlier than this write, it is flagged. The reason code depends on the case:

  | Case | `reason` | Wording |
  |---|---|---|
  | The intent is `correct` | `correct` | "The value you read has been corrected" |
  | The part of the changed interval that is earlier than "now" | `retroactive` | "The value at the valid time you read has since been changed retroactively" |
  | The part of the changed interval that is not earlier than "now" | `plan_changed` | "A future plan you read has changed" |

  A retroactive change may be "it changed long ago but was learned late", or "decided today, effective backwards"; saveslot cannot tell which, so the wording stays neutral: only when the agent explicitly marks `correct` is "has been corrected" said.
  A read that passes no time is recorded as the entry instant (as that day for day granularity), so "read today's value earlier today, and today's value is changed afterwards" is hit naturally by the same criterion.
- **The scope is the part where the value actually changed**: on a state table only the valid-time intervals where the value really changed count, and the parts covered by the same value do not (see "Time · Three kinds of table").
- **The correcting party's own locating read is excluded**: the read used before the correction to find this row does not count as affected, because it was read in order to make the correction. `ver` corresponds to a version, not to a particular read, so precisely:
  **the most recent row-by-row read of that target and that version by the same connection + the same `task` (when no `task` is carried, only the connection)**; when `ver` was obtained by fallback, it is the read used for the fallback.
- **The flag is removed when the value is restored**: if a later revert or change makes the value that a read saw at the time hold again (for example, after being changed retroactively to 3000 it is reverted to 5000), the `possibly_affected` of that read is removed.
  The comparison is made one by one over "the fields that read asked about × valid time", and the flag is removed only if all are restored; this check is made for all writes that reach a target carrying flags, and also for deletion confirmations and cancelled deletions (only removing, never adding, see "After deletion").
- **One correction may change many rows** (such as "all runs last week were recorded 1 km too many"): each corrected version goes downstream separately and the results are merged.
- **Query incrementally each time a correction happens, not by periodic full scans.** Only the impact of this one correction is computed, and the result is stored on the spot as flags (belonging to the read audit, and like read_log part of the local running state);
  it is carried out with the result at the next relevant read, and does not depend on push.
- **Relationship with the premises of a write** (see the next section): the two share the computation of "which (row, field, valid-time interval) values actually changed in this operation", the comparison of "the flag is removed when the value is restored", and the division into three reasons on state tables. The differences are: the correction impact query matches read records, and the flag is given only to the connection that read it and is stored in local running state; a premise matches declarations in the log, and the flag is given to any reader and is derived from the log. The trigger condition differs in only one place: an `update` on an event table or timeless table does not trigger the correction impact query, but does make the premise change.

### The premises of a write

**A write can declare which values already read it takes as its premise; if a premise later changes, the rows that depend on it carry `premise_changed` (premise changed), visible to any reader.** The value does not move: whether the row still holds is for the agent to judge, and saveslot only points out that the premise changed. A write that declares no premises behaves exactly as if this mechanism did not exist.

Example: an agent reads the row "release date December 1", writes three tasks on that basis; the user then changes the release date to November 20. The values of the three tasks have not changed, but they stand on a value that has changed. The read record can only tell the connection that read the release date "the value you read has changed"; another agent reading the task list sees three normal tasks. A premise puts this relationship into the log and points it out on the task rows.

| Concept | What it points to | After the target changes |
|---|---|---|
| Evidence | The original text of source data: which sentence this value came from | The original text cannot "change", it can only be privacy-deleted; deletion cascades along the value source |
| `ref` field | The ID of another row, which is the **value** of this row | The referring side does not move; when the target is revoked or deleted it carries `dangling_ref`; a change in the target's field values is not flagged |
| Derivation dependency | The tables and columns a rule refers to | Recomputed in the same transaction, the value follows automatically |
| Read record | The version a read read | Only reminds the connection that read it (`possibly_affected`); not in the log, has a retention period |
| **Premise** | The values of some fields of another row in saveslot at some version: the value of this row was written after looking at them | This row carries `premise_changed` for any reader; the value does not move, and waits for the agent to handle it |

Deletion propagates only along evidence, **not along premises** (see "Deletion · Two principles").

**Only explicit declarations are accepted; nothing is inferred automatically.** Which values read were really used is known only to the agent; treating "everything this connection read before" as premises would over-report to the point of no signal, and moreover the read record is not in the log, its granularity cannot reach fields, and it cannot see session boundaries. Under-reporting is handled by tool descriptions and evals (eval 10). "Taint tracking" inferred from the read record remains an option (see "Integrity of provenance") and can later be added, purely incrementally, as a weaker kind of flag.

**What a declaration has** (the optional `premises` on an op, an array; for the type see `PremiseRef` in [`../04-contract-types.md`](../04-contract-types.md)):

| Element | Rule |
|---|---|
| Target | A row or an entity, written the same way as a write target (`row`, `entity` or `entity_key`, or the temporary name of a row newly created in this request), exactly one given besides `table`. There is no form by external key: read the row ID first and then declare |
| `fields` | Optional. If given, the premise counts as changed only when these fields change; not given = the whole row (any field, and whether the row exists) |
| `ver` | Should be passed back as obtained when reading it. If not carried, the same fallback as for the `ver` of the write target is used (`warnings` gives `premise_ver_fallback`), and when there is nothing to fall back on it reports `read_first`. When the target is a row newly created in this request, the version seen is recorded as "this request" |
| Valid time | Only for targets on state tables: `valid_at` (a point) or `valid_during` (a stretch), mutually exclusive; when neither is given, see below |
| Value | **Not recorded**; only the identifier and the version are. The value of a premise is a copy of another contribution, and each extra copy means one more place to clean up in a privacy deletion (the same reason as for "the value before the write is not recorded") |

**An origin item has only one effective declaration for a premise target**: one set of fields, one range (see "Superseding" below). So when two declarations in the `premises` of one op resolve to the same target, it is rejected with `invalid_argument` (`premise_duplicate_target`, pointing to the one that appears later, with the indexes of the two attached); the judgement is made by the resolved target, and `row` and `entity_key` may point to the same one. To take several fields of the same target as premises, merge them into the `fields` of one declaration; to take two stretches of valid time as premises, give a `valid_during` that covers both, or give no range, reporting too many rather than too few.

**What range is taken when a target on a state table gives no valid time.** With "the budget of November" as the premise, a change to the budget of December should not set a flag; a plan by day takes only the target of that day as its premise. So:

- **If the dependent row (the row that declares the premises) has valid time of its own, take that.** A dependent row on an event table: take the value of the time field written by this op (a point), regardless of whether this part is in effect, became a candidate or went to awaiting confirmation; the declaration says "as I wrote this row", and whether it is adopted later does not change that; if this op wrote no time field, take the value in effect of this field after the op. A dependent row on a state table: take the interval written by this op, again regardless of whether it is in effect.
- **When the dependent row has no valid time** (a timeless table; an event table whose time field is empty; a restate or clear without an interval on a state table), take "from now on": `[entry instant, ∞)`. The read record records a read that passes no time as the point of the entry instant, because it asks whether what was read at that time was correct; a premise looks forward: a plan laid out by "the current budget" should be pointed out at the moment "the budget goes down from next month" is recorded, and that write did not change the value at the point "now".
- **Aligned by granularity** (see "Time · Three kinds of table"): when the table of the target has `date` granularity, an instant is taken as that day in the slot's time zone, and "from now on" starts from "today". When the target has `instant` granularity and the time of the dependent row is a date, take the start and end instants of that day in the slot's time zone. When the interval of the dependent row is an `instant`-granularity `[a, b)` and the target has `date` granularity, take every day that intersects it: from the day containing `a`, up to the day after the day containing the last moment before `b` (when `b` is exactly at midnight it is the day of `b`; an open end stays open). Better to report one day too many than to miss one.
- **A range taken from the dependent row is fixed at declaration time.** If the time of the dependent row is changed later, the range does not follow: changing the time is a write, and the agent simply carries the new premises when it changes it.
- "From now on" is derived from the entry instant and contains no value given by the caller, so it is metadata; an explicitly given valid time and a valid time taken from the dependent row are content, recorded in the data block with a source (see "Deletion · Content derived from source data").

**What it can point to**:

| Target | First version |
|---|---|
| A row / entity of a base table in the same slot | Yes |
| A row newly created in this request | Yes ("create a milestone, then three tasks that take it as their premise" in one request): `row` is written as the temporary name `"@m"` given by an earlier op with `as`, or, by `entity_key`, an entity newly created earlier in this request. The state seen is taken at the end of this request (`ver.basis: "same_request"`; a later op in the same request changing it again does not count as the premise changing), and `ver` is not carried (carrying it reports `invalid_argument` (`mutually_exclusive`)); when that creation did not take effect in this request (went to awaiting confirmation or became a candidate), the declaring side is rejected with `invalid_argument` (`premise_target_pending`, with the temporary name of the target and the index of that op); send that creation on its own first, and declare after it takes effect. When the temporary name is bound to an existing row hit by external key, it is that row, with `ver` carried as usual (or fallback) |
| The target row of this op itself | No, `invalid_argument` (`premise_self`) |
| A row of a derived table | No, `not_in_this_version`. The impact query of the first version does not cover reads of derived values, and derived rows store no history, so there is nothing to compare for "the flag is removed when the value is restored". To take a derived total as a premise, declare the base rows it summarizes |
| A table of another slot (the table is within the visible range) | No, `invalid_argument` (`cross_slot`). `ref`, writes and deletions are all limited to one slot; a flag across slots has no answer under partial copying by slot and under visible range by slot |
| A table or row outside the visible range | The same as not existing: a table reports `unknown_table`, a row reports `not_found` (see "Visible scope") |
| A historical version read by instant | No, `invalid_argument` (`premise_historical_ver`): taking a value that is long since no longer current as the premise, it has already changed at declaration time |

**Which ops can carry it**:

| op | Can it carry | Meaning |
|---|---|---|
| `insert` | Yes | The newly written row takes these as its premise |
| `update` / `correct`, with `set` | Yes | The value written this time takes these as its premise; the other still-effective values of this row are also checked against these (see "covering" below) |
| `update`, without `set`, with non-empty `premises` | Yes | **Restate**: the value does not change, and the values this row now has still hold on the basis of these premises |
| `update`, with `premises: []` (with or without `set`) | Yes | **Clear**: all premise declarations of this row are removed, and the flags disappear with them. This is the only way to remove premises |
| An op with `revert` | No, `invalid_argument` (`premises_with_revert`) | A revert writes back the values of other contributions, and their own premises come back together with the contributions |
| `revoke` | No, `invalid_argument` (`premises_with_revoke`) | A revoke gives no value |
| `resolve` | No (it has no such parameter) | Adopting a candidate or confirming a proposal carries over the contribution of the original write, and the premises of the original write take effect with it |
| An op by external key | No, `invalid_argument` (`premises_with_external_key`) | A connector has not read the row it writes, and an op by external key that is unchanged goes into no event. To declare premises, let the agent restate them separately after reading |

- A restate or clear whose target row is already revoked reports `revoked`, the same as an ordinary `update`. An `update` without `set` that also carries no `premises` reports `invalid_argument` (`missing`).
- **The validation of premises** is in step 5 of the order of judgement (validation that depends on the current state, at the same place as the `ref` target), and is done for all the declarations an op carries, whether or not the op takes effect; the format and mutual-exclusion checks are in step 1. When the target does not exist, has been privacy-deleted or is outside the visible range, it is **rejected** (`not_found`, with the position of the declaration at fault; when removed by a deletion within the grace period, the deletion ID is attached): taking something that does not exist as a premise is most likely a mistyped ID. When the target has been revoked, the write is **made as usual and the flag is set immediately** (reason `revoke`) when the version seen is earlier than that revoke: the row existed and was read, and its later revocation is exactly "the premise changed". When the version seen is itself that revoke (what was read is the revoked state), `current` is recorded and no flag is set: nothing has changed since.
- **A `ver` that has expired is not rejected**: when the current value on the declared range differs from the value at the version seen (for the criterion see "What counts as a changed premise" below; a value that changed in between and changed back does not count), the write is made as usual and this row carries the flag as soon as it is written (`state: "changed"` in the receipt, and `warnings` gives `premise_already_changed`); when they are the same, the write is made as usual and no flag is set. Rejecting would leave the evidence unrecorded; recording it as a candidate leaves no "current value" to conflict with. A `ver` obtained before a restore from backup or an import has its position seen converted according to the rule for `ver` in "Deletion · The deletion register", and then these two paragraphs are applied.

**What counts as a changed premise**: **the premise of a declaration has changed if and only if, on the (field × valid time) it declares, the current value differs from the value at the version seen.** On event tables and timeless tables the range is the declared fields; on state tables it is field × valid time. "Value" is compared by the same-value criterion of the field type (see "Criteria for the same value"). **When the target is revoked, regardless of which fields were declared, it always counts as changed**: the revoke intersects every field (on a state table valid time must also intersect). This is the same sentence as the criterion of the correction impact query, and the trigger condition differs in only one place:

| Write | Correction impact query (`possibly_affected`) | Premise (`premise_changed`) |
|---|---|---|
| Event table, timeless table: `correct` | Checked | Flagged, reason `correct` |
| Event table, timeless table: `revoke` | Checked | Flagged, reason `revoke` |
| Event table, timeless table: `update` | **Not checked** | **Flagged**, reason `update` |
| State table: any write that makes a value change | Checked, reason `correct` / `retroactive` / `plan_changed` | Flagged, same reason; a revoke with an interval is recorded as `revoke`. When one write has both a retroactive part and a future part on the declared range, the reason is `retroactive` |
| A write with the same value (no-op, corroboration) | Not checked | Not flagged |
| A write that becomes a candidate or goes to awaiting confirmation | Not checked (not in effect) | Not flagged; when it is later adopted or confirmed, judged by the write that resolution triggers |
| Revert (`undo`), take the previous value | One write, by its intent and the actual change | Same as the left; most of the time the effect is to remove the flag |
| A privacy deletion changed a value | Only removing, never adding | **Flagged**, reason `deleted` (see "Deletion · After deletion") |

- **Why `update` is flagged too**: the correction impact query asks about the past: was the value read earlier correct at the time, and `update` means it was correct at the time. A premise asks about the present: what this row now stands on; if the release date changed, whether it was recorded wrongly or changed by decision, the tasks all need a fresh look.
- **When retroactive and future parts coexist, take `retroactive`**: a declaration gets only one reason, and `retroactive` says that "the part that is already past has also changed", which makes the reader look back at least once, a stronger hint than `plan_changed`.
- There are seven reason codes in total: `correct`, `update`, `revoke`, `retroactive`, `plan_changed`, `deleted`, `schema_switched` (a schema switch removed the declared field, see the end of "Detection" below).
- Some common cases: only `date` was declared and the target's `name` changed: not flagged; the change to the target is undone with `undo`, or changed back to the same value by another write: the flag is removed (not a special rule, the criterion is the value); the dependent row has been restated on the new value and then the change to the target is undone with `undo`: **flagged again**, with the reason taken from the intent of that `undo` write; the target has an open conflict: not flagged because of the dispute itself (the value in effect has not changed).

**Covering, superseding and clearing**. An op that carries `premises` means "by the version I saw, the values this row now has take these as their premises". It covers two parts:

1. **The items this op itself writes** (whether in effect, candidate or awaiting confirmation): covered by (event, target), that is, all items of this op on that target, including the indexes newly produced on them by deletion restatement.
2. **The other items of this row that were already in effect at the version the op saw and are still in effect after the op**, recorded explicitly in the event. They are covered only when all fields of this op are already in effect (`applied`, `corroborated`, `noop`): when some field became a candidate or went to awaiting confirmation, its judgement about the whole row takes the landing of its own change as its premise. When this op later takes effect through adopting a candidate or through deletion, part 2 is not recorded additionally, and the other fields of this row still show flags according to the original declarations.

A restate has no part 1, only part 2.

- **Superseding**: for the same origin item (see below) and the same premise target, the latest declaration that covers it prevails. So if `due` is changed and premises pointing to the new version of the release date are carried, the old declarations of `title` and `status` are superseded together and the flags disappear; if `due` is changed without `premises`, the new value of `due` has no premise, and `title` and `status` still follow the old declarations; if the new `premises` point to another row, that adds a premise, and the old declarations are not affected.
- **Clear** (`premises: []`): on the items it covers, all declarations before it become invalid together, whichever target they point to; the items it writes itself have no premise. **Part 2 of a clear is not subject to the restriction "all fields are already in effect"**: a clear makes no judgement on values, so even if a field of a clear with `set` became a candidate or went to awaiting confirmation, the other items of this row that were already in effect at the version seen and are still in effect are cleared all the same: "clear the premise declarations of this row" means the whole row. To remove only one of two premises: in the same request clear first, then use a restate op to declare the one to keep (later ops see the results of earlier ones). When the premise target has been privacy-deleted as a whole row, restating it reports `not_found`, and the flag is removed with a clear.
- A restate and a clear should carry the `ver` of the dependent row (or fallback): they cover only the items that were already in effect at the version seen, and values that others wrote into this row after you read it, which you have not seen, are not restated for you. They make no conflict judgement and never become candidates.
- A restate and a clear are one `write`: with an operation number, a logical write head and source data, **no base write**, and the `ver` of the row does not change. They cannot be undone with `undo` (there is no change to undo); to overturn a restate, restate again or rewrite.
- **Setting a flag, removing a flag, restating and clearing all leave the `ver` of the dependent row unchanged**: the value has not changed, and the `ver` in other agents' hands should not be invalidated because of it.

**On which row a flag appears.** A premise hangs on a contribution, not on a row: when a revert, taking the previous value, or deletion replay brings the value back to an earlier contribution, the premise goes back with it. The flag on a row (on a state table: a segment) is computed at read time:

1. Take the **origin item of the current value** of each field: the contribution that gives the current value; if it was carried over (a revert, adopting a candidate, the written-back items of taking the previous value, and the carry-overs in a deletion result), follow the carry-over references to the end; add the corroboration items that still count (the same as the current value, not reverted, and on a state table with an interval that intersects this cell; if the value changes away and back again, the earlier corroborations still count). A value whose source is a schema constant, "no value", and a written-back item that only does registration have no origin item.
2. Find the effective declarations that cover these origin items (excluding superseded ones and ones invalidated by a later clear). Part 1 covers by (event, target), and the indexes newly produced by deletion restatement are covered with it; part 2 covers by the recorded items, and the indexes newly produced by deletion restatement are covered together with the item they were split from; "which item it was split from" is judged by the interval block at the time of writing, and when that block has been cleared by a deletion executed on schedule, by the original interval of that item (see "Deletion · The authoritative definition of reverting" step 6).
3. For those whose state is "changed", each produces one flag; the `fields` in the flag are the fields it covers, listing only those still present in the current version.

The premise of an old value that was covered by a later write is no longer shown. When a read asked for `fields` and none of those fields is in the `fields` of a flag, that flag is not carried (the same rule as for `disputed` and `awaiting`). A row lists at most 10, from newest to oldest by `since`, and gives the total separately. The input flags of derived rows and the flag summary of `sql` each add one count, counting only base rows that carry this flag on the fields the rule depends on. For the shape of the flag see [`../04-contract.md`](../04-contract.md) section 7.

**Detection**. After an operation (a write, a write triggered by a resolution, a deletion confirmation, a cancelled deletion) has produced its base events (for a schema switch see the end of this section):

1. Take the (row, field or "existence", valid-time interval) in this operation **whose value actually changed**: an input the correction impact query already has. For a deletion confirmation and a cancellation, take the fields and segments in the result whose value differs from before the deletion (before the cancellation); a change only of who gives the value, with the value unchanged, does not count. **Also the declarations whose range was changed to the whole timeline by this deletion**: when a deletion confirmation lists the valid time that a declaration took from its dependent row (`premise_valid`) in the position list, from this deletion confirmation on that declaration is treated as covering the whole timeline (not waiting for the tombstone), and in this detection it is judged once more over the whole timeline: if it is still "unchanged" but the value on the whole timeline now differs from the version seen, **or the content of that cell at the version seen has been deleted or is pending deletion (cannot be compared)**, it is converted to "changed" (better to over-report; "unchanged" still means the value equals what was seen), with `since` being this operation number and the reason `deleted`, written into the premise change event of this operation. When this deletion is cancelled the range is restored and judged once more in the same way (those "changed" are compared over the restored range, and those that are the same and comparable are converted back to "unchanged"). The tombstone is responsible only for clearing the copy of valid time in `premise_decls`.
2. **Set flags**: find the declarations in state "unchanged" by premise target; those whose declared fields and range intersect the result of step 1 are converted to "changed", with `since` being this operation number and the reason taken from the intent of this write (a revoke is always `revoke`, a deletion is `deleted`, and on state tables with coexisting retroactive and future parts `retroactive`). This step does not read history: a declaration being "unchanged" means that up to before this operation the value on its range had always equaled the value seen; if this operation changed it, it has changed.
3. **Remove flags**: find the declarations in state "changed" by premise target; those whose range intersects the result of step 1 have "the current value" compared with "the value at the version seen"; only if all are the same and comparable (the content of that cell at the version seen has neither been deleted nor is pending deletion) are they converted back to "unchanged". After a schema switch both sides read the version table of the current version: the switch converts item by item, the origin items (event, field ID, index) do not change, and the version seen is an operation number, independent of the schema version, so there is no need to read historical values across versions, and `premise_edges` is not converted by the switch either; when `migrate` is not injective, two values that were different before become the same in the new version, and removing a flag holds more easily than before, since what is compared is the value on the new version. The switch itself does not re-judge declarations: this kind of flag removal happens in the next operation after the switch that touches this premise target, compared as in this step, with both sides reading the new version.
4. **Re-pointing** (only in deletion confirmations and cancellations): for a declaration that is still "changed", if this deletion changed the value on its range, or removed the contribution that the operation its `since` points to made on this range, `since` is changed to this operation number and the reason to `deleted`. Otherwise the flag would point to an operation that did nothing after the deletion.
5. The results of steps 2 to 4 are written as one `premise.changed` (present only when there is a change, at most one per operation).

A **schema switch** does not follow the five steps above: a switch changes only the notation, not the facts the agent uses, and sets no flag, removes no flag, and re-points nothing. The one exception is when the new version removes a field that a declaration declares (including fields removed with a dropped table): declarations of this kind that are "unchanged" are converted to "changed", with `since` being the operation number of the switch and the reason `schema_switched`, written into a `premise.changed` in the switch operation; those already "changed" are left alone (`since` and `reason` stay); a declaration that declared several fields and lost only one of them is likewise converted to "changed"; the declaration is not widened to the whole row.

Only declarations that are still effective for some origin item are processed, including declarations in candidate and awaiting-confirmation writes (their state is directly usable when they later take effect). `since` records the first operation that made the premise differ, and later changes of the premise do not record it again (except re-pointing): otherwise every time the depended-on row changed, all the dependent rows already carrying flags would have to be listed again in the event.

**Invariant** (written as a property test): for each declaration that is still effective, if its state is "unchanged", the current value on its range equals the value at the version seen. The reverse direction is not required: when comparison is impossible, over-reporting is allowed.

**Not transitive**. A changes; B, which takes A as its premise, carries a flag; the value of B has not changed, and C, which takes B as its premise, does not. C declares "taking the value of B at some version as the premise", the value of B has not changed, and by the criterion the premise of C has not changed; flagging C would be asserting on the agent's behalf that B has become invalid. If B changes its value when handled, C is flagged by the ordinary rule; if B is restated after checking, C should not be disturbed. The number of flags set by one operation therefore depends only on the number of declarations that depend on it directly, not on the length of the chain. While B has not been settled, a party reading C can see all premises of C in detailed mode, B among them.

**Limits** (initial values, adjusted with evals and experiments):

| Item | Limit | When exceeded |
|---|---|---|
| Number of declarations in one op | 16 | `too_large` (`premise_entries`) |
| How many effective declarations point to one row / entity | 1,000 | The **declaring side** is rejected: `too_large` (`premise_fan_in`), with the target and the current count attached |
| Flags listed on one row | 10, with the total given separately | Truncated |
| Affected flags listed in the receipt (`premise_affected.rows`: one per flagged declaration on a dependent row) | 20, with the number of dependent rows given separately | Truncated |

- **Effective declaration**: the write it belongs to has taken effect (not a candidate or awaiting confirmation), it has not been fully superseded by a later declaration, it has not been cleared, and the dependent row is not revoked. The count at declaration time uses the coverage that still counts (not superseded, not cleared), and does not subtract those whose dependent row is already revoked or whose write has not yet taken effect, so it can only over-count, never under-count, and rejection may come slightly early.
- **The limit falls on the declaring side and is checked only at declaration time**. If it fell on the changing side, "once others have declared enough, this row can no longer be changed", and one connection could block another's writes with declarations. Cases in which it is exceeded later, through adopting a candidate, undoing a revoke, cancelling a deletion and the like, are allowed to exist and are not rejected retroactively: the initiator of these operations is not the declaring side.
- Premises count into the admission estimate of a write (including a write triggered by a resolution); **a privacy deletion and a cancelled deletion are never affected by it**: deletion cannot be done in batches, and if it were counted, others' declarations could block the right to be forgotten. The detection inside a deletion is done as usual, and its cost is merged into the deletion itself (see "Refresh scope and admission of writes").

**Where it is recorded**:

- The **declaration** is the original argument of the caller and is recorded in the logical write head; it has only identifiers, field IDs and versions, and is a metadata block; an explicitly given valid time and a valid time taken from the dependent row are data blocks (see above).
- The **change of a flag** is a judgement result of saveslot, recorded in `premise.changed`, produced by the write and deletion pipelines in the transaction that produces the change; `apply` does as told and does not compare values itself: removing a flag requires the value at the version seen, which is a historical version, and after physical erasure of content it cannot be compared during replay; writing it into the event means the comparison is made only online, once, at that time.
- `apply` maintains two (b)-class tables: `premise_decls` (each declaration with its state, reason and `since`) and `premise_edges` (for each origin item and each premise target, the currently effective declaration, plus clear entries). All the inputs are in the log, so after an export or a restore the flags are still there; they are not put in local running state.
- **Premises take no part in any value judgement**: same value, conflict, high impact, the existence of a row, revert, and deletion replay do not read them. The pseudocode of revert does not need to know they exist.
- For the shape of the events see `write.head` and `premise.changed` in [`../09-event-format.md`](../09-event-format.md).

### Connection identity (done in the first version)

**Each connection is issued its own credential, named by the user** (such as "MacBook · Claude Code"): in local mode it is written into that client's MCP configuration,
and in remote mode it corresponds to one separate OAuth authorization. All writes and reads are attributed to this connection.

| Level of identification | By what | Trustworthy? |
|---|---|---|
| Which user | Local credential / OAuth token | Trustworthy |
| Which client application | The client_id of the remote OAuth | Trustworthy, only to the application level |
| Which instance | The separate credential issued at connection time | Trustworthy |
| The name and version the client reports (clientInfo) | Reported by the client | Not trustworthy, for reference only |
| Which session / sub-agent inside the instance | The task identifier in the request | Self-reported, used only to correlate reads and writes |

Reasons: the provenance record ("which agent and which client this write came from") depends on it; the cost is low; permissions hang directly on this credential, without changing the structure.

**Authorization = action scope × slot range.** The slot range is "all" or "a list of slots"; the same set of scopes applies identically to every slot in the range (for "A writable, B read-only", issue two connections). When the range is "all", slots created later are included automatically; when it is a list, the list does not change, and this credential cannot create slots either. A slot outside the range is exactly the same as nonexistent for this credential (see "Visible scope"). The range of a user session is always all. Table-level and field-level data permissions come later. The authority for the range is in the log: the issuing event records the list of slot IDs (default = all), and the service layer builds the visible range from it; the control plane does not keep another copy.

- **The first version is a single node**: connections are registered by the user session, and **registration, renaming and revocation are all log events**; the scope and the slot range are fixed at issue time and cannot be changed in the first version (to change them, revoke and reissue; reissuing changes the connection, and the uniqueness range of an external key does not include the connection, so continuing the sync does not add duplicates). With multiple nodes (later): registered by the node that issued it, with a globally unique ID (with a node prefix), propagated by sync; the primary node accepts offline writes made by "a connection issued by some node
  and already registered"; a revocation takes effect naturally when an offline node comes back online and does "pull first, then push".
- **Deactivation**: on an import into an empty tenant, all user principals and connections that were registered before the import and are still valid (except `system`; already revoked ones stay revoked) are set to deactivated (`disabled`) uniformly by the import event, and the user who initiated the import is registered as a new principal. Deactivation is parallel to revocation: a revocation is the user's decision about a certain connection, and a deactivation is the uniform handling brought by an import. A deactivated principal cannot authenticate and cannot be restored in the first version; the actor of data they wrote does not change, their names are still displayed, marked "deactivated"; the items they initiated and that are not yet handled are kept as usual, and are handled by a user session or a newly issued connection.

### Integrity of provenance

| Record | Can completeness be guaranteed | How it is guaranteed |
|---|---|---|
| change_log: every write is recorded | Yes | The only write entrance (the API); at the database layer only saveslot's service account has write permission, and raw SQL is not opened; in the same transaction as the business write; the event header chain; reconciliation of log replay against the business tables (see "Integrity and provenance": protection against mistakes, not against a party that can write to the storage) |
| change_sources: the sources of derived writes | Yes | Rules are executed by saveslot, and the inputs are decided by saveslot |
| change_sources: the sources of base writes | Partly | It can guarantee that "the evidence the writer handed in" is recorded; it cannot guarantee that no other information was used |

The third row is the essential boundary: once information has been read by an agent, it may appear in anything the agent writes afterwards, and saveslot cannot see the agent's context.
**saveslot guarantees the completeness of the provenance chain inside saveslot; for the stretch that passes through the agent it can only check and validate:**

| Layer | What is checked | Example | Uses a model? |
|---|---|---|---|
| Deterministic validation | Type, unit, range, expected version, duplicate submission (idempotency key) | A negative distance; the same request submitted twice | No |
| Statistical anomaly (not judged and produces no item in the first version; the definition is undecided, see architecture §14) | Deviation that is too large compared with this user's own history | Usually 5 km, suddenly 50 km | No |
| Literal match | Whether the written value literally appears in the original text of the attached evidence; only recorded, not rejected (see "Source level") | Evidence "ran 5 km", written 5 km: hit | No |
| Evidence checking (not done in the first version) | Whether the written value agrees in meaning with the attached evidence | The evidence says "5 km", 15 is written | Yes, in the background, asynchronously |

An obvious violation is rejected with an error directly; a suspicious one goes to awaiting confirmation and is flagged (never blocking).

**Taint tracking (optional, not a required item of the first version)**: the provenance of a write is, besides the declared sources, also "the data it read earlier in the same task"
(taken from read_log, requiring reads and writes to carry the same task identifier). Deleted data is regarded as tainted, and what was written after reading it is regarded as "possibly tainted too".
It over-counts, so inferred provenance serves only as the "possibly affected" level and is not deleted automatically; in a privacy deletion it is listed for the user to decide.
Explicitly declared premises are its precise version and are already in the first version (see "The premises of a write"): the agent itself lists the values it used, they go into the log and are visible to all readers; what is inferred from the read record remains optional.

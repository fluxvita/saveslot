# saveslot · The surfaces: the CLI and the getting-started flow

> Translated from docs/zh-CN/spec/06-cli.md, updated in the same commit as this file.
> The Chinese edition is authoritative; where the two differ, the Chinese one holds.

> This document describes the first version's CLI: who uses it, how it connects to saveslot, the getting-started flow from zero to the first working Agent, the command list, the interaction for human confirmation, output conventions and security.
> The CLI is, alongside the MCP and HTTP in [`05-surfaces.md`](05-surfaces.md), one more surface of the contract: the shape of operations is defined by [`04-contract.md`](04-contract.md) and the kernel rules by [`03-data-model/`](03-data-model/README.md); undecided numeric items are in [`08-open-questions.md`](08-open-questions.md).

## 1. Conclusion

- **The CLI is the entry point for people in the first version**: the first version has no app, so issuing and revoking connections, handling pending items, deletion and cancelling a deletion, export and import, validation and creating slots are all done by a person through the CLI, or by a person instructing a caller Agent to do them through MCP (confirmation is delegated to the caller, see [`02-architecture.md`](02-architecture.md) §3).
- **The CLI sets no rules of its own**: apart from the few commands that manage the local process, every command maps to one operation (or a sequence of operations) of the contract and goes through `client` over HTTP; the CLI itself decides only interaction, rendering and exit codes.
- **Local connection: the saveslot service listens only on a unix domain socket** (the first version supports only macOS and Linux locally; Windows is later, and will use a named pipe then); the socket file is readable and writable only by the current system user; the CLI and `saveslot mcp` (a stdio bridge for MCP hosts) both call HTTP / MCP through it. Loopback TCP is off by default and can be turned on as needed.
- **The user session credential**: locally, `saveslot init` generates it and stores it in the saveslot configuration directory (mode 0600); on the cloud service it is obtained through `saveslot login` (browser + PKCE, or the OAuth device code when there is no browser).
- **Design requirement for attaching a host**: **whatever the deployment, in the flow of attaching a host, the user makes at most choices and gives one consent; saveslot completes the remaining steps. Every way of attaching added later is checked against this rule.**
  - Choices: which template, which hosts to attach, which scope to give, which slots can be seen, what the slot is called. Every choice has a default, and going through with all defaults also works.
  - One consent: consent once, as a whole, to "what saveslot will do on the host's side". Locally it is one answer to "run the following commands"; in server mode it is one "Authorize" on the authorization page.
  - Not counted: installing saveslot itself; a person's first login to their own account (`saveslot login` in server mode, which does not appear again after that); a restart the host itself requires. Optional enhancements (the custom instructions of 3.4) are also outside this: attaching does not depend on them.
  - When it cannot be done, say so: a host that has no add command and can only have its configuration pasted by hand is a known exception to this requirement (3.2).
  - Rationale: every manual step of attaching filters out some people, and none of these steps needs a person's judgement; what a person has to judge is only "whether to attach, and how much permission to give". Narrowing a person's involvement to choices and consent is also a security improvement: what is consented to is a complete, written-out list.
- **Getting started in one line**: `npm install -g @fluxvita/saveslot` → `saveslot setup` → ask one question in the host (in Claude Code you can also type `/mcp__saveslot__overview`). `setup` only orchestrates existing commands (3.3); doing it step by step is `saveslot init` → `saveslot start` → `saveslot slot create health --template running` → `saveslot connect claude-code` → paste the printed command into a terminal → ask one question in the host → `saveslot reads` shows a read other than the self-check.
- **A confirmation is explicitly bound to its content**: when the CLI resolves an item it always carries the `item_ver` it has just shown to the person, and a deletion always carries the `dc_` of the preview that was shown; non-interactive use (`--yes`) is allowed, but this binding token must be given explicitly, otherwise the CLI refuses to run. The two kinds of resolution that the contract says are not bound by `item_ver` are the exception (cancelling a deletion does not check it; `accept_all` of `migration_diff` is bound to `diff_upto`), see section 5.

## 2. Role and boundaries

### Who uses it and for what

| User | What it uses the CLI for |
|---|---|
| The user themselves | Install and start the local saveslot service (`saveslot setup` in one command, or step by step); create slots; issue a connection for each Agent and attach it to a host; handle pending items; deletion and cancelling a deletion; see who read what; export and import; validation |
| Agents with a shell, scripts | Queries and `--json` output. **They should run with their own connection token** (environment variable `SAVESLOT_TOKEN`): limited by scope, with reads and writes recorded under that connection. With the user session they can do anything, and everything is recorded under the user's name (section 8 states this boundary) |
| MCP hosts | Use only `saveslot mcp`: the host starts it over stdio, and it forwards MCP messages to the local saveslot service |

### What it does not do

- **No business writes**: the first version has no `saveslot write`. A write has to turn the user's words into an intent, rows, values and evidence, and that is the Agent's job (the positioning document, "The data layer"); for a person to change data, they tell the Agent, and the evidence is those exact words. A script without an Agent uses HTTP `POST /v1/writes`.
- **Does not open the data directory directly**: apart from `saveslot init` it does not touch PGlite, and every read and write goes through the saveslot service, so the single-writer lock and the audit are not bypassed.
- **Does not judge kernel rules**: conflicts, high impact and the result of a deletion are all computed by the kernel, and the CLI only renders the structured fields the contract returns.
- **Does not edit the host's configuration files, nor the host's instruction files**: it only prints the host's own add command or configuration snippet; with `--apply` and `saveslot setup` it runs the host's own command on the user's behalf, and does not edit files such as `~/.claude.json` or `~/.codex/config.toml` directly; the text suggested for the host's custom instructions (3.4) is placed by the user, and saveslot does not write files such as `CLAUDE.md` or `AGENTS.md`. Reasons:
  1. **The format and the location belong to the host, and they change.** One host has several places of configuration (split by scope; some hosts have two sets of MCP configuration, one of which is to be removed) and the formats differ (JSON, JSON with comments, TOML). The host's own command follows the host; if saveslot wrote the files itself, it would have to chase every change of every host.
  2. **Those files hold more than saveslot.** They contain the user's other MCP servers, other keys and settings. If saveslot's write goes wrong (a concurrent rewrite while the host is running, losing comments and formatting, a half-written file), what breaks is something unrelated to saveslot, and the user can hardly tell who did it. An instruction file is more sensitive: it is text the user wrote by hand, and it directly decides how the model acts.
  3. **What is consented to can be shown word for word.** What is shown to the user is the very command that will run, the one written in the host's documentation that the user could type too; "saveslot will modify a certain section of a certain file" cannot be as definite. Quietly modifying another program's configuration is how unwelcome software behaves, and hosts and security software may block it in the future.
  4. **Revoking is symmetric**: the host's remove command removes it completely, leaving no trace of saveslot's own.

  The cost is that a host with no add command can only have its configuration pasted by hand; this is a known exception to the design requirement of section 1, and it is accepted: no exception is made to edit files for it.

### Relation to HTTP and MCP

| | MCP | HTTP | CLI |
|---|---|---|---|
| Main caller | Agent | Scripts, programs | People |
| Credential | Connection | Connection or user session | User session (default); when `SAVESLOT_TOKEN` is set, that connection's token |
| Administrative operations ([`04-contract.md`](04-contract.md), "Administrative operations") | Not provided | Provided | Provided, through the HTTP administrative endpoints |
| Op-level `acknowledge` | Not open | Open | Not involved (no business writes) |
| Text rendering | The MCP renderer ([`05-surfaces.md`](05-surfaces.md) 4.2 "Flags", 4.3 "Warnings and hints") | None, JSON only | The CLI renderer: flags are written as in MCP, and the next step is written as a CLI command |

**Where the code is** ([`02-architecture.md`](02-architecture.md) §11): the `cli` package depends only on `client`; the service-group commands (`init`, `start`, `stop`, `status`, `service`, `doctor`, `config`, `mcp`, `server …`) are provided by the `daemon` package; the `saveslot` executable is an entry package that only dispatches, and depends on `cli` and `daemon`. `saveslot setup` spans two groups of commands (initializing and starting belong to the service group, issuing and attaching belong to `cli`), so it is orchestrated by the entry package, and each step still calls the same implementation as the original command. The `cli` package also depends on age's official JS implementation `age-encryption` (version pinned), used only for export encryption and for decryption before import (4.8); the kernel, the service layer and `daemon` do not depend on it.

### How the CLI connects to saveslot

| Deployment | Transport | Credential |
|---|---|---|
| Local (default) | HTTP over unix socket: `~/.saveslot/run/saveslot.sock` | User session token, `Authorization: Bearer` |
| Local · loopback TCP (optional) | `http://127.0.0.1:<port>`, turned on with `saveslot config set http.loopback on` | Same as above |
| Server mode (our cloud service or self-hosted) | HTTPS, `https://<domain>/v1` | The user session obtained with `saveslot login` |

The address in server mode can only be one origin (`https://<domain>[:port]`, without path, query or user information); `http:` accepts only loopback addresses (`127.0.0.1`, `::1`, `localhost`), for tests and local tunnels, and a token never leaves the machine in clear text. The CLI does not follow redirects: a 3xx is not a response of the contract, and the token is never carried to another address.

**Why a unix socket locally:**

1. **The operating system guarantees that it is for this machine only**: the directory holding the socket is 0700 and the file is 0600, so other system users cannot connect; it takes no port, and there is no configuration that could be wrongly bound to 0.0.0.0.
2. **A browser cannot reach it**: a loopback TCP port can be reached by a web page through DNS rebinding, and a unix socket cannot.
3. **The single writer already requires a resident process**: PGlite lives in the DB Worker of the saveslot service process ([`02-architecture.md`](02-architecture.md) §7), and several Agents on the same machine can share it only through this one process; the CLI does not open storage of its own.
4. **MCP hosts need not support sockets**: the host starts `saveslot mcp` (stdio), which forwards to `/mcp` on the socket; the MCP adapter has only one implementation, Streamable HTTP.

Loopback TCP is turned on only for hosts or tools that must be given a URL; once on, it binds only `127.0.0.1` / `::1`, checks `Host` and `Origin` (rejecting non-local origins), and every request still has to carry the token.

### The user session credential

| Deployment | How it is obtained | Where it is stored | How it ends |
|---|---|---|---|
| Local | `saveslot init` generates a random token; the control plane stores only its hash | `~/.saveslot/credentials/session`, 0600 | `saveslot init --rotate-session` replaces it, and the old token stops working at once. Run `saveslot stop` first: it replaces only the hash in the control plane and does not touch the data directory, and the saveslot service reads the new hash at its next start; while the service is running, the command is refused all the same |
| Cloud service | `saveslot login`: by default it opens a browser and runs the authorization code flow + PKCE (the local loopback receives the callback, accepts only the one carrying this login's `state`, answers any other with 400 and keeps waiting); `--device` uses the OAuth device code (RFC 8628), suited to SSH sessions with no browser; the polling interval is capped at 60 seconds and the device code is waited for at most one hour, even if the server gives longer values; the user code is 8 letters drawn from the 20 consonants `BCDFGHJKLMNPQRSTVWXZ`, written as `XXXX-XXXX` in the response, and on input it is case-insensitive with hyphens and white space ignored; the CLI checks only the shape `[A-Z]{4}-[A-Z]{4}`, not the alphabet, so a self-hosted server works too | `~/.saveslot/credentials/<profile>.json` (access token + refresh token, keys below), 0600 | `saveslot logout` revokes the refresh token and deletes the file |

- The CLI refuses to use a credential file whose permissions are wider than 0600 and prompts the user to fix it, in the same way as ssh treats private keys. In the first version credentials are kept in files; putting them in the system keychain (which can require a person to be present to retrieve them) is done together with desktop packaging.
- **profile** distinguishes connection targets: `local` (default), `cloud` (our cloud service, at `https://api.saveslot.ai`), and the profile newly created for a self-hosted server by `saveslot login --server <URL> --profile <name>`; switch with `--profile` or `saveslot profile use`. The targets are not connected to one another (the first version has no sync).
  - The name of a profile: 1 to 32 characters, `a-z`, `0-9` and `-`, not starting with `-`; `local` and `cloud` are built in and cannot be registered.
  - **`~/.saveslot/profiles.json`** is the CLI's own file (not configuration of the saveslot service): `{"format": 1, "current": "<name>", "servers": {"<name>": "<address>"}}`, where `current` is the profile in use and `servers` holds the registered self-hosted servers (the address is written as an origin, the rule is in "How the CLI connects to saveslot" above). When the file is absent, the current profile is `local` and there are no registered servers. The keys are exactly these, no more and no fewer, and parsing is strict: a form it does not recognize is refused.
  - **`credentials/<profile>.json`** (the user session of a server profile): `{"format": 1, "server", "access_token", "access_expires_at", "refresh_token"}`, exactly these keys. `server` is the server the tokens were issued to; the tokens are used only when it is identical, character for character, to this profile's address, and otherwise no token is sent and the user is prompted to log in again. When the access token is within 60 seconds of expiry (or has just been refused as `unauthenticated`), the refresh token is used first to obtain a new one; a refresh token can be used only once, so renewing first takes this profile's lock (`credentials/<profile>.json.lock`, created exclusively; one older than 30 seconds counts as left over, and waiting is at most 10 seconds; a request made while holding the lock takes at most 20 seconds, and the remaining 10 seconds are left for re-reading and writing the file, so the lock is never taken as left over while a request has not finished), and after it is taken the file is read once more, and if another command has already renewed, what it obtained is used. The new pair is written to the file first and used afterwards; when it cannot be written, this login is over (the old refresh token has been spent), the user is prompted to log in again, and the new tokens in memory are not used further. When the refresh is refused (`invalid_grant`) the file is kept and the user is prompted to log in again; only `saveslot logout` deletes the file. After `saveslot login` has written the new pair, it makes a best effort to revoke the refresh token of the login it replaced: this is sent only when the `server` of the old file is identical, character for character, to this profile's address, and if the revocation fails it only prompts once and does not change the exit code.
  - Both files follow the rules of the credential file above: the directory they are in is 0700, the file is 0600, it belongs to the current user and must not be a symbolic link, all checked before every read and write; a write goes to a temporary file in the same directory, is synced, renamed, and then the directory is synced.
  - Before it sends anything to the server (and so before it opens a browser or asks for a device code), `saveslot login` checks the home, `credentials/` and the profile's existing credentials file against this rule, only those that exist: if one fails, nothing is sent, exit code 6. Otherwise a sign-in would be refused only when the credentials are written, and the authorization the person just gave in the browser would be thrown away. When this rule refuses (for `login` and every other command alike), the message names, on a line of its own, the directory or file that was refused.
- **Running with a connection token**: when the environment variable `SAVESLOT_TOKEN` is set, the CLI uses it in place of the user session; what it can do follows that connection's scope, administrative commands report `insufficient_scope`, and reads, writes and confirmations are all recorded under that connection. It is for Agents with a shell and for scripts (section 8.3). The token is sent to the target of the chosen profile: for `local` that is the local saveslot service, for a server profile it is its server (the static token issued by `saveslot connect http --profile …` in server mode is used this way). When `SAVESLOT_TOKEN` is set but empty, or is not in the form of a connection token, the CLI refuses to run (exit code 6) and does not fall back to the user session: the user session can do anything, and it is used only when this variable is not set.

## 3. The getting-started flow (local, from zero to the first working Agent)

One command (details in 3.3):

```
$ npm install -g @fluxvita/saveslot    # one package with the CLI and the saveslot service; needs Node 24.22.1 or later (26.12.1 or later on the 26 line)
$ saveslot setup
[1/5] Created ~/.saveslot (0700)
[2/5] The saveslot service started in the background · pid 4211
[3/5] Which templates to make the first slots from?
        1 [x] running   running records → slot health
        2 [ ] spending  daily spending → slot ledger
        3 [ ] budget    budget → slot plan
      numbers to switch on or off, Enter when done:
      Created slot health · schema v1 · 2 tables (runs, weekly_mileage)
[4/5] Which hosts to add saveslot to?
        1 [x] Claude Code (claude 2.x)
        2 [x] Codex (codex 0.x)
        3 [ ] Cursor (no command to add saveslot: set it up by hand with saveslot connect cursor)
      numbers to switch on or off, Enter when done:
[5/5] A connection instance will be issued for each host, and the host's command run (scope saveslot.read saveslot.write saveslot.schema):
        /usr/local/bin/claude mcp add saveslot --scope user -e SAVESLOT_TOKEN=<token> -- /usr/local/bin/saveslot mcp
        /opt/homebrew/bin/codex mcp add saveslot --env SAVESLOT_TOKEN=<token> -- /usr/local/bin/saveslot mcp
      Run these 2 commands? [Y/n]
Claude Code: added · MacBook · Claude Code (ci_01JF…)
Codex: added · MacBook · Codex (ci_01JG…)
Done. In Claude Code, type /mcp__saveslot__overview (shown as /saveslot:overview in the / menu); in any host, you can ask "what is in saveslot?"
optional: saveslot snippet claude-code (text to put in the host's custom instructions)
```

**Prerequisite of the installation**: `npm install -g` requires npm's global directory to be writable. On Linux, when Node is installed under `/usr/local`, an ordinary user has no write permission there and the installation reports `EACCES`; the message gives npm's way out: set a user-level prefix (`npm config set prefix ~/.npm-global`, and add `~/.npm-global/bin` to `PATH`), and does not recommend `sudo` (the installed files would belong to root, and the entry path registered with the host would also land in a system directory).

The exact form of the host commands is maintained by the CLI's host adapter table (3.2) and **is tested host by host at implementation time**. The choice uses a text prompt with numbers (type a number to switch an item, press Enter to confirm), does not put the terminal in raw mode and adds no dependency; choosing with arrow keys and the space bar is left for desktop packaging. The host commands that are run are written with the absolute path found in `PATH` (3.2).

**Step by step** (what `setup` calls is exactly these commands; evals and scripts keep using them):

```
$ saveslot init
Created ~/.saveslot (0700)
  data/          PGlite data directory (one tenant; the tenant genesis is written, registering the user principal and system)
  control/       control plane (files): credential hashes, the tenant directory, the anchor (deletion register, `seq` high-water mark, restore count), the handle signing key
  credentials/   the user session token (0600)
  run/           the saveslot service's runtime (0700): saveslot.lock (the lock at the level of the service process), saveslot.pid, saveslot.sock, last-failure.json (the reason code and moment of the last failed start, with the step that failed when it was an upgrade of the storage format; deleted once the service is ready), saveslot.log (the service's log when it runs in the background, 0600, appended to; it records only event names and reason codes, no paths, tokens or user data. The service writes this file itself, and after a line is written, if the file is over 10 MiB it rotates: the oldest copy is deleted, `saveslot.log.1` is renamed to `.2`, the current file is renamed to `.1`, and a new one is opened, keeping at most two old copies; what Node writes to standard error when it crashes goes to the file that `saveslot start` handed to the process, which after a rotation is the newest old file)
$ saveslot start
The saveslot service started in the background · pid 4211 · listening on ~/.saveslot/run/saveslot.sock · data ~/.saveslot/data
$ saveslot schema templates
running   running records: runs (events) + weekly_mileage (derived, distance per week)
budget    budget: budgets (state, by category)
spending  daily spending: expenses (events, CNY) + monthly_total (derived)
$ saveslot slot create health --template running --timezone Asia/Shanghai
Created slot health · schema v1 · 2 tables (runs, weekly_mileage)
$ saveslot connect claude-code --name "MacBook · Claude Code"
issued connection instance MacBook · Claude Code (ci_01JF…) · scope saveslot.read saveslot.write saveslot.schema
self-check passed: the new token read 1 slot(s)
The token is shown only this once. Paste the command below into a terminal:
  claude mcp add saveslot --scope user -e SAVESLOT_TOKEN=<connection token> -- /usr/local/bin/saveslot mcp
optional: saveslot snippet claude-code (text to put in the host's custom instructions)
```

After `init`, `tmp/` (0700) also appears in the home: `tmp/reconcile/<tenant ID>` is the temporary storage of the replay comparison (`saveslot verify --replay`), one per tenant, created by the service when the replay comparison starts; when it ends, whether it succeeded or not, it is deleted, and the service clears what a crash left behind when it opens the tenant ([`02-architecture.md`](02-architecture.md) §3).

In Claude Code, ask "which slots are in saveslot?", and then:

```
$ saveslot reads --connection "MacBook · Claude Code" --since 10m
11-10 21:03  MacBook · Claude Code  catalog list  slot health (sv 1)  self-check (saveslot connect)
11-10 21:04  MacBook · Claude Code  catalog list  slot health (sv 1)
```

The first line is the self-check that `saveslot connect` performs itself and does not count; only when a read record other than the self-check appears does it show that the host really is connected to saveslot through this connection. To attach Codex as well, repeat `saveslot connect codex --name "MacBook · Codex"`; the two Agents share the same data and each leaves its own trace.

Key points of each step:

1. **Install**: the first version ships one npm package, containing the CLI and the saveslot service; the standalone executable and the desktop installer wait for the conclusion of experiment 6 (desktop packaging) ([`07-scope-v1.md`](07-scope-v1.md), "Implementation order").
2. **Initialize**: `saveslot init` is the only command that opens storage directly, and it refuses to run while the saveslot service is running. The data directory can be put elsewhere with `--data-dir` (a relative path is resolved against the current directory and what is recorded is the normalized absolute path; it cannot be used together with `--rotate-session`), and a warning is given when it falls inside a synced folder such as iCloud Drive or Dropbox ([`02-architecture.md`](02-architecture.md) §7); a location put elsewhere is recorded in `control/tenant.json`, and when the saveslot service starts it opens the data directory only at the recorded location, and refuses to start if it does not exist there or has no tenant genesis, and never creates an empty database there or anywhere else (a data directory that was moved away, or a disk that was not mounted, must not quietly be replaced by empty data). The data directory, whether the default or put elsewhere, is created by `init` with 0700 (an existing one is tightened to 0700). A data directory put elsewhere is not inside the home's 0700, and the files storage creates there could be read or written by others, so when the saveslot service starts it checks it by the home's rule (the owner is the current user, it is not open to the group or others, it is not a symbolic link) and refuses to start if that fails (reason code `data_dir_permissions`, and the message names the data directory and the fix); the default location `<home>/data` is inside the 0700 home where others cannot reach it, so it is not checked separately, and the service does not change its permissions either. Under `control/` are a few files: `credentials.json` (the hashes of tokens, the user session), `tenant.json` (the tenant directory), `anchor.json` (anchor storage: the deletion register, the `seq` high-water mark, the restore count, and the "restore in progress" and "import in progress" marks) and `keys/` (the handle signing key); every write is "write a temporary file → flush to disk → rename over", and only the saveslot service process writes ([`02-architecture.md`](02-architecture.md) §5, §8). The anchor is not in the data directory; but in the default layout both are in `~/.saveslot/` and a system-level backup usually restores them together, in which case saveslot can neither make up the deletions nor detect the need. Only when the data directory is put elsewhere with `--data-dir` and only the data directory was restored can deletions be re-applied from the register: start with `saveslot start --restored`, and the service runs the restore flow before it serves; when the restore flow is interrupted midway, the next start, with or without `--restored`, finishes it before serving ([`02-architecture.md`](02-architecture.md) §8; [`03-data-model/03-deletion.md`](03-data-model/03-deletion.md), "After deletion").
3. **Start / stop / start at login**: `saveslot start` starts in the background (`--foreground` in the foreground, for watching the log); `saveslot stop` flushes the read_log buffer to disk and drains the write queue before it exits; it signals only a process it has verified: when `GET /health` answers and the pid it reports equals the one in `run/saveslot.pid`, it sends SIGTERM to this process and waits for it to exit; only when `/health` does not answer does it look at `run/saveslot.lock`: if it is not held, the service is not running (a leftover pid file does not count), and if it is held (starting or stuck), no signal is sent ([`02-architecture.md`](02-architecture.md) §7). Probing the lock means taking it briefly, and a service that is starting may take the lock at just that moment and make the probe fail, so `stop` and `status` both ask `/health` first, and do not probe the lock if there is an answer. When `saveslot start` has waited 60 seconds and the service is still not ready, it does not stop that process (it may be running the restore flow), and the error says its pid is still running and to check with `saveslot status` later. While the service upgrades the storage format (`/health` reports `starting` with `upgrade`, [`02-architecture.md`](02-architecture.md) §8 "The upgrade mechanism"), `saveslot start` does not count these 60 seconds and waits on, writing a line to standard error as each new step begins; once the upgrade is done, it waits 60 seconds afresh. When the upgrade fails the exit code is 5, and it says which step failed and what to do next (the service log has the database's error code; with a full disk, free space first, and the next start goes on upgrading from that step). `saveslot mcp` does not wait for an upgrade: when it starts the service and sees an upgrade it stops waiting, and while the upgrade runs it answers each tool call `unavailable`, with a message saying the storage format is being upgraded and which step. Start at login is `saveslot service install` (a user-level launchd agent on macOS, a systemd user service on Linux; it requires the home to be initialized, and installing again rewrites it with the current Node and saveslot paths): the installed job starts the service at login, and starts it again when it exits with a failure after it began serving ([`02-architecture.md`](02-architecture.md) §7); one that failed before it began serving, or was stopped by `saveslot stop`, is not started again; `saveslot service uninstall` removes the job and also stops the service it started. When a host starts `saveslot mcp` and the saveslot service is not running, `saveslot mcp` starts it first; if two hosts start it at the same time, the later one finds the socket already there and connects straight away, and the single-writer lock is the fallback that guarantees no two processes write data; this way hosts work even before start at login is installed. Automatic start is on by default and can be turned off with the configuration `mcp.autostart = false`; on `saveslot stop` it prompts: "An MCP host that connects again starts it again; to stop it for good, set mcp.autostart = false or remove saveslot from the host." `saveslot mcp` always connects to the local saveslot service and does not change with `--profile` / `saveslot profile use` (the cloud service does not go through it, and the host uses remote MCP directly).
   **The test clock** (used only by evals, [`02-architecture.md`](02-architecture.md) §11, "What the evals require of the implementation"): `saveslot start --eval-clock <moment>` (RFC 3339, with a time offset; `--foreground` likewise) makes the service run forward from this moment at real speed, and every place in the service process that takes "the current moment" uses it (requests, writing read records, shutdown, the "how long ago" in MCP text), while log lines still use the system time. While it runs, the user session can `POST /v1/eval/clock` (`{"advance": "PT2H"}`, ISO 8601 days, hours, minutes and seconds, forward only) to move it faster; when started without `--eval-clock` this route does not exist (404). It does not read environment variables and does not go into `config.toml`, and the automatic start of `saveslot mcp` never carries it. One eval run is one service process: the first start with `--eval-clock` leaves an eval mark in `control/eval.json` (not in the log); a home with the mark refuses every start without `--eval-clock` (including automatic start), and refuses a start with it as well: if the service exits midway, this run is void (the reason code in both cases is `eval_dir_refused`). A home without the mark accepts `--eval-clock` only when the log holds nothing but the tenant genesis (just after `init`) and the genesis's recorded moment is not later than the test clock's starting point, and otherwise refuses (`eval_clock_refused`): the first condition keeps it from being turned on over the user's real data; the second is because when the clock lags behind the end of the log, later events are all recorded at the end's moment ([`02-architecture.md`](02-architecture.md) §8), and the test clock could no longer be seen in the log. The eval runner writes the tenant genesis with the fixture's clock, and `saveslot init` uses the system time and does not take this parameter. The saveslot service has no automatic exit when idle, so nothing else needs to be turned off for the test clock.
4. **Create the first slot**: `saveslot slot create` is `schema_draft` (`base_version: null`), a new slot takes effect once it compiles and returns `sv: 1` ([`04-contract.md`](04-contract.md), "`schema_draft`"); creating a slot also has the kernel write a default slot policy event. A connection that has `saveslot.schema` and a range of all slots can also let an Agent create a slot through MCP `saveslot_schema_draft`, which is the same operation ([`05-surfaces.md`](05-surfaces.md) section 9).
5. **Where the starter schema comes from**: see section 3.1.
6. **Issue and attach to a host**: see section 3.2.
7. **Verify the connection**: `saveslot connect` makes one `catalog` call with the new token (carrying the fixed `task: "saveslot-connect-selfcheck"`, marked "self-check" in `saveslot reads`; `task` is self-reported, and this mark is only for telling it apart, not a guarantee), proving that the token, the scope and the saveslot service all work; whether the host side really uses it is decided by whether a read of this connection **other than the self-check** appears in `saveslot reads`. When the issued connection has no `saveslot.schema` (it was removed explicitly), the output adds one more sentence: "the agent can read and write the existing tables through this connection instance, but cannot create a slot; to let it, connect again with schema among the scopes (without `--scope -schema`, or with schema in the `--scope` list)" (for a read-only instance it says "can read" in place of "can read and write"); in the summary of `setup`, when a connection issued because a host was attached this time has no `saveslot.schema`, the same sentence is written at the end; when no host was attached and nothing was issued, it is not written. `saveslot doctor` checks item by item: the saveslot service is running, the socket permissions, the credential file permissions, the data directory is not in a synced folder, the holder of the single-writer lock, the versions agree, whether there are deletions overdue for physical erasure, and whether the executable path in each host's saveslot entry still exists (through the host's own look-up command, such as `claude mcp get saveslot`; a host with no look-up command is not checked, and "not checked" is stated, and its configuration file is not read); three more results are "reminders": the system clock is more than 5 minutes behind the recorded moment of the end of the log, and **the data size**: tables whose row count is over the comfortable line or the tested line (table name, row count, level), together with the tenant-level total of events, the size of the data directory and the duration of the most recent cold start (compared with the tested range of the architecture document, "Capacity limits and measured values"); and **the host has not yet read through its connection instance**: for each host in which a saveslot entry is found, look at the connections in `saveslot connections list` that are not revoked and whose name belongs to this host (the two tiers of item 7 of 3.3 taken together: a name equal to the host display name, or ending with " · <host display name>", possibly with a sequence number); when there are such instances and the read records hold no read by any of them other than the self-check, a reminder is given, stating "the agent in this host has not read anything through saveslot yet; if you have asked it to record something and nothing was recorded, the host has most likely not allowed it to use saveslot's tools", followed by how this host allows them: for Claude Code, "it asks once at the first call, allow it; where there is no terminal to ask in (`claude -p`), add `--allowedTools "mcp__saveslot"`", and for other hosts, "confirm in the host that it may use saveslot's tools". This reminder is inferred from saveslot's own read records, not looked up: a tool call the host refuses never reaches saveslot, Claude Code has no command that shows its approval rules, and its settings files are not read either; so a host just connected and not yet used, and a host not used for longer than the retention of the read records, get this reminder too, and it no longer appears once the host has read through the instance. When there is no such connection instance (the user named it otherwise), this reminder is not written. The result of each item is one of "pass / FAIL / remind"; a reminder is not a failure and does not affect the exit code.

### 3.1 The starter schema: templates bundled with the CLI

- **How the first version does it**: the CLI package carries a few written schema documents (the three listed above); they are ordinary user schemas, with the format entirely as in [`03-data-model/07-schema-evolution.md`](03-data-model/07-schema-evolution.md), "Schema document format", without `extends` / `compatibility`. `saveslot slot create --template` replaces the slot name and the time zone in the template with the values given on the command line and submits it as a draft; when `--timezone` is not given, it takes this machine's time zone (the time zone name the runtime gives), and says in the output that it was taken this way. With `--file`, the slot name is likewise the one given on the command line, the time zone stays as in the file, and `--timezone`, when given, takes precedence.
- **Once created, it belongs to the user**: the slot has no further link to the template, and a CLI upgrade that changes the templates does not affect slots already created; to change the structure, use a schema change (P4).
- **Why bundle them with the package instead of fetching them from the web**: they work offline, their content is fixed by the CLI version, and they do not introduce a "remote schema source" as a surface for prompt injection (the open questions, "Security of community schemas + SKILL").
- **When not using a template**: `saveslot slot create <name> --file schema.json`, where the file can be one saved after having an Agent draft it; or give an Agent `saveslot.schema` and let it create the slot directly through `saveslot_schema_draft`.
- The official schema is in the first version only a reserved place in the compiled definition and is not implemented (the data model, "The official schema and user schemas"; the details are in the open questions, "Details of the official schema"); once it is implemented, the templates change to the `extends` form of the official schema, and slots already created from the old templates are not affected. New templates beyond these three (health, nutrition and so on) are written after the structure is settled.

**The content of the three templates.** Units are taken from the unit vocabulary, precision is not written and the default is used (for currencies the number of digits of the ISO 4217 minor unit, for the rest 6 digits, rounding `half_up`, see the data model, "Field types, same value and units"). `slot` and `timezone` are replaced by the command-line values. The evals' fixtures ([`10-evals.md`](10-evals.md), "Shared fixtures") use exactly these three.

- The currency templates are written in CNY. To use another currency, save the template as a file, change the unit of `amount`, and create the slot with `--file`; changing the currency after creation is a "change of dimension", which goes through a schema change with a conversion given ([`03-data-model/07-schema-evolution.md`](03-data-model/07-schema-evolution.md), "Kinds of change and means of migration").
- A suspected duplicate in `spending` is judged as "same day, same category, same amount"; in `running`, as "same day, same distance". A hit only produces one flagged item and does not reject the write.
- **Coverage columns**: a derived table bucketed by time carries three columns: `days_recorded` (the days in the bucket that have records), `first_date` and `last_date` (the dates of the earliest and the latest record in the bucket). Whether "ran 21 km this week" is a complete week or only four days were recorded is judged by the reader from these three columns: `days_recorded` equal to the number of days the bucket should have means complete (how many days it should have is domain knowledge, written in the field description); less means partial, and the first and last dates show whether the gap is at the head, the tail or the middle, and when the current bucket has not finished yet, the distance between `last_date` and today shows whether it is "not there yet" or "not recorded"; no row for the bucket means there is not a single record in that period (a grouped aggregate produces no row for a bucket with no input). The rule does not refer to "today", otherwise it would become a computation at read time and could not be cached. `budget` has no derived table. The `count(DISTINCT …)` used, and `min` / `max` over `date`, must be on the allowlist of restricted SQL (the data model, ["Restricted SQL"](03-data-model/11-restricted-sql.md)); a table with "one row per day" uses `count(*)` directly.

**Design conventions that the later official templates must follow** (templates such as health and nutrition are written after the official schema is implemented):

1. **Two granularities, no third**: one row per activity (event table: a run, a sleep, a meal); one row per day (event table, by `date`: that day's steps, resting heart rate, average blood glucose, total sleep duration).
2. **No tables of point-by-point readings.** Heart rate curves, blood glucose curves and GPS tracks stay in the device or service that produces them; saveslot keeps all versions and sources for every row, and the cost of these guarantees grows with the row count (the scope of application of "The scenario test: things tracked over time" in the positioning document).
3. **Point to the past with evidence**: the evidence of a summary row uses `file_ref` (file name, type, size, content hash, source location) or `tool_result` (the summary text the source service returned), and `origin` gives the location of the raw series at the source. saveslot does not keep the files themselves.
4. **The summary values are fields of this row** (such as `avg_hr`, `max_hr`, `min_glucose`), computed beforehand by the source side or the caller Agent and written in; derivation rules summarize again on top of the summary rows (week, month) and do not compute on raw readings.
5. The description of the table states the granularity ("one row per day; do not write readings one by one").
6. A derived table bucketed by time carries the coverage columns.
7. In nutrition templates, a volume field that copies numbers from labels uses `mL`, and the field description states: US food labels count 1 fluid ounce as 30 milliliters, which is a rounding convention of labels, while `floz` in the vocabulary takes the defined value.

### 3.2 Issuing a connection and attaching a host

`saveslot connect <host> --name <name> [--scope …] [--slots <name>,<name>]` = `connections.issue`, and then it generates the way of attaching for the host. The table below is the CLI's **host adapter table**: for each host it also records the executable file name and the argument that gets the version (`saveslot setup` uses it to discover which hosts are installed on this machine, 3.3); the exact form of the commands is **tested host by host at implementation time**.

| Host | What it generates | `setup` can attach it automatically |
|---|---|---|
| `claude-code` | `claude mcp add saveslot --scope user -e SAVESLOT_TOKEN=<token> -- <absolute path of saveslot> mcp` (there are also `claude mcp get` / `list` / `remove`; tested with 2.1.323, it writes into `~/.claude.json`) | Yes |
| `codex` | `codex mcp add saveslot --env SAVESLOT_TOKEN=<token> -- <absolute path of saveslot> mcp`, or the `[mcp_servers.saveslot]` snippet of `config.toml` (there are also `codex mcp get` / `list` / `remove`, and for how `get` behaves see 3.3 item 7; tested with 0.171.0, the add command writes into the user-level `~/.codex/config.toml`; the argument that chooses the scope is not verified) | Yes |
| `cursor` | No add command: it prints a configuration snippet to be pasted by a person, and says to put it under `mcpServers` in `~/.cursor/mcp.json` (effective for all projects; put it in the project's `.cursor/mcp.json` for one project only) (tested with 3.31.15: it is read at startup and connected, and the Agent can call it) | No |
| `claude-desktop` | No add command: it prints a configuration snippet to be pasted by a person, and says to put it under `mcpServers` in `claude_desktop_config.json` (the file opened by Settings → Developer → Edit Config; on macOS in `~/Library/Application Support/Claude/`, on Linux in `~/.config/Claude/`), and after the change to quit completely and open again (tested with 6.28899.6: once attached, it appears in the list under + → Connectors in the input box, in the same place as remote connectors) | No |
| `vscode` | `code --add-mcp '{"name": "saveslot", "command": "<absolute path of saveslot>", "args": ["mcp"], "env": {"SAVESLOT_TOKEN": "<token>"}}'`, **printed only, not run** (`--apply` is a usage error), and below it three things are stated: use it in the Agent mode of GitHub Copilot Chat; an entry of the same name is overwritten directly; after writing, change that `mcp.json` to 0600 (`chmod 600`, see "the form of host commands" below the table). Tested with 1.147.0: it writes into the user-level `mcp.json` (on macOS in `~/Library/Application Support/Code/User/`; on Linux in `~/.config/Code/User/`, not verified), under `servers` | No |
| `generic` | Generic JSON: `{"command": "<absolute path of saveslot>", "args": ["mcp"], "env": {"SAVESLOT_TOKEN": "<token>"}}` | No |
| `http` | Generates no host configuration, and only prints the token and the socket path (for scripts and connectors; `curl --unix-socket` can call it directly) | No |

How hosts present saveslot's prompts ([`05-surfaces.md`](05-surfaces.md) 10.1): in Claude Code (tested with 2.1.327) the slash menu shows `/saveslot:overview`, and typing `/saveslot:overview` or `/mcp__saveslot__overview` both work; but when the colon form is followed by arguments it reports "Unknown command", and with arguments only `/mcp__saveslot__pending health` can be written. Arguments are split on white space and matched by position, and extra words do not enter the prompt; a value containing spaces is quoted. Cursor's documentation says prompts are supported but does not say how to invoke them (not verified); Codex (tested with 0.167.2) does not support prompts: `/mcp verbose` does not list prompts, and both forms report "Unrecognized command". The hint at the end of `setup` is written according to this result: when Claude Code is among the attached hosts (attached this time, or already having an entry), it writes its slash command form and then "in any host, you can ask"; when it is not, it writes only "in any host, you can ask" and does not mention Claude Code.

- **The form of host commands**: the service name first, then `-e` / `--env`, then `--` and the executable. Add commands are always written at **user level**: saveslot's data is per person, not per project, so attaching should take effect for all of this user's projects; Claude Code's add command defaults to the "current project" level, so it explicitly carries `--scope user`, and other hosts that have a similar option are handled the same way. `vscode` has an add command, but neither `--apply` nor `setup` runs it, and it is only printed for the user to run: VS Code's MCP host is the Agent mode of GitHub Copilot Chat (the Ask and Edit modes do not call MCP tools), and its add command `code --add-mcp '<JSON>'` (tested with 1.147.0) writes into the user-level `mcp.json` (structured as `{"servers": {"saveslot": {…}}, "inputs": []}`), overwrites an entry of the same name directly, with exit code 0 and no prompt, and a newly created file has permission 0644, so the token ends up in a file that other users on this machine can read; `code` also has no command to look up a single entry, so "first use the host's look-up command to judge an existing entry" in 3.3 item 7 cannot be done. Running it on the user's behalf would mean silently overwriting an entry the user already has; tightening the file's permission would mean changing the host's configuration file, and saveslot does neither. So `connect vscode` states below the command: an entry of the same name will be overwritten; the `mcp.json` the token is written into can be read by other users, and after writing, `chmod 600` that file yourself (the path is given for macOS and for Linux).
- **A host with no add command** (`cursor`, `claude-desktop`) can only be pasted by hand, which is a known exception to the design requirement of section 1.
- **The token is shown only once**: the control plane stores only the hash; if it is lost, revoke and issue again. With `--apply` the CLI runs the host's own add command from the table above, and the token is not written into any file of the CLI, **but it does end up elsewhere**: a command pasted into the terminal enters the shell history; while `--apply` runs the host command the token is in the process arguments, and other users on this machine can see it with `ps` during the run; finally it lives in the host's configuration file. When `--apply` succeeds, the token is no longer shown: it prints "added to <host>, by running (the token not shown again):" and the command that ran, with the token's place written as `<token>` (the connection's ID, name and scope are on the line of issuing); the output of `--json` is unchanged and is still the result of issuing (including the token). The hint "The token is shown this once" is written to standard error (also with `--json`), and standard output holds only what is to be pasted. When only the unix socket is used, these exposures are harmless to other system users (they cannot connect to the socket), and once loopback TCP is turned on they are not (section 8.1). The exact form of each host's commands is maintained by the CLI's host adapter table and tested host by host at implementation time.
- **Commands use absolute paths**: when a host starts `saveslot mcp`, its PATH does not necessarily include npm's global directory (hosts started from a graphical interface, environments that switch Node with a version manager), so the generated commands always use the absolute path of the `saveslot` executable; `saveslot doctor` checks through the host's own look-up command whether the path in the entry still exists.
- **The entry file can be executed directly**: what the host gets is the path of the entry file, which it executes directly, so the first line of the entry file is `#!/usr/bin/env node` and it has the execute bit; the build sets the execute bit after compilation, and the build fails when the entry does not begin with this line. Running from a source checkout: after `pnpm install && pnpm build` the entry is `packages/saveslot/dist/bin.js`; execute it directly (`packages/saveslot/dist/bin.js setup`), or use `node packages/saveslot/dist/bin.js setup`; either way, what is registered with the host is the absolute path of this file.
- **The form of `--scope`**: when not given it is `saveslot.read saveslot.write saveslot.schema` (read and write, and it lets an Agent create a new slot through `saveslot_schema_draft`; it cannot delete, and MCP has no entry point for deleting a slot). The scope is fixed at issuing and does not change afterwards: for a connection issued earlier without `saveslot.schema` to gain the ability to create slots, `connect` again. There are two forms, which cannot be mixed:
  - Incremental: `--scope +delete` (add to the default), `--scope -schema`, `--scope -write` (remove from the default; not letting the Agent create slots is `--scope -schema`, and read-only is `--scope -write,-schema`); it can be repeated or joined with commas (`--scope +delete,-schema`). `+schema` is already in the default and is still a valid form.
  - Complete: `--scope read,write,schema`, where what is listed is everything.
  - The names may omit the `saveslot.` prefix. **Every connection must have `saveslot.read`**: `-read`, or a complete form that does not contain `read`, is a usage error (exit code 2), and no request is sent.
  - In the first version the scope cannot be changed after issuing; to change it, revoke and issue again ([`04-contract.md`](04-contract.md), "Callers: credentials and scope").
- **What is checked before issuing** (if any fails, nothing is issued, exit code 1):
  - The entry path (the item above) exists, is executable, and can be shown as it is.
  - Every form of output that is about to be written can be shown as it is and does not fall into the untrusted boundary: the host's command line, every line of the configuration snippet (after JSON encoding, so that for example a `"` in a path becomes `\"` with an escape), and the socket path of `http`. Output that falls into the boundary is of no use when pasted, while the token has already been shown.
  - `--apply`: the host's executable is found by the CLI itself in `PATH` (looking only at entries with absolute paths and taking the first executable file); if it is not found, nothing is issued; what is run and what is shown is the absolute path found, in both success and failure.
- **Failures after issuing**:
  - The token the service gave has the wrong shape (or there is none): treated as a failed self-check.
  - The self-check fails (calling `catalog` with the new token does not work): the CLI revokes the connection just issued at once, does not show the token, exits with code 1, and states the error the self-check reported; the revoked name is still taken, and the prompt says to use another name for connect.
  - Standard output cannot be written (it was closed): the token is only in this output, so the CLI makes a best effort to revoke the connection just issued and exits with code 1; when `--apply` has already succeeded, it does not revoke (the token is with the host).
  - `--apply` fails to run the host command (non-zero exit, terminated by a signal, the system cannot execute the file, not finished within 60 seconds): the connection is kept, the complete command (including the token) is printed for the person to run themselves, and the exit code is 1; standard error states which of these it was. On a timeout the host is stopped together with the processes it started (it is in its own process group). The host is executed without a shell, and its own output is read and discarded and is not passed to the user (it may echo the arguments it received).
- **The form of `--slots`**: a comma-separated list of slot names, and when not given = all (including those created later). Every one given must exist (otherwise `not_found` (`slot`)), and it cannot be empty. A connection with a limited range sees only these slots, cannot create slots, and slots created later by others are not included either; the range cannot be changed after issuing, and to change it, revoke and issue again ([`04-contract.md`](04-contract.md), "Callers: credentials and scope"). The `catalog` call of the self-check is made as usual, and it will only see the slots in the range.
- **Name suggestion: "device · host"**, which appears in history, as the initiator of items, and in the read audit.
- **A connector obtains its credential**: a connector (a program that periodically moves data from an external system into saveslot, not part of saveslot) uses `saveslot connect http --name "Band · connector" --slots health` to obtain a static token that touches only the slots it is responsible for, and writes through HTTP ([`05-surfaces.md`](05-surfaces.md) section 13).
- **The hint on completion**: at the end of `connect` and `setup` there is a line "optional: saveslot snippet <host>" (3.4).
- **Server mode (cloud service or self-hosted)**: the host goes through remote MCP and does the OAuth authorization itself; `saveslot connect claude-code --profile cloud` (for a self-hosted server, use its profile instead) prints the add command in remote form `claude mcp add saveslot --scope user --transport http https://<domain>/mcp` (its form has also been tested); this command has **no token**, so `--apply` and `saveslot setup --profile` run it on the user's behalf. On the authorization page the user names the connection and chooses the scope, both with defaults; the connection obtained through authorization has a slot range of all slots, and if the user changes nothing they click "Authorize" only once ([`05-surfaces.md`](05-surfaces.md) section 15). After authorization completes, `saveslot connections list` shows it, and renaming and revoking work as usual. The CLI issues nothing in this case, and `--name`, `--scope` and `--slots` are usage errors (they are decided on the authorization page; for a static token, use `connect http`); a host with no add command gets an entry to paste (`cursor`: according to public information its remote authorization needs dynamic client registration, which 0.1.0 does not provide, so in 0.1.0 Cursor attaches to a server with the static token of `connect http`. The output does not say the host signs in itself; it says this, gives the command that issues the token, `saveslot connect http --profile <profile> --name <name>`, and then one item under `mcpServers`, `{"url": "https://<domain>/mcp", "headers": {"Authorization": "Bearer TOKEN"}}`, for the user to fill into its `mcp.json` with the issued token in place of `TOKEN`; `--json` is still `{host, server, url}`. Dynamic registration is after 0.1.0, see [`08-open-questions.md`](08-open-questions.md); `generic`: `{"url": …}`), or an add command that is only printed (`vscode`: `code --add-mcp '{"name": "saveslot", "type": "http", "url": "https://<domain>/mcp"}'`; tested with 1.147.0, what is written into `mcp.json` is `{"type": "http", "url": …}`, and whether it can complete the authorization on its own from this one entry has not been tested; an entry of the same name is overwritten just the same, and the entry holds no token, so the file's permission is not mentioned), or an address to fill in on the host's interface (`claude-desktop`: a custom connector). Hosts that have only a web interface (the Claude web app, ChatGPT) have no command to run, and `saveslot connect <host> --profile cloud` gives the address to fill in on the host's interface, which is a known exception to the design requirement. Scripts and connectors without an Agent cannot go through OAuth: `saveslot connect http --profile cloud [--slots …]` issues a static token from the user session, which, as locally, follows scope and slot range and can be revoked.

### 3.3 `saveslot setup`: getting started with one command

`saveslot setup` only orchestrates, and each step calls the same implementation as the existing command; it introduces no ability that they lack. On the name: `init` already has a definite meaning (create the directory, write the tenant genesis; it is the only command that opens storage directly, and it refuses to run while the service is running), and adding "start the service, issue credentials, touch the hosts" to it would give one word two meanings. It is not made to run automatically after installation: post-install scripts would run without the user having expressed any intent, and package managers often disable them.

| Step | What it does | Equivalent to | When already done |
|---|---|---|---|
| 1 | Initialize | `saveslot init` | `~/.saveslot/` is already initialized: skipped |
| 2 | Start the service | `saveslot start` | Already running: compare the versions of the service and the CLI first, and skip if they agree; if they differ, stop and prompt to run `saveslot stop` first and run again (no automatic restart: a host may be connected), exit code 1 |
| 3 | Create a slot (a choice) | `saveslot slot create <name> --template <template>` | Any slot already exists: no question, skipped |
| 4 | Discover and choose hosts (a choice) | None | None |
| 5 | Show the host commands that are about to run, and ask once (the consent) | None | None |
| 6 | Host by host: issue a connection, self-check, run the host's add command | `saveslot connect <host> --apply` | The host already has an entry named `saveslot`: skipped, not issued again; at the same time check whether there is a corresponding valid connection (item 7) |
| 7 | Check and summarize | The host's look-up command; `saveslot status` | None |

**Details of each item**:

0. **Where it can run**: only on macOS and Linux (the first version supports only these two locally); on Windows it says it is not supported, does nothing, and exits with code 2. When `SAVESLOT_TOKEN` is set it also does nothing and exits with code 6: issuing a connection needs the user session.
1. **How it discovers which hosts are installed on this machine**: it finds the executable recorded in the adapter table (3.2) in `PATH` and successfully runs its version command (5-second timeout). It runs only the host's executable and does not read the host's configuration files. A host with no add command (an app with no command line) is judged by "whether the configuration directory exists", looking only at whether the path exists and not reading its content: for Cursor, `~/.cursor`; for Claude desktop, `~/Library/Application Support/Claude` on macOS and `~/.config/Claude` on Linux. A host it cannot discover does not appear in the list, and the user can still attach it separately with `saveslot connect <host>`.
2. **How to choose among several hosts**: interactively, it is a numbered list, where typing a number switches the item on or off and pressing Enter confirms. Hosts that have an add command and were discovered are ticked by default; a host with no add command is listed but given no number (it cannot be selected), and it is stated that `setup` does not attach it and that it must be configured by hand with `saveslot connect <host>`. **One connection per host**, with the default name "<host name> · <host display name>": the host name is taken up to the first segment (`MacBook-Pro.local` gives `MacBook-Pro`), at most 64 code points (cut by code point, not splitting a surrogate pair); when the host name is empty the name uses only the host's display name; several hosts do not share one connection, otherwise "who read, who wrote" cannot be told apart.
3. **Consent is asked only once, and the default is to run**: step 5 shows all the host commands together, with the token's place written as `<token>`, and one answer is given; pressing Enter means "run". **Consent first, issuing afterwards**: when the user refuses, no connection is issued and no host is touched, the exit code is 8, and it prompts "Later, saveslot connect <host> adds one host".
4. **Scope and slot range**: the scope is by default `saveslot.read saveslot.write saveslot.schema`, the consent screen lists these three truthfully, and `--scope` can change it, written as in `saveslot connect` and in effect for all hosts attached this time; to give hosts different scopes, attach them separately with `saveslot connect`. `setup` issues only connections whose slot range is all slots and has no `--slots`: it is meant for first-time getting started, and limiting the range is a deliberate choice, done separately with `saveslot connect --slots`.
5. **The host's add command is written at user level**, in the form of 3.2 (the service name first, then `-e` / `--env`, then `--` and the executable); the exact form is maintained by the adapter table and tested host by host at implementation time.
6. **Non-interactive environments** (standard input is not a terminal, or the standard error on which the questions are written is not a terminal: with `saveslot setup 2>log` a person cannot see the questions, and pressing Enter cannot count as consent):
   - Without `--yes`: nothing is run, the steps that would be taken are written to standard error, and the exit code is 8 (consistent with 5.4). No connection has been issued at this point, and the token's place in the written host commands is likewise written as `<token>`.
   - With `--yes`: the choices all come from arguments: `--template <template>` (repeatable; the slot name is the template's default name), `--timezone`, `--host <host>` (repeatable) and `--scope`. **A choice not given is treated as "do not"**: without `--template` no slot is created, and without `--host` no host is attached; it does not guess, and does not take "all discovered hosts". When no one is watching, doing less is safer than doing more.
   - `--host` pointing at a host with no add command: a usage error, exit code 2. That path would have to show the token, which should not happen where no one is watching.
   - These arguments can also be given interactively, and an item that is given is no longer asked.
   - A value repeated in `--host` and `--template` counts only once (keeping the order of first appearance) and is not an error; `--timezone` is used only for slots created with `--template`, and giving it alone is a usage error, exit code 2.
   - Creating a slot is the same code as `saveslot slot create --template`: an invalid time zone reports the same error and prompt, and the exit code follows that error.
7. **Running again is safe**: every step looks at the state before deciding whether to do it (the rightmost column of the table above). "The host already has a saveslot entry" is judged with the host's own look-up command (`claude mcp get saveslot` for Claude Code; `codex mcp get saveslot` for Codex). So a second run only completes the steps left unfinished and attaches newly installed hosts, does not issue again, and does not run into a "same name already exists" error. To replace an existing attachment: first remove the entry with the host's remove command, revoke the old connection with `saveslot connections revoke`, and run once more.
   - **An entry in the host does not mean the attachment is valid**: the token is not stored, so `setup` cannot work out from the entry which connection it uses. When skipping on the basis of an "existing entry", first look at whether the entry holds this saveslot's absolute path: both the standard output and the standard error of the look-up command are looked at, terminal escape sequences (CSI, OSC and a single ESC) are removed first, and at most 1 MiB is read from each stream; the path counts as "present" if the characters immediately on both sides of it are not path characters (letters, digits, `.`, `_`, `-`, `/`, `~`, `+`, `@`), or if the path is at the beginning or the end (`…/saveslot-old`, `…/saveslot+x`, `…/saveslot@2`, `…/saveslot~`, `/opt/usr/local/bin/saveslot` and `~/usr/local/bin/saveslot` do not count; a path with brackets, commas or color codes around it counts). When the host writes the path in another form (a resolved symbolic link, `~`, quoted or escaped), it cannot be seen; tests show that Claude Code 2.1.327 and Codex 0.167.2 both write the path as it was when added (symbolic links are not resolved, `~` is not written, and a path with spaces is not quoted), so it can be seen under the rule above. Two more test findings: when there is no entry, both exit with code 1 and empty standard output; `claude mcp get` starts the server to show its status, and when the start fails the exit code is still 0, so a successful look-up command only shows that the entry is there and does not show that it works. When the path is not seen: it is recorded as "unconfirmed" (`path_not_seen`), with the statement "it could not be confirmed to point at this saveslot. If saveslot works in the host, leave it; if not, remove it and run setup again", and the host's remove command is given. When the path is seen: look at the host's connections in `saveslot connections list` that are not revoked, in two tiers. The first tier is those whose name is exactly the name `setup` would give under the current host name ("<host name> · <host display name>", possibly with a sequence number): if there is exactly one, the summary records it as "existing" and gives it; if there is more than one, it is still recorded as "existing", but **does not identify** which of them it is (the token is not stored, and the token in the look-up output is not read for the sake of judging), lists all these instances (ID, name, the last read other than the self-check, and says so when there is none), and the user revokes those not in use. When there is no first tier and only a second tier (a name equal to the host display name, or ending with " · <host display name>", possibly with a sequence number), that is, signed under another host name (host names change: macOS renames machines according to the network) or named so by the user: it does not identify, records "unconfirmed" (`instance_unsure`), lists these instances, states "If saveslot works in the host, leave it; if not, remove it and run setup again", gives the host's remove command, and issues nothing new. When neither tier exists: it is recorded as "unconfirmed" (`no_instance`), with the statement "the host has an entry named saveslot, but no live connection instance of its name was found", and the host's remove command is given. "Unconfirmed" does not change the exit code.
   - **After adding, success is not decided by the path**: if before adding it was checked that there was no entry, the add command succeeded, and afterwards an entry is found, then it is attached and recorded as "done" (`done`); when the path is not seen in the entry it only writes one more line of explanation (each host has its own way of writing). "The add succeeded but the entry points to another path" can only happen when an entry already existed before adding, and in that case no add is made at all. Not finding the entry afterwards is a failure (item 8).
   - **Only one `setup` can run at a time**: when `setup` starts (before initialization; if `~/.saveslot/` and `run/` do not exist they are first created with 0700) it takes an exclusive lock under `~/.saveslot/run/setup/`, separate from the saveslot service's lock, and releases it only at the end; when it cannot take it, it does nothing and exits with code 7, prompting "another saveslot setup is running". Otherwise two terminals would both see "no slot" and "no entry" at the same time, each go to create and to issue, and then each report a failure.
8. **The state and recovery when it fails midway**:

   | Where it fails | What is left | How to recover |
   |---|---|---|
   | Initialization | There may be an incomplete `~/.saveslot/` | Stop, exit code 1; handle it according to the error of `saveslot init` and run again |
   | Starting the service | Initialized, the service did not start | Stop, exit code 7; `saveslot doctor`, and run again after fixing |
   | Creating a slot | Initialized, the service is running, no slot | Stop, the exit code follows the error of `slot create`; running again asks for the template once more |
   | Issuing | This host has no connection | This host is recorded as failed, and it continues with the next host |
   | Self-check | Nothing: the connection just issued is revoked at once (same as `connect`) | Same as above |
   | The host's add command fails | **Nothing: the connection just issued is revoked at once** | Standard error states the exit status of the host command; it continues with the next host; running again retries this host |
   | The host command succeeds, and afterwards the look-up command does not find the entry (or the look-up did not finish) | The connection is kept (the host may already be using it) | The summary states "the host's command ran, but its look-up shows no entry named saveslot", and gives the two commands to undo it: the host's remove command and `saveslot connections revoke <ID>`; this host is recorded as failed (`no_entry`; when the look-up did not finish it is `lookup_failed`) |
   | The host's look-up command does not finish (5 seconds) | This host has no connection | This host is recorded as failed (`lookup_failed`), and it continues with the next host |
   | SIGINT / SIGTERM / SIGHUP (the terminal closed) / SIGQUIT is received | The host command being run (add, `--version`, look-up) is killed together with its process group, and the wait for the service to become ready also stops; a connection that was just issued and whose host command did not succeed is revoked on a best-effort basis, and this host is recorded in the result as usual (`interrupted`, with its instance and the state after revocation); when interrupted while discovering hosts (`--version`), hosts not yet probed are not recorded in the result and it is not said that they were not found | Standard error gets one line "stopped: saveslot was asked to stop" and how far it got, and not the closing "Done."; it exits following the signal convention (129 / 130 / 131 / 143, that is, 128 plus the signal number). Other errors that come after the signal are reported for their own reason, and the exit code follows that too |
   | Input ended at a question | The steps finished before that question | Standard error states what has been done (initialized, the service is running, which slot was created, which hosts were attached), exit code 8 |
   | Initialization: the home cannot be used as it is (it already exists and its permission is not 0700 (for example the user did `mkdir ~/.saveslot` themselves), it is a symbolic link, it is a file, it belongs to another user, or it does not exist yet and the nearest existing directory above it is not writable by the current user; the `control/`, `credentials/` and `run/` already in the home are symbolic links, are files, belong to another user or have a permission other than 0700) | Unchanged: it is checked before anything is created in the home (including `run/`, where the `setup` lock lives) | It states the path, the reason and the corresponding fix: for a wrong permission, `chmod 700 <path>`, and says whether the directory is empty or already holds some items (when it already holds things, `--home` can also be used to choose another place); for a symbolic link, use `--home` to give the directory it points to; for a file in the way, move it away (stating which one is in the way, such as `run`); when the parent is not writable, create the home yourself (0700) or choose another place; for a wrong permission on a subdirectory such as `control/`, `chmod 700 <its path>`. Exit code 1, and `--json` gives `{"initialized": "failed"}`; a standalone `saveslot init` does the same |
   | The process is killed "after issuing, before the host command" | A connection whose token no one holds | A rerun does not revoke it automatically (a connection of the same name may also have been issued by the user themselves and be in use elsewhere); the newly issued name gets a sequence number appended (the names of revoked or disabled connections are still taken, and the same name cannot be issued again), and the summary lists this host's old connections (as in item 7, ignoring the host name segment): "older connection instance ci_…, with no reads besides its self-check since it was issued; it can be revoked with saveslot connections revoke" |

   When any host fails, the final exit code is 1; the summary states step by step "existing / done / failed". When a host command fails, its exit status (or being terminated by a signal, being unable to run, a timeout) is written to standard error, in both the text and the `--json` output. When started from npx's cache, as with `connect`, it warns that the path may become invalid. When a host command fails the connection is revoked rather than kept, unlike `saveslot connect --apply`: `connect` prints the command (including the token) for the person to run themselves, while `setup` does not show the token, and keeping a connection whose token no one has is of no use.
9. **Where the token passes**: only in the memory of the CLI process, in the process arguments while the host command runs, and in the host's configuration file; it is not shown on the terminal and does not enter the shell history (for the comparison table see 8.2). The `--json` output has no token; neither do the steps written to standard error when `--yes` is not given in a non-interactive environment (nothing has been issued at that point).
10. **It does not place the text of 3.4 on the user's behalf**, and only prompts with a line at the end, "optional: saveslot snippet <host>".
11. **Relation to existing commands**: `init`, `start`, `slot create`, `connect` and `connections …` are all kept and their behavior is unchanged; the default of `connect` is still to print, and only `--apply` runs; evals and scripts keep using single commands. `setup` does not install start at login (the automatic start of `saveslot mcp` already guarantees that hosts work); the hint in the summary about `saveslot service install` is added together with that command (P6).
12. **`--json`**: see 6.1.
13. **Server mode**: `saveslot setup --profile <name>` (the name is `cloud` or a registered server profile; `local` or not given means the local branch, regardless of the profile currently in use) replaces the steps with: if not logged in, first go through `saveslot login`; when there is no slot, create one from a template; for the chosen hosts, run the add command in remote form (3.2). On this path there is **no token**: the credential is obtained by the host itself through OAuth, and the "Authorize" on the authorization page is that one consent.
    - It does not initialize and does not start the local service; the lock of item 7 is still taken locally under `~/.saveslot/run/setup/` (created first with 0700 when the home does not exist). Item 0 still applies: when `SAVESLOT_TOKEN` is set, exit code 6.
    - **Login**: if this profile's login state can be used (the file is there, the server matches, and the refresh succeeds when needed), it is skipped; otherwise, interactively, `saveslot login` is run once (when `--device` is given, the device code is used; `--device` is used only for this server branch, and giving it alone is a usage error, exit code 2), and when login fails it stops with that command's exit code, and when the person refuses on the authorization page the exit code is 8; non-interactively (or with `--yes`) it does not log in and does nothing, prompting to run `saveslot login --profile <name>` first, exit code 8. An error between the CLI and the server during a refresh (cannot connect, the answer cannot be read, refused) is reported as a server error and not described as the local service, and the exit code is as in 6.2. The steps written to standard error when `--yes` is not given in a non-interactive environment likewise include the "login" step.
    - **Hosts**: discovery follows item 1; only hosts that have a remote add command (`claude-code`, `codex`) can be attached automatically, and the rest are listed with no number, stating to use `saveslot connect <host> --profile <name>`. `--host` pointing at a host with no remote add command is a usage error, exit code 2. `--scope` is a usage error, exit code 2: the scope is decided on the authorization page.
    - **Consent**: step 5 shows the remote add command (which has no token), and states that the authorization page will open the first time the host is used; one answer is given.
    - **The host already has an entry named `saveslot`**: if the entry shows this server's `<address>/mcp` (judged as item 7 judges the path), it is "existing"; if it does not (the local one, or one of another server), it is not overwritten, and is recorded as "unconfirmed" (`other_entry`), and the host's remove command is given. After adding, look up again as in item 7: if found, it is "done", and when the address is not seen in the entry it only writes one more line of explanation; if not found, it is a failure (`no_entry`).
    - **Failures**: this branch issues nothing, so there is no "revoke" column. A failed login: stop, the exit code follows the login; the person refuses on the authorization page: stop, exit code 8; the host's add command fails: this host is recorded as failed, the exit status is written to standard error, and it continues with the next host; the entry cannot be found afterwards: recorded as a failure (`no_entry`), and the host's remove command is given.
    - It does not switch the profile currently in use; at the end of the summary it prompts that the host must be authorized on the authorization page at its first use, and prompts `saveslot profile use <name>`. In `--json` there are no `initialized` and `service`, replaced by `signed_in`, see 6.1; when the home cannot be used as it is, `--json` gives `{}`.

### 3.4 Optional: custom instructions for the host

saveslot provides a piece of text that is suggested for pasting into the host's custom instructions. The host's own instruction file usually carries more weight and is a place the user can see and change; for some hosts, whether the host hands the server's `instructions` to the model has not been verified. **It is an optional enhancement, not a required step of integration**: without this text, the integration still completes, and the pass line of the main eval configuration is also computed without it ([`10-evals.md`](10-evals.md) "The Agent side" reports it separately as an additional variant).

**The text** (English is the default, and there is a Chinese version; it is written in the user's voice, because it sits in the user's own instruction file):

```
## saveslot
My long-term records (things that change over time: spending, workouts, budgets, progress) live in saveslot and are shared by all my agents.
- When I ask about my own records, numbers or history, check saveslot first (`saveslot_catalog`, then `saveslot_query` or `saveslot_sql`) rather than answering from memory.
- When I state a new fact that belongs in one of its tables, or correct an earlier one, save it with `saveslot_write` and include my exact words as evidence.
- If a receipt says something is pending confirmation, or a deletion is involved, show me the details and wait for my go-ahead.
```

```
## saveslot
我的长期记录（会随时间变化的事情：支出、运动、预算、进度）都在 saveslot 里，我用的各个 Agent 共用同一份。
- 我问到自己的记录、数字或过去的情况时，先查 saveslot（`saveslot_catalog`，再 `saveslot_query` 或 `saveslot_sql`），不要凭记忆回答。
- 我说出一件属于其中某张表的新事实、或更正之前说过的，用 `saveslot_write` 记下，并把我的原话作为证据带上。
- 回执说有内容待确认、或涉及删除时，先把详情给我看，等我同意再继续。
```

The text contains no user data and does not list slot names (those are given by `instructions`, and change with the data).

**`saveslot snippet [<host>] [--lang en|zh-CN]`**: prints the text and where that host takes it; without a host it prints the text and the table below. It is not a contract operation and does not connect to the saveslot service. It is not called `instructions`: that word already means the service-level description of MCP.

```
$ saveslot snippet claude-code
Add this to ~/.claude/CLAUDE.md (for every project), or to a project's CLAUDE.md:

## saveslot
My long-term records (things that change over time: spending, workouts, budgets, progress) live in saveslot …
```

**Where each host takes it** (the user level is recommended: saveslot is per person, not per project):

| Host | User level | Project level |
|---|---|---|
| Claude Code | `~/.claude/CLAUDE.md` | `./CLAUDE.md` or `./.claude/CLAUDE.md` |
| Codex | `~/.codex/AGENTS.md` (when `CODEX_HOME` is set, the `AGENTS.md` in it) | the `AGENTS.md` at each level from the project root down to the current directory |
| VS Code (Copilot) | `~/.copilot/copilot-instructions.md` | `.github/copilot-instructions.md` or `AGENTS.md` |
| Cursor | can only be set in the interface (User Rules) | `AGENTS.md`, or `.mdc` files with a header under `.cursor/rules/` |
| Gemini CLI | `~/.gemini/GEMINI.md` | the `GEMINI.md` in the workspace and the directories above it |
| Antigravity CLI | `~/.gemini/AGENTS.md` or `~/.gemini/GEMINI.md` | the `AGENTS.md`, `GEMINI.md` or `.agents/rules/*.md` from the launch directory up to the repository root |
| Claude desktop and web | Settings → Your Claude → Instructions (can only be changed in the interface; applies to all conversations) | project instructions |
| ChatGPT | custom instructions under Settings → Personalization | project instructions |

This table changes with the hosts' documentation and is maintained together with the adapter table; each entry is verified one by one before release. Gemini CLI and Antigravity CLI coexist: Antigravity CLI is for all users, while Gemini CLI can still be used through an enterprise license and a paid API key; both read `~/.gemini/GEMINI.md`, so putting the text there takes effect for both.

**Who places it: the user.** saveslot does not write the host's instruction file, and `setup` does not place it on the user's behalf after consent either (for the reasons see section 2, "What it does not do"). No host provides a command to "append content to the instruction file"; placing it on the user's behalf could only be done by editing the file directly, and an instruction file is text the user wrote by hand that directly decides how the model works, so a tool that writes into it must let the user read it word for word. It is indeed a manual step, so it counts as an optional enhancement and is not in the count of design requirements in section 1.

## 4. The command list

Global options: `--profile <name>`, `--json` (outputs the structured result of the contract, see section 6), `--yes` (non-interactive confirmation, see section 5), `--limit` / `--cursor` (paging, same as the contract). `saveslot --version` (used alone) prints this saveslot's version and exits 0: it is the same version the service reports on `/health`, that `saveslot start` compares, and that `saveslot status` writes as "this saveslot"; it does not connect to the service. `saveslot --help` prints the usage. The "Appears in" column corresponds to the implementation steps in section 7.

### 4.1 The service (local only; it manages the process and is not a contract operation)

| Command | Purpose | Key parameters | Output highlights | Appears in |
|---|---|---|---|---|

**Operations commands for self-hosted servers** (P5; run on the server, provided by `daemon`, not contract operations; our cloud service uses the same set):

| Command | Purpose |
|---|---|
| `saveslot server init` | Creates the tables of the control database (the control plane's, the remote authorization's, and the chosen identity provider's: external login's when `SAVESLOT_IDENTITY_*` is set, the built-in local accounts' when it is not), generates the handle signing key, creates the first user; the connection and the public address come from "Server mode configuration" below. It can be run repeatedly: when the control database is already initialized it only checks its format version, when the key file already exists it leaves it alone, and when a user already exists it does not create a first user again (and does not ask for a password), with one exception: if the last `init --user` created an account of the same name but did not finish creating its tenant, this run finishes it; if the format version is not one this saveslot knows, it does nothing and reports an error. The first user's name is given by `--user <name>`, and the password is read as for `user add`; without `--user` no user is created. Only for built-in local accounts: when external login (`SAVESLOT_IDENTITY_*`) is set, giving `--user` does nothing, exit code 5 |
| `saveslot server start` | Starts in server mode (in the foreground, left to systemd or a container to manage); after receiving SIGTERM or SIGINT it goes down in three steps, each with a time limit: (1) the state in `/health` becomes `stopping` and `GET /ready` answers 503, while every other request is handled as before, for `SAVESLOT_SHUTDOWN_DRAIN` seconds, so that the load balancer notices and stops forwarding; (2) it takes no new connections, a new request on a connection still open gets `unavailable` (`stopping`; a path outside `/v1` gets 503), an import still uploading its request body is aborted, and it waits for the requests in progress to finish, for at most `SAVESLOT_SHUTDOWN_TIMEOUT` seconds, after which the connections still open are closed; (3) it closes the tenants (for at most 10 seconds), releases the lock, closes the control database, and exits with code 0. A tenant not closed by then is no longer waited for: the database connection held by a use stuck on it (for example, waiting for the tenant's write lock) goes when the process exits, its transaction rolling back with it, and its client was already disconnected in (2); the process still exits after releasing the lock, with the same exit code, and logs a warning. Another SIGTERM or SIGINT during the shutdown skips what is left of the waits in (1) and (2) and goes straight to (3), still releasing the lock. The container's termination grace period must be no shorter than the sum of the three steps. `GET /ready`, like `/health`, needs no token; it is for the load balancer's health check and the container's readiness probe: it answers 200 when the state is `ready` and 503 otherwise (`starting`, `stopping`, `failed`), with the same body as `/health`; `/health` answers 200 in every state, the state being only in the body. At startup it first takes the "server is running" lock on the same control database and goes on only when it has it, holding it throughout the run: another `server start` cannot get it, exits with code 7 and does nothing; `server restore` cannot get it during this time either. The lock lives on the control database's connection: if this connection drops while running (the database restarts, a primary-standby switch, a middlebox cuts an idle connection), the lock is gone with it, and the service then stops immediately (`/health` reports `failed`, reason `control_database_lost`; other requests get 503), closes the tenants and exits with code 7, to be restarted by the process manager, which takes the lock again. The tables in the control database are only checked, not created: the control plane's tables, the remote authorization's tables and the chosen identity provider's tables (the `SAVESLOT_IDENTITY_*` of "Server mode configuration" below) are all created by `server init`; when they are missing or their format is not recognized, it exits with code 5 and hints to run `server init` first; after changing the identity provider, also rerun `server init` first with the new settings |
| `saveslot server user add <name>` / `list` / `disable <name>` / `enable <name>` | Manage the built-in local accounts; registration is not open. Only for built-in local accounts: when external login is set, these commands are refused before the control database is opened, exit code 5 (the accounts are managed by the external platform). They do not take the "server is running" lock and can be run while the server is running. `add` also creates a tenant for this user. `list` gives one line per account, by name: name, state (`active` / `disabled`), tenant ID (the one `server restore --tenant` uses). `disable` disables the account: while it is disabled, all credentials of this user's tenant (user sessions and connections, including those obtained through OAuth authorization) are rejected at authentication, `unauthenticated`, with `reason` `account_disabled` ([`04-contract.md`](04-contract.md) section 16); no credential is revoked, no event is written into the tenant's log, and the tenant and the data are untouched. `enable` enables it again: these credentials are restored as they were, and those that came due during the disabled period expire as usual. To stop a connection for good, revoke it with `connections.revoke` |
| `saveslot server user passwd <name>` | Changes a local account's password and invalidates this user's existing logins and user sessions (a session issued before the change cannot be renewed either); connections are not affected, and no event is written into the log. When the account does not exist, exit code 4 |
| `saveslot server restore --tenant <tenant>` / `--user <name>` | After a tenant database has been put back from a backup and before it serves again, runs the restore flow on it: appends the "restore" event, re-applies deletions according to the deletion register, runs the deletions that are already due; if interrupted it can be run again and carries on to the end ([`02-architecture.md`](02-architecture.md) §8). The tenant is given by ID (`--tenant`), or by the name of a built-in local account (`--user`: that account's tenant is restored); exactly one of the two must be given, once, otherwise it is a usage error (exit code 2). `--user` finds the account by name as `server user disable` does: no account with that name (including a name that breaks the rules for account names) is exit code 4; an account whose tenant has not finished being created (a `server user add` that stopped; run `add` again with the same name to finish it) is exit code 5; a disabled account is restored as usual (disabling is about authentication only). `--user` is only for built-in local accounts: when external login is set it is refused before the control database is opened, exit code 5, and the tenant is given with `--tenant`. Finding the account by name is also done under the lock below. The control database is not put back: the restore flow works from the deletion register and the `seq` high-water mark in it. It runs only when no server is running on the same control database: it first takes the same lock that `server start` holds while running, does nothing if it cannot get it, exits with code 7, and hints to stop the server first; it holds the lock throughout, and during that time `server start` cannot start. A database that was swapped in without going through this command, and is found so when it is opened, is refused by the service, which hints to run it |

The passwords of `server init`, `user add` and `user passwd` are read only from a terminal or from a password file (`--password-file <path>`), and a password in a command line argument is not accepted: arguments end up in the shell history and the process list. With no terminal and no `--password-file`, nothing is done and the exit code is 8 (same as `export --encrypt`). On a terminal nothing is echoed and the password is typed twice; if the two differ it is asked again, and after three tries that all differ nothing is done. The password file is checked as `SAVESLOT_HANDLE_KEY_FILE` is (after following symbolic links it is a regular file, readable by this process, with no permission bits for "other"; group-readable is also fine; pipes are not accepted), and its first line is taken (without the line ending, and without a leading UTF-8 BOM). A file that does not exist, is not a regular file, cannot be read, is open to others, or whose first line is empty each reports its own reason, nothing is done, and the exit code is 2; when the password itself breaks its rules (8 to 1024 characters) the exit code is 5. When `server init --user` is given a password file, all of these are checked before anything is created; when reading from a terminal, it is asked only after the tables are built and it is settled that this account will be created, and then three tries with two different entries (2), a password that breaks the rules (5) or Ctrl-C (130) only mean that this account is not created: the key file and the tables are already in place, the message says so truthfully, and rerunning `server init --user` is enough.

The count of failed logins goes by this address. An entry with bits set after its prefix, a prefix length out of range or not strictly written, one covering every address (`0.0.0.0/0`, `::/0` and the like), or one with a port or a zone is handled as malformed ([`02-architecture.md`](02-architecture.md) §5) | Empty |

| `SAVESLOT_IDENTITY_LOGIN_URL` | External login: the platform's login address, to which a browser login is sent, carrying only `state`. It must be `https://`; `http://` is accepted only when the host is a loopback address | Unset |
| `SAVESLOT_IDENTITY_KEYS_FILE` | External login: the platform's public key file, a JWK Set (`{"keys": [...]}`), each key an Ed25519 public key with a `kid`. To change the public keys, replace this file and restart | Unset |
| `SAVESLOT_SHUTDOWN_DRAIN` | The shutdown's drain: how many seconds requests are still handled as usual after the stop signal (`/ready` already answers 503 during it, see `server start` above), an integer from 0 to 3600; 0 means no wait | `10` |
| `SAVESLOT_SHUTDOWN_TIMEOUT` | The shutdown's limit for requests in progress: after the drain, at most how many seconds to wait for the requests in progress to finish, an integer from 0 to 3600; the connections still open by then are closed; 0 means no wait, closing them at once | `30` |
| `SAVESLOT_TENANT_CONNECTIONS` | The most tenants a process has open at once, which is the most tenant connections it holds (each open tenant has one connection, [`02-architecture.md`](02-architecture.md) §7 "Connection"), an integer from 1 to 10000. At the limit, the tenant idle for longest is closed first; with none idle, requests wait in line, and one that gets no place within 5 seconds gets `unavailable` (`busy`). The default of 50 fits one process, by the connection budget below, within PostgreSQL's default `max_connections` of 100, with room left for the control database, imports and operations; with more than one process, lower it or raise `max_connections`; a large deployment raises it within its connection budget | `50` |
| `SAVESLOT_TENANT_IDLE` | How many seconds after its last use an idle tenant is closed and its connection given back, an integer from 1 to 86400 | `300` |

**Connection budget**: the PostgreSQL connections a deployment uses must satisfy `SAVESLOT_TENANT_CONNECTIONS` × processes + 4 × processes + imports at the same time × 2 ≤ the connections the instance has available. The 4 for each process are the fixed connections the limit does not count: one to the control database; one to the maintenance database for creating databases, and one to the database of the tenant being created, for databases and tenants are each created one at a time in a process, and one waiting behind another waits at most 5 seconds, then is answered busy for now (an external login's first sign-in gets 503 with `Retry-After`; `server user` and `server init` exit with code 7); one to the maintenance database for dropping databases, for drops happen one at a time in a process, with no limit on the wait since no one waits for their answer (a drop waits for a checkpoint, slow on a busy server, so it does not share the creations' turn and hold back first sign-ins); an import opens two databases directly; the connections available are `max_connections` less `superuser_reserved_connections`, `reserved_connections` and what operators use themselves.

When a required variable is missing or its value is malformed, the command does nothing, says which variable, and exits with code 5 (the same as when `config.toml` is rejected, 6.2); the error does not contain the value of a variable (a connection string may contain a password), and only `SAVESLOT_TRUSTED_PROXIES` and `SAVESLOT_ALLOWED_ORIGINS` name the entry that does not fit (an address or an origin holds nothing that needs to be kept secret).

| `saveslot delete apply <dc_…>` | `deletion_preview` (`{confirm}`: the preview is produced again from this `dc_`) → person confirms → `delete` | `--yes` (skips showing and asking) | The full preview, the confirmation prompt, the deletion receipt | P3 |
| `saveslot delete cancel <pi_…>` | `resolve` (`deletion` · `cancel`) | `--yes` | The result of the cancellation: the writes returned to their original state, the items restored, the new `ver`; (later: the candidates that were judged again and the result of each, `rejudged`) | P3 |
| `saveslot delete status <pi_…>` | `pending` (details, `deletion`) | — | When the grace period ends, the state of each place (logical deletion → physical erasure → the date the backups expire); it can still be queried after it ends | P3 |

Revoking a row is not a deletion; it is an ordinary business write, done by the Agent with `revoke`.

### 4.7 Queries and history (for people to read)

| Command | Contract operation | Key parameters | Output highlights | Appears in |
|---|---|---|---|---|
| `saveslot query <table>` | `query` | `--where 'distance>5km'` (repeatable), `--order`, `--fields`, `--valid-at` / `--valid-during`, `--include-revoked`, `--detail` | The row text of MCP `saveslot_query`: `ver`, values, all flags (including "premise changed"); `--detail detailed` puts indented lines of its own below each row: the operation number and moment of the latest change, the literal match and source level of each field (a `ref` field carries a summary of the referenced row), and all premise declarations currently in effect (in the same words as the MCP text, 05 §4.1, §4.2) | P1 (`--detail detailed` P2; on a derived table the service answers `not_in_this_version`, and the CLI outputs it as a general error and adds a hint) |

| `saveslot sources [list / search <term> / get <s_…>]` | `sources` | `--slot`, `--kind`, `--from` / `--to` | A list of source data or the original text; for deleted ones only the tombstone information | P2 |

`history changes` is a subcommand: when the first word after `history` is `changes`, it is read as the subcommand, and the following words are the table name. So when a table happens to be named `changes`, its timeline must be written with a qualified name: `saveslot history <slot>.changes <row or entity>` (the first word is not `changes`, so it is handled as a timeline); the changes of this table are written `saveslot history changes changes --since 0` or `saveslot history changes <slot>.changes --since 0`. Writing `saveslot history changes <row>` does not get the timeline of that table: `<row>` is taken as a table name, and without `--since` it reports a usage error (exit code 2), with it `unknown_table` (exit code 4).

The shorthand of `--where` only splits `field operator value` into the contract's `{field, op, value}`; a quantity with a unit has the unit written after the number (`'distance>5km'`), and omitting the unit reports a usage error; other unsupported forms likewise report a usage error; complex conditions use `--where-json` (a condition object or an array of conditions, which can be given together with `--where` and are merged into one list). Values are given by the field's type: integers and decimals are written as they are (sent as decimal text, with no limit on digits), booleans are written `true` / `false`, and the rest are taken as strings as they are; the field types come from the `catalog` of this table (read one extra time, only when `--where` is given). A condition containing `<` or `>` must be quoted, otherwise the shell takes it as a redirection. `--valid-during` is written `<from>,<to>`, with the end left empty meaning open; `history --as-of` takes an operation number or a moment, and `--as-of-read` takes a read ID. The statement of `saveslot sql` is one argument (quote the whole statement); `--param` is repeatable and corresponds to `$1`, `$2`… in order of appearance, always sent as strings, and the service decides the type by how `$n` is used in the statement (dates, numbers and text are all given this way); booleans and `NULL` are written directly in the statement. The number of rows per page uses `--max-rows` (default 100, upper limit 1,000), and `--limit` is not accepted; paging uses `--cursor`; `--at` is the moment of evaluation. Reads by the CLI are recorded in the read_log like those of an Agent, with the user as the actor; when `SAVESLOT_TOKEN` is set, the connection is.

| `saveslot verify --replay` | `log.reconcile` | — | The `seq` compared up to; the result of replaying the log from an empty store and comparing it table by table with the online logical tables of kind (b); on a mismatch the tables and rows are listed (IDs only). It shows progress while running (replay, catching up, comparing), and on entering the comparison phase it hints "writes are queued for the moment"; the end of the output says that it cannot detect results that `delete` itself computed wrongly | P2 |

**Where the output goes**: `-o <file>` uses exclusive creation (`O_CREAT|O_EXCL`, in one step, not check-then-write) with permissions 0600; when the file is already there it is refused, not a single byte is written, and the exit code is 2; this check is made once before a request is sent to the service and before the password is read, and the final exclusive creation is kept as it is. To overwrite, give `--force`: it writes to a temporary file newly created in the same directory (exclusive creation, 0600), and renames it over the target only after the whole stream has ended successfully; on a failure midway the temporary file is deleted, the original file is left exactly as it was, and this is said truthfully. When `-o` is a symbolic link, `--force` replaces the link itself and the file the link points to is untouched; without `--force` a link counts as "already there" just like a file. When a write without `--force` fails halfway (a broken stream, a full disk), the file left behind is incomplete, and the message says so. The reason: an export file is often just the backup, and the cost of overwriting it by a slip is greater than the cost of typing one more option. The file is created only when the first bytes from the service arrive, so an export that the service refuses leaves no empty file. With `--encrypt`, when standard output is a terminal and there is no `-o`, it is refused with exit code 2, saying that the encrypted output is binary and that `-o <file>` or a redirect should be used; without encryption, NDJSON can be written to a terminal as usual.

`--include-pending-deletion` asks for one more confirmation in interactive use: "this export will hold content that is waiting to be deleted: after the grace period ends it stays in the export file. Export it anyway?" In non-interactive use `--yes` must be given at the same time, otherwise it is not run and the exit code is 8.

**Password encryption of the export** (`--encrypt`). The export format does not change; encryption is an optional feature of the CLI, using the public age v1 format with a passphrase recipient (scrypt), and it encrypts the whole export stream (including the manifest on the first line). No private format is made: the project is open source, so a container of our own would hide nothing and would only add a format that nobody else recognizes. Not chosen: OpenPGP (the implementations do not interoperate on the new authenticated encryption modes, and its licenses are stricter than the project's), `openssl enc` (no authentication, so a modified ciphertext goes undetected), JWE (encrypts one whole piece at once, unsuited to the stream of a large file), encrypted ZIP (weak key derivation, and the file headers are not encrypted).

- **Where the passphrase comes from**: by default it opens the controlling terminal directly and reads without echo, asks twice and starts over when they differ; what is read is the controlling terminal and not standard input, so `saveslot export --encrypt > file` can still prompt as usual. `--passphrase-file <path>` reads the first line of that path (without the line ending `\r\n` / `\n`), for scripts and password managers; the output of a password manager is handed to it with the shell's process substitution: `saveslot export --encrypt --passphrase-file <(pass show saveslot) -o backup.ndjson.age`. The path is opened as given (following symbolic links: on Linux the `/dev/fd/63` that process substitution gives is itself a link), and what is checked is the object obtained after opening: a regular file must belong to the current user and have permissions no wider than 0600, the same rule as for credential files, otherwise it is refused and the message says how to fix it; a pipe (process substitution, a named pipe) must belong to the current user, and the permission bits differ by platform and are not looked at; a character device (`/dev/stdin` on a terminal) is accepted; directories, sockets and block devices are refused. When reading from a pipe it waits at most 30 seconds, and refuses if the writing side never writes, so it does not hang; it is closed as soon as it is read. Giving `--passphrase-file` without `--encrypt` is a usage error (exit code 2), and is not quietly taken as encryption. With no terminal and no password file: not run, exit code 8.
- **The passphrase does not appear in command line arguments or environment variables**: there is no `--passphrase <passphrase>` (command line arguments end up in the shell history, and other users on the machine can see them with `ps` while it runs); and the first version does not read an environment variable either (on some systems other processes can read it, and child processes inherit it).
- **Only `--passphrase-file` is supported on Windows**: there is no corresponding controlling terminal device file there. On Windows, giving `--encrypt` without `--passphrase-file` is a usage error (exit code 2). The local service only supports macOS and Linux anyway, so this only affects a CLI that runs on Windows with a server profile.
- **Requirements for the passphrase**: it must not be empty; shorter than 12 characters it warns once and does not refuse. The passphrase is used byte for byte as given, without Unicode normalization (consistent with age); so that the same passphrase gives the same bytes from a file, a pipe and a terminal, one from any source that contains a control character (including Tab) or starts with a byte order mark (BOM) is refused with an explanation, and not quietly stripped. On a terminal, an empty passphrase or one with a control character is asked again just like "the two entries differ", three tries at most. saveslot does not store the passphrase and has no way to recover it, and in interactive use says so before it reads the passphrase.
- **The work factor** uses the format's default (scrypt log₂N = 18), and no option to adjust it is provided: the official JS implementation rejects values above 20 when decrypting, and raising it would produce files that "encrypt, but cannot be opened by the same library". When standard output is a terminal, outputting ciphertext is refused (a usage error); the first version does no text wrapping.
- **Resuming**: each export (including a continuation with `--after-seq`) is an independent age file with its own header and salt, and can use a different passphrase. Ciphertexts cannot be concatenated (an age file followed by extra data is rejected): to join several segments, decrypt each first, then join the plaintexts in order by the continuation rules of the export format. An encrypted export that was interrupted midway is a truncated age file, which reports an error when decryption reaches the end and cannot be continued by appending; export that segment again with the same `--after-seq`. After encryption the manifest line cannot be seen without decrypting, so the end of the run says the `upto` to use for the next continuation.
- **Decryption**: use any age implementation, saveslot is not needed (`age -d -o export.ndjson export.ndjson.age`, or `rage -d`); the first version does not provide a decryption command of saveslot's own. When `saveslot import` meets an age file it decrypts it in the CLI and then uploads the plaintext, with the same sources and rules for the passphrase as for export; the server does not accept age files, because that would mean handing the passphrase to the server.
- **What it guards against and what it does not**: it guards against the export file being obtained by others after it leaves this machine (cloud drives, external disks, backups, forwarding). It does not guard against programs with the user's own permissions on this machine at the moment of export (they can read the data directory anyway), a passphrase that is too weak, or a forgotten passphrase. It is not storage encryption: the first version does no application-level encryption of storage (positioning "Technology choices").
- **Implementation**: the `cli` package depends on the official `age-encryption` (version pinned). CI runs an interoperability test: a file from `saveslot export --encrypt` is opened with the `age` command line and is byte for byte the same as the plaintext export; the passphrase is supplied non-interactively through `age-plugin-batchpass` (`AGE_PASSPHRASE_FD`), so it runs in CI without a terminal.

```
$ saveslot export --encrypt -o saveslot-2026-11.ndjson.age
The passphrase is not kept: if it is forgotten, this export cannot be opened.
Passphrase:
Again:
exported 1284 events, last seq 1311, without the content waiting to be deleted, encrypted with the passphrase (age v1)
to continue later: --after-seq 1311; to decrypt: age -d -o export.ndjson saveslot-2026-11.ndjson.age
```

**Import** (`saveslot import`) loads an export into an **empty tenant** (the log holds only the genesis event, and the anchors hold no registrations or marks in progress); in local mode the target is the tenant that exists after `saveslot init`, and in server mode `--profile` is added. Continuation files are given in order, and the CLI uploads them in the same request body. Before running it reads the manifest and asks for confirmation; in non-interactive use `--yes` must be given (otherwise exit code 8). The principals registered before the import that are still valid (the original users and connections) are all disabled (revoked ones stay revoked), the writers in the history are still shown as before, marked "disabled"; all integrations must be issued again at the target. The way to migrate is: stop writing at the source → export → import → issue again at the target → disable the source. The rules are in [`04-contract.md`](04-contract.md) "Administrative operations".

## 5. Interaction for human confirmation

### 5.1 Listing and details

`saveslot pending` sorts by how long items have been open, the earliest first; items do not expire, and the CLI offers no shortcut to "clean up old items". The rendering of `saveslot pending show`:

```
pi_9B… awaiting confirmation · marketing.budgets promo · opened 3 h ago · version iv_7e…
  Initiated by: MacBook · Codex, 11-10 18:02 · reason: erases a recorded change point
  Proposed: from 11-02 set to 3000 CNY (continuing on)
  Segments that would be overwritten:
    from 11-10 4000 CNY (#103, recorded by MacBook · Codex) → will become 3000
  The value in effect does not change until confirmed.
  Choices: confirm / reject
```

- **The segments that would be overwritten, the writes that would be reverted, and the rows that still reference the row** (the `impact` of the item details) are listed one by one: the write's `#seq`, the writer, the old value → the new value, the interval (with its endpoints in plain words).
- A conflict lists the current value in effect and each candidate (the same as `saveslot_pending` in [`05-surfaces.md`](05-surfaces.md) "Key points of the text for each tool"); a schema change lists `changes[]` and the impact preview according to the draft part of the item details, and states that the impact preview is an estimate made when the draft was submitted.
- Only the decisions available to the current credential are listed; a user session can use all of them.

### 5.2 Resolving: how a confirmation is bound to its content

`saveslot pending resolve <pi_…> <decision>` does three steps in one call:

1. It fetches the details (`pending`), gets the `item_ver`, and renders it for the person as in 5.1;
2. In interactive use it asks: `Run confirm on pi_9B…? The 1 segment listed above will be overwritten [y/N]`;
3. It calls `resolve` with **the `item_ver` obtained in step 1**.

- **The CLI never relies on the fallback**: the contract allows that, when `item_ver` is not passed, the version most recently read by this connection is used ([`04-contract.md`](04-contract.md) "Version tokens: `ver`, `sv`, `item_ver`"), but the fallback takes the version this credential read most recently: a newer version that another terminal, or another program using the same credential, has just read would be taken, while the person in front of the screen looked at an older one; the CLI always passes explicitly the version it showed this time, so that "what is confirmed is what the person has just seen".
- **The caller gave `--item-ver`**: it is sent as it is and is not replaced with the version the CLI has just fetched. In interactive use, when the version fetched differs from it, it says directly "the item changed since the version given; this is what it is now", shows the current content and asks again; with `--yes` it **does not fetch the details**, does not show them, and calls `resolve` directly, and a mismatch is reported by the server as `confirmation_mismatch`.
- **The item is already closed when the details are fetched in step 1**: it does not ask, says what it was resolved by or what superseded it, exit code 3 (the same as when `resolve` returns `item_closed`).
- **A conflict item has several candidates and `--candidate` was not given**: in interactive use the candidates are listed (index, value, writer) for the person to choose; in non-interactive use it is a usage error, exit code 2, and the output lists the candidate indexes.
- **Decisions that the contract specifies are not bound by `item_ver` follow the contract**: the `cancel` of `deletion` is not checked (5.3); the `accept_all` of `migration_diff` carries the `diff_upto` from when it was shown (with `--yes`, `--diff-upto` must be given; comes with P4b).
- **The content changed** (`confirmation_mismatch`): in interactive use it renders the current content attached to the error, says "the content has changed since you looked at it", and asks again; in non-interactive use it does not retry automatically, exit code 3, and outputs the new `item_ver`.
- **Already closed** (`item_closed`): it says what it was resolved by, or which write superseded it, exit code 3 (written as in the item details: who, which decision, which candidate `take_candidate` took, and the note given at resolution; the note is text written by the caller and is put inside the untrusted boundary); when resending the same decision gets a replayed result, it writes "this item was resolved as confirm at …; this time nothing new was recorded", exit code 0.
- `--note` is recorded in the log (`UntrustedText`, which can be cleared along with a deletion); the person's written reason goes here.

### 5.3 Deletion: preview, confirm, cancel

```
$ saveslot delete --source s_R1
Will delete 1 source, affecting 1 row, recomputing 1 derived value
runs r_01JC… whole-row deletion: date comes only from this sentence
These writes were not in effect and will take effect:
  (none)
Will not be deleted: the enum values and descriptions in the schema; the metadata kept after deletion (that a row once existed, and by whom it was written how many times)
Local service: if saveslot is not running when the time comes, the physical erasure is carried out at the next start; old copies in system-level backups such as Time Machine are not managed by saveslot
To confirm the deletion, type delete: delete
Deleted. It can be cancelled within 24 hours (until 11-11 21:05): saveslot delete cancel pi_4K…
```

- The sections of the preview are rendered as in [`03-data-model/03-deletion.md`](03-data-model/03-deletion.md) "What the preview and the receipt must state"; the "writes that were not in effect and will take effect" are on a line of their own, and "(none)" is written when there are none, so that the person knows this item was looked at.
- **Confirmation requires typing `delete`; a single key `y` is not accepted**: deletion is the only operation that cannot be reversed after the grace period.
- What is used at confirmation is the `dc_` of the preview that was just shown. On `preview_outdated` the contract gives a new preview: in interactive use it is shown again and asked again; in non-interactive use the exit code is 3 and the new `dc_` is output. `handle_expired` (more than 10 minutes) is the same, with a hint to preview again.
- **`saveslot delete apply <dc_…>`**: it first fetches the preview from the contract again with this `dc_` (the `{confirm}` of `deletion_preview`), shows it as above, and then requires typing `delete`: the `dc_` it was given may have been generated by another caller, and the person must see what it deletes before confirming. With `--yes` it neither shows nor asks, and the guarantee on this path is that "what is executed is the scope computed when this `dc_` was generated".
- **When the preview is long**: the first screen gives the totals first and the row-by-row results are shown in pages; the confirmation prompt repeats the totals ("will delete 3 sources, affecting 1,024 rows"). It can be confirmed without paging to the end, but the person has at least seen the scale. When the "writes that will take effect" or the "writes that will become awaiting confirmation" are not empty, the confirmation prompt likewise repeats their counts.
- Cancelling with `saveslot delete cancel` does not check the item version ([`04-contract.md`](04-contract.md) "Pending items: kind × decision × effect × scope"), and it can be cancelled directly from another terminal; it still asks for one `y/N` confirmation, because cancelling makes the writes made within the grace period on the state after the deletion be recomputed. Within the grace period, items cannot be resolved and writes cannot be undone on rows affected by this deletion: when such a command reports an error, it says which deletion it is and when it comes due, and gives two ways out (wait until it comes due, or cancel this deletion first).

### 5.4 The boundary between interactive and non-interactive use

| Case | Behavior |
|---|---|
| Standard input is a terminal, `--yes` not given | Shows the content and then asks |
| Standard input is not a terminal, `--yes` not given | Does not ask and does not run, exit code 8, with a hint to first fetch the content and the binding token with `saveslot pending show --json` / `saveslot delete preview --json` and then run with `--yes` (the token is not printed in the hint) |
| `--yes` given | Does not ask; but confirmation commands that change data must also be given the binding token: `saveslot pending resolve` needs `--item-ver`, and deletion can only use `saveslot delete apply <dc_…>` (`saveslot delete --source … --yes` is refused); `saveslot delete cancel` and `saveslot connections revoke` need only `--yes` |

**Why non-interactive confirmation is allowed**: saveslot does not distinguish whether a confirmation comes from a person or an Agent ([`02-architecture.md`](02-architecture.md) §3), and interactive asking cannot stop a program that can operate the terminal either; adding an extra flag such as "I am really sure" provides no guarantee and only adds steps. The real guarantee is content binding: a script must first get the token with `saveslot pending show --json` / `saveslot delete preview --json`, and what is executed is the very version that was handed to it. The CLI cannot guarantee that the script looked at the content; it only guarantees that the version executed is the version handed over, and that nothing is executed if the content has changed.

## 6. Output conventions

### 6.1 Human-readable text and `--json`

- **Human-readable text** (the default): produced by the CLI renderer from the contract's fields. Flags are written as in MCP ([`05-surfaces.md`](05-surfaces.md) 4.2 "Flags", 4.3 "Warnings and hints"), and the renderer tests likewise check that every contract flag appears in the text; `notices[]` are written at the end; `warnings[]` are all rendered (including `multi_segment_unmapped`, from which a person can go back and add the evidence mapping). `saveslot pending show` lists, for a `flagged` item, the rows that matched and the group of keys that matched; the `dangling_ref` flag in a read result is rendered as MCP writes it. The next steps in hints are written as CLI commands, not as `saveslot_` tool names.
- **`--json`**: standard output holds only one JSON value, the structured result of the contract, in the same shape as the HTTP receipt; the CLI does not rename or drop fields; `export` is the exception, and is an NDJSON stream. On an error it outputs the contract's `{"error": {...}}`; errors that the CLI finds itself (such as `ambiguous_name` when the name given to `connections revoke` matches more than one connection) also use the same outline, and then the `code` is the CLI's own and is not among the contract's error codes. A combined command outputs the result of the last contract operation (that of `resolve` for `pending resolve`, that of `delete` for `delete --source`); `connect` outputs the result of `connections.issue` with an added `selfcheck` field; a `connect` on a server profile where the host signs in itself (section 3.2 "Server mode", nothing is issued) outputs `{host, server, url, command?, applied?}`: `server` is the profile's server address, `url` is the remote MCP address, `command` is the host's add command (an array of arguments, without a token; a host with no add command has no such entry), and when `--apply` is given `applied` is added (`true` / `false`, by the result of the host command); `connect http --profile` is the same as local and outputs the result of `connections.issue` plus `selfcheck`; `profile list` outputs `{current, profiles}`, where `profiles` is `[{name, at}]` (`at` is the socket path of `local` or the server address; the built-in `local` and `cloud` come first, and registered ones follow sorted by name), and `profile use` outputs `{current}`; `setup` outputs one object, which contains no token: `initialized` (`existing` / `done` / `failed`; when initialization fails the object has only this entry), `service` (`ready` / `failed`; when startup fails the object ends here, and the exit code follows `start`), `slots` (`[{template, slot}]`), `slot_failed` (present only when creating a slot failed, and holds the name of that template; `hosts` is then an empty array, and the exit code follows the error of slot creation), and `hosts` (in the order of the arguments or the list, each entry `{host, state, reason?, connection?, connections?}`). `state` has six values: `existing`, `done`, `unconfirmed`, `failed`, `manual` (listed but there is no add command) and `not_found` (`--host` was given but not found). `failed` and `unconfirmed` carry a `reason`, which is a stable code: for `failed` it is `command_failed`, `command_signal`, `command_timeout`, `cannot_run`, `interrupted`, `no_entry`, `self_check_failed`, `issue_failed`, `lookup_failed` or `unshowable`; for `unconfirmed` it is `path_not_seen`, `instance_unsure`, `no_instance` (§3.3 item 7) or `other_entry` (the server branch, §3.3 item 13). Other states carry no `reason` (`not_found` is itself the reason). `connection` is `{id, name, state}`, with `state` being `live` or `revoked`; when the host already has an entry and there is more than one valid instance in the first tier (`existing`), or when there are only instances of the second tier (`unconfirmed` / `instance_unsure`), no `connection` is given and `connections` is given instead (`[{id, name, last_read}]`, where `last_read` is the moment of the last read other than the self-check, or null). When it stops midway, `stopped` is added (`declined`, `input_ended`, `interrupted`), and it only means that a person or the input made `setup` stop. The server branch (§3.3 item 13) has no `initialized` or `service`, and the object begins with `signed_in`: `existing` (already signed in: the token is usable or was refreshed successfully), `done` (this run signed in successfully), `failed` (sign-in failed: the issuer is wrong, the server rejected it, or both the refresh and a new sign-in did not succeed; the object ends here, and the exit code follows `login`), `needed` (not signed in and no terminal to sign in on, nothing was done; the object ends here, exit code 8, with a hint to run `saveslot login --profile <name>` first); a person's refusal on the authorization page is `signed_in: "failed"` plus `stopped: "declined"`, exit code 8; after that come `slots`, `slot_failed` and `hosts`, the same as the local branch (the entries of `hosts` have no `connection` / `connections`: this branch issues nothing). A script must look at fields such as `status` and not only the exit code (the same rule as for HTTP).
- Interactive prompts, progress, and lines like "the token is shown only once" go to standard error, so that with `--json` standard output stays parsable.

### 6.2 Exit codes

| Exit code | Meaning | Corresponds to |
|---|---|---|
| 0 | Completed (including replays and results like `outcome: pending` that are "recorded but not in effect": look at the output) | — |
| 1 | An internal error of the CLI or the saveslot service; integration not completed | `internal`; a failed self-check of `saveslot connect` (the connection just issued is revoked) or a failure of the host command run by `--apply` (the connection is **kept**, and the command has been printed for the person to run); `saveslot setup` with a failed host (when the host command fails the connection just issued is **revoked**, because the token was not shown to anyone), a failed initialization, a mismatch between the versions of the service and the CLI |
| 2 | Command usage error (found by the CLI itself) | For example an option that takes only one value was given twice (it is not "the last one counts"); the name given to `connections revoke` matches more than one connection; the password file of `export` cannot be used (a regular file with permissions wider than 0600, not owned by the current user, not a file or pipe, unreadable, nothing written to the pipe in 30 seconds, empty, containing a control character, each with its own reason and fix; this is a usage error before any request is sent, not 6, which is reserved for credentials), the file of `-o` is already there; the password file of `server init --user`, `server user add` or `server user passwd` cannot be used, or the two entries differ three times on a terminal; both or neither of `server restore`'s `--tenant` and `--user` are given |
| 3 | Read again first / the content has changed | `read_first`, `confirmation_mismatch`, `item_closed`, `preview_outdated`, `handle_expired`, `draft_outdated`, `schema_incompatible` |
| 4 | Not found | `not_found`, `unknown_table`, `unknown_field`; the tenant named by `server restore` does not exist, or the account named by `--user` does not; the account named by `server user disable`, `enable` or `passwd` does not exist |
| 5 | Request rejected | `saveslot init` meets an initialized directory or a running service (nothing is changed), `saveslot start` meets an uninitialized directory, or after the service is up finds the storage format too old or too new, or the upgrade of the storage format fails (`upgrade_failed`; in each the storage must be dealt with first, and the same retry is useless); `config.toml` is invalid (`saveslot start` before it spawns the process, foreground start and `saveslot config get` all refuse this way, see 4.2); an environment variable of server mode is missing or malformed (4.1 "Server mode configuration"); `invalid_argument`, `validation_failed`, `field_unmatched`, `sql_rejected`, `sql_timeout`, `too_large`, `derived_readonly`, `revoked`, `not_in_this_version`, `import_rejected`, `rate_limited` (`quota`), `referenced` (later), `lease_expired` (later); `server restore` meets a control database without tables or in a format it does not recognize (with `--user`, the local accounts' tables included), a tenant whose creation has not finished (with `--user`, an account with no tenant registered included), `--user` while external login is set, a tenant database with no log (the backup has not been put back yet), a tenant with an import in progress, or a tenant that has entries in the deletion register (this version cannot yet re-apply deletions, and nothing is changed); `server restore`, `server user` or `server init` meets a storage format upgrade that fails as it opens a tenant (`upgrade_failed`: only the step that failed and the SQLSTATE are written, not the database's error text, [`02-architecture.md`](02-architecture.md) §8); `server start` meets tables not yet created by `server init` or tables in an unrecognized format; `server user` meets such tables, a name that is taken or breaks the rules, a password that breaks the rules, or external login is set (`server init --user` likewise) |
| 6 | Credential or permission | Not logged in, a credential file with permissions that are too wide, `unauthenticated` (the token is invalid, revoked, or the session has expired), `insufficient_scope`; for `saveslot mcp` the `SAVESLOT_TOKEN` is unset, empty or not a connection token (including a user session token); at `saveslot login` the server's issuer is not this server, or the authorization is refused by the server |
| 7 | Cannot connect or temporarily unavailable (retry later) | The saveslot service is not running (`saveslot stop` is the exception: exit code 0 when it is not running); at `saveslot stop`, the pid reported by `/health` differs from `run/saveslot.pid`, or `/health` does not answer while `run/saveslot.lock` is held (in both cases no signal is sent); `saveslot start` cannot wait until it is ready (the process is still running; while the storage format is upgraded it waits on, and that does not count), the service fails by itself after it came up (the data directory is missing, an internal error and so on; see `saveslot status` and the service log for the reason; except a storage format that is too old or too new, or an upgrade that failed, see 5), the socket is unreachable, `unavailable` (busy, restoring, importing, comparing, starting, upgrading the storage format included), `rate_limited` (`busy`); `saveslot start` or `saveslot setup` fails to start the service, or another `setup` is running; the profile's lock cannot be obtained after waiting the full 10 seconds (the same for `login`, `logout` and replacing the token; consistent with the lock of `setup`); at `server restore` a server is running on the same control database (nothing was done); at `server start` a server is already running on the same control database (nothing was done), or the control database connection dropped while running (the lock is lost with it, and the server stops) |
| 8 | Not executed | A person declines at a prompt (including the refusal at step 5 of `saveslot setup`: nothing was issued; `saveslot login` refused on the authorization page, that is `access_denied`); the device code of `saveslot login` expired or the wait timed out (in both cases nothing was written); non-interactive use without `--yes` or the binding token; `export --encrypt` with no terminal and no password file; `server init`, `server user add` and `server user passwd` with no terminal and no password file |
| 9 | Validation found problems | `saveslot verify` reports a break / mismatch, `saveslot verify --replay` reports an inconsistency, `saveslot doctor` has failing items (with only warnings, 9 is not given) |
| 129 / 130 / 131 / 143 | Stopped by a signal (128 plus the signal number: SIGHUP / SIGINT / SIGQUIT / SIGTERM) | `saveslot setup` that receives one of these four signals finishes up and exits this way (§3.3 item 8); `server user add` and `server user passwd` on Ctrl-C at the password prompt (130, nothing was done); `server init --user` on Ctrl-C at the password prompt (130: the key file and the tables are in place, the account was not created, rerun it); `saveslot login` that receives them while waiting for the browser or the device code (including when received while the request to exchange the token is in flight) closes the local loopback listener, writes nothing, and exits this way |

Exit codes are only broad classes; the authoritative information is the `error.code` in `--json`; error codes that the contract adds later fall into the closest class other than 1, and unknown ones are handled as 5.

### 6.3 How errors are shown

The text is rendered from the `code` and the accompanying fields (the same content as [`05-surfaces.md`](05-surfaces.md) "The text of errors"), written to standard error; the first line is `error <code>: <one sentence>`, followed by next steps that can be carried out:

```
error confirmation_mismatch: pi_9B… has changed since you looked at it
  Now proposed: from 11-02 set to 3500 CNY (continuing on)
  To look again: saveslot pending show pi_9B…
```

For validation errors, the `details` are one line each: the detail's `code` (for those with `max` / `min`, "at most N" / "at least N" is written after the code, consistent with the MCP text), then where it is: those of `op`, `path`, `table`, `field` and `line` that were given (the keys are the CLI's own wording, and the values are put inside the untrusted boundary); when `valid` is present (the `required_in_gap` found at judgement), the interval of that stretch is written too, in the same form as an interval in a read result (an open start and a whole stretch of time are written as there). When the slot count has reached its limit (`out_of_bounds` with `path` `slot`), one more line is started, pointing to the command that removes an empty slot (`saveslot slot remove`). For example:

```
error validation_failed (「write」): 「the write falls where the entity has no value」
  required_in_gap  at op 0, table 「plan.budgets」, field 「amount」, valid 「2026-11-05」 to 「2026-11-06」 (inclusive)
```

### 6.4 Untrusted text in the terminal

The `UntrustedText` of the contract ([`04-contract.md`](04-contract.md) "Untrusted text") carries two kinds of risk in a terminal: one is that control characters in the original text rewrite the terminal (ANSI escape sequences, clearing the screen, Unicode bidirectional override characters that make one piece of text display as another), and the other is that an Agent with a shell, when reading the output of the CLI, is injected by instructions in the original text.

- **Control characters are always escaped**: C0 / C1 control characters, ESC, and bidirectional override and isolate characters are shown in a visible escaped form (such as `\x1b`, `<U+202E>`); the range of escaping is the same as for MCP ([`05-surfaces.md`](05-surfaces.md) section 5 "The untrusted boundary"), plus: the corner brackets 「」 and the characters that become 「」 after compatibility normalization; space-like characters other than U+0020; consecutive U+0020 from the third on (written as `\x20`, so that a screen full of spaces cannot use the terminal's line wrapping to forge a "next line"); a `<` that would be read as an escaped form or a boundary tag, and a `<` at the end of a value. A backslash is written as `\\`, so that escaped text can be restored to only one original text; truncation truncates only the original value and then escapes it, and the truncation marker is written outside the untrusted region. `--json` writes the same escape set (the same rules, without the consecutive-spaces rule) as `\uXXXX`, the same as the way MCP writes the raw JSON; the value does not change, and it is still valid JSON.
- **In human-readable text, untrusted values are enclosed in corner brackets** (`「legs a bit sore, very tired」`), and when the terminal supports color they are shown in a muted color, to tell them apart from saveslot's own explanations.
- **When standard output is not a terminal** (read through a pipe or by an Agent), untrusted values are instead wrapped in numbered boundary tags (`<untrusted-data-NUMBER>…</untrusted-data-NUMBER>`, the opening and closing with the same number, a new number for each output), in the form and with the rules of MCP ([`05-surfaces.md`](05-surfaces.md) "The untrusted boundary"); a person processing through a pipe uses `--json`, or turns it off with `--untrusted-tags never` (`always` forces it on).
- The descriptions written by a caller in a schema are marked with both the writer and the version, as in MCP.

## 8. Security

### 8.1 The local service is for this machine only

| Measure | What it guards against |
|---|---|
| Listens only on a unix socket, the directory 0700 and the socket 0600 | Other system users, anyone on the network |
| Loopback TCP is off by default; when on, it binds only the loopback address and checks `Host` / `Origin` | Access from the local network; access from web pages through DNS rebinding. **When it is on, other system users on this machine can also connect**, and for them the token is the only line of defense left |
| Every request needs a token (a connection or a user session), and the socket permissions do not replace authentication. The only exception is `GET /health`: it involves no principal and no data, and `saveslot start` needs it to compare versions and `saveslot mcp` needs it to tell whether the service is already up; the response has only `state` (`starting` / `ready` / `stopping` / `failed`), `version`, `pid` and `since`, with, on `failed`, a reason code that contains no paths or user data; the local service also carries `writer_lock: "held"`: the process that answers took the home's single-writer lock before it began listening (`saveslot status` writes its single-writer lock line from this), this one value only, with no path or anything else; when running with a test clock it also carries `eval_clock` (`now`, `started_at`, step 3 of section 3), and this field is absent otherwise; while the storage format is upgraded (`starting`) and when the upgrade failed (`failed`, `upgrade_failed`) it also carries `upgrade` (`from` and `to`, two format versions, and `step`, the step it is on or failed at, written `5->6`), and this field is absent otherwise. The recorded moment at the end of the log counts as activity information about the data and is not put into `/health`; `saveslot status` gets it through a request that carries the user session (the same place as the pending count). Any other path without a token gets 401 (`unauthenticated`, the same as [`05-surfaces.md`](05-surfaces.md) section 14) | Tells principals apart and limits scope: each Agent can do only what its connection was granted, and reads and writes each leave a trace. It is not a defense against programs with the same permissions: a program that can reach the socket can generally read the credential file too (8.3) |
| The data directory is created by `init` with 0700; one placed outside the home with `--data-dir` has its owner and permissions checked when the service starts, and startup is refused if they do not fit (section 3 step 2) | Other system users on the same machine reading and writing the tenant database: the files that storage creates would be readable and writable by others, and only the directory keeps them out |
| Local mode provides no configuration to bind to a non-loopback address | A misconfiguration exposing personal data to the network; for use across devices use server mode (our cloud service, or self-hosting, which is another startup form with OAuth, not opening a port for local mode) |

The CLI and `saveslot mcp` use only the fixed socket path under the home (`run/saveslot.sock`), and do not accept changing it to another address from an environment variable or an argument, which removes one way of being misled elsewhere by a misconfiguration; this is not a defense, since a program with the same permissions can change the files under the home all the same.

### 8.2 The credential file

- `~/.saveslot/` is 0700; each file under `credentials/` is 0600, and the CLI refuses to use one whose permissions are too wide.
- The control plane stores only the hash of a token; a connection token is shown only once at issuance, and the CLI does not keep it.
- A connection token lives in the host's MCP configuration ([`03-data-model/02-integrity-and-records.md`](03-data-model/02-integrity-and-records.md) "Connection identity (done in the first version)"), and its protection is the host's responsibility; when a token leaks, `saveslot connections revoke` takes effect at once.
- The handle signing key is in `control/keys/`, apart from the data directory.
- **The places a connection token passes through**, by integration method:

  | Place | Pasting after `connect` | `connect --apply` | `setup` |
  |---|---|---|---|
  | Display on the terminal (scrollback buffer) | Yes | Only on failure | **No** |
  | Shell history | Yes | No | **No** |
  | The process arguments of the host's add command (visible to other users on this machine while it runs) | Yes | Yes | Yes |
  | The host's configuration file | Yes | Yes | Yes |
  | Any file of the CLI itself | No | No | No |

  While loopback TCP is off, another system user who gets hold of it still cannot connect (they cannot reach the socket); before turning on loopback TCP, first confirm that none of these places leaks, and when in doubt revoke and issue again. In server mode the host goes through OAuth, and there is no static token on this path.

  When `--apply` runs the host command, the host inherits the whole environment of the CLI: the host is the user's own tool and needs its environment (`PATH`, `HOME` and so on). `SAVESLOT_TOKEN` is not carried over: if it is set, `connect` itself is refused (issuing can only use a user session).

### 8.3 Operations only a user session can perform

| Operation | CLI command | Why a connection is not given it |
|---|---|---|
| `connections.issue` / `update` / `revoke` | `connect`, `connections …` | An Agent that can issue credentials can give itself any scope, and the scope would lose its meaning; revocation is the only means by which a person takes back permission |
| `slots.remove` | `slot remove` | Removing a slot decides which slots this tenant has and to whom the quota goes; an empty slot an Agent created by mistake is cleaned up by the user |
| `policy.set` (later) | — | The policy decides which changes take effect without confirmation, which amounts to changing the confirmation rules |
| `reads.list` | `reads` | What is audited is exactly the connections; the party being audited should not be able to read the whole audit |
| `log.verify`, replay comparison | `verify` | For operations; it reads the whole log; of no use to an Agent |
| `log.end` | `status` (clock warning) | For operations; the moment of the last write counts as activity information about the data, and is not given to a connection |
| `export` | `export` | It takes all the data and the original text of the source data in one go, bypassing "read on demand, leave a trace each time"; taking the data away is the user's right, not an Agent's |
| `import` | `import` | It replaces the whole content of an empty tenant with an export, and disables the principals registered before the import that are still valid (revoked ones stay revoked); it decides what is in this tenant and whose credentials are still valid |

The other operations (reads, each kind of `resolve`, `delete`, `schema_draft`) can be done by a connection according to its scope, and a user session can do them all.

**The boundary stated truthfully**: the local user session credential is a file on this machine, and programs with the same permissions as the current system user, Agents with a shell included, can read it and can also run `saveslot` directly; saveslot cannot guard against this kind of program, which is the same boundary as their being able to read and write the data directory directly ([`02-architecture.md`](02-architecture.md) §10). The restrictions in the table above block Agents that connect only through MCP / HTTP. To keep a certain Agent from reaching these operations, do not give it shell access to `~/.saveslot/`.

**Traces are the same boundary**: for a CLI run with the user session credential, reads, confirmations and deletions are all recorded under the user's name; when an Agent with a shell does so, it cannot be told apart from a human's operation, and "who read it, who confirmed it" does not hold on this path. Give such an Agent a connection token and have it run the CLI with `SAVESLOT_TOKEN` set (or call HTTP directly), and only then do the traces go under its name.

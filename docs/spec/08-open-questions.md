# saveslot · Open questions

English · [简体中文](../zh-CN/spec/08-open-questions.md)

> The only list of undecided items: every item in the design that is not yet settled is recorded here, and when other documents mention "undecided" they point to this document.
> For positioning and technology choices see [`01-positioning.md`](01-positioning.md); rules already settled are written in the individual design documents, and this document lists only the undecided parts.
> Grouped by "when it must be decided" into three groups; for the phase numbers see [`07-scope-v1.md`](07-scope-v1.md) section 4.

## I. To decide before development

Things that will be written into log events and are hard to change once settled. They block P1.

**None at present.** The following have been settled: the unit vocabulary, the default precision and rounding, and the criteria for the same value (data model, "Field types, same value and units"); the default slot policy (data model, "What a slot contains"); the structure fingerprint of read records and the type of `visibility` (data model, "Reads"); how identifiers are written (data model, "How identifiers are written"). Undecided items that appear before the event format is frozen and that would enter events are recorded here.

| Before P3 | **The symmetry of the conflict criterion holds only within one range; whether to change the rules for the three cases outside it** (the range and the three cases are written in the symmetry paragraph of the data model, "Conflict handling · Conflict criteria", each with a fixed case, see [`11-claims.md`](11-claims.md)). The three are: (a) a write with an explicit interval and a write that passes no end point, with the same start and the same value, do not conflict, but when merged the default end point is resolved against the current state, and the end point of the explicit write that arrived first became a stop point, so the end states of the two orders differ (in one order the original value is kept after the explicit end point, in the other the new value is continued), and neither opens an item; (b) when a write goes into awaiting confirmation because of high impact, it does not count as the L of another write, so for the same pair of writes, in one order "one side becomes a candidate" and in the other "one side is awaiting confirmation and the other takes effect": both need a person to handle them, but the kinds of item differ; (c) the default end point of one write stops at some stop point in the version seen, while another write carrying `acknowledge` erased that stop point: base `5000 [10-01, ∞)`, #12 `4000 [11-25, ∞)`, both from v12, L = "4000, from 11-10" with no end point, carrying `acknowledge` (after which 11-25 is no longer a change point), A = "6000, from 11-20" with no end point. L first: A merges, the default end point is resolved against the current state, and it is written as `[11-20, ∞)`; A first: A stops at 11-25, and `[11-25, ∞)` is still 4000. Both orders merge and neither opens an item, but the end states differ, and it is the same when A is a corroboration (5000); in the L-first order A also overwrites the value of `[11-25, ∞)` in the version it saw, although A never said anything about that stretch, which contradicts "by default, known facts are not broken". What has to be decided: keep the rule as it is and promise symmetry only within the range now written; or change the rule so that (a) is symmetric too (for example, an explicit interval × a default end point with the same value is also handled as intersecting). A candidate change for (c): on merging, if the stop point at which a write stopped in the version seen has since been erased by a later write, do not merge and handle it as a conflict |

## III. Can be decided after development

- **Setting the center by data ownership**: which data must, from the very beginning, "never leave the device"? (Only needed with multiple nodes; the slot's "owning node" field is already reserved.)
- **Security of community schemas + SKILL**: a SKILL is executed by the user's Agent; how are permission declarations and review to be done (the risk of prompt injection)? The templates of the first version are bundled with the CLI, and no remote source is introduced.
- **`unavailable` has no reason for "the service has failed"**: when the local service has failed (a check failed when the tenant was opened, and the like; it stays failed until it is stopped, 02-architecture §7), `/v1` now answers `unavailable` with the reason `stopping` and no `retry_after`: the contract's reasons have no "failed", and `stopping` (it takes no new requests) is the closest. Where it is not accurate: the service is not stopping and will not recover by itself; someone has to look at `saveslot status` / `saveslot doctor`, deal with it and restart it; and MCP's text for `stopping`, "saveslot is stopping; try again shortly", leads a model to retry for nothing in this case. A reason `failed` for the contract is considered (without `retry_after`, its text pointing to `saveslot status` / `doctor`); it changes the operation contract and needs a decision record first.
- **The last-used moment of a connection** (`Connection.last_used_at`): not given in the first version. The initial idea is to take, at query time, the moment of this connection's most recent operation from the log and the read records, writing nothing on the authentication path.
- **Whether read_log should be chained like the log** (preventing mistaken operations). read_log is local run state, and whether it is added or not, the log is not touched.
- **Table-level and field-level data permissions (later versions)**: the slot level is already in the first version: the authorization of a connection = action scope × slot range (all, or a list of slots), and a slot outside the range is the same as nonexistent to it (contract section 12, P5). What remains:
  - Resources down to the table, and sensitive fields down to the field level; giving the same connection different scopes for different slots (in the first version, to get that, sign two connections); changing the range after signing (in the first version, revoke and sign again; the event format has reserved `principal.scope_changed` for it). Table level must first answer "by what are items and source data filtered" (they belong to a slot, not to a table), and whether the complete schema document (the `schema` tier of `catalog`, the document of a draft, the `schema_change` item) may be given to a caller who can see only some of the tables (this version gives it only when every table of the slot is visible: the text of a derivation rule carries out the names of the tables it reads); field level has to touch the visibility of derived tables and the shape of read results.
  - **How source data is given under a table-level visible range**: source data belongs to a slot, and the original text and the request of an `api_call` may mention any table of the slot. In the first version, when a caller's visible range on a slot is not the whole slot, the source data of that slot does not exist for it, without exception (contract, "`sources`"). The details are decided when table-level ranges are opened up: filtering by which tables the data it produced landed in; whether the original text is given when the data it produced spans visible and invisible tables; whether the original text of evidence and the request of an `api_call` are handled separately.
  - **Derived data inherits permission by provenance**: a derived table that comes from both health and bookkeeping data requires a reader to have read permission on all its sources; saveslot has the complete provenance relation and can enforce this. In the first version derivation rules do not cross slots, and at the slot level a derived table and its base tables go in and out together, so this is not needed yet.
  - A table without permission is invisible in the catalog; read-only SQL is also bound by the same permissions (row / column level isolation); in remote mode OAuth scopes can be divided by domain (the slot range of the first version is not encoded into the scope string).
- **Choosing the slot range on the authorization page**: in the first version the range of a connection authorized remotely is always all, and a credential with a limited range can only be a static token signed by a user session (surfaces section 15). When it is added back, these have to be decided:
  - How a client declares the slots it wants: an extension field in the client metadata, provisionally named `saveslot_slots`, to be verified at implementation; when it is written wrongly, whether to ignore it or reject it.
  - The preselection rule: when the client declared slots, preselect those of them that exist, and how to list on the page the ones that were declared but do not exist; when it did not declare, preselect "all"; whether the selector is always shown.
  - Step-up: for the new connection obtained by authorizing again after an overreach, whether the range carries over from the original, the original is preselected, or it is chosen anew.
  - What to do when, after the user agrees on the authorization page and before the authorization code is exchanged, a selected slot is deleted (refuse the exchange, or sign for what remains).
  - The slot list is not passed back in the authorization result and the token response (a slot name is the user's own data), and the client sees the slots in range only through `catalog`: this stays as it is.
- **When "some kinds of operation accept confirmation only from a user session" is implemented**: the structure of the slot policy already has a place reserved for it; it depends on changing the slot policy (`policy.set`), and comes later together with high impact ③.
- **System ruling by source level**: the rank table and the structure of the re-judgement event have a place reserved; the details of the ruling rules (how to compare when one side hits and the other does not, whether a sequential write of a lower level can directly overwrite the user's own words) are decided when it is added back. The rule for who declares the "external authority" level is settled (data model, "Source level": it is decided by the permission granted to the connection, and the writer cannot claim it); the details still undecided: the form of the grant (a new scope, or a separate item on the connection), whether it can be granted per slot, whether the level a credential declared is still recognized in rulings after the credential is revoked, and the relation to literal match.
- **Conversion between temperature units**: in the first version `Cel`, `degF` and `K` are each their own dimension and are not converted. When it is added back, an optional offset is added to the unit definition, and existing definitions do not change.
- **Correcting the key of an entity (`rekey`)**: in the first version a key cannot be changed, and a wrongly written key is handled by revoking and writing again, so the history breaks into two entities; the receipt marks existing keys that are written similarly (`similar_keys`). If writing the wrong key turns out to be common in the evals (eval 4d), `rekey` is added; it is a new write intent or op parameter, and does not change existing events.
- **Custom units outside the vocabulary**: in the first version units come from a fixed vocabulary, and a quantity outside the vocabulary uses a `decimal` / `integer` field with the unit stated in the description. Whether a slot may carry its own unit definitions is decided together with a new version of the unit vocabulary.
- **Table and field names only ASCII**: in restricted SQL a Chinese identifier has to be quoted and models easily get it wrong, so the first version accepts only letters, digits and underscores; description text is not restricted. Whether to open it up depends on user feedback. When it is opened up, the slot list in `instructions` has to be looked at again: it relies on this character set to block line breaks, punctuation and forged boundary tags.
- **The definition of a statistical anomaly**: the threshold, what to group by and what to do at cold start are all unwritten. The first version does not judge and does not produce items; when it is added back it is a new judgement result, and an old event without it means "not judged".
- **A table declaring its expected record frequency, and read results carrying a coverage mark**: the first version has no such mechanism; "there should be a record every day" is domain knowledge, and the coverage columns of the derived tables in the templates (the number of days with records, the first and last dates) hand it to the Agent to judge. If in the evals the Agent often calls "partial" "complete", then consider: an optional declaration on base tables (expected one per day, one per week, or none declared); and having reads by time window and derived rows bucketed by time carry a coverage mark accordingly (complete / partial / no data). It is a new optional key on the schema document and on read results, and does not change existing events. What has to be decided: how the frequency is written; whether the mark is computed at read time or enters the derived writes; how to express that the user explicitly said "there was none that day" (which differs from "not recorded").
- **A manual way out of a deterministic migration**: a purely deterministic migration has no manual way out; if the evals find that a large deterministic migration also needs people to be able to give up midway, it is added (the "give up migration" event has a place reserved and the first version does not produce it; adding the way out is adding a new kind of event and does not change existing events).
- **The cost of aggregating `input_marks` when reading a derived table**: in the first version every `query` of a derived table first reads the marks on the base tables the rule reads; if there are no marks it looks no further, and when there are marks it works out only for the marked rows which partition they fall in, so the cost varies with the number of marked rows and not with the size of the table. Whether to switch to maintaining membership by partition when there are many marks is for the numbers of experiment 4 to decide.
- **Rounding decimal group keys before grouping**: the first version accepts only `decimal` / `quantity` group keys whose upper bound of decimal places does not exceed the inferred precision (for how the upper bound is computed see [`03-data-model/11-restricted-sql.md`](03-data-model/11-restricted-sql.md), "Types"; those containing division or `avg`, or whose products or literals have more digits than the precision, are not accepted). If needed, change it to round the key to the field's precision first and then group: a `half_even` key needs its own rounding, and the grouping semantics change with it, so it has to go into the specification and a new allowlist version has to be issued.
- **Whether restricted SQL on PostgreSQL needs a separate read-only connection**: a trade-off between concurrency and cell capacity. The first version shares the connection.
- **The hosted cluster capacity experiment** (to be done before the cloud service scales out; it does not affect the design itself): crash recovery and standby switchover time on Linux cloud disks; autovacuum coverage and wraparound margin under 24 hours of full load, which decides whether each group holds 2,000 or 5,000 user databases. Also to be measured: cold-user restore latency and concurrent tail latency.
- **When a cold-tenant archive becomes void after the tenant is restored to the cluster**: left until the cloud service capacity phase. The initial idea: void after the restore and a passing `verify`, once the next regular backup succeeds; no cold archive is made for a tenant with a deletion not yet due.
- **Whether the kernel can be instantiated in runtimes other than Node, Bun and the Electron main process**: not verified.
- **Whether read_log is replicated with the log** (multiple nodes).
- **Developer SDK** (later versions): how the interface is designed and to which layer it is opened; the tenant model when developers buy hosting (developer / application → end user → slot) and data ownership
  (whether it belongs to the end user or to the developer, and whether the end user can export and move it away); whether embedded storage is merged into the saveslot service as a node; the form for non-JS hosts (such as Python), which in practice can only be a local sidecar process.
- Cost and commercialization: not discussed for now.

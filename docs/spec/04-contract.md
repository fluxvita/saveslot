## What this document is

**The contract is the shape of the operations, independent of the transport: which operations exist, which parameters each takes, which structured result each returns, and which errors each reports.** MCP, HTTP, the CLI, the App and a future developer SDK are all generated from it and have equal standing (architecture §2, §11).

- **Two parts**: part one, `contract-core`, is the shape of the data, and the kernel depends on it; part two, `contract`, is the outer wrapping (idempotency, paging, handles, credentials, outer errors), and the service layer and the surfaces depend on it.
- **No kernel rules**: the authoritative definitions of conflicts, high-impact writes, supersession and deletion results are in the data model; this document only refers to them and states how they appear on the interface.
- **Nothing about the surfaces**: how text is rendered, the wording of flags, MCP tool names and annotations, HTTP paths and status codes are all in 05-surfaces.md; the CLI commands and interaction are in 06-cli.md.
- Errors, flags and warnings have only structured fields in the contract (a code and the fields that accompany it); the explanation for a person is rendered by the surface from these fields.

## The operations at a glance

| Operation | Read / write | Required scope | What it does | First version |
|---|---|---|---|---|
| `catalog` | Read | `saveslot.read` | The catalog: slots, tables, fields, relations, profile, rules; the full schema document | Yes (simplified overview) |
| `query` | Read | `saveslot.read` | Simple queries, optionally by valid time | Yes |
| `sql` | Read | `saveslot.read` | Read-only restricted SQL | Yes |
| `history` | Read | `saveslot.read` | The timeline of a row / entity, how it looked at a recorded moment, the changes over a period, how a derived value is composed | Yes (no `composition`) |
| `sources` | Read | `saveslot.read` | List, search and read source data | Yes (search is substring matching) |
| `deletion_preview` | Read | `saveslot.read` | A preview of the impact of a deletion; returns a deletion confirmation handle | Yes (only privacy deletion by source data) |
| `pending` | Read | `saveslot.read` | Pending items: list, view details | Yes (no jobs) |
| `write` | Write | `saveslot.write` | Write base tables: add / change / correct / revoke, including revert | Yes (no jobs) |
| `resolve` | Write | By item kind × decision (section 6) | Handle one pending item | Yes (no `migration_diff`) |
| `schema_draft` | Write | `saveslot.schema` | Submit a schema draft; returns the compile result and an impact preview | Yes (no re-extraction) |
| `delete` | Write (irreversible) | `saveslot.delete` | Execute one deletion that has been previewed | Yes |
| `extract_claim` / `extract_submit` | Write | `saveslot.read` + `saveslot.write` | Claim and submit extraction work items | Later |
| Administrative (section 17) | Read / write | User session¹ | Connections, removing an empty slot, slot policy, reading the audit, log verification, comparison, export, import into an empty tenant | Yes (`policy.set` later) |

¹ `policy.get` is the exception: any credential with `saveslot.read` can call it.

The "First version" column states the design scope of the first version. 0.1.0 does not provide yet `deletion_preview` and `delete` from this list, nor the comparison `log.reconcile` among the administrative operations; these report `not_in_this_version`. `policy.set` comes after the first version.

## How reads and writes work together

Read before writing: before a write, first read the row to be changed (`query`, or the `timeline` of `history`). The result carries the `ver` of that row (the version token, section 2) and the `sv` of the slot (the schema version), and `write` passes them back unchanged, which means "this write was made after seeing this version". If the row has been changed by someone else since then, and the change reached the same conflict unit (a field, or a group of fields that the schema declares with `together`, defined in 5.4), the write does not overwrite the current value: it is recorded as a candidate, and a conflict item is created or merged into. Candidates and items (pending items, section 6) are kept persistently, never expire, and stay until they are handled with `resolve`. A high-impact write (the list is in "Writing state" in the data model) does not take effect at once: it creates an item awaiting confirmation, which `resolve` confirms or rejects. Every write carries evidence (the user's own words, a file reference and so on, section 3), which is stored as source data. The receipt states per field what happened to each field: applied, corroborated, no-op, became a candidate, awaiting confirmation (5.4). When handling an item, `resolve` passes back the version token of the item, `item_ver` (section 2), which means "this decision was made after seeing the current content of the item". A write can also declare premises (which rows already read in saveslot this write is based on, see 5.1 "The premises of a write"), or write by external key (locating a row by the record key in the source system, see 5.1 "Writing by external key").

# Part one · contract-core (the shape of the data)

## 1. References, sequence numbers and the encoding of values

For the types, see types section 1.

- **Table**: the qualified name `ledger.expenses`, or just `expenses` when it is unique within the visible range; when it is ambiguous, `invalid_argument` (`ambiguous_table`) is reported with the candidates attached. The **slot** parameter accepts a name or a `slot_id`.
- **Names are resolved only within the visible range** (the visible range is in section 12): the uniqueness judgement, the candidates of `ambiguous_table` and old-name resolution all look only at the slots and tables visible to this credential. Old-name resolution applies only to table names and field names: after a slot is renamed, the old name no longer resolves, and a qualified name written with the old name and any place that takes a slot name as a parameter behave as if the name does not exist ("How long an old name is still recognized" in the data model). A name outside the visible range does not appear in any result, error, candidate or hint.
- **Names are resolved by version**: a write resolves names by the `sv` the request carries (a write that carries an old name after a rename is accepted as usual); a read accepts old names from the last few versions, and `warnings` carries `renamed` ("Schema document format" in the data model). Aliases of tables and fields (`aliases`) are not names and do not take part in resolution; see `catalog` in section 10.
- **Row**: event tables and timeless tables use `row`; state tables use `entity` or `entity_key` (the natural key declared by the schema); derived tables use `key` (the group key, read-only; saveslot internally replaces it with an opaque `partition_id`). Exactly one is given besides `table`. When an event table or timeless table declares an external key (the key that identifies the same record in the source system, see 5.1 "Writing by external key"), a write can also locate a row with `external_key` (5.1); the parameters of read operations do not accept `external_key`, and giving it reports `invalid_argument`. In a result the server always gives the ID, and gives the natural key / group key / external key as well when there is one.
- **Values and meta fields are layered**: in a read result, the values of the fields are under `values` of each row, and the row identity, `ver`, interval and flags are on the row object. User field names therefore never collide with meta fields.
- **Names are unique regardless of ASCII case**: slot names, table names and field names are judged unique within their own scope with ASCII case-insensitive comparison (`Expenses` and `expenses` cannot coexist); name resolution in requests and in restricted SQL is likewise case-insensitive.
- **Names and reserved names**: slot names, table names and field names use only letters, digits and underscores, start with a letter, and have at most 63 characters (so they **must not start with `_`**); a field name **must not be `valid`, `valid_from`, `valid_to`, `row_id` or `entity_id`**. A name that does not follow this form and the use of a reserved name both report `validation_failed` (`reserved_name`); see "Field types and value ranges" in the data model.
  - `row_id` and `entity_id` are system columns that every table has in restricted SQL ("[Restricted SQL](03-data-model/11-restricted-sql.md)" in the data model).
  - The three names `valid`, `valid_from` and `valid_to` share one namespace with field names in `evidence_by_field` (`valid`) and in the `where` of `query` (`valid_from` / `valid_to`).
  - The `_` prefix is reserved for future meta fields: any name added to such a shared namespace later will start with `_`, so existing schemas need no migration.
- **Operation number**: each `write`, `resolve`, `delete` and deletion cancellation has one operation number (the `seq` of its head event; that of a `write` is also called the write number). **All sequence numbers that appear externally are operation numbers**: the `seq` of a receipt, the sequence number inside `ver`, the entries of a `timeline`, the target of `undo`, the values of `as_of` / `since` / `until`. The sequence numbers of the individual events inside an operation are not exposed ("Numbering" in the data model).
- **The encoding of values** (types 1.4):
  - `decimal` and `integer` accept a decimal string (recommended) or a JSON number on writes; the server parses the original text, not through a double; the value is always returned as a string. `integer` is a 64-bit signed integer; a value beyond the JSON-number safe range (2^53 − 1) must be written as a string.
  - **The precision of a JSON number depends on the channel**: on the HTTP channel saveslot parses the request body itself, and a JSON number is parsed from its original text. Through channels such as MCP, where the host or an SDK parses the parameters, what saveslot receives is already a double, and it takes the shortest round-trip decimal form of it: a safe integer (an integer whose absolute value does not exceed 2^53 − 1) is accepted with any number of digits, because it is exact in the first place; any other value is accepted with at most 15 significant digits (a decimal original of up to 15 digits, parsed to a double and written back, is still the original), and with more than 15 digits `validation_failed` (`malformed`) is reported, with a hint to write it as a string; a number received by an `integer` field must in addition be a safe integer, otherwise `malformed` is reported as well. When the host has already parsed the original into something distorted (for example `1.0000000000000001` parsed as `1`), saveslot has no way to detect it: write it as a string to get more digits.
  - **The decimal original handed in by the caller** (the value of `decimal` and `integer`, the `value` of `quantity`): a string and a JSON number use the same grammar, namely the grammar of a JSON number `-?(0|[1-9][0-9]*)(\.[0-9]+)?([eE][+-]?[0-9]+)?`, with an exponent allowed. Leading zeros (`01`), a plus sign (`+1`), `.5`, `1.`, `NaN` and `Infinity` are not accepted and report `validation_failed` (`malformed`). The original has at most 100 characters; a longer one also reports `malformed`, judged before parsing. A raw value therefore has only one grammar.
  - An `integer` field that receives a value with a fractional part (`"1.5"` or `1.5`): whether written as a string or a number, it reports `validation_failed` (`type_mismatch`).
  - When `quantity` or `decimal` has more fractional digits than the field's `scale`, it is rounded according to the field's `rounding` and then recorded, and `warnings` carries `rounded` ("Precision and rounding" in the data model). Exception: a `quantity` whose unit has been converted carries only `unit_converted` (`to` is the value after conversion and rounding) and no separate `rounded`, because the exact value after conversion is not necessarily a finite decimal, and the `from` of `rounded` cannot be written.
  - **Clearing**: writing the value `null` clears an optional field, and it is a contribution with a source; a required field cannot be cleared and reports `validation_failed` (`required_missing`). On event tables and timeless tables, clearing cannot hold up a row by itself ("Existence of a row or entity" under "Deletion · Replay rules" in the data model): on a table with no required field, an `insert` that gives no field a non-empty value reports `validation_failed` (`empty_row`, the details carry `op` and `table`), and nothing is recorded. Only the values this op gives itself are looked at; a later op in the same request cannot make up for it. An `update` / `correct` that clears all remaining values of a row is not rejected: the row still exists by virtue of earlier non-empty contributions, and its fields are empty. On state tables, clearing itself counts as having a value ("Time · Intervals without a value" in the data model), so this rule does not apply.
  - A `quantity` must carry `unit`; if it is missing, `validation_failed` (`unit_missing`) is reported; the unit is taken from a fixed unit vocabulary, and one not in the vocabulary reports `unit_unknown`; a dimension different from the field's (including a different currency) reports `unit_dimension`; a unit of the same dimension is converted automatically to the unit declared by the field, and `warnings` carries `unit_converted`.
  - A JSON type of the value that does not match the type the field declares (for example an object or a boolean given to an `integer` field): `validation_failed` (`type_mismatch`). A value of an `enum` field that is not among the declared values: `validation_failed` (`enum_value`, with `allowed_values` attached).
  - A `zoned_datetime` without a time zone uses the slot time zone, and `warnings` carries `timezone_assumed`. A time zone is written as `[UTC]` or `[region/place]` and must be a name the runtime recognizes, under the same rule as the slot time zone ("Schema document format" in the data model); notations such as `PRC`, `EST` and `+08:00`, and an offset that does not match the time zone, report `validation_failed` (`type_mismatch`). When a time zone name differs from the canonical name of the runtime only in case, the normalized value uses the canonical spelling, and the original value is recorded as the caller wrote it ("Criteria for the same value" in the data model).
  - **The range of dates and instants**: an instant after conversion to UTC, and for a table with day granularity the day it falls on in the slot time zone, must lie within 0001-01-01 to 9999-12-31. A field value out of range reports `validation_failed` (`out_of_range`); an interval parameter or `stated_at` out of range reports `invalid_argument` (`malformed`). Offsets follow RFC 3339: hours 00–23 and minutes 00–59, otherwise the notation is wrong (`type_mismatch` for a field value, `malformed` for an interval parameter). An instant has at most millisecond precision; finer digits must all be 0, otherwise the notation is wrong in the same way.
  - A `ref` is written as the `row` / `entity` of the referenced row, or as the temporary name `"@p1"` of a row newly inserted in the same request.
  - `text` must be well-formed Unicode (no lone surrogates) and must not contain NUL (U+0000: the PostgreSQL `text` type cannot store it), otherwise `validation_failed` (`type_mismatch`) is reported; the 8 KB limit is judged on both the caller's original text and the result after NFC, and exceeding it reports `out_of_range`. When returned it is untrusted text (section 8).

## 2. Version tokens: `ver`, `sv`, `item_ver`

| Token | What it is | Rule |
|---|---|---|
| `ver` | The token of the current version of a row / an entity, encoded as (the operation number of the latest operation that changed its current state, the tenant restore count), written `v57.0`. The restore count starts at 0 | Returned on reads, passed back unchanged on writes. It is renewed when a business write, a system ruling, a deletion confirmation or the cancellation of a deletion changed it; a migration, a derived refresh and a same-value corroboration do not change it. Whether it is renewed depends only on whether the cell of this row / entity in the version table changed: the value changed, or the value did not change but the cell is now given by this operation (see "The version mark `ver`" in the data model and architecture §8 "version table"). For example, revoking again in an interval that is already revoked makes that segment given by the later revoke, so it is renewed; undoing the same write once more writes back a value and an origin identical to the present ones, so it is not renewed; a revoke that falls on a period where no value was ever written has no cell change, so it is not renewed either. State tables give it per entity, not per segment. An operation number that is not a write of this row / entity reports `invalid_argument` (`not_this_target`) |
| | A derived row also carries `ver`: the operation number of the latest operation that changed its value. A derived row computed at read time (`marks.computed_at_read`) does not carry it | Used only to identify a version, not for writes |
| | A historical version returned by the `as_of` of `history` is written `h41.0` and carries `historical: true` in addition: the operation number is that of the last operation at or before the position of `as_of` that changed this row / entity (same as `ver`, a schema switch not counted), and the restore count is the one at the time of reading | Not usable for writes, and does not take part in the fallback |
| `sv` | The schema version of a slot: an increasing integer that is **not guaranteed to be consecutive**, because a version number is assigned when a draft is compiled, and a number once occupied by a rejected or superseded draft is not reused. The current version of a slot is the version most recently switched to, not the one with the largest number (the largest may still be awaiting confirmation or already rejected) | Every result carries the `sv` it used; writes should pass it back. A caller compares it only for equality and order, and does not add to or subtract from it |
| `item_ver` | The version token of a pending item (`iv_…`), encoded as (item ID, the operation number of the latest change to the item content, the tenant restore count) | Renewed when the item is created, merged into, refreshed, has an entry cleared, is superseded or is resolved. Passed back on `resolve`. What each decision is bound to is in section 6 |

**Fallback** (defined only in this section, referred to everywhere else): when `ver`, `item_ver` or `sv` is not passed, the version most recently read by this connection is used, and `warnings` carries `ver_fallback` / `item_ver_fallback` / `sv_fallback` (with the source read attached; when the `ver` fallback is taken from this connection's own write receipt, no read is attached, and the operation number of that write, `from_write`, is attached instead). When there is nothing to fall back on, `read_first` is reported.

- **Unit**: the connection. When called with a user session it is that user session (all of its calls share one "most recently read"); a surface meant for people should pass the versions back explicitly and not rely on the fallback.
- **`task`**: a call that carries `task` recognizes only reads under the same `task`; a call that carries no `task` recognizes only reads that carry no `task`. When something was read but under a different `task`, the `reason` of `read_first` is `task_mismatch`; the self-check that `saveslot connect` makes with the new token (`task: "saveslot-connect-selfcheck"`, [`06-cli.md`](06-cli.md) §3 step 7) is not a read by the agent itself and is not counted, so the reason is then `no_read`.
- **What counts as having read `ver`**: reading row by row, that is, the current version returned by `query` and by the `timeline` of `history` (`changes` does not return `ver` and does not count); and the **applied** `ver` in this connection's own write receipts. `sql`, aggregate reads and historical versions read by moment do not count; the `current_ver` attached to a `candidate` result in a receipt does not count. The `ver` of a derived row cannot be used for writes, and reading a derived table does not register a row version and counts only as having read `sv`.
- **What counts as having read `item_ver`**: viewing the details of that item; the `current` attached when `resolve` reports `confirmation_mismatch`, which is the details of that item at that moment and equivalent to viewing the details; or the item was **newly created** by this write / deletion / draft submission and the receipt gives its entire content ("Pending items · Item ID and item version" in the data model). A place that lists only item IDs does not count; one marked `merged` or `refreshed` in a receipt does not count, and the details must be viewed first.
- **What counts as having read `sv`**: any read by this connection of that slot, including `catalog`. A passed-back `sv` that is behind is not rejected across the board: only a write to a field with an incompatible change is rejected (`schema_incompatible`).
- **`ver` in a premise** (`ops[i].premises[j].ver`, 5.1) follows the same rule as the `ver` of the write target: it should be passed back, the fallback applies when it is not passed, and the warning is `premise_ver_fallback`; when there is nothing to fall back on, `read_first` is reported.
- **An op by external key does not use the fallback**: it carries no `ver`, the version seen is the synchronization baseline taken by the kernel (5.1), the read record is not consulted, and `read_first` is not reported even if nothing was read.

How the tokens are handled after restoring a backup or an import is in section 15.

## 3. Evidence

For the types, see types section 2.

| `kind` | Meaning | Default source level |
|---|---|---|
| `user_message` | The user's own words | `user_stated` |
| `agent_note` | The caller's paraphrase, inference or summary | `agent_inferred` |
| `tool_result` | Output of a tool or a device | `agent_inferred` |
| `file_ref` | A reference to an external file: saveslot does not keep the file, it stores only the file name, type, size, content hash, and optionally the origin location and a text excerpt | `agent_inferred` |
| `source_ref` | A reference to source data that already exists in the same slot, without copying the original | Same as the one referenced |
| (generated by saveslot) `api_call` | The request itself, when no evidence was passed. `write`: one is stored for each op that left something in the events, containing only that op (a contribution, a premise declaration, a restate and a clear all count as leaving something); the value of a no-op field is not recorded; an op by external key that did not enter the events (`unchanged`, `skipped`, 5.1) stores none. `resolve`: when a `note` was passed, or when it triggers a write and no evidence was passed, one is stored together with the `note`. It appears only in source data, and the caller cannot pass it | `agent_inferred` |

- **"Correction" is an annotation, not a kind**: when a source is used as the value source of a write whose intent is `correct`, the read result carries `correction: true` (types 4.6); it is derived from the intent of the write and does not change the kind or the source level of that source.
- **Required**: the `text` of the three kinds of text segments is required and must be non-empty; `name`, `mime`, `size` and `sha256` of `file_ref` are required, while `origin` and `excerpt` are optional; the `id` of `source_ref` is required, and referencing source data that is pending deletion within the grace period reports `invalid_argument` (`pending_deletion_source`); what is referenced must be source data handed in by the caller, and one of kind `api_call` cannot be referenced and reports `invalid_argument` (`malformed`); referencing source data visible in another slot reports `invalid_argument` (`cross_slot`), and one that does not exist or is not visible reports `not_found` (`source`).
- **Size** (initial values, "Numeric values and details of the interfaces" in the open questions): 32 KB per segment, 256 KB per request; **counted in UTF-8 bytes, only `text` and `excerpt`**. Exceeding it reports `too_large` (`evidence_segment` / `request`). A request has at most 1,000 segments (request-level and all inline segments together, `source_ref` segments included); exceeding it reports `too_large` (`evidence_segments`, with `limit` and `actual` attached, both counts of segments), checked in the same step as the byte limit. For large text, hand in only a `file_ref` with an excerpt. The `name` and `mime` of a `file_ref` have at most 256 characters each, and `origin` at most 2048 characters (counted by code points), with no control characters.
- **Evidence text** (`text`, `excerpt` and every text item of a `file_ref`) must be well-formed Unicode and contain no NUL; one that does not comply or is too long reports `invalid_argument` (`malformed`, with `param` pointing to that item).
- **Declaring a level**: the `level` on a segment overrides the default derived from `kind`; `external_authority` is not open in the first version, and declaring it reports `not_in_this_version`. A level takes part in conflict adjudication only on a literal match ("Source level" in the data model).
  - When `external_authority` is opened later, whether it can be declared is decided by the permissions granted to the connection: it can only be granted by a user session at issuance, the writer cannot claim it for itself, and another connection cannot pass it on; the grant is recorded in the principal registration event. Declaring it without having been granted it rejects the whole request and does not downgrade to `agent_inferred`, because a downgrade would make the writer believe its value carries an authoritative level.
- **Statement time**: the optional `stated_at` on a segment, when the statement was made; if not given it is unknown. It is only recorded and takes part in no judgement in the first version.
- **Where segments go**: request-level `evidence` (shared by several ops), or written in an op (`ops[i].evidence`, belonging only to this op). An op references request-level segments with `ops[i].evidence_refs` (an array of indexes).
- **The segments visible to an op** = its inline segments, plus the request-level segments listed in `evidence_refs`; when neither is given, all request-level segments are referenced. **An empty array is the same as not given**: a request-level `evidence: []`, `ops[i].evidence: []` and `ops[i].evidence_refs: []` are all treated as not given (a `[]` filled in when completing optional parameters means "nothing to say", not "reference no segment at all").
- **Pointing by field**: `ops[i].evidence_by_field`, field name → array of indexes. The indexes count the segments visible to this op: **first the inline segments, then the request-level segments in the order of `evidence_refs`**. The key `valid` points to the origin of the interval parameters of a state table. An index out of range reports `invalid_argument` (`index_out_of_range`); a mapping to an empty array reports `invalid_argument` (`empty_mapping`); an index that is not an integer, or is repeated in the same array, reports `invalid_argument` (`malformed`, the same for `evidence_refs`). A key that is a field name the table does not have reports `unknown_field` (with similar names attached); a key that is a field the table has but to which this op gives no value (not in `set`, and not a key of `entity_key`) reports `invalid_argument` (`malformed`): a revoke gives no field value and can map only `valid`. `valid` is used only for state tables, otherwise `invalid_argument` (`not_state_table`) is reported; when this op gives no interval parameter at all (a whole revoke, or a write from now until the next change) there is no interval to point to, and `invalid_argument` (`malformed`, with `param` pointing to this key) is reported. `undo` writes no values of its own, and carrying a non-empty `evidence_by_field` reports `invalid_argument` (`mutually_exclusive`). An empty object is the same as not given.
- **When a field references several segments, those segments are needed at the same time** (including the default when no mapping is given; the rule is in "Deletion · Provenance" in the data model). When several segments are carried and no field mapping is given, `warnings` carries `multi_segment_unmapped`.
- **A field whose value did not change counts as corroboration only when evidence is explicitly pointed to by field**; one not pointed to is a no-op (section 5).

## 4. Time parameters

| Parameter | Meaning | Available in which operations |
|---|---|---|
| (not passed) | What is known now, what is in effect now | All read operations |
| `valid_at` | One moment of valid time (state tables: the interval contains it) | `query`, `sql` (`FOR VALID_TIME AS OF`), the `as_of` of `history` |
| `valid_during` | A valid-time interval `[a, b)` | `query`, `sql` (`FOR VALID_TIME FROM … TO …`) |
| `at` | The evaluation moment: "today" (a derived value that depends on "today") and reading a state table without a time qualifier both take it; when not passed, the entry moment is taken | `query`, `sql` |
| `as_of` | Recorded time: what saveslot knew at that time | **Only in `history`** |

- **Intervals are always closed on the left and open on the right.** In a result, the interval on a table with day granularity also carries `valid_to_inclusive` (the last day in the interval); for an interval that continues indefinitely `valid_to` is `null`.
- **Conversion between dates and instants**: a table with day granularity that receives an instant takes the day it falls on in the slot time zone, and `warnings` carries `time_truncated`; a table with instant granularity that receives a date reports `invalid_argument` (`granularity`) on both reads and writes, and `example` gives the start and end instants of that day in the slot time zone.
- **State tables**:
  - A default read returns for each entity the segment currently in effect, with its `valid_from` / `valid_to`; an entity that currently has no value does not appear. "Current" takes the evaluation moment `at` (the entry moment when not passed): on a table with day granularity it is the day of that moment in the slot time zone, and on a table with instant granularity it is that very moment.
  - `valid_at`: returns the segment in effect at that moment.
  - `valid_during`: returns every segment that intersects the interval, one row per segment. The endpoints are not clipped to the interval by default (only `clip: true` clips); adjacent segments with the same value are merged by default on the selected fields (only `coalesce: false` does not merge). `valid_from` / `valid_to` in `where` are usable only when `valid_during` is carried. The order is:
    1. conditions on fields first filter the original segments of the entity;
    2. among the remaining segments, those that touch and have the same value in the selected fields are merged, whether or not each of them intersects the interval: what the caller sees is the real start and end of this value. Only values are looked at, not flags: flags are those at the time of reading, and if they decided how to merge, a flag appearing during paging would split rows that have already been given. A merged row carries the flags of the segments: a flag of an item kind carries the segments where the item interval intersects this row (`spans`; after clipping, those that intersect the clipped row; an item that no longer intersects is not flagged), and `corrected` is present if any segment comes from a correction;
    3. those that intersect the interval are kept;
    4. the conditions on `valid_from` / `valid_to` act on the segments after merging;
    5. `clip` comes last.
  - `clip` and `coalesce` are used only when reading a state table with `valid_during`: used on other tables they report `invalid_argument` (`not_state_table`), and used on a state table without `valid_during` they report `invalid_argument` (`malformed`). They are not silently ignored.
  - `valid_at` and `valid_during` given together: `invalid_argument` (`mutually_exclusive`).
- An **event table** has no valid interval: passing `valid_at` reports `invalid_argument` (`event_table_valid_at`), and `example` gives the rewriting as `valid_during` or `where`. `valid_during` filters on the occurrence-time field; when the field is a `zoned_datetime` and the interval is given as dates, the calendar day in the slot time zone is used.
- A **timeless table** that is passed `valid_at` / `valid_during`: `invalid_argument` (`no_time_table`).
- A **derived table** has no valid time: passing `valid_at` / `valid_during` reports `invalid_argument` (`derived_table`); for a derived table bucketed by week or month, use `where` to filter on the group key.
- **`as_of: S`** = the state when all operations with an operation number not greater than S have fully taken effect; when a moment is given it is replaced by the last operation number not later than it, and a moment in the future equals the latest. `as_of` without `valid_at` reading a state-table entity returns all the segments known at that time. The `since` of `changes` is exclusive and `until` is inclusive.
- `FOR SYSTEM_TIME` appearing in `sql` reports `sql_rejected` (`system_time`), with `use: "history"` attached. Reading a state table without a time qualifier = the segment that contains the evaluation moment (`at`, the entry moment when not passed).

## 5. Writes: intents and ops

For the types, see types 5.1. The ops in one request belong to the same slot, are **executed in order, as one transaction as a whole**, and share one write number (a request that produces no event has no write number, see 5.4).

### 5.1 How an op is written

| Intent | Target | `ver` | Content |
|---|---|---|---|
| `insert` | Not given. Used only for tables without `entity_key`; used on a state table with `entity_key` it reports `invalid_argument` (`insert_with_entity_key`); an external-key field appearing in `set` reports `invalid_argument` (`insert_with_external_key`), and writing by external key is used instead | Not carried | `set`, required fields complete |
| `update` / `correct` | `row`, `entity` or `entity_key` | Should be passed back | `set` or `revert`, one of the two; an `update` that carries `premises` (premises: which rows already read this write is based on, see "The premises of a write" below) may carry neither (restate, clear) |
| `update` / `correct`, by external key | `external_key`, no `row` | Not carried | `set` |
| `revoke` | `row`, `entity` or `entity_key` | Should be passed back | No `set`, no `revert` |

- **"Should be passed back"**: when it is not carried, the fallback of section 2 applies, and only if there is none is `read_first` reported. An op by external key is the exception: it carries no `ver` and no `row`. An op that adds a key to a row that has none (see below) is an ordinary `update` and carries `row` and `ver` as usual.
- **`update` and `correct`**: `update` is for a change of circumstances or added information; `correct` is for when the original value was wrong to begin with, and it triggers the correction impact query. Only the caller can tell them apart, so it must be annotated explicitly ("The write request" in the data model).
- **Writing by `entity_key` = write if it exists, create if it does not**: the intent is `update`; when the entity does not exist it is created, and the result carries `created_entity: true` and `existing_keys` (the entity keys the table already has, at most 10; keys newly created earlier in the same request also count, and come first). The text of the key is given in a form that can be written back unchanged (for an instant with a time zone, the local instant with offset in that time zone, plus the time zone name).
  - When the new key is similar in form to an existing key, `similar_keys` (at most 5) is carried as well, each with the reason for the similarity `match`: `fold` (the same after folding case, full-width / half-width forms and whitespace), `affix` (one is the beginning or the end of the other), `edit` (differing by only one or two characters); a revoked entity is additionally marked `revoked`. The criterion is `keymatch@1` ("Similar keys" in the data model), and the range compared is all entities of that table visible to this call, including revoked ones; when there are more than 5,000 entities, only the 5,000 most recently written are compared (initial value). Similar keys in `existing_keys` come first, the rest by most recent write.
  - Both items are hints computed from the state at the moment of the write: the write takes effect as usual, no item is created, and nothing enters the events. The way to fix a wrongly written key is to revoke the entity just created (a `revoke` without an interval) and then write by the correct key.
- **The slot of the request**: when the table name is written as a qualified name `slot.table` it is that slot; when only the table name is written, the one slot within the visible range that has this table is taken, and when several slots have it `invalid_argument` (`ambiguous_table`, with the qualified names of the candidates attached) is reported, and when none has it `unknown_table` is reported. Ops that fall in different slots report `invalid_argument` (`cross_slot`, with `param` pointing to the `ops/<i>/table` of the first inconsistent op).
- **State-independent parameter validation** (step 1 of the order of judgement): a passed-back `sv` greater than the current version, or not a version number that has been in effect in this slot (a number occupied by a draft awaiting confirmation, rejected or superseded), reports `invalid_argument` (`malformed`, `param` is `sv`); a `ver` written as a historical version (`h41.0`) or in another notation reports `invalid_argument` (`malformed`); `entity_key` used on a table that is not a state table reports `invalid_argument` (`not_state_table`), a state table that declares no natural key reports `malformed`, a missing key field reports `missing` and an extra one reports `malformed` (`param` pointing to that key); writing a derived table reports `derived_readonly`.
- **The other state-independent reason codes** (also step 1 of the order of judgement; `param` always points to the item with the problem):
  - An object in a request recognizes only its own keys; a key whose value is `undefined` is treated as not written (a request that arrives via JSON never has one, an embedded call may); an array with a hole reports `invalid_argument` (`malformed`). A parameter key that is not recognized reports `invalid_argument` (`malformed`).
  - More than 1,000 ops in one request: `too_large` (`ops`, with `limit` and `actual` attached, both counts of ops; a temporary value, "Numeric values and details of the interfaces" in the open questions).
  - `task` or `idempotency_key` that is empty, longer than 256 characters (counted by code points), not well-formed Unicode or containing control characters: `invalid_argument` (`malformed`).
  - `row` given on a state table: `invalid_argument` (`state_table`).
  - Two keys in the same `set` that are the same field when compared case-insensitively: `invalid_argument` (`malformed`, `param` pointing to the second spelling); the same in `entity_key`, with `param` pointing to that key.
  - A repeated item in `acknowledge` or `evidence_refs`: `invalid_argument` (`malformed`, `param` pointing to the second occurrence).
  - The slot of a qualified name `slot.table` is not the slot of this request: `invalid_argument` (`cross_slot`).
  - `valid_from` not earlier than `valid_to` on a state table: `invalid_argument` (`malformed`, `param` is `valid_to`). When both ends are given this is at this step; when only `valid_to` is given and the start is computed as "now" (the day or the moment in the slot time zone), it is known only when this op is judged, comes after `not_found` and `read_first`, and likewise reports `invalid_argument` (`malformed`, `param` is `ops/<i>/valid_to`).
  - A `ref` written as the temporary name `"@p1"`: it must have been declared with `as` by an op earlier in this request; if no op declares it, or the op that declares it comes later, `validation_failed` (`ref_not_found`) is reported.
  - `as`: 1 to 64 letters, digits, `_` and `-`, otherwise `invalid_argument` (`malformed`); it can be used only on `insert` and on ops by external key, and another op that carries it reports `invalid_argument` (`mutually_exclusive`, `param` pointing to `ops/<i>/as`); two ops in the same request using the same temporary name report `invalid_argument` (`duplicate_name`, `param` pointing to the later one).
- **`valid_from` / `valid_to` are used only for state tables**; used on other tables they report `invalid_argument` (`not_state_table`). The key fields of an entity do not change with valid time: when a write with an interval carries a key field of `entity_key` whose value differs from the key of the entity, `invalid_argument` (`key_field_changed`) is reported.
- **Several ops in the same request acting on the same row / entity**: a later op sees the results of the earlier ops. For a row / entity newly created in this request, a later op needs no `ver`; for one that existed before the request, the `ver` carried by each op means "the version seen at the start of the request", and the conflict judgement compares only writes from outside the request. Each op is judged independently: one op becoming a candidate does not affect the other ops taking effect. The same row / entity gets only one new `ver`.
- **`acknowledge: ["overwrite"]`**: the overwrite kind of high-impact write has been confirmed with the user and takes effect directly. **It is valid only when this op explicitly carries the current `ver`**, otherwise it goes into awaiting confirmation as usual ("Writing state" in the data model). Which surfaces open it is in surfaces.

#### Writing by external key

For event tables and timeless tables when the schema declares `external_key`; the authoritative definition of the rules is in "Writing by external key" in the data model.

- **How to write**: `external_key` gives the values of all key fields (one missing, or `null` given, reports `invalid_argument` (`missing`)); the intent is `update` or `correct` (a `revoke` and an op with `revert` that carry `external_key` report `invalid_argument` (`mutually_exclusive`)); it carries no `ver` (carrying one reports `invalid_argument` (`mutually_exclusive`)) and no `row`; it cannot carry `premises` (`invalid_argument` (`premises_with_external_key`)). Used on a table that declares no external key it reports `invalid_argument` (`no_external_key`).
- **Update if it exists, add if it does not**: the kernel locates by key. If there is no such row it is added; if there is, a three-way comparison is made: the value this field was last handed in by external key (the baseline value), the current value in effect, and the value handed in this time. A field equal to the baseline value is a no-op (the source did not change, and the user's changes in saveslot are not overwritten by every synchronization); a different one takes effect or becomes a candidate under the ordinary conflict criterion, with the baseline position of this field as the version seen. When the key hits a revoked row, or the key is held by a deletion within the grace period, this op is skipped and no error is reported. The outcome of each op is in the `outcome` of the receipt (5.4).
- **The same key appearing twice in the same request** rejects the whole request: `invalid_argument` (`duplicate_external_key`, with the indexes of the two ops attached).
- **The temporary name `as`**: when adding, it is bound to the newly allocated row; when an existing row is hit, it is bound to the row hit; later ops in the same request can use it to write `ref`. When this op is skipped the temporary name is not bound: a later op by external key that uses it to write `ref` is skipped along with it (`skip_reason: "ref_skipped"`), and an ordinary op reports `validation_failed` (`ref_not_found`).
- **Key fields cannot be changed**: a key field appearing in `set` with a value different from the one on the row reports `invalid_argument` (`key_field_changed`).
- **Adding a key once to a row that has none**: an ordinary `update`, carrying `row` and `ver` (it may carry `set` at the same time to change other fields), and in addition `external_key`; only this form can give `row` and `external_key` together. The row must be unrevoked and have no value in any of the key fields; when the row already has a key, one equal to the existing key is a no-op and a different one reports `key_field_changed`. The state of the key decides the result:
  - A deletion within the grace period will remove the contributions of this key on any row (the key is frozen): `invalid_argument` (`external_key_in_use`, with the IDs of all the deletions that freeze it attached).
  - Held by an unrevoked row: `invalid_argument` (`external_key_in_use`, with the ID of the row holding it attached). To transfer it, revoke that row first.
  - Held by a revoked row: transfer of a key is later; see "Transferring an external key (later)" below.
  - Not held: it is added. After that the key of this row cannot be changed.

##### Transferring an external key (later)

The first version does not do transfer: when the key is held by a revoked row (the first and second cases below), `not_in_this_version` is always reported (`param` pointing to `ops/<i>/external_key`). The rules of transfer are as follows.

- Held by a revoked row that had this key from creation: the key moves to this row.
- Held by a revoked row whose key came from adding a key: `invalid_argument` (`external_key_not_transferable`, with the ID of the row holding it attached). No chained transfer.
- **A revoked row that gave up its key cannot exist again**: an `undo` of that revoke, a revert with `include_later` that reverts it along with others, or confirming such an awaiting-confirmation revert reports `invalid_argument` (`external_key_transferred`, with the ID of the row that now holds the key attached) when it would take effect. No path currently reports `external_key_transferred`; it is only defined in the error code table of the types file.

#### The premises of a write

`ops[i].premises`; the authoritative definition of the rules is in "The premises of a write" in the data model.

- **What it is**: which rows already read in saveslot the content written this time was decided from. If the values of those rows later change in the declared fields (and valid time), this row carries the `premise_changed` flag for any reader (section 7); the value of this row does not move. A premise is not evidence: evidence points to the original text of source data, while a premise points to data in saveslot that can change.
- **One premise**: a target (`row`, `entity` or `entity_key`, exactly one given besides `table`; `row` may also be the temporary name `"@p1"` bound by an earlier op in this request, see "The premises of a write · What it can point to" in the data model), optional `fields` (not given = the whole row), and `ver` (should be passed back, fallback in section 2); when the target is on a state table, `valid_at` or `valid_during` may be carried, and when neither is given, the valid time of the row that declares the premise is taken if it has one, otherwise it is "from now on". Each op has at most 16, and exceeding it reports `too_large` (`premise_entries`).
- **Which ops can carry it**: `insert`, `update`, `correct`. An op with `revert`, `revoke`, and an op by external key cannot carry it, and report `invalid_argument` (`premises_with_revert` / `premises_with_revoke` / `premises_with_external_key`) respectively. `resolve` has no such parameter.
- **Restate and clear**: an `update` without `set` and with non-empty `premises` is a **restate**: the value does not change, and as of the `ver` seen, the values this row now has still hold on the basis of these premises. An `update` with `premises: []` is a **clear**: all premise declarations of this row are removed, and this is the only way to remove premises. Neither changes the `ver` of the row, and neither can be reverted with `undo` (there is no change to undo). An `update` without `set` that also carries no `premises` reports `invalid_argument` (`missing`).
- **What an op that carries `premises` covers**: the items it writes itself, plus the other items of this row that were already in effect at the version seen and are still in effect afterwards; the latter are covered only when all fields of this op have taken effect (when a field became a candidate or entered awaiting confirmation, only the items it wrote itself are covered); a clear is not subject to this rule and clears the whole row regardless. The `premise_covered` of the receipt gives the number of additional fields covered.
- **Validation** (step 5 of the order of judgement, at the same place as the validation of `ref` targets):
  - A table that does not exist or is not visible reports `unknown_table`, and a field that does not exist reports `unknown_field`; a row / entity that does not exist, has been privacy-deleted or is not visible reports `not_found` (`param` pointing to `ops/<i>/premises/<j>`; when the whole row is removed by a deletion within the grace period, the IDs of all the related deletions are attached).
  - A temporary name that is not bound to a row of this table (no earlier op declares it, its op was skipped, or it is bound to a row of another table): `not_found`; pointing to a row newly created in this request while carrying `ver`: `invalid_argument` (`mutually_exclusive`); that creation not having taken effect at the end of this request: `invalid_argument` (`premise_target_pending`, with `as` and `op` attached).
  - Pointing to the target of this op itself: `invalid_argument` (`premise_self`). Two declarations of the same op that resolve to the same target: `invalid_argument` (`premise_duplicate_target`, `param` pointing to the one that appears later, with the indexes of both attached): an origin item has only one effective declaration for a premise target, so to cover several fields merge them into the `fields` of one declaration, and to cover two periods of time give one `valid_during` that covers both or give no range. Pointing to a derived table: `not_in_this_version` (`value`). Pointing to a table visible in another slot: `invalid_argument` (`cross_slot`). A `ver` that is a historical version: `invalid_argument` (`premise_historical_ver`); one that is not a version of this target: `invalid_argument` (`not_this_target`). `valid_at` / `valid_during` used on a target in a table that is not a state table: `invalid_argument` (`not_state_table`); both given together: `invalid_argument` (`mutually_exclusive`).
  - A target already pointed to by 1,000 effective declarations: the declaring side is rejected, `too_large` (`premise_fan_in`, with the target and the current count attached). The limit is checked only at declaration time and falls on the declaring side: the depended-on side can never be unable to write because of someone else's declarations.
  - **Two cases that are not rejected**: a `ver` that has expired and, in the declared range, the current value now differs from the value at the version seen (a value that changed in between and changed back does not count); a premise target that has been revoked and a version seen earlier than that revoke (a version seen that is itself that revoke is recorded as `current` and not flagged). In both cases the write is made as usual, this row carries the flag as soon as it is written, the `premises[].state` of the receipt is `changed`, and `warnings` carries `premise_already_changed`. The reason: the evidence (what the user has just said) must be recorded, the flag is visible to all readers, and the writer knows in the same receipt. A `ver` that has expired but where the declared range has not changed is written as usual and not flagged.
  - A restate or clear whose target row is already revoked: `revoked`, the same as an ordinary `update`.

### 5.2 Intervals on state tables

| What was passed | Result |
|---|---|
| Neither, and the intent is not `correct` | Start = now; end = the next recorded change (`next_change`) |
| Neither, and the intent is `correct` | Each field takes the **whole valid period of the segment that contains "now" and is bounded by stop points**. When the point "now" has no value, `invalid_argument` (`no_value_now`) is reported, with a hint to give an interval |
| Only `valid_from` passed | End = `next_change` |
| `valid_to` is a date / instant, or `"open"` | Used as given, the same for all fields in the op |

- **`next_change` is resolved per field**: each field takes as its end the first stop point strictly later than the start; if there is no stop point after it, it continues indefinitely. A stop point is a place where the value of this field changes (including the border between having a value and having none), and the endpoint of an explicit corroboration ("Writing state" in the data model). The `resolved` of the receipt gives the resolution field by field; when the end is not "continues indefinitely", `next_change` is attached: the value, starting at the end, of the segment this write did not change (`null` when it has no value). An explicitly given end (`to_as: "given"`) likewise carries it, as long as there is still a recorded step (with or without a value) starting at the end; when nothing is recorded after the end it is not attached. It is given according to the state when this operation completes, and replaying the same request gives the same value.
- **Interval without a value**: the part of a write that falls on an interval without a value must carry all the required fields, otherwise `validation_failed` (`required_in_gap`, with the missing fields and the interval attached). An explicit interval that spans an interval without a value fills it as given, which is high-impact; the intervals without a value that would be filled are listed only in `impact.filled_gaps` and do not count as segments that would be overwritten (`impact.overwritten`).
- **`revoke`** without an interval revokes the whole entity, and with an interval turns that period into one without a value.

### 5.3 Reverting

`revert` replaces `set`, and the intent may be omitted. The intent of a write that reverts: for `undo`, if the caller gave an intent it is used, and if not, the intent of **the `write.base` with the greatest `seq` of the undone operation on this row (or entity)** is taken, not looking at writes reverted along with it by `include_later`; for `take_previous`, the intent of **the `write.base` that holds the event with the greatest `seq` in the revert record** is taken, and `update` when the revert record is empty.

| Form | Meaning |
|---|---|
| `{undo: n, include_later?}` | Undo all the changes that write number n made to this row / entity. The fields and intervals are taken by the kernel from that write |
| `{to: n, fields}` (later) | Take the values of these fields of this row / entity at operation number n; on a state table an interval and `ver` must be carried at the same time |

- **By default only the part still in effect is undone**; a part that has been overwritten by a later write is skipped: it does not appear in the results per field, and `undo.skipped_superseded` lists it item by item (field, interval, the write that overwrote it).
- **`include_later: true`** reverts the later writes together with it, and always goes into awaiting confirmation as high-impact. In this case the `proposal` of the item awaiting confirmation carries no `set` and carries `revert: {undo, include_later}` (`set` is left for the two proposals of a field value and a revoke, and `set: null` specifically proposes a revoke); the later writes that would be reverted are listed in `impact.reverted`, and the values reverted to are given in the receipt after the confirmation is executed. The `awaiting` flag of a read result correspondingly carries `proposed_revert` and not `proposed`.
- **`undo` does no version-conflict judgement, and `ver` may be omitted**: the caller has named the write to undo, by default only the part of it still in effect is undone, and values others wrote after it are not touched. It still goes through the state-dependent validation (a revoked row reports `revoked`, and `revoked_by` points to the revoke currently in effect that should be undone first; it is not reported when what is being undone is exactly the revoke currently in effect; a written-back `ref` value has its target validated in the same way, a revoked target reports `validation_failed` (`ref_not_found`), and the whole revert does not take effect) and the high-impact judgement. Undoing a revoke with an interval (restoring the value of that period) does not count as high-impact.
- **A write on an affected row cannot be undone within the grace period**: when the target row / entity is affected by a deletion that is still to be executed, `undo` reports `invalid_argument` (`pending_deletion_target`, `param` pointing to that op), with the related deletions and the latest expiry moment attached, and the whole request does not take effect; after the deletion expires or is canceled it proceeds as usual. When the row has been deleted as a whole, `not_found` is reported. A revert by version is an ordinary write and is not restricted.
- **`reverted_later` in the receipt and `impact.reverted` of an item awaiting confirmation do not use the same criterion**: the former is the entries marked `later` in the revert record, listed as the record has them; the latter is a preview shown to a person before confirmation, and lists only the later writes that a reader after the confirmation would see differently, whether or not they are in the revert record, and the confirmation of the undone `undo` itself is not counted. So for the same undo, the writes listed in the two places can differ, and either side can have one more.
- The target is an insert or a first creation: `invalid_argument` (`undo_target`), with a hint to use `revoke`. The target is a candidate or an awaiting-confirmation write that never took effect: the same error, with a hint to use `resolve`. The target is the operation number of a schema switch (the entry of a `backfill` constant fill): the same error, with a hint to submit a new schema draft. The target has no change that can be undone on this row / entity (only same-value corroboration was done, all no-ops and so on): the same error. When the target is a revoke, a system ruling or a write triggered by `resolve`, it can be undone.
- n is not a write of this row / entity: `invalid_argument` (`not_this_target`); the target content has been deleted: `invalid_argument` (`content_deleted`).
### 5.4 Judgement and the receipt

#### The order of judgement

**The order of judgement** ("The write request" in the data model): checks that do not depend on state (`sv`, type, unit, the format and mutual exclusion of parameters) → lookup of the request key; when there is no hit, check the sources referenced by `source_ref` in the evidence (once for the whole request, ahead of the fallback for `sv` / `ver` and ahead of `read_first`) → same value → `ver` and conflict → checks that depend on state, on the part that is about to take effect (including `ref` targets and premises) → high-impact → suspected duplicate. For an op by external key, the kernel first locates the row by the key, and the same-value and conflict steps are replaced by the inputs of a three-way comparison (5.1).

#### Results per field

**Results per field** (`FieldResult` in 04-contract-types.md). For the candidates, conflict items, awaiting-confirmation items and `item_ver` in it, see section 6 and section 2:

| `result` | When | Does it take effect |
|---|---|---|
| `applied` | The value has taken effect. When the `ver` passed back is not the current version but nobody has touched this field since, `merged: true` is added | Yes |
| `corroborated` | Same value as the version seen, and the evidence is pointed to explicitly with `evidence_by_field`: a source is appended, there is no new version | The value is unchanged |
| `noop` | Same value as the version seen, and no evidence is pointed to: it is not a change made by this write | The value is unchanged |
| `candidate` | The `ver` does not match, and this conflict unit (defined below) has since been changed by another write: it is recorded as a candidate, and a conflict item is generated or the candidate is merged into one | No |
| `awaiting` | High-impact: an awaiting-confirmation item is generated | No |

- These five results have the same names and meanings as the effect states of fields in the event format ([`09-event-format.md`](09-event-format.md) 6.3). The parts skipped by an `undo` are not a kind of field result; see 5.3.
- **The written-back entries of a revert and of "back to before the conflict"** all have the result `applied`, and may carry no `after` but one of two flags instead (in `timeline` as well):
  - `no_value: true`: this place goes back to the state of "no contribution at all": there was no value here before the reverted write. It differs from writing an optional field explicitly as `null`: the latter is an empty value with provenance.
  - `uncovered: true`: this segment merely "no longer counts" and is given no value: what was reverted is a value filled into a gap left by a revocation, and after the revert the gap shows again. The value under the revocation was not touched; when that revocation is later undone or deleted, it appears as usual.
- **A value whose provenance is a schema constant**: when a written-back entry or a deletion result goes back to a value filled in by the constant `backfill` at some schema switch, this entry in `timeline` lists no sources under `sources` and carries `schema_const: {sv}` (the backfill of which version); the `reverted_to` of a deletion result likewise carries `schema_const: {sv}` and does not carry `from_seq`. The per-field results of a write receipt give no provenance. Such a value has no original words to look up. The constant itself is not removed by deletion, but on a state table, when the contribution a backfilled segment depends on is deleted, that backfilled segment no longer exists ("Deletion · Provenance: value source and operation source" in the data model).
- **Same value is judged by the version the writer saw** (the version the `ver` passed back points to), not by the current value. A field passed back unchanged is therefore not taken for a change and does not cause a conflict.
- **A conflict unit** is one field, or a group of fields that the schema declares with `together`. A revocation changes "existence" and intersects every conflict unit; the key of its result is `"*"`. On a state table the intervals must also intersect; for the criterion see "Conflict handling" in the data model.
- **Both a version mismatch and high-impact**: it first becomes a candidate; the `candidate` result carries `impact` (what it would overwrite if it took effect), and `take_candidate` is the confirmation of it.
- **Writing to a revoked row** (event tables, timeless tables): `update` / `correct` report `revoked` (with the write number that revoked it); `revoke` again is a no-op. A state table has no "revoked" state: a revocation is an interval without a value.
- **A request in which every field is a no-op**: the source data is stored and the write number recorded as usual, `status: saved`, and `ver` is unchanged. Exception: when all ops in a request are `unchanged` or `skipped` ops by external key, this request **appends no event at all**: there is no write number, no source data, no request key; the receipt is still given, without `seq`. Evidence that the caller carried explicitly is **not stored** in this case either: nothing needs it ("evidence carried explicitly is stored" holds only for a request that produced events); the `warnings` of the receipt give `evidence_not_stored`, stating truthfully that these segments were not stored. In a request that produced events, the evidence segments inlined by an op by external key that did not enter an event are likewise not stored (no source data is stored for it), and `evidence_not_stored` is also reported (`evidence` is empty, the segments are listed in `op_evidence`); evidence segments at the request level are stored as usual, and those referenced only by ops that did not enter an event report `evidence_unreferenced`.

#### The receipt's `status`

**The receipt's `status`**:

| `status` | Meaning |
|---|---|
| `saved` | All fields have taken effect (including `corroborated` and `noop`); it is also `saved` when `flagged` items were generated |
| `pending` | Any field became a candidate or went to awaiting confirmation |
| `job` (later) | Turned into a background job |

**A rejected write is not a status, it is an error** (section 11): the whole request does not take effect.

- `pending[]`: the items generated, merged into or refreshed by this write. A newly generated one carries `item_ver`; `merged` (merged into an existing item) and `refreshed` (the write touched the target of an open item that it had not read, or the item was not touched but its recomputed content changed) do not carry it, and the details must be looked at first.
- `superseded[]`: the items superseded by this write. **An item is superseded only when a writer who has read the current version of the item changes its target**; when it has not been read, the item is refreshed and stays open ("Pending items" in the data model).
- `affected_reads`: given when the impact query is triggered: `correct`, `revoke`, and any write on a state table that makes a value change. It counts by reason and does not include the read that the `ver` carried by this write came from; `covered_since` is the moment up to which the read record is kept, and reads earlier than that are not in the count; `possible` is the number of reads among them that can only be counted as "possibly affected" (reads by restricted SQL that read many rows and kept only a table-level record, and reads matched by a set of versions): such a read cannot tell whether it used the row that was changed, and it is better to over-report, so it is counted separately; `not_covered` lists the kinds of reads that are not covered.
- `derived[]`: the affected derived values, one entry for each changed field on a derived row (group key fields are not listed separately, they are in `key`), at most 20 entries, with `derived_total` (the total number of field entries) given in addition. What is listed is the change of values: when a derived row appears or disappears, fields that are null both before and after have no entry; a derived row whose fields other than the group key are all null both before and after is not in `derived[]`, and `derived_total` does not count it either. In the receipt of an idempotent replay `derived[]` is empty, and `derived_total` is the number of derived writes of this operation (one for each affected partition); see section 14. A derived value computed at read time has no derived write, is not listed in `derived[]` and is not counted in `derived_total`; its value is computed from the data at that time on the next read.
- `premise_affected`: the change to premises declared by other rows, on the rows changed by this operation: the number of dependent rows newly carrying `premise_changed` (`count`), the number of dependent rows whose flag was removed (`matched`), counts by reason (counted by row; when a row counts toward several reasons at once it is counted once for each, so the sum of the items can be greater than `count`), and the flags listed one by one: one for each declaration flagged on each dependent row, at most 20 (at most 50 in `deletion_preview` and `delete`), while `count` is still the number of rows. A revoked dependent row is counted and listed all the same, on the same basis as a read with `include_revoked`. It is not given when there is none. The writes triggered by `resolve`, the result of `delete`, and the `cancelled` of cancelling a deletion have it too; in `deletion_preview` it is a forecast.
- The `premises[]` of each op correspond one to one with the `premises` of the request: the version seen that was actually adopted (when the fallback applied, the one the fallback arrived at), and `state` (`current` / `changed`; with `changed`, the reason and the operation number that made the premise change are attached).
- `replayed`: an idempotent replay (section 14).

#### Outcomes of an op by external key

**Outcomes of an op by external key** (`OpResult.outcome`, carried only by ops by external key):

| `outcome` | Meaning | What the receipt carries |
|---|---|---|
| `created` | A row was added | `target.row`, `ver`, per-field results |
| `updated` | At least one non-key field took effect or became a corroboration (other fields may have become candidates); when all fields are corroborations it is also `updated`: the corroborations enter the event and a record is left | Per-field results |
| `unchanged` | All fields are no-ops | Only `target` and the original `ver`, without per-field results |
| `pending` | No field took effect, and some fields became candidates or went to awaiting confirmation | Per-field results |
| `skipped` | Hit a revoked row, the key is held by a deletion within its grace period, or used the temporary name of a skipped op | `skip_reason`: `revoked` (with `revoked_by`) / `pending_deletion` (with `deletion`) / `ref_skipped` (with the index `ref_op` of that op). These are taken from the current state at the time of the write |

- An `unchanged` or `skipped` op **enters no event**, and no source data is stored for it; the other ops in the same request are executed as usual.
- The receipt also gives `external_key_summary`: five counts, `created`, `updated`, `unchanged`, `pending`, `skipped`, covering only ops by external key.
- The rules for `status` are unchanged: `skipped` does not affect it, and a warning `external_key_skipped` (listing the indexes of the skipped ops) is given in addition.
- Being skipped is not an error: an ordinary write to a revoked row reports `revoked`, because the caller named this row; a connector hands in a whole batch and does not know which of them the user has revoked, and one revoked record should not make the rest of the same batch fail. Restoring is up to a person: undo that revocation with `revert: {undo}` by row ID.

#### Admission of writes

**Admission of writes**: exceeding the admission threshold reports `too_large` (`admission`), with `estimated_rows` and `suggested_batch`, and the caller splits the batch. After jobs are added later, a request with `mode: "job"` is turned into a job. In the first version every base change recomputes the affected rules in full, the cost grows with the tables the rules read and does not vary with the size of the request, and splitting into batches cannot lower it, so admission does not reject and does not report this reason; it is enabled after the estimate by affected partitions ("Cost estimate and admission threshold for derived refresh" in the open questions).

## 6. Pending items: kind × decision × effect × scope

The authoritative definitions of execution semantics, the rules for superseding and merging, and item IDs and item versions are in "Pending items" in the data model; this table gives only the combinations at the interface. For the kinds see section 4.8 of 04-contract-types.md.

| Kind | Arises from | Does the value take effect | Decision (`decision`) | Required scope |
|---|---|---|---|---|
| `awaiting_confirmation` | A high-impact write (for the list see "Writing state" in the data model); when a privacy deletion makes a conflict disappear while the candidate is still high-impact, it is turned from a conflict item | No: what is read is the current value plus the proposal | `confirm` / `reject` | `saveslot.write` |
| `flagged` | Suspected duplicate (`duplicate_keys`) | Yes | `keep` / `revoke` | `saveslot.write` |
| `conflict` | A write carrying a stale `ver` changed a conflict unit that someone else has changed since; later candidates on the same target are merged into the same item | The value in effect is given by the rule (the first version: keep the current value) | `keep_effective` / `take_candidate` (with `candidate`, the index of the candidate, when there are several candidates) / `take_previous` | `saveslot.write` |
| `schema_change` | `schema_draft` (a change that cannot take effect automatically) | No | `confirm` / `reject` | `saveslot.schema` |
| `deletion` | A confirmed deletion, in its 24-hour grace period | Logically deleted | `cancel` | `saveslot.delete` |
| `migration_diff` (later) | A migration whose result must go into the list of differences | No | `accept_all` / `rows` / `keep_rest_and_switch` / `abandon` | `saveslot.schema` |

- **The target of an item**: a row / entity plus the conflict unit (`unit`), and on a state table also the intervals (given segment by segment, possibly several disjoint intervals). On the same (row / entity, conflict unit), a candidate whose interval intersects the interval of an existing item (by any one segment) is merged into it; when it intersects several at once it is merged into the earliest; one that does not intersect becomes a separate item. For a conflict in which a revocation takes part, `unit` is `["*"]`. Awaiting-confirmation items are not merged: each high-impact write makes one item of its own.
- **The three decisions on a conflict**:
  - `keep_effective`: keep the current value in effect, and no candidate takes effect.
  - `take_candidate`: adopt one candidate, and apply only the conflict unit of this item. When the candidate is a revocation, the revocation takes effect; when the candidate is a modification and the row is currently revoked, the row is restored and the modification is applied.
  - `take_previous`: go back to the merge base, which is the earliest of the `ver` values carried by the candidates the item currently has, and take the value at that version on this conflict unit (and interval). The `previous` of the details gives this value, and `reverted_by_previous` lists the writes whose results would change for what is read if the merge base were restored (for the basis see "Writes and reads · Undoing a write" in the data model).
- **What each decision is bound to** ("Pending items · Item ID and item version" in the data model):

  | Item · decision | What `resolve` must carry | What is checked |
  |---|---|---|
  | Default | `item_ver` (or the fallback) | The content of the item has not changed since it was read |
  | `deletion` · `cancel` | Nothing needed | Not checked, as long as it is still in the grace period; when the grace period has passed, `item_closed` (`expired`) is reported |
  | `migration_diff` (later) · `abandon` / `keep_rest_and_switch` | `item_ver` (or the fallback) | Only which migration it is and the restore count are checked |
  | `migration_diff` (later) · `accept_all` | `diff_upto` | Only entries with sequence number ≤ k are accepted |
  | `migration_diff` (later) · `rows` | `item_ver` (or the fallback) | Only that the difference entries of the listed rows have not changed is checked |

- The details of an item list only the decisions **available to the current credential** (`decisions`); using a decision that is not available reports `insufficient_scope`.
- **An item whose target is affected by a deletion that is still pending** (other than `deletion` and `schema_change`): `decisions` is empty, and `blocked` is carried in addition (the reason `pending_deletion`, the relevant deletions, and the latest expiry moment); in a list such an item carries `blocked: true`. Calling any decision then reports `invalid_argument` (`pending_deletion_target`).
- **Confirmation is delegated to the caller**: saveslot does not distinguish whether a confirmation comes from a person or an agent (the architecture document §3). A slot policy can specify that "this kind of decision accepts only the confirmation of a user session"; the `user_session_only` in the item details then lists these decisions, and a connection calling them reports `insufficient_scope` (`required_scope: "user_session"`); this switch is not implemented in the first version.
- **Who last changed a row that was read**: rows of base tables read by `query` and by the `as_of` of `history` carry `changed_by`: the writer of the operation in its `ver`, given only when it is not the caller itself. When the caller sees that someone else has just changed the row it is about to change, it tells the user first and writes after asking; the kernel does not reject or re-judge the write because of this (writing with the `ver` just read means, by the contract, writing after having seen the latest).

## 7. Data flags

A flag is a structured field, not text (the architecture document §6). For the types see section 3 of 04-contract-types.md.

| Flag | Meaning |
|---|---|
| `disputed` | There is an open conflict item; what is given is the value in effect as given by the rule. It carries the item, the fields in the conflict unit, and the intervals |
| `awaiting` | A proposal has not yet taken effect; what is given is the current value |
| `flagged` | The value has taken effect and is only flagged; whether it counts is for the reader to judge |
| `corrected` | The row has been corrected. On a state table it is given by segment: the value of the fields read in this segment comes from a correction write (for merged segments, it is enough that any one segment does) |
| `revoked` | The row has been revoked; it appears only with `include_revoked: true` |
| `possibly_affected` | A version this connection read earlier has since been affected; it is removed if the value is later restored |
| `partially_deleted` | In a read by instant, when restoring, part of the data of that time has been deleted |
| `pending_deletion` | The row is affected by a deletion that can still be cancelled (for the criterion see "affected" in "Deletion · Cancelling a deletion and the grace period" in the data model; during this time the items on it cannot be handled and writes to it cannot be `undo`ne) |
| `dangling_ref` | The row or entity pointed to by some `ref` field of this row has been revoked or privacy-deleted; the value of the referencing side is unchanged and is only marked. It carries the field and the state (`revoked` / `deleted`) |
| `premise_changed` | A premise (5.1) used by the current value of this row has since changed; the value has not moved, and whether it still holds is for the reader to judge. **Any reader** can see it. It carries the row where the premise is, the declared fields, the version seen when declared, the reason, the operation number that made it change, the fields in this row covered by this declaration, and which write declared it |
| `computed_at_read` | The derived row was computed at read time (the rule depends on "now", or reads a state table without a valid time qualifier): the value depends on the moment of reading, and this row carries no `ver` |
| `stale` / `pending_extraction` (later) | A large write job is in progress / extraction was not finished when the migration switched |

- **`disputed`, `awaiting` and `premise_changed` are flagged only when the value read would change with them**: when `fields` was requested and does not contain the fields the item involves (for `premise_changed`: the fields this declaration covers), this row does not carry this flag.
- The `reason` of `possibly_affected`: `correct` (the value you read has been corrected), `revoke` (a record it contains has been revoked), `retroactive` (the value at the valid time you read has since been modified retroactively), `plan_changed` (a future arrangement you read has been changed).
- The `reason` of `premise_changed`: the four above, with the same names and meanings, and in addition `update` (the premise was changed), `deleted` (a privacy deletion changed the value of the premise) and `schema_switched` (a schema switch removed the declared field). When a write has both a retroactive part and a future part on the declared range, `retroactive` is taken.
- The difference between `premise_changed` and `possibly_affected`: the latter is given only to the connection that read the old version, answers "was what you read then right", and is not in the log; the former is the state of this row, follows from an explicit declaration and enters the log, and an `update` on event tables and timeless tables can trigger it too. At most 10 entries are listed per row, from new to old by `since` (among entries with the same `since`, the one declared later comes first), and when there are more, the total is given in addition. Setting or removing a flag does not change the `ver` of this row.
- When the table (or slot) where the target of a premise is not visible to the reader, the flag is still given, with `hidden: true`: the value of the dependent row stands on a premise that has already changed, which matters to everyone who can read this row. It carries only what belongs to this row itself: the fields covered in this row and `since`; the reader learns only that some record this row relies on has changed and from which operation, and does not learn which table, which row or which fields, nor how it changed (no reason is given). It is counted as usual in the cap of 10 and in the total, and the `fields` filter applies as usual.
- A derived row has no flags of its own and carries `input_marks`: it counts only base rows that carry flags on the fields the rule depends on (including the count of `premise_changed`). When the rule reads a state table without a time qualifier, what is read is, for each entity, the segment that contains the evaluation moment, and the valid time range of a flag counts only when it also intersects that segment, which is the same as whether the flag would be set when reading the base table at that moment.
- The result of `sql` carries a summary of the same shape (`marks_summary`), computed from the set of row versions this query read. Each item is counted by row, and on state tables by entity, not by segment: if any segment of an entity carries a flag, it is counted once, regardless of which segment this read got and not varying with `at`, so it can be more than what a row-by-row read at that moment would give.

## 8. Untrusted text

**Text that comes from user content or is written by a caller and may contain instructions is marked in the contract with the type `UntrustedText`** (`x-untrusted: true` is added in OpenAPI / JSON Schema). The field value stays as it is and carries no label of any kind; the untrusted boundary is added uniformly by the renderer of the surface (for MCP see "The untrusted boundary" in 05-surfaces.md), and the renderer tests check that these fields are all wrapped (the architecture document §6, §11).

What belongs to `UntrustedText`: values of type `text` and example values; the original text of source data, the excerpts of `file_ref`, file names and source locations; the whole `rows` of `sql`; the current value / proposed value / candidate value and the `note` in pending items; the keys in `existing_keys` and `similar_keys`; user input echoed in errors; descriptions, aliases (`aliases`) and rule texts written by a caller in a schema (with the writer and the version); the `instructions` of extraction work items and the original text of writes.

**On the entry side**: when, in a document received by `schema_draft`, a description or alias contains the boundary marker of a surface (of the form `<untrusted-data-`, `</untrusted-data-`), `validation_failed` (`untrusted_marker`) is reported: it means the caller brought back a label it had read, as it was. Other writes do not make this check: source data is stored as it is.

## 10. Rules of each operation

For the structure of parameters and results and a JSON example of each operation, see sections 4 and 5 of 04-contract-types.md.

### `catalog`

- Three levels: `list` (the default, the list of slots and tables, paged by table), `table` (the fields, units, precision, relations, rule text, dependencies and profile of some tables; `tables` is required, 1 to 10 tables), `schema` (the complete schema document of a slot, with the slot policy; `slot` is required). A missing required parameter reports `invalid_argument` (`missing`).
- Only slots and tables in the visible range are listed; the profile, example values and relations involve only visible tables. When the `slot` parameter points to a slot that does not exist or is not visible, `not_found` (`slot`) is reported.
- **Aliases**: tables and fields can carry `aliases` (the user's wording, old names and colloquial names written by the schema author). The `list` level carries the aliases of tables, the `table` level carries the aliases of tables and of every field, and the `schema` level is the document as it is. Aliases are untrusted text (section 8) and **take no part in name resolution**: requests and restricted SQL recognize only names, and a request that wrote an alias still reports `unknown_table` / `unknown_field`; for how `nearest` in the error uses aliases to give the right name, see section 11. The change code for changing aliases is `change_aliases`, which belongs to the automatically-effective category `description`.
- The table definition at the `table` level carries `external_key` (when an external key is declared: the name of the key field).
- The document ID and `base_version` returned by the `schema` level are already filled in, so it can be modified and handed to `schema_draft` directly; handing it back unchanged is `no_change`. The document is generated from the compiled definition of the current version, and the text of a derivation rule is the original text at submission (see "Schema document format" in the data model). With `draft` (a draft ID), it returns the document of the whole slot after switching to that draft: generated from the compiled definition of the draft, in the same way as above (for the derived tables the draft lists, the rule text in the draft is used, and for those it does not list, the one currently in effect), whatever state the draft is in; `sv` is the version this draft compiles to. The `base_version` of the document is the version at which it holds, and when it is handed back, staleness is judged by it as usual:
  - A draft awaiting confirmation: the current version of the slot (while the draft is open the slot does not switch). Handing it back unchanged submits an identical new draft that supersedes it; changing one place and handing it back is the same.
  - A draft that has taken effect: its own version. When it is still the current version, handing it back unchanged is `no_change`; if the slot has switched since, handing it back reports `draft_outdated`.
  - A draft that was superseded or rejected and never took effect: the `base_version` at its submission. If the slot has switched since, handing it back reports `draft_outdated`; if it has not switched (after a rejection), handing it back submits an identical new draft.

  The read is recorded in the read record as usual. A draft that does not exist, does not belong to the `slot` in the parameters, or is not visible reports `not_found` (`draft`), and the three are byte-for-byte identical. The `schema` level, with or without `draft`, is given only when every table of the slot is in the visible range, otherwise `not_found` (`slot`) is reported, the same as when the slot does not exist: the first version does not give a document "containing only the visible tables", because the text of a derivation rule would reveal the names of the tables it reads ("Visible scope" in the data model). A caller that named all the current tables and reads the document of a draft will see the tables newly added by the draft (which have no ID yet and cannot be named): this is intended. When the receipt of `schema_draft` cut the full text of the document, use this to read it again (the document in the receipt is the submitted original text with IDs filled back in and lists only the tables the draft changed; this one is the whole). The document cannot be paged; exceeding the result budget of the surface reports `too_large` (`result_budget`) and does not truncate. (This is a read operation and nothing was recorded; an operation that has already been recorded does not use this error, see section 3 of 05-surfaces.md.)
- Profile: the number of rows, the valid time range, and the most recent K distinct values of each field (taken by operation number, deterministic). At the `table` level every table carries `profile` (the number of rows, the valid time range and a scale hint), counting only tables within the caller's visible range; a derived table computed at read time does not carry it: it has no stored rows to count, and computing the rule once on the spot is not what a catalog should do. The number of rows counts the rows currently in the table: event tables and timeless tables count rows that are not revoked, state tables count interval segments (adjacent segments whose fields all have the same value are merged first; how they are physically cut does not change the result, on the same basis as the `total` of `query`), and derived tables count their own rows. The valid time range: for an event table, `from` and `to` are the earliest and latest values of the time field, both ends included (only rows that are not revoked are counted); for a state table, `from` is the earliest interval start and `to` is the latest `valid_to`, not included (the same convention as every `valid_to` in the contract), and when there is a segment that continues indefinitely, `to` is not given; timeless tables, derived tables and empty tables do not give it. It is computed from the current data at read time and does not enter events. When the slot has a migration in progress, the `list` level carries `migration`; during this period, calls that involve this slot give `migration_progress` in `notices` (the target version and the progress).
- **Scale hint**: when the number of rows crosses a line, the profile at the `table` level carries `scale`: above the comfortable line (`comfortable_rows`) and not above the tested line (`tested_rows`) it is `large`, and above the tested line it is `beyond_tested`; the values of the two lines are released with the kernel version ("Capacity limits and measured values" in the architecture document). It is computed at read time from the current `profile.rows` of this table, does not enter events, and is not a data flag; it is not carried when the comfortable line is not exceeded. The `list` level does not carry it.

### `query`

- **Row-by-row read**: the `ver` returned can be used for writes and also as the fallback. A read is recorded automatically in the read_log ("Read records" in the data model).
- For the types each operator of `where` applies to, see 4.3 of 04-contract-types.md; using it on a type it does not apply to reports `invalid_argument` (`operator_type`). The comparison value of `quantity` carries a unit and is compared after same-dimension conversion.
  - **Comparison values are read by the same rules as writes** (section 1, "The encoding of values"), and one that does not qualify reports `invalid_argument` (`malformed`, with `param` pointing to that value). The comparison value of `text` is put through NFC before comparing, and so is `contains`. `decimal`, `integer` and `quantity` are compared by exact value, not rounded to the precision of the field (rounding would let the comparison value cross a stored value).
  - `zoned_datetime` is compared by instant. Comparing with a date reports `invalid_argument` (`malformed`), and `example` gives the way to write an instant; comparing by day requires the internal date column, which is left until it is implemented. This differs from the same-value criterion (same instant and same time zone) on purpose: ordering operators can only compare by instant, and it would be worse if `=` were inconsistent with `<=` plus `>=`. When the comparison value carries no offset or time zone, it is read in the slot time zone and `warnings` gives `timezone_assumed`.
  - The names written by the caller that are echoed in an error (`name`, the segments in `param`) are each cut to 200 characters.
  - The result of `!=` includes rows where the field is empty (empty is not equal to any value); `<`, `<=`, `>`, `>=` do not include them.
- By default only rows that are not revoked are returned; with `include_revoked: true`, revoked rows carry `marks.revoked`. On a state table a revocation is an interval without a value and there is no "revoked row", so `include_revoked` gives nothing extra.
- Default order: event tables by occurrence time descending, and for the same time by row ID ascending; state tables by entity ID ascending, then by `valid_from` ascending; timeless tables by latest change descending, and for the same change by row ID ascending; derived tables by group key ascending. When `order` is given, it is applied first, followed by this set of default keys. Empty values come last in both ascending and descending order; text is compared by code point. `cursor` is based on this set of keys: the next page starts after the key of the last row of the previous page.
- `total` counts the rows returned, that is, the segments after merging (`coalesce`); the segments of one entity can fall on two pages.
- On state tables one segment is one row; `ver` is given by entity, and the segments of the same entity have the same one. For time parameters see section 4.
- A row may carry `premise_changed` (section 7). For `detail` see section 13.

### `sql`

- A single SELECT; tables and fields are used by name; for the allowlist (statements, nodes, functions, operators, aggregates), parsing and defenses see "[Restricted SQL](03-data-model/11-restricted-sql.md)" in the data model.
- **It can reference tables of several slots within the visible range**: `sql` is read-only and involves neither version ownership nor atomicity; the `sv` of the result is given per slot. Derivation rules and `ref` fields do not cross slots, and this is unchanged. Referencing a table that does not exist or is not visible reports `sql_rejected` (`unknown_name`); `marks_summary` counts only visible rows.
- The result is column definitions plus an array of rows; the unit of a `quantity` column is in the column definition, and the cell is a decimal string. Positional parameters are scalars; a quantity with a unit is passed as a decimal string in the unit declared for that column.
- `max_rows` is the number of rows per page (default 100, upper limit 1,000), and `cursor` turns to the next page.
- The result carries no `ver` and adds no row ID automatically, does not count as a row-by-row read and cannot serve as the fallback; it carries `marks_summary`. The whole `rows` is untrusted text.
- A timeout reports `sql_timeout`. The time limit is enforced only on PostgreSQL (server mode); local mode (PGlite) does not enforce a timeout.

### `history`

Four modes, with parameters distinguished by mode (written as `oneOf` in JSON Schema); a mismatch between mode and parameters reports `invalid_argument` (`mode_mismatch`), and `example` gives a complete example of that mode.

| `mode` | What it answers |
|---|---|
| `timeline` (default) | Each operation on a row / entity: who, when, with what intent, the result and the values before and after for each field, the provenance (value source and operation source kept apart); the reads that read each version. It returns the current `ver` and counts as a row-by-row read |
| `as_of` | What the target looked like at some recorded moment; `ver` is a historical version. Rows carry only the `corrected` and `revoked` of that time: the item flags (`disputed`, `awaiting`) and `premise_changed` describe the present state (the state of premise declarations is not kept by moment), and are not given; for the same reason a row with `detail: "detailed"` does not carry `premises`, and the other details are given as of that recorded moment |
| `changes` | The changes between two recorded moments; the target may be omitted, and the changes of the whole table are returned |
| `composition` (later) | Which base rows a derived row is composed of |

- All four modes are paged by `limit` / `cursor`.
- `timeline` lists all operations on this row / entity, including those that did not take effect (candidates, awaiting confirmation) and those triggered by `resolve`, deletion and cancelling; the `via` of an entry explains where it came from. A field whose content has been removed by deletion carries `removed: true`. A value filled in by the constant `backfill` at a schema switch is also an entry: its `intent` is `schema_switch`, its `via` is `{schema: {sv}}`, its `actor` is `system`, and it has no source data; it does not change the `ver` of the row, so the operation number in the current `ver` can be earlier than this entry. A field written back by a revert may carry `no_value` or `uncovered` (for the meaning see 5.4). A write that declared premises carries `premises` (target, fields, version seen, whether it has changed by now); a restate and a clear are each an entry too, and the `premises` of a clear is an empty array; several ops on the same row in the same request are each an entry, from the last to the first by op index. A declaration that no longer counts (superseded by a later declaration on the same target, or cleared) gives `ended` and carries no reason or `since`. Later pages stop at the operation number of the first page, but the state of the premises is the present one, so `since` can be greater than that operation number. When the table where the target of a premise is not visible to the reader, that entry gives only `hidden: true`, whether it has changed by now, and `since`, and does not give the target, fields, version seen or reason: this is an intended exception, the reader knows that some record this write relied on has changed and from which operation, and does not know what it is or how it changed.
- `as_of` accepts an operation number, an instant, `{read}` (a read by any connection) or `{task}` (that task **of this connection only**, taking by default its last read of this target, with `other_reads` listing the others; the read made by `as_of` itself reads a historical version and is not counted); the latter two restore by the position of the state seen by that read, and when that read read the same table, its valid time condition is also carried over, while a read of another table contributes only its position. An instant earlier than the first operation gives `seq: 0`, carries no `recorded_at`, and the result is empty. The result states the `sv` of that time, and values are interpreted by it; for a position earlier than the first time this slot took effect, `sv` is taken from its first version (table names and field names also follow it). `{read}` pointing to a read outside the visible range reports `not_found` (`read`); under `{task}`, a target that has not been read reports `not_found` (`read`, with `param` being `as_of/task`).
  - On event tables and timeless tables, rows that were already revoked by that time are still returned, with `marks.revoked`; a target that did not exist yet at that time gives an empty result.
  - When the target has never had any version (the writes to it have not taken effect, for example the only write became just a candidate or awaiting confirmation), `not_found` (`row` / `entity`) is reported, the same as when the ID does not exist, and the same in every mode; when the target has had versions and `as_of` is earlier than its first version, the result is empty (the previous item).
- Paging is as in section 15: the later pages of `timeline` list only entries up to and including the operation number of the first page, with `ver` taken at that moment; `reads` is given only on the first page, and only the first page returns and registers the current `ver`. The pages of `as_of` go by the start of the segment; the record point (an instant, an operation number beyond the log, `{read}`, `{task}`) is resolved on the first page, cut to the operation number of the first page, and carried to later pages with the position, and later writes and reads do not change it. The pages of `changes` go newest first and, within the same operation, by target ID; the window (the operation numbers that `since` and `until` resolve to; `"my_last_read"` is also resolved on the first page) is fixed on the first page and carried to later pages with the position: later writes do not enter the window, and the read registered by the first page itself does not change the `since` of later pages. The later pages of `reads.list` list only up to the last read record at the time of the first page.
- An entry of `timeline` is one base write: when several ops in the same request write the same row, each is an entry, with the same `seq`, and `total` counts entries. The `before` of a field is the value before this write at the start of this item's interval (for what an earlier op in the same request has already written, it is the value it wrote; when there was no value here before, it is not given). The provenance of an item that did not take effect (candidate, awaiting confirmation) is taken from the event of this write itself.
- **The window of `changes`**: only operations whose operation number is in `(since, until]` are looked at, `since` excluded and `until` included, and when `until` is not given it runs to the latest. A point is an operation number or an instant, resolved as in `as_of` (taking the last operation number not later than it; an instant earlier than the first operation is 0, and one beyond the latest is the latest), and `0` (looking from the beginning) is also allowed. The `since` and `until` of the result are the operation numbers they resolved to. When `since` is not earlier than `until`, the result is empty and no error is reported. `since` is required, and a missing one reports `invalid_argument` (`missing`).
- **The entries of `changes`**: an entry is the change made by one operation to one row / entity, newest first and, within the same operation, by target ID; when several ops in the same request write the same row it counts as one entry and gives the net change before and after this operation (an entry of `timeline` is one base write, which differs from this). A net change of zero (written first and then changed back) has no entry. The `intent` of an entry is that of the last op in this operation (when the intents in the same request differ, the first is not taken). Only fields whose value actually changed are listed, and unchanged ones do not appear: writing the same value again, and the parts of a state table where a write cut a segment into several but the value did not change, have no entry. A write that did not take effect (candidate, awaiting confirmation) is not a change; it counts only at the operation in which it takes effect (for a write triggered by `resolve`, by the operation number of that operation). `before` and `after` are not given when there is no value. The `intent` is the intent that this operation wrote into the version table (including `deletion`, `deletion_cancelled`, `schema_switch`); an undo (`undo`) is a write, and its entry gives the value it wrote back, with the intent it recorded, carries no `via`, and `timeline` is to be used to see where it came from.
  - Event tables, timeless tables: one object for each changed field. State tables: each changed field is an array, and each item is a stretch of valid time in which the values before and after differ (adjacent stretches with the same before and after values are merged), carrying `valid`.
  - `*` (whether this row / this segment exists): given when a revocation or the undoing of a revocation changed it, `before` and `after` are booleans, and `true` means it exists; on event tables and timeless tables it is an object, on state tables it is an array, each item carrying the segment `valid` that was revoked or restored. An addition does not give `*`. A revocation with an interval makes that period have no value, and the field also gives the disappearance of the value for this stretch.
- `since: "my_last_read"` of `changes` = of the positions this connection (when `task` is carried, only the same task is recognized; when it is not carried, only reads without `task` are recognized; for a user session, this session) has read, the latest of them: of those reads, the greatest "position of the state seen" ("Read records" in the data model). It is compared by position, not by the order the reads were made or recorded in (architecture §7 "Durability of read_log"). **It is recognized by the range the read covered**: for `changes` whose target is a whole table (no row or entity given), only reads that cover this table are recognized: `query`, and `changes` whose target is the whole table and which was given the whole window; for `changes` whose target is one row or entity, reads that cover this table are recognized, plus reads of this row or entity (`timeline`, `as_of`, `changes` on it), taking the one of the greatest position. When only one row was read, asking `"my_last_read"` for the whole table gives `read_first` (`no_read`): it has not seen the other rows of that table, and no answer with omissions is given. For a read by recorded moment (`as_of`), the position is its record point; reads of derived tables, of other tables and of other connections do not count; a read by `sql` does not count either: which rows it reads depends on the query, and what the read record keeps is a superset, so it cannot be taken as having looked at this table. The self-check read of `saveslot connect` does not count; no read, or a read only under another `task`, both report `read_first` (`target: "table"`, `param: "since"`; `reason` is `no_read` and `task_mismatch` respectively, and the latter carries `read_task` and `task` and does not carry `ver`). **It counts as read only when the whole window has been read**: `changes` registers the position as `until` only when it has given the whole window (`since` to `until`): when the first page can hold the whole window, it registers on the first page; when it cannot, neither the first page nor the middle pages register, and it registers when the last page is returned. What is recorded as read must be exactly what was given back to the caller. `changes` returns no `ver`, does not count as a row-by-row read and does not serve as the fallback for `ver`; it registers the `sv` of the slot read (on the first page), and a write that carries no `sv` can pass by `sv_fallback` through this.
- On a **derived table computed at read time** (`marks.computed_at_read`), `timeline` and `as_of` report `not_in_this_version` (`param` is `table`): its rows were not written by any operation and it has no state by moment.
- **`changes` does not take a derived table as its target**; when `table` is a derived table it reports `invalid_argument` (`derived_table`). A party that has read a derived value (such as a monthly total) and wants to know whether what it read no longer holds: run `changes` on the base table that the derivation rule summarizes, with `since` taken as the operation number of that read result (not `my_last_read`: a party that has read only the total has no read record on the base table and would get `read_first`); or read the total again directly. The impact query of the first version does not cover reads of derived values, and this is the only way for the reader.

### `sources`

- `list` (the default), `search` (`q` is required; in the first version it is substring matching), `get` (`id` is required). `from` / `to` go by recorded time, `[from, to)`. The values of `kind` include the `api_call` generated by saveslot; those used by a correction write as value source carry `correction: true`. Only the source data of visible slots is returned; a `slot` filter pointing to a slot that does not exist or is not visible reports `not_found` (`slot`), and an ID of source data that is not visible reports `not_found`. When the caller's visible range for a slot is not the whole slot (only some of its tables), in the first version the source data of this slot does not exist for it at all: `list` and `search` do not give it, `get` reports `not_found`, the same as for non-existence, and filtering by the name of this slot gives an empty list (the slot itself is still visible), because source data belongs to the slot, and the original text and the request of an `api_call` may mention any table of this slot ([`08-open-questions.md`](08-open-questions.md)). `list` and `search` go by `seq` descending (the order in the log, not by recorded moment: when the clock is set back, recorded moments are not monotonic), and the paging key is also it. `search` compares against the original text, the name and excerpt of `file_ref`, and the request text of `api_call`, and not against the slot name or the writer; both sides are put through NFC first, and only the ASCII letters A to Z are case-folded (the same basis as the comparison of names, with no Unicode case folding); an empty `q`, or one that is empty after NFC, reports `invalid_argument`; there is an upper limit on the number of entries scanned by one call, so a page may not be full and still give a next page.
- `get` returns the original text or file reference, the slot it belongs to, the recorded time, the writer, and which data it produced (listing only the tables visible to the caller). An `api_call` has no original text: the `text` of `get` gives the JCS text of its request, and the `excerpt` of a list gives the first 200 characters of that text. `correction: true` means it is the value source of a write whose intent is `correct`. All three modes are recorded in the read_log, recording only the operation, the mode and the ID, and not the search term.
- **Source data pending deletion within the grace period** returns no content and carries `deletion: {state: "pending", item, expires_at}`; **source data that has been physically erased** carries `deletion: {state: "removed", at, reason}`. A list treats them the same way. **The limitation of 0.1.0**: 0.1.0 has no privacy deletion and source data can only be in the existing state, so the `deletion` field does not appear. When the kernel meets source data that is not in the existing state, every call of the three modes reports `not_in_this_version` for the whole call (`reason` is `not_implemented`), before looking at the mode, the filter or the paging, and gives no content.

### `deletion_preview`

Not provided in 0.1.0 yet: `deletion_preview` (including the `dc_` handle) reports `not_in_this_version`; this section is design ([`07-scope-v1.md`](07-scope-v1.md) section 7).

**It deletes nothing.** Two ways of calling: give `{kind, sources}` to produce a preview; or give only `{confirm}` to produce the preview again for the target bound to an existing `dc_` (what is returned is still the same `dc_`, and its validity period is unchanged).

- `sources` is required and non-empty and must belong to the same slot, otherwise `invalid_argument` (`cross_slot`). When one sentence involves two slots, it is two sources, previewed separately and deleted separately.
- When `sources` contains an ID that does not exist, is already pending deletion within the grace period, or has been physically erased: `not_found`, with `sources[]` giving the state of each.
- What the result must state is defined by "Deletion · What the preview and the receipt must state" in the data model. **Writes that were originally not in effect and will take effect because of the deletion are listed separately** (`now_effective`); writes whose conflict will disappear but which are still high-impact and will turn to awaiting confirmation are listed in another place (`now_awaiting`). `not_deleted` states truthfully what will not be deleted: external files, text in schemas, retained metadata, the names of connections (`connection_names`: they are not derived from source data and are not within the scope of the cascade), and the task identifiers and explicit idempotency keys self-reported by operations that have no source data at all (`operation_labels`).
- **Source data that is retained after the deletion but no longer supports any data** (`orphaned_sources`): lists only the IDs of source data that, after this deletion, go from "supporting data" to "supporting nothing", typically another evidence segment of the same write, or a later retelling of the same matter. They are not within the scope of this deletion and are retained as usual; they are listed for the caller to decide whether to delete them together.
- **Rows that take the values to be changed as their premise** (`premise_affected`, the forecast): the deletion will make them carry `premise_changed` (reason `deleted`), and they themselves are not deleted. Deletion does not propagate along premises: the value source of a dependent row is its own evidence.
- **External key**: when an affected row has an external key, `warnings` gives `external_key_resync`: after physical erasure saveslot does not remember this key, and when a connector synchronizes the same record again it appears again as a new row; to forget it entirely, first delete it in the source system, or make the connector stop synchronizing it. When all the sources of a row are deleted, later synchronization will not fill back the records that were skipped at that time (skipped ops do not enter the log, and the preview does not list them one by one). One deletion can freeze several keys at the same time; the same key can also be frozen by several deletions at the same time, and only after all of them are cancelled or executed is the holder recomputed from the state after deletion; cancelling one of them does not unfreeze. A row that is retained but will lose its external key carries `external_key_removed` in the per-row result. The per-row results of the preview and of the receipt carry `external_key_frozen` on rows whose key will be frozen (the key value is not listed); when the same key is also frozen by several other deletions not yet executed, `also_by` is attached (the deletion IDs of those): after this one is cancelled it is still frozen, and it has to wait until they are cancelled or executed. A key removed by this deletion within the grace period still holds its place: an op by external key that hits it is skipped (`pending_deletion`).
- The per-row results list the rows whose value, or whose contribution to the value, differs from before the deletion: for a row whose value is unchanged and that is listed only because the giver, the judgement result, or the block that gave them was given again, `result` is `sources_changed` (for example: a value given by the deleted write is also given by another corroboration; a revocation that gave a hole is resolved again because of the deletion, and the hole is still where it was).
- Intervals on a state table that go from having a value to having none are listed separately in `gaps_opened` of the per-row result, with a reason: `required_field_removed` means a required field has no contribution still standing there; `revocation_extended` means a revocation that carried only a start was extended by the deletion and swallowed a later write that did not carry all the required fields; an interval is listed only once, and when it falls within a revocation the latter is taken, otherwise the former ("What the preview and the receipt must state" in the data model). It is computed on the spot in the preview and the receipt and does not enter events. On event tables and timeless tables, deleting a whole row is expressed by `result` and this is not used.
- The `reverted_to` of `fields_reverted` in the per-row result states whose value each field goes back to: exactly one of `from_seq` (back to the value of that write) and `schema_const: {sv}` (back to the backfill value of the constant `backfill` at the schema switch of that version, with no write to point to).
- **Only `rows[]` is paged**; the other lists each have at most 50 entries, with the total given in addition. `totals` is always the full amount; `dc_` is bound to the whole preview and does not change with paging.
- **The deletion ID is pre-allocated at preview time** and bound in `dc_`. Recognizing that "this `dc_` has already been executed" relies on looking up the deletion table by this deletion ID, not on a content hash.
- **When a preview expires**: after the preview, a write, a resolution or a deletion changed any of the rows / entities, items or source data the preview lists ("What the preview and the receipt must state" in the data model).
- The order of judgement when producing the preview again by `{confirm}`: this `dc_` has already been executed → `handle_expired` (`executed`, with the deletion ID); the signature has expired or the restore count does not match → `handle_expired`; a write later than the preview within the scope of impact → `preview_outdated` (with the new preview).

### `pending`

- Give `id` to see the details; without it, a list is given. `status` defaults to `open`, ordered by pending duration descending. Only items of visible slots are listed; a `slot` filter pointing to a slot that does not exist or is not visible reports `not_found` (`slot`), and an item ID that is not visible reports `not_found`.
- **The details of an item give all the content of the item**: the target, the current value, the proposal or candidates, the impact, and the available decisions. The impact is within the scope to which the item version is bound ("Pending items" in the data model). Viewing the details counts as having read that item version.
- **A closed item can always be looked up by ID**: a resolved one gives `resolution`, and a superseded one gives `superseded`. When the row that a `flagged` item matched is revoked or changed, the reason for superseding (or refreshing) is `matched_changed`: it does not look at whether the writer read the item. A `deletion` item can still be looked up with `states[]` after it expires: after the execution at expiry (physical erasure) it is resolved, and `resolution` is the executed branch (`executed: true`, the operation number and moment of the tombstone, the reason), it has no decision, and `actor` is always `system` and is not given; when the grace period has passed and physical erasure has not happened yet, it is still `open`, `decisions` is empty, and it carries `overdue`; during this period, calls that involve this slot give `deletion_overdue` in `notices` (with the deletion ID), until the tombstone is recorded. When an affected row once had an external key, the details of the `deletion` item after it closes at expiry give `external_key_resync` once more in `warnings`: the first synchronization after that will write the record back, and no other prompt will exist at that point.
- After a `schema_change` item is confirmed, while the migration is in progress or when it fails, the details carry `migration` (the target version, the state, the progress): the caller finds out by item ID how far the migration has gone.

### `resolve`

**The order of judgement** ("Pending items" in the data model):

1. The item does not exist → `not_found`.
2. The item is already closed: resolved with the same decision → return the original result, `replayed: true`; resolved with a different decision, or superseded → `item_closed` (with the existing result, or the reason for superseding). So resending the same decision with an old `item_ver` after a long time is also returned as a replay.
3. The item is neither `deletion` nor `schema_change`, and its target is affected by a deletion that is still pending ("Deletion · Cancelling a deletion and the grace period" in the data model) → `invalid_argument` (`pending_deletion_target`), with the relevant deletions and the latest expiry moment; the bound content is not checked, and no event is produced.
4. Check the bound content by section 6; a mismatch → `confirmation_mismatch`, with `current`: the details of the item at this moment (including the new `item_ver`), the same as what viewing the details at the same moment would give, and it counts as a read (section 2).
5. `confirm` of a `schema_change`: judged again within the same transaction. For any change in the draft compiled as "never written" (structural changes opened only for tables never written, and the items that belong to `restructure_unused`, see the `schema_draft` section), if the table it is on has been written by the time of confirmation, `draft_outdated` (`table_written`) is always reported; when the draft carries `migrate` (`migrate` comes after the first version; in the first version a draft carrying it reports `not_in_this_version`, see the `schema_draft` section), the new writes after the trial run (writes carrying the old `sv` during the migration) are evaluated again, and a failure reports `draft_outdated` (`migrate_failed`); when the draft renames the slot (`rename_slot`) and the new name is by then used by another slot (regardless of ASCII case), `draft_outdated` (`name_taken`, "Judged again at confirmation" in the data model) is reported; when the draft tightens a constraint without giving `backfill`, and in the meantime the old version wrote values that violate the new constraint, `draft_outdated` (`backfill_required`, with details the same as the `backfill_required` of `schema_draft`) is reported. In all four cases no event is produced and the item stays open; the caller `reject`s this draft, or submits a new draft to supersede it (with `backfill` in the case of `backfill_required`). `base_version` is no longer checked: the version a draft awaiting confirmation is based on is the current version at confirmation, since any switch in the meantime comes from a new draft, and the new draft, when submitted, first superseded it (its item closes with it, and confirming it again reports `item_closed`).

- **The writes it triggers also go through the check of `ref` targets** ("When a `ref` field is written" in the data model): when adopting a candidate, going back to the merge base, or confirming an awaiting-confirmation write (including confirming an undo), the `ref` values that are about to take effect are checked against the state at handling time, and a failure reports `validation_failed` (`ref_not_found` / `ref_wrong_table`), with details that carry no `op` and carry `table` and `field`; no event is produced and the item stays open.
- `take_candidate` must give `candidate` when the item has several candidates (the `index` of the candidate in the details; an index is not reused during the life of the item), otherwise `invalid_argument` (`candidate_required`, with the candidates `candidate_choices`: the index of each candidate, the operation number of the write it belongs to, and the writer).
- `evidence` and `note`: `resolve` has no request-level evidence; the evidence is only `evidence` and `evidence_by_field`, and `evidence_refs` is not accepted; the indexes of `evidence_by_field` count the `evidence` array of this call, and when handling triggers a write, they point out by field the evidence of that write (not accepted in the first version, reporting `not_in_this_version`: in the first version the items of the writes triggered by every decision are carried over, and pointing out evidence by field cannot change their provenance; it is useful only when the `set` of `migration_diff` carries a value). Each `evidence` segment is stored as one source; when a `note` is carried, or the handling triggers a write and no evidence is carried, the resolve request itself (including the `note`) is stored as one more `api_call`. **Decisions that trigger no write (`keep_effective`, `reject`, `keep`, confirming and rejecting a schema) are the same**, so a `note` always has somewhere to land and can always be cleared by privacy deletion. They are only operation sources; the `resolution.note` in the item details is echoed from this source, and is no longer echoed after the source is deleted. A resolution that carries neither evidence nor `note` and triggers no write produces no source data.
- Result: when a write was triggered, `write` is carried (the same shape as the corresponding part of a write receipt, including `premise_affected`); a `schema_change` carries `schema`: for `confirm` it is switched and the new `sv` (or the migration state), and for `reject` it is `switched: false`; the `cancel` of a `deletion` carries `cancelled` (the new `ver` of the affected rows, the writes returned to their original state, the items restored, the items kept as "superseded", the writes not returned because they have been taken as the baseline, and the change of premises `premise_affected`).
- **Candidates judged again at cancel time** (`cancelled.rejudged[]`, later): this does not occur in the first version: items cannot be resolved on affected rows within the grace period, and a candidate removed by the deletion goes back, when the deletion is cancelled, to the original item that is still open, or closes with the original item if that is closed. It occurs only when resolving items on affected rows is also allowed within the grace period: a deletion once removed a candidate from a conflict item, and that item was resolved within the grace period. After the cancel the candidate comes back, the resolution of the original item is not touched, and the candidate is judged again against the current value at the time of the cancel, one entry per candidate: if some part still differs from the current value → `reopened`, and another conflict item is opened for it (cause `restored_candidate`, with the `related_item` of the details pointing back to the original item; the `id` and `item_ver` of the new item are attached); if all are the same as the current value and some of them pointed to evidence → `corroborated`, and it becomes a corroboration; if all are the same and none pointed to evidence → `dropped`, and it is no longer a change. The latter two have no item to handle, so they must be listed here for the caller to know that write finally did not take effect.
- **The confirmation record** also records `via: "call" | "elicitation"` (`elicitation` later): it is filled in by the surface and cannot be passed by the caller, and serves only as a record.
### `schema_draft`

Not provided in 0.1.0 yet: migrations that require rebuilding the physical table (adding a field to a table that has been written to, dropping a field, tightening a constraint, changing precision, changing the unit) report `not_in_this_version`, and migration progress (`migration`, `migration_progress`) is likewise only in the design. These parts of this section are the design ([`07-scope-v1.md`](07-scope-v1.md), section 7); for the state of 0.1.0 see "Changes not accepted (the first version and 0.1.0)".

#### What it returns

- The parameter is the schema document (data-model "Schema document format"); when a slot is created, `base_version: null`. A newly submitted draft supersedes the slot's earlier draft that is not yet confirmed (the `schema_change` item of the earlier draft is marked superseded, with reason `draft_replaced`).
- **One call returns the compile result and the impact preview together**: the document with IDs and inferred results filled in; each change (change code `change`, category, whether it is compatible with writes made against the old version, whether it is destructive, whether it can take effect automatically); and the impact (number of affected rows, changes to derived values, callers that use the old name, and the trial-run results of `migrate` / `backfill`). **0.1.0 does not compute consumers and always treats a slot as in use (goes to awaiting confirmation)**: the receipt for a change to an existing slot does not carry `consumers` (an empty list would amount to the conclusion "no consumers"), and "nobody is using it" is likewise always treated as in use. So a rename (`rename_unused`) always needs confirmation, and the `restructure_unused` category does not take effect automatically either; all these changes go to awaiting confirmation.
- A draft with no change at all compared with the current version reports `invalid_argument` (`no_change`, with `param` being `document`), produces no event and uses no version number. The judgement is made only against the current version: a draft whose content is identical to the one awaiting confirmation (outside the idempotency window, or with a different `task`) supersedes it as usual and gets a new version number.
- Order of errors when changing an existing slot: slot not found or outside the visible range → the form of `base_version` → draft outdated (`draft_outdated`, `base_version`) → migration in progress (`draft_outdated`, `migrating`, with `current_sv` and `migration`) → the rest.

  | `outcome` | When |
  |---|---|
  | `applied` | A new slot (takes effect once it compiles, `sv: 1`); or all changes can take effect automatically under the slot policy. Returns the new `sv`; carries `migration` when a background build is needed |
  | `pending` | Generates a `schema_change` item, with `id` and `item_ver`; this receipt already gives all of its content, so it counts as a read |

- **A draft takes effect automatically if and only if the category of each of its changes is in the slot policy's `auto_apply`** (the mapping table in types 5.3); otherwise the whole draft goes to awaiting confirmation. The default policy has all eight categories on. A slot's policy is the full text written when the slot was created and does not change with the kernel's default policy: for a slot whose policy has no `restructure_unused`, this category of change means "needs confirmation". The first version also has no operation to change the policy.

#### Tables never written

- On a **table never written** (the log has no base write targeting this table; a table that was written to but whose rows are all revoked or whose content is all deleted does not count), the following changes are allowed: changing the table's time type (`change_time_type`), adding, removing or changing `entity_key` (`change_entity_key`), changing `granularity` (`change_granularity`), changing `base` to `derived` (`change_table_kind`; the opposite direction is still not supported), converting between a field and `ref` or changing the target of a `ref` (`change_ref`), adding / removing / replacing an external key (`add_external_key` / `drop_external_key` / `change_external_key`). The table ID and field IDs do not change.
  - When no connection other than the submitter has read or written this table by name in the last 30 days, these changes, together with `drop_field`, `change_type`, `change_dimension`, `change_unit`, `change_precision`, `tighten_constraint`, `add_required_field` and `change_time_field` on the same table, all fall under `restructure_unused` and take effect automatically: there is no value to lose, `class` is recorded as `metadata`, `destructive` is `false`, and `migrate` need not be given. Adding a required field or changing optional to required still requires a constant-form `backfill`. When someone else has read or written it, confirmation is needed, and `consumers` of the impact lists them. 0.1.0 does not compute consumers, see "What it returns".
  - Derivation rules that depend on this table are recompiled against the new definition in the same compilation; a rule whose output has not changed is not listed as a separate change.
  - After any change that took effect through `restructure_unused`, every write to this table that carries the old `sv` is rejected: `schema_incompatible`, with `changed_fields` giving one item `{field: "*", change: <change code>}`, where `"*"` means the whole table. After a table is dropped (`drop_table`), a write to it that carries the `sv` from before the drop is rejected in the same way, with `change` being `drop_table`.
  - If the table is written to while the draft awaits confirmation, none of the changes in the draft that were compiled as "never written" hold any more, and confirmation reports `draft_outdated` (`table_written`, see `resolve`) for all of them.

#### Changes not accepted (the first version and 0.1.0)

- **Changes not provided in 0.1.0 yet**: migrations that require rebuilding the physical table. For changes such as adding a field to a table that has been written to, dropping a field, tightening a constraint, changing precision, or changing the unit within the same dimension, the draft can be submitted and previewed; in 0.1.0 a draft that would take effect automatically reports `not_in_this_version` (with `reason` being `table_written`) at submission, and a draft that needs confirmation reports `not_in_this_version` at confirmation, and the draft stays. When the table has never been written, these changes take effect as usual (a new table is empty and needs no migration). For `migrate` and the expression form of `backfill`, see the last item below.
- **Keys or changes the first version does not support**: `reextract`, `extends`, `compatibility`, `derived` changed to `base`; on a table that has been written to: changing the time type, adding, removing or changing `entity_key`, changing `granularity`, changing `base` to `derived`, converting between a field and `ref` and changing the target, replacing the set of external keys (`change_external_key`), changing the type of an external key field or tightening its constraint. On a table that has been written to, an external key can still be added (the key fields must be fields added by the same draft) or removed, and both need confirmation. When one appears in a draft, the whole draft reports `not_in_this_version`, with `param` pointing to that key, and no event is produced; where it is unsupported because the table has been written to, `reason` is `table_written`.
- **Derivation rules the first version does not accept when a slot is created**: those that use `saveslot_date`, and those whose group key is `decimal` / `quantity` and whose upper bound of decimal places may exceed the inferred precision (for the algorithm see [`03-data-model/11-restricted-sql.md`](03-data-model/11-restricted-sql.md), "Decimal group keys"). All report `not_in_this_version`, with `param` pointing to the rule of that derived table (`tables/<i>/rule`), and no event is produced. A derivation rule that reads a derived table computed at read time likewise reports `not_in_this_version` in the first version, with `param` being `tables/<i>/rule/sql`.
- `migrate` on a field and the expression form of `backfill` come after the first version: in the first version a draft that carries them reports `not_in_this_version` on any table (`param` points to that key), and the constant form of `backfill` works as usual. By design they can only refer to the old value of this field and to constants, are evaluated only at positions that have a value, and pass an empty value through unchanged.

#### The form of the document and its validation

- **Creating a new slot**: the requirements on the credential's slot range and scope are in section 12 (a credential limited to a slot range reports `insufficient_scope`, `required_scope: "all_slots"`).
- A document of the wrong form reports `invalid_argument`, and `param` is the position in the document (written like `path` in the details, for example `tables/0/fields/2/min`): the document is not an object, the JSON type of a key is wrong, an unknown key appears, a string is not well-formed Unicode (including lone surrogates, which cannot be written to the log), an enum value does not meet the content rules (see data-model "Field types and value ranges") (`malformed`); a required key is missing (`missing`). Unknown keys are not ignored: if a misspelled `requried` were ignored, the field would quietly become optional. When `param` falls on the rule of a derived table (`tables/<i>/rule` and the keys under it, or a `tables/<i>/sql` written on the table instead of in the rule), `example` gives a complete rule `{sql, time_dependency}`; when it falls on `time_dependency`, `allowed_values` is also given, which are the values the first version accepts when creating a slot (`none`, `bucketed`, `now`). `min` / `max` may be written as a decimal string (without an exponent) or as a JSON number, but a number is accepted only as an integer within ±(2^53 − 1); a bound with a fractional part is always written as a string: once a JSON number is parsed, it can no longer be told which decimal number the caller wrote.
- A compile failure reports `validation_failed` (`schema`), and `details[]` points to the position in the document item by item. `base_version` not being the current version, or a migration in progress, reports `draft_outdated` (with `current_sv`): **an outdated draft is always reported first**, right after the form of `base_version` is checked, and whatever else is wrong with the draft is not looked at: the caller must first draft again against the current version. An existing field that was not matched and not listed for removal reports `field_unmatched`.
- `drop_tables` and a table's `drop_fields` accept names as well as IDs; when a string is the name of one item and the ID of another, it is taken as the name.
- Tables and fields are matched by `id` first; those without an `id` are then matched by name among those not claimed by an `id`. A newly added table or field that uses an old name changed by another item in the same draft (A is renamed to B, and a new one named A is added at the same time) reports `validation_failed` (`name_renamed_away`); the name is not guessed to mean either one.
- For a conflict between two items (duplicate names, a name equal to an alias), when one side is listed in the draft, the error is reported on the listed side: a table not listed in the draft is not in the document, and an error reported there would leave the caller nowhere to change it. Two tables with the same name report `duplicate_name`. When one table's name equals another table's alias: if the table that holds the alias is listed in the draft, the error is reported on that alias, `alias_invalid` (`reason: name`, same as the rule in "Aliases"); if it is not listed, there is no alias position to point to, so the error is reported on the `name` of the listed side, `duplicate_name`. Findings on references by that name that follow from a duplicate name (the target of a `ref`) are not reported separately.

#### Compile detail codes

- Four compile detail codes concern data:
  - `still_referenced`: a table or field to be dropped is still depended on (a table pointed to by a `ref`; a field used by a derivation rule, `entity_key`, `external_key`, `time.field`, `duplicate_keys` or `together`). `referenced_by` lists the dependents: when the draft lists a dependent, its position in the document is given (such as `tables/0/fields/8`); when it does not, the name is given (`table.field`, the table name for a derived table). The judgement is made on the result after the change: dropping or changing the dependent in the same draft is enough.
  - `backfill_const_required`: adding a required field, or changing optional to required, always requires a constant-form `backfill`, regardless of whether the table has rows at that time. The expression form is evaluated only at positions that have a value, and a position with no old value can only be given a value by a constant.
  - `backfill_required`: when `min` / `max` is tightened or an enum value is removed, existing rows violate the new constraint and no `backfill` is given; carries the number of violating rows and samples (`rows`, `samples`: at most 5 samples, giving only positions, rows or entities, not values; a state table counts by entity). How it divides the work with `backfill_const_required`: changing to required (adding a required field, changing optional to required) does not look at whether there are rows, it looks at whether there is a constant-form `backfill`; the other tightenings look at whether any row violates.
  - `backfill_both_forms`: both the constant form and the expression form of `backfill` are given; only one may be given (when a range is tightened and the field is also made required, give only the constant).
- When the other compile detail codes appear:

  | Detail code | When |
  |---|---|
  | `description_missing` | A table, field or derived field has no description (`description` is required), or it is written as an empty string or only whitespace |
  | `unknown_type` | A field's `type` is not one of the `FieldType` of types 4.2. The detail carries `allowed_values`: all `FieldType` |
  | `entity_key_not_required` | A field listed in `entity_key` is not a required field |
  | `unknown_reference` | Something the document points to by name does not exist: a field name in `time.field`, `entity_key`, `external_key`, `together` or `duplicate_keys`, or a table name in `ref.table` |
  | `key_not_applicable` | A key or its value is used on a type or table it does not apply to: `min` / `max` not on `integer`, `decimal`, `quantity`; `values` not on `enum`; `unit` not on `quantity`; `scale` / `rounding` not on `decimal`, `quantity`; `ref` not on a `ref` field; `entity_key` not on a state table; `duplicate_keys` on a state table; the field `time.field` points to is not a required `date` or `zoned_datetime`; `ref.target` is `row` and the target is a state table, or is `entity` and the target is not a state table; `ref.table` points to a derived table (`ref` only goes between base tables); `time`, `entity_key`, `together` or `duplicate_keys` written on a derived table, or `rule` written on a base table; `required`, `min`, `max`, `values` or `ref` written on a derived field, a `type` that is not `decimal` written on it, or `unit` written on a `decimal` field. For the two cases of a wrong type, the detail carries `allowed_values`: for the field `time.field` points to, `["date", "zoned_datetime"]`; for the `type` of a derived field, `["decimal"]`; when the field `time.field` points to is not required, the detail carries `reason: "not_required"`; when both type and required are wrong, two entries are reported |
  | `out_of_bounds` | A value is out of bounds: `min` is greater than `max`; `min` / `max` exceeds the range of the type (`integer` is a 64-bit signed integer, and `decimal` and `quantity` have at most 18 digits in the integer part); `scale` is not in 0–12; a table has no fields; a slot has no base table (the detail carries `min: "1"`); a tenant's slots, a slot's tables (base and derived tables together), or a table's fields exceed the limit (the detail carries `max`; the limit is a temporary value, see open-questions "Numeric values and details of the interfaces"); an enum has no values or more than 200, an enum value is empty or longer than 64 characters; a description is longer than 500 characters; `entity_key` is empty, `external_key` is not 1–4 fields, a group of `together` has fewer than two fields, a group of `duplicate_keys` is empty. Length is counted in code points. `min` / `max` in the detail are the bounds the value at `path` should fall within, as many as apply, written as decimal strings: for a description `max: "500"`; for the number of enum values `min: "1"`, `max: "200"`, and for a single value `min: "1"`, `max: "64"`; for `scale`, `min: "0"`, `max: "12"`; for `entity_key`, `min: "1"`; for `external_key`, `min: "1"`, `max: "4"`; for a group of `together`, `min: "2"`; for a group of `duplicate_keys`, `min: "1"`; when `min` / `max` exceeds the range of the type, both ends of the type are given (`integer` is ±64 bit, `decimal` and `quantity` are ±`999999999999999999.999999999999`); when `min` is greater than `max`, it is reported on `…/max`, carrying `min` (the `min` that was given: `max` must be at least that) |
  | `duplicate_entry` | A repeated item in the same list: a repeated enum value (case sensitive); the same field appearing twice in one group of `entity_key`, `external_key`, `together` or `duplicate_keys`; a field in two `together` groups. A collision of names is `duplicate_name` (for a name equal to another item's alias, see above) |
  | `timezone_unknown` | The slot's `timezone` is not a recognized time zone name: it is not `UTC` or of the form "region/place" (such as an offset `+08:00`, or a short name without `/` such as `CST`), or it is not in the time zone database in use |

- Compile detail codes for external keys: declared on a state table or a derived table (`external_key_table_kind`); the type of a key field is not `text`, `enum` or `integer` (`external_key_field_type`); an existing field on a table that has been written to is declared as a key (`external_key_existing_field`); a key field appears in `together` (`external_key_in_together`). When only one key field is declared, `warnings` carries `single_field_external_key`: when several source systems write this table, IDs may collide.
- When the group key of a derived table's rule comes from a free-text field (`text`, not `enum`), `warnings` carries `group_key_free_text`: the group key is the user's original text, and it is cleared together with the group on deletion (data-model "The identity of a derived row").
- Aliases that break the rules (more than 8, longer than 64 characters, empty after normalization, containing a newline or control character, with whitespace at either end, repeated within the same object, or equal to a name that still resolves in the same scope): `validation_failed`, detail code `alias_invalid`, `path` pointing to that item, and `reason` stating which rule is violated (`count`, `length`, `empty`, `control`, `surrounding_space`, `repeat`, `name`; when one item violates several, the first in this order is taken; `count` and `length` carry `max`).

### `delete`

Not provided in 0.1.0 yet: `delete` and canceling a deletion (`resolve` with `deletion` · `cancel`) report `not_in_this_version`; this section is the design ([`07-scope-v1.md`](07-scope-v1.md), section 7).

- The only parameter is `confirm` (the `dc_` returned by `deletion_preview`). It only executes and does not preview.
- **Order of judgement**: this `dc_` has already been executed → returns the original result, `replayed: true`; the signature has expired or the restore count does not match → `handle_expired`; there is a write within the affected scope later than the preview → `preview_outdated` (with the new preview and a new `dc_`).
- Result = the preview content recomputed from the state at confirmation, plus the items the receipt adds. Every list in the preview is also in the receipt, with the same limits and totals as the preview: the totals; the per-row results (with the new `ver` as well); writes that took effect because of the deletion, writes turned into awaiting confirmation (with the items generated), and items superseded; the group keys cleared (`group_keys_cleared`); rows that still refer to deleted rows (`dangling_refs`); content that will not be deleted; source data that no longer supports any data after the deletion (`orphaned_sources`); changes to premises (`premise_affected`); deferred execution in local mode (`local_deferred`). Also given: the deletion ID (the same object as the `deletion` item in the grace period), the expiry time, and how to cancel; the affected derived values; the state and time of each; the metadata kept after the deletion. When an affected row has an external key, `external_key_resync` is given in the same way. It does not claim "deleted from all backups".
- Canceling goes through `resolve` (a `deletion` item, `cancel`). Revoking a row is not a deletion; use `revoke` of `write`.

### Extraction jobs: `extract_claim` / `extract_submit` (later)

After the first version: this whole section is not in the first version, and calling it reports `not_in_this_version`.

For the rules (source clusters, translations must be given in full, re-extraction after a deletion, what goes into the diff list), see data-model "Extraction jobs".

Parameters of `extract_claim`: `job` (optional; when absent, claims the earliest job this connection has permission for), `max_items` (optional; the server also trims by a byte budget), `schema_digest` (optional: the digest obtained at the last claim). The same connection + `task` with an unexpired lease gets the original lease back. When there is no work item to claim, it does not report an error and returns `items: []` with `reason`: `none_available` / `job_ended`.

```json
{
  "lease": "ls_…", "expires_in": 900,
  "job": { "id": "jb_…", "kind": "migration_reextract", "slot": "health", "target_version": 3, "done": 120, "total": 2300 },
  "schema_digest": "sd_…",
  "target_schema": { "tables": [{ "name": "runs", "fields": [
    { "name": "effort", "type": "enum", "values": ["easy", "moderate", "hard"], "description": "Subjective effort" },
    { "name": "soreness", "type": "text", "description": "Sore area and degree" } ] }] },
  "instructions": "Split effort and soreness out of the original feeling and the source text; leave blank if the text does not mention it",
  "items": [{
    "item": "it_1", "table": "runs", "row": "r_01JC…",
    "writes": [
      { "op": "w_41", "intent": "insert", "source": "Ran 15 km today, legs a bit sore, felt very tired",
        "old": { "feeling": "Legs a bit sore, very tired" } }
    ]
  }]
}
```

- The first claim returns `target_schema` and `instructions` in full; afterwards, when `schema_digest` is given and the content has not changed, these two are omitted.
- Text values in `instructions`, `source` and `old` are `UntrustedText`; when `source` is `null`, `reason: "evidence_deleted"` is attached.

Parameters of `extract_submit`:

```json
{
  "lease": "ls_…", "model": "claude-…",
  "results": [
    { "item": "it_1", "writes": [{ "op": "w_41", "set": { "effort": "hard", "soreness": "Legs a bit sore" } }] },
    { "item": "it_2", "skip": { "reason": "no_content" } }
  ]
}
```

- `model`: optional, the self-reported model name, recorded in the log for reference only.
- Each work item goes through the deterministic checks of a write; a failed one is given its reason item by item and can be submitted again within the lease; a partial submission is allowed, and it is idempotent by `(lease, item)`. The only skip reason codes are `no_content` / `ambiguous`.
- Result: the number of work items accepted / failed validation / skipped, the job's progress, and whether there are still work items to claim.
- After the migration has been abandoned or has switched, submitting with the original lease reports `lease_expired`, with `reason`.

## 11. Domain errors

For the shape of the error object, the fields each error code carries, and which operations return which error codes, see types section 9.

- `code` and the structured fields it carries are defined by the contract; the human-readable explanation and the next step are rendered by the surface from these fields.
- **A write succeeds or fails as a whole**: when any op violates the deterministic checks, the whole request does not take effect and only an error is returned; `details[]` points to the op and field item by item.
- **A rejected write produces no event and is not deduplicated** (section 14).
- **A conflict is not an error**: when `ver` does not match and the change is to the same conflict unit, the write is recorded as a candidate, and the receipt has `status: pending`.
- **Nonexistent and invisible report the same error**: for this credential, something outside the visible range is exactly the same as something that does not exist (the visible range is in section 12). It does not appear in the catalog; `notices` is computed only over the visible range; name resolution is done only within the visible range (section 1); the judgement of conflicts, same values, high impact and suspected duplicates does not change with the range.
  - Referenced by name (table name, field name): the error that operation already reports for a name that does not exist: `query`, `history`, `write` and `catalog` report `unknown_table` / `unknown_field`, and `sql` reports `sql_rejected` (`unknown_name`).
  - Referenced by ID (row, entity, item, source, draft, a read): `not_found`, the same as when the ID does not exist. The same holds for row IDs written in parameters: the value of a `ref` field pointing to an invisible row reports `validation_failed` (`ref_not_found`), and a premise pointing to an invisible row reports `not_found`; `ref_wrong_table` and `cross_slot` are reported only when the target is visible, otherwise "this ID exists elsewhere" would leak out through the error code.
  - Parameters that specify a slot by name or ID (`slot` of `catalog`, the `slot` filter of `sources` and `pending`, `policy.get`, `slots` of `connections.issue`): `not_found` (`slot`).
- **`nearest`** (the closest names attached to `unknown_table` / `unknown_field`) is taken only from visible names. An object whose alias, folded by `keymatch@1` (data-model "Similar keys"), equals the name in the request, has its **name** placed first; the rest are ordered by edit distance to the name in the request after `keymatch@1` folding, from small to large, with ties ordered by the `C` collation of the name (by code point); at most 3 are given. What is returned is names, not alias text, so no untrusted text appears in the error. For a table name without a slot, tables with the same name in several slots count as one name, and their aliases are compared together. The exception is the `table` filter of `reads.list`: it recognizes the table names that appear in read records, and `nearest` is given only from those table names, without borrowing aliases.

| `code` | When |
|---|---|

# Part two · contract (the outer wrapping)

## 12. Callers: credentials and scope

**Two kinds of credentials** (the first version is a single node and has no node credential):

| Credential | Held by | What it can do |
|---|---|---|
| User session | A person: generated locally by `saveslot init`, and in server mode logged in through the CLI (the App is later) | Everything, including issuing and revoking connections, audit, export |
| Connection | An agent or a script (local: a token written into the MCP configuration; remote: one OAuth authorization, or a static token issued by a user session, for scripts that cannot do OAuth) | According to scope and slot range |

- The actor is always derived from the credential and cannot be filled in in the request. Confirmation and the authenticity of data are delegated to the caller, see architecture §3.
- **scope** (chosen when a connection is issued):

  | scope | Allows |
  |---|---|
  | `saveslot.read` | All read operations (including `deletion_preview`, `policy.get`) |
  | `saveslot.write` | `write`; the combinations of `resolve` that need `saveslot.write` |
  | `saveslot.schema` | `schema_draft`; the handling of `schema_change` in `resolve` |
  | `saveslot.delete` | `delete`; `cancel` of `deletion` in `resolve` |

- **Default values of scope**:
  - When `connections.issue` (including `saveslot setup` and `saveslot connect` on the local machine) is given no scope, the default is `saveslot.read saveslot.write saveslot.schema`: it can read and write and can create slots, but cannot delete.
  - When an OAuth authorization request requests no scope, `saveslot.read saveslot.write` is given; `saveslot.schema` can be added on the authorization page.
  - `saveslot.delete` is always added explicitly.

- **Every connection must have `saveslot.read`**: a write has to read first (`ver`, `sv`, the item detail), and a connection without read permission cannot get through any flow. Issuing without `saveslot.read` reports `invalid_argument` (`missing_read_scope`). A read-only connection is one that has only `saveslot.read`.
- **Authorization = scope × slot range**: the slot range is "all" or "a list of slots", fixed at issue (`slots` of `connections.issue`; when not given, all). The same set of scopes applies equally to every slot in the range; for "A writable, B read-only", issue two connections. A slot is the smallest unit of a credential's authorization range; table-level and field-level data permissions are later (open-questions "Table-level and field-level data permissions"). A user session's range is always all.
  - **A slot out of range is exactly the same as one that does not exist for this credential**: for how this shows up in each place and the judgement rules, see "Nonexistent and invisible report the same error" in section 11.
  - **When the range is "all", it includes slots created later**; when the range is a list, slots that others create later are not included.
  - **A credential with a limited range cannot create a slot**: it reports `insufficient_scope` (`required_scope: "all_slots"`), whether or not the slot name in the draft duplicates the name of some invisible slot. The slot created would not be in its list, and it could not see it itself; have a user session or a connection whose range is "all" create it first, then issue a credential limited to it. When the credential also lacks `saveslot.schema`, the missing scope is reported first: the action is checked first, then the range.
  - The authority for the range is in the log (the principal registration event), and the service layer builds the call context's visible range from it.
- **In the first version, neither scope nor slot range can be changed after issue**: to change them, revoke and issue again. A step-up of a remote authorization (reauthorizing after exceeding permissions) yields a new connection, and the original one does not change. The only range of uniqueness of an external key is the table, not including the connection, so continuing the sync from another connection does not add duplicates.
- **Permission to declare the "external authority" level** (later): when `external_authority` is opened in the future, it is a permission that a user session grants a connection at issue, recorded in the principal registration event together with the scope and slot range (section 3).
- **Credential failure**: a missing, invalid or revoked token, or an expired session, is always `unauthenticated`, and `reason` tells the four cases apart (section 16). A revocation takes effect immediately.
- **Account deactivation** (server mode): while the tenant owner's account is deactivated, all credentials of this tenant (user sessions and connections) report `unauthenticated` (`account_disabled`) at authentication, and the tenant is not opened; no revocation is written to the log, and the credentials are not deleted, so they work as usual after the account is reactivated. The account state is given by the identity provider (architecture §12); when it does not recognize the account, the credential is handled as invalid (`invalid`).
- **What is left after a revocation**: a revocation only causes this credential's later requests to be rejected; it triggers no deletion and does not change existing data. The `actor` of the data it wrote does not change; `Actor.name` in results is still its name, `Actor.state` is `revoked`, and in text rendering the name is followed by the mark "revoked". Its name **is still taken**: a connection with the same name cannot be issued again under the same user, so that in history one name refers to only one principal. Items it started that are not yet handled (conflicts, awaiting confirmation, flagged, schema changes, deletions in the grace period) are kept as usual and handled by a user session or another connection with the corresponding scope; a deletion in the grace period still executes at expiry. Its reads in the read record still take part in impact queries as usual.
- **Disabled principals**: importing into an empty tenant (section 17) sets all the user principals and connections registered before the import that are still valid to disabled (except `system`; already revoked ones stay revoked). A disabled principal cannot authenticate and cannot be restored in the first version; the data it wrote and the items it started that are not yet handled are exactly the same as after a revocation; `Actor.state` is `disabled`, in text rendering the name is followed by the mark "disabled", and the name is likewise still taken. A connection in `connections.list` also carries `state` (`revoked` / `disabled`).

## 13. Tasks, paging and accompanying information

- **`task`**: except for administrative operations, every operation has an optional task identifier, self-reported, used to correlate the reads and writes of the same task; it takes part in the fallback (section 2) and in the server-side request key (section 14).
- **Paging**: `limit` defaults to 20 with an upper limit of 200; `cursor` is an opaque handle (section 15). The result gives `total` and `next_cursor`. When the surface cuts off early according to its own result budget, `truncated` is also given, and the cut-off point is the page boundary: `next_cursor` starts from the first row not shown.
- **`detail`**: `concise` (default) / `detailed` (each row also gives the operation number and recorded time of the latest change, and for each field its ID, source level and literal match; a `ref` field carries a summary of the referenced row; all premise declarations currently in effect on this row, including unchanged ones, from which the reader sees "what this row stands on"). The literal match of a field is aggregated over the segments in the value sources it still has: `hit` if any segment hits, otherwise `miss` if any segment misses, otherwise `na` (none applies or there is no segment, for example when the value comes from a schema constant or is empty); the source level is given only with `hit`, and is the highest declared level among the segments that hit. The summary of a referenced row is all of its field values visible at the same read position, in the same shape as when it is read directly; a state entity takes the value at the moment of the read (the evaluation time for `query`, that recorded moment for `as_of`); it is not given when the target table is not visible, when the target is revoked or does not exist, or when there is no value at that moment; a referenced row whose summary is read is recorded in the read record of this read (the same connection and task), but it is not a fallback for `ver` and does not count as `my_last_read`: a summary is not the whole row, and the reader has not seen the other fields of that row or its `ver`. A premise declaration whose target table is not visible gives only `hidden`, `state`, `since` and `fields`, the same as `Marks.premise_changed`; there is no cap, and the ordering and the projection by `fields` are the same as `Marks.premise_changed` (changed ones first, unchanged ones after). It exists only where rows are returned: `query`, and `as_of` of `history`. On derived tables (computed at read time and stored), `detailed` reports `not_in_this_version`: a derived row has no operation number, recorded time or field provenance of its own to give.
- **`warnings[]`**: structured warnings tied to some part of this call; for the code table see types section 7.
- **`notices[]`**: notices relevant to this call, at most 3; for the code table see types section 7. The order of the kinds of notice is `deletion_overdue`, `migration_progress`, `schema_updated`, `pending_items`, and within one kind by that kind's own order; when together they exceed 3, they are cut off in this order. Every kind of notice is computed only over the visible range, and a slot out of range appears in no notice. "Relevant" means the slots this call involves: the slots that `catalog` lists or points to, the slot of the tables `query` / `history` reads, the slot of the tables `write` writes, the slot of the item `resolve` handles, the slot `schema_draft` creates. Notices are computed from the state at this moment, and the computation itself is not recorded in the read record; an error result carries no notices.
- **`replayed`**: true on an idempotent replay.

## 14. Idempotency

- **Write operations are always idempotent on the server** (`write`, `resolve`, `schema_draft`, `delete`).
  - Without an `idempotency_key`: request key = caller + `task` + the normalized request content.
  - With an `idempotency_key`: request key = caller + that key.
  - **The caller** is the connection; when called with a user session, it is this user session.
  - **Normalization**: the request body the caller sent is encoded with JCS (RFC 8785), excluding `task` and `idempotency_key`, and **excluding the `ver` / `sv` / `item_ver` the server filled in as a fallback**. So a request resent unchanged after a read is still the same request key.
  - **How JSON numbers are written in the canonical form depends on the channel** (section 1): on a channel where saveslot parses the request body itself, a number is written as the original text in the request body; on a channel parsed by the host, what arrives is a double, written by the JCS number rules. So the same request body sent over HTTP and over MCP may have different canonical forms (`1.50` and `1.5`) and be two request keys; an unchanged resend on the same channel is not affected.
  - **Exception one: the version of premises**. Normalization **includes the version seen of each premise after resolution** (including those obtained by fallback). "The premise changed again, check once more, with the request body unchanged word for word" is the normal use of a restate; without it, the second restate would be treated within the window as a replay of the first and return an outdated `state: current`. This applies to premises only; the `ver` that the fallback fills in for the write target still does not enter normalization. An explicit idempotency key is not affected by this: it replays by key and request body and does not look at the premise versions, so sending the same key with the request body unchanged word for word, even if the premise changed in between, returns the receipt of the first time; to check again, use a different key.
  - **Exception two: a request that contains only ops by external key does not compute a server-side request key**, whether or not it is within the window, and a resend is compared three ways op by op: the external key itself makes a resend idempotent, and submitting the same content again gets `unchanged`. An explicit `idempotency_key` still works: when the request produced events, it is recorded as usual; when the request produced no event, it is not recorded, and a resend is judged again by external key with the same result. A request that contains ordinary ops still computes a request key (over the original request body, in which the content of the ops by external key is likewise included); a connector can simply send ops by external key and ordinary ops in separate requests.
  - The two exceptions act on different requests: an op by external key cannot carry premises.
- **Windows** (a service layer policy, handed to the kernel through the call context, K13 unchanged): **24 hours for an explicit `idempotency_key`; 10 minutes for a server-computed request key**. A request with the same content outside the window is a new request; recording the same thing twice is caught by external keys (submitting the same external record again is an update or a no-op) and by `duplicate_keys` (whether two rows are a duplicate), not by idempotency.
- The same explicit key paired with different request content: `invalid_argument` (`idempotency_key_reuse`). For this, the explicit key also records a fingerprint of the request content; the fingerprint is content and is deleted with the evidence (architecture K13).
- **Only terminal results that produce events are deduplicated**: `saved`, `pending` (and later `job`). **A rejected write produces no event and is not deduplicated**: on a resend it is validated again against the state at that time (for example, resending unchanged after reading as `read_first` asked executes normally); transient errors such as `rate_limited` and `unavailable` are likewise not recorded.
- **Exactly once is guaranteed by the kernel** (architecture K13): the request key is recorded and checked for duplicates in the same transaction as the write; a resend after a crash does not write twice either. The request key is content and is deleted along with the evidence deletion of that write; a request key already listed as pending deletion before physical erasure still hits, and the result carries `original_deleted` and does not write again (data-model "Cancelling a deletion and the grace period").
- **What a replay returns**: `replayed: true`, with no new write. The receipt is rebuilt from the log: the operation number, the per-field result of each op, the `ver` obtained at that time, the IDs of newly created rows / entities, and the IDs of items generated or merged into at that time. Parts that cannot be rebuilt from the log are omitted and listed in `omitted[]`: `affected_reads`; the before and after values of derived values (`derived_values`; in this case `derived[]` is empty, and `derived_total` is given as the number of derived writes of this operation in the log, which differs from the first receipt's count by field entries); the before values in the per-field results: the log does not record the value before a write, and it cannot be fetched when the contribution it came from has been deleted (`before_values`); the spans of the parts skipped by `undo` (`skipped_spans`); the parts whose content from this write itself has been deleted (`deleted_content`, with `original_deleted` as well in this case); ops by external key that did not enter an event (`unrecorded_ops`: for these indexes only `op_index` is given, and the counts of `unchanged` and `skipped` in `external_key_summary` are not given either); `existing_keys` and `similar_keys` (the value is `existing_keys`; both are computed from the state at the moment of the write and do not enter events). The span of a no-op field and the resolution result (its entry in `resolved`) are given neither in the first receipt nor in a replay: the log keeps only its field name and no span. Warnings (`warnings`) are never given and are not listed in `omitted` either: a warning is a hint attached at the moment of the write and does not enter the log, and a replay restores only what is in the log; `merged` in the per-field results is computed from the version seen in the log and the row's version, and is given as usual. These parts are not recomputed from the current state: that would make the two receipts of the same request differ. `notices` is not among them: it is computed from the state at the moment of the replay, since notices speak of the present and never enter the log. The premise parts (`premises`, `premise_covered`, `premise_affected`) are recorded in the metadata and can be rebuilt completely, with the flag state being that of the time. An item is given only its **current state** (open / resolved with the decision / superseded), without `item_ver`; neither the `ver` nor the items in the receipt count as read, and they do not take part in the fallback.
- When a write with content and evidence identical word for word really happens again within the window, the caller must pass a different `idempotency_key`; otherwise it is handled as a resend.
- While a request with the same request key is still executing, a later arrival waits for the result of the earlier one and is not executed in parallel.
- A resend of `resolve` for an item already resolved with the same decision returns the original result; the write it triggered (`write`) is rebuilt by the write replay rules above, parts that cannot be rebuilt are likewise listed in `write.omitted[]`, and `derived_total` is likewise given as the number of derived writes; a resend of `delete` with the same `dc_` returns the original result.

## 15. Handles and tokens

| Handle | Prefix | Nature | Validity | After it becomes invalid |
|---|---|---|---|---|
| Pending item | `pi_` | A short stable ID, not signed and not bound to content; content binding relies on `item_ver` | Does not expire | A closed one reports `item_closed` |
| Schema draft | `d_` | A stable ID | Same as its `schema_change` item | — |
| Deletion confirmation | `dc_` | Signed, bound to "tenant + restore count + deletion ID (preallocated at preview) + target + hash of the impact summary + the operation number at preview" | 10 minutes | `handle_expired`, preview again; one already executed carries the deletion ID. A changed impact scope reports `preview_outdated` |
| Paging | `cur_` | Signed, bound to the query conditions + the operation number of the first page + the restore count | 1 hour | `handle_expired`, query again |
| Job, extraction lease (later) | `jb_`, `ls_` | A stable ID; signed | 30 days after the job ends; 15 minutes | `not_found`; `lease_expired` |

- Paging is pinned to the operation number of the first page: new writes during paging cause no missing or repeated rows; changing the conditions invalidates it. Later pages give rows and values by the recorded state at the moment of the first page (and the evaluation time of the first page); flags are those at the time of reading (an open item has no history), and how rows are split is not affected by flags. If a restore or an import happened after the first page, later pages report `handle_expired` (`restored`). `changes` of `history` also records in the position the `since` resolved on the first page. A derived table has no state by instant: if this derived table was refreshed after the first page, later pages report `handle_expired` (`derived_changed`), and the read starts again from the first page; if it was not refreshed, what is read is the same as at the moment of the first page. A derived table computed at read time has no derived writes: the position records the operation number of the first page and the evaluation time `at`; if the base tables the rule reads have a new version after the operation number of the first page, later pages report `handle_expired` (`derived_changed`); if not, the table is recomputed at the same `at`, giving the same as at the moment of the first page. The handle is bound to the query conditions, not including `limit`: the number of rows per page can change between pages.
- **After a backup restore or an import**: `ver`, `item_ver`, `dc_` and `cur_` all carry the tenant's restore count. A restore and an import both add 1 to the restore count, and everything issued before no longer matches. The **restore point** is the `restored_to` of the most recent restore (`tenant.restored`), or the `imported_upto` of the import (`tenant.imported`).
  - `ver`: one whose restore count is **exactly 1 less than the current** and whose operation number does not exceed the restore point is judged for conflicts by its own operation number; the others (operation number after the restore point, or an older restore count) take the restore point as the position it read, and are compared by the conflict criterion against the writes after the restore point. `ver` in a premise is the same.
    - Reason: events at and before the restore point are byte-for-byte identical in the two timelines, so judging by the original operation number cannot go wrong and can also find concurrent changes before the restore point; the part after the restore point may have been lost, and can only be handled conservatively. When the restore counts differ by 2 or more, there is no way to tell whether the timeline before the intermediate restore matches the present one, so it is not relaxed.
  - `item_ver` reports `confirmation_mismatch` (`restored`);
  - a handle reports `handle_expired` (`restored`). After an import, handles are also invalidated because the signing key and tenant ID differ, and the same error is reported;
  - `pi_` reports `not_found` when it does not exist in the restored log (data-model "After deletion · The deletion register").
- The confirming user and credential are recorded in the confirmation record, not in the handle; the hash of the impact summary bound by `dc_` is written into the content block of the "deletion confirmed" event and is deleted at expiry along with the deleted content.

## 16. Outer errors

For the fields carried, see types section 9.

| `code` | When |
|---|---|
| `unauthenticated` | The credential is missing (`missing`), invalid (`invalid`), revoked (`revoked`), or expired (`expired`); in server mode, the tenant owner's account is deactivated (`account_disabled`) |
| `insufficient_scope` | The credential lacks the required scope (including a `resolve` decision the current credential cannot use); a connection calls an administrative operation that only a user session may call (`required_scope: "user_session"`); a credential limited to a slot range creates a slot (`required_scope: "all_slots"`, see section 12) |
| `rate_limited` | Rate limiting or quota (`quota`); a replay comparison or an import is already running for the same tenant (`busy`) |
| `handle_expired` | A signed handle has expired (`expired`), the restore count does not match (`restored`), a `dc_` has already been executed and a preview is requested again with it (`executed`), the derived table was refreshed during paging (`derived_changed`) |
| `not_in_this_version` | A parameter, value or operation was called that the first version does not implement or that 0.1.0 does not provide yet. `reason` says which kind, with which one attached; when a change in a schema draft that is allowed only for tables never written is used on a table that has been written to, `reason` is `table_written` |
| `unavailable` | Temporarily cannot be handled: the tenant is occupied or cannot be opened at the moment (writes queued, a lock timeout, its storage not yet released; or, in server mode, a read's read records could not be written before the answer, and the read's content is not given) (`busy`); the tenant is going through a restore (`restoring`); the tenant is being imported (`importing`); a replay comparison entered the comparison phase and timed out in the queue (`reconciling`); the service has just started and is still catching up on due tasks (`starting`); the service is stopping and takes no new requests (`stopping`). When retryable, `retry_after` is attached |
| `internal` | An internal server error. `incident` is attached (a number for troubleshooting, containing no user content) |
| `import_rejected` | The imported file is not acceptable: unrecognized format (`unsupported_format`), not starting from the beginning (`not_from_start`), resumed segments in the wrong order (`segment_order`), a broken event header chain (`chain_broken`), a content checksum mismatch (`checksum_mismatch`), the count or the end does not match, the manifest does not match the content (`incomplete`, for example the restore count in the manifest is not that of the imported log itself), a replay failure (`replay_failed`). Only positions (`seq`, `path`) are given, and no content is echoed |

- **What the first version does not implement and what 0.1.0 does not provide yet are always reported as `not_in_this_version` and never silently ignored**: these parameters and values do not appear in the generated schema, but the server recognizes the names in the full design and gives this explicit error on receiving them, instead of a general `invalid_argument`.
- `item_closed` and `preview_outdated` are in section 11: they are judged by the kernel. Only the expiry of the signature itself is `handle_expired` here.

## 17. Administrative operations

Part of the contract. Except for `policy.get`, they are given only to user sessions (a connection calling one reports `insufficient_scope`, `required_scope: "user_session"`); they do not go into MCP (surfaces). For parameters and results see types section 8.

| Operation | What it does |
|---|---|
| `connections.issue` | Issues a connection: name, scope, slot range (`slots`: an array of slot names or `slot_id`; when not given, all; names are not case sensitive for ASCII, and a slot listed several times is recorded once; each must exist and be visible, otherwise `not_found` (`slot`), and the response is the same whether it is not found by name or by ID; an empty array reports `invalid_argument` (`empty_slots`)). The token in the result is returned only this once, and saveslot stores only its hash |
| `connections.list` / `update` / `revoke` | List (including each connection's slot range; with `include_revoked: true`, revoked and disabled ones are also listed), rename, revoke. `update` can only rename; a revocation takes effect immediately, and revoking again returns the same result: revoking an already revoked or disabled connection records no event and returns its current state (a disabled one is still `disabled`). Issuing, renaming and revoking are all recorded as log events |
| `slots.remove` | Removes an empty slot. **It accepts only `slot_id`, not a name** (`invalid_argument`, `param: "slot_id"`): a name can be reused after a slot is removed, and if a removal by name were resent, it would delete the slot later created with the same name; the CLI first resolves the name to a `slot_id`, shows it on the confirmation screen, and then sends by ID. "Empty" is judged by the log: under this slot's name there is no event other than structure (`schema.*`) and policy (`slot.policy_set`) (the `item.*` of a schema change item does not count either); it is judged and `slot.removed` is recorded in the same write transaction; a slot that is not empty reports `invalid_argument` (`slot_not_empty`); for the criterion and how each event type is classified, see [`../process/decisions/remove-empty-slot.md`](../zh-CN/process/decisions/remove-empty-slot.md) (Chinese), and for it alongside the table-level "never written" see data-model "Schema evolution". While a schema change item is still open, `slot_not_empty` is reported in the same way, with `details` carrying the reason and the item ID. A `slot_id` that does not exist reports `not_found` (`slot`). It does not accept `Idempotency-Key`: removing an already removed slot again returns the result of the first time and records no event. After the removal: the name can be reused, and a slot created with the same name is another slot (another `slot_id`), which no connection's slot range or read record points to; a connection whose range has only removed slots sees nothing (an empty range is not the same as no limit on slots), and its `slots` in `connections.list` is an empty array; read records are kept as before, and when listed, a slot whose name cannot be found is written with the raw `slot_id`; filtering by the name of a removed slot reports `not_found` |
| `policy.get` | The slot policy: the policy version (`policy_version`), the rule for the value in effect during a conflict (`effective_value_rule`), the rank table of source levels (in the first version only recorded, not used), and which schema changes take effect automatically. Any credential with `saveslot.read` may call it; the slot must be within its visible range, otherwise `not_found` (`slot`) |
| `policy.set` (later) | Changes the slot policy |
| `reads.list` | Read audit: which connection read which data at what time (including reads of the original text of source data). It gives only versions, not values; each entry carries `task`; the result states up to which moment the read record is kept (when nothing has been cleaned up, the moment the tenant was created). `since` is inclusive and `until` exclusive; a `slot` that does not exist reports `not_found` (`slot`), and a `table` that does not exist reports `unknown_table` (as elsewhere when a table is pointed to by name: with `name` and `nearest`, listing names with the slot if `slot.table` was given and table names if only the table name was given). When the number of row versions one read saw on one table exceeds the threshold (initial value 1,000, seen mostly in aggregates of restricted SQL), this table is not listed row by row and is listed in `coarse`: only the table and the position of the state this read saw (data-model "Read records") |
| `log.verify` | Verifies the log: the total number of events, whether the event header chain is intact (or from which one it is broken), positions where the content checksum does not match, positions where the index columns do not match the event header (not counted as a break), the number removed by deletion, and the sequence gaps left by a restore (not counted as a break) |
| `log.end` | The end of the log: the `seq` and recorded time of the latest event (null when the log is empty). Read-only and takes no parameters; `saveslot status` uses it to compare against the local clock |
| `log.reconcile` | Not provided in 0.1.0 yet: `log.reconcile` reports `not_in_this_version`; this row is the design ([`07-scope-v1.md`](07-scope-v1.md), section 7). Replay comparison: replays the log from empty storage into a temporary store and compares it table by table with the live logical tables (for the scope see architecture §11). It returns synchronously and takes long when the log is large; only the final comparison phase queues the tenant's writes, and on PostgreSQL it completes within a read snapshot and need not queue writes (architecture §7). Only one runs at a time per tenant, and a second call reports `rate_limited` (`busy`). The result gives only the IDs of tables / rows / fields and does not echo values. **It cannot find results that `delete` itself computed wrongly** (architecture §11, "The record agrees with recomputation") |
| `export` | Exports all log events, NDJSON: the first line is the manifest, and each later line is one event, in the shape defined by section 8 of [`09-event-format.md`](09-event-format.md), and it can be replayed on any backend through `apply`. Content pending deletion in the grace period is replaced by a placeholder by default, and is included only with `include_pending_deletion: true`; `after_seq` resumes from after a position (recorded as `after` in the manifest). Read records are not in the export |
| `import` | Imports into an empty tenant: loads an export into an empty tenant (the log has only the genesis event, and the anchor has no deletion register, no restore record and no restore or import in progress). Events are appended unchanged one by one and handed to `apply` to replay, one `tenant.imported` is appended, and the restore count is increased by 1; the principals registered before the import that are still valid are all disabled (already revoked ones stay revoked, section 12), and credentials are issued again by the user at the target. As a whole it either completes or the target tenant stays empty; during it, other requests for this tenant report `unavailable` (`importing`). Placeholders of content pending deletion in the export are tombstoned immediately at import, and those deletions cannot be canceled at the target. Read records, the contents of the control plane (credentials, authorizations, signing keys, the source's deletion register) and external files cannot be brought over, and the result lists this truthfully. Errors: `invalid_argument` (`tenant_not_empty`), `import_rejected`, `rate_limited` (`busy`), `too_large` (`import_line`: a line of the file exceeds the limit, 09 §8). Merging imports and migration flows are not in the first version |

Deleting a whole slot that has records is not done in the first version (positioning "Later plans"); an empty slot is removed with `slots.remove`.

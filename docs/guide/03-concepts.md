# 03 · Core concepts

English · [简体中文](../zh-CN/guide/03-concepts.md)

The previous chapter's example introduced a number of concepts. This chapter explains them one by one: what each concept is, why it exists, and where it is most easily misunderstood. The examples continue with the same ledger.

The order goes from the outside in: first how data is organized (tenants, slots, tables), then how data is stored (two layers of data, the log, `apply`), and then three cross-cutting mechanisms (provenance, time, pending items).

## 1. Tenants, slots and tables

### Tenants

**A tenant is saveslot's unit of "one independent body of data": one log, one set of sequence numbers, one independent store.** In the first version, one tenant is one user.

Different users' data is separate at the storage level: in local mode it is one data directory, and in server mode each user has an independent database. The kernel only knows how to "open the store of a given tenant"; there is no such thing as "filtering by user ID in one big table".

The word "tenant" is used instead of "user" to leave room for the future: a ledger shared by several people, for example, would be an independent tenant plus member authorizations. The first version does not do this.

### slots

**A slot is a division inside a tenant: a group of related tables, plus the source data of those tables.** For example "bookkeeping", "health", "a particular project".

The name takes the sense of "save slot": a slot holds a complete state that can be picked up and continued, like a save slot, so that any agent that arrives can carry on from where the last one stopped. The project name saveslot comes from this.

A slot is the unit for three things:

- **Schema version.** A slot has one current schema version (`sv`). A change to table structure raises the version per slot. The time zone is also set per slot.
- **The scope of one deletion.** One privacy deletion touches the source data of only one slot. When one sentence speaks about things in two slots, it is stored as two pieces of source data, and each is deleted on its own (chapter 8; privacy deletion is not provided yet in 0.2.0, see [`../spec/07-scope-v1.md`](../spec/07-scope-v1.md) section 7).
- **The smallest unit of a credential's authorization scope.** When a credential is issued it can be limited to certain slots: a connector responsible only for health data gets a credential that sees only `health`, and the other slots are, for it, the same as nonexistent (chapter 11). A scope goes down to the slot level only, not to a single table or field; table-level and field-level data permissions are for later.

Export is not per slot: the first version exports the whole log of the tenant (chapter 11). Exporting only one slot is for later.

Each slot also carries a **policy**: a setting that states which schema changes may take effect automatically without confirmation, which value counts while a conflict is open, and so on. saveslot writes a default one when the slot is created; the first version has no operation to modify it (chapter 9).

Slots do not overlap:

- Each table belongs to exactly one slot.
- Each piece of source data belongs to exactly one slot. When one user sentence involves two slots ("ran 5 km today, spent 600 on running shoes"), the agent splits it into two writes, each with its own evidence fragment. The two writes are independent of each other: when one succeeds and the other fails, the one that succeeded is not rolled back, and the agent has to retry the failed one itself.
- One write involves only one slot.
- The first version does not allow derivation rules or reference fields (fields that point to another row) across slots. When needed, the agent queries the two slots separately and puts the results together, or uses one read-only SQL statement that joins the tables of the two slots (chapter 6).

A slot is a logical division, not a physical one: it is only a partition label inside the tenant's single log, not a separate log and not a separate database.

### Tables

There are two kinds of table:

- **Base tables**: tables the agent writes, such as `expenses`. Each row has a row ID generated by saveslot.
- **Derived tables**: tables generated entirely by rules, such as `monthly_total`. The rules are part of the schema and are executed by saveslot; the agent can only read. When a base table changes, the affected derived rows are recomputed in the same transaction.

A derived table is generated only by rules, and this is a hard constraint. It guarantees that derived data can always be recomputed from base data, so derived data never gets in the way of deletion and does not need a separate history.

Specification: [`../spec/03-data-model/01-objects.md`](../spec/03-data-model/01-objects.md), "The slot and the timeline of a thing" and "Identifiers and objects".

## 2. Two layers of data: source data and table data

The data in saveslot has two layers.

```
table data    ← structured data organized by schema; what agents and products on top query
source data   ← original evidence: user's words, tool results, file references...; append-only, never modified
```

- **Source data** is the original evidence. In the example, `s_1`, "I spent 45 yuan on lunch today", is one piece of source data. It is not the whole conversation, only the part the agent cut out that is relevant to this write.
- **Table data** (the specification calls it "modelled data") is the structured result derived from source data according to the schema: that one row in `expenses`.

There are three relationships between the two layers, and the mechanisms that follow are all built on them:

1. **Every value in table data can be traced to source data.** This is the answer to "on what grounds".
2. **Every write has source data.** When evidence is passed, the evidence is stored as source data; when none is passed (for example a script calling the interface directly), saveslot stores the request itself as source data. There is no "write without a source". (The one exception is a sync request that changed nothing: all the records it brought were unchanged or skipped, and it leaves nothing in the log; chapter 5, section 3.)
3. **A correction is a new piece of source data; it does not edit the old one.** When the user says "No, it is 54 yuan", that sentence itself is recorded, and a correction write is then produced from it. The original sentence and the original value both remain in the history.

A piece of source data has a kind: the user's words, an agent's paraphrase or inference, a tool result, a reference to an external file. The kind determines its default **source level**: the user's words are "user explicit", and the rest are "agent inferred". The source level is there for conflict resolution: in the full design, a candidate with a higher source level can take effect by rule. The first version does not do this: every conflict keeps the current value, and levels take no part in the decision; they are still determined and recorded in the event, for later resolution to use (step 3 of chapter 2).

Specification: [`../spec/03-data-model/01-objects.md`](../spec/03-data-model/01-objects.md), "Data layers" and "What a source is"; [`../spec/03-data-model/04-write-and-read.md`](../spec/03-data-model/04-write-and-read.md), "Invariant: every write has source data".

## 3. The log, `apply` and the three kinds of state

This is the foundation of the whole design.

### The log is the only source of truth

**In a tenant's store, only one append-only event log counts as "fact". All the tables that are queried day to day are computed from the log, and if lost they can be recomputed.**

Each entry in the log is an **event**. Events are numbered in order, and the number is called `seq` (#21 and #22 in the example). Source data, every write, every refresh of a derived table, the creation and resolution of pending items, the confirmation and cancellation of deletions, and every change to the schema are all events in this log. The first event of the log is "tenant genesis", which registers the tenant and its user; after that, creating a slot and issuing a credential each leave events as well. The ledger in the previous chapter starts at #21, and the first 20 events are these, plus the three expenses recorded in October (the overview table is at the end of chapter 2).

**One operation, one operation number.** One request from a caller (one write, one resolution of an item, one deletion confirmation) appends several consecutive events to the log. The first of them is called the **head event**, and its `seq` is the **operation number** of the operation; the head event of a write is the logical write head, so the operation number of a write is also called the **write number**. The four events #21–#24 of step 1 in the previous chapter belong to the same operation, and the operation number is 21.

Wherever saveslot refers to "which operation", it always uses the operation number: the sequence number in a receipt, the version mark `ver`, the numbers in the history. In this guide, "write #25" means the write whose write number is 25, while `#27` alone or "event #27" means the 27th event in the log.

The operation number is used instead of the sequence number of a single event so that one operation is one instant in recorded time. If "the state at that time" were read by the sequence number of a single event, one could read a half-done write, a shape that never really existed.

The operation number is also the "recorded time": at which step saveslot learned of the matter.

### `apply`: from events to tables

**`apply` is the function that lands an event in the tables, and it is the only place that can change a table.** Each time an event is appended, `apply` changes the tables according to it, and the event and the table changes are committed in the same transaction.

`apply` has one key property: **it only executes; it does not judge.**

"Does this write conflict with someone else's", "up to which day does this value hold", "what should this row look like after the deletion": these judgements are all made at the time by the module responsible for the write or the deletion, and **the result is written into the event**. `apply` only changes the tables according to the result written in the event; it does not judge again, and it does not read the current time. What it does by itself is only computation that contains no judgement, such as "land this already-effective field value onto this row".

The reason is that the log must be **replayable**: take the same log, change the database backend, wait a year, upgrade the kernel version, hand it to `apply` from the start, and the same tables must come out. If `apply` judged again during replay, the result could differ from what it was at the time.

### The three kinds of state

The specification requires that everything in a tenant's store must fall into one of three kinds:

| Kind | What it is | If lost | Examples |
|---|---|---|---|
| (a) Fact | The log events themselves | Must not be lost. This is what is exported | Source data, writes, the creation and resolution of items, the confirmation and cancellation of deletions |
| (b) Materialized state | Tables computed from the log through `apply` | Rebuilt from (a) | Business tables, the historical versions of each row, provenance tables, the current state of pending items, flags on data, all kinds of indexes |
| (c) Local operating state | Not computed from the log, and not exported | Every item must state "what happens if it is lost" | Read records, the progress of background tasks |

**This rule guards against a "fourth kind": state that is important but exists only in some table.** Such state cannot be taken away on export and does not come back on rebuild. Two examples:

- If "this field has a conflict" were recorded only in one table, then losing the table and rebuilding from the log would make the conflict disappear.
- If "this one has been deleted" were recorded only in one table, then exporting the log and replaying it would bring the deleted data back to life.

So the creation and resolution of conflicts, and the confirmation and cancellation of deletions, are all log events. #40, #41 and #42 in the previous chapter are examples.

Read records belong to (c): they are large in volume, have their own retention period, and are cleaned up when it expires, so they do not suit a permanent log. The cost is stated: after an export, the read history does not travel with the data.

### What this design buys

- **The data can be taken away.** Export is the log. Replaying it on the embedded database on a local machine and on PostgreSQL on a server gives the same state.
- **It can check itself.** Replay the log from an empty database and compare it row by row with the live tables. This finds defects in the kernel itself, and also finds that someone changed the database directly, bypassing saveslot.
- **History and provenance come built in.** "What was it at some moment" and "on what grounds is this value" need no separate mechanism.
- **Changing table structure is the same action.** Tables of the new version are built by replaying the log into the new structure.

> Three things in this section are not provided yet in 0.2.0: the replay comparison used for self-checking (`saveslot verify --replay`); migrations that rebuild physical tables, the kind that replays the log into a new structure; and the clean-up of read records at expiry (0.2.0 does not clean up read records; they only grow). See [`../spec/07-scope-v1.md`](../spec/07-scope-v1.md) section 7.

Specification: [`../spec/02-architecture.md`](../spec/02-architecture.md) §3 "The log is the only source of truth"; which tables each kind has is in §8 "Storage format v1" of the same file; the fields of each kind of event are in [`../spec/09-event-format.md`](../spec/09-event-format.md), and a first reading does not need to go through all of it.

## 4. Event headers are separate from content

"The log is append-only" and "the user has the right to demand complete deletion" conflict. saveslot's solution is to split each event into two parts (the clearing of whole blocks described in this section comes from privacy deletion, which is not provided yet in 0.2.0; see [`../spec/07-scope-v1.md`](../spec/07-scope-v1.md) section 7):

| | What is in it | Can it be deleted | Is it in the chain |
|---|---|---|---|
| **Event header** | Sequence number, event type, who did it, recorded time, which operation it belongs to, which slot it belongs to, the hash of the previous event header | Never deleted or changed | Yes |
| **Content block** | Everything else, divided into blocks, each with a checksum | Can be cleared block by block | No |

**The event header is deliberately kept small.** It has only the general fields above. Even "which table, which row this write targets, and what the intent is" is not in the event header but in a content block. The reason is that once an event header is in the chain it can never be changed; the less is left in it, the more room there is later for deciding what can still be kept after a deletion.

Event headers are strung into a chain one after another: each event header carries the hash of the previous event header (the algorithm is SHA-256). This chain can detect missing events, reordered events, and event headers changed by accident.

**Content is divided into blocks, and deletion goes block by block.** The content of an event is not one lump but a group of **content blocks**: the original words are one block, the value of each field is one block, and the provenance of each field is one block each. A block that contains user content (or something computed from it) records which source data it comes from; when that source data is privacy-deleted, these blocks are cleared whole, and in the original place a marker "removed by a deletion event" is left, with no content in it. A block that contains only internal IDs and fixed enumerations (for example "which table, which row this write targets, and what the intent is") is not deleted in the first version. How blocks are addressed, and which blocks a real event has, are covered in chapter 4, section 6.

Two details decide that the deletion is clean:

- **The event header holds no value computed from user content.** Not even a hash of the content. Otherwise, after the content is deleted, someone could still compute the hash of a guessed sentence and compare, to verify "did the user ever say this sentence". Each block's checksum is stored together with its content and is cleared with it. The **request key** is the example of this rule that is asked about most often: it is a value saveslot computes from the content of a request to recognize that "the same request has been resent" (chapter 5, section 8); the request contains the user's own words, so it too counts as content, is placed in a block that can be deleted, and is deleted together with the evidence of that request. Whenever later chapters say "the request key is also within the scope of the clearing", the reason is this rule.
- **The event header and the blocks that are not deleted use only internal IDs.** Readable names such as table names and field names are all in blocks that can be deleted.

What is left after a deletion is two layers:

- The event header: it shows that at some moment an event of some type existed, who did it, and which operation it belongs to.
- The blocks that contain no content: they show which row of which table (by internal ID), what the intent was, and which events were referenced.

It cannot show what value was written, what the original words were, or what the tables and fields were named. The item-by-item list is in section 9 of the event format specification, and that is also the material handed to legal counsel for review; if it is later required that not even these be kept, they can be cleared too, without touching the event header.

A boundary to know: **the goal of this integrity mechanism is "traceable and protected against mistakes", not tamper-proofing.** A person who can write to the store directly (the operator included) can change the content and recompute the checksum, and the check still passes. saveslot provides no proof against this.

Specification: [`../spec/03-data-model/02-integrity-and-records.md`](../spec/03-data-model/02-integrity-and-records.md), "Integrity and provenance"; [`../spec/09-event-format.md`](../spec/09-event-format.md), sections 1–3 and section 9.

## 5. Who did it, and on what basis: actor and provenance

These two concepts are easily confused, because both sound like they answer "where did this change come from". They answer different questions.

| | What it answers | What it is | Where it is recorded |
|---|---|---|---|
| **actor** | Who did it | An authenticated principal | The event header of every event |
| **Provenance** | On what basis | One or several pieces of source data | In the content of each write, down to the field |

### actor

The actor is the principal that calls saveslot. There are three common kinds:

- **Connection**: one agent's one connection. For each connection saveslot issues an independent credential, named by the user, for example "MacBook · Claude Code". A and B in the example are two connections.
- **User session**: the user in person, operating through an entry point meant for people, such as the command line.
- **`system`**: events produced by the saveslot kernel itself (for example carrying out a physical erasure when it falls due) are recorded under this reserved principal name.

The actor is derived from the credential; the caller cannot fill it in.

### Provenance

Provenance says which piece of source data the value of this write comes from, or which piece of source data triggered this write. It is recorded at the level of the **field**, and comes in two kinds.

- **Value source**: the field's value comes from it. In step 1 of the example, the value sources of the date, category and amount are all `s_1`.
- **Operation source**: it triggered this write but provided no value.

The typical case of an operation source is revoking. The user says "revoke that lunch entry", and the agent calls `write` with the intent `revoke`, passing the row ID and this sentence as evidence. This write has no field values; it only marks the row as revoked. This sentence is recorded as the operation source: it explains on what grounds this revoke happened, but no value comes from it. Similar cases are reverting to an old version, and the evidence passed when resolving a pending item.

### Four easily misunderstood points

**First, an operation source is not an "operator".** The operator is the actor. An operation source, like a value source, refers to one piece of source data (a sentence, a request); it is only that its role in this write is "triggering" rather than "providing a value".

**Second, the kind of source is not a property of the original words themselves; it is recorded per "which write, which field".** The same sentence can be both. The user says "revoke that lunch entry, and dinner cost 80 yuan":

- For the write that revokes lunch, this sentence is an operation source;
- For the row that adds dinner, this sentence is the value source of the amount.

**Third, "which fields this sentence proves" is declared by the agent, and saveslot records it as declared.** saveslot does not understand semantics. The rules are:

- For a field whose **value was changed** in a write, the evidence visible to that write is the value source. The agent can use `evidence_by_field` to point different fields at different evidence segments. "Changed or not" is compared against the version the agent read, not against the current value.
- A field whose **value did not change** is one of two cases. When the agent explicitly pointed it at evidence with `evidence_by_field`, it is called **corroboration**: it counts as a contribution of this write and appends a source to that field, without producing a new version. When it is not pointed at anything, it is called a **no-op**: fields passed back unchanged in a whole-row resend are of this kind, and no source is recorded.

The reason for the second rule was explained in the previous chapter: an unchanged value in the agent's hands is often only something read back from saveslot, whose origin is an earlier sentence; it cannot be counted as a contribution of new evidence just because it appears in a new request.

**Fourth, a source is not a premise.** A source answers "which sentence does this value come from". There is another relationship that sounds similar: the agent wrote this row only after looking at the value of another row in saveslot. For example, it reads "release date December 1" and arranges three tasks accordingly: the values of the tasks come from the user's sentence "arrange the tasks by the release date", and that is the source; the tasks were decided after looking at the release date row, and that is called a **premise**.

| | What it answers | What it points to | When that thing later changes |
|---|---|---|---|
| Source | Which sentence the value comes from | One piece of source data | The original text does not change, it can only be privacy-deleted; deletion follows the sources to find the affected values |
| Premise | Which values the value was decided from | The value of another row in saveslot at some version | The rows that depend on it get a "premise has changed" flag; the value does not move, and whether it still holds is for the agent to judge |

A premise exists only when the agent declares it explicitly at write time; saveslot does not infer it for the agent (chapter 5, section 6). Privacy deletion propagates only along sources, not along premises: delete the sentence about the release date, and the three tasks are not deleted with it; they only get a flag.

### Why there are two kinds of source

So that deletion is computed correctly (privacy deletion is not provided yet in 0.2.0; this describes the design, see [`../spec/07-scope-v1.md`](../spec/07-scope-v1.md) section 7). Privacy deletion propagates only along **value sources**: when a sentence is deleted, the values it provided must be handled; but writes that it only "triggered" are not affected.

Take revoking: the user says "revoke that lunch entry", and later asks to delete this sentence. Deletion follows value sources to find the affected values, finds no value provided by this sentence, so the row's state does not change and it remains revoked. What is deleted is only the sentence itself. Without the two kinds of source, deleting this sentence would make that row "come back to life", which amounts to undoing, on the user's behalf, a decision the user had made.

### Summary: traceability lives on the fields

The previous sections add up to one sentence: **saveslot's "traceability" does not live on the row but on the field.** Look at it in three layers:

- **Provenance and history are recorded per field.** Each field of a row has its own provenance and its own change history. The date of the lunch row comes from `s_1` and the amount from `s_2`, and the two are unrelated.
- **Conflicts are judged per field (or per group of fields declared to be judged together).** A changing the note and B changing the amount is not a conflict; only two people changing the same field is (chapter 5).
- **Undo is initiated per operation and executed per field; privacy deletion also lands on fields.** Undoing a write reverts the part of the fields it changed that is still in effect, and fields that others changed later are left alone. Deleting a sentence affects the fields whose values it provided, and fields in the same row that come from other sentences stay (chapter 8).

So there is no single answer to "how did this row come to be" in saveslot; what is asked is "how did this field of this row come to be".

### A boundary: how accurate provenance is depends on how accurately the agent declares it

What saveslot guarantees is this: the evidence the agent brings is recorded completely, and the provenance chains inside saveslot (for example which base data a piece of derived data comes from) are complete. It cannot guarantee that the agent did not use other information when writing, and it cannot detect an agent pointing a field at a sentence that in fact does not mention it.

The consequences of the two kinds of improper declaration are asymmetric:

- The agent **under-declares** (did not corroborate what should have been corroborated): deletion leans toward deleting more. The row deleted whole in case 2 of the previous chapter is an example.
- The agent **declares wrongly**: the recorded provenance does not reflect the facts. This falls under "the truthfulness of the data is the responsibility of the calling agent".

saveslot's own side has only one mechanical check, called the **literal match**: whether the written value literally appears in the original text of the evidence. It rejects no write, and in the first version it only records the result (chapter 5, section 5).

Specification: [`../spec/03-data-model/03-deletion.md`](../spec/03-data-model/03-deletion.md), "Provenance: value source and operation source"; [`../spec/03-data-model/02-integrity-and-records.md`](../spec/03-data-model/02-integrity-and-records.md), "Connection identity (done in the first version)" and "Integrity of provenance"; [`../spec/03-data-model/04-write-and-read.md`](../spec/03-data-model/04-write-and-read.md), "Source level: declared level and literal match".

## 6. Version marks and read records

These two things let saveslot detect concurrent modification and find the affected parties after a correction.

**The version mark `ver`.** Each row has a token for its current version, returned on read and passed back unchanged on modification. It is written like `v21.0`: the first number is the operation number of the operation that last changed this row, and the second number is the number of times the tenant has been restored from a backup (importing data into a new tenant also counts as one). From this saveslot knows "which version your modification was based on", and this version is called the **version seen** of the write. When it does not match, saveslot does not simply refuse but compares per field: if the field you want to change has not been touched by anyone else since, the change is merged and takes effect; only if it has been touched does it count as a conflict (step 3 of the previous chapter).

`ver` is renewed when a field of this row changes: its value changes, or the value stays the same but is now given by another operation (for example, revoking again within an interval already revoked). A derived refresh, a migration or corroboration with the same value does not renew it. The complete list is in chapter 5, section 3.

**The external key: for writers who have not read the row.** `ver` assumes that the writer has read the row it wants to change. A program that syncs data from an external system on a schedule (the connector mentioned in chapter 1) has not; all it has is the identifier of each record in the source system. So event tables and timeless tables can declare an **external key** in the schema: when writing by external key, an existing row is updated and a missing one is added, with no `ver`; when judging conflicts, saveslot uses "the values brought by the last sync" in place of the version seen. Chapter 5, section 3 covers this in detail.

The slot's schema version `sv` is used the same way: obtained when reading, passed back when writing.

**The read record (read_log).** saveslot automatically records each read: which connection, when, and which version of which rows it read. It records only version numbers, not the values read, so it does not become a second copy of the data, and deleted content does not linger in it.

It has three uses:

- **Correction impact.** After a value is corrected, find out which tasks read the old value.
- **Restoring by moment.** Which version a given task saw at that time.
- **Fallback.** When the agent forgot to pass `ver` in a write, saveslot substitutes the version this connection most recently read, and says so in the receipt.

Read records have a retention period and are cleaned up when it expires. So a correction impact query can cover only the reads within the retention period, and the result states up to which day it covers. Chapter 6 covers this in detail. (The clean-up at expiry is not provided yet in 0.2.0: 0.2.0 does not clean up read records; they only grow. See [`../spec/07-scope-v1.md`](../spec/07-scope-v1.md) section 7.)

Specification: [`../spec/03-data-model/02-integrity-and-records.md`](../spec/03-data-model/02-integrity-and-records.md), "The read record: `read_log`" and "Querying the reads a correction affects".

## 7. Time: two timelines, three kinds of table

Only the basic concepts are established here; the details are left to chapter 7.

### Two timelines

- **Recorded time**: when saveslot recorded the matter. Expressed externally by the operation number.
- **Valid time**: when the matter happened or took effect in reality.

Most of the time the two are the same instant. They come apart when the user says something after the fact: on November 12 the user tells the agent "actually, since November 2 the dining budget has been cut to 3000". The recorded time is 11-12, and the valid time is 11-02.

The two timelines correspond to two different kinds of question:

- "What was the budget on November 5?" asks about valid time.
- "When that task ran last week, what did saveslot believe the budget was on November 5?" asks about both timelines.

### Three kinds of table

The schema declares a time type for each table.

| Type | What a row is | Examples | How valid time shows |
|---|---|---|---|
| Timeless | A fact with no time meaning | Preferences, a project's basic information | None |
| Event | Something that happened | One expense, one run | The time of occurrence is an ordinary field in the table |
| State | The value of something over a period of time | Monthly budget, a goal, a project's status | Each value carries a valid interval |

`expenses` in the example is an event table: `date` is an ordinary field.

The difference of a state table is that the unit the agent reads and writes is not the "row" but the **entity** (a tracked thing such as "the dining budget") plus a **valid interval**. "The dining budget is 5000 from October 1 and 4000 from November 10" is two segments of the same entity. How intervals are cut and stored is managed by saveslot.

When writing a state table there is a default rule worth knowing first: **when no end point is given, the new value holds only until the next recorded change.** If "4000 from November 10" is already recorded and you now write "3000 from November 2", the result is 3000 from 11-02 to 11-09, and 4000 from 11-10 on, as before. The reason for this default is that a wrong guess then has the consequence of "changed too little", which the receipt will point out; whereas if the default were to continue indefinitely, a wrong guess would quietly overwrite a fact that is already recorded. A write that would erase a recorded change is a **high-impact write**; by default it does not take effect directly and must be confirmed first (the "awaiting confirmation" item in the next section).

Specification: [`../spec/03-data-model/05-time.md`](../spec/03-data-model/05-time.md).

## 8. Pending items

Some matters saveslot cannot decide by itself, and a person or an agent has to judge. saveslot unifies these matters into one kind of object, called a **pending item**.

| Type | When it is produced | Has the data taken effect | How it can be handled |
|---|---|---|---|
| Conflict | A write brought back a version that is not the current one, and the fields it wants to change were changed by someone else since | A definite value in effect is given by rule | Keep the current value / take the candidate / revert to before the conflict |
| Awaiting confirmation | A high-impact write | No, it waits for confirmation | Confirm / reject |
| Flagged | A suspected duplicate record | Yes, it is only marked out | Keep / revoke |
| Schema change | A table structure change that cannot take effect automatically | No, it waits for confirmation | Confirm / reject |
| Deletion grace period (not provided yet in 0.2.0) | A confirmed deletion, within 24 hours | Can no longer be read, not yet physically erased | Cancel the deletion |

(There is one more kind of item, related to table structure migration, left for chapter 9.)

They share four properties.

**Persistent.** An item belongs to a slot and is stored in saveslot; its creation, merging, refreshing, superseding and resolution are all log events. It does not depend on push notifications, and does not depend on some session still being open.

**Non-blocking.** While an item is unhandled, reads and writes go on as usual. When related data is read, the result carries a flag ("disputed", "a proposal not yet in effect", "flagged"), and the flag states which item it is and which fields it concerns; the reading party decides for itself what to do. A party that only reads the date is not asked to stop because of a dispute over the amount.

**It does not expire and is not quietly closed.** saveslot has no judgement, and any length of time after which something is "handled automatically" is a guess, so it does not rule on behalf of people. Items do not pile up, because of this:

- Conflict items are counted per **conflict unit**: a conflict unit is a field, or a group of fields the schema declares are judged together. On the same conflict unit of the same row there is at most one open conflict item, and later conflicts are merged into it; on a state table the intervals count too: a candidate is merged only when its interval intersects the existing item's, and one that does not intersect becomes an item of its own.
- When a later write changes a field the item concerns, there are two cases. If the writer **has seen the details of the item**, the item is marked "superseded", because the writer made a new decision after seeing the candidate. If the writer **has not seen it**, the item is only **refreshed** (the current value is replaced with the new value) and stays open.

The reason for the second rule: the party reading data sees only the value in effect and a flag, and has not seen what the candidate is. Suppose the value in effect is 9.5 inferred by an agent, and the candidate is 10 said by the user in person, and an unattended agent writes 9.6 as an external tool sync; if the item were closed just like that, the 10 the user said would no longer appear in any pending item. A candidate can be closed only by a party that has seen it.

**A confirmation is bound to its content.** When handling an item, the caller passes back the item version (`item_ver`) it read. If the content of the item changed in the meantime, the version does not match, and saveslot refuses and returns the current content. This guarantees that "what is confirmed is what is executed": it cannot happen that the user agrees to one piece of content and another is actually executed. The deletion confirmation handle `dc_` follows the same idea.

Who handles it? A person (in the first version through the command line) or an agent (through MCP) can. saveslot cannot tell whether a confirmation actually came from a person or an agent; whether the user's consent was really obtained is the responsibility of the calling agent. What saveslot is responsible for is recording who made each confirmation and what content was confirmed.

Specification: [`../spec/03-data-model/01-objects.md`](../spec/03-data-model/01-objects.md), "Pending items: one unified object"; [`../spec/04-contract.md`](../spec/04-contract.md), section 6.

## Summary

This chapter compressed into a few sentences:

- One tenant has one append-only log, and the log is the only fact; tables are computed from the log by `apply` and can be discarded and rebuilt.
- Everything in storage is either an event, or can be computed from events, or states what happens if it is lost.
- One operation is several consecutive events in the log, and has only one operation number externally.
- Events divide into an event header and content blocks: the event header has only a few general fields, is strung into a chain and is never deleted or changed; content is stored in blocks that can be cleared block by block.
- Every write has source data; every field records its provenance; provenance is of two kinds, "provided the value" and "only triggered", declared by the agent.
- The actor answers "who did it" and provenance answers "on what basis"; a premise answers "which values were looked at before writing this", and the agent must declare it explicitly.
- Two timelines: when saveslot recorded it, and when it happened in reality.
- What saveslot cannot decide becomes a pending item: persistent, non-blocking, non-expiring, not closed by a write that has not seen it, and a confirmation is bound to its content.

The following chapters build on this foundation: how the kernel is layered (04), writes and conflicts (05), reads and impact queries (06), time (07), deletion (08), and how table structure evolves (09).
